Neither side has a strict majority (3 out of 5), but both sides believe they are the leader. Under Raft's safety properties, neither side can commit new log entries because both lack a majority. However, if the network partition is asymmetric (N1 and N2 can still reach N3 but N3 cannot reach N4), the behavior becomes unpredictable.
====
Neither side has a strict majority (3 out of 5), so under Raft neither side can actually win an election: a candidate needs votes from 3 nodes, and each side can supply only 2. The cluster stays leaderless until the partition heals, and lock requests fail rather than being granted twice. The genuinely dangerous case is a stale leader. If the old leader ends up in a minority partition, it may keep believing it is the leader for a short time, but it cannot commit new entries, and a new leader with a higher term is elected on the majority side. The risk to the lock service comes from clients that keep acting on a lock granted by that old leader, which is why fencing tokens matter.

The write latency increases with cluster size because the leader must wait for a majority (ceil(N/2) nodes) to acknowledge each write. The throughput decreases because each write requires replication to more nodes.

For most production systems, a 3-node cluster is optimal. It tolerates one node failure, which covers the common failure scenarios (single machine crash, single availability zone outage). A 5-node cluster is appropriate for cross-region deployments where the cluster must tolerate one full region failure.
====
The figures above are illustrative rather than benchmarks. In general, write latency creeps up with cluster size because the leader must wait for a majority (floor(N/2) + 1 nodes, itself included) to acknowledge each write, and throughput falls a little because each write is replicated to more nodes. Reads are cheap only if they may be served by any node; linearizable reads still involve the leader.

For most production systems, a 3-node cluster is a good default. It tolerates one node failure, which covers the common failure scenarios (single machine crash, single availability zone loss during maintenance). A 5-node cluster is appropriate when the cluster must survive two simultaneous failures, for example during a rolling upgrade, or a whole failure domain when nodes are spread as 2-2-1 across three zones or regions.
