A vertically scaled single-node system is a CA system in CAP theorem terms: it provides Consistency and Availability because there is no network partition within a single machine. There is no P (Partition Tolerance) trade-off because there is no distribution.
====
A vertically scaled single-node system is usually described as "CA" in CAP theorem terms: with one machine there is no network between replicas, so no partition can split the data and you never have to choose between consistency and availability. Strictly speaking, CAP only constrains distributed systems, so the label is a teaching shorthand. It still captures the point: you get strong consistency for free, and the price is that one machine failing takes the whole system down.

**What happens**: On a multi-socket server, threads pinned to one socket access memory allocated on another socket. Cross-socket memory access is 50-100% slower than local access. When cross-socket traffic exceeds 30% of total memory access, throughput drops significantly.

**Why it happens**: Default NUMA balancing in Linux automatically migrates memory pages between sockets. This is designed to balance memory usage but adds migration overhead. Without explicit NUMA pinning, the database process may have threads running on socket 0 accessing memory on socket 1.

**What happens**: On a multi-socket server, threads running on one socket access memory allocated on another socket. Cross-socket memory access is 50-100% slower than local access. When cross-socket traffic exceeds 30% of total memory access, throughput drops significantly.

**Why it happens**: Linux's automatic NUMA balancing tries to move pages toward the threads that use them, but the scanning and page migration add overhead, and a database with one large shared buffer pool touched by every backend gives it nothing stable to optimize. Without explicit NUMA pinning or interleaving, the database process may have threads running on socket 0 accessing memory on socket 1.

**What happens**: EBS volumes have burst credits for IOPS. When credits are exhausted, IOPS throttle to the baseline rate. For gp3 volumes, the baseline is 3,000 IOPS regardless of volume size. A database that exceeds this for sustained periods will see I/O latency spike.

**Why it happens**: Instance types have EBS bandwidth limits. A `r7g.4xlarge` can drive up to 20 Gbps to EBS. The gp3 volume may support only 1,000 MB/s throughput. If the database writes WAL at 500 MB/s (checkpoint burst), the volume saturates and I/O queue depth increases.
====
**What happens**: An EBS volume delivers only the IOPS and throughput it was provisioned for. A gp3 volume includes 3,000 IOPS and 125 MB/s regardless of size, and you pay to raise either. (The older gp2 type instead used burst credits, and throttled to a size-based baseline once they ran out.) A database that pushes past the provisioned limits for sustained periods sees I/O latency spike.

**Why it happens**: Both the instance and the volume have limits, and the lower one wins. A `r7g.4xlarge` can drive up to 10 Gbps (about 1.25 GB/s) to EBS. A gp3 volume tops out at 1,000 MB/s or less depending on what you provisioned. If the database writes at 500 MB/s during a checkpoint burst and the volume is provisioned for 125 MB/s, the volume saturates and the I/O queue depth increases.

### Failure 5: Storage Volume Pinning

**What happens**: When upgrading instance types, the root EBS volume may be unpinned from the old instance type's optimized path. IOPS and throughput drop because the new instance type uses a different EBS optimization configuration.

**Why it happens**: Instance types have different EBS-optimized bandwidth. A `c5.xlarge` supports up to 2.5 Gbps EBS bandwidth. A `c5.4xlarge` supports up to 4.75 Gbps. If an EBS volume was attached to the `c5.xlarge` and then the instance is stopped and started as `c5.4xlarge`, the volume inherits the new instance's EBS configuration, but if the volume was attached during the stop, it may not be recognized as EBS-optimized by the new instance until explicitly re-attached.

**Blast radius**: I/O throughput drops to non-optimized levels (approximately 50% of expected). Database performance degrades until the volume is detached and re-attached.

**Recovery**: Detach and re-attach the EBS volume after the instance type change, or use the AWS Console's "Modify Instance" action which handles EBS optimization correctly.
====
### Failure 5: Instance-Level EBS Burst Exhaustion

**What happens**: After an upgrade the database is fast for a while, then I/O throughput suddenly drops, often 30 minutes or more into a heavy job such as a backup, a reindex, or a bulk load.

**Why it happens**: Many smaller and mid-sized instance types advertise EBS bandwidth as "up to" a number. That number is a burst rate, available for a limited window each day. The baseline bandwidth, which is what you get for sustained load, can be several times lower. A `c5.xlarge`, for example, advertises up to 4.75 Gbps but sustains far less. Moving to a bigger size raises both numbers, but the burst-versus-baseline gap is still there.

**Blast radius**: I/O throughput falls to the baseline (often a fraction of the burst figure) once the burst window is spent. Database performance degrades until the heavy job ends, and it looks like a storage problem even though the volume is fine.

**Recovery**: Check the instance's baseline EBS bandwidth in the EC2 documentation before choosing a size, not just the "up to" figure. Pick a size whose baseline covers your sustained I/O, and watch the CloudWatch `EBSIOBalance%` and `EBSByteBalance%` metrics, which show how much burst is left.

Running a commercial database (Oracle, SQL Server Enterprise) on a large instance without accounting for per-core licensing. Oracle Database Enterprise Edition lists at $47,500 per processor license, and on x86 a 64-core server needs 32 of them (a core factor of 0.5), so the list price is about $1,520,000 before annual support. SQL Server Enterprise lists at roughly $15,000 per two-core pack, so 64 cores is about $480,000. Either way, the license dwarfs the instance cost, and doubling the core count doubles the license bill.

**When zero-downtime upgrades are mandatory.** Every vertical scaling instance upgrade requires a stop-start or blue-green switch. For four-nines (99.99%) uptime targets, this window is too large. Horizontal deployments allow rolling upgrades without downtime.
====
**When zero-downtime upgrades are mandatory.** Every vertical scaling instance upgrade requires a stop-start or blue-green switch. A four-nines (99.99%) target allows only about 52 minutes of downtime a year, so even 30-60 seconds per upgrade, plus kernel patches and failovers, eats a real share of that budget. Horizontal deployments allow rolling upgrades without downtime.
