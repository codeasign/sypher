**How it works**: Cassandra's `COUNTER` column uses a PN-CRDT internally. Each coordinator writes to a local commit log and asynchronously propagates to replicas. Read queries contact all replicas and merge their values.

**Strengths**: Native CRDT counter with automatic convergence; tunable consistency (ONE, QUORUM, ALL for both reads and writes); survives node failures without data loss (within the async replication window); no single point of contention per counter.

**Weaknesses**: Read latency is higher (must contact all replicas); counter reads with QUORUM can timeout if a replica is slow; decommissioning a node requires migrating counter state carefully; write throughput per counter is lower than a single Redis INCR.

**How it works**: Cassandra's `COUNTER` column type stores per-replica contributions and merges them to produce the total. A counter update is applied on a replica (which reads the current value before writing) and then replicated to the others.

**Strengths**: Built-in counter type with tunable consistency (ONE, QUORUM, ALL for both reads and writes); replicated across nodes and datacenters; no single point of contention per counter.

**Weaknesses**: Counter updates are not idempotent: if a write times out, you cannot know whether it was applied, so a retry can double-count and skipping the retry can lose the increment. Counter writes are slower than ordinary writes because of the read-before-write. Counter tables have restrictions (for example, they cannot be mixed with regular columns and do not support TTL). Write throughput per counter is lower than a single Redis INCR.

### Google Cloud Firestore (Datastore Mode)

**Feature**: Firestore `sum` aggregate query provides a server-side counter. Use `set` with `merge: true` to update only the counter field.

**Strengths**: Managed; strong consistency (reads always see the latest write within a regional instance); integrates with Cloud Functions for event-driven processing.

**Weaknesses**: Write throughput is limited to 1,000 operations per second per document. Exceeds this, and writes are rejected. Firestore is not designed for high-frequency counter increments.
====
### Google Cloud Firestore

**Feature**: Firestore's `FieldValue.increment()` applies an atomic server-side increment to a numeric field, so concurrent clients do not overwrite each other.

**Strengths**: Managed; strong consistency; integrates with Cloud Functions for event-driven processing. Google documents a "distributed counter" pattern that spreads a counter over many shard documents and sums them on read.

**Weaknesses**: Firestore recommends sustaining only about one write per second to any single document (short bursts are tolerated), so a single document is a poor fit for a counter that receives frequent increments. That is exactly why the sharded-counter pattern exists.

### Azure Redis Cache

**Feature**: Azure Redis Cache provides managed Redis with `INCR` semantics identical to open-source Redis.

**Cost/ops trade-off**: P1 tier (6 GB, 1,000 connections) at $420/month handles approximately 50,000 ops/sec. For 100,000 ops/sec, you need two instances at $840/month. Adding clustering (C1 tier) for automatic sharding: approximately $1,500/month for 4 shards.

**Strengths**: Fully compatible with open-source Redis commands; geo-replication across regions; active geo-replication with conflict resolution (using last-writer-wins, accepts clock skew risk).
====
### Azure Cache for Redis

**Feature**: Azure's managed Redis offerings provide `INCR` semantics like open-source Redis. (Microsoft is transitioning customers to Azure Managed Redis, so check which offering applies.)

**Cost/ops trade-off**: Throughput depends on the tier and size. To go beyond one node's throughput, use a clustered tier so that counters are sharded across nodes, and size the number of shards for your peak increments per second. Look up current pricing for the tier you choose.

**Strengths**: Compatible with open-source Redis commands; geo-replication across regions. The enterprise-grade tiers offer active geo-replication built on CRDTs, in which counters merge their increments from different regions instead of overwriting each other.
