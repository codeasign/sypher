Even-node clusters require witness nodes to achieve a majority. A 2-node cluster with a witness becomes a 3-vote system requiring 2 votes for decisions.
====
A 2-node cluster cannot tolerate any failure on its own, and an even-sized cluster can split into two equal halves that both lack a majority. A witness (a vote without data) fixes this. A 2-node cluster with a witness becomes a 3-vote system requiring 2 votes for decisions.

- Leader holds a lease in etcd with fencing token
- Replicas monitor leader via etcd and PostgreSQL streaming replication
- On leader failure, replicas attempt to acquire lock in etcd
- First replica to acquire lock becomes new leader
- Old leader's connection is rejected by etcd (stale token)
- Patroni uses the "no overdue leader" safety check
====
- The leader holds a leader key in the DCS with a time-to-live and must keep renewing it
- Replicas watch the key and PostgreSQL replication state
- If the leader cannot renew the key (for example it cannot reach the DCS), Patroni demotes PostgreSQL on that node, so an isolated leader stops accepting writes
- On leader failure or key expiry, replicas race to create the key, and the winner is promoted
- An optional watchdog (for example the Linux softdog) reboots a node whose Patroni process hangs, which acts as a last-resort fence
- Synchronous mode can limit promotion to a replica known to have all acknowledged writes

The pod anti-affinity ensures each replica runs in a different availability zone. The liveness probe checks quorum health: a pod that loses quorum is restarted. The readiness probe checks leader status: a pod that is not the leader is removed from service.
====
The pod anti-affinity ensures each replica runs in a different availability zone. Be careful with the probes in this example. A liveness probe that checks quorum would restart every pod on the minority side of a partition (and every pod when the DCS blips), turning a partition into a crash loop, so liveness should normally check only that the process is healthy. The readiness probe checks leader status, which removes a pod that is not the leader from the primary service.

When a node is fenced, the Kubernetes control plane can update the network policy to block traffic to and from the fenced pod. This provides network-level fencing without IPMI access.
====
When a node is fenced, the Kubernetes control plane can update the network policy to block traffic to and from the fenced pod. This provides network-level fencing of clients without IPMI access, but it depends on the network plugin enforcing the policy on the isolated node, so it complements storage-level or token-based fencing rather than replacing it.

Kubernetes operators can manage the full split brain lifecycle by watching cluster state and taking action. Note that StatefulSets already give an "at most one" guarantee for each pod identity: if a node becomes unreachable, Kubernetes will not start a replacement for that pod until it is sure the old one is gone (the pod stays Terminating or Unknown until the node is confirmed dead, deleted, or fenced). That deliberate caution is itself a split-brain protection.

Kafka's controller can become split if the ZooKeeper ensemble that manages cluster metadata splits. Each side might assign different partition leaders.
====
A Kafka cluster has one controller at a time, chosen through ZooKeeper (or through KRaft in newer versions). A controller that loses its ZooKeeper session can briefly still believe it is the controller (a "zombie controller"). Kafka fences it with a controller epoch that brokers check.
>>>>
<<<<
Kafka Controller Split:
- ZooKeeper ensemble has 3 nodes
- Partition isolates controller from 2 ZooKeeper nodes
- Controller cannot write to ZooKeeper (no quorum)
- Remaining ZooKeeper nodes elect new controller
- Two controllers exist: split brain

Impact:
- Both controllers attempt partition leadership assignments
- Some partitions have multiple leaders
- Producers write to both leaders
- Consumers read from one leader, missing writes from the other
- Data is duplicated or lost

Mitigation:
- Use 5-node ZooKeeper ensemble (survives 2 failures)
- Set unclean.leader.election.enable=false
- Configure min.insync.replicas=2 for critical topics
- Use Kafka's built-in fencing via epoch numbers
====
Kafka Zombie Controller:
- ZooKeeper ensemble has 3 nodes and is healthy
- The current controller broker is partitioned away from it
- Its ZooKeeper session times out and the /controller znode disappears
- Another broker becomes controller with a higher controller epoch
- The old controller may still send requests until it notices the loss

Impact if unfenced:
- Both controllers could try to assign partition leaders
- Brokers could act on conflicting leader assignments

Mitigation:
- Brokers reject requests carrying a lower controller epoch
- Partition leader epochs fence stale partition leaders
- Set unclean.leader.election.enable=false
- Use acks=all with min.insync.replicas=2 for critical topics
- KRaft mode replaces the ZooKeeper dependency with Raft consensus

RabbitMQ's queue mirroring across nodes requires careful split brain handling.
====
RabbitMQ's classic mirrored queues had well-known split-brain problems when the cluster was partitioned. Mirroring was deprecated and removed in RabbitMQ 4.0, and quorum queues (Raft-based) are the recommended replacement. Classic clusters also offer partition handling modes (`pause_minority`, `autoheal`, `ignore`), and `pause_minority` follows the same quorum principle as the rest of this lesson.
