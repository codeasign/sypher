Consul's SWIM implementation uses a suspicion mechanism with exponential backoff. When multiple independent nodes confirm a suspicion, the timeout is extended proportionally. This prevents cascading failures where a brief network hiccup causes multiple nodes to be prematurely declared dead.
====
Consul's memberlist includes the Lifeguard extensions to SWIM. When a node first suspects a peer, the suspicion timeout starts long, and it shrinks as more independent nodes confirm the suspicion. A genuinely dead node is therefore declared dead quickly once several nodes agree, while a slow but alive node gets time to refute the suspicion. Lifeguard also lets a node that notices it is itself slow (missed acks, CPU starvation) back off its own probing, which avoids a struggling node falsely accusing healthy peers.

**Rolling update with state transfer:**
In systems like Cassandra where gossip carries application state (token ownership), a rolling update must account for state transfer. Steps:
1. Mark the node as "leaving" in gossip.
2. Wait for the cluster to rebalance token ownership (minutes to hours depending on data size).
3. Restart the node with the new version.
4. The node rejoins and reacquires its token range through gossip.
====
**Rolling update in a system with persistent state:**
In systems like Cassandra, where gossip carries application state such as token ownership, a node keeps its data and tokens across a restart, so a rolling update does not move data. Steps:
1. Drain the node (in Cassandra, `nodetool drain` flushes memtables and stops accepting writes), so that it goes down cleanly and gossips that it is shutting down.
2. Stop the node and upgrade its software.
3. Restart the node. It keeps its host ID and tokens, gossips with a new generation number, and the other nodes mark it up again.
4. Other nodes replay hints they stored while it was down. Verify the node is up and healthy (for example with `nodetool status`) before moving to the next one.

Data movement (streaming) only happens when nodes are added, removed, or replaced, which is a different and much longer operation than a rolling restart.

For gossip-based systems that support it:
1. Deploy a new cluster (green) alongside the old cluster (blue).
2. Both clusters have independent gossip rings.
3. In the green cluster, configure seed nodes from the blue cluster as bridges.
4. Gradually migrate traffic from blue to green.
5. Once migration is complete, decommission the blue cluster.
====
For stateless gossip-based services (where nodes do not own data), a blue-green approach works directly:
1. Deploy a new cluster (green) alongside the old cluster (blue).
2. Both clusters have independent gossip rings, with their own seed nodes.
3. Gradually migrate traffic from blue to green.
4. Once migration is complete, decommission the blue cluster.

For data-owning systems such as Cassandra, do not join the two rings by pointing green at blue's seeds unless you intend to merge the clusters. The usual approach is to add the new nodes to the same ring (or as a new data center with replication configured) so that data streams to them, and then decommission the old nodes one at a time.
