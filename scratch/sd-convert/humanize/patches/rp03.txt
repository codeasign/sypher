The primary handles 50,000 writes per second. Each write must be streamed to six replicas. The primary's network outbound is saturated at 9 Gbps. Replicas three and four are in a different AWS Availability Zone with 2 ms of additional latency, and they lag 8 seconds behind during peak.
====
The primary handles 50,000 writes per second. Each write generates about 5 KB of WAL (row data, index changes, and full-page images), so the primary produces roughly 250 MB/s of WAL. Streaming that to six replicas needs about 1.5 GB/s, more than a 10 Gbps network card can carry. Replicas three and four, in a different AWS Availability Zone, fall about 8 seconds behind at peak because the outbound link is saturated.

Solution: The cache invalidation message is sent through a queue that
the primary processes. The primary writes the new value AND publishes
an invalidation event. The cache evicts the stale entry. Subsequent
reads fetch from a replica that has the latest data.
====
The race: the application writes to the primary and immediately deletes the
cache entry. Before the replica has replayed the write, a reader misses the
cache, reads the OLD value from the replica, and caches it again. The stale
value now lives in the cache until its TTL expires.

Solutions:
  - Drive invalidation from the replication stream itself (for example, a
    service that tails the binlog or WAL and invalidates once the change is
    committed), so invalidation follows the data instead of racing it.
  - Or send the reads that repopulate the cache to the primary for a short window.
  - Or store a version number with each cached value and refuse to overwrite a
    newer version with an older one.

Kafka and RabbitMQ replicate data across brokers using their own replication protocols. The pattern differs from database replication because queues are ephemeral: they tolerate some data loss.
====
Kafka and RabbitMQ replicate data across brokers using their own replication protocols. The pattern differs from database replication because queue messages are usually short-lived and consumers can often tolerate duplicates. Durability is still configurable: Kafka is frequently used as a durable log, so it is run with `acks=all` and `min.insync.replicas=2` when messages must not be lost.
