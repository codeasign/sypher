When a vertically scaled server crashes, the recovery time scales with the data size. For a PostgreSQL database with 2 TB of data, recovery can take 30-60 minutes.
====
When a vertically scaled server crashes, recovery has two parts. The first is replaying the write-ahead log since the last checkpoint, which usually takes seconds to a few minutes. The second is re-warming the buffer cache, which scales with the size of the working set. For a PostgreSQL database with 2 TB of data, the server accepts connections quickly but can run slowly for 30-60 minutes while its caches refill. Restoring from a backup after losing the disk takes hours.

Scenario: Local cache on single node
  1. App writes new value to PostgreSQL (committed)
  2. App invalidates local cache entry
  3. Another thread reads the cache key
  4. Cache entry is being rebuilt: thread sees empty cache
  5. Thread falls through to database, reads fresh value
  6. Race: if step 5 starts before step 2, thread reads stale data

Resolution:
  - Use read-through cache with TTL (stale tolerated for TTL duration)
  - Use Redis on the same node with exclusive cache-aside pattern
  - Disable local caching if strong consistency is required
====
Scenario: Local cache on a single node (cache-aside)
  1. Thread A reads key K, misses the cache, and reads the old value from PostgreSQL
  2. Thread B writes a new value for K to PostgreSQL (committed)
  3. Thread B invalidates the cache entry for K
  4. Thread A, still holding the old value, writes it into the cache
  5. Every later read of K returns the stale value until the entry expires

Resolution:
  - Give every cache entry a TTL so stale data heals itself
  - Use a versioned cache write, or a short delayed second invalidation
  - Disable local caching if strong consistency is required
