**Model answer.** The CAP theorem says a distributed data store cannot provide consistency, availability, and partition tolerance all at once. Since partitions are unavoidable, the real choice is between consistency and availability while a partition lasts. Consistency means every read returns the most recent write.

This is AP. Comments must never be lost. I use DynamoDB global tables (or Cassandra) with eventually consistent reads. The comment table is keyed by (post_id, created_at). Writes are acknowledged after a majority of local replicas have them (in Cassandra, `LOCAL_QUORUM` or `ONE`). Reads use eventual consistency (single-digit milliseconds, usually converging within about a second). A write-through cache (ElastiCache) serves the most recent comments for each post. During a partition, writes keep succeeding in every region, and some reads may return slightly stale data. When the partition heals, the replication layer and (in Cassandra) hinted handoff and read repair restore consistency. Because comments are keyed by their own unique ID and timestamp, two users posting at once do not conflict, and edits to the same comment resolve with last-write-wins using server-assigned timestamps (client clocks can be wrong).

Stage 1: Ingestion (AP across datacenters). Events arrive from 10,000 services. Each event has a unique idempotency key (resource_id + timestamp + sequence). All events must be accepted. Each datacenter runs its own Kafka cluster (16 partitions, replication factor 3, `acks=all`, `min.insync.replicas=2`), so ingestion keeps working locally even if the datacenter is cut off from the others, and replication to the central pipeline is asynchronous (for example with MirrorMaker 2). Producers retry until acknowledged. The key insight: losing an event is worse than ingesting a duplicate, because duplicates are detected by idempotency keys.

Every event must be counted once. Kafka Streams or Apache Flink reads from Kafka, deduplicates by idempotency key, and orders events by timestamp within each resource_id. Effectively-once processing needs coordination, which is a CP-style guarantee. Flink's checkpointing in exactly-once mode, combined with the idempotency keys, ensures that every event affects the result once, even during failures.
