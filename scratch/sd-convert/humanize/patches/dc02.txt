The routing layer computes `consistent_hash("abc123")` on the consistent hash ring of 1,024 virtual nodes. The hash maps to shard 417. The router attaches `{"shard_id": 417, "version": 3}` to the request metadata and forwards to shard 417's Redis primary node.
====
The counter for a post is split into 1,024 slots to avoid a single hot key. The routing layer picks a slot by hashing the user ID (`hash("user456") % 1024 = 417`), so the same user always lands on the same slot, which keeps the idempotency check in Step 5 local to one slot. The router attaches `{"shard_id": 417, "version": 3}` to the request metadata and forwards to the Redis primary that holds slot 417.

Shard 417 receives the command `INCR post:abc123`. Redis executes this on a single-threaded event loop. The increment is guaranteed atomic: no concurrent read or write interleaves. The command modifies the in-memory hash table entry for `post:abc123`.
====
Shard 417 receives the command `INCR post:abc123:slot417`. Redis executes this on a single-threaded event loop. The increment is guaranteed atomic: no concurrent read or write interleaves. The command modifies the in-memory hash table entry for `post:abc123:slot417`.

Two clients like the same post at nearly the same instant. Client A's request routes to shard 417. Client B's request also routes to shard 417 (same key = same shard). Redis processes them sequentially on its single-threaded event loop: INCR post:abc123, then INCR post:abc123 again. No data loss, no race.

This is the fundamental advantage of sharded counters over CRDT counters for concurrent writes: a single shard's serial execution eliminates the merge problem entirely, at the cost of a single-writer bottleneck per key.
====
Two clients like the same post at nearly the same instant. If they hash to the same slot, Redis processes the two increments sequentially on its single-threaded event loop: INCR post:abc123:slot417, then INCR post:abc123:slot417 again. If they hash to different slots, each increments its own key. Either way, no data loss and no race.

This is the fundamental advantage of sharded counters over CRDT counters for concurrent writes: each slot has a single writer that executes serially, so there is no merge problem within a slot. The cost is that reading the total requires summing all the slots.
