<<<<
Larger quorums provide more safety but reduce availability because more nodes must be online to make decisions.
====
A majority is the smallest quorum that is safe, because any two majorities of the same cluster overlap in at least one node. Requiring more than a majority adds no safety and reduces availability. What cluster size changes is fault tolerance, write cost, and the effect of correlated failures.
>>>>
<<<<
Quorum size controls two competing properties:

Safety increases: More nodes must agree, harder to corrupt.
N=3, quorum=2: 2 nodes must agree (67%)
N=5, quorum=3: 3 nodes must agree (60%)
N=7, quorum=4: 4 nodes must agree (57%)

Availability decreases: More nodes must be online.
N=3 with 99% uptime per node:
  P(all 3 up) = 0.99^3 = 97.0%
  P(quorum lost) = P(2 down) + P(3 down)
  = 0.0285 + 0.000001 = 2.85%

N=5 with 99% uptime per node:
  P(all 5 up) = 0.99^5 = 95.1%
  P(quorum lost) = P(3 down) + P(4 down) + P(5 down)
  = 0.098 + 0.0048 + 0.0000001 = 10.3%
====
Cluster size controls fault tolerance, cost, and write latency:

Majority quorum sizes:
N=3, quorum=2: tolerates 1 failure
N=5, quorum=3: tolerates 2 failures
N=7, quorum=4: tolerates 3 failures

Availability with 99% uptime per node (assuming independent failures):
N=3: quorum is lost when 2 or more nodes are down
  P(quorum lost) = 3 x 0.01^2 x 0.99 + 0.01^3 = about 0.03%
  Availability of the quorum: about 99.97%

N=5: quorum is lost when 3 or more nodes are down
  P(quorum lost) = 10 x 0.01^3 x 0.99^2 + small terms = about 0.001%
  Availability of the quorum: about 99.999%

N=7: quorum is lost when 4 or more nodes are down
  Availability of the quorum: about 99.9999%
>>>>
<<<<
A 5-node cluster has 10.3% chance of quorum loss per event with 99% per-node uptime. This is 3.6 times worse than a 3-node cluster for the same per-node reliability. The trade-off is fault tolerance versus availability probability.
====
With independent node failures, a larger cluster loses quorum much less often, so the 5-node cluster is far more available than the 3-node one. The costs are higher infrastructure spend, slightly higher write latency (a write waits for more acknowledgements), and more network paths that can partition. In practice correlated failures (a shared switch, a bad deployment, a shared power feed) dominate, which is why nodes should be spread across independent failure domains such as availability zones.

<<<<
A 2-node cluster has no way to break a tie. Both nodes will claim leadership during a partition. This is always unsafe.
====
A 2-node cluster has no way to break a tie. During a partition, each node must either claim leadership (risking split brain) or refuse to act (losing availability). Without a tiebreaker it cannot be both safe and available.
