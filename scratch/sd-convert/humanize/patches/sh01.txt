With 256 vnodes per shard, data movement during scaling is 1/256 of the dataset per vnode, fine-grained and fast. Cassandra uses 256 vnodes per node by default.
====
With 256 vnodes per shard, each vnode owns only a tiny slice of the ring (1/(256 x N) of the data in an N-shard cluster), so scaling moves many small pieces from many shards in parallel, which is fine-grained and fast. Cassandra historically defaulted to 256 vnodes per node and defaults to 16 since version 4.0.

<<<<
Consistent hashing avoids this problem entirely: only 1/N of data moves when adding a node.
====
Consistent hashing helps most when you add a few nodes at a time: adding one node to N moves only about 1/(N+1) of the data. Doubling the cluster moves about half of the data either way. Another common approach is to create many logical shards up front (say 256 logical shards on 8 machines), so that scaling means moving whole logical shards to new machines without re-hashing any rows.

<<<<
Discord's solution (from their engineering blog) was to shard by `guild_id` and within each guild, partition messages by channel. When a guild becomes too large, the guild's data is split across multiple shards using a "shard split" operation. The key insight: Discord originally used range-based sharding by guild_id, but found that a single large guild caused a hot spot. They migrated to consistent hashing with virtual nodes to allow gradual rebalancing.
====
Discord's engineering blog describes partitioning its message store by channel and a time bucket, so that a channel's recent history is stored together and no single partition grows without bound. It also describes coalescing identical concurrent requests in a data service so that a burst of reads for one hot channel becomes a single database query. The key insight: choose a shard key that matches the dominant query, and add a second component (like a time bucket) or a protective layer to handle the few keys that are far hotter than the rest.
