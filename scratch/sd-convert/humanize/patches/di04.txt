Distributed ID systems are **CP** (Consistency and Partition Tolerance) systems under the CAP theorem. They sacrifice availability during clock skew events to maintain consistency (no duplicate IDs). However, the availability loss is bounded (milliseconds) and local (only the affected worker).
====
CAP fits an ID generator loosely, because it is not a replicated data store. Generation is local, so it stays available during a network partition (AP-like), and uniqueness is guaranteed by construction (a unique worker ID plus a timestamp plus a sequence) instead of by agreement at runtime. What you give up is global ordering: IDs from different workers are only roughly ordered by time. The one part that needs consistency is worker ID assignment, which relies on a CP coordination service. And when a worker's clock jumps backward, it deliberately pauses generation briefly to protect uniqueness. That pause is bounded and local to the affected worker.
>>>>

**Recovery:** Monitor the difference between the ID's embedded timestamp and the actual wall clock across all workers. If a worker's IDs consistently embed timestamps ahead of the current time, that worker's clock is fast. Manually reset the clock via NTP and wait for IDs to normalize.

**Recovery:** Monitor the difference between the ID's embedded timestamp and the actual wall clock across all workers. If a worker's IDs consistently embed timestamps ahead of the current time, that worker's clock is fast. Correct the clock via NTP. Note that correcting a clock that jumped forward moves it backward relative to IDs already issued, which triggers the backward-clock handling and can block generation for as long as the size of the jump, so many systems also cap how far ahead of wall time a generator may run.

UUID v4 inserts cause page splits on every single insert, increasing write amplification by 10-100x and causing index fragmentation that persists until the table is rebuilt. Real impact: a system with 500GB of data required 5TB of index space due to UUID v4 fragmentation.
====
UUID v4 inserts land at random positions in the index, causing frequent page splits, higher write amplification, and index fragmentation that persists until the table is rebuilt. The impact can be severe on large tables: indexes that are much larger than they need to be, and insert throughput that falls once the index no longer fits in memory.
