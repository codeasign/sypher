A reasonable merge combines both changes: the document becomes "Hello world, edited by Bob" which includes Alice's original text and Bob's edit. If the application-level merge function detects that Bob's edit fully incorporates Alice's text, no further action is needed.

If the edits were conflicting (e.g., Alice deleted a paragraph and Bob modified it), the system would store both versions and request manual resolution.
====
The vector clocks only tell the system that the versions are concurrent. They do not say how to combine them. Combining needs application logic, typically a three-way merge against the last version both editors started from (or a CRDT for text). In this example, Alice's version is "Hello world" and Bob's is "Hello world, edited by Bob". Bob's text already contains Alice's text as a prefix, so a merge function can keep Bob's version and the merged clock [Alice=1, Bob=1] records that both histories are included.

If the edits were conflicting (for example, Alice deleted a paragraph and Bob modified it), a merge function cannot decide automatically, so the system would keep both versions as siblings and ask a person to resolve them.

After recovery, Node A has clock [A=5, B=10, C=8] from the backup. The current state on other nodes is [A=15, B=10, C=8]. Node A's clock shows A=5, but the actual counter should be A=15.

Now Node A receives a write from a client whose clock is [A=12, B=10, C=8]. Node A compares this with its own clock:
- Node A's clock: [A=5, B=10, C=8]
- Client clock: [A=12, B=10, C=8]
- Comparison: Client clock is a DESCENDANT of Node A's clock. The write is "fresh" and accepted.

But the client's write [A=12, B=10, C=8] is actually based on events that happened BEFORE Node A's crash (A=15 on other nodes). The write is stale: other nodes have moved past A=15 to A=16, A=17, etc. But Node A, with its restored backup showing A=5, incorrectly treats the write as fresh.

The resulting clock becomes [A=13, B=10, C=8] (Node A increments to 13 after applying the client's write). When Node A syncs with Node B, Node B sees [A=15, B=10, C=8] and [A=13, B=10, C=8]. Now A=13 is concurrent with A=15 (no node B or C differences). The system creates a false version that does not actually represent a concurrent update in the real timeline.
====
After recovery, Node A has clock [A=5, B=10, C=8] for key K from the backup. The other nodes hold [A=15, B=10, C=8]. Node A's own counter is at 5, but it has already issued counter values up to 15 before the crash, so it has lost track of its own history.

Now Node A accepts a new write from a client that read the key from the restored node, whose clock is [A=5, B=10, C=8]. Node A increments its counter and stamps the write [A=6, B=10, C=8]. Two things go wrong:
- The value 6 was already used before the crash, for a different write that other nodes still hold. Two different values now carry an identical counter, so the system may treat them as the same version or order them wrongly.
- When the new write reaches the other nodes, they compare [A=6, B=10, C=8] with their stored [A=15, B=10, C=8] and conclude that the new write is an ancestor of what they already have. They discard it as stale. The client was told the write succeeded, but it is silently lost.

The rest of the cluster may also see the restored node's old values as "older" than they really are, which makes the restored data resurface as apparent concurrency or as stale reads.

**Migration strategy: Phased rollout**
====
**A caution before the migration plan:** A hybrid logical clock orders events consistently with causality, but it cannot detect concurrency. Two concurrent writes get different HLC values, and the higher one simply wins. Moving from version vectors to HLCs therefore changes the system's conflict semantics from "detect and preserve concurrent versions" to last-writer-wins. That must be an explicit product decision, and the migration plan below should be read with it in mind: the mismatches it measures are precisely the conflicts that would be silently dropped after the switch.

**Migration strategy: Phased rollout**
