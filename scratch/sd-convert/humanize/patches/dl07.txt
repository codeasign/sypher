Use a 7-node etcd cluster with a per-region topology. Place 3 nodes in us-east-1 (primary), 2 in eu-west-1, and 2 in ap-southeast-1. The leader is pinned to the primary region, and all lock acquisitions go through it. Committing a write needs 4 of the 7 voters, so the leader waits for at least one remote region (roughly 70-100ms to eu-west-1). Clients in ap-southeast-1 also pay their own round trip to the leader, which can approach 200ms, so meeting the 200ms P99 target for those clients needs either a leader placement that is closer to them or a design where locks are partitioned by home region and each partition's leader sits near its clients. Read-only replicas in other regions can serve lock status queries as hints, but acquisition always goes through the leader.

For disaster recovery, the lock service is backed by an asynchronous replication stream to a backup cluster. If the primary region fails entirely, operations shift to eu-west-1 with a 60-second cutover, accepting the risk of lost lock state during the 60-second window.
====
Losing any single region still leaves at least 4 of the 7 voters, so quorum holds and a new leader is elected within seconds, with no lost lock state and no manual cutover. Losing two regions at once breaks quorum, and lock operations stop (which is the safe outcome). Recovery from that is a deliberate disaster recovery procedure: restore the cluster from the latest snapshot, require all clients to re-acquire their locks, and make sure fencing tokens cannot go backwards, for example by starting a new token epoch. An asynchronous standby cluster is deliberately not used for automatic failover, because promoting it could grant locks that the failed primary had already granted.

This fix does not replace Redis but adds a monotonic counter for token generation. The counter must survive failures: use Redis RDB or AOF persistence with fsync to ensure the counter value is not lost on restart.
====
Before processing a job, the worker checks if its token is the highest seen for that job. If not, it aborts. That check has to be atomic with the write it protects, so it should be a conditional update in the job store (for example `UPDATE jobs SET last_token = ?, ... WHERE id = ? AND last_token <= ?`), not a read followed by a write.

This fix does not replace Redis but adds a monotonic counter for token generation. The counter must survive failures: use Redis RDB or AOF persistence with fsync to ensure the counter value is not lost on restart, and note that asynchronous replication can still lose recent increments at failover. A simpler fix that needs no token at all is to make job processing idempotent, by recording completion under a unique job ID so that a second execution is rejected.

3. **Read-only mode**: The remaining nodes can serve read-only lock state queries immediately. Write operations (lock acquisition, release) require the full consensus path.

4. **Recovery**: When a failed node rejoins, it enters a catch-up phase. It downloads all log entries it missed from the leader. During catch-up, it does not participate in voting or log commitment. Once caught up, it resumes normal operation.
====
3. **Reads**: Linearizable reads must go through the leader (which confirms it still has a majority) or use a read-index round. A follower answering from its local state may return stale lock information. Write operations (lock acquisition, release) require the full consensus path.

4. **Recovery**: When a failed node rejoins, it acts as a follower. The leader sends it the log entries it missed, or a snapshot if it is too far behind, and Raft's election restriction ensures that a node with a stale log cannot win an election. Once caught up, it counts toward the majority again. If the cluster is going to be running with a reduced margin for long, replace the node rather than waiting.

The solution is priority inheritance: while a high-priority process waits for a low-priority holder, the holder temporarily inherits the higher priority, so medium-priority processes cannot preempt it or delay it during the grace period.

The candidate should also point out that forced release is only safe with fencing. The preempted holder may be paused or slow and may still be writing when the lock is granted to the new requester, so the grant must carry a higher fencing token and the protected resource must reject the old holder's writes.
