Vector clocks grow linearly with the number of nodes. To control size, systems implement pruning strategies. The simplest strategy removes nodes whose counter is zero (meaning that node has never modified the data item).

More sophisticated pruning uses a threshold: if a node's counter has not changed for a configurable number of merge operations, remove it from the clock. The removed entries are treated as zero in subsequent comparisons.
====
Vector clocks grow linearly with the number of nodes. To control size, systems implement pruning strategies. The simplest strategy removes nodes whose counter is zero (meaning that node has never modified the data item). Most implementations never store those entries in the first place, so this rarely saves anything.

More sophisticated pruning removes entries that look stale: for example, if a node's counter has not changed for a configurable number of merge operations, remove it from the clock. The removed entries are treated as zero in subsequent comparisons. This is lossy. Once a real entry is dropped, two clocks that were causally related can compare as concurrent (or equal), so the system may produce extra siblings or, in the worst case, misjudge which version is newer. Dynamo's paper accepts this trade-off and notes that it did not cause problems in production, but it should be a deliberate decision.

The number of concurrent versions is bounded by the number of replicas of the key. In a system with N replicas, at most N concurrent versions can exist for any key (assuming each replica modifies the key at most once without synchronization). In practice, N is typically 3, so the maximum sibling count is 3.
====
When replicas coordinate writes, each replica can create one branch, so a key with N replicas is bounded by N concurrent versions only if every write goes through a distinct replica and each replica accepts one write between syncs. In practice the count is not bounded that tightly: several clients writing through the same replica with the same stale clock each create another sibling, and a busy key can accumulate dozens of siblings (the "sibling explosion" problem seen in Riak). Dotted version vectors and regular reconciliation on read keep the count down.

When a node restarts, its vector clock counters are lost. The node must recover its clock state from its persistent store or from other nodes. The recovery process involves:

1. Reading all local data items and their associated vector clocks.
2. Calculating the maximum counter value for each remote node from the stored clocks.
3. Setting the local node's counter to the maximum value found in any stored clock.

This ensures the node's clock is at least as large as any clock it had before the restart, preventing clock "reset" that could create false concurrent events.
====
When a node restarts without its in-memory counters, it must recover its clock state from its persistent store or from other nodes. The recovery process involves:

1. Reading all local data items and their associated vector clocks.
2. Calculating the maximum counter value for each node, including itself, from the stored clocks.
3. Setting the local node's counter to its own maximum plus one.

This ensures the node never issues a counter value it has already used, which would make two different writes look identical (or one look like a descendant of the other) and could silently lose data. The recovery is only as good as what was persisted: a write that was acknowledged but not yet flushed to disk can vanish in a crash, and the restarted node could then reuse its counter. Systems guard against this by persisting counters before acknowledging, or by giving each incarnation of a node a new identity (an epoch or a fresh node ID).
