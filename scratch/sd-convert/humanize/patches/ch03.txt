A Redis cluster uses consistent hashing to partition cache keys across nodes. Each Redis node stores a subset of keys. Virtual nodes ensure even distribution. The sidecar proxy handles routing, retries, and replica failover.

**Key metrics**: 10-node Redis cluster with 1,000 virtual nodes each achieves 99.2 percent balanced distribution (max node load / average node load = 1.08). Compare to 1 virtual node per node: max/average = 2.4.
====
A fleet of Redis or Memcached nodes uses a consistent hash ring (for example the ketama algorithm in a client library or proxy) to partition cache keys across nodes. Each node stores a subset of keys. Virtual nodes ensure even distribution. The sidecar proxy handles routing, retries, and replica failover. (Redis Cluster itself uses a close cousin of this idea: 16,384 fixed hash slots that are assigned to nodes and moved one at a time, which gives the same minimal-movement behavior without a ring.)

**Key metrics**: A 10-node ring with 1,000 virtual nodes each achieves a max node load / average node load of about 1.08. Compare to 1 virtual node per node: max/average is about 2.4.

For a given ring, the recommended virtual node count per physical node is:

```
v = N * 100  (for clusters under 50 nodes)
v = N * 20   (for clusters over 50 nodes)
```

Where N is the total number of physical nodes. A 10-node cluster gets 1,000 virtual nodes each. A 200-node cluster gets 4,000 virtual nodes each (20 * 200 = 4,000).
====
For a given ring, 100-200 virtual nodes per physical node is a good starting point at any cluster size, and 1,000 is common for small clusters where balance matters more than memory:

```
10-node cluster,  1,000 vnodes each = 10,000 ring entries
200-node cluster,   200 vnodes each = 40,000 ring entries
```

Tune by measuring the skew ratio (max node load divided by average) in production. More virtual nodes give better balance but cost memory and make topology changes slower.

**Duration**: The add operation takes minutes to tens of minutes, depending on the data volume and the network. The topology update itself is atomic in the configuration service, but proxies learn about it within milliseconds to seconds, so for a brief window two proxies may disagree. Nodes should forward a request to the new owner, or clients should retry, to cover that window.
