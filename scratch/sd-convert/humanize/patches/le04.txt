### Failure Mode 6: Zeno's Paradox of Elections

In edge cases, a node can be repeatedly elected but immediately fail before sending a heartbeat. This creates an infinite loop of elections, each consuming resources and extending unavailability.

**Root cause:** A node crashes immediately after winning an election but before sending the first heartbeat. Followers detect the absence of heartbeats and re-elect the same node (because its timeout fires first again).

**Impact:** Complete cluster unavailability during the loop. Resources are wasted on repeated elections.

**Mitigation:** Implement a backoff mechanism. A node that has been recently elected should wait for a full heartbeat interval before accepting the leader role. If it crashes before completing the interval, it must wait for a longer timeout before starting another election.

### Failure Mode 7: Clock Skew

Leader election protocols assume bounded clock skew between nodes. If clocks drift significantly, the timeout mechanism breaks.

**Root cause:** Clock skew exceeding 50% of the election timeout. A node with a slow clock may never time out. A node with a fast clock may time out prematurely.

**Impact:** The fast-clock node constantly starts elections. The slow-clock node is perpetually the leader (its lease never expires from its perspective).

**Mitigation:** Use NTP with tight synchronization (sub-millisecond precision). Monitor clock skew and alert if it exceeds 100ms. Increase the election timeout to accommodate known clock skew in the deployment.

### Failure Mode 5: A Failing Node Repeatedly Wins Elections

In edge cases, a node that is unhealthy can win an election, fail before it does useful work, and win again. This creates a loop of elections, each consuming resources and extending unavailability.

**Root cause:** A node with a failing disk or an overloaded process wins an election but crashes, stalls, or cannot replicate before the followers' timers fire. The cluster re-elects, and the same node can win again if its timer fires first.

**Impact:** Repeated write unavailability during the loop. Resources are wasted on repeated elections.

**Mitigation:** Use pre-vote so a node that cannot reach a majority does not disrupt the cluster, and use health checks so a node with a failing disk or a starved process removes itself from candidacy. A failing node can also be taken out of the cluster by an operator or an automated playbook.

### Failure Mode 6: Clock Drift and Pauses

Leader election protocols depend on timers. If clocks run at very different rates, or if a process is paused, the timeout mechanism misbehaves.

**Root cause:** Raft election timers measure elapsed local time, so an absolute offset between two nodes' clocks does not matter. What matters is the rate at which clocks tick and sudden jumps or pauses (a VM suspend, a long GC pause, or a stepped clock). A node with a slow-running timer takes longer to notice a dead leader, and a node with a fast one can time out prematurely. Time-based leader leases are more sensitive, because they assume bounded drift between the leader's and the followers' clocks.

**Impact:** A fast-timer node starts unnecessary elections. A leader that was paused may wake up believing its lease is still valid after a new leader has been elected.

**Mitigation:** Use monotonic clocks for timers, keep NTP healthy, monitor drift, and leave a safety margin in lease durations. Have the storage layer reject stale leaders with fencing tokens or term numbers, so a paused old leader cannot do damage.
