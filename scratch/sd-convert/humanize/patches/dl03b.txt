The lock service (etcd, ZooKeeper) limits the number of concurrent connections. etcd has a default limit of 10,000 client connections per cluster. ZooKeeper has a default limit of 60 connections per client IP by default.

Each application server should maintain a connection pool to the lock service. The pool size depends on the number of concurrent lock operations the server needs to perform.
====
Lock services bound the number of concurrent connections in different ways. ZooKeeper limits connections per client IP per server (`maxClientCnxns`, 60 by default). etcd has no fixed default cap; the practical limit comes from file descriptors, memory and the load balancer in front of it. Each connection carries state and keepalive traffic, so a fleet of hundreds of servers with many connections each can still be a problem.

For services that need one connection per in-flight operation (a SQL-based lock, for example), each application server should maintain a connection pool. The pool size depends on the number of concurrent lock operations the server needs to perform. Clients of gRPC-based services such as etcd multiplex many operations over one connection, so a single shared client per process is the usual choice, and the arithmetic below is the worst case.

====
If the lock service or the load balancer in front of it is sized for 10,000 connections, 300 servers at 60 connections each would exceed that. The solution is either to raise the limit (OS-level `ulimit -n` tuning, load balancer limits) or to reduce the connection pool per server, for example by sharing one multiplexed client per process.

**Lease renewal**: In Yellow level, renew leases earlier than normal (when 40% of the TTL remains instead of 25%). In Orange level, renew when 50% of the TTL remains. This leaves more room for retries when the network is slow. In Red level, never relax the safety rule: if no renewal has been confirmed and the TTL (minus a margin) has elapsed locally, stop using the lock. Continuing past the TTL without confirmation is exactly how two holders end up operating at once.

For 100,000 concurrent locks, the memory requirement is 25 MB for the lock data plus approximately 50 MB for the etcd in-memory index. This is still modest: a 64 GB server has over 1,000 times the required memory.

**The real memory cost is the WAL**: Each lock acquisition and release generates one or more WAL entries. With 100,000 lock acquisitions per second and an average entry size of 200 bytes, the WAL grows at 20 MB/second or 72 GB/hour. WAL compaction and snapshotting must keep pace with this growth to prevent disk exhaustion.
====
For 100,000 concurrent locks, the memory requirement is roughly 25 MB for the lock data plus a few tens of megabytes for etcd's in-memory index. These are rough estimates rather than measurements, but the conclusion is robust: this is modest, and a 64 GB server has hundreds of times the required memory.

**The real cost is disk, not memory**: Each lock acquisition and release generates one or more WAL entries, and every write creates a new revision in the database. At 5,000 lock operations per second and an average entry size of 200 bytes, the WAL grows at about 1 MB/second, or 3.6 GB/hour. Old WAL segments are removed after snapshots, and etcd's history must be compacted (automatically or with `etcdctl compact`) and the database defragmented, or it will grow until it reaches the storage quota.

Removing a node from a consensus cluster is more dangerous than adding one. Never remove more than one node at a time. Removing a node reduces the quorum size, which reduces failure tolerance.
====
Removing a node from a consensus cluster is more dangerous than adding one. Never remove more than one node at a time, and never remove a member of a cluster that is already missing a member. Going from 5 nodes to 4 leaves the same failure tolerance as 3 nodes (one failure), and going from 3 to 2 leaves none at all.

Beyond that, Raft heartbeat overhead dominates the available CPU and commit latency degrades: the coordination cost grows roughly quadratically with cluster size.
- **Majority-commit delay**: every WAL appender must wait for at least a majority to commit, so each additional node directly increases commit delay without adding throughput.
====
Beyond that, replication traffic from the leader (which grows linearly with the member count) and the cost of waiting for a larger majority reduce write throughput without adding capacity for writes.
- **Majority-commit delay**: every write must wait for a majority to acknowledge it, so adding voting nodes does not add write throughput and can make commits slower, because the majority gets larger.

Blue-green deployment for a lock service cluster where cipher key data is subsequently updated is non-trivial, since all state must be migrated from the old cluster to the new one.  Unlike stateless servers that can switch traffic instantly, lock state is ephemeral and must be handled in steps.
====
Blue-green deployment for a lock service cluster is non-trivial, because two clusters must never both grant the same lock at the same time. Unlike stateless servers that can be switched over gradually, lock state is ephemeral and the switch has to be handled in steps with a clean cut-over.
>>>>
<<<<
No lock should be migrated while it is held. Wait for all existing locks to expire. New lock acquisitions during this phase should still go to the blue cluster. Set a maximum drain timeout of 15 minutes. If locks persist beyond this timeout, force-release them (after verifying that the holders are healthy and can reacquire).
====
No lock should be migrated while it is held. Put the blue cluster into a mode where it stops granting new locks (clients retry or wait), and wait for the existing locks to be released or to expire. Set a maximum drain timeout of 15 minutes. If locks persist beyond this timeout, force-release them only after verifying that the holders have stopped or that the protected resources enforce fencing tokens.
