Improvement: Use a witness node in a third region instead of a full data node. This reduces the data node count to 5, quorum to 3, and write latency to local region only (2 local nodes + 1 witness acknowledgment).
====
Improvement options: A witness (a vote without data) can replace one data node to save cost, for example 2 data nodes in each of two regions plus a witness in a third, giving 5 votes with quorum 3. Writes from the leader region still need one remote vote, so latency stays cross-region. Keeping every write within one region would require placing a majority of the votes there (for example 3 of 5), but then losing that region loses quorum, which is the trade-off between write latency and region-failure tolerance.

CRDTs eliminate the need for split brain prevention because they are designed to handle concurrent updates safely. However, they are limited to data types that have well-defined merge semantics. Complex data structures like ordered lists or maps with nested fields are harder to implement as CRDTs.
====
CRDTs remove the need for conflict resolution for the data types they support, because concurrent updates merge safely. They do not remove the need for safety mechanisms when an invariant spans replicas (for example, a balance that must never go negative, or an inventory that must never oversell), because a merge cannot undo an update that both sides already accepted. CRDTs are also limited to data types that have well-defined merge semantics. Complex data structures like ordered lists or maps with nested fields are harder to implement as CRDTs.

====
Prevention: Never fence simultaneously. The fencing mechanism should have a priority-based ordering. The node with the higher fencing token should fence first. The lower-token node should wait 2x the fencing timeout before attempting its own fence. (Cluster managers such as Pacemaker offer fencing delay settings for exactly this reason: in a 2-node cluster, one node is given a delay so that the other wins the fencing race.)
