**Trade-off**: Riak's fixed partition count keeps ownership simple: adding a node hands it a share of the existing partitions (about 1/N of the data), and no key is re-hashed. The catch is that the partition count is a design decision made at cluster creation, and it caps how far the cluster can grow (newer versions can resize the ring online, at some cost).

ScyllaDB is a C++ rewrite of Cassandra that maintains API compatibility while redesigning the consistent hashing layer. ScyllaDB uses a shard-aware consistent hash ring: each CPU core on each node acts as an independent shard on the ring.

**Trade-off**: ScyllaDB's shard-aware ring eliminates cross-core coordination within a node, achieving 10x throughput per node compared to Cassandra. However, the shard-level mapping adds complexity to topology management: a 10-node cluster with 32 cores each has 320 ring entries.
====
ScyllaDB is a C++ rewrite of Cassandra that maintains API compatibility. Across nodes it uses the same token ring idea as Cassandra. Inside each node it also splits the data across CPU cores in a shard-per-core design, and its drivers are shard-aware, so a request can go straight to the right core on the right node.

**Trade-off**: The shard-per-core design eliminates cross-core coordination within a node, and users and vendor benchmarks often report several times more throughput per node than Cassandra. The cost is a different operational model, and it is less flexible when a workload does not spread evenly across cores.

For any hash function, hash 1 million random keys into 1,000 buckets and compare the spread with what pure chance predicts: each bucket should hold about 1,000 keys with a standard deviation near the square root of that (about 32, or 3 percent). A much larger spread means the hash is biased.
