If the leader fails, the cluster elects a new leader, which takes from a few hundred milliseconds to a couple of seconds depending on the election timeout (etcd's default is 1 second, and it can be tuned lower on fast networks). During the election, lock operations are not available. Unavailability is not itself a safety problem, but clients that lost contact with the service must treat their locks as possibly expired, and fencing tokens protect the resource if they do not.

**Database integration**: The lock protects database operations. The fencing token is passed as a session variable or a comment in the SQL query. The database trigger checks the token and rejects stale operations.

```sql
-- Safe database operation with fencing token
SET @fencing_token = 1042;
UPDATE payments SET status = 'processed'
WHERE batch_id = 847
  AND @fencing_token > (
    SELECT MAX(last_token) FROM lock_tokens
    WHERE resource = 'batch_847'
  );
```
====
**Database integration**: The lock protects database operations. The fencing token is stored next to the protected data, and the token check and the write happen in one transaction so that no other writer can slip in between them.

```sql
-- Safe database operation with fencing token 1042
START TRANSACTION;

-- Advance the stored token; this matches no row if a newer holder has already written
UPDATE lock_tokens
SET last_token = 1042
WHERE resource = 'batch_847'
  AND last_token <= 1042;

-- If the UPDATE affected 0 rows, the token is stale: ROLLBACK and abort.
-- Otherwise perform the protected write in the same transaction.
UPDATE payments SET status = 'processed' WHERE batch_id = 847;

COMMIT;
```

A 3-region Geo-Raft cluster with nodes in us-east-1, eu-west-1, and ap-southeast-1 has a commit latency of 150ms (the slowest inter-region link). This is acceptable for coarse-grained locking but not for high-throughput operations.
====
Raft needs only a majority, so in a 3-region cluster with nodes in us-east-1, eu-west-1, and ap-southeast-1, the leader waits for the nearest other region rather than the farthest. With the leader in us-east-1, commits take roughly one us-east-1 to eu-west-1 round trip (about 70-100ms). If the leader sits in the middle of the pack, commits from far regions still pay a cross-region round trip. This is acceptable for coarse-grained locking but not for high-throughput operations.

<<<<
- **No recovery from stale snapshots**: Lock state is ephemeral. A snapshot from 1 hour ago shows locks that were held at that time, but all those locks have since expired. Recovery is only useful for reconstructing the last known state before a catastrophic failure.
====
- **Treat restored state as ephemeral**: Lock state is short-lived. A snapshot from 1 hour ago shows locks that were held at that time, and clients that held them may be long gone. After a restore, clients should re-acquire their locks rather than assume ownership. A restore from an old snapshot also rewinds the revision counter, which means fencing tokens taken from revisions can be reused, so resources should be told to reset their last-seen token or the cluster should be restored from the most recent snapshot possible.

Leader election in a 3-node cluster takes 150-300ms under normal conditions. If the cluster is under load, election time can extend to 1-2 seconds as the Raft candidates process pending log entries.
====
Leader election in a 3-node cluster typically completes within one or two election timeouts (with etcd's 1-second default, expect roughly 1-3 seconds after the leader is lost; tuned clusters on fast networks can be faster). If the cluster is under load or a split vote occurs, another round with a fresh randomized timeout is needed.

<<<<
The commit latency is the latency of the median follower, not the fastest or slowest. If the four followers have latencies of 0.5ms, 1ms, 3ms, and 50ms, the commit latency is determined by the 3ms follower (the median of the three fastest followers counting the leader). The 50ms follower can be slow without affecting performance.
====
The commit needs the leader plus the two fastest followers. If the four followers have latencies of 0.5ms, 1ms, 3ms, and 50ms, the commit latency is determined by the 1ms follower (the second-fastest), and the 3ms and 50ms followers can be slow without affecting performance.

A witness node is a lightweight participant in the consensus protocol that participates in elections but does not hold the full lock registry. Witness nodes are useful for maintaining quorum without the cost of a full data node.
====
A witness node is a lightweight voting participant that helps break ties without holding the full lock registry. The idea appears in some replicated systems, but etcd and ZooKeeper do not ship a data-less witness role (etcd has non-voting learners, and ZooKeeper has non-voting observers, which do not help quorum), so treat this section as an architectural pattern rather than a feature you can switch on.
>>>>
<<<<
It does not store the lock registry or the WAL. It participates only in the Raft voting process. If the witness node fails, the cluster degrades to 2 full nodes operating with 2/2 quorum, still functional but unable to tolerate another failure.
====
It does not store the lock registry, and it keeps only the minimal state needed to vote (term and vote records, plus enough log metadata to judge which candidate is up to date). If the witness node fails, the cluster degrades to 2 full nodes operating with 2/2 quorum, still functional but unable to tolerate another failure. The trade-off is durability: an entry acknowledged only by the leader and the witness exists on one data node, so a system like this needs rules such as requiring a data-bearing follower's acknowledgement before committing.
