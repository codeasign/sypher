AWS does not offer a managed sharding service. Instead, Aurora Global Database provides multi-region replication. Sharding must be implemented at the application layer using a sharding library or a proxy. AWS recommends using Amazon RDS Proxy with application-level sharding.

**Cost/ops trade-off:** Low operational overhead (RDS manages the database), but sharding logic is the customer's responsibility. Aurora auto-scales storage to 128 TB, delaying the need for sharding for many workloads.
====
AWS offers several paths. DynamoDB partitions data automatically. Aurora Limitless Database (introduced in 2024) adds managed horizontal sharding for PostgreSQL-compatible workloads. Aurora Global Database provides multi-region replication. With standard RDS or Aurora, sharding is implemented at the application layer using a sharding library or a proxy.

**Cost/ops trade-off:** Low operational overhead (AWS manages the database), but with standard RDS and Aurora the sharding logic is the customer's responsibility. Aurora's storage auto-scales to at least 128 TB, which delays the need for sharding for many workloads.

Discord sharded by guild ID because every query filters by guild. Uber sharded by city because 90 percent of queries filter by city. Cloudflare sharded by domain name because every DNS query specifies a domain. The shard key must match the access pattern; uniform data distribution is a secondary concern.
====
Discord partitions messages by channel because users read one channel at a time. Uber's Schemaless shards by row key because most access is by key. Instagram places a user's data on one logical shard because most queries are about one user. The shard key must match the access pattern; uniform data distribution is a secondary concern.
>>>>
<<<<
Uber's city + date scheme gave them both geographic query isolation and time-based retention. Discord's guild + channel scheme gave them guild-level routing and channel-level ordering. A single shard level forces a compromise between query performance and data management.
====
Discord's (channel, time bucket) partition key gives it channel-level routing, bounded partition sizes, and cheap access to recent history. Instagram's logical-to-physical mapping separates where data lives from which machine holds it. A single level of partitioning often forces a compromise between query performance and data management.

Every company that did rebalancing the wrong way lost data or caused outages. Use proven tools (Vitess reshard, Cassandra nodetool, custom tool with dual-writes and checksum verification).
====
Teams that rebalance carelessly lose data or cause outages. Use proven tools (Vitess Reshard, the Citus rebalancer, Cassandra's streaming bootstrap, or a custom tool with dual-writes and checksum verification).

====
A problem like an oversized partition or a hot shard is invisible in an average until you monitor the individual partition or shard. Every metric that matters for the cluster matters more for individual shards.

Cloudflare's SQLite sharding worked because the simpler alternatives (indexing, vertical scaling) had already been exhausted. Discord went to Cassandra because MongoDB's single-instance limit was a hard ceiling.
====
Cloudflare replicates its configuration data to every server instead of sharding it, because the data is small and read-mostly. Discord went to Cassandra because its message history outgrew what a single MongoDB replica set could serve.
