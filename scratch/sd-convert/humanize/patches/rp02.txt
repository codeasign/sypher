In PostgreSQL, the LSN is a 64-bit integer represented as two 32-bit hexadecimal values (e.g., `0/16B4F30`). The LSN serves as both a position identifier and a checkpoint marker.

**Structure:** `LSN = (logFileId << 32) | offset`. The high 32 bits identify the WAL segment file; the low 32 bits identify the byte offset within that file.
====
In PostgreSQL, the LSN is a 64-bit integer written as two 32-bit hexadecimal values (e.g., `0/16B4F30`). The LSN serves as both a position identifier and a checkpoint marker.

**Structure:** `LSN = (high << 32) | low`. It is simply a byte position in the overall WAL stream, which only ever grows. The WAL segment file that holds a given LSN is derived from it (with 16 MB segments by default).

A single replica can apply approximately 500,000 to 1 million writes per second, depending on the storage engine. MySQL's single-threaded SQL thread is a notorious bottleneck: it can apply only as fast as one core.
====
Depending on the storage engine and hardware, a single replica can apply from tens of thousands to a few hundred thousand simple row changes per second. Single-threaded apply is a classic bottleneck: MySQL's SQL thread was notorious for it (parallel replication now helps), and PostgreSQL's recovery process also replays WAL in a single process.

The WAL buffer on the primary consumes memory proportional to the maximum replication lag. A common configuration is 64 MB to 256 MB for the WAL buffer. Each replication slot adds approximately 100 bytes of memory overhead.

Replicas need additional memory for the WAL receiver buffer (typically 64 MB default) and the local WAL segment cache. The storage engine's buffer pool is sized independently and should be equal to or larger than the primary's for consistent read performance.
====
The in-memory WAL buffer on the primary (`wal_buffers`, automatically sized and capped at one 16 MB WAL segment by default) is small and does not depend on replication lag. What grows with lag is the WAL retained on disk for slow replicas. Each replication slot itself adds only a tiny amount of memory overhead.

Replicas need little extra memory for replication itself. The storage engine's buffer pool is sized independently, and it should be similar in size to the primary's if the replica serves the same read workload.
