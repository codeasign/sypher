A system with 1,024 shards can handle 15 million writes per second.
====
A system with 1,024 shards can, in theory, handle about 15 million writes per second (1,024 shards at roughly 15,000 writes per second each).
>>>>
<<<<
Simpler to implement and reason about. Used by Vitess (with controlled rebalancing), MySQL Fabric.
====
Simpler to implement and reason about. Adding a shard reshuffles most of the data, so it fits best when the shard count rarely changes. Vitess takes a related approach: it hashes each key to a keyspace ID and assigns contiguous ranges of that ID to shards, which lets it split one shard into two without touching the others.
>>>>
<<<<
Each scatter-gather hits all 64 shards, generating 64,000 database connections and consuming 80 percent of the cluster's CPU.
====
Each scatter-gather hits all 64 shards, generating 64,000 shard queries per second and consuming 80 percent of the cluster's CPU.
>>>>
<<<<
This is a security concern. Never expose shard identity outside the internal network.
====
This is a minor information-disclosure risk. Avoid exposing shard identity outside the internal network.
>>>>
<<<<
use a proven rebalancing tool (Vitess `reshard`, Cassandra `nodetool rebuild`, custom tool with dual-writes and checksum verification).
====
use a proven rebalancing tool (Vitess's Reshard workflow, the Citus shard rebalancer, Cassandra's built-in bootstrap and decommission streaming, or a custom tool with dual-writes and checksum verification).
>>>>
<<<<
consider a schemaless database (MongoDB, Cassandra) that handles schema changes natively.
====
consider a flexible-schema document database such as MongoDB that handles schema changes more gracefully.
