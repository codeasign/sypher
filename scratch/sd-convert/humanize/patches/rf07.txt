<<<<
The entry is not committed because it was replicated to only 2 nodes (leader + 1 follower), which is not a majority of 3 (quorum = 2, but the leader needs 2 followers to acknowledge = 3 total).
====
The entry is not committed because it is stored on only 2 of the 5 nodes (the leader and 1 follower), and a majority of 5 is 3.

<<<<
**Approach 1:** Expand to 5 nodes: 3 in us-east-1, 2 in eu-west-1. Quorum is 3 of 5. This tolerates 1 node failure in any region or a full region failure of eu-west-1. However, if us-east-1 fails completely, only 2 nodes survive, which is not a majority: the cluster is unavailable until us-east-1 recovers.

Write latency: approximately 80ms (one cross-region RTT to replicate to eu-west-1 nodes and achieve quorum of 3).
Read latency: us-east-1 reads are 1-2ms (local leader). eu-west-1 reads are either forwarded to the leader (80ms) or served locally with stale data (0.2ms).
====
**Approach 1:** Expand to 5 voting nodes: 3 in us-east-1, 2 in eu-west-1. Quorum is 3 of 5. This tolerates the loss of any 2 nodes, including a full region failure of eu-west-1. However, if us-east-1 fails completely, only 2 nodes survive, which is not a majority: the cluster is unavailable until us-east-1 recovers.

Write latency: with the leader in us-east-1, a quorum of 3 can be reached with the three local nodes, so commits take a few milliseconds. Writes issued from eu-west-1 still pay the 80ms round trip to reach the leader. If the leader moves to eu-west-1, every commit needs at least one us-east-1 node, so latency becomes about 80ms.
Read latency: us-east-1 reads are 1-2ms (local leader). eu-west-1 reads are either forwarded to the leader (80ms) or served locally with stale data (0.2ms).
>>>>
<<<<
**Recommendation:** Use Approach 1. At 100 writes/sec, the 80ms write latency is acceptable for configuration data. Add read-only followers in eu-west-1 to serve local reads with read-index optimization (5-10ms each, including the round trip to get the commit index).
====
**Recommendation:** Use Approach 1 with leadership pinned to us-east-1 (for example through leader priority or leadership transfer), because the extra voting nodes improve fault tolerance at no cost to write latency while the leader stays in the US. At 100 writes/sec, even the occasional 80ms write from Europe is acceptable for configuration data. Serve eu-west-1 reads locally with the read-index technique (which needs one round trip to the leader for the commit index, so it is still about 80ms) or accept stale local reads for data that tolerates them.
>>>>
<<<<
A single Raft group cannot handle 50,000 writes/sec. Even with batching (64 entries per RPC), the leader performs approximately 800 rounds/sec (50,000 / 64), each requiring at least one fsync. Practical fsync limits are 10,000-20,000 per second on modern SSDs. Additionally, AppendEntries RPCs to followers create network overhead.
====
A single Raft group is a poor fit for this workload. With batching (64 entries per RPC), 50,000 writes/sec is only about 800 batches per second, which is within reach of fast hardware, and published benchmarks of single Raft groups show numbers in the tens of thousands of writes per second. But the same leader would also have to serve 200,000 linearizable reads per second and ship every entry to every follower, with no headroom for growth, GC pauses, or a slow disk. Sharding gives both headroom and scale.

The lease duration is set in the state machine command itself, so all replicas agree on the expiration time. The leader checks expiration when processing acquire requests (not proactively; expiration only matters when another client tries to acquire).
====
The leader stamps each command with an absolute expiry time, so all replicas agree on it, and expiration is checked when another client tries to acquire (not proactively). This relies on the leader's clock being reasonably close to real time across leader changes. Because a paused client can outlive its lease, each grant should also return a fencing token, such as the log index of the acquire entry, which the protected resource checks so a stale holder cannot cause damage.

**Fairness:** Keep a FIFO queue of waiters per lock in the state machine, and grant the lock to the head of the queue when it is released or expires. That prevents starvation.
