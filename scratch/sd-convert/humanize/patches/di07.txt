**Key requirement:** IDs must not reveal order volume. Counter-based sequential IDs reveal it directly: two order numbers a day apart tell a competitor how many orders were placed in between (the "German tank problem"). Snowflake IDs do not carry a running total, but they still expose creation time and, through their sequence bits, hints about the order rate. The public identifier must not leak that.

"I would use Snowflake IDs internally (64-bit) but encode them with base62 before exposing them in order URLs. The base62 encoding produces a 9-11 character string: `https://example.com/order/3hT5kMmF9`. This encoding hides the sequential nature from external observers. Internally, the database stores the raw 64-bit integer and benefits from B-tree-friendly sequential inserts. The timestamp in the high bits provides sortability without exposing the exact order rate. For 5 regions, I would allocate 3 bits for the region ID (supporting up to 8 regions) and 7 bits for worker IDs (128 workers per region)."
====
"I would use Snowflake IDs internally (64-bit), so the database keeps B-tree-friendly inserts and sortability by creation time. I would not expose them directly. Base62 encoding alone only shortens the ID: it is reversible and still increases with time, so it hides nothing. Instead, each order gets a separate public order number that is random (for example 12 to 16 characters from a secure random source), stored in a unique-indexed column and mapped to the internal ID. An alternative is to encrypt the internal ID with a keyed permutation before exposing it. Internal systems sort by the Snowflake ID, and customers and competitors only ever see the opaque public number. For 5 regions, I would allocate 3 bits for the region ID (supporting up to 8 regions) and 7 bits for worker IDs (128 workers per region)."

**Approach:** This is an advanced variant where the ID must carry cryptographic proof. One solution: append an HMAC-SHA256 truncated signature to a standard Snowflake ID. The ID becomes 128 bits (64-bit Snowflake + 64-bit signature). The signature uses a per-worker HMAC key that is rotated daily. **Approach:** This is an advanced variant where the ID must be verifiable. One solution: append a truncated HMAC-SHA256 tag to a standard Snowflake ID, so the ID becomes 128 bits (64-bit Snowflake + 64-bit tag). An HMAC is symmetric, so verifying it requires the secret key, which means only parties that hold that key can verify IDs. If regulators must verify without holding a secret, use an asymmetric signature (for example Ed25519) instead. Signatures are at least 64 bytes, though, so a common design keeps the ID small and stores the signature in a separate, append-only audit record keyed by the ID.
>>>>

- The truncated HMAC trade-off: 64-bit HMAC gives 2^32 forgery-attempt resistance before a collision (acceptable for most regulatory bodies).

- The truncated HMAC trade-off: a 64-bit tag means a forger who can submit guesses succeeds with probability 2^-64 per attempt, which is strong if verification attempts are rate-limited, but a shorter tag or an unlimited-guess setting would weaken it.
