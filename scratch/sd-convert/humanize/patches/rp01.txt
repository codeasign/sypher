**Q2: You deploy replicas in three different AWS regions. A user in Sydney writes data, then a user in London reads the Sydney data 500 milliseconds later and gets stale results. What happened?**

The Sydney write was committed to the primary in Sydney. Replication to the London replica takes approximately 200-400 milliseconds of network latency (Sydney to London is about 160 ms round-trip) plus any processing lag on the replica. At 500 ms after the write, the replica may still be catching up. This is expected behavior with asynchronous replication across geographic distances.
====
**Q2: You deploy replicas in three different AWS regions. A user in Sydney writes data, then a user in London reads the Sydney data 100 milliseconds later and gets stale results. What happened?**

The Sydney write was committed to the primary in Sydney. The network path from Sydney to London is long: the round trip is roughly 250-300 ms, so one way is about 130-150 ms, plus processing time on the replica. At 100 ms after the write, the change cannot have arrived yet. This is expected behavior with asynchronous replication across geographic distances, and it is a physical limit no tuning can remove.

The primary cannot acknowledge writes until the synchronous replica confirms them. If the replica is down, every write to the primary hangs. Production systems handle this with a timeout: if the synchronous replica does not respond within a configurable window (typically 1-5 seconds), the primary degrades it to asynchronous mode and continues. This prevents a slow replica from taking down write availability.
====
The primary cannot acknowledge writes until the synchronous replica confirms them. If the replica is down, every write to the primary hangs. Production systems handle this in different ways. MySQL semi-synchronous replication falls back to asynchronous after a timeout. Plain PostgreSQL does not fall back on its own: it waits until the standby returns or an operator (or a tool like Patroni) changes the setting. Either way, the trade-off is the same: waiting protects against data loss but risks write availability, and falling back does the opposite.

With W=2, you need at least two nodes to acknowledge a write. If three nodes fail, only two remain, so you can still write. If four nodes fail, only one remains and writes fail. With R=2, same logic: you can still read as long as at least two nodes are available. In practice, if more than two nodes are down the cluster is degraded and operators should intervene.
====
Only the three replicas that hold a given key matter for that key. With W=2, a write succeeds as long as 2 of those 3 replicas acknowledge it, so you can lose 1 replica and still write. If 2 of the 3 are down, writes to that key fail. R=2 works the same way for reads. Because R + W = 4 is greater than the replication factor of 3, every read quorum overlaps every write quorum in at least one node, so a read sees the latest acknowledged write (assuming no other failures or sloppy quorums). Losing other nodes in the five-node cluster does not affect keys whose replicas are all healthy.
