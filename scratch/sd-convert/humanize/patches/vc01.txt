Dotted version vectors extend version vectors to handle concurrent updates to the same item by the same replica. In standard version vectors, if a replica modifies an item twice without syncing, the second update overwrites the first. Dotted version vectors add an additional per-object counter called a "dot" that tracks individual writes uniquely.

Riak's distributed database popularized dotted version vectors. They reduce sibling explosion (where an object accumulates many conflicting versions) by ensuring that updates from the same replica in sequence produce a single version rather than multiple concurrent versions.
====
Dotted version vectors solve a specific problem with plain version vectors. When several clients write to the same key through the same replica, and the version vector has only one entry per replica, those writes look causally ordered even when the clients had not seen each other's writes, so one silently overwrites the other. The workaround of giving every client its own entry makes the vectors grow without bound. Dotted version vectors keep one entry per replica and add a single "dot", the (replica, counter) identity of the one write that created this version. That lets a replica tell "this write is concurrent with the others I already hold" from "this write supersedes them", so concurrent writes are preserved as siblings without per-client entries.

Riak adopted dotted version vectors in version 2.0. They reduce both lost updates and sibling explosion (where an object accumulates many conflicting versions that were never truly concurrent).

For systems with 1,000 nodes where only 50 are active at any time, ITCs use approximately 50 entries instead of 1,000.
====
The aim is that the clock size follows the number of participants that are currently active rather than every participant that has ever existed, so it stays small in systems where nodes join and leave often. ITCs are more compact in those cases but are harder to implement and reason about, which is why plain version vectors remain far more common in practice.

====
Spanner picks a commit timestamp T and then waits ("commit wait") until TrueTime guarantees that T is in the past everywhere before it reports the commit. Any transaction that starts afterwards gets a later timestamp, which gives external consistency (a strong form of linearizability for transactions) without vector clocks.

====
If event A happened before event B, then A's timestamp is smaller than B's. The reverse does not hold: if A has timestamp 5 and B has timestamp 7, you cannot conclude that A happened before B, because they may be concurrent and simply ordered by the counters. With a tiebreaker (usually the node ID) every pair of events gets an order, but for concurrent events that order is arbitrary.

Vector clocks were introduced by Friedemann Mattern in 1988 in the paper "Virtual Time and Global States of Distributed Systems." The concept built on Lamport's 1978 "happens-before" relation and timestamps. Mattern recognized that a single integer was insufficient for detecting concurrency and proposed using a vector of counters.

The first major production use of vector clocks was Amazon's Dynamo system, described in the 2007 SOSP paper "Dynamo: Amazon's Highly Available Key-value Store." The Dynamo paper demonstrated that vector clocks were practical for large-scale production systems and inspired a generation of distributed databases including Cassandra, Riak, and Voldemort.
====
Vector clocks were introduced independently by Colin Fidge and by Friedemann Mattern in 1988 (Mattern's paper is "Virtual Time and Global States of Distributed Systems"). The concept built on Lamport's 1978 "happens-before" relation and timestamps. Both recognized that a single integer was insufficient for detecting concurrency and proposed using a vector of counters.

The most influential early production use was Amazon's Dynamo system, described in the 2007 SOSP paper "Dynamo: Amazon's Highly Available Key-value Store." The Dynamo paper showed that versioning with vector clocks was practical at large scale and inspired a generation of distributed databases. Riak and Voldemort used vector clocks (Riak later moved to dotted version vectors), while Cassandra borrowed Dynamo's partitioning and replication ideas but chose per-cell timestamps with last-write-wins instead of vector clocks.
