In standard version vectors, if Node A modifies key K twice before synchronizing with Node B, the two versions look like: [A=1] and [A=1]. But these versions are siblings: they cannot be distinguished because both have the same vector clock. Dotted version vectors add a per-write sequence number: the first write creates dot [1] with clock [A=1], the second write creates dot [2] with clock [A=2]. The sibling versions become distinguishable: one has clock [A=1] with dot [1], the other has clock [A=2] with dot [2].
====
Suppose two clients each read key K (seeing no versions), and both write through Node A. With a plain version vector, Node A stamps the first write [A=1] and the second [A=2], and [A=2] looks like a descendant of [A=1], so the second write silently replaces the first even though its client never saw it. Dotted version vectors record each write's identity as a dot: the first write is (A,1) and the second is (A,2), and both carry the same context (the empty history the clients read). Because neither context includes the other's dot, the two writes are recognized as concurrent and are kept as siblings for the application to reconcile.
>>>>

Riak's dotted version vectors reduced sibling explosion by 60-80% in production workloads compared to standard version vectors. The primary benefit was for workloads where a single node processed multiple writes to the same key without immediate synchronization, a common pattern in write-intensive applications.
====
Riak's documentation describes dotted version vectors as the fix for both lost updates and sibling explosion in workloads where many clients write the same key through the same node, and Riak turned them on by default for bucket types in version 2.0.

DynamoDB uses vector clocks (version numbers) for conflict detection in its DynamoDB Accelerator (DAX) and global tables features. DynamoDB's implementation is simplified compared to the Dynamo paper: each item has a version number that increments on every write. However, DynamoDB uses last-writer-wins for cross-region replication, so vector clock conflict detection is only exposed through the DynamoDB Streams API.
====
The DynamoDB service does not expose vector clocks. It differs from the Dynamo paper: within a region, writes go through a single leader per partition, and applications get optimistic concurrency with conditional writes and a version attribute that they maintain themselves. Global tables replicate between regions and resolve concurrent writes to the same item with last-writer-wins based on timestamps, so conflicting updates are not surfaced for reconciliation.

Apache CouchDB uses a variant of vector clocks called "revision trees" for document versioning. Each document has a revision history that tracks which nodes have modified it. The revision tree is a tree structure where each branch represents an independent edit path.
====
Apache CouchDB does not use vector clocks. It tracks document history with revision trees: each revision has an ID (a counter plus a hash) and points to its parent, and a document's revision tree is a tree whose branches represent independent edit paths. A branch that has been updated concurrently on two nodes shows up as a conflict that the application must resolve. This solves a similar problem to vector clocks, but it records the history of revisions rather than per-node counters.

Vector clocks are fundamental to collaborative editing systems like Google Docs, Notion, and Figma. These systems use operation transformation (OT) or CRDTs to merge concurrent edits from multiple users.
====
Collaborative editing systems need to merge concurrent edits from multiple users, and the underlying ideas overlap with vector clocks. The main approaches are operational transformation (OT) and CRDTs, and different products make different choices.
>>>>
<<<<
Google Docs uses operational transformation (OT), which relies on a form of vector clock called a "state vector" or "version vector." Each collaborator has a vector tracking the number of operations they have received from each other collaborator. When a user makes an edit, the system checks if any remote operations have arrived since the user last synchronized. If so, the local operation is transformed against the remote operations before being applied.
====
Google Docs is built on operational transformation (OT) with a central server that gives operations a single order. In OT systems, an operation is transformed against the concurrent operations that arrived before it before being applied, and peer-to-peer variants use vector-clock-like structures to know which operations each participant has seen. The centralized server design in Google Docs makes that per-peer bookkeeping largely unnecessary.
>>>>
<<<<
Notion and Figma use CRDTs (specifically, y-crdt and automerge) for real-time collaboration. These libraries implement vector clocks internally to track operation ordering and detect concurrent edits. The CRDT provides automatic conflict resolution for common data types like text, lists, and maps.
====
Products differ in how they do this. Figma has described a server-authoritative multiplayer design that borrows ideas from CRDTs but is not a general-purpose CRDT library (the server resolves conflicts per property). Open-source libraries such as Yjs and Automerge implement CRDTs for text, lists, and maps and track per-client counters (state vectors) to know what each replica has seen, which is the vector-clock-like part. The CRDT provides automatic conflict resolution for common data types.
