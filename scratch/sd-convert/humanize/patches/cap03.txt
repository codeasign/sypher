This is a CP system: consistency is maintained through synchronous replication. During a partition, the primary stops accepting writes if it cannot reach a quorum of replicas.
====
Configured with synchronous replication, this is a CP-leaning system: consistency is maintained by waiting for replica acknowledgments (for example `ANY 1` in `synchronous_standby_names`). During a partition, the primary stops committing writes if it cannot reach enough synchronous replicas. With PostgreSQL's default asynchronous replication, it favors availability instead, at the risk of losing recent writes on failover.
>>>>
<<<<
A message queue like Kafka or RabbitMQ is typically configured as AP. Messages must be available for consumption even during partitions. The queue sacrifices ordering guarantees for availability.

Producers write to any partition leader. Consumers read from any partition. During a partition, messages may be duplicated or delivered out of order. Consumers must handle this through idempotency.
====
A message queue like Kafka or RabbitMQ can be configured either way. Kafka with `acks=all`, `min.insync.replicas=2`, and unclean leader election disabled favors consistency: producers get errors instead of losing acknowledged messages when too few replicas are reachable. Kafka with `acks=1` and unclean leader election enabled favors availability: writes keep succeeding, but acknowledged messages can be lost on failover. Log ingestion and analytics pipelines often choose the availability side.

Producers write to the leader of each partition, and consumers read from it. Around failures and retries, messages may be duplicated, and ordering is guaranteed only within a partition. Consumers must handle duplicates through idempotency.
>>>>

A write in us-east-1 may take 1-3 seconds to propagate to eu-west-1.
====
A write in us-east-1 typically reaches eu-west-1 in about a second, and concurrent writes to the same item in different regions are resolved with last-writer-wins.

<<<<
For AP systems, the rolling deploy is simpler. Any number of nodes can be down simultaneously (within reason). Deploy all nodes at once using a blue-green pattern: spin up a new cluster alongside the old one, switch traffic, tear down the old cluster.
====
For AP systems, the rolling deploy is simpler. Several nodes can be down at the same time as long as the replication factor and consistency level still let requests succeed. Replacing a stateful cluster wholesale with a blue-green switch would need a full data copy, so it is rarely the right choice for databases.
>>>>
<<<<
Major version upgrades require a cluster-wide upgrade. For CP systems, this means taking down the old cluster and bringing up the new one. Plan for downtime. Use tools like ZooKeeper's rolling upgrade feature when available.
====
Major version upgrades need planning. Most CP systems, such as ZooKeeper and etcd, support rolling upgrades one node at a time while the remaining nodes keep the quorum. Read the release notes for version-skew limits and take a backup first.
