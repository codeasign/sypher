<<<<
Detection (2-5 seconds via health check), DNS record update (30-60 seconds for TTL-based DNS, or instant if using Route 53 health checks), connection pool reconfiguration (1-2 seconds), application connection retries (1-5 seconds depending on backoff strategy). Total with standard DNS: 34-72 seconds, potentially exceeding the budget. Solution: use a connection pooler (PgBouncer) that detects failover and reconnects immediately, bypassing DNS. Or use RDS Proxy, which has sub-second failover detection.
====
The steps are: failure detection by RDS, promotion of the standby, an update of the endpoint's DNS record, and reconnection by the application (which may be holding cached DNS entries and dead connections). A classic Multi-AZ instance failover typically takes 60-120 seconds in total, which exceeds the 30-second budget. Multi-AZ DB clusters (with two readable standbys) usually fail over in about 35 seconds or less, which is close. Ways to get under the budget: use a Multi-AZ DB cluster, use RDS Proxy (it keeps application connections open and routes to the new primary, which AWS says reduces failover time substantially), keep DNS caching short in the application and drivers, and use aggressive but backed-off connection retries. Then measure a real failover, because the numbers above vary by engine, instance size, and load.

Note that in practice, services in this space often keep metadata in a strongly consistent sharded store with the server as the authority, and devices sync through a change log. Discussing both and choosing between them is part of a strong answer.

*Model answer key:* Use Redis with CRDT-based replication (active-active geo-distribution) for the real-time scores. Shard by score range or player ID. Use a write-behind cache pattern: players write to Redis, Redis appends to a WAL-like log, and a background process periodically persists to the durable database. Each shard has its own leader to distribute write load. Leaderboard reads hit the Redis replicas (sub-millisecond latency). Strong consistency is achieved by routing a player's score read to the same shard and leader that handles their writes.
====
*Model answer key:* Keep the live leaderboard in Redis sorted sets, which support score updates and rank lookups in O(log n). 50,000 updates per second is within reach of a single Redis primary, and separate leaderboards (per game mode or season) can be spread across primaries. If one board must be split, sharding by score range preserves the global order, while sharding by player ID forces a scatter-gather merge to compute ranks. Persist match results to a durable database through a queue (write-behind), and rebuild the sorted set from it if a primary is lost, because asynchronous Redis replication can lose the last few writes on failover. Serve top-N reads from replicas, where slightly stale results are fine. For strong consistency on a player's own rank, read it from the primary. Avoid CRDT-based active-active replication here: it is eventually consistent, which conflicts with the requirement.
