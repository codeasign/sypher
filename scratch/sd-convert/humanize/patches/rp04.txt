<<<<
Write with `W=ALL` for CP behavior. Write with `W=ONE` for AP behavior.
====
Write with `W=ALL` (or QUORUM on both reads and writes) for behavior closer to CP. Write with `W=ONE` for AP behavior.
>>>>
<<<<
In PostgreSQL, `max_standby_streaming_delay` allows the query to complete, but the WAL applier queues up behind it.
====
In PostgreSQL, when `max_standby_streaming_delay` is set high (or to -1), the replica lets the query finish before replaying conflicting WAL, so the applier queues up behind it. (With the default of 30 seconds, PostgreSQL cancels the query instead.)
>>>>
<<<<
The old primary must be destroyed and rebuilt as a replica. Never rejoin a node that was a primary during a failover without a full rebuild.
====
The old primary must be rebuilt as a replica, either by a full re-clone or, in PostgreSQL, with `pg_rewind`, which discards the old primary's divergent writes. Never rejoin a node that was a primary during a failover as-is.
>>>>
<<<<
Write latency goes from 1 ms to 300 ms. The application's throughput drops by 90%.
====
Write latency goes from 1 ms to 200-300 ms. The throughput of each connection drops by two orders of magnitude, and the application needs far more connections to compensate.
>>>>
<<<<
When the report runs, WAL replay blocks. The primary stops acknowledging writes.
====
When the report runs, the replica slows down and falls behind. If the replica must confirm each write before the primary can commit (for example with `synchronous_commit = remote_apply`, or simply because it is overloaded), the primary stops acknowledging writes.
