### Key Design Decisions

**The data is small enough to replicate everywhere.** Configuration for millions of zones is measured in gigabytes, not petabytes, so every server can hold a complete copy.

**Reads dominate and writes are rare.** Zone changes are infrequent compared with queries. A read-mostly, slowly changing dataset is the best case for replication.

**Local reads beat network reads.** Serving from local storage removes the network from the read path, which matters when a query must be answered in milliseconds.

### Lessons Learned

**Sharding solves a data-volume or write-throughput problem.** If your dataset fits on one machine and reads dominate, replication or caching is simpler and faster than sharding, and it avoids cross-shard queries and rebalancing entirely.

**Check the numbers first.** Estimate data size, write rate, and read rate before choosing an approach. Many "we need to shard" conversations end at "we need a replica and a cache."
