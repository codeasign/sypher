### GitHub: A Failover That Went Wrong (October 2018)

GitHub's October 2018 incident is one of the best-documented replication failures. It shows how automated failover can turn a very short network problem into a day-long incident.

**The architecture:** GitHub ran MySQL with a primary in one US data center and replicas in another, managed by an automated failover tool (Orchestrator). Replication between data centers was asynchronous.

**What happened:** On October 21, 2018, routine maintenance briefly severed connectivity between the two data centers for about 43 seconds. During that window Orchestrator promoted new primaries in the other data center. When connectivity returned, the original data center held a small number of writes that had never been replicated, and the new primaries held writes of their own. The two sides had diverged.

**The impact:** Because the data sets had diverged, GitHub could not simply fail back. It took its data stores out of service to reconcile them, and the service ran in a degraded state for more than 24 hours. GitHub's post-incident analysis describes the timeline and what changed afterward.

**Lessons:** Asynchronous cross-region replication means a failover can lose or fork writes. Failover automation needs to account for short partitions, not only real failures. Recovery from divergence is slow and manual, so it is worth preventing.

**Public reference:** GitHub Engineering, "October 21 post-incident analysis" (2018).

### Cloudflare: Replicated Storage for Durable Objects

Cloudflare's Durable Objects provide strongly consistent storage close to where users are, and they show replication used for durability rather than for read scaling.

**The architecture:** Each Durable Object is a single-threaded instance that processes requests one at a time and owns its own storage. All requests for that object are routed to one location, so there is no need for replicas to serve reads. Storage writes are replicated to other machines in nearby data centers, and Cloudflare has described waiting for a quorum of those copies before the write is considered durable.

**The replication challenge:** Replication delays grow with distance, so the copies are kept within a region rather than spread worldwide. Waiting for a nearby quorum keeps the added write latency to a few milliseconds, and the single-location design provides strong consistency for reads.

**Public reference:** Cloudflare Blog posts on Durable Objects and on the storage engine behind them.
