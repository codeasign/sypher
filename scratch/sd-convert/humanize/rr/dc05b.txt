### Facebook TAO: Counts Stored with the Data

Facebook's TAO, the graph store described in its 2013 paper, keeps counts of associations (for example, the number of likes on a post or comments on an object) as a first-class operation. Rather than counting rows on every read, TAO maintains the count alongside the association list.

**Architecture**: Data is sharded by object ID, and the associations of an object live on the same shard as the object. Because the count and the list are stored together, adding an association updates the list and the count in one operation on one shard, so there is no cross-shard coordination and no read-modify-write race across machines. A large cache tier in front of the database serves the counts and absorbs read traffic, and invalidations keep the caches fresh.

**Trade-off**: Keeping the count next to the data makes reads cheap and writes simple, but all updates to one object's count go through one shard, so very popular objects concentrate load on it. Caching and read replicas help with reads, and write hot spots remain a concern.

**Public reference**: "TAO: Facebook's Distributed Data Store for the Social Graph" (USENIX ATC 2013).

### Metrics Pipelines: The Two-Layer Counter in Practice

The two-layer design (a local buffer plus a global aggregator) is the standard shape of metrics systems. A StatsD-style agent, for example, keeps counters in memory on each host and flushes the accumulated totals to a central service on an interval (10 seconds by default). Instead of sending one network message per event, each host sends one message per interval per counter. (The details in the diagram below are an illustrative example of this design.)

**Architecture**: Each application server buffers increments locally and flushes them in batches to a shared aggregator, such as a Redis cluster or a metrics backend. The batch size and interval control how much Redis write load is saved: a server that handles 500 increments per flush interval sends one command instead of 500.

**Trade-off**: Data loss on application server crash. Each server's unflushed buffer is lost if the server dies. That is acceptable when the counter is a real-time estimate and the system of record (a trip database, billing events, logs) persists the underlying events separately.
