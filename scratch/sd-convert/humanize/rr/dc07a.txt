**Counter structure**: Redis Sorted Set. Key = `leaderboard:game_id`. Member = `player_id`. Score = `current_score`. Each score change is `ZINCRBY leaderboard:game_id <delta> <player_id>`. Redis Sorted Sets use a skip list internally, giving O(log N) for ZINCRBY and O(log N + K) for reading a range.

**Top-100 reads**: `ZREVRANGE leaderboard:game_id 0 99 WITHSCORES`. This is O(log N + K) where K = 100. For 1 million players, each read is roughly 20 skip-list steps plus 100 results, so it completes in well under 1ms.

**Write throughput**: With 1 million concurrent players generating 3 score updates per second each, the raw load is 3,000,000 writes per second. A single Redis instance handles on the order of 50,000 to 100,000 commands per second, so one sorted set cannot take that load. Two ideas fix it:

1. **Batch on the game servers.** Each game server accumulates the deltas for its players and flushes once per second, so a player's 3 updates become one `ZINCRBY` with the summed delta. That cuts the load to about 1,000,000 commands per second, and pipelining lowers the per-command cost further. At 60% utilization of a 50,000 ops/sec shard (30,000 per shard), that needs about 34 shards, so plan on 36.

2. **Shard the leaderboard by player and merge the tops.** Split players across K sorted sets by `hash(player_id) % K`. Each shard keeps its own sorted set, so writes scale with K. To build the global top 100, read the top 100 from every shard and merge those K x 100 entries. This is exact: any player in the global top 100 must be in the top 100 of their own shard. A small service repeats the merge every 500ms and publishes the result, which meets the 2-second SLA (up to 1 second of batching plus 500ms of merging).

**Burst handling**: A burst of 10 score updates in 100ms for the same player. With local batching, the game server accumulates all 10 updates in the buffer and flushes a single ZINCRBY with the sum (100 points) instead of 10 individual commands. This is both correct (the order of updates within a flush window does not matter for the total score) and efficient (1 Redis command instead of 10).

**Evaluation**: Identifies sorted set as the data structure = 1 point. Recognizes the single-shard bottleneck = 2 points. Proposes batching or sharding with a top-K merge = 2 points.
