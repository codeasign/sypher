### Case Study 5: Two Older Designs: Flickr Ticket Servers and MongoDB ObjectId

**Flickr ticket servers**: Flickr's 2010 engineering post, "Ticket Servers: Distributed Unique Primary Keys on the Cheap," describes a deliberately simple design. Two MySQL servers act as ticket servers. Each has a table with a single auto-increment column, and the servers are configured so that one hands out odd numbers and the other even numbers (`auto_increment_increment = 2` with different offsets). An application gets an ID by running `REPLACE INTO Tickets64 (stub) VALUES ('a')` and then reading `LAST_INSERT_ID()`. Clients alternate between the two servers, so if one fails the other keeps issuing IDs. The design works because the number of IDs Flickr needed per second was modest, and it needs no clocks. Its limits are the network hop for every ID, and that IDs are only roughly time-ordered.

**MongoDB ObjectId**: A MongoDB ObjectId is 12 bytes: a 4-byte timestamp (in seconds), a 5-byte random value that is fixed per process, and a 3-byte counter that starts at a random value and increments. Each client process can generate IDs with no coordination and no worker ID assignment. The timestamp makes ObjectIds roughly sortable by creation time. The design trades a larger ID (96 bits) for removing the need for any registry of workers.

**Lesson**: Distributed IDs are a spectrum of trade-offs among size, coordination, ordering, and throughput. Flickr chose coordination with a small central service. MongoDB chose randomness plus a counter. Twitter and Instagram chose structured 64-bit IDs.
