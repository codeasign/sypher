## Case Study 1: Discord: From MongoDB to Cassandra Partitioning

### The Problem

Discord launched in 2015 on a single MongoDB replica set for message storage. As the platform grew, the data and its indexes stopped fitting in memory. Reads of older messages became random disk reads, latency turned unpredictable, and it was clear that adding RAM would only delay the problem. Discord's engineering blog ("How Discord Stores Billions of Messages", 2017) describes the move to Cassandra.

Discord evaluated several options. A relational database was a poor fit for an ever-growing message log, and Cassandra offered linear scaling, replication, and a data model built around partitions. They chose Cassandra.

### The Architecture

Discord partitions messages by channel and a time bucket. Every message belongs to a channel, and the dominant query is "show recent messages in this channel." The partition key is `(channel_id, bucket)`, where the bucket is a fixed window of time, and messages within a partition are ordered by message ID (a time-sortable Snowflake ID). Cassandra's partitioner hashes the partition key to place it on the ring.
