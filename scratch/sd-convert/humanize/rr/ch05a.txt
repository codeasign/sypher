### Case Study 1: Discord: From MongoDB to Cassandra to ScyllaDB

Discord started with a single MongoDB replica set for message storage. As the platform grew, MongoDB could not keep the data and indexes in memory, and the team moved message storage to Cassandra around 2016 to 2017, as described in Discord's engineering blog. Cassandra distributes data using a consistent hash ring with virtual nodes.

Discord partitions messages by `(channel_id, bucket)`, where the bucket is a window of time, so that a channel's recent history sits in one partition and no partition grows without bound. Cassandra hashes that partition key onto the ring and places it on the nodes that own that token range. Because placement depends only on the ring, adding a node moves a small share of the data and the rest of the cluster carries on.

As the cluster grew to hundreds of nodes, Discord found operations harder: garbage-collection pauses, compaction, and hot partitions made latency unpredictable. In 2022 it began migrating message storage to ScyllaDB, a Cassandra-compatible database written in C++, and reported that the same data needed far fewer nodes. Its later blog post describes putting a Rust data service in front of the database that coalesces identical concurrent requests, which protects the ring from hot keys that consistent hashing alone cannot spread.

**The lesson**: Consistent hashing gives you cheap scaling, but it does not fix uneven access. You still need a good partition key and protection for hot keys.

**Public references**: Discord Engineering Blog, "How Discord Stores Billions of Messages" (2017) and "How Discord Stores Trillions of Messages" (2023).

### Case Study 2: Netflix: EVCache, Consistent Hashing Inside a Global Cache

Netflix's caching layer is EVCache, a distributed in-memory store built on Memcached with a Java client library. Netflix's engineering blog describes how data is replicated across availability zones and regions, so that each zone holds a full copy of the cached data and reads can be served from the local zone.

Within a zone, the client library spreads keys across the Memcached nodes with consistent hashing, so adding or removing a node moves only a fraction of the keys. Service discovery tells each client which nodes currently exist.

A useful operational point from running caches like this: when nodes in one cluster have different sizes, giving every node the same number of virtual nodes leaves the larger nodes underused, so virtual nodes should be weighted by capacity. Another is warm-up: a new node joins with an empty cache, so cache-heavy systems either pre-load new nodes from their neighbors or accept a short burst of extra misses.

**Public reference**: Netflix Tech Blog, "Caching for a Global Netflix" (2016).

### Case Study 3: Cloudflare: A Load Balancer Built on the Same Idea

Cloudflare's Unimog, a layer 4 load balancer that runs on every server in its data centers, needs to spread connections across many servers, change which servers take traffic as they get busy or are drained, and keep existing connections on the server they started on. Cloudflare's engineering blog describes the design, which is closely related to consistent hashing and to Google's Maglev load balancer.

Connections are hashed into a fixed number of buckets. A table maps each bucket to a server, and changing the table moves only the buckets that need to move, so most connections are unaffected when a server is added or removed. This keeps disruption low for long-lived TCP connections: if a server change caused most connections to land on a different server, clients would see resets and reconnect storms at the origin.

**The lesson**: The value of consistent hashing is not just balanced data placement. Any place where a mapping from keys to servers must stay stable while the server set changes benefits from it, including load balancers.

**Public reference**: Cloudflare Blog, "Unimog: Cloudflare's edge load balancer" (2020).
