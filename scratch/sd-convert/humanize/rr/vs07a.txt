**Model answer**: "The visible symptom is the connection pool: all 50 connections are busy and new requests queue, which is why P99 is 850ms. But the pool is not the root cause. CPU is at 75% across all 16 cores, and queueing starts well before 100% utilization, so the database and application are CPU-bound. Fifty active queries on 16 cores means the queries are competing for CPU, and each one runs slower as a result. By Little's law, a pool of 50 connections can only sustain 5,000 requests per second if the average query takes about 10ms (50 / 5,000). So the real question is why queries take longer than that. I would check `pg_stat_statements` for the slowest and most frequent queries and look at their plans for missing indexes. Raising the pool to 200 would make things worse, because more concurrent queries on the same 16 cores means more context switching and contention. The change with the largest payoff is reducing CPU per query (index or query fixes). If that is not enough, the next step is more vCPU: move the database to its own instance or to a larger size. Memory at 28 of 32 GB is also close to the limit, so any upgrade should add RAM alongside CPU."
