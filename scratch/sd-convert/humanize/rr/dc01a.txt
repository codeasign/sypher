### Step 8: Reconciliation During Partition Healing

When a network partition heals (say, two Redis slots of the same counter were isolated from each other for 2 seconds), the replicas exchange their state. Each replica kept incrementing its own contribution while isolated. Slot 7 received 4,200 increments and slot 8 received 3,800. Because each slot owns its own element and increments are commutative (A+1+2 equals A+2+1), the merge cannot lose or double-count anything.

```
Before the partition:
  slot 7: 142,000     slot 8: 138,000
During the partition:
  slot 7 receives +4,200 -> 146,200
  slot 8 receives +3,800 -> 141,800
After the merge, every replica holds both elements:
  [slot 7: 146,200, slot 8: 141,800]
  Total: 146,200 + 141,800 = 288,000
```

The merge is lossless because each node's contribution is an independent vector element, and the merge takes the element-wise maximum (for a G-Counter) or the element-wise maximum of two G-Counters (for a PN-Counter), never a simple overwrite of the whole state.

### Step 9: Keeping Counter State Small (PN-Counter)

A PN-Counter stores its decrements in a separate grow-only counter. There are no per-operation tombstones: the state is one number per node for the positive side and one per node for the negative side, so it grows with the number of distinct node IDs, not with the number of increments.

The growth risk comes from IDs that come and go. If every autoscaled application instance gets a fresh ID, the vectors gain a permanent entry each time an instance starts. Two mitigations keep the state bounded:

- Use stable slot or shard IDs (for example slots 0 to 63) rather than ephemeral instance IDs, so the vector has a fixed size.
- If you must retire node IDs, fold their contributions into a single base value once every replica is known to have seen them. This compaction needs coordination, because zeroing an entry that some replica has not yet merged would change the total.

```
Positive: [slot 0: 482,000, slot 1: 310,000]
Negative: [slot 0: 12,000,  slot 1: 14,000]
Total: (482,000 + 310,000) - (12,000 + 14,000) = 766,000
```

A real-time display counter is still usually an estimate. The authoritative total (for billing, for example) is typically computed from an event log in a data warehouse.
