### Discord: From a Single MongoDB Replica Set to Cassandra and ScyllaDB (2015-2023)

Discord started with a single MongoDB replica set for message storage, as described in their engineering blog posts "How Discord Stores Billions of Messages" (2017) and its 2023 follow-up on trillions of messages.

**What they did**: Discord launched on MongoDB because it was quick to build with. As message volume grew, the data and indexes no longer fit in memory. Reads for old messages turned into random disk reads, latency became unpredictable, and the team could see that a single replica set would not keep up. Adding RAM or a bigger machine would only delay the problem.

**The vertical scaling ceiling**: A chat history is append-only, so the total data only grows. Once the working set (the messages people actually scroll back to) is larger than the memory of the biggest practical machine, more hardware cannot restore cache hit rates. The database had to become distributed.

**The transition**: Discord moved message storage to Apache Cassandra, partitioning messages by channel and time bucket so one channel's recent history sits together. Years later, after hot partitions and garbage-collection pauses became a maintenance burden at a scale of hundreds of nodes, they migrated again to ScyllaDB, which needed far fewer nodes for the same data.

**Lesson**: Discord hit the vertical scaling ceiling because their data was append-only and unbounded. Any system with unbounded storage growth will eventually exceed the largest machine. There is no vertical scaling solution for unbounded data; only data retention limits or horizontal partitioning can solve it. The second lesson is that the choice of partition key (channel plus time bucket) mattered as much as the choice of database.

### Cloudflare: Big Nodes, Many of Them

Cloudflare serves tens of millions of HTTP requests per second across data centers in hundreds of cities. Its engineering blog shows an architecture that pairs high-end individual servers with wide horizontal spread.

**What they do**: Each data center (PoP) contains many servers, and every server runs the same software stack. A layer 4 load balancer called Unimog spreads incoming connections across the servers in a PoP based on their current load. Adding capacity means adding another server, and losing a server just shifts its traffic to the others.

**Why big nodes still matter**: Cloudflare designs its own server generations around modern many-core CPUs, and much of its performance work targets making one machine do more: efficient kernel networking paths, careful cache and NUMA use, and per-core tuning. Vertical efficiency lowers the number of servers they need. It does not replace having many.

**Where it breaks**: No single server can absorb a PoP's traffic, and no single PoP can serve the world. Capacity comes from horizontal scaling at two levels: many servers per PoP and many PoPs.

**Lesson**: Cloudflare is not a case of "vertical scaling at massive scale". It is the hybrid that most large systems end up with: make each node as capable as you economically can, and scale out across nodes and locations for capacity and fault tolerance.

### Uber: Splitting One Database by Data Characteristics (2014-2016)

Uber began with a monolithic application backed by a single PostgreSQL database. As Uber expanded to many cities, the monolith and its database became a scaling and reliability constraint.

**What they did**: One database held trip, driver, and payment data, so every workload competed for the same machine. Analytical queries and live trip writes fought over the same resources.

**The transition**: Uber broke the monolith into services and gave the heavy data stores purpose-built homes. For trip data it built Schemaless, an append-only, sharded datastore layered on MySQL, and it used Cassandra for some other workloads. In 2016 it published why it moved its main relational workload from PostgreSQL to MySQL, citing write amplification and replication behavior at its scale. Smaller, bounded datasets stayed on single relational instances.

**Lesson**: Uber's migration shows that vertical scaling is not binary: you can vertically scale some services while horizontally scaling others. Trip history needed unbounded storage (horizontal). Small relational data with transactional requirements did not (vertical). Different data characteristics call for different scaling strategies.
