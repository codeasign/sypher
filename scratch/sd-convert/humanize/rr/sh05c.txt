### Key Design Decisions

**Shard by row key, with a fixed number of shards.** Hashing the row key spreads trips evenly across shards. Choosing a large fixed shard count up front means that adding capacity moves whole shards to new hosts rather than re-hashing rows.

**Append-only storage.** Instead of updating a record in place, Schemaless writes new versions of a cell. That keeps writes cheap and makes replication and recovery simpler.

**Migrate with dual writes and verification.** Moving live trip data off PostgreSQL was itself a large project. Uber described writing to both the old and new stores, backfilling historical data, and comparing results on reads before switching over.

**Secondary indexes built asynchronously.** Queries by something other than the row key use an index maintained by background workers. That keeps the write path fast at the cost of indexes that can lag slightly.

### Lessons

The lasting lesson from this migration is the pattern: pick a shard key that matches the main access path, choose many small logical shards, and treat the migration as a project with dual writes and verification, not a one-time cutover.

## Case Study 3: Instagram: Thousands of Logical Shards on a Few Servers

### The Problem

Instagram's early data lived in PostgreSQL, and as the service grew rapidly it needed to distribute that data. Instagram's engineering blog ("Sharding & IDs at Instagram", 2012) describes its approach.

### The Architecture

Instagram created a large number of **logical shards** (thousands), implemented as separate PostgreSQL schemas, and mapped them onto a much smaller number of physical database servers. A lookup determines which logical shard holds a piece of data, and another maps that logical shard to a physical server.

### Key Design Decisions

**Logical shards separate "where data lives" from "which machine holds it."** When a server fills up, a logical shard can be moved to another machine as a unit. The number of logical shards never changes, so no row is ever re-hashed.

**IDs that carry the shard.** Instagram generated 64-bit IDs made of a millisecond timestamp (41 bits), the logical shard ID (13 bits), and a per-shard sequence number (10 bits), generated inside PostgreSQL. The ID both sorts roughly by time and tells you which shard holds the row.

### Lessons Learned

**Plan for more logical shards than you need today.** Splitting or merging shards later is painful. Starting with thousands of logical shards on a handful of servers made growth mostly a matter of moving them.

**Keep related data together.** Because a user's data is placed on one logical shard, most queries touch only one shard.

## Case Study 4: Cloudflare: When Replicating Beats Sharding

### The Problem

Cloudflare has a very large amount of configuration data (such as DNS zones and customer settings) that must be available with very low latency on servers in hundreds of cities. It is a natural question whether this data should be sharded.

### The Architecture

Cloudflare took the opposite approach: instead of sharding the data, it replicates all of it. Its **Quicksilver** system distributes configuration to every server, and each server keeps a full local copy in an embedded key-value store, so lookups never leave the machine.
