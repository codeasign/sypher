### Case Study 4: Uber: Ringpop for Sharded Service Communication

Uber built Ringpop, an open-source library that gives a cluster of application servers a shared consistent hash ring. Ringpop uses the SWIM gossip protocol for failure detection and membership, combined with a consistent hash ring for request routing.

Each service instance joins the ring, and Ringpop keeps every member's view of the ring up to date. A request for a given key can arrive at any instance, and that instance can compute which instance owns the key and forward the request there. The ring uses a number of replica points per member (100 in the reference implementation) to smooth the distribution.

SWIM detects failures without a central coordinator. Members periodically ping each other. If a ping fails, the member asks a few other members to probe the suspect indirectly before declaring it dead, and a suspicion period lets a slow but healthy member refute the accusation. This reduces false positives from transient network problems.

The lesson from Ringpop: consistent hashing is not just for data storage. Any pool of interchangeable service instances that needs key-affine routing (the same key always goes to the same instance, for caching or in-memory state) can use a ring with minimal rebalancing.

**Public reference**: Uber Engineering Blog, "Ringpop" (2015) and the Ringpop project documentation.

### Case Study 5: Amazon Dynamo and DynamoDB

The 2007 Dynamo paper is the origin of many production uses of consistent hashing. Its design has these key pieces:

- **Consistent hashing with virtual nodes**: Each key is hashed onto a ring, and each physical node owns many virtual positions.
- **A preference list**: A key is stored on the N nodes that follow its position on the ring (N is typically 3), skipping positions that belong to the same physical node.
- **Sloppy quorum and hinted handoff**: If a target replica is down, another node accepts the write and hands it back when the replica recovers.
- **Gossip membership and anti-entropy**: Nodes learn about the ring through gossip, and Merkle trees let replicas find and repair differences efficiently.

Cassandra and Riak took direct inspiration from this design. The managed DynamoDB service that AWS runs today is a different system, built on the same goals but with a different architecture. Its 2022 paper describes tables split into partitions by hashing the partition key. Partitions split as they grow, and each partition is replicated across three availability zones using a leader-based protocol.

**Public references**: "Dynamo: Amazon's Highly Available Key-value Store" (SOSP 2007); "Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service" (USENIX ATC 2022).
