**Why**: CRDT counter entries are never removed on their own. Each distinct node ID that ever incremented or decremented a counter leaves an entry behind. The size of the state depends on the number of IDs, not on the number of operations, so a busy counter with 64 stable slots stays small, while a counter touched by thousands of short-lived instance IDs grows steadily.

**Blast radius**: Gradual. Memory usage increases by approximately 100 MB per day (assuming 100M counters and uniform distribution). The impact is on RAM cost and cache efficiency, not correctness.

**Recovery**: (1) Use stable slot or shard IDs instead of ephemeral instance IDs, so the vector has a fixed size. (2) Compact retired IDs into a base value, but only after every replica is known to have merged them, because compacting earlier changes the total. (3) Use bucketed counters that roll over daily (counters are stored with a date prefix: `post:abc123:2026-07-01`). (4) For long-lived counters, archive old data to a data warehouse and reset the active counter to the archived total plus recent delta.
