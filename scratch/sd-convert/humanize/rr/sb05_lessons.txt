### Key Lessons

**A shared mount is not a lock.** NFS is a network file protocol. It provides no built-in fencing or lease mechanism for the active-passive pattern. Multiple clients can mount the same share read-write, and the filesystem itself does nothing to stop two of them from writing conflicting data.

**Shared storage does not prevent split brain.** A common assumption is that putting the data on one shared volume removes split brain because there is only one copy. In reality the shared volume simply becomes the place where two writers collide, and it can corrupt files that no replication protocol could have reconciled.

**Fence before takeover.** The standby must not mount the volume read-write until the original server is confirmed to be unable to write (powered off, disconnected from storage, or blocked with storage-level reservations). Fencing is what turns "the active seems dead" into "the active is dead".

**Recovery procedures need testing at production scale.** Recovery from this kind of incident typically means choosing an authoritative copy, restoring from backup, and reconciling records by hand. Runbooks that delete or overwrite data must be tested against realistic volumes and must check what they are deleting.

**A real-world reference:** In October 2018, GitHub described a network partition of about 43 seconds between its US East Coast network hub and its primary East Coast data center. Its automated MySQL failover tooling promoted primaries in a different region while the original primaries still held recent writes that had not replicated. When connectivity returned, the two sides had diverged. GitHub chose to preserve data integrity over speed, so it degraded service for just over 24 hours while it restored from backups and reconciled the diverged writes. Its public post-incident report is worth reading in full: it shows how automated failover, cross-region topology, and asynchronous replication interact.
