Anchor tagged the current open backlog by category: 34 dependency upgrade tickets, 41 test gap tickets, 22 architecture tickets, 15 documentation tickets.

| Category | Count | Share |
| --- | --- | --- |
| Dependency upgrades | 34 | 30.4% |
| Test gaps | 41 | 36.6% |
| Architecture | 22 | 19.6% |
| Documentation | 15 | 13.4% |

![Donut chart of Anchor debt backlog split across dependency upgrades, test gaps, architecture, and documentation](https://syhpher-next-datastore-gvaf.b-cdn.net/svgs/measuring-technical-debt/debt-by-category.svg)

*Shown as a donut chart because this is composition, how the whole open backlog splits by category.*

Test gaps is the largest slice at 36.6%. That matters for planning: test gaps are usually cheaper to close incrementally (add a test alongside the next PR that touches that code) than architecture debt, which often needs dedicated project time.

A category breakdown like this is what turns "we have a lot of debt" into a plan. Dependency upgrades can often be batched and mostly automated. Architecture debt cannot be squeezed into spare sprint capacity the same way, it needs to be scheduled like a project.

**TRY IT**

**1. Test gaps are the largest category by count, but architecture debt is only 22 tickets. Does that mean architecture debt is the lower priority?**

**Suggested answer:** Not necessarily, ticket count does not equal effort or risk. A single architecture ticket can represent months of work and carry far more risk than dozens of small test-gap tickets. Category share tells you where volume sits, not where the most consequential work sits; you would need effort or risk estimates per ticket to answer the priority question properly.
