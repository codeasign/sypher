Cyclomatic complexity counts the number of independent paths through a function or file, roughly, how many different ways execution can branch. Higher numbers mean more paths to reason about and more places for a bug to hide.

| File | ledger.py | session.py | invoice.py | reconcile.py | webhooks.py | export.py |
| --- | --- | --- | --- | --- | --- | --- |
| Complexity | 42 | 38 | 31 | 27 | 24 | 19 |

payments/ledger.py scores 42, the highest in the codebase, more than double the lowest-scoring file at 19.

![Bar chart comparing cyclomatic complexity scores across six Ledger files](https://syhpher-next-datastore-gvaf.b-cdn.net/svgs/measuring-code-quality/complexity-hotspots.svg)

*Shown as a bar chart because the point is comparing six files against each other to find the worst offenders, not a trend.*

A complexity score is not automatically a problem. Some domains are inherently branchy. But payments/ledger.py sitting at the top of this list, in a payments-adjacent module, in a fintech codebase, is exactly the kind of file that deserves deliberate refactoring attention before its complexity causes a bug that is expensive to find.

**TRY IT**

**1. Should Ledger set a hard complexity limit and block any PR that exceeds it?**

**Suggested answer:** A hard limit risks blocking legitimate, necessarily branchy business logic (tax rules, currency conversion edge cases) while missing that complexity concentrated in a critical file matters more than complexity spread evenly. A better approach: flag files above a threshold for review priority, not automatic rejection, and weight the review by how critical the file is, not just its raw score.
