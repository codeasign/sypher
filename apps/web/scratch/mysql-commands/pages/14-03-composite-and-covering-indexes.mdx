An index can cover **several columns**. Such a *composite* index is powerful, but it follows one strict rule about which queries can use it: the **leftmost prefix**. Understanding this rule is worth more interview points than almost anything else about indexes.

## What you'll learn

- Creating a composite index
- The leftmost-prefix rule
- Covering indexes
- Choosing the column order

## Syntax

```sql
CREATE INDEX index_name ON table_name (column_a, column_b, column_c);
```

## Set up

A copy of `payment` with no indexes, then one composite index on `(customer_id, payment_date)`:

```sql
CREATE TABLE payment_plain AS SELECT * FROM payment;

CREATE INDEX idx_customer_date ON payment_plain (customer_id, payment_date);

SHOW INDEX FROM payment_plain;
```

| Table | Non_unique | Key_name | Seq_in_index | Column_name | Index_type |
|---|---:|---|---:|---|---|
| payment_plain | 1 | idx_customer_date | 1 | customer_id | BTREE |
| payment_plain | 1 | idx_customer_date | 2 | payment_date | BTREE |

*2 rows returned.*

Think of the index as a phone book sorted by **surname, then first name**. It is sorted by `customer_id` first, and within each customer by `payment_date`.

## The leftmost-prefix rule

A composite index can be used by a query that filters on the **first** column, or the first **two**, and so on, but not by one that skips the first column.

### The first column alone: used

```sql
EXPLAIN SELECT * FROM payment_plain WHERE customer_id = 5;
```

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---:|---|---:|---|
| 1 | payment_plain | ref | idx_customer_date | idx_customer_date | 2 | const | 38 | NULL |

*1 row returned.*

### Both columns: used, and better

`key_len` grows because more of the index is used:

```sql
EXPLAIN SELECT * FROM payment_plain
WHERE customer_id = 5 AND payment_date >= '2005-07-01';
```

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---:|---|---:|---|
| 1 | payment_plain | range | idx_customer_date | idx_customer_date | 7 | NULL | 30 | Using index condition |

*1 row returned.*

### The second column alone: not used

You cannot find a first name in a phone book without the surname. Filtering only on `payment_date` cannot use the index:

```sql
EXPLAIN SELECT * FROM payment_plain WHERE payment_date >= '2005-07-01';
```

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---|---|---:|---|
| 1 | payment_plain | ALL | NULL | NULL | NULL | NULL | 16044 | Using where |

*1 row returned.*

`key` is `NULL` and `type` is `ALL`: a full scan.

## Covering indexes

If the index contains **every column the query needs**, MySQL answers from the index and never touches the table:

```sql
EXPLAIN SELECT customer_id, payment_date
FROM payment_plain
WHERE customer_id = 5;
```

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---:|---|---:|---|
| 1 | payment_plain | ref | idx_customer_date | idx_customer_date | 2 | const | 38 | Using index |

*1 row returned.*

`Using index` in `Extra` confirms it. The moment you also select a column that is not in the index (`amount`), MySQL has to go and read the table for it:

```sql
EXPLAIN SELECT customer_id, payment_date, amount
FROM payment_plain
WHERE customer_id = 5;
```

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---:|---|---:|---|
| 1 | payment_plain | ref | idx_customer_date | idx_customer_date | 2 | const | 38 | NULL |

*1 row returned.*

## Sorting for free

An index is already sorted, so it can also avoid a sort. With an equality on the first column, the second column is in order:

```sql
EXPLAIN SELECT payment_id, payment_date
FROM payment_plain
WHERE customer_id = 5
ORDER BY payment_date;
```

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---:|---|---:|---|
| 1 | payment_plain | ref | idx_customer_date | idx_customer_date | 2 | const | 38 | NULL |

*1 row returned.*

There is no `Using filesort` here, because the rows come out of the index already sorted.

## Choosing the column order

A good rule of thumb for the order of columns in a composite index:

1. Columns compared with `=` first.
2. Then the column with a range (`>`, `BETWEEN`) or the sort column.
3. Among the equality columns, put the most selective first if you can, but the leftmost-prefix rule (which queries you must support) matters more.

## Try it yourself

Create an index on `(store_id, customer_id)` on a copy of `customer`, and use `EXPLAIN` on queries filtering on `store_id`, on `customer_id`, and on both.

## Watch out

### Column order is not interchangeable

`(a, b)` and `(b, a)` are different indexes that serve different queries. Look at your real queries before deciding.

### A range stops the prefix

Columns **after** a range condition cannot be used to narrow the search. With `WHERE customer_id > 5 AND payment_date >= ...` on this index, only `customer_id` narrows the lookup.

### Do not create an index for every column combination

Each index costs writes and space. One well-chosen composite index usually replaces several single-column ones. An index on `(customer_id)` is redundant once `(customer_id, payment_date)` exists.

### `SELECT *` defeats a covering index

Selecting every column forces a look at the table row. Selecting only what you need lets a covering index shine.

## Interview corner

**"What is the leftmost-prefix rule?"**
A composite index on `(a, b, c)` can serve queries that filter on `a`, on `a, b`, or on `a, b, c`, but not on `b` or `c` alone.

**"What is a covering index?"**
An index that contains all the columns a query needs, so the query is answered from the index without reading the table (`Using index`).

**"How do you decide the order of columns in a composite index?"**
Equality columns first, then range or sort columns, guided by the queries you need to support.

**"Would an index on `(a, b)` help `WHERE b = 1`?"**
No, because `b` is not the leftmost column. You would need an index that starts with `b`.

## Practice

### Warm-up: is it used?

On a copy `rental_plain` of `rental` with an index on `(customer_id, rental_date)`, run `EXPLAIN` for `SELECT * FROM rental_plain WHERE customer_id = 9`. Return the `key` used as part of the `EXPLAIN` output.

**Your result should look like this:**

| id | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---:|---|---|---|---|---:|---|---:|---|
| 1 | rental_plain | ref | idx_cust_date | idx_cust_date | 2 | const | 23 | NULL |

*1 row returned.*

<details>
<summary>Hint</summary>

The filter is on the leftmost column, so the index is used.

</details>

<details>
<summary>Show solution</summary>

```sql
DROP TABLE IF EXISTS rental_plain;
CREATE TABLE rental_plain AS SELECT * FROM rental;
CREATE INDEX idx_cust_date ON rental_plain (customer_id, rental_date);

EXPLAIN SELECT * FROM rental_plain WHERE customer_id = 9;
```

</details>
