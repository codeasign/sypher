Every column has a **data type**, a rule about what it may hold. Choosing the right type keeps bad data out, saves space and speeds up queries. Here are the ones you will actually use, and what happens when you break their rules.

## What you'll learn

- The main numeric, text and date types
- Why money belongs in `DECIMAL`
- What MySQL does when a value does not fit

## The types you will use

| Group | Type | Use it for |
|---|---|---|
| Whole numbers | `TINYINT` (1 byte), `SMALLINT` (2), `INT` (4), `BIGINT` (8) | counts, ids, quantities |
| Exact decimals | `DECIMAL(p, s)` | money, anything that must be exact |
| Approximate | `FLOAT`, `DOUBLE` | science and measurements, never money |
| Text | `CHAR(n)`, `VARCHAR(n)`, `TEXT` | names, titles, long text |
| Dates and times | `DATE`, `TIME`, `DATETIME`, `TIMESTAMP`, `YEAR` | days and moments |
| Choices | `ENUM('a','b')`, `SET(...)` | a fixed list of allowed values |
| Yes/no | `BOOLEAN` (a `TINYINT(1)`) | flags |
| Other | `JSON`, `BLOB` | documents, binary files |

`INT UNSIGNED` means no negative numbers, which doubles the top of the range. `DECIMAL(10, 2)` holds 10 digits in total, 2 of them after the decimal point.

## Set up a table to experiment on

```sql
CREATE TABLE type_demo (
  small_number TINYINT,
  positive_number TINYINT UNSIGNED,

DESCRIBE type_demo;
```

## Examples

### Numbers have a range

A `TINYINT` holds -128 to 127. An `UNSIGNED` one holds 0 to 255:

```sql
INSERT INTO type_demo (small_number, positive_number) VALUES (127, 255);

SELECT small_number, positive_number FROM type_demo;
```

| small_number | positive_number |
|---:|---:|
| 127 | 255 |

*1 row returned.*

### Decimal is exact, double is not

Computers store `DOUBLE` in binary, and many decimal fractions cannot be stored exactly in binary. Compare adding tenths:

```sql
SELECT 0.1 + 0.2 = 0.3 AS decimal_is_exact,
       CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE) = CAST(0.3 AS DOUBLE) AS double_is_exact;
```

| decimal_is_exact | double_is_exact |
|---:|---:|
| 1 | 0 |

*1 row returned.*

`DECIMAL` says `1` (true). `DOUBLE` says `0`: the sum is `0.30000000000000004`. That is why prices go in `DECIMAL`.

### CHAR pads, VARCHAR does not

`CHAR(5)` always uses 5 characters (padding with spaces), and drops trailing spaces when you read it back. `VARCHAR` remembers exactly what you stored:

```sql
INSERT INTO type_demo (short_code, title) VALUES ('ab   ', 'ab   ');

SELECT CHAR_LENGTH(short_code) AS char_length, CHAR_LENGTH(title) AS varchar_length
FROM type_demo
WHERE short_code IS NOT NULL;
```

| char_length | varchar_length |
|---:|---:|
| 2 | 5 |

*1 row returned.*

### Valid dates and enums

```sql
INSERT INTO type_demo (mood, born) VALUES ('happy', '2005-06-15');

SELECT mood, born FROM type_demo WHERE mood IS NOT NULL;
```

| mood | born |
|---|---|
| happy | 2005-06-15 |

*1 row returned.*

## Try it yourself

Create a table with a `DECIMAL(6, 2)` price and insert `1234.567`. See what is stored. Then try `99999.99`.

## Watch out

### A value that does not fit is an error

In MySQL's default (strict) mode, a value outside the range is refused rather than quietly changed:

```sql
INSERT INTO type_demo (small_number) VALUES (128);
```

```text
ERROR 1264 (22003): Out of range value for column 'small_number' at row 1
```

```sql
INSERT INTO type_demo (positive_number) VALUES (-1);
```

```text
ERROR 1264 (22003): Out of range value for column 'positive_number' at row 1
```

### Text that is too long is refused

```sql
INSERT INTO type_demo (title) VALUES ('this title is much too long');
```

```text
ERROR 1406 (22001): Data too long for column 'title' at row 1
```

`title` was declared `VARCHAR(10)`, and this text is longer. In strict mode MySQL refuses (error 1406) rather than silently cutting the text.

### An ENUM accepts only its list

```sql
INSERT INTO type_demo (mood) VALUES ('angry');
```

```text
ERROR 1265 (01000): Data truncated for column 'mood' at row 1
```

`mood` is an `ENUM('happy', 'sad')`. It accepts only the values listed when the table was created, and `'angry'` is not one of them (error 1265).

### An impossible date is refused

```sql
INSERT INTO type_demo (born) VALUES ('2005-02-30');
```

```text
ERROR 1292 (22007): Incorrect date value: '2005-02-30' for column 'born' at row 1
```

February has no 30th day, so MySQL refuses the date (error 1292) instead of storing an impossible one.

### Do not store money in FLOAT

Small rounding errors add up over thousands of rows. Use `DECIMAL(10, 2)` (or store whole cents in an `INT`).

### Pick the smallest type that is safe

A `TINYINT` for a rating from 1 to 5 uses one byte instead of four. Across millions of rows that saves memory and makes indexes smaller. But do not choose so small that real growth will not fit.

## Interview corner

**"What is the difference between `CHAR` and `VARCHAR`?"**
`CHAR(n)` is fixed length (padded with spaces), so it suits codes of a set length. `VARCHAR(n)` stores just the characters given (plus a length byte), so it suits variable text.

**"What is the difference between `VARCHAR` and `TEXT`?"**
`VARCHAR(n)` has a maximum you set and can be fully indexed; `TEXT` is for long text (up to 64 KB), with restrictions on indexing and default values.

**"Which type would you use for money?"**
`DECIMAL(p, s)`, because it is exact. `FLOAT` and `DOUBLE` are approximations.

**"What is the difference between `DATETIME` and `TIMESTAMP`?"**
`TIMESTAMP` is stored in UTC, shown in the session's time zone, and covers 1970 to 2038. `DATETIME` has no time zone conversion and covers years 1000 to 9999.

## Practice

### Warm-up: decimal versus double

Return two columns, `decimal_total` and `double_total`: the sum `0.1 + 0.2 + 0.3` as exact decimals, and the same values cast to `DOUBLE` and added, compared to `0.6` with `=`. Show each comparison as `1` or `0`.

**Your result should look like this:**

| decimal_total | double_total |
|---:|---:|
| 1 | 0 |

*1 row returned.*

<details>
<summary>Hint</summary>

`0.1 + 0.2 + 0.3 = 0.6` and the same with `CAST(... AS DOUBLE)` on each term.

</details>

<details>
<summary>Show solution</summary>

```sql
SELECT 0.1 + 0.2 + 0.3 = 0.6 AS decimal_total,
       CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE) + CAST(0.3 AS DOUBLE) = CAST(0.6 AS DOUBLE) AS double_total;
```

</details>

### Core: a table with the right types

Create `product` with `id INT`, `name VARCHAR(40)`, `price DECIMAL(8, 2)` and `in_stock BOOLEAN`. Insert one row `(1, 'Notebook', 4.50, TRUE)` and return it, showing `in_stock` as-is.

**Your result should look like this:**

| id | name | price | in_stock |
|---:|---|---:|---:|
| 1 | Notebook | 4.50 | 1 |

*1 row returned.*

<details>
<summary>Hint</summary>

BOOLEAN is stored as 1 or 0.

</details>

<details>
<summary>Show solution</summary>

```sql
DROP TABLE IF EXISTS product;
CREATE TABLE product (
  id INT,
  name VARCHAR(40),
  price DECIMAL(8, 2),
  in_stock BOOLEAN
);
INSERT INTO product VALUES (1, 'Notebook', 4.50, TRUE);

SELECT id, name, price, in_stock FROM product;
```

</details>

### Stretch: the rounding you get

Create `price_test (p DECIMAL(6, 2))`, insert the values `1.005`, `2.675` and `3.994`, and return them ordered by value. What was stored?

**Your result should look like this:**

| p |
|---:|
| 1.01 |
| 2.68 |
| 3.99 |

*3 rows returned.*

<details>
<summary>Hint</summary>

MySQL rounds a DECIMAL to its scale when storing (with a warning, not an error).

</details>

<details>
<summary>Show solution</summary>

```sql
DROP TABLE IF EXISTS price_test;
CREATE TABLE price_test (p DECIMAL(6, 2));
INSERT INTO price_test VALUES (1.005), (2.675), (3.994);

SELECT p FROM price_test ORDER BY p;
```

</details>
