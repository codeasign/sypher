An **index** is a sorted lookup structure that lets MySQL find rows without reading the whole table. It works like the index at the back of a book: instead of reading every page to find a word, you jump straight to the right page. Adding the right index is the single most effective way to speed up a slow query.

## What you'll learn

- What an index does, and what it costs
- `CREATE INDEX`, `DROP INDEX` and `SHOW INDEX`
- Unique indexes
- How to measure the difference with real numbers

## Syntax

```sql
CREATE INDEX index_name ON table_name (column1, column2);
CREATE UNIQUE INDEX index_name ON table_name (column1);
DROP INDEX index_name ON table_name;
SHOW INDEX FROM table_name;
```

## Set up a table with no indexes

To see an index at work we need a table that has none. This copy of `payment` has the data, but not the keys and indexes of the original:

```sql
CREATE TABLE payment_plain AS SELECT * FROM payment;

SELECT COUNT(*) AS rows_in_table FROM payment_plain;

SHOW INDEX FROM payment_plain;
```

| rows_in_table |
|---:|
| 16044 |

*1 row returned.*

*No rows returned.*

`SHOW INDEX` returns nothing: there are no indexes at all.

## Measuring: how many rows did MySQL read?

MySQL keeps counters of how many rows it read. `Handler_read_rnd_next` counts rows read by scanning the table one after another. We reset the counters, run a query, and look:

```sql
FLUSH STATUS;

SELECT COUNT(*) AS payments_of_customer_5
FROM payment_plain
WHERE customer_id = 5;

SHOW SESSION STATUS LIKE 'Handler_read_rnd_next';
```

| payments_of_customer_5 |
|---:|
| 38 |

*1 row returned.*

| Variable_name | Value |
|---|---:|
| Handler_read_rnd_next | 16045 |

*1 row returned.*

To find customer 5's payments, MySQL had to read the **entire table** (every row, plus one). That is a *full table scan*.

## Add an index

```sql
CREATE INDEX idx_customer ON payment_plain (customer_id);

SHOW INDEX FROM payment_plain;
```

| Table | Non_unique | Key_name | Seq_in_index | Column_name | Index_type |
|---|---:|---|---:|---|---|
| payment_plain | 1 | idx_customer | 1 | customer_id | BTREE |

*1 row returned.*

Now the same query and the same counters:

```sql
FLUSH STATUS;

SELECT COUNT(*) AS payments_of_customer_5
FROM payment_plain
WHERE customer_id = 5;

SHOW SESSION STATUS WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next', 'Handler_read_rnd_next');
```

| payments_of_customer_5 |
|---:|
| 38 |

*1 row returned.*

| Variable_name | Value |
|---|---:|
| Handler_read_key | 1 |
| Handler_read_next | 38 |
| Handler_read_rnd_next | 0 |

*3 rows returned.*

`Handler_read_key` says MySQL looked up **one** place in the index, and `Handler_read_next` says it then read only the entries for customer 5. The full scan (`Handler_read_rnd_next`) is gone. Instead of reading thousands of rows it read a few dozen.

## A unique index

A `UNIQUE` index makes lookups fast **and** refuses duplicates:

```sql
CREATE UNIQUE INDEX uq_payment_id ON payment_plain (payment_id);

SELECT index_name, non_unique
FROM information_schema.statistics
WHERE table_schema = DATABASE() AND table_name = 'payment_plain'
ORDER BY index_name;
```

| INDEX_NAME | NON_UNIQUE |
|---|---:|
| idx_customer | 1 |
| uq_payment_id | 0 |

*2 rows returned.*

`non_unique = 0` means the index enforces uniqueness.

## Drop an index

```sql
DROP INDEX idx_customer ON payment_plain;

SELECT COUNT(*) AS indexes_left
FROM information_schema.statistics
WHERE table_schema = DATABASE() AND table_name = 'payment_plain';
```

| indexes_left |
|---:|
| 1 |

*1 row returned.*

## Try it yourself

Create a copy of another table, time a query on an unindexed column, add an index, and compare the row counters again.

## Watch out

### Indexes are not free

Every index has to be updated on each `INSERT`, `UPDATE` and `DELETE`, so more indexes make **writes slower**. They also take disk space and memory. Add an index because a real query needs it, not "just in case".

### Index the columns you search and join on

The best candidates are columns in `WHERE`, `JOIN ... ON`, `ORDER BY` and `GROUP BY` of slow queries. Primary keys and foreign keys are indexed for you.

### Low-value columns are poor candidates

An index on a column with only a few different values (a yes/no flag, or `rating` with five values) helps little, because each value matches a large fraction of the table. Look for columns with many different values (high **selectivity**).

### Too many similar indexes

An index on `(customer_id)` is already covered by one on `(customer_id, payment_date)`, as the next pages show. Redundant indexes only add cost.

### An index only helps if the query can use it

A query written in the wrong way ignores the index entirely. Page 14.4 shows how that happens.

## Interview corner

**"What is an index, and why does it speed up queries?"**
A separate, sorted structure (a B+tree in InnoDB) that points to rows, so MySQL can find them with a few lookups instead of scanning the table.

**"What is the downside of indexes?"**
They use space and slow down writes, because each index must be kept up to date.

**"Which columns should you index?"**
Those used often to filter, join or sort, especially with many different values, and always foreign key columns.

**"What is the difference between a clustered and a secondary index in InnoDB?"**
The primary key index is **clustered**: the table's rows are stored in the primary key's order inside it. Every other index is **secondary**, and it stores the indexed columns plus the primary key value to find the row.
