**ACID** is the promise a transactional database makes about your data. It stands for Atomicity, Consistency, Isolation and Durability, and it is one of the most common interview questions there is. Here you see each letter happen for real.

## What you'll learn

- What each letter of ACID guarantees
- How to see atomicity and consistency in action
- What makes a commit durable

## The four letters

| Letter | Promise | Plain English |
|---|---|---|
| **A**tomicity | all or nothing | a transaction never leaves half its changes behind |
| **C**onsistency | rules always hold | after a transaction, every constraint is still true |
| **I**solation | no interference | concurrent transactions do not see each other's half-finished work |
| **D**urability | commits survive | once committed, the data survives a crash |

## Set up

```sql
CREATE TABLE account (
  id INT PRIMARY KEY,
  owner VARCHAR(20) NOT NULL,
  balance DECIMAL(10, 2) NOT NULL,
  CONSTRAINT balance_not_negative CHECK (balance >= 0)
);

INSERT INTO account VALUES (1, 'Asha', 100.00), (2, 'Ben', 100.00);

SELECT id, owner, balance FROM account ORDER BY id;
```

| id | owner | balance |
|---:|---|---:|
| 1 | Asha | 100.00 |
| 2 | Ben | 100.00 |

*2 rows returned.*

The `CHECK` is a rule the database enforces: no account may go below zero.

## Atomicity: all or nothing

A transfer of 150 from Asha, who has only 100. The first step (adding 150 to Ben) works. The second step breaks the rule, so the whole transfer must be undone:

```sql
START TRANSACTION;

UPDATE account SET balance = balance + 150 WHERE id = 2;
UPDATE account SET balance = balance - 150 WHERE id = 1;

ROLLBACK;

SELECT id, owner, balance FROM account ORDER BY id;
```

```text
ERROR 3819 (HY000): Check constraint 'balance_not_negative' is violated.
```

| id | owner | balance |
|---:|---|---:|
| 1 | Asha | 100.00 |
| 2 | Ben | 100.00 |

*2 rows returned.*

The second update failed, we rolled back, and **Ben's +150 disappeared too**. Both balances are back to 100. Without the transaction, Ben would have kept money that never left Asha.

## Consistency: the rules always hold

The failed statement above shows consistency as well: MySQL refused the update, because it would have broken the `CHECK`. A foreign key protects data in the same way:

```sql
INSERT INTO rental (rental_date, inventory_id, customer_id, staff_id)
VALUES ('2005-06-01 10:00:00', 1, 60000, 1);
```

```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`sypher-mysql-DvdRental`.`rental`, CONSTRAINT `fk_rental_customer` FOREIGN KEY (`customer_id`) REFERENCES `customer` (`customer_id`) ON DELETE RESTRICT ON UPDATE CASCADE)
```

No committed state ever breaks a constraint. The rules are part of the database, not left to the application.

## Isolation: transactions do not interfere

While one transaction is half done, another must not see the half-done state (or, at least, only in ways you have chosen). Exactly how strict this is depends on the **isolation level**, which is the topic of the next page. The default level in MySQL is:

```sql
SELECT @@transaction_isolation AS default_isolation_level;
```

| default_isolation_level |
|---|
| REPEATABLE-READ |

*1 row returned.*

## Durability: a commit survives a crash

When you `COMMIT`, InnoDB writes the change to its **redo log** on disk before it says "done". After a crash, MySQL replays that log and the committed data is back. How strictly the log is flushed is a setting:

```sql
SELECT @@innodb_flush_log_at_trx_commit AS flush_log_at_commit;
```

| flush_log_at_commit |
|---:|
| 1 |

*1 row returned.*

`1` (the default) flushes the log to disk at every commit, which is the safe choice. `0` and `2` are faster but can lose the last second or so of commits in a crash.

## Try it yourself

Add a `CHECK (balance <= 1000)`, and try a transfer that would take an account above 1000. See which statement fails.

## Watch out

### ACID is a property of the engine, not just of your code

You get it from InnoDB and from using transactions properly. Two statements run outside a transaction, in autocommit mode, are two separate commits, and a failure between them leaves the data half changed.

### Atomicity does not mean you ignore errors

The database keeps the promise only if you call `ROLLBACK` (or the connection drops). Application code has to handle errors.

### Consistency means constraint consistency, not "correct"

The database guarantees your rules hold. It cannot know a business rule you never wrote as a constraint.

## Interview corner

**"Explain ACID."**
Atomicity: all or nothing. Consistency: constraints hold before and after. Isolation: concurrent transactions do not see each other's uncommitted work. Durability: committed data survives a crash. Give the bank-transfer example.

**"How does MySQL provide atomicity and durability?"**
InnoDB uses an **undo log** (to roll changes back, and for consistent reads) and a **redo log** (to replay committed changes after a crash).

**"How is isolation implemented?"**
With MVCC (multi-version concurrency control) for consistent reads, and locks for writes. The next two pages show both.

### Core: a failed transfer leaves nothing behind

Create the `account` table above (with the `CHECK`), start a transaction, take 500 from Asha (this breaks the rule), and roll back. Return the balances `owner` and `balance`, ordered by `id`.

**Your result should look like this:**

| owner | balance |
|---|---:|
| Asha | 100.00 |
| Ben | 100.00 |

*2 rows returned.*

<details>
<summary>Hint</summary>

The update fails, so ROLLBACK, then SELECT. Nothing has changed.

</details>

```sql
DROP TABLE IF EXISTS account;
CREATE TABLE account (
  id INT PRIMARY KEY,
  owner VARCHAR(20) NOT NULL,
  balance DECIMAL(10, 2) NOT NULL,
  CONSTRAINT balance_not_negative CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'Asha', 100.00), (2, 'Ben', 100.00);

START TRANSACTION;
UPDATE account SET balance = balance - 500 WHERE id = 1;
ROLLBACK;

SELECT owner, balance FROM account ORDER BY id;
```
