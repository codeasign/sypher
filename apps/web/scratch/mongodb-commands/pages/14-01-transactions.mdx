A single write to one document is always atomic, and good modelling makes that enough most of the time. When a change must touch **several documents** and either all succeed or none does (a money transfer, an order with stock), you use a **multi-document transaction**. Transactions need a replica set.

## What you'll learn

- Why one document is already atomic
- Running a replica set in the lab
- `withTransaction`: commit, abort and retry
- What a transaction protects you from

## Syntax

```js
const session = db.getMongo().startSession()
session.withTransaction(() => {
  session.getDatabase("shop").accounts.updateOne({ _id: "a" }, { $inc: { bal: -50 } })
  session.getDatabase("shop").accounts.updateOne({ _id: "b" }, { $inc: { bal: 50 } })
})
```

## Examples

### The lab needs a replica set

Transactions are not available on a standalone server. The lab folder defines a single-node replica set as a second MongoDB service. Add it to `docker-compose.yml` and start it:

```yaml
  mongodb-rs:
    image: mongo:8
    command: ["--replSet", "rs0", "--bind_ip_all"]
    ports:
      - "27019:27017"
    healthcheck:
      test: ["CMD-SHELL", "mongosh --quiet --eval \"try { rs.status().ok } catch (e) { rs.initiate({ _id: 'rs0', members: [{ _id: 0, host: 'localhost:27017' }] }).ok }\""]
      interval: 5s
      retries: 20
```

```bash
docker compose up -d mongodb-rs
```

Every example below runs against this replica set. Check its state:

```js
rs.status().members.map((m) => m.stateStr)
```

```text
[ 'PRIMARY' ]
```

### One document is already atomic

An update to a single document, even one touching many fields and nested arrays, is all-or-nothing without any transaction. That is the main reason to embed related data:

```js
const shop = db.getSiblingDB("lab_tx")
shop.accounts.insertMany([{ _id: "a", bal: 100 }, { _id: "b", bal: 20 }]);
shop.orders.insertOne({ _id: 1, items: [{ sku: "pen", qty: 2 }], total: 4, status: "new" });
shop.orders.updateOne({ _id: 1 }, { $push: { items: { sku: "ink", qty: 1 } }, $inc: { total: 6 }, $set: { status: "paid" } });
shop.orders.findOne({ _id: 1 })
```

```text
{
  _id: 1,
  items: [ { sku: 'pen', qty: 2 }, { sku: 'ink', qty: 1 } ],
  total: 10,
  status: 'paid'
}
```

### The problem: two documents

Moving 50 from `a` to `b` is two writes. If the process stops between them, money disappears:

```js
shop.accounts.updateOne({ _id: "a" }, { $inc: { bal: -50 } });
shop.accounts.find().sort({ _id: 1 }).toArray().map((d) => d.bal)
```

```text
[ 50, 20 ]
```

`a` lost 50 and `b` has not received it yet. Put it back and do it properly.

### A transaction

```js
shop.accounts.updateOne({ _id: "a" }, { $inc: { bal: 50 } });
const session = db.getMongo().startSession();
session.withTransaction(() => {
  const acc = session.getDatabase("lab_tx").accounts;
  acc.updateOne({ _id: "a" }, { $inc: { bal: -50 } });
  acc.updateOne({ _id: "b" }, { $inc: { bal: 50 } });
});
session.endSession();
shop.accounts.find().sort({ _id: 1 }).toArray().map((d) => d.bal)
```

```text
[ 50, 70 ]
```

Both writes committed together: 50 and 70.

### Abort: nothing happens

If the callback throws, the whole transaction is rolled back:

```js
const s2 = db.getMongo().startSession();
try {
  s2.withTransaction(() => {
    const acc = s2.getDatabase("lab_tx").accounts;
    acc.updateOne({ _id: "a" }, { $inc: { bal: -30 } });
    acc.updateOne({ _id: "b" }, { $inc: { bal: 30 } });
    throw new Error("insufficient funds check failed");
  });
} catch (e) {}
s2.endSession();
shop.accounts.find().sort({ _id: 1 }).toArray().map((d) => d.bal)
```

```text
[ 50, 70 ]
```

Still 50 and 70: the first update was rolled back.

### Isolation: other clients do not see uncommitted work

Inside the transaction the change is visible; outside it is not, until commit:

```js
const s3 = db.getMongo().startSession();
s3.startTransaction();
s3.getDatabase("lab_tx").accounts.updateOne({ _id: "a" }, { $set: { bal: 999 } });
const inside = s3.getDatabase("lab_tx").accounts.findOne({ _id: "a" }).bal;
const outside = shop.accounts.findOne({ _id: "a" }).bal;
s3.abortTransaction();
s3.endSession();
[inside, outside, shop.accounts.findOne({ _id: "a" }).bal]
```

```text
[ 999, 50, 50 ]
```

### Checking a condition inside the transaction

Read, decide and write in one transaction, so the check and the change cannot be split by another client:

```js
const s4 = db.getMongo().startSession();
let ok = null;
s4.withTransaction(() => {
  const acc = s4.getDatabase("lab_tx").accounts;
  const from = acc.findOne({ _id: "b" });
  ok = from.bal >= 500;
  if (ok) { acc.updateOne({ _id: "b" }, { $inc: { bal: -500 } }); acc.updateOne({ _id: "a" }, { $inc: { bal: 500 } }); }
});
s4.endSession();
[ok, shop.accounts.find().sort({ _id: 1 }).toArray().map((d) => d.bal)]
```

```text
[ false, [ 50, 70 ] ]
```

### Clean up

```js
shop.dropDatabase()
```

```text
{ ok: 1, dropped: 'lab_tx' }
```

## Try it yourself

Model an order placement: decrease stock in `products` and insert a row in `orders`, in one transaction, and make it abort when the stock would go negative.

## Watch out

### Transactions cost more than single-document writes

They hold snapshots and locks. Prefer a model where the change fits in one document. Use transactions for the cases that truly span documents.

### Keep them short

A transaction has a default lifetime limit of 60 seconds and should touch few documents. Do not do user interaction or slow network calls inside one.

### Use the session for every operation in it

An operation that does not use the session's database or collection runs **outside** the transaction, without warning.

### Not on a standalone server

`startTransaction` on a standalone `mongod` fails. Development containers need the replica set too.

### Read your own writes and retry

Handle `TransientTransactionError` by retrying the whole transaction. `withTransaction` does that for you.

## Interview corner

**"Is MongoDB ACID?"**
Yes: single-document operations are always atomic, and since 4.0 (replica sets) and 4.2 (sharded clusters) multi-document transactions provide ACID across documents and collections.

**"When would you use a transaction?"**
When a change must span several documents and either all or none must apply, such as transfers or stock plus order records.

**"Why avoid transactions where possible?"**
They add latency and contention. Good schema design (embedding) usually makes single-document atomicity enough.
