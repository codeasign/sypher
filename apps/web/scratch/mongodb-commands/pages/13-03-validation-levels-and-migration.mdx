Adding rules to a collection that already has data is where things get tricky: old documents may break the new rules. MongoDB gives you **validation levels** and **actions** to roll rules out gently, and a **schema version** field to migrate documents step by step.

## What you'll learn

- `validationAction`: `error` versus `warn`
- `validationLevel`: `strict`, `moderate`, `off`
- Tightening rules on a live collection with `collMod`
- The schema versioning pattern for migrations

## Syntax

```js
db.runCommand({ collMod: "users", validator: { $jsonSchema: { ... } }, validationLevel: "moderate", validationAction: "warn" })
```

## Examples

```js
const lab = db.getSiblingDB("lab_migrate")
lab.users.insertMany([
  { _id: 1, name: "Ann Lee", email: "ann@x.com" },
  { _id: 2, name: "Bob Ray", email: "bob@x.com" },
  { _id: 3, name: "Cy", email: "cy@x.com" }
]);
lab.users.countDocuments()
```

```text
3
```

### Step 1: add the rule in warn mode

The new rule wants `first` and `last` names instead of one `name`. With `warn`, violating writes are allowed but logged, so you can watch how many break before you enforce:

```js
lab.runCommand({ collMod: "users", validator: { $jsonSchema: { bsonType: "object", required: ["first", "last"] } }, validationLevel: "strict", validationAction: "warn" })
```

```text
{ ok: 1 }
```

```js
lab.users.insertOne({ _id: 4, name: "Di Fox", email: "di@x.com" });
lab.users.countDocuments()
```

```text
4
```

The insert broke the rule and still succeeded (a warning went to the server log).

### Step 2: migrate the data in batches

An update pipeline splits `name` into the two fields. The `schemaVersion` marker records which documents are done:

```js
lab.users.updateMany({ schemaVersion: { $exists: false } }, [
  { $set: { first: { $arrayElemAt: [{ $split: ["$name", " "] }, 0] }, last: { $ifNull: [{ $arrayElemAt: [{ $split: ["$name", " "] }, 1] }, ""] }, schemaVersion: 2 } },
  { $unset: "name" }
])
lab.users.find({}, { _id: 0 }).sort({ email: 1 }).toArray()
```

```text
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 4,
  modifiedCount: 4,
  upsertedCount: 0
}
[
  { email: 'ann@x.com', first: 'Ann', last: 'Lee', schemaVersion: 2 },
  { email: 'bob@x.com', first: 'Bob', last: 'Ray', schemaVersion: 2 },
  { email: 'cy@x.com', first: 'Cy', last: '', schemaVersion: 2 },
  { email: 'di@x.com', first: 'Di', last: 'Fox', schemaVersion: 2 }
]
```

### Step 3: check nothing violates the rule

The same `$jsonSchema` used as a query finds documents that still break it:

```js
lab.users.countDocuments({ $nor: [{ $jsonSchema: { required: ["first", "last"] } }] })
```

```text
0
```

### Step 4: switch to enforcing

Now change the action to `error`. From now on, bad writes are rejected:

```js
lab.runCommand({ collMod: "users", validationAction: "error" })
```

```text
{ ok: 1 }
```

```js
lab.users.insertOne({ name: "Old style", email: "old@x.com" })
```

```text
MongoServerError: Document failed validation
Additional information: {
  operatorName: '$jsonSchema',
  schemaRulesNotSatisfied: [
    {
      operatorName: 'required',
      specifiedAs: { required: [ 'first', 'last' ] },
      missingProperties: [ 'first', 'last' ]
    }
  ]
}
```

### Levels: strict, moderate and off

`strict` checks every insert and update. `moderate` checks inserts and updates to documents that already **satisfy** the rules, and leaves already-invalid documents alone, which helps during a migration:

```js
lab.legacy.insertMany([{ _id: 1, note: "old" }, { _id: 2, note: "old" }]);
lab.runCommand({ collMod: "legacy", validator: { $jsonSchema: { required: ["ver"] } }, validationLevel: "moderate", validationAction: "error" });
lab.legacy.updateOne({ _id: 1 }, { $set: { note: "edited" } });
lab.legacy.findOne({ _id: 1 })
```

```text
{ _id: 1, note: 'edited' }
```

The already-invalid document could still be updated. A new document must comply:

```js
lab.legacy.insertOne({ _id: 3, note: "new" })
```

```text
MongoServerError: Document failed validation
Additional information: {
  operatorName: '$jsonSchema',
  schemaRulesNotSatisfied: [
    {
      operatorName: 'required',
      specifiedAs: { required: [ 'ver' ] },
      missingProperties: [ 'ver' ]
    }
  ]
}
```

### Bypassing validation

Users with the right privilege can skip validation for a single write. Use it for repairs, never for routine writes:

```js
lab.legacy.insertOne({ _id: 4, note: "forced" }, { bypassDocumentValidation: true });
lab.legacy.countDocuments()
```

```text
3
```

### Reading the current settings

```js
lab.getCollectionInfos({ name: "users" })[0].options.validationAction + "/" + lab.getCollectionInfos({ name: "users" })[0].options.validationLevel
```

```text
error/strict
```

### Clean up

```js
lab.dropDatabase()
```

```text
{ ok: 1, dropped: 'lab_migrate' }
```

## Try it yourself

Design a migration that turns a `price` stored as text (`"12.50"`) into a `Decimal128`, using `schemaVersion`, an update pipeline with `$convert`, and a validator that requires the decimal type after the migration.

## Watch out

### Migrate in batches on big collections

One `updateMany` over millions of documents runs for a long time. Loop over `_id` ranges and check progress with the `schemaVersion` filter.

### Readers must handle both versions during the migration

Code should accept old and new shapes until every document is migrated. The version field tells it which it got.

### `warn` writes go to the log, not to the client

You will not see a warning in your application. Read the server log (or use `explain`/audit) to count violations.

### Do not leave validation off or in `warn` for ever

Warn mode is a step on the way to `error`, not a destination.

## Interview corner

**"How do you add validation to a collection that already has data?"**
Add the rule with `validationAction: "warn"` first, migrate and audit the data with a `$jsonSchema` query, then switch to `error` (and `strict`, or `moderate` while old data remains).

**"What is the difference between `strict` and `moderate`?"**
`strict` validates all inserts and updates. `moderate` skips updates to documents that already violate the rules.

**"What is the schema versioning pattern?"**
A `schemaVersion` field on each document so code and migrations know which shape it has, allowing gradual, low-downtime migrations.

### Stretch: a version migration

Insert `{ v: 1, name: "A B" }`, then migrate to `{ v: 2, first, last }` with an update pipeline, and return the document without `_id`.

**Your result should look like this:**

```text
{ v: 2, first: 'A', last: 'B' }
```

<details>
<summary>Hint</summary>

`$split` the name, set `v: 2`, `$unset` `name`.

</details>

<details>
<summary>Show solution</summary>

```js
const lab = db.getSiblingDB("lab_migrate")
lab.c.insertOne({ v: 1, name: "A B" });
lab.c.updateMany({ v: 1 }, [{ $set: { first: { $arrayElemAt: [{ $split: ["$name", " "] }, 0] }, last: { $arrayElemAt: [{ $split: ["$name", " "] }, 1] }, v: 2 } }, { $unset: "name" }]);
const d = lab.c.findOne({}, { _id: 0 })
lab.dropDatabase();
```
