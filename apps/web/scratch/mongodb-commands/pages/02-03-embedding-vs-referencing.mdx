The biggest design choice in MongoDB is where related data lives. You can **embed** it inside the parent document, or **reference** it by storing an id and looking it up. The DVD Rental database uses both, and seeing them side by side is the fastest way to learn the trade-off.

## What you'll learn

- What embedding and referencing mean
- Where this database embeds and where it references
- How to follow a reference (a first look at `$lookup`)
- A rule of thumb for choosing

## Syntax

```js
// embedded: the data is inside the document
{ _id: 1, category: { categoryId: 6, name: "Documentary" } }

// referenced: only the id is stored, the data lives elsewhere
{ rentalId: 76, filmId: 663 }
```

## Examples

### Embedded: a film carries its cast

One read returns the film and all its actors. No second query, no join:

```js
db.films.findOne({ _id: 1 }, { title: 1, actors: { $slice: 2 } })
```

```text
{
  _id: 1,
  actors: [
    { actorId: 1, firstName: 'PENELOPE', lastName: 'GUINESS' },
    { actorId: 10, firstName: 'CHRISTIAN', lastName: 'GABLE' }
  ],
  title: 'ACADEMY DINOSAUR'
}
```

### Embedded: a customer carries their rentals

The customer, every rental, and every payment come back together:

```js
db.customers.aggregate([
  { $match: { _id: 1 } },
  { $project: { _id: 0, name: 1, rentalCount: { $size: "$rentals" }, firstRental: { $arrayElemAt: ["$rentals", 0] } } },
  { $project: { name: 1, rentalCount: 1, "firstRental.rentalId": 1, "firstRental.filmId": 1, "firstRental.payments.amount": 1 } }
])
```

```text
[
  {
    name: { first: 'MARY', last: 'SMITH' },
    rentalCount: 32,
    firstRental: { filmId: 663, payments: [ { amount: 2.99 } ], rentalId: 76 }
  }
]
```

### Referenced: a rental points at a film

A rental does not contain the film. It stores `filmId`. To get the title you look the film up:

```js
const rental = db.customers.findOne({ _id: 1 }).rentals[0]
const film = db.films.findOne({ _id: rental.filmId }, { title: 1 });
[rental.rentalId, rental.filmId, film.title]
```

```text
[ 76, 663, 'PATIENT SISTER' ]
```

### Following references in one query: $lookup

`$lookup` is MongoDB's join. It fetches matching documents from another collection into a new field:

```js
db.customers.aggregate([
  { $match: { _id: 1 } },
  { $project: { name: 1, first: { $arrayElemAt: ["$rentals", 0] } } },
  { $lookup: { from: "films", localField: "first.filmId", foreignField: "_id", as: "film" } },
  { $project: { _id: 0, name: 1, "first.rentalId": 1, film: { $arrayElemAt: ["$film.title", 0] } } }
])
```

```text
[
  {
    name: { first: 'MARY', last: 'SMITH' },
    first: { rentalId: 76 },
    film: 'PATIENT SISTER'
  }
]
```

### Why is `filmId` a reference and not an embedded film?

Copying the whole film into every rental would repeat the same 1000 films across 16044 rentals, and a change to a film would have to be made everywhere. So the film stays in `films`, and rentals point at it.

## Choosing: a rule of thumb

| Embed when | Reference when |
|---|---|
| The data is read together ("a film and its cast") | The data is large or used in many places |
| The child belongs to one parent | Many parents share it (many-to-many) |
| The list is small and bounded | The list can grow without limit |
| The child rarely changes on its own | The child changes often and must stay consistent |

## Try it yourself

Find which store owns inventory copy `1` (look in `stores.inventory`), and decide whether `inventory` was better embedded in `stores` or referenced.

## Watch out

### A document has a size limit

One document can be at most **16 MB**. An embedded list that grows for ever (every rental of a very active customer, every log line) will one day hit it. Bounded lists embed well; unbounded ones do not.

### Embedded copies can go stale

If you copy a value into many documents (a film title inside every rental), you must update every copy when it changes. Reference instead, or accept and manage the duplication.

### $lookup is not free

It works, but it is slower than reading one embedded document, and it does not cross **sharded** collections easily. Design so that the common reads need no `$lookup`.

### Arrays inside arrays are awkward

A payment inside a rental inside a customer needs a `$unwind` per level to analyse. Do not nest deeper than you can bear to query.

## Interview corner

**"When would you embed and when would you reference?"**
Embed when data is read together, belongs to one parent and is bounded. Reference when data is shared, large, unbounded or changes independently.

**"What is `$lookup`?"**
An aggregation stage that performs a left outer join with another collection in the same database, adding the matching documents as an array field.

**"What is the maximum size of a MongoDB document?"**
16 MB. It is the reason to avoid unbounded embedded arrays.

### Stretch: a lookup

Using `$lookup` from `customers` to `films`, return the **title** of the film of customer 3's first rental (a document `{ title: ... }`).

**Your result should look like this:**

```text
[ { title: 'RINGS HEARTBREAKERS' } ]
```

<details>
<summary>Hint</summary>

`$project` the first rental, `$lookup` on its `filmId`, then take the first title.

</details>

<details>
<summary>Show solution</summary>

```js
db.customers.aggregate([
  { $match: { _id: 3 } },
  { $project: { first: { $arrayElemAt: ["$rentals", 0] } } },
  { $lookup: { from: "films", localField: "first.filmId", foreignField: "_id", as: "film" } },
  { $project: { _id: 0, title: { $arrayElemAt: ["$film.title", 0] } } }
])
```

</details>
