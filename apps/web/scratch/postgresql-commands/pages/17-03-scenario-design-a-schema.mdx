> "Design the database for an online bookshop. Take your time and talk me through it."

Nobody expects a perfect answer. The interviewer wants to see **how you think**: do you ask questions, find the entities, choose keys, think about relationships and about the queries the system will run? This page gives a repeatable method and then builds the design for real, so you can see it work.

## What you'll learn

- A five-step method for schema design questions
- How to turn requirements into tables, keys and relationships
- Where indexes and constraints go
- How to check the design with real queries

## The method

1. **Clarify the requirements.** What must the system do? Who uses it? How big will it get?
2. **Find the entities** (the nouns): customers, books, authors, orders.
3. **Find the relationships** between them: one-to-many, many-to-many.
4. **Choose keys and columns**, and normalise to about 3NF.
5. **Add constraints and indexes** that the important queries need, then test the design with sample data and queries.

## Step 1: clarify

Questions worth asking aloud: Can a book have several authors? Can a customer have several addresses? Do we need to keep the price at the time of purchase? Do we track stock? Do we store reviews? Is it thousands of orders a day or millions? The answers change the design.

Our assumptions: a book has **one or more authors**, an order has **several lines**, prices change over time, and we track stock.

## Steps 2 and 3: entities and relationships

```text
customer 1---< order 1---< order_line >---1 book >---< book_author >---1 author
                                            |
                                            +---1 publisher
```

A customer has many orders; an order has many lines; each line is for one book. Book to author is many-to-many, so it needs a link table.

## Steps 4 and 5: build it

We use a scratch schema called `bookshop`, so nothing here touches the DVD Rental tables:

```sql
CREATE SCHEMA bookshop;
SET search_path = bookshop;

CREATE TABLE publisher (
  publisher_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL UNIQUE
);

CREATE TABLE author (
  author_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE book (
  book_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn text NOT NULL UNIQUE,
  title text NOT NULL,
  publisher_id int NOT NULL REFERENCES publisher,
  price numeric(8, 2) NOT NULL CHECK (price >= 0),
  stock int NOT NULL DEFAULT 0 CHECK (stock >= 0)
);

CREATE TABLE book_author (
  book_id int NOT NULL REFERENCES book ON DELETE CASCADE,
  author_id int NOT NULL REFERENCES author,
  PRIMARY KEY (book_id, author_id)
);

CREATE TABLE customer (
  customer_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE,
  name text NOT NULL
);

CREATE TABLE customer_order (
  order_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id int NOT NULL REFERENCES customer,
  ordered_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_line (
  order_id int NOT NULL REFERENCES customer_order ON DELETE CASCADE,
  book_id int NOT NULL REFERENCES book,
  quantity int NOT NULL CHECK (quantity > 0),
  unit_price numeric(8, 2) NOT NULL,
  PRIMARY KEY (order_id, book_id)
);

CREATE INDEX idx_order_customer ON customer_order (customer_id);
CREATE INDEX idx_line_book ON order_line (book_id);
CREATE INDEX idx_book_author_author ON book_author (author_id);

SELECT table_name FROM information_schema.tables WHERE table_schema = 'bookshop' ORDER BY table_name;
```

| table_name |
|---|
| author |
| book |
| book_author |
| customer |
| customer_order |
| … |

*Showing the first 5 of 7 rows.*

### Why each choice

- **Surrogate primary keys** (`identity`) plus `UNIQUE` on the natural identifiers (`isbn`, `email`), so both are protected.
- **`unit_price` in `order_line`**: the price **at the time of sale**, because the catalogue price changes.
- **Link table `book_author`** with a composite primary key, so a pair cannot repeat.
- **Foreign keys everywhere**, and **indexes on the foreign key columns** PostgreSQL does not index for you (`customer_order.customer_id`, `order_line.book_id`, `book_author.author_id`).
- **`CHECK` constraints** on price, stock and quantity.

**Question 1: revenue per customer**

```sql
SET search_path = bookshop;

SELECT c.name, SUM(l.quantity * l.unit_price) AS revenue
FROM customer c
JOIN customer_order o ON o.customer_id = c.customer_id
JOIN order_line l ON l.order_id = o.order_id
GROUP BY c.name
ORDER BY revenue DESC;
```

| name | revenue |
|---|---:|
| Asha | 39.99 |
| Ben | 29.97 |

**Question 2: a book with all its authors** (this needs the link table)

```sql
SET search_path = bookshop;

SELECT b.title, string_agg(a.name, ', ' ORDER BY a.name) AS authors
FROM book b
JOIN book_author ba ON ba.book_id = b.book_id
JOIN author a ON a.author_id = ba.author_id
GROUP BY b.book_id, b.title
ORDER BY b.title;
```

| Small Gods | Terry Pratchett |

**Question 3: what is out of stock but has been ordered?**

```sql
SET search_path = bookshop;

SELECT DISTINCT b.title
FROM book b
JOIN order_line l ON l.book_id = b.book_id
```

The constraints protect the data too. A negative price is refused, and so is a line for a book that does not exist:

```sql
SET search_path = bookshop;

INSERT INTO book (isbn, title, publisher_id, price) VALUES ('444', 'Bad Price', 1, -5);
INSERT INTO order_line VALUES (1, 999, 1, 1.00);
```

```text
ERROR:  new row for relation "book" violates check constraint "book_price_check"
DETAIL:  Failing row contains (4, 444, Bad Price, 1, -5.00, 0).
```

```text
ERROR:  insert or update on table "order_line" violates foreign key constraint "order_line_book_id_fkey"
DETAIL:  Key (book_id)=(999) is not present in table "book".
```

## What to say out loud

1. "Before designing, I would ask what the system must do and roughly how big it gets."
2. "The entities are customer, order, book, author and publisher. Book to author is many-to-many, so I need a link table."
3. "Each table gets a surrogate primary key. I would keep `isbn` and `email` as `UNIQUE`. I would store the **price at the time of sale** in the order line."
4. "I would normalise to 3NF, and add foreign keys, and `CHECK` constraints on things like price and quantity."
5. "Indexes follow the queries: orders by customer and date, and book search by title (a trigram or full-text index). PostgreSQL does not index foreign key columns automatically, so I would add those."
6. "If reporting becomes heavy I would consider a materialised view, summary tables or a read replica, and only then denormalise."

## Try it yourself

Extend the design on paper: add **reviews** (a customer reviews a book, once), **addresses** (a customer has many), and **categories** (a book can be in several). Which are one-to-many and which are many-to-many?

## Watch out

### Do not skip the questions

Jumping straight to tables shows you did not think about the requirements. Asking about scale, edge cases (several authors, price changes) and the main queries is part of the answer.

### Do not over-normalise, and do not under-normalise

Splitting everything into tiny tables makes every query a maze. Repeating the customer's name in every order is an update problem. Aim for 3NF, and know when to bend it.

### Money and time

Use `numeric` for money, and store the price actually charged on the order line. Use `timestamptz` for moments, so time zones are handled for you.

### Think about deletion

What happens to orders if a customer is deleted? (Here the foreign key refuses it, which is usually right: you keep financial history. Some systems "soft delete" with an `is_active` flag.)

## Interview corner

**"How do you model a many-to-many relationship?"**
With a link table holding the two foreign keys, usually as a composite primary key.

**"Why store the price in the order line?"**
The catalogue price changes, but an order must always show what the customer actually paid.

**"How would this design change at ten times the size?"**
Check the indexes against real query plans, consider partitioning very large tables (orders by date), add read replicas for reporting, and cache hot reads.

**"Surrogate or natural primary keys?"**
Surrogate (generated integer) primary keys, plus `UNIQUE` constraints on natural identifiers such as ISBN and email.

```sql
CREATE SCHEMA shop2;
CREATE TABLE shop2.book (book_id int PRIMARY KEY, price numeric CHECK (price >= 0), stock int CHECK (stock >= 0));

SELECT COUNT(*) AS checks
FROM information_schema.table_constraints
WHERE table_schema = 'shop2' AND constraint_type = 'CHECK' AND constraint_name NOT LIKE '%not_null';
```

### Core: add reviews

In a fresh schema `shop3` with `customer` and `book` tables (each with just an `int` primary key), add a `review` table: `review_id`, `book_id`, `customer_id`, `stars smallint` (1 to 5 with a `CHECK`), with a **unique pair** so a customer can review a book only once. Insert two reviews for book 1 (from customers 1 and 2) and return the average stars as `avg_stars`.

**Your result should look like this:**

| avg_stars |
|---:|
| 4.5000000000000000 |

*1 row returned.*

<details>
<summary>Hint</summary>

`UNIQUE (book_id, customer_id)` and `CHECK (stars BETWEEN 1 AND 5)`.

</details>

<details>
<summary>Show solution</summary>

```sql
CREATE SCHEMA shop3;
CREATE TABLE shop3.customer (customer_id int PRIMARY KEY);
CREATE TABLE shop3.book (book_id int PRIMARY KEY);
CREATE TABLE shop3.review (
  review_id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id int NOT NULL REFERENCES shop3.book,
  customer_id int NOT NULL REFERENCES shop3.customer,
  stars smallint NOT NULL CHECK (stars BETWEEN 1 AND 5),
  UNIQUE (book_id, customer_id)
);
INSERT INTO shop3.customer VALUES (1), (2);
INSERT INTO shop3.book VALUES (1);
INSERT INTO shop3.review (book_id, customer_id, stars) VALUES (1, 1, 4), (1, 2, 5);

SELECT AVG(stars) AS avg_stars FROM shop3.review;
```

</details>

```sql
CREATE SCHEMA shop4;
CREATE TABLE shop4.book (book_id int PRIMARY KEY);
CREATE TABLE shop4.category (category_id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE shop4.book_category (book_id int REFERENCES shop4.book, category_id int REFERENCES shop4.category, PRIMARY KEY (book_id, category_id));
INSERT INTO shop4.book VALUES (1);
INSERT INTO shop4.category VALUES (1, 'Fantasy'), (2, 'Humour');
INSERT INTO shop4.book_category VALUES (1, 1), (1, 2);

SELECT c.name
FROM shop4.book_category bc
JOIN shop4.category c ON c.category_id = bc.category_id
WHERE bc.book_id = 1
ORDER BY c.name;
```
