**SQL injection** is one of the most common and most damaging security flaws in web applications. It happens when a program builds a SQL statement by gluing user input into the text, so that a clever input changes the *meaning* of the query. Here you will see an injection happen against the DVD Rental data, so you will recognise the pattern, and then see the fix: **parameters**.

This is a defensive lesson: you attack only your own practice database, to learn how to write code that cannot be attacked.

## What you'll learn

- How string-built SQL gets hijacked
- Why parameters (`$1`, `USING`) stop it
- `PREPARE` and `EXECUTE`
- Safe dynamic SQL with `format('%I', ...)` and `quote_literal`

## The setup

Imagine a search box: "find customers by last name". The application takes what the user typed and builds the query by **concatenating** it into a string. We can imitate that inside PostgreSQL with a function that builds the text and runs it with `EXECUTE`:

```sql
CREATE FUNCTION find_unsafe(p_name text) RETURNS SETOF text
LANGUAGE plpgsql AS $$
BEGIN
  RETURN QUERY EXECUTE 'SELECT first_name::text FROM customer WHERE last_name = ''' || p_name || '''';
END $$;

SELECT * FROM find_unsafe('SMITH');
```

| find_unsafe |
|---|
| MARY |

*1 row returned.*

With a normal input, it works as intended.

## Attack 1: return everything

The attacker types a name plus a quote plus an always-true condition: `x' OR '1'='1`:

```sql
CREATE OR REPLACE FUNCTION find_unsafe(p_name text) RETURNS SETOF text
LANGUAGE plpgsql AS $$
BEGIN
  RETURN QUERY EXECUTE 'SELECT first_name::text FROM customer WHERE last_name = ''' || p_name || '''';
END $$;

SELECT COUNT(*) AS customers_returned FROM find_unsafe('x'' OR ''1''=''1');
```

| customers_returned |
|---:|
| 599 |

*1 row returned.*

The extra text closed the string early and added `OR '1'='1'`, which is true for every row. The search that should find one surname returned **every customer**. In a login form, the same trick logs the attacker in without a password.

## Attack 2: read another table

With `UNION`, the attacker adds a second query whose results appear in the same list. Here they pull the staff usernames into the customer search:

```sql
CREATE OR REPLACE FUNCTION find_unsafe(p_name text) RETURNS SETOF text
LANGUAGE plpgsql AS $$
BEGIN
  RETURN QUERY EXECUTE 'SELECT first_name::text FROM customer WHERE last_name = ''' || p_name || '''';
END $$;

SELECT * FROM find_unsafe('nobody'' UNION SELECT username FROM staff --');
```

| find_unsafe |
|---|
| Jon |
| Mike |

*2 rows returned.*

Data from a table the search box was never meant to touch came back. The `--` is a comment marker that swallows the closing quote the application added, so the query stays valid.

## The fix: parameters, not concatenation

`EXECUTE ... USING` sends the values **separately** from the query text. The `$1` is a placeholder. Whatever you put in it is treated as a *value*, never as SQL, however many quotes it contains:

```sql
CREATE FUNCTION find_safe(p_name text) RETURNS SETOF text
LANGUAGE plpgsql AS $$
BEGIN
  RETURN QUERY EXECUTE 'SELECT first_name::text FROM customer WHERE last_name = $1' USING p_name;
END $$;

SELECT COUNT(*) AS malicious_input FROM find_safe('x'' OR ''1''=''1');
SELECT * FROM find_safe('SMITH');
```

| malicious_input |
|---:|
| 0 |

*1 row returned.*

| find_safe |
|---|
| MARY |

*1 row returned.*

The same malicious text now finds **0** customers, because PostgreSQL looks for someone whose last name is literally `x' OR '1'='1`. And the honest search still works. This is what your programming language's database library does when you use parameters (`WHERE last_name = $1`).

## PREPARE and EXECUTE

`PREPARE` parses a statement once, with `$1`, `$2` placeholders, and `EXECUTE` runs it with values, as many times as you like:

```sql
PREPARE customers_by_name (text) AS
  SELECT customer_id, first_name FROM customer WHERE last_name = $1 ORDER BY customer_id;

EXECUTE customers_by_name('SMITH');
EXECUTE customers_by_name('x'' OR ''1''=''1');

DEALLOCATE customers_by_name;
```

| customer_id | first_name |
|---:|---|
| 1 | MARY |

*1 row returned.*

| customer_id | first_name |
|---|---|

*No rows returned.*

The statement lives only for your connection. The malicious value returns nothing, again.

## Identifiers cannot be parameters: use format()

A placeholder can stand for a **value**, never for a table or column name. If a user picks a sort column, build the text with `format('%I')`, which quotes an identifier safely, and `%L` for a literal:

```sql
SELECT format('SELECT * FROM %I WHERE last_name = %L', 'customer', 'O''Brien') AS safe_text,
       format('%I', 'name; DROP TABLE x') AS quoted_identifier;
```

| safe_text | quoted_identifier |
|---|---|
| SELECT * FROM customer WHERE last_name = 'O''Brien' | "name; DROP TABLE x" |

*1 row returned.*

An allow-list is even better: compare the choice against a fixed list of names in your code, and use only the value from the list.

## Try it yourself

Rewrite `find_unsafe` so it filters on both a last name and a store id using `USING $1, $2`, and try the same malicious input.

## Watch out

### Never build SQL by concatenating input

That is the whole lesson. If you see `"... WHERE name = '" + input + "'"` in code, it is a bug waiting for an attacker.

### Escaping is not enough

Hand-written "escape the quotes" functions get forgotten and bypassed. If you must build text, use `format('%L')` / `quote_literal`, or better, parameters.

### Stacked queries

Some drivers allow several statements in one call (`...; DROP TABLE ...`). Prefer the extended query protocol (parameters), which sends one statement at a time.

### Defence in depth

- Connect with a role that has **only the privileges the app needs** (page 16.1). A search box should never connect as a superuser.
- Validate input (length, format), as an extra layer.
- Hide detailed database errors from users.
- Keep software patched.

### A prepared statement is not always a speed-up

Parsing is a small part of most queries. The main reason to use prepared statements is **safety**. PostgreSQL may also switch between a custom and a generic plan after several executions (`plan_cache_mode`).

## Interview corner

**"What is SQL injection, and how do you prevent it?"**
Attacker-controlled input changes the structure of a query because it was concatenated into the SQL text. Prevent it with parameterised queries (prepared statements), least-privilege database roles, and input validation. Escaping alone is not sufficient.

**"Can you use a parameter for a column name?"**
No. Placeholders are for values only. For identifiers, check the input against an allow-list, or use `format('%I', ...)`.

**"What can an attacker do with SQL injection?"**
Read data they should not see (including other tables), bypass logins, change or delete data, and sometimes run commands on the server, depending on privileges.

**"Why does connecting as a low-privilege role help?"**
Even if an injection succeeds, the attacker can only do what that role may do, not drop tables or read the `pg_authid` catalogue.
