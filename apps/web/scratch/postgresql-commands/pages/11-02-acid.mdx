**ACID** is the promise a transactional database makes about your data. It stands for Atomicity, Consistency, Isolation and Durability, and it is one of the most common interview questions there is. Here you see each letter happen for real.

## What you'll learn

- What each letter of ACID guarantees
- How to see atomicity and consistency in action
- What makes a commit durable (the write-ahead log)

## The four letters

| Letter | Promise | Example |
|---|---|---|
| **A**tomicity | All the statements in a transaction take effect, or none | A transfer never moves money out without moving it in |
| **C**onsistency | Every committed state obeys the rules (constraints) | No account below zero |
| **I**solation | Concurrent transactions do not see each other's half-done work | Two transfers at once do not corrupt the balance |
| **D**urability | Once committed, the data survives a crash | The transfer is still there after a power cut |

## Set up

The `CHECK` is a rule the database enforces: no account may go below zero.

```sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance numeric NOT NULL CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'Asha', 100), (2, 'Ben', 100);
```

## Atomicity: all or nothing

A transfer of 150 from Asha, who has only 100. The first step (adding 150 to Ben) works. The second step breaks the rule, so the whole transfer must be undone:

```sql
BEGIN;
UPDATE account SET balance = balance + 150 WHERE owner = 'Ben';
UPDATE account SET balance = balance - 150 WHERE owner = 'Asha';
ROLLBACK;

SELECT * FROM account ORDER BY id;
```

```text
ERROR:  new row for relation "account" violates check constraint "account_balance_check"
DETAIL:  Failing row contains (1, Asha, -50).
```

| id | owner | balance |
|---:|---|---:|
| 1 | Asha | 100 |
| 2 | Ben | 100 |

*2 rows returned.*

The second update failed, we rolled back, and **Ben's +150 disappeared too**. Both balances are back to 100. Without the transaction, Ben would have kept money that never left Asha.

## Consistency: the rules always hold

The failed statement above shows consistency as well: PostgreSQL refused the update, because it would have broken the `CHECK`. A foreign key protects data in the same way:

```sql
INSERT INTO rental (inventory_id, customer_id, staff_id, rental_period)
VALUES (1, 99999, 1, tsrange(now()::timestamp, NULL));
```

```text
ERROR:  smallint out of range
```

No committed state ever breaks a constraint. The rules are part of the database, not left to the application.

## Isolation: transactions do not interfere

While one transaction is half done, another must not see the half-done state (or, at least, only in ways you have chosen). Exactly how strict this is depends on the **isolation level**, which is the topic of the next page. The default level in PostgreSQL is:

```sql
SHOW default_transaction_isolation;
```

| default_transaction_isolation |
|---|
| read committed |

*1 row returned.*

## Durability: a commit survives a crash

When you `COMMIT`, PostgreSQL writes the change to its **write-ahead log (WAL)** on disk before it says "done". After a crash, PostgreSQL replays that log and the committed data is back. How strictly the log is flushed is a setting:

```sql
SELECT name, setting
FROM pg_settings
WHERE name IN ('synchronous_commit', 'fsync', 'wal_level')
ORDER BY name;
```

| name | setting |
|---|---|
| fsync | on |
| synchronous_commit | on |
| wal_level | replica |

*3 rows returned.*

`synchronous_commit = on` (the default) waits for the log to reach disk at every commit, which is the safe choice. `off` is faster but can lose the last fraction of a second of commits in a crash (never corrupting the database). `fsync = off` is dangerous and only for throwaway data.

## Try it yourself

Add a `CHECK (balance <= 1000)`, and try a transfer that would take an account above 1000. See which statement fails.

## Watch out

### ACID is a property of your transactions, not just the engine

You get it by using transactions properly. Two statements run outside a transaction, in autocommit mode, are two separate commits, and a failure between them leaves the data half changed.

### Atomicity does not mean you ignore errors

The database keeps the promise only if you call `ROLLBACK` (or the connection drops). Application code has to handle errors.

### Consistency means constraint consistency, not "correct"

The database guarantees your rules hold. It cannot know a business rule you never wrote as a constraint.

## Interview corner

**"Explain ACID."**
Atomicity: all or nothing. Consistency: constraints hold before and after. Isolation: concurrent transactions do not see each other's uncommitted work. Durability: committed data survives a crash. Give the bank-transfer example.

**"How does PostgreSQL provide atomicity and durability?"**
Atomicity comes from MVCC: changes are new row versions that only become visible at commit, so a rollback just ignores them. Durability comes from the write-ahead log, which is flushed to disk at commit and replayed after a crash.

**"How is isolation implemented?"**
With MVCC (multi-version concurrency control): each statement or transaction reads from a snapshot, so readers do not block writers. Locks handle write conflicts. The next pages show both.

### Core: a failed transfer leaves nothing behind

Create the `account` table above (with the `CHECK`), start a transaction, take 500 from Asha (this breaks the rule), and roll back. Return the balances `owner` and `balance`, ordered by `id`.

**Your result should look like this:**

| owner | balance |
|---|---:|
| Asha | 100 |
| Ben | 100 |

*2 rows returned.*

<details>
<summary>Hint</summary>

The failing UPDATE aborts the transaction; end with ROLLBACK, then SELECT.

</details>

<details>
<summary>Show solution</summary>

```sql
CREATE TABLE account5 (id int PRIMARY KEY, owner text NOT NULL, balance numeric NOT NULL CHECK (balance >= 0));
INSERT INTO account5 VALUES (1, 'Asha', 100), (2, 'Ben', 100);

BEGIN;
UPDATE account5 SET balance = balance - 500 WHERE owner = 'Asha';
ROLLBACK;

SELECT owner, balance FROM account5 ORDER BY id;
```
