Every database will one day lose data: a mistaken `DELETE`, a bad deployment, a failed disk. A **backup** is the only real protection, and **a backup you have never restored is only a hope**. This page shows how to take a backup with `pg_dump`, restore it, and prove it worked, and explains how point-in-time recovery works.

## What you'll learn

- Logical backups with `pg_dump` (plain SQL and custom format)
- Restoring with `psql` and `pg_restore`
- Checking a restore
- Point-in-time recovery and WAL archiving, in outline

## Logical and physical backups

A **logical** backup (`pg_dump`) exports the data as SQL or a portable archive. It is easy to read and restore, and can move between versions, but is slower on very large databases. A **physical** backup (`pg_basebackup`, storage snapshots) copies the data files, and together with archived WAL it enables point-in-time recovery. This page uses `pg_dump`, which ships with PostgreSQL.

## Take a backup, and restore it

The commands below run in a terminal on your machine, in the `sypher-db-lab` folder. First a small table to back up:

```sql
CREATE TABLE backup_demo AS SELECT category_id, name FROM category;
CREATE TABLE backup_demo_keep AS SELECT * FROM backup_demo;
```

Dump that table to a plain SQL file. `--no-owner` leaves out ownership commands, so the file restores under any account. The file is just text:

```bash
docker compose exec -T postgres pg_dump -U sypher -d sypher-postgresql-DvdRental -t backup_demo --no-owner > backup_demo_one.sql
grep -c '' backup_demo_one.sql
grep -E '^(CREATE TABLE|COPY)' backup_demo_one.sql
```

```text
65
CREATE TABLE public.backup_demo (
COPY public.backup_demo (category_id, name) FROM stdin;
```

The file holds a `CREATE TABLE` and a `COPY` with the rows. Now destroy the table, and restore it from the file (in one run of commands, so the file is still there):

```bash
docker compose exec -T postgres pg_dump -U sypher -d sypher-postgresql-DvdRental -t backup_demo --no-owner > backup_demo_two.sql
docker compose exec -T postgres psql -X -q -U sypher -d sypher-postgresql-DvdRental -c 'DROP TABLE backup_demo'
docker compose exec -T postgres psql -X -q -U sypher -d sypher-postgresql-DvdRental < backup_demo_two.sql > /dev/null
docker compose exec -T postgres psql -X -At -U sypher -d sypher-postgresql-DvdRental -c 'SELECT COUNT(*) FROM backup_demo'
```

```text
16
```

The table is back, with its rows.

## The custom format, and restoring somewhere else

The custom format (`-Fc`) is compressed, and `pg_restore` can restore parts of it, in parallel, into any database. Here we dump the **whole** database, list what it contains, and restore into a new scratch database:

```bash
docker compose exec -T postgres pg_dump -U sypher -d sypher-postgresql-DvdRental -Fc --no-owner -f /tmp/full.dump
docker compose exec -T postgres pg_restore -l /tmp/full.dump | grep -c 'TABLE DATA'
docker compose exec -T postgres createdb -U sypher scratch_restore
docker compose exec -T postgres pg_restore -U sypher -d scratch_restore --no-owner /tmp/full.dump
docker compose exec -T postgres psql -X -At -U sypher -d scratch_restore -c 'SELECT COUNT(*) FROM film'
docker compose exec -T postgres dropdb -U sypher scratch_restore
```

```text
24
1000
```

The dump contains one `TABLE DATA` entry per table (partitions included). The restore into `scratch_restore` brought back all films. Always restore into a scratch database first, and compare with the original.

## Windows: PowerShell and redirection

In Windows PowerShell, the `>` operator does not write plain UTF-8: depending on the version it writes UTF-16 or adds a byte-order mark, and `psql` may then fail to read the dump (typically with a syntax error on the very first line). To stay safe, let the container write the file itself (`-f /tmp/file`) and copy it out with `docker compose cp postgres:/tmp/file .`.

## Point-in-time recovery (PITR)

A nightly backup means losing up to a day of work. To recover to *just before a mistake*, PostgreSQL writes every change to the **write-ahead log (WAL)**. If you archive the WAL, you can restore a base backup and then **replay the log up to a chosen moment**. These are the settings that make it possible:

```sql
SELECT name, setting
FROM pg_settings
WHERE name IN ('wal_level', 'archive_mode', 'archive_command', 'max_wal_senders')
ORDER BY name;
```

| name | setting |
|---|---|
| archive_command | (disabled) |
| archive_mode | off |
| max_wal_senders | 10 |
| wal_level | replica |

*4 rows returned.*

This lab does not archive its WAL (`archive_mode` is off), so PITR is not set up here. The outline on a real server:

```sql
-- postgresql.conf
archive_mode = on
archive_command = 'cp %p /backups/wal/%f'

-- restore: put a base backup in place, then in postgresql.conf
restore_command = 'cp /backups/wal/%f %p'
recovery_target_time = '2026-01-15 09:59:00'
-- create an empty recovery.signal file and start the server
```

## Watch out

### An untested backup is not a backup

Restore into a scratch database regularly, and check the row counts and a few real queries. Discovering that a backup file is empty or corrupt during an emergency is far too late.

### Keep backups somewhere else

A backup on the same disk as the database dies with it. Copy backups to another machine or to cloud storage, and keep several generations.

### pg_dump is consistent, but roles are separate

`pg_dump` takes a consistent snapshot of one database without blocking writers. It does **not** dump roles and cluster-wide settings: use `pg_dumpall --globals-only` for those.

### Dumps contain everything, including secrets

The dump holds all your data. Encrypt it and control who can read it.

### Passwords on the command line are visible

`PGPASSWORD` or a password in a connection string can show up in a process list. In real scripts, use a protected `.pgpass` file or a service file.

### Analyse after restoring

A restored database has no planner statistics until `ANALYZE` runs (page 14.8).

### Know your recovery targets

How much data can you afford to lose (**RPO**), and how long can you be down (**RTO**)? A nightly dump gives an RPO of a day. WAL archiving brings it to seconds, and a replica shortens the RTO.

## Interview corner

**"How do you back up a PostgreSQL database?"**
Logically with `pg_dump` (plain or `-Fc` custom format, restored with `psql` or `pg_restore`), or physically with `pg_basebackup` plus archived WAL for point-in-time recovery, or with a storage snapshot.

**"How do you restore a backup?"**
`psql db < backup.sql` for a plain dump, or `pg_restore -d db backup.dump` for the custom format (with `-j` for parallel restore).

**"What is point-in-time recovery?"**
Restoring a base backup and then replaying the archived write-ahead log up to just before the failure, so you lose almost nothing.

**"How do you know a backup is good?"**
By restoring it regularly to a test server and verifying the data.

**"What are RPO and RTO?"**
Recovery Point Objective: the most data loss you accept, measured in time. Recovery Time Objective: how long recovery may take.
