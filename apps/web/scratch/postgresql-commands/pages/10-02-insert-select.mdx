`INSERT ... SELECT` fills a table from the result of a query. Instead of typing the values, you tell PostgreSQL where to get them. It is how you copy, archive and transform data in bulk.

## What you'll learn

- Copying rows from one table into another
- Making a table with the same structure (`LIKE`)
- Creating a table from a query (`CREATE TABLE AS`)
- `SELECT ... INTO` and `RETURNING`

## Syntax

```sql
INSERT INTO target_table (column1, column2)
SELECT column1, column2
FROM source_table
WHERE condition;

CREATE TABLE new_table AS
SELECT ... FROM source_table;
```

The columns you insert into and the columns you select must match in number and type.

## Examples

### Copy some rows into a new table

First create an empty table with the same structure as `film`, then copy the long films into it. `LIKE ... INCLUDING DEFAULTS INCLUDING CONSTRAINTS` copies the columns plus their defaults and rules:

```sql
CREATE TABLE film_long (LIKE film INCLUDING DEFAULTS INCLUDING CONSTRAINTS);

INSERT INTO film_long
SELECT * FROM film WHERE length > 180;

SELECT COUNT(*) AS copied FROM film_long;
```

| copied |
|---:|
| 39 |

*1 row returned.*

### Choose the columns

Insert only some columns. Here, a small table of active customers' emails:

```sql
CREATE TABLE mailing_list (customer_id int PRIMARY KEY, email text NOT NULL);

INSERT INTO mailing_list (customer_id, email)
SELECT customer_id, email FROM customer WHERE activebool;

SELECT COUNT(*) AS subscribers FROM mailing_list;
```

| subscribers |
|---:|
| 549 |

*1 row returned.*

### Create and fill in one step

`CREATE TABLE ... AS SELECT` builds the table from the query result in one go:

```sql
CREATE TABLE rating_report AS
SELECT rating, COUNT(*) AS films, round(AVG(length), 1) AS avg_length
FROM film
GROUP BY rating;

SELECT * FROM rating_report ORDER BY rating;
```

| rating | films | avg_length |
|---|---:|---:|
| G | 178 | 111.1 |
| PG | 194 | 112.0 |
| PG-13 | 223 | 120.4 |
| R | 195 | 118.7 |
| NC-17 | 210 | 113.2 |

*5 rows returned.*

The new table gets the query's columns, but not the keys, defaults or indexes of the source.

### Transforming while copying

Calculations, joins and functions all work in the `SELECT`:

```sql
CREATE TABLE customer_names AS
SELECT customer_id, initcap(last_name) || ', ' || initcap(first_name) AS badge
FROM customer;

SELECT * FROM customer_names ORDER BY customer_id LIMIT 3;
```

| customer_id | badge |
|---:|---|
| 1 | Smith, Mary |
| 2 | Johnson, Patricia |
| 3 | Williams, Linda |

*3 rows returned.*

## Watch out

### Column count must match

```sql
CREATE TABLE tiny (a int, b int);
INSERT INTO tiny (a, b) SELECT film_id FROM film;
```

```text
ERROR:  INSERT has more target columns than expressions
LINE 1: INSERT INTO tiny (a, b) SELECT film_id FROM film;
                             ^
```

The `SELECT` returns one column but the `INSERT` names two, so PostgreSQL refuses. The columns you insert into and the columns you select must match in number.

### Generated columns cannot be inserted into

The `film` table has two **generated columns** (`rentals_to_breakeven` and `revenue_projection`), whose values PostgreSQL calculates itself. `INCLUDING ALL` copies them as generated columns, and then `SELECT *` cannot supply a value for them:

```sql
CREATE TABLE film_generated (LIKE film INCLUDING ALL);
INSERT INTO film_generated SELECT * FROM film WHERE film_id = 1;
```

```text
ERROR:  cannot insert a non-DEFAULT value into column "rentals_to_breakeven"
DETAIL:  Column "rentals_to_breakeven" is a generated column.
```

List the ordinary columns in the `INSERT`, or copy with `INCLUDING DEFAULTS` as above (which turns them into plain columns).

### Copying into a table with a primary key can collide

If you run the same `INSERT ... SELECT` twice into a table with a primary key, the second run fails with a duplicate-key error. Use `ON CONFLICT DO NOTHING` or `ON CONFLICT DO UPDATE` (page 10.5) to handle re-runs.

### CREATE TABLE ... AS SELECT loses constraints

The new table has the data but no primary key, foreign keys or indexes. Use `CREATE TABLE ... (LIKE ... INCLUDING ALL)` followed by `INSERT ... SELECT` when you need the structure too.

### A table you copy into is not kept in sync

The copy is a snapshot. Changes to the original later are not reflected. (For a copy that stays up to date, use a view or a materialised view: Module 15.)

## Interview corner

**"How do you copy data from one table into another?"**
`INSERT INTO target (cols) SELECT cols FROM source WHERE ...`.

**"What is the difference between `CREATE TABLE ... (LIKE ...)` and `CREATE TABLE ... AS SELECT`?"**
`LIKE ... INCLUDING ALL` copies the structure (columns, defaults, constraints, indexes) and no data. `AS SELECT` copies the query result's columns and data, but not the keys and indexes.

**"How would you back up a table quickly before a risky change?"**
`CREATE TABLE t_backup AS TABLE t;` (`TABLE t` is shorthand for `SELECT * FROM t`), or `LIKE` plus `INSERT ... SELECT` if you want the indexes too.
