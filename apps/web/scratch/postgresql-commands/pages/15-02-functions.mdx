A **function** is a named piece of logic that takes values and **returns** a result. Unlike a procedure, you do not `CALL` it: you use it inside a query, exactly like `upper()` or `round()`. It is how you teach PostgreSQL a calculation of your own. Because your lab account is a superuser, there are no extra privileges to worry about.

## What you'll learn

- Creating a function with `CREATE OR REPLACE FUNCTION ... RETURNS`
- The languages `sql` and `plpgsql`
- Functions that return several rows (`RETURNS TABLE`)
- Volatility: `IMMUTABLE`, `STABLE`, `VOLATILE`

## Syntax

```sql
CREATE OR REPLACE FUNCTION name(arg type, ...)
RETURNS return_type
LANGUAGE sql          -- or plpgsql
[IMMUTABLE | STABLE | VOLATILE]
AS $$
  -- body
$$;
```

The body sits between `$$` markers (dollar quoting), so quotes and semicolons inside it need no special care.

## Examples

### Functions that already exist

The DVD Rental database has some, in the `public` schema. Their names, arguments and languages are in `pg_proc`:

```sql
SELECT p.proname AS name, pg_get_function_arguments(p.oid) AS arguments, l.lanname AS language
FROM pg_proc p
JOIN pg_language l ON l.oid = p.prolang
WHERE p.pronamespace = 'public'::regnamespace AND p.proname IN ('inventory_in_stock', 'last_day', 'get_customer_balance')
ORDER BY p.proname;
```

| name | arguments | language |
|---|---|---|
| get_customer_balance | p_customer_id integer, p_effective_date timestamp without time zone | plpgsql |
| inventory_in_stock | p_inventory_id integer | plpgsql |
| last_day | timestamp without time zone | sql |

*3 rows returned.*

`last_day` is one that works:

```sql
SELECT last_day(timestamp '2007-02-10') AS end_of_february;
```

| end_of_february |
|---|
| 2007-02-28 |

*1 row returned.*

### A shipped function that is broken

`inventory_in_stock` was written when `rental` still had a `return_date` column. That column was later replaced by the `rental_period` range, and PostgreSQL does **not** re-check a function's body when a table changes, so the function now fails when called:

```sql
SELECT inventory_in_stock(1);
```

```text
ERROR:  column rental.return_date does not exist
LINE 3:     AND rental.return_date IS NULL
                ^
QUERY:  SELECT COUNT(rental_id)                 FROM inventory LEFT JOIN rental USING(inventory_id)
    WHERE inventory.inventory_id = p_inventory_id
    AND rental.return_date IS NULL
CONTEXT:  PL/pgSQL function inventory_in_stock(integer) line 17 at SQL statement
```

This is a real lesson: unlike a view, a function is only checked when it runs. Here is a repaired version that reads the new range column. A copy is in stock when it has no rental that is still open (`upper_inf`):

```sql
CREATE OR REPLACE FUNCTION copy_in_stock(p_inventory_id integer) RETURNS boolean
LANGUAGE sql STABLE
AS $$
  SELECT NOT EXISTS (SELECT 1 FROM rental WHERE inventory_id = p_inventory_id AND upper_inf(rental_period))
$$;

SELECT inventory_id, copy_in_stock(inventory_id) AS in_stock
FROM inventory
WHERE inventory_id BETWEEN 1 AND 4
ORDER BY inventory_id;
```

| inventory_id | in_stock |
|---:|---|
| 1 | t |
| 2 | t |
| 3 | t |
| 4 | t |

*4 rows returned.*

### A calculation with no table access

A function that turns a rental price into a band. `IMMUTABLE` promises that the same input always gives the same output:

```sql
CREATE OR REPLACE FUNCTION rate_band(rate numeric) RETURNS text
LANGUAGE sql IMMUTABLE
AS $$
  SELECT CASE WHEN rate < 1 THEN 'Budget' WHEN rate < 3 THEN 'Regular' ELSE 'Premium' END
$$;

SELECT rate_band(0.99) AS a, rate_band(2.99) AS b, rate_band(4.99) AS c;
```

| a | b | c |
|---|---|---|
| Budget | Regular | Premium |

*1 row returned.*

### Using it anywhere a value fits

Once it exists, a function works in `WHERE`, `GROUP BY` and `ORDER BY` too:

```sql
CREATE OR REPLACE FUNCTION rate_band(rate numeric) RETURNS text
LANGUAGE sql IMMUTABLE
AS $$ SELECT CASE WHEN rate < 1 THEN 'Budget' WHEN rate < 3 THEN 'Regular' ELSE 'Premium' END $$;

SELECT rate_band(rental_rate) AS band, COUNT(*) AS films
FROM film
GROUP BY 1
ORDER BY 1;
```

| band | films |
|---|---:|
| Budget | 341 |
| Premium | 336 |
| Regular | 323 |

*3 rows returned.*

### PL/pgSQL: variables, IF and loops

`plpgsql` is PostgreSQL's procedural language. It adds variables, `IF`, loops and error handling:

```sql
CREATE OR REPLACE FUNCTION customer_tier(p_customer_id integer) RETURNS text
LANGUAGE plpgsql STABLE
AS $$
DECLARE
  total numeric;
BEGIN
  SELECT COALESCE(SUM(amount), 0) INTO total FROM payment WHERE customer_id = p_customer_id;
  IF total >= 150 THEN
    RETURN 'gold';
  ELSIF total >= 100 THEN
    RETURN 'silver';
  ELSE
    RETURN 'bronze';
  END IF;
END;
$$;

SELECT customer_id, customer_tier(customer_id) AS tier FROM customer WHERE customer_id <= 3 ORDER BY customer_id;
```

| customer_id | tier |
|---:|---|
| 1 | silver |
| 2 | silver |
| 3 | silver |

*3 rows returned.*

### A function that returns rows

`RETURNS TABLE` makes a function you can use in `FROM`, like a parameterised view:

```sql
CREATE OR REPLACE FUNCTION films_in_category(p_name text)
RETURNS TABLE (film_id integer, title text)
LANGUAGE sql STABLE
AS $$
  SELECT f.film_id, f.title::text
  FROM film f
  JOIN film_category fc ON fc.film_id = f.film_id
  JOIN category c ON c.category_id = fc.category_id
  WHERE c.name = p_name
$$;

SELECT * FROM films_in_category('Horror') ORDER BY film_id LIMIT 3;
```

| film_id | title |
|---:|---|
| 2 | ACE GOLDFINGER |
| 4 | AFFAIR PREJUDICE |
| 8 | AIRPORT POLLOCK |

*3 rows returned.*

### Defaults and named arguments

```sql
CREATE OR REPLACE FUNCTION greet(name text, greeting text DEFAULT 'Hello') RETURNS text
LANGUAGE sql IMMUTABLE AS $$ SELECT greeting || ', ' || name || '!' $$;

SELECT greet('Asha') AS a, greet('Ben', greeting => 'Hi') AS b;
```

| a | b |
|---|---|
| Hello, Asha! | Hi, Ben! |

*1 row returned.*

CREATE OR REPLACE FUNCTION tmp_fn() RETURNS int LANGUAGE sql AS 'SELECT 1';

## Watch out

### Volatility matters

`IMMUTABLE` (same input, same output, no table reads) lets PostgreSQL cache and index on the function. `STABLE` (may read tables but not change data, constant within a statement) suits lookups. `VOLATILE` (the default) may do anything, and is re-run for every row. Declaring `IMMUTABLE` when it is not true gives wrong cached results.

### A function runs once per row

`customer_tier(customer_id)` in a query over 599 customers runs a query 599 times. On a large table this is far slower than a single `JOIN` with `GROUP BY`. Use functions for small, cheap calculations, not for fetching data row by row.

### A function on a column blocks an index

As with `date_trunc(col)`, `WHERE my_function(col) = x` cannot use an index on `col` (unless you index the function's result, which needs an `IMMUTABLE` function).

### Overloading by argument types

The same name with different argument types is a different function. `DROP FUNCTION name` may be ambiguous: write `DROP FUNCTION name(numeric)`.

### SECURITY DEFINER runs with the owner's rights

A `SECURITY DEFINER` function runs with the privileges of its creator, not the caller. That is powerful and dangerous: set `search_path` inside it.

## Interview corner

**"What is the difference between a function and a procedure?"**
A function returns a value and is used inside SQL expressions. A procedure (page 15.3) is run with `CALL`, returns no value (other than `OUT` parameters), and can control transactions.

**"What do `IMMUTABLE`, `STABLE` and `VOLATILE` mean?"**
`IMMUTABLE`: the result depends only on the arguments. `STABLE`: constant within one statement but may read the database. `VOLATILE`: may change from call to call and may modify data. The planner uses these to optimise and to allow indexes.

**"When would you write a function in `sql` and when in `plpgsql`?"**
`sql` for a single query (it can be inlined into the caller and optimised). `plpgsql` when you need variables, branching, loops or exception handling.

### Stretch: a function that reads a table

Create `films_of_category(p_name text) RETURNS integer` (language `sql`, `STABLE`) returning the number of films in that category. Return `films_of_category('Horror')` as `horror_films`.

**Your result should look like this:**

| horror_films |
|---:|
| 56 |

*1 row returned.*

<details>
<summary>Hint</summary>

A SELECT COUNT(*) joining film_category and category.

</details>

<details>
<summary>Show solution</summary>

```sql
CREATE OR REPLACE FUNCTION films_of_category(p_name text) RETURNS integer LANGUAGE sql STABLE AS $$
  SELECT COUNT(*)::integer FROM film_category fc JOIN category c ON c.category_id = fc.category_id WHERE c.name = p_name
$$;

SELECT films_of_category('Horror') AS horror_films;
```

</details>
