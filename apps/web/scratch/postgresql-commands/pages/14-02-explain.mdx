`EXPLAIN` shows **how PostgreSQL plans to run a query**: which indexes it will use, in what order it will read the tables, how it will join them, and roughly how many rows it expects at each step. It is the first tool you reach for when a query is slow, and a very common interview topic.

## What you'll learn

- How to read a plan: nodes, costs and row estimates
- The scan types: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`
- The join types: `Nested Loop`, `Hash Join`, `Merge Join`
- What `EXPLAIN ANALYZE` adds, and its warning

## Syntax

```sql
EXPLAIN SELECT ...;                           -- the plan, with estimates; does NOT run the query
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;        -- RUNS the query, adds real rows, time and pages read
EXPLAIN (COSTS OFF) SELECT ...;               -- plan shape only, easier to read
```

`EXPLAIN` does not run the query. `EXPLAIN ANALYZE` **does run it**, so wrap data-changing statements in a transaction you roll back.

## Step zero: refresh the statistics

`EXPLAIN` is only as good as PostgreSQL's **statistics** about a table: how many rows it has, and how the values are spread. Autovacuum keeps them fresh in the background, but right after a database is first loaded they can be missing or out of date, and every plan on this page would look wrong. `VACUUM (ANALYZE)` refreshes them (and marks pages as "all visible", which makes index-only scans possible):

```sql
VACUUM (ANALYZE) film, rental, customer, inventory, payment, actor, film_actor;
```

Run `ANALYZE` whenever a plan looks strange after a big load or a big change.

## Reading a plan

The plan is a tree. Indentation shows nesting: the inner lines run first and feed the outer ones. Here is a query with the numbers shown:

```sql
EXPLAIN SELECT * FROM film WHERE film_id = 100;
```

```text
Index Scan using film_pkey on film  (cost=0.28..8.30 rows=1 width=395)
  Index Cond: (film_id = 100)
```

Each node shows `(cost=start..total rows=N width=bytes)`. **Cost** is PostgreSQL's own unit (mostly disk pages read), **rows** the estimated number of result rows, and **width** the average row size in bytes. The numbers are estimates: only compare them with each other.

## The scan types

### Index Scan: one row by primary key

```sql
EXPLAIN (COSTS OFF) SELECT * FROM film WHERE film_id = 100;
```

```text
Index Scan using film_pkey on film
  Index Cond: (film_id = 100)
```

### Bitmap Heap Scan: several rows by an index

When a query matches a moderate number of rows, PostgreSQL first collects their positions from the index into a bitmap, then reads those table pages in order:

```sql
EXPLAIN (COSTS OFF) SELECT * FROM film_actor WHERE film_id < 20;
```

```text
Bitmap Heap Scan on film_actor
  Recheck Cond: (film_id < 20)
  ->  Bitmap Index Scan on idx_fk_film_id
        Index Cond: (film_id < 20)
```

### Seq Scan: no usable index

`length` has no index, so PostgreSQL has to read the whole table:

```sql
EXPLAIN (COSTS OFF) SELECT * FROM film WHERE length > 100;
```

```text
Seq Scan on film
  Filter: (length > 100)
```

### Index Only Scan: a covering index

If every column the query needs is inside the index, PostgreSQL never reads the table:

```sql
EXPLAIN (COSTS OFF) SELECT film_id FROM film WHERE film_id < 20;
```

```text
Index Only Scan using film_pkey on film
  Index Cond: (film_id < 20)
```

### Sorting

Sorting by an unindexed column makes PostgreSQL sort the rows itself:

```sql
EXPLAIN (COSTS OFF) SELECT * FROM film ORDER BY length;
```

```text
Sort
  Sort Key: length
  ->  Seq Scan on film
```

## Join types

For a join, the plan shows how the two inputs are combined:

```sql
EXPLAIN (COSTS OFF)
SELECT c.last_name, r.rental_id
FROM customer c
JOIN rental r ON r.customer_id = c.customer_id
WHERE c.customer_id = 5;
```

```text
Nested Loop
  ->  Index Scan using customer_pkey on customer c
        Index Cond: (customer_id = 5)
  ->  Seq Scan on rental r
        Filter: (customer_id = 5)
```

Read it from the inside out. `customer` is found by its primary key (`Index Scan`), and for that one customer the join looks for matching rentals. Look at the last node: `Seq Scan on rental`. The `rental` table has **no index on `customer_id`**, so PostgreSQL must read every rental to find that customer's. That is a real gap in this database, and pages 14.3 and 14.6 fix it.

| Join node | How it works | Good when |
|---|---|---|
| `Nested Loop` | For each row of one side, look up matches on the other | One side is small, and the other has an index |
| `Hash Join` | Build a hash table of one side, probe it with the other | Large inputs, equality join |
| `Merge Join` | Walk two sorted inputs together | Both inputs already sorted |

## EXPLAIN ANALYZE: what really happened

`EXPLAIN` guesses. `EXPLAIN ANALYZE` **runs the query** and adds the actual row counts for each step, so you can compare the estimate with reality:

```sql
EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF)
SELECT * FROM rental WHERE customer_id = 5;
```

```text
Seq Scan on rental (actual rows=38.00 loops=1)
  Filter: (customer_id = 5)
  Rows Removed by Filter: 16006
```

Compare `rows` (the estimate, in a plain `EXPLAIN`) with `actual rows`. A big gap means stale or misleading statistics: run `ANALYZE`. With `TIMING` and `BUFFERS` left on, the output also shows the real time per step and how many pages came from cache (`shared hit`) or disk (`read`). Those numbers change on every run, so we switched them off here, but you should run it yourself.

Run `EXPLAIN` on a few of your own queries from earlier in this course. Which ones scan the whole table (`Seq Scan`)? Which use an index?

## Watch out

### Estimates are guesses

`rows=` is an estimate from statistics, not a count. It can be far off after big changes, or for skewed data. `ANALYZE` refreshes it, and `EXPLAIN ANALYZE` shows what really happened.

### A Seq Scan is fine on a small table

On a table with 20 rows, a full scan is faster than using an index. Do not add indexes to fix a "problem" on small tables.

### EXPLAIN ANALYZE really executes the query

An `INSERT`, `UPDATE` or `DELETE` under `EXPLAIN ANALYZE` changes the data. Use `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`.

### The plan can change

The plan depends on the data and statistics. A query that is fast today may switch to a worse plan as the table grows, or after a large `DELETE` without `ANALYZE`.

### The first run may be slow

Data that is not yet in memory is read from disk. Run a query twice before you compare timings, and look at `Buffers` too.

## Interview corner

**"How do you find out why a query is slow?"**
Run `EXPLAIN (ANALYZE, BUFFERS)` and look for `Seq Scan` on a big table, estimates far from actual rows, a `Sort` that spills to disk, and nested loops with huge loop counts. Then add or change an index, or rewrite the query.

**"What is the difference between `Seq Scan`, `Index Scan` and `Bitmap Heap Scan`?"**
`Seq Scan` reads the whole table. `Index Scan` follows the index and fetches each row as it goes. `Bitmap Heap Scan` collects matching positions from the index first, then reads the table pages in order, which is better for medium numbers of rows.

**"What is the difference between `EXPLAIN` and `EXPLAIN ANALYZE`?"**
`EXPLAIN` shows the estimated plan without running the query. `EXPLAIN ANALYZE` runs it and adds real timings and row counts.

**"What does `Index Only Scan` mean?"**
The query was answered from the index alone, without visiting the table (for pages the visibility map marks as all visible).
