A **CTE** (common table expression) is a named, temporary result you define at the top of a query with `WITH`, then use like a table. It turns a tangle of nested subqueries into steps you can read from top to bottom.

## What you'll learn

- Writing a query with `WITH`
- Chaining several CTEs
- `MATERIALIZED` and `NOT MATERIALIZED`
- Data-modifying CTEs with `RETURNING`

## Syntax

```sql show
WITH step_one AS (
  SELECT ...
),
step_two AS (
  SELECT ... FROM step_one
)
SELECT ... FROM step_two;
```

## Examples

### Step one, then step two

Total spending per customer first, then compare with the average. Each step has a name:

```sql run
WITH totals AS (
  SELECT customer_id, SUM(amount) AS total_spent
  FROM payment
  GROUP BY customer_id
)
SELECT customer_id, total_spent
FROM totals
WHERE total_spent > (SELECT AVG(total_spent) FROM totals)
ORDER BY total_spent DESC, customer_id
LIMIT 5;
```

This is the question from the subquery page, and you can now read it in order. A CTE can also be used more than once in the same query, as `totals` is here.

### Several CTEs

Separate them with commas. Each can use the ones before it:

```sql run
WITH per_film AS (
  SELECT f.film_id, f.rating, COUNT(*) AS rentals
  FROM film f
  JOIN inventory i ON i.film_id = f.film_id
  JOIN rental r ON r.inventory_id = i.inventory_id
  GROUP BY f.film_id, f.rating
),
per_rating AS (
  SELECT rating, SUM(rentals) AS rentals, COUNT(*) AS films
  FROM per_film
  GROUP BY rating
)
SELECT rating, films, rentals, round(rentals::numeric / films, 1) AS rentals_per_film
FROM per_rating
ORDER BY rating;
```

### Controlling how a CTE runs

Since PostgreSQL 12 a CTE that is used **once** is merged into the main query like a subquery. One that is used **twice or more** is computed once and stored. You can override that:

```sql run
WITH long_films AS MATERIALIZED (
  SELECT film_id, title FROM film WHERE length > 180
)
SELECT COUNT(*) AS long_films FROM long_films;
```

`MATERIALIZED` forces "compute once, store it" (a fence the planner cannot see through). `NOT MATERIALIZED` forces the merge.

### A data-modifying CTE

`INSERT`, `UPDATE` and `DELETE` can be CTEs, and their `RETURNING` rows can feed the next step. Here a delete on a scratch copy reports what it removed, in one statement:

```sql run destructive
CREATE TABLE film_copy AS SELECT film_id, title, rating FROM film;

WITH removed AS (
  DELETE FROM film_copy WHERE rating = 'NC-17' AND film_id <= 60 RETURNING film_id, title
)
SELECT COUNT(*) AS rows_removed, MIN(title) AS first_title FROM removed;
```

## Watch out

### A CTE lasts for one query

It is not stored. Once the statement ends, the name is gone (a *view*, Module 15, is the permanent version).

### CTEs are not always faster

Since PostgreSQL 12 they are mostly a readability tool. Before that a CTE was always an optimisation fence, which made some queries slower. Do not add one expecting speed.

### Name clashes

A CTE name hides a real table of the same name inside that query. Do not call a CTE `film` or `payment`.

### A data-modifying CTE always runs

Even if the main query never reads its result, a `WITH ... DELETE` still executes. That is a feature, but read such queries carefully.

## Interview corner

**"What is a CTE, and how is it different from a subquery?"**
A CTE is a named subquery defined first with `WITH`. It reads better, can be reused within the statement, and allows recursion. A plain subquery is written inline and has no name to reuse.

**"Is a CTE faster than a subquery?"**
Not by itself. In PostgreSQL 12 and later a CTE used once is inlined like a subquery; one used several times is computed once. Use `MATERIALIZED` / `NOT MATERIALIZED` to choose.

**"Can a CTE change data?"**
Yes: `WITH x AS (DELETE ... RETURNING *) SELECT ...`. It is a neat way to move rows in one atomic statement.

## Practice

### Warm-up: rewrite with WITH

Using a CTE called `film_stats`, compute per `rating` the number of films and the average length, then show the ratings whose average length is above 115. Return `rating`, `films` and `avg_length` (rounded to 1 decimal), ordered by rating.

```sql practice
-- hint: `WITH film_stats AS (SELECT rating, COUNT(*) AS films, AVG(length) AS avg_length FROM film GROUP BY rating)`.
WITH film_stats AS (
  SELECT rating, COUNT(*) AS films, AVG(length) AS avg_length
  FROM film
  GROUP BY rating
)
SELECT rating, films, round(avg_length, 1) AS avg_length
FROM film_stats
WHERE avg_length > 115
ORDER BY rating;
```

### Core: two steps

Using two CTEs, first find each customer's number of rentals, then show the customers with **more than the average** number of rentals (`customer_id`, `rentals`), most first (ties by `customer_id`). Show the first rows.

```sql practice
-- hint: `counts AS (...)`, then compare to `(SELECT AVG(rentals) FROM counts)`.
WITH counts AS (
  SELECT customer_id, COUNT(*) AS rentals
  FROM rental
  GROUP BY customer_id
)
SELECT customer_id, rentals
FROM counts
WHERE rentals > (SELECT AVG(rentals) FROM counts)
ORDER BY rentals DESC, customer_id;
```

### Stretch: a delete that reports

On a scratch copy `film_scratch` (`CREATE TABLE film_scratch AS SELECT film_id, title FROM film`), delete the films with `film_id` up to 5 with a `WITH ... DELETE ... RETURNING` CTE and return how many rows were removed as `removed`.

```sql practice destructive
-- hint: `WITH gone AS (DELETE FROM film_scratch WHERE film_id <= 5 RETURNING film_id) SELECT COUNT(*) AS removed FROM gone`.
CREATE TABLE film_scratch AS SELECT film_id, title FROM film;

WITH gone AS (
  DELETE FROM film_scratch WHERE film_id <= 5 RETURNING film_id
)
SELECT COUNT(*) AS removed FROM gone;
```
