# Accessibility Testing — Hands On

⏱ 28 minutes

## Breaking It Down

### Step 1: Install `@axe-core/playwright`

From the repo root, alongside your existing `@playwright/test` install:

```bash
npm install --save-dev @axe-core/playwright
```

This package doesn't bundle a separate browser or test runner — it injects the axe-core engine into whatever page your existing Playwright `page` object already has open, and gives you `AxeBuilder`, a fluent builder for configuring and running a scan.

### Step 2: Scan the Login Form

Create `tests/accessibility.spec.ts`. A scan needs nothing but a `page` that's navigated to the screen you want checked:

```typescript title="tests/accessibility.spec.ts"
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test.describe('Accessibility — login form', () => {
  test('has no automatically detectable violations', async ({ page }) => {
    await page.goto('/login');
    await expect(page.getByLabel('Username')).toBeVisible();

    const results = await new AxeBuilder({ page }).analyze();

    expect(results.violations).toEqual([]);
  });
});
```

The `expect(page.getByLabel('Username')).toBeVisible()` line before the scan isn't decoration — it's a web-first wait that guarantees the login form has actually finished rendering before axe inspects the DOM. Without it, `analyze()` can run against a half-rendered page and either miss real violations or report a spurious one that resolves itself a moment later.

`results.violations` is an array, and an empty one means axe didn't find anything to flag against its default ruleset. Give it a run now, with both servers up:

```bash
npx playwright test accessibility.spec.ts
```

### Step 3: Scan an Authenticated Dashboard, Scoped to One Form

A full-page scan of a dashboard is noisier and slower than it needs to be when you only care about one form. `AxeBuilder` lets you scope a scan to a CSS selector with `.include()`, the same way a Playwright locator scopes to a root element:

```typescript title="tests/accessibility.spec.ts"
test.describe('Accessibility — doctor dashboard', () => {
  test.use({ storageState: 'storage/doctor.json' });

  test('Add Medical Record modal has no automatically detectable violations', async ({ page }) => {
    await page.goto('/dashboard');

    const appointmentRow = page.getByRole('row', { name: /Jane Doe/ });
    await appointmentRow.getByRole('button', { name: 'Add Medical Record' }).click();

    const dialog = page.getByRole('dialog');
    await expect(dialog).toBeVisible();

    const results = await new AxeBuilder({ page })
      .include('[role="dialog"]')
      .analyze();

    expect(results.violations).toEqual([]);
  });
});
```

Two things matter about this test beyond the scan itself: it reuses the doctor's `storageState` from the authentication lesson, so there's no login flow inside the test body, and it waits for the dialog to be visible before scanning it — the same rendering-race guard as Step 2, but now guarding against a modal transition instead of a page navigation.

### Step 4: Read and Triage a Violation

Scans don't stay clean forever, though — say the "Add Medical Record" modal's `Notes` textarea loses its `<label>` somewhere down the line, in a future markup change. Here's the kind of entry that shows up in `results.violations` once that happens:

```typescript
[
  {
    id: 'label',
    impact: 'critical',
    description: 'Ensures every form element has a label',
    helpUrl: 'https://dequeuniversity.com/rules/axe/4.9/label',
    nodes: [
      {
        target: ['textarea#notes'],
        html: '<textarea id="notes" name="notes"></textarea>',
        failureSummary:
          'Fix any of the following:\n  Form element does not have an implicit (wrapped) <label>\n  Form element does not have an explicit <label>\n  aria-label attribute does not exist or is empty',
      },
    ],
  },
]
```

Every violation carries an `impact` — `critical`, `serious`, `moderate`, or `minor` — and that field, not where the entry happens to sit in the array, is what tells you how to triage it:

- **`critical`/`serious`** — treat these as build-breaking, every time. A missing form `label`, a button with no accessible name, insufficient `color-contrast` on interactive text — these all land here, and each one means a real category of user simply cannot use the feature.
- **`moderate`** — usually worth fixing, but rarely worth blocking a merge over by itself. A missing landmark region (`<main>`, `<nav>`) is a genuine gap, but it doesn't stop anyone from completing a task.
- **`minor`** — often just noise in context. A `color-contrast` violation against a disabled button's placeholder text, or a `region` rule firing because your scan was scoped with `.include()` to a fragment that legitimately has no `<main>` of its own (the surrounding page already has one) — that's axe correctly applying a rule outside the context that makes it meaningful, not a real defect. Still, read the `nodes[].html` before you dismiss anything as noise; a scoped scan throwing a landmark complaint about the fragment you deliberately scoped to is expected, but it's worth confirming that's actually what's happening.

In practice, most suites assert that `results.violations.filter(v => ['critical', 'serious'].includes(v.impact))` comes back empty, and track `moderate`/`minor` findings separately instead of folding them into the same pass/fail gate — Step 6 below covers what goes wrong when you get either side of that balance wrong.

### Step 5: Tab Order on the Login Form

A scan tells you the username field has a label. It says nothing about whether pressing `Tab` from the page's initial state actually lands there first. Test the real key presses:

```typescript title="tests/keyboard-nav.spec.ts"
import { test, expect } from '@playwright/test';

test.describe('Keyboard navigation — login form', () => {
  test('tab order visits username, password, then submit', async ({ page }) => {
    await page.goto('/login');

    const username = page.getByLabel('Username');
    const password = page.getByLabel('Password');
    const submit = page.getByRole('button', { name: 'Log In' });

    await page.keyboard.press('Tab');
    await expect(username).toBeFocused();

    await page.keyboard.press('Tab');
    await expect(password).toBeFocused();

    await page.keyboard.press('Tab');
    await expect(submit).toBeFocused();
  });

  test('a keyboard-only user can log in without touching the mouse', async ({ page }) => {
    await page.goto('/login');

    await page.keyboard.press('Tab');
    await page.keyboard.type('admin');

    await page.keyboard.press('Tab');
    await page.keyboard.type('admin123');

    await page.keyboard.press('Tab');
    await page.keyboard.press('Enter');

    await expect(page).toHaveURL('/dashboard');
  });
});
```

`toBeFocused()` is a web-first assertion — it retries until the element you named actually has focus, or times out and fails with a clear message naming what was focused instead. That's the entire point of asserting focus this way instead of just asserting each locator is visible: visibility says the element is on the page, `toBeFocused()` says the keyboard is actually on it right now.

### Step 6: Tab Order and Focus Trap Inside the Add Medical Record Modal

A modal is where keyboard testing earns its keep. Once the "Add Medical Record" dialog is open, `Tab` must cycle only through the elements inside it — `Diagnosis`, `Notes`, `Cancel`, `Confirm` — and never escape onto the appointment table behind it. `Shift+Tab` from the first field must wrap back to the last, not escape backward either:

```typescript title="tests/keyboard-nav.spec.ts"
test.describe('Keyboard navigation — Add Medical Record modal', () => {
  test.use({ storageState: 'storage/doctor.json' });

  test('tab order stays inside the dialog and Confirm is reachable', async ({ page }) => {
    await page.goto('/dashboard');

    const appointmentRow = page.getByRole('row', { name: /Jane Doe/ });
    await appointmentRow.getByRole('button', { name: 'Add Medical Record' }).click();

    const dialog = page.getByRole('dialog');
    await expect(dialog).toBeVisible();

    const diagnosis = dialog.getByLabel('Diagnosis');
    const notes = dialog.getByLabel('Notes');
    const cancel = dialog.getByRole('button', { name: 'Cancel' });
    const confirm = dialog.getByRole('button', { name: 'Confirm' });

    await expect(diagnosis).toBeFocused();

    await page.keyboard.press('Tab');
    await expect(notes).toBeFocused();

    await page.keyboard.press('Tab');
    await expect(cancel).toBeFocused();

    await page.keyboard.press('Tab');
    await expect(confirm).toBeFocused();

    // Forward trap: Tab from the last focusable element wraps to the first,
    // it does not escape onto the appointment table behind the dialog.
    await page.keyboard.press('Tab');
    await expect(diagnosis).toBeFocused();

    // Backward trap: Shift+Tab from the first element wraps to the last.
    await page.keyboard.press('Shift+Tab');
    await expect(confirm).toBeFocused();
  });
});
```

`await expect(diagnosis).toBeFocused()` right after the dialog becomes visible, with no `Tab` press in between, asserts something specific: opening the modal moves focus *into* it automatically, onto its first field. A modal that opens without moving focus leaves a keyboard user's cursor still sitting on the "Add Medical Record" button underneath it — technically on the page, but nowhere useful.

## How It Works Internally

`AxeBuilder` doesn't run a separate process — `.analyze()` injects the axe-core JavaScript engine into the page via `page.evaluate()`, runs its ruleset against the live DOM exactly as the browser has rendered it right now, and serializes the results back across the Playwright-to-browser bridge as the plain object you asserted on in Step 4. That's why the visibility guard in Steps 2 and 3 matters: `analyze()` inspects whatever DOM exists at the moment it runs, with no awareness of animations or async renders still in flight.

`page.keyboard.press('Tab')` dispatches a real keyboard event at the OS/browser level — it isn't a simulated `focus()` call, it's the same event a physical key press produces. So whichever element the browser's own focus-management logic decides comes next is the one that actually gets it; `toBeFocused()` then reads `document.activeElement` and compares it against the locator you asserted, retrying on Playwright's usual web-first schedule until it matches or the timeout elapses. That's also why this technique can catch a focus-trap failure that no amount of `toBeVisible()` assertions would ever see — the dialog's elements are all still visible and correctly labeled even when focus has quietly leaked out from under them.
