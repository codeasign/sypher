# Accessibility Testing — Review

⏱ 4 minutes

## Key Takeaways

- `@axe-core/playwright`'s `AxeBuilder` injects the axe-core engine into the page via `page.evaluate()` and scans the live, rendered DOM — scope it with `.include()` to one form or dialog instead of an entire page, and always wait for that target to be visible before calling `.analyze()`.
- An axe results object's `violations` array carries an `impact` per entry — `critical`, `serious`, `moderate`, `minor` — and that's what should drive your triage order: fail the build on `critical`/`serious`, and track the rest separately so a real signal doesn't drown in noise.
- A clean axe scan is one necessary layer, not proof of accessibility. It catches structural defects like missing labels and low contrast just fine, but it says nothing about tab order or focus management — only keyboard simulation can verify those.
- `page.keyboard.press('Tab')` paired with `expect(locator).toBeFocused()` tests the real tab order one press at a time, which matters because a `toBeVisible()` assertion on the same elements proves nothing about the order the keyboard actually visits them in.
- A correct focus trap wraps in both directions: `Tab` from a dialog's last focusable element has to return to its first, and `Shift+Tab` from its first has to return to its last — test only the forward direction, and a real leak can ship silently.

## Recap in 60 Seconds

If you only remember three things:

1. Scan with `new AxeBuilder({ page }).analyze()`, scoped to what changed, after asserting it's visible — then triage `results.violations` by `impact` rather than failing on every entry equally.
2. Tab order and focus traps need real key presses and `toBeFocused()` assertions, because no scan and no visibility check can verify either one for you.
3. Test both `Tab` and `Shift+Tab` on every modal's focus trap — a trap that only wraps forward is still a broken trap.

## Try It

Now try applying the same pattern somewhere new: extend the "Add Medical Record" keyboard test from this lesson to the nurse's "Schedule Appointment" modal (`page.getByRole('button', { name: 'Schedule Appointment' })`, fields labeled `Patient` and `Date`, from the page-object-model lesson's `NurseDashboardPage`). Write both an `AxeBuilder` scan scoped to `[role="dialog"]` and a focus-trap test covering `Tab` and `Shift+Tab` across its `Patient`, `Date`, `Cancel`, and `Confirm` elements, and confirm the tab order and trap hold with `storage/nurse.json` as the `storageState` — the same way you did for the doctor's modal.

## Further Reading

- [`@axe-core/playwright` on npm](https://www.npmjs.com/package/@axe-core/playwright) — the API reference for `AxeBuilder`, including `.include()`, `.exclude()`, and `.withTags()`
- [Deque University — axe-core rule descriptions](https://dequeuniversity.com/rules/axe/) — a good place to look up what each rule ID (like `label` or `color-contrast`) actually checks and why
- [WCAG 2.1 Quick Reference](https://www.w3.org/WAI/WCAG21/quickref/) — the standard that axe-core's rules are mapped against
- [Playwright — Keyboard input](https://playwright.dev/docs/input#keyboard) — the full `page.keyboard` API you'll draw on for tab-order and focus-trap tests
