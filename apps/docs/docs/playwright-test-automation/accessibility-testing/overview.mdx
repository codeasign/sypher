# Accessibility Testing

⏱ 20 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Install `@axe-core/playwright` and use `AxeBuilder` to run automated accessibility scans against the RBAC app's login form and role dashboards
- Read an axe results object, including the `violations` array, `impact` levels, `nodes`, and `helpUrl`, closely enough to turn it into a pass/fail assertion your suite can act on
- Learn to prioritize real defects (missing form labels, insufficient color contrast, missing ARIA roles) over axe's own noise and known false positives
- Test keyboard-only tab order on the login form and the "Add Medical Record" form, confirming focus lands on the expected element at each `Tab` press
- Verify that a modal traps focus correctly, so `Tab` and `Shift+Tab` cycle within the dialog and never escape to the page behind it

## Why This Matters

Every test you've written so far in this course proves the RBAC app works for a mouse-and-screen user whose locators happen to resolve. That's most of your users, but not all of them. The RBAC app is a healthcare system: patients booking appointments, doctors entering diagnoses, nurses scheduling care. Healthcare software has both a moral and, in many jurisdictions, a legal obligation to work for people using a screen reader, a keyboard alone, or assistive technology that depends on correct ARIA roles and labels. (ARIA, short for Accessible Rich Internet Applications, is a set of HTML attributes that tell assistive technology what a UI element is and what state it's in.) A patient-record form that's functionally correct but has an unlabeled input isn't a passing test with a minor cosmetic issue. It's a form some of your users literally cannot fill in.

Playwright's `getByRole` and `getByLabel` locators already lean on the accessibility tree, the browser's internal representation of a page for assistive technology, which is a good habit but not the same thing as testing accessibility. A test can pass every `getByLabel('Diagnosis')` call and still leave the page in a state where a screen reader announces nothing useful, color contrast is unreadable, or a keyboard user opens a modal and then finds their `Tab` key walks them out of it and onto the dashboard behind it. This lesson adds the layer your existing locator-based tests don't cover: automated rule-based scanning for structural violations, and keyboard simulation for behaviors no scan can verify on its own.

## The Problem

Here's a login test that has passed in every module so far:

```typescript
test('logs in as admin', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();
  await expect(page).toHaveURL('/dashboard');
});
```

This test tells you `getByLabel('Password')` resolves to *something*, but it doesn't tell you whether that something is a real `<label for="password">` associated with the input, or a placeholder attribute that Playwright's `getByLabel` happened to also match through an `aria-label`. It doesn't tell you whether a keyboard user tabbing from the username field lands on the password field next, or skips past it into a hidden element. It doesn't tell you whether the "Log In" button has enough color contrast against its background to be readable. Every one of those is a real defect a functional test like this one is structurally incapable of catching, because it never asks any of those questions. It only asks "did the values I typed end up submitted."

## The Concept

Accessibility testing in this course happens in two distinct layers, because no single tool covers both:

1. **Automated rule-based scanning.** `@axe-core/playwright` runs the axe-core ruleset against the page's live, rendered DOM and reports structural violations: missing labels, insufficient contrast, invalid or missing ARIA roles, and dozens of other WCAG-mapped checks. (WCAG, the Web Content Accessibility Guidelines, is the standard these rules are checked against.) This is cheap, fast, and catches a real, if partial, slice of accessibility defects automatically, the same way a linter catches a real slice of code-quality issues automatically.
2. **Keyboard simulation.** `page.keyboard.press('Tab')`, paired with asserting focus using `expect(locator).toBeFocused()`. Axe can tell you an element is focusable and correctly labeled, but it cannot tell you what order your keyboard actually visits elements in, or whether a modal correctly traps focus once it's open. That takes actually pressing the keys and checking where focus lands, step by step. There's no shortcut around simulating the interaction.

Neither layer replaces the other, and neither replaces real assistive-technology testing with an actual screen reader. Automated tools are widely estimated to catch only somewhere between a third and half of all WCAG issues, so this is not a complete accessibility audit. What you do get for the effort is a fast, repeatable regression net that runs on every commit, catching the specific slice of defects (missing labels, broken tab order, a leaky focus trap) most likely to slip in through an otherwise unremarkable frontend change.

Picture these two layers running side by side against the same two screens: the login form and the "Add Medical Record" modal. The automated-scanning layer calls `new AxeBuilder({ page }).include('#login-form').analyze()` and catches missing form labels, low color contrast, and missing or invalid ARIA roles. The keyboard-simulation layer calls `page.keyboard.press('Tab')` and asserts with `expect(locator).toBeFocused()`, and catches a different category of problem entirely: wrong tab order, a focus trap that leaks, or focus getting lost when a modal closes. Both layers point at the same UI, but each one is watching for something the other cannot see.
