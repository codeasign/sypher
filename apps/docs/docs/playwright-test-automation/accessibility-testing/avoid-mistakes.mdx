# Accessibility Testing: Common Mistakes

⏱ 9 minutes

## When NOT to Use This

An automated axe scan is not a substitute for testing with a real screen reader, and this lesson doesn't pretend otherwise. It's meant to be a fast, repeatable regression net for the slice of defects a rule engine can detect mechanically, not a certification that a page is fully accessible. So if the RBAC app were ever going through an actual accessibility audit before a healthcare compliance sign-off, that audit needs a human using real assistive technology, not just a green `results.violations` array.

Keyboard tab-order and focus-trap tests earn their keep on screens with real interactive sequences worth protecting: forms, modals, multi-step flows. They don't add much value on a static, read-only screen with no focusable elements beyond a single link, because at that point you're really just testing the browser's default tab behavior, not your app.

## The Pattern to Remember

- **Pattern:** scope an `AxeBuilder` scan to the form or dialog you changed, wait for it to be visible first, triage violations by `impact` before deciding what breaks the build, and back the scan up with a real keyboard-simulation test for the tab order and focus traps that no scan can verify on its own.
- **When to use:** any screen with a form, any modal, any screen with a meaningful keyboard interaction sequence. In the RBAC app, that covers most of the login flow and every dashboard's create/edit modals.
- **When NOT to use:** as a stand-in for manual assistive-technology testing before a real compliance sign-off, or on static screens that have no interactive elements to scan in the first place.
- **Mental model:** think of axe as a linter for the DOM: fast, mechanical, and confident about a narrow slice of rules. Keyboard simulation is the only way to actually walk in a keyboard-only user's shoes. Neither one is optional if the other is all you've got.

## Common Mistakes

### Mistake 1: Treating a Zero-Violation Scan as "Fully Accessible"

**Mistake:** Seeing `results.violations` come back as an empty array and concluding, right then, that the screen is accessible, full stop.

**Why it happens:** An empty array just reads as a clean bill of health, and it's tempting to treat automated tooling the same way you'd treat a green functional test suite: no violations, no problem.

**Symptoms:** Real accessibility bugs slip through anyway: confusing focus order, a screen reader announcing an element's role but not its current state, color choices that pass a contrast ratio but are still hard to distinguish for some forms of color blindness. None of those are rules axe-core checks for.

**Fix:** Treat a clean axe scan as one necessary layer, not the complete answer. Pair it with the keyboard-simulation tests from this lesson, and be careful not to present "zero axe violations" as equivalent to "accessible" in a PR description or a compliance conversation.

### Mistake 2: Scanning Before the Page or Modal Has Finished Rendering

**Mistake:** Calling `new AxeBuilder({ page }).analyze()` immediately after `page.goto()` or a modal-opening click, with no wait in between.

**Why it happens:** Playwright's own actions auto-wait, so it's an easy assumption to carry over that `analyze()` does too. It doesn't. It just inspects whatever DOM happens to exist the instant it runs.

**Symptoms:** Flaky scans, basically. Sometimes it runs against a half-rendered login form and reports a spurious missing-label violation that would have resolved itself a moment later; other times it runs against a still-closed dialog and reports nothing at all, which gives you false confidence that the modal has no violations when really it was never inspected.

**Fix:** Always assert that the target is visible, with `await expect(dialog).toBeVisible()`, before calling `.analyze()`, exactly as Steps 2 and 3 in Build It do. That's what guarantees the scan runs against the DOM state you actually meant to test.

### Mistake 3: Failing the Build on Every Violation Regardless of Impact

**Mistake:** Asserting `expect(results.violations).toEqual([])` everywhere, including on scans of large, unfamiliar pages, and blocking every PR the moment axe reports anything at all, `minor` findings and scoping artifacts included.

**Why it happens:** `toEqual([])` is about the simplest assertion you could write, and it feels appropriately rigorous, so it's an easy default to reach for without thinking through what it actually blocks.

**Symptoms:** Eventually the team starts ignoring or disabling accessibility tests altogether, usually after enough PRs get blocked by a `moderate` landmark-region complaint on a `.include()`-scoped fragment that was never going to have its own `<main>` anyway. That's a real rule, correctly firing, but not a defect worth holding up a merge for. Once a check has trained people to expect noise, they stop reading it before they dismiss it.

**Fix:** Filter by `impact` before you assert. Fail the build on `critical` and `serious`, and track `moderate`/`minor` findings separately (a follow-up ticket, a non-blocking report) instead of folding them into the same pass/fail gate, as covered in Step 4 of Build It.

### Mistake 4: Confusing "Element Is Visible" With "Element Has Focus"

**Mistake:** Writing a tab-order test that only asserts each field is `toBeVisible()` in the order you expect, without ever actually pressing `Tab` or asserting `toBeFocused()`.

**Why it happens:** Visibility assertions are the pattern you've used everywhere else in this course, so it's a natural habit to reach for here too, even though it isn't actually testing the thing you care about.

**Symptoms:** The test passes even when the real tab order is completely different from what's asserted, because visibility says nothing about focus order. A field that's visible fourth on the page but reachable first by keyboard (or not reachable by keyboard at all, if it has a broken `tabindex`) still sails through a visibility-only test.

**Fix:** Actually dispatch the key press with `page.keyboard.press('Tab')` and assert the specific element you expect next with `expect(locator).toBeFocused()`, one press at a time, exactly as Step 5 in Build It does. There's simply no way to verify tab order without simulating the tabbing itself.

### Mistake 5: Testing Only the Forward Tab Direction on a Modal

**Mistake:** Writing a focus-trap test that presses `Tab` repeatedly to confirm the trap wraps forward, but never getting around to testing `Shift+Tab`.

**Why it happens:** Forward tabbing is just the more common interaction, so it's the one people think to test first. Once that passes, the test tends to feel complete even though it's only checking half the behavior.

**Symptoms:** A modal that correctly wraps `Tab` from its last element back to its first, but quietly leaks `Shift+Tab` from its first element out onto the page behind it, ships with a passing test suite anyway. A keyboard user hitting `Shift+Tab` out of habit, reversing direction to double-check a field they just filled, ends up back on the dashboard with no clear indication they ever left the dialog.

**Fix:** Test both directions, as Step 6 in Build It does: assert the forward wrap (`Tab` from the last element returns to the first) and the backward wrap (`Shift+Tab` from the first element returns to the last) as two separate assertions in the same test.
