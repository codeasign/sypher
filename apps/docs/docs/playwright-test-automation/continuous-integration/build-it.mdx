# Continuous Integration for Playwright Tests: Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Create the Workflow File

GitHub Actions discovers workflows by location, not by name. Anything under `.github/workflows/` with a `.yml` extension is picked up automatically. From your fork's repo root:

```bash
mkdir -p .github/workflows
```

Create `.github/workflows/playwright.yml` and start with the trigger and job shell:

```yaml title=".github/workflows/playwright.yml"
name: Playwright Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    name: Run Playwright suite
    runs-on: ubuntu-latest
    timeout-minutes: 30
```

A `push` to `main` covers changes that land directly, while a `pull_request` targeting `main` covers every proposed change before it's even merged. Between the two, nothing slips through unchecked. `timeout-minutes: 30` is there as a safety net: without it, a genuinely hung test (as opposed to one that just fails cleanly) can quietly burn CI minutes for hours before anyone notices.

### Step 2: Add the JWT Secret as a Repository Secret, Not a File

The backend needs `JWT_SECRET` to start, same as it did locally during setup. Locally, that lived in a `.env` file you never committed. In CI there is no `.env` file at all: you never checked one in, and you shouldn't. Instead, add a repository secret: on your fork, go to **Settings → Secrets and variables → Actions → New repository secret**, name it `JWT_SECRET`, and give it any long random value. This has nothing to do with the value being "real" (it's a signing secret for tokens that only exist for the lifetime of one CI run), but pulling it from `secrets` instead of writing it into the workflow file keeps the habit consistent with everywhere else in this course.

Add the job-level environment block:

```yaml
    env:
      PORT: 5000
      JWT_SECRET: ${{ secrets.JWT_SECRET }}
      NODE_ENV: test
```

Every step in the job inherits these, and because Playwright's `webServer` spawns the backend as a child process of the same job, so does the backend when it starts.

### Step 3: Checkout and Install Node

```yaml
    steps:
      - name: Checkout your fork
        uses: actions/checkout@v4

      - name: Install Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
```

`actions/checkout@v4` clones the exact commit that triggered the run (the pushed commit, or the PR's merge commit) into the runner's working directory, and right after that, `actions/setup-node@v4` installs Node 20 and puts it on `PATH` so every step that follows can use it.

### Step 4: Cache `node_modules` Across Runs

The RBAC project has three separate `package-lock.json` files (root, `backend/`, and `frontend/`), so cache all three `node_modules` directories together, keyed on the combined hash of all three lockfiles:

```yaml
      - name: Cache node_modules
        id: cache-node-modules
        uses: actions/cache@v4
        with:
          path: |
            node_modules
            backend/node_modules
            frontend/node_modules
          key: ${{ runner.os }}-node-modules-${{ hashFiles('package-lock.json', 'backend/package-lock.json', 'frontend/package-lock.json') }}
```

The `key` only changes when one of the three lockfiles changes. Most commits touch test code or app code, not dependencies, so most runs hit this cache and skip installation entirely. The `id: cache-node-modules` line gives the next steps something to check.

### Step 5: Install Dependencies Only on a Cache Miss

```yaml
      - name: Install root dependencies
        if: steps.cache-node-modules.outputs.cache-hit != 'true'
        run: npm ci

      - name: Install backend dependencies
        if: steps.cache-node-modules.outputs.cache-hit != 'true'
        working-directory: ./backend
        run: npm ci

      - name: Install frontend dependencies
        if: steps.cache-node-modules.outputs.cache-hit != 'true'
        working-directory: ./frontend
        run: npm ci
```

`npm ci` (not `npm install`) is deliberate here: it installs exactly what each `package-lock.json` specifies and fails outright if the lockfile and `package.json` disagree, instead of silently resolving a different tree. That's the correct behavior in CI, where reproducing precisely what's committed matters more than convenience.

### Step 6: Recreate the Database Directory and Seed It

Setup's `mkdir database` step has no memory across CI runs. Every job starts from a clean checkout, so this has to happen every time, cache or no cache:

```yaml
      - name: Create the backend database directory
        run: mkdir -p backend/database

      - name: Seed the database
        working-directory: ./backend
        run: npm run seed
```

Without this, the backend either crashes on startup (no `database/` directory) or starts against an empty database with none of the role accounts your tests log in as: the exact two failure modes covered in setup's Avoid Mistakes lesson, just happening on a runner instead of your laptop.

### Step 7: Cache and Install Playwright's Browsers

Browser binaries live outside `node_modules`, at `~/.cache/ms-playwright`, so they get their own cache step:

```yaml
      - name: Cache Playwright browsers
        id: cache-playwright-browsers
        uses: actions/cache@v4
        with:
          path: ~/.cache/ms-playwright
          key: ${{ runner.os }}-playwright-${{ hashFiles('package-lock.json') }}

      - name: Install Playwright browsers
        if: steps.cache-playwright-browsers.outputs.cache-hit != 'true'
        run: npx playwright install --with-deps

      - name: Install Playwright OS dependencies only
        if: steps.cache-playwright-browsers.outputs.cache-hit == 'true'
        run: npx playwright install-deps
```

`--with-deps` installs both the browser binaries and the Linux system libraries (`libnss3`, `libatk`, and similar) they need to launch on a bare `ubuntu-latest` runner. On a cache hit the binaries are already restored, but the system libraries are not part of the cached path and don't persist between jobs, so `install-deps` alone still needs to run to reinstall just those, without re-downloading browsers you already have.

### Step 8: Run the Suite, and Let `webServer` Do the Rest

```yaml
      - name: Run Playwright tests
        run: npx playwright test
```

That's the entire step. There is no separate "start backend" or "start frontend" step, and no `services:` block spinning up containers. The `webServer` array from the project structure and config lesson in `playwright.config.ts` already starts both processes, because GitHub Actions sets `CI=true` on every runner automatically, which makes `reuseExistingServer: !process.env.CI` evaluate to `false`. Playwright launches fresh `backend/` and `frontend/` processes, waits for each `webServer` entry's `url` to respond, runs the suite, and shuts both processes down when it finishes: the identical config from that lesson, unmodified, doing the right thing in a completely different environment than it was written on.

### Step 9: Upload the Report and Traces

A failed run on a GitHub-hosted runner leaves nothing behind once the job ends unless you explicitly save it:

```yaml
      - name: Upload HTML report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14

      - name: Upload failure traces
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-traces
          path: test-results/
          retention-days: 14
```

The HTML report uploads with `if: always()`: you want it even on a passing run, to confirm what actually executed. Traces upload only `if: failure()`, since `trace: 'on-first-retry'` from setup's config only produces trace files when a test fails and gets retried, and there is nothing to upload on a clean pass. Both artifacts appear on the workflow run's summary page in your fork's Actions tab, downloadable as zip files, and the trace one opens directly in [trace.playwright.dev](https://trace.playwright.dev) without needing a local Playwright install at all.

### Step 10: Add a Fast PR-Gate Smoke Job

The test organization and tagging lesson tagged a subset of specs `@smoke`: the handful of tests that catch the most common breakages fastest. Running the full suite on every PR is safe, but it's slow, and that's exactly where a smaller job earns its keep: run only `@smoke` on `pull_request` while keeping the full suite on `push` to `main`, and you get fast feedback on PRs without weakening the safety net where it matters most. Add a second job:

```yaml
  smoke:
    name: PR smoke gate
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    timeout-minutes: 10
    env:
      PORT: 5000
      JWT_SECRET: ${{ secrets.JWT_SECRET }}
      NODE_ENV: test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm ci
        working-directory: ./backend
      - run: npm ci
        working-directory: ./frontend
      - run: mkdir -p backend/database
      - run: npm run seed
        working-directory: ./backend
      - run: npx playwright install --with-deps
      - run: npx playwright test --grep @smoke
```

This job intentionally skips the caching steps to stay simple and self-contained. On a PR you want correctness feedback in minutes, and a `@smoke` run is short enough that the install cost is tolerable. The full `test` job from Steps 1 through 9 still runs on the same PR in parallel, so nothing meaningful is skipped. The smoke job just reports back first.

### Step 11: Commit, Push, and Watch It Run

```bash
git add .github/workflows/playwright.yml
git commit -m "Add Playwright CI workflow"
git push origin main
```

Open your fork on GitHub and click the **Actions** tab. You'll see the workflow run start within a few seconds of the push, its steps executing one by one exactly as you defined them. This is the moment setup's fork pays off directly. You own this repository, so this tab exists, the workflow has permission to run, and the run's artifacts belong to you to download.

## How It Works Internally

`actions/cache@v4` doesn't literally store files "in GitHub" the way a commit does. It uploads a compressed archive of the given `path` entries to GitHub's cache service, keyed on the exact `key` string you provide. On the next run, before your `if: steps.cache-*.outputs.cache-hit` steps even evaluate, the `actions/cache` step itself checks whether an archive already exists under that key; if one does, it downloads and extracts it before your workflow continues, and sets `cache-hit` to `'true'` so later steps can skip redundant work. If any file the key depends on changes (a lockfile edit changes what `hashFiles(...)` returns), the key changes too, so the next run computes a fresh cache automatically instead of restoring a stale one.

`CI=true` is not something this workflow sets explicitly anywhere. GitHub Actions injects it into every job's environment before your first step runs, as do effectively all major CI providers. That single inherited variable is the entire reason the project structure and config lesson's `webServer` config needed no CI-specific branch of its own: `reuseExistingServer: !process.env.CI` was already written to do the right thing here, months before this lesson existed.
