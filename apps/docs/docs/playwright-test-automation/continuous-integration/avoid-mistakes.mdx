# Continuous Integration for Playwright Tests — Common Mistakes

⏱ 8 minutes

## When NOT to Use This Workflow

This lesson's workflow runs the full suite on every push to `main` and every pull request. That's correct for `main`, but not necessarily for every branch or every commit while you're actively iterating — pushing a work-in-progress commit every few minutes to a feature branch and waiting on a full CI run each time is a slow feedback loop for a problem `npx playwright test --ui` on your own machine solves faster. Use the workflow as the gate before merge, not as a substitute for running tests locally while you write them. Similarly, don't point this workflow's `baseURL` at a real staging or production deployment — the `webServer` config exists specifically to spin up a disposable backend and frontend per run, and running destructive test data against a shared environment defeats that isolation entirely.

## The Pattern to Remember

- **Pattern:** fork (not clone) → cache dependencies and browsers → let `webServer` start both servers because `CI=true` → run the suite → upload the report and traces on failure.
- **When to use:** on every push to `main` and every pull request — this is the merge gate for this repository.
- **When NOT to use:** as a stand-in for running tests locally while you're still iterating, or pointed at a real staging/production environment instead of the disposable servers `webServer` starts per run.
- **Mental model:** think of the workflow file as a script of everything you've done by hand since setup, written down once so a machine that has never seen this repository before can do it identically, every time, without you standing over it.

## Common Mistakes

### Mistake 1: Cloning Instead of Forking Back During Setup

**Mistake:** Having cloned `codedbyabhishekc/rbac-healthcare-system` directly instead of forking it first, and only discovering the difference when trying to set up CI.

**Why it happens:** Up through the test organization and tagging lesson, it genuinely doesn't matter whether you forked or cloned — locators, fixtures, the permission matrix, tagging, none of it cares which repository your code lives in. So the gap stays invisible right up until the moment you actually need to push a workflow file and watch it run.

**Symptoms:** `git push` fails with a permissions error, because you don't have write access to someone else's repository. Even if you work around that by pushing to a personal fork at this point, there's no Actions tab history, no repository secrets configured, and no `main` branch that matches what you've actually been testing against for the last eighteen modules.

**Fix:** Fork `rbac-healthcare-system` now if you haven't already, then re-point your local `origin` remote at the fork: `git remote set-url origin https://github.com/<you>/rbac-healthcare-system.git`, and push. Going forward, this is the repository the workflow in this module actually runs against.

### Mistake 2: Forgetting `--with-deps` on a Fresh Linux Runner

**Mistake:** Running `npx playwright install` without `--with-deps` on `ubuntu-latest`, assuming it behaves the same as it does on your own machine.

**Why it happens:** On your own laptop, the operating system libraries that Chromium, Firefox, and WebKit need in order to launch (`libnss3`, `libatk-bridge2.0-0`, and a long list of others) are usually already there, left behind by other software you've installed over time. A bare `ubuntu-latest` runner has no such history, so it has none of them either.

**Symptoms:** Browser installation itself succeeds, but the very first test fails immediately with an error about a missing shared library or a browser that "failed to launch" — a failure that has nothing to do with your test code or locators.

**Fix:** Use `npx playwright install --with-deps` on the install step, exactly as shown in Build It. It installs both the browser binaries and the Linux system packages they depend on in a single command.

### Mistake 3: Committing `JWT_SECRET` Instead of Using a Repository Secret

**Mistake:** Hardcoding a `JWT_SECRET` value directly into `playwright.yml`, or copying the value from a local `.env` file into the workflow as plain text, so the backend has something to start with in CI.

**Why it happens:** It's the fastest way to get the workflow running the first time, and unlike a real production credential, a JWT signing secret for a CI-only SQLite database that gets destroyed at the end of the job doesn't feel like it's protecting anything valuable.

**Symptoms:** The value sits in plain text in your commit history and workflow logs forever, visible to anyone who can read the repository — and the habit transfers badly the first time a workflow file does need a real credential.

**Fix:** Store it as a repository secret (**Settings → Secrets and variables → Actions**) and reference it as `secrets.JWT_SECRET` in the workflow's `env` block, exactly as shown in Build It. The workflow never contains the value itself, only a reference to where it's stored.

### Mistake 4: Manually Starting Servers as CI "Services" Instead of Trusting `webServer`

**Mistake:** Adding a `services:` block to the workflow, or separate `run: npm start &` steps for the backend and frontend, to bring the servers up before Playwright runs — duplicating what the project structure and config lesson's `webServer` config already does.

**Why it happens:** Tutorials for other testing tools often model backend and frontend startup as explicit CI services, so it's a reasonable pattern to reach for out of habit, especially if the project structure and config lesson feels like a while ago by the time you get here.

**Symptoms:** At best, redundant complexity — two things racing to bind the same ports, one of them (usually `webServer`, since `reuseExistingServer: !process.env.CI` is `false` in CI) failing because the port is already taken. At worst, silent flakiness that depends on which process happens to win the race on a given run.

**Fix:** Delete any manually added `services:` block or background `run: npm start &` steps. Let `npx playwright test` alone trigger `webServer`, which already knows how to start both processes correctly in CI because you configured it in the project structure and config lesson — there is nothing left for the workflow file to do here.

### Mistake 5: Only Uploading Artifacts on Success, or Not Uploading Them at All

**Mistake:** Adding an `upload-artifact` step with no `if:` condition (which defaults to only running when every prior step succeeded), or skipping the artifact upload steps entirely to keep the workflow file short.

**Why it happens:** The workflow "looks complete" without them — it checks out, installs, and runs the tests — and the gap is invisible until the first real failure, when there's suddenly nothing to look at.

**Symptoms:** A red run in the Actions tab with no report and no trace to open — just a wall of terminal-style log text to scroll through, which is exactly the debugging experience trace viewer exists to replace, gone the moment the run happens on a machine you can't `npx playwright show-trace` on directly.

**Fix:** Use `if: always()` for the HTML report upload and `if: failure()` for trace uploads, as shown in Build It. The small storage cost of keeping fourteen days of reports around is negligible compared to the time lost re-running a flaky failure locally just to see what it looked like.
