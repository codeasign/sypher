# Continuous Integration for Playwright Tests

⏱ 15 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Write a complete GitHub Actions workflow that installs dependencies, seeds the database, and runs your full Playwright suite on every push and pull request
- Trust the `webServer` config from the project structure and config lesson to start the backend and frontend automatically in CI, with no extra "service container" setup needed
- Cache `~/.cache/ms-playwright` and `node_modules` between runs with `actions/cache`, so most CI runs skip reinstalling browsers and dependencies entirely
- Upload the HTML report and failure traces as workflow artifacts, so a red run in CI is still debuggable without reproducing it locally
- Explain exactly why this workflow only works because you forked the RBAC repo back during setup, instead of cloning it

## Why This Matters

Back during setup, the very first instruction was to fork `rbac-healthcare-system`, not clone it, with a promise that this would matter later. This is later. Everything in this lesson — pushing a workflow file, watching it run in the Actions tab, seeing an artifact you can download — depends on owning the repository the workflow lives in. A clone of someone else's repository has no Actions tab configured for you to enable, no permission for a workflow to run under your account, and nowhere to push a `.github/workflows/playwright.yml` file to in the first place. Forking was not a formality back then — it was the one decision that makes this entire module possible.

Every test you've written since early in this course has run on your machine, with you watching it happen. That proves the test works today, on your laptop, with both servers already warm. It proves nothing about whether the test still passes after a teammate's change, on a machine that has never run `npm install` before, at 2 a.m. when nobody is watching. Continuous integration is what turns "it passed when I ran it" into "it passes, automatically, on every single change, for everyone" — and it is the point where a personal test suite becomes a team's safety net.

## The Problem

Imagine you push a change to a doctor dashboard component. Locally, your Playwright suite still passes — but you only ran it because you remembered to. A teammate pushes a change to the same component an hour later, doesn't run the suite, and merges. Nothing catches the regression until a patient-facing bug report days later, and by then nobody remembers which of a dozen intervening commits caused it.

Nothing about your test suite is wrong. The problem is that it only runs when a human chooses to run it, on whatever machine that human happens to be using. Without CI, a correct test suite provides safety only for the one person disciplined enough to run it every time — which, across a team and over months, is nobody.

## The Concept

A GitHub Actions workflow for this project needs to do, unattended, exactly what you've been doing by hand since setup: get the code, install dependencies for the root project plus `backend/` and `frontend/` separately, seed the database, bring both servers up, run `npx playwright test`, and leave behind evidence of what happened.

The key insight is that almost none of this requires CI-specific logic. The `webServer` config from the project structure and config lesson already handles starting both servers correctly in any environment, because `reuseExistingServer: !process.env.CI` reads an environment variable GitHub Actions sets automatically. Locally, `CI` is unset, so Playwright reuses your already-running terminals. On a GitHub Actions runner, `CI` is always `true`, so `!process.env.CI` is `false` — Playwright always launches fresh backend and frontend processes before the first test, and tears them down when the run ends. You do not write a single conditional for this; the config you built earlier already does the right thing in both places.

What the workflow file adds on top of that is CI-specific housekeeping: checking out the right commit, installing Node, restoring caches so the run doesn't reinstall browsers from scratch every time, and — critically — preserving the HTML report and trace files as downloadable artifacts, since a failed run on a GitHub-hosted runner has no terminal you can inspect afterward.
