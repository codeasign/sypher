# Reporting in Playwright — Common Mistakes

⏱ 8 minutes

## When NOT to Use This

Not every run needs all four reporters. While you're iterating on a single spec locally — writing a new nurse-appointment test, rerunning it a dozen times as you fix a locator — `html`, `json`, `junit`, and a Slack-posting custom reporter are all overhead you don't need yet. Playwright's built-in `list` reporter (or `dot` for a terser view) is enough for that loop; you can always pass `--reporter=list` on the command line to override your config's `reporter` array for one run without editing the file:

```bash
npx playwright test appointments.spec.ts --reporter=list
```

Reach for the full reporter set when the run is one you or a CI system actually needs to inspect after the fact — a full local suite run, or anything in CI — not every iteration while you're still writing the test.

## The Pattern to Remember

- **Pattern:** reach for `html` when a human needs to debug a specific failure, `json` when scripts and custom tooling need to consume the run, `junit` when a CI system needs to parse it, and a custom reporter only when none of the built-ins produce what you actually need.
- **When to use:** wire up `reporter: [['html'], ['json', {...}], ['junit', {...}]]` for any full suite run that's worth keeping a record of — local end-to-end runs, and every CI run once continuous integration is wired up.
- **When NOT to use:** don't drag the full reporter array through every single iteration while you're still writing one spec — override with `--reporter=list` for that loop instead, and switch back once the test is done.
- **Mental model:** the test run itself produces just one stream of events; each reporter is simply an independent listener translating that same stream into whatever shape its consumer — you, a script, a CI system, Slack — actually needs.

## Common Mistakes

### Mistake 1: Forcing the HTML Reporter to Auto-Open in CI

**Mistake:** Setting `reporter: [['html', { open: 'always' }]]` because it's convenient to have the report pop open automatically after a local run — without stopping to notice that this setting ships into every environment the config touches, CI included.

**Why it happens:** `open: 'always'` genuinely improves the local workflow, since you skip the separate `npx playwright show-report` call, so it's tempting to just set it and move on. What's easy to miss is that Playwright's own default (`open: 'on-failure'`, which itself resolves to never opening when `process.env.CI` is set) already handles this correctly on its own — you're quietly overriding something that didn't need fixing.

**Symptoms:** A GitHub Actions job that runs Playwright hangs or fails oddly, because a CI runner has no browser display to open a report into, and `open: 'always'` doesn't know it's running headless in CI.

**Fix:** Leave `open` at its default, or set it explicitly based on the environment: `open: process.env.CI ? 'never' : 'on-failure'`. Never hardcode `'always'` in checked-in config that also runs in CI.

### Mistake 2: Pointing CI Annotations at the JSON Reporter Instead of JUnit

**Mistake:** Configuring only `['json', { outputFile: 'results.json' }]` and expecting a CI test-reporting action or plugin to annotate a pull request with per-test results from it.

**Why it happens:** `results.json` has all the same underlying data as `results.xml` — every test, every status, every error — so it looks like it should work for anything JUnit works for.

**Symptoms:** The CI annotation step either errors outright (it was built to parse `<testsuite>`/`<testcase>` XML elements, not Playwright's JSON schema) or silently produces no annotations at all, with no clear indication why.

**Fix:** Add `['junit', { outputFile: 'results.xml' }]` specifically for anything that needs to integrate with CI tooling. Keep `json` for your own scripts and dashboards — the two formats serve different consumers, not the same one twice.

### Mistake 3: Parallel CI Jobs Overwriting Each Other's Report Files

**Mistake:** Running the suite as multiple sharded or matrix jobs in CI (covered in the parallelism/sharding lesson and the continuous integration lesson) with the same fixed `outputFile: 'results.xml'` in every job, then uploading them all to the same artifact location.

**Why it happens:** A single local run only ever produces one `results.xml`, so the fixed filename never causes trouble — right up until multiple CI jobs start running concurrently and each one writes to that exact same name.

**Symptoms:** Only one shard's results survive — whichever job's upload step ran last — and the others are silently overwritten, giving you an incomplete picture of what actually passed or failed across the full sharded run.

**Fix:** Include the shard or job index in the filename — build `outputFile` from `process.env.SHARD_INDEX` instead of a fixed string — and give each job a matching unique artifact name, then merge or inspect them separately, or use a JUnit-merging step in the CI workflow (covered in the continuous integration lesson).

### Mistake 4: Not Awaiting Async Work in a Custom Reporter's `onEnd`

**Mistake:** Firing off the Slack `fetch()` call in `onEnd` without `await`ing it, or without marking `onEnd` `async` at all.

**Why it happens:** `onTestEnd` in the earlier example is synchronous, so it's easy to write `onEnd` the same way out of habit, especially since the POST request "looks like" it fires immediately.

**Symptoms:** The Slack message never arrives, or arrives inconsistently — Playwright's process exits as soon as `onEnd` returns, and an un-awaited `fetch()` promise gets abandoned mid-flight along with it. This is a silent failure: the test run itself reports success or failure correctly, only the notification is missing.

**Fix:** Declare `onEnd` as `async` and `await` every asynchronous call inside it, exactly as shown in [Build It](./build-it). Playwright waits for `onEnd`'s returned promise to resolve before the process exits, specifically so reporters can do this safely.

### Mistake 5: Never Uploading Report Artifacts, So a CI Failure Is Just as Opaque as the Terminal Was

**Mistake:** Adding `html`, `json`, and `junit` to a CI workflow, but never adding a step that uploads `playwright-report/`, `results.json`, and `results.xml` as CI artifacts before the job's workspace is torn down.

**Why it happens:** All three reporters write their files successfully during the run, so nothing about the CI job itself ever looks broken — the gap only shows up later, when someone actually needs to open a report after a failure and finds nothing there.

**Symptoms:** A test fails in CI, JUnit correctly annotates the pull request with which test broke, but there's no trace, no screenshot, and no HTML report anywhere to actually investigate why — you're back to this lesson's opening problem, just with a slightly more specific error message.

**Fix:** In the CI workflow (covered in the continuous integration lesson), add an artifact-upload step — for example `actions/upload-artifact` on GitHub Actions — that runs `if: always()` so it uploads `playwright-report/` even when the test step fails, not only on success.
