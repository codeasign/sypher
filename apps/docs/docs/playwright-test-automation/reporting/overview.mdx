# Reporting in Playwright

⏱ 15 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Read a failed test in the built-in HTML report and follow its trace link straight into trace viewer
- Configure multiple reporters at once (`html`, `json`, and `junit`) and explain what each output is actually for
- Explain why CI systems consume JUnit XML specifically for test-result annotations, and why JSON isn't a substitute for that
- Sketch a minimal custom reporter class implementing the `Reporter` interface's `onTestEnd` and `onEnd` hooks
- Decide when a built-in reporter is enough and when a custom one earns its keep

## Why This Matters

Since the project structure and config lesson, your `playwright.config.ts` has had one line quietly doing a lot of work: `reporter: 'html'`. Every test run you've watched pass or fail in this course has been writing a full HTML report to disk the entire time. You just haven't needed to open it yet, because your terminal's pass/fail summary was enough to tell you what happened.

That stops being true the moment a test fails in a way the terminal can't explain, or the moment your tests run somewhere you can't watch them run (a GitHub Actions runner covered later in this course, for instance). A terminal line reading `1 failed` tells you a nurse-schedules-an-appointment test broke. It does not tell you which locator timed out, what the DOM looked like at that instant, what network requests fired, or whether the JWT the frontend sent still carried the right role claim. And a CI system reading raw terminal output cannot annotate a pull request with "this test failed, here's why." It needs a report shaped like data, not like prose.

This lesson is about matching the reporter to the consumer: a human debugging a failure reads the HTML report and follows its trace link; a CI system parses JUnit XML to annotate a PR; and anything else, like a Slack message with pass/fail counts or a custom dashboard, needs a reporter you write yourself, because no built-in format was ever going to guess what you wanted to do with the result.

## The Problem

A teammate's pull request fails one test in CI. The terminal output GitHub Actions shows you is this:

```text
1) [chromium] › appointments.spec.ts:42:5 › nurse schedules an appointment

    Error: expect(locator).toBeVisible() failed

  1 failed
  12 passed (48s)
```

That's it. No screenshot, no DOM snapshot, no network log, no indication of which step in a five-step flow actually broke. You can't reproduce it locally without guessing, and you can't tell your teammate anything more specific than "it failed." The terminal was never designed to carry this much information. It's a status line, not a debugging tool.

## The Concept

Playwright separates *what happened during a test run* from *how that gets surfaced*, and the `reporter` option in `playwright.config.ts` is where you choose one or more surfacing formats for the same underlying run:

1. **`html`**: a self-contained, browsable report built for a human looking at a specific failure after the fact: pass/fail per test, and for failures, screenshots, the full error, and (when `trace` captured one) a link straight into trace viewer.
2. **`json`**: the entire run serialized as structured data, meant for scripts and custom tooling to consume rather than for a human to read directly: every test, its status, duration, and error, all in one file.
3. **`junit`**: an XML format with roots in the Java testing world, decades old, that every major CI platform already knows how to parse, specifically so a CI system can turn individual `<testcase>` failures into inline pull-request annotations without needing to understand anything Playwright-specific.
4. **A custom reporter**: a TypeScript class implementing the `Reporter` interface, for anything none of the above does out of the box: posting a Slack message with pass/fail counts, writing to a custom dashboard, failing a build only under conditions the built-in reporters don't express.

`reporter` accepts an array, and Playwright runs every entry in it against the same test run simultaneously. You are not choosing one report format over another, you're choosing which combination of consumers gets fed.
