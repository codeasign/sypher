# Reporting in Playwright: Review

⏱ 3 minutes

## Key Takeaways

- `reporter: 'html'`, set since the project structure and config lesson, has quietly been writing a full browsable report (screenshots, errors, and trace links) on every run all along, whether you opened it or not; `npx playwright show-report` is how you finally look at it.
- A failure's **View trace** link in the HTML report hands you off directly into trace viewer (covered in the debugging and troubleshooting lesson), so you can confirm in under a minute whether a failure is a real bug or a bad assertion, just by inspecting the DOM and network activity at the exact moment it happened.
- `reporter` accepts an array of `[name, options]` tuples, so `[['html'], ['json', { outputFile: 'results.json' }], ['junit', { outputFile: 'results.xml' }]]` runs all three together against the same test run, not as three separate executions of it.
- JUnit XML is the CI-facing format specifically because every major CI platform (GitHub Actions and others, as covered in the continuous integration lesson) already knows how to parse its `<testsuite>`/`<testcase>` shape into per-test pull-request annotations. JSON carries the exact same data, but nothing built into CI tooling expects that schema.
- A custom reporter is just a class implementing the `Reporter` interface's hooks (`onTestEnd` for per-test bookkeeping, `onEnd` for a final action like posting to Slack), and it only earns its place once no built-in reporter produces what you actually need.

## Recap in 60 Seconds

If you only remember three things:

1. The HTML report has been sitting there since the project structure and config lesson. Open it with `npx playwright show-report` and follow a failure's trace link into trace viewer instead of guessing from the terminal.
2. Add `json` for scripts and `junit` for CI alongside `html`, since they're different formats built for different consumers, not redundant copies of the same report.
3. Only reach for a custom reporter when you need something none of the built-ins do. Implement `onTestEnd` to accumulate state and `async onEnd` to act on it, and always `await` your async work inside `onEnd` so it actually completes before the process exits.

## Try It

Extend the custom `SlackReporter` from [Build It](./build-it): track failed test titles in an array (not just a count) inside `onTestEnd`, and have `onEnd` include the list of failed test names in the Slack message when `result.status !== 'passed'`, instead of just the pass/fail totals. Then reconfigure `reporter` to run the full suite against all four roles' authenticated `storageState` fixtures from the authentication lesson, and confirm `results.xml` produces one `<testcase>` per role per spec, the shape a CI test-reporting action would actually parse.
