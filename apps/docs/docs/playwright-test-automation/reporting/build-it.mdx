# Reporting in Playwright — Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Trigger a Real Failure

Reporters are easiest to understand against a failure you caused on purpose. Take the nurse-schedules-an-appointment spec and break one locator deliberately, so you have something real to read in the report:

```typescript title="tests/appointments.spec.ts"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/nurse.json' });

test('nurse schedules an appointment', async ({ page }) => {
  await page.goto('/dashboard');
  await page.getByRole('button', { name: 'Schedule Appointment' }).click();

  await page.getByLabel('Patient').selectOption({ label: 'Priya Nair' });
  await page.getByLabel('Doctor').selectOption({ label: 'Dr. Amara Okafor' });
  await page.getByLabel('Date').fill('2026-08-10');
  await page.getByRole('button', { name: 'Confirm' }).click();

  // Deliberately wrong text, to produce a real failure for this lesson.
  await expect(page.getByText('Appointment booked successfully')).toBeVisible();
});
```

Run it:

```bash
npx playwright test appointments.spec.ts
```

The terminal reports one failure and one line you've likely skimmed past in every module so far:

```text
1 failed
  [chromium] › appointments.spec.ts:6:5 › nurse schedules an appointment

To open last HTML report run:

  npx playwright show-report
```

### Step 2: Open and Read the HTML Report

Run the command the terminal just gave you:

```bash
npx playwright show-report
```

This opens `playwright-report/index.html` in a browser — the file `reporter: 'html'` has been writing since the project structure and config lesson, on every run, whether or not you looked at it. Click the failed test. You get, in one place:

- The exact assertion that failed — `expect(locator).toBeVisible()` — and the locator it was checking (`getByText('Appointment booked successfully')`)
- A screenshot of the page at the moment of failure
- The full error stack, including how long Playwright retried before giving up
- If a trace was captured for this run, a **View trace** link

This is already more than the terminal gave you: you can see the confirmation toast actually said something else, at a glance, without reproducing anything locally.

### Step 3: Follow the Trace Link into Trace Viewer

Your `playwright.config.ts` has had `trace: 'on-first-retry'` since setup, so a trace only exists for this failure if the test retried at least once. For this lesson, force a trace on every run so there's always one to inspect:

```typescript title="playwright.config.ts"
use: {
  baseURL: process.env.BASE_URL ?? 'http://localhost:3002',
  trace: 'on',
},
```

Re-run the spec, reopen the report, and click **View trace** on the failure. This hands off from the HTML report straight into trace viewer — the same tool the debugging and troubleshooting lesson covers in depth for diagnosing flaky tests. From here you can:

- Scrub through every action the test took, step by step
- Inspect the DOM exactly as it existed at the moment `getByText('Appointment booked successfully')` gave up looking
- Read the Network tab and confirm `POST /api/appointments` actually succeeded — proving the failure is a text mismatch, not a broken booking flow

That last point is the real value of the HTML-report-to-trace-viewer path: it answers "was this a real bug or a bad assertion" in under a minute, without adding a single `console.log` or rerunning anything locally with `--debug`.

Revert `trace` back to `'on-first-retry'` once you're done — capturing a trace on every single run is useful for this lesson, not for your everyday config, since it adds overhead to every test whether it fails or not.

```typescript title="playwright.config.ts"
use: {
  baseURL: process.env.BASE_URL ?? 'http://localhost:3002',
  trace: 'on-first-retry',
},
```

### Step 4: Add JSON and JUnit Reporters Alongside HTML

The HTML report is for you, reading it in a browser — nothing about it is meant to be parsed by another program. Now add two more reporters alongside it, each built for a different kind of consumer:

```typescript title="playwright.config.ts"
export default defineConfig({
  testDir: './tests',
  fullyParallel: true,

  reporter: [
    ['html'],
    ['json', { outputFile: 'results.json' }],
    ['junit', { outputFile: 'results.xml' }],
  ],

  // ...webServer, use, and projects unchanged from the project structure and config lesson
});
```

`reporter` now takes an array of `[name, options]` tuples instead of a single string. All three run against the same test run — you haven't replaced the HTML report, you've added two more outputs alongside it.

### Step 5: Inspect the JSON Output

Run the suite again, then open `results.json`:

```bash
npx playwright test
```

```json title="results.json (excerpt)"

      "specs": [
        {
          "title": "nurse schedules an appointment",
          "tests": [
            {
              "results": [
                {
                  "status": "passed",
                  "duration": 1834
                }

            }

  ],
  "stats": {
    "expected": 13,

    "flaky": 0,
    "duration": 24671

```

This is the entire run, structured, in one file — every spec, its status, its duration, and (for failures) the full error object. Nobody reads this file directly; it exists so a script can. If you wanted to build a custom dashboard, compute your own flake rate over time, or feed results into an internal tool, `results.json` is the format built for that — not `results.xml`, and not scraping the HTML report's markup.

### Step 6: Inspect the JUnit Output, and Why CI Wants This One Specifically

Open `results.xml`:

```xml title="results.xml (excerpt)"
<testsuites id="" name="" tests="13" failures="0" skipped="0" errors="0" time="24.671">
  <testsuite name="appointments.spec.ts" timestamp="2026-07-26T10:15:03.000Z" tests="1" failures="0" time="1.834">
    <testcase name="nurse schedules an appointment" classname="appointments.spec.ts" time="1.834" />
  </testsuite>
</testsuites>
```

JUnit XML predates Playwright by two decades — it came out of the Java testing ecosystem, and by now every major CI platform (GitHub Actions, GitLab CI, CircleCI, Jenkins) already ships built-in support for parsing it, specifically the `<testsuite>` / `<testcase>` / `<failure>` shape. That's the entire reason it's still the CI-facing format in 2026: not because the format is elegant, but because it's the one format a CI system doesn't need Playwright-specific knowledge to understand.

This matters concretely once CI enters the picture: a GitHub Actions workflow can point a test-reporting action at `results.xml` and get per-test pass/fail annotations directly on a pull request's **Checks** tab — a red X next to the exact test that broke, on the exact line of the diff, without anyone opening a report by hand. `results.json` cannot do this, not because it's missing data, but because GitHub's (and every other CI platform's) annotation tooling was built to read `<testcase>` elements, not Playwright's JSON schema.

### Step 7: Write a Minimal Custom Reporter

Neither `html`, `json`, nor `junit` posts to Slack. When you need something a built-in reporter doesn't produce, you write a class implementing Playwright's `Reporter` interface. Here's the minimum viable version — a running pass/fail tally, posted to a Slack webhook when the run ends:

```typescript title="slack-reporter.ts"
import type {
  Reporter,
  TestCase,
  TestResult,
  FullResult,
} from '@playwright/test/reporter';

class SlackReporter implements Reporter {
  private passed = 0;
  private failed = 0;

  onTestEnd(test: TestCase, result: TestResult): void {
    if (result.status === 'passed') {
      this.passed += 1;
    } else if (result.status === 'failed' || result.status === 'timedOut') {
      this.failed += 1;
    }
  }

  async onEnd(result: FullResult): Promise<void> {
    const webhookUrl = process.env.SLACK_WEBHOOK_URL;
    if (!webhookUrl) {
      console.warn('SLACK_WEBHOOK_URL not set — skipping Slack notification.');
      return;
    }

    const summary = `RBAC suite: ${this.passed} passed, ${this.failed} failed (${result.status})`;

    await fetch(webhookUrl, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ text: summary }),
    });
  }
}

export default SlackReporter;
```

`onTestEnd` fires once per test, with that test's final `status` — this is where you accumulate whatever you care about, the same way you'd update counters in any loop. `onEnd` fires exactly once, after every test has finished, with the run's overall `status` (`'passed'`, `'failed'`, `'timedout'`, or `'interrupted'`) — this is where you do something with what you accumulated. `onEnd` can be `async`; Playwright waits for it to resolve before the process exits, so the Slack POST reliably completes before the run reports itself done.

The webhook URL comes from `process.env.SLACK_WEBHOOK_URL`, never hardcoded — set it locally in your shell, and as a CI secret in the continuous integration lesson's GitHub Actions workflow.

### Step 8: Register the Custom Reporter Alongside the Built-In Ones

Add it to the `reporter` array by file path, exactly like the built-in entries:

```typescript title="playwright.config.ts"
reporter: [
  ['html'],
  ['json', { outputFile: 'results.json' }],
  ['junit', { outputFile: 'results.xml' }],
  ['./slack-reporter.ts'],
],
```

Run the suite once more:

```bash
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/your/webhook/url npx playwright test
```

All four reporters run against the same test run: `html` writes a browsable report, `json` and `junit` write their respective files, and `SlackReporter` posts one summary message when everything finishes. None of the four know the others exist — `reporter` runs each one independently against the same stream of test events.

## How It Works Internally

Every reporter — built-in or custom — implements the same `Reporter` interface: `onBegin` (once, when the run starts, with the full list of tests), `onTestBegin` / `onTestEnd` (once per test), and `onEnd` (once, when the run finishes, with the overall result). Playwright doesn't run tests once per reporter — it runs the suite exactly once and calls every registered reporter's matching hook, in the order you listed them, as each event happens. That's why adding `json` and `junit` alongside `html` doesn't slow your suite down proportionally to the number of reporters: they're all just listeners on the same run, not separate executions of it.

This is also why a custom reporter can safely accumulate state across `onTestEnd` calls in instance fields, the way `SlackReporter` does with `passed` and `failed` — Playwright constructs one instance of your reporter class per run and calls its hooks against that same instance throughout, not a fresh instance per test.
