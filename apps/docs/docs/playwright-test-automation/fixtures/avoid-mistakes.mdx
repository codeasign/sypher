# Fixtures: Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Not every piece of setup deserves a fixture. A value used by exactly one test, or setup that legitimately needs to vary per test in a way that would make a shared fixture's parameters more complicated than the inline code it replaces, is often clearer written directly in that one test. Fixtures earn their keep through reuse and through the setup/teardown discipline they enforce. A fixture nobody else will ever destructure is indirection with no payoff.

Worker scope specifically is not a shortcut for "run this less often" in general. It's for setup that is genuinely safe to share across every test in that worker. Anything a test mutates in a way another test in the same worker must not see belongs at test scope, even if that means paying the setup cost more times. Sharing something worker-scoped that shouldn't be shared doesn't save time; it produces order-dependent test failures that are far more expensive to debug than the time the sharing was meant to save.

## The Pattern to Remember

- **Pattern:** Match fixture scope to the real-world cost and blast radius of the setup. Expensive and safely shareable goes to `'worker'` scope, while anything a test mutates, or that must stay isolated from other tests, stays at the `'test'` scope default.
- **When to use:** Reach for a fixture when setup or teardown logic repeats across more than a couple of spec files, especially when there's a cleanup step that's easy to forget by hand.
- **When NOT to use:** Skip it for one-off setup used by a single test, or for state that genuinely needs to differ per test in ways a shared fixture's parameters can't express cleanly.
- **Mental model:** Think of a fixture as a small, self-contained setup-and-teardown unit. The spec declares what it needs by destructuring it, and `test.extend()` is the container that knows how to build it, in what order, and how to tear it down, so the spec body never has to know any of that.

## Common Mistakes

### Mistake 1: Making the DB Reset Test-Scoped

**Mistake:** You define `dbReset` (or an equivalent seed-reset fixture) with the default `'test'` scope instead of `'worker'`, so it ends up running before every single test instead of once per worker.

**Why it happens:** `'test'` is the default scope, so a fixture written without thinking about scope explicitly ends up test-scoped by default, and it works correctly the first time you run it, just slowly.

**Symptoms:** A suite that used to run in two minutes starts taking twenty, and the slowdown scales linearly with the number of tests rather than the number of workers. That's a strong signal that something expensive is running per test instead of per worker.

**Fix:** Move genuinely shareable, expensive setup to `{ scope: 'worker' }`, as in this lesson's `dbReset`. Reserve test scope for things that must be isolated per test, like `testPatient`, where the whole point is that each test gets its own disposable record.

### Mistake 2: Skipping Teardown After a Failed Assertion

**Mistake:** You write a fixture that creates something (a browser context, an API-created patient) but structure the code so an early `return` or a thrown error before `use()` skips the cleanup that comes after it, or you leave the cleanup out entirely and trust the next test run to overwrite the leftover state.

**Why it happens:** The teardown line lives after `await use(value)`, so it's easy to write and verify against a passing test without noticing that a *failing* test would take a different code path through the fixture and never reach that line.

**Symptoms:** Orphaned patients or appointments accumulate in the seeded database across CI runs; a later test's assertion on "the list has exactly 15 patients" starts failing for a reason that has nothing to do with the code that test is actually checking.

**Fix:** Keep the fixture body linear: setup, `await use(value)`, teardown, with no early returns between setup and `use()`. Playwright runs the code after `use()` even when the test itself throws, so a straightforward fixture body gets the guarantee for free; a fixture with conditional branches around `use()` can defeat it.

### Mistake 3: Assuming `storageState` Authenticates `APIRequestContext` Too

**Mistake:** You point an `APIRequestContext` fixture at the same `storageState` file a `Page` fixture uses, and expect API requests to come back authenticated.

**Why it happens:** `storageState` does authenticate `page.request` calls made through an already-authenticated browser context, so it's a reasonable guess that it authenticates any `APIRequestContext` the same way. For a JWT stored in `localStorage` after login, though, `storageState`'s cookie replay has nothing to attach to a bare request context that never ran any frontend JavaScript.

**Symptoms:** Requests made through the fixture return `401 Unauthorized`, even though the exact same `storageState` file works perfectly for `doctorPage` and every UI-level test passes.

**Fix:** Give API-scoped fixtures their own explicit login step, as `adminRequest` does in this lesson: `POST /api/auth/login`, read the token out of the response body, and set it as an `Authorization: Bearer` header via `extraHTTPHeaders`. Treat browser auth and API auth as two different fixtures with two different mechanisms, not one `storageState` file doing double duty.

### Mistake 4: A Worker-Scoped Fixture Depending on a Test-Scoped One

**Mistake:** You write a worker-scoped fixture that destructures a test-scoped fixture as one of its own parameters, for example, trying to make `dbReset` depend on `doctorPage`.

**Why it happens:** Fixture composition (Step 5 of this module's Build It lesson) makes dependency between fixtures feel completely general, so it's a natural assumption that any fixture can depend on any other.

**Symptoms:** A TypeScript compile error, or at runtime an error naming the fixture and explaining that a worker-scoped fixture cannot depend on a test-scoped one, because a test-scoped fixture is rebuilt for every test, and a worker-scoped fixture that only builds once has no single instance of it to attach to.

**Fix:** Dependencies only flow one direction: test-scoped fixtures can depend on worker-scoped ones (as `doctorPage` implicitly can depend on the built-in worker-scoped `browser` fixture), never the other way around. If a worker-scoped fixture seems to need something test-scoped, that's a sign the setup actually belongs at test scope.

### Mistake 5: Building One God Fixture Instead of Composing Small Ones

**Mistake:** You fold DB reset, authentication, and test-data seeding into a single fixture, for example, one `doctorPageWithPatient` fixture that does everything `dbReset`, `doctorPage`, `adminRequest`, and `testPatient` do combined, instead of composing four small, independently reusable ones.

**Why it happens:** It feels like less code to write once, and for the first spec that needs exactly that combination, it works fine.

**Symptoms:** A second spec needs a doctor page without a test patient, or a patient fixture without doctor auth, and the "clean" single fixture has to be copy-pasted and modified rather than reused. The exact duplication problem fixtures exist to eliminate reappears one level up.

**Fix:** Keep each fixture responsible for one thing (one role's authenticated page, one API client, one disposable record type) and let specs compose the ones they need by destructuring more than one, the way `test('doctor views a freshly created patient record', async ({ doctorPage, testPatient }) => { ... })` does. Composition at the point of use scales; composition baked into one fixture's implementation doesn't.
