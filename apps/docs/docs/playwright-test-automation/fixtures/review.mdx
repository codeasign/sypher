# Fixtures: Review

⏱ 4 minutes

## Key Takeaways

- `test.extend<TestFixtures, WorkerFixtures>({ ... })` layers custom setup and teardown onto Playwright's base `test`. A spec destructures only the fixtures it needs, and Playwright takes care of resolving and tearing each one down without the spec body ever seeing the plumbing.
- Scope is something you choose deliberately, not a default to accept without thinking: `'worker'`-scoped fixtures (like `dbReset`) build once per worker process and are safe for expensive, shareable setup, while `'test'`-scoped fixtures (the default) build fresh per test and are the right home for anything a test mutates or that must stay isolated, like `doctorPage`, `adminRequest`, and `testPatient`.
- `auto: true` runs a fixture for every test in its scope without any spec having to destructure it, a good fit for a guarantee like "the database is seeded," which shouldn't depend on a spec author remembering to ask for it.
- `storageState` authenticates a browser `Page`/context by replaying cookies and `localStorage`, but it doesn't authenticate an `APIRequestContext` the same way for a JWT/`localStorage`-based app, so API-facing fixtures need their own explicit login and bearer token, the way `adminRequest` does.
- Fixture composition, one fixture depending on another (`testPatient` on `adminRequest`), and a spec destructuring more than one fixture together (`{ doctorPage, testPatient }`), is what replaces the repeated login-then-seed boilerplate every spec would otherwise have to carry on its own.

## Recap in 60 Seconds

If you only remember three things:

1. `test.extend()` gives every spec exactly the setup it asks for, with teardown guaranteed even when the test fails, so write it once in `fixtures.ts`, and import `test` from there instead of `@playwright/test`.
2. Match scope to cost and blast radius: expensive and shareable goes worker-scoped, while anything mutated or isolation-sensitive stays test-scoped.
3. `storageState` covers browser `Page` auth only, so give API fixtures their own login step and bearer token.

## Try It

Extend `fixtures.ts` with a `nursePage` fixture, parallel to `doctorPage` but pointed at `playwright/.auth/nurse.json`, and a `testAppointment` fixture composed on top of `adminRequest` the same way `testPatient` is, creating a disposable appointment via `POST /api/appointments` before the test and deleting it via `DELETE /api/appointments/:id` after. Then write a spec that destructures `{ nursePage, testAppointment }` together and asserts that the nurse's dashboard shows the new appointment and that the nurse can cancel it, reusing the RBAC permission matrix's rule, covered later in this course, that nurses can cancel appointments.
