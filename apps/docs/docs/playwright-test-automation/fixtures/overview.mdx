# Fixtures

⏱ 15 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Write custom fixtures with `test.extend()`, typing both the test-scoped and worker-scoped values correctly
- Hand a test a page that's already authenticated as a given role, so no login steps get repeated inside the test body
- Choose between worker-scoped and test-scoped fixtures based on cost and isolation, and use that to reset the RBAC database once per worker instead of once per test
- Compose an authenticated-page fixture with an API-seeded test-data fixture, so a single spec gets both without having to wire them together itself
- Recognize why `storageState` authenticates a browser `Page` but not an `APIRequestContext` talking to a JWT-based API

## Why This Matters

A previous lesson solved login at the **project** level: `playwright.config.ts` defines an `admin`, `doctor`, `nurse`, and `patient` project, each with its own `use.storageState`, and `globalSetup` produces the four `playwright/.auth/{role}.json` files those projects load. That works well for a spec file where every test is the same role. Run it with `--project=doctor` and every test in that file gets a doctor's `page` fixture, no login code anywhere.

It stops working the moment a single test needs more than one role at once. "A nurse schedules an appointment, then a doctor completes it, and the assertion checks both dashboards" cannot run under one project, because a project's `storageState` picks exactly one role for the whole file. There's no way to hand that one test a second, differently-authenticated `page` from inside it. That gap, plus the same recurring need for disposable test data (a patient created via the API before the test, deleted after), is what custom fixtures solve. A `doctorPage` fixture builds its own context from `playwright/.auth/doctor.json` on demand, independent of whatever project the file is running under, so a test can request `doctorPage` and `nursePage` side by side in the same function signature.

Fixtures are Playwright's answer to this: a way to hand each test exactly the setup it asks for, similar in spirit to dependency injection if you've used that term elsewhere. A spec asks for what it needs (`doctorPage`, `testPatient`) and `test.extend()` figures out how to build it, in what order, and how to tear it down, without the spec body knowing any of the plumbing.

## The Problem

Picture a spec testing that a doctor can view a patient's medical record, a scenario that, per the above, doesn't fit cleanly into one project because it also needs a patient created specifically for this test:

```typescript
test('doctor views a patient medical record', async ({ browser, request }) => {
  const context = await browser.newContext({
    storageState: 'playwright/.auth/doctor.json',
  });
  const page = await context.newPage();

  // create a patient to view, by hand, inline, using an admin-authenticated
  // request context built from scratch right here
  const loginResponse = await request.post('http://localhost:5000/api/auth/login', {
    data: { username: 'admin', password: 'admin123' },
  });
  const { token } = await loginResponse.json();
  const createResponse = await request.post('http://localhost:5000/api/patients', {
    headers: { Authorization: `Bearer ${token}` },
    data: { firstName: 'Test', lastName: 'Patient', dateOfBirth: '1990-01-01' },
  });
  const patient = await createResponse.json();

  await page.goto(`/patients/${patient.id}`);
  await expect(page.getByRole('heading', { name: patient.lastName })).toBeVisible();

  // cleanup, easy to forget, easy to skip on a failing test
  await request.delete(`http://localhost:5000/api/patients/${patient.id}`, {
    headers: { Authorization: `Bearer ${token}` },
  });
  await context.close();
});
```

Multiply this by every spec that needs a doctor-authenticated page alongside a disposable patient, and two things go wrong. First, the setup code drowns the assertion that actually matters: you have to read past a dozen lines of context, login, and fetch plumbing to find the one `expect()` the test is about. Second, cleanup is easy to skip, especially when a test fails partway through and the teardown lines never run, leaving orphaned patients that the next test run has to work around.

## The Concept

`test.extend()` builds a new `test` function layered on top of Playwright's base `test`. Each fixture you define is a function that receives the fixtures it depends on, sets something up, hands it to the test via `use(value)`, and, after the test finishes, runs whatever comes after that `use()` call as teardown. A spec that destructures `{ doctorPage, testPatient }` in its test function never sees any of that; it just gets a logged-in `Page` and a patient record that already exists.

Two things make fixtures more than a helper function you could `import` instead:

1. **Scope.** A fixture is either `'test'`-scoped (the default, built fresh for every test, torn down after) or `'worker'`-scoped (built once per worker process, shared by every test that worker runs, torn down when the worker exits). A worker, in Playwright terms, is one of the parallel processes that actually runs your tests. A cheap per-test login stays test-scoped. An expensive DB reset that's safe to share belongs at worker scope, since running it before every single test would make your suite slow for no isolation benefit, given that the seed data itself doesn't change between tests that don't mutate it.
2. **Composition.** Fixtures can depend on other fixtures, including ones you wrote yourself. A `testPatient` fixture that needs an authenticated API client just destructures `adminRequest` as one of its own parameters, and Playwright resolves the dependency graph and builds things in the right order automatically.

Put those two ideas together and you get a small hierarchy for this app. At the bottom sits a worker-scoped `dbReset` fixture, marked `auto: true` so it runs on its own without any spec having to ask for it: it re-seeds the database once per worker process, giving every test in that worker the same clean baseline. Above that sit three test-scoped fixtures, each built fresh per test. `doctorPage` logs in from the stored `storageState` and hands back an authenticated `Page`. `adminRequest` logs in against the API directly and hands back a bearer token wrapped in an `APIRequestContext`. `testPatient` composes on top of `adminRequest`: it creates a patient before the test runs and deletes it afterward, using the token `adminRequest` already obtained. A spec never has to ask for `adminRequest` directly. It only asks for `testPatient`, and Playwright pulls the dependency in underneath, the same way it pulls in `dbReset` at the very start of the worker's first test.

That's fixture composition, and it's what turns the fetch-and-cleanup boilerplate from the Problem section into a single destructured parameter.
