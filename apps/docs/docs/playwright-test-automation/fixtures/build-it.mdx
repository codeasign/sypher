# Fixtures — Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Define the Fixture Types

`test.extend()` takes two type parameters: the test-scoped fixtures object shape, and the worker-scoped fixtures object shape. Declaring both up front is what gives you autocomplete and compile errors if a spec asks for a fixture that doesn't exist.

Create `fixtures.ts` at your repo root, next to `playwright.config.ts`:

```typescript title="fixtures.ts"
import { test as base, type Page, type APIRequestContext } from '@playwright/test';

type TestPatient = {
  id: number;
  firstName: string;
  lastName: string;
  dateOfBirth: string;
};

type TestFixtures = {
  doctorPage: Page;
  adminRequest: APIRequestContext;
  testPatient: TestPatient;
};

type WorkerFixtures = {
  dbReset: void;
};
```

`dbReset` has no meaningful value to hand back to a test — its job is the side effect of reseeding, not a return value — so its type is `void`. `doctorPage`, `adminRequest`, and `testPatient` all hand a real object to the test, so they're typed accordingly.

### Step 2: Add a Worker-Scoped DB Reset Fixture

Several later modules in this course mutate data — cancelling an appointment, deleting a user, that kind of thing. If those mutations from one test leaked into the next, the results would start depending on run order. Re-seeding before every single test would fix that but cost real time for no benefit on the majority of tests that don't touch shared data. A worker-scoped fixture splits the difference: reseed once when a worker process starts, share that baseline across every test the worker runs.

```typescript title="fixtures.ts (continued)"
import path from 'node:path';
import { execSync } from 'node:child_process';

const BACKEND_DIR = path.resolve(__dirname, '../rbac-healthcare-system/backend');
```

Adjust `BACKEND_DIR` to wherever your fork of `rbac-healthcare-system` actually lives relative to your Playwright project.

### Step 3: Add a Test-Scoped Authenticated `doctorPage` Fixture

This is the fixture that replaces the `browser.newContext({ storageState })` boilerplate from every spec. It reuses the storageState file the authentication lesson's `globalSetup` already produced — this fixture doesn't do any authentication of its own, it just wires an existing credential into a fresh browser context per test.

```typescript title="fixtures.ts (continued)"
const DOCTOR_STORAGE_STATE = 'playwright/.auth/doctor.json';
```

`doctorPage` is test-scoped (the default) because a `Page` is cheap to create and each test should get its own isolated context — sharing one `Page` object across tests would let one test's navigation or state bleed into the next.

### Step 4: Add an API-Authenticated `adminRequest` Fixture

This is the fixture the module's "Common Mistakes" page in this series calls out directly: `storageState` authenticates a browser `Page` by replaying its saved cookies and `localStorage`, but `APIRequestContext` has no DOM and no `localStorage` — a JWT the frontend stores in `localStorage` after login never reaches a raw API request just because you point it at the same `storageState` file. An API-scoped fixture needs its own login step and an explicit bearer token.

```typescript title="fixtures.ts (continued)"
const BACKEND_URL = 'http://localhost:5000';
const ADMIN_CREDENTIALS = { username: 'admin', password: 'admin123' };
```

### Step 5: Compose an API-Seeded `testPatient` Fixture

`testPatient` depends on `adminRequest` — it doesn't log in on its own, it destructures the fixture from Step 4 and uses it. This is fixture composition: one custom fixture built on top of another, with Playwright resolving the order.

Check your fork's Swagger UI at `http://localhost:5000/api-docs` for the exact request/response shape of the patients endpoint before wiring this into a real spec — the field names below are illustrative of the pattern, not a guarantee of this exact schema.

### Step 6: Extend `test` and Export It

Now assemble every fixture from Steps 2–5 into one `test.extend()` call. This is the complete file:

```typescript title="fixtures.ts (complete)"
import { test as base, expect, type Page, type APIRequestContext } from '@playwright/test';
import path from 'node:path';
import { execSync } from 'node:child_process';

const BACKEND_DIR = path.resolve(__dirname, '../rbac-healthcare-system/backend');
const BACKEND_URL = 'http://localhost:5000';
const DOCTOR_STORAGE_STATE = 'playwright/.auth/doctor.json';
const ADMIN_CREDENTIALS = { username: 'admin', password: 'admin123' };

type TestPatient = {
  id: number;
  firstName: string;
  lastName: string;
  dateOfBirth: string;
};

type TestFixtures = {
  doctorPage: Page;
  adminRequest: APIRequestContext;
  testPatient: TestPatient;
};

type WorkerFixtures = {
  dbReset: void;
};

export const test = base.extend<TestFixtures, WorkerFixtures>({
  // Worker-scoped: runs once when a worker process starts, shared by
  // every test that worker runs. `auto: true` means a spec never has to
  // destructure it for the reset to happen.
  dbReset: [
    async ({}, use) => {
      execSync('npm run seed', { cwd: BACKEND_DIR, stdio: 'inherit' });
      await use();
    },
    { scope: 'worker', auto: true },
  ],

  // Test-scoped: a fresh browser context per test, pre-authenticated as
  // doctor via the storageState the authentication lesson's globalSetup captured. No login
  // steps run inside the test body.
  doctorPage: async ({ browser }, use) => {
    const context = await browser.newContext({ storageState: DOCTOR_STORAGE_STATE });
    const page = await context.newPage();
    await use(page);
    await context.close();
  },

  // Test-scoped: an APIRequestContext carrying an admin bearer token.
  // storageState does not carry over to APIRequestContext for a
  // JWT/localStorage app, so this logs in for itself.
  adminRequest: async ({ playwright }, use) => {
    const loginContext = await playwright.request.newContext({ baseURL: BACKEND_URL });
    const loginResponse = await loginContext.post('/api/auth/login', { data: ADMIN_CREDENTIALS });
    const { token } = await loginResponse.json();
    await loginContext.dispose();

    const adminContext = await playwright.request.newContext({
      baseURL: BACKEND_URL,
      extraHTTPHeaders: { Authorization: `Bearer ${token}` },
    });
    await use(adminContext);
    await adminContext.dispose();
  },

  // Test-scoped, composed on top of adminRequest: creates a disposable
  // patient before the test, deletes it after — regardless of whether
  // the test passed or failed.
  testPatient: async ({ adminRequest }, use) => {
    const createResponse = await adminRequest.post('/api/patients', {
      data: {
        firstName: 'Fixture',
        lastName: `Patient-${Date.now()}`,
        dateOfBirth: '1990-01-01',
      },
    });
    const patient: TestPatient = await createResponse.json();

    await use(patient);

    await adminRequest.delete(`/api/patients/${patient.id}`);
  },
});

export { expect };
```

### Step 7: Use the Fixtures Together in a Spec

Import `test` and `expect` from `fixtures.ts` instead of `@playwright/test` in any spec that needs these fixtures. A test that needs both an authenticated doctor page and a disposable patient just destructures both — this is the fixture composition from the overview lesson, now at the point of use:

```typescript title="tests/patient-record.spec.ts"
import { test, expect } from '../fixtures';

test('doctor views a freshly created patient record', async ({ doctorPage, testPatient }) => {
  await doctorPage.goto(`/patients/${testPatient.id}`);

  await expect(
    doctorPage.getByRole('heading', { name: `${testPatient.firstName} ${testPatient.lastName}` }),
  ).toBeVisible();
  await expect(doctorPage.getByText(testPatient.dateOfBirth)).toBeVisible();
});
```

Compare this to the Problem section's version: no `browser.newContext()`, no manual `fetch()`, no cleanup line to forget. The spec body is entirely the scenario — navigate, assert — because every piece of setup and every piece of teardown lives in `fixtures.ts`, written once and reused by every spec that needs it.

## How It Works Internally

When a test function destructures `{ doctorPage, testPatient }`, Playwright doesn't just look up two independent values — it walks the fixture dependency graph. `testPatient` declares `adminRequest` as a parameter, so before `testPatient` can run, Playwright builds `adminRequest` first. `doctorPage` has no such dependency, so it builds independently. Fixtures with no dependency relationship to each other build in parallel; fixtures that depend on one another build in the order the dependency requires, automatically, without you sequencing anything by hand.

Every fixture function is really two phases split by `await use(value)`. Everything before that call is setup, everything after it is teardown, and Playwright guarantees the teardown for every fixture that was actually built — including ones for tests that failed — runs in the reverse order the fixtures were built in. That's why `testPatient`'s `DELETE` call after `use(patient)` is safe to write with confidence: it runs even if the `expect()` in the spec throws.

Scope changes when this all happens. `dbReset` is worker-scoped with `auto: true`, so Playwright builds it exactly once, the first time that worker process needs to run any test, before anything else — and tears it down only when the worker itself shuts down at the end of the run. `doctorPage`, `adminRequest`, and `testPatient` are test-scoped, so each one is built fresh and torn down completely for every single test, even tests running back-to-back in the same worker. That's the isolation guarantee: two tests in the same worker share the same seeded baseline from `dbReset`, but never share a `Page`, a `APIRequestContext`, or a patient record with each other.
