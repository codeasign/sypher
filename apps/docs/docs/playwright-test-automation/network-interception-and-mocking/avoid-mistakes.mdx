# Network Interception and Mocking: Common Mistakes

⏱ 8 minutes

## When NOT to Use This

Mocking is for isolating the frontend from backend state and for producing responses the real backend won't hand you on demand. It is not for verifying the backend actually works. A test that mocks `POST /api/appointments` to always return a success response proves nothing about whether the real Express route, its validation, or its SQLite write actually behave correctly. That's what your true end-to-end tests (hitting the real backend, as in every lesson before this one) and the `supertest-api-testing` course's in-process API tests are for. If you find yourself mocking a response just to make a test pass without understanding why the real one fails, stop. That's not isolation, that's avoidance.

## The Pattern to Remember

- **Pattern:** register `page.route()` before navigation. Use `route.fulfill()` to stub a response for frontend isolation or edge cases, and `route.continue()` after inspecting the request to verify headers or payload without touching the response.
- **When to use:** rendering logic tests that shouldn't depend on live seed data, edge-case responses (empty lists, server errors) the real backend can't produce on demand, and verifying the frontend sends correct auth headers or payloads.
- **When NOT to use:** as a substitute for real end-to-end coverage, or for verifying backend business logic. Use the real backend for that, or the `supertest-api-testing` course's in-process approach for API-level correctness.
- **Mental model:** `page.route()` is a checkpoint on the highway your browser's traffic already travels on its way to `localhost:5000`. Supertest never builds the highway at all; it hands the request straight to the Express app's mailroom, in the same process.

## Common Mistakes

### Mistake 1: Registering `page.route()` After `page.goto()`

**Mistake:** Calling `page.route('**/api/appointments', handler)` after the navigation that triggers the request it's meant to intercept.

**Why it happens:** It's easy to write the test in the order you're thinking about it ("go to the dashboard, then mock its data") without realizing the dashboard's `fetch` call already fired the instant `page.goto()` resolved.

**Symptoms:** The mock silently never applies. The test either shows real seeded data instead of your mocked payload, or times out waiting for mocked content that never appears, with no error pointing at the route registration itself.

**Fix:** Always call `page.route()` before the navigation or action that triggers the request. Register routes at the top of the test, before `page.goto()`.

### Mistake 2: Forgetting to Resolve an Intercepted Route

**Mistake:** Writing a route handler that reads `route.request()` to inspect headers or payload, but never calling `route.continue()`, `route.fulfill()`, or `route.abort()`.

**Why it happens:** When you're only trying to *observe* a request, like checking the `Authorization` header, it's easy to forget the request is genuinely paused, waiting for an explicit decision, not just being logged in passing.

**Symptoms:** The request hangs indefinitely. The page never finishes loading the data that depended on it, and the test times out with no obvious connection to the route handler.

**Fix:** Every route handler must end in exactly one of `route.continue()`, `route.fulfill()`, or `route.abort()`. If you only want to observe, call `route.continue()` as the last line of the handler.

### Mistake 3: Mocking the Response, Then Asserting Against Real Backend State

**Mistake:** Mocking `GET /api/appointments` in one part of a test, then asserting later in the same test against counts or records that only exist in the real, seeded database.

**Why it happens:** Once a route is active, it stays active for every matching request for the rest of the test. It's easy to forget it's still intercepting when you write a later assertion that assumes real data.

**Symptoms:** Confusing, hard-to-explain failures where the dashboard shows your mocked data everywhere, including in a later step of the test that was meant to check something about the real backend.

**Fix:** Keep tests that mock a route narrowly scoped to what the mock is isolating. If part of a test needs real backend data, use `page.unroute()` to remove the mock before that part runs, or split the mocked assertion into its own test.

### Mistake 4: Mocking So Much the Test Stops Proving Anything

**Mistake:** Intercepting every API call a page makes (appointments, auth, medical records, user profile) and fulfilling all of them with hand-written fixtures.

**Why it happens:** Once you've mocked one endpoint to stabilize a flaky test, it's tempting to mock the rest for the same "stability," especially under CI time pressure.

**Symptoms:** The suite passes reliably in CI and still ships a broken dashboard to production, because nothing in the test ever exercised the real backend's actual behavior. The tests were verifying that your fixtures render correctly, not that the app works.

**Fix:** Mock only the specific endpoint(s) relevant to the behavior you're isolating. Leave every other call to hit the real backend, or write the test as a full end-to-end test with no mocking at all if that's really what you need.

### Mistake 5: A Glob Pattern Broader Than the Endpoint You Meant to Touch

**Mistake:** Using a route pattern like `'**/api/*'` when you only meant to intercept `'**/api/appointments'`.

**Why it happens:** The broader pattern is quicker to type and "obviously" matches the endpoint you care about. It's easy not to notice it matches several others too.

**Symptoms:** Unrelated requests, like an auth-refresh call or a user-profile fetch, get pulled into the same handler and either hang (if the handler doesn't expect them) or get mocked with data that doesn't match what that endpoint actually returns, producing failures far from the endpoint you were testing.

**Fix:** Scope route patterns as narrowly as the specific endpoint you're mocking or inspecting. If a handler needs to branch on more than one endpoint, check `route.request().url()` explicitly inside it rather than widening the pattern to catch everything.
