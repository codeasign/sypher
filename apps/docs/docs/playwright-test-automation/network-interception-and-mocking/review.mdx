# Network Interception and Mocking — Review

⏱ 3 minutes

## Key Takeaways

- `page.route(urlPattern, handler)` intercepts a real browser network request before it's sent, so every handler has to resolve it with `route.fulfill()`, `route.continue()`, or `route.abort()`.
- `route.fulfill()` stubs a response entirely — useful for isolating dashboard-rendering tests from live seed data, and for producing edge-case responses (empty lists, 500 errors) the real backend won't give you on demand.
- `route.continue()` lets the real request through unmodified after you've inspected it — the way to assert on the JWT `Authorization` header and role claims, or an outgoing payload, without altering what the backend actually returns.
- Routes must be registered before the navigation or action that triggers the request; a route registered after `page.goto()` silently never applies.
- Mock for frontend isolation and edge cases you can't otherwise arrange; hit the real backend for true end-to-end coverage — the `supertest-api-testing` course's in-process approach (no socket, no browser, calling the Express `app` directly) is a different technique for a different layer, not a substitute for either.

## Recap in 60 Seconds

If you only remember three things:

1. `page.route()` intercepts a real request the browser is about to send — `fulfill()` to mock it, `continue()` to inspect and pass it through unchanged, and always resolve the route or the request hangs.
2. Register routes before navigation, keep glob patterns as narrow as the endpoint you mean to touch, and don't let a mocked response bleed into an assertion that expects real backend data.
3. Mocking isolates the frontend; it doesn't replace testing the real backend — Supertest tests the same Express app in-process with no network layer at all, which is why the two courses exist side by side rather than one replacing the other.

## Try It

Extend the nurse scheduling test from [Build It](./build-it): intercept `POST /api/appointments` and assert the outgoing payload's `date` field matches what you typed into the form, exactly as shown, but this time also assert on the `Authorization` header in the same handler, confirming the token's decoded `role` claim is `'nurse'` before calling `route.continue()`. Then write a second test, for the patient role, that mocks `GET /api/appointments` to return a 403 response and asserts the patient dashboard renders an appropriate access-denied message — a state you can't reliably arrange against the real backend on demand.
