# Network Interception and Mocking: Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Mock GET /api/appointments to Isolate the Dashboard Test

Start with the doctor dashboard test from the previous lesson's problem, but this time, instead of asserting against whatever the seed script happened to produce, hand the page a fixed payload and assert against that.

```typescript
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/doctor.json' });

test('doctor dashboard renders a mocked appointment list', async ({ page }) => {
  await page.route('**/api/appointments', (route) => {
    route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([
        { id: 101, patientName: 'Priya Nair', date: '2026-08-03', status: 'scheduled' },
        { id: 102, patientName: 'Tom Reyes', date: '2026-08-04', status: 'completed' },
      ]),
    });
  });

  await page.goto('/dashboard');

  await expect(page.getByRole('row', { name: /Priya Nair/ })).toBeVisible();
  await expect(page.getByRole('row', { name: /Tom Reyes/ })).toBeVisible();
  await expect(page.getByRole('row')).toHaveCount(3); // 2 data rows + header row
});
```

`page.route()` has to be registered **before** `page.goto()`. Playwright only intercepts requests it's watching for at the moment they're sent, so a route registered after navigation has already started is too late for the request that navigation triggers.

The `storageState` from the fixtures lesson's doctor fixture still does the authentication work here. You're not bypassing login, just replacing what the appointments endpoint returns after login succeeds. This test now proves one thing precisely: given this exact appointment data, the dashboard renders it correctly. It no longer cares how many appointments the seed script created.

### Step 2: Produce Edge Cases the Real Backend Won't Give You

An empty appointments list and a failed request are both real states the doctor dashboard has to handle, and neither is something you can reliably arrange by talking to the live backend.

```typescript
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/doctor.json' });

test('doctor dashboard shows an empty state with no appointments', async ({ page }) => {
  await page.route('**/api/appointments', (route) => {
    route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([]),
    });
  });

  await page.goto('/dashboard');

  await expect(page.getByText('No appointments scheduled')).toBeVisible();
});

test('doctor dashboard shows an error banner when the API fails', async ({ page }) => {
  await page.route('**/api/appointments', (route) => {
    route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({ error: 'Internal server error' }),
    });
  });

  await page.goto('/dashboard');

  await expect(page.getByRole('alert')).toContainText('Something went wrong');
});
```

Neither of these tests could be written reliably against the live backend without first deleting real seeded rows (breaking every other test that depends on them) or modifying the Express app to fail on command. Mocking gives you both states on demand, deterministically, without touching shared data.

### Step 3: Assert on an Outgoing Request Without Mocking the Response

Not every use of `page.route()` is about replacing the response. You can intercept a request purely to inspect it (its headers, method, and URL) and then call `route.continue()` so the real backend still answers it. This is how you verify the frontend is sending the JWT `Authorization` header correctly, without faking anything about what comes back.

```typescript
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/nurse.json' });

test('nurse dashboard sends a bearer token with the correct role claim', async ({ page }) => {
  let capturedAuthHeader: string | undefined;

  await page.route('**/api/appointments', async (route) => {
    const headers = route.request().headers();
    capturedAuthHeader = headers['authorization'];

    // Let the real request go through. This only observes, it doesn't mock.
    await route.continue();
  });

  await page.goto('/dashboard');
  await expect(page.getByRole('heading', { name: 'Nurse Dashboard' })).toBeVisible();

  expect(capturedAuthHeader).toMatch(/^Bearer .+/);

  const token = capturedAuthHeader!.replace('Bearer ', '');
  const payload = JSON.parse(Buffer.from(token.split('.')[1], 'base64').toString());

  expect(payload.role).toBe('nurse');
});
```

`route.request()` gives you the outgoing request before it's sent: its `headers()`, `url()`, and `method()`. Because you call `route.continue()` instead of `route.fulfill()`, the real backend still receives this exact request and answers it for real. The dashboard renders real data, and the test still passes or fails on real rendering behavior. The only thing you've added is an assertion on what the frontend sent, decoded straight out of the JWT payload: proof that the frontend attached the nurse's role claim correctly, not an assumption about it.

Every intercepted route must be resolved with `continue()`, `fulfill()`, or `abort()`. If your handler does none of these, the request hangs and the page never finishes loading.

### Step 4: Assert on an Outgoing Request Payload

The same technique applies to request bodies, not just headers. Here's a nurse scheduling an appointment, the one action nurses are permitted under the RBAC matrix, where the test verifies the exact payload the frontend sends to `POST /api/appointments`, then lets the real creation happen:

```typescript
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/nurse.json' });

test('scheduling an appointment sends the correct payload', async ({ page }) => {
  let capturedPayload: Record<string, unknown> | undefined;

  await page.route('**/api/appointments', async (route) => {
    if (route.request().method() === 'POST') {
      capturedPayload = route.request().postDataJSON();
    }
    await route.continue();
  });

  await page.goto('/dashboard');
  await page.getByRole('button', { name: 'Schedule Appointment' }).click();

  await page.getByLabel('Patient').selectOption({ label: 'Priya Nair' });
  await page.getByLabel('Doctor').selectOption({ label: 'Dr. Amara Okafor' });
  await page.getByLabel('Date').fill('2026-08-10');
  await page.getByRole('button', { name: 'Confirm' }).click();

  await expect(page.getByText('Appointment scheduled')).toBeVisible();

  expect(capturedPayload).toMatchObject({
    date: '2026-08-10',
  });
  expect(capturedPayload).toHaveProperty('patientId');
  expect(capturedPayload).toHaveProperty('doctorId');
});
```

`route.request().postDataJSON()` parses the outgoing body for you. Because the route only reads it and calls `route.continue()`, the appointment really gets created against the real backend. This one spec verifies both the outgoing contract (the payload shape the API expects) and the real end-to-end result (the confirmation message).

### Step 5: Scope Routes Deliberately

`page.route()` only applies to the `page` (and its popups) it was registered on, and only for the current test. Playwright tears it down automatically when the test ends, so you don't need manual cleanup in the common case. If you register a route you need to remove mid-test, use `page.unroute()`:

```typescript
await page.unroute('**/api/appointments');
```

The pattern you pass to `page.route()` is a glob pattern, a wildcard string where `**` matches anything, including slashes. Keep those patterns as narrow as the endpoint you actually mean to touch, because a broader pattern costs you more than you'd expect. `'**/api/appointments'` matches only that one resource, while `'**/api/*'` matches every API call the page makes, including ones you never meant to intercept, like an auth-refresh request the dashboard quietly fires in the background.

## How It Works Internally

`page.route()` works by attaching to the browser's DevTools Protocol (CDP), the same low-level interface Chrome DevTools itself uses, and telling the browser to pause any request matching your pattern before it leaves the network stack, instead of sending it immediately. That's why `route.continue()`, `route.fulfill()`, and `route.abort()` all exist as explicit resolutions: the browser is genuinely waiting, mid-flight, for Playwright to tell it what to do next. When you call `route.fulfill()`, Playwright hands the browser a synthetic response, and the real request is never dispatched onto the network at all. When you call `route.continue()`, the paused request resumes exactly as the browser originally built it (or as you've modified it, if you passed overrides), and travels to `localhost:5000` for real.

This is why `page.route()` and Supertest are not two ways of doing the same thing. Supertest's `supertest(app).get(...)` calls the Express `app` object as a function, in the same Node process running your test. There's no browser, no CDP, no socket, and therefore nothing for a network interceptor to pause. Playwright's mocking exists specifically because there *is* a real browser issuing a real request that something has to intercept; Supertest's approach exists specifically because it skips that layer entirely to test the API in isolation from any client.
