# Network Interception and Mocking

⏱ 15 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Use `page.route()` to stub a backend response, so your frontend tests stop depending on whatever the RBAC app's live, seeded database happens to contain right now
- Produce edge-case API responses (empty lists, server errors) that would be hard or flat-out impossible to arrange through the real backend
- Intercept an outgoing request and assert on its headers and payload, including the JWT `Authorization` header and role claims, then let the real response through unmodified
- Decide when to mock the backend and when to hit it for real, and explain why that decision looks different in Playwright than it does in the `supertest-api-testing` course

## Why This Matters

Every dashboard test you've written so far talks to the real backend. That's the right approach for most of this course: it's a real integration test, exercising the real Express routes, the real SQLite database, and the real JWT middleware. But it also means every one of those tests is coupled to whatever the seeded database happens to contain right now. A test that asserts the doctor dashboard shows exactly 22 appointments breaks the moment another test schedules a 23rd, or someone re-runs `npm run seed` with different counts, or a prior test in the same run leaves data behind. None of that is a bug in your app. It's a test that accidentally depends on state it doesn't own.

There's a second problem that no amount of careful seeding solves: some responses you need to test simply don't exist in the live backend on demand. What does the doctor dashboard render when the appointments list is empty? What does it render when `GET /api/appointments` returns a 500? You could try to force the database into those states before each test, but that's slow and fragile, and for a 500 response it's often impossible without modifying the backend itself.

`page.route()` solves both problems by intercepting the browser's real network request before it leaves your machine and answering it yourself. This lesson also draws a line you'll need for the rest of this course: mocking is a tool for isolating the frontend, not a substitute for testing against the real backend. The `supertest-api-testing` course tests this same Express app by calling it in-process, never opening a socket at all. That's a fundamentally different technique aimed at a different layer, and this lesson contrasts the two directly.

## The Problem

Here's a dashboard test that looks reasonable and is actually brittle:

```typescript
import { test, expect } from '@playwright/test';

test('doctor dashboard shows all appointments', async ({ page }) => {
  await page.goto('/dashboard');

  // Brittle: this count is only true because the seed script happens
  // to have created 22 appointments right now, for this doctor's data.
  await expect(page.getByTestId('appointment-row')).toHaveCount(22);
});
```

This test passes today. It fails the day someone reseeds the database with different numbers, the day a parallel test creates an extra appointment, or the day you deliberately want to see what the dashboard looks like with *zero* appointments, a state the real backend won't hand you on request. The test isn't verifying dashboard rendering logic. It's verifying today's seed data, which isn't what you meant to test at all.

## The Concept

`page.route(urlPattern, handler)` registers an interceptor for requests matching a URL pattern. When the browser is about to send a matching request, Playwright pauses it before it leaves the page and hands it to your handler, and that handler has to make a decision, because the request is genuinely sitting there mid-flight, waiting to find out what happens to it. You have three options:

- **`route.fulfill({...})`** answers the request with a response you construct yourself. The request never reaches the real backend at all.
- **`route.continue()`** lets the request go out to the real backend unmodified, after you've optionally inspected it.
- **`route.abort()`** simulates a network failure outright.

```typescript
import { test, expect } from '@playwright/test';

test('doctor dashboard renders a mocked appointment list', async ({ page }) => {
  await page.route('**/api/appointments', (route) => {
    route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([
        { id: 1, patientName: 'Jane Doe', date: '2026-08-01', status: 'scheduled' },
      ]),
    });
  });

  await page.goto('/dashboard');

  await expect(page.getByText('Jane Doe')).toBeVisible();
});
```

The real backend on `:5000` never sees this request. `route.fulfill()` answers it directly, with a payload you control completely. The dashboard has no way to tell the difference between this and a real response, because as far as the browser's network stack is concerned, it isn't one. Playwright is standing between the page and the network, deciding what comes back.

This is a fundamentally different mechanism from how the `supertest-api-testing` course tests the same backend. Supertest calls the Express `app` object directly, in the same Node process, and never opens a real socket, so there's no network layer to intercept because there's no network call to begin with. `page.route()`, by contrast, intercepts a request the browser is actually, really about to send over the network. Both are valid ways to isolate a test from full-system state. They operate at different layers, and this course and the Supertest course each exist to cover one of those layers properly.

To picture the difference: a Playwright test opens a real browser, which fires a real `fetch('/api/appointments')` call. `page.route()` sits on that call like a checkpoint, and either waves it through to the real Express backend on port 5000 (SQLite database, JWT middleware and all) or answers it itself with mocked JSON, in which case no request ever reaches the backend. A Supertest test skips all of that: it calls `supertest(app).get('/api/appointments')` against the Express app object directly, in the same Node process as the test, so there's no browser and no socket, and therefore nothing for a network interceptor to pause in the first place.
