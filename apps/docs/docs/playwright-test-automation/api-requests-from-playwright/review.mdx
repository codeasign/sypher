# API Requests from Playwright — Review

⏱ 5 minutes

## Key Takeaways

- Every test gets a `request` fixture (`APIRequestContext`) alongside `page` — it makes real HTTP calls straight to `http://localhost:5000/api/...`, with no browser involved at all.
- The hybrid pattern is: use `request` for everything that isn't the point of the test (background data, other roles' state), and `page` for the one flow the test actually exists to verify.
- `request` has its own identity model — log in with `request.post('/api/auth/login')`, capture the `token`, and attach it as an `Authorization: Bearer` header yourself on every call; it doesn't share `storageState` or cookies with `page`.
- Seeding five records via five API calls in a `beforeEach` is faster and more focused than five trips through a UI form — the test is left to check exactly one thing, not five unrelated form submissions plus one thing.
- This module overlaps with `supertest-api-testing` only at the mechanics of making an HTTP call. Pure API-level correctness testing belongs to that course; hybrid flows that combine an API call with a real page only exist here, because only here is there a `page` to combine it with.

## Recap in 60 Seconds

If you only remember three things:

1. `request` bypasses the browser entirely — direct HTTP to the backend, always checked with `expect(response.ok())` before you trust the body.
2. Seed and verify state via API when the API call isn't what's under test; keep at least one real UI-driven test for any form whose behavior the product actually depends on.
3. API setup and UI verification (or the reverse) can live in the same `test()` block — that combination is this course's reason to have a `request` fixture at all.

## Try It

Extend the appointment example from [Build It](./build-it): authenticate as a nurse via `request`, then `POST` a medical-record-worthy scenario — schedule three appointments for the same patient with three different doctors on three different dates. Then log in as that **patient** through the UI (not the doctor), `page.goto('/dashboard')`, and write a web-first assertion that all three appointments appear in the patient's own appointment list, each with the correct doctor and date. While you're there, add one negative check: authenticate as a *different* patient via `request` and confirm, through the UI, that their dashboard does **not** show any of the three appointments you just seeded.
