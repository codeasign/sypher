# API Requests from Playwright

⏱ 20 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Use the `request` fixture and `APIRequestContext` to call the RBAC backend directly over HTTP, from inside a test, without a browser involved at all
- Seed test data with a direct API call and verify it landed correctly through the UI, the hybrid pattern this module is built around
- Replace slow, repeated UI setup with fast API calls in `beforeEach`, so a test spends its time on the one thing it's actually checking
- Explain exactly where this overlaps with a dedicated API-testing course and where it doesn't

## Why This Matters

Most of what you've done so far in this course drives the browser to set up a scenario before testing it: log in through the login form, click through a multi-step "Schedule Appointment" flow, wait for a confirmation toast. That's correct when the flow itself is what you're testing. It's wasted motion when it isn't.

Say you're testing that a doctor's dashboard correctly lists their upcoming appointments. The thing under test is the dashboard's rendering and filtering logic, not the appointment-scheduling form. Driving the UI five times just to get five appointments into the database before your real assertion even starts is slow, and every one of those five trips through the form is a place a locator change or a loading-state race can break your setup for a reason that has nothing to do with what the test claims to verify.

The RBAC backend already exposes everything you need to create that data directly: a documented REST API at `http://localhost:5000/api`, visible in full at `/api-docs`. Playwright's `request` fixture lets a test reach into that API directly, the same test file, the same `test()` block, no separate tool, and combine it with real UI verification. That combination, API setup feeding a UI assertion (or the reverse: a UI action verified against the API), is what this module covers.

## The Problem

Here's the instinct you've built through the earlier lessons, applied to a scenario that doesn't need it:

```typescript
import { test, expect } from '@playwright/test';

test('doctor dashboard lists a newly scheduled appointment', async ({ page }) => {
  // Log in as nurse through the UI
  await page.goto('/login');
  await page.getByLabel('Username').fill('nurse1');
  await page.getByLabel('Password').fill('nurse123');
  await page.getByRole('button', { name: 'Log In' }).click();

  // Click through the entire scheduling form just to create one row of data
  await page.getByRole('link', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption({ label: 'Patient D' });
  await page.getByLabel('Doctor').selectOption({ label: 'Dr. Patel' });
  await page.getByLabel('Date').fill('2026-08-03');
  await page.getByLabel('Time').fill('10:30');
  await page.getByRole('button', { name: 'Confirm' }).click();
  await expect(page.getByText('Appointment scheduled')).toBeVisible();

  // Log out, log back in as the doctor, THEN finally get to what we're testing
  // ...
});
```

Everything above the comment "THEN finally get to what we're testing" is setup, not verification. It's also the part most likely to fail for an unrelated reason: a renamed label, a slower-than-usual confirmation toast, a `selectOption` that needs an exact value instead of a label. None of that failure would tell you anything about whether the doctor's dashboard actually renders appointments correctly, which is the one thing this test exists to check.

## The Concept

Every test written with `@playwright/test` already has access to a `request` fixture, injected the same way `page` is. `request` is an `APIRequestContext`, an HTTP client scoped to the test, completely independent of the browser:

```typescript
test('example', async ({ page, request }) => {
  // page drives the browser
  // request makes direct HTTP calls, no browser involved
});
```

Calling `request.post(...)`, `request.get(...)`, and so on sends a real HTTP request straight to whatever URL you give it, in this course, straight to `http://localhost:5000/api/...`. Nothing renders, nothing waits on a DOM, there's no actionability check to satisfy, because there's no page. It's the same shape of call a dedicated API-testing tool makes, just available from inside a Playwright test instead of a separate one.

That's the key distinction this module is built on: `request` isn't here to replace UI testing, and it isn't here to duplicate what a pure API-testing course already does well. It's here for **hybrid** flows: a single test that uses the API for the parts that aren't the point (creating background data, checking what actually landed in the database) and the UI for the part that is:

1. **API setup, then UI verification.** Create a patient, an appointment, or a medical record with a direct `POST`. It's fast, and it leaves you precise about exactly what state exists. Then `page.goto('/dashboard')` and assert, with a web-first `expect(locator)`, that the UI renders it correctly.
2. **UI action, then API verification.** Drive a real user flow through the browser, because that flow itself is what's under test, then use `request` to confirm the backend actually persisted what the UI claims it did, without waiting on another page to render it back to you.

Picture one test using both fixtures side by side. The `request` fixture (an `APIRequestContext`, no browser involved) sends a `POST` straight to the backend at `:5000`, say `/api/appointments`, with an `Authorization: Bearer <jwt>` header, and that write lands in the SQLite database. Separately, in the same test, the `page` fixture calls `page.goto('/dashboard')` against the frontend at `:3002`, and a web-first `expect(locator)` assertion confirms the doctor dashboard renders the appointment that request just created.

Both fixtures live in the same test, side by side. Nothing about `request` requires you to give up web-first assertions or auto-waiting for the part of the test that does touch the page. You get the speed of a direct API call exactly where you want it, and real UI verification exactly where that's the point.
