# API Requests from Playwright: Common Mistakes

⏱ 8 minutes

## When NOT to Use This

The hybrid pattern from this module, API setup feeding a UI assertion, is for the parts of a test that aren't the point. It stops being appropriate the moment the API call would replace the very thing you're supposed to be testing.

If a test exists to verify that the "Schedule Appointment" form validates correctly, disables the submit button until required fields are filled, or shows the right error when a nurse picks a date in the past, you cannot seed that appointment via `request.post()` and call the form tested. You'd be testing the API's validation instead, and calling it UI coverage. Keep at least one real, UI-driven test for every flow whose form behavior actually matters, and reserve API seeding for every other test that just needs the *result* of that flow to already exist. Pure API-level correctness, does the endpoint reject bad input, return the right status codes, enforce the permission matrix at the HTTP layer regardless of what any frontend does with the response, belongs to a dedicated API-testing course that never opens a browser at all. This module's `request` fixture isn't a replacement for that discipline; it's for tests that need both a real API call and a real page in the same run.

## The Pattern to Remember

- **Pattern:** use `request` for everything that isn't the point of the test (background data, other actors' state, verification of what actually persisted) and `page` for the one flow the test exists to check.
- **When to use:** repetitive setup (multiple records, other roles' data), and confirming a UI action actually persisted server-side without waiting on another page to render it back to you.
- **When NOT to use:** when the form, click, or page behavior itself is under test, that needs `page`, not `request`. When you're testing pure API correctness with no UI involved at all, that belongs in a dedicated API-testing course instead.
- **Mental model:** `request` calls are stagehands, setting props before the curtain rises. They can build the whole set in seconds. But if the test is about how the actors move, you still need the actors on stage. API calls can't stand in for the one scene you're actually reviewing.

## Common Mistakes

### Mistake 1: Calling the API Without Authenticating First

**Mistake:** Firing `request.post('http://localhost:5000/api/appointments', { data: { ... } })` straight away, with no `Authorization` header, the way you might for a public endpoint.

**Why it happens:** `request.get('/api-docs')` and a handful of read endpoints work fine unauthenticated, so it's easy to assume the rest of the API behaves the same way.

**Symptoms:** A `401` response that the test doesn't check for, so it sails past the failed `POST` and fails much later, on the UI assertion, with no obvious connection back to the real cause.

**Fix:** Log in via `request.post('/api/auth/login')` first, capture the `token`, and attach it as `Authorization: Bearer <token>` on every subsequent authenticated call. Do this explicitly per test or per role. There's no `storageState` shortcut here, because `APIRequestContext` doesn't share a browser's cookie jar.

### Mistake 2: Hitting the Frontend Port Instead of the Backend Port

**Mistake:** Writing `request.post('http://localhost:3002/api/appointments', ...)`, the frontend's port from `baseURL`, instead of `http://localhost:5000/api/appointments`, the backend's.

**Why it happens:** Every `page.goto()` call in this course resolves against `baseURL: 'http://localhost:3002'`, so `:3002` becomes the reflexive port to reach for. `request` has no `baseURL` unless you configure one. It needs the full URL, and that URL points at the backend, not the frontend.

**Symptoms:** A connection failure or a `404`, because `:3002` is serving the React app, not the Express API. There's no `/api/appointments` route there at all.

**Fix:** Always target `http://localhost:5000/api/...` for `request` calls in this course. If you want to avoid repeating the host, create the context explicitly with `request.newContext({ baseURL: 'http://localhost:5000' })` and use relative paths from there. Just don't confuse that base URL with the one `page` uses.

### Mistake 3: Not Checking `response.ok()` Before Trusting the Body

**Mistake:** Calling `response.json()` and reading fields off it immediately, without checking `response.ok()` or `response.status()` first.

**Why it happens:** A failed request still returns a JSON body, often `{ "error": "..." }`, so `response.json()` doesn't throw. The code looks like it worked.

**Symptoms:** The test proceeds to `page.goto('/dashboard')` expecting an appointment that was never created, and the resulting failure, a missing row on the dashboard, looks like a frontend rendering bug when the real problem was a `400` from the API three lines earlier.

**Fix:** Assert `expect(response.ok()).toBe(true)` (or check `response.status()` against the expected code) immediately after every `request` call, before doing anything with the body. Treat it the same as checking a login actually succeeded before proceeding, because that's exactly what it is.

### Mistake 4: Leftover API-Created Data Bleeding Between Tests

**Mistake:** Seeding appointments, patients, or records via `request` in a `beforeEach` with no corresponding cleanup, and no isolation between test files or parallel workers.

**Why it happens:** A single test run feels fine. The data you created is exactly what your assertions expect. The problem only shows up once the suite grows: another test's dashboard assertion now sees appointments a completely different spec created, or two parallel workers write conflicting appointment data to the same SQLite file at the same time.

**Symptoms:** Flaky, order-dependent failures: a test passes alone and fails in the full suite, or passes on one CI run and fails on the next with no code change.

**Fix:** This is a preview of the parallelism, sharding, and test isolation lesson covered later in this course; worker-scoped database resets or per-worker isolation are the real fix. Until you get there, keep API-seeded data scoped as narrowly as you can (unique, test-specific values instead of reused fixed IDs where the endpoint allows it) and don't assume a fresh database between runs unless you've actually reset it.

### Mistake 5: Using API Seeding to Skip Coverage You Still Need

**Mistake:** Replacing *every* appointment-related test with the hybrid pattern, including the ones that are supposed to verify the scheduling form itself, because API seeding is faster and the temptation is to use it everywhere.

**Why it happens:** Once the pattern from Step 5 of [Build It](./build-it) proves how much time it saves, it's tempting to apply it universally rather than selectively.

**Symptoms:** The scheduling form's validation, error states, and submit-button behavior quietly stop being tested by anything, because every test that used to drive the form now seeds around it, and a real regression in the form ships without a single red test.

**Fix:** Keep the "When NOT to Use This" boundary explicit in review: for any flow whose *form behavior* is part of the product's contract, at least one test still has to drive it through `page`, not around it through `request`.
