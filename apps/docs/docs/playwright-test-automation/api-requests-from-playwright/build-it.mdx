# API Requests from Playwright: Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Call the Backend Directly with the `request` Fixture

Every test function already receives `request` alongside `page`, you don't import or construct anything extra. Confirm it can reach the backend before building anything on top of it:

```typescript
import { test, expect } from '@playwright/test';

test('backend is reachable directly, no browser involved', async ({ request }) => {
  const response = await request.get('http://localhost:5000/api-docs');

  expect(response.ok()).toBe(true);
});
```

Run it, then compare it mentally to every test you've written so far: there's no `page.goto()`, nothing rendered, no locator anywhere. `request.get()` sent a real HTTP `GET` and got a real HTTP response back. That's the whole mechanism.

### Step 2: Authenticate the `APIRequestContext`

Most of the RBAC API requires a JWT, just like the frontend does, so you get one the same way the frontend does: a `POST` to the login endpoint.

A note on the credentials used from here on: `nurse1`/`nurse123` and `doctor2`/`doctor123` in this lesson's examples are placeholders standing in for the pattern, the same way the authentication lesson warned that doctor, nurse, and patient credentials come from your own `npm run seed` output, not from a fixed, documented value the way the admin account is. Swap in your fork's real seeded usernames and passwords before running these against your own database.

```typescript
test('a nurse can authenticate directly against the API', async ({ request }) => {
  const response = await request.post('http://localhost:5000/api/auth/login', {
    data: {
      username: 'nurse1',
      password: 'nurse123',
    },
  });

  expect(response.ok()).toBe(true);

  const body = await response.json();
  expect(body.token).toBeTruthy();
});
```

`response.json()` parses the JSON body the way you'd expect. The login endpoint returns a `token`, exactly what `/api-docs` documents for `POST /api/auth/login`. From here on, every authenticated call attaches that token as a bearer header:

```typescript
const createResponse = await request.post('http://localhost:5000/api/appointments', {
  headers: {
    Authorization: `Bearer ${token}`,
  },
  data: {
    /* ... */
  },
});
```

There's no `storageState` file involved here. That mechanism from the authentication lesson captures a *browser* context's cookies and `localStorage` for reuse by `page`. `request`'s `APIRequestContext` is a separate HTTP client with its own headers; you carry the token yourself, on each call, exactly like any other API client would.

### Step 3: Seed a Real Appointment via a Direct API Call

Per the RBAC role-permission matrix, scheduling an appointment is a nurse action. Authenticate as a nurse, then `POST` to create one:

```typescript
test('a nurse can create an appointment via the API', async ({ request }) => {
  const loginResponse = await request.post('http://localhost:5000/api/auth/login', {
    data: { username: 'nurse1', password: 'nurse123' },
  });
  const { token } = await loginResponse.json();

  const createResponse = await request.post('http://localhost:5000/api/appointments', {
    headers: { Authorization: `Bearer ${token}` },
    data: {
      patientId: 4,
      doctorId: 2,
      date: '2026-08-03',
      time: '10:30',
      reason: 'Follow-up consultation',
    },
  });

  expect(createResponse.ok()).toBe(true);

  const appointment = await createResponse.json();
  expect(appointment.id).toBeTruthy();
});
```

The `patientId` and `doctorId` values here come from your own seeded database. Open `/api-docs`, call `GET /api/users` (or check your `npm run seed` output) to find real IDs for a patient and a doctor before running this against your fork.

Checking `createResponse.ok()` before trusting anything in the body matters. See [Avoid Mistakes](./avoid-mistakes) for what happens when you skip it.

### Step 4: Verify the Appointment on the Doctor's Dashboard

Now it's time to bring `page` back into the picture. Because the permission matrix says a doctor only views their own appointments, you'll authenticate as the doctor whose `doctorId` you just used, navigate to their dashboard, and assert that the appointment renders:

```typescript
test('an API-created appointment appears on the doctor dashboard', async ({ page, request }) => {
  // 1. Seed via API, as a nurse
  const nurseLogin = await request.post('http://localhost:5000/api/auth/login', {
    data: { username: 'nurse1', password: 'nurse123' },
  });
  const { token } = await nurseLogin.json();

  const createResponse = await request.post('http://localhost:5000/api/appointments', {
    headers: { Authorization: `Bearer ${token}` },
    data: {
      patientId: 4,
      doctorId: 2,
      date: '2026-08-03',
      time: '10:30',
      reason: 'Follow-up consultation',
    },
  });
  expect(createResponse.ok()).toBe(true);

  // 2. Verify via UI, as the doctor
  await page.goto('/login');
  await page.getByLabel('Username').fill('doctor2');
  await page.getByLabel('Password').fill('doctor123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.goto('/dashboard');

  const appointmentRow = page.getByRole('row', { name: /10:30.*Follow-up consultation/ });
  await expect(appointmentRow).toBeVisible();
});
```

Everything before `// 2. Verify via UI` is a fast, precise HTTP call, no waiting on a form, no chance of a `selectOption` mismatch. Everything after it is a real UI assertion, auto-waiting exactly the way every other locator in this course does, against exactly the piece of behavior, "does the dashboard render an appointment that exists in the database," this test is actually about.

### Step 5: Speed Up Setup: Five Appointments, Two Ways

Now for the pattern this whole module has been building toward. Say a test needs five existing appointments in place before it can check anything, for example, that the doctor dashboard paginates correctly once there's a fifth one. Here are two ways to get there, so you can see the difference for yourself.

**Slow and brittle: five trips through the UI:**

```typescript
test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('nurse1');
  await page.getByLabel('Password').fill('nurse123');
  await page.getByRole('button', { name: 'Log In' }).click();

  const patientIds = [4, 5, 6, 7, 8];

  for (const patientId of patientIds) {
    await page.getByRole('link', { name: 'Schedule Appointment' }).click();
    await page.getByLabel('Patient').selectOption(String(patientId));
    await page.getByLabel('Doctor').selectOption('2');
    await page.getByLabel('Date').fill('2026-08-03');
    await page.getByLabel('Time').fill('10:30');
    await page.getByRole('button', { name: 'Confirm' }).click();
    await expect(page.getByText('Appointment scheduled')).toBeVisible();
  }
});
```

That's five full round trips through the form before the actual test even starts, and five separate places where a label rename, a slow toast, or a re-render can fail your setup for a reason that has nothing to do with pagination.

**Fast and focused: five API calls:**

```typescript
test.beforeEach(async ({ request }) => {
  const loginResponse = await request.post('http://localhost:5000/api/auth/login', {
    data: { username: 'nurse1', password: 'nurse123' },
  });
  const { token } = await loginResponse.json();

  const patientIds = [4, 5, 6, 7, 8];

  for (const patientId of patientIds) {
    const response = await request.post('http://localhost:5000/api/appointments', {
      headers: { Authorization: `Bearer ${token}` },
      data: {
        patientId,
        doctorId: 2,
        date: '2026-08-03',
        time: '10:30',
        reason: 'Routine check-up',
      },
    });
    expect(response.ok()).toBe(true);
  }
});

test('doctor dashboard paginates after five appointments', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('doctor2');
  await page.getByLabel('Password').fill('doctor123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.goto('/dashboard');

  await expect(page.getByRole('button', { name: 'Next page' })).toBeVisible();
});
```

You end up in the same state either way, five appointments sitting in the database before the test body runs, but this time it's built from five direct HTTP calls instead of five form submissions. That leaves the test free to verify exactly one thing: pagination. Nothing about how those five rows got created is part of what's being checked, so nothing about how they got created should be able to make the test fail.

## How It Works Internally

`request` and `page` are unrelated network paths. `page` drives a real browser, which makes its own requests as a side effect of rendering, a form submission, a `fetch()` the frontend code issues, all visible to `page.route()` from the network interception lesson if you choose to intercept them. `request`'s `APIRequestContext` skips the browser entirely: it's a standalone HTTP client, similar in spirit to `fetch` or `axios`, that Playwright happens to expose as a fixture so it shares your test's lifecycle and reporting.

That's also why authentication doesn't transfer between them automatically. A `page` context that logged in via the UI has a JWT sitting in `localStorage` or a cookie, scoped to that browser context. An `APIRequestContext` that logged in via `request.post('/api/auth/login')` has a token sitting in a JavaScript variable in your test file, which you attach to each subsequent call yourself via the `Authorization` header. They're two separate identities as far as the mechanics go, even when, as in Step 4, you deliberately authenticate as two different roles (nurse via API, doctor via UI) in the same test on purpose.
