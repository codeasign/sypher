# Cross-Browser and Responsive Testing — Review

⏱ 3 minutes

## Key Takeaways

- `projects` in `playwright.config.ts` is a general mechanism for running the same spec files under different environments — a previous lesson used it for role/`storageState`, and this module adds a second, independent axis on top: browser engine and device.
- The `chromium`, `firefox`, and `webkit` projects spread `devices['Desktop Chrome']`, `devices['Desktop Firefox']`, and `devices['Desktop Safari']` into `use` to select the engine, and `--project=<name>` lets you run just one at a time.
- `devices['iPhone 13']` configures a mobile viewport, user agent, `isMobile`, and `hasTouch` together in one project's `use` block — that's genuine device emulation, not just a resized window.
- `testMatch` scopes the cross-browser and responsive projects down to only visual and responsive spec files, which is why the RBAC permission-matrix and other functional specs keep running once, on the default engine, instead of getting multiplied by every new project.
- RBAC permission logic and API behavior don't change per browser, so they simply don't need multi-engine coverage; layout, CSS, visual snapshots (covered in the visual and snapshot testing lesson), and responsive breakpoints are exactly where that coverage actually earns its cost.

## Recap in 60 Seconds

If you only remember three things:

1. Add browser-engine and device projects as a *separate*, `testMatch`-scoped group — never by copying the role-based projects per engine.
2. `devices['iPhone 13']` (or any device entry) gives you viewport, user agent, and touch behavior all together; `page.setViewportSize()` alone gives you none of that.
3. Before giving a test cross-browser coverage, ask yourself "does this test's outcome actually depend on rendering?" If the answer is no, one engine is correct — not incomplete.

## Try It

Extend the responsive spec from [Build It](./build-it): add a `dashboard.responsive.spec.ts` case for the doctor role that checks the "Complete Appointment" action stays reachable (`toBeInViewport()`) on the `mobile-iphone-13` project, using `playwright/.auth/doctor.json` as that project's `storageState` instead of the patient's. Run it alongside the existing patient case with `npx playwright test --project=mobile-iphone-13` and confirm both pass without duplicating the menu-toggle test you already wrote.
