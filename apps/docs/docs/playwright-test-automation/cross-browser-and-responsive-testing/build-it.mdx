# Cross-Browser and Responsive Testing — Hands On

⏱ 22 minutes

## Breaking It Down

### Step 1: Add the Three Desktop Browser-Engine Projects

Open your `playwright.config.ts`. Leave the `admin`, `doctor`, `nurse`, and `patient` projects from the authentication lesson untouched, and add three new projects below them — `chromium`, `firefox`, and `webkit` — each spreading a desktop `devices` entry and each scoped with `testMatch` so it only picks up visual and responsive spec files:

```typescript title="playwright.config.ts"
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  // ...testDir, webServer, use, reporter from earlier modules

  projects: [
    // Role-based functional projects (from auth setup) — unchanged.
    { name: 'admin', use: { storageState: 'playwright/.auth/admin.json' } },
    { name: 'doctor', use: { storageState: 'playwright/.auth/doctor.json' } },
    { name: 'nurse', use: { storageState: 'playwright/.auth/nurse.json' } },
    { name: 'patient', use: { storageState: 'playwright/.auth/patient.json' } },

    // Cross-browser projects — visual and responsive specs only.
    {
      name: 'chromium',
      testMatch: /.*\.(visual|responsive)\.spec\.ts/,
      use: {
        ...devices['Desktop Chrome'],
        storageState: 'playwright/.auth/patient.json',
      },
    },
    {
      name: 'firefox',
      testMatch: /.*\.(visual|responsive)\.spec\.ts/,
      use: {
        ...devices['Desktop Firefox'],
        storageState: 'playwright/.auth/patient.json',
      },
    },
    {
      name: 'webkit',
      testMatch: /.*\.(visual|responsive)\.spec\.ts/,
      use: {
        ...devices['Desktop Safari'],
        storageState: 'playwright/.auth/patient.json',
      },
    },
  ],
});
```

Two details are worth pausing on here. First, `testMatch: /.*\.(visual|responsive)\.spec\.ts/` means these three projects only ever pick up spec files named like `dashboard.visual.spec.ts` or `dashboard.responsive.spec.ts` — your RBAC permission-matrix specs and every other functional spec file don't match that pattern, so they never run under `chromium`, `firefox`, or `webkit`, only under the four role-based projects, once, exactly as before. Second, each project reuses `playwright/.auth/patient.json` from the authentication lesson's `storageState` files, because layout and rendering don't depend on which role is logged in — one authenticated session is enough to reach the dashboards you're checking, so there's no need to run these projects under all four roles.

### Step 2: Run One Engine at a Time

Confirm all three engines are installed — setup's `npm init playwright@latest` installed them, but it's worth checking directly:

```bash
npx playwright install
```

Now run each project individually with `--project`:

```bash
npx playwright test --project=chromium
npx playwright test --project=firefox
npx playwright test --project=webkit
```

Each command runs only that project's matched spec files, and only in that one engine. Since you haven't written any `.visual.spec.ts` or `.responsive.spec.ts` files yet, don't be surprised when all three currently report zero tests found — that's expected, and it's actually a good sign, since it confirms `testMatch` is scoping correctly before you add any real specs.

### Step 3: Add the Mobile Viewport Project

Add a fourth project using `devices['iPhone 13']`. Unlike the desktop projects, scope this one to responsive specs only — visual snapshot baselines are a separate concern per browser engine (covered in the visual and snapshot testing lesson), not per device:

```typescript title="playwright.config.ts"
{
  name: 'mobile-iphone-13',
  testMatch: /.*\.responsive\.spec\.ts/,
  use: {
    ...devices['iPhone 13'],
    storageState: 'playwright/.auth/patient.json',
  },
},
```

`devices['iPhone 13']` sets `viewport: { width: 390, height: 844 }`, a mobile `userAgent` string, `isMobile: true`, `hasTouch: true`, and `deviceScaleFactor: 3` — all at once, from a single spread. That's exactly what lets the frontend's mobile-specific rendering path (a media query keyed to viewport width, a touch-triggered menu) actually activate, the same way it would for someone genuinely holding a phone.

### Step 4: Write a Responsive Spec for the Patient Dashboard

Create `tests/dashboard.responsive.spec.ts`. This spec runs under `chromium`, `firefox`, `webkit`, and `mobile-iphone-13` — check that the patient dashboard's key content and primary action stay reachable at every size, not just that the page loads:

```typescript title="tests/dashboard.responsive.spec.ts"
import { test, expect } from '@playwright/test';

test.describe('patient dashboard — responsive', () => {
  test('key heading and primary action stay visible and reachable', async ({ page }) => {
    await page.goto('/dashboard');

    await expect(page.getByRole('heading', { name: 'My Appointments' })).toBeVisible();

    const viewRecordsLink = page.getByRole('link', { name: 'View Medical Records' });
    await expect(viewRecordsLink).toBeVisible();
    await expect(viewRecordsLink).toBeInViewport();
  });

  test('mobile menu toggle is reachable on a small viewport', async ({ page, isMobile }) => {
    test.skip(!isMobile, 'menu toggle only renders below the responsive breakpoint');

    await page.goto('/dashboard');

    const menuToggle = page.getByRole('button', { name: 'Menu' });
    await expect(menuToggle).toBeVisible();

    await menuToggle.click();
    await expect(page.getByRole('link', { name: 'View Medical Records' })).toBeVisible();
  });
});
```

`toBeInViewport()` is a web-first assertion that confirms an element actually intersects the visible viewport, not just that it exists somewhere on a page that might require scrolling to reach — a more honest check of "usable" than `toBeVisible()` alone on a cramped mobile layout. The second test uses the built-in `isMobile` fixture value, which Playwright derives from the project's `devices` entry, to skip the mobile-only menu check on the three desktop projects instead of duplicating the spec file per device.

### Step 5: Run the Full Cross-Browser and Responsive Set

```bash
npx playwright test --project=chromium --project=firefox --project=webkit --project=mobile-iphone-13
```

Open the HTML report:

```bash
npx playwright show-report
```

Each project appears as its own row per test, so a failure that only shows up under `webkit` — a WebKit-specific flexbox quirk, say — is immediately distinguishable from one that fails everywhere. That per-engine breakdown is the entire point of running more than one project: a failure isolated to one row tells you exactly where the bug lives before you've read a single line of the trace.

## How It Works Internally

Worth understanding what's actually happening under the hood: `testMatch` on a project is evaluated independently, per project, against every spec file Playwright discovers under `testDir`. A file can match zero, one, or several projects depending on how many `testMatch` patterns it satisfies — there's no rule that says a spec file has to belong to exactly one project. That's why `dashboard.responsive.spec.ts` correctly runs under all four cross-browser projects (the three desktop engines match `.(visual|responsive).spec.ts`, and the mobile project matches `.responsive.spec.ts` specifically), while never running under `admin`, `doctor`, `nurse`, or `patient` at all. Those four projects have no `testMatch` restricting them, so they default to matching everything under `testDir` — which is exactly why they still run your RBAC permission-matrix specs just as they always did.

`--project` filters which of the configured projects Playwright even considers for a given run; it doesn't change `testMatch` itself. Passing it more than once, as in Step 5, runs the union of the named projects' matched specs, each project still isolated in its own worker processes with its own browser instance.
