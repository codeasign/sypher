# Cross-Browser and Responsive Testing: Common Mistakes

⏱ 8 minutes

## When NOT to Use This

Cross-browser projects exist for tests whose outcome actually depends on rendering: layout, CSS, viewport-driven behavior. They're not a general-purpose way to "be thorough," so don't reach for them just because more coverage feels safer. The RBAC permission-matrix specs, the hybrid API-seeded flows from the API-requests-from-Playwright lesson, and anything that asserts against the Express backend's response rather than pixels on screen all belong on the role-based `admin`/`doctor`/`nurse`/`patient` projects only, running once on the default Chromium engine. Running those same specs under `firefox` and `webkit` too doesn't buy you anything, because the RBAC permission logic lives entirely on the backend: no browser engine can make an Express route return a different status code. Save the extra engines for the tests that can actually disagree across them.

## The Pattern to Remember

- **Pattern:** keep functional and RBAC specs on the role-based projects, unscoped, so they keep running once on the default engine. Give layout-sensitive specs (visual snapshots, responsive breakpoints) their own `chromium`/`firefox`/`webkit`/mobile projects, scoped with `testMatch` so they never end up re-running the functional suite too.
- **When to use:** visual regression baselines (covered in the visual and snapshot testing lesson), responsive breakpoint checks, and anything where a CSS or rendering difference between engines is the exact thing you're trying to catch.
- **When NOT to use:** permission-matrix logic, API-integration checks, or any spec whose assertion is really about the backend's response, since a browser engine can't change that answer no matter which one you pick.
- **Mental model:** think of three browser engines as three painters working from the same instructions, the DOM and CSS. Testing all three only matters when you care whether the painting looks right, not whether the instructions were followed correctly.

## Common Mistakes

### Mistake 1: Multiplying Role Projects by Browser Engines

**Mistake:** Copying each of the `admin`, `doctor`, `nurse`, and `patient` projects three times, once per engine, instead of keeping them separate from the cross-browser projects.

**Why it happens:** "More coverage" feels safe by default, and copy-pasting an existing project block is simply the path of least resistance when you want a new engine added.

**Symptoms:** CI time roughly triples, because every permission-matrix and functional spec now runs twelve times instead of four, and none of those extra nine runs ever produce a different result than the original four did, since RBAC logic doesn't change per rendering engine.

**Fix:** Keep the role-based projects exactly as the authentication lesson built them, with no `devices` override. Add cross-browser projects separately, scoped with `testMatch` to only the visual and responsive spec files, as in [Build It](./build-it).

### Mistake 2: Assuming All Three Engines Are Installed

**Mistake:** Running `npx playwright test --project=webkit` for the first time and assuming it'll just work because Chromium always has.

**Why it happens:** Setup's `npm init playwright@latest` installs all three engines by default, but if you answered "No" to the browser-install prompt back then, or you're on a fresh machine that's only ever run the Chromium-only role projects, you may never have actually triggered a WebKit or Firefox install.

**Symptoms:** The run fails immediately with an error naming a missing executable, something like `browserType.launch: Executable doesn't exist at ...`, that looks like a configuration bug but is actually a missing install step.

**Fix:** Run `npx playwright install` before your first cross-browser run. It's safe to run repeatedly; it skips engines that are already present.

### Mistake 3: Treating `devices['iPhone 13']` as Just a Smaller Viewport

**Mistake:** Reaching for `page.setViewportSize({ width: 390, height: 844 })` instead of `devices['iPhone 13']`, on the assumption that a resized window is equivalent to mobile emulation.

**Why it happens:** The visible result, a narrower page, looks the same either way, so the difference isn't obvious just from glancing at a screenshot.

**Symptoms:** UI paths that only activate for `isMobile: true` or `hasTouch: true` (a touch-triggered menu, a mobile-specific user-agent check on the frontend) never actually get exercised. That means a spec can pass locally while the real mobile behavior it was supposed to verify was never actually reached.

**Fix:** Spread the full `devices['iPhone 13']` entry into the project's `use` block, as in [Build It](./build-it). It configures viewport, user agent, `isMobile`, `hasTouch`, and device scale factor together, the combination that actually matches a real device, not just its screen size.

### Mistake 4: Forgetting `testMatch`, Rerunning the Whole Suite Per Engine

**Mistake:** Adding the `chromium`, `firefox`, `webkit`, and `mobile-iphone-13` projects without a `testMatch` restriction, so they default to matching every spec file under `testDir`.

**Why it happens:** `testMatch` is easy to skip when you're focused on just getting the new engine working, and the omission doesn't throw an error to warn you. It just quietly produces a much bigger test run.

**Symptoms:** The RBAC permission-matrix specs and every other functional spec now run under all four new projects too, on top of the four role-based ones: eight total runs of specs that only ever needed to run once, and some of them may fail outright because they were never written with mobile viewports or `storageState`-less contexts in mind.

**Fix:** Every cross-browser and responsive project needs an explicit `testMatch` scoping it to visual and responsive spec files only, exactly as shown in [Build It](./build-it).

### Mistake 5: Comparing Visual Baselines Across Engines and Platforms Without Regenerating Them

**Mistake:** Capturing `toHaveScreenshot()` baselines locally on one engine and OS, then running the full `chromium`/`firefox`/`webkit` project set in CI and expecting them all to match the same baseline files.

**Why it happens:** The baseline images look perfectly correct at the moment you generate them, and on the surface, adding new projects doesn't seem related to snapshot testing at all.

**Symptoms:** CI fails on `firefox` and `webkit` (and often even `chromium` if CI runs a different OS than your machine) with pixel-diff errors, even though nothing about the actual page changed. Font rendering and anti-aliasing differ enough between engines and operating systems that a baseline captured on one is never a valid comparison target for another.

**Fix:** As the visual and snapshot testing lesson covers, `toHaveScreenshot()` names baseline files per project and per platform automatically. Let it. Generate baselines by running `--update-snapshots` once per project in the same environment (ideally CI itself) that will later verify them, rather than hand-copying one engine's baseline to cover all three.
