# Cross-Browser and Responsive Testing

⏱ 18 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Extend the `projects` array in `playwright.config.ts` (from the project structure and config lesson) with Chromium, Firefox, and WebKit engine projects, and run each one on its own with `--project`
- Add a mobile-viewport project using `devices['iPhone 13']` in that project's `use` block, and see what device emulation actually gives you beyond a resized window
- Write a responsive spec that checks the RBAC app's patient dashboard stays genuinely usable — not just present — on a small viewport
- Reconcile the browser-engine axis you're adding here with the role-based `admin`/`doctor`/`nurse`/`patient` projects from the authentication lesson, without multiplying every project by three
- Walk away with a concrete, opinionated rule for which categories of RBAC tests actually need multi-browser coverage, and which don't

## Why This Matters

Every test you've written so far in this course has run against exactly one browser engine: Chromium, either because it's the only project you defined during setup, or because the role-based projects from the authentication lesson never specified a different one. That's been fine — better than fine, deliberate — because none of what you've been testing (RBAC permission logic, API responses, authentication) has any reason to differ by rendering engine.

Layout, though, does. A CSS flexbox bug, a responsive breakpoint that collapses navigation into a hamburger menu below a certain width, a WebKit-specific rendering quirk in a date picker — none of that shows up in Chromium alone, and none of it shows up in an API test at all. The moment your suite includes visual snapshots (covered in the visual and snapshot testing lesson) or a claim like "the patient dashboard is usable on a phone," you need more than one engine and more than one viewport in the loop, or you're not actually testing the claim you're making.

There's a trap on the other side too, and it's just as real. If you add Firefox and WebKit projects naively — by copying every existing project and just changing the engine — you triple your CI time for tests that were never going to produce a different result across engines in the first place. This lesson is about drawing that line correctly: which tests earn multi-browser coverage, and which ones would only be spending CI minutes to confirm something you already know.

## The Problem

You have four role-based projects from the authentication lesson, each pinned to a `storageState` file:

```typescript title="playwright.config.ts (from the authentication lesson)"
projects: [
  { name: 'admin', use: { storageState: 'playwright/.auth/admin.json' } },
  { name: 'doctor', use: { storageState: 'playwright/.auth/doctor.json' } },
  { name: 'nurse', use: { storageState: 'playwright/.auth/nurse.json' } },
  { name: 'patient', use: { storageState: 'playwright/.auth/patient.json' } },
],
```

None of these specify a browser, so all four run on Chromium — the default engine when a project's `use` block doesn't spread a `devices[...]` entry. Now say you want Firefox and WebKit coverage too. The naive move is to copy each role project three times, once per engine:

```typescript title="Don't do this"
projects: [
  { name: 'admin-chromium', use: { ...chromiumAdmin } },
  { name: 'admin-firefox', use: { ...firefoxAdmin } },
  { name: 'admin-webkit', use: { ...webkitAdmin } },
  { name: 'doctor-chromium', use: { ...chromiumDoctor } },
  // ...and eight more, for nurse and patient
],
```

That's twelve projects in total, and every permission-matrix spec from the RBAC permission-matrix lesson — tests that assert `expect(locator)` against an Express API response, not against pixels — now runs three times over, in three browsers that can never disagree about whether a JWT grants access to `/api/appointments`. You've tripled your CI bill and caught zero additional bugs, because the thing those tests check doesn't live in the rendering engine at all.

## The Concept

`projects` in `playwright.config.ts` is a general mechanism — a list of independent environments the same test files can run under, each with its own `use` overrides. A previous lesson used that mechanism for one axis: which role is authenticated. This lesson adds a second, independent axis: which browser engine (and, for mobile, which device) renders the page. The mistake in the problem above wasn't adding that second axis — it was crossing the two axes for every single test, instead of stopping to ask which tests actually depend on which axis in the first place.

The fix is simply to keep the two project groups separate, and scope each one to the tests that actually need it:

1. **Role-based projects** (`admin`, `doctor`, `nurse`, `patient`) stay exactly as the authentication lesson built them, with no browser override, so they keep running on Chromium by default. Permission-matrix and functional specs belong here, since their outcome is decided by the Express backend, not by whichever engine happened to render the response.
2. **Cross-browser and responsive projects** (`chromium`, `firefox`, `webkit`, and a mobile project) are new, and each one uses `testMatch` to pick up *only* the visual and responsive spec files — not the whole suite. That's why a file named `dashboard.responsive.spec.ts` runs under all four of these projects, while `permission-matrix.spec.ts` never does: it simply doesn't match the pattern.

Three of those new projects spread a desktop `devices` entry — `devices['Desktop Chrome']`, `devices['Desktop Firefox']`, `devices['Desktop Safari']` — into `use`, which is what actually switches the underlying engine (Safari's entry maps to WebKit, since that's the engine real Safari uses). The fourth spreads `devices['iPhone 13']`, which configures far more than a smaller window: a mobile viewport (390×844), a mobile user agent string, `isMobile: true`, and `hasTouch: true` together. That combination is what lets touch-triggered UI — a hamburger menu that only appears for mobile-flagged sessions — actually render the way a real phone would trigger it. `page.setViewportSize()` alone would shrink the window and miss all of that.

`--project` is how you run one of these at a time: `npx playwright test --project=firefox` runs only the specs matched to the `firefox` project; omit the flag and Playwright runs every project whose `testMatch` matches at least one file.
