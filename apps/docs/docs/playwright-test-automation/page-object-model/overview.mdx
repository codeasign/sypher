# Page Object Model for a Role-Based App

⏱ 18 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Explain what the Page Object Model (POM) buys you over inline locators scattered across spec files
- Design a `BasePage` class that holds navigation and logout — behavior every authenticated role shares
- Build a per-role dashboard page object (`DoctorDashboardPage`) that encapsulates that role's specific locators and actions
- Extract shared UI — a modal, a toast notification — into component objects composed into page objects instead of duplicated inside each one
- Recognize the point where one-page-object-per-role stops scaling, ahead of this course's permission-matrix testing later on

## Why This Matters

There are four roles here, and four dashboards to go with them, and each one renders different navigation, different tables, and different action buttons — a doctor sees "Complete Appointment," a nurse sees "Schedule Appointment," an admin sees a user-management table nobody else can even reach. If every spec file reaches into the page directly with its own `page.getByRole('button', { name: 'Complete Appointment' })`, that locator gets copy-pasted into every doctor spec you write. The day the app's copy changes from "Complete Appointment" to "Mark as Completed," you are not fixing one line — you are grepping across a dozen spec files hoping you found all of them.

The Page Object Model exists to make that a one-line fix. A page object is a class that owns the locators and actions for one screen (or one role's screen), so specs describe *what* a test does in domain language — `await doctorDashboard.completeAppointment('Jane Doe')` — while the page object alone knows *how*, in terms of actual DOM structure. Locator changes become a one-file edit, and test intent becomes readable without anyone needing to know the app's markup.

## The Problem

Picture two spec files, written independently, both testing doctor behavior:

```typescript title="tests/doctor-appointments.spec.ts"
test('doctor completes an appointment', async ({ page }) => {
  await page.goto('/dashboard');
  await page
    .getByRole('row', { name: 'Jane Doe' })
    .getByRole('button', { name: 'Complete' })
    .click();
  await expect(page.getByText('Appointment completed')).toBeVisible();
});
```

```typescript title="tests/doctor-medical-records.spec.ts"
test('doctor logs out from the dashboard', async ({ page }) => {
  await page.goto('/dashboard');
  await page.getByRole('button', { name: 'Logout' }).click();
  await expect(page.getByRole('heading', { name: 'Login' })).toBeVisible();
});
```

Both files know the doctor dashboard's DOM, which means both will break, separately, the moment a locator changes — and there's no single place to look to understand "everything a doctor can do on their dashboard." Multiply this by four roles and dozens of specs, and the specs stop being a readable description of behavior; they become a distributed, duplicated map of the app's markup.

## The Concept

A page object is a class that wraps one screen: it exposes methods named after user intent (`completeAppointment`, `logout`) while hiding the locators that intent actually requires underneath. For a role-based app like this one, three layers of page objects work together:

1. **`BasePage`** — an abstract class every dashboard page object extends. It owns what every authenticated screen shares: the top nav, the logout button, the page's readiness check. No role-specific locator lives here.
2. **Per-role dashboard page objects** — `DoctorDashboardPage`, `NurseDashboardPage`, `PatientDashboardPage`, `AdminDashboardPage`, each extending `BasePage` and adding only that role's own locators and actions. A doctor's `completeAppointment()` has no reason to exist on `PatientDashboardPage`, because a patient can't do that — the type system enforces it just by which class you instantiate.
3. **Component objects** — classes for UI fragments reused *inside* multiple page objects, not tied to any one role: a `Modal` that every "confirm delete" or "add patient" dialog uses, a `Notification` toast that appears after almost every action. These are composed as properties on a page object (`this.modal = new Modal(page)`) rather than having their locators re-declared in every page object that needs them.

Notice what's absent from the diagram: no arrow from a spec file straight into a locator. Every path to the DOM goes through a page object or a component object it owns. That's the whole discipline POM asks for — and it's also exactly where it starts to strain. Testing "can a nurse do what a doctor can do" across every role and every action means either writing near-identical page objects four times over, or reaching for something more parameterized. A later lesson covers that; for now, one class per role is the right tool for role-specific flows, which is most of what you'll write.
