# Page Object Model for a Role-Based App — Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Build `BasePage`

Create `tests/pages/BasePage.ts`. It holds only what every authenticated dashboard shares — the top-level heading every dashboard renders, and the logout button — and declares an abstract `isReady()` that every subclass must implement with its own proof-of-load check.

```typescript title="tests/pages/BasePage.ts"
import { Page, Locator, expect } from '@playwright/test';

export abstract class BasePage {
  readonly page: Page;
  protected readonly logoutButton: Locator;
  protected readonly navHeading: Locator;

  constructor(page: Page) {
    this.page = page;
    this.logoutButton = page.getByRole('button', { name: 'Logout' });
    this.navHeading = page.getByRole('heading', { level: 1 });
  }

  /**
   * Each dashboard subclass proves its own screen loaded — a doctor sees
   * "Doctor Dashboard," a nurse sees "Nurse Dashboard," and so on. BasePage
   * cannot know which, so it requires the subclass to say.
   */
  abstract isReady(): Promise<void>;

  async gotoDashboard(): Promise<void> {
    await this.page.goto('/dashboard');
    await this.isReady();
  }

  async logout(): Promise<void> {
    await this.logoutButton.click();
    await expect(
      this.page.getByRole('heading', { name: 'Login' })
    ).toBeVisible();
  }
}
```

`BasePage` never declares a role-specific locator. If you find yourself adding `addPatientButton` here, stop — that belongs on `NurseDashboardPage` or `DoctorDashboardPage`, not on the class every role extends.

### Step 2: Build the Component Objects

Two pieces of UI recur across almost every dashboard action: a confirmation/entry modal, and a toast notification that reports the result. Build each as its own class in `tests/components/`, scoped to its own root locator so a page object composes it instead of re-declaring its internals.

```typescript title="tests/components/Modal.ts"
import { Page, Locator, expect } from '@playwright/test';

export class Modal {
  private readonly dialog: Locator;
  private readonly confirmButton: Locator;
  private readonly cancelButton: Locator;

  constructor(page: Page) {
    this.dialog = page.getByRole('dialog');
    this.confirmButton = this.dialog.getByRole('button', { name: 'Confirm' });
    this.cancelButton = this.dialog.getByRole('button', { name: 'Cancel' });
  }

  async waitUntilOpen(): Promise<void> {
    await expect(this.dialog).toBeVisible();
  }

  async fillField(label: string, value: string): Promise<void> {
    await this.dialog.getByLabel(label).fill(value);
  }

  async confirm(): Promise<void> {
    await this.confirmButton.click();
    await expect(this.dialog).toBeHidden();
  }

  async cancel(): Promise<void> {
    await this.cancelButton.click();
    await expect(this.dialog).toBeHidden();
  }
}
```

```typescript title="tests/components/Notification.ts"
import { Page, Locator, expect } from '@playwright/test';

export class Notification {
  private readonly toast: Locator;

  constructor(page: Page) {
    this.toast = page.getByRole('alert');
  }

  async expectMessage(text: string): Promise<void> {
    await expect(this.toast).toBeVisible();
    await expect(this.toast).toHaveText(text);
  }
}
```

Both classes take only a `Page` in their constructor and scope every internal locator off their own root (`this.dialog`, `this.toast`) rather than the bare `page`. That's what makes them safe to compose: `this.dialog.getByRole('button', { name: 'Confirm' })` only ever matches a Confirm button *inside the currently open dialog*, even if some other part of the screen also has a button with that name.

### Step 3: Build `DoctorDashboardPage`

This is where role-specific behavior lives. `DoctorDashboardPage` extends `BasePage`, composes `Modal` and `Notification` as properties instead of duplicating their locators, and exposes methods named after what a doctor actually does — completing an appointment, cancelling one, adding a medical record.

```typescript title="tests/pages/DoctorDashboardPage.ts"
import { Page, Locator, expect } from '@playwright/test';
import { BasePage } from './BasePage';
import { Modal } from '../components/Modal';
import { Notification } from '../components/Notification';

export class DoctorDashboardPage extends BasePage {
  readonly modal: Modal;
  readonly notification: Notification;

  constructor(page: Page) {
    super(page);
    this.modal = new Modal(page);
    this.notification = new Notification(page);
  }

  async isReady(): Promise<void> {
    await expect(this.navHeading).toHaveText('Doctor Dashboard');
  }

  private appointmentRow(patientName: string): Locator {
    return this.page.getByRole('row', { name: new RegExp(patientName) });
  }

  async completeAppointment(patientName: string): Promise<void> {
    await this.appointmentRow(patientName)
      .getByRole('button', { name: 'Complete' })
      .click();
    await this.notification.expectMessage('Appointment marked as completed');
  }

  async cancelAppointment(patientName: string): Promise<void> {
    await this.appointmentRow(patientName)
      .getByRole('button', { name: 'Cancel' })
      .click();
    await this.notification.expectMessage('Appointment cancelled');
  }

  async addMedicalRecord(
    patientName: string,
    diagnosis: string,
    notes: string
  ): Promise<void> {
    await this.appointmentRow(patientName)
      .getByRole('button', { name: 'Add Medical Record' })
      .click();
    await this.modal.waitUntilOpen();
    await this.modal.fillField('Diagnosis', diagnosis);
    await this.modal.fillField('Notes', notes);
    await this.modal.confirm();
    await this.notification.expectMessage('Medical record added');
  }

  async expectAppointmentVisible(patientName: string): Promise<void> {
    await expect(this.appointmentRow(patientName)).toBeVisible();
  }
}
```

Every locator that touches the DOM lives inside this class or one it composes, which is why nothing in a spec file will ever need to call `page.getByRole(...)` directly against the doctor dashboard again.

### Step 4: Write a Spec Against It

With the role-based `storageState` from the authentication lesson already in place, a spec starts out already authenticated as a doctor, so there's no login flow to write inside the test body.

```typescript title="tests/doctor-dashboard.spec.ts"
import { test, expect } from '@playwright/test';
import { DoctorDashboardPage } from './pages/DoctorDashboardPage';

test.use({ storageState: 'storage/doctor.json' });

test.describe('Doctor dashboard', () => {
  test('completes an appointment and adds a medical record', async ({ page }) => {
    const doctorDashboard = new DoctorDashboardPage(page);
    await doctorDashboard.gotoDashboard();

    await doctorDashboard.completeAppointment('Jane Doe');
    await doctorDashboard.addMedicalRecord(
      'Jane Doe',
      'Seasonal allergies',
      'Prescribed antihistamine, follow up in two weeks'
    );

    await doctorDashboard.expectAppointmentVisible('Jane Doe');
  });

  test('logs out from the dashboard', async ({ page }) => {
    const doctorDashboard = new DoctorDashboardPage(page);
    await doctorDashboard.gotoDashboard();

    await doctorDashboard.logout();
  });
});
```

Read that spec back: it says what a doctor does, in domain terms, with no mention of dialogs, rows, or button roles. That readability is the entire payoff of the three steps before it.

### Step 5: The Other Three Roles Follow the Same Shape

`NurseDashboardPage`, `PatientDashboardPage`, and `AdminDashboardPage` each extend `BasePage` and compose `Modal`/`Notification` the same way `DoctorDashboardPage` does — only the role-specific methods differ, because only the role-specific *permissions* differ.

```typescript title="tests/pages/NurseDashboardPage.ts"
export class NurseDashboardPage extends BasePage {
  // ...same constructor shape as DoctorDashboardPage: composes Modal, Notification

  async isReady(): Promise<void> {
    await expect(this.navHeading).toHaveText('Nurse Dashboard');
  }

  async scheduleAppointment(patientName: string, date: string): Promise<void> {
    await this.page.getByRole('button', { name: 'Schedule Appointment' }).click();
    await this.modal.waitUntilOpen();
    await this.modal.fillField('Patient', patientName);
    await this.modal.fillField('Date', date);
    await this.modal.confirm();
    await this.notification.expectMessage('Appointment scheduled');
  }

  async cancelAppointment(patientName: string): Promise<void> {
    // same pattern as DoctorDashboardPage.cancelAppointment
  }
}
```

```typescript title="tests/pages/AdminDashboardPage.ts"
export class AdminDashboardPage extends BasePage {
  async isReady(): Promise<void> {
    await expect(this.navHeading).toHaveText('Admin Dashboard');
  }

  async deleteUser(username: string): Promise<void> {
    await this.page
      .getByRole('row', { name: new RegExp(username) })
      .getByRole('button', { name: 'Delete' })
      .click();
    await this.modal.confirm();
    await this.notification.expectMessage('User deleted');
  }
}
```

Notice the duplication that's already visible even across two roles: `cancelAppointment` on `DoctorDashboardPage` and the one you'd write on `NurseDashboardPage` do nearly the same thing against nearly the same row. That's a small, tolerable amount of repetition for two roles. Section 9 in the review lesson flags exactly where that stops being tolerable — testing every action against every role turns this pattern combinatorial.

## How It Works Internally

Three design choices make this hierarchy hold up as the app grows:

- **Inheritance for "is-a," composition for "has-a."** `DoctorDashboardPage extends BasePage` because a doctor dashboard *is* an authenticated dashboard with nav and logout. `DoctorDashboardPage` composes `Modal` as `this.modal = new Modal(page)` because a doctor dashboard *has* a modal, not *is* one — a nurse dashboard has one too, and neither should inherit from `Modal` to get it.
- **Locators are computed once, in the constructor, off `page` or off another locator.** `this.logoutButton = page.getByRole(...)` in `BasePage`'s constructor doesn't query the DOM immediately — Playwright locators are lazy descriptions, resolved only when an action or assertion runs against them. That's why constructing a page object is cheap and safe to do even before `page.goto()` has run.
- **Component objects scope every internal locator to their own root.** `Modal`'s `confirmButton` is `this.dialog.getByRole('button', { name: 'Confirm' })`, not `page.getByRole('button', { name: 'Confirm' })`. If the same dashboard has a "Confirm" button somewhere outside the dialog too, the unscoped version would be ambiguous; the scoped version can't be, because it only ever looks inside the currently-open dialog.
