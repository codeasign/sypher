# Page Object Model for a Role-Based App: Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Page objects earn their cost when a screen or a flow is exercised by more than a couple of specs. For a genuinely one-off check, a quick exploratory poke at the app in UI mode or `codegen` while you're figuring out whether a feature even works yet, writing a whole class first is wasted motion. Reach for a page object once you're about to write the *second* spec that touches the same screen, not before.

The bigger place this pattern stops fitting is permission-matrix testing. `DoctorDashboardPage`, `NurseDashboardPage`, `PatientDashboardPage`, and `AdminDashboardPage` are the right shape for testing what one role does on its own dashboard. They are the wrong shape for testing "can role X perform action Y" across every role and every action in the RBAC matrix. That's role times resource times action, and a page object per role doesn't give you a clean way to ask "does this role even see this button" as a parameter. A later lesson covers the role-parameterized alternative that handles the full matrix without four (or more) near-duplicate classes. Don't try to force today's POM structure to cover that ahead of time; recognize the boundary and keep going.

## The Pattern to Remember

- **Pattern:** `BasePage` owns what every authenticated screen shares; each role's dashboard extends it and owns only that role's locators and actions; shared UI fragments are component objects composed in, not copy-pasted.
- **When to use:** any screen or flow more than one spec touches, which, in this course, is nearly everything from here on.
- **When NOT to use:** true one-off exploratory checks, and full permission-matrix testing across every role and action (a role-parameterized pattern covered later in this course instead).
- **Mental model:** a page object is a translator standing between your test's plain-English intent and the DOM's actual structure. The test speaks intent, the page object speaks markup, and they should never swap places.

## Common Mistakes

### Mistake 1: Letting Role-Specific Locators Leak into `BasePage`

**Mistake:** Adding a doctor-only locator like `completeAppointmentButton` directly onto `BasePage` because "it was convenient to have it in one place."

**Why it happens:** `BasePage` is already imported everywhere, so adding one more locator there feels faster than creating or extending a role-specific class.

**Symptoms:** `PatientDashboardPage` and `AdminDashboardPage` now inherit a `completeAppointmentButton` locator that will never resolve on their screens, because patients and admins can't complete appointments. Nothing catches this at compile time. The mistake only shows up when a stray call to it times out in a patient test, and whoever's debugging has to work out why a doctor-only button is even reachable from `PatientDashboardPage` at all.

**Fix:** Keep `BasePage` to what every role's dashboard genuinely shares: nav, logout, the shared readiness check. The moment a locator or method only makes sense for one role, it belongs on that role's own subclass, even if that means the same-looking method name appears on two subclasses with two different implementations.

### Mistake 2: Duplicating Modal and Notification Locators Instead of Composing Them

**Mistake:** Writing `this.dialog = page.getByRole('dialog')` and `this.toast = page.getByRole('alert')` again inside `NurseDashboardPage`, instead of composing the same `Modal` and `Notification` classes `DoctorDashboardPage` already uses.

**Why it happens:** Copying a locator from a class you already have open feels quicker than importing and instantiating a separate component class, especially under deadline pressure on the second or third page object.

**Symptoms:** The app's confirmation dialog changes, a "Confirm" button becomes "Save," and you fix it in `Modal.ts`, then watch nurse and admin specs keep failing because those page objects have their own, now-stale, copy of the same locator.

**Fix:** Build `Modal` and `Notification` once, in `tests/components/`, and compose them into every page object that needs them (`this.modal = new Modal(page)`). One fix location for shared UI is the entire reason component objects exist.

### Mistake 3: Scoping a Component's Locators to the Whole Page Instead of Its Own Root

**Mistake:** Writing `Modal`'s `confirmButton` as `page.getByRole('button', { name: 'Confirm' })` instead of `this.dialog.getByRole('button', { name: 'Confirm' })`.

**Why it happens:** It works the first time you test it, because at that moment there's only one "Confirm" button anywhere on the screen.

**Symptoms:** Weeks later, a different part of the same dashboard adds its own unrelated "Confirm" button, a bulk-action bar, say, and `Modal.confirm()` starts throwing a strict-mode violation for matching two elements, or worse, silently clicks the wrong one if strict mode isn't catching it.

**Fix:** Every component object should scope its internal locators off its own root locator (`this.dialog`, `this.toast`), never off the bare `page`. That's what makes a component object safe to reuse across dashboards that might each have their own unrelated instance of a similarly-named element.

### Mistake 4: Exposing Raw Locators Instead of Intent-Named Methods

**Mistake:** Giving `DoctorDashboardPage` a public getter like `getCompleteButton(patientName: string): Locator` and letting the spec call `.click()` on it directly, instead of a method like `completeAppointment(patientName)` that does the click and confirms the result.

**Why it happens:** Returning a `Locator` feels flexible, since the spec can do whatever it wants with it, and it's less code to write on the page object side.

**Symptoms:** Specs drift back into knowing DOM details (`.click()`, which element property to check) instead of expressing intent, and the exact problem POM was introduced to solve, locator changes requiring edits across many spec files, comes right back, just one layer removed.

**Fix:** Page object methods should read as an action or a question in domain language, `completeAppointment()`, `expectAppointmentVisible()`, and do the clicking, filling, and waiting internally. Reserve returning a raw `Locator` for genuinely reusable low-level building blocks, not for actions a spec should just call directly.

### Mistake 5: Copy-Pasting a Whole Page Object per Role Instead of Recognizing the Matrix

**Mistake:** Faced with "test that only doctors and nurses can cancel appointments, but not admins or patients," writing four nearly-identical `cancelAppointment` methods across four dashboard page objects, then bolting on more copy-pasted methods every time a new role/action combination needs coverage.

**Why it happens:** Each individual addition looks small, "just one more method on one more class," so the combinatorial cost only becomes visible after several roles and several actions have accumulated.

**Symptoms:** The permission matrix has 4 roles and 9+ actions from the README's own table. Covering all of it this way means dozens of near-identical methods spread across four classes, most of them differing only in which role is "allowed" and which locator does or doesn't exist for that role.

**Fix:** For role-specific flows, a doctor completing an appointment, a nurse scheduling one, keep the per-role page object; it's the right tool. For systematically testing allowed-vs-denied *across* the whole matrix, that's the job of a lesson covered later in this course, using a role-parameterized approach instead of one more subclass per combination. Recognizing that boundary early keeps this module's pattern from being stretched past where it holds up.
