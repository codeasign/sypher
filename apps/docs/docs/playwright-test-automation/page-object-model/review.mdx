# Page Object Model for a Role-Based App: Review

⏱ 4 minutes

## Key Takeaways

- `BasePage` holds only what every authenticated dashboard shares (nav, logout, an abstract `isReady()` each subclass implements) and never a role-specific locator.
- Each role gets its own page object (`DoctorDashboardPage`, `NurseDashboardPage`, `PatientDashboardPage`, `AdminDashboardPage`) extending `BasePage`, exposing methods named after intent (`completeAppointment`) instead of raw locators.
- Shared UI fragments, `Modal`, `Notification`, are component objects composed into page objects (`this.modal = new Modal(page)`), scoped to their own root locator, never duplicated inside every class that needs them.
- Inheritance models "is-a" (a doctor dashboard *is* an authenticated dashboard); composition models "has-a" (a doctor dashboard *has* a modal). Mixing them up is what leads to bloated base classes or duplicated component locators.
- One page object per role is the right tool for role-specific flows, but not for exhaustive permission-matrix testing across every role and action. That combinatorial problem calls for a role-parameterized pattern covered later in this course, not more subclasses here.

## Recap in 60 Seconds

If you only remember three things:

1. `BasePage` is shared scaffolding; per-role page objects extend it and add only what that role can actually do.
2. Compose reusable UI, `Modal`, `Notification`, as component objects scoped to their own root locator; never re-declare their internals inside every page object that uses them.
3. This pattern covers role-specific flows well; it breaks down for role x action permission-matrix testing, which a later lesson solves differently.

## Try It

Extend `NurseDashboardPage` from Build It into a complete class, mirroring `DoctorDashboardPage`'s structure:

- Give it a full `scheduleAppointment(patientName: string, date: string)` method using the composed `Modal`, following the same confirm/notification flow as `DoctorDashboardPage.addMedicalRecord`.
- Give it a full `cancelAppointment(patientName: string)` method. Note it does the same *thing* `DoctorDashboardPage.cancelAppointment` does, but ask yourself whether that similarity is duplication worth fixing yet, or the kind Mistake 5 says to leave alone until the RBAC permission-matrix lesson covered later in this course.
- Write a spec, `tests/nurse-dashboard.spec.ts`, using `test.use({ storageState: 'playwright/.auth/nurse.json' })`, that schedules an appointment and then asserts it's visible with `expect(locator).toBeVisible()`. No `page.getByRole` calls inside the spec itself, only calls into `NurseDashboardPage`.

## What Comes Next

With `BasePage`, per-role dashboard page objects, and composed `Modal`/`Notification` component objects in place, the next problem is setup repetition: every spec you've written so far still constructs its own page object and calls `gotoDashboard()` by hand. [Fixtures](../fixtures/overview) covers custom fixtures that inject an already-navigated, already-authenticated page object per role directly into your test function, so that boilerplate disappears from every spec file at once.
