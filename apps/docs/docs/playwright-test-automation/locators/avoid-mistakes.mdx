# Finding Elements With Playwright Locators: Common Mistakes

⏱ 9 minutes

## When NOT to Use This

Role-based locators assume the app exposes meaningful roles, labels, and accessible names in the first place. They can't invent semantics the frontend never provided. If you're testing a genuinely inaccessible widget (no ARIA role, no label, purely visual state), `getByTestId` or a CSS fallback isn't a mistake there; it's the honest tool for a real gap, and it's worth flagging that gap to whoever owns the frontend rather than treating it as normal. Similarly, this lesson's locator strategies are for driving and asserting on the *rendered* UI. If what you actually want to verify is a business rule ("a nurse can schedule an appointment") independent of how it renders, testing that directly against the backend's REST API is often the faster and more stable choice; this course's own [API Requests from Playwright](../api-requests-from-playwright/overview) module covers exactly that. Use UI locators when the thing under test is what the user sees and can interact with; use the API layer when the thing under test is the rule itself.

## The Pattern to Remember

- **Pattern:** `getByRole` / `getByLabel` first, `getByText` for static copy, `getByTestId` as a deliberate escape hatch, CSS/XPath only as a last resort. Scope with chaining, narrow with `.filter()`, and assert with retrying `expect(locator)` checks.
- **When to use:** every locator in every test in this course, from here forward.
- **When NOT to use:** don't reach for `getByTestId` or CSS to route around an element that's missing a role or label. Fix that in the app, or at minimum recognize it as a gap rather than the norm.
- **Mental model:** you're querying the page the way a user or assistive technology perceives it (role, label, visible text), not the way a developer happened to implement it today (class names, DOM depth, element order).

## Common Mistakes

### Mistake 1: Reaching for CSS Selectors First

**Mistake:** Copying a selector straight out of DevTools, `page.locator('.btn.btn-primary.add-patient-btn')`, instead of trying `getByRole` first.

**Why it happens:** DevTools makes copying a CSS path a single right-click, and it works immediately, which makes it feel like the correct answer rather than the fast one.

**Symptoms:** The test passes today and fails the next time anyone touches the button's markup or styling (a class rename, a component library swap, a wrapping `<div>` added for layout), even though the button itself, and what it does, never changed.

**Fix:** Start every locator with `getByRole('button', { name: 'Add Patient' })`. It resolves through the accessibility tree, which is far more stable than class names or DOM structure, and it reads as a description of what the element *is*, not how it's currently built.

### Mistake 2: Using getByText for Interactive Elements

**Mistake:** Locating the "Add Patient" button with `page.getByText('Add Patient')` instead of `page.getByRole('button', { name: 'Add Patient' })`.

**Why it happens:** `getByText` feels simpler, and for a button whose visible label matches its accessible name, it often finds the same element, so the mistake doesn't show up right away.

**Symptoms:** Two failure modes, both silent until they aren't. It might match unrelated text elsewhere on the page that happens to contain the same string (a heading, a tooltip, a toast notification), producing a strict-mode violation. Or the button's visible label changes for a copy tweak ("Add Patient" becomes "Add New Patient") while its underlying role and purpose don't, breaking a test that had nothing to do with copy.

**Fix:** Reserve `getByText` for elements whose entire purpose is displaying text: headings, banners, confirmations. For anything interactive, buttons, links, form controls, use `getByRole` with the appropriate role and accessible name.

### Mistake 3: Not Scoping Locators to a Container

**Mistake:** Calling `page.getByRole('button', { name: 'Complete' })` directly on the doctor dashboard's appointment list, when the list renders one "Complete" button per appointment.

**Why it happens:** It works cleanly against a freshly seeded database with exactly one appointment, so the test passes in isolation and the problem doesn't surface until the data changes.

**Symptoms:** `strict mode violation: locator resolved to 3 elements`. Playwright refuses to guess which "Complete" button you meant, and the test fails with an error that (correctly) blames ambiguity, not a missing element.

**Fix:** Scope first. Find the specific row with `.filter({ hasText: 'Jordan Reyes' })`, then chain `.getByRole('button', { name: 'Complete' })` off that row locator, not off `page` directly.

### Mistake 4: Reaching for .nth() Instead of .filter()

**Mistake:** Writing `page.getByRole('listitem').nth(2)` to target "the appointment for Jordan Reyes," because that row happens to render third in the currently seeded data.

**Why it happens:** `.nth()` requires no thought about what actually distinguishes the row you want. It's the path of least resistance when you're looking at the page right now and can just count.

**Symptoms:** The test breaks the moment the seed data changes, a new appointment gets added ahead of it, or the list gets re-sorted, none of which have anything to do with whether the feature under test still works.

**Fix:** Use `.filter({ hasText: ... })` or `.filter({ has: ... })` to select by what actually identifies the row, such as a patient name, a status, or a nested element, not by position. Reserve `.first()` / `.nth()` for cases where you genuinely mean "any one" or "position itself is the thing under test."

### Mistake 5: Checking Absence With a Non-Retrying Check

**Mistake:** Asserting the patient dashboard hides the "Add Patient" button with `expect(await page.getByRole('button', { name: 'Add Patient' }).isVisible()).toBe(false)` instead of `await expect(page.getByRole('button', { name: 'Add Patient' })).not.toBeVisible()`.

**Why it happens:** `.isVisible()` returns a plain boolean immediately, which feels more direct than an `expect(locator)` call, especially coming from other testing tools where checking a boolean is the normal pattern.

**Symptoms:** A flaky false negative: the dashboard hasn't finished deciding which role's UI to render yet (a brief loading state, an async permission check) at the exact millisecond `.isVisible()` runs, so it reports `true` even though the button correctly disappears half a second later. The test fails intermittently for a permission boundary that actually holds.

**Fix:** Use the web-first form, `await expect(locator).not.toBeVisible()` or `await expect(locator).toBeHidden()`, which retries until the element settles into its final state or the timeout elapses, instead of reading the DOM once at an arbitrary moment.
