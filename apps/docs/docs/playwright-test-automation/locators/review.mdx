# Finding Elements With Playwright Locators: Review

⏱ 4 minutes

## Key Takeaways

- Locator priority order is `getByRole` / `getByLabel` first, `getByText` for static copy, `getByTestId` as a deliberate escape hatch, and CSS/XPath only as a rare last resort. Each step down that order trades resilience for convenience.
- Role-based locators query the accessibility tree, not the DOM's current markup, which is why they keep passing through class renames, `<div>` restructuring, and styling-library swaps that would break a CSS selector.
- Chaining scopes a search to a container (`appointmentRow.getByRole('button', { name: 'Complete' })`); `.filter({ hasText: ... })` or `.filter({ has: ... })` narrows a list by what actually identifies the element you mean, not by position.
- `.first()` and `.nth()` are for genuine positional intent only. Reach for `.filter()` whenever what you actually mean is "the row for this patient," even if it happens to render first today.
- Role-conditional UI in the RBAC app, like the "Add Patient" button rendering for doctor/nurse and not for patient/admin, is asserted with the same locator both ways: `.toBeVisible()` for the roles that should see it, `.not.toBeVisible()` or `.toBeHidden()` for the roles that shouldn't, both retrying rather than checking once.

## Recap in 60 Seconds

If you only remember three things:

1. Reach for `getByRole` or `getByLabel` before anything else. They describe what the element *is*, not how it's currently built.
2. Scope with chaining and narrow with `.filter()` instead of counting positions with `.nth()`.
3. Assert presence and absence with retrying `expect(locator)` checks, `.toBeVisible()` and `.not.toBeVisible()` / `.toBeHidden()`, never a one-shot `.isVisible()` boolean.

## Try It

Extend `tests/locators.spec.ts` with a nurse-role version of the role-conditional pattern: log in as a seeded nurse account, navigate to `/dashboard`, and assert that the "Add Patient" button is visible (nurses can add patients, per the RBAC app's stated permission matrix). Then add a second test, still as the nurse, that navigates to `/appointments` and uses `.filter({ hasText: ... })` to locate a specific appointment row, chaining `.getByRole('button', { name: 'Cancel' })` off it (nurses can cancel appointments, per the same matrix). If either assertion doesn't hold against your seeded data, that's not your test being wrong. It's the exact kind of permission-matrix gap the RBAC app's own README warns you about, and worth noting for this course's dedicated coverage of RBAC permission-matrix testing later on.
