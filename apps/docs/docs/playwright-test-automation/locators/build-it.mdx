# Finding Elements With Playwright Locators — Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: getByRole on the Login Form

Create `tests/locators.spec.ts` in your RBAC repo. Start with the login form — every role starts here, so it's the most-exercised part of the app in this whole course.

```typescript title="tests/locators.spec.ts"
import { test, expect } from '@playwright/test';

test('login form has a username field, password field, and log in button', async ({ page }) => {
  await page.goto('/login');

  await expect(page.getByRole('textbox', { name: 'Username' })).toBeVisible();
  await expect(page.getByRole('textbox', { name: 'Password' })).toBeVisible();
  await expect(page.getByRole('button', { name: 'Log In' })).toBeVisible();
});
```

`getByRole('textbox', { name: 'Username' })` doesn't care whether that input is a plain `<input>`, wrapped in three `<div>`s, or styled with a CSS-in-JS class that changes every deploy. It queries the accessibility tree: an element with the `textbox` role, whose accessible name is `Username`. That accessible name usually comes from an associated `<label>`, which is exactly why `getByRole` and `getByLabel` so often point at the same element from two different angles.

### Step 2: getByLabel for Form Filling

For actually filling a form, `getByLabel` reads more naturally than `getByRole('textbox', ...)`, and it's just as resilient — both resolve through the same label association:

```typescript
test('admin can log in', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page).toHaveURL('/dashboard');
});
```

Use `getByRole` when you're asserting on structure ("this is a button," "this is a heading") and `getByLabel` when you're driving a form field. Both outrank anything CSS-based for the same reason: they describe the element's role in the interface, not its implementation.

### Step 3: getByText for Static Copy

The dashboard greets the logged-in user by name. That's plain text, not a form control and not (necessarily) an interactive element, so `getByText` is the right tool:

```typescript
test('dashboard greets the logged-in admin', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page.getByText('Welcome, admin')).toBeVisible();
});
```

Notice what `getByText` is *not* used for here: the "Log In" button above stayed a `getByRole` call, not `getByText('Log In')`. A button's text is an implementation detail of how the button currently renders its label; its role as a `button` with an accessible name is the actual contract. Reach for `getByText` for headings, banners, confirmation messages, and empty-state copy — content whose entire job is to be read, not clicked.

### Step 4: getByTestId as a Deliberate Escape Hatch

Some elements genuinely have no meaningful role or label — a decorative status dot on an appointment row, for instance, that conveys state through color alone. For those, `getByTestId` is the honest choice, not a shortcut around doing the other three properly:

```typescript
test('appointment status indicator reflects a scheduled appointment', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();
  await page.goto('/appointments');

  await expect(page.getByTestId('appointment-status-scheduled').first()).toBeVisible();
});
```

If you find yourself reaching for `getByTestId` on something that clearly *is* a button or a form field, that's usually a sign to check whether the element is missing an accessible role or label in the frontend itself — worth a bug report to whoever owns that code, not just a workaround in your test.

### Step 5: Chaining Locators to Scope a Search

The doctor dashboard's appointment list renders one row per appointment, and every row contains the same set of controls — a patient name, a date, and action buttons. `page.getByRole('button', { name: 'Complete' })` on its own matches every "Complete" button on the page at once, which fails in strict mode the moment there's more than one appointment — so instead of asking the whole page, chain from a specific row:

```typescript
test('doctor completes a specific patient appointment', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('dr.chen');
  await page.getByLabel('Password').fill('doctor123'); // use your own seeded doctor credentials from setup
  await page.getByRole('button', { name: 'Log In' }).click();
  await page.goto('/appointments');

  const appointmentRow = page
    .getByRole('listitem')
    .filter({ hasText: 'Jordan Reyes' });

  await appointmentRow.getByRole('button', { name: 'Complete' }).click();

  await expect(appointmentRow.getByText('Completed')).toBeVisible();
});
```

`appointmentRow` is itself a locator — chaining `.getByRole('button', { name: 'Complete' })` off it searches only inside that one row, not the whole page. This is the same principle as `getByLabel` versus `getByRole`, applied to structure: scope first, then locate.

### Step 6: Filtering With .filter()

`.filter({ hasText: ... })` is how you turned a list of appointment rows into the one row you meant, above. It also accepts `has`, for filtering by a nested locator instead of text — useful when the distinguishing feature of the row you want isn't a piece of text but the presence of another element:

```typescript
test('finds the appointment row that has a Cancel button available', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('nurse.patel');
  await page.getByLabel('Password').fill('nurse123'); // use your own seeded nurse credentials from setup
  await page.getByRole('button', { name: 'Log In' }).click();
  await page.goto('/appointments');

  const cancellableAppointment = page
    .getByRole('listitem')
    .filter({ has: page.getByRole('button', { name: 'Cancel' }) });

  await expect(cancellableAppointment.first()).toBeVisible();
});
```

`.filter()` re-evaluates every time Playwright retries the locator, so it stays correct even as the underlying list changes between renders — a row that gets cancelled and re-fetched from the API is still matched or excluded correctly on the next retry.

### Step 7: .first() and .nth() — Use Sparingly, and Only for Position

Sometimes you genuinely mean "whichever one renders first," not "the one matching some content." The seeded data always has at least one appointment, and you don't care which:

```typescript
test('at least one appointment is listed', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();
  await page.goto('/appointments');

  await expect(page.getByRole('listitem').first()).toBeVisible();
});
```

`.nth(n)` is the same idea for an arbitrary index, and it's the locator equivalent of a hardcoded array index — correct only as long as the order never changes. Prefer `.filter()` whenever the thing you actually mean is "the row for this patient" or "the row with this status," even if, today, that row also happens to render first.

### Step 8: Role-Conditional UI — the Add Patient Button

This is the pattern the whole lesson has been building toward. The RBAC app's dashboard renders an "Add Patient" button for doctor and nurse sessions, and omits it entirely for patient and admin sessions — so the same locator, pointed at two different roles, ends up backing two opposite assertions:

```typescript
test('doctor dashboard shows the Add Patient button', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('dr.chen');
  await page.getByLabel('Password').fill('doctor123'); // use your own seeded doctor credentials from setup
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByRole('button', { name: 'Add Patient' })).toBeVisible();
});

test('patient dashboard hides the Add Patient button', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('patient.jsmith');
  await page.getByLabel('Password').fill('patient123'); // use your own seeded patient credentials from setup
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByRole('button', { name: 'Add Patient' })).not.toBeVisible();
});
```

`.not.toBeVisible()` and `.toBeHidden()` both work here, and both are web-first — Playwright retries the check until the timeout elapses rather than reading the DOM once and giving up. That distinction matters more than it looks: if the dashboard briefly renders a loading skeleton before deciding which role's UI to show, a one-shot check could catch that transient state and report a false negative. A retrying assertion waits it out. Prefer `.not.toBeVisible()` when the element might exist in the DOM but be styled invisible (`display: none`, `visibility: hidden`), and `.toBeHidden()` interchangeably for the same case — they're equivalent for this purpose. Neither one is the right tool for asserting an element was never rendered at all; for that, assert on `.toHaveCount(0)` against the locator instead.

Logging in through the UI for every test, as these examples do, is correct for this lesson and slow for a whole suite — a later lesson on session-based authentication replaces the `getByLabel` login block with a `storageState` captured once per role, so tests like these skip straight to the assertion. The locators themselves don't change; only how you arrive at an authenticated page does.

## How It Works Internally

`getByRole` doesn't parse HTML tags — it resolves the browser's computed accessibility tree, the same structure a screen reader consumes. A `<button>` element gets an implicit `button` role for free; a `<div onClick={...}>` styled to look like a button does not, unless the frontend explicitly sets `role="button"`. This is why `getByRole` locators sometimes fail against markup that looks correct visually but was built with the wrong semantic element — and why that failure is usually pointing at a real accessibility gap in the app, not a mistake in your test.

Every `getByRole`, `getByLabel`, `getByText`, and `getByTestId` call returns a `Locator`, not an element handle. A `Locator` is a lazy, retrying query — it doesn't search the page at the moment you write `page.getByRole(...)`, only when you later call an action or an assertion on it (`.click()`, `expect(...).toBeVisible()`). That's what makes chaining and filtering cheap: `appointmentRow.getByRole('button', { name: 'Complete' })` composes two unresolved queries into one, and the whole chain re-runs together, from scratch, on every retry.
