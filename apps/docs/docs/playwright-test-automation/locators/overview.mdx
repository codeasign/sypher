# Finding Elements With Playwright Locators

⏱ 18 minutes · Difficulty: Beginner

## What You Will Learn

By the end of this lesson you will be able to:

- Reach for `getByRole`, `getByLabel`, `getByText`, and `getByTestId` in the right priority order, and explain why that order matters
- Chain and scope locators so they target one element inside a container instead of matching everything on the page
- Filter a list of matching elements down to the one you mean with `.filter()`, `.first()`, and `.nth()`
- Recognize the rare cases where falling back to a CSS or text selector is actually the right call
- Locate role-conditional UI in the RBAC app, such as the "Add Patient" button that renders for some roles and not others, and assert on its presence or absence correctly

## Why This Matters

A locator isn't a lookup. It's a live, retrying query against the page. Every action and every assertion you write in this course starts with a locator, and the quality of that locator decides whether your test survives the next time someone on the RBAC app's frontend renames a CSS class, restructures a `<div>`, or redesigns a dashboard layout. A test built on `page.locator('.btn-primary-lg')` breaks the moment that class name changes, even though nothing about the button's actual behavior changed. A test built on `page.getByRole('button', { name: 'Add Patient' })` keeps passing, because it queries the same thing a screen reader or a real user would: an interactive element with a specific accessible name.

This matters more in a role-based app than almost anywhere else. The RBAC app renders different UI for admin, doctor, nurse, and patient sessions, so the same dashboard route can produce four different accessibility trees depending on who's logged in. Getting locators right here isn't just about resilience to refactors. It's the mechanism you'll use to prove a permission boundary actually holds in the rendered UI, not just in the API response.

## The Problem

Say you want to test that a doctor can add a new patient. Your first instinct might be to open the browser's DevTools, right-click the "Add Patient" button, copy its CSS selector, and paste it into your test:

```typescript
await page.locator('#dashboard > div.toolbar > button.btn.btn-primary.add-patient-btn').click();
```

It works, but it also breaks the next time anyone touches that toolbar's markup, whether that's reordering the buttons, wrapping them in a new `<div>`, or switching the styling library. None of those changes affect what the button *does* or what a user sees, yet they break your test anyway, because the selector was never really describing the button. It was describing today's implementation of the button.

## The Concept

Playwright gives you a small set of built-in locator methods, and they are not interchangeable. They exist in a deliberate priority order, from most resilient to least:

1. **`getByRole`**: queries the accessibility tree by role and accessible name (`button`, `textbox`, `link`, `heading`, and so on). This is what a screen reader sees, and it is largely immune to styling and markup changes.
2. **`getByLabel`**: finds a form control by its associated `<label>` text. Ideal for the RBAC app's login and patient-record forms.
3. **`getByText`**: finds an element by its visible text content. Useful for headings, confirmation messages, and static copy, but brittle if that copy changes.
4. **`getByTestId`**: finds an element by a `data-testid` attribute. An explicit escape hatch for elements with no meaningful role or label.
5. **CSS / XPath selectors**: `page.locator('.some-class')` or an XPath expression. The least resilient option, and the one you should reach for last, if at all.

The reasoning behind this order comes down to what each method is actually asking the page. The first four methods query the page the way a *user*, or an assistive technology, perceives it: what role does this element play, what's it labeled, what does it say. CSS selectors, on the other hand, query the page the way a *developer* happened to implement it today. That distinction matters because implementations change constantly, while roles, labels, and visible text change far less often. Changing them changes the product itself, not just the code behind it.

So a good way to picture the whole priority list at once: it runs from "describes what the element is" down to "describes how it happens to be built today." `getByRole` sits at the top because it reads the accessibility tree directly and survives CSS, class, and markup churn. `getByLabel` comes next, tied to form fields through their `<label>`. `getByText` follows, matching visible copy, fine for static text but brittle for anything whose wording might change. `getByTestId` is the deliberate escape hatch for elements with no accessible role or label at all. And CSS or XPath selectors sit at the very bottom, as the last resort that describes today's markup rather than the actual UI.

There's a second dimension beyond *which* method you use: how you narrow a locator down to exactly one element. `getByRole('listitem')` on the doctor dashboard's appointment list matches every row, not the one row you care about. Playwright gives you `.filter()` to narrow by content, and `.first()` / `.nth()` to narrow by position, and picking the right one is its own skill. `.filter({ hasText: 'Jane Doe' })` still finds the right row if the list gets reordered; `.nth(2)` does not.

Applied to the RBAC app, this all comes together in a concrete, testable claim: a doctor's dashboard renders an "Add Patient" button, and a patient's dashboard does not. `page.getByRole('button', { name: 'Add Patient' })` is the locator; whether it resolves to a visible element or not, per role, is the assertion. That single pattern, a role-based locator plus a web-first visibility assertion, is how you turn "this app enforces role permissions" from a claim in a README into something a test suite actually checks.
