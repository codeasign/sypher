# Handling Dynamic and Async UI — Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Wait on the Resulting UI Change First

Start with the case auto-waiting already solved, because it's still the right tool most of the time. Log in as a nurse (via your `storageState` from the authentication lesson), schedule an appointment, and wait for the new row — not a timeout, the row itself:

```typescript
import { test, expect } from '@playwright/test';

test.use({ storageState: 'auth/nurse.json' });

test('scheduling an appointment adds it to the list without a fixed delay', async ({ page }) => {
  await page.goto('/appointments');

  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption('Jane Doe');
  await page.getByLabel('Doctor').selectOption('Dr. Patel');
  await page.getByLabel('Date').fill('2026-08-03');
  await page.getByRole('button', { name: 'Confirm' }).click();

  const newRow = page.getByRole('row', { name: /Jane Doe.*Dr\. Patel/ });
  await expect(newRow).toBeVisible();
});
```

No `waitForTimeout`, no guessed delay. `expect(newRow).toBeVisible()` polls the DOM on its own retry schedule until the row exists or the assertion's timeout runs out. Whether the frontend's refetch takes 80 milliseconds or 1.5 seconds, this test passes as soon as the row actually renders and not a moment later — which is also why it's faster on a fast day and still correct on a slow one. This is the majority case. If a locator assertion can express what you're waiting for, use it and stop reading the rest of this lesson for that particular test.

### Step 2: Recognize When a Locator Isn't Enough

The nurse's confirmation toast on this screen reads "Appointment #`<id>` scheduled for `<date>`" — and that ID comes from the server, generated at insert time. You can't know it in advance to build a locator for it, and you don't want to assert on the toast's presence alone when the actual thing you need to verify is that the ID it displays matches the ID the backend just created.

That's a response-shaped fact, not a DOM-shaped one. This is where `waitForResponse` earns its place.

### Step 3: Set Up `waitForResponse` Before the Action, Not After

The single most important detail with `waitForResponse` is ordering. The response can arrive before your code gets around to waiting for it — a fast backend, a slow test runner — so you register the wait and trigger the action together, with `Promise.all`, rather than one after the other:

```typescript
test('the confirmation toast quotes the server-generated appointment ID', async ({ page }) => {
  await page.goto('/appointments');

  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption('Jane Doe');
  await page.getByLabel('Doctor').selectOption('Dr. Patel');
  await page.getByLabel('Date').fill('2026-08-03');

  const [response] = await Promise.all([
    page.waitForResponse(
      (res) => res.url().includes('/api/appointments') && res.request().method() === 'POST',
    ),
    page.getByRole('button', { name: 'Confirm' }).click(),
  ]);

  expect(response.status()).toBe(201);
  const { id } = await response.json();

  await expect(page.getByText(`Appointment #${id} scheduled`)).toBeVisible();
});
```

Compare this to writing `await page.getByRole('button', { name: 'Confirm' }).click();` followed by a separate `await page.waitForResponse(...)` on the next line. If the POST resolves in the gap between those two statements — entirely possible on a fast backend — the second call misses it and hangs until its own timeout. `Promise.all` closes that gap by registering the listener and firing the click in the same tick.

Notice, too, that the predicate checks both the URL and the HTTP method. `rbac-healthcare-system` has a `GET /api/appointments` on the same path that runs on page load — matching on URL alone would happily resolve against that unrelated request instead of the POST you actually triggered.

### Step 4: `waitForLoadState` for Background Requests After a Navigation

The admin dashboard is a different shape of async problem. Logging in as admin and navigating to `/admin/dashboard` fires several requests in parallel — users, appointments, medical records counts — none of which you triggered individually, so there's no single action to pair a `waitForResponse` with. Here, waiting for the page's overall load state is the right level of granularity:

```typescript
test.use({ storageState: 'auth/admin.json' });

test('the admin dashboard settles before you interact with it', async ({ page }) => {
  await page.goto('/admin/dashboard');
  await page.waitForLoadState('networkidle');

  await expect(page.getByRole('heading', { name: 'Admin Dashboard' })).toBeVisible();
  await expect(page.getByText(/Total Patients: \d+/)).toBeVisible();
});
```

`networkidle` waits until there have been no new network connections for a short window, which is a reasonable proxy for "the dashboard's background fetches are done" when there are several of them and you don't want to enumerate each one. It is not free, though — it's a blanket wait, not a targeted one, and Step 6 of this lesson shows a trace where it's the actual source of a flaky test rather than the fix for one. Prefer it for this specific shape of problem — several unrelated requests after a navigation — and reach for `waitForResponse` when you care about one specific call.

### Step 5: Combine Both When a Flow Needs It

The full nurse flow benefits from both tools at once: `waitForResponse` to confirm the POST succeeded and grab the server-generated ID, then a locator assertion for the resulting DOM state, because that's still the most precise way to confirm the UI actually reflects it:

```typescript
test('scheduling an appointment: response and resulting UI both verified', async ({ page }) => {
  await page.goto('/appointments');
  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption('Jane Doe');
  await page.getByLabel('Doctor').selectOption('Dr. Patel');
  await page.getByLabel('Date').fill('2026-08-03');

  const [response] = await Promise.all([
    page.waitForResponse(
      (res) => res.url().includes('/api/appointments') && res.request().method() === 'POST',
    ),
    page.getByRole('button', { name: 'Confirm' }).click(),
  ]);

  const { id } = await response.json();

  await expect(page.getByText(`Appointment #${id} scheduled`)).toBeVisible();
  await expect(page.getByRole('row', { name: /Jane Doe.*Dr\. Patel/ })).toBeVisible();
});
```

Neither wait replaces the other here. `waitForResponse` tells you the write succeeded and hands you data only the server knows; the locator assertion tells you the UI actually caught up to that write. A test that only checked the response could pass while the list silently failed to refresh — that's a real bug this app has been known to have, and it's exactly the kind of gap a response-only assertion would miss.

### Step 6: Debug a Flaky Wait With Trace Viewer

Suppose the `networkidle` test from Step 4 fails intermittently in CI but not locally. Turn tracing on for the run — either `trace: 'on-first-retry'` in `playwright.config.ts` from Setup, or force it for a single run:

```bash
npx playwright test admin-dashboard.spec.ts --trace on
```

Open the resulting trace:

```bash
npx playwright show-report
```

From the HTML report, click the failed test, then open its trace. Work through it in this order:

1. **Timeline first.** The timeline strip along the top shows every action and every network request as a block in time. Look for a request that starts late or keeps recurring — a polling call the app makes every few seconds for a "last updated" indicator is a classic reason `networkidle` never quite settles, because there's never truly a quiet window.
2. **Network tab, filtered to XHR/fetch.** Confirm which specific request `waitForLoadState('networkidle')` was actually waiting on. If you see it waiting past the requests you care about, on a background poll you don't, you've found your flake — a wait that watches for something adjacent to the thing you actually need, not one that's genuinely still incomplete.
3. **DOM snapshots at each step.** Trace viewer captures a DOM snapshot before and after each action. Step through them around the failure point — if the data you needed was already rendered in the "before" snapshot of a step that still failed, the wait resolved correctly and the *assertion* is wrong, not the wait. That distinction matters: it tells you whether to fix the wait or fix the locator.
4. **Console and errors panel.** A silently failing background request (a 500 from an unrelated endpoint) can also stall `networkidle` indefinitely by keeping a connection open in a retry loop. The console and network status codes together usually surface this faster than staring at the timeline alone.

In practice, a `networkidle` flake in this app is almost always the polling endpoint on the admin dashboard's "last synced" indicator. The fix isn't a longer timeout on `networkidle` — it's replacing the blanket wait with a targeted `waitForResponse` for the specific request the test actually depends on, the same substitution you made in Step 3.

## How It Works Internally

`page.waitForResponse()` doesn't poll anything — it attaches a one-time listener to the page's `response` event, which Playwright's browser-side instrumentation fires for every network response as it completes. That's why ordering matters: if the response event fires before your code has attached the listener, there's nothing left to catch it, and the call hangs until its own timeout expires. `Promise.all([page.waitForResponse(...), page.click(...)])` works because both promises start synchronously in the same tick — the listener is attached before the click's resulting request can possibly resolve.

`waitForLoadState('networkidle')` works differently: it tracks the count of in-flight network connections and resolves once that count has been zero for a short quiet window (roughly 500 milliseconds). That's a heuristic, not a precise signal tied to any one request — which is exactly why a page with any recurring background activity (polling, analytics beacons, a websocket-less "refresh every N seconds" pattern) may never produce a long enough quiet window, and why `networkidle` is a poor default to reach for everywhere rather than a targeted tool for the specific "several unrelated requests settle after navigation" shape of problem.
