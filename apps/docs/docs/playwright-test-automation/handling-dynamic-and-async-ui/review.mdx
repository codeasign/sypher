# Handling Dynamic and Async UI: Review

⏱ 4 minutes

## Key Takeaways

- Auto-waiting locators still handle most async UI. If the result of a network call ends up visible and stable in the DOM, `expect(locator)...` already polls for it correctly and you don't need anything from this lesson.
- `waitForResponse` is for the narrower case: a fact that lives only in a response, like a server-generated ID or a status code, that no locator can point at.
- Always register `waitForResponse` before the action that triggers it, paired with `Promise.all`. Attaching the listener after the click risks missing a response that resolves faster than your code gets to the next line.
- `waitForLoadState('networkidle')` waits for a quiet window in network activity, which suits a navigation with several one-time background requests but can hang indefinitely on a page with recurring polling. Match on the specific request you need instead when that's the case.
- When a wait-related test is flaky, trace viewer's timeline and network tab tell you which specific wait was watching the wrong thing. That's a faster and more reliable diagnosis than guessing and raising a timeout.

## Recap in 60 Seconds

If you only remember three things:

1. Ask what you're actually waiting for, a DOM-visible result or a response-only fact, before picking a tool; most cases are still a plain locator assertion.
2. `waitForResponse` goes inside `Promise.all` with the triggering action, matched on both URL and method, never called as a lone line after the click.
3. When a wait is flaky, open its trace before you touch the timeout. The timeline and network tab show you which wait was actually the problem.

## Try It

Extend the flow from Build It Step 3 to a different role and a different mutation. Log in as a doctor (`storageState: 'auth/doctor.json'`) and complete an appointment instead of scheduling one:

- Trigger the `PATCH /api/appointments/:id` request that marks an appointment complete, using `Promise.all` with `waitForResponse` matched on method `PATCH` and a URL pattern that tolerates the appointment ID changing between runs.
- Assert on the response status and on a field in its body (for example, a `completedAt` timestamp) that only the server can produce.
- Then assert the resulting UI state with a locator. The appointment's row should now show a "Completed" status badge, so the test verifies both the write and the render, the way Build It Step 5 combines both tools.
- Deliberately break the test by swapping `Promise.all` for two sequential `await` calls, run it several times in a row, and see whether you can reproduce the race condition from Avoid Mistakes Mistake 2. Then fix it back and confirm it passes consistently.
