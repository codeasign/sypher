# Handling Dynamic and Async UI

⏱ 20 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Recognize the narrow set of cases where auto-waiting locators do not cover you, and why that set is smaller than it feels
- Wait for a network-driven UI change (a new appointment row, a refreshed list) by asserting on the change itself instead of guessing a delay
- Use `waitForResponse` to wait on one specific API call, and set it up before the action that triggers it, not after
- Use `waitForLoadState` to wait for a navigation's background requests to settle, and know when `networkidle` helps and when it doesn't
- Open a trace for a flaky test in trace viewer and identify exactly which wait was the actual problem

## Why This Matters

You already know that Playwright locators auto-wait: `click()`, `fill()`, and `expect(locator).toBeVisible()` all retry against the live DOM until the condition holds or a timeout elapses. That single fact eliminates most of the flakiness you'd otherwise hand-roll waits for. It is tempting to conclude the waiting problem is fully solved and move on.

It isn't quite. `rbac-healthcare-system` has several flows where the thing you actually need to wait for isn't "does this element eventually appear." It's "did this specific network round-trip finish, and did it finish the way I expect." Take the nurse who schedules an appointment: the patient's appointment list needs to refresh with a new row, and that part you can still wait for with a locator, so you should. But when you need to assert on the response itself, things like its status code, a server-generated ID, or the exact JWT claims the frontend sent, there's no DOM element to point a locator at. That's the case this module is for: not undoing auto-waiting, but recognizing the narrower slice it doesn't cover.

Get this distinction wrong in either direction and you pay for it. Reach for `waitForResponse` everywhere and your tests become brittle, tightly coupled to endpoint URLs that have nothing to do with what you're actually verifying. Never reach for it and you'll eventually write a test that passes locally nine times out of ten and fails in CI, flaky in the specific way that arbitrary timeouts and "it usually works" waits produce.

## The Problem

Here's a test for the nurse-schedules-an-appointment flow that looks reasonable:

```typescript
await page.getByRole('button', { name: 'Schedule Appointment' }).click();
await page.getByLabel('Patient').selectOption('Jane Doe');
await page.getByLabel('Doctor').selectOption('Dr. Patel');
await page.getByLabel('Date').fill('2026-08-03');
await page.getByRole('button', { name: 'Confirm' }).click();

// Don't do this: guessing how long the refresh takes
await page.waitForTimeout(2000);

await expect(page.getByRole('cell', { name: 'Jane Doe' })).toBeVisible();
```

On your machine, against a backend running on `localhost:5000` with nothing else competing for CPU, two seconds is probably enough for the `POST /api/appointments` call to resolve and the frontend to re-render the list. In CI, on a shared runner, under load, it might not be. Worse, on a fast day it wastes two full seconds doing nothing, and on a slow day it fails outright. Either way, the number `2000` was never actually connected to the thing you were waiting for. That disconnect between the timeout you wrote and the event you actually cared about is the root of almost every flaky async test.

## The Concept

The fix isn't a bigger number. It's asking a more precise question: what am I actually waiting for, and does a locator see it?

Two categories of "waiting for async state" show up in this app, and each one calls for a different tool.

Sometimes **the result lands in the DOM eventually.** The new appointment row, the updated patient count, the doctor's dashboard reflecting a completed appointment: all of these are visible, stable UI state once the async work finishes, and that's exactly what a web-first `expect(locator).toBeVisible()` already polls for, for as long as its timeout allows. That means it's still squarely auto-waiting's territory, so you don't need `waitForResponse` here, and reaching for it anyway just couples your test to an endpoint URL for no benefit.

Other times, **the thing you need to verify isn't (only) in the DOM.** Sometimes it's the response status code. Sometimes it's a server-generated appointment ID you need before you can assert the confirmation toast quotes it correctly. Sometimes it's confirming the frontend actually sent the nurse's JWT (the token proving who's logged in) and not a stale one, or making sure every background request a dashboard fires on load has settled before you start interacting with it. None of that is a locator's job. It's `waitForResponse` and `waitForLoadState` doing something a DOM-polling locator structurally cannot.

Same trigger, two possible branches. The POST request either produces a DOM change a locator will pick up on its own, or it produces a fact that only exists in the response itself, one that needs `waitForResponse` set up before the click that causes it.
