# Handling Dynamic and Async UI: Common Mistakes

⏱ 8 minutes

## When NOT to Use This

Nothing in this lesson replaces auto-waiting locators. If the thing you're waiting for ends up as a stable, visible piece of the DOM (a new row, an updated count, an enabled button), a web-first `expect(locator)...` assertion already handles it, and reaching for `waitForResponse` or `waitForLoadState` there is unnecessary machinery that couples your test to an endpoint URL for no benefit. This lesson is for the narrower case: a fact you need that only exists in a response body, or a navigation with enough parallel background requests that waiting on any single locator doesn't represent "the page is ready." If you're not in one of those two situations, you don't need anything from this lesson. Go back to a plain locator assertion.

## The Pattern to Remember

- **Pattern:** start by asking what you're actually waiting for, and let that decide the tool. If it's a DOM-visible result, reach for `expect(locator)...`. If it's a response-only fact (status, body, headers), reach for `waitForResponse`, registered before the triggering action via `Promise.all`. And if it's several unrelated background requests settling after a navigation, `waitForLoadState('networkidle')` is the right tool, used sparingly.
- **When to use:** a specific `POST`/`PATCH`/`DELETE` response you need to inspect, or a navigation that fires requests you didn't individually trigger.
- **When NOT to use:** any state change that ends up visible and stable in the DOM. That's still a locator's job.
- **Mental model:** locators watch the DOM; `waitForResponse` watches the network. Pick the one that's actually watching the thing you care about, not the one that feels more thorough.

## Common Mistakes

### Mistake 1: Reaching for `waitForResponse` When a Locator Would Do

**Mistake:** Wrapping every action that touches the network in `waitForResponse`, including ones where the result is already visible in the DOM. For example, waiting for the `GET /api/appointments` response after scheduling, instead of just asserting the new row is visible.

**Why it happens:** It feels more thorough. You're "waiting for the real thing," not just hoping the UI catches up. It also mirrors habits from tools without Playwright's auto-waiting model, where waiting on the network was often the only reliable option.

**Symptoms:** Tests that break every time an endpoint URL changes or an extra request gets added to a flow, even though the actual UI behavior you care about never changed. The test is now coupled to implementation details it doesn't need to know about.

**Fix:** Ask whether the result lands in the DOM. If it does, use `expect(locator).toBeVisible()` (or the equivalent) and delete the `waitForResponse` call entirely.

### Mistake 2: Calling `waitForResponse` After the Triggering Action

**Mistake:** Writing the click first and the wait second, instead of pairing them with `Promise.all`:

```typescript
// Don't do this: the response can arrive before this line runs
await page.getByRole('button', { name: 'Confirm' }).click();
const response = await page.waitForResponse((res) => res.url().includes('/api/appointments'));
```

**Why it happens:** It reads more naturally top to bottom, click, then wait for what the click caused, and it works most of the time, which is exactly what makes it dangerous.

**Symptoms:** A test that passes reliably in local development, where the backend is slightly slower relative to Playwright's own event loop, and then fails intermittently in CI or on a faster machine where the response resolves before the `waitForResponse` listener is attached. The failure looks like a timeout with no obvious cause.

**Fix:** Register the wait and trigger the action together with `Promise.all`, as shown in Build It Step 3, so the listener is attached before the request can possibly resolve.

### Mistake 3: Using `waitForTimeout` as the "Quick Fix"

**Mistake:** Reaching for a fixed delay to paper over a wait you haven't diagnosed yet:

```typescript
// Don't do this: the delay isn't connected to the thing you're waiting for
await page.getByRole('button', { name: 'Confirm' }).click();
await page.waitForTimeout(2000);
await expect(page.getByText('Appointment #1 scheduled')).toBeVisible();
```

**Why it happens:** It's the fastest way to make a failing test pass right now, and under deadline pressure "it passes" and "it's correct" get treated as the same thing.

**Symptoms:** A number that was tuned to whatever made the test pass once, that quietly becomes wrong the moment the backend gets slower, the CI runner gets busier, or the flow gains one more step. The test either wastes time waiting past when it could have finished, or starts failing again with no code change to explain why.

**Fix:** Replace it with the specific wait the situation calls for: a locator assertion, `waitForResponse`, or `waitForLoadState`, following the decision in this lesson's Concept section. There is no situation in this app's test suite where a fixed delay is the right final answer, only ones where it's a placeholder for a diagnosis you haven't finished yet.

### Mistake 4: Treating `networkidle` as a Default Habit

**Mistake:** Adding `await page.waitForLoadState('networkidle')` after every `page.goto()` in the suite, regardless of whether the page in question has background polling.

**Why it happens:** It worked the first time it was used, on the admin dashboard, so it gets copied forward as the standard "make sure the page is ready" line without re-checking whether it fits.

**Symptoms:** Tests against pages with any recurring background activity (and the admin dashboard's "last synced" indicator polls every few seconds) hang until `networkidle`'s own timeout, because there's never a long enough quiet window in network activity for it to resolve. The failure looks like a slow page, not a wait that was never going to succeed.

**Fix:** Reserve `networkidle` for navigations with several unrelated one-time background requests and no polling. When a page has recurring activity, wait for the specific element or response you actually need instead. Build It Step 6 walks through diagnosing exactly this failure in trace viewer.

### Mistake 5: Matching `waitForResponse` Too Loosely

**Mistake:** Matching only on a URL substring, without checking the HTTP method. For example, `res.url().includes('/api/appointments')` alone, which matches the page's own `GET /api/appointments` load as readily as the `POST` you actually triggered.

**Why it happens:** The URL is the most visible part of a request, and a substring match looks specific enough at a glance.

**Symptoms:** `waitForResponse` resolves immediately against an unrelated request that happened to share the URL fragment, so the test proceeds to assert on stale or missing data instead of actually waiting for the request it cared about. This is often more confusing than an outright timeout, because the test doesn't fail where you'd expect. It fails later, on an assertion that looks unrelated to waiting at all.

**Fix:** Match on both URL and method, as in Build It Step 3: `res.url().includes('/api/appointments') && res.request().method() === 'POST'`. For endpoints with path parameters (`/api/appointments/42`), match a stable prefix or a regular expression rather than an exact string, so the test survives the ID changing between runs.
