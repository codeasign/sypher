# Actions and Web-First Assertions: Hands On

⏱ 28 minutes

## Breaking It Down

With both servers running, backend on `:5000`, frontend on `:3002`, you'll work through each action against the RBAC app, pairing it every time with the web-first assertion that confirms it actually worked.

### Step 1: `fill`, the Login Form

Create `tests/login.spec.ts`:

```typescript title="tests/login.spec.ts"
import { test, expect } from '@playwright/test';

test('admin can log in with valid credentials', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page.getByRole('heading', { name: 'Admin Dashboard' })).toBeVisible();
});
```

`fill()` waits for its target to be attached, visible, enabled, and editable before it clears the field and types the value. It will not silently fill a disabled or not-yet-rendered input. The `click()` on the login button waits through the same actionability checklist described in the overview lesson.

The assertion at the end is the part worth pausing on. It does not check that the login request returned a success status. It checks that the *page* now shows the admin's dashboard heading, polling until that becomes true. That is what "the test passed" should mean for a UI test: the user-visible outcome happened, not just that a network call didn't error.

### Step 2: `check`, Marking an Appointment Complete

Log in as a doctor first, then locate the appointment row and its checkbox:

```typescript title="tests/appointments.spec.ts"
import { test, expect } from '@playwright/test';

test('doctor can mark an appointment complete', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('dr.patel');
  await page.getByLabel('Password').fill('doctor123');
  await page.getByRole('button', { name: 'Log In' }).click();

  const appointmentRow = page.getByRole('row', { name: /Jane Doe/ });
  await appointmentRow.getByRole('checkbox', { name: 'Mark appointment complete' }).check();

  await expect(appointmentRow.getByRole('checkbox', { name: 'Mark appointment complete' })).toBeChecked();
  await expect(page.getByText('Appointment completed')).toBeVisible();
});
```

`check()` is a specialized action: it waits through the same actionability list as `click()`, but additionally verifies the element actually is a checkbox or radio input, and it's a no-op if the box is already checked. It will never double-toggle it back off. `toBeChecked()` is the web-first assertion that matches it: it polls the checkbox's checked state directly, rather than trusting that the click succeeded just because `check()` didn't throw.

The second assertion, `expect(page.getByText('Appointment completed')).toBeVisible()`, is the one doing the real work here. Checking the box triggers an API call to update the appointment's status, and the confirmation banner only renders after that call resolves. Because `toBeVisible()` retries, the test waits exactly as long as the real update takes, no more and no less.

### Step 3: `selectOption`, Filtering by Role

The admin dashboard's user list includes a role filter dropdown. Selecting an option should filter the visible rows:

```typescript title="tests/role-filter.spec.ts"
import { test, expect } from '@playwright/test';

test('admin can filter the user list by role', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.getByRole('combobox', { name: 'Filter by role' }).selectOption('Doctor');

  await expect(page.getByRole('row', { name: /Doctor/ }).first()).toBeVisible();
  await expect(page.getByRole('row', { name: /Patient/ })).toHaveCount(0);
});
```

`selectOption()` waits for the `select` element to be attached, visible, enabled, and, specific to this action, for the option value you're passing in to actually exist among its `option` children before it fires the native change event. You can pass a value, a label, or an index; matching by visible label (as above) reads best in a test and survives the underlying `value` attribute changing later.

`toHaveCount(0)` is worth calling out here as still web-first: it polls the number of matching elements until it equals zero, rather than reading the count once immediately after the dropdown changes, which would very likely still show the pre-filter row count, since the table re-render hasn't happened yet.

### Step 4: `uploadFile`, Attaching a Medical Record

A doctor uploading a scan or report to a patient's medical record uses a file input. Playwright's action for this is `setInputFiles()`, called through the locator:

```typescript title="tests/upload-record.spec.ts"
import { test, expect } from '@playwright/test';
import path from 'path';

test('doctor can attach a file to a medical record', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('dr.patel');
  await page.getByLabel('Password').fill('doctor123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.goto('/medical-records/new');
  await page.getByLabel('Attachment').setInputFiles(
    path.join(__dirname, 'fixtures', 'lab-result.pdf')
  );
  await page.getByRole('button', { name: 'Save Record' }).click();

  await expect(page.getByText('lab-result.pdf')).toBeVisible();
});
```

`setInputFiles()` doesn't simulate a user dragging a file through the OS file picker. It sets the input's file list directly through the browser's DevTools protocol, which is both faster and more reliable than trying to automate a native dialog. It still waits for the input element to be attached and enabled first. Note the assertion again: it checks that the uploaded file's name appears back in the page, confirming the round trip actually completed, not just that the button click didn't throw.

### Step 5: Web-First vs. Generic, Side by Side

To make the distinction concrete, here's the same check written both ways against the appointment-completion flow from Step 2:

```typescript title="generic: snapshots once, never retries"
// Reads the text immediately, then compares. If the confirmation
// hasn't rendered yet, this either throws or fails outright: it
// gets no second attempt.
const text = await page.getByText('Appointment completed').textContent();
expect(text).toBe('Appointment completed');
```

```typescript title="web-first: polls until it passes or times out"
// Polls the DOM for this condition, repeatedly, until it's true
// or the timeout elapses. Whether the confirmation takes 10ms or
// 900ms, this passes as soon as it's actually there.
await expect(page.getByText('Appointment completed')).toBeVisible();
```

Both lines look similar, but only one of them is safe to put immediately after an action that triggers a network request, which, in a real application, is most of them.

## How It Works Internally

Every web-first `expect(locator)` matcher shares one retrying implementation under the hood: Playwright resolves the locator against the current DOM, evaluates the specific condition (visibility, text content, checked state, count, whatever the matcher checks), and if it doesn't hold yet, waits a short interval and tries again. This repeats until the condition holds, at which point the assertion resolves immediately (it does not wait out the rest of the timeout), or until the timeout is reached, at which point it throws with a message describing the last observed state. That's why Playwright's assertion failures tend to be diagnosable without opening trace viewer.

Generic `expect(value)` from vanilla Jest-style assertion libraries has no locator to re-resolve and no DOM to re-query. By the time it runs, `value` is already a plain JavaScript value that was captured once. There is nothing for it to retry against, which is exactly why it should never sit directly downstream of an action in a UI test.
