# Actions and Web-First Assertions

⏱ 18 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Perform the five core Playwright actions — `click`, `fill`, `check`, `selectOption`, and `uploadFile` — against real forms and controls in the RBAC app
- Explain the actionability checks each action waits for automatically, before it ever touches the element
- Tell the difference between a web-first `expect(locator)` assertion and a generic `expect(value)` assertion, and know why that difference matters
- Explain why web-first assertions retry on a polling loop until timeout, while generic assertions snapshot once and never retry
- Replace `waitForTimeout` and hand-rolled polling loops with the correct auto-retrying assertion — for good

## Why This Matters

A locator finds an element, while an action actually does something to it — two different jobs, which is why Playwright treats them differently on purpose. `page.getByLabel('Username')` just describes where to look; it doesn't touch the page at all until you call `.fill()` on it. The moment you call an action, Playwright runs a short checklist against the real, live DOM before it does anything, and it keeps re-checking that list until every item passes or a timeout is hit.

This is the mechanism that makes Playwright tests reliable against a real application like the RBAC healthcare app, where the UI is genuinely asynchronous — a doctor's dashboard fetches appointments over the network, a role filter re-renders the table, a "Mark appointment complete" click triggers an API call before the UI updates. None of that happens instantly, and a test that assumes it does will be flaky roughly in proportion to how loaded the machine running it is.

The same idea extends to assertions. `expect(locator).toBeVisible()` doesn't check once — it polls, the same way an action does, until the condition is true or time runs out. `expect(value).toBe(...)` does the opposite: it reads whatever `value` already is, right now, and compares it exactly once. Knowing which one you're writing, and why, is the single most consequential habit this course can give you for avoiding flaky tests later.

## The Problem

Here's a test that looks reasonable and fails intermittently:

```typescript
await page.getByLabel('Username').fill('admin');
await page.getByLabel('Password').fill('admin123');
await page.getByRole('button', { name: 'Log In' }).click();

const message = await page.getByText('Appointment completed').textContent();
expect(message).toBe('Appointment completed');
```

The `click()` on the login button is fine — Playwright waits for it to be actionable. The problem is the last two lines. `.textContent()` reads whatever text is in that element the instant the line executes. If the "Mark appointment complete" click a moment earlier triggered an API call that hasn't resolved yet, the element might not contain "Appointment completed" yet — or might not exist yet at all — and `.textContent()` throws or returns something else. The test doesn't wait for the outcome of the click; it just checks whatever is there right now, once, and reports whatever it finds.

The fix isn't a longer timeout bolted on afterward — it's writing the assertion in a form that already knows how to wait.

## The Concept

Two separate waiting mechanisms are doing the real work in this module, and once you see it, you'll notice they both share the same underlying idea:

**Actionability checks (actions).** Before `click`, `fill`, `check`, `selectOption`, or `setInputFiles` (the method behind file-upload interactions) actually acts on an element, Playwright polls the element against a checklist specific to that action — commonly: attached to the DOM, visible, stable (not mid-animation), enabled, and able to receive events (nothing else is covering it). Only once every relevant check passes does the action fire. If a check keeps failing, the action keeps retrying the check until the default timeout, then throws a specific, readable error telling you which check never passed.

**Web-first assertions (`expect(locator)...`).** These take the same polling idea and apply it to a condition you want to become true, such as `toBeVisible()`, `toHaveText(...)`, or `toBeChecked()`. The assertion re-evaluates the condition against the live DOM repeatedly until it passes or the timeout elapses. This is why `await expect(page.getByText('Appointment completed')).toBeVisible()` succeeds correctly whether the confirmation message renders in 10 milliseconds or 900 — the assertion is still polling at 900ms, whereas a generic `expect(value).toBe(...)` had already read and judged its one snapshot long before that.

The practical rule that falls out of this: whenever the thing you're checking lives in the page — text, visibility, a checkbox's checked state, an input's value — assert on the locator, not on a value you pulled out of it a moment earlier. Pulling the value out first is exactly what throws away the retry behavior you wanted.
