# Actions and Web-First Assertions: Review

⏱ 4 minutes

## Key Takeaways

- Actions, `click`, `fill`, `check`, `selectOption`, and `setInputFiles` (the file-upload action), all wait through an actionability checklist (attached, visible, stable, enabled, receives events) before they ever touch the element, which is exactly what keeps you from clicking something that isn't actually ready yet.
- `expect(locator)...` assertions are web-first, meaning they poll the live DOM, re-evaluating the condition repeatedly until it's true or the timeout elapses. That's what lets `await expect(page.getByText('Appointment completed')).toBeVisible()` pass correctly whether the confirmation takes 10ms or 900ms.
- `expect(value)` is generic: it reads and compares once, with no DOM to re-query and nothing to retry against, so it's correct for values your test computed itself but wrong for anything just read off the page.
- `waitForTimeout` and hand-rolled polling loops are always the wrong fix for a flaky assertion after an action, because they either waste time waiting out a worst case that never happened, or fail anyway once the real wait exceeds the fixed guess. A web-first assertion replaces both, and does it better.
- Every action with a visible outcome needs a web-first assertion on that outcome afterward, since an action that doesn't throw only proves the interaction was possible, not that it actually produced the result you expected.

## Recap in 60 Seconds

If you only remember three things:

1. Actions poll for actionability before acting, and web-first `expect(locator)` assertions poll a condition on the live page until it's true or it times out. Both retry, by design.
2. Generic `expect(value)` snapshots once and never retries, so use it only on values that never touched the DOM, never on something you just read off the page.
3. Delete every `waitForTimeout` and hand-rolled polling loop you find and replace it with the matching web-first assertion instead. It's shorter, better-tuned, and gives you a useful failure message instead of a guess.

## Try It

Extend the role-filter test from [Build It](./build-it) to cover the nurse role. Log in as a nurse, open the appointment-scheduling view, and use `selectOption` to select a patient from a dropdown before scheduling an appointment. Then assert the outcome two ways, so you can see the difference for yourself: first with `await expect(page.getByText('Appointment scheduled')).toBeVisible()`, and then rewrite that same check as a generic `expect(value).toBe(...)` using `.textContent()` first. Run both versions several times in a row (`npx playwright test --repeat-each=5`) and compare how each one behaves under repeated runs.
