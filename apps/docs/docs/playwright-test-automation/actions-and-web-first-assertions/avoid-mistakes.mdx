# Actions and Web-First Assertions: Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Web-first assertions cover the overwhelming majority of what a UI test needs to check: visibility, text, checked state, counts, attribute values, basically anything the live DOM can show you. But they're not the right tool for asserting on things that never touched the DOM at all, like a value your test computed itself, the shape of a JSON body your test fetched directly through `request.get()`, or a plain TypeScript object you built as test data. For those, a generic `expect(value)` is the correct choice, and there's nothing to retry, because the value already exists in full, once, and re-checking it wouldn't change anything. So the mistake was never "using generic assertions" in general. It's using one on something that came out of the page.

## The Pattern to Remember

- **Pattern:** actions wait until they're actionable before they act, and web-first assertions do the same thing to a condition instead, polling the live page until it's true or the timeout runs out.
- **When to use:** for any check on something rendered in the browser, such as text, visibility, checked state, option selection, or element count.
- **When NOT to use generic `expect(value)`:** on anything you just pulled straight off the page. It's still fine for values your test computed or fetched itself, outside the page entirely.
- **Mental model:** an action is a persistent knock on a door that only opens once the room behind it is actually ready. A web-first assertion is that same persistent knock, just applied to a question instead of an interaction. A generic assertion, by contrast, is a single glance through a window that never happens twice.

## Common Mistakes

### Mistake 1: Reaching for `waitForTimeout` After an Action

**Mistake:**

```typescript
await page.getByRole('checkbox', { name: 'Mark appointment complete' }).check();
await page.waitForTimeout(2000);
await expect(page.getByText('Appointment completed')).toBeVisible();
```

**Why it happens:** the confirmation banner didn't appear immediately in a quick manual test, so a fixed delay "fixed" it, and the test passed that time.

**Symptoms:** the test is fast and green on your machine, then flakes in CI, where the backend response for the appointment update sometimes takes longer than 2000ms under load. Worse, the test is now unconditionally 2 seconds slower even on the runs where the banner appeared in 50ms. The sleep charges you the worst case every single time, not just when it's needed.

**Fix:** delete the `waitForTimeout` line entirely. `expect(page.getByText('Appointment completed')).toBeVisible()` already retries until the banner appears or the assertion's own timeout is hit. It needs no help, and adding a sleep in front of it only adds latency without adding reliability.

### Mistake 2: Reading a Value Before Asserting On It

**Mistake:**

```typescript
const text = await page.getByText('Appointment completed').textContent();
expect(text).toBe('Appointment completed');
```

**Why it happens:** it reads naturally as two separate steps, "get the text, then check it," and it's exactly how you'd write a unit test assertion on a plain string.

**Symptoms:** intermittent failures, always under load or on a slower CI runner, and always on the `textContent()` line: either it throws because the element doesn't exist yet, or it returns an empty string because the element exists but hasn't received its text yet. The failure message rarely mentions timing, so it looks like a locator bug.

**Fix:** assert on the locator directly, `await expect(page.getByText('Appointment completed')).toBeVisible()`, or `toHaveText('Appointment completed')` if you need the exact string. Never separate "read from the page" and "check what you read" into two lines when the value in question lives in the DOM.

### Mistake 3: Hand-Rolling a Polling Loop

**Mistake:**

```typescript
let visible = false;
for (let i = 0; i < 10; i++) {
  visible = await page.getByText('Appointment completed').isVisible();
  if (visible) break;
  await page.waitForTimeout(500);
}
expect(visible).toBe(true);
```

**Why it happens:** it feels like it's "doing the right thing," retrying instead of checking once, without realizing Playwright already has a purpose-built, better-tuned version of exactly this behind `expect(locator).toBeVisible()`.

**Symptoms:** it works, but it's five lines standing in for one, it re-implements retry timing worse than the built-in version (fixed 500ms steps instead of Playwright's tuned polling interval), it produces a useless failure message (`expected false to be true` tells you nothing about what the element actually looked like), and it doesn't show up correctly in trace viewer the way a native assertion does.

**Fix:** `await expect(page.getByText('Appointment completed')).toBeVisible();`. If you find yourself writing a loop with `isVisible()`, `isChecked()`, or similar polled inside it, stop. There is almost certainly a web-first matcher that already does exactly that.

### Mistake 4: Calling an Action Instead of Asserting Its Outcome

**Mistake:**

```typescript
await page.getByRole('checkbox', { name: 'Mark appointment complete' }).check();
// test ends here, with no assertion at all
```

**Why it happens:** `check()` didn't throw, so the assumption is that it must have worked. Actionability checks confirm the checkbox was clickable. They say nothing about what happened afterward, like whether the backend actually persisted the change or a validation error silently rolled it back.

**Symptoms:** the test passes even when the appointment's status update fails server-side, because nothing in the test ever looked at the outcome, only at whether the interaction itself was physically possible.

**Fix:** every action that's supposed to produce a visible outcome needs a web-first assertion on that outcome afterward: `toBeChecked()` on the checkbox itself, and/or `toBeVisible()` on whatever confirms the change took effect. An action without a following assertion is a click into the void.

### Mistake 5: Using a Generic Assertion on Something the Page Rendered

**Mistake:**

```typescript
const options = await page.getByRole('combobox', { name: 'Filter by role' })
  .locator('option')
  .allTextContents();
expect(options).toContain('Doctor');
```

**Why it happens:** `allTextContents()` returns a plain array, and arrays feel natural to check with a generic matcher like `toContain`, so the retry problem doesn't feel obviously present the way a single string does.

**Symptoms:** flakes specifically on a slower load of the role-filter dropdown, if its options are populated by a request rather than baked into the initial HTML. The array is captured before the options exist, and `expect(options)` never gets a second look at the (by-then-correct) DOM.

**Fix:** where a web-first equivalent exists, prefer it: `await expect(page.getByRole('combobox', { name: 'Filter by role' }).locator('option')).toHaveText(['Admin', 'Doctor', 'Nurse', 'Patient'])` retries the whole comparison against the live DOM. Reach for `allTextContents()` plus a generic assertion only once you've already confirmed, with a web-first assertion, that the element is in its final state, for example, asserting `toHaveCount(4)` on the options first.
