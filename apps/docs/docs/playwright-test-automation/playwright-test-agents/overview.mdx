# Playwright Test Agents: Planner, Generator, Healer

⏱ 20 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Explain what `npx playwright init-agents` sets up, and what each of the three built-in agents (Planner, Generator, Healer) is responsible for
- Run the agent workflow against a real RBAC flow: a patient booking an appointment, verified from the doctor's side
- Read a Planner's plan critically, checking its assumptions against what you already know about the app instead of accepting it as fact
- Read a Generator's draft spec critically, checking locator quality, assertion correctness, and for hardcoded waits before it goes anywhere near your suite
- State, precisely, why agent output is a first draft and not a merge-ready pull request

## Why This Matters

Every module up to this one has been classical, scripted automation: you decide what to test, you write the locator, you write the assertion, and the same script does the same thing on every run. That assumption doesn't disappear starting here, but the *authorship* of the first draft can now come from somewhere else. Playwright ships three built-in agents (Planner, Generator, and Healer) that turn a plain-language goal into a test plan, turn that plan into a draft spec file, and repair a spec that breaks against a changed DOM. This is a genuine capability shift, not a rebrand of `codegen`: the input is a goal, not a recorded click stream, and the output is meant to be read as a draft, not accepted as-is.

Stay grounded about what that means. None of these agents understands your app's business rules the way you do. A Planner doesn't know the RBAC healthcare app's permission matrix unless you tell it or it happens to discover the relevant behavior while exploring the app. A Generator writes code that runs without throwing, which is a much lower bar than code that asserts the right thing. A Healer's job, mechanically, is to make a red test green again, and green is not the same claim as correct. The rest of this course's discipline (locator quality, web-first assertions, no hardcoded waits) doesn't get suspended because an agent wrote the first draft. It becomes the checklist you run the draft through before it's allowed to become your test.

## The Problem

Say you want a test proving that when a patient books an appointment, it shows up on the assigned doctor's side. Writing this by hand means: log in as a patient, find the booking form, fill it out, submit it, log in as the doctor, find the right dashboard, and assert the new entry is there. That's five or six UI surfaces you have to locate and script yourself, most of which you've never opened before if this is a part of the app you haven't tested yet.

Ask a Planner for a plan instead, and you get a numbered sequence of steps for that exact flow in a few seconds, assuming, provisionally, that its steps are correct. Ask a Generator to turn that plan into a spec, and you get a file with locators and assertions already written, assuming, provisionally, that the locators are the right kind and the assertions check the right thing. Both of those assumptions need to be checked, not trusted, and that's the actual subject of this lesson: not "how to run the agents," which is a few commands, but "what to verify before you accept what they produced," which is where the real work is.

## The Concept

Here's how the work splits across the three agents, each with a distinct job, always run in the same fixed order:

- **Planner** takes a goal stated in plain language ("as a patient, book an appointment with a doctor, and verify it appears on the doctor's dashboard") and produces a test plan: a numbered sequence of steps describing what a test should do, generally by exploring the running app to see what's actually there. A plan is not code. It's closer to a written test case a human QA engineer might hand off to be automated.
- **Generator** takes that plan and writes an actual `.spec.ts` file: real locators, real actions, real `expect()` calls, following the plan's steps as far as it can map them onto the running app. This is the first point where you have working code, and also the first point where the three review questions in this lesson's Build It apply: locator quality, assertion correctness, hardcoded waits.
- **Healer** takes an already-existing, already-failing spec and the current state of the app, and proposes a diff that makes the test pass again, typically because a locator no longer resolves the way it used to. Healer is out of scope for how deep this lesson goes; the self-healing tests lesson, [Self-Healing Tests and AI-Assisted Maintenance](../self-healing-tests/overview), is where the guardrails around it get the full treatment. This lesson only takes you far enough to run it once and see what a repair diff looks like.

The exact commands, flags, and terminal output for these three agents are still evolving as Playwright ships new releases. This lesson describes the shape of the workflow and the review discipline it demands, not a transcript of one specific version's CLI output. Run `npx playwright init-agents --help` against whatever version you have installed to see the current options before following Build It literally.
