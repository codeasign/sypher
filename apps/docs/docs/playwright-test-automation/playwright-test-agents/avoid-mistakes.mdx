# Playwright Test Agents — Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Test agents earn their keep when you're facing a flow you haven't automated yet and don't want to hand-locate every element yourself — think new coverage, an unfamiliar part of the app, or a quick exploratory pass. They're the wrong tool when you already know the exact flow, the locators, and the assertions you want: writing `page.getByRole(...)` yourself for a flow you've already got memorized is faster than describing it in prose, waiting on a plan and a draft, and then reviewing both. Reach for an agent to produce a first draft of something new; write it by hand when the "draft" step would take longer than just writing the real thing. And never reach for these agents as your CI execution mechanism — Planner, Generator, and Healer are authoring and maintenance tools you run locally, reviewing their output before it's committed; `npx playwright test` running your already-reviewed, already-committed suite is what actually executes in CI.

## The Pattern to Remember

- **Pattern:** the goal goes to the Planner, the plan goes to the Generator, and the draft has to pass a fixed review checklist — locator quality, assertion correctness, no hardcoded waits — before it becomes a committed test.
- **When to use:** new coverage for a flow you haven't automated yet, or a quick exploratory pass over unfamiliar UI.
- **When NOT to use:** a flow you can already locate and assert on quickly by hand, or anything you're tempted to run as your CI execution step instead of a pre-committed, reviewed spec.
- **Mental model:** a Planner and a Generator are a fast, capable junior engineer's first pass at a ticket — worth having, never worth merging unreviewed, because "it ran without an error" and "it does what the ticket asked" are two different claims, and only a human reliably checks the second one.

## Common Mistakes

### Mistake 1: Merging Generator Output Without Checking Locator Quality

**Mistake:** Taking a Generator's draft spec, seeing it pass locally, and committing it as-is — including whatever CSS selectors (`#doctor-select`, `.submit-btn`) it happened to write.

**Why it happens:** The draft runs, the assertions (however weak) pass, and reviewing every single locator feels like re-doing work the agent just did.

**Symptoms:** The very next time someone touches the booking form's markup — a class name gets renamed as part of an unrelated styling pass — every test built on that draft breaks, for a reason that has nothing to do with the booking flow actually changing. This is precisely the fragility the locators lesson spends its whole time establishing, reintroduced by generation instead of by a human's first instinct to right-click and copy a selector.

**Fix:** Run every locator in a Generator's draft against the locators lesson's priority order before committing anything — `getByRole` and `getByLabel` first, CSS last and only as a deliberate, justified fallback. Treat a CSS locator in generated output exactly as skeptically as one you'd write yourself.

### Mistake 2: Accepting an Assertion That Only Proves the Page Didn't Crash

**Mistake:** Leaving a Generator's assertion as something like `expect(await page.title()).toContain('Dashboard')` because the test goes green and the goal was, loosely, "get to the dashboard."

**Why it happens:** A weak assertion and a strong one both make the test pass on a working app, so nothing about a green run tells you which one you're looking at — the gap only shows up when the app actually breaks and the test doesn't notice.

**Symptoms:** A real regression — the booked appointment silently fails to save, or appears under the wrong doctor — ships with this spec fully green, because nothing in it ever checked the appointment itself, only that some page with "Dashboard" in its title loaded.

**Fix:** Trace every assertion back to the original goal and ask what it would take for this exact assertion to fail if the feature were actually broken. For "verify the appointment appears on the doctor's dashboard," that means asserting on the specific row, tied to the specific patient, with the specific status — not a generic page-level check.

### Mistake 3: Leaving `waitForTimeout` in Because "the Generator Wrote It"

**Mistake:** Keeping `await page.waitForTimeout(2000)` calls in a committed spec because they were already there in the Generator's draft and the test passed with them in.

**Why it happens:** The actions-and-web-first-assertions lesson frames hardcoded waits as a mistake you reach for yourself under time pressure — it's easy to forget the same anti-pattern shows up just as often in generated code, arguably more often, since nothing about generation enforces the review discipline a human might apply out of habit.

**Symptoms:** Exactly the same failure mode that lesson describes — a suite that's slower than it needs to be on every run, and still flaky in CI whenever the real condition (a network response, a DOM update) takes longer than the fixed sleep assumed.

**Fix:** Search every Generator draft for `waitForTimeout` before anything else — it's the fastest single check in the whole review — and delete every instance, replacing it with a web-first `expect(locator)...` on whatever the wait was actually standing in for, exactly as that lesson teaches for hand-written tests.

### Mistake 4: Trusting the Planner's Plan as Ground Truth for RBAC Behavior

**Mistake:** Accepting a Planner's plan step like "confirm the appointment appears as scheduled on the doctor's dashboard" at face value, without checking it against the RBAC permission-matrix lesson's permission matrix, which lists scheduling as a nurse-only action.

**Why it happens:** A plan reads like a confident, complete description of how the app behaves, because it's written in the same numbered, procedural voice a human test case would use — nothing about its phrasing signals that it might be guessing at a detail the agent never actually confirmed.

**Symptoms:** A Generator turns an unverified plan step directly into an assertion, and the resulting test either asserts something the app doesn't actually do (and fails for a confusing reason later), or — worse — happens to pass by accident against a status the app returns for the wrong reason, giving you false confidence in a claim nobody actually checked.

**Fix:** Before a plan reaches the Generator, check any step involving role-specific behavior against what you already know from the RBAC permission-matrix lesson's matrix. If the plan and the matrix disagree, that's exactly the moment to go confirm the actual behavior against the running app yourself — not to silently trust whichever source sounds more authoritative.

### Mistake 5: Skipping Review on a Healer's Diff Because the Test Went Green

**Mistake:** Running the Healer on a failing spec, seeing the test pass afterward, and merging the diff without reading what actually changed.

**Why it happens:** A green test after a red one feels like confirmation the fix was correct — the same instinct that makes "it works now" feel like a complete answer, even though "it works" and "it works for the right reason" are different claims.

**Symptoms:** A diff that quietly changed what an assertion expects, rather than just how a locator finds an element, gets merged unread — which is the exact failure mode the self-healing tests lesson is built around, and the reason this module ends with a rule rather than a shortcut: read every healed diff, every time, before it merges.

**Fix:** Apply the same rule you already used on Generator output — check what actually changed, not just whether the test is green afterward. A locator-only diff is low-risk; anything touching an assertion's expected value needs a human asking whether the app changed or the test's ability to catch a bug just got quietly removed. The self-healing tests lesson covers this distinction in full.
