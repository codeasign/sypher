# Playwright Test Agents — Hands On

⏱ 28 minutes

## Breaking It Down

### Step 1: Install the Agents

From the root of your forked `rbac-healthcare-system` repo, with Playwright already installed from Setup:

```bash
npx playwright init-agents
```

What this scaffolds — the exact files, prompts, and directory it writes to — depends on which version of Playwright you have installed and which AI coding assistant you tell it to target. In practice, expect it to ask (or accept a flag) for which client you're integrating with — GitHub Copilot Chat, Claude Code, or another MCP-capable assistant — and to write back a set of agent definitions for that client to pick up: one each for Planner, Generator, and Healer. Run it with `--help` first:

```bash
npx playwright init-agents --help
```

Treat whatever prompt sequence or output you actually see as authoritative for your version, not this page. The three agents' jobs — plan, generate, heal — are stable across versions even when the exact scaffolding mechanics aren't.

### Step 2: Give the Planner a Goal

From your AI coding assistant, invoke the Planner agent with a plain-language goal describing the flow you want tested:

```text
As a patient, book an appointment with a doctor.
Verify the appointment appears on the doctor's side.
```

The Planner explores the running app — the login screen, the patient dashboard, whatever booking flow exists — and comes back with a numbered plan. A plan you get back for this goal will look something like this in shape, even if the exact wording differs:

```text title="Planner output — a plan, not code"
1. Log in as a seeded patient account (patient1 / patient123).
2. From the patient dashboard, open the appointment booking flow.
3. Select a doctor and an available time slot.
4. Submit the booking.
5. Confirm the UI acknowledges the submission.
6. Log in as the doctor tied to that booking.
7. Confirm the new appointment appears on the doctor's dashboard.
```

Before this goes anywhere near the Generator, read it against what you already know from earlier in this course — specifically the RBAC permission matrix, which lists scheduling appointments as a nurse-only action, not a patient one. That doesn't necessarily mean the plan above is wrong: a patient-facing "book an appointment" flow and a nurse-facing "schedule an appointment" action can reasonably be two different things in the same app — a patient's booking might land as a pending request that a nurse then formally schedules, rather than appearing already-scheduled the instant the patient submits it. What it does mean is that step 7's exact claim — "appears on the doctor's dashboard" — needs to be checked against the app's actual behavior, not assumed from the plan's wording. This is the first review checkpoint, and it happens before you've generated a single line of test code: does the plan's account of the app's behavior match what the RBAC permission-matrix lesson already taught you about who can do what?

### Step 3: Hand the Plan to the Generator

With the plan reviewed, hand it to the Generator agent, which turns it into an actual spec file. A first draft for this plan will look something like this — every issue called out below is deliberate, because this is what unreviewed Generator output tends to contain:

```typescript title="tests/generated/patient-books-appointment.spec.ts — Generator draft, before review"
import { test, expect } from '@playwright/test';

test('patient books an appointment', async ({ page }) => {
  await page.goto('/login');
  await page.locator('#username').fill('patient1');
  await page.locator('#password').fill('patient123');
  await page.locator('.login-btn').click();

  await page.waitForTimeout(2000);

  await page.locator('.book-appointment-btn').click();
  await page.selectOption('#doctor-select', { label: 'Dr. Amina Yusuf' });
  await page.locator('#slot-2026-08-03-10-00').click();
  await page.locator('.submit-btn').click();

  await page.waitForTimeout(3000);

  expect(await page.title()).toContain('Dashboard');
});
```

Don't commit this. Three separate problems are visible in it, and none of them are unusual for a first Generator pass — they're the exact three things this course has been building the muscle to catch since the locators lesson and the actions-and-web-first-assertions lesson.

### Step 4: Review the Draft — Locator Quality

Every locator in the draft is a CSS selector: `#username`, `.login-btn`, `.book-appointment-btn`, `#doctor-select`, `#slot-2026-08-03-10-00`, `.submit-btn`. None of these describe what a user perceives — a labeled field, a named button — they describe today's class names and IDs. The locators lesson covers exactly why this is fragile: a designer renames a CSS class or a build tool hashes it differently, and every one of these locators breaks despite nothing about the app's actual behavior changing.

The fix is to replace each one with the role- or label-based equivalent the locators lesson ranks above it, checking against the app's real accessibility tree (open the login form and the booking flow yourself, or use `codegen`, to confirm the actual roles and labels — don't guess):

```typescript title="fixed locators"
await page.getByLabel('Username').fill('patient1');
await page.getByLabel('Password').fill('patient123');
await page.getByRole('button', { name: 'Log In' }).click();

await page.getByRole('button', { name: 'Book Appointment' }).click();
await page.getByLabel('Doctor').selectOption('Dr. Amina Yusuf');
await page.getByRole('button', { name: 'Aug 3, 10:00 AM' }).click();
await page.getByRole('button', { name: 'Submit Request' }).click();
```

### Step 5: Review the Draft — Assertion Correctness

The draft's only assertion is `expect(await page.title()).toContain('Dashboard')`. This proves almost nothing about the actual goal. It would pass if the booking silently failed and the page merely redirected somewhere with "Dashboard" in its title. It says nothing about whether the appointment was created, nothing about which doctor it's tied to, and nothing about whether it's visible from the doctor's side at all — which is the entire point of the test, per the original goal. This is the "page didn't crash" trap: a Generator can produce code that runs cleanly and asserts almost nothing, and a passing test built on it tells you almost nothing.

The fix is to assert on the actual claim: that the specific appointment the patient created is visible, correctly, when the doctor looks:

```typescript title="a real assertion on the actual goal"
await expect(page.getByText('Appointment requested')).toBeVisible();
```

and, on the doctor's side, an assertion tied to the specific patient and appointment, not a generic page check:

```typescript title="the assertion that actually proves the goal"
await expect(
  doctorPage.getByRole('row').filter({ hasText: 'patient1' })
).toContainText('Pending');
```

`Pending` here reflects Step 2's review checkpoint: if a patient's booking lands as a request rather than an already-scheduled slot, the assertion should say so, not claim a status the app doesn't actually produce. Confirm the real status text against the running app before locking in the exact string.

### Step 6: Review the Draft — Hardcoded Waits

Both `waitForTimeout` calls in the draft are exactly the anti-pattern the actions-and-web-first-assertions lesson covers: a fixed delay standing in for the thing you actually want, which is a condition becoming true. Delete both. The corrected version needs no replacement wait at all — that lesson's web-first assertions already retry until the condition holds or their own timeout elapses, which is a better mechanism than any fixed sleep a Generator might insert:

```typescript title="no wait needed — the assertion itself retries"
await page.getByRole('button', { name: 'Log In' }).click();
await expect(page.getByRole('heading', { name: 'Patient Dashboard' })).toBeVisible();
```

If you ever see a `waitForTimeout` in Generator output, read it as a signal that the Generator didn't have (or didn't use) a reliable condition to wait on — delete it and replace it with a web-first assertion on whatever the wait was actually standing in for, the same way you would for a hand-written test.

### Step 7: The Reviewed Spec, End to End

Putting Steps 4 through 6 together, reusing the `getPageAs` role fixture from the authentication lesson and the RBAC permission-matrix lesson instead of the draft's raw `page` fixture, gives you the version that's actually fit to commit:

```typescript title="tests/rbac-patient-books-appointment.spec.ts — after review"
import { test, expect } from './fixtures/role-page';

test('patient booking appears as a pending appointment on the doctor dashboard', async ({ getPageAs }) => {
  const patientPage = await getPageAs('patient');
  await patientPage.goto('/dashboard');
  await patientPage.getByRole('button', { name: 'Book Appointment' }).click();

  await patientPage.getByLabel('Doctor').selectOption('Dr. Amina Yusuf');
  await patientPage.getByRole('button', { name: 'Aug 3, 10:00 AM' }).click();
  await patientPage.getByRole('button', { name: 'Submit Request' }).click();

  await expect(patientPage.getByText('Appointment requested')).toBeVisible();

  const doctorPage = await getPageAs('doctor');
  await doctorPage.goto('/dashboard');

  await expect(
    doctorPage.getByRole('row').filter({ hasText: 'patient1' })
  ).toContainText('Pending');
});
```

Every locator is role- or label-based, both assertions check the actual claim from the original goal, and nothing in the file waits on a clock instead of a condition. This is the version that goes into your suite — not the Generator's first pass.

### Step 8: Run the Healer Once, on Purpose

To see what a repair diff actually looks like — the self-healing tests lesson depends on you having done this at least once — deliberately break the committed spec. Rename the button in the frontend from "Book Appointment" to "Request Appointment" (or simulate the rename by editing your local copy of the component), then run the suite:

```bash
npx playwright test tests/rbac-patient-books-appointment.spec.ts
```

It fails: `getByRole('button', { name: 'Book Appointment' })` no longer resolves to anything, because that accessible name no longer exists on the page. Invoke the Healer agent against this failing spec. What it should propose, for a rename like this, is a narrow, single-line diff:

```diff
- await patientPage.getByRole('button', { name: 'Book Appointment' }).click();
+ await patientPage.getByRole('button', { name: 'Request Appointment' }).click();
```

Read the diff before accepting it. A locator-only change like this one, where the underlying element still does the same thing under a new name, is the case a Healer is built for. If a proposed diff ever touches what an assertion expects rather than just how a locator finds something, stop — that is a different, higher-risk situation, and the self-healing tests lesson is where you learn to tell the two apart in detail.

## How It Works Internally

Planner and Generator both work by combining an LLM with access to the running app — typically the same kind of accessibility-tree inspection Playwright's own trace viewer and `codegen` already use, rather than reading raw pixels. That's why a Planner can propose steps against a page it's never seen a script for: it's looking at the same structured view of the page a screen reader would use, which is also exactly why the locators lesson's locator priority order matters even to the agents themselves — role- and label-based locators are closer to what the agent actually inspected to write the plan in the first place. Neither agent has your app's business rules as separate input unless you supply them; what they know about "who can do what" is limited to whatever the running app's UI reveals or whatever you tell them directly in the goal. Healer works the same way in reverse: it re-runs the failing test, inspects the current accessibility tree at the point of failure, diffs it against what the stale locator or assertion expected, and proposes the smallest change that reconciles the two — a mechanism with no independent way to know whether reconciling them is actually the right thing to do, which is precisely why every proposal from it gets read, not trusted.
