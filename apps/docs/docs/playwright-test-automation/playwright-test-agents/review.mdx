# Playwright Test Agents — Review

⏱ 5 minutes

## Key Takeaways

- `npx playwright init-agents` scaffolds three built-in agents — Planner, Generator, Healer — each with a distinct job: Planner turns a plain-language goal into a numbered plan, Generator turns that plan into a draft spec file, and Healer repairs an already-committed test that's failing against the current DOM.
- A Planner's plan is a starting point, not ground truth about your app — check any role-specific behavior it describes against what you already know from the RBAC permission-matrix lesson before it reaches the Generator.
- A Generator's draft spec needs the same three checks every time before it's fit to commit: are the locators role- or label-based rather than brittle CSS (covered in the locators lesson), does every assertion check the actual claim rather than just confirming the page didn't crash, and has every `waitForTimeout` been found and deleted (covered in the actions-and-web-first-assertions lesson).
- Generated code that runs without throwing and generated code that correctly tests your feature are two different claims — a passing test built on a weak assertion or a stale wait tells you far less than it appears to.
- A Healer's repair diff gets read before it merges, exactly like a Generator's draft — a locator-only change is low-risk, but any change to what an assertion expects needs a human, a rule the self-healing tests lesson covers in full.

## Recap in 60 Seconds

1. Planner writes a plan, Generator writes a draft spec from that plan, Healer repairs an already-failing committed spec — three agents, three distinct jobs, none of them merge-ready on their own.
2. Every Generator draft gets the same review before it's committed: role-based locators over CSS, assertions that check the real claim, and zero hardcoded waits.
3. Agent output — plans, drafts, and healed diffs alike — is a first draft you read and correct, never a pull request you wave through because it happened to run green.

## Try It

Pick a different flow from the RBAC app and run the full workflow on it yourself: as a nurse, cancel an appointment, and verify it disappears from the patient's upcoming-appointments list. Work through these four steps:

1. Write the goal in plain language and, if you have an agent set up, hand it to the Planner. If you don't, write the plan yourself in the same numbered-step style Build It showed, and deliberately check any step touching role permissions against the RBAC permission-matrix lesson's matrix before moving on.
2. Draft (or generate) the spec, then run it through the three checks from this module: locator quality, assertion correctness, hardcoded waits. Note every issue you find, even in a hand-drafted version — the checklist doesn't only apply to agent output.
3. Reuse the `getPageAs` fixture from the authentication lesson and the RBAC permission-matrix lesson so the reviewed version authenticates as nurse and patient the same way this lesson's example did.
4. Deliberately rename one locator's accessible name in your local frontend copy, break the test, and — if you have a Healer available — run it once and read the diff it proposes before deciding whether to accept it.
