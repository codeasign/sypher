# Parallelism, Sharding, and Test Isolation — Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Per-worker database isolation isn't something every suite needs, so it's worth knowing when to skip it. Take a handful of read-only specs — say, checking that the Swagger docs load, or that the login page renders its fields — they never write anything, so there's nothing for them to collide on no matter how many workers touch them, which means isolating them just adds startup cost for no real benefit. It's also not the first thing to reach for if your suite is still small enough to run comfortably on a single worker in CI: `workers: 1` is a perfectly legitimate, boring fix while a suite is young, and you can put off building fixture-level isolation until parallelism is actually slow enough to make the plumbing worth it. Once your suite is both parallel and writing shared state — appointments, patients, medical records — that's when it's time to reach for the pattern in this lesson, which for this course starts around the RBAC permission-matrix tests.

## The Pattern to Remember

- **Pattern:** give every worker its own backend process and its own copy of the seeded SQLite file, addressed by `workerInfo.workerIndex`, so nothing two workers write can ever land in the same file.
- **When to use:** any suite where `fullyParallel` (or CI `workers > 1`) runs specs that create, update, or delete rows the RBAC app's other specs also read or write.
- **When NOT to use:** small, read-only, or already single-worker suites — as covered above.
- **Mental model:** think of workers as roommates who each believe they have the apartment to themselves. Browser contexts are their own bedrooms — genuinely private. The database, though, is the shared kitchen. Give each roommate their own kitchen (a file copy) rather than asking them to take turns and never bump into each other, because sooner or later, they will.

## Common Mistakes

### Mistake 1: Assuming Worker Isolation Covers the Database Too

**Mistake:** You read that Playwright test contexts are fully isolated and assume that means the whole worker — including whatever backend and database it talks to — must be isolated in the same way.

**Why it happens:** [Why Playwright, and How It Differs](../why-playwright/overview) genuinely does promise per-test browser context isolation, and it's an easy promise to round up from "the browser is isolated" to "everything is isolated."

**Symptoms:** Specs that pass reliably on their own start failing intermittently under `--workers=4`, with no exception that points at your test code — because your test code isn't the problem, the shared SQLite file underneath it is.

**Fix:** Treat browser-context isolation and database isolation as two separate guarantees. Playwright hands you the first one for free. The second one, you have to build yourself, as shown in [Build It](./build-it).

### Mistake 2: Reaching for Transactional Rollback Against a Live HTTP Backend

**Mistake:** You try to wrap a Playwright test in a database transaction and roll it back afterward, the same way you might in an in-process API test suite.

**Why it happens:** Transactional rollback is such a well-known pattern from backend testing that it seems like it should transfer over directly.

**Symptoms:** Either the rollback code has nothing to attach to — your test file has no open connection to the SUT's database, the Express process does — or, if you force the issue by having the backend hold a transaction open across requests, unrelated requests from other workers start blocking on that held-open lock, and your "isolation" fix becomes a new source of hangs.

**Fix:** Save transactional rollback for tests that call the database layer in-process, in the same Node process as the test — that's the shape of testing this course's companion `supertest-api-testing` course uses. For a full end-to-end Playwright test driving a browser against a separately running server, reach for per-worker file copies instead (Build It, Steps 2 to 4).

### Mistake 3: Binding Every Per-Worker Backend to the Same Port

**Mistake:** You spawn a backend process per worker but leave `PORT` hardcoded to `5000` in the spawn call, instead of deriving it from `workerInfo.workerIndex`.

**Why it happens:** `:5000` is the port every earlier module in this course has used, so it's the natural value to paste in without giving it a second thought.

**Symptoms:** The first worker's backend starts up fine, but every other worker's `npm start` crashes immediately with an `EADDRINUSE` error — and the test run either hangs waiting for a "Server running" message that never arrives, or fails with connection-refused errors that look, misleadingly, like a frontend problem.

**Fix:** Derive the port from the worker index, as in Step 3 (`5000 + workerInfo.workerIndex + 1`), so every worker running concurrently binds a port nothing else is using.

### Mistake 4: Treating `--shard` as a Fix for Flaky Shared State

**Mistake:** You split a flaky suite across CI shards, notice individual jobs failing less often because each one now runs fewer files, and conclude that sharding solved the isolation problem.

**Why it happens:** Fewer tests per job really does statistically reduce how often two colliding specs land in the same job at the same time, so the flake rate visibly drops — just not to zero, and not for the reason it looks like.

**Symptoms:** The flake comes back, seemingly at random, whenever two colliding specs happen to land in the same shard together, or whenever that shard's own `workers` setting gets increased. It's exactly as intermittent as before, just rarer.

**Fix:** Sharding decides which files a machine runs; it has nothing to say about whether those files are safe to run concurrently once they're there. Fix the underlying database collision first (Build It, Steps 2 to 4) — sharding is a throughput tool you add on top of an already-isolated suite, not a substitute for isolating it.

### Mistake 5: Reusing One Seeded Copy Across All Workers

**Mistake:** You copy the seeded SQLite file once, before the run starts, and point every worker's backend at that same single copy — instead of copying it once per worker.

**Why it happens:** It looks like isolation was achieved, since the copy step ran and nothing threw an error; the real mistake is copying too early and too few times, not skipping the copy altogether.

**Symptoms:** You get the exact same collision as Step 1 of Build It, just against a copy instead of the original file — because a copy that every worker shares is still just one shared file to every worker writing to it.

**Fix:** Do the copy inside the worker-scoped fixture, keyed by `workerInfo.workerIndex`, so the copy step itself runs once per worker and produces one file per worker, not one file total.
