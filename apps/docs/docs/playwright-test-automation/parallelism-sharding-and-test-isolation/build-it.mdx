# Parallelism, Sharding, and Test Isolation — Hands On

⏱ 35 minutes

## Breaking It Down

### Step 1: Reproduce the Collision on Purpose

Before you fix anything, let's see the actual failure with your own eyes. Create `tests/parallel-collision.spec.ts`:

```typescript title="tests/parallel-collision.spec.ts"
import { test, expect } from '@playwright/test';

test('nurse schedules an appointment for the seeded patient', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('nurse1');
  await page.getByLabel('Password').fill('nurse123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.getByRole('link', { name: 'Appointments' }).click();
  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption({ label: 'Patient One' });
  await page.getByRole('button', { name: 'Confirm' }).click();

  await expect(page.getByText('Appointment scheduled')).toBeVisible();
});

test('admin sees the correct total appointment count', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.getByRole('link', { name: 'Appointments' }).click();

  // Seeded count is 22. This assumes nothing else wrote to the
  // appointments table between seeding and this exact read.
  await expect(page.getByTestId('appointment-count')).toHaveText('22');
});
```

Run the file several times in a row with the default parallel workers:

```bash
npx playwright test tests/parallel-collision.spec.ts --repeat-each=5
```

Somewhere in those five repeats, the admin spec fails — it reads `23`, not `22`, because the nurse spec's `INSERT` landed on the shared SQLite file a moment before the admin spec's count query ran on a different worker. Now run it again with `--workers=1`, and notice it never fails — that gap is exactly the signature that should point you at shared state, not at either test being "wrong." Once you've watched it fail at least once, go ahead and delete this spec — it's done its job.

### Step 2: Let the Backend Read Its Database Path From an Environment Variable

The fix hinges on each worker's requests landing on a database file no other worker touches, which means making one small, one-time change to the RBAC backend: point its SQLite connection at a path you control instead of a hardcoded one.

Open `backend/database/db.ts` (or wherever the app opens its SQLite connection) and change the hardcoded path to read from an environment variable, falling back to the existing default so nothing else in the app breaks:

```typescript title="backend/database/db.ts"
const dbPath = process.env.DB_PATH ?? './database/healthcare.db';
const db = new Database(dbPath);
```

This is the only change you make to the SUT itself for this whole module. Everything else — spinning up per-worker backend processes, copying the seeded file, picking ports — happens from the Playwright side.

### Step 3: Write a Worker-Scoped Fixture That Copies the Database Per Worker

Create `tests/fixtures/isolated-backend.fixture.ts`:

```typescript title="tests/fixtures/isolated-backend.fixture.ts"
import { test as base } from '@playwright/test';
import { spawn, ChildProcess } from 'child_process';
import { copyFileSync, mkdirSync } from 'fs';
import path from 'path';

type IsolatedBackend = { baseURL: string };

const SEEDED_DB = path.resolve(__dirname, '../../backend/database/healthcare.db');
const WORKER_DB_DIR = path.resolve(__dirname, '../../backend/database/workers');

export const test = base.extend<{}, { isolatedBackend: IsolatedBackend }>({
  isolatedBackend: [
    async ({}, use, workerInfo) => {
      mkdirSync(WORKER_DB_DIR, { recursive: true });

      // Each worker gets a fresh copy of the already-seeded file —
      // no re-seeding step needed, and no risk of two workers
      // copying mid-write since copyFileSync happens once per worker
      // before that worker runs a single test.
      const workerDbPath = path.join(WORKER_DB_DIR, `worker-${workerInfo.workerIndex}.db`);
      copyFileSync(SEEDED_DB, workerDbPath);

      const port = 5000 + workerInfo.workerIndex + 1;

      const backend: ChildProcess = spawn('npm', ['start'], {
        cwd: path.resolve(__dirname, '../../backend'),
        env: { ...process.env, PORT: String(port), DB_PATH: workerDbPath },
        shell: true,
      });

      await new Promise<void>((resolve) => {
        backend.stdout?.on('data', (chunk) => {
          if (chunk.toString().includes('Server running')) resolve();
        });
      });

      await use({ baseURL: `http://localhost:${port}` });

      backend.kill();
    },
    { scope: 'worker' },
  ],
});

export { expect } from '@playwright/test';
```

`workerInfo.workerIndex` is Playwright's own stable, zero-based ID for the worker process running this fixture — worker 0 gets `worker-0.db` on port `5001`, worker 1 gets `worker-1.db` on port `5002`, and so on. Because the fixture is worker-scoped (`{ scope: 'worker' }`), this setup runs once per worker process, not once per test — every test that worker runs shares that one isolated backend and database file.

### Step 4: Point Tests at the Per-Worker Backend

Rewrite the collision spec to use the fixture instead of the shared `page`/`baseURL`:

```typescript title="tests/parallel-collision-isolated.spec.ts"
import { test, expect } from './fixtures/isolated-backend.fixture';

test('nurse and admin never collide once each worker owns its database', async ({ page, isolatedBackend }) => {
  await page.goto(`${isolatedBackend.baseURL}/login`);
  await page.getByLabel('Username').fill('nurse1');
  await page.getByLabel('Password').fill('nurse123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await page.getByRole('link', { name: 'Appointments' }).click();
  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption({ label: 'Patient One' });
  await page.getByRole('button', { name: 'Confirm' }).click();

  await expect(page.getByText('Appointment scheduled')).toBeVisible();
});
```

Run it with the original collision spec's structure repeated across workers:

```bash
npx playwright test tests/parallel-collision-isolated.spec.ts --repeat-each=5 --workers=4
```

It passes every time, at any worker count, because there is no longer a shared row for two workers to disagree about — each worker's SQLite file only ever sees that worker's own writes.

### Step 5: Understand the Alternative — Transactional Rollback

The file-copy approach works well here because SQLite is just a file — `copyFileSync` on a fully-seeded database is close to instant, and every worker gets a completely independent copy of real seeded data. The other common isolation strategy, transactional rollback, wraps each test in a database transaction that's rolled back once the test finishes, so nothing the test wrote ever actually commits:

```typescript title="conceptual sketch — not runnable against the unmodified RBAC backend"
async function withRollback(dbConnection, testFn) {
  await dbConnection.exec('BEGIN');
  try {
    await testFn();
  } finally {
    await dbConnection.exec('ROLLBACK');
  }
}
```

This pattern shines when your test calls the database layer directly, in-process — exactly the shape of testing this course's companion `supertest-api-testing` course does, where there's one Node process and one open connection to wrap in a transaction. It breaks down for the kind of full end-to-end test you write in Playwright: your test drives a browser, which sends real HTTP requests to a separately running Express process, which opens its own SQLite connection per request. There is no single shared connection for your test file to `BEGIN` a transaction on — the transaction would have to be started and held open *inside the backend process*, across multiple unrelated HTTP requests, which means teaching the SUT itself a test-only concept it has no reason to know about otherwise. For an unmodified, realistically-running app like this one, reached over real HTTP, the per-worker file copy from Steps 2 to 4 is the practical choice. Keep transactional rollback in mind for the day you're testing a service layer in-process rather than over the network.

### Step 6: Add CI Sharding on Top

Sharding is a separate axis from any of the above — it decides how much of your total spec list a given CI job even attempts, independent of how many workers that job then runs. Add a shard flag to a CI script:

```bash
npx playwright test --shard=1/4
```

In a GitHub Actions matrix, each of four jobs runs the same command with a different shard index, and each of those four jobs still applies its own `workers` setting from `playwright.config.ts` on top:

```yaml title=".github/workflows/playwright.yml (excerpt)"
strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }}/4
```

With `workers: 4` in config and a 4-way shard matrix, this composes to 16 test files genuinely running at the same time across your CI fleet — not 4, and not 16 workers on one machine, but 4 machines each running 4 workers on their own quarter of the suite. Because Step 4's fixture makes every worker on every shard bring its own isolated database file, none of those 16 concurrent executions can collide with any other, on the same machine or across machines.

## How It Works Internally

`workerInfo.workerIndex` is assigned once per worker process and never reused within a single `npx playwright test` invocation, and that's exactly what makes it safe to use as a database-file and port suffix — no two live workers can ever compute the same path or bind the same port at the same time. (Playwright also exposes `workerInfo.parallelIndex`, which is reused as workers are recycled across a long run; `workerIndex` is the one to reach for when you need a value that's unique for the life of the process, such as a file path.) Because the fixture is worker-scoped, its setup function runs exactly once when the worker starts up and its teardown (killing the spawned backend) runs exactly once when the worker shuts down, regardless of how many tests that worker executes in between — the per-worker backend and database file are amortized across every test that worker happens to run, not recreated per test.

Sharding, by contrast, is settled entirely before any worker even exists. `--shard=N/M` runs on the Playwright CLI's own test-file discovery step, partitioning the full sorted list of spec files into `M` roughly equal groups and handing this invocation only group `N`. Everything downstream — `workers`, fixtures, `workerIndex` — operates only on that one shard's slice of files, with no visibility into or coordination with the other `M - 1` shards running elsewhere. That's why the two techniques compose so cleanly: sharding decides *which files* a machine sees at all, and worker parallelism (plus per-worker isolation) decides how safely that machine runs them.
