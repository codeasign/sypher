# Parallelism, Sharding, and Test Isolation: Review

⏱ 5 minutes

## Key Takeaways

- Playwright's default parallel workers give you real isolation for browser contexts, but nothing outside the browser. The RBAC app's one Express process and one SQLite file are shared by every worker unless you go out of your way to isolate those too.
- A parallelism-induced flake has a pretty recognizable signature: it's intermittent under multiple workers, it never reproduces with `--workers=1`, and there's no exception in your own test code pointing at the real cause.
- A worker-scoped fixture keyed by `workerInfo.workerIndex` can spin up a dedicated backend process and a private copy of the seeded SQLite file for each worker. This works nicely here because SQLite is just a file, so copying a fully-seeded one is close to instant.
- Transactional rollback is the other real isolation strategy out there, but it's suited to in-process database testing (like `supertest-api-testing`), not a full end-to-end Playwright test that drives a browser against a separately running HTTP server.
- Sharding (`--shard=N/M`) and worker parallelism (`workers`) are different axes that compose together: `M` shards on `M` machines, each running `N` workers, means `M × N` spec files are genuinely executing at once across your CI fleet, not just `N`.

## Recap in 60 Seconds

If you only remember three things:

1. Browser-context isolation comes for free; database isolation is something you have to build yourself. Give each worker its own SQLite file copy and backend process, keyed by `workerInfo.workerIndex`.
2. Transactional rollback works well for in-process DB tests, but not for Playwright's real HTTP requests against a separately running server. Reach for file-copy isolation there instead.
3. Sharding splits *which* files a CI machine runs; worker parallelism decides how many of that machine's files run at once. Fix isolation first, then add sharding on top for throughput.

## What Comes Next

Now that every worker is isolated and sharding composes cleanly on top, your suite is fast and safe to scale. But scaling it up also means more failures will happen somewhere you didn't get to watch live. That's where the [Debugging and Troubleshooting](../debugging-and-troubleshooting/overview) lesson picks up: it covers UI mode's time travel, stepping through a trace file's network tab and DOM snapshots, using `codegen` as a starting point rather than a final answer, and treating retries as a diagnostic signal instead of a fix for a flake you haven't actually tracked down yet.
