# Parallelism, Sharding, and Test Isolation

⏱ 20 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Explain what a Playwright "worker" actually is, and why running four of them in parallel is safe for the browser but not automatically safe for a shared database
- Reproduce a real parallelism-induced flake against the RBAC app's SQLite backend, on purpose, so you know exactly what it looks like when it happens to you
- Give each worker its own isolated SQLite database, either by file copy or by transactional rollback, and explain the real tradeoffs between the two for a SQLite-backed app
- Distinguish CI sharding (`--shard=1/4`) from worker parallelism (`workers: 4`), and calculate how many tests actually run concurrently when both are combined

## Why This Matters

Up to this point, it's been easy to think of `npx playwright test` as a command that just runs your suite from start to finish. It doesn't quite work that way, though. By default, Playwright has been running your suite as several worker processes at once the whole time, and every test you've written so far got away with that because it either just read data, or touched a patient record no other test happened to care about. In other words, you've been safe by luck, not by design.

As this course's suite grows, that luck runs out. A permission-matrix spec (from the RBAC permission-matrix lesson) that creates and deletes an appointment, run alongside another spec that lists all appointments, will occasionally see the other worker's write mid-flight: a patient count that's briefly off by one, an appointment that's "gone" because a different worker just deleted it for its own test. These failures are the worst kind: they pass most of the time, they never reproduce with `--workers=1`, and by the time your CI suite is at a hundred specs across four workers, someone's re-running the whole job "because it's probably nothing." It probably isn't nothing. It's four processes writing to one SQLite file with no coordination.

## The Problem

Say two specs both exist in your suite:

```typescript
test('nurse can schedule an appointment for Patient One', async ({ page }) => {
  // creates an appointment for the seeded patient "Patient One"
});

test('admin can view all appointments', async ({ page }) => {
  // asserts the seeded appointment count for Patient One
});
```

Run alone, each passes every time. Run together under Playwright's default parallel workers, they land on two different OS processes that happen to execute at nearly the same moment. Both talk to the same running backend on `:5000`, and that backend has exactly one SQLite file behind it. If the nurse spec's `INSERT` and the admin spec's count-read interleave in the wrong order, the admin spec sees a count that doesn't match what it expected, not because either test is wrong, but because they were never told they'd be sharing state with a stranger.

Worse, this doesn't fail consistently. It fails when the OS scheduler happens to interleave the two processes unfavorably, which might be one run in twenty. You get exactly the symptom that erodes trust in a test suite fastest: green on rerun, red under load, and no stack trace that points at the real cause.

## The Concept

There are two things you've probably been taking for granted, and it turns out both are only half true.

**Worker parallelism gives you process isolation, not data isolation.** Playwright spins up multiple Node.js worker processes (four by default on a typical machine, scaled to your CPU count) and hands each one a slice of your test files. Inside each worker, tests get their own browser context per test. That part really is fully isolated, cookies and `localStorage` included, as you saw in [Why Playwright, and How It Differs](../why-playwright/overview). What isolation does *not* extend to is anything outside the browser: the one Express process on `:5000`, and the one SQLite file it reads and writes. Every worker's HTTP requests land on that same process and that same file, regardless of how isolated their browser contexts are from each other.

**Sharding and worker parallelism are two different axes, not the same knob at two settings.** `workers` controls how many test processes run *on the machine currently executing `npx playwright test`*. `--shard=1/4` controls how much of the *total test file list* a given invocation of `npx playwright test` even sees. The other three quarters are handed to three other invocations, typically on three other CI machines, each of which then applies its own `workers` setting on top. They compose: a 4-way shard where each shard runs 4 workers is 16 test files genuinely executing at the same moment across your CI fleet, not 4.

Fixing the flake, then, is not about running fewer workers. That just slows the suite down while leaving the underlying collision possible. It's about making sure every worker's slice of state is its own, so there is nothing left to collide on no matter how many workers or shards you run.
