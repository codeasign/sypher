# Why Playwright, and How It Differs — Review

⏱ 3 minutes

## Key Takeaways

- Playwright's action methods (`.click()`, `.fill()`, `.check()`) and web-first assertions (`expect(locator)...`) auto-wait for you: they retry actionability checks or the assertion condition until it holds or a timeout is reached, so a slow `fetch` to the RBAC backend never needs a manual wait.
- That's what eliminates the whole class of flakiness Selenium's `findElement()`-then-act model produces, where an element can exist in the DOM without actually being visible, stable, or enabled yet.
- A browser **instance** is one running Chromium/Firefox/WebKit process, while a browser **context** is an isolated, incognito-style profile inside it. The Playwright test runner gives every test a fresh context by default, which is why an admin login in one test never leaks into a doctor test running alongside it.
- `npx playwright codegen http://localhost:3002` generates a first-draft spec with role-based locators by watching what you click — a starting point, not a finished, assertion-bearing test.
- `npx playwright test --ui` and trace viewer are meant to be used constantly while you write and debug tests, not saved for CI emergencies — both let you see the exact DOM state at any step of a run.

## Recap in 60 Seconds

If you only remember three things, make it these:

1. Playwright actions and `expect(locator)` assertions auto-wait on actionability, so you never need `waitForTimeout` for a UI condition.
2. Every test gets its own isolated browser context by default, and one browser instance can safely host many contexts at once.
3. `codegen`, UI mode (`--ui`), and trace viewer are core daily tools, not add-ons you reach for only when something breaks.

## Try It

Take the two-role isolation test from Step 6 of Build It and extend it to cover all four RBAC roles, not just admin and doctor. Using `npx playwright codegen http://localhost:3002`, record what a nurse and a patient login look like — you'll need seeded credentials for each, so check your `npm run seed` output from Setup — then write a single test that:

1. Opens four separate browser contexts, one per role (admin, doctor, nurse, patient)
2. Logs in as each role in its own context, using `getByLabel` and `getByRole` locators
3. Asserts each role lands on its own dashboard with a role-appropriate heading, using `expect(page.getByRole('heading', { name: ... })).toBeVisible()`
4. Asserts that none of the four pages can see another role's dashboard heading — for example, that the patient's context never shows "Admin Dashboard"

Run it in UI mode (`npx playwright test --ui`) first, and time-travel through all four logins happening independently. Then deliberately force one assertion to fail and read the resulting trace, to confirm you can see exactly which context and which step failed.
