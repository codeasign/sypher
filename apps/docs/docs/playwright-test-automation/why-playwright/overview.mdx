# Why Playwright, and How It Differs

⏱ 15 minutes · Difficulty: Beginner

## What You Will Learn

By the end of this lesson you will be able to:

- Explain why Playwright's auto-waiting model wipes out an entire category of flaky test that plagues Selenium-style automation
- Tell a browser **instance** apart from a browser **context**, and explain why that context-level isolation is what makes Playwright's parallel test runs safe
- Use `npx playwright codegen` to record a real interaction against the RBAC app's login screen
- Use `npx playwright test --ui` to run and time-travel through a test, rather than treating debugging as an afterthought
- Describe what the trace viewer captures, and why that matters before you've even hit your first failing test

## Why This Matters

Every browser automation tool eventually has to answer the same question: how does the tool know an element is actually ready to be clicked, typed into, or read? Get this wrong and you get flaky tests — tests that pass most of the time and fail unpredictably, usually in CI, usually right before a release. Flaky tests are worse than tests that fail every time, because a test that fails every time gets fixed immediately, while a flaky test gets re-run, ignored, and eventually distrusted entirely.

Playwright's answer to that question — auto-waiting, tied to a rich set of actionability checks — is the single biggest reason it displaced Selenium as the default choice for new browser automation projects. It is not a minor implementation detail buried in the docs; it is the mental model this entire course is built on, and every test you write against the RBAC app from here onward depends on you understanding it correctly.

The second thing this lesson establishes is Playwright's isolation model — browser contexts versus browser instances — which is what makes it possible to run the RBAC app's four roles (admin, doctor, nurse, patient) in parallel, in the same test run, without one role's session leaking into another's. And the third is a mindset shift: trace viewer, UI mode, and codegen are not optional extras you bolt on later when things go wrong. They are core to how you write and debug Playwright tests from your very first spec file.

## The Problem

Imagine you're testing the RBAC app's login screen with a Selenium-style approach — find an element by its locator, then act on it immediately:

```typescript
// Selenium-style: find, then click, with no guarantee the element is ready
const loginButton = driver.findElement(By.id('login-btn'));
await loginButton.click();
```

`findElement` returns as soon as the element exists **somewhere in the DOM** — even if it's still disabled, still animating in, still covered by a loading spinner, or about to be re-rendered because a `fetch` call to `http://localhost:5000/api/auth/login` hasn't resolved yet. On a fast local machine, this click usually works, because the RBAC React app renders quickly and there's no visible delay. But add a network hiccup, a CI runner sharing CPU with three other jobs, or a component that briefly re-renders after an initial data fetch, and the exact same test starts failing — not because your test logic is wrong, but because the click landed on a button that existed in the DOM but wasn't actually interactive yet.

Classic Selenium automation papers over this with explicit waits sprinkled everywhere:

```typescript
// Selenium-style: the "fix" is more code, and it's still a guess
await driver.wait(until.elementIsEnabled(loginButton), 5000);
await loginButton.click();
```

This works, until it doesn't. You have to remember to add a wait before *every* interaction that might race a re-render, you have to guess the right condition (`elementIsEnabled`? `elementIsVisible`? `elementIsClickable`, which doesn't reliably exist?), and you have to guess a timeout that's long enough to avoid false failures but short enough not to make your suite unbearably slow. Multiply that across a suite testing four different RBAC roles' dashboards, each with its own async data loading, and explicit waits become the majority of the code you write and the majority of the flakiness you debug.

## The Concept

Playwright's locators are not references to a DOM node at all — they're a strategy for **finding** a node, re-evaluated at the moment of every action. When you call an action method like `.click()` or `.fill()`, Playwright runs a sequence of actionability checks against whatever the locator currently resolves to, and retries automatically until they all pass or a timeout is reached:

```typescript
import { test, expect } from '@playwright/test';

test('admin can log in', async ({ page }) => {
  await page.goto('/login');

  // Playwright waits for this button to be attached, visible, stable
  // (not animating), enabled, and not obscured — all automatically —
  // before the click is actually dispatched.
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page).toHaveURL('/dashboard');
});
```

There's no explicit wait anywhere in that test. `page.getByRole('button', { name: 'Log In' })` doesn't find the button once — it's a live query that Playwright re-runs right before the click, waiting (up to the default 30-second actionability timeout) for the RBAC login form to actually be interactive: attached to the DOM, visible, not moving, not disabled, and not covered by another element like a loading overlay. If the login page is still waiting on an initial `fetch` to populate form state, Playwright simply keeps checking until it settles — no guessed timeout, no `elementIsEnabled` call you had to remember to add.

This is the categorical difference from Selenium's model: Selenium separates *finding* an element from *waiting* for it to be ready, and makes waiting your responsibility, per interaction. Playwright fuses the two — every action is inherently a "wait until ready, then act" operation, applied consistently everywhere, so an entire class of race-condition flakiness simply cannot occur in the first place.

The same principle extends to assertions. `expect(locator).toBeVisible()` doesn't check once and fail — it retries until the condition holds or times out, which is why every assertion in this course is written against a locator, not a plain value:

```typescript
// Web-first: retries automatically until the dashboard heading appears
await expect(page.getByRole('heading', { name: 'Doctor Dashboard' })).toBeVisible();
```

Auto-waiting solves *what happens within a single page*. But the RBAC app has four roles, and a real test suite needs to run admin, doctor, nurse, and patient tests — often in parallel, often in the same run — without one role's cookies, `localStorage`, or JWT leaking into another's. That's what browser **contexts** solve, and it's a different mechanism from auto-waiting entirely.

A browser **instance** is one running copy of Chromium, Firefox, or WebKit — heavyweight to start, and something Playwright test runner launches once per worker process, not once per test. A browser **context**, by contrast, is like an incognito profile inside that running browser: its own cookie jar, its own `localStorage`, its own session storage, completely isolated from every other context in the same browser instance, and cheap enough to create fresh for every single test.

```typescript
import { test } from '@playwright/test';

// Each test in the Playwright test runner automatically gets its own
// fresh browser context — a clean slate. No shared cookies, no shared
// JWT from a previous test's login.
test('doctor sees only their own appointments', async ({ page }) => {
  // page here belongs to a context that has never seen a login before.
});

test('nurse can schedule an appointment', async ({ page }) => {
  // A completely separate context — no risk this test sees the doctor
  // test's session, even if both run in the same worker.
});
```

This is why you can safely write a suite that logs in as admin in one test file and as patient in another, run them in parallel workers, and never worry about the patient test accidentally inheriting the admin's JWT. One browser instance can host many contexts simultaneously; Playwright's test runner manages this for you so that "isolated by default" is the starting position, not something you have to configure.

Finally, this course treats three tools as first-class from lesson one, not optional add-ons you discover later. **`npx playwright codegen http://localhost:3002`** opens a real browser alongside a code generator window, and every click and fill you perform against the RBAC login screen gets recorded live as Playwright TypeScript — including role-based locators like `getByRole` and `getByLabel` — so you end up with a starting draft, not a finished test. **`npx playwright test --ui`** launches UI mode, a visual test runner where you can run a spec, watch it re-run automatically as you edit the file, and time-travel through each action to see exactly what the page looked like at that step. And **trace viewer** captures a full timeline of a test run — DOM snapshots, network requests, console logs — that you can step through after the fact, which is how you diagnose a failure without adding a single `console.log`.
