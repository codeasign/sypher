# Why Playwright, and How It Differs: Common Mistakes

⏱ 8 minutes

## When NOT to Use This

Auto-waiting covers actionability: is this element attached, visible, stable, and enabled, not arbitrary application state. If a test needs to wait for something that never shows up as a locator condition, like confirming a specific network response was received before moving on, auto-waiting alone doesn't help. Reaching for `page.waitForResponse()` (covered later in this course) is the correct tool there, not a workaround. Auto-waiting also isn't a substitute for correct backend behavior: if the RBAC API genuinely never returns because of a bug, no amount of retrying makes the button appear. The test should time out and fail, because that's a real problem worth seeing.

Likewise, browser contexts solve isolation between independent sessions, not everything about test independence. Two tests in separate contexts can still collide if they both write to the same seeded database rows. Context isolation is a browser-level guarantee, not a database one. Per-worker database isolation is covered separately later in this course; don't assume context isolation alone makes your suite safe against shared state.

## The Pattern to Remember

- **Pattern:** let locator actions and web-first assertions handle the waiting, let a fresh browser context handle session isolation, and treat codegen, UI mode, and trace viewer as tools you reach for constantly, not only when something breaks.
- **When to use:** every test in this course, from here on out. This is your default posture, not a special case you opt into.
- **When NOT to use:** when you're waiting on a non-UI condition (reach for `waitForResponse`/`waitForLoadState` instead, covered later), or when you need to isolate shared database state across workers (that's per-worker DB isolation, also covered later).
- **Mental model:** in Selenium, you're the traffic controller, manually timing every interaction. In Playwright, the *browser* is the traffic controller, and your job is just to describe what "ready" looks like, not to decide when it happens.

## Common Mistakes

### Mistake 1: Adding `waitForTimeout` "Just in Case"

**Mistake:** An old Selenium habit creeps back in: dropping `await page.waitForTimeout(2000)` before or after an action "just to be safe," even though auto-waiting already has it covered.

**Why it happens:** Explicit sleeps feel like insurance, especially if you spent years defending against Selenium's lack of built-in waiting. It's hard to trust that the tool is already handling it for you.

**Symptoms:** Your suite gets slower for no real benefit, since every `waitForTimeout` adds fixed dead time whether it was needed or not. Worse, it can mask a genuine problem: a `waitForTimeout(2000)` might happen to be long enough on your local machine but too short under CI load, which produces exactly the flakiness it was meant to prevent.

**Fix:** Delete the sleep. If a specific action or assertion is timing out, that's Playwright correctly telling you the element or condition genuinely isn't showing up, so investigate with trace viewer (Step 5, Build It) instead of masking the timeout behind a longer arbitrary wait.

### Mistake 2: Reaching for CSS Selectors Out of Old Habit

**Mistake:** Writing `page.locator('#login-btn')` or `page.locator('.btn-primary')` against the RBAC login form instead of `page.getByRole('button', { name: 'Log In' })`, simply because `By.id` and `By.className` were the default reflex in Selenium.

**Why it happens:** CSS and ID selectors feel more precise and more familiar, especially early on, and to be fair, they do work. The RBAC frontend genuinely does have IDs and classes on its elements.

**Symptoms:** Tests break the moment a frontend refactor changes a class name or restructures a `div`, even though the button's visible label and role never changed at all. It's telling that codegen against the RBAC app (Step 1, Build It) reaches for `getByRole`/`getByLabel` first on its own. CSS selectors are only what it falls back to when there's no accessible role or label to use.

**Fix:** Default to `getByRole`, `getByLabel`, and `getByText` for anything a real user would identify by role or visible text. Save CSS/XPath locators for genuine fallback cases with no accessible name, and treat ever needing one as a signal worth flagging to whoever owns the frontend's accessibility.

### Mistake 3: Treating Codegen Output as a Finished Test

**Mistake:** Running `npx playwright codegen http://localhost:3002`, copying the recorded output straight into a spec file, and committing it as-is without adding assertions or reviewing the locators.

**Why it happens:** The recorded code runs immediately and looks complete: it clicks, it fills, it navigates. It's an easy trap to mistake "runs without error" for "actually tests something."

**Symptoms:** The spec passes even when the RBAC login is broken, because a recording of clicks and fills with no `expect()` calls doesn't verify any outcome at all. It just replays actions. Sooner or later a reviewer finds a "test" that has never once failed, which is itself a red flag.

**Fix:** Use codegen for exactly what Step 1 and Step 2 of Build It demonstrate: a fast first draft of locators. Then add the actual assertions (`toHaveURL`, `toBeVisible`, and so on) by hand, and double-check that each recorded locator is the role-based version, not a brittle one codegen fell back to.

### Mistake 4: Sharing One Page or Context Across Tests to "Save Time"

**Mistake:** Hoisting a single `page` (or `browser.newContext()`) into a `beforeAll` hook and reusing it across multiple tests to skip repeated logins, instead of letting each test get its own fresh context.

**Why it happens:** Logging in as admin once and reusing that session feels like an obvious speed win, and honestly, it does cut down on repeated `page.goto('/login')` calls.

**Symptoms:** Tests start failing depending on run order. A test that expects to be logged out finds itself still authenticated from a previous test's session, or a test that passes fine on its own fails once it runs as part of the full suite, simply because state leaked across tests that were never supposed to share any.

**Fix:** Let the default `page` fixture give every test its own context, as shown in Step 6 of Build It. If repeated logins are genuinely slow, reach for `storageState` instead, which reuses authenticated *state* across fresh contexts rather than sharing a raw context that quietly couples your tests together.

### Mistake 5: Only Opening Trace Viewer or UI Mode After Something Breaks in CI

**Mistake:** Writing every spec headless, from the command line, and only reaching for `npx playwright test --ui` or trace viewer as a last resort once a test is already failing mysteriously in CI.

**Why it happens:** Selenium tooling rarely made a visual, replayable debugger feel like part of the everyday workflow, so it's an easy habit to keep treating Playwright's equivalents the same way, as an emergency tool, not a default one.

**Symptoms:** You end up spending far longer than necessary debugging locally with `console.log` and guesswork, when UI mode's watch-and-time-travel workflow (Step 4, Build It) would have shown you the exact DOM state at the moment of failure in seconds.

**Fix:** Default to `npx playwright test --ui` while you're actively writing or debugging specs, not just headless `npx playwright test`. Treat trace viewer as something you open the moment any test surprises you, not only once it's already a CI incident.
