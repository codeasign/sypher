# Why Playwright, and How It Differs: Hands On

⏱ 20 minutes

## Breaking It Down

### Step 1: Record the RBAC Login Flow with codegen

With both servers running (backend `:5000`, frontend `:3002`), open a new terminal at the repo root and run:

```bash
npx playwright codegen http://localhost:3002
```

Two windows open: a real Chromium browser pointed at the RBAC app's login screen, and a separate "Playwright Inspector" window showing generated code updating live. In the browser window:

1. Click the **Username** field and type `admin`
2. Click the **Password** field and type `admin123`
3. Click the **Log In** button

Watch the Inspector window as you do this. Codegen doesn't just record raw coordinates. It infers role-based locators from the page's accessibility tree, producing something close to:

```typescript
await page.getByLabel('Username').click();
await page.getByLabel('Username').fill('admin');
await page.getByLabel('Password').click();
await page.getByLabel('Password').fill('admin123');
await page.getByRole('button', { name: 'Log In' }).click();
```

This is exactly why `getByLabel` and `getByRole` are this course's default locator strategy from lesson one: they're what Playwright itself reaches for first when it has no prior knowledge of the page. Close both codegen windows once you've seen the generated code; you don't need to save this exact recording.

### Step 2: Turn the Recording into a Real Spec

Codegen output is a draft, not a finished test. It has no assertions and no `test()` wrapper. Create `tests/why-playwright.spec.ts`:

```typescript title="tests/why-playwright.spec.ts"
import { test, expect } from '@playwright/test';

test('admin can log in and reach the dashboard', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByRole('heading', { name: 'Admin Dashboard' })).toBeVisible();
});
```

Run it:

```bash
npx playwright test tests/why-playwright.spec.ts
```

It should pass. Nothing here waits explicitly for the login `fetch` to resolve, or for the dashboard's initial data load to finish. `toHaveURL` and `toBeVisible` are web-first assertions that poll and retry on their own until the condition is true or the timeout elapses.

### Step 3: See Auto-Waiting Handle a Slow Network

To see auto-waiting actually earn its keep, rather than take it on faith, throttle the page before logging in, simulating the kind of slow `fetch` to `http://localhost:5000/api/auth/login` that causes Selenium-style flakiness:

```typescript title="tests/why-playwright.spec.ts"
import { test, expect } from '@playwright/test';

test('login succeeds even under a slow network', async ({ page }) => {
  // Simulate latency on every request the RBAC login form makes
  await page.route('**/api/auth/login', async (route) => {
    await new Promise((resolve) => setTimeout(resolve, 1500));
    await route.continue();
  });

  await page.goto('/login');
  await page.getByLabel('Username').fill('admin');
  await page.getByLabel('Password').fill('admin123');
  await page.getByRole('button', { name: 'Log In' }).click();

  // No waitForTimeout, no manual poll: the assertion itself retries
  // until the redirect to /dashboard actually happens.
  await expect(page).toHaveURL('/dashboard');
});
```

Run it again. It still passes, just visibly slower. `toHaveURL` doesn't check once and give up; it keeps polling until the delayed response resolves and the app navigates. This is the exact scenario that breaks a Selenium test written as `driver.findElement(By.id('login-btn')).click()` immediately followed by an unconditional `assertEquals(driver.getCurrentUrl(), ...)` with no wait at all. That kind of test would read the URL before the navigation happens and fail, despite the login itself working correctly a moment later.

### Step 4: Open UI Mode and Time-Travel Through the Run

Run the same spec in UI mode instead of headless:

```bash
npx playwright test --ui
```

A window opens listing your test files on the left. Click **why-playwright.spec.ts**, then run the `admin can log in and reach the dashboard` test. Once it finishes:

- Click through the timeline at the top, where each step (`goto`, `fill`, `click`, each `expect`) is its own frame you can select
- Select a step to see a DOM snapshot of the page **at that exact moment**, along with the action log on the right
- Toggle **watch mode** (the eye icon) so the test re-runs automatically every time you save the spec file

That's time travel through a real run, not a log file you have to mentally reconstruct. Leave UI mode open. You'll use it again in later modules whenever a test does something unexpected.

### Step 5: Force a Failure and Read the Trace

Now deliberately break the test, so you can see what a failure looks like with tracing turned on. Change the expected heading text to something wrong:

```typescript title="tests/why-playwright.spec.ts"
await expect(page.getByRole('heading', { name: 'Super Admin Dashboard' })).toBeVisible();
```

Run it from the command line, outside UI mode, so a trace file gets written on first retry (per the `trace: 'on-first-retry'` setting from `playwright.config.ts` in Setup):

```bash
npx playwright test tests/why-playwright.spec.ts --retries=1
```

The test fails on both attempts. Open the HTML report it generated:

```bash
npx playwright show-report
```

Find the failed test and click the trace icon. Trace viewer opens showing the full timeline: a DOM snapshot at every action, the network tab showing the actual `/api/auth/login` request and response, console output, and the precise actionability checks Playwright was retrying against `getByRole('heading', { name: 'Super Admin Dashboard' })` right up until it gave up. You can see, directly, that the real heading text was `Admin Dashboard`, with no `console.log` needed anywhere.

Revert the heading text back to `Admin Dashboard` before continuing.

### Step 6: Prove Context Isolation with Two Roles at Once

Confirm that browser contexts are actually isolated, not just isolated in theory, by logging in as two different RBAC roles inside the same test and checking neither session leaks into the other:

```typescript title="tests/why-playwright.spec.ts"
import { test, expect } from '@playwright/test';

test('admin and doctor sessions never share state', async ({ browser }) => {
  // Two separate contexts in the same browser instance: separate
  // cookie jars, separate localStorage, completely isolated.
  const adminContext = await browser.newContext();
  const doctorContext = await browser.newContext();

  const adminPage = await adminContext.newPage();
  const doctorPage = await doctorContext.newPage();

  await adminPage.goto('/login');
  await adminPage.getByLabel('Username').fill('admin');
  await adminPage.getByLabel('Password').fill('admin123');
  await adminPage.getByRole('button', { name: 'Log In' }).click();
  await expect(adminPage).toHaveURL('/dashboard');

  // The doctor page has never authenticated, so its context has no
  // knowledge of the admin login that just happened next to it.
  await doctorPage.goto('/dashboard');
  await expect(doctorPage).toHaveURL('/login');

  await adminContext.close();
  await doctorContext.close();
});
```

Run it:

```bash
npx playwright test tests/why-playwright.spec.ts -g "sessions never share state"
```

`doctorPage`, navigating to `/dashboard` with no session of its own, gets redirected back to `/login`, even though `adminPage` in the very same test, same worker, same browser instance, is fully authenticated a few lines above it. That's context isolation, not a coincidence of test ordering.

## How It Works Internally

Every action method on a locator, `.click()`, `.fill()`, `.check()`, `.selectOption()`, runs the same underlying loop before it does anything else. First it resolves the locator against the current DOM, then it runs Playwright's actionability checks (attached, visible, stable, receives events, and, for `.click()`/`.fill()`/`.check()`, enabled). If any of those checks fails, it waits a short interval and tries the whole thing again. That repeats until every check passes or the action's timeout (30 seconds by default) is reached, at which point it throws with a clear message naming exactly which check failed. Nothing about this requires you to write a wait yourself. It's baked into what "clicking" means in Playwright.

Browser contexts implement isolation the same way a real browser's separate profiles do: each context gets its own cookie store, `localStorage`, `sessionStorage`, and permission grants, all scoped to that context object in memory. Creating a context is cheap, cheap enough that the Playwright test runner creates a brand-new one for every single test by default via the `page` fixture, while launching a whole new browser **instance** per test would be far too slow to run a real suite. One instance, many contexts, is what makes both isolation and speed possible at the same time.
