# Setting Up Your Playwright Test Environment — Hands On

⏱ 20 minutes

## Breaking It Down

### Step 1: Fork the Repo — Not Clone

Go to [github.com/codedbyabhishekc/rbac-healthcare-system](https://github.com/codedbyabhishekc/rbac-healthcare-system) and click **Fork**, not **Clone**.

This matters for more than just this lesson. Later on, the continuous integration lesson has you add a GitHub Actions workflow to this exact repo, and that only works on a repository you own. Cloning just gets you the code, but forking gets you a repo you can push to, configure Actions on, and evolve across the whole course.

Once forked, clone **your fork**:

```bash
git clone https://github.com/<your-username>/rbac-healthcare-system.git
cd rbac-healthcare-system
```

### Step 2: Install and Run the Backend

```bash
cd backend
npm install
mkdir database
```

The `database` directory has to exist before the app's first run — it's where the SQLite file gets created, and the app does not create the directory itself.

Create a `.env` file inside `backend/`:

```bash
PORT=5000
JWT_SECRET=<any-long-random-string>
NODE_ENV=development
```

Start the backend:

```bash
npm start
# or: npm run dev
```

Confirm it's up by opening [http://localhost:5000/api-docs](http://localhost:5000/api-docs) — you should see the Swagger UI listing every API endpoint. Leave this terminal running; you'll use it for the rest of the course.

### Step 3: Seed the Database

In a new terminal, from `backend/`:

```bash
npm run seed
```

This creates the fixed set of accounts and records every lesson in this course tests against:

| Role | Count | Default login |
|---|---|---|
| Admin | 3 | `admin` / `admin123` |
| Doctor | 8 | seeded, see seed script output |
| Nurse | 7 | seeded, see seed script output |
| Patient | 15 | seeded, see seed script output |
| Appointments | 22 | — |
| Medical Records | 15 | — |

You'll use the admin account (`admin` / `admin123`) as your first authenticated login once you get to the authentication and session state lesson.

### Step 4: Install and Run the Frontend

```bash
cd ../frontend
npm install
```

The repo's own README defaults the frontend to port `3000`. This course pins it to **`3002`** instead, permanently — not as a workaround, but because `3000` is the single most commonly occupied port on a developer machine (Create React App, Next.js, and half of everything else defaults to it too), and a course you'll be running for many lessons should not fight that collision every session. Start it on `3002` explicitly:

```bash
PORT=3002 npm start
```

On Windows PowerShell, set the variable first:

```powershell
$env:PORT=3002
npm start
```

Confirm it's up by opening [http://localhost:3002/login](http://localhost:3002/login) in a browser — you should see the app's login screen, exactly like this:

At this point you should have two terminals running: backend on `:5000`, frontend on `:3002`. Leave both of them running for every lesson in this course — nothing here starts or stops these servers for you, until the continuous integration setup later on, which runs them as services instead.

### Step 5: Install Playwright

In a third terminal, from the repo root (not inside `backend/` or `frontend/`):

```bash
npm init playwright@latest
```

Answer the prompts:

- **TypeScript or JavaScript?** → TypeScript
- **Where to put your tests?** → `tests` (the default)
- **Add a GitHub Actions workflow?** → No for now — a later lesson builds this properly, with the backend and frontend running as CI services, which is more than the scaffolded default handles
- **Install Playwright browsers?** → Yes

This generates `playwright.config.ts`, a `tests/` folder with an example spec, and installs Chromium, Firefox, and WebKit.

### Step 6: Set the Permanent baseURL

Open `playwright.config.ts` and find the `use` block. Set `baseURL` there:

```typescript title="playwright.config.ts"
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  reporter: 'html',

  use: {
    baseURL: 'http://localhost:3002',
    trace: 'on-first-retry',
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
});
```

The `baseURL` you just set here is permanent, checked-in project configuration — not something you'd set as an environment variable, and not something any individual test should override. Every test file in every lesson of this course calls `page.goto('/login')`, `page.goto('/dashboard')`, and so on, and all of them resolve against this one value.

### Step 7: Verify Everything End to End

With both servers still running, confirm Playwright can see and list its example test:

```bash
npx playwright test --list
```

You should see the scaffolded example test listed with no errors. Now delete the example spec — you don't need it — and confirm the two servers respond directly:

```bash
curl -I http://localhost:5000/api-docs
curl -I http://localhost:3002/login
```

Both should return an HTTP success status. If either doesn't, stop here and go to [Avoid Mistakes](./avoid-mistakes) before continuing — every later module assumes this exact setup is already working.

As one last sanity check, log in with the seeded admin account (`admin` / `admin123`) directly in the browser. You should land on the admin dashboard, seeded with the exact counts from Step 3 — 34 total users, 8 doctors, 7 nurses, 15 patients:

## How It Works Internally

When a test calls `page.goto('/login')`, Playwright doesn't literally send `/login` anywhere — it resolves that relative path against `use.baseURL` from your config, producing the actual navigation target `http://localhost:3002/login`, the same way a browser resolves a relative link on a page against that page's own URL. That's exactly why `baseURL` has to be set before you write a single test — every relative `page.goto()` call in the whole suite is quietly depending on it being correct.
