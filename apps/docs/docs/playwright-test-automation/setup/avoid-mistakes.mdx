# Setting Up Your Playwright Test Environment — Common Mistakes

⏱ 8 minutes

## When NOT to Use This Setup

Everything in this lesson is built for **local development** — you, on your own machine, running both servers yourself in terminals you're watching. Once you get to the continuous integration lesson later in this course, you'll swap this for a `webServer` entry in `playwright.config.ts` that starts and stops both servers automatically as part of `npx playwright test`, which is what actually runs inside GitHub Actions. So don't try to hand-manage two terminal windows inside a CI runner — that's precisely the problem the `webServer` config exists to solve, and we'll cover it properly once you get there.

## The Pattern to Remember

- **Pattern:** get both servers running and seeded first, set `baseURL` once in checked-in config, then verify everything end to end before you write a single test.
- **When to use:** every local session in this course, every single time, in this order.
- **When NOT to use:** in CI (that's what the `webServer` config covered later in this course is for instead), or when you're just poking around the API through Swagger with no Playwright involved yet.
- **Mental model:** think of the backend and frontend as the stage and the actors, and `playwright.config.ts` as the address printed on your ticket — get that address wrong and it won't matter how good the show is, you'll never find the theater.

## Common Mistakes

### Mistake 1: Cloning Instead of Forking

**Mistake:** Running `git clone` directly on `codedbyabhishekc/rbac-healthcare-system` instead of forking first.

**Why it happens:** Cloning is the more familiar first instinct, and it works fine right up until you actually need to push a workflow file to CI.

**Symptoms:** The GitHub Actions workflow later in this course fails to push or has no repository to attach Actions to, because you don't own the remote.

**Fix:** Fork on GitHub first, then clone your fork's URL, not the original's. If you already cloned the original, fork now and change your `origin` remote: `git remote set-url origin https://github.com/<you>/rbac-healthcare-system.git`.

### Mistake 2: Forgetting to Seed the Database

**Mistake:** Starting the backend and frontend, then immediately writing a login test, without running `npm run seed`.

**Why it happens:** The backend starts and looks completely healthy — Swagger loads fine, the API responds — because an empty database is still a *valid* database, just one with no users in it.

**Symptoms:** Every login attempt fails with an authentication error, even with the documented default credentials (`admin` / `admin123`), because that account doesn't exist yet.

**Fix:** Run `npm run seed` from `backend/` before any test that logs in. If you ever reset or delete the SQLite file, re-run it.

### Mistake 3: Hardcoding the URL Instead of Using baseURL

**Mistake:** Writing `await page.goto('http://localhost:3002/login')` directly in a test file instead of `await page.goto('/login')`.

**Why it happens:** It works identically the first time you write it, so there's no immediate signal anything is wrong.

**Symptoms:** The moment your environment changes — a different port, a staging URL, a CI runner's internal hostname — every hardcoded test breaks, and you have to find and fix them one by one instead of changing one config value.

**Fix:** Stick to relative paths (`page.goto('/login')`) and let `baseURL` in `playwright.config.ts` do the resolving for you. If you genuinely need a different base for a specific project — a staging suite, say — override it in that project's config block, not scattered across individual tests.

### Mistake 4: Skipping the `mkdir database` Step

**Mistake:** Running `npm start` in `backend/` without creating the `database/` directory first.

**Why it happens:** Most Node apps create whatever directories they need automatically. This one doesn't — it expects `database/` to already exist so it can place the SQLite file inside it.

**Symptoms:** The backend crashes on startup with a file-system error about being unable to open or create the database file, and the error message doesn't always make the missing directory obvious.

**Fix:** `mkdir database` inside `backend/` before your first `npm start`. You only need to do this once — after that, the directory and the SQLite file persist.

### Mistake 5: Assuming the Frontend Runs on Port 3000

**Mistake:** Following the repo's own README literally and expecting (or configuring `baseURL` for) `localhost:3000`.

**Why it happens:** `3000` is the README's documented default, and it's also the overwhelmingly common default across the Node ecosystem, so it's the reasonable first guess.

**Symptoms:** `playwright.config.ts` points at `:3000`, nothing is listening there because you started the frontend on `:3002` as this lesson instructs, and every test times out on `page.goto()` with a connection error that looks like a locator problem but isn't.

**Fix:** Remember that this course pins the frontend to `:3002` permanently, so start it with `PORT=3002 npm start` and make sure `baseURL` in `playwright.config.ts` matches exactly. If you ever see a mismatch, check both the terminal that started the frontend and the config file — don't assume it's just one or the other.
