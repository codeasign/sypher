# When to Use Agents vs. When to Write the Test Yourself: Review

⏱ 5 minutes

## Key Takeaways

- The decision framework has one axis: how much you already know about the page state and flow you're testing. Unfamiliar page state routes to Planner, Generator, and MCP exploration (covered in the previous two lessons); a known, stable flow routes to a hand-written script.
- Agentic runs cost meaningfully more tokens and wall-clock time than a scripted `npx playwright test` run, because every reasoning step invokes an LLM, while a scripted step executes a decision that was already made once, ahead of time.
- This course's position, stated plainly: agents belong in exploration, spec generation, and healing, never in routine CI execution. The continuous integration lesson's pipeline should always run the deterministic, already-reviewed suite.
- The full lifecycle this course has been building toward is: agent-generated draft (from the Playwright Test Agents lesson) → human review for locator quality, assertion correctness, and no smuggled `waitForTimeout` (covered in the actions-and-web-first-assertions and self-healing tests lessons) → committed, version-controlled spec that runs deterministically in CI forever after (covered in the continuous integration lesson).
- Once a spec is committed, its origin stops mattering. A generated-then-reviewed spec and a hand-written one are maintained the same way, reviewed the same way, and trusted the same way when they fail.

## Recap in 60 Seconds

If you only remember three things:

1. If the flow is unfamiliar, reach for an agent: Planner, Generator, MCP. If it's known and stable, write the script yourself, because it's cheaper, deterministic, and faster in CI.
2. Every agent-drafted spec gets a human review pass before it merges. The same discipline the self-healing tests lesson taught for healed diffs applies here to generated ones.
3. Once reviewed and committed, a spec runs as a plain deterministic script in CI from then on. No agent is involved in any subsequent run. The agent's job ended the moment the spec became known.

## Try It

Take the RBAC app's `View all appointments` row from the RBAC permission-matrix lesson's matrix (Admin: yes, Nurse: yes, Doctor: no, Patient: no) and imagine the maintainers just added a new filter control to that view: a dropdown letting an admin or nurse filter the appointment list by status (Scheduled, Completed, Cancelled). You have never seen this control.

1. Decide, using this module's framework, which parts of this task are "unfamiliar" and which are "known." (The permission is known from the RBAC permission-matrix lesson. The filter control's markup and behavior are not.)
2. Sketch the MCP exploration prompt you'd send to get an accessibility snapshot of the new filter dropdown, the way Build It did for the cancellation modal.
3. Sketch the goal you'd hand to Planner/Generator to draft a spec asserting that filtering by "Cancelled" only shows cancelled appointments, for a nurse.
4. List the three things you'd check in human review before committing it (locator quality, assertion correctness, and no hardcoded waits) the same checklist Build It applied to the cancellation flow.
5. State, in one sentence, why this spec never needs an agent again once it's merged and running in the continuous integration lesson's CI.

If you can walk through all five steps without hesitating on which stage a given piece of work belongs to, you've internalized the framework this entire module was built around.
