# When to Use Agents vs. When to Write the Test Yourself

⏱ 18 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Apply a concrete decision framework that separates "reasoning about unfamiliar page state" from "executing a known, stable flow" — and route each to the right tool
- State, in plain numbers, why an agentic run costs meaningfully more tokens and wall-clock time than `npx playwright test`, and why that cost is the whole reason this decision matters
- Explain why this course's position is that agents belong in exploration, spec generation, and healing — not in routine CI execution
- Trace the full lifecycle this course has been building toward: agent-drafted spec → human review → committed, version-controlled test → deterministic execution in CI forever after
- Walk a new, unfamiliar RBAC flow through that entire lifecycle end to end, from first exploration to a merged spec that never needs an agent again

## Why This Matters

Every lesson since the Playwright Test Agents lesson has handed you a genuinely capable tool: an agent that can plan a test from a goal, generate the spec, explore a page it has never seen through MCP, and repair a test broken by markup churn. None of that capability answers the question this final module exists to ask: given a specific testing task in front of you right now, should you actually reach for one of these agents, or should you just write the test?

The honest answer is that it depends on exactly one thing — how much of what you're testing is already known. An agent earns its cost when it is doing something you genuinely cannot do faster by hand: reasoning about a page whose structure you haven't seen yet, or repairing drift across a large suite you'd otherwise chase manually. A hand-written script wins everywhere else, because it is cheaper to run, fully deterministic, and faster in CI by an order of magnitude that only grows as your suite does. Getting this backwards — running an agent for your login test on every commit, or hand-exploring an unfamiliar new feature click by click when an agent could map it in an accessibility-tree snapshot — wastes exactly the resource each tool is good at conserving.

This module is the course's closing synthesis, not a new technique. It takes everything from the Playwright Test Agents lesson (drafting), the Playwright MCP lesson (exploring), the Self-Healing Tests lesson (healing), and the Continuous Integration lesson (CI) and shows how they compose into one lifecycle: an agent does the expensive, one-time reasoning work once, a human reviews it once, and a deterministic script runs the result forever after at effectively zero marginal cost.

## The Problem

Picture two testers on the same RBAC project, each making the opposite mistake.

The first tester loves the Planner and Generator agents from the Playwright Test Agents lesson and, having seen how well they work, wires an agent into the CI pipeline itself — every pull request re-generates and re-runs the entire login and permission-matrix suite through an LLM instead of running the committed `.spec.ts` files directly. The suite that used to finish in ninety seconds on `npx playwright test` now takes several minutes and consumes a meaningful amount of tokens on every single push, to re-derive tests for flows that have not changed in months.

The second tester has the opposite instinct. The RBAC app just shipped a new appointment-cancellation confirmation flow — a modal, a reason dropdown, a toast — and nobody has scripted against it yet. Distrustful of agents after reading the Self-Healing Tests lesson's warning about over-confident healers, this tester opens the browser and clicks through the new modal by hand for twenty minutes, inspecting DOM structure in dev tools to find the right locators before writing a single line of TypeScript.

Neither tester is wrong to be careful. Both are solving the wrong problem with the wrong tool. The first task is a known, stable, already-scripted flow — it should never touch an agent again after it was first committed. The second task is exactly the kind of unfamiliar exploration an MCP-connected agent handles in a fraction of the time a human spends clicking through dev tools, precisely because the Playwright MCP lesson built it to read an accessibility-tree snapshot instead of guessing at markup by eye.

## The Concept

The decision this module teaches has a single axis: **how much do you already know about the page state and flow you're testing?**

- **Unfamiliar page state.** You're exploring a part of the RBAC app you haven't scripted against before, or a flow whose steps aren't fully clear yet — a new feature, an edge case nobody has documented, a screen you've never opened. Here, iterative reasoning about what's actually on the page is the expensive part, and that's exactly what the Playwright Test Agents lesson's Planner/Generator and the Playwright MCP lesson's MCP-driven exploration are for. An agent inspecting a live accessibility tree and proposing a plan is faster and more thorough than you clicking through dev tools node by node.
- **Known, stable flow.** The login test. The RBAC permission matrix from earlier in this course, once it's scripted. Any flow you have already run, reviewed, and committed. There is nothing left to discover — the locators are known, the assertions are known, the only thing left to do is execute the same deterministic steps every time. A hand-written script does this at a fraction of the cost and time of an agentic run, with zero variance between executions, which is exactly the property a CI gate needs.

The cost difference is not subtle. A scripted `npx playwright test` run drives a real browser through fixed, pre-written steps — no inference, no token cost beyond the test process itself, finished in seconds to a couple of minutes depending on suite size. An agentic run — Planner reasoning about a goal, Generator drafting code, or an MCP client interpreting a live accessibility snapshot to decide its next click — invokes an LLM at each reasoning step, at real per-token cost, and takes meaningfully longer wall-clock time per action than a script executing a locator it already knows is correct. Neither fact makes agents not worth using. It makes them worth using *once*, for the part of the job that actually requires reasoning, and never again for the part that doesn't.

That's why this course's position, stated plainly, is: agents belong in exploration, spec generation, and healing (the last three lessons) — never in routine CI execution (covered in the continuous integration lesson). Routine CI runs the deterministic suite: hand-written specs, or agent-drafted specs that a human has already reviewed and committed. The agent's job ends the moment a reviewed spec lands in version control. From that point forward, the flow is known, and the continuous integration lesson's pipeline runs it the cheap, fast, deterministic way, indefinitely.

Notice that both paths converge on the same destination: a committed spec running deterministically in CI. The agent's involvement is a one-time cost paid once, at the point where reasoning is genuinely required. Everything downstream of that commit is exactly as cheap and fast as any other test in your suite.
