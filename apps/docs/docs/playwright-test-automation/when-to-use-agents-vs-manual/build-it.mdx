# When to Use Agents vs. When to Write the Test Yourself — Hands On

⏱ 25 minutes

## Breaking It Down

The RBAC app's maintainers just shipped a new appointment-cancellation confirmation flow: cancelling an appointment now opens a modal asking for a cancellation reason from a dropdown, requires an explicit "Confirm Cancellation" click, and shows a toast before the appointment's row updates to a "Cancelled" status. The RBAC permission matrix already tells you *who* can cancel — Doctor: yes, Nurse: yes, Admin: no, Patient: no — but nobody has scripted *this exact flow* yet, and you've never opened the new modal. That combination — a known permission, an unfamiliar UI — is exactly the case this module's decision framework exists for.

### Step 1: Recognize This as an Exploration Task First

Before writing anything, apply this lesson's framework honestly: is this a known, stable flow, or unfamiliar page state? The *permission* is known (from the RBAC permission-matrix lesson), but the *flow* — the modal, the dropdown, the confirmation step, the toast — is not. You have never seen this DOM. That answer routes you to the Playwright MCP lesson's MCP exploration before the Playwright Test Agents lesson's Generator, not straight to hand-writing a spec from a guess.

### Step 2: Explore the Unfamiliar Modal Through MCP

With your MCP client connected to `@playwright/mcp` and already authenticated as a nurse (the Playwright MCP lesson's `storageState` session-persistence pattern, so no login flow burns tokens on every exploration step), navigate to the dashboard and ask the agent to open the cancellation flow for an existing appointment:

```text title="MCP client prompt"
Navigate to /dashboard, find an appointment row that can be cancelled,
click its cancel action, and give me an accessibility snapshot of
whatever appears.
```

The agent drives `browser_navigate`, `browser_click`, and `browser_snapshot` and returns a tree, not a screenshot:

```text title="Accessibility snapshot (abridged)"
- dialog "Cancel Appointment"
  - text "Why are you cancelling this appointment?"
  - combobox "Cancellation reason"
    - option "Patient requested"
    - option "Scheduling conflict"
    - option "No longer needed"
  - button "Confirm Cancellation"
  - button "Keep Appointment"
- status "Appointment cancelled" (appears after confirm)
```

This is the payoff the Playwright MCP lesson promised: three tool calls and a tree read gave you the entire shape of a modal you'd otherwise have had to click through by eye and inspect in dev tools. You now know the accessible names of every control you need — `combobox "Cancellation reason"`, `button "Confirm Cancellation"`, and the `status` role the toast uses — before writing a single line of TypeScript.

### Step 3: Hand the Goal to Planner and Generator

With the flow's shape known, hand a goal to the same Planner/Generator workflow from the Playwright Test Agents lesson:

```text title="Agent goal"
As a nurse, cancel an appointment giving the reason "Scheduling conflict",
confirm the cancellation, and verify the appointment's status updates to
Cancelled in the dashboard list.
```

The Generator returns a first draft:

```typescript title="Generator draft — tests/appointment-cancellation.spec.ts (NOT YET REVIEWED)"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'auth/nurse.json' });

test('nurse cancels an appointment with a reason', async ({ page }) => {
  await page.goto('/dashboard');
  await page.locator('.appointment-row').first().locator('.cancel-btn').click();
  await page.getByRole('combobox', { name: 'Cancellation reason' }).selectOption('Scheduling conflict');
  await page.getByRole('button', { name: 'Confirm Cancellation' }).click();
  await page.waitForTimeout(1000);
  await expect(page.locator('.appointment-row').first()).toContainText('Cancelled');
});
```

### Step 4: Review the Draft — Don't Merge on Sight

This is where the Self-Healing Tests lesson's diff-review discipline applies to a *generated* draft exactly as it applied to a *healed* one: read it like a pull request from a fast but context-blind contributor, not a finished artifact. Three problems surface immediately:

1. **A brittle CSS fallback locator.** `.appointment-row` and `.cancel-btn` are class-name selectors — the locators lesson's priority order puts `getByRole`/`getByLabel`/`getByText` first precisely because class names churn with every styling pass, and the accessibility snapshot from Step 2 already gave you role-based alternatives.
2. **A smuggled hardcoded wait.** `page.waitForTimeout(1000)` is exactly the anti-pattern the actions-and-web-first-assertions lesson warns against — it guesses at how long the cancellation takes to process and either wastes time or flakes under load, instead of waiting on a real, observable condition.
3. **An assertion that isn't web-first on the thing that actually confirms success.** The toast that Step 2's snapshot showed as a `status` role is never asserted at all — the draft only checks the row's text after an arbitrary sleep, which is weaker than asserting the toast Playwright's auto-waiting can actually retry on.

### Step 5: Fix the Draft by Hand

Apply the fixes directly, using the accessible names the MCP exploration already handed you:

```typescript title="tests/appointment-cancellation.spec.ts (reviewed)"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'auth/nurse.json' });

test('nurse cancels an appointment with a reason', async ({ page }) => {
  await page.goto('/dashboard');

  const firstAppointment = page.getByRole('row').filter({ hasText: 'Scheduled' }).first();
  await firstAppointment.getByRole('button', { name: 'Cancel' }).click();

  const dialog = page.getByRole('dialog', { name: 'Cancel Appointment' });
  await dialog.getByRole('combobox', { name: 'Cancellation reason' }).selectOption('Scheduling conflict');
  await dialog.getByRole('button', { name: 'Confirm Cancellation' }).click();

  await expect(page.getByRole('status')).toHaveText('Appointment cancelled');
  await expect(firstAppointment).toContainText('Cancelled');
});
```

Every locator here is role-based and traceable straight back to the Step 2 snapshot. Both assertions are web-first `expect(locator)...` calls that retry on their own — the toast assertion first, because it's the earliest observable signal of success, then the row-status assertion, with no `waitForTimeout` anywhere doing the waiting's job for it.

### Step 6: Verify Locally, Then Commit It to Run in CI Forever

Run the reviewed spec against your local servers:

```bash
npx playwright test tests/appointment-cancellation.spec.ts
```

Once it passes cleanly, commit it to your fork the same way you'd commit any hand-written spec:

```bash
git add tests/appointment-cancellation.spec.ts
git commit -m "Add appointment-cancellation flow test"
git push
```

From this point forward, the continuous integration lesson's GitHub Actions workflow runs this spec on every push and pull request exactly like every other test in your suite — as a plain scripted Playwright test, with no Planner, no Generator, no MCP client, and no LLM inference involved in any subsequent run. The agent's job was to shorten the distance between "I don't know this flow" and "here's a reviewed, correct spec." Once that spec exists in version control, the flow is no longer unfamiliar, and this lesson's own decision framework says the tool for a known, stable flow is a hand-written script running deterministically — which is precisely what you now have.

## How It Works Internally

The cost asymmetry this lifecycle is built around is structural, not incidental. An agentic step — Planner reasoning about a goal, an MCP client interpreting a live accessibility snapshot to pick its next action — necessarily invokes an LLM, at real per-token cost, for every decision it makes along the way. A scripted step executes a locator and an assertion that were already decided, once, ahead of time; there is no inference in the loop, only browser automation, which is why `npx playwright test` runs an entire suite in roughly the time a single agentic exploration step takes to reason about one page. The lifecycle in this lesson pays the inference cost exactly once, at Steps 2 and 3, where reasoning about something unknown is genuinely the expensive but necessary part. Every run after Step 6 pays none of it, because nothing about the flow is unknown anymore — it's a fixed sequence of steps a human already verified, and fixed sequences are exactly what a deterministic test runner is for.
