# When to Use Agents vs. When to Write the Test Yourself: Common Mistakes

⏱ 9 minutes

## When NOT to Use This

The decision framework in this module has a narrow, specific job: deciding which tool drafts or repairs a *given* test. It does not apply once a spec is already committed and passing. At that point the answer is always "run it as a plain script," full stop, with no re-evaluation needed on every run. Don't reach for an agent:

- **On any flow already covered by a committed, passing spec.** The RBAC permission matrix, the login flow, anything reviewed and merged: these are known and stable by definition. Re-deriving them through an agent on every CI run adds cost and latency for zero additional information.
- **Inside the routine CI pipeline itself (covered in the continuous integration lesson).** CI's job is to execute a known suite as fast and deterministically as possible. An LLM in that loop makes every run slower, more expensive, and (because inference is not bit-for-bit reproducible the way a script is) very slightly less deterministic than the pipeline is designed to be.
- **As a substitute for actually understanding a new flow before shipping the test.** MCP exploration (covered in the Playwright MCP lesson) and Generator drafts (covered in the Playwright Test Agents lesson) shorten the distance to a first correct spec. They don't remove the requirement that a human reads and understands what got committed.

## The Pattern to Remember

- **Pattern:** when the page state or flow is unfamiliar, send it to Planner, Generator, and MCP exploration once. A human reviews that draft once, and from there the reviewed spec gets committed and runs as a deterministic script in CI forever after.
- **When to use an agent:** you're exploring a part of the app you haven't scripted before, drafting a first-pass spec for a new flow, or repairing locator drift on an existing one (covered in the self-healing tests lesson).
- **When NOT to use an agent:** the flow is already known, stable, and committed. Just run it as a script, every time, in CI.
- **Mental model:** think of an agent as the surveyor who maps unfamiliar terrain once, and the committed script as the road built afterward that everyone drives on for free. You don't send the surveyor out again every time a car needs to make the same trip.

## Common Mistakes

### Mistake 1: Wiring an Agent into Routine CI Execution

**Mistake:** Replacing `npx playwright test` in the GitHub Actions workflow from the continuous integration lesson with an agentic run that re-derives or re-executes the suite through an LLM on every push.

**Why it happens:** Having just seen how capable the Planner, Generator, and Healer agents are, it's tempting to assume "more AI" is strictly better everywhere, including the parts of the pipeline that were never the bottleneck.

**Symptoms:** CI runs that used to finish in under two minutes now take significantly longer and consume real token cost on every single commit, for a suite that hasn't functionally changed in weeks.

**Fix:** Keep the continuous integration lesson's CI job running the committed `.spec.ts` files directly, exactly as scripted. Reserve agents for the one-time drafting and healing work that happens *before* a spec reaches `main`, never for the repeated execution that happens after.

### Mistake 2: Hand-Exploring an Unfamiliar Flow Instead of Using MCP

**Mistake:** Clicking through a brand-new feature (like the appointment-cancellation modal in Build It) manually in a browser and inspecting DOM nodes in dev tools to find locators, instead of using the MCP-connected agent from the Playwright MCP lesson to get an accessibility-tree snapshot in three tool calls.

**Why it happens:** Manual exploration feels more "hands-on" and trustworthy, especially right after the self-healing tests lesson's warning about over-trusting agent output.

**Symptoms:** Twenty minutes spent clicking and inspecting to reconstruct information an MCP snapshot would have returned in seconds, and the resulting locators are often worse, because dev-tools inspection tends to surface whatever class name happens to be visible rather than the accessible role the locators lesson tells you to prefer.

**Fix:** For genuinely unfamiliar page state, start with an MCP snapshot. It's not a replacement for understanding the flow (you still read the tree yourself) but it's a faster and more reliable way to get there than manual DOM archaeology.

### Mistake 3: Merging a Generated Draft Without Reading It

**Mistake:** Taking a Generator's first draft (like the one in Build It with `.appointment-row`, `.cancel-btn`, and a `waitForTimeout(1000)`) and committing it straight to the suite because it passed once locally.

**Why it happens:** A generated spec that runs green looks finished, and it's easy to extend the same trust you'd give a human-written passing test to output that merely resembles one.

**Symptoms:** A suite that accumulates brittle CSS-class locators and hidden sleeps over time, each one indistinguishable from a hand-written mistake until someone hunts through the file, and flakiness that traces back to arbitrary timeouts nobody remembers adding.

**Fix:** Apply the exact review habit from the self-healing tests lesson's healed-diff checklist to generated drafts too: check locator quality against the locators lesson's `getByRole`/`getByLabel`/`getByText` priority, check that every wait is a web-first `expect(locator)...` assertion per the actions-and-web-first-assertions lesson, and check that assertions actually verify the behavior that matters, not just whatever the draft happened to check first.

### Mistake 4: Re-Running the Agent Instead of Editing the Committed Spec

**Mistake:** Whenever the appointment-cancellation spec needs a small change (a new cancellation reason added to the dropdown, say) regenerating the whole spec from scratch through the Planner/Generator workflow instead of editing the existing, reviewed file directly.

**Why it happens:** It feels consistent to always use "the same process" that produced the original spec, especially if the agent workflow is fast and convenient to invoke.

**Symptoms:** Every small change churns the entire spec's structure and locators, discarding the review history and confidence built up around the previous version, and every regeneration has to be re-reviewed in full instead of reviewing one small diff.

**Fix:** Once a spec is committed, treat it as ordinary hand-maintained code. Small changes get small, hand-written diffs reviewed like any other pull request. Reach for Planner/Generator again only when the flow itself changes enough that you're effectively exploring something new, not for routine maintenance of something already known.

### Mistake 5: Treating "Agent-Generated" as a Permanent Excuse to Skip Scrutiny

**Mistake:** Assuming that because a spec originated from an agent, any future failure it reports must also be something an agent should silently resolve, routing every red run on that spec straight to the Healer without asking whether it's catching a real regression.

**Why it happens:** It's an easy category error to carry the file's origin forward as a permanent label, as if "agent-drafted" and "needs agent maintenance forever" were the same fact.

**Symptoms:** A real regression on the cancellation flow (say, the confirm button silently stops requiring a reason) gets routed straight into the self-healing tests lesson's healing workflow and risks the exact failure mode that lesson warns about: an assertion quietly rewritten to match the bug instead of a human investigating why a known-good test just went red.

**Fix:** Once a spec is committed, its origin stops mattering. A failing test is a failing test. Investigate it the same way regardless of whether a human or an agent wrote the original draft, and apply the self-healing tests lesson's locator-drift-versus-regression judgment every time, not just for specs you personally hand-wrote.
