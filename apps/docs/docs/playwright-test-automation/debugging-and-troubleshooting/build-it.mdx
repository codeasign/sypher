# Debugging and Troubleshooting — Hands On

⏱ 30 minutes

## Breaking It Down

### Step 1: Time-Travel a Passing Test in UI Mode

With both servers running (backend `:5000`, frontend `:3002`), create `tests/nurse-appointments.spec.ts` using the `nurse` storage-state project from the authentication lesson:

```typescript title="tests/nurse-appointments.spec.ts"
import { test, expect } from '@playwright/test';

test('nurse can view all appointments', async ({ page }) => {
  await page.goto('/dashboard');

  await expect(page.getByRole('heading', { name: 'All Appointments' })).toBeVisible();

  const appointmentRows = page.getByRole('row');
  await expect(appointmentRows).toHaveCount(23); // 22 seeded + header row
});
```

Open UI mode instead of running headless:

```bash
npx playwright test tests/nurse-appointments.spec.ts --ui --project=nurse
```

Run the test, then click through the timeline at the top of the window — `goto`, each `expect`, each intermediate wait — one frame at a time. Selecting any step shows the exact DOM snapshot at that instant, plus the action log and matched locator on the right. This is what "time travel" means concretely: you're not reading a description of what happened, you're looking at the actual page as it existed at that step.

Toggle watch mode (the eye icon in the top-left of the test list). Change the expected count from `23` to `24`, save the file, and watch the test re-run automatically and fail — no need to switch back to a terminal and re-type the command. Change it back to `23` before continuing.

### Step 2: Simulate a Failed CI Run and Capture a Trace

CI runs headless, unattended, and typically only enables tracing on the first retry (the `trace: 'on-first-retry'` setting from `playwright.config.ts` in Setup) rather than always — full tracing is relatively expensive, so it's normally reserved for the runs most likely to need it. To reproduce that here, force a failure and capture a trace from the command line the same way CI would:

```typescript title="tests/nurse-appointments.spec.ts"
import { test, expect } from '@playwright/test';

test('nurse can view all appointments', async ({ page }) => {
  await page.goto('/dashboard');

  // Deliberately wrong text, to force a realistic-looking CI failure
  await expect(page.getByRole('heading', { name: 'Every Appointment' })).toBeVisible();
});
```

```bash
npx playwright test tests/nurse-appointments.spec.ts --project=nurse --trace=on --retries=1
```

`--trace=on` forces a trace to be written regardless of pass or fail, giving you a `trace.zip` to work with. Find it under `test-results/<test-name>/trace.zip`, or generate the HTML report and let it point you to the same file:

```bash
npx playwright show-report
```

### Step 3: Open the Trace and Find the Real Failure Point

Open the trace file directly, the way you would after downloading a `trace.zip` artifact from a failed GitHub Actions run:

```bash
npx playwright show-trace test-results/nurse-appointments-nurse-can-view-all-appointments-nurse/trace.zip
```

Trace viewer opens with three things worth checking, in order:

1. **The timeline and DOM snapshot.** Click the final `expect` step. The DOM snapshot shows the actual page at the moment the assertion gave up — in this run, a heading that reads `All Appointments`, not `Every Appointment`. That alone confirms the assertion text was simply wrong, and you could stop here for this particular failure.
2. **The network tab.** Select the `goto` step and open the network tab below it. Every request the page made during that step is listed, including `GET http://localhost:5000/api/appointments`. Click it — you can see the request headers (including the `Authorization: Bearer <jwt>` header supplied by the nurse's storage state), the response status, and the full response body. This is where you'd look if the DOM snapshot showed an empty table or an "Access Denied" screen instead of data: a `401` or `403` here would immediately tell you it's an authentication problem, not a rendering one, without you having to guess.
3. **The console tab.** Still on the same step, switch to the console tab. Any `console.error` or `console.warn` the React app logged during that step shows up here — for example, a caught fetch failure the frontend logs before falling back to an error state. This is often the fastest way to catch a bug the DOM snapshot alone doesn't make obvious.

Now imagine a variant of this same failure that's genuinely worth the full three-tab walkthrough: the assertion text is correct (`All Appointments`), but the heading never appears at all. Opening the trace, the DOM snapshot shows an "Access Denied" screen instead of the appointments table. The network tab on the `goto` step shows `GET /api/appointments` returned `401 Unauthorized` — not because the nurse account is misconfigured, but because the `nurse.json` storage state file used in this run was captured hours earlier by a previous CI job and its JWT had since expired. The console tab confirms it: `Failed to fetch appointments: 401`. Nothing about this is a locator problem or a nurse-permissions bug — it's the authentication lesson's `globalSetup` producing a session that outlived its own token, and the fix belongs in how often storage state gets regenerated, not in this spec at all. You only know that with confidence because you checked the network tab instead of guessing from the timeout message alone.

Revert the spec's assertion text back to `'All Appointments'` before continuing.

### Step 4: Scaffold a New Spec with codegen

Record a real interaction instead of hand-writing it from scratch. With both servers running:

```bash
npx playwright codegen http://localhost:3002
```

In the browser window that opens, log in as a nurse and schedule a new appointment (seeded nurse credentials are in your setup `npm run seed` output). Click through the login form, navigate to the scheduling form, pick a patient and a doctor from the dropdowns, and submit. Watch the Inspector window generate code as you go — it produces something close to:

```typescript
await page.getByLabel('Username').fill('nurse_seeded_username');
await page.getByLabel('Password').fill('seeded_password');
await page.getByRole('button', { name: 'Log In' }).click();
await page.getByRole('button', { name: 'Schedule Appointment' }).click();
await page.getByLabel('Patient').selectOption('Patient Name');
await page.getByLabel('Doctor').selectOption('Doctor Name');
await page.locator('form.schedule-form > button.btn-submit').click();
```

Notice that the first five lines and the last one aren't quite the same quality. The first five resolve to `getByLabel` and `getByRole`, because the login form and the scheduling button both have proper accessible labels and roles — codegen reaches for those first, the same way it did the first time you used it. The last line is different: `page.locator('form.schedule-form > button.btn-submit')` is a CSS selector, which means codegen couldn't find an accessible role or label for the form's actual submit button and fell back to structure instead.

This is exactly the situation the course's locator conventions from [the locators lesson](../locators/overview) warn about. Don't commit that last line as-is. Go back to the RBAC frontend, check what the submit button actually renders — in this case it's a `<button>` with visible text "Confirm Schedule" that simply wasn't picked up because a wrapping `<div>` intercepted the accessible name — and upgrade the locator by hand:

```typescript title="tests/nurse-schedule.spec.ts"
import { test, expect } from '@playwright/test';

test('nurse can schedule a new appointment', async ({ page }) => {
  await page.goto('/dashboard');

  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption('Patient Name');
  await page.getByLabel('Doctor').selectOption('Doctor Name');
  await page.getByRole('button', { name: 'Confirm Schedule' }).click();

  await expect(page.getByText('Appointment scheduled')).toBeVisible();
});
```

Treat every codegen session this way: record it for speed, then read every generated line and ask whether it's the locator a real user's assistive technology would use, or a structural fallback codegen only reached for because nothing better existed. Upgrade the second kind before it ever reaches a commit.

### Step 5: Diagnose a Flaky Test with `--repeat-each`

The scheduling flow you just wrote has a subtle timing issue: after confirming, the appointments table re-renders twice in quick succession — once optimistically, then again once the server response actually lands — and a test that clicks a freshly-created row too early can occasionally hit a detached element. Extend the spec to click the new row after scheduling:

```typescript title="tests/nurse-schedule.spec.ts"
import { test, expect } from '@playwright/test';

test('newly scheduled appointment appears in the table', async ({ page }) => {
  await page.goto('/dashboard');

  await page.getByRole('button', { name: 'Schedule Appointment' }).click();
  await page.getByLabel('Patient').selectOption('Patient Name');
  await page.getByLabel('Doctor').selectOption('Doctor Name');
  await page.getByRole('button', { name: 'Confirm Schedule' }).click();

  const newRow = page.getByRole('row', { name: /Patient Name.*Doctor Name/ });
  await expect(newRow).toBeVisible();
  await newRow.getByRole('button', { name: 'View Details' }).click();

  await expect(page.getByRole('heading', { name: 'Appointment Details' })).toBeVisible();
});
```

Run it once and it probably passes. That tells you almost nothing — a single pass or fail is a coin flip's worth of evidence for a suspected race. Instead, measure it:

```bash
npx playwright test tests/nurse-schedule.spec.ts --project=nurse --repeat-each=20
```

`--repeat-each=20` runs the exact same test 20 times in a row and reports each result individually — it's a diagnostic instrument, not a fix, and critically it is not the same thing as retries. Suppose the output shows 2 failures out of 20: that's real, measurable evidence of roughly a 1-in-10 flake rate, caused by `newRow.getByRole('button', ...)` occasionally resolving against the optimistic row right before it gets replaced by the server-confirmed one. Compare that against running it in a different browser project to rule out a browser-specific rendering timing difference:

```bash
npx playwright test tests/nurse-schedule.spec.ts --project=nurse --repeat-each=20 --workers=1
```

If the failure rate holds steady across repeats regardless of worker count, you've ruled out cross-test interference and confirmed it's isolated to this one interaction. Only now, with an actual measured rate and a specific mechanism identified, do you fix the real cause — in this case, asserting on the settled state before interacting with it, rather than clicking as soon as any matching row appears:

```typescript title="tests/nurse-schedule.spec.ts"
const newRow = page.getByRole('row', { name: /Patient Name.*Doctor Name/ });
await expect(newRow).toBeVisible();
await expect(newRow).not.toHaveClass(/optimistic/); // wait for the server-confirmed render
await newRow.getByRole('button', { name: 'View Details' }).click();
```

Re-run `--repeat-each=20` again to confirm the failure count is now zero, not just lower. Never treat `retries: 2` in `playwright.config.ts` as the fix here — retries hide exactly this kind of race by quietly re-running until it happens to pass, which turns a real, fixable timing bug into a permanently green checkmark that occasionally runs twice for no visible reason.

## How It Works Internally

A `trace.zip` file is not a single log — it's a self-contained archive of everything Playwright's tracing recorder captured during the run: a full-fidelity DOM snapshot before and after every action, a HAR-format record of every network request and response, all console output, and a screenshot at each step. Trace viewer is just a UI for replaying that archive; `npx playwright show-trace` works completely offline because nothing in a trace depends on the original test run still being reachable — you can open a trace file weeks later, on a different machine, long after the CI runner that produced it is gone.

`--repeat-each` and `retries` sound similar but measure opposite things. `--repeat-each=N` runs a test `N` times unconditionally and reports every result, which is what makes it useful for measuring a flake rate. `retries` re-runs a test only after it fails, and only up to the configured limit, stopping at the first pass — which is exactly why using `retries` to "fix" a flaky test doesn't fix anything; it just hides the failure behind an extra attempt, and the underlying race is still there the next time it's unlucky.
