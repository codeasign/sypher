# Debugging and Troubleshooting

⏱ 18 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Time-travel through a test's actions in UI mode (`npx playwright test --ui`) and use watch mode to re-run automatically as you edit a spec
- Open a trace file from a failed CI run with `npx playwright show-trace trace.zip` and read its network tab, console tab, and DOM snapshots to find the actual failure point
- Use `npx playwright codegen http://localhost:3002` to scaffold a new spec quickly, and know exactly which parts of its output need review before you trust them
- Diagnose a flaky test systematically with `--repeat-each` and Playwright's retry mechanism, distinguishing a test that always fails from one that fails 1 run in 10, and a browser-specific failure from a universal one

## Why This Matters

Every module up to this point has taught you how to write a correct test. None of them has taught you what to do the moment a test stops being correct — and on a suite this size, testing four roles across dashboards, permissions, network calls, and visual state, that moment arrives constantly. A test that passes on your machine and fails in CI. A test that passes nine times out of ten. A test whose failure message is a 30-second timeout and nothing else.

The instinct under pressure is to guess: add a `console.log`, add a longer wait, re-run it and hope. That instinct is expensive, because guessing scales linearly with how confusing the failure is, while reading a trace does not — a five-minute trace-viewer session tells you definitively whether a failure was a locator problem, a network problem, or an actual application bug, regardless of how confusing the symptom looked from the outside. The tools in this lesson — UI mode, trace viewer, codegen, and systematic flake diagnosis — are what make debugging a fixed-cost activity instead of an open-ended one.

## The Problem

Picture a CI run against the RBAC app that fails with nothing more than this:

```text
1) [chromium] › tests/nurse-appointments.spec.ts:12:5 › nurse can view all appointments

    Error: Timed out 5000ms waiting for expect(locator).toBeVisible()

    Locator: getByRole('heading', { name: 'All Appointments' })
    Expected: visible
    Received: <element(s) not found>
```

That's everything the console gives you. It doesn't tell you whether the heading text changed, whether the nurse's session failed to authenticate, whether the backend returned an error, or whether the frontend simply rendered slower than usual that run. Every one of those has the same surface symptom — a locator that never became visible — and a completely different fix. Without more information, "debugging" this is just guessing which of the four it is and hoping you're right on the first try.

## The Concept

Playwright gives you three tools that each answer a different question, and knowing which one to reach for is most of what this lesson teaches:

- **UI mode** (`npx playwright test --ui`) answers "what is happening right now, while I'm actively writing or re-running this test on my own machine?" It's interactive and local — you watch a test run, time-travel through its steps, and re-run it on every save via watch mode.
- **Trace viewer** (`npx playwright show-trace trace.zip`) answers "what happened during a run I wasn't watching?" — most importantly, a CI run. A trace file is a complete, replayable recording: a DOM snapshot at every action, every network request and response the test made, and every line the browser's console logged. You open it after the fact, with no ability to interact with the live app, and it still tells you exactly what happened.
- **`codegen`** answers a different kind of question entirely: "what's a fast first draft of a new spec?" It records real clicks and fills against the RBAC app and turns them into Playwright code — a starting point you review and upgrade, never a finished test you commit unread.

A fourth situation doesn't have a single tool — it has a method. A flaky test (one that fails intermittently) can't be diagnosed by staring at one failure, because the interesting information is in the *pattern* across many runs: does it fail 1 time in 10, or 9 times in 10? Only in Firefox, or everywhere? Playwright's `--repeat-each` flag and its retry mechanism exist for exactly this — used as measurement tools before you touch a single line of test code, not as a way to paper over the failure.
