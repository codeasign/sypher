# Debugging and Troubleshooting — Common Mistakes

⏱ 8 minutes

## When NOT to Use This

UI mode is a local, interactive tool — it has no place in a CI pipeline, and trying to run `--ui` on a headless runner will simply fail to open a window. CI is exactly where trace viewer earns its keep instead: capture with `trace: 'on-first-retry'` or `trace: 'retain-on-failure'` in `playwright.config.ts`, upload `trace.zip` as a build artifact, and open it locally afterward with `npx playwright show-trace`.

Not every failure needs this level of investigation, either. If a test fails with a message that already tells you exactly what's wrong — a straightforward assertion mismatch where the DOM snapshot in the HTML report's inline screenshot already makes the cause obvious — opening the full trace viewer is a few extra seconds you don't always need to spend. Reserve the deep walkthrough (network tab, console tab, step-by-step DOM snapshots) for failures where the one-line error message genuinely isn't enough, which in practice is most CI failures but not literally every one.

And `--repeat-each` is a diagnostic step, not a permanent part of your test suite. Once you've measured a flake rate and fixed the underlying cause, running every spec 20 times on every commit would make your CI pipeline unusably slow for no ongoing benefit — reach for it when you suspect a specific test, confirm the fix worked, then drop it from your regular run.

## The Pattern to Remember

- **Pattern:** reach for UI mode while you're actively writing or re-running a test locally; reach for trace viewer's network, console, and DOM-snapshot tabs to diagnose a failure you weren't there to watch; treat codegen output as a first draft that always gets a locator review; treat `--repeat-each` and retries as measurement tools that answer "how often and where," never as the fix itself.
- **When to use:** every confusing failure, from here forward — the goal is to make "I don't know why this failed" a five-minute problem instead of an open-ended one.
- **When NOT to use:** UI mode in CI (use trace capture instead), full trace walkthroughs for failures a one-line error message already explains, `--repeat-each` as a permanent fixture in your regular test run, or `retries` as a substitute for fixing a known race.
- **Mental model:** UI mode is a dashboard camera — useful while you're driving. Trace viewer is the black box recorder — useful after the fact, precisely because it doesn't need you to have been watching. `--repeat-each` is a diagnostic test, not a treatment.

## Common Mistakes

### Mistake 1: Raising `retries` Instead of Diagnosing with `--repeat-each`

**Mistake:** A test starts failing intermittently in CI, and the fix is to bump `retries: 2` to `retries: 3` in `playwright.config.ts` and move on.

**Why it happens:** Retries make the symptom disappear immediately, with a one-line config change, while actually diagnosing a race takes real investigation. Under deadline pressure, the config change looks like the cheaper option.

**Symptoms:** The same test keeps needing "just one more retry" every few months as the underlying race gets slightly more or less likely to trigger. CI gets slower — every retried test reruns its full setup — and nobody remembers why this particular spec needs more retries than the others, because the actual cause was never identified, only hidden.

**Fix:** When a test is flaky, run it with `--repeat-each=20` (Step 5, Build It) before touching `retries` at all. That gives you an actual failure count and lets you isolate the mechanism — a race condition, a stale locator, a browser-specific timing difference — so you can fix the thing that's actually wrong. `retries` exists for genuinely transient infrastructure blips (a CI runner's momentary network hiccup), not as a stand-in for fixing your own test's race condition.

### Mistake 2: Committing codegen Output's Brittle Selectors Unreviewed

**Mistake:** Recording a flow with `npx playwright codegen http://localhost:3002`, pasting the output directly into a spec, and committing it — including any `page.locator('form.schedule-form > button.btn-submit')`-style CSS selector codegen fell back to.

**Why it happens:** The recording runs successfully the moment you paste it in, which feels like proof it's correct. Reviewing every generated line for locator quality feels like an extra step when the test already passes.

**Symptoms:** The very next unrelated frontend change — a wrapping `<div>` added around a button, a class rename during a styling pass — breaks the test, even though the button's visible role and text never changed. The failure has nothing to do with the feature the test is supposed to verify.

**Fix:** Treat every codegen session the way Step 4 of Build It does: record for speed, then read every line and replace structural fallbacks with `getByRole`/`getByLabel` wherever the underlying element actually has an accessible name — per [the locators lesson](../locators/overview)'s locator conventions. If codegen fell back to CSS, that's often a real accessibility gap in the RBAC frontend worth flagging, not just a test-authoring inconvenience.

### Mistake 3: Not Enabling Trace Capture in CI, So There's Nothing to Open

**Mistake:** Leaving `trace` unset (or `'off'`) in `playwright.config.ts` for the CI project, then trying to debug a CI-only failure with nothing but the console log.

**Why it happens:** Trace capture has a small performance and storage cost, and `trace: 'off'` is easy to overlook as "fine for now" while a suite is still small — until the exact moment a hard-to-reproduce CI-only failure shows up and there's no artifact to inspect.

**Symptoms:** A failure that only reproduces in CI, never locally, and the only evidence is the same one-line timeout message from the Problem section of this lesson's Overview — with no DOM snapshot, no network log, and no console output to narrow it down.

**Fix:** Set `trace: 'on-first-retry'` (captures a trace only on a test's first retry, keeping cost low) or `'retain-on-failure'` in `playwright.config.ts`, and upload `test-results/` as a build artifact in CI so `trace.zip` files survive the run. Do this before you need it — a trace setting added after a mysterious failure can't retroactively capture a run that already happened.

### Mistake 4: Guessing at the Cause Instead of Checking the Network Tab

**Mistake:** Seeing a test fail on `expect(locator).toBeVisible()` and immediately assuming it's a locator problem — rewriting the selector, adding more specific text matching, trying `getByTestId` instead — without first checking whether the element failed to appear because the underlying API call never succeeded.

**Why it happens:** The error message names a locator, so it's natural to assume the locator itself is at fault. Locator syntax is also the part of the test you have the most direct control over, so it feels like the obvious place to start.

**Symptoms:** Time spent rewriting a locator that was already correct, followed by the same failure recurring, because the actual cause — as in Step 3 of Build It, where a `401` from `/api/appointments` was hiding behind what looked like a rendering timeout — was never in the DOM at all.

**Fix:** Before touching a locator, open the trace and check the network tab for the request the failing UI depends on. A non-2xx response, an unexpectedly empty payload, or a request that never fired at all tells you immediately whether you're looking at a frontend rendering bug, a backend/API bug, or a stale session — three different fixes that a locator rewrite won't touch.

### Mistake 5: Debugging Headless with `console.log` Instead of Opening UI Mode

**Mistake:** Sprinkling `console.log()` calls throughout a spec and re-running it headless repeatedly to narrow down where it's failing, instead of running `npx playwright test --ui` and time-traveling through the actual steps.

**Why it happens:** `console.log` debugging is a habit that transfers from ordinary application code, and it feels like it's making progress because you get new output on every run.

**Symptoms:** Several headless re-runs and a handful of temporary log statements later, you still don't know what the page actually looked like at the failing step — because a log line tells you what your test code did, not what state the RBAC app's UI was actually in when it did it.

**Fix:** Default to `npx playwright test --ui` while actively debugging, as shown in Step 1 of Build It. A single time-traveled run shows you the real DOM snapshot at the exact failing step, which is strictly more information than any number of log statements, and it costs you one command instead of several edit-and-rerun cycles.
