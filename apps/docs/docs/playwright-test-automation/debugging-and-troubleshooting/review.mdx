# Debugging and Troubleshooting: Review

⏱ 3 minutes

## Key Takeaways

- `npx playwright test --ui` gives you a local, interactive view of a run (time-travel through each action's DOM snapshot, plus watch mode to re-run automatically on save) and it's meant to be your default while actively writing or debugging a test, not a last resort.
- `npx playwright show-trace trace.zip` replays a run you weren't watching, most importantly a CI failure, entirely offline. Its network tab, console tab, and step-by-step DOM snapshots together tell you whether a failure was a locator problem, a network/auth problem, or a real application bug.
- `npx playwright codegen http://localhost:3002` scaffolds a spec fast by recording real interactions, but its output is always a first draft. Every generated locator needs review, and any CSS/structural fallback should be upgraded to `getByRole`/`getByLabel` before it's committed.
- `--repeat-each=N` runs a suspected-flaky test N times unconditionally and reports every result, which is what makes it useful for measuring an actual failure rate and testing whether a failure is browser-specific. `retries` only re-runs after a failure and stops at the first pass, so it hides a race instead of diagnosing it.
- The fastest debugging session is the one where you check the network tab before rewriting a locator: a failing `expect(locator).toBeVisible()` can just as easily mean the API call behind it returned a `401` as it can mean the locator itself is wrong.

## Recap in 60 Seconds

If you only remember three things:

1. UI mode is for live, local debugging with time travel and watch mode, and trace viewer is for reconstructing a CI failure you weren't there to see, using its network, console, and DOM-snapshot tabs.
2. `codegen` scaffolds fast, but every locator it produces gets reviewed and upgraded before it's trustworthy. Never commit it unread.
3. Diagnose flaky tests with `--repeat-each` to get a real failure rate and mechanism first, then fix the actual race, and never reach for `retries` as a substitute for that diagnosis.

## Try It

Take the `nurse-schedule.spec.ts` flaky-row test from Step 5 of Build It and extend the diagnosis across all three browser projects, not just `nurse`/chromium. Use the `admin`, `doctor`, `nurse`, and `patient` projects you built during authentication setup, and the Chromium/Firefox/WebKit projects from the cross-browser and responsive testing lesson:

1. Run the un-fixed version of the test (before the `not.toHaveClass(/optimistic/)` guard from Step 5) with `--repeat-each=20` against Chromium, then again against WebKit, and record the failure count for each
2. If the failure rate differs meaningfully between browsers, use trace viewer on one failing run from each to compare the DOM snapshot at the moment of failure. Is the optimistic row rendered differently, or does one engine simply re-render faster than the other?
3. Apply the fix from Step 5, re-run `--repeat-each=20` on both browsers, and confirm zero failures on each before considering it resolved
4. Finally, deliberately record a second RBAC flow with `npx playwright codegen http://localhost:3002` (doctor completing an appointment) and find at least one generated locator that needs upgrading before you'd commit it

Write down the actual failure counts you observe rather than eyeballing "seems flaky" or "seems fine." A measured rate is the whole point of this lesson's diagnostic approach.
