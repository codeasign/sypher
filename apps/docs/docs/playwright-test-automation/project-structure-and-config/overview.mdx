# Playwright Project Structure and Configuration

⏱ 15 minutes · Difficulty: Beginner

## What You Will Learn

By the end of this lesson you will be able to:

- Read every top-level key `defineConfig` accepts — `projects`, `use`, `reporter`, `webServer` — and explain what each one owns
- Configure a `webServer` array that starts the RBAC backend and frontend automatically, so `npx playwright test` becomes a single command instead of a three-terminal ritual
- Explain why `reuseExistingServer: !process.env.CI` behaves differently on your machine than it does in a CI runner
- Read `baseURL` from an environment variable with a sensible local fallback, instead of a value hardcoded into the file
- Recognize `projects` as the mechanism later lessons use to run the same suite against multiple browsers without duplicating spec files

## Why This Matters

Right now, your `playwright.config.ts` does exactly one useful thing: it sets `baseURL`. Everything else about your environment — the backend running on `:5000`, the frontend running on `:3002`, both seeded and healthy — depends on you personally remembering to open two terminals and start them by hand, every session, before you run a single test.

That works today because you're the only person running this suite, on the one machine you set it up on. It stops working the moment a teammate clones your fork and runs `npx playwright test` without reading your setup notes, or the moment the CI workflow covered later in this course tries to run the exact same command on a GitHub Actions runner that has never heard of `localhost:3002`. A config file that only knows *where* the app lives, and not *how to start it*, is not portable — and a Playwright config that only works on the machine that wrote it is not really configuration, it's a personal habit.

This lesson turns `playwright.config.ts` from "a file with `baseURL` in it" into the single source of truth for how this project runs, anywhere: what browsers to test against, what to report and how, and — critically — how to bring the system under test itself up, on demand, without a human at a keyboard.

## The Problem

Imagine a teammate pulls your fork, installs dependencies, and runs the one command your initial setup taught you:

```bash
npx playwright test
```

They never read your two-terminal instructions. Nothing is listening on `:5000` or `:3002`. Every test that calls `page.goto('/login')` fails — not with a locator error, but with a connection refused, because `baseURL` correctly resolves the relative path to `http://localhost:3002/login`, and then Playwright tries to connect to a server that was never started.

Your config knows *where* the app should be. It has no idea it's also responsible for making sure something is actually there.

## The Concept

`defineConfig` in `playwright.config.ts` accepts four keys, and together they describe your entire test run. **`projects`** is the list of browser or device configurations a suite runs against — one project per target, Chromium today, with Firefox, WebKit, and mobile viewports joining in later lessons, and each one inherits from `use` unless it deliberately overrides a value. **`use`** holds the options every test shares by default, things like `baseURL` and `trace`, along with anything else `page` and `context` need to be set up with before a test even starts. **`reporter`** decides how results get surfaced once the run finishes, whether that's the HTML report you've been using or JSON and JUnit output for CI to consume in later lessons. And then there's **`webServer`** — one or more local processes Playwright starts before the first test runs, and, when it's the one that started them, tears back down after the last one finishes. That's the piece your current config is missing.

`webServer` accepts either a single object or an array, and because the RBAC app needs two independent processes — the Express backend and the React frontend — it's an array of two entries here, each with its own `command`, working directory, and health-check `url` that Playwright polls until it gets a response.

Once `webServer` owns starting both processes, `npx playwright test` works identically for you, for a teammate who just cloned the repo, and for a CI runner that has never run this project before — because the config, not a human's memory, is responsible for bringing the system under test to life.
