# Playwright Project Structure and Configuration: Review

⏱ 3 minutes

## Key Takeaways

- `defineConfig`'s four core keys (`projects`, `use`, `reporter`, `webServer`) work together to describe your entire test run: which browsers to target, what options every test shares, how results get surfaced, and which local processes Playwright manages for you.
- A `webServer` array lets you register the RBAC backend and frontend as two independent entries, each carrying its own `command`, `cwd`, health-check `url`, and `timeout`.
- `reuseExistingServer: !process.env.CI` leaves your original setup terminals untouched during local development, while still guaranteeing CI always launches fresh backend and frontend processes, keyed off the `CI` environment variable every major CI provider sets automatically.
- Reading `baseURL` as `process.env.BASE_URL ?? 'http://localhost:3002'` preserves the exact original default when nothing is set, but also makes the target overridable per environment without ever touching the config file.
- `env` on a `webServer` entry, rather than shell syntax stuffed inside `command`, is how you pass variables like `PORT`. It's what keeps the config identical across bash, PowerShell, and CI runners.

## Recap in 60 Seconds

If you only remember three things:

1. `webServer` is an array of two entries, backend and frontend, each carrying a `command`, `cwd`, and a health-check `url` that Playwright polls before it lets any test run.
2. `reuseExistingServer: !process.env.CI` reuses your already-running local servers, but always starts clean ones the moment it's running in CI.
3. `baseURL: process.env.BASE_URL ?? 'http://localhost:3002'` keeps the original default working while letting any environment override it with a single variable.

## Try It

Extend your `playwright.config.ts` with two changes, then verify both actually work:

1. Change `reporter` from the single `'html'` string to an array that produces both the HTML report and terminal output as the run progresses: `reporter: [['html'], ['list']]`. Run `npx playwright test` and confirm you see per-test lines printed to the terminal in addition to the HTML report still being generated at the end.
2. Simulate what CI will actually do. With your original setup terminals still running, temporarily set `CI=true` in your shell and run the suite:

```bash
CI=true npx playwright test
```

On Windows PowerShell:

```powershell
$env:CI="true"
npx playwright test
```

Watch the output carefully. Because `reuseExistingServer` evaluates to `false` when `CI` is set, Playwright will attempt to start a *second* copy of both the backend and frontend even though your original terminals are still up. You should see the port-collision failure described in Mistake 1 of the previous lesson happen on purpose. Stop both of your original terminals first, run the same `CI=true` command again, and confirm this time Playwright starts both servers cleanly on its own, runs the suite, and shuts them down when it finishes. Unset `CI` afterward so your next local run goes back to reusing servers normally.
