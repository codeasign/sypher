# Playwright Project Structure and Configuration: Common Mistakes

⏱ 8 minutes

## When NOT to Use This

`webServer` is for processes Playwright itself is responsible for bringing up and tearing down: your own fork's `backend/` and `frontend/`. It is the wrong tool the moment the system under test is something you don't control the lifecycle of, such as a shared team staging deployment, a long-running QA environment other people are also using, or a server that takes real, expensive setup (a full data warehouse load, a paid third-party sandbox) that shouldn't be started and stopped on every local test run.

In those cases, skip `webServer` for that target entirely and just point `baseURL` (or `process.env.BASE_URL`, from this lesson's Step 4) at wherever it already lives. Trying to make `webServer` manage infrastructure it doesn't actually own leads to Playwright either failing to start something that's not its job to start, or, worse, tearing down a shared environment other people are relying on when your test run ends.

## The Pattern to Remember

- **Pattern:** `webServer` starts every process *this* test run owns, while `baseURL` (read from an environment variable) simply points at whatever the run should actually test against, whether you own it or not.
- **When to use:** for any process you'd otherwise start by hand in a terminal before testing, such as your own fork's backend and frontend, a mock server, or a local API you built for the tests themselves.
- **When NOT to use:** for shared or expensive-to-restart environments you don't own the lifecycle of. Point `baseURL` at those instead and leave `webServer` out of the picture for that target.
- **Mental model:** think of `webServer` as a stagehand who shows up early, sets the stage, and locks up after, but only for the parts of the stage you built. Anything borrowed from someone else's theater, you just need directions to.

## Common Mistakes

### Mistake 1: Omitting `reuseExistingServer` and Colliding with Your Own Terminals

**Mistake:** Adding a `webServer` entry without setting `reuseExistingServer` at all, while your original setup terminals are still running the backend and frontend by hand.

**Why it happens:** It's an easy line to skip, because `reuseExistingServer` looks optional and the config runs fine without it, right up until you already have a server listening on the port `webServer` is about to claim.

**Symptoms:** Playwright tries to spawn a second `npm start` on a port that's already bound, so the command fails with an address-in-use error (`EADDRINUSE`) before any test runs. It's a confusing failure that looks like a config problem rather than what it actually is: a "two processes, one port" problem.

**Fix:** Always set `reuseExistingServer: !process.env.CI` on every `webServer` entry. Locally, this treats an already-running server as ready instead of trying to start a duplicate; in CI, where nothing is running yet, it launches cleanly every time.

### Mistake 2: Pointing `url` at the Wrong Health Check

**Mistake:** Setting the backend's `webServer.url` to something like `http://localhost:5000/` (the bare root) instead of a route that only responds once the app is truly ready, such as `/api-docs`.

**Why it happens:** Express can accept TCP connections on its port slightly before every route, including ones registered later in startup like Swagger, has finished being wired up. A bare root path or raw port check can report "ready" a moment too early.

**Symptoms:** Intermittent failures early in a run: the first test or two error out trying to reach an endpoint that technically has a listener but hasn't finished initializing. The failure looks flaky rather than like a startup-ordering problem, and it often disappears on a retry, which makes it easy to misdiagnose.

**Fix:** Point `url` at a route that only becomes available once the app has genuinely finished starting, such as `/api-docs` for this backend, since Swagger only serves after every route it documents is registered. If a target doesn't have an obvious "fully ready" route, prefer one further along in your app's startup sequence over the bare root.

### Mistake 3: Hardcoding `baseURL` So the Environment Variable Does Nothing

**Mistake:** Writing `baseURL: 'http://localhost:3002'` directly, then later trying to override it with `BASE_URL=... npx playwright test` and being confused when the override has no effect.

**Why it happens:** The hardcoded version and the environment-variable version look identical when nothing is set, so it's easy to copy the wrong one from an old branch or an example, and you won't notice the mistake until the moment you actually need the override.

**Symptoms:** Setting `BASE_URL` in your shell or in a CI job's environment variables changes nothing. Every test still runs against `localhost:3002`, silently, with no error to tell you the override was ignored.

**Fix:** Use `baseURL: process.env.BASE_URL ?? 'http://localhost:3002'` so an unset variable falls back to the same default you've always used, but a set one actually takes effect.

### Mistake 4: Putting Shell-Specific Syntax Inside `command`

**Mistake:** Writing the frontend's `webServer` entry as `command: 'PORT=3002 npm start'` instead of using the `env` field.

**Why it happens:** That's the exact command you typed by hand in a bash terminal during setup, so copying it directly into `command` feels natural.

**Symptoms:** The config works on your machine, then fails outright, or silently starts the frontend on the wrong port, the moment it runs on Windows PowerShell or a CI runner using a different default shell, because `PORT=3002 npm start` is bash syntax, not something every shell understands.

**Fix:** Keep `command` as the plain, shell-agnostic `npm start`, and set the port through the `env` object instead: `env: { PORT: '3002' }`. Playwright applies this directly to the spawned process's environment, independent of whatever shell is running it.

### Mistake 5: Forgetting `cwd` Is Relative to the Config File, Not Your Terminal

**Mistake:** Setting `cwd: 'backend'` (or omitting it) while running `npx playwright test` from somewhere other than the repository root, then being surprised the process fails to spawn.

**Why it happens:** It's easy to assume `cwd` resolves against whatever directory your terminal happens to be sitting in when you run the command, since that's how relative paths normally feel.

**Symptoms:** Playwright reports it couldn't spawn the `npm start` process at all, throwing an `ENOENT`-style error that points at a path that doesn't exist, because `cwd` got resolved relative to the wrong starting point and landed somewhere with no `package.json` in it.

**Fix:** Always run `npx playwright test` from the repository root, and write `cwd` paths (`./backend`, `./frontend`) relative to `playwright.config.ts` itself, not to wherever your terminal happens to be. If you're not sure, run `pwd` (or `cd` with no arguments on Windows) before testing and confirm you're at the repo root.
