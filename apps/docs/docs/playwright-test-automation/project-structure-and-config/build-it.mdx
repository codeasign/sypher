# Playwright Project Structure and Configuration: Hands On

⏱ 20 minutes

## Breaking It Down

### Step 1: Look at the Full Anatomy Before You Change Anything

Open the `playwright.config.ts` you produced during setup. Before adding anything, lay out where each of the four keys from the previous lesson will live:

```typescript title="playwright.config.ts (current state after setup)"
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  reporter: 'html',

  use: {
    baseURL: 'http://localhost:3002',
    trace: 'on-first-retry',
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
});
```

`reporter: 'html'` and `projects` are already here from your initial setup, but `use.baseURL` is still hardcoded, and there's no `webServer` key at all yet. That's exactly why you've had two terminal windows open for every lesson so far. You're going to fix both of those in this lesson.

### Step 2: Add the `webServer` Array as Backend and Frontend Entries

The RBAC app is two independent processes, so `webServer` is an array, not a single object. Add it as a sibling of `use` and `projects`:

```typescript title="playwright.config.ts"
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  reporter: 'html',

  webServer: [
    {
      command: 'npm start',
      cwd: './backend',
      url: 'http://localhost:5000/api-docs',
      reuseExistingServer: !process.env.CI,
      timeout: 120 * 1000,
    },
    {
      command: 'npm start',
      cwd: './frontend',
      url: 'http://localhost:3002',
      reuseExistingServer: !process.env.CI,
      timeout: 120 * 1000,
      env: {
        PORT: '3002',
      },
    },
  ],

  use: {
    baseURL: 'http://localhost:3002',
    trace: 'on-first-retry',
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],
});
```

Each entry has the same shape:

- **`command`**: the exact shell command to run, same as you'd type it yourself: `npm start`.
- **`cwd`**: the directory to run that command in, relative to the config file. This is what lets one config start two processes that live in two different folders of the same repo.
- **`url`**: the health-check endpoint. Playwright polls this URL until it gets any response, and only then considers that server ready. For the backend, `/api-docs` (Swagger) is a reliable readiness signal; it only serves once the Express app has fully booted. For the frontend, the app root is enough.
- **`reuseExistingServer`**: covered in Step 3.
- **`timeout`**: how long Playwright waits for the `url` to respond before giving up and failing the whole run. `120 * 1000` (two minutes) comfortably covers startup for both processes when dependencies are already installed; raise it if your machine is slower.

Notice the frontend entry's `env: { PORT: '3002' }` instead of writing `PORT=3002 npm start` directly in `command`. Setup had you set `PORT` differently on bash (`PORT=3002 npm start`) versus Windows PowerShell (`$env:PORT=3002`), because that's shell syntax, not something Node controls. `webServer`'s `env` object sidesteps that entirely. Playwright sets the environment variable on the spawned process directly, so `command` stays `npm start` regardless of what shell is running it.

### Step 3: Understand `reuseExistingServer: !process.env.CI`

This one line is why the config behaves correctly in two completely different environments without an `if` statement anywhere in your test code. Locally, `process.env.CI` is unset, so `!process.env.CI` evaluates to `true`. That means when you run `npx playwright test` with your original setup terminals still open and both servers already answering on `:5000` and `:3002`, Playwright's health check succeeds immediately, sees `reuseExistingServer: true`, and doesn't bother spawning a second copy of either process. Your existing terminals just keep running exactly as before. In CI, though, it plays out differently: GitHub Actions (and every major CI provider) sets `CI=true` in the environment automatically, so you never have to set this yourself, and that flips `!process.env.CI` to `false`. That means Playwright always launches fresh `backend/` and `frontend/` processes before the first test, regardless of whether anything happens to be listening on those ports already, and shuts them down again once the run finishes.

If you hardcoded `reuseExistingServer: true` instead, a CI run could silently pass against a stale, leftover process from a previous job instead of a clean one, which is a much harder bug to track down than a slow test.

### Step 4: Read `baseURL` from an Environment Variable

Replace the hardcoded `use.baseURL` with a value read from `process.env.BASE_URL`, falling back to the same `localhost:3002` you've used since setup:

```typescript title="playwright.config.ts"
use: {
  baseURL: process.env.BASE_URL ?? 'http://localhost:3002',
  trace: 'on-first-retry',
},
```

The `??` (nullish coalescing) operator only falls back when `BASE_URL` is `undefined` or `null`. An empty string would still win, which is the correct behavior here. With nothing set, every test you've already written keeps resolving against `http://localhost:3002` exactly as before; nothing breaks. But now a teammate testing against a staging deploy, or a CI job pointed at a different environment, can override it without touching this file:

```bash
BASE_URL=https://staging.rbac-healthcare-system.example npx playwright test
```

On Windows PowerShell:

```powershell
$env:BASE_URL="https://staging.rbac-healthcare-system.example"
npx playwright test
```

### Step 5: Verify the Single-Command Workflow

Stop both terminals from your original setup. Actually close them, or `Ctrl+C` each process, so nothing is listening on `:5000` or `:3002`. Then run:

```bash
npx playwright test
```

Watch the output: Playwright starts the backend, waits for `/api-docs` to respond, starts the frontend, waits for `:3002` to respond, and only then begins running your tests. What used to require three terminals and a mental checklist is now one command.

Now start your original setup terminals back up manually, leave them running, and run `npx playwright test` again. This time the health checks succeed immediately against your existing processes, `reuseExistingServer` kicks in, and Playwright never spawns duplicates. You'll see the run start noticeably faster, with no "starting server" output at all.

## How It Works Internally

When Playwright encounters a `webServer` entry, it does not treat `url` as a value to trust. It actively sends requests to it in a loop, on a short interval, until one of two things happens: it gets *any* HTTP response (the status code doesn't matter, only that something answered), at which point that server is "ready" and the run proceeds, or the `timeout` elapses with no response, at which point Playwright fails the entire run before a single test executes, with an error naming which `webServer` entry never came up. This is why `url` should point at something that only responds once your app has genuinely finished booting. The RBAC backend's `/api-docs` is a better health-check target than, say, a raw TCP port, because a port can accept a connection before Express has finished registering its routes.

The same logic applies in reverse at teardown: Playwright only stops a `webServer` process it actually started. If `reuseExistingServer` caused it to skip launching one, because something was already listening, it skips stopping it when the run ends too, which is exactly why your original setup terminals survive a local `npx playwright test` run untouched.
