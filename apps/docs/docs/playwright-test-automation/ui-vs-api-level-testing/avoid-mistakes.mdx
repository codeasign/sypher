# Comparing UI-Level and API-Level Testing — Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Running the same permission boundary at both layers is worth the cost when the two layers can genuinely disagree — which is true any time a frontend independently decides what to render and a backend independently decides what to allow, exactly the situation in the RBAC healthcare app. It's not worth it for a single-role internal tool with no separate backend to bypass, or for logic that has nothing to do with authorization — a validation rule or a calculation belongs in an ordinary feature spec at whichever single layer owns it, not duplicated across both just because this module's pattern is available. And it's not a one-time audit: the value is in keeping both layers in CI permanently, so a regression at either one is caught the moment it lands, not in treating this comparison as a documentation exercise you run once and move on from.

## The Pattern to Remember

- **Pattern:** the UI layer proves what the user experiences; the API layer proves what the server actually allows; a permission boundary is only proven closed when both are green, and each layer's job is to catch what the other structurally cannot.
- **When to use:** any role-based system where hiding a control and enforcing a permission are implemented in two different places — which, in practice, is nearly every real system with a frontend and a backend.
- **When NOT to use:** single-role tools, logic unrelated to authorization, or a one-off check you don't intend to keep running in CI.
- **Mental model:** testing a locked door by checking the doorknob is missing tells you nothing about whether the lock still holds if someone reaches for where the knob used to be. A missing knob is a UI-level fact. A working lock is an API-level fact. You need both to call the door secure.

## Common Mistakes

### Mistake 1: Duplicating the Full Matrix at Both Layers

**Mistake:** Taking the RBAC permission-matrix lesson's 36-row `permissionMatrix` and writing an equivalent UI spec for every single row, on top of the API-level coverage `supertest-api-testing` already owns.

**Why it happens:** The data-driven pattern from the RBAC permission-matrix lesson is right there, already proven to work, and looping it over every row feels like thoroughness rather than waste.

**Symptoms:** Your UI suite's runtime grows in lockstep with the matrix instead of with the boundaries that actually need slow, rendering-level proof. Every new role or resource now means writing — and maintaining — the same row twice, in two repos, in two languages of assertion, for a return that Step 6 of [Build It](./build-it) shows isn't there for most of the matrix.

**Fix:** Let the API layer carry the exhaustive matrix. Reserve UI-level rows for the boundaries where a rendering bug is genuinely costly — irreversible actions and anything exposing another person's data — the way this module's Step 6 outlines.

### Mistake 2: Treating a Green UI Suite as Proof the Backend Is Secure

**Mistake:** Seeing the RBAC permission-matrix lesson's full matrix pass, including `deleteUsers` for every role, and concluding the delete endpoint itself is safe from unauthorized calls.

**Why it happens:** A UI test that clicks through a real browser feels like it's testing "the whole system," end to end, because a real network request does leave the browser when a click succeeds.

**Symptoms:** The exact scenario in this module's Bug A — a role check silently dropped from the backend route — ships with a fully green UI suite and no signal anything is wrong, because the UI suite never sends the request that would have caught it.

**Fix:** Never read "the button is hidden" as "the server refuses." They're two different claims. Only an API-level assertion — this course's own via the `request` fixture, or properly, `supertest-api-testing`'s dedicated suite — proves the second one.

### Mistake 3: Treating a Green API Suite as Proof the Frontend Is Correct

**Mistake:** Seeing `supertest-api-testing`'s suite pass, including a `403` for every non-admin role on `DELETE /api/users/:id`, and concluding the frontend never exposes that action to the wrong role.

**Why it happens:** If the server is the one actually enforcing the rule, it's tempting to treat the server's correctness as the whole story — the API is where the "real" security lives, so it can feel like the UI layer is just cosmetic on top of it.

**Symptoms:** The exact scenario in this module's Bug B — a leftover debug flag rendering a Delete button for a nurse — ships with a fully green API suite and no signal anything is wrong, because the API suite never renders anything and has no way to observe what a user actually sees.

**Fix:** A correct backend does not guarantee a correct frontend. Keep the targeted UI-level smoke checks from Step 6 specifically because they're the only thing watching what actually renders.

### Mistake 4: Treating the In-Course API Smoke Check as a Substitute for `supertest-api-testing`

**Mistake:** Writing the Step 3 `request`-fixture spot check from [Build It](./build-it) for `deleteUsers`, seeing it pass, and calling the API layer "covered" without a dedicated `supertest-api-testing` suite behind it.

**Why it happens:** The spot check uses real tools from the API-requests-from-Playwright lesson, sends a real request, and gets a real `403` back — it looks and feels like proper API testing, just running from inside a Playwright test file.

**Symptoms:** Only one row of the matrix actually gets checked, while the other 35 go untested. The illusion of "we test the API too" quietly substitutes for the exhaustive coverage the API layer is supposed to own, so gaps in the matrix go unnoticed simply because something at that layer is technically green.

**Fix:** Use the `request`-fixture version as a fast sanity check during development, not as your API-level test suite. The exhaustive matrix belongs in `supertest-api-testing`, run independently, with its own CI job.

### Mistake 5: Only Testing the Allowed Role, Not the Denied Ones

**Mistake:** Writing a UI spec that confirms an admin sees the Delete button, and stopping there, without the matching assertion that a nurse, doctor, or patient does not.

**Why it happens:** The "happy path" — the role that's supposed to work — is the first thing anyone thinks to check, and it's easy to feel done once it passes.

**Symptoms:** The suite proves the control exists for the role that should have it, but never proves it's absent for the roles that shouldn't — exactly the half of the boundary Bug B depends on going unchecked. A regression that starts showing the Delete button to every role slips through untouched.

**Fix:** Write both assertions together, as Step 2 of [Build It](./build-it) does — the allowed role sees the control, and at least one denied role does not — every time, for every boundary you add UI-level coverage for.
