# Comparing UI-Level and API-Level Testing — Review

⏱ 4 minutes

## Key Takeaways

- The same rule — a nurse cannot delete a user — gets proven twice: a Playwright UI test in this course asserts the Delete control isn't visible, and a Supertest API test in `supertest-api-testing` asserts `DELETE /api/users/:id` returns `403`. Neither test can substitute for the other.
- A UI-level test catches frontend access-control bugs — a control rendered for a role that shouldn't have it — even when the backend behind that control is completely correct.
- An API-level test catches backend business-logic bugs — a request the server should refuse but doesn't — even when the frontend correctly hides every path to triggering it.
- A permission boundary is only proven closed when both layers are green. A green UI suite says nothing about what the server allows; a green API suite says nothing about what actually renders.
- Don't duplicate the full permission matrix at both layers. Let the API layer — fast, cheap, stable — carry the exhaustive role × resource × action coverage, and reserve UI-level testing for a targeted smoke pass on the highest-stakes boundaries, like irreversible actions and anything exposing another person's data.

## Recap in 60 Seconds

1. A green UI suite proves a control is hidden or shown correctly — it proves nothing about what the server does if the request is sent anyway.
2. A green API suite proves the server accepts or rejects a request correctly — it proves nothing about what a user actually sees on screen.
3. Cover the full matrix exhaustively once, at the API level, and cover only the highest-stakes boundaries again at the UI level — don't pay the cost of the full matrix twice.

## Try It

Pick another row from the RBAC permission-matrix lesson's matrix — `createMedicalRecords` for a nurse is a good candidate, since it's another `deny` case with real stakes if it's wrong. Do three things:

1. Write the UI-level check, following Step 2 of [Build It](./build-it) — one test proving the role that should have the control sees it, one proving a denied role doesn't.
2. Sketch, as a comment or a short reference file, what the equivalent `supertest-api-testing` check would assert against the underlying endpoint — you don't need that course's code to exist yet, just state the request, the role's JWT, and the expected status.
3. In your own fork, deliberately introduce one bug from each class — drop a role check from the backend route, and separately, add a stray conditional that renders the control for the wrong role in the frontend. Run both your UI spec and your sketch of the API check against each bug in turn, and confirm only the layer that should catch it goes red.
