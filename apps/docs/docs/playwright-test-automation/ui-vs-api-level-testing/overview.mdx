# Comparing UI-Level and API-Level Testing

⏱ 20 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Take the exact "a nurse cannot delete a user" case from the RBAC permission-matrix lesson and see it proven at two different layers — a Playwright UI test in this course, and the API test `supertest-api-testing` would write against the same rule
- State precisely what a UI-level test catches that an API-level test structurally cannot, and the reverse
- Recognize one concrete bug each layer would catch that the other layer would let ship straight to production
- Decide, for a real role-based system, where UI coverage earns its cost and where the exhaustive matrix belongs instead
- Read this course and `supertest-api-testing` as one testing strategy split across two layers, not two unrelated projects that happen to share a backend

## Why This Matters

This is a capstone lesson, so it doesn't introduce any new Playwright API — everything you need mechanically (`getByRole`, `storageState`, the `request` fixture) you already have from the authentication, API-requests-from-Playwright, and RBAC permission-matrix lessons. What this lesson teaches instead is how to read those tools as one part of a larger strategy, because a role-based system like the RBAC healthcare app enforces every permission in two separate places that can silently disagree: the frontend decides what to render, and the backend decides what to allow. Nothing forces those two decisions to stay in sync, which means a test suite that only ever looks at one of them can be fully green while the other one is quietly broken.

That's not a hypothetical for this specific app. It's the direct, practical reason `supertest-api-testing` exists as a separate course testing the same backend, and the reason the RBAC permission-matrix lesson flagged the overlap instead of treating API verification as this course's job to skip. A permission boundary in a system like this one isn't "the button is hidden" or "the server rejects the call" — it's both of those, true at the same time, verified independently.

## The Problem

Picture two test suites, both fully green, both testing the same rule: a nurse cannot delete a user.

**Suite 1 — this course.** The RBAC permission-matrix lesson's `deleteUsers` check runs as `nurse`, finds the Delete button in `/admin/users` not visible, and passes. Every role in the matrix behaves as documented. Green.

**Suite 2 — `supertest-api-testing`.** A test authenticates as `nurse`, sends `DELETE /api/users/:id`, and asserts a `403`. The backend correctly rejects it. Green.

Now imagine only one of those two suites actually exists — a common, reasonable-looking starting point for a small team. Two very different bugs can now ship, each invisible to whichever suite is missing:

- If only Suite 1 exists, someone removes the role check from the `DELETE /api/users/:id` route handler by accident — a copy-paste refactor, a middleware ordering mistake, whatever the real cause turns out to be. The button is still hidden, because the frontend's role check was never touched. Suite 1 stays green. A nurse who opens Swagger, or a browser's network tab, or just `curl`, can now delete a user, and nothing in this course's suite will ever notice, because this course's suite never leaves the browser.
- If only Suite 2 exists, someone reintroduces a leftover debug flag in the frontend — `role === 'admin' || localStorage.getItem('debugMode')` — that renders the Delete button for a nurse session with debug mode on. The backend still correctly returns `403` the moment the button is clicked, so Suite 2 stays green. But a nurse now sees a Delete button on a user they cannot actually delete — a confusing, unprofessional, screenshot-able UI bug that Suite 2 cannot see, because it never renders anything.

Neither suite is wrong about what it checked. Each is simply blind to the layer it doesn't test.

## The Concept

Treat "UI-level" and "API-level" as two independent proofs of the same rule, not two ways of writing the same test:

| | UI-level test (this course) | API-level test (`supertest-api-testing`) |
|---|---|---|
| What it drives | A real browser, against the frontend at `:3002` | A direct HTTP client, against the backend at `:5000` |
| What it proves | The control a user would click is present or absent correctly | The server accepts or rejects the request correctly |
| What it's blind to | Whether the backend would reject the same action if the frontend's decision were bypassed entirely | Whether the frontend renders a control it shouldn't, or hides one it should show |
| Failure it catches | A frontend access-control bug: wrong role sees or can reach a control | A backend business-logic bug: wrong role's request is allowed through |
| Speed and stability | Slower — browser launch, network, rendering; more brittle to markup churn | Fast — a single HTTP call; stable against anything except the API contract itself |

Here is the same rule, `nurse` cannot delete a user, asserted at both layers. First, the UI-level test — this is code you write in this course, extending the RBAC permission-matrix lesson's `getPageAs` fixture and `deleteUsers` check to a single focused assertion:

```typescript title="tests/rbac-delete-user-ui.spec.ts"
import { test, expect } from './fixtures/role-page';

test.describe('delete user — UI-level boundary', () => {
  test('nurse does not see the Delete control', async ({ getPageAs }) => {
    const page = await getPageAs('nurse');
    await page.goto('/admin/users');

    const deleteButton = page
      .getByRole('row')
      .filter({ hasText: 'Doe' })
      .getByRole('button', { name: 'Delete' });

    await expect(deleteButton).not.toBeVisible();
  });

  test('admin does see the Delete control', async ({ getPageAs }) => {
    const page = await getPageAs('admin');
    await page.goto('/admin/users');

    const deleteButton = page
      .getByRole('row')
      .filter({ hasText: 'Doe' })
      .getByRole('button', { name: 'Delete' });

    await expect(deleteButton).toBeVisible();
  });
});
```

Second, the API-level test — this is conceptual code that belongs in `supertest-api-testing`, not in this course's `tests/` folder. It's shown here only so you can see the same rule proven at the other layer:

```typescript title="[supertest-api-testing] tests/users.delete.spec.ts — reference only, not written in this course"
import request from 'supertest';
import { app } from '../src/app';
import { getJwtFor } from './helpers/auth';

describe('DELETE /api/users/:id — permission boundary', () => {
  it('rejects a nurse with 403', async () => {
    const nurseToken = await getJwtFor('nurse');

    const response = await request(app)
      .delete('/api/users/some-user-id')
      .set('Authorization', `Bearer ${nurseToken}`);

    expect(response.status).toBe(403);
  });

  it('allows an admin with 200', async () => {
    const adminToken = await getJwtFor('admin');

    const response = await request(app)
      .delete('/api/users/some-user-id')
      .set('Authorization', `Bearer ${adminToken}`);

    expect(response.status).toBe(200);
  });
});
```

Both tests assert the same rule. Neither test can stand in for the other — the first proves nothing about the second's outcome, and the second proves nothing about the first's.
