# Comparing UI-Level and API-Level Testing: Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Restate the Case from the RBAC Permission-Matrix Lesson

The RBAC permission-matrix lesson's matrix has this row:

```typescript title="tests/data/permission-matrix.ts (from the RBAC permission-matrix lesson)"
{ role: 'nurse', action: 'deleteUsers', expected: 'deny' },
```

backed by this check:

```typescript title="tests/data/action-checks.ts (from the RBAC permission-matrix lesson)"
deleteUsers: async (page) => {
  await page.goto('/admin/users');
  const deleteButton = page
    .getByRole('row')
    .filter({ hasText: 'Doe' })
    .getByRole('button', { name: 'Delete' });
  return deleteButton.isVisible();
},
```

That check already exists and already runs, as one row among 36, inside the RBAC permission-matrix lesson's full matrix suite. Nothing in this module replaces it. What this module adds is the other half of the same boundary, the part that lesson deliberately left for `supertest-api-testing` to cover, made explicit instead of implied.

### Step 2: The UI-Level Assertion, Isolated

The RBAC permission-matrix lesson's version of this check is folded into a data-driven loop, which is correct for covering the whole matrix but makes any one row hard to point at directly. Pull just this one boundary into its own focused spec, reusing the same `getPageAs` fixture from that lesson:

```typescript title="tests/rbac-delete-user-ui.spec.ts"
import { test, expect } from './fixtures/role-page';

test.describe('delete user: UI-level boundary', () => {
  test('nurse does not see the Delete control', async ({ getPageAs }) => {
    const page = await getPageAs('nurse');
    await page.goto('/admin/users');

    const deleteButton = page
      .getByRole('row')
      .filter({ hasText: 'Doe' })
      .getByRole('button', { name: 'Delete' });

    await expect(deleteButton).not.toBeVisible();
  });

  test('admin does see the Delete control', async ({ getPageAs }) => {
    const page = await getPageAs('admin');
    await page.goto('/admin/users');

    const deleteButton = page
      .getByRole('row')
      .filter({ hasText: 'Doe' })
      .getByRole('button', { name: 'Delete' });

    await expect(deleteButton).toBeVisible();
  });
});
```

Two tests, one boundary, checked from both sides: the role that shouldn't see the control doesn't, and the role that should does. That's also the edge of what Playwright, on its own, can ever tell you about this rule. It never sends a `DELETE` request, and it never asks the server anything.

### Step 3: The API-Level Assertion, What `supertest-api-testing` Writes

This is where the same rule gets checked from the other side, in the sister course, against the backend directly:

```typescript title="[supertest-api-testing] tests/users.delete.spec.ts (reference only, not written in this course)"
import request from 'supertest';
import { app } from '../src/app';
import { getJwtFor } from './helpers/auth';

describe('DELETE /api/users/:id: permission boundary', () => {
  it('rejects a nurse with 403', async () => {
    const nurseToken = await getJwtFor('nurse');

    const response = await request(app)
      .delete('/api/users/some-user-id')
      .set('Authorization', `Bearer ${nurseToken}`);

    expect(response.status).toBe(403);
  });

  it('allows an admin with 200', async () => {
    const adminToken = await getJwtFor('admin');

    const response = await request(app)
      .delete('/api/users/some-user-id')
      .set('Authorization', `Bearer ${adminToken}`);

    expect(response.status).toBe(200);
  });
});
```

You don't write this file in this course. It's shown so the comparison in the next two steps has something concrete on both sides.

If you want a lightweight, in-course stand-in for this specific check, not a replacement for `supertest-api-testing`'s suite, just a spot check using what the API-requests-from-Playwright lesson already gave you, Playwright's own `request` fixture can send the same call:

```typescript title="tests/rbac-delete-user-api-smoke.spec.ts"
import { test, expect } from '@playwright/test';

test('nurse cannot delete a user via the API directly', async ({ request }) => {
  const loginResponse = await request.post('http://localhost:5000/api/auth/login', {
    data: { username: 'nurse1', password: 'nurse123' },
  });
  const { token } = await loginResponse.json();

  const deleteResponse = await request.delete('http://localhost:5000/api/users/some-user-id', {
    headers: { Authorization: `Bearer ${token}` },
  });

  expect(deleteResponse.status()).toBe(403);
});
```

This is useful as a fast sanity check while you're developing, and it proves the point of this module works with tools you already have. It is not a substitute for the exhaustive, dedicated coverage `supertest-api-testing` is built to own. Step 6 explains why that distinction matters.

### Step 4: Bug A, a Business-Logic Bug the UI Test Cannot See

Suppose someone refactors the backend's route middleware and the role check quietly drops off the delete route:

```javascript title="backend/routes/users.js (the bug)"
// Before: router.delete('/:id', authenticate, authorize('admin'), deleteUser);
router.delete('/:id', authenticate, deleteUser);
```

`authorize('admin')` is gone. Any authenticated user, regardless of role, can now delete a user. Nothing about the frontend changed. The Delete button is still conditionally rendered exactly as before, so the RBAC permission-matrix lesson's UI check and Step 2's UI spec above are both still green. Run the whole of this course's suite and you'll see no red anywhere. The only test that catches this is the one that actually sends the request: Step 3's `supertest-api-testing` spec, or its in-course `request`-fixture stand-in, both of which would now see a `200` where they expect a `403`.

This is a business-logic bug, and it lives entirely on the server. A UI-level test, by construction, only ever observes what the frontend chooses to render. It has no way to notice that the backend behind an already-hidden button has quietly stopped protecting itself.

### Step 5: Bug B, a Frontend Bug the API Test Cannot See

Now suppose the backend is untouched and correct, but a leftover debug affordance ships in the frontend:

```tsx title="frontend/src/pages/AdminUsers.tsx (the bug)"
const canDelete = role === 'admin' || localStorage.getItem('debugMode') === 'true';

// ...

{canDelete && <button onClick={() => handleDelete(user.id)}>Delete</button>}
```

A nurse with `debugMode` set in `localStorage` (left over from someone's earlier troubleshooting session, or set by a browser extension, or copy-pasted from a Slack message) now sees a Delete button in `/admin/users`. Clicking it still fails: the backend's `authorize('admin')` middleware is untouched, so the request still comes back `403`, and `supertest-api-testing`'s suite from Step 3 stays exactly as green as it was before this bug existed. Nothing about the API changed.

But the button is visible to a role it shouldn't be visible to, and Step 2's UI spec, `expect(deleteButton).not.toBeVisible()` for a nurse, now fails, correctly. That's a real defect: a nurse looking at a control that implies an ability she doesn't have is a broken user experience and a legitimate access-control bug in the frontend, even though the server was never at risk. An API-level suite, by construction, only ever observes what the server does with a request it receives. It has no way to notice that a control the user should never have seen was rendered in the first place.

### Step 6: The Coverage Split

Bugs A and B show the two layers aren't redundant. Each catches something real that the other cannot. That does not mean the right answer is running the full 36-row matrix at both layers. Doing that doubles the maintenance cost of every future role or resource added to the app, for a return that's smaller than it looks: most of the matrix's cells are ordinary "hide a link, check a role" pairs where a rendering bug and a business-logic bug are both plausible, but not equally costly if missed.

A more realistic split for a role-based system like this one:

| Coverage | Layer | Why |
|---|---|---|
| The full role × resource × action matrix, all cells | API level (`supertest-api-testing`) | Fast, no browser, no rendering. Cheap enough to run exhaustively on every change, and it's the layer where the actual authorization decision is enforced |
| A targeted smoke pass, one or two checks per role | UI level (this course) | Slower and more sensitive to markup changes, so reserve it for the boundaries where a rendering bug is most damaging: irreversible actions (`deleteUsers`), and anything exposing another person's data (`viewMedicalRecords`) |
| Negative direct-URL access (from the RBAC permission-matrix lesson, Step 5) | UI level, kept minimal | Proves routing enforces roles the nav never links to, a handful of routes, not all of them |

Concretely: don't write a UI spec for `completeAppointments`, `cancelAppointments`, and `scheduleAppointments` for every role just because the matrix has rows for them. Let `supertest-api-testing` own that exhaustively, fast, in seconds. Do keep a UI spec for `deleteUsers` and `viewMedicalRecords`, because a rendering bug on those two specifically has real consequences, a visible-but-broken delete control, or a patient glimpsing another patient's chart, that are worth the slower, more expensive layer of proof.

## How It Works Internally

The split in Step 6 isn't a style preference. It's a direct consequence of what each layer actually costs to run. A `supertest` call is a function call into an in-process (or locally networked) Express app: no browser process, no rendering, no network round trip through a real socket in most setups, routinely single-digit milliseconds per assertion. A Playwright UI test launches or reuses a browser context, navigates a real page, waits for the DOM to settle, and only then evaluates a locator, routinely two to three orders of magnitude slower per test, and that gap compounds across a CI budget the more rows you duplicate at the UI layer. Exhaustive coverage is affordable at the layer where each check is cheap, and has to be rationed at the layer where each check is expensive. That's exactly why the API layer gets the matrix and the UI layer gets the smoke pass, not the other way around and not both in full.
