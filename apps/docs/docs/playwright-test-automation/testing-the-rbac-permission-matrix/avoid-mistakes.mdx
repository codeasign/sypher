# Testing the RBAC Permission Matrix — Common Mistakes

⏱ 10 minutes

## When NOT to Use This

A full role × action matrix suite is worth its weight when a system has more than two or three roles, when permissions change often enough that a spreadsheet or README can't be trusted to stay accurate, and when the cost of a permission bug is high — exactly the situation the RBAC healthcare app is modeling. It's overkill for a two-role app (admin/everyone-else) where a handful of hand-written tests cover the whole surface, and it's the wrong tool for testing business logic that has nothing to do with who's allowed to do it — validation rules, calculation correctness, and the like belong in ordinary feature specs, not folded into permission data rows just because the pattern is sitting there.

## The Pattern to Remember

- **Pattern:** the matrix is data (role, action, expected outcome), the test body is one generic function that reads a row and asserts allow or deny, and the loop that turns rows into `test()` calls is the only thing that "adds" a test.
- **When to use:** any system with three or more roles, or a permission set that's documented separately from the code and therefore drifts.
- **When NOT to use:** systems with one or two roles, or when you're testing logic that has nothing to do with authorization.
- **Mental model:** the matrix is a contract the app signed with itself. Your suite doesn't decide what the contract says — the table does. The suite's only job is checking whether the running app is honoring it.

## Common Mistakes

### Mistake 1: Editing the Expected Value to Match a Bug

**Mistake:** A row fails — the app doesn't match the matrix — and instead of filing that as a defect, you change `expected: 'allow'` to `expected: 'deny'` in the data file so the suite goes green.

**Why it happens:** A red suite feels like your problem to fix, and changing one line of data is far less friction than opening a bug ticket and waiting on someone else's sprint. It's also easy to rationalize in the moment: "well, that's what it actually does."

**Symptoms:** Over a few weeks, the "spec" in your data file quietly converges on whatever the app currently does, right or wrong, and the suite stops being able to catch new regressions in that same area — because it's no longer testing against an independent source of truth, just against itself.

**Fix:** Treat the README's matrix (or whatever document defines intended permissions) as the only place `expected` values come from. A failing row is a bug report against the app, not a bug in your test — file it, leave the test red or explicitly `test.fixme()` it with a link to the ticket, and only flip `expected` if the *matrix itself* is updated by someone with the authority to change the spec.

### Mistake 2: Checking Only Whether UI Elements Are Hidden

**Mistake:** Writing every check as "is the button/link visible," and calling the permission verified once the button doesn't render for a role that shouldn't have it.

**Why it happens:** UI checks are the easiest thing to reach for — `page.getByRole(...).isVisible()` reads naturally as "can this role do this," and for a lot of the matrix it happens to be true.

**Symptoms:** A role that can't see the "Delete User" button can still delete a user by hitting the API route directly, or by navigating to a URL the frontend simply doesn't link to anywhere. Hiding a button is a UX decision; it is not an authorization boundary, and a suite that only checks visibility never notices when the two have quietly come apart.

**Fix:** Pair every "is it visible" check with a "does direct navigation to the URL actually work" check, the way Step 5 in [Build It](./build-it) does. If your app also exposes the underlying API (this one does, via Swagger), verifying the API rejects the action too closes the loop completely — that's exactly where this module and the `supertest-api-testing` course's coverage of the same matrix overlap on purpose.

### Mistake 3: Reusing One Browser Context Across Roles

**Mistake:** Instead of opening a fresh context per role, logging in as one role inside a test, running a check, then logging in as a different role in the same context to save setup time.

**Why it happens:** It looks like a reasonable performance optimization — one browser context instead of four, less setup code per test.

**Symptoms:** Tests pass or fail depending on execution order, or a check for "nurse cannot view all users" passes only because a leftover admin cookie from the previous check in the same context was doing the actual authorizing, not the nurse's own session. This is one of the worst outcomes a permission test can produce: a false pass.

**Fix:** Give every role its own browser context, as `getPageAs` does in this module — one `storageState`, one context, closed at teardown. The small setup cost buys you certainty that a pass means the role itself was authorized, not some other session still lingering underneath it.

### Mistake 4: Writing One Test Function Per Row Instead of Looping Over Data

**Mistake:** Copy-pasting a near-identical `test(...)` block for each of the 36 matrix cells instead of generating them from the `permissionMatrix` array with a loop.

**Why it happens:** It's what shows up first when you're translating a table into tests by hand, row by row, especially if you started with two or three rows before realizing the full matrix needed covering.

**Symptoms:** You're right back to the problem this module opened with — adding a role or an action means writing new, hand-copied test blocks instead of adding a data row, and a typo in one copy-pasted block (an `expected: 'allow'` that should say `'deny'`) is much easier to miss buried in 36 near-identical functions than in one 36-row array of plain data.

**Fix:** If you're writing `test(` more than once with only the strings inside changing, that's a signal the loop from Step 4 belongs there instead. The generic test body reads one row; the array is the only thing with 36 entries.

### Mistake 5: Letting Parallel Tests Fight Over the Same Seeded Record

**Mistake:** Running the cancel-appointment and complete-appointment checks against the same seeded appointment ID, in parallel, without realizing `test.describe.parallel` will run them concurrently on different workers.

**Why it happens:** The seed script only creates 22 appointments, and it's easy to write a check that grabs "the first appointment in the list" without thinking about which other test in the same parallel run might also be reading — or mutating — that same row.

**Symptoms:** Flaky, order-dependent failures: the cancel check sometimes finds an appointment already completed by the other worker, or the complete check finds one already canceled, and the failure has nothing to do with permissions at all — it's a race on shared backend state.

**Fix:** Make each permission check read state without mutating it where possible (as the checks in this module do — they check button visibility, not click the button), and where a check genuinely needs to perform a mutating action, seed dedicated data for it via the API request fixture from the API-requests-from-Playwright lesson rather than reaching into the shared seeded rows every other test is also reading.
