# Testing the RBAC Permission Matrix

⏱ 22 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Turn a role-permission matrix into an executable specification instead of a wall of prose
- Write data-driven tests that run the same assertions across all four roles by looping over data, not by copy-pasting spec files
- Build a single table-driven suite covering every role × action combination in the RBAC app, so a new role or resource means adding a row, not a new file
- Write negative tests that attempt direct URL navigation into another role's screens, not just check that a link is hidden
- Recognize when a failing test is correctly catching a real bug in the app, and resist the urge to "fix" the test instead of reporting the defect

## Why This Matters

A permission matrix like the one below usually gets written once, in a README or a ticket, and then drifts out of sync with the actual code within a few sprints. Nobody re-reads the README before every pull request. What keeps a permission matrix honest is a test suite that asserts against it directly. The moment code and matrix disagree, a test goes red instead of the mismatch sitting silently in production until a patient sees another patient's medical record.

This matters more here than in a typical example app, because the RBAC healthcare app you have been using all course is not a bug-free demo built to make the lessons look clean. Its own README lists the role permissions matrix and explicitly marks it **"Not Completely Implemented."** That's not a flaw in this course, it's the most realistic thing about it. Every real system you will ever test has a permissions model that's partially aspirational: written down as intent, only partially true in the running code. Learning to write tests that assert the *intended* spec, and letting mismatches surface as failures instead of quietly adapting to whatever the app currently does, is the actual skill this lesson teaches.

## The Problem

Imagine you write one spec file per role: `admin.spec.ts`, `doctor.spec.ts`, `nurse.spec.ts`, `patient.spec.ts`. Each file logs in as that role and manually asserts what it can and cannot see. It works, at first. Then a fifth role gets added (`receptionist`, say) and you write a fifth file, mostly copy-pasted from the other four with the assertions inverted in a few places. Six months later, someone adds a `Reschedule appointment` action, and now every one of those five files needs the same new block added by hand. It's only a matter of time before one file gets missed.

The underlying issue is that "one spec file per role" ties your test *structure* to something that should be *data*. The role, the action, and whether that role is allowed to perform that action are three columns in a table, not three separate code paths. Every time the table grows, the code shouldn't need to.

## The Concept

Treat the permission matrix as data, not prose. This is the ground-truth spec every test in this module asserts against, copied verbatim from the RBAC app's own README:

| Action | Admin | Doctor | Nurse | Patient |
|---|---|---|---|---|
| View all users | Yes | No | No | No |
| Delete users | Yes | No | No | No |
| View all appointments | Yes | No | Yes | No |
| View own appointments | No | Yes | No | Yes |
| Schedule appointments | No | No | Yes | No |
| Complete appointments | No | Yes | No | No |
| Cancel appointments | No | Yes | Yes | No |
| Create medical records | No | Yes | No | No |
| View medical records | Yes | Yes | No | Yes (own only) |

Read that table as a contract, not a description: every row says what *should* happen. Turn it into TypeScript data and loop a `test()` call over every cell, and you end up with one suite that grows by adding a row rather than writing a new file whenever a role or action is added. It runs every role against every action, so a permission nobody thought to check by hand still gets covered, and it fails loudly on the specific row the moment the running app disagrees with the table. Because you already know this table is marked incomplete in the app's own README, you should *expect* some of those failures. That's the suite doing its job, not the suite being wrong.

The three pieces that make this work together are the data (the matrix as a TypeScript array), the role-based authentication set up earlier in this course (so each test row runs as the correct already-logged-in role), and a single parameterized test body that reads one row and makes one assertion: allowed or denied.
