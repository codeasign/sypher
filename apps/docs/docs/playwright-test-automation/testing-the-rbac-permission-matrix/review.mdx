# Testing the RBAC Permission Matrix — Review

⏱ 4 minutes

## Key Takeaways

- The permission matrix — nine actions across four roles — is data, not prose: a `PermissionCase[]` array of `{ role, action, expected }` objects, with the RBAC app's own README as the single source of truth for what `expected` should be.
- A role-aware `getPageAs(role)` fixture, built on the authentication lesson's `storageState` files and the fixtures lesson's fixture pattern, gives every test an isolated, already-authenticated context per role, so no login flow and no cross-role session leakage sits inside the test body.
- `test.describe.parallel` combined with a `for` loop over the matrix array generates one independently named, independently reportable test per role × action cell — 36 tests from one file, growing by adding a data row instead of a new spec.
- Checking that a button is hidden proves a UX decision, not an authorization boundary — negative tests that navigate directly to another role's URL (a patient hitting `/admin/users`) test the actual boundary the UI hiding a link cannot.
- The matrix is documented as "Not Completely Implemented" in the RBAC app's own README, so a failing row is expected and correct behavior from your suite — it's a bug report against the app, never a reason to quietly edit the test's `expected` value to match whatever the app currently does.

## Recap in 60 Seconds

If you only remember three things:

1. Turn the matrix into a typed data array once; let a loop over that array generate every `test()` call, not hand-written duplicates.
2. Test the boundary, not just the button — direct URL navigation into another role's screen has to be blocked, whether or not the link is hidden.
3. A red test here can mean the app is wrong, not the test — treat a matrix mismatch as a bug to report, never as data to quietly rewrite until the suite goes green.

## Try It

Add a tenth action to the matrix: `updateOwnProfile`, which every role should be able to do (`expected: 'allow'` for all four roles — the one row in this matrix where every column agrees). Add the corresponding rows to `permissionMatrix`, write an `actionChecks.updateOwnProfile` function that navigates to a profile route and checks for an editable field (`getByLabel` on a name or email input, for instance), and run the suite. Confirm all four new rows pass without touching anything in `rbac-permission-matrix.spec.ts` itself — if you had to edit the spec file to add a role-agnostic action, something in Step 4's loop isn't as data-driven as it should be.
