# Testing the RBAC Permission Matrix: Hands On

⏱ 30 minutes

## Breaking It Down

### Step 1: Turn the Matrix into a Typed Data Array

Start from the ground-truth table in [Overview](./overview): nine actions across four roles, copied verbatim from the RBAC app's README. Every cell becomes one object in a flat TypeScript array:

```typescript title="tests/data/permission-matrix.ts"
export type Role = 'admin' | 'doctor' | 'nurse' | 'patient';
export type Expected = 'allow' | 'deny';

export interface PermissionCase {
  role: Role;
  action: string;
  expected: Expected;
}

export const permissionMatrix: PermissionCase[] = [
  // View all users
  { role: 'admin', action: 'viewAllUsers', expected: 'allow' },
  { role: 'doctor', action: 'viewAllUsers', expected: 'deny' },
  { role: 'nurse', action: 'viewAllUsers', expected: 'deny' },
```

That's thirty-six rows, one for every cell in the matrix. None of it is a test yet. It's the spec, expressed as data a loop can consume.

### Step 2: Map Each Action to a UI Check

Each `action` string needs one function that performs it (or attempts to) and reports whether the role was actually permitted to do it. Keep this separate from the data. The matrix says *what should be true*; this file says *how to observe whether it is*:

```typescript title="tests/data/action-checks.ts"
import type { Page } from '@playwright/test';

type ActionCheck = (page: Page) => Promise<boolean>;

export const actionChecks: Record<string, ActionCheck> = {
  viewAllUsers: async (page) => {
    await page.goto('/admin/users');
    return page.getByRole('heading', { name: 'All Users' }).isVisible();
  },

  deleteUsers: async (page) => {
    await page.goto('/admin/users');
    const deleteButton = page
      .getByRole('row')
      .filter({ hasText: 'Doe' })
      .getByRole('button', { name: 'Delete' });
    return deleteButton.isVisible();
  },

  viewAllAppointments: async (page) => {
    await page.goto('/appointments');
    return page.getByRole('heading', { name: 'All Appointments' }).isVisible();
  },

  viewOwnAppointments: async (page) => {
    await page.goto('/appointments');
    return page.getByRole('heading', { name: 'My Appointments' }).isVisible();
  },

  scheduleAppointments: async (page) => {
    await page.goto('/appointments');
    return page.getByRole('button', { name: 'Schedule Appointment' }).isVisible();
  },

  completeAppointments: async (page) => {
    await page.goto('/appointments');
    return page.getByRole('button', { name: 'Complete' }).first().isVisible();
  },

  cancelAppointments: async (page) => {
    await page.goto('/appointments');
    return page.getByRole('button', { name: 'Cancel' }).first().isVisible();
  },

  createMedicalRecords: async (page) => {
    await page.goto('/medical-records');
    return page.getByRole('button', { name: 'Add Medical Record' }).isVisible();
  },

  viewMedicalRecords: async (page) => {
    await page.goto('/medical-records');
    return page.getByRole('heading', { name: 'Medical Records' }).isVisible();
  },
};
```

Every check returns a plain boolean ("is this role currently permitted to do this") so the test body never has to branch on which action it happens to be running.

### Step 3: Build a Role-Aware Fixture

You already have the pieces for this: the authentication lesson gave you a `storageState` file per role, and the fixtures lesson gave you fixtures that inject an already-authenticated page. Here, you'll generalize that into one fixture that hands back an authenticated page *for any role you ask for*, so a single test can request different roles instead of being locked to one role per project:

```typescript title="tests/fixtures/role-page.ts"
import { test as base, expect, type Page } from '@playwright/test';
import type { Role } from '../data/permission-matrix';

const storageStateFor: Record<Role, string> = {
  admin: 'playwright/.auth/admin.json',
  doctor: 'playwright/.auth/doctor.json',
  nurse: 'playwright/.auth/nurse.json',
  patient: 'playwright/.auth/patient.json',
};

type Fixtures = {
  getPageAs: (role: Role) => Promise<Page>;
};

export const test = base.extend<Fixtures>({
  getPageAs: async ({ browser }, use) => {
    const openContexts: Awaited<ReturnType<typeof browser.newContext>>[] = [];

    await use(async (role: Role) => {
      const context = await browser.newContext({ storageState: storageStateFor[role] });
      openContexts.push(context);
      return context.newPage();
    });

    for (const context of openContexts) {
      await context.close();
    }
  },
});

export { expect };
```

`getPageAs` opens a fresh browser context per call, seeded with that role's `storageState` from the authentication lesson, and Playwright's fixture teardown closes every context it opened once the test finishes. There's no manual cleanup in the test body, and no risk of one role's session leaking into another's check.

### Step 4: Data-Driven Tests, One `describe` Block Per Role

With the data, the checks, and the fixture all in place, you can generate the suite by looping: `test.describe.parallel` groups the roles, and a plain `for` loop handles each role's rows:

```typescript title="tests/rbac-permission-matrix.spec.ts"
import { test, expect } from './fixtures/role-page';
import { permissionMatrix, type Role } from './data/permission-matrix';
import { actionChecks } from './data/action-checks';

const roles: Role[] = ['admin', 'doctor', 'nurse', 'patient'];

test.describe.parallel('RBAC permission matrix', () => {
  for (const role of roles) {
    test.describe(`as ${role}`, () => {
      const casesForRole = permissionMatrix.filter((c) => c.role === role);

      for (const { action, expected } of casesForRole) {
        test(`${action}: expected ${expected}`, async ({ getPageAs }) => {
          const page = await getPageAs(role);
          const isPermitted = await actionChecks[action](page);

          if (expected === 'allow') {
            expect(isPermitted, `${role} should be able to ${action}`).toBe(true);
          } else {
            expect(isPermitted, `${role} should NOT be able to ${action}`).toBe(false);
          }
        });
      }
    });
  }
});
```

This one file produces 36 individually named, individually reportable tests (`as admin > viewAllUsers: expected allow`, `as patient > viewAllUsers: expected deny`, and so on) without a single hand-written duplicate. Add a fifth role to the RBAC app later, and this suite grows by adding rows to `permissionMatrix`, not by writing `receptionist.spec.ts`.

### Step 5: Negative Testing (Direct URL Access, Not Just Hidden Links)

Everything so far checks what a role's own dashboard renders. That proves the UI hides the right buttons. It says nothing about whether the backend actually stops a role that knows (or guesses) a URL it isn't supposed to have. A patient who types `/admin/users` into the address bar is not clicking a hidden link; they're testing the boundary directly, and your suite should too:

```typescript title="tests/rbac-direct-url-access.spec.ts"
import { test, expect } from './fixtures/role-page';
import type { Role } from './data/permission-matrix';

const forbiddenRoutes: { role: Role; path: string }[] = [
  { role: 'patient', path: '/admin/users' },
  { role: 'nurse', path: '/admin/users' },
  { role: 'doctor', path: '/admin/users' },
  { role: 'patient', path: '/appointments' },
];

test.describe.parallel('direct URL access is blocked, not just hidden', () => {
  for (const { role, path } of forbiddenRoutes) {
    test(`${role} navigating directly to ${path} is redirected or blocked`, async ({
      getPageAs,
    }) => {
      const page = await getPageAs(role);

      await page.goto(path);

      const blockedHeading = page.getByRole('heading', {
        name: /access denied|not authorized|login/i,
      });
      await expect(blockedHeading).toBeVisible();
      await expect(page).not.toHaveURL(path);
    });
  }
});
```

Note the fourth row: a patient hitting `/appointments`, the *all-appointments* route rather than their own, is included deliberately. It targets the same "own vs. all" boundary the matrix draws between `View own appointments` and `View all appointments`, a boundary that's easy to get right in the nav (just don't render the link) and easy to get wrong in the router (just don't check the role on the way in).

### Step 6: Run It, and Read a Failure as a Bug Report

```bash
npx playwright test tests/rbac-permission-matrix.spec.ts tests/rbac-direct-url-access.spec.ts
```

Because the RBAC app's own README marks this matrix "Not Completely Implemented," expect some red here on your first run. When a row fails (say `as nurse > viewAllAppointments: expected allow` comes back with `isPermitted: false`), that is not your test being wrong. It means the running app currently disagrees with its own documented spec: a nurse should see all appointments and, in the deployed code, cannot. Treat that the same way you'd treat any other failing test that caught a real defect: file it, don't silently change `expected: 'allow'` to `expected: 'deny'` in the data file just to turn the suite green. Loosening the assertion to match broken behavior doesn't fix the bug; it deletes the only thing that was telling you about it.

## How It Works Internally

`test.describe.parallel` doesn't change what each nested `test()` call does. It changes how Playwright schedules them. Tests declared inside a `describe.parallel` block run across available workers concurrently instead of sequentially within that block, the same way top-level test files already run in parallel by default. The `for` loops around `test()` calls are pure TypeScript, evaluated once when the file loads (this happens during Playwright's test-collection phase, before any test runs), and each iteration registers one more named test with the runner, which is why `npx playwright test --list` shows 36 distinct entries for a 36-row matrix instead of one.

The `getPageAs` fixture is deliberately test-scoped, not worker-scoped: every call opens a brand-new browser context. That costs a little more setup time per test than sharing one authenticated context across a whole worker would, but it buys correctness that matters specifically for permission testing: a context is exactly the browser's isolation boundary for cookies and storage, so reusing one across roles risks one role's session state bleeding into the next check. For a suite whose entire job is proving isolation between roles, the fixture's own isolation has to be airtight first.
