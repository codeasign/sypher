# Visual and Snapshot Testing: Hands On

⏱ 28 minutes

## Breaking It Down

### Step 1: Write Your First Screenshot Assertion

The login page is a good first candidate: it has no per-role variation, no timestamps, and no generated IDs. Every pixel on it should be identical from one run to the next unless someone actually changes the layout.

```typescript title="tests/visual/login.spec.ts"
import { test, expect } from '@playwright/test';

test('login page matches its baseline', async ({ page }) => {
  await page.goto('/login');

  await expect(
    page.getByRole('heading', { name: 'Login' })
  ).toBeVisible();

  await expect(page).toHaveScreenshot('login-page.png');
});
```

Notice the `expect(page.getByRole(...)).toBeVisible()` line sitting above `toHaveScreenshot()`. That's not decorative. It gives Playwright's auto-waiting something functional to settle on before the screenshot is taken, so you're not racing the page's initial render, which is exactly why you should never take a screenshot as the very first assertion in a test.

### Step 2: Generate the Baseline and Read What Playwright Wrote to Disk

Run the test:

```bash
npx playwright test tests/visual/login.spec.ts
```

There is no baseline yet, so Playwright creates one and passes:

```text
Error: A snapshot doesn't exist at tests/visual/login.spec.ts-snapshots/login-page-chromium-win32.png, writing actual.
1 passed (1.2s)
```

Look inside the generated `tests/visual/login.spec.ts-snapshots/` directory. The file is named `login-page-chromium-win32.png`, not `login-page.png`. Playwright appended the browser project name (`chromium`) and the platform (`win32`) automatically. If your `playwright.config.ts` also runs a `firefox` or `webkit` project, each gets its own baseline file the first time that project's test runs. This is the mechanism from the Overview lesson made concrete: one logical screenshot, one baseline file per platform/browser combination that actually rendered it.

Commit this file to the repo. It's the source of truth that every future run will compare against.

### Step 3: Catch a Real Layout Regression

To see the check actually catch something, simulate the frontend regression from the Overview lesson: in your `rbac-healthcare-system` fork, temporarily remove the `display: flex` rule from the doctor dashboard's appointment card container (or add an equivalent inline override) and restart the frontend.

Write the equivalent test for the dashboard, using the role-based `storageState` from the authentication lesson so the test starts already authenticated:

```typescript title="tests/visual/doctor-dashboard.spec.ts"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'storage/doctor.json' });

test('doctor dashboard layout matches its baseline', async ({ page }) => {
  await page.goto('/dashboard');

  await expect(
    page.getByRole('heading', { name: 'Doctor Dashboard' })
  ).toBeVisible();

  await expect(page).toHaveScreenshot('doctor-dashboard.png');
});
```

Run it once against the working frontend to capture a clean baseline, restore the frontend to normal, then reintroduce the broken CSS and run the test again:

```bash
npx playwright test tests/visual/doctor-dashboard.spec.ts
```

This time it fails:

```text
Error: Screenshot comparison failed:
  2481 pixels (ratio 0.031 of all image pixels) are different.
  Expected: doctor-dashboard-chromium-win32.png
  Actual:   doctor-dashboard-actual.png
  Diff:     doctor-dashboard-diff.png
1 failed (0.9s)
```

Open `doctor-dashboard-diff.png` from the HTML report and you'll see it highlight exactly the overlapping card region in red, against an otherwise unchanged page. That's the same regression that ordinary `getByRole` assertions had no way to see, because every element they check for is still present and still clickable.

### Step 4: Mask Dynamic Content Before Comparing

Revert the frontend to its working state, then look at what the doctor dashboard actually renders: a "Last updated" timestamp in the header and an auto-incrementing appointment ID (`#A1043`) in each row. Both change on every run: the timestamp because it reflects the current time, the ID because it comes from the database's auto-increment counter and depends on exactly how many records have been created in this seed run.

Without masking, this test would fail almost every time, for reasons that have nothing to do with layout:

```typescript title="tests/visual/doctor-dashboard.spec.ts"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'storage/doctor.json' });

test('doctor dashboard layout matches its baseline', async ({ page }) => {
  await page.goto('/dashboard');

  await expect(
    page.getByRole('heading', { name: 'Doctor Dashboard' })
  ).toBeVisible();

  await expect(page).toHaveScreenshot('doctor-dashboard.png', {
    mask: [
      page.getByTestId('last-updated'),
      page.getByRole('row', { name: /Jane Doe/ }).getByText(/^#A\d+$/),
    ],
    maskColor: '#FF00FF',
  });
});
```

Each locator passed to `mask` gets painted over with a solid box (`maskColor` here is magenta, so a masked region is obvious at a glance in the diff report) in both the newly rendered screenshot and the stored baseline before they are compared. The timestamp and the ID can change freely between runs; the layout around them, the card structure, the spacing, the rest of the page, still gets checked exactly as before.

Regenerate the baseline once with masking in place (see Step 5), and this test now passes reliably on every run regardless of what time it is or how many appointments the current seed created, while still catching the Step 3 regression, because the masked regions are a small fraction of the page and the overlapping cards are not inside either of them.

### Step 5: Update Baselines Deliberately, Never Blindly

Once you add `mask`, the existing baseline from Step 2 no longer matches. It was captured without masking, so its "before" pixels in the timestamp and ID regions are real content, not a magenta box. This is an intentional, expected change, not a regression, so this is exactly when `--update-snapshots` is the right tool:

```bash
npx playwright test tests/visual/doctor-dashboard.spec.ts --update-snapshots
```

Playwright re-renders the page, applies the mask, and overwrites the baseline file with the new masked version. Before committing it, open the new PNG and confirm two things by eye: the masked regions are solid magenta boxes in the right places, and the rest of the layout looks correct. `--update-snapshots` regenerates whatever the test currently produces. It has no idea whether "currently produces" means "intentional change" or "the same regression from Step 3 that you forgot to revert." Reviewing the new baseline before committing it is the only thing standing between those two cases.

This is also why `--update-snapshots` should never run automatically inside a CI job. A CI step that catches a screenshot failure and re-runs with `--update-snapshots` to make the build green is not fixing anything. It is teaching the suite to treat whatever the current, possibly broken, output looks like as correct, permanently, with no human ever looking at the diff. Treat a failing visual test in CI as a signal to investigate locally, decide whether it is a real regression or an intentional change, and only then run `--update-snapshots` on your own machine and commit the result as a reviewable diff in the pull request.

### Step 6: Keep Baselines Platform-Consistent for CI

If your CI pipeline (built properly in the continuous integration lesson) runs on a Linux runner and you generated every baseline in Steps 2 through 5 on Windows, every one of those tests will fail in CI on the first run. Not because anything regressed, but because `login-page-chromium-win32.png` does not exist on Linux, and the platform suffix means Playwright will not fall back to it. You have two options, and picking one deliberately now avoids a confusing failure in that lesson later:

- **Generate baselines inside a container matching CI.** Run `npx playwright test --update-snapshots` inside the same Docker image (`mcr.microsoft.com/playwright:...`) your CI job uses, so the committed baselines were rendered on the same platform they'll be compared against.
- **Generate baselines in CI itself, once, and commit the artifact back.** Some teams run a one-off CI job with `--update-snapshots`, download the resulting PNGs, and commit them from a real pull request, reviewed like any other change, never auto-committed by the pipeline itself.

Either way, the rule from Step 5 still applies: a baseline update is a reviewed, deliberate action, not something a CI job does to itself on a failure.

## How It Works Internally

`toHaveScreenshot()` renders the page (or element) to a PNG, then compares it against the stored baseline pixel by pixel using the same comparison engine Playwright uses internally (`pixelmatch`). How forgiving that comparison is comes down to three config values, settable globally in `playwright.config.ts` under `expect: { toHaveScreenshot: { ... } }` or per-call as a second argument. `threshold` (0 to 1, default `0.2`) controls how different a single pixel's color has to be before it counts as "changed" at all. Push it higher and you tolerate more per-pixel color drift, which helps absorb font anti-aliasing differences between runs on the same platform. `maxDiffPixels` then caps the absolute number of changed pixels allowed before the whole comparison fails, while `maxDiffPixelRatio` expresses that same idea as a fraction of the total image instead of a raw count, which scales better across screenshots of different sizes.

`mask` runs before any of that comparison happens. For each locator you pass, Playwright resolves its current bounding box and draws a filled rectangle over that region, in the color given by `maskColor`, directly on top of both the freshly rendered screenshot and the stored baseline before `pixelmatch` ever sees either one. A masked region always compares as identical, solid color against solid color, no matter what was underneath, which is exactly why it works for content that is expected to differ on every run.
