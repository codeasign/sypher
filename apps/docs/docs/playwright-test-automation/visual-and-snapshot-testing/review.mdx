# Visual and Snapshot Testing — Review

⏱ 4 minutes

## Key Takeaways

- `toHaveScreenshot()` compares a rendered page or element against a stored baseline pixel by pixel, which lets it catch layout and appearance regressions that role- and text-based assertions simply can't see — after all, the elements involved are still present, still labeled correctly, and still clickable.
- Playwright names baseline files per OS, browser, and project (`login-page-chromium-win32.png`) because font rendering and layout genuinely differ across platforms — baselines have to be generated on the same platform they'll be compared against, or comparisons fail for reasons unrelated to your app.
- The `mask` option paints a solid box over specified locators, in both the new screenshot and the baseline, before comparing — use it on anything that legitimately changes every run, like the doctor dashboard's "Last updated" timestamp or an appointment's auto-incrementing ID.
- `--update-snapshots` is a deliberate, reviewed action you run locally after confirming a change is intentional, never a step a CI job runs on itself to turn a failing build green.
- Reserve visual coverage for stable, layout-critical UI — the login form, a dashboard's overall structure — and skip it for pages whose content churns every run, like the patient list, where functional `expect(locator)` assertions already do the real work.

## Recap in 60 Seconds

If you only remember three things:

1. `toHaveScreenshot()` catches layout regressions your functional tests can't see, but only on pages stable enough that a difference is worth investigating every time.
2. Mask anything that's supposed to change — timestamps, generated IDs, record numbers — or the test will fail on legitimate data, not real regressions.
3. Update baselines deliberately, by hand, after looking at the new image — never automatically, and never inside CI.

## Try It

Extend the doctor dashboard test from Build It to cover the nurse dashboard instead, using `storage/nurse.json`. The nurse dashboard shows a "Schedule Appointment" button the doctor dashboard doesn't, and its appointment rows include a status badge that can read "Pending," "Confirmed," or "Cancelled" depending on live data. Write a `toHaveScreenshot()` test for it, decide which elements need masking beyond the ones you already identified for the doctor dashboard, and generate a reviewed baseline. Then ask yourself the decision-framework question from this lesson: does the nurse dashboard's overall structure change rarely enough to justify this test, or does it belong on the "functional assertions only" side of the line — and be ready to defend either answer.
