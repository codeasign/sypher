# Visual and Snapshot Testing — Common Mistakes

⏱ 9 minutes

## When NOT to Use This

Visual snapshot testing isn't a general-purpose substitute for the functional assertions you've been writing since early in this course, so don't reach for it out of habit. `expect(page.getByRole('row', { name: /Jane Doe/ })).toBeVisible()` should still be how you check that a specific patient's row exists, because a screenshot assertion would only tell you that *some* pixels changed somewhere on the page, not what actually broke or why. Save `toHaveScreenshot()` for layout and appearance specifically, on pages stable enough that a real difference is worth a human's attention every time it fires — not as your default assertion for everything.

It is also the wrong tool for any page whose content changes on essentially every run by design. The RBAC app's patient list is the clearest example in this course: 15 seeded patients today, a different count and a different set of names the next time `npm run seed` runs, or after any test in the RBAC permission-matrix suite creates or deletes a record. A screenshot of that page is comparing against a moving target — masking would have to cover almost the entire content area, at which point the assertion no longer checks anything meaningful.

## The Pattern to Remember

- **Pattern:** stable, layout-critical UI gets a `toHaveScreenshot()` test with dynamic regions masked; baselines are reviewed and committed deliberately, on the same platform CI will compare against.
- **When to use:** the login form, a dashboard's overall structural layout, anything where "does this still look right" is a real question independent of the exact data on screen.
- **When NOT to use:** pages whose content churns on every run (the patient list), anything already thoroughly covered by functional `expect(locator)` assertions with no meaningful layout risk, or as a first-line check for behavior rather than appearance.
- **Mental model:** a screenshot test is a smoke alarm for layout, not a metal detector for bugs — it tells you something visual changed, not what broke or why; keep it aimed at rooms where a fire would actually matter.

## Common Mistakes

### Mistake 1: Committing Baselines Generated on the Wrong Platform

**Mistake:** Running the test suite locally on a Windows or macOS machine, committing the resulting `*-win32.png` or `*-darwin.png` baselines, and expecting them to work against a Linux CI runner.

**Why it happens:** The test passes locally, the baseline file exists, and there's no obvious signal that platform matters until CI actually runs it.

**Symptoms:** Every visual test fails on its first CI run with a "snapshot doesn't exist" error, because Playwright looks for a `-linux.png` suffix that was never generated, or — worse, if the suffix logic is bypassed — fails with a wall of unrelated-looking pixel differences caused by font rendering, not layout.

**Fix:** Generate baselines inside a container matching your CI image (Step 6 of Build It), or generate them in a one-off CI job and commit the result back through a normal, reviewed pull request. Never assume a baseline captured on your laptop is valid evidence for what CI will render.

### Mistake 2: Auto-Updating Baselines Inside a CI Job

**Mistake:** Adding a step to the CI pipeline that catches a `toHaveScreenshot()` failure and re-runs with `--update-snapshots` so the build goes green.

**Why it happens:** It "fixes" the failing build immediately, and the mechanism looks identical to how you'd resolve it manually — just automated.

**Symptoms:** Real visual regressions stop failing builds entirely. A pull request that genuinely breaks the doctor dashboard's layout merges cleanly, because the pipeline silently accepted the broken render as the new correct baseline before anyone looked at it.

**Fix:** Treat any `--update-snapshots` run as a human decision made after looking at the new image, not an automatic response to a failure. If CI needs to help generate a baseline (Step 6's second option), have it produce a diffable artifact for a person to review and commit — never have the pipeline commit for itself.

### Mistake 3: Forgetting to Mask Dynamic Content

**Mistake:** Writing `toHaveScreenshot()` against the doctor dashboard or a medical record page without masking the "Last updated" timestamp or the auto-incrementing appointment/record IDs.

**Why it happens:** The test passes the moment you write it, because the baseline was captured with whatever timestamp and ID happened to exist at that instant — the problem only shows up on the *next* run.

**Symptoms:** The test fails intermittently, sometimes every run, always on a diff limited to a small text region, with a diff image that looks like nothing actually changed except a number. It gets misdiagnosed as "flaky" and either ignored or, worse, deleted.

**Fix:** Before writing any `toHaveScreenshot()` call against a page with generated or time-based content, identify every such element with `getByTestId`, `getByLabel`, or another precise locator, and pass all of them to `mask`. If a screenshot test keeps failing on content instead of layout, that's the signal you missed a mask, not that visual testing itself is unreliable.

### Mistake 4: Applying Screenshot Coverage to Every Page

**Mistake:** Adding `toHaveScreenshot()` to the patient list, the appointment history table, and every other frequently-changing view in the RBAC app, on the reasoning that "more coverage is always better."

**Why it happens:** It's an appealing shortcut — one line of code feels like it checks "everything" about a page at once, especially after you've spent dozens of lines writing narrow, specific `expect(locator)` assertions by hand.

**Symptoms:** The suite develops a permanent backlog of visual failures that nobody investigates individually anymore, because most of them turn out to be a changed patient count or a reordered row rather than an actual bug. Reviewers start rubber-stamping `--update-snapshots` diffs without reading them, which quietly defeats Mistake 2's fix even without a CI job doing it automatically.

**Fix:** Apply the decision framework from Key Takeaways before adding a screenshot test to any page: is this page's overall structure stable, and would a human actually want to know if it visually broke? If the honest answer is "its content changes every run and nobody would look at a diff carefully anyway," cover it with functional assertions instead and leave visual testing for pages where it earns its keep.

### Mistake 5: Skipping the Diff Review Before Committing an Update

**Mistake:** Running `--update-snapshots` after a visual test fails, seeing the suite go green, and committing the new baseline without opening the resulting PNG.

**Why it happens:** `--update-snapshots` is a single command that "fixes" the failure, and once the test passes there's no automatic prompt asking you to look at what you just approved.

**Symptoms:** A baseline update accidentally locks in the exact regression the test was supposed to catch — the Step 3 broken-layout scenario, committed as if it were the new, correct expected state, because nobody actually looked at the image before `git add`-ing it.

**Fix:** Make opening the newly generated screenshot a non-negotiable step before committing any baseline update — confirm the masked regions are in the right places and the surrounding layout looks correct. A baseline is a claim about what "correct" looks like; treat updating it with the same scrutiny you'd give any other change to what a test asserts.
