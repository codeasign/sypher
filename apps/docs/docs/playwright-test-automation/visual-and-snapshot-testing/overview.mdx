# Visual and Snapshot Testing

⏱ 20 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Capture and compare screenshots with `toHaveScreenshot()`, and read what Playwright does on a match, a mismatch, and a first run
- Explain why Playwright names baseline snapshot files per OS, browser, and project, and why that matters the moment CI enters the picture
- Update baselines deliberately with `--update-snapshots`, and explain why running that flag blindly inside a CI job defeats the entire purpose of the check
- Use the `mask` option to exclude specific locators — timestamps, appointment IDs, generated record numbers — from a pixel comparison so a snapshot only fails on layout regressions, not on legitimately-changing data
- Decide, with a real framework rather than a guess, which pages in the RBAC app are worth visual coverage and which ones would just generate noise

## Why This Matters

Every test you have written so far in this course checks *behavior*: does the right element exist, is the right text visible, does clicking the button trigger the right navigation. None of it checks *appearance*. A `getByRole('heading', { name: 'Doctor Dashboard' })` assertion passes whether that heading renders at the top of a clean, well-spaced page or is jammed against an overlapping appointment card because someone deleted a CSS `flex` rule in the same pull request. The element is still there, with the same role and the same accessible name — your functional tests have nothing to say about how it looks.

Visual snapshot testing fills that specific gap. It is not a replacement for `getByRole` and `expect(locator).toBeVisible()` — it is a second, narrower kind of test that catches a category of regression the first kind is structurally blind to: the page still *works*, but it no longer *looks right*.

## The Problem

Imagine a frontend pull request against the RBAC app removes a `display: flex` declaration from the doctor dashboard's appointment card container, while leaving every element, role, and label untouched. Run the suite you built in earlier modules and it passes cleanly:

```typescript title="tests/doctor-dashboard.spec.ts"
test('doctor sees their appointment list', async ({ page }) => {
  await page.goto('/dashboard');

  await expect(
    page.getByRole('heading', { name: 'Doctor Dashboard' })
  ).toBeVisible();

  await expect(
    page.getByRole('row', { name: /Jane Doe/ })
  ).toBeVisible();
});
```

Every locator still resolves, and every assertion still passes — but in a real browser, the appointment cards now stack on top of each other instead of flowing into a grid, and a doctor opening the dashboard sees a visually broken page. Nothing in the earlier lessons catches this, because none of it was designed to — those lessons test what the DOM contains and how it behaves, not where things land on screen or whether they overlap.

## The Concept

`toHaveScreenshot()` is Playwright's built-in pixel comparison assertion. The first time it runs against a given test, there is no baseline yet, so Playwright captures one, saves it to disk next to the spec file, and passes the test. Every run after that renders the page (or element) again, compares the new image pixel-by-pixel against the saved baseline, and fails the test if the difference exceeds a configurable threshold — producing a diff image alongside the actual and expected ones so you can see exactly what changed.

Two details make this different from an assertion like `toBeVisible()`:

**Baselines are named per platform.** By default, Playwright appends the operating system, browser, and project name to the snapshot filename — something like `dashboard-chromium-win32.png` versus `dashboard-chromium-linux.png`. This exists because font rendering, anti-aliasing, and subpixel layout genuinely differ between operating systems, even for identical HTML and CSS. A baseline captured on your Windows laptop will not byte-for-byte match what Chromium renders on a Linux CI runner — not because anything is broken, but because the two platforms rasterize text and shapes differently. Baselines have to be generated on the same platform they will be compared against, or comparisons will fail for reasons that have nothing to do with your app.

**Some content in the RBAC app is supposed to change.** The doctor dashboard renders a "Last updated" timestamp, appointment records show auto-incrementing IDs, and medical records display generated record numbers. Every one of those values is different on every run, by design. A screenshot assertion that includes them in the pixel comparison will fail constantly — not because the layout regressed, but because `#A1042` legitimately became `#A1043` since the baseline was captured. The `mask` option solves this: you pass it the locators covering that dynamic content, and Playwright paints a solid box over each one, in both the baseline and the new screenshot, before comparing pixels. The layout around the masked region is still checked; the ever-changing content inside it is not.

The masked regions never contribute to the diff — only the surrounding layout does. That is what turns a screenshot assertion from something that fails on every run into something that fails only when the layout actually changes.
