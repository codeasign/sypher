# Playwright MCP and Driving the Browser from an AI Client: Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Playwright MCP is for interactive exploration: you have a goal, no script, and you want an agent to navigate an unfamiliar flow and report back. It's worth being clear about what it isn't, because it's easy to reach for it in places where this course already gives you a better tool.

It's not a CI test runner. An MCP session is a conversation with a live browser, not a deterministic, repeatable test run, and the continuous integration lesson's CI pipeline runs `npx playwright test`, not an MCP client, so nothing about an exploration session belongs in a GitHub Actions job. It's not a substitute for `toHaveScreenshot()` either: MCP can take a screenshot on request, but it has no baseline to compare against and no pixel-diff logic, so visual regression testing is still the visual and snapshot testing lesson's job. It's also not a substitute for the Playwright Test Agents workflow once you already know the flow. If you already know exactly which spec you want generated, `npx playwright init-agents`' Planner/Generator pair is the more direct tool, and MCP is what you reach for instead when you don't yet know what's there to test. And it's not a place to leave write-heavy exploration unattended: an agent clicking "Complete," "Delete," or "Cancel" against the seeded RBAC database mutates real rows in a shared SQLite file, the same database every other module's tests assume is in a known, seeded state.

## The Pattern to Remember

- **Pattern:** connect an MCP client to `@playwright/mcp`, load a `storageState` file from the authentication lesson so the browser starts authenticated, explore from a natural-language goal, read `browser_snapshot` output as the primary signal, and commit any real finding as an ordinary reviewed spec.
- **When to use:** you have a goal but no script yet: an unfamiliar flow, a "what actually happens when" question, or scaffolding the first draft of a new area of coverage.
- **When NOT to use:** CI execution, visual regression, or any flow you can already describe precisely enough to hand-write or generate directly.
- **Mental model:** MCP gives an agent a keyboard and a pair of eyes for the same browser your tests already use. It is a way of looking around, not a way of running your suite.

## Common Mistakes

### Mistake 1: Skipping storageState and Burning Tokens on Login Every Session

**Mistake:** Connecting `@playwright/mcp` with no `--storage-state` flag, so every exploration session starts at the login screen and the agent has to authenticate from scratch before doing anything useful.

**Why it happens:** The overview and quickstart examples for `@playwright/mcp` default to a bare, unauthenticated launch. It's the simplest thing to copy-paste, and it works fine for a one-off look at the login page itself.

**Symptoms:** Every session opens with several tool calls (`browser_navigate` to `/login`, two `browser_type` calls, a `browser_click`) before the agent even reaches the page you actually wanted explored, and you pay that cost in tokens and turns every single time you reconnect.

**Fix:** Point `--storage-state` at the authentication lesson's file for whichever role you're exploring as (`playwright/.auth/doctor.json`, `nurse.json`, and so on). The browser context starts already authenticated, exactly the way a `storageState` project does for a real test run.

### Mistake 2: Defaulting to Screenshots for Routine Navigation

**Mistake:** Asking the agent to work primarily from `browser_take_screenshot` instead of `browser_snapshot` for ordinary "click this, check that" exploration.

**Why it happens:** A screenshot feels more intuitively like "what a human would look at," so it's a natural first instinct when you're thinking about an agent driving a browser.

**Symptoms:** Sessions cost noticeably more tokens per turn, and the agent occasionally clicks the wrong element because it's estimating a click point from a rendered image instead of targeting a specific accessible element by role and name.

**Fix:** Let `browser_snapshot` be the default lens for anything about structure, labels, or state. It's cheaper and it targets elements the same way a `getByRole` locator would. Reserve `browser_take_screenshot` for genuinely visual questions: layout, overlap, spacing, the visual and snapshot testing lesson's territory.

### Mistake 3: Mistaking a Chat Transcript for a Test Suite

**Mistake:** Treating a successful MCP exploration session, where the agent clicked through a flow and reported it worked, as equivalent to having test coverage for that flow.

**Why it happens:** The session felt exactly like watching a test pass: the agent navigated, clicked, and confirmed the expected outcome, so it's easy to file the flow away as "covered."

**Symptoms:** Weeks later, that exact flow breaks in production, and there's no failing CI run to catch it, because nothing from the exploration session was ever committed as a spec that runs on its own.

**Fix:** Treat every useful MCP finding the way Step 6 of Build It does. Write it up as a real `.spec.ts` file with `storageState` and `getByRole` locators, and let it run in CI from then on. The session is where you discover what to test, not where the test lives.

### Mistake 4: Sharing One Browser Context Across Roles

**Mistake:** Running MCP sessions for multiple roles (admin, then doctor, then patient) against the same non-isolated browser profile, without a per-role `storageState` or the `--isolated` flag.

**Why it happens:** Reusing one running MCP server across a working session is the path of least resistance, and nothing errors immediately when you switch roles mid-conversation.

**Symptoms:** An exploration session "as a patient" unexpectedly shows admin-only UI, or a login from one role silently overwrites the session state you expected for another, and you can't tell whether that's a real permission bug or just state bleed from your own setup.

**Fix:** Launch with `--isolated` and a specific `--storage-state` per role you intend to explore as, the same one-file-per-role discipline the authentication lesson uses for real test projects. Switching roles means reconfiguring the server's storage state, not trusting one shared context to behave like four.

### Mistake 5: Letting an Agent Mutate Seeded Data Without Tracking It

**Mistake:** Giving an MCP-driven agent free rein to click "Complete," "Cancel," or "Delete" against the seeded RBAC database during exploration, without treating those as real writes to shared fixture data.

**Why it happens:** An MCP session feels like a read-only conversation, you're "just looking around," even though every click it performs is a real Playwright action against the real running app and its real SQLite file.

**Symptoms:** A later module's test fails because an appointment or patient record the seed script created no longer exists, or now has a different status, and nobody connects the failure back to an exploration session from days earlier.

**Fix:** Treat MCP write actions with the same care as any other test run touching shared state. Prefer read-oriented goals ("show me what a doctor sees") for open-ended exploration, and re-run `npm run seed` if a session mutated data you or later modules depend on.
