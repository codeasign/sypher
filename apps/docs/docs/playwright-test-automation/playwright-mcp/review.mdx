# Playwright MCP and Driving the Browser from an AI Client — Review

⏱ 5 minutes

## Key Takeaways

- MCP (Model Context Protocol) is a standardized bridge that exposes Playwright's own browser actions — `browser_navigate`, `browser_click`, `browser_snapshot`, and more — as tools any MCP-capable LLM client can call against a live browser.
- `@playwright/mcp` is Microsoft's reference server; you register it with an MCP client via `claude mcp add` or a JSON `mcpServers` config, and it launches its own browser context on demand.
- `browser_snapshot` returns a structured accessibility tree — roles, names, values, and refs — the same information a `getByRole` locator resolves against, and it's the default, cheaper, more reliable lens for an agent's routine navigation.
- `browser_take_screenshot` costs more tokens and answers a narrower question — layout, overlap, visual appearance — and stays the visual and snapshot testing lesson's territory rather than the default exploration tool.
- Pointing the MCP server's `--storage-state` flag at a file from the authentication lesson (`playwright/.auth/doctor.json` and the like) means the browser context starts already authenticated, so an agent doesn't burn tool calls and tokens re-logging-in every session.

## Recap in 60 Seconds

If you only remember three things:

1. MCP connects an LLM client's reasoning to a real, running Playwright browser through a standard set of tools — it's a way of looking around an app you haven't scripted yet, not a new test runner.
2. Default to `browser_snapshot`'s accessibility tree, not `browser_take_screenshot`, for anything about structure or state — it's cheaper and it targets elements the way your locators already do; reach for a screenshot only for genuinely visual questions.
3. Wire in a `storageState` file from the authentication lesson before exploring, so the agent starts authenticated instead of re-running the login flow on every single session — and always turn a real finding into a committed, reviewed spec, because nothing in an MCP session runs again on its own.

## Try It

Using the nurse role instead of the doctor role, connect `@playwright/mcp` with `--storage-state playwright/.auth/nurse.json --isolated`, then give your MCP client this goal, with no spec written in advance:

"Find the scheduling flow on the nurse dashboard, schedule a new appointment for any seeded patient, and tell me exactly what confirmation the UI shows — a message, a redirect, or a change to a list."

1. Read the `browser_snapshot` output at each step and note which elements the agent targeted by role and name.
2. Ask the agent to also take a screenshot at the moment of confirmation, and compare: did the screenshot tell you anything the tree didn't, or vice versa?
3. Write up whatever the agent found as a real `.spec.ts` file using `test.use({ storageState: 'playwright/.auth/nurse.json' })` and web-first `expect(locator)` assertions — the same conversion from finding to committed spec as Build It's Step 6.

If the confirmation behavior you find here contradicts something the RBAC permission-matrix lesson's permission matrix implies about nurse scheduling, that's not a lesson bug — treat it exactly like that lesson taught you to: a legitimate discovery worth its own assertion, not a detail to paper over.
