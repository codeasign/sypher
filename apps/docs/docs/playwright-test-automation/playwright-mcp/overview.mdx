# Playwright MCP and Driving the Browser from an AI Client

⏱ 20 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Explain what the Model Context Protocol (MCP) is doing in this context: a standardized bridge that exposes Playwright's own browser actions as callable tools to any MCP-capable LLM client
- Install and register Microsoft's reference server, `@playwright/mcp`, with an MCP client (Claude Code, Claude Desktop, or Cursor)
- Drive the RBAC app from a natural-language goal (no pre-written spec) and read the `browser_snapshot` output the agent is actually reasoning over
- Explain why an accessibility-tree snapshot is usually a better "view" for an agent than a screenshot, and identify the cases where a screenshot is still the right tool
- Wire a `storageState` file from the authentication lesson into the MCP server's launch so an agent explores the app already authenticated, instead of re-logging-in on every session

## Why This Matters

Every module before this one assumes you already know what you want to test. You write a locator because you already know which button opens the "Add Patient" form. But the first time you touch an unfamiliar corner of the RBAC app (say, you've never actually looked at what a doctor sees after completing an appointment) you don't have a spec yet. You have a browser, a goal, and no script.

The usual options for that situation are both awkward. Clicking through the app yourself in a real browser works, but nothing you learn gets captured anywhere. Writing a throwaway Playwright script just to look around means writing code before you even know what's there. Playwright MCP gives you a third option: point an LLM client at the running browser, tell it what you're trying to find out in plain language, and let it navigate, read the page, and report back. It uses the exact same underlying Playwright APIs a hand-written test would use, just called by an agent instead of by your keyboard.

## The Problem

Picture this goal: "As a doctor, what happens after I mark an appointment complete? Does it move to a history list, or just disappear?" Nobody has written a test for this yet, and you don't know the page structure well enough to write one blind.

Without MCP, you're left choosing between a few imperfect options. You could log in manually in a real browser and click around. That's fast, but nothing you find is reusable, and you'll have forgotten the exact steps by the time you sit down to write the actual spec. You could write a throwaway `page.goto()` / `page.click()` script just to explore, except you don't yet know the locators, which is the whole thing you're trying to discover in the first place. Or you could open devtools and read the DOM by hand, which is slow and only gets you markup, not the accessible structure a `getByRole` locator actually depends on.

None of these connect an LLM's reasoning to a live, running instance of the app. That's the gap Playwright MCP closes: it lets an MCP client call the same `browser_navigate`, `browser_click`, and `browser_snapshot` primitives Playwright's own APIs are built on, so an agent can explore the doctor's post-appointment flow interactively and tell you what it found, in the same session where you'll eventually turn that finding into a real spec.

## The Concept

MCP (Model Context Protocol) is a standardized way for an LLM client to discover and call tools exposed by a separate server process, over a local connection, without either side needing custom integration code. Microsoft's `@playwright/mcp` is a server that implements this protocol and exposes Playwright's own browser automation as a set of callable tools: `browser_navigate`, `browser_click`, `browser_type`, `browser_snapshot`, `browser_take_screenshot`, `browser_wait_for`, and more. Any MCP-capable client (Claude Code, Claude Desktop, Cursor) can connect to that server, see the list of available tools, and call them in response to your natural-language request.

The critical design choice in `@playwright/mcp` is what it hands back to the agent after each action: by default, not a screenshot, but a structured accessibility-tree snapshot, the same role/name/value information a `getByRole` locator resolves against. The agent reads that structured tree, decides what to click by role and name (exactly how you'd write a locator yourself), and calls `browser_click` against a specific element reference from that snapshot. Nothing about this bypasses Playwright's auto-waiting or its locator model. It's the same engine this whole course has been teaching, just being driven by an agent's reasoning loop instead of a `.spec.ts` file you wrote in advance.

Because the MCP server launches its own browser context, it starts unauthenticated by default. Every session would otherwise begin at the RBAC app's login screen, and every agent turn that needs to be "logged in as a doctor" would first have to fill in the login form itself, burning tool calls and tokens on a flow that has nothing to do with what you're actually exploring. The `storageState` files from the authentication lesson solve this exactly the way they solve it for hand-written tests: point the MCP server's launch at `playwright/.auth/doctor.json`, and the browser context it opens starts already authenticated as a doctor, before the agent's first tool call.
