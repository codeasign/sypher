# Playwright MCP and Driving the Browser from an AI Client: Hands On

⏱ 30 minutes

## Breaking It Down

### Step 1: Install and Register the Playwright MCP Server

`@playwright/mcp` doesn't need a separate global install. An MCP client launches it on demand via `npx`. Register it with Claude Code from your project root:

```bash
claude mcp add playwright -- npx @playwright/mcp@latest
```

If your client uses a JSON config instead (Claude Desktop, for example), add a `playwright` entry under `mcpServers`:

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}
```

Restart the client so it picks up the new server, then confirm the connection: in Claude Code, `/mcp` should list `playwright` as connected, with tools like `browser_navigate`, `browser_click`, `browser_type`, and `browser_snapshot` available.

### Step 2: Explore With No Storage State: Feel the Cost First

Before wiring in authentication, try the goal from the overview with a bare connection, so you can see the problem `storageState` solves. With both RBAC servers running, give your MCP client this goal:

```text
Navigate to the RBAC app at http://localhost:3002 and tell me what the login
page looks like: what fields and buttons does it expose?
```

The agent calls `browser_navigate` to `http://localhost:3002/login`, then `browser_snapshot` to read the page. You'll get back something like:

```yaml
- heading "Sign In" [level=1]
- textbox "Username" [ref=e3]
- textbox "Password" [ref=e4]
- button "Log In" [ref=e5]
```

That's the accessibility tree, not a picture: roles, accessible names, and a `ref` the agent uses to target that exact element on a follow-up `browser_click`. Now ask a second goal in the same session:

```text
Log in as the seeded admin account and open the Users page.
```

The agent fills `admin` / `admin123` into the two textboxes by `ref`, clicks "Log In," and navigates from there. That works, but notice what just happened: an entire login round trip (two `browser_type` calls, one `browser_click`, one navigation wait) just to get to the page you actually wanted to look at. Every new session with this agent repeats it.

### Step 3: Wire In the Authentication Lesson's Storage State

Reuse the `playwright/.auth/doctor.json` file the authentication lesson's `globalSetup` already produced. Reconfigure the MCP server to load it at launch:

```bash
claude mcp remove playwright
claude mcp add playwright -- npx @playwright/mcp@latest --storage-state playwright/.auth/doctor.json --isolated
```

Or, in a JSON config:

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": [
        "@playwright/mcp@latest",
        "--storage-state",
        "playwright/.auth/doctor.json",
        "--isolated"
      ]
    }
  }
}
```

`--storage-state` points the browser context the server launches at that exact file: cookies and `localStorage` for a doctor session, captured once by the authentication lesson's `globalSetup`. `--isolated` keeps this context from persisting or bleeding into a shared user-data directory across sessions, so each MCP session starts from that same known doctor state, not whatever a previous exploration left behind.

Restart the client, then give it the same kind of goal as before:

```text
Go to the dashboard and tell me what a doctor sees.
```

This time there's no login tool call at all. `browser_navigate` to `/dashboard` lands the agent directly on the authenticated view, because the browser context was already carrying the doctor's session before the first tool call ran.

### Step 4: Explore an Unscripted Flow From a Natural-Language Goal

With the doctor session already authenticated, give the agent the actual goal from the overview: something nobody has written a spec for yet.

```text
Find an appointment on the doctor dashboard that isn't completed yet, mark it
complete, and tell me exactly what changes on the page afterward: does the
appointment move somewhere, get relabeled, or disappear?
```

Watch the tool calls the agent makes, not just its final answer: a `browser_snapshot` to see the current appointment list, a `browser_click` on a specific appointment row's "Complete" action by its `ref`, another `browser_snapshot` to read the page afterward, and a comparison between the two trees. The agent might report back something like: "The appointment stayed in the same list but its status column changed from `Scheduled` to `Completed`, and a new `Cancel` action button was replaced with a disabled state." That's a real, previously-undocumented finding about the app's behavior, discovered by reasoning over accessibility-tree snapshots, with no script written in advance.

### Step 5: Compare a Snapshot to a Screenshot for the Same State

Ask the agent to also take a screenshot of the same dashboard state:

```text
Now take a screenshot of the same dashboard and describe what you see.
```

Compare what came back. The `browser_snapshot` gave you a compact, structured list of roles and names: a few hundred tokens, exactly the same information a `getByRole` locator would query. The screenshot is an image the agent has to interpret visually, costs far more tokens to transmit and reason over, and can't tell you precisely which DOM element holds a given piece of text. It can only describe what's visually present. For "did the status column change from Scheduled to Completed," the tree answered directly; the screenshot required the agent to guess at layout and re-describe it in words.

Now try a case where the screenshot earns its keep:

```text
Take a screenshot of the appointment list and tell me if any of the status
badges are visually overlapping their row's action buttons.
```

The accessibility tree has no concept of layout. It can tell you a badge and a button both exist, but not whether they're rendered on top of each other. That's a visual regression question, and it's exactly the visual and snapshot testing lesson's territory: reach for `browser_take_screenshot` (or, in a committed test, `toHaveScreenshot()`) when the question is about how something looks, not what it is or what it's labeled.

### Step 6: Turn a Finding Into a Committed Spec

The appointment-completion behavior you just discovered in Step 4 is a real fact about the app now, worth keeping, not just worth having seen once in a chat session. Write it up as an ordinary Playwright spec, using the same `storageState` project convention from the authentication lesson:

```typescript title="tests/doctor-dashboard/complete-appointment.spec.ts"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'playwright/.auth/doctor.json' });

test('completing an appointment updates its status without removing it', async ({ page }) => {
  await page.goto('/dashboard');

  const appointmentRow = page.getByRole('row', { name: /Scheduled/ }).first();
  await appointmentRow.getByRole('button', { name: 'Complete' }).click();

  await expect(appointmentRow.getByText('Completed')).toBeVisible();
  await expect(appointmentRow.getByRole('button', { name: 'Complete' })).toBeHidden();
});
```

This is the point of the whole exercise: MCP exploration produces a finding; a hand-written, reviewed spec is what actually runs in CI from here on. The agent session did the discovery work faster than clicking through manually and typing notes, but nothing from that session runs automatically ever again unless you commit a spec like this one.

## How It Works Internally

Each MCP tool call is a request/response round trip between the client (the LLM reasoning about what to do next) and the `@playwright/mcp` server (which actually holds the running browser). `browser_snapshot` asks Playwright for the current page's accessibility tree, the same tree structure the browser exposes to screen readers, and the same one every `getByRole` locator in this course queries against, and serializes it into the compact, ref-annotated text format you saw in Step 2. When the agent calls `browser_click` with a specific `ref`, the server resolves that ref back to the actual DOM element and performs a real Playwright `click()` against it, with the same auto-waiting guarantees any hand-written test gets.

This is why `browser_snapshot` is the default lens and `browser_take_screenshot` is the exception: the tree is what locators are made of, so an agent reading it is reasoning in the same terms your test code will eventually use. A screenshot hands the agent a rendering to interpret instead: useful when the question is genuinely about pixels, layout, or visual overlap, but a strictly noisier and more expensive channel for "what is on this page and what does it do."
