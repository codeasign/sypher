# Test Organization and Tagging

⏱ 18 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Group related specs with `test.describe` so the RBAC app's per-role suites (doctor dashboard, nurse dashboard, and so on) read as organized units instead of a flat pile of `test()` calls
- Break a single test into named, nested steps with `test.step` so trace viewer shows a readable timeline instead of one undifferentiated block
- Tag tests `@smoke` and `@regression` using Playwright's title-based tag convention, and know when the newer `tag` test option is the better fit
- Run a subset of the suite with `--grep @smoke` and exclude a subset with `--grep-invert @regression`
- Split the RBAC suite into a fast PR-gate smoke subset and a full nightly run, and explain concretely which tests from the RBAC permission-matrix, visual and snapshot testing, and cross-browser testing lessons belong in each

## Why This Matters

By this point in the course, the RBAC suite is no longer small. The permission matrix alone spans nine actions across four roles, which works out to thirty-six data-driven test cases. Add visual snapshots per dashboard and viewport, and cross-browser runs across three engines, and a single `npx playwright test` invocation with no filtering can easily mean several hundred individual test executions. That's exactly the coverage you want before a release — just not what you want blocking a pull request that changes one line of copy on the login form.

Every real test suite eventually hits this tension: thoroughness and speed pull in opposite directions, and you cannot buy both for free. The fix is not to trim coverage — it is to organize the suite so different slices of it run at different times, for different purposes. `test.describe` and `test.step` make a large suite navigable. Tags turn that organization into something the test runner can filter on from the command line, so a pull request gets a fast, representative signal in minutes, and the full RBAC matrix, every visual baseline, and every browser engine still get exercised every night, without either sacrificing the other's job.

## The Problem

Imagine the RBAC suite as one flat set of spec files with no structure beyond folder names:

```typescript
// tests/doctor.spec.ts — no grouping, no tags, no way to run a subset
test('doctor logs in', async ({ page }) => { /* ... */ });
test('doctor views own appointments', async ({ page }) => { /* ... */ });
test('doctor completes an appointment', async ({ page }) => { /* ... */ });
test('doctor cannot view all users', async ({ page }) => { /* ... */ });
// ...and the same shape repeated for admin, nurse, patient,
// plus 36 permission-matrix rows, plus visual snapshots per dashboard,
// plus every one of the above again on Firefox and WebKit
```

There is no way to ask this suite "just run the handful of tests that prove the app fundamentally still works" without either running everything — several minutes, on every push, for every contributor — or manually hand-picking file paths, which breaks the moment someone renames a file or adds a new one. A CI pipeline that gates every pull request on the full nightly-scale run either makes contributors wait ten-plus minutes for feedback on a trivial change, or teams quietly start skipping CI, both of which defeat the purpose of having a fast feedback loop at all.

## The Concept

Three separate mechanisms solve three separate problems, and this lesson covers all three because they compose:

1. **`test.describe`** groups related tests under a shared heading, which makes them easier to read in code and in the HTML reporter, and gives you a unit you can tag together.
2. **`test.step`** breaks the *inside* of one test into named phases, so trace viewer's timeline reads as "navigate to dashboard → open appointment → mark complete → verify record" instead of one opaque block of actions.
3. **Tags** (`@smoke`, `@regression`) are just text embedded in a test's title, following Playwright's own convention of an `@word` token. The test runner's `--grep` and `--grep-invert` flags are ordinary regex filters that happen to work perfectly against that convention, because `--grep` matches against a test's *full title* — its `describe` title plus its own title, concatenated.

None of these three change what a test does — they change how you can find, read, and selectively run tests as the suite grows from dozens of tests to hundreds.

The split is not arbitrary. The smoke subset answers one question fast: "did I break something fundamental for one of the four roles?" The nightly run answers a slower, deeper question: "does the app still match the full permission matrix, look right, and work correctly on every supported browser?" Both questions matter. They just do not have to be answered on the same schedule.
