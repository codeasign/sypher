# Test Organization and Tagging — Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Group Related Specs with test.describe

Start with the doctor dashboard tests. Instead of a flat list of `test()` calls in `tests/doctor-dashboard.spec.ts`, wrap them in a `test.describe` block:

```typescript title="tests/doctor-dashboard.spec.ts"
import { test, expect } from '@playwright/test';

test.describe('Doctor Dashboard', () => {
  test.use({ storageState: 'playwright/.auth/doctor.json' });

  test('doctor sees their own appointments list', async ({ page }) => {
    await page.goto('/dashboard');

    await expect(
      page.getByRole('heading', { name: 'My Appointments' })
    ).toBeVisible();
  });

  test('doctor can mark an appointment complete', async ({ page }) => {
    await page.goto('/dashboard');

    await page
      .getByRole('row', { name: /Jane Patient/ })
      .getByRole('button', { name: 'Complete' })
      .click();

    await expect(
      page.getByRole('row', { name: /Jane Patient/ })
    ).toContainText('Completed');
  });

  test('doctor cannot view the admin user list', async ({ page }) => {
    await page.goto('/admin/users');

    await expect(
      page.getByRole('heading', { name: 'Access Denied' })
    ).toBeVisible();
  });
});
```

`test.use({ storageState: ... })` inside the `describe` block applies to every test nested inside it. That's the same storageState pattern from the authentication lesson — just scoped to this one group instead of the whole project. The HTML reporter (covered in the reporting lesson) now shows these three tests nested under "Doctor Dashboard" instead of as three unrelated rows, and you can target the whole group from the command line:

```bash
npx playwright test --grep "Doctor Dashboard"
```

`describe` blocks nest, too. If the doctor suite grows large enough to need its own sub-groups — appointments versus medical records, say — nest a second `test.describe` inside the first, and `--grep` still matches against the full concatenated title.

### Step 2: Add test.step for Readable Trace Output

`test.describe` organizes tests *between* each other. `test.step` organizes what happens *inside* one test. Take a longer, multi-part flow — a nurse scheduling an appointment end to end — and break it into named steps:

```typescript title="tests/nurse-dashboard.spec.ts"
import { test, expect } from '@playwright/test';

test.describe('Nurse Dashboard', () => {
  test.use({ storageState: 'playwright/.auth/nurse.json' });

  test('nurse schedules an appointment for a patient', async ({ page }) => {
    await test.step('open the schedule-appointment form', async () => {
      await page.goto('/dashboard');
      await page.getByRole('button', { name: 'Schedule Appointment' }).click();
    });

    await test.step('fill in patient and doctor', async () => {
      await page.getByLabel('Patient').fill('Jane Patient');
      await page.getByLabel('Doctor').selectOption({ label: 'Dr. Smith' });
      await page.getByLabel('Date').fill('2026-08-10');
    });

    await test.step('submit and verify it appears on the list', async () => {
      await page.getByRole('button', { name: 'Save' }).click();

      await expect(
        page.getByRole('row', { name: /Jane Patient.*Dr\. Smith/ })
      ).toBeVisible();
    });
  });
});
```

Without steps, a failure in this test shows trace viewer as one long, undifferentiated sequence of actions — you have to scrub through every click to find where things went wrong. With steps, trace viewer's timeline shows three collapsible phases by name. When "submit and verify it appears on the list" is the one that's red, you know immediately that the form filled out correctly and the failure is in submission or in the list refresh — you don't have to replay the whole test to localize the problem.

### Step 3: Tag Tests with @smoke and @regression

Playwright's tag convention is deliberately simple: a tag is just an `@word` token, anywhere in a test's title or its `describe` title. No special API is required to create one — `--grep` is a regular expression matcher, and `@smoke` is a valid regex that happens to also read as a tag:

```typescript title="tests/doctor-dashboard.spec.ts"
test.describe('Doctor Dashboard', () => {
  test.use({ storageState: 'playwright/.auth/doctor.json' });

  test('@smoke doctor sees their own appointments list', async ({ page }) => {
    await page.goto('/dashboard');
    await expect(
      page.getByRole('heading', { name: 'My Appointments' })
    ).toBeVisible();
  });

  test('@regression doctor can mark an appointment complete', async ({ page }) => {
    // covered in the nightly run, not the PR gate
  });

  test('@smoke @regression doctor cannot view the admin user list', async ({ page }) => {
    // RBAC boundary check — cheap enough to run in both buckets
  });
});
```

A test can carry more than one tag — the negative RBAC check above is fast enough to belong in the smoke subset, but it's also part of what the nightly run should re-verify as a matter of policy, so it carries both. Playwright 1.42 and later also support a structured `tag` option instead of embedding the token in the title:

```typescript
test('doctor sees their own appointments list', {
  tag: ['@smoke'],
}, async ({ page }) => {
  // same test, tag expressed as an option instead of title text
});
```

Both forms produce the same `--grep`-filterable result. This course uses the title convention in examples because it's visible directly in the HTML reporter and in trace viewer's test name without opening the test's options, but either is a legitimate choice — pick one per project and apply it consistently.

### Step 4: Run Subsets with --grep and --grep-invert

With tags in place, filter a run from the command line:

```bash
# only tests whose full title contains @smoke
npx playwright test --grep @smoke

# everything except tests tagged @regression
npx playwright test --grep-invert @regression

# combine a tag filter with a single project, for the fastest possible signal
npx playwright test --grep @smoke --project=chromium
```

`--grep` and `--grep-invert` both match against a test's *full title* — the `describe` title and the test's own title, joined together — which is why Step 1's grouping and Step 3's tagging compose instead of competing. A test titled `@smoke doctor sees their own appointments list` inside a `describe('Doctor Dashboard')` block has an effective full title of `Doctor Dashboard @smoke doctor sees their own appointments list`, and `--grep @smoke` matches it regardless of where the tag sits in that string.

### Step 5: Build the PR-Gate Smoke Suite

A smoke suite proves the app fundamentally works, for every role, in the time it takes to make a coffee — not the time it takes to make lunch. Tag one or two of the most critical flows per role, aiming for roughly a dozen tests total:

```typescript title="tests/smoke/rbac-smoke.spec.ts"
import { test, expect } from '@playwright/test';

test.describe('RBAC Smoke — Admin', () => {
  test.use({ storageState: 'playwright/.auth/admin.json' });

  test('@smoke admin can view the full user list', async ({ page }) => {
    await page.goto('/admin/users');
    await expect(page.getByRole('table')).toBeVisible();
  });

  test('@smoke admin can view all appointments', async ({ page }) => {
    await page.goto('/admin/appointments');
    await expect(page.getByRole('table')).toBeVisible();
  });
});

test.describe('RBAC Smoke — Doctor', () => {
  test.use({ storageState: 'playwright/.auth/doctor.json' });

  test('@smoke doctor can view their own appointments', async ({ page }) => {
    await page.goto('/dashboard');
    await expect(
      page.getByRole('heading', { name: 'My Appointments' })
    ).toBeVisible();
  });

  test('@smoke doctor can complete an appointment', async ({ page }) => {
    await page.goto('/dashboard');
    await page
      .getByRole('row', { name: /Jane Patient/ })
      .getByRole('button', { name: 'Complete' })
      .click();
    await expect(
      page.getByRole('row', { name: /Jane Patient/ })
    ).toContainText('Completed');
  });
});

test.describe('RBAC Smoke — Nurse', () => {
  test.use({ storageState: 'playwright/.auth/nurse.json' });

  test('@smoke nurse can schedule an appointment', async ({ page }) => {
    await page.goto('/dashboard');
    await page.getByRole('button', { name: 'Schedule Appointment' }).click();
    await page.getByLabel('Patient').fill('Jane Patient');
    await page.getByLabel('Doctor').selectOption({ label: 'Dr. Smith' });
    await page.getByLabel('Date').fill('2026-08-10');
    await page.getByRole('button', { name: 'Save' }).click();
    await expect(
      page.getByRole('row', { name: /Jane Patient.*Dr\. Smith/ })
    ).toBeVisible();
  });
});

test.describe('RBAC Smoke — Patient', () => {
  test.use({ storageState: 'playwright/.auth/patient.json' });

  test('@smoke patient can view their own medical records', async ({ page }) => {
    await page.goto('/records');
    await expect(page.getByRole('table')).toBeVisible();
  });

  test('@smoke patient cannot view all users', async ({ page }) => {
    await page.goto('/admin/users');
    await expect(
      page.getByRole('heading', { name: 'Access Denied' })
    ).toBeVisible();
  });
});
```

That's eight tests here, plus the doctor and nurse describe blocks from Steps 1 and 2 contributing a few more once tagged — comfortably inside the 10-15 range this suite targets. Each one exercises a genuinely different code path (one core action per role, plus one negative RBAC check), so a single failure tells you specifically which role's core flow broke, not just "something broke."

### Step 6: Build the Full Nightly Suite

The nightly run picks up everything the smoke suite deliberately leaves out, trading speed for depth. Concretely, three whole modules' worth of tests get tagged `@regression` and folded into one scheduled run:

- **The entire permission matrix from the RBAC permission-matrix lesson** — all thirty-six role × action rows (nine actions × four roles) from the data-driven suite, not just the handful of actions the smoke suite spot-checks
- **Every visual snapshot from the visual and snapshot testing lesson** — `toHaveScreenshot()` baselines for each of the four role dashboards, across whatever viewports that suite covers
- **The full cross-browser matrix from the cross-browser and responsive testing lesson** — the same critical flows run against all three `projects` entries (Chromium, Firefox, WebKit), not just Chromium

```typescript title="tests/regression/permission-matrix.spec.ts"
import { test, expect } from '@playwright/test';
import { permissionMatrix } from './permission-matrix-data';

test.describe('RBAC Permission Matrix @regression', () => {
  for (const row of permissionMatrix) {
    test(`${row.role} - ${row.action}`, async ({ page }) => {
      // the authentication lesson's role-based storageState, selected per row.role,
      // then one allow/deny assertion per row — see the RBAC permission-matrix
      // lesson's Build It for how this loop and its fixture wiring are constructed.
    });
  }
});
```

Tagging the `describe` block itself, once, tags every test generated by the loop inside it — you don't have to touch the parameterized test body to apply the tag to all thirty-six cases.

```bash
# the nightly run: everything tagged @regression, across every configured project
npx playwright test --grep @regression
```

Because this run covers the full permission matrix on three browser engines plus every visual baseline, it can easily take the better part of an hour where the smoke suite takes under a minute. That is the tradeoff this split exists to manage: nightly answers "is everything still correct, everywhere," on a schedule where an hour doesn't block anyone, while smoke answers "did this specific change break something obvious," fast enough to run on every push.

### Step 7: Wire Both into package.json Scripts

Give both filters a memorable name so nobody has to remember the exact `--grep` flag:

```json title="package.json"
{
  "scripts": {
    "test:smoke": "playwright test --grep @smoke --project=chromium",
    "test:regression": "playwright test --grep @regression",
    "test:all": "playwright test"
  }
}
```

`npm run test:smoke` becomes the command the continuous integration lesson's CI workflow runs on every pull request, while `npm run test:regression` becomes the command a nightly scheduled workflow runs across every browser project. Both read from the same suite, the same spec files, the same tags — there is exactly one source of truth for what a test does, and two different slices of it run on two different schedules.

## How It Works Internally

`--grep` and `--grep-invert` don't know anything about "tags" as a concept — Playwright has no separate tag registry or metadata store for the title-convention approach. What actually happens is simpler: at collection time, Playwright builds each test's full title by joining every enclosing `describe` title with the test's own title, in order, then runs your `--grep` pattern as a regular expression against that one string. `@smoke` matches because that exact string is sitting right there in the title text you wrote. This is also why a stray typo — `@somke` in one test, `@smoke` everywhere else — silently drops that test out of every smoke run without any error: there's no schema validating tag names, so a misspelled tag simply never matches. The structured `tag` option from Step 3 exists specifically to close this gap — Playwright validates and reports on `tag` values in a way plain title substrings cannot be checked automatically, though even that option is ultimately resolved into the same title-matching machinery under `--grep`.
