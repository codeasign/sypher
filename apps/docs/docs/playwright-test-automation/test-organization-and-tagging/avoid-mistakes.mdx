# Test Organization and Tagging — Common Mistakes

⏱ 10 minutes

## When NOT to Use This

A tagged smoke/regression split earns its keep once a suite is large enough that running all of it on every push is genuinely slow — the RBAC suite's permission matrix, visual snapshots, and cross-browser runs combined. If you're still early in this course, with a handful of spec files and a run that finishes in a few seconds, don't force a smoke/regression split onto it yet. Tags and two schedules are overhead you pay to solve a slowness problem you don't have yet, and premature tagging tends to mean everything gets tagged `@smoke` by default just to keep the suite "in" the fast run, which quietly recreates the exact problem this lesson exists to prevent.

## The Pattern to Remember

- **Pattern:** `test.describe` groups related specs, `test.step` names the phases inside one test, and `@smoke`/`@regression` tags in titles let `--grep` and `--grep-invert` pull out a fast subset and a full subset from the same suite.
- **When to use:** once the suite is large enough that a full run meaningfully slows down pull-request feedback — which for this course is the point where the RBAC permission matrix, the visual snapshots, and the cross-browser runs are all present.
- **When NOT to use:** a small suite that already runs in seconds, or a suite where "smoke" would end up being most of the tests anyway — a smoke suite that isn't dramatically smaller than the full suite isn't buying you anything.
- **Mental model:** tags are labels on a shared bookshelf, not two separate bookshelves. Every test lives in one suite, one source of truth; tags just tell `--grep` which shelf to pull from for a given occasion.

## Common Mistakes

### Mistake 1: Tagging Almost Everything @smoke

**Mistake:** Adding `@smoke` to a test "just in case" it seems important, until the smoke subset quietly grows to be most of the suite.

**Why it happens:** Every test feels important to whoever wrote it, and there's no automatic pressure keeping the tag honest — nothing stops you from tagging fifty tests `@smoke` the same way you'd tag five.

**Symptoms:** `npm run test:smoke` used to finish in under a minute and now takes several minutes, and pull requests are waiting on it again — the exact problem the split was supposed to solve, right back where you started, just with extra bookkeeping on top.

**Fix:** Treat the smoke count as a budget, not a wishlist — this course's target is roughly 10-15 tests across all four roles. Before adding a new `@smoke` tag, ask what specifically breaks if this test only runs nightly instead. If the honest answer is "nothing urgent," it belongs in `@regression`.

### Mistake 2: Forgetting That describe-Level Tags Apply to Every Nested Test

**Mistake:** Tagging a `test.describe` block `@regression`, then being surprised that `--grep @smoke` still picks up tests inside it because an individual test title also happens to contain `@smoke`.

**Why it happens:** It's easy to assume a tag on a `describe` block "overrides" tags on the tests inside it, the way some configuration systems let an inner scope win. Playwright's title-matching doesn't work that way — every tag anywhere in the full concatenated title is equally visible to `--grep`, with no precedence between levels.

**Symptoms:** A test you intended to be nightly-only shows up in the fast PR-gate run, silently adding time and failure surface you didn't plan for.

**Fix:** Decide tagging scope deliberately. If every test in a `describe` block should be nightly-only, tag the block once and don't also tag individual tests inside it `@smoke`. If one test in an otherwise-regression block genuinely needs to run in both, tag it explicitly with both — the way this lesson's negative RBAC check does — rather than leaving it ambiguous.

### Mistake 3: Assuming @smoke and @regression Are Mutually Exclusive by Default

**Mistake:** Running `npm run test:smoke` in the morning and `npm run test:regression` at night, and assuming between the two of them every test in the suite runs exactly once.

**Why it happens:** "Smoke" and "regression" sound like they should partition the suite cleanly, the way a permission matrix's allow/deny columns do.

**Symptoms:** A test tagged both `@smoke` and `@regression` — like this lesson's negative RBAC check — runs twice a day, once in each schedule, which is sometimes exactly what you want and sometimes wasted CI time nobody decided on purpose.

**Fix:** Tags describe *inclusion in a run*, not partition membership. If you want a strict partition — every test in exactly one bucket — use `--grep-invert @smoke` for the nightly run instead of a separate `@regression` tag, so nightly is defined as "everything not already covered by the fast run" rather than a second manually maintained tag that can drift out of sync with the first.

### Mistake 4: Mismatched or Unescaped Tag Text in --grep

**Mistake:** Typing `--grep smoke` without the `@`, or `--grep @smoke` with a typo like `@somke` in some test titles, and not noticing the run silently included or excluded fewer tests than expected.

**Why it happens:** `--grep` is a plain regex match against title text, with no schema behind it — there's nothing that validates a tag exists anywhere in the suite before the run starts, and no error if zero tests match.

**Symptoms:** `npx playwright test --grep @smoke` reports "0 tests ran" or an unexpectedly small number, with no explanation beyond the count itself, because the pattern simply didn't match anything (or didn't match everything you intended).

**Fix:** Keep the `@` in both the tag and the `--grep` pattern, spell it identically everywhere, and check the reported test count against your expected smoke count after any tagging change. If you need exact-match safety instead of substring matching, prefer the structured `tag` option from this lesson's Build It — Playwright validates that form more strictly than free-text titles.

### Mistake 5: Splitting the Suite Without Splitting the Schedule

**Mistake:** Tagging tests `@smoke` and `@regression`, adding both npm scripts, and then still running `npm run test:all` on every pull request out of habit.

**Why it happens:** Tagging is the visible, satisfying part of the work. Actually changing which command CI runs, and when, is a separate step in a different file (the continuous integration lesson's workflow) that's easy to leave for later and then forget.

**Symptoms:** The tags exist, the scripts exist, but pull requests still wait on the full suite — all the organizational work with none of the speed benefit it was meant to produce.

**Fix:** Tagging and rescheduling are one change, not two. The moment `@smoke` and `@regression` are in place, update the CI workflow in the same pull request to actually call `npm run test:smoke` on push and `npm run test:regression` on a nightly schedule — the continuous integration lesson covers wiring this into GitHub Actions directly.
