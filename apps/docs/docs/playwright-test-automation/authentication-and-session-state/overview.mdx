# Authentication and Session State

⏱ 15 minutes · Difficulty: Intermediate

## What You Will Learn

By the end of this lesson you will be able to:

- Explain why logging in through the UI on every single test is slow — and why it's actually worse than slow, since it means a bug on the login page can take down every spec in the suite, not just the login spec
- Authenticate against the RBAC app's real API to get a JWT directly, without ever touching a browser
- Capture that authenticated session as Playwright `storageState` — cookies and `localStorage` together, saved per role
- Write a `globalSetup` function that logs in all 4 roles (admin/doctor/nurse/patient) once per test run and writes out 4 separate storage state files
- Define 4 Playwright `projects`, each pinned to its own storage state file, so an entire spec file can run "as a doctor" or "as a patient" with zero login code inside the test itself

## Why This Matters

Every module from here forward tests role-specific behavior — a doctor's dashboard, a nurse's scheduling permissions, a patient's own-records-only view. If every one of those tests starts by filling in a login form and clicking submit, you end up paying that cost — a full page load, a form fill, a network round trip, a redirect — in every single test, and that cost multiplies by however many specs run for however many roles. On a suite with even a few dozen role-specific tests, that adds up to minutes of pure login overhead before a single real assertion runs.

And it's worse than just slow. If the login page itself has a bug — a broken button, a slow-loading script — every test in the entire suite fails along with it, simply because every test depends on the login UI working, even the ones that have nothing to do with authentication. A test verifying that a nurse can schedule an appointment shouldn't be able to fail because of a CSS regression on the login page. That's why separating "prove authentication works" (a small, dedicated set of tests) from "start already authenticated" (everything else) fixes both problems at once.

## The Problem

Picture a spec file that needs to run as a doctor:

```typescript
test('doctor can view assigned patients', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('dr_seeded_username');
  await page.getByLabel('Password').fill('seeded_password');
  await page.getByRole('button', { name: 'Log In' }).click();
  await expect(page).toHaveURL('/dashboard');

  // the actual test doesn't start until here
  await expect(page.getByRole('heading', { name: 'My Patients' })).toBeVisible();
});
```

Now imagine copying those first four lines into every doctor test, every nurse test, every patient test, every admin test — dozens of times, across every module for the rest of this course. Change one thing about the login form (a relabeled field, an added MFA step) and suddenly you have to find and fix every single copy. That repetition is the real defect here, not the login flow itself.

## The Concept

The key idea here is that Playwright lets you separate "how a session gets established" from "what a test needs to run." The RBAC app's backend already exposes a login endpoint through its API (visible in Swagger at `/api-docs`) that returns a JWT independent of any browser, so you can call that endpoint directly — no `page`, no form, no click — and get back a token that's exactly as valid as one a real login would produce.

That's useful because Playwright's `storageState` is a serializable snapshot of a browser context's cookies and `localStorage`, per origin. Once you have a valid session — however you got it — you can save that snapshot to a JSON file and hand it to a *different* browser context later, and that context just starts out already logged in. Put the two together and you get this: authenticate programmatically via the API once per role, capture the result as `storageState`, and every test file that needs "a logged-in doctor" just loads `doctor.json` instead of performing a login of its own.

Playwright runs this capture step through `globalSetup` — a function that runs once before the whole test run starts, not once per test or per file. For 4 roles, `globalSetup` authenticates each one in turn and writes 4 files: `playwright/.auth/admin.json`, `doctor.json`, `nurse.json`, `patient.json`. From there, `playwright.config.ts` defines 4 `projects` — `admin`, `doctor`, `nurse`, `patient` — each with `use: { storageState: '<path-to-that-role's-file>' }`. Run `npx playwright test --project=doctor` and every test in that project starts with a browser context that's already authenticated as a doctor, before the test function's first line even executes.
