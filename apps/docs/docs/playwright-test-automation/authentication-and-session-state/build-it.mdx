# Authentication and Session State: Hands On

⏱ 25 minutes

## Breaking It Down

### Step 1: Confirm the Login Endpoint in Swagger

With the backend running, open [http://localhost:5000/api-docs](http://localhost:5000/api-docs) and find the `Auth` tag. This app exposes login as `POST /api/auth/login`, which accepts a JSON body of `{ username, password }` and returns a JSON response containing a `token` field, a signed JWT. Before you write any code against it, use Swagger's **Try it out** to confirm the exact response shape, since some role setups nest the token under a different key. Copy the real field name from the response you actually get back, not from this page.

### Step 2: Create the Auth Directory and Ignore It

```bash
mkdir -p playwright/.auth
```

Storage state files contain live JWTs, which means they're credentials, not code, so add them to `.gitignore` right away, before you generate even the first one:

```bash title=".gitignore"
playwright/.auth/
```

### Step 3: Write `globalSetup.ts`

Create `playwright/global-setup.ts`. This function runs once, before any test in the run starts, and for each role it walks through the same sequence: it gets a JWT from the real API, opens a real page so the app's own frontend has an origin to write to, injects the token into that origin's `localStorage` the same way the app's login flow would, and then saves the resulting context as a `storageState` file.

```typescript title="playwright/global-setup.ts"
import { chromium, request as playwrightRequest } from '@playwright/test';
import fs from 'fs';
import path from 'path';

const BASE_URL = 'http://localhost:3002';
const API_URL = 'http://localhost:5000';
const AUTH_DIR = path.join(__dirname, '.auth');

type Role = 'admin' | 'doctor' | 'nurse' | 'patient';

// The admin account is the one fixed, documented credential from setup's
// seed step. The other three are generated by `npm run seed` and are NOT
// fixed values: pull the real ones from `backend/seed.js` or your seed
// script's console output and pass them in as environment variables. Do not
// hardcode guessed usernames here.
const CREDENTIALS: Record<Role, { username: string; password: string }> = {
  admin: { username: 'admin', password: 'admin123' },
  doctor: {
    username: process.env.RBAC_DOCTOR_USERNAME ?? '',
    password: process.env.RBAC_DOCTOR_PASSWORD ?? '',
  },
  nurse: {
    username: process.env.RBAC_NURSE_USERNAME ?? '',
    password: process.env.RBAC_NURSE_PASSWORD ?? '',
  },
  patient: {
    username: process.env.RBAC_PATIENT_USERNAME ?? '',
    password: process.env.RBAC_PATIENT_PASSWORD ?? '',
  },
};

async function authenticateRole(role: Role): Promise<void> {
  const { username, password } = CREDENTIALS[role];
  if (!username || !password) {
    throw new Error(
      `Missing credentials for role "${role}". Set RBAC_${role.toUpperCase()}_USERNAME/PASSWORD to a seeded account.`,
    );
  }

  // 1. Authenticate via the real API. No browser involved yet.
  const apiContext = await playwrightRequest.newContext({ baseURL: API_URL });
  const response = await apiContext.post('/api/auth/login', {
    data: { username, password },
  });

  if (!response.ok()) {
    throw new Error(
      `Login failed for role "${role}": ${response.status()} ${await response.text()}`,
    );
  }

  const { token } = await response.json();
  await apiContext.dispose();

  // 2. A JWT by itself isn't a storageState. This app's frontend keeps the
  // token in localStorage, not a cookie, so storageState only captures it
  // if a page actually visits the frontend's origin and writes it there,
  // the same thing the real login form would do.
  const browser = await chromium.launch();
  const page = await browser.newPage({ baseURL: BASE_URL });
  await page.goto('/login');
  await page.evaluate((jwt) => {
    window.localStorage.setItem('token', jwt);
  }, token);

  // 3. Reload into an authenticated route so the app boots in its
  // logged-in state before the snapshot. Some apps only read
  // localStorage during initial app load, not on every render.
  await page.goto('/dashboard');
  await page.waitForLoadState('networkidle');

  // 4. Snapshot cookies + localStorage for this origin to disk.
  await fs.promises.mkdir(AUTH_DIR, { recursive: true });
  await page.context().storageState({ path: path.join(AUTH_DIR, `${role}.json`) });
  await browser.close();
}

export default async function globalSetup(): Promise<void> {
  const roles: Role[] = ['admin', 'doctor', 'nurse', 'patient'];
  // Sequential, not Promise.all: four simultaneous logins against one
  // small SQLite-backed backend is a race you don't need to introduce
  // into a step that only runs once per test run anyway.
  for (const role of roles) {
    await authenticateRole(role);
  }
}
```

### Step 4: Wire `globalSetup` into `playwright.config.ts`

```typescript title="playwright.config.ts"
import { defineConfig, devices } from '@playwright/test';
import path from 'path';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  reporter: 'html',
  globalSetup: require.resolve('./playwright/global-setup.ts'),

  use: {
    baseURL: 'http://localhost:3002',
    trace: 'on-first-retry',
  },

  projects: [
    {
      name: 'admin',
      use: {
        ...devices['Desktop Chrome'],
        storageState: path.join(__dirname, 'playwright/.auth/admin.json'),
      },
    },
    {
      name: 'doctor',
      use: {
        ...devices['Desktop Chrome'],
        storageState: path.join(__dirname, 'playwright/.auth/doctor.json'),
      },
    },
    {
      name: 'nurse',
      use: {
        ...devices['Desktop Chrome'],
        storageState: path.join(__dirname, 'playwright/.auth/nurse.json'),
      },
    },
    {
      name: 'patient',
      use: {
        ...devices['Desktop Chrome'],
        storageState: path.join(__dirname, 'playwright/.auth/patient.json'),
      },
    },
  ],
});
```

Remember that `globalSetup` runs once before any project's tests start, so by the time the `doctor` project's first test executes, `playwright/.auth/doctor.json` already exists, which means `use.storageState` has something real to load.

### Step 5: Set the Required Environment Variables

Before running anything, export the seeded doctor/nurse/patient credentials you pulled from `backend/seed.js` or the `npm run seed` output in Step 3:

```bash
export RBAC_DOCTOR_USERNAME=<your-seeded-doctor-username>
export RBAC_DOCTOR_PASSWORD=<your-seeded-doctor-password>
export RBAC_NURSE_USERNAME=<your-seeded-nurse-username>
export RBAC_NURSE_PASSWORD=<your-seeded-nurse-password>
export RBAC_PATIENT_USERNAME=<your-seeded-patient-username>
export RBAC_PATIENT_PASSWORD=<your-seeded-patient-password>
```

On Windows PowerShell, use `$env:RBAC_DOCTOR_USERNAME = "..."` for each instead.

### Step 6: Write a Spec With Zero Login Code

Create `tests/doctor-dashboard.spec.ts`:

```typescript title="tests/doctor-dashboard.spec.ts"
import { test, expect } from '@playwright/test';

test('doctor dashboard shows the doctor-only patient view', async ({ page }) => {
  await page.goto('/dashboard');

  // No login happened above. The "doctor" project's storageState
  // already put this context in an authenticated session.
  await expect(page.getByRole('heading', { name: 'My Patients' })).toBeVisible();
  await expect(page.getByRole('button', { name: 'Complete Appointment' })).toBeVisible();
});
```

Run it against the `doctor` project specifically:

```bash
npx playwright test --project=doctor tests/doctor-dashboard.spec.ts
```

The test passes without a single `page.getByLabel('Username')` in sight. Swap `--project=doctor` for `--project=patient` against a patient-scoped spec and the same pattern holds: the project, not the test, decides who's logged in.

### Step 7: Verify All 4 Roles Independently

```bash
npx playwright test --project=admin
npx playwright test --project=doctor
npx playwright test --project=nurse
npx playwright test --project=patient
```

Each run should authenticate cleanly during `globalSetup` (watch the terminal: a credential error surfaces immediately, before any test runs) and each project's tests should see role-appropriate UI.

## How It Works Internally

It helps to know what `storageState` actually is under the hood: a JSON snapshot with two parts, an array of cookies and an `origins` array where each entry pairs a URL origin with the `localStorage` key/value pairs recorded for it. When a new browser context is created with `use: { storageState: 'doctor.json' }`, Playwright pre-loads exactly those cookies and exactly that `localStorage` data into the context *before* the first `page.goto()` runs. That's why, by the time your test's first line executes, the app's frontend code can read a valid token out of `localStorage` on its very first render, exactly as if a real login had just completed. The context has no memory of how that data got there in the first place. A JWT written by a real login form and one written by `page.evaluate()` in `globalSetup` look completely indistinguishable to the app.

That also explains why `page.goto('/login')` in `globalSetup` matters, even though no form actually gets filled in: `localStorage` is scoped per-origin, and `page.evaluate()` can only write into whatever origin the page is currently on. Calling the API alone never establishes an origin for the browser to write into, so the token has to be written from inside a page that's already navigated to the frontend's own URL.
