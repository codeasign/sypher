# Authentication and Session State — Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Since `storageState` skips the login flow entirely, it's the wrong tool for the handful of tests whose entire job is verifying that login flow itself. For those, keep a small, dedicated login spec (invalid password, empty fields, the redirect after a correct login) that runs with no `storageState` at all and drives the real form through `page.getByLabel('Username')`, `fill()`, and a click. Everything else — the other 95% of the suite that just needs to already be logged in as some role — is exactly what this lesson's pattern is for. Just don't let the two swap places: if your dedicated login spec quietly starts using `storageState`, you've stopped testing login at all.

## The Pattern to Remember

- **Pattern:** authenticate each role once via the real API in `globalSetup`, save cookies + `localStorage` as `storageState`, then load a different file per Playwright `project`.
- **When to use:** any test where "already logged in as role X" is just a precondition, not the thing actually under test — which describes most of this course from here on.
- **When NOT to use:** the login flow's own tests, and one-off manual exploration where the setup overhead genuinely doesn't matter.
- **Mental model:** think of `storageState` as a save file. `globalSetup` plays the game up to the save point once; every test after that just loads the save and starts mid-game, instead of replaying from the title screen.

## Common Mistakes

### Mistake 1: Committing `playwright/.auth/*.json` to Git

**Mistake:** The generated storage state files get added and pushed just like any other project file.

**Why it happens:** They look like ordinary config or fixture JSON, and nothing in `git status` visually flags them as sensitive, so it's easy not to think twice about them.

**Symptoms:** A live JWT — a working, unexpired credential for a real seeded account — ends up sitting in your commit history, readable by anyone with repo access, indefinitely, even after you delete the file in a later commit.

**Fix:** Add `playwright/.auth/` to `.gitignore` before the first file is ever generated (Step 2 of Build It does this first, deliberately, for exactly this reason). And if one already got committed, treat the underlying account credentials as compromised and rotate them — deleting the file alone isn't enough.

### Mistake 2: Capturing `storageState` Before the Page Has Written to `localStorage`

**Mistake:** Calling `context.storageState({ path })` right after the API login call, with no `page.goto()` to the frontend's origin in between.

**Why it happens:** The JWT is already in hand at that point, so it feels like the state has already been "captured" — the extra browser step looks redundant, even though it isn't.

**Symptoms:** The generated `doctor.json` ends up with an empty or missing `origins` array. Every test in the `doctor` project then loads a context with no `localStorage`, the frontend renders as logged out, and tests fail on the very first assertion with no obvious connection back to auth setup.

**Fix:** Always navigate to the frontend origin (`page.goto('/login')` or any page on that origin) before writing to `localStorage` and calling `storageState()`. Because `localStorage` is per-origin, there's simply no origin to write into until a page has actually navigated there.

### Mistake 3: One Shared `storageState` for All Four Roles

**Mistake:** Generating a single `storageState` file (usually from the admin account, since it's the one credential documented during setup) and pointing every project at it "just for now."

**Why it happens:** It's the fastest way to get green tests while you're still wiring things up, and since admin can usually see everything, nothing obviously breaks — so it's tempting to leave it that way.

**Symptoms:** RBAC tests quietly stop meaning anything — a test asserting "a nurse cannot delete a user" passes not because the permission check actually works, but because every request in every project is really running as admin. The suite reports 100% green while the underlying permission logic could be completely broken underneath it.

**Fix:** Generate and use all 4 files, one per real role, exactly as `globalSetup` produces them. If a permission test passes, it should be because the role in that project's storage state was genuinely denied — not because it was never really tested in the first place.

### Mistake 4: Stale `storageState` After a Database Reseed

**Mistake:** Re-running `npm run seed` (which regenerates users, often with new IDs) without also regenerating the storage state files that were captured against the old data.

**Why it happens:** Reseeding is a backend-only action, so there's no obvious connection between it and a `playwright/.auth/` folder sitting quietly in the project root.

**Symptoms:** Tests that were passing suddenly start failing with 401s or a redirect back to `/login`, and it looks exactly like a flaky auth failure — when what's really going on is that a JWT's payload references a user ID that no longer exists in the freshly reseeded database.

**Fix:** Treat storage state as derived, disposable data tied to the current database contents, and regenerate it (just re-run the suite, which reruns `globalSetup`) any time you reseed. Never hand-edit or reuse an old `.auth/*.json` file across a reseed.

### Mistake 5: Re-Authenticating Inside Fixtures Instead of Once in `globalSetup`

**Mistake:** Moving the login-and-capture logic out of `globalSetup` and into a per-test or per-file fixture that runs the same API login again for every test.

**Why it happens:** Fixtures feel like "the Playwright way" to inject setup, so it's a natural instinct to reach for one here too — even though it undoes the whole point of this lesson.

**Symptoms:** The suite gets slower in direct proportion to test count — a login round trip on every single test instead of 4 total for the whole run — so you end up reintroducing almost the exact overhead this lesson exists to remove, just moved one layer down.

**Fix:** Keep authentication in `globalSetup`, which runs once per test run regardless of how many tests or files use each role. Fixtures still have a place in this course (a later lesson covers them), but for authenticating the 4 fixed roles, `globalSetup` plus project-level `storageState` is the right layer to use — not a fixture re-run per test.
