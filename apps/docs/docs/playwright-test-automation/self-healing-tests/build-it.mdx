# Self-Healing Tests and AI-Assisted Maintenance: Hands On

⏱ 30 minutes

## Breaking It Down

### Step 1: Reproduce the Benign Break: a Renamed Button

Start from the nurse-dashboard spec you already have from earlier in this course:

```typescript title="tests/nurse-dashboard.spec.ts"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'auth/nurse.json' });

test('nurse can open the add-patient form', async ({ page }) => {
  await page.goto('/dashboard');
  await page.getByRole('button', { name: 'Add Patient' }).click();
  await expect(page.getByRole('heading', { name: 'New Patient' })).toBeVisible();
});
```

Simulate a real-world change: in the RBAC app's frontend, rename the dashboard button's label from `Add Patient` to `New Patient`, a small copy tweak a designer might make with no functional change at all. Run the suite:

```bash
npx playwright test tests/nurse-dashboard.spec.ts
```

It fails. The button still exists, still opens the same form, still creates a patient, but `getByRole('button', { name: 'Add Patient' })` no longer resolves to anything, because the accessible name it's looking for doesn't exist on the page anymore.

### Step 2: Let the Healer Repair It, and Read the Diff

Hand the failing spec to the same Healer agent workflow from the Playwright Test Agents lesson. It inspects the current page, finds a button in the same position performing the same click-to-open-form action, and proposes a diff:

```diff title="Healer-proposed diff: tests/nurse-dashboard.spec.ts"
- await page.getByRole('button', { name: 'Add Patient' }).click();
+ await page.getByRole('button', { name: 'New Patient' }).click();
```

Read this diff the way you would read any pull request, not the way you'd glance at a green checkmark. Ask three questions:

1. Did only the locator's `name` change, or did an assertion's expected outcome change too? Here, only the locator changed: the heading assertion below it is untouched.
2. Does the element the new locator resolves to still do the same thing? Click through manually: the renamed button still opens the same create-patient form.
3. Is this a role-based locator (`getByRole`), not a brittle fallback the healer reached for because the role-based query failed? It is: the fix stayed in `getByRole`, matching this course's locator conventions from the locators lesson.

All three check out, and that's exactly what a Healer should be doing: absorbing UI copy churn so you don't have to hunt down every renamed label by hand. So approve the diff, merge it, and move on.

### Step 3: Reproduce the Dangerous Break: a Real Regression

Now reproduce a very different kind of failure. Go back to the RBAC permission-matrix lesson's permission matrix, specifically the **View medical records** row, where a patient is allowed to view records, but only their own. This spec asserts that row's "own only" boundary:

```typescript title="tests/permission-matrix/medical-records.spec.ts"
import { test, expect } from '@playwright/test';

test.use({ storageState: 'auth/patient.json' });

test("patient cannot view someone else's medical records", async ({ page }) => {
  await page.goto('/patients/12/records');
  await expect(page.getByRole('heading', { name: 'Access Denied' })).toBeVisible();
  await expect(page.getByText('Diagnosis')).not.toBeVisible();
});
```

Patient ID `12` is not the logged-in patient's own ID, so this should always render an access-denied screen. Simulate a backend authorization regression: the record ownership check on that route silently starts returning the record for any authenticated patient, not just its owner. Run the suite:

```bash
npx playwright test tests/permission-matrix/medical-records.spec.ts
```

It fails: the `Access Denied` heading never appears, because the app now renders the actual medical record instead.

### Step 4: Watch What a Naive Healer Proposes: and Reject It

Hand this failing spec to a Healer with no additional judgment applied. Its job, mechanically, is to look at what's currently on the page and make the test agree with it. Nothing about the locators here is broken: `getByRole('heading', { name: 'Access Denied' })` is a perfectly valid, perfectly findable query for what's *supposed* to be there. So an over-confident healer, trying to turn red into green by any means available, reaches for the only lever left: the assertion itself.

```diff title="DO NOT MERGE: Healer-proposed diff: tests/permission-matrix/medical-records.spec.ts"
- await expect(page.getByRole('heading', { name: 'Access Denied' })).toBeVisible();
- await expect(page.getByText('Diagnosis')).not.toBeVisible();
+ await expect(page.getByRole('heading', { name: 'Medical Record' })).toBeVisible();
+ await expect(page.getByText('Diagnosis')).toBeVisible();
```

Read that diff the same way you read the safe one, with the same three questions:

1. Did only the locator change? No: the *expected outcome* changed. The test no longer expects a denial; it now expects the record to be visible.
2. Does the page still do the same thing it should? No. Cross-check against the RBAC permission-matrix lesson's matrix row directly: **Patient, View medical records, own only.** Patient ID `12` viewing patient ID `12`'s record while logged in as a different patient is not "own only." This is not a UI refresh. It is the exact behavior the original test existed to catch.
3. Is there any legitimate product change that would justify this? None was made. Nobody updated the permission matrix, filed a ticket to loosen this rule, or shipped an intentional change to record visibility. The only thing that changed is a bug got introduced, and the test caught it correctly, on the first run.

This is the failure mode this entire lesson is built around: accepting this diff does not fix a test. It deletes the one thing standing between a real authorization bug and production. The test goes from red-and-correct to green-and-wrong, and every future run of this suite will now report "all clear" while a patient can read another patient's diagnosis. Reject the diff outright. Leave the test failing. File the regression against the app's authorization layer, referencing the RBAC permission-matrix lesson's matrix row it violates, and treat the still-red test as the tracking signal until the actual bug is fixed, not the healed spec.

### Step 5: Build the Guardrail: Mandatory Diff Review, No Auto-Merge

The difference between Step 2 and Step 4 was never visible in the terminal: both started as a red test and a healer-proposed patch. It was only visible in the diff. That means the guardrail has to live at the diff-review stage, every time, with no exceptions carved out for "obviously simple" fixes:

- Never enable auto-merge on a branch or PR opened by a healing run. A Healer's output is a proposal, not a commit: treat it exactly like a draft PR from a junior contributor who has never seen your permission matrix.
- Route every healed diff through the same code review your handwritten changes go through. If your repo uses `CODEOWNERS`, make sure files under `tests/permission-matrix/` require a reviewer regardless of who (or what) opened the PR.
- Read every diff for what *kind* of change it makes before checking whether it's correct: a locator's `name`/`role`/`label` changing is a different risk class than an assertion's expected value, visibility, or comparison changing. Assertion changes on anything derived from the RBAC permission-matrix lesson's matrix get read against that table, every time, not against whether the test now passes.
- When a healed diff changes an assertion, ask "what changed in the app to justify this" before asking "does this make the test pass." If you can't point to a real, intentional product change, you're looking at Step 4's failure mode, not a legitimate fix.

## How It Works Internally

A Healer agent works from a comparison: the DOM and accessibility tree the failing test expected (captured from the last passing run or the test's own locators) versus the DOM and accessibility tree the page actually has right now. When it finds an element with a similar role, position, and function to the one the broken locator was looking for, it proposes retargeting the locator. That's locator drift repair, and it's a purely structural comparison with no notion of correctness attached.

What it does not have is any independent model of what the app is *supposed* to do. It cannot open the RBAC permission-matrix lesson's permission matrix and check whether a patient viewing another patient's record is allowed. It only sees "the assertion says X, the page currently shows Y, here is a diff that reconciles them." Locator drift and behavioral regression produce the identical input to that mechanism: a mismatch between expected and current. Only a human, holding the actual intended spec, can tell which kind of mismatch it is. That's the whole reason diff review isn't a formality here: it's the one step in the pipeline that has access to intent.
