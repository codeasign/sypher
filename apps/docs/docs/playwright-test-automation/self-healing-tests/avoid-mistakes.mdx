# Self-Healing Tests and AI-Assisted Maintenance: Common Mistakes

⏱ 10 minutes

## When NOT to Use This

Self-healing is for absorbing UI churn that doesn't change what the app does: renamed labels, a `div` wrapper added around an existing element, an `aria-label` tightened for accessibility. It is not a general-purpose "make CI green" tool, and there are places it should never run unsupervised:

- **Never point a Healer at your suite in CI with auto-merge enabled.** Every healed change needs a human reading the diff before it reaches `main`, no matter how routine the underlying UI change seemed.
- **Never let a Healer's mandate extend to assertion values on anything tied to the RBAC permission-matrix lesson's permission matrix.** Those tests exist specifically to catch behavior changes: the one category of "fix" a healer should never be trusted to make on its own.
- **Don't reach for a Healer when a test is flaky, not broken.** A flaky test (covered in the debugging and troubleshooting lesson) has a timing or isolation problem; a healer will either mask it with a locator that happens to work this run, or misdiagnose it as drift. Fix flakiness at the root, don't heal around it.
- **Don't use a Healer as a substitute for understanding why a test broke.** Even a correctly-healed locator diff is worth reading closely enough to say, in your own words, what changed in the app and why the new locator is still correct, not just that CI is green again.

## The Pattern to Remember

- **Pattern:** a human reads every healed diff before it merges, sorts it into locator-only or assertion-changing, and checks any assertion-changing diff on a permission-related test against the RBAC permission-matrix lesson's matrix directly.
- **When to use:** for UI copy and markup churn (renamed buttons, restructured DOM, tightened accessible names) on tests that aren't asserting security- or permission-sensitive behavior.
- **When NOT to use:** unattended in CI, auto-merged, or anywhere near an assertion's expected value on a permission-matrix test, unless a human has confirmed the app's behavior really was meant to change.
- **Mental model:** think of a Healer agent as a spellchecker for locators, not a proofreader for behavior. It can tell you a word is misspelled, but it can't tell you a sentence is a lie.

## Common Mistakes

### Mistake 1: Rubber-Stamping a Healed PR Because CI Is Green

**Mistake:** Seeing a healing run turn a red suite green and merging the PR without reading the actual diff line by line.

**Why it happens:** Green is the signal you've trained yourself to trust for months of manual test-writing. A healed PR produces the same green checkmark a correct handwritten fix would, so it's easy to extend the same trust to it without noticing the fix wasn't yours.

**Symptoms:** Weeks later, a bug that should have been caught immediately turns up in production, and `git blame` on the test that should have caught it points to a healing commit nobody actually reviewed.

**Fix:** Treat every healed PR as an unreviewed contribution from a fast but context-blind teammate. Read the diff before merging, every time, with the same three questions from Build It: did only the locator change, does the element still do the same thing, is there a legitimate reason for any assertion change.

### Mistake 2: Letting a Healer Touch Assertion Values on Permission Tests

**Mistake:** Granting a Healer the same latitude on `tests/permission-matrix/` specs that you'd grant it on cosmetic UI specs, including rewriting what a test expects to be true.

**Why it happens:** The tooling doesn't distinguish file paths by risk on its own; a permission-matrix spec looks like any other failing test to the agent, and it will "fix" it the same way it fixes everything else: by reconciling the assertion with current behavior.

**Symptoms:** A regression in the app's authorization logic gets silently absorbed into the test suite as the new expected behavior, exactly like the medical-records example in Build It: the suite goes green, the bug ships.

**Fix:** Restrict healed diffs on permission- and security-related specs to locator-only changes as a hard policy, enforced by human review, not by hoping the agent behaves conservatively on its own. Any assertion change in that directory is an automatic "stop and investigate," not a routine approval.

### Mistake 3: Treating Diff Size as a Proxy for Diff Safety

**Mistake:** Approving a one-line healed diff faster or with less scrutiny than a large one, on the assumption that small changes are inherently low-risk.

**Why it happens:** Code review instincts trained on refactors generalize badly here. A large diff usually does mean more surface area for bugs in ordinary code, but a healed diff's risk comes from *what kind* of line changed, not how many lines.

**Symptoms:** A single-line assertion rewrite (like flipping `.not.toBeVisible()` to `.toBeVisible()`) sails through review because it "looks small," while a five-line locator refactor gets scrutinized heavily for no better reason than its line count.

**Fix:** Classify every healed diff by kind before judging it by size: a locator's `role`, `name`, or `label` changing is one risk class; an assertion's expected value, visibility, or comparison operator changing is a different and higher one, regardless of how many lines are touched.

### Mistake 4: Not Cross-Checking Healed Permission Diffs Against the Matrix

**Mistake:** Judging whether a healed assertion change "looks reasonable" from the diff alone, without reopening the RBAC permission-matrix lesson's permission matrix to check the specific row it affects.

**Why it happens:** The diff reads fluently (new heading text, a plausible-sounding assertion) and nothing about it looks obviously wrong in isolation, especially under review-fatigue after a long PR queue.

**Symptoms:** A reviewer approves a diff that quietly loosens a permission boundary because, read on its own, it looked like a reasonable update rather than a violation of a specific, documented row in the matrix.

**Fix:** Keep the RBAC permission-matrix lesson's matrix open as the literal source of truth any time a healed diff touches a permission-adjacent test. The question is never "does this diff look right." It's "does this diff match row N, column role, in the matrix," checked directly against the table, not from memory.

### Mistake 5: Rejecting a Bad Diff but Not Tracking the Real Bug

**Mistake:** Correctly rejecting a dangerous healed diff (leaving the test red) but treating that as the end of the process instead of the start of a bug report.

**Why it happens:** Rejecting the diff feels like the safety-critical action, and it is the right first move, but it's easy to stop there once the immediate danger (a bad merge) has been avoided.

**Symptoms:** The same test stays red for weeks, engineers get used to seeing it fail and start ignoring it as "a known flaky one," and the actual authorization regression it's reporting never gets triaged or fixed.

**Fix:** A rejected healing diff on a permission test is a confirmed regression, not a false alarm. File it immediately, reference the specific matrix row it violates, and keep the test red and visible (not silenced or skipped) until the underlying app bug is actually fixed.
