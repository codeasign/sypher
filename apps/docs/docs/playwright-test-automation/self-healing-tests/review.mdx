# Self-Healing Tests and AI-Assisted Maintenance — Review

⏱ 5 minutes

## Key Takeaways

- A Healer agent repairs failing tests by comparing what the current page looks like to what the failing locator or assertion expected — it has no independent notion of whether the app's current behavior is actually correct.
- Locator drift — an accessible name, DOM position, or wrapper element changing while the underlying function stays the same — is safe to heal, because nothing about what the app does changed, only how it's addressed.
- A behavioral regression — like a permission check in the RBAC permission-matrix lesson's matrix no longer blocking something it should — must stay a failing test, because the only "fix" available to an unsupervised healer is rewriting the assertion to match the bug.
- The single most dangerous failure mode in this lesson is a healer converting a caught regression into a silently passing test by editing expected values instead of leaving the mismatch flagged — on an RBAC app, that can mean a patient's medical records becoming visible to another patient with nothing left in CI to catch it.
- Every healed diff needs mandatory human review before merge, with locator-only changes and assertion-changing changes treated as different risk classes — and no healed change ever gets auto-merged, especially on anything derived from the permission matrix.

## Recap in 60 Seconds

If you only remember three things:

1. A Healer fixes *how a test finds something*, not *whether the app is right* — it can safely rename a stale locator, but it cannot tell a real regression from a UI refresh.
2. Read every healed diff before merging: a changed locator name is low-risk; a changed assertion — especially on a permission-matrix test — is not, and gets checked against the RBAC permission-matrix lesson's table directly.
3. Never auto-merge a healed change. If a healer proposes making a permission test pass by loosening what it expects, reject the diff, keep the test red, and file the regression it just caught.

## Try It

Extend the "Schedule appointments" row of the RBAC permission-matrix lesson's matrix — the one where only nurses are allowed to schedule appointments, and doctors and patients are denied. Build two scenarios against the RBAC app and decide, for each, what a Healer should be allowed to do:

1. **Benign scenario:** the nurse dashboard's "Schedule Appointment" button gets renamed to "Book Appointment," with the underlying form and behavior unchanged. Write the original spec with `getByRole('button', { name: 'Schedule Appointment' })`, break it with the rename, and write out the diff you would expect a Healer to propose. Confirm it only touches the locator.
2. **Regression scenario:** simulate a backend bug where a doctor's account can now successfully schedule an appointment, which the matrix says should be denied. Write a spec asserting the doctor sees a denial (an error message or disabled control) when attempting to schedule, then imagine the equivalent "healed" diff that would make this pass by asserting success instead. Write one sentence explaining, citing the matrix row, why that diff must be rejected.

Compare the two diffs side by side. If you can't immediately tell which one is safe from the diff alone, without rereading the underlying test's intent, that's the signal for why human review of every healed change matters more than how confident the tooling seems.
