# Self-Healing Tests and AI-Assisted Maintenance

⏱ 22 minutes · Difficulty: Advanced

## What You Will Learn

By the end of this lesson you will be able to:

- Explain what a Healer agent is actually doing when it repairs a broken test: inspecting the current page, comparing it to what the failing locator or assertion expected, and proposing a diff
- Distinguish locator drift (a button's accessible name or DOM position changed, but its function did not) from a real regression (the app now does something it should not)
- Recognize the single most dangerous failure mode in AI-assisted test maintenance: a healer quietly rewriting an assertion to match broken current behavior instead of leaving a real bug caught
- Apply a concrete guardrail (mandatory diff review, no auto-merge) before any healed change reaches your suite
- Decide, for a specific failing RBAC test, whether it is safe to hand to a healer or whether it must stay red until a human investigates

## Why This Matters

A Healer agent is genuinely useful. UI markup and copy churn constantly in a real frontend (a designer renames a button, a component gets wrapped in a new container `div`, an `aria-label` gets tightened for accessibility) and none of that changes what the app actually does. Manually chasing every one of those changes across a large suite is tedious, low-value work, and it is exactly the kind of maintenance a healer can take off your hands.

But a healer's job, mechanically, is to make a failing test pass again. Nothing in that mechanism distinguishes between two very different reasons a test is red: the selector is stale, or the app is now wrong. An agent that is rewarded for green checkmarks and has no independent notion of what the app is *supposed* to do will, left unsupervised, treat both cases the same way, and the fix for the second case is not a locator update, it is updating the expected result to match the bug. That converts a test that was doing exactly its job (catching a regression) into a test that now actively hides it. On a healthcare RBAC app, the regression a healer could paper over this way is a patient seeing another patient's medical record. That is the risk this lesson is built around, and it is the reason self-healing gets its own module instead of a paragraph inside the Playwright Test Agents lesson.

## The Problem

Picture two failing tests landing in your inbox on the same morning, from the same CI run, both red for the first time:

```typescript title="tests/nurse-dashboard.spec.ts"
test('nurse can open the add-patient form', async ({ page }) => {
  await page.goto('/dashboard');
  await page.getByRole('button', { name: 'Add Patient' }).click();
  await expect(page.getByRole('heading', { name: 'New Patient' })).toBeVisible();
});
```

```typescript title="tests/permission-matrix/medical-records.spec.ts"
test("patient cannot view someone else's medical records", async ({ page }) => {
  await page.goto('/patients/12/records');
  await expect(page.getByRole('heading', { name: 'Access Denied' })).toBeVisible();
  await expect(page.getByText('Diagnosis')).not.toBeVisible();
});
```

The first test broke because a designer renamed the button from "Add Patient" to "New Patient": the form it opens, the fields on it, and what happens when you submit it are all unchanged. The second test broke because a bug in the backend's authorization check now lets a logged-in patient load another patient's record page directly. Both tests show the identical surface symptom: red, with a locator or assertion that no longer matches what is currently on the page. A Healer agent asked to "fix" both will, by default, try to make both pass, but making the second one pass means erasing the exact bug the test exists to catch.

## The Concept

The question every healed diff has to answer, before you accept it, is not "does this make the test pass?" It is: **did the target change, or did the behavior change?**

- **The target changed, the behavior did not.** The "Add Patient" button still opens the same form, does the same thing on submit, and occupies the same functional role in the page: only its accessible name changed. A locator update here is safe because nothing about what the app *does* is different. This is locator drift, and it is exactly what a Healer is for.
- **The behavior changed.** The patient-records page used to redirect to an access-denied screen for another patient's ID and now renders the record instead. Nothing about the *locator* is wrong: `getByRole('heading', { name: 'Access Denied' })` still correctly describes what *should* be there. What changed is the app underneath it. No amount of locator repair fixes this, because the locator was never the problem. The only "fix" available to a healer here is rewriting the assertion itself, and that is not a fix. It is deleting the test's ability to catch this exact bug.

This is why the guardrail in this lesson is not "review healed tests occasionally." It is: every healed diff gets read, line by line, before merge, specifically to catch the difference between a locator changing and an assertion's *expected value* changing. A locator diff (`name: 'Add Patient'` to `name: 'New Patient'`) is low-risk and fast to verify. An assertion diff, anything that changes what the test expects to be true, especially on a permission-matrix test tied to the RBAC permission-matrix lesson's table, is exactly the diff that needs a human asking "is this now correct, or did we just make a bug invisible?"
