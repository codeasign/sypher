You've already seen how a union type lets you say "this can only be one of a few specific values." BookHaven's order status is a good example:

```typescript
type OrderStatus = "pending" | "shipped" | "delivered";
```

That's great for catching typos and invalid values up front. But it raises a new question: once you actually have a value of type `OrderStatus`, how do you write code that does something *different* for each possibility? You can't just assume it's `"shipped"` and call `.slice()` or run some shipped-only logic — TypeScript won't let you treat a value as one specific member of the union unless you've proven which one it is first. That process of proving it — checking a value so TypeScript narrows the union down to just the branch you're in — is called **type narrowing**.

The good news is narrowing usually just means writing the checks you'd already write in plain JavaScript. TypeScript is simply smart enough to follow along.

## Narrowing with plain `if` checks

Say you want to print a friendly message based on an order's status:

```typescript
function describeOrder(status: OrderStatus): string {
  if (status === "pending") {
    return "Your order is being prepared.";
  } else if (status === "shipped") {
    return "Your order is on its way!";
  } else {
    return "Your order has been delivered.";
  }
}
```

Inside the `if (status === "pending")` branch, TypeScript knows `status` can *only* be `"pending"` there — it has narrowed the type down from the full union to just that one literal value. Same thing in the `"shipped"` branch, and by the time you reach the final `else`, TypeScript has ruled out both `"pending"` and `"shipped"`, so it knows the only value left is `"delivered"`.

This matters because it means you get real safety, not just a runtime check. If you misspell a status anywhere in these comparisons — say you write `status === "shpped"` — TypeScript will flag it immediately, because `"shpped"` isn't one of the values `OrderStatus` allows. A plain JavaScript `if` chain would let that typo slip through silently and just never match.

## Narrowing with `typeof`

`if` checks against exact values work great when you're comparing against specific strings like `"shipped"`. But sometimes a value's *type* is what varies, not just which value it holds. A common example at BookHaven: a book's `price` usually arrives as a `number`, but if it came from a web form, it might arrive as a `string` instead, like `"14.99"`.

```typescript
function formatPrice(price: number | string): string {
  if (typeof price === "number") {
    return `$${price.toFixed(2)}`;
  } else {
    return `$${parseFloat(price).toFixed(2)}`;
  }
}
```

`typeof price === "number"` is a check you're probably already used to writing in JavaScript — TypeScript just pays extra attention to it. Inside that `if` branch, TypeScript narrows `price` down to plain `number`, so it lets you call `.toFixed(2)` directly, since that's a method numbers have. In the `else` branch, TypeScript knows the only option left is `string`, so it lets you call `parseFloat()` on it, but it would stop you from calling `.toFixed()` there directly, since strings don't have that method.

That's the whole idea behind narrowing: check the value, and TypeScript rewards you by unlocking exactly the operations that are safe for whatever you've proven it to be at that point in the code.

## Try it

Write a function `orderIcon(status: OrderStatus): string` that returns `"📦"` when the status is `"pending"`, `"🚚"` when it's `"shipped"`, and `"✅"` when it's `"delivered"`. Use plain `if`/`else` checks like the `describeOrder` example above, then call your function with all three possible statuses to confirm each one returns the right icon.
