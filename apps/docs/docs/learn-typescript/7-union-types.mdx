Sometimes a value can't be pinned down to just one type. It can be one of a few things — and only those things. That's the whole idea behind a union type: you're telling TypeScript "this value is either A, B, or C, and nothing else."

Let's ground this in something BookHaven deals with every day: order status. An order in BookHaven's system isn't just "any string" — it can only ever be `"pending"`, `"shipped"`, or `"delivered"`. Nothing else makes sense. Here's how you write that as a type:

```typescript
type OrderStatus = "pending" | "shipped" | "delivered";
```

That `|` symbol is read as "or." So `OrderStatus` means: a value of type `OrderStatus` is `"pending"` **or** `"shipped"` **or** `"delivered"`. This particular flavor — a union of specific string values rather than the general `string` type — is often called a **union of string literals**, because each option is a literal, exact string rather than the whole universe of possible strings.

Now let's use it:

```typescript
function printOrderStatus(status: OrderStatus): void {
  console.log(`Order is currently: ${status}`);
}

printOrderStatus("pending");
printOrderStatus("shipped");
printOrderStatus("delivered");
```

All three of those calls are perfectly valid, because all three strings are members of the `OrderStatus` union. TypeScript checks each one against the list and says "yep, that's allowed."

## What happens when you try something else

Here's where the union type earns its keep. Try passing a status that isn't in the list:

```typescript
printOrderStatus("cancelled");
```

TypeScript stops you right there, with an error along these lines:

```text
Argument of type '"cancelled"' is not assignable to parameter of type 'OrderStatus'.
```

That's a genuinely useful catch. Without the union type, `status` would just be a plain `string`, and TypeScript would happily accept `"cancelled"`, `"CANCELLED"`, `"cancled"` (typo included), or literally any other text — and you wouldn't find out something was wrong until the order status showed up broken somewhere in the BookHaven app. With `OrderStatus` as a union of exact values, the typo gets caught the moment you write it, before the code ever runs.

The same idea applies to variables, not just function parameters:

```typescript
let currentStatus: OrderStatus = "pending";
currentStatus = "shipped"; // fine — still one of the allowed values
currentStatus = "returned"; // error — "returned" isn't in the union
```

## Unions aren't just for strings

While `OrderStatus` is a union of string literals, unions can combine any types at all. For example, maybe a BookHaven book's `price` field is allowed to be a `number` or the string `"contact-us"` for special orders:

```typescript
type BookPrice = number | "contact-us";

function displayPrice(price: BookPrice): void {
  console.log(price);
}

displayPrice(24.99);
displayPrice("contact-us");
```

But for this module, the pattern to remember is the one you'll use constantly: a small, fixed set of allowed string values, combined with `|`, given a name with `type`. It reads almost like plain English — `"pending" | "shipped" | "delivered"` really does mean "pending, shipped, or delivered, and nothing else."

This same `OrderStatus` union is going to come back later when we look at how TypeScript can narrow down which branch of a union you're in, and again when we compare unions like this one to another way of modeling a fixed set of options. For now, just get comfortable with the shape: list the exact values you'll allow, separated by `|`, and let TypeScript reject anything outside that list.

## Try it

Define a union type called `PaymentMethod` that can only be `"credit-card"`, `"paypal"`, or `"gift-card"`. Then write a function `processPayment` that takes a `PaymentMethod` as its only parameter and logs a message like `Processing payment via credit-card`. Call your function once with a valid method, and then try calling it with `"cash"` to see the error TypeScript gives you. Read the error message carefully — it should tell you exactly which values are allowed.
