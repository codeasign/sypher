Remember the generic wrapper we built earlier, the one that could hold a `Book`, a `Member`, or even a plain string, all with the same function? Generics are already useful at that basic level. This page adds two small but handy tools on top: putting a limit on what a generic type parameter is allowed to be, and giving a generic a sensible type to fall back on when nobody specifies one.

## The problem: sometimes "any type" is too loose

Say BookHaven wants a function that applies a discount to something priced. It might be a `Book`, or it might be an `Order` (a customer's whole cart total). Both have a `price`, so the discount math is identical either way:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

interface Order {
  orderId: string;
  price: number;
}
```

If you write a fully generic function like `function applyDiscount<T>(item: T, percentOff: number)`, TypeScript has no idea `item` even has a `price` on it; `T` could be anything at all, including a string or a number with no `price` field. You'd get an error the moment you tried `item.price`.

## Constraining a generic with `extends`

The fix is to tell TypeScript "`T` can be whatever you like, as long as it has at least a `price` field." That's what `extends` does in a generic: it's a constraint, not inheritance in the class sense, just a minimum shape the type has to match.

```typescript
function applyDiscount<T extends { price: number }>(item: T, percentOff: number): T {
  return { ...item, price: item.price - item.price * (percentOff / 100) };
}
```

`<T extends { price: number }>` means: whatever type gets used for `T`, it must at least have a `price: number` property. It's free to have other properties too; `T` isn't limited to *only* `price`, it just has to include it. Now `item.price` is always safe to use inside the function, because TypeScript knows every possible `T` has it.

Here it is working with both a `Book` and an `Order`, no changes needed:

```typescript
const book: Book = {
  title: "The Hobbit",
  author: "J.R.R. Tolkien",
  price: 14.99,
  inStock: true,
};

const discountedBook = applyDiscount(book, 10);
console.log(discountedBook.price, discountedBook.title);

const order: Order = { orderId: "BH-2291", price: 58.5 };
const discountedOrder = applyDiscount(order, 10);
console.log(discountedOrder.price, discountedOrder.orderId);
```

Both calls work, and both keep their full original shape: `discountedBook` still has `title` and `inStock`, `discountedOrder` still has `orderId`. That's because the function returns `T`, not some fixed "priced item" type, so whatever specific shape came in comes back out, just with the price adjusted. And if you tried calling `applyDiscount("mystery novel", 10)`, TypeScript would immediately reject it, because a plain string has no `price`, so it doesn't satisfy the constraint.

## Generic defaults: filling in a sensible default type

The other tool is giving a generic type parameter a default, so callers don't have to specify a type every single time if the common case is obvious. Think back to the generic container that wrapped a value together with a fetch time:

```typescript
interface StoreResult<T> {
  value: T;
  fetchedAt: string;
}
```

Every time someone uses `StoreResult` on its own (not inferred from a function call, say, as a variable's type annotation), they have to write out the type, like `StoreResult<Book>`. But in BookHaven, the overwhelmingly common case is wrapping a `Book`. A generic default lets you say "if nobody specifies a type, assume `Book`":

```typescript
interface StoreResult<T = Book> {
  value: T;
  fetchedAt: string;
}
```

The `= Book` is the default. Now you can leave the type argument off entirely when you mean `Book`, and only specify something else when you actually need to:

```typescript
const bookResult: StoreResult = {
  value: { title: "Dune", author: "Frank Herbert", price: 18.5, inStock: true },
  fetchedAt: new Date().toISOString(),
};

const memberResult: StoreResult<{ name: string; email: string }> = {
  value: { name: "Priya Shah", email: "priya@example.com" },
  fetchedAt: new Date().toISOString(),
};
```

`bookResult` uses no type argument at all, so TypeScript fills in `Book` from the default, and `bookResult.value` is checked as a `Book`. `memberResult` explicitly names a different shape, which overrides the default just fine. The default only kicks in when nothing else is provided; it never forces `Book` on you, it just saves typing for the common case.

## Try it

Write a generic function called `restock` that works on anything with an `inStock` boolean field, using a constraint like `T extends { inStock: boolean }`. It should take an item and return a copy of it with `inStock` set to `true`.

Try calling it with a `Book` object, and with a second, made-up interface of your own (something like a `Magazine` with its own fields plus `inStock`). Both should work with the exact same function. Then try calling `restock` with a plain object that has no `inStock` field at all, and confirm TypeScript stops you.
