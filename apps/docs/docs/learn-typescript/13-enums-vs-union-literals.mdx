Remember the status type we made a union out of earlier, back when BookHaven needed a way to track where an order was in its journey?

```typescript
type OrderStatus = "pending" | "shipped" | "delivered";

function printStatus(status: OrderStatus) {
  console.log(`This order is currently: ${status}`);
}

printStatus("shipped");
```

That's a union of string literals: a type that can only be one of a fixed set of exact string values. TypeScript will yell at you if you try to pass `"cancelled"` or `"Shipped"` (wrong casing) because those aren't in the allowed set.

TypeScript also has a built-in language feature for exactly this kind of "one of a fixed set of named options" idea, called an `enum` (short for "enumeration," which just means "a list of named values"). Here's the same `OrderStatus` concept written as an enum instead:

```typescript
enum OrderStatusEnum {
  Pending = "pending",
  Shipped = "shipped",
  Delivered = "delivered",
}

function printStatusEnum(status: OrderStatusEnum) {
  console.log(`This order is currently: ${status}`);
}

printStatusEnum(OrderStatusEnum.Shipped);
```

Both of these do roughly the same job: they restrict a value to one of a small, named set of options. But they behave a little differently in practice, and it's worth seeing exactly how.

## Working with the union version

With the union type, an `OrderStatus` is just a plain string at runtime. There's no extra object floating around; `"shipped"` is `"shipped"`, full stop. That means you can write plain string literals directly wherever an `OrderStatus` is expected, and you can log them, compare them, or send them over JSON without any translation step:

```typescript
const status: OrderStatus = "delivered";

if (status === "delivered") {
  console.log("Your BookHaven order has arrived!");
}
```

This is especially handy in BookHaven's case because order statuses often come from a database or an API response as plain strings. With a union, that string can be used directly. TypeScript checks, at compile time, that you only ever assign or compare against `"pending"`, `"shipped"`, or `"delivered"`, but once your code runs, it's just working with ordinary strings.

## Working with the enum version

The enum version gives you a named object you can reference, `OrderStatusEnum.Shipped`, rather than typing out the raw string `"shipped"` yourself. Some people like that because it reads a bit more like a label and can be easier to autocomplete in an editor:

```typescript
function describeOrder(status: OrderStatusEnum): string {
  switch (status) {
    case OrderStatusEnum.Pending:
      return "We're preparing your BookHaven order.";
    case OrderStatusEnum.Shipped:
      return "Your BookHaven order is on its way.";
    case OrderStatusEnum.Delivered:
      return "Your BookHaven order has been delivered.";
  }
}

console.log(describeOrder(OrderStatusEnum.Pending));
```

But enums come with a catch: because `OrderStatusEnum` is a real object that exists at runtime (not just a type that disappears after compiling), if a status string arrives from outside your code (say, from BookHaven's order API), you can't just hand it a raw string like `"shipped"` and expect it to match `OrderStatusEnum.Shipped` without an explicit cast. You'd have to write something like `status as OrderStatusEnum`, and TypeScript won't actually verify at compile time that the string you're casting is really one of the valid options. That's an easy way to accidentally let a typo slip through.

## Which one should you reach for?

In modern TypeScript codebases, union literals like `OrderStatus` are the more common choice. They're lighter-weight (no extra object generated at runtime), and they work more naturally with plain JavaScript values like the strings you get back from APIs or databases. Enums have a few quirks, like the casting issue above, that make them less popular for new code these days. That said, you'll still run into enums plenty in older TypeScript projects, so it's worth being able to read them comfortably even if you end up reaching for unions yourself.

## Try it

Add a fourth status to BookHaven's order tracking: `"returned"`.

1. Add `"returned"` to the `OrderStatus` union type.
2. Add a matching `Returned = "returned"` member to `OrderStatusEnum`.
3. Update `describeOrder` so its `switch` statement handles `OrderStatusEnum.Returned` too, returning a message like `"Your BookHaven order was returned."`.
4. Call `printStatus` with `"returned"` and confirm it prints correctly.
