If you've been following along with BookHaven, you've almost certainly already seen a red squiggly line or a wall of red text from TypeScript. That's completely normal; it happens to everyone, every day, no matter how experienced they are. The goal of this page isn't to help you avoid errors forever (you won't), it's to help you read them calmly, figure out what they're actually telling you, and fix them in seconds instead of staring at them in confusion.

TypeScript's error messages look intimidating because they're very literal and very precise. But underneath the formal wording, almost every error is really just saying one of a small handful of things: "you gave me the wrong kind of value," "you're missing something required," or "this isn't one of the options I was told to expect." Let's walk through real BookHaven mistakes and translate each one.

## Mistake 1: passing the wrong type into a typed field

Say BookHaven has this `Book` interface, which you've seen in earlier pages:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

function printReceipt(book: Book) {
  console.log(`${book.title}: $${book.price.toFixed(2)}`);
}
```

Now imagine you call it like this, accidentally passing the price as text instead of a number:

```typescript
printReceipt({
  title: "The Quiet Shelf",
  author: "Mara Todd",
  price: "12.50",
  inStock: true,
});
```

TypeScript stops you with something like this:

```text
Argument of type '{ title: string; author: string; price: string; inStock: boolean; }'
is not assignable to parameter of type 'Book'.
  Types of property 'price' are incompatible.
    Type 'string' is not assignable to type 'number'.
```

That's a lot of words, but read it from the bottom up: the bottom line is usually the actual root cause, and everything above it is just TypeScript explaining how it traced the problem back there. "Type 'string' is not assignable to type 'number'" means: you handed me text, but I was told to expect a number. The line above it tells you where, the `price` property specifically. And the top line just says "this whole object doesn't match `Book`" because of that one mismatched field. Fix: drop the quotes, `price: 12.50`, and the error disappears.

## Mistake 2: forgetting a required property

Here's another common one. You're building a new book object and you forget a field:

```typescript
const newArrival: Book = {
  title: "Salt and Ledger",
  author: "Priya Nandan",
  price: 18,
};
```

TypeScript says:

```text
Property 'inStock' is missing in type '{ title: string; author: string; price: number; }'
but required in type 'Book'.
```

This one's the friendliest kind of error, because it names the exact missing piece by name: `inStock`. No detective work needed: just add the property TypeScript names, and you're done. It's worth noticing the pattern too: "missing in type ___ but required in type ___" is TypeScript's standard phrasing whenever an object is short a property that its target type demands.

## Mistake 3: a typo'd property name

This one trips people up because the message looks scarier than the mistake actually is. Say you meant to write `inStock` but fat-fingered it:

```typescript
const reorder: Book = {
  title: "Salt and Ledger",
  author: "Priya Nandan",
  price: 18,
  inStok: true,
};
```

```text
Type '{ title: string; author: string; price: number; inStok: boolean; }'
is not assignable to type 'Book'.
  Object literal may only specify known properties, and 'inStok' does not exist
  in type 'Book'.
```

Read the last line closely: "'inStok' does not exist in type 'Book'." TypeScript isn't confused about what a `Book` is; it's telling you, quite specifically, that the property name you typed doesn't match any of the ones it knows about. Whenever you see "does not exist in type," your first move should be to double-check spelling and capitalization on both sides: the property you wrote, and the property the type actually declares. Here the fix is just correcting `inStok` back to `inStock`.

## Mistake 4: a value outside a union's allowed options

BookHaven tracks order status with a union of exact strings, which you've seen before:

```typescript
type OrderStatus = "pending" | "shipped" | "delivered";

function printOrderStatus(status: OrderStatus): void {
  console.log(`Order is ${status}`);
}

printOrderStatus("cancelled");
```

```text
Argument of type '"cancelled"' is not assignable to parameter of type 'OrderStatus'.
```

Notice this message doesn't tell you what the allowed values *are*; it just tells you `"cancelled"` isn't one of them. That's fine; it's enough of a clue. Hover over `OrderStatus` in your editor (or jump to where it's defined) and you'll see the full list: `"pending" | "shipped" | "delivered"`. Any time you see "is not assignable to type" and the target type is a short list of quoted strings, you're looking at a union mismatch: either a typo in the value you passed, or a genuinely new status that needs to be added to the union itself.

## Mistake 5: a generic constraint error

This is the one that looks the scariest the first time you meet it, so let's take it slowly. Recall the `applyDiscount` function from earlier, which works on anything that at least has a `price` field:

```typescript
function applyDiscount<T extends { price: number }>(item: T, percentOff: number): T {
  return { ...item, price: item.price - item.price * (percentOff / 100) };
}
```

Now imagine you accidentally call it with a plain customer record that has no `price` at all:

```typescript
const member = { name: "Jordan Lee", memberSince: 2021 };

applyDiscount(member, 10);
```

```text
Argument of type '{ name: string; memberSince: number; }' is not assignable to
parameter of type '{ price: number; }'.
  Property 'price' is missing in type '{ name: string; memberSince: number; }'
  but required in type '{ price: number; }'.
```

It looks unfamiliar because of the `<T extends ...>` in the function signature, but strip that away and this is exactly the same shape of error as mistake 2: a required property is missing. The constraint `T extends { price: number }` just means "whatever you pass in here must, at minimum, have a `price` field," and the error is TypeScript confirming that `member` doesn't. The fix is the same instinct as always: either pass in something that does have a `price` (like a `Book`), or add one to the object you're passing. Generic errors read exactly like non-generic ones once you know to look past the extra angle-bracket syntax.

## A few habits that make errors easier

A handful of small habits go a long way here. First, when a message is several lines long, start at the bottom; that's usually the specific, concrete problem, and the lines above it are just TypeScript zooming back out. Second, look for the type names it mentions (`Book`, `OrderStatus`, `{ price: number }`) and go check what those actually require, rather than guessing from memory. Third, phrases like "is not assignable to," "is missing in type," and "does not exist in type" are patterns you'll see over and over; once you recognize the pattern, you can usually guess the fix before you've even finished reading the message. And finally, your editor will underline the exact spot the problem starts, so you rarely have to hunt through a whole file; the squiggly line is already pointing at the culprit.

None of this means every error will be obvious immediately. Some are genuinely gnarly, especially once types get deeply nested. But the vast majority of day-to-day BookHaven errors are one of the five patterns above wearing slightly different clothes: wrong type, missing property, typo'd property, value outside a union, or a generic constraint not being met.

## Try it

Take this BookHaven snippet:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

const misprint: Book = {
  title: "Harbor Light",
  athor: "Devon Cruz",
  price: 15,
  inStock: false,
};
```

Without running it yet, predict what error TypeScript will give you and which line it's pointing at. Then paste it into your editor (or the TypeScript Playground) and check whether your prediction matches the real message. Fix the mistake, then introduce a different one on purpose: try making `price` a string, or setting `inStock` to `"false"` as text instead of the boolean, and practice reading that error too before fixing it.
