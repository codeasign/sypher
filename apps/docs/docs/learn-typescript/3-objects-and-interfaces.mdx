BookHaven's catalog is full of, well, books. So far you've described values one at a time: a `string` for a title, a `number` for a price. But a real book in the system isn't just a title floating on its own; it's a bundle of related fields that all belong together. That's where **interfaces** come in.

An interface is a way of describing the *shape* of an object: which properties it has, and what type each one is. Think of it as a contract. If something claims to be a `Book`, TypeScript will hold it to that contract everywhere it's used.

Here's the shape BookHaven will use for the rest of this course:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}
```

Now you can create a value and tell TypeScript it should match that shape:

```typescript
const novel: Book = {
  title: "The Midnight Library",
  author: "Matt Haig",
  price: 14.99,
  inStock: true,
};
```

Try removing a property, or misspelling one, and TypeScript will complain immediately, before you ever run the code. That's the whole point of describing the shape up front: typos and missing fields get caught at the moment you write them, not when a customer hits a broken page.

```typescript
const brokenBook: Book = {
  title: "The Midnight Library",
  author: "Matt Haig",
  price: 14.99,
  // Error: Property 'inStock' is missing
};
```

Functions can lean on this too. Instead of listing four separate parameters, you can accept one `Book` and know exactly what's inside it:

```typescript
function describeBook(book: Book): string {
  return `${book.title} by ${book.author} — $${book.price}`;
}

describeBook(novel);
```

## Optional properties

Not every book in BookHaven's catalog has a description written yet. Maybe it was just added and nobody's gotten around to writing the blurb. Marking a property as **optional** (using a `?` after its name) tells TypeScript that it's fine for that field to be missing entirely.

```typescript
interface CatalogBook {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
  description?: string;
}

const withDescription: CatalogBook = {
  title: "Project Hail Mary",
  author: "Andy Weir",
  price: 16.5,
  inStock: true,
  description: "A lone astronaut must save humanity from extinction.",
};

const withoutDescription: CatalogBook = {
  title: "Dune",
  author: "Frank Herbert",
  price: 12.0,
  inStock: false,
};
```

Both objects above are valid `CatalogBook` values, because `description` is allowed to be absent. If it weren't marked with `?`, the second object would fail to compile.

## Readonly properties

Some fields shouldn't change once a book is created, like an internal catalog code assigned when the book is first added to BookHaven's system. Marking a property `readonly` tells TypeScript to stop you from reassigning it after the object exists.

```typescript
interface CatalogBook {
  readonly catalogId: string;
  title: string;
  author: string;
  price: number;
  inStock: boolean;
  description?: string;
}

const classic: CatalogBook = {
  catalogId: "BH-1001",
  title: "1984",
  author: "George Orwell",
  price: 9.99,
  inStock: true,
};

classic.price = 8.5; // fine, price isn't readonly
classic.catalogId = "BH-9999"; // Error: cannot assign to 'catalogId' because it is a read-only property
```

`readonly` doesn't make the whole object frozen; you can still update `price` or `inStock` any time. It just locks down that one field, which is perfect for an identifier that should stay stable for the life of the object.

## Try it

Define an interface called `Order` for a BookHaven customer order, with these properties:

- `readonly orderId: string`
- `bookTitle: string`
- `quantity: number`
- `giftWrapped?: boolean`

Then create two `Order` values: one that includes `giftWrapped`, and one that leaves it out. Both should compile without errors. Finally, try assigning a new value to `orderId` on one of them and confirm that TypeScript stops you.
