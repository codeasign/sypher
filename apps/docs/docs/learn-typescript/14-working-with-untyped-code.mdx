Sooner or later you'll want to use a JavaScript package in your BookHaven project that has no TypeScript types at all. Nothing breaks; TypeScript just shrugs and treats everything from that package as `any`, which means it stops checking it for you. Let's look at what to do about that.

## The `@types` packages

For popular JavaScript libraries, someone has usually already written the type definitions for you and published them separately under the `@types` scope on npm. If you install a package called `some-package` and TypeScript complains it can't find type information, the first thing to try is:

```bash
npm install --save-dev some-package
npm install --save-dev @types/some-package
```

That second command pulls down a matching set of `.d.ts` files (declaration files, meaning files that describe a shape without containing any actual runnable code) written and maintained by the community, under a project called DefinitelyTyped. Once it's installed, TypeScript picks it up automatically and you get full autocomplete and type checking for that library, even though the library itself is plain JavaScript.

This works for a huge number of well-known packages. But not every package has a matching `@types` entry; smaller, older, or more obscure libraries sometimes ship with nothing at all.

## When there are no types: writing your own

Imagine BookHaven's team has an old internal helper library called `bookhaven-legacy-utils`. It's a small, fictional package they wrote years ago, before anyone bothered with types, and nobody's gotten around to adding them. It exports a function like this:

```javascript
// from the (fictional) bookhaven-legacy-utils package — no types shipped
function formatPrice(book) {
  return "$" + book.price.toFixed(2);
}
```

If you import `formatPrice` into a TypeScript file as-is, TypeScript has no idea what `book` is supposed to look like, so it treats it as `any`. That means if you accidentally pass in a string, or a book object missing a `price`, TypeScript won't warn you; it'll just let the mistake through and you'll only find out when the code crashes.

The fix doesn't require rewriting the library. You just tell TypeScript the shape you expect, in your own project:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

declare function formatPrice(book: Book): string;
```

The `declare` keyword says "trust me, this function exists somewhere and here's its shape." You're not implementing `formatPrice` again, just describing it. Now when you call `formatPrice(myBook)`, TypeScript checks that `myBook` actually matches the `Book` shape before letting the call through:

```typescript
const paperback: Book = {
  title: "The Quiet Shelf",
  author: "Mara Todd",
  price: 12.5,
  inStock: true,
};

formatPrice(paperback);
```

That's it: one small local declaration, and an untyped function suddenly behaves like a fully typed one everywhere you use it in your project.

## When is `any` okay?

Sometimes you're prototyping quickly, or pulling in a one-off script, and you just don't want to stop and think about types yet. In that situation, letting something be `any` is a perfectly reasonable shortcut that lets you keep moving. But it's usually worth spending the extra minute to write even a rough local type, like the `Book` interface above, because that's what actually catches typos and mismatched data before they turn into bugs. `any` isn't wrong to reach for; it's just that a little bit of typing tends to pay for itself almost immediately.

## Try it

BookHaven's legacy utils package also exports this untyped function:

```javascript
function applyDiscount(book, percentOff) {
  return book.price - book.price * (percentOff / 100);
}
```

Write a `declare function` for `applyDiscount` using the `Book` interface from this page, so that calling it with a `Book` and a `number` is fully type-checked. Then try calling it with a made-up book object that's missing the `inStock` field and see what error TypeScript gives you.
