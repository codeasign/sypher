Right now, if you've been following along building BookHaven, you probably have all your types and functions crammed into one file. That works fine for a small example, but real projects don't stay small. The fix is simple: split your code into multiple files, and use `export` and `import` to share things between them.

## Export: making something available to other files

By default, everything you write in a TypeScript file is private to that file. If you want another file to be able to use an interface, a function, or a variable, you have to `export` it.

The easiest way is to put `export` right in front of the declaration:

```typescript
// types.ts
export interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

export interface Member {
  id: string;
  name: string;
  favoriteGenre: string;
}
```

Here, `types.ts` is a file whose whole job is to hold shared type definitions. Nothing in it runs any logic; it just describes shapes. That's a common and very tidy pattern once a project grows past a handful of types.

## Import: pulling something into another file

To use `Book` or `Member` somewhere else, you `import` them from the file that exports them. You write the path to that file, without the `.ts` extension:

```typescript
// store.ts
import { Book, Member } from "./types";

function describeBook(book: Book): string {
  return `${book.title} by ${book.author} — $${book.price.toFixed(2)}`;
}

const catalog: Book[] = [
  { title: "The Silent Shelf", author: "Mara Voss", price: 14.99, inStock: true },
  { title: "Bound in Ink", author: "Theo Lang", price: 22.5, inStock: false },
];

const member: Member = { id: "m-101", name: "Priya", favoriteGenre: "Mystery" };

catalog.forEach((book) => console.log(describeBook(book)));
```

That `./` at the start of the path means "look for a file called `types` in this same folder." TypeScript (and the JavaScript that it compiles down to) uses this file-based system to know exactly where `Book` and `Member` are coming from.

Notice what this buys you: `Book` is now defined in exactly one place. If BookHaven adds a `genre` field to books next month, you update the interface once in `types.ts`, and every file that imports `Book` (`store.ts` and any others) immediately knows about the change and gets checked against it.

## A few named exports, or one default export

So far you've seen **named exports**: you export several things by name (`Book`, `Member`), and the importing file picks exactly which names it wants inside curly braces `{ }`. This is the style you'll use most often for types, since a file often holds more than one of them.

There's also **default export**, for when a file's main job is to hand out one primary thing:

```typescript
// bookRepository.ts
export default class BookRepository {
  private books: Book[] = [];

  add(book: Book): void {
    this.books.push(book);
  }
}
```

```typescript
// main.ts
import BookRepository from "./bookRepository";

const repo = new BookRepository();
```

Notice the import has no curly braces; that's the tell that you're importing a default export. Default exports are handy for a file whose whole purpose is "here is one class" or "here is one function," but named exports (like our `types.ts`) are usually the better fit when a file exports several related things.

## Renaming an import

Occasionally two files each export something with the same name, or you just want a clearer local name. You can rename anything as you import it with `as`:

```typescript
import { Book as BookRecord } from "./types";

const item: BookRecord = { title: "Paper Trails", author: "Iris Kwan", price: 9.99, inStock: true };
```

`BookRecord` is only a local nickname inside this file; `types.ts` still exports it as `Book`.

## Why bother splitting files at all?

For a tiny script, you don't need to. But as soon as more than one file needs the same interface (say both `store.ts` and a future `checkout.ts` need to know what a `Book` looks like), copy-pasting the interface into both files is a trap. The two copies will quietly drift apart the first time someone edits only one of them. A shared `types.ts` file, imported wherever it's needed, keeps a single source of truth.

This same idea scales up: as BookHaven grows, you might add a `validators.ts` for input-checking functions, an `api.ts` for functions that talk to a server, and so on, each file focused on one job, importing whatever types it needs from `types.ts`.

## Try it

Create two files:

1. `types.ts`: export an `Order` interface with `id: string`, `bookTitle: string`, and `quantity: number`.
2. `receipt.ts`: import `Order` from `./types`, then write a function `printReceipt(order: Order): string` that returns a sentence like `"Order o-1: 2x The Silent Shelf"`. Call it with a sample order and log the result.

Once it works, try renaming `Order` to `PurchaseOrder` on import using `as`, and update the rest of `receipt.ts` to use that new local name.
