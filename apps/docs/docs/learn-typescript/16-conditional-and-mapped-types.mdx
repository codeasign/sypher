The two things in this module are ones you'll use **occasionally, not constantly**. Most days writing TypeScript, you won't reach for either of them. But they show up all the time when you're *reading* type definitions from libraries (React, database ORMs, and all sorts of packages define their types this way), so it's worth knowing what you're looking at, and how to write a small one yourself when you need to.

Let's start from the BookHaven `Book` interface you already know well:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}
```

## The problem: building a new type from an existing one, automatically

You've already seen utility types like `Partial<Book>`, which takes `Book` and makes every property optional. That's really useful, but have you ever wondered how `Partial` actually works under the hood? It's not magic; it's built using a feature called a **mapped type**. And sometimes you want a type that changes *depending on* another type: "if this is an array, do one thing; if it's a single item, do another." That's a **conditional type**.

Both of these are just tools for transforming types automatically, instead of writing every variation out by hand.

## Mapped types: looping over a type's properties

A mapped type lets you loop over every property in a type and do something to each one, kind of like using `.map()` on an array, except you're mapping over property names instead of values.

Let's build our own version of `Partial`, applied to `Book`, so you can see exactly how it works instead of just using the built-in one:

```typescript
type MyPartial<T> = {
  [Key in keyof T]?: T[Key];
};

type PartialBook = MyPartial<Book>;

const draft: PartialBook = {
  title: "The Hobbit",
};
```

Let's break that down piece by piece:

- `keyof T` means "every property name in `T`." For `Book`, that's `"title" | "author" | "price" | "inStock"`.
- `[Key in keyof T]` loops over each of those names, one at a time, calling the current one `Key`.
- `T[Key]` looks up the type of that property on the original type, so for `"title"` it's `string`, for `"price"` it's `number`, and so on.
- The `?` marks each one as optional, just like it would in a hand-written interface.

So `MyPartial<Book>` walks through every property on `Book` and rebuilds it with a `?` added. That's all `Partial` is doing behind the scenes.

Now let's write one that's actually new: a `ReadonlyBook`, where none of the fields can be changed after the book is created:

```typescript
type ReadonlyBook = {
  readonly [Key in keyof Book]: Book[Key];
};

const classic: ReadonlyBook = {
  title: "Dune",
  author: "Frank Herbert",
  price: 18.5,
  inStock: true,
};

classic.price = 15.0; // Error: cannot assign to 'price' because it's read-only
```

Same pattern as before, just with `readonly` in front instead of `?` at the end. That's the whole trick to mapped types: pick a modifier (`readonly`, `?`, or neither), loop over `keyof T`, and rebuild the type property by property.

## Conditional types: a type that branches based on another type

A conditional type is a type-level version of an `if` statement. It reads almost exactly like the ternary operator you already know from JavaScript (`condition ? valueIfTrue : valueIfFalse`), except it's checking types instead of values, using `extends` instead of a plain condition:

```typescript
type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<string>; // "yes"
type B = IsString<number>; // "no"
```

Read `T extends string ? "yes" : "no"` as "if `T` can be treated as a `string`, the result is `"yes"`; otherwise it's `"no"`." Nothing runs when your program executes; TypeScript works this out ahead of time, while it's checking your types.

Here's a more useful one for BookHaven. Say you've got a function that can be called with either a single `Book` or a whole array of them, and you want a type that describes "just give me back a single `Book`, no matter which one was passed in":

```typescript
type ElementType<T> = T extends (infer Item)[] ? Item : T;

type FromArray = ElementType<Book[]>; // Book
type FromSingle = ElementType<Book>;  // Book
```

The new piece here is `infer Item`. It means "if `T` turns out to be an array, grab whatever type is *inside* that array and call it `Item` so I can use it on the other side of the `?`." So when `T` is `Book[]`, TypeScript infers `Item` as `Book`, and the whole type resolves to `Book`. When `T` is already just `Book` (not an array), the `extends` check fails, and the type falls through to `T` itself, which is still `Book`. Either way, you end up with a plain `Book`, whether you started with one or a whole shelf of them.

## Where you'll actually run into these

You almost never need to write a conditional type from scratch in everyday app code. Where they matter is *reading* someone else's types. If you open up the type definitions for a library and see something like `T extends (infer U)[] ? U : never`, you now know exactly what's happening: it's checking whether `T` is an array and pulling out what's inside it. Same with mapped types: when you see `{ [K in keyof T]: ... }` in a library's types, you know it's rebuilding every property on `T` with some kind of tweak applied.

Don't worry if this feels a little less natural than everything before it. That's normal; these are genuinely one of the more advanced corners of TypeScript. Being able to recognize the pattern and follow along is the real goal here; reaching for these yourself in daily code is the exception, not the rule.

## Try it

Using the `Book` interface from this page, write a mapped type called `BookFlags` that takes `Book` and turns **every** property into a `boolean`, no matter what the original type was, so `title` (a `string`) and `price` (a `number`) both end up typed as `boolean` in the result. Then create an object of type `BookFlags` where every field is `true` or `false`.

Hint: instead of writing `T[Key]` on the right-hand side of your mapped type like the examples above, write `boolean` directly. That's what forces every property to that one type regardless of what it used to be.
