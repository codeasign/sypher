Functions are where TypeScript starts to feel really useful. Once you tell TypeScript what a function expects and what it hands back, it will stop you from calling it wrong, with no more digging through code to figure out what argument order some function wants.

Let's start with a function that formats a book's price for display on BookHaven's storefront:

```typescript
function formatPrice(price: number): string {
  return `$${price.toFixed(2)}`;
}

formatPrice(14.99); // "$14.99"
```

Two things are typed here. `price: number` is a **typed parameter**. It tells TypeScript (and anyone reading the code) that this function only accepts numbers. And `: string` right after the parameter list is the **typed return value**. It says this function always hands back a string. If you accidentally tried to `return price` instead of the formatted string, TypeScript would immediately flag it as an error, because a `number` isn't a `string`.

## Typing parameters that are objects

Functions often take a whole object as a parameter, not just a single value. Here's a function that checks whether a `Book` is available to purchase:

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

function isAvailable(book: Book): boolean {
  return book.inStock;
}

const dune: Book = {
  title: "Dune",
  author: "Frank Herbert",
  price: 12.5,
  inStock: true,
};

isAvailable(dune); // true
```

Because `book` is typed as `Book`, TypeScript knows exactly which properties it has. Try `book.author` and you get full autocomplete. Try `book.publisher` (which doesn't exist on `Book`) and TypeScript will tell you that property doesn't exist.

## Optional parameters

Sometimes a function has a parameter that's genuinely optional, because the caller might not always have a value for it. BookHaven might want to apply a discount to a book, but not every call site has a discount code to apply:

```typescript
function applyDiscount(book: Book, discountCode?: string): number {
  if (discountCode === "SAVE10") {
    return book.price * 0.9;
  }
  return book.price;
}

applyDiscount(dune); // 12.5, no discount code passed
applyDiscount(dune, "SAVE10"); // 11.25
```

The `?` right after `discountCode` marks it as **optional**: a parameter the caller is allowed to leave out entirely. Inside the function, `discountCode` has the type `string | undefined`, meaning "either a string, or nothing was passed." That's why we check it before using it, rather than assuming it's always there.

## Default parameters

A **default parameter** is similar to optional, but instead of allowing `undefined`, you give it a fallback value to use when the caller doesn't provide one. Let's say most BookHaven orders are for a single copy, but customers can order more:

```typescript
function orderBook(book: Book, quantity: number = 1): string {
  return `Ordered ${quantity} x "${book.title}"`;
}

orderBook(dune); // "Ordered 1 x \"Dune\""
orderBook(dune, 3); // "Ordered 3 x \"Dune\""
```

With `quantity: number = 1`, TypeScript already knows `quantity` is a `number`; it infers that from the default value, so you technically don't even need to write `: number` yourself. But writing it explicitly is fine too, and can make the intent clearer at a glance.

The difference between optional and default parameters comes down to what happens when the caller skips the argument: with optional, you get `undefined` and have to handle that case yourself; with default, TypeScript quietly fills in the fallback value for you, so the rest of your function can just assume it's there.

## Arrow functions, briefly

Everything above works exactly the same with **arrow function** syntax, which is just a shorter way to write a function using `=>`. Here's `formatPrice` again, written as an arrow function:

```typescript
const formatPriceArrow = (price: number): string => `$${price.toFixed(2)}`;
```

Same parameter type, same return type, same behavior, just a more compact shape. You'll see both styles throughout real-world TypeScript code, and which one you reach for is mostly a matter of taste and context.

## Try it

Write a function called `describeBook` that takes a `Book` and an optional `note` parameter (a `string`). It should return a `string`:

- If `note` was passed, return `"${book.title} — ${note}"`.
- If `note` was not passed, return just `book.title`.

Try calling it both with and without the second argument, and check that TypeScript doesn't complain either way.
