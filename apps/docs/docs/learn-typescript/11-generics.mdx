Say you're building BookHaven, and you write a little helper function that wraps a `Book` together with the time it was fetched, so the rest of the app can show "last updated" info next to a book's details.

```typescript
interface Book {
  title: string;
  author: string;
  price: number;
  inStock: boolean;
}

interface BookResult {
  value: Book;
  fetchedAt: string;
}

function wrapResult(value: Book): BookResult {
  return { value, fetchedAt: new Date().toISOString() };
}
```

That works fine for books. But then you need the exact same wrapper for a `Member` (a customer account), and then again for a plain search string, and then again for a list of order totals. Are you really going to write `MemberResult`, `StringResult`, and a whole new function for each one? They'd all look identical except for one type. That copy-and-paste-with-a-different-type-name pattern is exactly the problem generics exist to solve.

## The plain-English problem

You want to write **one** function or **one** type that works with many different types, without giving up type safety. You don't want to fall back to `any`, either. `any` would work with anything, but it also throws away all the checking TypeScript gives you. You'd lose autocomplete, and typos or wrong property access wouldn't get caught.

Generics let you write code with a placeholder for "whatever type gets used here," and TypeScript fills in the real type each time you use it, keeping full type safety without the copy-pasting.

## A container that works with anything

Let's build that wrapper properly, using a generic type parameter. By convention it's called `T` (short for "Type"), though you can name it anything you like.

```typescript
interface StoreResult<T> {
  value: T;
  fetchedAt: string;
}

function wrapResult<T>(value: T): StoreResult<T> {
  return { value, fetchedAt: new Date().toISOString() };
}
```

The `<T>` after `StoreResult` and after `wrapResult` is the placeholder. It says "this type/function needs a type filled in before it's complete." You don't pick what `T` is when you write the function; you pick it when you *use* the function, and TypeScript figures the rest out from there.

Here it is wrapping a `Book`:

```typescript
const book: Book = {
  title: "The Midnight Library",
  author: "Matt Haig",
  price: 14.99,
  inStock: true,
};

const bookResult = wrapResult(book);
// bookResult.value is a Book — title, author, price, inStock all available
console.log(bookResult.value.title);
```

TypeScript looked at what you passed to `wrapResult` (a `Book`), figured out that `T` must be `Book` for this call, and typed `bookResult.value` as a `Book` automatically. You never had to write `wrapResult<Book>(book)` yourself, though you could have; TypeScript is just inferring it for you.

## The same function, a different type

Here's the payoff: that exact same `wrapResult` function also works for a `Member`, with zero changes.

```typescript
interface Member {
  name: string;
  email: string;
  loyaltyPoints: number;
}

const member: Member = {
  name: "Priya Shah",
  email: "priya@example.com",
  loyaltyPoints: 240,
};

const memberResult = wrapResult(member);
console.log(memberResult.value.loyaltyPoints);
```

`memberResult.value` is correctly typed as a `Member`: TypeScript knows it has `loyaltyPoints`, not `title` or `author`. And it works just as well with a plain string, say for wrapping a search query:

```typescript
const searchResult = wrapResult("mystery novels");
console.log(searchResult.value.toUpperCase());
```

`searchResult.value` is a `string`, so `.toUpperCase()` is available. If you tried `searchResult.value.loyaltyPoints`, TypeScript would immediately flag it as an error, because in this call `T` is `string`, not `Member`. That's the part that makes generics different from `any`: each call still gets checked against the specific type it was used with, and you just didn't have to write three separate functions to get there.

## Why not just use `any`?

You could write `value: any` instead of `value: T`, and it would technically compile. But watch what you'd lose:

```typescript
function wrapResultLoosely(value: any) {
  return { value, fetchedAt: new Date().toISOString() };
}

const looseBook = wrapResultLoosely(book);
console.log(looseBook.value.titl);
```

That typo, `titl` instead of `title`, would slide right through, because `any` tells TypeScript to stop checking entirely. With the generic version, `bookResult.value.titl` would be flagged immediately, because TypeScript still knows `bookResult.value` is a `Book` with a `title` property, not `titl`. Generics give you the flexibility of "works with many types" while keeping the safety of "but TypeScript still knows exactly which type it is."

## A note on naming

You'll see `T` everywhere in generic code, and that's a fine default for "the one type this thing works with." When there's more than one type parameter, or when a more descriptive name helps readability, people use things like `TValue` or a full word. None of that matters to TypeScript; it only cares about the placeholder being used consistently. For now, sticking with `T` is perfectly normal and easy to read.

## Try it

Write a generic function called `firstItem` that takes an array of some type `T` and returns the first element of that array. Its signature should look like `firstItem<T>(items: T[]): T`.

Then call it three times:

1. With an array of `Book` objects, and log the returned book's `title`.
2. With an array of numbers (say, a list of order totals), and log the returned number.
3. With an array of strings (say, a list of genre names), and log the returned string.

Check that TypeScript correctly infers the return type each time. Try accessing `.title` on the result of the numbers call and confirm TypeScript gives you an error.
