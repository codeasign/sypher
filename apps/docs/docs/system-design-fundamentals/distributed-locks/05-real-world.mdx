## Case Study 1: The Redlock Controversy

In 2014, Salvatore Sanfilippo (Antirez), the creator of Redis, published the Redlock algorithm. The goal was to create a distributed lock that works correctly even when individual Redis nodes fail. The algorithm uses N independent Redis nodes and requires a majority to agree before granting a lock.

In 2016, Martin Kleppmann published a detailed critique of Redlock in his blog post "How to do distributed locking." Kleppmann argued that Redlock is neither simple enough to be a good efficiency lock nor safe enough to be a correctness lock. Its main flaw is that it does not provide fencing tokens, and it depends on timing assumptions. Without fencing tokens, a process that experiences a GC pause, network delay, or clock jump can continue writing to the protected resource after the lock has expired, causing data corruption.

The controversy played out publicly. Antirez responded with a blog post ("Is Redlock safe?") defending Redlock, arguing that the algorithm's timing assumptions (bounded clock drift, bounded network delay) are reasonable for most systems and that a client can check the elapsed time after acquiring the lock. Kleppmann countered that these assumptions are not guaranteed in production environments, since a process can be paused at any point, for example by garbage collection, after its last check.

### The Resolution

The industry has not reached a consensus. The practical outcome is nuanced:

- For non-critical operations (cache rebuilding, log rotation, non-critical job scheduling), Redlock is safe enough. The cost of a rare duplicate operation is low.
- For critical operations (financial transactions, resource allocation, leader election), Redlock should not be used. Use ZooKeeper or etcd with fencing tokens instead.
- The controversy improved the entire field. Lock implementations now routinely document their safety guarantees and failure modes. Teams make informed choices rather than assuming any lock implementation is perfectly safe.

## Case Study 2: Google Chubby

Google Chubby is a distributed lock service designed for coarse-grained locking, described in a 2006 paper by Mike Burrows. The paper reports that Google's infrastructure used it for master election and for storing small amounts of metadata: GFS and Bigtable use it to elect a master, and Bigtable also uses it to discover tablet servers. Chubby is also widely used as a name service inside Google.

Chubby exposes a filesystem-like interface with directories and files. Each file can be locked for exclusive access, and locks are advisory (they only exclude other lock holders, not plain reads and writes). Clients hold a session with the Chubby cell that is kept alive through a lease renewed by KeepAlive calls. If the session lease expires, the client's locks are released.

Chubby also introduced a form of fencing: a lock holder can request a *sequencer*, an opaque byte string describing the lock and its generation, and pass it along with requests, and the receiving server can check with Chubby (or compare against the most recent generation it has seen) that the lock is still valid.

### Lessons from Chubby

**Coarse-grained locking is the right default**: Chubby is designed for locks that are held for minutes to hours. Fine-grained locking (milliseconds) is not its intended use case. This simplicity makes Chubby robust: the overhead of consensus is amortized over the long lock duration.

**Cache aggressively, invalidate on change**: Clients cache file data and metadata and the master sends invalidations when they change. Most requests are served from client caches, which is how a single Chubby cell supports tens of thousands of clients that would otherwise overwhelm it with polling.

**Master leases**: The Chubby master holds a lease granted by the replicas and extends it while it is healthy. If the master fails, the replicas wait for the lease to run out and elect a new master. The Chubby paper reports failovers on the order of seconds to tens of seconds, during which lock operations are unavailable, and clients are given a grace period so that short failovers do not expire their sessions. Applications must tolerate this window.

## Case Study 3: ZooKeeper in Kafka

Apache Kafka uses ZooKeeper for broker metadata management and leader election. Each Kafka partition has one leader and multiple followers. The leader is responsible for all reads and writes. If the leader fails, a controller broker (elected via ZooKeeper) assigns a new leader.

The controller election uses a simple ephemeral znode rather than the sequential-znode queue. Each broker that wants to be controller tries to create an ephemeral node at `/controller`. The first broker to create the node becomes the controller. If the controller broker crashes, the ephemeral node is deleted (after the ZooKeeper session timeout), and another broker can create the node and become the new controller.

### Lessons from Kafka

**Session timeout is critical**: Kafka's controller failover time is directly tied to the ZooKeeper session timeout. For example, a 6-second timeout means the cluster can have no controller for up to 6 seconds after the controller crashes (recent Kafka versions default to 18 seconds). KRaft mode, introduced in Kafka 2.8 as an early-access feature and production-ready from 3.3, removes this dependency, and Kafka 4.0 dropped ZooKeeper entirely.

**Watch the root, not the leaves**: Brokers watch the /controller znode, not individual partitions. When the controller changes, the new controller rebuilds the partition leadership assignments. This is more efficient than setting watches on every partition.

**Eliminating the external coordination service**: Kafka's move to KRaft (Raft-based consensus built into Kafka) shows that an external coordination service is sometimes an intermediate step. Mature systems can absorb that functionality into their core architecture, which removes a whole class of operational problems.

## Case Study 4: Leader Election in Kubernetes

Kubernetes stores all cluster state in etcd, but its control plane components (the scheduler and the controller manager) do not talk to etcd directly for leader election. They use the leader election library in `client-go`, which coordinates through a `Lease` object served by the API server (and therefore stored in etcd).

Each replica of a component tries to create or update the Lease. The current leader writes its identity into the Lease and renews the `renewTime` field periodically. Other replicas keep watching. A replica may take over only when the Lease has not been renewed for the lease duration, measured by that replica's own clock since it last saw the record change, so no cross-machine clock agreement is needed. Updates carry the object's `resourceVersion`, so etcd's compare-and-swap ensures that only one writer wins a contested update.

```go
// Kubernetes-style leader election with client-go (simplified)
lock := &resourcelock.LeaseLock{
    LeaseMeta:  metav1.ObjectMeta{Name: "my-component", Namespace: "kube-system"},
    Client:     clientset.CoordinationV1(),
    LockConfig: resourcelock.ResourceLockConfig{Identity: podName},
}
leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
    Lock:          lock,
    LeaseDuration: 15 * time.Second, // how long a non-leader waits before taking over
    RenewDeadline: 10 * time.Second, // the leader must renew within this time or step down
    RetryPeriod:   2 * time.Second,  // how often candidates and the leader retry
    Callbacks: leaderelection.LeaderCallbacks{
        OnStartedLeading: func(ctx context.Context) { run(ctx) },
        OnStoppedLeading: func() { os.Exit(1) }, // stop acting as leader immediately
    },
})
```

### Lessons from Kubernetes

**Leadership is just a small record**: A Lease holds an identity and a renewal time, which makes leadership easy to inspect and debug (`kubectl get lease -n kube-system`). The lock service is the API server plus etcd, and the component does not need its own coordination cluster.

**Timing parameters need a sensible relationship**: With the typical defaults, a crashed leader is replaced after up to about 15 seconds. The retry period (2 seconds) must be well below the renew deadline (10 seconds), which must be below the lease duration (15 seconds), so that a healthy leader has several chances to renew before anyone else may take over. Shortening the durations speeds up failover but raises the write load on the API server and makes false failovers more likely.

**Step down on doubt**: A leader that cannot renew in time exits (or stops all leader work) rather than continuing. This is a lease, not a fenced lock: a paused process can still wake up and act after its lease has passed to someone else. Kubernetes controllers are designed to be idempotent, and the API server's `resourceVersion` checks reject writes based on stale state, which plays the role of a fencing check for the objects they modify.

## Open Source Implementations

### Redisson

Redisson is a Java Redis client that provides a comprehensive distributed lock implementation. It supports Redlock, fair locks (FIFO ordering), read-write locks, and semaphores. Redisson handles the complexities of lock renewal, retry, and connection management automatically.

Redisson's lock implementation uses a "watchdog" for lease renewal. By default the lock is taken with a 30-second TTL, and while the client is alive the watchdog extends it (by default every 10 seconds) with a Lua script that first checks the lock is still owned by this client. If the client crashes, the renewals stop and the lock expires on its own. If you pass an explicit lease time to `lock()`, the watchdog is disabled and the lock simply expires after that time.

### Apache Curator

Apache Curator is a Java ZooKeeper client that provides a high-level API for distributed coordination. Curator's `InterProcessMutex` implements the ZooKeeper lock recipe. It supports reentrant locks, read-write locks, and semaphores.

Curator handles the watch setup, session management, and retry logic. It also provides a `LeaderSelector` for leader election that handles the complexity of ephemeral znode creation, session monitoring, and leader re-election.

### etcd Concurrency Package

etcd's Go `concurrency` package provides `sync.Mutex`-like distributed locks and an election API. The `Mutex` type uses etcd's lease and transaction mechanisms. The `Session` type manages lease lifecycle and heartbeat.

The package is small and used by `etcdctl lock` and `etcdctl elect` as well as by applications. (Kubernetes components use a different mechanism, Lease objects, as described above.) The API is straightforward: `NewSession` to create a lease, `NewMutex` to create a lock, `Lock` and `Unlock` for the critical section. If the session's lease is lost, the `Session.Done()` channel closes, which is the signal to stop working.

## Cloud Services

### AWS ElastiCache for Redis

AWS ElastiCache provides managed Redis clusters. For distributed locks, ElastiCache with cluster mode disabled (single shard, multiple replicas) provides the basic SETNX functionality. Cluster mode enabled supports partitioning across shards, but Redlock needs independent Redis deployments, so the shards or replicas of one ElastiCache cluster are not a substitute for five separate instances.

ElastiCache provides automatic failover with Multi-AZ enabled (it does not use Sentinel). The failover typically takes from tens of seconds to a couple of minutes, during which lock operations are unavailable. After failover, the new primary may not have all lock keys if they were not replicated.

### Azure Cache for Redis

Azure Cache for Redis provides managed Redis with data persistence and replication. The Premium tier supports Redis clustering. Azure's Redis implementation includes additional features like geo-replication across regions.

The key limitation for distributed locks is the same as all Redis-based approaches: asynchronous replication can lead to lock duplication on failover. Azure's active geo-replication reduces the replication lag but does not eliminate it. (Microsoft has announced Azure Managed Redis as the successor to this service, so check which offering applies to your deployment.)

### Google Cloud Memorystore

Google Cloud Memorystore provides managed Redis and Memcached. Memorystore for Redis supports Redis 7.0 features including ACLs and sharded pub/sub. The Standard tier provides replication with automatic failover in under 1 minute.

## Production Lessons

**Lesson 1**: Monitor lock hold duration. A spike in hold duration often precedes a crash. Set an alert when a lock is held for more than 80% of the TTL.

**Lesson 2**: Always set a TTL. A lock without a TTL is a memory leak waiting to happen. If the holder crashes, the lock is held forever. Every lock must have an expiration time.

**Lesson 3**: Test clock synchronization. Ensure all nodes in the lock service run NTP with the same time source. Monitor clock skew between nodes. A skew of more than 100ms can cause subtle lock failures.

**Lesson 4**: Use a dedicated lock service cluster. Sharing a ZooKeeper or etcd cluster between locks and other purposes (configuration storage, service discovery) increases the risk of lock starvation. A busy configuration change can delay lock operations.

**Lesson 5**: Plan for lock service unavailability. The lock service will go down eventually. Design the application to handle lock service unavailability gracefully: retry with backoff, queue operations locally, and alert on extended unavailability.

**Lesson 6**: Graceful shutdown matters. On application shutdown, the process must release all locks it holds. Install a shutdown hook that iterates through all held locks and releases them. This speeds up recovery for other processes.

## More Open Source Implementations

### Kazoo for Python

Kazoo is a pure-Python ZooKeeper client whose recipes include a lock built on the ephemeral sequential znode pattern. The lock is a context manager, and Kazoo handles the watch on the preceding znode for you.

```python
from kazoo.client import KazooClient

zk = KazooClient(hosts="zk1:2181,zk2:2181,zk3:2181")
zk.start()

lock = zk.Lock("/locks/batch-847", identifier="worker-7")
with lock:  # blocks until the lock is acquired
    process_batch(847)
```

The lock is only as safe as the session behind it. If the session expires, the ephemeral znode disappears and another client can take the lock, so long-running work should register a connection-state listener (`zk.add_listener`) and stop as soon as the connection is suspended or lost.

### Redis Locks in Python and Go

Libraries such as `redis-py` (its built-in `Lock` class), `python-redis-lock`, and `redsync` (a Go implementation of Redlock) wrap the `SET key value NX PX ttl` pattern with a safe unlock script that deletes the key only if it still holds the caller's random value. Some add automatic renewal. They give you mutual exclusion with the caveats discussed earlier (asynchronous replication, timing assumptions, no fencing token), which makes them a good fit for efficiency locks such as avoiding duplicate work, and a poor fit for correctness-critical ones.

### Hazelcast CP Subsystem

Hazelcast's CP Subsystem offers a Raft-based `FencedLock`. Its distinguishing feature is that acquiring it returns a fencing token, which is exactly the mechanism the protected resource needs.

```java
FencedLock lock = hazelcast.getCPSubsystem().getLock("batch-847");
long fence = lock.lockAndGetFence();  // monotonically increasing token
try {
    resource.write(data, fence);      // the resource rejects a stale fence
} finally {
    lock.unlock();
}
```

### Consul Sessions

Consul provides locks through sessions and its key-value store (`consul lock` on the command line, and the lock API in client libraries). A key can be acquired against a session, and the key is released when the session is invalidated or its TTL lapses. Consul's key-value entries carry a `ModifyIndex` that can be used as a version check.

## More Cloud Services

### Google Cloud Spanner Locks

Google Cloud Spanner provides built-in distributed locking at the database level. Spanner uses TrueTime, Google's clock API with bounded uncertainty, to give transactions globally meaningful commit timestamps. Read-only transactions and snapshot reads are lock-free, and read-write transactions use locks.

Spanner's read-write transactions take locks on the data they touch (two-phase locking). Transactions that span multiple Paxos groups commit with two-phase commit, coordinated by the participant groups. The key properties are:

- **Row-level locking**: Each row modification acquires a lock on that specific row. Multiple transactions can modify different rows concurrently.
- **Lock-free reads**: Spanner's reads do not acquire locks. Reads use TrueTime to read a consistent snapshot without blocking writers.
- **Deadlock avoidance**: Spanner uses wound-wait, in which an older transaction can abort ("wound") a younger one that holds a lock it needs, so cycles never form.
- **Automatic retry**: Transactions that Spanner aborts are retried by the client library's transaction runner, so application code should be safe to run more than once.

```sql
-- Spanner uses standard SQL transactions with implicit locking
BEGIN TRANSACTION;

-- This statement acquires a row-level lock on the account row
UPDATE accounts
SET balance = balance - 100
WHERE account_id = "acc_847"
  AND balance >= 100;

-- The lock is held until COMMIT or ROLLBACK
INSERT INTO transactions (id, account_id, amount, timestamp)
VALUES ("txn_901", "acc_847", -100, CURRENT_TIMESTAMP());

COMMIT;
```

Spanner is a distinctive cloud database that offers external consistency (its strongest consistency model) across regions, together with high availability through Paxos replication. Other systems, such as CockroachDB and YugabyteDB, offer strong consistency too, with different mechanisms and guarantees. The trade-off is cost and latency: cross-region synchronous replication adds write latency, and Spanner is typically more expensive than a conventional database for the same throughput. Locks taken inside a Spanner transaction are for keeping the database consistent, and they are not a general-purpose lock service for arbitrary external resources.

### AWS DynamoDB Conditional Writes

DynamoDB does not provide explicit locks, but its conditional write operations can be used to implement a locking mechanism. The pattern uses DynamoDB's conditional expression to atomically check and set a lock attribute.

```python
# DynamoDB-based distributed lock
import boto3
import time
import uuid

dynamodb = boto3.resource("dynamodb")
table = dynamodb.Table("distributed_locks")

def acquire_lock(lock_name, ttl_seconds=30):
    owner_id = str(uuid.uuid4())
    now = int(time.time())
    expiry = now + ttl_seconds
    
    try:
        # Conditional write: only succeeds if lock does not exist OR is expired
        table.put_item(
            Item={
                "lock_name": lock_name,
                "owner_id": owner_id,
                "expires_at": expiry
            },
            ConditionExpression=(
                "attribute_not_exists(lock_name) OR "
                "expires_at < :now"
            ),
            ExpressionAttributeValues={
                ":now": now
            }
        )
        return owner_id
    except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
        return None  # Lock is held by another process

def release_lock(lock_name, owner_id):
    # Conditional delete: only succeeds if we still own the lock
    try:
        table.delete_item(
            Key={"lock_name": lock_name},
            ConditionExpression="owner_id = :owner",
            ExpressionAttributeValues={":owner": owner_id}
        )
        return True
    except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
        return False  # Lock was taken by another process
```

The DynamoDB approach has limitations. The minimum granularity is one lock per item (DynamoDB item). There is no built-in fencing token mechanism. The lock relies on wall-clock time for expiry, which is vulnerable to clock drift. You can add a fencing token yourself with a version attribute that is incremented on each acquisition, and AWS Labs publishes a DynamoDB lock client library for Java that packages this pattern with heartbeats. For non-critical lock use cases within an AWS-only infrastructure, DynamoDB provides a low-overhead solution.

## Production War Stories

The scenarios below are composites, written to illustrate failure patterns that are widely reported in distributed systems practice. They are not accounts of any specific company's incident, and the numbers in them are illustrative.

### Scenario 1: Redis Failover Produces Duplicate Work

A team runs a Redis master with replicas for a job scheduler. Workers take a lock on the job on the master before processing it. The master crashes, and a replica that has not yet received the most recent lock writes is promoted. A second worker acquires the lock for a job that the first worker is still processing. Both workers finish, and downstream systems receive duplicate events.

The typical fixes come in layers:
1. Make the downstream work idempotent, with the job ID as a deduplication key. This is the fix that actually removes the risk.
2. Use Redis's `WAIT` command after lock writes to require acknowledgement from at least one replica. This narrows the window but does not close it.
3. Move critical coordination to a consensus-based service (ZooKeeper or etcd) and keep Redis locks for cache invalidation and other work where a rare duplicate is cheap.

### Scenario 2: Migrating from ZooKeeper to etcd

A platform team wants to move its coordination layer from ZooKeeper to etcd, for example to standardize on the same store its Kubernetes clusters already use. Migrations like this commonly run for months and go through phases like these:

1. **Shadow mode**: etcd is deployed alongside ZooKeeper, lock operations are sent to both, ZooKeeper's answer is authoritative, and etcd's answer is only logged for comparison. This phase tends to surface configuration problems such as disk sync settings.
2. **Dual-authority mode**: A lock is considered acquired only if both systems grant it, which lets services migrate one at a time.
3. **Primary mode**: etcd becomes the authority, and ZooKeeper remains as a fallback for a period.
4. **etcd only**: ZooKeeper is decommissioned.

Lessons that carry over to most such migrations:
- Log every disagreement between the two systems while running in parallel.
- Budget months, not weeks, and expect to touch every service that consumes locks.
- Migrate services independently, so that the migration does not depend on a single coordinated release.

### Scenario 3: Short Leases for Fast Failover

A service assigns each voice channel to one server using a Redis lock. The lock has a 10-second TTL and the holder renews it every second. If the holder crashes, renewals stop and the lock expires within the TTL, so a replacement can take over in at most 10 seconds. The one-second renewal interval does not make failure detection faster than the TTL. It only gives the holder about ten chances to renew before the lock lapses, which keeps a transient network blip from causing a false takeover. A shorter TTL (with a matching renewal interval) is what speeds up failover, at the price of more renewal traffic and more false failovers.

The pattern below shows a holder that renews in the background and exposes a flag it checks before every protected action.

```python
import threading

class LockLostError(Exception):
    pass

class RenewingLock:
    def __init__(self, lock, ttl_s):
        self.lock, self.ttl_s = lock, ttl_s
        self.lost = threading.Event()
        self._stop = threading.Event()
        threading.Thread(target=self._renew_loop, daemon=True).start()

    def _renew_loop(self):
        # Renew a few times per TTL; wait() returns True when stopped
        while not self._stop.wait(self.ttl_s / 10):
            try:
                if not self.lock.renew(self.ttl_s):
                    self.lost.set()
                    return
            except Exception:
                self.lost.set()  # cannot confirm the lock: assume it is lost
                return

    def check(self):
        """Call before every protected write."""
        if self.lost.is_set():
            raise LockLostError("lock lost, aborting")

    def release(self):
        self._stop.set()
        self.lock.release()
```

Because the lock expires on its own if the holder dies, the design is crash-only: the holder does not need to release cleanly for others to make progress.

## Lessons from Incident Patterns

### Pattern 1: The Renewal Thread That Silently Stops

A common incident pattern (reported in many postmortems in different forms) goes like this:
1. A bug or a resource problem causes the lock renewal background thread to stop after a network hiccup, and nothing notices.
2. The lock holder keeps working without the lock, believing it still holds it.
3. Another process finds the lock expired, acquires it, and starts working on the same resource.
4. Both processes write conflicting data to the storage layer.

Contributing factors are usually the same:
- The renewal thread had no health check, so no monitor noticed that it had died.
- Lock loss was communicated asynchronously (an event), and the holder did not check for it before each write.
- The storage layer accepted writes without verifying that they came from the current lock holder.

The fixes follow directly:
1. Monitor the renewal loop (for example, alert when a lock's last successful renewal is older than a threshold).
2. Make lock loss a flag that is checked before every write, as in `RenewingLock.check()` above, and abort immediately if it is set.
3. Have the storage layer verify a fencing token on every write and reject writes without a valid, current one.

### Pattern 2: Metadata Locks in Sharded Databases

Sharded databases coordinate metadata changes such as chunk migration and topology changes with some form of cluster-wide lock, and this pattern has produced real operational problems. In MongoDB's sharded clusters, for example, the balancer historically took a distributed lock stored on the config servers before migrating chunks, and chunk metadata carries a version that includes an epoch, so that stale routing information can be detected. The failure pattern is the general one: an operation outlives its lock, a second actor starts a conflicting change, and the system has to detect and repair inconsistent metadata. Recovery is faster when the operation is interruptible (it aborts and rolls back when it notices the lock is gone), when lock timeouts are set relative to the slowest realistic operation instead of the average one, and when writes carry a version or epoch that the storage layer can check. Check the documentation of your MongoDB version for how the balancer coordinates today, as this area has changed between releases.

## Migration Strategies

### Moving from Redis to ZooKeeper

Migrating from Redis-based locks to ZooKeeper locks is a common upgrade path as systems grow and safety requirements increase. The migration strategy must account for the behavioral differences between the two systems.

**Phase 1. Parallel deployment**: Deploy a ZooKeeper ensemble alongside the existing Redis lock infrastructure. Both systems receive all lock operations. Redis provides the response the application acts on; ZooKeeper responses are logged for analysis. This phase identifies discrepancies between the Redis lock state and the ZooKeeper lock state.

**Phase 2. Dual-authority mode**: The application checks both Redis and ZooKeeper before acting on a lock. The lock is considered acquired only if both systems grant it. This phase catches cases where Redis would have incorrectly granted a lock (false positive) or incorrectly denied one (false negative).

**Phase 3. ZooKeeper primary**: ZooKeeper becomes the authority. Redis can remain in place for non-critical locks, but lock state must not be read from a cache, since a stale "free" answer causes exactly the problem the migration is meant to fix. For non-critical locks, the system may fall back to Redis when ZooKeeper is unavailable, using a circuit breaker to limit how long the fallback lasts.

**Phase 4. ZooKeeper only**: Redis is removed from the lock path. The system now relies entirely on ZooKeeper for lock coordination.

Common pitfalls during this migration:
- **TTL mismatch**: Redis locks use TTL expiration. ZooKeeper locks use session expiration. The two mechanisms have different timing behaviors. Processes that rely on lock expiration timing (such as lease renewal) need adjustment.
- **Connection pooling**: Redis connection handling is different from ZooKeeper connection handling. ZooKeeper maintains persistent connections with session management. Redis typically uses connection pools. The client code must handle both patterns during the migration.
- **Performance regression**: ZooKeeper lock operations are 2-5x slower than Redis operations. The application must be load-tested with ZooKeeper before production deployment.

### Moving from ZooKeeper to etcd

Some organizations migrate from ZooKeeper to etcd for consistency of infrastructure (Kubernetes environments) or for operational simplicity. The migration has distinct challenges.

**Key differences between ZooKeeper and etcd locks**:

| Aspect | ZooKeeper | etcd |
|--------|-----------|------|
| Lock primitive | Ephemeral sequential znode | Lease + transaction |
| Session model | Long-lived session, heartbeat | Short-lived lease, periodic renewal |
| Watch mechanism | One-time watch, must re-register | Streaming watch, continuous |
| Data model | Hierarchical (znode tree) | Flat key-value with prefix support |
| Consensus protocol | Zab | Raft |

**Migration steps**:

1. **Lease mapping**: ZooKeeper's ephemeral znodes map to etcd leases. Each ephemeral znode becomes an etcd key created with a lease. The lease TTL matches the ZooKeeper session timeout.

2. **Sequence mapping**: ZooKeeper's sequential znode numbering maps to etcd's revision-based ordering. Creating keys under a common prefix and ordering waiters by create revision, as in the etcd lock recipe, provides equivalent ordering guarantees.

3. **Watch mapping**: ZooKeeper's one-time watches map to etcd's streaming watches. The client must be updated to handle the streaming watch model, where events continue to arrive after the first event.

4. **Namespace mapping**: ZooKeeper's hierarchical znodes (`/locks/resource/child`) map to etcd's key prefix model (`/locks/resource/` prefix with keys containing child identifiers).

```go
// etcd lock equivalent of ZooKeeper ephemeral sequential znode
// ZooKeeper pattern: create /locks/resource/lock- (ephemeral, sequential)
// etcd equivalent:
func acquireLock(client *v3.Client, lockPath string, leaseID v3.LeaseID) (string, error) {
    // Create a key with the lease attached: equivalent to ephemeral
    // The lease ensures the key is deleted if the holder crashes
    resp, err := client.Put(ctx, lockPath+"/lock-", "locked",
        v3.WithLease(leaseID),
        v3.WithSerializable(), // Ensure linearizable read
    )
    if err != nil {
        return "", err
    }
    // The created key's revision acts as the sequence number
    return fmt.Sprintf("%s/lock-%d", lockPath, resp.Header.Revision), nil
}
```

## Lock Patterns in Specific Domains

### Gaming Leaderboards

Real-time gaming leaderboards require distributed locks to ensure consistent score updates. The challenge is high write throughput combined with strong consistency requirements for ranking calculations.

One approach uses sharded Redis locks per score bucket. Each score range (0-999, 1000-1999, etc.) gets its own lock. When a player's score changes, the system acquires the lock for the player's current score bucket, updates the leaderboard, and releases the lock. Many leaderboards need no lock at all, because a Redis sorted set updates scores atomically (`ZADD`, `ZINCRBY`), so this pattern is mainly useful when an update must touch several data structures together.

```python
# Gaming leaderboard lock pattern
def update_score(player_id, delta_score, current_score):
    # Lock bucket: score range determines which lock to acquire
    bucket = (current_score // 1000) * 1000
    lock_key = f"leaderboard:lock:score_bucket_{bucket}"
    
    # Acquire lock on the score bucket
    owner = acquire_lock(lock_key, ttl=2000)  # 2 second TTL
    if not owner:
        return RETRY_LATER
    
    try:
        # Read current leaderboard for this bucket
        bucket_scores = redis.zrangebyscore(
            "leaderboard", bucket, bucket + 999, withscores=True
        )
        # Update score in sorted set
        redis.zincrby("leaderboard", delta_score, player_id)
        # Recalculate rank
        new_rank = redis.zrevrank("leaderboard", player_id)
        return new_rank
    finally:
        release_lock(lock_key, owner)
```

The key insight is that gaming leaderboards can tolerate brief lock contention because score updates are small operations. The lock granularity is at the bucket level, not the individual player level, reducing the total number of lock operations.

### Financial Exchanges

Financial exchanges require distributed locks with the strongest possible safety guarantees. A single lock failure in an exchange can result in financial loss, regulatory penalties, and reputational damage.

Trading systems are commonly built around a single-threaded sequencer or matching engine rather than general-purpose locks, since one component that orders all events removes the need for mutual exclusion. Where locks are used around it, systems in this space tend to want properties like the following:

- **Deterministic lock ordering**: All lock operations are ordered by a single sequencer (or a very precisely synchronized clock, such as hardware timestamping with GPS or PTP), so there is no ambiguity about which request came first.
- **Dual-lock pattern**: Critical operations require two independent lock services to grant the lock before proceeding. This protects against a single lock service granting a lock it should not have.
- **Audit trails**: Every lock acquisition, release, and failure is logged with high-precision timestamps. The audit trail is immutable and stored in a separate system from the lock service.

```python
# Financial exchange dual-lock pattern (conceptual)
def acquire_trading_lock(symbol, trader_id):
    # Both lock services must agree
    lock1 = acquire_zk_lock(f"/trading/locks/{symbol}", trader_id)
    lock2 = acquire_etcd_lock(f"/trading/locks/{symbol}", trader_id)
    
    if lock1 and lock2:
        # Both locks acquired: safe to proceed
        log_audit("LOCK_ACQUIRED", symbol, trader_id)
        return True
    else:
        # Release whichever was acquired
        if lock1: release_zk_lock(lock1)
        if lock2: release_etcd_lock(lock2)
        log_audit("LOCK_FAILED", symbol, trader_id)
        return False
```

The dual-lock pattern is an example of defense in depth: two independent services must both wrongly grant the lock before mutual exclusion is violated. The cost is availability, because if either service is down the lock cannot be granted, and it does not remove the need for fencing tokens against paused clients.

### IoT Device Coordination

IoT systems coordinate millions of devices through distributed lock services. The lock patterns for IoT differ from traditional server-side locking because devices have intermittent connectivity, low bandwidth, and limited power.

The coordinator lock pattern for IoT works as follows:

1. A device connects to the cloud and requests a lock for a specific operation (firmware update, data upload).
2. The lock service grants a lock with a long TTL (5-10 minutes) to account for device-to-cloud latency.
3. The device performs the operation and reports completion.
4. The lock service releases the lock.
5. If the device disconnects without releasing the lock, the TTL expires and the lock is released.

```python
# IoT device lock coordination
def coordinate_firmware_update(device_id, firmware_version):
    lock_key = f"iot:fw_update:{device_id}"
    
    # Long TTL for intermittent devices
    owner = acquire_lock(lock_key, ttl=300)  # 5 minute TTL
    if not owner:
        return DEVICE_BUSY
    
    try:
        # Send firmware URL to device
        send_command(device_id, "UPDATE_FIRMWARE", firmware_version)
        # Wait for device to report completion (up to 4 minutes)
        result = wait_for_completion(device_id, timeout=240)
        return result
    finally:
        release_lock(lock_key, owner)
```

IoT lock patterns must also handle device clock drift. Many IoT devices lack NTP synchronization and have hardware clocks that drift significantly. For this reason, IoT lock services use server-side timestamps exclusively and never rely on device-reported timestamps for lock expiry calculations.

## Benchmarking Methodology

Benchmarking a distributed lock service requires measuring multiple dimensions of performance and reliability. A single metric (such as average latency) does not capture the full picture.

### Metrics to Measure

**Latency percentiles**: Measure P50, P90, P99, and P99.9 lock acquisition latency under various load levels. P99.9 is the most important metric because lock timeouts are typically caused by tail latency spikes.

```bash
# Example benchmark setup with redis-benchmark
redis-benchmark -h lock-cluster.example.com -p 6379 \
  -n 100000 -c 50 \
  -r 1000 \
  SET lock:{rand:000-999} "owner-{rand}" NX PX 30000
```

**Throughput**: Maximum lock operations per second (acquisitions + releases) before saturation. The throughput ceiling is determined by the consensus protocol in ZooKeeper/etcd, or by the Redis single-threaded execution model.

**Contention ratio**: Percentage of lock acquisition attempts that fail because the lock is already held. A contention ratio above 30% indicates the lock granularity is too coarse.

**Lease renewal success rate**: Percentage of lease renewals that succeed. A renewal failure rate above 1% indicates the lease TTL is too short relative to network latency.

**Failover time**: Time from lock holder crash to lock release (TTL expiry or session timeout). Measured under controlled crash scenarios.

**False grant rate**: Percentage of lock grants where more than one process receives the same lock. This is the most important reliability metric. A non-zero false grant rate is acceptable only if the application has fencing tokens.

### Benchmarking Scenarios

| Scenario | Configuration | What to Measure |
|----------|--------------|-----------------|
| Low contention | 10 workers, 1000 lock keys | P50/P99 latency |
| High contention | 100 workers, 1 lock key | Contention ratio, throughput |
| Burst load | 50 workers, all start simultaneously | Thundering herd behavior |
| Network partition | Isolate lock service leader node | Failover time, false grants |
| Clock skew | Introduce 500ms NTP offset | Lease expiry behavior |
| Process crash | Kill a lock holder process | Recovery time, lock release |

### Sample Benchmarking Code

```python
import time
import statistics
import threading
from concurrent.futures import ThreadPoolExecutor

def benchmark_lock_throughput(num_workers, num_locks, runtime_seconds):
    """
    Benchmark lock throughput with N workers contending for M locks.
    """
    results = []
    lock = threading.Lock()
    stop_event = threading.Event()
    
    def worker(worker_id):
        local_ops = 0
        while not stop_event.is_set():
            lock_name = f"lock:{worker_id % num_locks}"
            owner = f"worker-{worker_id}"
            
            start = time.monotonic()
            acquired = redis_lock_acquire(lock_name, owner, ttl=5000)
            latency = time.monotonic() - start
            
            if acquired:
                redis_lock_release(lock_name, owner)
                local_ops += 1
                
            with lock:
                results.append({
                    "latency_ms": latency * 1000,
                    "acquired": acquired
                })
        return local_ops
    
    with ThreadPoolExecutor(max_workers=num_workers) as executor:
        futures = [executor.submit(worker, i) for i in range(num_workers)]
        time.sleep(runtime_seconds)
        stop_event.set()
    
    # Analyze results
    latencies = [r["latency_ms"] for r in results if r["acquired"]]
    contention = 100 * (1 - len(latencies) / len(results))
    
    return {
        "total_ops": len(results),
        "acquisitions": len(latencies),
        "contention_ratio": contention,
        "p50_latency_ms": statistics.median(latencies),
        "p99_latency_ms": sorted(latencies)[int(len(latencies) * 0.99)]
    }
```

### Interpreting Results

When benchmarking a lock service, compare the results against the operational requirements:

- Lock acquisition latency below 5ms for Redis, below 20ms for ZooKeeper/etcd at P50, with P99 below 3x P50.
- Throughput above 5,000 ops/sec for a single ZooKeeper/etcd cluster, above 50,000 ops/sec for a single Redis instance.
- Contention ratio below 20% for healthy lock granularity. Above 50% indicates the critical section is too long or locks are too coarse.
- False grant rate of zero for consensus-based systems. For Redis, the false grant rate depends on replication configuration and should be measured under partition scenarios.

Benchmarking must be performed in an environment that mirrors production conditions. A development environment with no network latency, no clock skew, and no competing load will produce optimistic results that do not reflect production behavior.
