## Case Study 1: A Shared-Storage Split Brain (Composite)

This case study describes a failure pattern that has affected many organizations. It is an illustrative composite, not an account of any single company's incident. An active-passive pair of servers shares an NFS volume that holds the application's data. A network problem makes the standby believe the active server is dead, so it takes over and mounts the volume read-write while the original server, still alive, keeps writing to it. Two writers modify the same files without coordination, and the data is corrupted. Repair takes hours of restoring from backups and reconciling records by hand. The diagram below illustrates the pattern; treat its labels and figures as illustrative rather than as a report of a real incident (for a real, well-documented one, see the GitHub incident described under Key Lessons).

### Key Lessons

**A shared mount is not a lock.** NFS is a network file protocol. It provides no built-in fencing or lease mechanism for the active-passive pattern. Multiple clients can mount the same share read-write, and the filesystem itself does nothing to stop two of them from writing conflicting data.

**Shared storage does not prevent split brain.** A common assumption is that putting the data on one shared volume removes split brain because there is only one copy. In reality the shared volume simply becomes the place where two writers collide, and it can corrupt files that no replication protocol could have reconciled.

**Fence before takeover.** The standby must not mount the volume read-write until the original server is confirmed to be unable to write (powered off, disconnected from storage, or blocked with storage-level reservations). Fencing is what turns "the active seems dead" into "the active is dead".

**Recovery procedures need testing at production scale.** Recovery from this kind of incident typically means choosing an authoritative copy, restoring from backup, and reconciling records by hand. Runbooks that delete or overwrite data must be tested against realistic volumes and must check what they are deleting.

**A real-world reference:** In October 2018, GitHub described a network partition of about 43 seconds between its US East Coast network hub and its primary East Coast data center. Its automated MySQL failover tooling promoted primaries in a different region while the original primaries still held recent writes that had not replicated. When connectivity returned, the two sides had diverged. GitHub chose to preserve data integrity over speed, so it degraded service for just over 24 hours while it restored from backups and reconciled the diverged writes. Its public post-incident report is worth reading in full: it shows how automated failover, cross-region topology, and asynchronous replication interact.

## Case Study 2: MongoDB Replica Set Split Brain

MongoDB replica sets use a Raft-like election protocol, so there is at most one primary per term, but an old primary can briefly keep accepting writes after a partition until it notices it has lost its majority. Writes acknowledged with w:1 by that old primary can be rolled back when the partition heals. Jepsen's analyses of MongoDB found several versions where such writes were lost, which is why write concern and read concern settings matter.

### MongoDB Safety Recommendations

```
1. Keep electionTimeoutMillis at its default (10,000ms) unless
   you have measured a reason to change it.
   Lower values fail over faster but cause more elections on
   short network blips. Higher values lengthen the window
   before a dead primary is replaced.

2. Always use an odd number of voting members.
   3 members is the minimum for production.
   Prefer a data-bearing member over an arbiter when you need
   an extra vote, since arbiters weaken durability guarantees.

3. Use priority=0 for members that should never be primary,
   and priorities to prefer a primary in a particular location.

4. Use writeConcern: majority for critical writes.
   This ensures writes are acknowledged by a majority and
   survive failover. Writes with w:1 can be rolled back after
   a failover.

5. Test failover behavior with network fault injection.
   Verify that a partitioned primary steps down, that rollbacks
   are handled, and that clients retry safely.
```

## Case Study 3: Cassandra and Virtual Nodes

Cassandra uses a peer-to-peer architecture that eliminates leader-based split brain. It has no leader to split, but during a partition both sides can accept writes for the same keys, and hinted handoff, timestamps and repair decide what survives afterwards.

### Cassandra Safety Recommendations

```
1. Use consistent clocks (NTP with tight bounds).
   Cassandra relies on timestamps for conflict resolution.
   200ms clock skew can cause incorrect last-writer-wins.

2. Use QUORUM or LOCAL_QUORUM for both reads and writes on
   critical data so that read and write sets overlap, and run
   regular anti-entropy repair (nodetool repair).
   Read repair happens automatically on reads at higher
   consistency levels.

3. Use LOCAL_QUORUM for local writes and reads.
   Avoid QUORUM (cross-datacenter) for latency-sensitive ops.
   LOCAL_QUORUM limits voting to the local datacenter.

4. Run repair within gc_grace_seconds (10 days by default).
   Tombstones are removed after gc_grace_seconds, and a replica
   that missed a delete and was not repaired in time can bring
   the deleted data back after a partition heals.

5. Know the hint window (max_hint_window, 3 hours by default).
   Hints are stored only for that long. After a longer outage,
   the node must be repaired instead of relying on hints.
```

## Case Study 4: Elasticsearch Split Brain

Elasticsearch versions before 7.0 were vulnerable to split brain when `discovery.zen.minimum_master_nodes` was not set to a majority of the master-eligible nodes. Version 7.0 replaced that mechanism with a new cluster coordination layer that manages voting configurations automatically, which removed most of that risk.

### Elasticsearch Recovery

```
Elasticsearch recovery from split brain:
1. Identify which cluster has the most recent data
2. Shut down all nodes in the other cluster
3. Restart the shut-down nodes one at a time
4. Each restarting node joins the surviving cluster
5. Translog replay catches up with committed writes
6. Uncommitted writes on shut-down nodes are lost

Recovery time: 5-30 minutes for a 5-node cluster
Data loss: Any write that was committed on the minority
           side during split brain is permanently lost.
```

## Open Source Tools

### Pacemaker / Corosync

Pacemaker is the standard cluster resource manager for Linux high-availability deployments. It uses Corosync for cluster membership and messaging.

```
Pacemaker split brain prevention:
- Corosync provides cluster membership and quorum
- Pacemaker manages fencing (STONITH) configuration
- Fencing topology: multiple fencing methods in sequence
- Resources are started only on quorate nodes

STONITH configuration example (illustration only: keep real credentials in a secret store):
  pcs stonith create ipmi-node1 fence_ipmilan \
    pcmk_host_list=node1 \
    ipaddr=192.168.1.101 \
    login=admin \
    passwd=secret \
    op monitor interval=60s

Quorum policy options:
  stop:        Stop all resources if quorum lost (default)
  freeze:      Keep running but don't start new resources
  suicide:     Fence self if quorum lost
  ignore:      Continue without quorum (dangerous)

Recommended policy: stop (safety first)
```

### ZooKeeper and etcd

ZooKeeper and etcd are consensus services that provide the foundation for split brain prevention in many distributed systems.

```
ZooKeeper:
- Uses Zab (ZooKeeper Atomic Broadcast) protocol
- Majority quorum required for leader election
- 3 servers minimum for production
- 5 servers for fault tolerance
- Fencing tokens via zxid (ZooKeeper transaction ID)
- zxid monotonically increases with each operation

etcd:
- Uses Raft consensus protocol
- Majority quorum for leader election
- Lease-based leadership with configurable TTL
- Cluster reconfiguration requires majority consent
- Fencing tokens via key revisions or lease IDs (the Raft term is internal to etcd)

Both provide:
- Reliable leader election
- Fencing token generation
- Configuration storage
- Cluster membership tracking
```

## Cloud Provider Solutions

### AWS Multi-AZ

AWS provides Multi-AZ deployments for RDS, ElastiCache, and other managed services. These deployments span multiple Availability Zones (AZs) within a region.

```
AWS RDS Multi-AZ:
- Synchronous replication to standby in different AZ
- Automatic failover with a DNS update (typically one to two minutes)
- AWS manages fencing and infrastructure isolation for you
- Single writer; in the standard Multi-AZ instance deployment the standby cannot serve reads (Multi-AZ clusters add readable standbys)

AWS ElastiCache for Redis (Cluster Mode):
- Automatic failover with replica promotion
- Quorum-based detection (consensus via majority nodes)
- Multi-AZ auto-failover available (and required for cluster mode)
- Node replacement automated by AWS

AWS benefits:
- AZs are physically isolated, reducing overlap risk
- AWS control plane handles fencing
- Separate management network is standard
- Automated recovery reduces operator error
```

### Azure Availability Zones

Azure provides Availability Zones that correspond to physically separate datacenters within a region.

```
Azure SQL Database:
- Built-in high availability, with failover and split brain handling managed by the service
- Microsoft manages failover internally
- Little customer configuration required
- Availability SLA of up to 99.995% in zone-redundant configurations

Azure Virtual Machines with Availability Zones:
- Customer-managed clustering
- Azure Load Balancer handles health probes
- Availability Sets protect against rack-level failures
- Managed disks support shared storage fencing

Azure Kubernetes Service (AKS):
- etcd managed by Azure control plane
- Node auto-repair detects and replaces unhealthy nodes
- Pod Disruption Budgets prevent simultaneous node removal
- Zone-redundant storage handles data plane availability
```

## Lessons Learned

### Common Patterns Across Incidents

1. **Configuration is a very common root cause.** Many split brain incidents involve a configuration error: wrong quorum size, incorrect timeout, missing STONITH configuration, or inconsistent settings across nodes.

2. **Testing is essential.** Organizations that test split brain scenarios regularly recover faster and with less data loss. Organizations that consider split brain "too rare to test" are the most affected when it happens.

3. **Monitoring must detect split brain specifically.** Generic "node down" alerts are not sufficient. Dedicated split brain detection with fencing token tracking and quorum health monitoring is necessary.

4. **Manual recovery is slow and error-prone.** Split brain recovery should be automated to the maximum extent possible. Manual steps introduce delay and risk of incorrect action.

5. **Every layer needs protection.** Application-level idempotency, database-level quorum, infrastructure-level fencing. Relying on a single protection layer is insufficient.
