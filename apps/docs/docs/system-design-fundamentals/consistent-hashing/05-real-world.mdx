## Company Case Studies

### Case Study 1: Discord: From MongoDB to Cassandra to ScyllaDB

Discord started with a single MongoDB replica set for message storage. As the platform grew, MongoDB could not keep the data and indexes in memory, and the team moved message storage to Cassandra around 2016 to 2017, as described in Discord's engineering blog. Cassandra distributes data using a consistent hash ring with virtual nodes.

Discord partitions messages by `(channel_id, bucket)`, where the bucket is a window of time, so that a channel's recent history sits in one partition and no partition grows without bound. Cassandra hashes that partition key onto the ring and places it on the nodes that own that token range. Because placement depends only on the ring, adding a node moves a small share of the data and the rest of the cluster carries on.

As the cluster grew to hundreds of nodes, Discord found operations harder: garbage-collection pauses, compaction, and hot partitions made latency unpredictable. In 2022 it began migrating message storage to ScyllaDB, a Cassandra-compatible database written in C++, and reported that the same data needed far fewer nodes. Its later blog post describes putting a Rust data service in front of the database that coalesces identical concurrent requests, which protects the ring from hot keys that consistent hashing alone cannot spread.

**The lesson**: Consistent hashing gives you cheap scaling, but it does not fix uneven access. You still need a good partition key and protection for hot keys.

**Public references**: Discord Engineering Blog, "How Discord Stores Billions of Messages" (2017) and "How Discord Stores Trillions of Messages" (2023).

### Case Study 2: Netflix: EVCache, Consistent Hashing Inside a Global Cache

Netflix's caching layer is EVCache, a distributed in-memory store built on Memcached with a Java client library. Netflix's engineering blog describes how data is replicated across availability zones and regions, so that each zone holds a full copy of the cached data and reads can be served from the local zone.

Within a zone, the client library spreads keys across the Memcached nodes with consistent hashing, so adding or removing a node moves only a fraction of the keys. Service discovery tells each client which nodes currently exist.

A useful operational point from running caches like this: when nodes in one cluster have different sizes, giving every node the same number of virtual nodes leaves the larger nodes underused, so virtual nodes should be weighted by capacity. Another is warm-up: a new node joins with an empty cache, so cache-heavy systems either pre-load new nodes from their neighbors or accept a short burst of extra misses.

**Public reference**: Netflix Tech Blog, "Caching for a Global Netflix" (2016).

### Case Study 3: Cloudflare: A Load Balancer Built on the Same Idea

Cloudflare's Unimog, a layer 4 load balancer that runs on every server in its data centers, needs to spread connections across many servers, change which servers take traffic as they get busy or are drained, and keep existing connections on the server they started on. Cloudflare's engineering blog describes the design, which is closely related to consistent hashing and to Google's Maglev load balancer.

Connections are hashed into a fixed number of buckets. A table maps each bucket to a server, and changing the table moves only the buckets that need to move, so most connections are unaffected when a server is added or removed. This keeps disruption low for long-lived TCP connections: if a server change caused most connections to land on a different server, clients would see resets and reconnect storms at the origin.

**The lesson**: The value of consistent hashing is not just balanced data placement. Any place where a mapping from keys to servers must stay stable while the server set changes benefits from it, including load balancers.

**Public reference**: Cloudflare Blog, "Unimog: Cloudflare's edge load balancer" (2020).

### Case Study 4: Uber: Ringpop for Sharded Service Communication

Uber built Ringpop, an open-source library that gives a cluster of application servers a shared consistent hash ring. Ringpop uses the SWIM gossip protocol for failure detection and membership, combined with a consistent hash ring for request routing.

Each service instance joins the ring, and Ringpop keeps every member's view of the ring up to date. A request for a given key can arrive at any instance, and that instance can compute which instance owns the key and forward the request there. The ring uses a number of replica points per member (100 in the reference implementation) to smooth the distribution.

SWIM detects failures without a central coordinator. Members periodically ping each other. If a ping fails, the member asks a few other members to probe the suspect indirectly before declaring it dead, and a suspicion period lets a slow but healthy member refute the accusation. This reduces false positives from transient network problems.

The lesson from Ringpop: consistent hashing is not just for data storage. Any pool of interchangeable service instances that needs key-affine routing (the same key always goes to the same instance, for caching or in-memory state) can use a ring with minimal rebalancing.

**Public reference**: Uber Engineering Blog, "Ringpop" (2015) and the Ringpop project documentation.

### Case Study 5: Amazon Dynamo and DynamoDB

The 2007 Dynamo paper is the origin of many production uses of consistent hashing. Its design has these key pieces:

- **Consistent hashing with virtual nodes**: Each key is hashed onto a ring, and each physical node owns many virtual positions.
- **A preference list**: A key is stored on the N nodes that follow its position on the ring (N is typically 3), skipping positions that belong to the same physical node.
- **Sloppy quorum and hinted handoff**: If a target replica is down, another node accepts the write and hands it back when the replica recovers.
- **Gossip membership and anti-entropy**: Nodes learn about the ring through gossip, and Merkle trees let replicas find and repair differences efficiently.

Cassandra and Riak took direct inspiration from this design. The managed DynamoDB service that AWS runs today is a different system, built on the same goals but with a different architecture. Its 2022 paper describes tables split into partitions by hashing the partition key. Partitions split as they grow, and each partition is replicated across three availability zones using a leader-based protocol.

**Public references**: "Dynamo: Amazon's Highly Available Key-value Store" (SOSP 2007); "Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service" (USENIX ATC 2022).

## Open Source Implementations

### Cassandra

Cassandra uses a consistent hash ring with virtual nodes (vnodes) as its core data distribution mechanism. Each Cassandra node owns a range of the ring. The ring is modified through the gossip protocol, which propagates topology changes across the cluster.

**Trade-off**: Cassandra historically used 256 virtual nodes per physical node by default. That gives good distribution but makes operations such as repair and streaming more expensive, so Cassandra 4.0 moved the default to 16 tokens per node and added a smarter token allocation algorithm to keep the load balanced with fewer tokens.

**Best for**: Write-heavy workloads requiring linear scalability across commodity hardware.

### Riak

Riak uses a consistent hash ring divided into a fixed number of partitions (64 by default, always a power of 2), which are shared among the nodes. Riak's implementation is notable for its use of hinted handoff: when a write target node is unavailable, another node temporarily accepts the write and forwards it when the target recovers.

**Trade-off**: Riak's fixed partition count keeps ownership simple: adding a node hands it a share of the existing partitions (about 1/N of the data), and no key is re-hashed. The catch is that the partition count is a design decision made at cluster creation, and it caps how far the cluster can grow (newer versions can resize the ring online, at some cost).

**Best for**: Systems requiring read-repair and hinted handoff for maximum write availability.

### ScyllaDB

ScyllaDB is a C++ rewrite of Cassandra that maintains API compatibility. Across nodes it uses the same token ring idea as Cassandra. Inside each node it also splits the data across CPU cores in a shard-per-core design, and its drivers are shard-aware, so a request can go straight to the right core on the right node.

**Trade-off**: The shard-per-core design eliminates cross-core coordination within a node, and users and vendor benchmarks often report several times more throughput per node than Cassandra. The cost is a different operational model, and it is less flexible when a workload does not spread evenly across cores.

**Best for**: High-throughput workloads where Cassandra's JVM garbage collection pauses cause latency spikes.

## Cloud Provider Implementations

### AWS: Amazon ElastiCache

Amazon ElastiCache for Redis supports cluster mode, which distributes keys across shards using the same idea as consistent hashing in a slot-based form: 16,384 fixed hash slots (standard Redis Cluster) rather than virtual nodes on a ring. Each shard owns a range of hash slots.

**Cost**: ElastiCache cluster mode charges per shard. A 10-shard cluster costs 10x the base node price. Consistent hashing is built in; no additional implementation cost.

**Ops**: AWS manages the ring topology. Adding a shard triggers an automatic rebalancing of hash slots. The rebalance runs in the background with configurable slot migration concurrency.

**Trade-off**: No fine-grained control over virtual node count or hash function. AWS uses Redis's built-in CRC16 hash over hash slots; no alternative hash function is available.

### GCP: Memorystore

Google Cloud Memorystore for Redis uses the same hash slot approach as AWS ElastiCache. Memorystore supports automatic rebalancing when nodes are added or removed.

**Cost**: Similar to ElastiCache: per-shard pricing. GCP offers committed-use discounts for 1-year and 3-year terms.

**Trade-off**: GCP does not support weighted nodes in the consistent hash ring. Every node in a Memorystore cluster gets the same number of hash slots, making heterogeneous clusters impractical.

### Azure: Azure Cache for Redis

Azure Cache for Redis Enterprise uses Redis Enterprise's clustering technology, which includes consistent hashing with proxy-based routing. Azure's implementation uses a proxy layer that abstracts the ring topology from clients.

**Cost**: Azure charges a premium for Enterprise tier, which includes the proxy-based consistent hashing. The Premium tier uses Redis Cluster's standard hash slot scheme at a lower price point.

**Trade-off**: The proxy layer adds a small amount of latency per request (typically well under a millisecond to about a millisecond). For very latency-sensitive workloads, measure whether that overhead matters.

## Lessons Learned

**Lesson 1**: Test the hash function before production. A non-uniform hash function creates hot spots that no amount of virtual nodes can fix. For any hash function, hash 1 million random keys into 1,000 buckets and compare the spread with what pure chance predicts: each bucket should hold about 1,000 keys with a standard deviation near the square root of that (about 32, or 3 percent). A much larger spread means the hash is biased.

**Lesson 2**: Pre-warm new nodes before topology propagation. Adding a cold node to the ring causes a cache-miss cascade. Stream keys from neighbors before updating the topology.

**Lesson 3**: Version the ring topology. Systems with many routers or clients (multi-datacenter deployments, migrations that run two systems in parallel) rely on topology versioning to prevent inconsistent routing. A version counter in the ring metadata is cheap insurance.

**Lesson 4**: Weight virtual nodes by node capacity. Heterogeneous clusters cannot achieve balanced load with equal vNode counts, so switch to capacity-weighted vNode counts. The rule: `vNodes = base_count * (node_capacity / avg_capacity)`.

**Lesson 5**: Plan for cascading failures. SWIM-based failure detection, as in Ringpop, includes indirect probes and a "suspicion" phase before declaring a node dead. This reduces false positives during network jitter compared with declaring a node dead after a single missed ping.
