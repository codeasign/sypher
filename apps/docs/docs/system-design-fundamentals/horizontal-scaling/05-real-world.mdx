# Horizontal Scaling in Production

## Company Case Studies

### Netflix: Stateless Microservices at 300 Million Subscribers

Netflix operates one of the largest horizontally scaled systems in the world, serving over 300 million subscribers in more than 190 countries. Its video is delivered from its own content delivery network, and its control plane (browsing, playback authorization, recommendations) handles enormous volumes of API requests.

**The challenge**: Netflix's original architecture was a monolithic application backed by a relational database in its own data center. After a major database corruption incident in 2008 halted DVD shipments, Netflix decided it could not rely on a single vertically scaled stack. It moved to AWS and split the monolith into many independently deployable services.

**The solution**: Netflix built a stateless microservice architecture on AWS. Each microservice is horizontally scaled behind a load balancer. Netflix open-sourced several of the components that made this work:

- **Eureka** (service discovery): Every service registers itself on startup and deregisters on shutdown, and clients look up healthy instances from the registry. Eureka is itself replicated across availability zones.
- **Zuul** (API gateway): Routes requests to the appropriate backend service and handles cross-cutting concerns like authentication and routing at the edge. Zuul runs in an auto-scaling group behind a load balancer.
- **Hystrix** (circuit breaker): Service-to-service calls went through Hystrix, which provided circuit breakers, thread pool isolation, and fallbacks to prevent cascading failures. Hystrix has three states (CLOSED, OPEN, HALF-OPEN) and tracks failures in a rolling window (10 seconds by default). Netflix put it into maintenance mode in 2018 in favor of adaptive concurrency limits, and resilience4j is the usual replacement in new Java projects, but the pattern it popularized is unchanged.
- **Scryer** (predictive auto-scaling): A forecasting engine that predicts demand from historical patterns and provisions instances before the demand arrives, avoiding the several-minute lag of purely reactive scaling.

### Uber: Sharded Storage for Trip Data

Uber handles tens of millions of trips per day, and each trip generates writes to many tables: the trip request, driver assignment, location updates, payment records, and rider feedback. (The figures in the diagram below are illustrative.)

**The challenge**: Uber started with a monolithic application and a single PostgreSQL database. As it grew across many cities, one primary could not keep up with the write rate, and schema changes on a huge shared database were slow and risky.

**The solution**: In 2014 Uber built **Schemaless**, an append-only, sharded key-value datastore layered on MySQL. Later it built **Docstore**, a general-purpose distributed database, also on MySQL. Some of the key ideas were:

- **Sharding by entity**: Rows are assigned to shards by a key such as the trip ID, so a request for one trip goes to one shard, and adding capacity means adding shards.
- **Append-only cells**: Schemaless stores immutable versions of each record, which keeps writes cheap and makes replication and recovery simpler.
- **Ringpop** (consistent hashing): Uber's open-source Ringpop library implements consistent hashing for application-layer sharding of service work. It uses a SWIM gossip protocol for membership detection and failure discovery. When a node fails, only the keys it owned (about 1/N of the total) move to the remaining nodes.

### Discord: Horizontally Scaled Real-Time Services

Discord serves well over 150 million monthly active users, with millions of people connected at the same time and billions of messages sent per day.

**The challenge**: Discord has two very different scaling problems: keeping millions of long-lived connections open and fanning out events to them in real time, and storing an ever-growing history of messages.

**The solution**: Discord scaled each layer differently:

- **Elixir/Erlang real-time gateway**: The connection layer runs on the Erlang VM, which is built for huge numbers of lightweight processes. Each server (guild) is handled by a process, and guilds are spread across many nodes, so capacity grows by adding nodes.
- **Message storage on Cassandra, later ScyllaDB**: Messages are partitioned by channel and time bucket, and the cluster grows by adding nodes. Discord moved from Cassandra to ScyllaDB to reduce operational pain at large scale.
- **Rust data services with request coalescing**: A service between the API and the database merges identical concurrent queries, so a burst of requests for the same hot data becomes one database query. This protects the database from hot partitions, the same problem as the cache stampede described earlier.

### Cloudflare: Global Load Balancing at Edge Scale

Cloudflare operates a global network in more than 330 cities that handles tens of millions of HTTP requests per second and serves a large share of all websites.

**The challenge**: Every request must reach a healthy edge data center within milliseconds, and the network has to survive the failure of entire data centers.

**The solution**: Anycast routing. Cloudflare announces the same IP addresses from all its data centers. BGP directs each user's traffic to a nearby data center, and if a data center fails, its route is withdrawn and traffic shifts to the next closest one, typically within about a minute. There is no DNS TTL to wait out. Inside each data center, a layer 4 load balancer called Unimog spreads connections across the many servers there.

## Open Source Implementations

### Cassandra

Apache Cassandra is natively horizontally scalable. It distributes data across nodes using consistent hashing on a ring. Each node owns a range of hash tokens. Data is replicated to N nodes (replication factor, typically 3). Reads can be served by any replica.

**Trade-offs:**
- Highly available by design (AP-leaning): with a low consistency level such as ONE, any node can accept writes even during network partitions
- Read consistency is tunable: ONE (read from one replica, may be stale), QUORUM (read from majority), ALL (read from all replicas)
- Operations-heavy: repair, compaction, and node replacement require experienced operators

### CockroachDB

CockroachDB is a horizontally scalable SQL database that provides ACID transactions across nodes. It uses the Raft consensus algorithm for replication and a distributed key-value store underneath the SQL layer.

**Trade-offs:**
- Strong consistency at the cost of write latency (Raft requires majority acknowledgment)
- SQL compatibility means existing applications can be migrated with minimal changes
- Higher write latency than Cassandra at low consistency levels, because every write needs a majority of replicas to acknowledge it

### Kubernetes

Kubernetes is the de facto standard for deploying horizontally scaled applications. Its core abstraction (the ReplicaSet) ensures N copies of a pod are running. The Horizontal Pod Autoscaler (HPA) adjusts replica counts based on CPU, memory, or custom metrics.

**Trade-offs:**
- Pod startup time: container image pull and initialization takes 10-60 seconds (not suitable for sub-minute traffic spikes)
- Cluster autoscaling (adding nodes to the cluster) takes 2-5 minutes
- StatefulSets for stateful applications require careful design (PersistentVolumeClaims are not auto-migrated)

## Lessons Learned

1. **Stateless is the foundation of horizontal scaling.** Companies that scaled horizontally with success, Netflix among them, invested heavily in making services stateless. Session data goes to Redis. File uploads go to S3. Local disk is empty. If your service writes to local disk, it cannot scale horizontally without complex shared storage.

2. **Horizontal scaling exposes every hidden serial dependency.** A database query that took 2ms under light load takes 200ms under high load because of queueing. A synchronous API call that chained 3 services added negligible latency at 100 RPS. At 10,000 RPS, it adds seconds. Measure and remove serial dependencies before they become bottlenecks at scale.

3. **Circuit breakers are not optional.** Large-scale operators such as Netflix built their resilience tooling because cascading failures kept happening. Adding a circuit breaker, timeout, and fallback to each dependency call takes a few hours per service, which is dwarfed by the cost of a single major outage.

4. **Auto-scaling is a lagging indicator.** By the time CPU crosses a threshold, traffic has already been high for minutes. Predictive and scheduled scaling are essential for traffic patterns with known peaks. Retailers typically pre-scale capacity for known events such as Prime Day or Black Friday rather than relying on reactive auto-scaling alone.

5. **Cross-region writes are the hardest problem in distributed systems.** Conflict resolution, replication lag monitoring, and failover testing remain hard even for the largest companies. The simplest approach (active-passive with a single write region) is the most reliable choice for most use cases.
