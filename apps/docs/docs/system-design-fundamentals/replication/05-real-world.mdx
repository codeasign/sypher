# Replication in Production

The theory of replication is well-understood. The practice is where reality diverges from the textbook. This page examines how major engineering organizations use replication in production, the incidents that shaped their architectures, and the open-source and cloud tools that implement replication at scale.

## Company Case Studies

### Netflix: Multi-Region Cassandra

Netflix runs Cassandra as a core operational database, replicated across multiple AWS regions. Its replication strategy is leaderless with tunable consistency, and it is one of the best-documented examples of active-active replication in production.

**The architecture:** Each region runs its own Cassandra cluster, and every piece of data has a replication factor of 3 within each region. Applications typically read and write at `LOCAL_QUORUM`, which needs 2 of the 3 local replicas and never waits on another region. The coordinator sends each write to the other regions asynchronously, so a remote region sees it after the cross-region delay.

**Why it was built this way:** Netflix moved away from a single relational database in its own data center after a major database corruption incident in 2008. On AWS, it designed for the failure of an entire availability zone, and later of an entire region. Netflix's engineering blog described how its multi-zone Cassandra design let it ride through the April 2011 AWS US-East outage far better than many other AWS customers. The lesson is that a single-region primary is a single point of failure, regardless of how many replicas you have inside that region.

**In operation:** Netflix runs Chaos Monkey to kill instances in production, and Chaos Kong-style exercises to evacuate an entire region. The data layer survives node failures transparently because every partition lives on three nodes in every region. Read repair, hinted handoff, and anti-entropy repair clean up the inconsistencies that asynchronous replication leaves behind.

**Public reference:** The Netflix Tech Blog has several posts on running Cassandra across regions and on lessons from the 2011 AWS outage.

### Uber: From PostgreSQL to MySQL and Schemaless

Uber's replication story is a good example of how the details of a replication format can decide a database choice.

**The architecture:** Uber's early storage was a single PostgreSQL database. In 2014 it built **Schemaless**, an append-only sharded datastore layered on MySQL, and later moved to a general-purpose system called **Docstore**, also based on MySQL. Each shard is a MySQL primary with replicas. Writes go to the shard's primary, and reads can go to replicas.

**The replication challenge:** In a 2016 engineering blog post, Uber described why it moved its main relational workload from PostgreSQL to MySQL. PostgreSQL's physical (WAL-based) replication streams changes to disk pages, so a small logical update that touches many indexes produces a lot of WAL. Across data centers, that meant a lot of replication bandwidth. Uber also described replicas that had trouble keeping up with long-running queries because of how MVCC conflicts interact with replay, and difficulties with upgrades between versions. MySQL's row-based logical replication was more compact and easier to work with for its needs.

**Lesson:** Replication is not just a switch you turn on. The format of the replication log (physical or logical), how replicas apply it, and how it behaves across versions all affect bandwidth, lag, and operational cost at scale.

**Public reference:** Uber Engineering Blog, "Why Uber Engineering Switched from Postgres to MySQL" (2016) and "Designing Schemaless, Uber Engineering's Scalable Datastore Using MySQL" (2016).

### Cascading Replication: An Illustrative Chat-Platform Topology

Large real-time platforms that run PostgreSQL often use **cascading replication** to keep replication load off the primary. The topology in the diagram below is an illustrative example of this technique, not a description of any specific company's production system.

**The architecture:** Each database shard is a PostgreSQL primary with several replicas. Instead of every replica streaming WAL directly from the primary, first-level (L1) replicas stream from the primary, and second-level (L2) replicas stream from the L1 replicas. That reduces the WAL bandwidth the primary has to send.

**The replication challenge:** Real-time products need very fresh reads. If a user sees a message on one device but not on another, replication lag is the likely cause. A common practice is to monitor lag per replica and to stop routing reads to any replica whose lag exceeds a threshold (for example 2 seconds), falling back to another replica or to the primary.

**The failure mode to plan for:** Cascading adds a dependency. If an L1 replica cannot keep up with replaying writes and forwarding WAL to L2 replicas at the same time, the whole subtree falls behind. The usual fixes are to add more L1 replicas, size their memory and I/O generously, and keep the cascade shallow.

### GitHub: A Failover That Went Wrong (October 2018)

GitHub's October 2018 incident is one of the best-documented replication failures. It shows how automated failover can turn a very short network problem into a day-long incident.

**The architecture:** GitHub ran MySQL with a primary in one US data center and replicas in another, managed by an automated failover tool (Orchestrator). Replication between data centers was asynchronous.

**What happened:** On October 21, 2018, routine maintenance briefly severed connectivity between the two data centers for about 43 seconds. During that window Orchestrator promoted new primaries in the other data center. When connectivity returned, the original data center held a small number of writes that had never been replicated, and the new primaries held writes of their own. The two sides had diverged.

**The impact:** Because the data sets had diverged, GitHub could not simply fail back. It took its data stores out of service to reconcile them, and the service ran in a degraded state for more than 24 hours. GitHub's post-incident analysis describes the timeline and what changed afterward.

**Lessons:** Asynchronous cross-region replication means a failover can lose or fork writes. Failover automation needs to account for short partitions, not only real failures. Recovery from divergence is slow and manual, so it is worth preventing.

**Public reference:** GitHub Engineering, "October 21 post-incident analysis" (2018).

### Cloudflare: Replicated Storage for Durable Objects

Cloudflare's Durable Objects provide strongly consistent storage close to where users are, and they show replication used for durability rather than for read scaling.

**The architecture:** Each Durable Object is a single-threaded instance that processes requests one at a time and owns its own storage. All requests for that object are routed to one location, so there is no need for replicas to serve reads. Storage writes are replicated to other machines in nearby data centers, and Cloudflare has described waiting for a quorum of those copies before the write is considered durable.

**The replication challenge:** Replication delays grow with distance, so the copies are kept within a region rather than spread worldwide. Waiting for a nearby quorum keeps the added write latency to a few milliseconds, and the single-location design provides strong consistency for reads.

**Public reference:** Cloudflare Blog posts on Durable Objects and on the storage engine behind them.

### Dropbox: Multi-Leader Sync with Conflicted Copies

Dropbox's sync model behaves like multi-leader replication where every user device is a leader for its own changes and the server mediates.

**The architecture:** Changes can originate from any device (phone, laptop, desktop, web). File contents are stored server-side as content-addressed blocks in Dropbox's own storage system, Magic Pocket, and file metadata is tracked separately. When two devices modify the same file at the same time, Dropbox keeps both versions and creates a "conflicted copy" (`filename (Conflicted Copy).ext`) instead of silently choosing a winner.

**The replication challenge:** The replicas here are user devices, not servers. Devices go offline for days or weeks, and the system must reconcile divergent state when they return. Detecting that two edits were concurrent, rather than one after the other, is the core problem that version vectors and similar techniques solve in multi-leader systems.

**Public reference:** Dropbox Engineering Blog posts on Magic Pocket and on the Nucleus sync engine.

## Open Source Implementations

### PostgreSQL Streaming Replication

PostgreSQL's built-in streaming replication is the most widely deployed open-source replication system. It uses a single-leader, WAL-based architecture.

**Strengths:** Simple basic setup (`wal_level = replica`, a replication user, and a `standby.signal` file on the replica; older versions used `recovery.conf`). Synchronous and asynchronous modes. Cascading replication. Hot standby (replicas serve read queries).

**Weaknesses:** No built-in automatic failover (requires Patroni or repmgr). WAL replay on a replica is done by a single process (recent versions add prefetching to speed it up, but not parallel apply). No multi-master support (BDR is a separate extension).

### MySQL Group Replication

MySQL's Group Replication provides multi-leader replication with built-in conflict detection, using a Paxos-based group communication system.

**Strengths:** Automatic failover. Multi-leader with conflict detection. Built into MySQL 8.0+. No external coordinator needed.

**Weaknesses:** Performance degrades under write contention (conflict detection adds overhead). Group size limited to 9 nodes. Network partition can cause the entire group to stop (if quorum is lost).

### Cassandra

Apache Cassandra implements leaderless replication with a Dynamo-style architecture. Each node accepts reads and writes. Data is partitioned across nodes using consistent hashing, and each partition is replicated to N nodes (replication factor).

**Strengths:** Linear scalability. No single point of failure. Tunable consistency (per-query W and R settings). Multi-datacenter support built in. Hinted handoff for temporarily unavailable nodes.

**Weaknesses:** Eventual consistency by default. No SQL joins, foreign keys, or transactions. Higher operational complexity. Read repair and anti-entropy operations consume significant CPU.

## Lessons Learned

1. **Failover is the most dangerous operation you will perform.** Many of the worst replication incidents happen during or right after a failover. GitHub's October 2018 incident began with a 43-second network partition, triggered an automated failover to another data center, and took more than 24 hours to fully recover because writes existed only on one side. Test failover in staging regularly, not once a year, and include short partitions in your tests.

2. **Replication lag is never zero under load.** Claiming "our replicas are always caught up" is false for any system under sustained write load. Measure your lag in production. Build your application to tolerate at least 10 seconds of lag. If you cannot, accept the latency cost of synchronous replication.

3. **Monitor the replica apply rate, not just the lag.** Lag tells you how far behind a replica is, but apply rate tells you whether the replica is keeping up with the write rate. If the primary writes at 10,000 entries/second and the replica applies at 9,500 entries/second, lag will grow indefinitely, just slowly.

4. **Cascading replication saves primary bandwidth but adds latency risk.** Each cascade level adds a little more lag (usually milliseconds, more under load). More than 2 levels of cascade are risky, because an intermediate replica becomes a bottleneck for everything below it.

5. **You need a plan for WAL growth that does not involve the on-call engineer at 3 AM.** Set WAL retention limits. Alert on WAL disk usage at 60% and again at 80%. Have an automated script that drops the oldest replication slots if disk crosses 90%.
