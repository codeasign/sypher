The trade-offs page laid out the theory. This page examines how four major technology companies apply stateless and stateful design in their production systems, what broke, and what they learned.

## Netflix: Stateless Compute, Stateful Data Layer

Netflix operates one of the largest stateless compute fleets in the world. Its engineering blog describes a design in which any instance of a service can handle any request, so instances can be added, removed, or killed at any time. (The figures in the diagram below are illustrative.)

### The Stateless API Layer

Netflix's edge and API services run as hundreds of microservices on AWS. The service instances are stateless. Cached and session-like data live in **EVCache**, Netflix's distributed caching layer built on Memcached, and durable data lives in stores such as Cassandra. User identity, viewing history, and playback state are all read from those external stores rather than held in an instance.

**Why stateless:** Netflix deploys many times per day. Stateless instances allow canary releases and quick rollbacks, because a new version can be brought up next to the old one, traffic shifted gradually, and shifted back if metrics degrade. No session state is pinned to a specific instance.

**How it scales:** Viewing follows a daily rhythm, with the peak in the evening. The fleet scales up and down with that pattern, and Netflix uses predictive scaling in addition to reactive rules. Each new instance registers with service discovery and starts handling requests. EVCache is partitioned across many nodes and replicated within and across regions.

**Key learning:** Netflix's Chaos Monkey deliberately kills instances in production to verify that the system survives. Because instances hold no state, killing one causes no data loss. The team treats instance death as normal, not exceptional.

### Precomputed Recommendations Served from Memory

Much of Netflix's personalization is computed offline in batch jobs, and the results are stored in caches and datastores so that the request path only has to look them up. This is state kept close to the compute, for speed.

**Trade-off:** The cache tier is harder to operate than the stateless API layer. Warm-up, invalidation, and replication all need care. But the latency gain is large: an in-memory lookup takes around a millisecond, while running model inference on every request would take many times longer.

## Uber: Stateless Rides, Stateful Dispatch

Uber's ride-matching system is a carefully balanced mix of stateless and stateful design. (The details in the diagram below are simplified illustrations.)

### The Stateless Request Layer

The ride request API is stateless. Every request contains the information needed: pickup location, destination, rider ID. The service validates the request and hands it to the stateful matching system. If an API instance crashes mid-request, the rider retries and the retry lands on any healthy instance.

**Why stateless:** Ride requests arrive in unpredictable bursts (rain, events, rush hour). Stateless API instances can be auto-scaled aggressively, with no session pinning during the critical few seconds between request and driver assignment.

### The Stateful Dispatch and Location Layer

Uber's dispatch system needs a live view of which drivers are available where. Uber has described keeping that supply and demand state in memory, sharded by geography, on a cluster of servers whose membership is managed by its open-source **Ringpop** library (consistent hashing plus SWIM gossip). Requests for a given area are routed to the server that owns that shard.

**Why stateful:** Driver locations change constantly. At one update every 2 seconds, 10,000 active drivers in one city generate about 5,000 location writes per second. Sending every update through a general-purpose database and reading it back to match riders would add latency and load for data that is only useful for seconds. Holding it in memory next to the matching logic is much faster.

**How failure is handled:** Because the location data is short-lived, the system can rebuild it quickly. Drivers keep sending fresh updates, so a server that takes over a shard has an accurate view again within seconds. Long-lived data such as trips and payments is written to durable, replicated stores.

## Discord: Stateful for Real-Time, Stateless for REST

Discord runs one of the largest real-time communication systems in the world, with millions of users connected at once. Its engineering blog describes very different designs for its real-time and request/response paths. (The figures in the diagram below are illustrative.)

### The Stateful Real-Time Layers

Voice is stateful by nature. A voice server holds the live state of each channel it hosts: who is connected, the media streams, and the encryption keys. Audio has to be relayed within a tight latency budget of tens of milliseconds, so a database round trip per packet would make the call unusable.

**How state is managed:** When a user joins a voice channel, Discord assigns them to a voice server. The voice server keeps this state in the memory of its processes. A voice server does not replicate its live call state to a backup. If a server crashes, clients reconnect and a new session is set up on another server.

**Why no replication:** Voice state is ephemeral. When a call ends, the state has no value. The cost of replicating live audio state continuously outweighs the benefit of slightly faster reconnection.

Discord's text real-time gateway is stateful too. Its Elixir gateway keeps each guild's state in a process, and connections are routed to it. That state is rebuilt from durable storage if a node is lost.

### The Stateless REST API

Discord's REST API for sending messages, managing guilds, and fetching history is stateless. Every request goes through a load balancer to any available API server. The API server reads from and writes to durable stores (Cassandra, later ScyllaDB, for messages).

**Why stateless:** API traffic is spiky. A community can grow by hundreds of thousands of members within hours. Stateless API servers can be provisioned and registered in minutes.

## Cloudflare: Stateless Edge, Stateful Workers

Cloudflare operates a global edge network where every request is stateless at the proxy layer but Workers (serverless functions) can be stateful.

### The Stateless CDN

Cloudflare's core CDN is the definition of stateless. A request for `image.png` arrives at any of Cloudflare's 330+ data centers. The edge server checks its local cache. If present, it serves the cached copy. If not, it fetches from the origin, caches it locally, and serves it. The edge server retains nothing about the request after the response is sent.

### Stateful Workers with Durable Objects

Cloudflare Workers can opt into stateful behavior via Durable Objects. A Durable Object is a single-instance stateful entity: all requests for a given object ID are routed to one instance, which processes them one at a time and has its own transactional, strongly consistent storage.

**Use case:** Real-time collaboration features (WebSocket connections, shared counters, multiplayer game state). The Durable Object holds the authoritative state for one room or document. All operations on that state go through the single instance, which is what gives strong consistency without distributed locking.

**Trade-off:** A Durable Object lives in one location, so users far from it pay the extra network latency. Anything held only in the object's memory is lost if the object is evicted or its host fails, so state that matters must be written to Durable Object storage, which is durable but slower than memory.

## Open Source Implementations

### Apache Kafka: Stateful Message Broker

Kafka is a stateful system. Each broker holds a subset of partitions in local log files. The partition leader handles writes for that partition (and, by default, reads). State (the log) is persisted to disk and replicated to followers.

**Trade-off:** Kafka's design, an append-only log on local disks with sequential I/O and heavy use of the OS page cache, is a large part of why it reaches very high throughput. In exchange, scaling Kafka requires careful partition management, rebalancing, and broker coordination.

### Redis: Stateful Cache

Redis is a stateful key-value store. All data lives in memory on a single node (or partitioned across a cluster). Writes are acknowledged when the data is in memory; persistence (AOF or RDB) is asynchronous by default.

**Why stateful:** Every Redis operation is a memory access, achieving sub-millisecond latency on the server. A cache that had to fetch from a remote store on every operation would lose that advantage.

### ZooKeeper: Stateful Coordination Service

ZooKeeper is a strongly consistent stateful service for cluster coordination. It maintains the cluster state tree in memory on every node, synchronized via ZAB (ZooKeeper Atomic Broadcast) consensus.

**Why stateful:** Coordination requires strongly consistent reads and writes. A stateless coordination service would need to fetch state from a remote database for every read, adding latency and failure risk exactly when a cluster is under stress.

## Cloud Provider Implementations

### AWS

**Stateless options:** AWS Lambda (stateless function execution), Fargate (stateless container orchestration), ELB with target groups (stateless load balancing).

**Stateful options:** ElastiCache (managed Redis/Memcached), DynamoDB Accelerator (DAX, in-memory cache), ElastiCache for Redis with replication across AZs.

**Cost trade-off:** Lambda is billed per invocation and is inherently stateless. RDS Proxy maintains a stateful connection pool so that Lambda functions can share database connections without overwhelming the database. The proxy adds a per-vCPU hourly charge, but it lets thousands of concurrent function invocations share a small pool of database connections.

### GCP

**Stateless options:** Cloud Run (stateless container execution), HTTP(S) Load Balancer (stateless request distribution), Cloud Functions.

**Stateful options:** Memorystore (managed Redis), Firestore (document DB with strong consistency), Bigtable (stateful wide-column store).

### Azure

**Stateless options:** Azure Functions, Azure Container Apps, Azure Front Door (stateless CDN).

**Stateful options:** Azure Cache for Redis, Cosmos DB with consistency levels ranging from strong to eventual.

## Lessons Learned

1. **Stateless is simpler at scale, not at startup.** For the first 1,000 users, local session state on a single server is easier and faster than setting up Redis. Migrate to stateless when you add a second server or when deployment frequency increases.

2. **The best architecture is a hybrid.** Every major company uses both stateless and stateful services. The trick is knowing which part of your system needs which. Latency-sensitive and coordination-heavy components are stateful. Everything else is stateless.

3. **Stateful failover is the hardest distributed systems problem.** Netflix can kill instances randomly because they are stateless. Voice platforms such as Discord's accept that a server crash drops active calls and rely on clients reconnecting. If your stateful service must survive failures without data loss, you need consensus, replication, and careful testing.

4. **Externalizing state does not eliminate state management.** Moving session state from server memory to Redis does not remove the state; it moves it. You now operate a Redis cluster with its own failure modes, capacity planning, and operational needs.

5. **Idempotency is the superpower of stateless systems.** The ability to retry any request without side effects makes stateless architectures resilient. Invest in idempotency keys and retry logic: they pay for themselves in reduced incident severity.
