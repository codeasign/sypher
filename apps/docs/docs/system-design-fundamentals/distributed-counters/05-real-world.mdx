## Company Case Studies

Four production designs show how counters are handled at scale. They are drawn from public engineering write-ups, and the diagrams below use illustrative figures.

### Netflix: A Counter Abstraction

Netflix has described a general-purpose "Distributed Counter Abstraction" in its engineering blog (2024). It exists because many teams need counters (how many times something was watched, how many experiments ran) and each needs a different trade-off between accuracy, latency, and cost. (The figures in the diagram below are illustrative.)

**Architecture**: The abstraction offers more than one counting mode:

- **Best-effort regional counters**: Increments go to a fast in-memory store (EVCache, Netflix's Memcached-based cache) within a region. They are cheap and low-latency, and they can under- or over-count, because an increment can be lost or a retry can be applied twice. They suit uses such as metrics and A/B test exposure counts, where an approximate number is enough.
- **Eventually consistent global counters**: Each increment is written as an event to a durable time-series store, and background processes roll the events up into a running total. Because the events are durable and each carries an identifier, retries are safe and the total converges to an accurate value, at the cost of a delay before the total is up to date.

**Trade-off**: The design makes the accuracy-versus-latency choice explicit. Cheap counters are fast but approximate, and accurate counters are built on an event log and are slightly delayed. Teams pick the mode that matches their need.

**Public reference**: Netflix Tech Blog, "Netflix's Distributed Counter Abstraction" (2024).

### Facebook TAO: Counts Stored with the Data

Facebook's TAO, the graph store described in its 2013 paper, keeps counts of associations (for example, the number of likes on a post or comments on an object) as a first-class operation. Rather than counting rows on every read, TAO maintains the count alongside the association list.

**Architecture**: Data is sharded by object ID, and the associations of an object live on the same shard as the object. Because the count and the list are stored together, adding an association updates the list and the count in one operation on one shard, so there is no cross-shard coordination and no read-modify-write race across machines. A large cache tier in front of the database serves the counts and absorbs read traffic, and invalidations keep the caches fresh.

**Trade-off**: Keeping the count next to the data makes reads cheap and writes simple, but all updates to one object's count go through one shard, so very popular objects concentrate load on it. Caching and read replicas help with reads, and write hot spots remain a concern.

**Public reference**: "TAO: Facebook's Distributed Data Store for the Social Graph" (USENIX ATC 2013).

### Metrics Pipelines: The Two-Layer Counter in Practice

The two-layer design (a local buffer plus a global aggregator) is the standard shape of metrics systems. A StatsD-style agent, for example, keeps counters in memory on each host and flushes the accumulated totals to a central service on an interval (10 seconds by default). Instead of sending one network message per event, each host sends one message per interval per counter. (The details in the diagram below are an illustrative example of this design.)

**Architecture**: Each application server buffers increments locally and flushes them in batches to a shared aggregator, such as a Redis cluster or a metrics backend. The batch size and interval control how much Redis write load is saved: a server that handles 500 increments per flush interval sends one command instead of 500.

**Trade-off**: Data loss on application server crash. Each server's unflushed buffer is lost if the server dies. That is acceptable when the counter is a real-time estimate and the system of record (a trip database, billing events, logs) persists the underlying events separately.

### Cloudflare: The Rate Limit Counter

Cloudflare's rate limiting counts requests per client to decide when to return HTTP 429. Its engineering blog describes a design that deliberately avoids a single global counter. (The exact figures depend on the product version, so check the blog for current details.)

**Architecture**: Counting happens locally in each data center. Requests are counted in fixed time windows in an in-memory store (Cloudflare described Memcached behind a Twemproxy layer that spreads keys across servers by consistent hashing). To avoid the sharp edges of fixed windows, the rate is approximated from the current and previous window counts: the previous window's count is weighted by how much of it still overlaps the sliding window, and the current window's count is added.

**Why local counting works**: A globally consistent counter would need cross-datacenter coordination on every request, adding tens to hundreds of milliseconds. Traffic from one client tends to arrive at the same nearby data center anyway, so per-location counters are accurate enough for the purpose. The cost is that a client spreading requests across many data centers can briefly exceed the nominal limit.

**Trade-off**: Approximate counting and a small overshoot in exchange for very low latency and no cross-datacenter dependency. For rate limiting, where the goal is to stop abuse and not to enforce an exact number, that is the right trade.

**Public reference**: Cloudflare Blog, "How we built rate limiting capable of scaling to millions of domains" (2017).

## Open Source Implementations

Three open-source systems implement distributed counters with different trade-offs.

### Redis (with Redis Cluster)

**How it works**: Redis `INCR` and `INCRBY` commands provide atomic single-node counters. Redis Cluster adds automatic sharding across nodes using 16,384 hash slots (a close relative of consistent hashing). Replication is asynchronous.

**Strengths**: Sub-millisecond latency; atomic INCR on the hot path; cluster mode scales to hundreds of nodes (about 1,000 is the practical maximum); AOF persistence provides crash recovery within the fsync window.

**Weaknesses**: Single-threaded per shard (hot key bottleneck); no native CRDT support (split-brain requires manual recovery); memory-bound (all counters in RAM).

**Best for**: High-throughput counters where the cost of RAM is acceptable and hot keys are rare.

### Cassandra

**How it works**: Cassandra's `COUNTER` column type stores per-replica contributions and merges them to produce the total. A counter update is applied on a replica (which reads the current value before writing) and then replicated to the others.

**Strengths**: Built-in counter type with tunable consistency (ONE, QUORUM, ALL for both reads and writes); replicated across nodes and datacenters; no single point of contention per counter.

**Weaknesses**: Counter updates are not idempotent: if a write times out, you cannot know whether it was applied, so a retry can double-count and skipping the retry can lose the increment. Counter writes are slower than ordinary writes because of the read-before-write. Counter tables have restrictions (for example, they cannot be mixed with regular columns and do not support TTL). Write throughput per counter is lower than a single Redis INCR.

**Best for**: Multi-datacenter deployments where counters must survive node and rack failures.

### Riak (with Riak DT)

**How it works**: Riak's data types module implements PN-Counters as part of its CRDT library. Each value is stored with its full vector clock. Reads trigger read repair: if a read encounters a replica with a stale vector clock, it automatically repairs the replica.

**Strengths**: Automatic read repair; configurable replication factor N, read quorum R, write quorum W; counters survive partitions with automatic merge.

**Weaknesses**: Riak's development and ownership have changed hands over the years, so check the project's current status before adopting it; vector clock metadata grows large for counters with many concurrent writers; read-heavy workloads require careful tuning.

**Best for**: Systems that need CRDT counters with automatic read repair and are already running Riak.

## Cloud Provider Implementations

Managed cloud services that implement distributed counter primitives.

### AWS DynamoDB

**Feature**: DynamoDB `UpdateItem` with `ADD` operation on a Number attribute provides atomic increment. The increment is applied server-side by the DynamoDB service.

**Cost/ops trade-off**: Each write consumes 1 write capacity unit (or write request unit) per 1 KB of item size. A counter item is typically under 200 bytes, so one increment costs one unit. In on-demand mode, writes cost roughly $0.6 to $1.25 per million (the price was cut in late 2024, and it varies by Region), so 100 million increments per day cost on the order of $60 to $125 per day. Check the current price list for exact numbers.

**Strengths**: Managed. No server to operate; auto-scaling; DAX (DynamoDB Accelerator) for sub-millisecond reads; Global Tables for multi-region replication.

**Weaknesses**: A single partition is limited to about 1,000 write units per second, which is roughly 1,000 increments per second on one hot counter item. Adaptive capacity helps with uneven load across partitions, but it cannot split a single hot item, so a hot counter should be sharded across several items. Cost at scale is higher than self-managed Redis.

### Google Cloud Firestore

**Feature**: Firestore's `FieldValue.increment()` applies an atomic server-side increment to a numeric field, so concurrent clients do not overwrite each other.

**Strengths**: Managed; strong consistency; integrates with Cloud Functions for event-driven processing. Google documents a "distributed counter" pattern that spreads a counter over many shard documents and sums them on read.

**Weaknesses**: Firestore recommends sustaining only about one write per second to any single document (short bursts are tolerated), so a single document is a poor fit for a counter that receives frequent increments. That is exactly why the sharded-counter pattern exists.

### Azure Cache for Redis

**Feature**: Azure's managed Redis offerings provide `INCR` semantics like open-source Redis. (Microsoft is transitioning customers to Azure Managed Redis, so check which offering applies.)

**Cost/ops trade-off**: Throughput depends on the tier and size. To go beyond one node's throughput, use a clustered tier so that counters are sharded across nodes, and size the number of shards for your peak increments per second. Look up current pricing for the tier you choose.

**Strengths**: Compatible with open-source Redis commands; geo-replication across regions. The enterprise-grade tiers offer active geo-replication built on CRDTs, in which counters merge their increments from different regions instead of overwriting each other.

## Lessons Learned

Five key lessons from production distributed counter implementations.

**Lesson 1: Accept loss on the write path, reconcile on the batch path.** Every cheap, eventually-consistent distributed counter can lose or double-count some increments. The production pattern is not to eliminate loss entirely: that requires consensus on every write, which caps throughput. Instead, build a separate batch reconciliation pipeline that computes authoritative totals from the event log and corrects the counter.

**Lesson 2: The hot key problem is the ceiling on throughput.** Even with 1,000 shards, a single viral post or a single popular emoji can overwhelm one shard. Pre-sharding at the application layer (splitting one logical counter into many sub-counters and summing them on read) is the reliable mitigation. Auto-scaling shards does not help: the hot key is a single point of serial execution.

**Lesson 3: Idempotency keys are not optional.** Every production incident where counters overcount traced back to missing or expired idempotency keys. Budget the idempotency TTL generously (at least 5x the maximum expected retry window). Monitor idempotency hit rates: a sudden increase means clients are experiencing timeouts.

**Lesson 4: Always have a second source of truth.** The distributed counter is a real-time estimate. The authoritative value comes from replaying the event log offline. Rate limiting counters are the exception (no second source of truth is needed for an ephemeral rate limit). For like counters, impression counters, trip counters, the event log is the truth, and the distributed counter is a cached projection.

**Lesson 5: Monitor staleness, not just throughput.** The most common failure mode is not "counter is down" but "counter is wrong." Monitor p99 staleness (not just p50), and alert when staleness exceeds twice the target SLA. A hot key event can leave p50 staleness at a few milliseconds while p999 climbs to seconds, and that gap goes unnoticed if you monitor only the median.
