# Vertical Scaling in Production

Real systems rarely stay purely vertical or purely horizontal. Atlassian sized up its PostgreSQL instances and then partitioned tenants across many of them. Discord outgrew a single MongoDB replica set and moved to distributed stores. Cloudflare builds very capable individual servers and still runs many of them. Uber split one database by the characteristics of the data. These stories show when vertical scaling works, where it breaks, and how to plan the migration. The company sections describe the general shape of each story from their public engineering write-ups, and specific figures are illustrative unless stated.

## Company Case Studies

### Atlassian: Vertical First, Then Splitting by Tenant (Jira Cloud)

Atlassian runs Jira Cloud on PostgreSQL. Their public engineering write-ups describe a pattern that fits this lesson well: each database instance was sized up as tenants grew, and once single instances stopped being the economical answer, tenants were spread across many databases instead of one giant one. (The exact instance sizes and customer counts in the diagram below are illustrative, not published figures.)

**What they did**: Atlassian kept relational transactions at the center of the product. ACID guarantees made application code simpler, and rewriting core transaction logic to work across shards would have carried risk and cost. So they invested in:

- Managed PostgreSQL with replication to a standby in another availability zone
- Per-tenant limits to prevent noisy-neighbor problems
- Regular vacuum and index maintenance to prevent bloat
- Query optimization and targeted indexing to reduce working set size

**Where a single instance stops working**: Once one database serves a huge tenant base, a few things arrive together. CPU stays high at peak. All writes funnel through one WAL. The working set outgrows RAM, so cache misses turn into disk reads. Upgrading the instance class buys time, but each step costs more per unit of capacity.

**The transition**: Rather than one global database, Atlassian partitions by tenant. A tenant's data lives in one database, and many databases share the load. Because a tenant never spans databases, transactions stay local and simple. Total cost is higher (more instances), but no single instance is a ceiling for the whole product.

**Lesson**: Vertical scaling bought Atlassian a long runway, and tenant-based partitioning removed the ceiling once it was needed. When your data has a natural partition key like a customer or tenant, the eventual move to horizontal scaling is far easier.

### Discord: From a Single MongoDB Replica Set to Cassandra and ScyllaDB (2015-2023)

Discord started with a single MongoDB replica set for message storage, as described in their engineering blog posts "How Discord Stores Billions of Messages" (2017) and its 2023 follow-up on trillions of messages.

**What they did**: Discord launched on MongoDB because it was quick to build with. As message volume grew, the data and indexes no longer fit in memory. Reads for old messages turned into random disk reads, latency became unpredictable, and the team could see that a single replica set would not keep up. Adding RAM or a bigger machine would only delay the problem.

**The vertical scaling ceiling**: A chat history is append-only, so the total data only grows. Once the working set (the messages people actually scroll back to) is larger than the memory of the biggest practical machine, more hardware cannot restore cache hit rates. The database had to become distributed.

**The transition**: Discord moved message storage to Apache Cassandra, partitioning messages by channel and time bucket so one channel's recent history sits together. Years later, after hot partitions and garbage-collection pauses became a maintenance burden at a scale of hundreds of nodes, they migrated again to ScyllaDB, which needed far fewer nodes for the same data.

**Lesson**: Discord hit the vertical scaling ceiling because their data was append-only and unbounded. Any system with unbounded storage growth will eventually exceed the largest machine. There is no vertical scaling solution for unbounded data; only data retention limits or horizontal partitioning can solve it. The second lesson is that the choice of partition key (channel plus time bucket) mattered as much as the choice of database.

### Cloudflare: Big Nodes, Many of Them

Cloudflare serves tens of millions of HTTP requests per second across data centers in hundreds of cities. Its engineering blog shows an architecture that pairs high-end individual servers with wide horizontal spread.

**What they do**: Each data center (PoP) contains many servers, and every server runs the same software stack. A layer 4 load balancer called Unimog spreads incoming connections across the servers in a PoP based on their current load. Adding capacity means adding another server, and losing a server just shifts its traffic to the others.

**Why big nodes still matter**: Cloudflare designs its own server generations around modern many-core CPUs, and much of its performance work targets making one machine do more: efficient kernel networking paths, careful cache and NUMA use, and per-core tuning. Vertical efficiency lowers the number of servers they need. It does not replace having many.

**Where it breaks**: No single server can absorb a PoP's traffic, and no single PoP can serve the world. Capacity comes from horizontal scaling at two levels: many servers per PoP and many PoPs.

**Lesson**: Cloudflare is not a case of "vertical scaling at massive scale". It is the hybrid that most large systems end up with: make each node as capable as you economically can, and scale out across nodes and locations for capacity and fault tolerance.

### Uber: Splitting One Database by Data Characteristics (2014-2016)

Uber began with a monolithic application backed by a single PostgreSQL database. As Uber expanded to many cities, the monolith and its database became a scaling and reliability constraint.

**What they did**: One database held trip, driver, and payment data, so every workload competed for the same machine. Analytical queries and live trip writes fought over the same resources.

**The transition**: Uber broke the monolith into services and gave the heavy data stores purpose-built homes. For trip data it built Schemaless, an append-only, sharded datastore layered on MySQL, and it used Cassandra for some other workloads. In 2016 it published why it moved its main relational workload from PostgreSQL to MySQL, citing write amplification and replication behavior at its scale. Smaller, bounded datasets stayed on single relational instances.

**Lesson**: Uber's migration shows that vertical scaling is not binary: you can vertically scale some services while horizontally scaling others. Trip history needed unbounded storage (horizontal). Small relational data with transactional requirements did not (vertical). Different data characteristics call for different scaling strategies. (The per-service table in the diagram below is a simplified illustration of that idea, not Uber's exact inventory.)

## Open Source Implementations

### PostgreSQL

PostgreSQL on a single large node is the most well-documented vertical scaling pattern. Key configurations for large instances:

```
PostgreSQL on 64-core / 512 GB instance:
  shared_buffers:        128 GB (25% of RAM)
  effective_cache_size:  384 GB (75% of RAM)
  max_connections:       500
  max_parallel_workers:  32
  max_parallel_workers_per_gather: 8
  max_worker_processes:  32
  wal_buffers:           16 MB (the automatic default caps here, larger rarely helps)

Trade-offs:
  + Strong ACID guarantees on single node
  + No distributed transaction overhead
  - Single node WAL write bottleneck (~500 MB/s max)
  - Crash recovery proportional to WAL since the last checkpoint, plus cache re-warming
  - Parallel query limited to 32 workers
```

### Redis

Redis on a single large instance provides the best latency at the cost of data volume limits:

```
Redis on 256 GB instance:
  maxmemory:         200 GB (leave 56 GB for OS + overhead)
  maxmemory-policy:  allkeys-lru
  maxclients:        10,000
  save: ""            (no RDB, cache workload)
  appendonly: no     (no AOF, cache workload)

Trade-offs:
  + Sub-millisecond P99 latency
  + Simple operational model
  - Hard memory ceiling (200 GB max)
  - Command execution is single-threaded (I/O threads help, but one core still runs commands)
  - No persistence for cache workloads (rebuild from DB on restart)
```

### SQLite

SQLite on a single large instance is an under-appreciated vertical scaling pattern for read-heavy workloads. On a fast SSD, with the working set cached, SQLite can serve well over 50,000 simple read transactions per second, which is enough for many applications.

```
SQLite on 48-core / 256 GB server:
  PRAGMA journal_mode = WAL;
  PRAGMA cache_size = -64000000;   (negative means KiB, so about 64 GB of cache)
  PRAGMA mmap_size = 268435456000; (256 GB mmap)
  PRAGMA synchronous = NORMAL;

Trade-offs:
  + Zero configuration, zero maintenance
  + No network latency (embedded, local file)
  + 50,000+ simple reads/sec on modern NVMe
  - Single-writer at a time
  - No built-in users or access control (protect the file at the OS level)
  - No replication built in
```

### AWS Vertical Scaling Path

AWS offers the broadest range of instance sizes. The typical vertical scaling path:

```
t3.medium (2 vCPU, 4 GB, $30/month)
  ──> m7g.large (2 vCPU, 8 GB, $60/month)
    ──> m7g.xlarge (4 vCPU, 16 GB, $120/month)
      ──> m7g.2xlarge (8 vCPU, 32 GB, $240/month)
        ──> r7g.4xlarge (16 vCPU, 128 GB, $625/month)
          ──> r7g.8xlarge (32 vCPU, 256 GB, $1,250/month)
            ──> r7g.16xlarge (64 vCPU, 512 GB, $2,500/month)
              ──> x2gd.16xlarge (64 vCPU, 1,024 GB, $4,900/month)
                ──> u-6tb1.metal (448 vCPU, 6 TB, roughly $30,000+/month)
                  ──> u-24tb1.metal (448 vCPU, 24 TB, well over $100,000/month)

(Approximate on-demand prices, us-east-1. Check current pricing before planning.)

Cost per GB of RAM:
  t3.medium:   $7.50/GB/month
  r7g.4xlarge: $4.90/GB/month
  r7g.16xlarge: $4.90/GB/month
  u-6tb1:      ~$5/GB/month

  Memory-optimized families have a similar per-GB cost across sizes.
  What a bigger size buys you is more vCPUs, network bandwidth, and
  EBS throughput, not a cheaper GB of RAM.
```

**RDS managed vertical scaling**:
- Downtime: a Single-AZ instance class change typically takes a few minutes of downtime while the instance restarts
- Storage scaling: gp3 supports online storage increase (no downtime)
- Multi-AZ: the standby is modified first, then a failover promotes it, typically one to two minutes of downtime

### GCP Vertical Scaling Path

GCP's machine types follow the same pattern. Changing a VM's machine type requires stopping it, so plan a short restart. (Live migration is a separate feature that moves running VMs during host maintenance, so those events rarely interrupt you.)

```
GCP n2 family:
  n2-standard-2 (2 vCPU, 8 GB, ~$70/month)
    ──> n2-standard-4 (4 vCPU, 16 GB, ~$140/month)
      ──> n2-standard-8 (8 vCPU, 32 GB, ~$285/month)
        ──> n2-standard-16 (16 vCPU, 64 GB, ~$570/month)
          ──> n2-standard-32 (32 vCPU, 128 GB, ~$1,140/month)
            ──> n2-standard-48 (48 vCPU, 192 GB, ~$1,700/month)
              ──> n2-standard-64 (64 vCPU, 256 GB, ~$2,270/month)

Key advantage: prices scale linearly within a family, and going from
one size to the next is a stop, resize, start operation.
```

**Cloud SQL managed vertical scaling**:
- Downtime: brief, typically a minute or two during a machine type change
- Storage: automatic increase (no downtime)
- High availability: failover replica in different zone

## Lessons Learned

### Lesson 1: Know Your Ceiling

Every cloud provider has a maximum instance size. On AWS, general-purpose and compute-optimized virtual instances top out around 192 vCPU (bare metal goes higher), and the largest memory-optimized instances offer 24 TB of RAM at a price that makes a horizontal design look cheap. Estimate how many months until you hit that ceiling given your growth rate. If the answer is under 18 months, start designing for horizontal migration now.

### Lesson 2: Vertical Scaling Is Not Binary

As Uber demonstrated, you can vertically scale some services and horizontally scale others. The choice depends on data characteristics:
- Bounded data with ACID requirements: vertical scaling
- Unbounded data or append-only logs: horizontal scaling
- Read-heavy with predictable working set: vertical scaling with caching
- Write-heavy with variable load: horizontal scaling

### Lesson 3: Cache Before You Scale

Before upgrading an instance, add a cache layer. Redis or Memcached on a separate node (or same node) can reduce database load by 80-95%. This often eliminates the need for the instance upgrade entirely. Large systems, including the ones above, put heavy caching in front of their databases to extend the useful life of each node.

### Lesson 4: Plan the Migration Before You Hit the Ceiling

Large data-store migrations, such as Discord's moves from MongoDB to Cassandra and later to ScyllaDB, take months of planning and testing even when the final data copy is quick. If your growth projections show the vertical ceiling is 12 months away, you should have started the migration 6 months ago. The migration itself requires rewriting data access patterns, changing application code, testing at scale, and running dual-write during the transition.

### Lesson 5: Monitor the Right Signals

The signal that it is time to scale up is not just CPU at 90%. Watch the trend of:
- **Cache hit ratio** (database and Redis): declining means working set is growing faster than RAM
- **Disk queue depth**: increasing means I/O throttling is imminent
- **Connection pool wait times**: increasing means more concurrent users than the pool handles
- **P99 latency trend**: creeping up by 5-10ms per month signals approaching saturation

Each of these gives a 3-6 month warning before the bottleneck becomes critical, long enough to plan either an instance upgrade or a horizontal migration.
