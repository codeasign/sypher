## Company Case Studies

### Case Study 1: Twitter (now X): Snowflake

In 2010, Twitter was moving its tweet storage from a single MySQL database to a distributed store. A distributed store cannot rely on a single auto-increment counter, so Twitter needed a way to generate IDs on many machines at once. The requirements it described were high rates (tens of thousands of IDs per second), rough time ordering, and IDs that fit in 64 bits. Traffic was growing quickly: the 2010 FIFA World Cup produced what was then a record, about 2,940 tweets per second.

**The solution:** Twitter engineers created Snowflake, a 64-bit ID generator that combined timestamp, worker ID, and sequence number. The 64-bit format gave 2^63 possible IDs, enough for 9.2 quintillion tweets. Each worker generated IDs locally, and only the worker IDs needed any coordination.

**Key design decisions:**
- 41-bit millisecond timestamp gave 69 years of range from the custom epoch (2010-11-04).
- 10-bit worker ID allowed 1,024 workers (Twitter split it into 5 bits for a data center and 5 bits for a worker).
- 12-bit sequence allowed 4,096 IDs per millisecond per worker.
- Custom epoch of 1288834974657 (November 4, 2010, 01:42:54 UTC), a date close to when the code was written, chosen so that the 41-bit timestamp would last as long as possible.

**Publicly known results:** Snowflake removed the central ID bottleneck, and its announcement post and open-source Scala implementation (2010) became the template for many later distributed ID systems, including the ones below.

### Case Study 2: Discord: Snowflake for Real-Time Messaging

Discord needed IDs for messages, channels, guilds, and users across a globally distributed real-time messaging platform. They adopted the Snowflake format with a custom bit layout tailored to their scale.

**Discord's Snowflake layout:**
- 42-bit timestamp (milliseconds since Discord epoch: January 1, 2015)
- 5-bit internal worker ID
- 5-bit process ID
- 12-bit sequence number (increment only, no overflow; Discord's throughput per node fits within 4,096/ms)

**Key publicly known details:**
- The layout is documented in Discord's public API documentation, including how to extract each field.
- The 5-bit internal worker ID and 5-bit process ID give 32 workers with 32 processes each, for 1,024 distinct generators.
- Discord exposes the ID's timestamp in their API: developers can extract the creation time of any Discord object from its Snowflake ID.

**Why it mattered:** A chat platform creates enormous numbers of messages, and the Snowflake scheme gives each one a unique, time-sortable ID without any cross-server communication. Time-sortable 64-bit IDs also fit naturally into the message store, because "the latest messages in a channel" is a range read on the ID.

### Case Study 3: Instagram: Sharded ID Generation

Instagram (acquired by Facebook/Meta) faced a different challenge: they sharded their PostgreSQL database across thousands of logical shards, each needing unique, time-sortable IDs. They could not use a single Snowflake-style generator because their IDs needed to encode the shard number for routing queries.

**Instagram's solution (publicly described in their 2012 engineering blog):**
- 41-bit timestamp (milliseconds since a custom epoch in 2011)
- 13-bit shard ID (supports up to 8,192 shards)
- 10-bit sequence number (1,024 IDs per millisecond per shard)

**Key insight:** By embedding the shard ID directly into the primary key, Instagram could route queries to the correct shard without a lookup table. An application layer extracted the shard ID bits, computed the target shard, and sent the query directly.

**Benefit:** The embedded shard ID removes a lookup step for queries by ID. Instagram also generated the IDs inside PostgreSQL itself (with a stored function), so it did not have to run a separate ID service.

### Case Study 4: Edge Request IDs (Cloudflare Ray IDs)

Cloudflare tags every HTTP request that passes through its edge network with a Ray ID, a 16-character hexadecimal value that appears in response headers and on error pages, and that support teams and logs use to correlate what happened to a request. Cloudflare handles millions of requests per second across hundreds of data centers, and every one of them needs an ID that is created locally, with no coordination, and that never collides. Cloudflare does not publish the exact algorithm, so this section uses the problem to show why the design of an ID matters at that volume. (The figures in the diagram below are illustrative.)

**Why randomness alone is not enough for 64 bits**: Suppose IDs were 64 random bits. By the birthday bound, collisions become likely after about 2^32 (roughly 4 billion) IDs. At 25 million requests per second, that is only a few minutes of traffic, and over a day you would expect on the order of a hundred thousand duplicates. So a 64-bit ID needs structure (a timestamp, a server or data center identifier, and a counter) rather than pure randomness.

**The alternative**: A 128-bit ID with plenty of randomness (as in a UUID or ULID) makes accidental collisions practically impossible even at that rate, at the cost of twice the storage. The choice between a structured 64-bit ID and a random 128-bit ID is the central trade-off of this whole topic, and each choice suits a different set of constraints.

**Public reference**: Cloudflare documentation on Ray IDs.

### Case Study 5: Two Older Designs: Flickr Ticket Servers and MongoDB ObjectId

**Flickr ticket servers**: Flickr's 2010 engineering post, "Ticket Servers: Distributed Unique Primary Keys on the Cheap," describes a deliberately simple design. Two MySQL servers act as ticket servers. Each has a table with a single auto-increment column, and the servers are configured so that one hands out odd numbers and the other even numbers (`auto_increment_increment = 2` with different offsets). An application gets an ID by running `REPLACE INTO Tickets64 (stub) VALUES ('a')` and then reading `LAST_INSERT_ID()`. Clients alternate between the two servers, so if one fails the other keeps issuing IDs. The design works because the number of IDs Flickr needed per second was modest, and it needs no clocks. Its limits are the network hop for every ID, and that IDs are only roughly time-ordered.

**MongoDB ObjectId**: A MongoDB ObjectId is 12 bytes: a 4-byte timestamp (in seconds), a 5-byte random value that is fixed per process, and a 3-byte counter that starts at a random value and increments. Each client process can generate IDs with no coordination and no worker ID assignment. The timestamp makes ObjectIds roughly sortable by creation time. The design trades a larger ID (96 bits) for removing the need for any registry of workers.

**Lesson**: Distributed IDs are a spectrum of trade-offs among size, coordination, ordering, and throughput. Flickr chose coordination with a small central service. MongoDB chose randomness plus a counter. Twitter and Instagram chose structured 64-bit IDs.

## Open Source Implementations

### Sonyflake

A Go implementation of Snowflake by Sony. Key differences from Twitter's original:
- 39-bit timestamp in units of 10 milliseconds (about 174 years from a configurable epoch)
- 8-bit sequence number (256 IDs per 10 milliseconds per machine, about 25,600 per second)
- 16-bit machine ID (65,536 machines), which by default is derived from the machine's private IP address

**Trade-off**: Lower peak throughput per machine, but a much longer lifetime and many more machines than the original layout supports. Better for large fleets of modest nodes that each need only moderate ID rates.

### KSUID (by Segment)

A 20-byte, K-sortable identifier: a 32-bit timestamp (in seconds, from a custom 2014 epoch) followed by 128 bits of random payload, usually written as a 27-character base-62 string.

**Trade-off**: Larger than a 64-bit ID and only second-level time ordering, but it needs no worker IDs and no clock precision, and the 128 random bits make collisions practically impossible.

### ULID (Go, JavaScript, and other implementations)

Many open-source implementations of the ULID spec exist for Go, JavaScript, Python, and other languages. ULID influenced the design of UUID v7 (standardized in RFC 9562), which uses a similar timestamp-then-random layout in the UUID format.

**Trade-off**: A ULID is a 26-character string, so it is not directly usable as a database BIGINT key and needs a string-compatible index (or storage as 16 bytes).

## Cloud Provider Implementations

**AWS:** Amazon does not offer a dedicated distributed ID service. DynamoDB does not generate keys for you, so applications supply UUIDs or other IDs. Aurora and RDS provide auto-increment columns (single-writer, not distributed). For Snowflake-style IDs, AWS customers typically run their own service or use a library.

**GCP:** Cloud Spanner does not offer an auto-increment that scales, because a monotonically increasing key creates a hot spot on one server. Google recommends UUIDs (Spanner has a `GENERATE_UUID()` function) or bit-reversed sequences, which spread sequential values evenly across the key space. TrueTime is used for Spanner's transaction ordering, not for generating IDs.

**Azure:** Cosmos DB requires each item to have an `id` that you supply (commonly a GUID). Azure SQL Database supports sequence objects, but they are scoped to one database, so they do not provide uniqueness across regions or databases by themselves.

**Cloud provider recommendation:** Running your own Snowflake-style service or an embedded library on any cloud is cost-effective and proven for most systems. For managed databases that partition by key range, prefer random or bit-reversed IDs (or UUID v7 when the database handles time-ordered keys well) so you do not create a write hot spot.

## Lessons Learned

**Lesson 1: Prefer time-ordered IDs for database primary keys at scale.** Random UUID v4 keys scatter inserts across the index, which causes page splits and fragmentation. The systems above (Snowflake-style IDs, ObjectId, KSUID, ULID) all put a timestamp first for this reason, among others. If you want UUIDs, use UUID v7 (time-ordered).

**Lesson 2: Plan for clock skew from day one.** Clock problems are the classic failure mode of timestamp-based IDs. Implement clock skew monitoring in your first deployment, not as a post-incident addition.

**Lesson 3: The coordination service for worker IDs is the system's single point of failure.** Design it for the same availability as your database. A 3-node ZooKeeper cluster with proper fencing is the minimum. Never use a single-node coordination service in production.

**Lesson 4: Embedding shard IDs in primary keys simplifies routing but locks in your sharding strategy.** Instagram could not change their shard count without an ID format change. If you expect to re-shard often, keep shard routing out of your IDs.

**Lesson 5: 64-bit IDs are sufficient for essentially every system built today.** Twitter estimated 69 years of headroom from their 2010 epoch. That takes Snowflake IDs to the year 2079. Discord's 42-bit timestamp gives 139 years. Even with IoT-scale growth, 9.2 quintillion IDs provides a massive safety margin.
