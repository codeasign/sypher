# PACELC in Production

Real systems implement PACELC trade-offs with concrete mechanisms. The following case studies show how major databases and cloud services handle the partition-regime and else-regime trade-offs in production.

---

## DynamoDB: PA/EL at Planet Scale

DynamoDB is the canonical PA/EL implementation. The DynamoDB service descends from the ideas in Amazon's Dynamo paper, which explicitly chose availability over consistency during partitions and low latency over consistency during normal operation. (The managed service's internals differ from the paper, but its defaults follow the same philosophy: eventually consistent reads are the default.)

### Key Numbers

DynamoDB advertises single-digit millisecond latency for reads and writes. In broad terms, and with the caveat that real numbers depend on the workload:
- Typical write latency: a few milliseconds
- Replication between replicas in a region: usually well under a second
- Cross-region (global tables) replication: typically about a second
- ConsistentRead (strong): costs twice the read capacity and slightly more latency, because it goes to the partition's leader

### Production Lesson: Shopping Cart at Amazon

Amazon's shopping cart service runs on DynamoDB with PA/EL defaults. The key insight is that a shopping cart does not need strong consistency. If a customer adds an item and it temporarily disappears, they can re-add it. The cost of a rare inconsistency (customer frustration) is far lower than the cost of adding latency to every add-to-cart operation (lost sales due to slow response).

Amazon has reported that DynamoDB handles well over 100 million requests per second at peak during Prime Day. That kind of scale is what the low-latency, availability-first design is built for.

### DynamoDB's ConsistentRead Option

DynamoDB offers `ConsistentRead=True` for operations that need strong consistency. This switches from PA/EL to PA/EC for that single read. The write path remains PA/EL, but the read path ensures the returned value is the latest across all replicas. This is used for checkout flows where the final cart total must be accurate.

### Production Lesson: Netflix and Apple on Cassandra

Netflix and Apple have both described very large Cassandra deployments in public talks and blog posts, and both run across multiple data centers or regions. The general pattern in such deployments, and an illustration of how the PACELC choice is made per workload, looks like this:

- For high-volume, append-mostly data such as activity events and metrics, a low consistency level (`LOCAL_ONE`) keeps write latency and cluster size down, and losing or delaying a few events does not break the product.
- For data whose staleness users would notice, such as account or synced user data, `LOCAL_QUORUM` gives consistent reads and writes within a data center while avoiding cross-data-center latency.

The specific settings each company uses are their own choices, so treat the list above as an example of the reasoning, not as a report of their configurations.

### Production Lesson: Google Ads

Spanner was built originally for Google's advertising business, which requires globally consistent financial reporting. An advertiser's budget must be deducted exactly once regardless of which data center handles the click event. Spanner's PC/EC guarantees make this possible without complex reconciliation.

The cost is significant: Spanner writes typically take 10-50ms compared to DynamoDB's 1-5ms. Google judged this acceptable because inconsistent ad budget deductions would cost real money through either overspend or underspend.

### Spanner's Read Flexibility

Spanner offers three read modes that map to different points on the PACELC spectrum:

- **Strong reads:** Linearizable. The serving replica must confirm it is up to date, which may involve the leader, so latency includes possible cross-region coordination.
- **Bounded staleness reads:** Client specifies maximum staleness (e.g., 10 seconds). The system reads from any replica that has caught up to that point, which is typically faster and can be served locally.
- **Exact staleness reads:** Client specifies exact timestamp. Useful for point-in-time queries.

This is Spanner's version of tunable consistency: a PC/EC base with optional PA/EL read modes.

### Production Lesson: Session Consistency as the Default

Session consistency is the default consistency level for Cosmos DB accounts. It guarantees monotonic reads, monotonic writes, and read-your-writes within a single client session. This maps to PA/EL during normal operation with a session-specific guarantee that prevents the most confusing inconsistency pattern (a user seeing their own write disappear). Data that must be globally consistent, such as configuration, can use Strong consistency, and telemetry can use Eventual consistency, with the latency and availability costs that each choice carries.

## Open Source Implementations

### Cassandra

Cassandra offers the widest range of tunable consistency in open source. It provides about a dozen consistency levels across reads and writes, covering the entire PA/EL to PC/EC spectrum. The gossip protocol detects partitions. Hinted handoff and read repair provide convergence. Merkle tree anti-entropy runs periodically.

### ScyllaDB

ScyllaDB is a C++ reimplementation of Cassandra that is API-compatible. It offers the same PACELC configuration model but with lower latencies and higher throughput per node in many workloads, through a shared-nothing per-core architecture. ScyllaDB's PACELC performance characteristics are the same pattern but with lower absolute latency numbers.

### Riak

Riak was an early Dynamo-style implementation. It used vector clocks for conflict resolution instead of LWW, giving applications more control over merge semantics. Riak's PACELC model: PA/EL default with configurable quorum sizes per bucket.

## Lessons Learned

**Lesson 1: The Else regime deserves as much attention as the Partition regime.** Partitions are rare, and your system runs in the Else regime nearly all the time, so its latency and consistency choices shape the everyday user experience.

**Lesson 2: Tunable consistency adds operational complexity.** Teams that configure per-operation consistency levels must test every path in their system. A single misconfigured consistency level can cause correctness bugs.

**Lesson 3: Session consistency is a practical sweet spot.** Read-your-writes guarantees eliminate the most confusing inconsistency pattern without the latency cost of full strong consistency.

**Lesson 4: Cross-region PACELC is different from within-region PACELC.** Within a region, latency is 1-5ms and the cost of consistency is low. Across regions, latency is 50-300ms and the cost of strong consistency is high. Plan accordingly.

**Lesson 5: Monitor both regimes separately.** A system that is healthy in the Else regime may perform completely differently during a partition. Monitor latency and consistency metrics for both regimes independently.
