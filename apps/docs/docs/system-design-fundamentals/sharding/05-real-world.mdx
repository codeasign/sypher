## How Companies Shard Data at Scale

The following case studies show how four organizations approached scaling their data, including one that chose replication over sharding. Each case study begins with the problem, describes the architecture, and explains the key design decisions, based on publicly available engineering blog posts. Figures inside the diagrams are illustrative.

---

## Case Study 1: Discord: From MongoDB to Cassandra Partitioning

### The Problem

Discord launched in 2015 on a single MongoDB replica set for message storage. As the platform grew, the data and its indexes stopped fitting in memory. Reads of older messages became random disk reads, latency turned unpredictable, and it was clear that adding RAM would only delay the problem. Discord's engineering blog ("How Discord Stores Billions of Messages", 2017) describes the move to Cassandra.

Discord evaluated several options. A relational database was a poor fit for an ever-growing message log, and Cassandra offered linear scaling, replication, and a data model built around partitions. They chose Cassandra.

### The Architecture

Discord partitions messages by channel and a time bucket. Every message belongs to a channel, and the dominant query is "show recent messages in this channel." The partition key is `(channel_id, bucket)`, where the bucket is a fixed window of time, and messages within a partition are ordered by message ID (a time-sortable Snowflake ID). Cassandra's partitioner hashes the partition key to place it on the ring.

### Key Design Decisions

**Channel as the partition key, not the whole server.** A "guild" (server) can contain thousands of channels, so partitioning by guild would have put a huge amount of unrelated data in one place. Partitioning by channel matches how users read: one channel at a time.

**A time bucket to bound partition size.** Without the bucket, a busy channel's partition would grow forever. Adding a time window to the key caps how large any one partition can get, so reading recent history touches one or two partitions.

**Time-sortable message IDs as the clustering key.** Because Snowflake IDs sort by time, "the latest 50 messages" is a short sequential read from the newest bucket.

**Replication factor 3.** Each partition is stored on 3 nodes, so a node can fail without data loss.

### Lessons Learned

**Hot partitions still happen.** A very active channel concentrates traffic on one partition and its replicas. Discord's later blog post ("How Discord Stores Trillions of Messages", 2023) describes putting a Rust data service in front of the database that coalesces identical concurrent requests, so a burst of reads for the same hot data becomes one query.

**Operations at scale matter as much as the data model.** Discord grew its Cassandra cluster to hundreds of nodes and found that garbage-collection pauses and compaction made performance hard to predict. It later migrated to ScyllaDB, a Cassandra-compatible database, which needed far fewer nodes for the same data.

**Consistent hashing makes scaling manageable.** Cassandra's ring lets nodes join and leave while only neighboring token ranges move, which made growing the cluster a routine operation.

## Case Study 2: Uber: Migrating Trip Data to Sharded MySQL

### The Problem

By 2014, Uber's trip data lived in a single PostgreSQL database that was running out of headroom on both storage and write capacity. As Uber grew across many cities, the trip store had to become horizontally scalable. Uber's engineering blog describes the effort ("Project Mezzanine") as a migration of the trip store to a new sharded datastore.

### The Architecture

Uber built **Schemaless**, an append-only, sharded datastore layered on MySQL. A record is addressed by a row key, and rows are assigned to shards by hashing the row key. Each shard is a MySQL primary with replicas. A separate layer of workers builds secondary indexes.

### Key Design Decisions

**Shard by row key, with a fixed number of shards.** Hashing the row key spreads trips evenly across shards. Choosing a large fixed shard count up front means that adding capacity moves whole shards to new hosts rather than re-hashing rows.

**Append-only storage.** Instead of updating a record in place, Schemaless writes new versions of a cell. That keeps writes cheap and makes replication and recovery simpler.

**Migrate with dual writes and verification.** Moving live trip data off PostgreSQL was itself a large project. Uber described writing to both the old and new stores, backfilling historical data, and comparing results on reads before switching over.

**Secondary indexes built asynchronously.** Queries by something other than the row key use an index maintained by background workers. That keeps the write path fast at the cost of indexes that can lag slightly.

### Lessons

The lasting lesson from this migration is the pattern: pick a shard key that matches the main access path, choose many small logical shards, and treat the migration as a project with dual writes and verification, not a one-time cutover.

## Case Study 3: Instagram: Thousands of Logical Shards on a Few Servers

### The Problem

Instagram's early data lived in PostgreSQL, and as the service grew rapidly it needed to distribute that data. Instagram's engineering blog ("Sharding & IDs at Instagram", 2012) describes its approach.

### The Architecture

Instagram created a large number of **logical shards** (thousands), implemented as separate PostgreSQL schemas, and mapped them onto a much smaller number of physical database servers. A lookup determines which logical shard holds a piece of data, and another maps that logical shard to a physical server.

### Key Design Decisions

**Logical shards separate "where data lives" from "which machine holds it."** When a server fills up, a logical shard can be moved to another machine as a unit. The number of logical shards never changes, so no row is ever re-hashed.

**IDs that carry the shard.** Instagram generated 64-bit IDs made of a millisecond timestamp (41 bits), the logical shard ID (13 bits), and a per-shard sequence number (10 bits), generated inside PostgreSQL. The ID both sorts roughly by time and tells you which shard holds the row.

### Lessons Learned

**Plan for more logical shards than you need today.** Splitting or merging shards later is painful. Starting with thousands of logical shards on a handful of servers made growth mostly a matter of moving them.

**Keep related data together.** Because a user's data is placed on one logical shard, most queries touch only one shard.

## Case Study 4: Cloudflare: When Replicating Beats Sharding

### The Problem

Cloudflare has a very large amount of configuration data (such as DNS zones and customer settings) that must be available with very low latency on servers in hundreds of cities. It is a natural question whether this data should be sharded.

### The Architecture

Cloudflare took the opposite approach: instead of sharding the data, it replicates all of it. Its **Quicksilver** system distributes configuration to every server, and each server keeps a full local copy in an embedded key-value store, so lookups never leave the machine. ### Key Design Decisions

**The data is small enough to replicate everywhere.** Configuration for millions of zones is measured in gigabytes, not petabytes, so every server can hold a complete copy.

**Reads dominate and writes are rare.** Zone changes are infrequent compared with queries. A read-mostly, slowly changing dataset is the best case for replication.

**Local reads beat network reads.** Serving from local storage removes the network from the read path, which matters when a query must be answered in milliseconds.

### Lessons Learned

**Sharding solves a data-volume or write-throughput problem.** If your dataset fits on one machine and reads dominate, replication or caching is simpler and faster than sharding, and it avoids cross-shard queries and rebalancing entirely.

**Check the numbers first.** Estimate data size, write rate, and read rate before choosing an approach. Many "we need to shard" conversations end at "we need a replica and a cache."

## Open Source Implementations

### Vitess (CNCF Graduated)

Vitess shards MySQL using a proxy architecture. VTGate routers intercept SQL queries, extract the shard key, and route to the correct MySQL shard. Vitess supports both hash-based and range-based sharding with online resharding.

**Trade-offs:** Adds a few milliseconds of latency per query through the proxy layer. Requires running a topology service (etcd, ZooKeeper, or Consul) for metadata management. Online resharding is complex but proven at YouTube scale (where Vitess originated).

**Best for:** MySQL workloads that have outgrown a single instance. Organizations that want to keep MySQL compatibility with application drivers.

### Cassandra / ScyllaDB

Cassandra shards using consistent hashing with virtual nodes. Each node is responsible for a range of the hash ring. Writes are replicated to N nodes (configurable replication factor). ScyllaDB is a Cassandra-compatible database written in C++ with significantly better performance.

**Trade-offs:** AP system: eventual consistency by default. Strong consistency requires quorum reads/writes, which reduce availability. CQL is SQL-like but lacks JOINs, subqueries, and transactions.

**Best for:** Write-heavy workloads, time-series data, messaging systems. Any workload where availability and partition tolerance are more important than strong consistency.

### Citus (PostgreSQL Extension)

Citus shards PostgreSQL using a coordinator node. The coordinator stores metadata about which shard holds which key ranges. Queries go through the coordinator, which either routes to one shard or fans out.

**Trade-offs:** A single coordinator can become a bottleneck (recent Citus versions can route queries through any node). Limited support for complex queries (subqueries, CTEs across shards). Provides PostgreSQL compatibility and ACID transactions within a shard.

**Best for:** Multi-tenant SaaS applications where each tenant fits in one shard. Real-time analytics on time-series data.

## Cloud Provider Implementations

### AWS: Amazon Aurora Global Database + Sharding

AWS offers several paths. DynamoDB partitions data automatically. Aurora Limitless Database (introduced in 2024) adds managed horizontal sharding for PostgreSQL-compatible workloads. Aurora Global Database provides multi-region replication. With standard RDS or Aurora, sharding is implemented at the application layer using a sharding library or a proxy.

**Cost/ops trade-off:** Low operational overhead (AWS manages the database), but with standard RDS and Aurora the sharding logic is the customer's responsibility. Aurora's storage auto-scales to at least 128 TB, which delays the need for sharding for many workloads.

### GCP: Cloud Spanner (Auto-Sharded)

Google Cloud Spanner is a globally distributed, strongly consistent database that handles sharding automatically. Spanner splits data across nodes using a split algorithm based on key ranges. The application sets the primary key, and Spanner handles the rest.

**Cost/ops trade-off:** Premium pricing (on the order of $1 per node-hour for a regional configuration, more for multi-region, and increasingly priced in processing units). Zero sharding operational overhead. Strong consistency and global replication built in. Best for applications that need sharding's scalability without the operational burden.

### Azure: Cosmos DB (Partitioned by Design)

Azure Cosmos DB requires every collection to have a partition key. The partition key determines how data is distributed across physical partitions. Cosmos DB limits each logical partition (all items sharing one partition key value) to 20 GB, and it automatically splits physical partitions as they grow.

**Cost/ops trade-off:** Pay-per-request pricing (RU/s). Automatic partition management. Limited to Cosmos DB's query model (SQL-like with restrictions). Best for greenfield applications that can design around Cosmos DB's query limitations.

## Lessons Learned

Five key lessons from the case studies, applicable to any sharding project.

**1. Choose the shard key based on the dominant query pattern, not data distribution.** Discord partitions messages by channel because users read one channel at a time. Uber's Schemaless shards by row key because most access is by key. Instagram places a user's data on one logical shard because most queries are about one user. The shard key must match the access pattern; uniform data distribution is a secondary concern.

**2. Two-level partitioning provides both scalability and operational convenience.** Discord's (channel, time bucket) partition key gives it channel-level routing, bounded partition sizes, and cheap access to recent history. Instagram's logical-to-physical mapping separates where data lives from which machine holds it. A single level of partitioning often forces a compromise between query performance and data management.

**3. Rebalancing is the hardest operation in distributed systems.** Teams that rebalance carelessly lose data or cause outages. Use proven tools (Vitess Reshard, the Citus rebalancer, Cassandra's streaming bootstrap, or a custom tool with dual-writes and checksum verification). Test rebalancing in staging before running in production.

**4. Monitor per-shard, not per-cluster.** Cluster-wide averages hide hot spots, skew, and individual shard failures. A problem like an oversized partition or a hot shard is invisible in an average until you monitor the individual partition or shard. Every metric that matters for the cluster matters more for individual shards.

**5. Sharding is a last resort, not a first choice.** Indexing, read replicas, connection pooling, vertical scaling, and caching solve 90 percent of database scaling problems with far less complexity. Cloudflare replicates its configuration data to every server instead of sharding it, because the data is small and read-mostly. Discord went to Cassandra because its message history outgrew what a single MongoDB replica set could serve. Verify that simpler approaches have failed before committing to sharding.
