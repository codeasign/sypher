Every module before this one has tested the RBAC app by guessing, from the Swagger UI or from trial and error, what an endpoint expects and returns. This module is the turning point: you'll pull the app's actual OpenAPI spec into Java as a queryable object, and from here forward, that spec — not a guess, not the Swagger UI's rendered page — is what every later module checks reality against.

## What's actually in an OpenAPI spec

An OpenAPI (formerly "Swagger") spec is a JSON (or YAML) document describing an API: every path, the HTTP methods each path supports, what request bodies and parameters they expect, and what responses they can return. The Swagger UI page you've been looking at since the setup module — `http://localhost:5000/api-docs` — isn't the spec itself; it's a JavaScript app that *renders* the spec into a browsable page. Underneath that page is a plain JSON document, and that's the part worth getting into Java directly.

## The endpoint that isn't quite where you'd expect

The obvious first move is to guess a JSON URL — most `swagger-ui-express` setups expose one at `/api-docs.json` or `/api-docs/swagger.json`. Try both:

```bash
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://localhost:5000/api-docs.json
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://localhost:5000/api-docs/swagger.json
```

```bash
404 text/html; charset=utf-8
200 text/html; charset=utf-8
```

Neither gives you JSON. The first is a plain `404` — that route doesn't exist. The second is more misleading: it returns `200`, but `content-type: text/html` gives it away — that's the Swagger UI's index page again, not a spec file; this particular `swagger-ui-express` setup doesn't register a dedicated JSON route at all, so any unmatched path under `/api-docs` just falls through to the same HTML shell. This is a real, verified property of *this specific app's* Swagger wiring, not a general rule about `swagger-ui-express` — worth confirming for any app you test, rather than assuming one of those two URLs will just work.

## Where the spec actually lives

The Swagger UI page has to get its data from *somewhere* to render anything at all. Looking at what that HTML page actually loads:

```bash
curl -s http://localhost:5000/api-docs/swagger-ui-init.js | head -c 200
```

```js
window.onload = function() {
  // Build a system
  var url = window.location.search.match(/url=([^&]+)/);
  ...
  var options = {
  "swaggerDoc": {
    "openapi": "3.0.0",
```

There it is — the real spec, embedded directly inside a JavaScript file as part of a `var options = {...}` assignment, generated fresh by the server on every request rather than served as a static file. It's not JSON on its own — it's a `.js` file with a JavaScript variable assignment wrapped around a JSON object — but that JSON is real, complete, and exactly what the Swagger UI page itself renders.

## Pulling it into Java

A small regex extracts the JSON object out of the surrounding JavaScript, and RestAssured's own `JsonPath` class — already on your classpath, no new dependency needed — parses it into something queryable:

```java
package com.example.rbactests.support;

import io.restassured.path.json.JsonPath;

import java.util.regex.Matcher;
import java.util.regex.Pattern;

import static io.restassured.RestAssured.given;

public final class OpenApiSpec {

    private static final Pattern OPTIONS_PATTERN =
            Pattern.compile("var options = (\\{.*?\\n\\});\\n\\s*url = options\\.swaggerUrl", Pattern.DOTALL);

    private OpenApiSpec() {
    }

    public static JsonPath fetch() {
        String script =
                given()
                    .baseUri("http://localhost:5000")
                .when()
                    .get("/api-docs/swagger-ui-init.js")
                .then()
                    .statusCode(200)
                .extract()
                    .asString();

        Matcher matcher = OPTIONS_PATTERN.matcher(script);
        if (!matcher.find()) {
            throw new IllegalStateException("Could not find embedded spec in swagger-ui-init.js");
        }

        JsonPath options = new JsonPath(matcher.group(1));
        return options.getJsonObject("swaggerDoc");
    }
}
```

`Pattern.DOTALL` makes `.` in the regex match newlines too, which it needs to since the embedded JSON spans hundreds of lines. The pattern captures everything between `var options = {` and the `});` that closes it, stopping right before `url = options.swaggerUrl` — that anchor is what keeps the non-greedy `.*?` from stopping too early or matching too much. `new JsonPath(matcher.group(1))` parses that extracted text exactly the way it would parse any JSON string — the fact that it started life wrapped in JavaScript doesn't matter once it's been sliced out cleanly. `options.getJsonObject("swaggerDoc")` then reaches one level in, since the outer `options` object has `swaggerDoc` as just one of its fields (alongside a few others Swagger UI itself uses for rendering, like `dom_id` and `deepLinking`, that this course has no use for).

Try it:

```java
JsonPath spec = OpenApiSpec.fetch();
System.out.println(spec.getString("info.title"));
System.out.println(spec.getMap("paths").keySet());
```

```bash
RBAC Healthcare System API
[/api/appointments, /api/appointments/{id}, /api/auth/register, /api/auth/login,
 /api/medical-records, /api/medical-records/{id}, /api/patients/{patientId}/records,
 /api/patients, /api/users, /api/users/{id}, /api/users/role/{role}]
```

Once you have `spec` as a `JsonPath`, `spec.getMap("paths")` gives you a `Map<String, Object>` keyed by URL path, and each value is itself a nested map keyed by HTTP method (`"get"`, `"post"`, and so on) — you can keep walking into it with more `JsonPath` calls, or read a `Map` out and navigate it directly with plain Java, whichever a given test finds more natural.

This is exactly the kind of quirk this course's whole philosophy is built around: don't assume where something lives — confirm it, the way you just did with two failed guesses and one that worked. A real project might reach for a dedicated OpenAPI-parsing library, or a proper `/openapi.json` endpoint if the app exposed one cleanly; this app doesn't, so extracting it directly is the honest, verified path — and it's a useful skill on its own, since not every real API you'll test in your career will make its spec conveniently available either.

## Caching it for the whole suite

Fetching and re-parsing the spec before every single test is wasted work — it doesn't change mid-run. A simple static cache on `OpenApiSpec` is enough for this course:

```java
// add to OpenApiSpec
private static JsonPath cached;

public static synchronized JsonPath spec() {
    if (cached == null) {
        cached = fetch();
    }
    return cached;
}
```

`synchronized` matters here specifically because the parallel-execution module later in this course runs tests concurrently across threads — without it, two threads could both see `cached == null` at the same moment and fetch the spec twice; with it, only one thread fetches, and every other caller simply waits and reuses the result. Every later module in this course calls `OpenApiSpec.spec()`, not `fetch()` directly.

## What's documented, and what isn't

Look at `spec.getMap("paths.'/api/appointments'.get.responses")` (the quotes around the path segment matter — `JsonPath` needs them because the raw key itself contains a `/`), and you'll find it lists only `"200"`. You already know from the last module that the *real* app also returns `401` and `403` from this exact endpoint when auth fails — the spec just doesn't say so. That's not a mistake you need to report anywhere; it's a real, common gap in hand-annotated specs, and it's exactly the kind of thing worth knowing about *before* you start writing tests based on "what the spec promises." The spec's documented responses are closer to a floor than a ceiling — later modules test both what it promises and what it leaves out.

## Try it

Using `OpenApiSpec.spec()`, write a test that asserts `/api/medical-records` supports both `"post"` and `"get"` methods, and that the `"post"` operation's request body marks `patient_id` and `diagnosis` as required (check `spec.getList("paths.'/api/medical-records'.post.requestBody.content.'application/json'.schema.required")`). This is the same nested-structure walking you'll automate into a full checklist in the next module.
