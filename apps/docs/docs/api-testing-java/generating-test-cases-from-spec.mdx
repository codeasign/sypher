You can now pull the real spec into a `JsonPath` you can query. This module turns that into something more useful than a curiosity: a checklist of test cases, derived directly from the spec's structure instead of from memory or guesswork.

## From spec structure to a checklist

Every path in `spec.getMap("paths")` maps to one or more HTTP methods, and each method is a candidate test case. Walk the whole thing and print it out:

```java
import io.restassured.path.json.JsonPath;
import java.util.List;
import java.util.Map;

JsonPath spec = OpenApiSpec.spec();
Map<String, Object> paths = spec.getMap("paths");

for (String path : paths.keySet()) {
    @SuppressWarnings("unchecked")
    Map<String, Object> methods = (Map<String, Object>) paths.get(path);
    for (String method : methods.keySet()) {
        System.out.printf("%-6s %s%n", method.toUpperCase(), path);
    }
}
```

```bash
POST   /api/appointments
GET    /api/appointments
GET    /api/appointments/{id}
PUT    /api/appointments/{id}
DELETE /api/appointments/{id}
POST   /api/auth/register
POST   /api/auth/login
POST   /api/medical-records
GET    /api/medical-records
GET    /api/medical-records/{id}
PUT    /api/medical-records/{id}
DELETE /api/medical-records/{id}
...
```

That is every single endpoint this app exposes, without you having to open Swagger UI and copy them down by hand. Just as importantly, if a route is ever added or removed, this checklist changes automatically the next time you run it, where a hand-maintained list silently goes stale.

The `@SuppressWarnings("unchecked")` cast is worth explaining rather than glossing over: `JsonPath.getMap(...)` returns `Map<String, Object>` because it has no way to know at compile time what type the nested values actually are. You, the caller, know from having looked at the spec that `methods` is really another map. The annotation tells the compiler "yes, I know this cast is not statically checked, and I am confident it is correct" rather than leaving an unexplained warning in the build output.

## Deriving expected status codes, not guessing them

For each operation, the spec also documents which status codes it can return. Pull those out the same way:

```java
@SuppressWarnings("unchecked")
Map<String, Object> responses =
        (Map<String, Object>) ((Map<String, Object>) methods.get("get")).get("responses");
System.out.println(responses.keySet());
```

For `GET /api/appointments/{id}`, that prints `[200, 404]`: the spec is telling you, in its own words, that this endpoint has exactly two documented outcomes, found or not found. A test suite built off this checklist writes a test for each one, rather than a developer's memory of "I think it 404s if the ID does not exist."

## Turning this into a real checklist class

Rather than re-walking the spec by hand in every test file, build one small class that produces a list of test cases you can iterate over:

```java
package com.example.rbactests.support;

import io.restassured.path.json.JsonPath;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;

public final class EndpointChecklist {

    public record Endpoint(String method, String path, List<Integer> documentedStatusCodes) {
    }

    private EndpointChecklist() {
    }

    public static List<Endpoint> buildFromSpec() {
        JsonPath spec = OpenApiSpec.spec();
        Map<String, Object> paths = spec.getMap("paths");
        List<Endpoint> endpoints = new ArrayList<>();

        for (String path : paths.keySet()) {
            @SuppressWarnings("unchecked")
            Map<String, Object> methods = (Map<String, Object>) paths.get(path);

            for (String method : methods.keySet()) {
                @SuppressWarnings("unchecked")
                Map<String, Object> operation = (Map<String, Object>) methods.get(method);
                @SuppressWarnings("unchecked")
                Map<String, Object> responses = (Map<String, Object>) operation.get("responses");

                List<Integer> codes = responses.keySet().stream()
                        .map(Integer::parseInt)
                        .sorted()
                        .toList();

                endpoints.add(new Endpoint(method.toUpperCase(), path, codes));
            }
        }

        return endpoints;
    }
}
```

`Endpoint` is a **Java `record`**, a compact way to define a small, immutable data class where the whole point is just carrying a few fields around together. Writing `record Endpoint(String method, String path, List<Integer> documentedStatusCodes)` gives you a constructor, getters (`method()`, `path()`, `documentedStatusCodes()`), `equals`/`hashCode`, and a readable `toString()`, all generated for you. A plain class doing the same thing would need considerably more boilerplate for something that is fundamentally just a labeled bundle of values.

Run it and print the result:

```java
EndpointChecklist.buildFromSpec().forEach(System.out::println);
```

```bash
Endpoint[method=POST, path=/api/appointments, documentedStatusCodes=[201]]
Endpoint[method=GET, path=/api/appointments, documentedStatusCodes=[200]]
Endpoint[method=GET, path=/api/appointments/{id}, documentedStatusCodes=[200, 404]]
...
```

This list is what the next several modules build tests from directly: CRUD testing walks it endpoint by endpoint, and the RBAC module reuses it as the base for a full role × endpoint matrix.

## Try it

Extend `EndpointChecklist.Endpoint` with one more field: whether that operation requires authentication (`operation.get("security") != null`). Print the full checklist again and confirm `POST /api/auth/login` and `POST /api/auth/register` are the only two entries where that is `false`. Every other endpoint in this app requires a token, which is exactly what you would expect from an app built around RBAC.
