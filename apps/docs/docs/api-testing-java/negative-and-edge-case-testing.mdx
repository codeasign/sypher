Every module so far has mostly tested the happy path: valid input, valid auth, expected result. Real bugs live in the paths nobody planned for: missing fields, wrong types, invalid tokens, boundary values. This module goes looking for them deliberately, and, this app being what it is, actually finds a few.

## Invalid and missing tokens, precisely

You have already built this in the authentication module, but it is worth restating as the foundation everything else in this module builds on:

```java
@Test
void noTokenReturns401() {
    given()
        .spec(ApiSpec.base())
    .when()
        .get("/api/appointments")
    .then()
        .statusCode(401)
        .body("error", equalTo("Access token required"));
}

@Test
void malformedTokenReturns403() {
    given()
        .spec(ApiSpec.base())
        .header("Authorization", "Bearer this.is.not.a.real.jwt")
    .when()
        .get("/api/appointments")
    .then()
        .statusCode(403)
        .body("error", equalTo("Invalid or expired token"));
}
```

## Missing required fields: the spec says required, the app disagrees

Back in the assertions module, the "Try it" exercise asked you to omit `reason` from a `POST /api/appointments` body, even though the spec marks it required. Here is what actually happens:

```java
@Test
void omittingASpecRequiredFieldStillSucceeds() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .body("""
                {
                  "patient_id": 20,
                  "doctor_id": 5,
                  "appointment_date": "2026-09-20T10:00:00"
                }
                """)
    .when()
        .post("/api/appointments")
    .then()
        .statusCode(201); // NOT a validation error -- verified against the real app
}
```

That test passes, and it is meant to. This is a real, verified gap between what the spec *promises* (`reason` is required) and what the app *enforces* (nothing checks for it at all). Documenting a gap like this as a passing test, with a comment explaining exactly what is going on, is more valuable than silently not testing it: a teammate reading this suite later can see, at a glance, "yes, we know about this, it is not an oversight in the tests."

## No fields at all: a 500, not a validation error

Push further and omit *every* field:

```java
@Test
void emptyBodyReturnsAServerErrorNotAValidationError() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .body("{}")
    .when()
        .post("/api/appointments")
    .then()
        .statusCode(500)
        .body("error", equalTo("Error creating appointment"));
}
```

This is a real bug, not a documented gap. A well-behaved API returns `400 Bad Request` with a clear validation message when a client sends a badly-shaped request; a `500 Internal Server Error` means the *server* choked trying to process it, which usually points to a database constraint failure or a null-pointer-style error bubbling straight up to the client with no handling in between. Worth writing this test specifically because a `500` on bad input is the kind of thing that is easy to miss if you only ever test with reasonably-shaped requests, and it is exactly the sort of finding a real QA pass on this app should flag back to the team that owns it.

## Type confusion: sending the wrong kind of value

```java
@Test
void aStringWherePatientIdShouldBeAnIntegerStillSucceeds() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .body("""
                {
                  "patient_id": "not-a-number",
                  "doctor_id": 5,
                  "appointment_date": "2026-09-20T10:00:00",
                  "reason": "type confusion test"
                }
                """)
    .when()
        .post("/api/appointments")
    .then()
        .statusCode(201); // no type validation -- verified
}
```

Another real, verified gap: nothing checks that `patient_id` is actually a number before writing it. In a stricter API this would be a `400`; here it is accepted. Whether that is acceptable depends entirely on what the team building this app decides matters. The point of this test is not to declare it "wrong," it is to make the app's real behavior visible and pinned down, so nobody discovers it by accident in production instead.

## Referencing something that doesn't exist

```java
@Test
void aPatientIdThatDoesntExistStillSucceeds() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .body("""
                {
                  "patient_id": 999999,
                  "doctor_id": 5,
                  "appointment_date": "2026-09-20T10:00:00",
                  "reason": "nonexistent patient test"
                }
                """)
    .when()
        .post("/api/appointments")
    .then()
        .statusCode(201); // no referential check -- verified
}
```

There is no foreign-key-style check here either: the app happily creates an appointment pointing at a patient id that has never existed. Combine this with the type-confusion result above and a clear picture forms: this endpoint trusts its input almost entirely, which is exactly the kind of thing negative testing exists to surface systematically rather than leave to chance.

## Boundary and edge values

Beyond outright invalid input, boundary values are worth testing on their own:

```java
@Test
void requestingAppointmentIdZeroReturns404NotAServerError() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
    .when()
        .get("/api/appointments/0")
    .then()
        .statusCode(404); // treated the same as any other nonexistent id
}

@Test
void aVeryLargeAppointmentIdReturns404NotAnOverflowError() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
    .when()
        .get("/api/appointments/999999999")
    .then()
        .statusCode(404); // large but valid integer, still just "not found"
}
```

Both of these pass cleanly, which is itself worth confirming rather than assuming. An id of `0`, or a number near the edge of what fits in a database's integer column, are exactly the kind of values that sometimes trip up code with an off-by-one assumption baked in somewhere. Confirming they behave the same as any other nonexistent id is a small, cheap test that rules out a real category of bug.

## Try it

Send a `PUT /api/appointments/{id}` request with `"status": "not-a-real-status"` (a value outside the `scheduled`/`completed`/`cancelled` enum you saw in the schema module) against a real appointment id. Check whether the app rejects it or accepts it, and if it accepts it, read the appointment back afterward to see what actually got stored. Write a test asserting on whatever you find. This module has been full of "the app is more permissive than you would guess," so do not assume this one behaves any differently until you have actually checked.
