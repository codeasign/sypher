With auth handled and the spec in hand, it is time to test the thing most API suites spend the bulk of their time on: Create, Read, Update, Delete. This module walks a full CRUD cycle against `/api/appointments`, checking each step against what the spec actually documents rather than just "did it seem to work."

## What the spec says about `/api/appointments`

From the checklist you built last module, this resource has five operations across two paths:

```bash
POST   /api/appointments        ──▶ 201
GET    /api/appointments        ──▶ 200
GET    /api/appointments/{id}   ──▶ 200, 404
PUT    /api/appointments/{id}   ──▶ 200
DELETE /api/appointments/{id}   ──▶ 200
```

The spec's request body schema for `POST /api/appointments` marks `patient_id`, `doctor_id`, `appointment_date`, and `reason` as required, with `notes` optional. That is exactly what you will build a request body from, rather than guessing which fields matter.

## Create

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import io.restassured.response.Response;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;
import static org.hamcrest.Matchers.notNullValue;

class AppointmentCrudTest {

    @Test
    void createReadUpdateDeleteAnAppointment() {
        String requestBody = """
                {
                  "patient_id": 20,
                  "doctor_id": 5,
                  "appointment_date": "2026-09-15T10:00:00",
                  "reason": "CRUD module test"
                }
                """;

        Response createResponse =
                given()
                    .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
                    .body(requestBody)
                .when()
                    .post("/api/appointments")
                .then()
                    .statusCode(201)
                    .body("message", equalTo("Appointment created successfully"))
                    .body("appointmentId", notNullValue())
                .extract()
                    .response();

        int appointmentId = createResponse.jsonPath().getInt("appointmentId");
        System.out.println("Created appointment id: " + appointmentId);

        // Read, Update, and Delete continue below, all reusing this same id.
    }
}
```

`"""` starts a **Java text block**, a multi-line string literal available since Java 15 that lets you write a chunk of JSON (or any multi-line text) without escaping every quote and stitching lines together with `+`. It is used throughout this course for any request body longer than a single line; for one-liners, a normal `"..."` string with escaped quotes is still fine and you have already seen plenty of those.

Notice the create response's body is `{"message": "...", "appointmentId": 22}`, not the full appointment object. That is a real, verified property of this endpoint: creating a resource here does not hand you back the resource itself, just confirmation and its new id. You have to make a second call, the read step, if you actually want the created object back, which is exactly what real API clients would have to do too.

## Read

Continue the same test method, using the `appointmentId` you just captured:

```java
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/" + appointmentId)
        .then()
            .statusCode(200)
            .body("id", equalTo(appointmentId))
            .body("patient_id", equalTo(20))
            .body("doctor_id", equalTo(5))
            .body("status", equalTo("scheduled"))
            .body("reason", equalTo("CRUD module test"))
            .body("patient_name", notNullValue())
            .body("doctor_name", notNullValue());
```

Two things worth noticing in that response, beyond what you sent: `status` defaults to `"scheduled"` even though you never set it, which is server-side default behavior worth documenting in a test rather than discovering by accident. And `patient_name`/`doctor_name` show up even though you only ever sent numeric ids: the server is joining against the `users` table to enrich the response, which is a detail no amount of reading the request schema alone would tell you. Only calling the real endpoint and looking reveals it.

## Update

```java
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
            .body("""
                    { "status": "completed", "notes": "updated via test" }
                    """)
        .when()
            .put("/api/appointments/" + appointmentId)
        .then()
            .statusCode(200)
            .body("message", equalTo("Appointment updated successfully"));

        // Confirm the update actually took, by reading it back again.
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/" + appointmentId)
        .then()
            .statusCode(200)
            .body("status", equalTo("completed"))
            .body("notes", equalTo("updated via test"));
```

That second block matters more than it might look. A naive test would stop at "the `PUT` call returned `200` with a nice message," but a `200` and a friendly message do not actually prove the update *took*. Reading the resource back and checking the fields changed is the difference between testing "the server said OK" and testing "the server actually did the thing." This habit, verify the write by reading it back, is one you will lean on again in the database-testing module, just one layer deeper (checking the database row directly instead of going back through the API).

## Delete

```java
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .delete("/api/appointments/" + appointmentId)
        .then()
            .statusCode(200)
            .body("message", equalTo("Appointment deleted successfully"));

        // Confirm it's actually gone.
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/" + appointmentId)
        .then()
            .statusCode(404);
```

Same principle as the update step: a `200` from `DELETE` is not proof the row is gone, only that the server accepted the request. The follow-up `GET` returning `404` is the actual proof. This is the kind of double-check a real bug (say, a soft-delete flag that the delete endpoint sets but every other endpoint forgets to check) would slip right past if you only asserted on the delete call's own response.
