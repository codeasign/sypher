Negative testing asks "what happens with bad input?" Security testing asks a sharper question: "can I get access I am not supposed to have?" This module tests three specific categories against the RBAC app, broken authentication, injection, and broken authorization, and one of them turns up a real, serious finding.

## Broken object-level authorization: can a patient reach someone else's data?

You have already confirmed pieces of this in earlier modules; here is the consolidated, deliberate version. A patient should only ever see their own records:

```java
@Test
void patientCannotReadAnotherPatientsAppointmentById() {
    // Appointment id 2 belongs to a different patient than patient1 (id 20).
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.PATIENT))
    .when()
        .get("/api/appointments/2")
    .then()
        .statusCode(403)
        .body("error", equalTo("Access denied"));
}

@Test
void patientCannotDeleteAnotherPatientsAppointment() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.PATIENT))
    .when()
        .delete("/api/appointments/2")
    .then()
        .statusCode(403);
}

@Test
void patientCannotReadAnotherPatientsRecordsByPatientId() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.PATIENT))
    .when()
        .get("/api/patients/21/records") // patient1 is id 20, not 21
    .then()
        .statusCode(403);
}
```

All three pass: the app does correctly stop a patient from reaching another patient's individual records by id. This is worth testing explicitly and not just assuming, because **object-level authorization**, checking not just "is this role allowed to call this endpoint" but "is this specific user allowed to touch this specific resource," is one of the most commonly broken security controls in real APIs, and it is exactly the kind of thing that is easy to get right for the obvious case and wrong for an edge case nobody thought to test.

## Injection: does the login endpoint trust its input?

A classic first move against any login form is a SQL-injection-style payload designed to trick a query into always returning true:

```java
@Test
void sqlInjectionStyleUsernameDoesNotBypassLogin() {
    given()
        .spec(ApiSpec.base())
        .body("""
                { "username": "admin' OR '1'='1", "password": "anything" }
                """)
    .when()
        .post("/api/auth/login")
    .then()
        .statusCode(401)
        .body("error", equalTo("Invalid credentials"));
}
```

This one passes cleanly: the app correctly rejects it, which strongly suggests it is using parameterized queries (or an ORM that does so under the hood) rather than building SQL by string concatenation. Worth stating plainly: a passing security test here is a genuinely good sign, not a boring one. Confirming an attack *does not* work is exactly as valuable as finding one that does. It is evidence, not an assumption.

## Broken authentication: self-registration and privilege escalation

Here is where this module finds something real. `POST /api/auth/register` accepts a `role` field directly from the request body, as documented in the spec back in the setup module: the schema lists `role` as required, with an enum of `Administrator`, `Doctor`, `Nurse`, `Patient`. Test what happens when an anonymous, unauthenticated caller simply asks for the top one:

```java
@Test
void anyoneCanRegisterThemselvesAsAnAdministrator() {
    String username = "security_test_admin_" + System.currentTimeMillis();

    given()
        .spec(ApiSpec.base())
        .body("""
                {
                  "username": "%s",
                  "email": "%s@example.com",
                  "password": "abc12345",
                  "role": "Administrator",
                  "full_name": "Security Test"
                }
                """.formatted(username, username))
    .when()
        .post("/api/auth/register")
    .then()
        .statusCode(201);

    // Now log in as the account that was just self-created.
    String token =
            given()
                .spec(ApiSpec.base())
                .body("""
                        { "username": "%s", "password": "abc12345" }
                        """.formatted(username))
            .when()
                .post("/api/auth/login")
            .then()
                .statusCode(200)
                .body("user.role", equalTo("Administrator")) // fully self-granted
            .extract()
            .path("token");

    // And confirm that token actually carries real admin privileges.
    given()
        .spec(ApiSpec.base())
        .header("Authorization", "Bearer " + token)
    .when()
        .get("/api/users") // Administrator-only endpoint
    .then()
        .statusCode(200); // succeeds -- a self-registered account has full admin access
}
```

This one **passes end to end**, and that is the finding: any unauthenticated caller can register with `"role": "Administrator"`, log in, and immediately have full administrative access, including `GET /api/users`, the one endpoint this whole course has been using as the clearest example of "Administrator only." This is a textbook case of what is often called **mass assignment**: an endpoint accepting a field from client input (`role`) that should only ever be set by a trusted, already-privileged actor (an existing admin, deciding to grant someone a role), not by the person registering themselves.

`"%s".formatted(...)` is Java's `String.formatted`, a cleaner way to substitute values into a text block than string concatenation, useful here since the username needs to be unique per test run (`System.currentTimeMillis()` keeps repeated test runs from colliding on a username that already exists).

This is a real, verified property of this specific training app, not a hypothetical, which is exactly why it is valuable as a teaching example. A finding like this in a real system would typically get written up and reported through whatever process that team uses (a ticket, a security disclosure channel, never silently patched by a test author acting alone), rather than just left as a passing test with no further action. In this course, writing the test that proves it, precisely and reproducibly, *is* the deliverable. That is what "API security testing" concretely looks like day to day: turning "I suspect this might be exploitable" into a test that either proves or disproves it beyond doubt.

## Parameter tampering: can a role be smuggled in on an update?

Registration is not the only place a client-controlled field is worth being suspicious of. Check whether the same trick works on `PUT /api/users/{id}`, which the spec documents as only accepting `full_name`, `phone`, and `email`:

```java
@Test
void attemptingToSmuggleARoleChangeThroughUserUpdateIsIgnored() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.PATIENT))
        .body("""
                { "full_name": "Still Just A Patient", "role": "Administrator" }
                """)
    .when()
        .put("/api/users/20") // patient1's own user id
    .then()
        .statusCode(200);

    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
    .when()
        .get("/api/users/20")
    .then()
        .statusCode(200)
        .body("role", equalTo("Patient")); // unchanged -- this endpoint ignores the extra field
}
```

This one behaves correctly: the update endpoint only reads the fields it is documented to accept and silently ignores `role` rather than acting on it, so this particular path is safe even though the registration path is not. That contrast is worth sitting with: two endpoints in the same app, both receiving a stray `role` field from a client, and only one of them actually uses it. Security testing means checking each path on its own terms, not assuming a finding on one endpoint generalizes to every endpoint that looks similar.

## Try it

Test whether the same self-registration trick works with `"role": "Doctor"` instead: register, log in, and confirm whether the resulting account can create a medical record (`POST /api/medical-records`, which you know from the RBAC module requires the Doctor role). If it works the same way, you have confirmed this is not specific to the Administrator role. It is the registration endpoint trusting *any* client-supplied role, which is the more precise, and more damning, way to describe the actual finding.
