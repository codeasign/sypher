This course assumes you are already comfortable with Java basics: variables, methods, classes, maybe a bit of Maven. What it does not assume is any API testing experience, so we start from the very beginning of that: getting a real backend running on your machine, and proving to yourself that you can talk to it before you write a single test.

Every module in this course runs against the same system under test: a 4-role RBAC (Role-Based Access Control) healthcare app called `rbac-healthcare-system`. It has an Express API, a SQLite database, JWT authentication, and a Swagger page documenting every endpoint. Because this is a Java course testing a Node/Express backend, every request you send is a real HTTP call over the network. There is no way to import the app in-process the way a Node test suite could, so your Java test project and the RBAC backend are always two completely separate processes. By the end of this page, that backend will be running on your machine, seeded with realistic data, your own Maven test project will exist alongside it, and you will have made one real request to prove the wiring works.

## Confirm your JDK and Maven are ready

You will need a JDK installed, version 17 or later is what this course uses. Check what you have:

```bash
java -version
mvn -version
```

You should see a Java version and a Maven version print out, and `mvn -version` will also confirm which JDK Maven itself is running on. Make sure that matches. If either command is not found, install a JDK (Temurin/Adoptium builds are a solid free choice) and [Maven](https://maven.apache.org/install.html) before continuing. This course uses Maven throughout rather than Gradle. Either works fine with RestAssured; Maven is just the more common default for this kind of project.

## Clone and run the RBAC app

Clone the system under test:

```bash
git clone https://github.com/codedbyabhishekc/rbac-healthcare-system.git
cd rbac-healthcare-system
```

This course only touches the `backend/` folder. There is no browser or UI involved anywhere in this course, and your Java project will live in its own folder entirely separate from this clone.

```bash
cd backend
npm install
mkdir database
```

The `database` folder is where the app's SQLite file lives once the server creates it. It is not checked into the repo, so you have to make it yourself.

Next, create a `.env` file inside `backend/`:

```bash
PORT=5000
JWT_SECRET=any-long-random-string-you-want
NODE_ENV=development
```

`JWT_SECRET` is the key the server uses to sign and verify login tokens. You will see exactly how that works in the authentication module. For local development, any long random string is fine; it just needs to exist.

Start the server once to confirm it boots and creates its database:

```bash
npm start
```

You should see:

```bash
Connected to SQLite database
Database initialized successfully
Server is running on port 5000
Swagger documentation available at http://localhost:5000/api-docs
```

Leave that running, and open [http://localhost:5000/api-docs](http://localhost:5000/api-docs) in a browser. That is the Swagger UI, a live, browsable list of every endpoint this app exposes, generated straight from comments in the route files. You will come back to this page a lot; whenever you are unsure what an endpoint expects, it is the fastest place to check. You will also see how to pull its raw spec as JSON in the OpenAPI module; Swagger UI itself is just a renderer for that underlying spec.

## Seed the database

A freshly created database is empty, and an empty database makes for a boring and unrealistic test suite. Stop the server (`Ctrl+C`) and run the seed script:

```bash
npm run seed
```

This populates the database with 3 Administrators, 8 Doctors, 7 Nurses, 15 Patients, 20 appointments, and 15 medical records. Every account uses the password `pass@123`, except the default admin account, which uses `admin` / `admin123`. That is the login you will use most often across this course. Start the server back up with `npm start` once seeding finishes, and leave it running for the rest of this page.

## Make one real request

Before touching Java or Maven at all, let's prove the environment works with a plain `curl` request, the same login request any client of this API would make:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```

You should get back something like this (the token itself will be a long, unreadable string, which is expected):

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": 1,
    "username": "admin",
    "email": "admin@hospital.com",
    "role": "Administrator",
    "full_name": "System Administrator"
  }
}
```

That response is the whole app in miniature: you sent credentials, the server checked them against the database, and it handed back a signed token plus the logged-in user's details. Every protected endpoint in this course expects that token on later requests. You will build a small reusable request spec around this exact call in the authentication module, so you never have to retype this logic again.

## Set up your own Maven project

With the backend confirmed working, create a completely separate folder for your Java test project. Do not put this inside the `rbac-healthcare-system` clone:

```bash
mkdir rbac-api-tests
cd rbac-api-tests
```

Create a `pom.xml` in that folder:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.example</groupId>
  <artifactId>rbac-api-tests</artifactId>
  <version>1.0.0</version>

  <properties>
    <maven.compiler.source>17</maven.compiler.source>
    <maven.compiler.target>17</maven.compiler.target>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <junit.version>5.10.2</junit.version>
    <restassured.version>5.4.0</restassured.version>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>${junit.version}</version>
      <scope>test</scope>
    </dependency>
    <dependency>
      <groupId>io.rest-assured</groupId>
      <artifactId>rest-assured</artifactId>
      <version>${restassured.version}</version>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.2.5</version>
      </plugin>
    </plugins>
  </build>
</project>
```

What each piece is for, since you will be looking at this file again in the next module: `junit-jupiter` is a single dependency that pulls in the whole JUnit 5 API, engine, and params modules together, rather than adding each separately. `rest-assured` is the library you will use to send HTTP requests and assert on responses. It is built specifically for testing REST APIs, with a fluent style you will meet properly in the next two modules. Both are scoped `test`, since neither belongs in a production build. This project only ever produces tests, but Maven's convention still expects that scope to be explicit. The `maven-surefire-plugin` is what runs your tests when you type `mvn test`; pinning its version avoids surprises from Maven silently picking a different default over time.

Create the standard Maven test source folder and one placeholder test:

```bash
mkdir -p src/test/java/com/example/rbactests
```

`src/test/java/...` is Maven's fixed convention for where test code lives. Nothing here needs configuring; Maven finds anything under `src/test/java` automatically as long as the class name ends in `Test` (or starts with `Test`, but ending in `Test` is the more common style and what this course uses throughout).

Create `src/test/java/com/example/rbactests/SmokeTest.java`:

```java
package com.example.rbactests;

import io.restassured.RestAssured;
import io.restassured.response.Response;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class SmokeTest {

    @Test
    void loginEndpointRespondsAndReturnsAToken() {
        Response response = RestAssured
                .given()
                    .baseUri("http://localhost:5000")
                    .contentType("application/json")
                    .body("{\"username\":\"admin\",\"password\":\"admin123\"}")
                .when()
                    .post("/api/auth/login");

        System.out.println("Response body: " + response.getBody().asString());

        assertEquals(200, response.getStatusCode());
    }
}
```

`@Test` marks this method as a test case JUnit should run. Without it, JUnit ignores the method entirely, no matter what it is named. `RestAssured.given()` starts a request definition, `.when()` marks the point where you specify the call being made, and `.post(...)` sends it. You will break this `given()/when()/then()` shape down properly in the next two modules; this is just enough to prove the environment works. The `System.out.println` is not part of the test's pass/fail logic; it is there so you can see the real response body while you are getting your bearings, a habit this course leans on early and drops once assertions do the checking for you.

Run it:

```bash
mvn test
```

You should see Maven download dependencies on the first run, then a `BUILD SUCCESS` with `Tests run: 1, Failures: 0, Errors: 0` in the output, plus that response body printed to the console along the way. If you see a connection error instead, double check the backend from earlier is still running on port 5000.

## Try it

With the server still running, change `SmokeTest` to log in as a different seeded user. Try `doctor1` with password `pass@123` instead of `admin`/`admin123`. Print the `role` field out of the response body and confirm it says `"Doctor"` instead of `"Administrator"`. That role field is what drives every permission check you will test later in this course, so it is worth seeing it change with your own eyes before moving on.
