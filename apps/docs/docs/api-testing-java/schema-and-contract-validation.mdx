Every assertion so far has checked individual fields — `body("status", equalTo("scheduled"))`, one at a time. That works, but it's tedious to keep exhaustive, and it's easy to add a new field to a response and never notice your tests didn't check it. This module validates a **whole response shape at once** against a JSON Schema, catching contract drift automatically instead of field by field.

## Adding the schema validation module

RestAssured's JSON Schema support ships as a separate artifact, since not every project needs it. Add it to `pom.xml`, alongside `rest-assured` itself:

```xml
<dependency>
    <groupId>io.rest-assured</groupId>
    <artifactId>json-schema-validator</artifactId>
    <version>5.4.0</version>
    <scope>test</scope>
</dependency>
```

Keep its version matching `rest-assured`'s own version — they're released together and expected to be used as a pair.

## Writing a schema from a real response

A JSON Schema describes the *shape* a response must have: which fields exist, their types, which are required, and constraints like allowed enum values. Rather than inventing one from imagination, base it on a real response you've actually seen. Here's what `GET /api/appointments/{id}` really returns:

```json
{
  "id": 22,
  "patient_id": 20,
  "doctor_id": 5,
  "appointment_date": "2026-09-15T10:00:00",
  "status": "scheduled",
  "reason": "CRUD module test",
  "notes": null,
  "created_at": "2026-08-15 23:08:21",
  "updated_at": "2026-08-15 23:08:21",
  "patient_name": "John Smith",
  "patient_email": "patient1@email.com",
  "doctor_name": "Dr. James Wilson",
  "doctor_email": "doctor1@hospital.com"
}
```

Create `src/test/resources/schemas/appointment-schema.json`:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["id", "patient_id", "doctor_id", "appointment_date", "status", "reason"],
  "properties": {
    "id": { "type": "integer" },
    "patient_id": { "type": "integer" },
    "doctor_id": { "type": "integer" },
    "appointment_date": { "type": "string" },
    "status": { "type": "string", "enum": ["scheduled", "completed", "cancelled"] },
    "reason": { "type": "string" },
    "notes": { "type": ["string", "null"] },
    "created_at": { "type": "string" },
    "updated_at": { "type": "string" },
    "patient_name": { "type": "string" },
    "patient_email": { "type": "string" },
    "doctor_name": { "type": "string" },
    "doctor_email": { "type": "string" }
  }
}
```

`src/test/resources` is Maven's standard location for non-Java files a test needs — anything under it lands on the test classpath automatically, which is what lets RestAssured load it by a plain relative path. `notes` is typed `["string", "null"]` rather than just `"string"` specifically because you've seen it come back `null` in a real response — a schema that only allowed `"string"` would fail every appointment that has no notes, which is a real, common state, not an edge case. `status` uses `"enum"` because the app's own update endpoint only accepts `scheduled`/`completed`/`cancelled` — you saw that in the spec's request schema for `PUT /api/appointments/{id}` back in the CRUD module, so the response schema should hold the same three values to a matching standard.

## Validating a response against it

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static io.restassured.module.jsv.JsonSchemaValidator.matchesJsonSchemaInClasspath;

class SchemaValidationTest {

    @Test
    void appointmentResponseMatchesItsSchema() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/1")
        .then()
            .statusCode(200)
            .body(matchesJsonSchemaInClasspath("schemas/appointment-schema.json"));
    }
}
```

One assertion, and it's checking every field's presence, every field's type, and the `status` enum all at once — a lot more coverage than the equivalent chain of a dozen `.body("field", ...)` calls, and it fails with a specific, readable diff telling you exactly which field or type didn't match if a real response ever drifts from this shape.

## Catching drift on purpose

To see this actually catch something, deliberately break the schema and watch it fail. Change `"status": { "type": "string", "enum": [...] }` in the schema file to `"enum": ["scheduled", "completed"]` — dropping `"cancelled"` — then run a test against an appointment you know is cancelled:

```java
@Test
void cancelledAppointmentFailsAgainstAnIncompleteEnum() {
    // First, put an appointment into "cancelled" status.
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .body("""
                { "status": "cancelled" }
                """)
    .when()
        .put("/api/appointments/1");

    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
    .when()
        .get("/api/appointments/1")
    .then()
        .statusCode(200)
        .body(matchesJsonSchemaInClasspath("schemas/appointment-schema.json")); // fails now
}
```

That failure is the whole point of this module: schema validation just caught a real appointment in a real, valid state that the schema didn't account for. In a real project this is exactly how schema drift gets caught — not by someone remembering to update a hand-written schema every time the app's behavior legitimately changes, but by a test failing loudly the moment reality and the schema disagree. Revert the schema back to all three status values before moving on.

## Try it

Write a schema for the `/api/patients` list response — remember this endpoint returns a JSON *array*, so the schema's top-level `"type"` should be `"array"`, with an `"items"` key describing the shape of each element instead of `"properties"` directly. Validate a real `GET /api/patients` response against it, authenticated as an Administrator.
