"Coverage" usually means code coverage: the percentage of lines or branches a test suite actually executes. That is a meaningful number for the RBAC app's own developers, working inside its codebase. It is the wrong number for this course's suite, since these tests never execute a single line of the app's code directly. Every one of them is an HTTP call from a completely separate project. What matters here is **endpoint coverage**: of everything the spec documents, how much of it does your suite actually exercise?

## Why code coverage doesn't apply here

A black-box test suite has no way to measure code coverage of the system it is testing, full stop. Tools like JaCoCo instrument the *bytecode being run*, and this suite's bytecode is entirely your own Java test code, not the RBAC app's Node/Express code. If code coverage numbers matter to a team running an app like this, they would need to instrument the *app itself* server-side and correlate that against the traffic this test suite generates, a legitimate thing to do, but a different tool and a different job than what this module covers.

## What endpoint coverage means instead

You already built the tool for this back in Module 06: `EndpointChecklist.buildFromSpec()` returns every method/path combination the spec documents. Endpoint coverage is simply this: for each of those, has this suite actually called it, at least once, with a real assertion attached?

## Building a coverage report

```java
package com.example.rbactests.support;

import java.util.List;
import java.util.Set;

public final class CoverageTracker {

    // Populate this by hand as you confirm each endpoint has a real test --
    // in a larger project this would be generated by scanning test source
    // for calls to a wrapped RestAssured client instead of maintained by hand.
    private static final Set<String> TESTED = Set.of(
            "POST /api/auth/login",
            "POST /api/auth/register",
            "GET /api/appointments",
            "POST /api/appointments",
            "GET /api/appointments/{id}",
            "PUT /api/appointments/{id}",
            "DELETE /api/appointments/{id}",
            "GET /api/medical-records",
            "POST /api/medical-records",
            "DELETE /api/medical-records/{id}",
            "GET /api/patients",
            "GET /api/patients/{patientId}/records",
            "GET /api/users",
            "GET /api/users/role/{role}",
            "PUT /api/users/{id}"
    );

    private CoverageTracker() {
    }

    public static void printReport() {
        List<EndpointChecklist.Endpoint> all = EndpointChecklist.buildFromSpec();
        int covered = 0;

        for (EndpointChecklist.Endpoint endpoint : all) {
            String key = endpoint.method() + " " + endpoint.path();
            boolean tested = TESTED.contains(key);
            if (tested) {
                covered++;
            }
            System.out.printf("%-6s %-4s %s%n", tested ? "[x]" : "[ ]", endpoint.method(), endpoint.path());
        }

        double percentage = 100.0 * covered / all.size();
        System.out.printf("%nCoverage: %d/%d endpoints (%.1f%%)%n", covered, all.size(), percentage);
    }
}
```

Run `CoverageTracker.printReport()` and you get a checklist straight out of the spec, marked against what this course's suite has actually exercised by this point:

```bash
[x]  POST /api/appointments
[x]  GET  /api/appointments
[x]  GET  /api/appointments/{id}
[x]  PUT  /api/appointments/{id}
[x]  DELETE /api/appointments/{id}
[x]  POST /api/auth/register
[x]  POST /api/auth/login
[x]  POST /api/medical-records
[x]  GET  /api/medical-records
[ ]  GET  /api/medical-records/{id}
[x]  DELETE /api/medical-records/{id}
[ ]  PUT  /api/medical-records/{id}
[x]  GET  /api/patients/{patientId}/records
[x]  GET  /api/patients
[x]  GET  /api/users
[x]  PUT  /api/users/{id}
[ ]  DELETE /api/users/{id}
[x]  GET  /api/users/role/{role}

Coverage: 15/18 endpoints (83.3%)
```

Three real gaps, named specifically rather than left as a vague sense that "coverage could be better": `GET /api/medical-records/{id}`, `PUT /api/medical-records/{id}`, and `DELETE /api/users/{id}` have never been called by a test in this suite. That is a concrete, actionable list, exactly what a coverage report is supposed to produce.

## Endpoint coverage is a floor, not a ceiling

Reaching 100% endpoint coverage means every route has been called *at least once*. It says nothing about whether it has been called with every role, every invalid input, every boundary condition the RBAC and negative-testing modules cared about. A suite could hit 100% endpoint coverage with one happy-path test per route and still miss the self-registration privilege-escalation finding from the security module entirely: that gap would not show up here as a coverage number, because the endpoint itself *was* called, just not with the input that mattered. Treat endpoint coverage as the first, cheapest question to ask, "have we even touched this route," not the last one.

## Try it

Write the three tests that close the gaps this report found (`GET /api/medical-records/{id}`, `PUT /api/medical-records/{id}`, and `DELETE /api/users/{id}`), then add all three keys to `TESTED` and confirm the report now shows 100%. For the `DELETE /api/users/{id}` test specifically, decide which role should be allowed to call it based on the spec's own summary, and verify that with a real request rather than assuming.
