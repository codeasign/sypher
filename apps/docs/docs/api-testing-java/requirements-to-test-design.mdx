Every test in this course so far has tested something that already existed — you could always start by calling the real endpoint and seeing what came back. Real feature work usually runs the other direction: a requirement or user story arrives *before* the code does, and designing the test cases is part of understanding what "done" actually means, not something that happens only after the code is written.

## A feature requirement, stated the way a ticket usually is

> As a Nurse, I want to be able to update a patient's phone number and email directly, without needing a Doctor or Administrator to do it, so that routine contact-detail corrections don't need to go through someone else.

That's a realistic requirement, written the way a product ticket typically reads — a role, a capability, a reason. It's also, deliberately, not fully specified: it doesn't say what happens if the Nurse tries to update a field beyond phone/email, what happens if the patient id doesn't exist, or whether a Nurse can do this for *any* patient or only ones they've had an appointment with. Filling in those gaps *before* writing any test code is the actual subject of this module.

## Turning it into concrete questions

Work through the requirement systematically, the same way the RBAC and negative-testing modules approached endpoints that already existed:

**Who can do this, precisely?**
- Nurse: should succeed (the requirement's core ask).
- Doctor, Administrator: presumably still allowed too — the requirement adds a capability for Nurse, it doesn't obviously say to *remove* it from anyone who might already have it via `PUT /api/users/{id}`.
- Patient: almost certainly should not be able to update *another* patient's contact details this way, even their own role's existing self-update path aside.

**What exactly can be changed?**
- `phone` and `email`, per the requirement.
- Everything else `PUT /api/users/{id}` already accepts (`full_name`) — does a Nurse get that too, or only phone/email specifically? This is a real ambiguity the ticket doesn't resolve, and it's exactly the kind of question worth raising with whoever wrote the requirement *before* writing tests that guess at an answer, not after.

**What are the failure cases?**
- A Nurse targeting a `patientId` that doesn't exist.
- A Nurse sending an invalid `email` format (you already know from the negative-testing module that this app is often more permissive with input than a spec might suggest — worth checking directly rather than assuming validation exists).
- A Nurse attempting this against another Nurse's or a Doctor's own user record, not a Patient's.

## From questions to a test case list

Each answered question becomes one or more concrete test cases — the same shape as the checklists Module 06 generated from the spec, just authored by hand this time, ahead of any implementation:

| # | Case | Expected |
|---|---|---|
| 1 | Nurse updates a patient's phone and email | 200, fields actually change |
| 2 | Doctor updates a patient's phone and email | 200 (existing behavior, shouldn't regress) |
| 3 | Administrator updates a patient's phone and email | 200 (existing behavior, shouldn't regress) |
| 4 | Patient attempts to update another patient's contact info | 403 |
| 5 | Nurse targets a nonexistent patient id | 404 |
| 6 | Nurse sends an obviously malformed email | TBD — confirm actual validation behavior, don't assume |
| 7 | Nurse also sends `full_name` in the same request | TBD — raise with requirement author before assuming an answer |

Rows 6 and 7 are marked `TBD` deliberately, not filled in with a guess — this table is meant to surface exactly these ambiguities to whoever owns the requirement, before a test gets written that quietly encodes an assumption nobody actually agreed to. Writing "TBD, needs clarification" into a test design document is a completely legitimate outcome of this exercise, and often the most valuable line in the whole table.

## Writing tests against the actual current behavior first

Since `PUT /api/users/{id}` already exists — this requirement is extending existing behavior, not introducing a brand-new endpoint — rows 2 and 3 (Doctor and Administrator, unchanged) can be written and verified against the app *right now*, before the Nurse-specific change ships, precisely to catch a regression if the new work accidentally narrows access instead of only widening it:

```java
@Test
void doctorCanStillUpdateAPatientsContactInfo() {
    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.DOCTOR))
        .body("""
                { "phone": "555-0199", "email": "updated-by-doctor@example.com" }
                """)
    .when()
        .put("/api/users/20")
    .then()
        .statusCode(200);
}
```

Row 1 (Nurse succeeding) can be written now too, as a test you *expect to fail* until the feature ships — a deliberately red test is a legitimate, useful artifact: it's a precise, executable statement of what "done" means, and it turns green the moment the real implementation lands, with no ambiguity about whether the feature actually works or just looks finished.

## The general shape of this process

1. Read the requirement as written, and resist filling gaps with assumptions.
2. List every role, every valid case, and every failure case you can think of — reusing the RBAC-matrix and negative-testing habits from earlier in this course.
3. Mark genuine ambiguities as questions, not guesses.
4. Write tests for behavior that already exists and shouldn't regress, immediately.
5. Write tests for the new behavior as failing placeholders, to be turned green by the real implementation.

## Try it

Take this requirement: *"As an Administrator, I want to deactivate a user account so they can no longer log in, without deleting their historical appointments or medical records."* Work through the same process — list the roles, the valid cases, the failure cases, and any genuine ambiguities the requirement leaves open. Note that this app doesn't currently support account deactivation at all (only `DELETE /api/users/{id}`, which is a real deletion) — write down what test cases you'd want *before* anyone starts implementing it, the same discipline this module just walked through.
