Every module up to this point has focused on one technique at a time, mostly against appointments and medical records. This capstone points the whole toolkit — the spec, auth, CRUD, the RBAC matrix, negative cases, schema validation, and the CI pipeline — at a part of the app this course has only ever touched in passing: the `/api/users` endpoints.

## The area you're covering

Users has come up constantly as a supporting character — you've logged in through it, decoded roles out of it, checked admin-only access through it — but it's never gotten a complete suite of its own. The coverage module named exactly this gap: `GET /api/users/{id}`, `PUT /api/users/{id}`, and `DELETE /api/users/{id}` were never fully exercised. It's a good capstone target for that reason — it's real, it's already partially familiar, and closing it out means applying everything from this course end to end, not learning anything new.

Here's what it actually does, and the real, verified rules governing it:

- `GET /api/users` — list every user. Administrator only.
- `GET /api/users/{id}` — view one user. An Administrator can view anyone (confirmed: a lookup for a nonexistent id returns `404`, not `403`, meaning admin gets past the access check every time); anyone else gets `403` viewing someone other than themselves, `200` viewing their own record.
- `PUT /api/users/{id}` — update `full_name`, `phone`, `email`. Same ownership rule as viewing.
- `DELETE /api/users/{id}` — Administrator only; every other role gets `403` with `requiredRoles: ["Administrator"]`.
- `GET /api/users/role/{role}` — list users by role. Open to any authenticated user, no restriction at all.

## Start from the spec, the way Module 05 did

```java
JsonPath spec = OpenApiSpec.spec();
System.out.println(spec.getMap("paths.'/api/users/{id}'"));
```

Confirm the spec's documented status codes match what you build tests around — `GET`/`PUT` document `200` and `404`, `DELETE` documents `200` and `404`. Nothing here documents `403` explicitly (the same kind of spec gap the negative-testing and RBAC modules kept finding), which is worth a comment in the suite itself, not a silent assumption.

## Building the suite, end to end

**Package and setup.** Nothing new to install — every helper this suite needs already exists from earlier modules:

```java
package com.example.rbactests.users;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.EnumSource;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;
```

**The RBAC matrix**, using `@EnumSource` the way the parameterized-testing module covered — since every role needs checking against the same endpoint:

```java
class UserListRbacTest {

    @ParameterizedTest(name = "{0} listing all users")
    @EnumSource(ApiSpec.Role.class)
    void listUsersIsAdministratorOnly(ApiSpec.Role role) {
        int expectedStatus = role == ApiSpec.Role.ADMINISTRATOR ? 200 : 403;

        given()
            .spec(ApiSpec.authenticatedAs(role))
        .when()
            .get("/api/users")
        .then()
            .statusCode(expectedStatus);
    }
}
```

**Ownership, not just role** — this endpoint's real rule isn't a flat allow/deny, it's "yourself, or an admin," which needs its own tests rather than a role table:

```java
class UserOwnershipTest {

    @Test
    void aPatientCanViewTheirOwnProfile() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.PATIENT))
        .when()
            .get("/api/users/20") // patient1's own id
        .then()
            .statusCode(200)
            .body("id", equalTo(20))
            .body("username", equalTo("patient1"));
    }

    @Test
    void aPatientCannotViewSomeoneElsesProfile() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.PATIENT))
        .when()
            .get("/api/users/5") // doctor1's id, not patient1's
        .then()
            .statusCode(403)
            .body("error", equalTo("Access denied"));
    }

    @Test
    void anAdministratorCanViewAnyonesProfile() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/users/20")
        .then()
            .statusCode(200);
    }
}
```

**CRUD, with a real read-after-write check** — the same discipline the CRUD module insisted on:

class UserUpdateTest {

    @Test

**Delete, Administrator only** — the exact gap the coverage module flagged, closed:

```java
class UserDeleteTest {

    @Test
    void nonAdminCannotDeleteAUser() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.NURSE))
        .when()
            .delete("/api/users/20")
        .then()
            .statusCode(403)
            .body("requiredRoles[0]", equalTo("Administrator"));
    }

    @Test
    void administratorCanDeleteAUser() {
        // Create a throwaway user via registration first, so this test
        // doesn't destroy real seed data -- the fixtures module's discipline.
        String username = "capstone_delete_target_" + System.currentTimeMillis();
        given()
            .spec(ApiSpec.base())
            .body("""
                    {
                      "username": "%s", "email": "%s@example.com", "password": "abc12345",
                      "role": "Patient", "full_name": "Delete Target"
                    }
                    """.formatted(username, username))
        .when()
            .post("/api/auth/register")
        .then()
            .statusCode(201);

        int newUserId =
                given()
                    .spec(ApiSpec.base())
                    .body("""
                            { "username": "%s", "password": "abc12345" }
                            """.formatted(username))
                .when()
                    .post("/api/auth/login")
                .then()
                .extract()
                .path("user.id");

        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .delete("/api/users/" + newUserId)
        .then()
            .statusCode(200)
            .body("message", equalTo("User deleted successfully"));
    }
}
```

**Negative cases**, the way Module 11 covered — don't assume, confirm:

```java
class UserNegativeTest {

    @Test
    void noTokenReturns401() {
        given()
            .spec(ApiSpec.base())
        .when()
            .get("/api/users")
        .then()
            .statusCode(401);
    }

    @Test
    void aNonexistentUserIdReturns404ForAnAdministrator() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/users/999999")
        .then()
            .statusCode(404)
            .body("error", equalTo("User not found"));
    }
}
```

**Schema validation**, the way Module 09 covered — write `src/test/resources/schemas/user-schema.json` from a real response the way you built the appointment schema, and add one assertion using it against `GET /api/users/20`.

**CI.** Nothing to add here at all — these files live under `src/test/java/com/example/rbactests/users/`, Surefire's default naming pattern picks up every `*Test.java` class automatically, and the GitHub Actions workflow from the reporting module already runs `mvn test` against the whole project. Push these files, and they're covered by the required check without touching the workflow at all.

## Where to go from here

You started this course sending a plain `curl` request and checking it returned a token. By this point you've built a suite that covers CRUD, the full RBAC matrix across 4 roles, schema and OpenAPI contract validation, direct database verification, deliberate security testing that found a real privilege-escalation bug, parallel execution, and a CI pipeline that gates merges on all of it. That's not a toy exercise — it's the actual shape of API test ownership on a real team.

If you want to take these same habits — the same RBAC app, the same real permission matrix — and point them at a browser instead of an API, this site's Playwright Test Automation course picks up from here, testing the same application's UI directly. And if API testing itself is what you want to go deeper on in a different language, this site's TypeScript and Python editions of this exact course cover the same ground with a different toolchain, so you can compare how the same problems get solved elsewhere.

Either way — you're not new to API testing anymore. You've found a real bug, documented a real security gap, and built a real, CI-gated suite from nothing. That's the job.
