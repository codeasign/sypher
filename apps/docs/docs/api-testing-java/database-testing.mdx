The CRUD module verified writes by reading them back *through the API*. That proves the API's contract holds, but it doesn't prove the database itself ended up in the state you'd expect — an API could theoretically cache a response, or a bug could make reads and writes disagree with what's actually persisted. This module goes one layer deeper: connecting to the RBAC app's real SQLite database directly, to verify what's actually stored.

## Why this is still black-box testing

This course tests everything through real HTTP calls — Java has no way to import the Express app in-process. Reading the underlying SQLite file directly doesn't change that: you're still never calling into the app's own code, and you're still only *reading*, never writing, through anything but the API. Think of it as an extra verification layer, not a different testing style — every write in this module still goes through `POST`/`PUT`/`DELETE` exactly as before; only the *checking* reaches past the API, straight to the data it produced.

## Connecting to the database

The backend stores its data in `backend/database/rbac.db`, a plain SQLite file on disk — visible in the config file's own database path (`path.join(__dirname, '../../database/rbac.db')`). Add a JDBC driver for SQLite to `pom.xml`:

```xml
<dependency>
    <groupId>org.xerial</groupId>
    <artifactId>sqlite-jdbc</artifactId>
    <version>3.45.3.0</version>
    <scope>test</scope>
</dependency>
```

Then a small helper to open a connection:

```java
package com.example.rbactests.support;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public final class Database {

    // Adjust this path to wherever you cloned rbac-healthcare-system relative
    // to this Maven project -- this course assumes the two are sibling folders.
    private static final String DB_PATH = "../rbac-healthcare-system/backend/database/rbac.db";

    private Database() {
    }

    public static Connection connect() throws SQLException {
        return DriverManager.getConnection("jdbc:sqlite:" + DB_PATH);
    }
}
```

`DriverManager.getConnection("jdbc:sqlite:...")` is standard JDBC — the `sqlite-jdbc` driver registers itself automatically once it's on the classpath, so no explicit driver-loading code is needed the way older JDBC code sometimes required.

## Verifying a write actually persisted

Create an appointment through the API, exactly as the CRUD module did, but this time verify the row directly in the database instead of reading it back through another API call:

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import com.example.rbactests.support.Database;
import org.junit.jupiter.api.Test;

import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;

import static io.restassured.RestAssured.given;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

class DatabaseVerificationTest {

    @Test
    void creatingAnAppointmentActuallyInsertsARow() throws Exception {
        int appointmentId =
                given()
                    .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
                    .body("""
                            {
                              "patient_id": 20,
                              "doctor_id": 5,
                              "appointment_date": "2026-10-05T09:00:00",
                              "reason": "database verification test"
                            }
                            """)
                .when()
                    .post("/api/appointments")
                .then()
                    .statusCode(201)
                .extract()
                    .path("appointmentId");

        try (Connection conn = Database.connect();
             PreparedStatement stmt = conn.prepareStatement(
                     "SELECT patient_id, doctor_id, status, reason FROM appointments WHERE id = ?")) {

            stmt.setInt(1, appointmentId);
            try (ResultSet rs = stmt.executeQuery()) {
                assertTrue(rs.next(), "Expected a row for appointment id " + appointmentId);
                assertEquals(20, rs.getInt("patient_id"));
                assertEquals(5, rs.getInt("doctor_id"));
                assertEquals("scheduled", rs.getString("status"));
                assertEquals("database verification test", rs.getString("reason"));
            }
        }

        // Clean up.
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .delete("/api/appointments/" + appointmentId);
    }
}
```

The `try (Connection conn = ...)` and `try (... ResultSet rs = ...)` blocks are **try-with-resources** — both `Connection` and `ResultSet` implement `AutoCloseable`, and this syntax guarantees each is closed automatically once the block exits, even if an assertion inside throws. Without it, a failed assertion partway through would leave the connection open, which adds up fast across a suite with hundreds of tests. `PreparedStatement` with `?` placeholders, rather than building the SQL string with concatenation, isn't optional style here — it's the same SQL-injection defense the app's own login endpoint benefits from, applied to your test code this time.

## Verifying a delete actually removed the row

The mirror image — proving `DELETE` didn't just return a friendly `200` while leaving the row behind:

```java
@Test
void deletingAnAppointmentActuallyRemovesTheRow() throws Exception {
    int appointmentId =
            given()
                .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
                .body("""
                        {
                          "patient_id": 20,
                          "doctor_id": 5,
                          "appointment_date": "2026-10-06T09:00:00",
                          "reason": "delete verification test"
                        }
                        """)
            .when()
                .post("/api/appointments")
            .then()
                .statusCode(201)
            .extract()
                .path("appointmentId");

    given()
        .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
    .when()
        .delete("/api/appointments/" + appointmentId)
    .then()
        .statusCode(200);

    try (Connection conn = Database.connect();
         PreparedStatement stmt = conn.prepareStatement(
                 "SELECT COUNT(*) AS row_count FROM appointments WHERE id = ?")) {

        stmt.setInt(1, appointmentId);
        try (ResultSet rs = stmt.executeQuery()) {
            rs.next();
            assertEquals(0, rs.getInt("row_count"));
        }
    }
}
```

This is a genuinely stronger check than the CRUD module's "read it back through the API and confirm `404`" — that only proves the API's *read path* agrees the row is gone; this proves the row is *actually gone from the table*, which rules out a whole class of bug where a delete endpoint sets some kind of hidden flag instead of really removing anything, and every read path just happens to respect that flag too.

## Test isolation and cleanup, revisited

Every test in this module cleans up its own row via the API, matching the fixtures module's convention — direct database access here is for *verification*, never for cleanup, precisely to keep every write flowing through the one path (the real API) whose behavior this whole course exists to test. A test suite that started deleting rows directly from the database to "clean up faster" would stop testing the app's own delete endpoint at all, which defeats the purpose.

## Try it

Write a test that creates a medical record through the API (as Doctor), then queries the `medical_records` table directly to confirm `visit_date` was set automatically even though your request body never included it (check the table's `CREATE TABLE` definition's `DEFAULT CURRENT_TIMESTAMP` behavior with your own eyes, in the actual stored row, rather than trusting that a default like this always works the way you'd expect).
