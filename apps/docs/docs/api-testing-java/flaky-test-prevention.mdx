A flaky test is one that passes sometimes and fails other times, with no code change in between. They're worse than a test that just always fails — a consistently failing test gets fixed or deleted; a flaky one gets ignored, re-run until it passes, and eventually trained everyone on the team to stop trusting the suite at all. This module covers the specific ways this course's own test style could become flaky, and how the patterns you've already been using mostly prevent it.

## Shared state between tests

The most common source of real flakiness in an API suite is tests that silently depend on each other's side effects. Picture two tests, written carelessly:

```java
// DON'T: this couples two tests together through shared mutable state
class FragileOrderDependentTest {

    static int sharedAppointmentId;

    @Test
    void test1_createsAnAppointment() {
        sharedAppointmentId =
                given().spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
                    .body("""{ "patient_id": 20, "doctor_id": 5, "appointment_date": "2026-11-01T09:00:00", "reason": "x" }""")
                .when().post("/api/appointments")
                .then().statusCode(201).extract().path("appointmentId");
    }

    @Test
    void test2_readsTheAppointmentFromTest1() {
        given().spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
            .when().get("/api/appointments/" + sharedAppointmentId)
            .then().statusCode(200);
    }
}
```

This works *by accident* as long as JUnit happens to run `test1` before `test2` — but JUnit 5 does not guarantee method execution order by default, and the parallel-execution module coming up next will make that assumption actively dangerous, not just theoretically risky. If `test2` runs first, `sharedAppointmentId` is still `0`, and the test fails for a reason that has nothing to do with a real bug. Every test in this course from the fixtures module onward has instead created what it needs in its own `@BeforeEach` and cleaned up in its own `@AfterEach` — that pattern isn't just good practice, it's what makes these tests immune to this exact category of flakiness.

## Timing and hardcoded waits

Never reach for `Thread.sleep(...)` to "wait for the server to catch up" — it's a guess, and guesses about timing are exactly what produces flaky tests: too short and the assertion runs before the state is ready, too long and every test run wastes time waiting on a delay that usually wasn't needed at all. Every write in this course's tests has instead been followed by an assertion that directly confirms the expected state — the CRUD module's "read it back to confirm the update took" pattern is doing double duty here: it's not just more thorough than trusting a `200`, it's also what makes the test deterministic instead of timing-dependent, since a request/response cycle against this backend either has completed by the time RestAssured returns control to you, or it hasn't — there's no "probably done by now" state to guess at with a `sleep`.

If you ever do need to wait for something to become true asynchronously — not something this app currently requires, but common in systems with background jobs or eventual consistency — the right tool is a polling helper with a real timeout and a clear failure message, not a fixed sleep:

```java
import java.time.Duration;
import java.time.Instant;
import java.util.function.BooleanSupplier;

public static void waitUntil(BooleanSupplier condition, Duration timeout) {
    Instant deadline = Instant.now().plus(timeout);
    while (Instant.now().isBefore(deadline)) {
        if (condition.getAsBoolean()) {
            return;
        }
    }
    throw new AssertionError("Condition was not met within " + timeout);
}
```

This polls as fast as the condition check itself allows and fails with a clear, specific message the moment the timeout is exceeded — no arbitrary fixed delay baked in either direction.

## Unclosed connections and resource leaks

The database-testing module's `try (Connection conn = ...)` blocks aren't just tidy — a JDBC connection or `ResultSet` left open across many test runs can genuinely cause a suite to slow down, hit connection limits, or behave inconsistently under the parallel execution the next module covers. Try-with-resources isn't optional cleanup style here; treat it as required for anything `AutoCloseable` in this suite.

## Nondeterministic assertions

Watch for assertions that are true *most* of the time but not guaranteed:

```java
// DON'T: appointment order isn't guaranteed by the API's contract
List<Integer> ids = response.jsonPath().getList("id");
assertEquals(Integer.valueOf(1), ids.get(0)); // assumes a specific order

// DO: assert on what's actually guaranteed -- membership, not position
assertTrue(ids.contains(1));
```

Nothing in the spec or the app's documented behavior promises `GET /api/appointments` returns rows in a specific order — asserting on `ids.get(0)` being a particular value is an assumption about implementation detail (probably insertion order, today, in SQLite, which is itself not something a spec typically guarantees) rather than the actual contract. A future database migration, an index change, or a query rewrite could all silently reorder results without breaking the *real* contract — and a position-based assertion would then fail for a reason that has nothing to do with an actual bug.
