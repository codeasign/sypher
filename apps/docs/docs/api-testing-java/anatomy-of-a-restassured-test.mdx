The last module got a request working. This one properly explains the `given()/when()/then()` chain, and — more importantly — introduces `RequestSpecification`, the piece that stops you from retyping `baseUri("http://localhost:5000")` in every single test you'll ever write in this project. Get this right now, because Module 04 builds directly on top of it to add authentication.

## `given()/when()/then()`, properly

Every RestAssured call follows the same three-part shape:

```java
given()
    .baseUri("http://localhost:5000")
    .contentType("application/json")
    .body(requestBody)
.when()
    .post("/api/auth/login")
.then()
    .statusCode(200)
    .body("user.role", equalTo("Administrator"));
```

- **`given()`** returns a `RequestSpecification` — an object you configure with everything about the request *before* it's sent: base URI, headers, content type, body, query params, auth. Nothing has gone over the network yet at this point; you're just describing the request.
- **`when()`** is where the request actually fires. The HTTP method call — `.get(path)`, `.post(path)`, `.put(path)`, `.delete(path)` — is what triggers the real network call and returns a `Response`.
- **`then()`** returns a `ValidatableResponse` — a wrapper around the response built specifically for chaining assertions directly onto it, rather than pulling values out with `jsonPath()` and asserting on them separately (both styles are valid RestAssured; `then()` reads more fluently for simple checks, `jsonPath()` gives you more control for anything more involved — you'll use both throughout this course depending on what a given test needs).

That `.body("user.role", equalTo("Administrator"))` line uses a **Hamcrest matcher** (`equalTo`) — Hamcrest is a matcher library RestAssured builds its assertion API on top of, and you'll meet it properly in the assertions module. For now, just recognize `equalTo(...)`, `hasSize(...)`, and similar calls as Hamcrest matchers rather than plain Java comparisons.

## The problem `RequestSpecification` solves

Every test so far repeats `baseUri("http://localhost:5000")` and `contentType("application/json")`. That's harmless with two tests. It's a real maintenance problem once you have two hundred — change the port, or add a header every request needs, and you're editing every single test file.

RestAssured's answer is `RequestSpecBuilder`: build the shared configuration once, and pass the resulting `RequestSpecification` into `given()` on every test instead of rebuilding it by hand each time.

Create `src/test/java/com/example/rbactests/support/ApiSpec.java`:

```java
package com.example.rbactests.support;

import io.restassured.builder.RequestSpecBuilder;
import io.restassured.filter.log.RequestLoggingFilter;
import io.restassured.filter.log.ResponseLoggingFilter;
import io.restassured.specification.RequestSpecification;

public final class ApiSpec {

    private ApiSpec() {
    }

    public static RequestSpecification base() {
        return new RequestSpecBuilder()
                .setBaseUri("http://localhost:5000")
                .setContentType("application/json")
                .addFilter(new RequestLoggingFilter())
                .addFilter(new ResponseLoggingFilter())
                .build();
    }
}
```

A few choices worth explaining. The class is `final` with a `private` constructor — this is a plain **utility class**, meant to hold static methods only, never instantiated; that pair of choices is a common Java idiom for saying exactly that. `RequestSpecBuilder` is a builder — each `.set...`/`.add...` call configures one piece and returns the builder itself, so they chain, and `.build()` at the end produces the actual immutable `RequestSpecification` object. The two logging filters print every request and response RestAssured makes to the console automatically — genuinely useful while you're building a suite and want to see exactly what's going out and coming back, without adding `System.out.println` calls by hand everywhere. You can quiet them down later once your suite is stable; for this course, leaving them on throughout keeps every module's real output visible.

## Using the shared spec

`given().spec(...)` passes a pre-built `RequestSpecification` in, and it applies everything that spec configured — as if you'd typed it all inline:

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

class AnatomyTest {

    @Test
    void loginUsesTheSharedRequestSpec() {
        given()
            .spec(ApiSpec.base())
            .body("{\"username\":\"admin\",\"password\":\"admin123\"}")
        .when()
            .post("/api/auth/login")
        .then()
            .statusCode(200)
            .body("user.role", equalTo("Administrator"));
    }
}
```

Notice this test never mentions `baseUri` or `contentType` at all — `ApiSpec.base()` already carries both, and `.spec(...)` merges them into the request being built. Every module after this one starts its requests with `given().spec(...)` instead of rebuilding the same three or four lines by hand — you'll extend `ApiSpec` again in the very next module to also carry an authenticated user's token.

## `ResponseSpecification` — the same idea, for expectations

`RequestSpecification` reuses what you *send*. `ResponseSpecification` does the equivalent for what you *expect back* — useful once several tests share the same "should succeed" shape:

```java
import io.restassured.builder.ResponseSpecBuilder;
import io.restassured.specification.ResponseSpecification;
import static org.hamcrest.Matchers.lessThan;

ResponseSpecification successfulJson = new ResponseSpecBuilder()
        .expectStatusCode(200)
        .expectContentType("application/json")
        .expectResponseTime(lessThan(2000L))
        .build();
```

Applied the same way, on the `then()` side: `.then().spec(successfulJson)`. This course doesn't lean on `ResponseSpecification` as heavily as `RequestSpecification` — most modules assert specific things about specific responses rather than a single reusable "success shape" — but it's worth knowing it exists for exactly that case, and you'll use it directly in the smoke-testing module for a lightweight response-time check across a whole batch of endpoints.

## Try it

Add a second method to `ApiSpec` called `baseWithoutLogging()` that returns the same spec but without the two logging filters, and write a test using it against `GET /api/auth/login` (note: this route only accepts `POST` — check what status code and body you actually get back for calling it with the wrong method, and assert on that).
