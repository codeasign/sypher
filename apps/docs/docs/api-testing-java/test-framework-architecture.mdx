Sixteen modules in, `rbac-api-tests` already has a real shape to it — `ApiSpec`, `OpenApiSpec`, `EndpointChecklist`, `Database`, `RetryHelper`, plus a growing pile of test classes. This module steps back and organizes that growth deliberately, the way a real project's suite needs to be organized once it's no longer four files.

## The package structure this course has been building toward

```
rbac-api-tests/
├── pom.xml
└── src/
    └── test/
        ├── java/
        │   └── com/example/rbactests/
        │       ├── support/
        │       │   ├── ApiSpec.java
        │       │   ├── OpenApiSpec.java
        │       │   ├── EndpointChecklist.java
        │       │   ├── Database.java
        │       │   └── RetryHelper.java
        │       ├── appointments/
        │       │   ├── AppointmentCrudTest.java
        │       │   └── AppointmentSchemaTest.java
        │       ├── medicalrecords/
        │       │   └── MedicalRecordCrudTest.java
        │       ├── auth/
        │       │   └── AuthenticationTest.java
        │       ├── rbac/
        │       │   └── PermissionMatrixTest.java
        │       └── security/
        │           └── SecurityTest.java
        └── resources/
            └── schemas/
                └── appointment-schema.json
```

Two organizing principles are doing the work here. First, `support/` holds everything that *isn't* itself a test — request specs, spec parsing, database access, retry logic — separated from `*Test.java` files the same way a production codebase separates its utilities from its business logic. Second, test classes are grouped by **resource or concern**, not by module number from this course — `appointments/`, `medicalrecords/`, `rbac/`, `security/` reads clearly to someone joining the project cold, where a structure mirroring "lesson 7, lesson 10, lesson 12" would mean nothing outside the context of this course.

## Shared request builders belong in one place

Every module since Module 04 has called `ApiSpec.authenticatedAs(role)` instead of re-deriving login logic. That's the core discipline this whole architecture is built around: **one canonical way to build a request**, reused everywhere, so a change to how auth works (a new required header, a different token format) means editing one file, not searching-and-replacing across a hundred test methods. Resist the temptation to let a single test file grow its own private copy of request-building logic "just this once" — that's exactly how a suite ends up with five slightly different, silently drifting versions of the same login helper a year later.

## Configuration, not hardcoded values

`ApiSpec.base()` hardcodes `"http://localhost:5000"` — fine for a course, but a real project's suite needs to run against more than one environment (local, staging, CI). Pull that into a small config layer instead:

```java
package com.example.rbactests.support;

public final class Config {

    private Config() {
    }

    public static String baseUri() {
        return System.getProperty("api.baseUri", "http://localhost:5000");
    }
}
```

`System.getProperty("api.baseUri", "http://localhost:5000")` reads a JVM system property if one was passed in, falling back to the local default otherwise — which means `mvn test -Dapi.baseUri=https://staging.example.com` points the entire suite at a different environment with zero code changes, just a command-line flag. Update `ApiSpec.base()` to call `Config.baseUri()` instead of its hardcoded string, and every test in the suite inherits the same flexibility through the one shared spec they already all go through.

## Separating what a test asserts from how it gets there

Compare a test that inlines everything against one that leans on the support layer:

```java
// Harder to read, harder to change
@Test
void doctorSeesOwnAppointmentsOnly() {
    String token = given().baseUri("http://localhost:5000").contentType("application/json")
        .body("{\"username\":\"doctor1\",\"password\":\"pass@123\"}")
        .post("/api/auth/login").jsonPath().getString("token");
    given().baseUri("http://localhost:5000").header("Authorization", "Bearer " + token)
        .get("/api/appointments").then().statusCode(200);
    // ...
}

// Reads as intent, not mechanics
@Test
void doctorSeesOwnAppointmentsOnly() {
    given().spec(ApiSpec.authenticatedAs(ApiSpec.Role.DOCTOR))
        .when().get("/api/appointments")
        .then().statusCode(200);
    // ...
}
```

The second version is what this course has been building toward since Module 04, and the difference matters more as a suite grows: a test file full of the first style is doing two jobs at once — describing *what's being verified* and re-explaining *how to talk to the API* — and the second job drowns out the first. A test file full of the second style reads almost like a specification of the app's behavior, which is exactly what a well-architected suite should read like to someone who didn't write it.

## Try it

Reorganize any three test classes you've written in earlier modules into this `support/` + resource-grouped structure, and update `ApiSpec.base()` to call the new `Config.baseUri()` instead of its hardcoded string. Run `mvn test -Dapi.baseUri=http://localhost:5000` explicitly and confirm it still passes — proving the override mechanism actually works, not just that the default still does.
