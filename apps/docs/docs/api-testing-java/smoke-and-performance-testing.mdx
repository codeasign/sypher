Not every test run needs the full suite. A **smoke test** answers one narrow question fast — "is the app even up and basically working?" — as a cheap first check before anything more thorough runs. This module builds one for the RBAC app, then looks at basic response-time assertions and where that stops being "testing" and starts being real performance engineering.

## What belongs in a smoke suite

A smoke suite should be small, fast, and cover the most critical paths only — not a subset chosen at random, but the handful of things that, if broken, mean nothing else is worth testing yet:

```java
package com.example.rbactests.smoke;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;

class SmokeTest {

    @Test
    void theServerIsUp() {
        given()
            .spec(ApiSpec.base())
        .when()
            .get("/api-docs")
        .then()
            .statusCode(200);
    }

    @Test
    void loginWorksForTheAdminAccount() {
        given()
            .spec(ApiSpec.base())
            .body("""
                    { "username": "admin", "password": "admin123" }
                    """)
        .when()
            .post("/api/auth/login")
        .then()
            .statusCode(200);
    }

    @Test
    void aCoreProtectedEndpointRespondsForAnAuthenticatedUser() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments")
        .then()
            .statusCode(200);
    }
}
```

Three tests, each answering a genuinely different "is this fundamentally broken?" question: is the server reachable at all, does authentication work, does an authenticated request to a real resource work. Run this before the full suite (or before deploying, or right after a deploy) and a red result here means stop — don't bother running the other twenty-odd modules' worth of tests against a backend that can't even log someone in.

## Basic response-time assertions

RestAssured can assert on response time directly:

```java
import java.util.concurrent.TimeUnit;
import static org.hamcrest.Matchers.lessThan;

@Test
void loginRespondsReasonablyFast() {
    given()
        .spec(ApiSpec.base())
        .body("""
                { "username": "admin", "password": "admin123" }
                """)
    .when()
        .post("/api/auth/login")
    .then()
        .statusCode(200)
        .time(lessThan(2000L), TimeUnit.MILLISECONDS);
}
```

`.time(lessThan(2000L), TimeUnit.MILLISECONDS)` fails the test if the response took two seconds or longer — a coarse, generous threshold on purpose. This is a **regression guard**, not a performance benchmark: its job is to catch something that's gone badly wrong (an endpoint that used to respond in 40ms suddenly taking 8 seconds is worth knowing about immediately), not to measure precisely how fast the app is under load.

## Where this stops being enough

A single request, timed once, tells you almost nothing about how the app behaves under real traffic. It doesn't reveal what happens when fifty users hit `/api/appointments` at the same second, whether response times climb as request volume grows, or where the actual bottleneck sits (the Express server, the SQLite database, the network). That's **load testing** and **performance testing** proper — a different discipline with its own dedicated tools (Gatling and JMeter are the two most common in the Java ecosystem specifically), built around ramping concurrent virtual users, sustained duration, and percentile-based latency reporting (p50, p95, p99) rather than a single pass/fail threshold on one request.

This course's response-time assertions are a smoke-level safety net, not a substitute for that. If the RBAC app were heading toward production traffic, a real performance test plan — run separately from this functional suite, usually on its own schedule rather than on every pull request — would be the next real step, not an extension of what `.time(...)` assertions sprinkled through a functional suite can responsibly claim to cover.

## Try it

Add a fourth smoke test that hits `GET /api/patients` as a Doctor and asserts both `statusCode(200)` and a response-time threshold of your own choosing. Then run just the smoke package (`mvn test -Dtest=com.example.rbactests.smoke.*`) and time how long the whole smoke suite takes end to end — that total is the number worth watching over time, more than any single test's individual threshold.
