Almost every endpoint in the RBAC app requires proof of who is asking before it does anything. You have been logging in by hand in every module so far. This is the module where that stops, and you build one small, reusable piece of test infrastructure that every module after this one imports instead.

## How the app's auth actually works

`POST /api/auth/login` takes a `username` and `password`. If they are valid, it signs a **JWT (JSON Web Token)**, a compact, self-contained string that encodes who the user is and what role they have, and sends it back:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"doctor1","password":"pass@123"}'
```

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": { "id": 5, "username": "doctor1", "role": "Doctor", "full_name": "Dr. James Wilson" }
}
```

Every protected endpoint expects that token sent back on an `Authorization` header, in the form `Bearer <token>`. The server verifies the token's signature (proving it was not tampered with) and reads the role encoded inside it to decide what that request is allowed to do. That role check is the entire foundation of the RBAC matrix you will test thoroughly soon.

Two failure modes are worth knowing precisely, because you will test both directly and they return *different* status codes:

- **No token at all** produces `401 { "error": "Access token required" }`. The server cannot even tell who is asking.
- **A token that is invalid, malformed, or expired** produces `403 { "error": "Invalid or expired token" }`. The server knows *something* was sent, but it does not trust it.

That distinction, missing credentials get `401` and credentials that exist but do not check out get `403`, is not a convention every API follows the same way, so it is worth confirming against the app you are actually testing rather than assuming. You will rely on it directly in the negative-testing module.

## The four accounts you'll use throughout this course

The seed data gives you one working account per role, and these four logins are what every RBAC-aware test in this course is built around:

| Role | Username | Password |
|---|---|---|
| Administrator | `admin` | `admin123` |
| Doctor | `doctor1` | `pass@123` |
| Nurse | `nurse1` | `pass@123` |
| Patient | `patient1` | `pass@123` |

## Extending `ApiSpec` with authentication

The last module's `ApiSpec.base()` carries the shared base URI and content type. Now extend it so it can also hand you back a `RequestSpecification` that is already authenticated as a given role. This is the piece every later module reaches for instead of re-deriving login logic.

Update `src/test/java/com/example/rbactests/support/ApiSpec.java`:

```java
package com.example.rbactests.support;

import io.restassured.builder.RequestSpecBuilder;
import io.restassured.filter.log.RequestLoggingFilter;
import io.restassured.filter.log.ResponseLoggingFilter;
import io.restassured.specification.RequestSpecification;

import java.util.Map;

import static io.restassured.RestAssured.given;

public final class ApiSpec {

    public enum Role {
        ADMINISTRATOR, DOCTOR, NURSE, PATIENT
    }

    private static final Map<Role, String[]> CREDENTIALS = Map.of(
            Role.ADMINISTRATOR, new String[]{"admin", "admin123"},
            Role.DOCTOR, new String[]{"doctor1", "pass@123"},
            Role.NURSE, new String[]{"nurse1", "pass@123"},
            Role.PATIENT, new String[]{"patient1", "pass@123"}
    );

    private ApiSpec() {
    }

    public static RequestSpecification base() {
        return new RequestSpecBuilder()
                .setBaseUri("http://localhost:5000")
                .setContentType("application/json")
                .addFilter(new RequestLoggingFilter())
                .addFilter(new ResponseLoggingFilter())
                .build();
    }

    public static String loginAndGetToken(Role role) {
        String[] creds = CREDENTIALS.get(role);
        String body = String.format("{\"username\":\"%s\",\"password\":\"%s\"}", creds[0], creds[1]);

        return given()
                    .spec(base())
                    .body(body)
                .when()
                    .post("/api/auth/login")
                .then()
                    .statusCode(200)
                .extract()
                    .path("token");
    }

    public static RequestSpecification authenticatedAs(Role role) {
        String token = loginAndGetToken(role);
        return new RequestSpecBuilder()
                .addRequestSpecification(base())
                .addHeader("Authorization", "Bearer " + token)
                .build();
    }
}
```

A couple of design choices worth explaining. `Role` is a Java `enum` rather than a plain `String`: calling `authenticatedAs(ApiSpec.Role.DOCTOR)` is a compile error if you typo it, the same way a typo'd string like `"Docter"` would silently fail at runtime instead. `CREDENTIALS` is an immutable `Map<Role, String[]>` built with `Map.of(...)`, so all four accounts live in exactly one place. Change a seeded password once, and every test that calls `authenticatedAs` picks up the change automatically.

`loginAndGetToken` uses `.extract().path("token")`. `.extract()` switches from a `ValidatableResponse` (built for chaining assertions) back into something you can pull a raw value out of, and `.path("token")` reads the `token` field the same way `jsonPath().getString("token")` would, just spelled as part of the fluent chain. It also asserts `.statusCode(200)` before extracting anything: if login itself is broken, you want that failure to surface immediately and clearly, right where the real problem is, rather than have every test that depends on it fail later with a confusing null-token error.

`authenticatedAs` builds a **new** `RequestSpecification` on top of the base one, using `addRequestSpecification(base())` to merge in everything `base()` already provides, then layering the `Authorization` header on top. This is the method every later module in this course actually calls.

## Using it

From here on, every module reaches for this exact pattern instead of re-deriving login logic:

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

class AuthHelperTest {

    @Test
    void doctorCanHitAProtectedEndpoint() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.DOCTOR))
        .when()
            .get("/api/appointments")
        .then()
            .statusCode(200);
    }

    @Test
    void noTokenAtAllIsRejectedWith401() {
        given()
            .spec(ApiSpec.base())
        .when()
            .get("/api/appointments")
        .then()
            .statusCode(401)
            .body("error", equalTo("Access token required"));
    }

    @Test
    void aGarbageTokenIsRejectedWith403() {
        given()
            .spec(ApiSpec.base())
            .header("Authorization", "Bearer not-a-real-token")
        .when()
            .get("/api/appointments")
        .then()
            .statusCode(403)
            .body("error", equalTo("Invalid or expired token"));
    }
}
```

All three pass against the real app. `authenticatedAs(Role.DOCTOR)` logs in fresh and returns a spec carrying a real, working token; a request with no `Authorization` header at all comes back `401`; a request with a token that fails signature verification comes back `403`. Every RBAC-aware test from this point forward starts the same way: `given().spec(ApiSpec.authenticatedAs(role))`.

## Try it

Add a `NURSE` case to a new test: authenticate as a nurse using `ApiSpec.authenticatedAs(ApiSpec.Role.NURSE)`, then send a request to `GET /api/users` (list all users, an Administrator-only endpoint) using that spec. Assert on the status code you get back, and print `response.jsonPath().getString("requiredRoles")` from the failure response. The server tells you exactly which roles it would have accepted.
