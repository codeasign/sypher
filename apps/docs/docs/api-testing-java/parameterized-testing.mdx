The RBAC matrix module already used `@ParameterizedTest` with `@MethodSource` to avoid writing twelve near-identical test methods by hand. This module goes deeper into JUnit 5's parameterized testing tools: the other source types, when each one fits, and how much duplication they can strip out of a growing suite.

## `@ValueSource`, a single list of simple values

The simplest case: running one test body against a plain list of values.

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

import static io.restassured.RestAssured.given;

class ParameterizedBasicsTest {

    @ParameterizedTest(name = "GET /api/appointments/{0} returns 404")
    @ValueSource(ints = {0, -1, 999999, 999999999})
    void nonexistentAppointmentIdsAllReturn404(int id) {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/" + id)
        .then()
            .statusCode(404);
    }
}
```

`@ValueSource` supports arrays of one primitive type at a time (`ints`, `strings`, `booleans`, and a few others). It is the right tool exactly when every case is a single value of the same type, like this boundary-value sweep from the negative-testing module, now expressed as four runs of one test instead of four separate methods.

## `@CsvSource`, multiple related values per case

Once a test needs more than one value per run, `@CsvSource` lets you write each case as a comma-separated row:

```java
import org.junit.jupiter.params.provider.CsvSource;
import static org.hamcrest.Matchers.equalTo;

@ParameterizedTest(name = "{0} logging in with correct password succeeds")
@CsvSource({
        "admin,     admin123",
        "doctor1,   pass@123",
        "nurse1,    pass@123",
        "patient1,  pass@123"
})
void eachSeededAccountCanLogIn(String username, String password) {
    given()
        .spec(ApiSpec.base())
        .body("{\"username\":\"%s\",\"password\":\"%s\"}".formatted(username, password))
    .when()
        .post("/api/auth/login")
    .then()
        .statusCode(200)
        .body("user.username", equalTo(username));
}
```

This reads almost like a small table, a format that is genuinely easier to scan and extend than four separate `@Test` methods, especially once you are looking at ten or twenty rows instead of four. `@CsvSource` is a good fit exactly when your cases are a handful of primitive values (strings, numbers, booleans); once a case needs something more structured (a whole request body, a role enum, a list of expected values), that is the signal to reach for `@MethodSource` and a `record` instead, the way the RBAC matrix module did.

## `@MethodSource`, revisited with more structure

The RBAC matrix module's `Case` record covered role/method/path/status. `@MethodSource` scales further than `@CsvSource` because the method producing your cases is just Java: it can build arbitrarily complex objects, pull values from the OpenAPI spec, or generate combinations programmatically instead of listing them by hand:

```java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.MethodSource;

import java.util.List;
import java.util.stream.Stream;

class RoleCrossEndpointTest {

    record Case(ApiSpec.Role role, boolean shouldSeeAllRows) {
    }

    static Stream<Case> visibilityCases() {
        return Stream.of(
                new Case(ApiSpec.Role.ADMINISTRATOR, true),
                new Case(ApiSpec.Role.NURSE, true),
                new Case(ApiSpec.Role.DOCTOR, false),
                new Case(ApiSpec.Role.PATIENT, false)
        );
    }

    @ParameterizedTest(name = "{0} sees all rows: {1}")
    @MethodSource("visibilityCases")
    void appointmentVisibilityMatchesExpectation(Case testCase) {
        List<Integer> ids =
                given()
                    .spec(ApiSpec.authenticatedAs(testCase.role()))
                .when()
                    .get("/api/appointments")
                .then()
                    .statusCode(200)
                .extract()
                    .jsonPath()
                    .getList("id");

        if (testCase.shouldSeeAllRows()) {
            org.junit.jupiter.api.Assertions.assertEquals(20, ids.size());
        } else {
            org.junit.jupiter.api.Assertions.assertTrue(ids.size() < 20);
        }
    }
}
```

This directly encodes the row-level-filtering finding from the RBAC module (Admin and Nurse see everything, Doctor and Patient see a subset) as four data-driven runs instead of four hand-written test methods that would otherwise repeat almost the exact same request/assertion shape four times over.

## `@EnumSource`, every value of an enum, for free

Since `ApiSpec.Role` is a proper Java `enum`, JUnit can enumerate every value of it automatically:

```java
import org.junit.jupiter.params.provider.EnumSource;

@ParameterizedTest
@EnumSource(ApiSpec.Role.class)
void everyRoleCanSuccessfullyLogIn(ApiSpec.Role role) {
    String token = ApiSpec.loginAndGetToken(role);
    org.junit.jupiter.api.Assertions.assertTrue(token.length() > 20);
}
```

No list to maintain at all here. Add a fifth role to the `Role` enum someday (and to `CREDENTIALS` in `ApiSpec`), and this test automatically picks up a fifth case the next time it runs, with zero changes to the test itself.

## Choosing between them

| Source type | Use when |
|---|---|
| `@ValueSource` | One primitive value per case |
| `@CsvSource` | A few primitive values per case, readable as a small table |
| `@MethodSource` | Cases need real objects, records, or programmatic generation |
| `@EnumSource` | Every value of an existing enum, with no separate list to maintain |

## Try it

Convert the security module's `PUT /api/users/{id}` field-smuggling test into a `@CsvSource`-driven test that tries smuggling several different disallowed fields in turn (`role`, `username`, `password`), each on its own row, asserting the field is silently ignored every time the way `role` was shown to be. If any of the three behaves differently from the other two, that is worth flagging as its own finding, the same way the registration endpoint's role handling was in the security module.
