A test suite that only reports "pass" or "fail" as a console log is a suite nobody outside your terminal can see. This module wires up real HTML reporting, then puts the whole suite into a GitHub Actions pipeline that runs it automatically on every pull request, the point where "I ran the tests on my machine" becomes "every PR is gated on the tests actually passing."

## Surefire's built-in reports

Maven Surefire already generates a report on every `mvn test` run, in `target/surefire-reports/`: one `.txt` and one `.xml` file per test class. The XML format (JUnit XML) is a de facto standard that most CI systems and reporting tools know how to parse directly, which is why it is worth knowing this exists even before adding anything fancier.

## Adding a proper HTML report with the Surefire report plugin

For something more readable than raw XML, add the Maven Surefire Report plugin:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-report-plugin</artifactId>
    <version>3.2.5</version>
</plugin>
```

Generate the report after a test run:

```bash
mvn test
mvn surefire-report:report-only
```

This produces `target/site/surefire-report.html`, a browsable page listing every test class, every method, pass/fail status, and timing, generated straight from the same XML Surefire already writes. Open it in a browser and you have a shareable artifact, not just a scroll of console output.

## Allure, for a richer report

Surefire's report is functional but plain. **Allure** produces a much more detailed, interactive report: steps within a test, attachments (like a captured response body), and trends across multiple runs. Add the Allure JUnit 5 integration:

```xml
<dependency>
    <groupId>io.qameta.allure</groupId>
    <artifactId>allure-junit5</artifactId>
    <version>2.27.0</version>
    <scope>test</scope>
</dependency>
```

Plus the AspectJ weaver Surefire needs to hook into JUnit 5's lifecycle for Allure's step tracking, configured on the Surefire plugin itself:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <version>3.2.5</version>
    <configuration>
        <argLine>-javaagent:"${settings.localRepository}"/org/aspectj/aspectjweaver/1.9.21/aspectjweaver-1.9.21.jar</argLine>
    </configuration>
</plugin>
```

Run the suite, then generate and open the report with the Allure command-line tool (installed separately, see [allurereport.org](https://allurereport.org)):

```bash
mvn test
allure serve target/allure-results
```

For this course's suite, Surefire's own HTML report is honestly enough. Allure earns its extra setup on a much larger suite where step-level detail and historical trends across many runs start to matter. Knowing both exist, and why you would reach for one over the other, matters more here than mastering Allure's full feature set.

## Wiring the suite into GitHub Actions

The real payoff: making the suite run automatically, on the real backend, on every pull request. Create `.github/workflows/api-tests.yml` in your `rbac-api-tests` project:

```yaml
name: API Tests

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Check out the test project
        uses: actions/checkout@v4

      - name: Check out the RBAC backend
        uses: actions/checkout@v4
        with:
          repository: codedbyabhishekc/rbac-healthcare-system
          path: rbac-healthcare-system

      - name: Set up Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install and start the RBAC backend
        working-directory: rbac-healthcare-system/backend
        run: |
          npm install
          mkdir -p database
          echo "PORT=5000" >> .env
          echo "JWT_SECRET=ci-only-secret" >> .env
          echo "NODE_ENV=development" >> .env
          npm start &
          npx wait-on http://localhost:5000/api-docs

      - name: Seed the database
        working-directory: rbac-healthcare-system/backend
        run: npm run seed

      - name: Restart the backend after seeding
        working-directory: rbac-healthcare-system/backend
        run: |
          pkill -f "node server.js" || true
          npm start &
          npx wait-on http://localhost:5000/api-docs

      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: 'maven'

      - name: Run the test suite
        run: mvn test

      - name: Upload Surefire report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: surefire-report
          path: target/surefire-reports/
```

A few details worth explaining. This workflow checks out **two** repositories, your test project (the default checkout) and the RBAC backend itself, into a `rbac-healthcare-system` subfolder, since CI starts from nothing, unlike your own machine where you already cloned the backend once in the setup module. `npx wait-on http://localhost:5000/api-docs` blocks the workflow until that URL actually responds, rather than guessing a fixed delay is long enough, the same "do not hardcode a wait" principle the flaky-test-prevention module covered, just applied at the infrastructure level instead of inside a test. The backend gets restarted after seeding specifically because, as the setup module noted, seeding happens with the server stopped in this app's own documented workflow; CI has to reproduce that exact sequence, not skip it. `if: always()` on the report upload step means the report gets attached to the workflow run even when tests fail, arguably more important than when they pass, since that is when you actually need to look at it.

## Making it a required check

Once this workflow exists and has run successfully at least once, a repository admin can mark it as a **required status check** in the branch protection settings for `main`. From that point on, a pull request literally cannot be merged while `mvn test` is failing. That is the actual destination of this module: not just "tests exist," but "tests are structurally impossible to ignore."

## Try it

Add a step to the workflow that runs `mvn surefire-report:report-only` after the tests and uploads `target/site/surefire-report.html` as a second artifact, separate from the raw XML. Trigger the workflow (push to a branch and open a PR, or use `workflow_dispatch` for a manual trigger) and confirm both artifacts show up and are downloadable from the workflow run's summary page.
