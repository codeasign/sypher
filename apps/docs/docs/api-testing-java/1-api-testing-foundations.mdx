Before writing a single line of Java, it is worth being precise about what "API testing" actually means, because it is easy to confuse with the testing you might already be more familiar with: clicking through a UI and checking that the right thing appears on screen.

## What API testing actually checks

Every API test in this course follows the same basic shape: send an HTTP request, and check that the response matches what is expected: the right status code, the right shape of data, the right behavior for the role making the request. There is no browser involved, no rendering, no waiting for a page to load. You are talking directly to the layer that a UI would normally talk to on your behalf.

Take the RBAC app's login endpoint. A UI test would open a login page, type a username and password into fields, click a button, and check that a dashboard eventually shows up. An API test skips all of that and sends the request directly:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```

Same underlying behavior, but you are testing it one layer down, closer to the logic, with nothing in between to slow the test down or introduce flakiness that has nothing to do with whether the login logic itself is correct.

## API testing vs UI testing

Neither replaces the other. They catch different kinds of bugs, and a mature test strategy uses both:

- **UI tests** confirm that what a real user sees and clicks works end to end, including rendering, layout, and browser behavior. They are slower, more brittle (a CSS change can break a test that has nothing to do with the underlying logic), and more expensive to run at scale.
- **API tests** confirm that the contract between client and server holds: the right data goes in, the right data (and the right status code) comes out, for the right roles, in the right shape. They are fast, deterministic, and can run in seconds rather than minutes.

A well-tested system usually has far more API tests than UI tests, precisely because API tests are cheaper to write, faster to run, and easier to pin down when something breaks. A failing UI test tells you "something is wrong somewhere between the click and the screen," while a failing API test tells you exactly which endpoint, with exactly which input, returned exactly what.

## The request/response contract

Every HTTP API is built around a contract: for a given request (method, path, headers, body), the server promises a particular kind of response (status code, headers, body shape). Testing an API means testing that contract holds, not just that the server "works" in some vague sense.

Look at what actually changes across a few calls to the RBAC app:

```bash
# No credentials at all
curl -i http://localhost:5000/api/appointments
```

```bash
HTTP/1.1 401 Unauthorized
{"error":"Access token required"}
```

```bash
# Valid token, wrong role for this endpoint
curl -i http://localhost:5000/api/users -H "Authorization: Bearer <nurse-token>"
```

```bash
HTTP/1.1 403 Forbidden
{"error":"Access denied. Insufficient permissions.","requiredRoles":["Administrator"],"userRole":"Nurse"}
```

Two different failures, two different status codes, two different bodies. A well-written test suite checks all three precisely, rather than a vague "it returned an error." That precision is what makes a test useful: a test that only checks `response.statusCode() != 200` would pass on *both* of these very different failures, and tell you nothing about which one happened.

## Why test against a spec, not just current behavior

It is tempting to write a test that just captures whatever the server does right now: send a request, see what comes back, assert on exactly that. The problem is that this only tells you the server did not *change*; it tells you nothing about whether the server is *right*.

This course takes a different approach, one it comes back to constantly: the RBAC app ships with an OpenAPI (Swagger) spec documenting what every endpoint is supposed to do. Testing against that spec, not just against whatever the code currently returns, catches a category of bug that "test current behavior" completely misses: the case where the code drifts away from what it is documented to do, and nothing notices until a real client breaks. You will meet the spec directly starting in Module 05, and from that point on, it is the thing every later module measures reality against.

## Try it

Using `curl`, send three requests to `http://localhost:5000/api/appointments`: one with no `Authorization` header at all, one with a header like `Authorization: Bearer not-a-real-token`, and one with a real token from logging in as `admin`/`admin123`. Write down the three status codes and the three response bodies you get back. You will use exactly this kind of comparison, precise, not vague, throughout the rest of this course.
