The suite you have built runs one test at a time by default. As it grows toward the size a real project's suite reaches, that starts to matter: a CI pipeline that takes twenty minutes to report back is a much worse experience than one that takes three. JUnit 5 supports running tests concurrently, but turning it on safely depends entirely on the discipline the last several modules have already been building.

## Turning parallel execution on

JUnit 5's parallel execution is off by default and configured through a properties file. Create `src/test/resources/junit-platform.properties`:

```properties
junit.jupiter.execution.parallel.enabled=true
junit.jupiter.execution.parallel.mode.default=concurrent
junit.jupiter.execution.parallel.mode.classes.default=concurrent
junit.jupiter.execution.parallel.config.strategy=dynamic
junit.jupiter.execution.parallel.config.dynamic.factor=1.0
```

`enabled=true` turns the feature on at all; without it, everything below is silently ignored. `mode.default=concurrent` and `mode.classes.default=concurrent` mean both individual test methods *and* whole test classes are eligible to run in parallel with each other, rather than just classes running in parallel while methods within a class stay sequential. `config.strategy=dynamic` with `factor=1.0` sizes the thread pool relative to the number of available CPU cores: `1.0` means roughly one thread per core, a reasonable default. Raising it further can help for I/O-bound work like this suite's HTTP calls, where threads spend much of their time waiting on the network rather than using the CPU.

## Why this is safe now, and wasn't earlier

Turning this on for the fragile, order-dependent test class from the flaky-test-prevention module would be actively dangerous: `static int sharedAppointmentId` mutated by one test and read by another has no defined behavior once both can run on different threads at the same moment. Every test written since the fixtures module avoids exactly that: `@BeforeEach` creates fresh, test-local data; `@AfterEach` cleans it up; nothing is shared across test methods through static mutable state. That discipline is what makes flipping this switch safe rather than a leap of faith.

## The one place this course's own code needs a second look

Go back to `OpenApiSpec.spec()` from Module 05:

```java
private static JsonPath cached;

public static synchronized JsonPath spec() {
    if (cached == null) {
        cached = fetch();
    }
    return cached;
}
```

That `synchronized` keyword, called out at the time as being specifically for this module, is what keeps this safe under parallel execution. Without it, two threads could both observe `cached == null` at the same instant, and both proceed to call `fetch()` concurrently; the spec would get fetched and parsed twice, wastefully, and depending on timing either result could "win" the race to be stored in `cached`, which is exactly the kind of bug that shows up rarely, non-deterministically, and is miserable to reproduce. `synchronized` ensures only one thread can be inside `spec()` at a time: the second thread simply waits its turn, sees `cached` already populated, and returns the same shared instance instead of re-fetching.

## Isolating destructive tests

Some tests genuinely cannot run safely alongside others touching the same data. The security module's mass-assignment test creates a real Administrator account, for instance, which is harmless in isolation but worth keeping away from anything else that might be enumerating all users at the same moment. `@Isolated` and `@ResourceLock` (from `org.junit.jupiter.api.parallel`) let you mark specific classes or methods as needing to run alone:

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.parallel.Isolated;

@Isolated
class SecurityTest {

    @Test
    void anyoneCanRegisterThemselvesAsAnAdministrator() {
        // ...
    }
}
```

`@Isolated` tells JUnit this class must run by itself, with no other test executing concurrently anywhere in the suite: a heavier-handed tool than fine-grained locking, but a clear and simple one for the handful of tests, like this one, where "just do not run anything else at the same time" is the easiest correct answer.

## Confirming it actually sped things up

Run the suite before and after enabling parallel execution and compare:

```bash
mvn test -Djunit.jupiter.execution.parallel.enabled=false
mvn test
```

The first command overrides the properties file for a single run, forcing sequential execution so you have a real baseline to compare against, worth doing once, concretely, rather than assuming parallel execution helped just because you turned it on.

## Try it

Time a full `mvn test` run with parallel execution disabled, then enabled, using your shell's own timing (`time mvn test` on macOS/Linux, `Measure-Command { mvn test }` in PowerShell). Report the difference, and if you do not see much improvement, check whether most of your suite's runtime is actually spent waiting on the RBAC backend itself rather than on JVM-side work: a backend that cannot handle concurrent requests well would cap how much parallel test execution can actually help, regardless of how the JUnit side is configured.
