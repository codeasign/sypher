Tests up to this point have relied on the seed data existing: `patient_id: 20` being patient1, `doctor_id: 5` being doctor1, 15 patients total. That is fine for learning, but it is fragile: reseed the database in a different order, or add a fixture, and hardcoded ids and counts start failing for reasons that have nothing to do with a real bug. This module fixes that with proper JUnit 5 lifecycle management and tests that create their own data instead of borrowing someone else's.

## `@BeforeEach` and `@BeforeAll`

JUnit 5 gives you two setup hooks, and picking the right one matters:

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import io.restassured.specification.RequestSpecification;
import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

class FixtureExampleTest {

    static RequestSpecification adminSpec;
    RequestSpecification doctorSpec;

    @BeforeAll
    static void loginAsAdminOnce() {
        adminSpec = ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR);
    }

    @BeforeEach
    void loginAsDoctorFresh() {
        doctorSpec = ApiSpec.authenticatedAs(ApiSpec.Role.DOCTOR);
    }

    @Test
    void adminAndDoctorSpecsAreBothUsable() {
        given().spec(adminSpec).when().get("/api/users").then().statusCode(200);
        given().spec(doctorSpec).when().get("/api/appointments").then().statusCode(200);
    }
}
```

`@BeforeAll` runs exactly once, before any test method in the class. Its method must be `static`, and so must anything it assigns, because it runs before JUnit has even created an instance of the test class. `@BeforeEach` runs before *every single* test method, fresh each time. The tradeoff: `@BeforeAll` is faster (one login instead of dozens), but anything it sets up is *shared* across every test in the class, so a test that accidentally mutates shared state can bleed into the next one. `@BeforeEach` costs more (an extra login per test), but guarantees total isolation. This course's `ApiSpec.authenticatedAs(...)` calls are cheap enough that `@BeforeEach` is the safer default for anything that is not purely read-only setup. Reach for `@BeforeAll` deliberately, not automatically.

## Creating your own data instead of borrowing the seed's

Every test from here on should create whatever data it needs and clean up after itself, rather than reaching for `patient_id: 20` and hoping it still means what it meant last time you looked. `@AfterEach` is the natural place to clean up:

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

class SelfContainedAppointmentTest {

    int createdAppointmentId;

    @BeforeEach
    void createAFreshAppointment() {
        createdAppointmentId =
                given()
                    .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
                    .body("""
                            {
                              "patient_id": 20,
                              "doctor_id": 5,
                              "appointment_date": "2026-10-01T09:00:00",
                              "reason": "fixture-created appointment"
                            }
                            """)
                .when()
                    .post("/api/appointments")
                .then()
                    .statusCode(201)
                .extract()
                    .path("appointmentId");
    }

    @AfterEach
    void deleteWhateverThisTestCreated() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .delete("/api/appointments/" + createdAppointmentId);
        // No assertion here on purpose -- cleanup best-effort, a failed cleanup
        // shouldn't itself fail the test that already ran and reported its result.
    }

    @Test
    void theFreshAppointmentStartsAsScheduled() {
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/" + createdAppointmentId)
        .then()
            .statusCode(200)
            .body("status", equalTo("scheduled"));
    }
}
```

This test never depends on the seed data's exact shape. It creates its own appointment in `@BeforeEach`, uses only the id it just got back, and removes it in `@AfterEach`. Run this test a hundred times, reseed the database in between, add new fixtures to the seed script: none of it breaks this test, because it never assumed anything about what data existed *before* it ran.

## Handling this app's seed data inconsistencies

Worth naming directly, since it affects how much you *can* rely on seed data even where you choose to: the seed script's own summary output reports different counts depending on which course's setup notes you compare against (20 vs 22 appointments, for instance, across different setup runs of this same repo), a sign the seed script itself has some variability, not a bug in your tests. That is exactly the reason this module pushes toward tests creating their own data rather than asserting on seed-data counts like "exactly 15 patients" wherever a test can reasonably do so instead. Where a test genuinely needs to reference seed data directly (Module 10's RBAC matrix, for one, where role-per-account is fixed by the seed script's design rather than something a test needs to create fresh), treat the specific accounts (`admin`, `doctor1`, `nurse1`, `patient1`) as stable, since those four are explicitly the ones this course, and the app's own seed script, are built around, and lean on freshly-created data for everything else.

## Try it

Rewrite one of the RBAC matrix module's tests that currently reads a fixed medical record id to instead create its own medical record in `@BeforeEach` (as Doctor, since that is the only role allowed to) and clean it up in `@AfterEach`. Confirm it still passes, then deliberately run it twice in a row without reseeding the database in between. It should pass both times, which is exactly the property seed-dependent tests do not reliably have.
