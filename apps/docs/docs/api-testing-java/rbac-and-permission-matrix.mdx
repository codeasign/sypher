Every module so far has tested one role against one endpoint at a time. RBAC-aware testing means something more systematic: the same endpoint, tested against *every* role, so you can see the full shape of who's allowed to do what — and just as importantly, where the app's behavior is more nuanced than a flat allow/deny.

## The real matrix, verified

Rather than guessing at a permission matrix from the spec's summaries alone, this table comes from actually calling every one of these endpoints as all four seeded accounts and recording exactly what came back:

| Endpoint | Admin | Doctor | Nurse | Patient |
|---|---|---|---|---|
| `GET /api/patients` | 200 (all) | 200 (all) | 200 (all) | 403 |
| `GET /api/users` | 200 (all) | 403 | 403 | 403 |
| `GET /api/appointments` | 200 (all, 20) | 200 (own only, 3) | 200 (all, 20) | 200 (own only, 2) |
| `GET /api/medical-records` | 200 (all, 16) | 200 (own patients only, 4) | 200 (all, 16) | 200 (own only, 3) |
| `GET /api/users/role/{role}` | 200 | 200 | 200 | 200 |
| `POST /api/medical-records` | — | 201 | 403 | — |
| `DELETE /api/medical-records/{id}` | 200 | 200 | 403 | — |
| `POST /api/appointments` | 201 | (not tested) | 201 | 201 |
| `DELETE /api/appointments/{id}` | 200 | (not tested) | (not tested) | 403 |

A few results are worth calling out specifically, because they're not what a flat "each role gets a fixed allow/deny per endpoint" model would predict:

- **`GET /api/appointments` and `GET /api/medical-records` never return `403` for any role** — every role gets `200`. What actually differs is the *content*: Admin and Nurse both see every row in the table, while Doctor and Patient each see only rows tied to them (a doctor sees appointments where they're the assigned doctor; a patient sees only their own). This is **row-level filtering**, not endpoint-level access control, and it's a real, deliberate design choice worth testing explicitly — a naive test that only checks `statusCode(200)` for every role would completely miss that Doctor and Nurse are seeing *different data* through the *same* endpoint.
- **`GET /api/users/role/{role}` has no role restriction at all** — every authenticated user, including a Patient, can look up doctors by role. That's consistent with a healthcare app where patients need to find doctors, not a gap — but it's still worth a test that explicitly documents "this one is open to everyone," so a future reader of the suite doesn't assume it's locked down just because most of its neighbors are.
- **Medical record deletion is Doctor **and** Admin, appointment deletion in the spec's summary reads Doctor **and** Admin too, but a Patient trying it gets a `403` body that names the roles explicitly**: `{"error":"Access denied. Insufficient permissions.","requiredRoles":["Administrator","Doctor"],"userRole":"Patient"}`. That `requiredRoles` field is worth asserting on directly, not just the status code — it's the server telling you, precisely, what it would have accepted.

## Building the matrix as data, not as separate test methods

Writing one `@Test` method per cell in that table would work, but it's a lot of near-identical code, and adding a fifth role or a tenth endpoint later means writing yet more near-identical methods by hand. `@ParameterizedTest` with `@MethodSource` lets you describe the matrix as data instead, and run one test method against every row:

```java
package com.example.rbactests;

import com.example.rbactests.support.ApiSpec;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.MethodSource;

import java.util.List;
import java.util.stream.Stream;

import static io.restassured.RestAssured.given;
import static org.junit.jupiter.api.Assertions.assertEquals;

class PermissionMatrixTest {

    record Case(ApiSpec.Role role, String method, String path, int expectedStatus) {
    }

    static Stream<Case> readEndpointCases() {
        return Stream.of(
                new Case(ApiSpec.Role.ADMINISTRATOR, "GET", "/api/patients", 200),
                new Case(ApiSpec.Role.DOCTOR, "GET", "/api/patients", 200),
                new Case(ApiSpec.Role.NURSE, "GET", "/api/patients", 200),
                new Case(ApiSpec.Role.PATIENT, "GET", "/api/patients", 403),

                new Case(ApiSpec.Role.ADMINISTRATOR, "GET", "/api/users", 200),
                new Case(ApiSpec.Role.DOCTOR, "GET", "/api/users", 403),
                new Case(ApiSpec.Role.NURSE, "GET", "/api/users", 403),
                new Case(ApiSpec.Role.PATIENT, "GET", "/api/users", 403),

                new Case(ApiSpec.Role.ADMINISTRATOR, "GET", "/api/appointments", 200),
                new Case(ApiSpec.Role.DOCTOR, "GET", "/api/appointments", 200),
                new Case(ApiSpec.Role.NURSE, "GET", "/api/appointments", 200),
                new Case(ApiSpec.Role.PATIENT, "GET", "/api/appointments", 200)
        );
    }

    @ParameterizedTest(name = "{0} {1} {2} → {3}")
    @MethodSource("readEndpointCases")
    void endpointReturnsExpectedStatusForRole(Case testCase) {
        int actualStatus =
                given()
                    .spec(ApiSpec.authenticatedAs(testCase.role()))
                .when()
                    .request(testCase.method(), testCase.path())
                .then()
                .extract()
                .statusCode();

        assertEquals(testCase.expectedStatus(), actualStatus);
    }
}
```

`record Case(...)` is the same pattern the checklist module used — a small, immutable bundle of values, here representing one cell of the matrix: which role, which request, what status that combination should produce. `@MethodSource("readEndpointCases")` tells JUnit to call that static method and run the test once per item in the returned `Stream` — twelve `Case` records here means twelve actual test runs, each reported individually. The `name = "{0} {1} {2} → {3}"` in `@ParameterizedTest` controls how each run is labeled in test output — `{0}` through `{3}` refer to the constructor arguments of whichever `Case` produced that run, so a failing row shows up in your test report as something readable like `PATIENT GET /api/patients → 403`, not just "test 4 of 12 failed."

`given().when().request(method, path)` — rather than `.get(path)` or `.post(path)` — is RestAssured's generic form that accepts the HTTP method as a `String` (or a `Method` enum), which is exactly what you need once the method itself is a variable rather than something you know at the time you're writing the code.

Twelve cases at once, each clearly reported, and adding a thirteenth is a one-line addition to `readEndpointCases()` rather than a whole new method.

## Testing the row-level filtering, not just the status code

The matrix above's real nuance — Doctor and Patient seeing filtered results while Admin and Nurse see everything — deserves its own explicit test, since a status-code-only matrix test would never catch it:

```java
@Test
void doctorOnlySeesTheirOwnAppointments() {
    var response =
            given()
                .spec(ApiSpec.authenticatedAs(ApiSpec.Role.DOCTOR))
            .when()
                .get("/api/appointments")
            .then()
                .statusCode(200)
            .extract()
            .response();

    List<Integer> doctorIds = response.jsonPath().getList("doctor_id");
    assertEquals(3, doctorIds.size());
    doctorIds.forEach(id -> assertEquals(5, id)); // doctor1's own id, from Module 4
}
```

`response.jsonPath().getList("doctor_id")` collects the `doctor_id` field out of every object in the returned array into one `List<Integer>` — the same field-collecting behavior you saw `everyItem(...)` use back in the assertions module, just consumed as a plain list here instead of wrapped in a Hamcrest matcher, since asserting "every one of these equals 5" reads more directly as a loop in this case.

## Try it

Add `POST /api/medical-records` and `DELETE /api/medical-records/{id}` as two more `Case` rows for all four roles (you'll need a real medical record id for the delete case — create one first with a Doctor-authenticated request, the way the CRUD module did). Confirm your matrix test's results match the table at the top of this module exactly, including the two `—` cells (skip those in your `Case` list, or add a fifth role-neutral "not applicable" expectation if you'd rather make the gap explicit rather than silently absent).
