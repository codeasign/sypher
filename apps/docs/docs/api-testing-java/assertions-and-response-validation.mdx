Every test so far has used a handful of assertions almost on autopilot: `statusCode(200)`, `body("field", equalTo("value"))`. This module slows down on assertions specifically: what Hamcrest actually is, the matchers you will reach for constantly, and how to check a response against what the spec declares rather than just what you happen to expect.

## Hamcrest, properly introduced

Every `.body("path", someMatcher)` call you have written relies on **Hamcrest**, a matcher library bundled transitively with RestAssured, built around the idea of composable, readable assertions. `equalTo(...)`, which you have already used, is one matcher out of dozens. The ones you will reach for most in an API testing context:

```java
import static org.hamcrest.Matchers.*;

.body("user.role", equalTo("Administrator"))          // exact match
.body("token", not(emptyString()))                     // non-empty string
.body("patients", hasSize(15))                          // exact collection size
.body("patients.name", hasItem("John Smith"))            // collection contains a value
.body("id", greaterThan(0))                              // numeric comparison
.body("status", anyOf(equalTo("scheduled"), equalTo("completed"), equalTo("cancelled")))
```

Matchers **compose**: `not(emptyString())` is `not(...)` wrapped around another matcher, `anyOf(...)` takes several matchers and passes if any one of them does. That composability is the point of Hamcrest: you build precise expectations out of small, readable pieces instead of writing custom comparison logic by hand for every check.

## Status code assertions, precisely

You have used `.statusCode(200)` everywhere so far, which is shorthand for `equalTo(200)`. It also accepts a matcher directly, which matters once you are asserting on a *range* rather than one exact value:

```java
import static org.hamcrest.Matchers.anyOf;

.then()
    .statusCode(anyOf(equalTo(200), equalTo(201)))
```

Or, more idiomatically for "any 2xx," RestAssured has a dedicated Hamcrest-style helper:

```java
import static io.restassured.matcher.RestAssuredMatchers.*;
```

is available if you want it, but this course sticks to explicit status codes almost everywhere. Asserting a precise `200` catches a real bug that asserting "some 2xx" would silently let through (an endpoint that starts returning `202 Accepted` instead of `200 OK`, say, when nothing in the spec or the app's actual behavior changed to justify it).

## Header assertions

Response headers are worth checking directly, not just the body:

```java
given()
    .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
.when()
    .get("/api/appointments")
.then()
    .statusCode(200)
    .header("Content-Type", containsString("application/json"));
```

`containsString(...)` rather than `equalTo(...)` here is deliberate. A real `Content-Type` header is often `application/json; charset=utf-8`, and asserting exact equality against just `"application/json"` would fail on the charset suffix even though the response genuinely is JSON. Matching on the substring you actually care about, instead of the whole header value, is a small but common source of flaky-looking test failures if you get it backwards.

## Body shape assertions with Hamcrest

Beyond single-field checks, Hamcrest handles whole-collection assertions cleanly:

```java
given()
    .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
.when()
    .get("/api/patients")
.then()
    .statusCode(200)
    .body("$", hasSize(15))
    .body("name", everyItem(not(emptyString())))
    .body("id", everyItem(greaterThan(0)));
```

`"$"` is a JsonPath root reference: when the response body is a JSON *array* at the top level (not an object), `"$"` refers to the whole array itself, which is what lets `hasSize(15)` check the array's length directly. `body("name", everyItem(...))` is doing something worth noticing: RestAssured is smart enough to collect the `name` field from *every* object in the array into a single list, then `everyItem(...)` checks that every element of that collected list passes the inner matcher, one line covering all 15 patients rather than 15 separate assertions.

That `hasSize(15)` is worth grounding against the real seed data specifically, not treated as a magic number: the seed script creates exactly 15 patients, so this assertion is checking a real, known fact about this database, not an arbitrary guess. Any test that hardcodes a count like this is implicitly coupled to the seed data staying the same, worth knowing, and exactly the kind of coupling the fixtures module addresses properly.

## Checking against what the spec actually declares

Everything above checks a response against what *you* expect. The more interesting move, and the one this course keeps coming back to, is checking a response against what the *spec* declares, so a test failure means either the code or the spec is wrong, not just that your assumption was wrong.

```java
import io.restassured.path.json.JsonPath;
import java.util.List;

JsonPath spec = OpenApiSpec.spec();
List<Integer> documentedCodes =
        spec.getMap("paths.'/api/appointments/{id}'.get.responses")
            .keySet().stream()
            .map(Integer::parseInt)
            .toList();

int actualCode =
        given()
            .spec(ApiSpec.authenticatedAs(ApiSpec.Role.ADMINISTRATOR))
        .when()
            .get("/api/appointments/999999")
        .then()
            .extract()
            .statusCode();

org.junit.jupiter.api.Assertions.assertTrue(
        documentedCodes.contains(actualCode),
        () -> "Got status " + actualCode + " but the spec only documents " + documentedCodes + " for this operation"
);
```

This test does not hardcode `404`. It asks the spec what is allowed, then checks the real response falls inside that set. If the spec is later updated to also document a `410 Gone` for deleted resources, or if the code starts returning something the spec never mentioned, this test surfaces exactly that drift, which is the entire value of spec-anchored testing over hardcoded-expectation testing. The third argument to `assertTrue`, a `Supplier<String>`, only builds that error message string if the assertion actually fails, which matters once you have thousands of assertions and do not want string-building overhead on every single passing one.

## Try it

Write a spec-anchored test for `POST /api/appointments`: read the documented status codes for that operation the same way this module did, send a valid create request, and assert the real response code is one the spec actually documents. Then deliberately send an invalid request (omit the required `reason` field) and print what status code and body you get back. You will formalize exactly this kind of negative case into its own module soon.
