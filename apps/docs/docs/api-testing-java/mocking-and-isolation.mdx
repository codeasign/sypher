Every test in this course so far has run against the real RBAC backend, and that is not changing here. This module is not about mocking the app you are testing. It is about a narrower, easy-to-miss case: sometimes the thing that needs testing is your own test *infrastructure*, not the app, and testing infrastructure code sometimes genuinely calls for a mock.

## What NOT to mock in this course

Never replace the RBAC backend itself with a fake in a test whose purpose is to verify the RBAC backend's behavior. A test using a mock instead of the real app is not testing the app anymore. It is testing that your mock behaves the way you told it to, which is circular. Every module up to this point (CRUD, RBAC, security, schema) is only meaningful because it is hitting a real, running server. That does not change from here forward either.

## Where a mock actually earns its place

The one place mocking is legitimate here is testing code *you* wrote *about* HTTP behavior, where you need to force a specific, hard-to-reproduce condition (a slow response, a malformed response, a connection that drops mid-request) that the real app will not reliably produce on demand. `WireMock` is a library purpose-built for standing up a fake HTTP server your test controls completely, and it is useful for exactly that narrow case.

Add it to `pom.xml`:

```xml
<dependency>
    <groupId>org.wiremock</groupId>
    <artifactId>wiremock</artifactId>
    <version>3.5.4</version>
    <scope>test</scope>
</dependency>
```

## A concrete case: testing a retry helper

Suppose you write a small helper that retries a flaky request a few times before giving up, useful infrastructure for a suite and exactly the kind of thing worth testing in isolation before you trust it. Create `src/test/java/com/example/rbactests/support/RetryHelper.java`:

```java
package com.example.rbactests.support;

import io.restassured.response.Response;

import java.util.function.Supplier;

public final class RetryHelper {

    private RetryHelper() {
    }

    public static Response withRetries(Supplier<Response> request, int maxAttempts) {
        Response lastResponse = null;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            lastResponse = request.get();
            if (lastResponse.getStatusCode() < 500) {
                return lastResponse;
            }
        }
        return lastResponse;
    }
}
```

Testing this against the real RBAC app is awkward: you would need the app to *reliably* return a `500` a specific number of times in a row before succeeding, which is not something you can make happen on demand. This is exactly the case WireMock solves: stand up a fake server that returns `500` twice, then `200`, and verify your retry logic actually calls it three times and returns the successful response.

```java
package com.example.rbactests.support;

import com.github.tomakehurst.wiremock.junit5.WireMockExtension;
import io.restassured.RestAssured;
import io.restassured.response.Response;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.RegisterExtension;

import static com.github.tomakehurst.wiremock.client.WireMock.*;
import static io.restassured.RestAssured.given;
import static org.junit.jupiter.api.Assertions.assertEquals;

class RetryHelperTest {

    @RegisterExtension
    static WireMockExtension wireMock = WireMockExtension.newInstance().build();

    @AfterEach
    void resetStubs() {
        wireMock.resetAll();
    }

    @Test
    void retriesUntilASuccessfulResponseComesBack() {
        wireMock.stubFor(get("/flaky")
                .inScenario("retry-demo")
                .whenScenarioStateIs(com.github.tomakehurst.wiremock.stubbing.Scenario.STARTED)
                .willReturn(aResponse().withStatus(500))
                .willSetStateTo("second-attempt"));

        wireMock.stubFor(get("/flaky")
                .inScenario("retry-demo")
                .whenScenarioStateIs("second-attempt")
                .willReturn(aResponse().withStatus(500))
                .willSetStateTo("third-attempt"));

        wireMock.stubFor(get("/flaky")
                .inScenario("retry-demo")
                .whenScenarioStateIs("third-attempt")
                .willReturn(aResponse().withStatus(200).withBody("{\"ok\":true}")));

        Response response = RetryHelper.withRetries(
                () -> given().baseUri(wireMock.baseUrl()).when().get("/flaky"),
                3
        );

        assertEquals(200, response.getStatusCode());
        wireMock.verify(3, getRequestedFor(urlEqualTo("/flaky")));
    }
}
```

`@RegisterExtension` with a `WireMockExtension` starts and stops a real, local HTTP server automatically around each test. `wireMock.baseUrl()` gives you its address, which is why `RetryHelper.withRetries` is called against `wireMock.baseUrl()` here instead of the real RBAC backend on `:5000`. WireMock's **scenarios** feature (`.inScenario(...)`, `.whenScenarioStateIs(...)`, `.willSetStateTo(...)`) is what makes the same endpoint return something different on the first, second, and third call, exactly the sequence needed to prove the retry logic actually retries rather than just checking it works against something that already returns `200` the first time. `wireMock.verify(3, getRequestedFor(...))` closes the loop: it does not just check the *final* response was `200`, it confirms the helper genuinely made three separate requests to get there, not one lucky one.

## The boundary, restated

Every other test in this course (CRUD, auth, RBAC, security, schema, database) stays exactly as it has been: real requests, against the real RBAC backend, on `:5000`. WireMock's only job in this suite is testing the retry helper itself, in complete isolation from network flakiness or the real app's actual behavior, because a flaky *test of a retry helper* would be a genuinely confusing thing to debug, and WireMock is what keeps it deterministic.

## Try it

Write a second WireMock-backed test proving `RetryHelper.withRetries` gives up correctly after `maxAttempts` if every response is a `500`: stub all three scenario states to return `500`, call `withRetries` with `maxAttempts = 3`, and assert the final returned response is still a `500` (not an exception, not a null) and that `wireMock.verify(3, ...)` confirms exactly three attempts were made, no more.
