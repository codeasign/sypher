## Page purpose

Module 6 locked down the Ticket Summarizer's contract: three fields, one system prompt, five ways to validate the output. Vespera's next move is to make `suggested_next_action` actually useful: instead of a generic suggestion, the feature now searches Vespera Helpdesk's knowledge base and past resolved tickets, and proposes a draft answer with citations the agent can review and send. That's a RAG system, retrieval-augmented generation, and it breaks the single-pass testing model from Module 6 in one important way: there are now two things that can independently go wrong. The retriever can fetch the wrong articles, or the model can be handed the *right* articles and still misuse them. This page teaches you to test those two failure surfaces separately, build a golden dataset for each, and, the sharpest lesson here, why an LLM-as-judge check that looks reassuring can still be wrong in a way only a human catches.

## Learning objectives

By the end of this page, you should be able to:

- Explain why retrieval quality and generation quality need independent evaluation, and what each one catches that the other doesn't.
- Build a golden dataset of (ticket, expected-relevant-KB-article-ids) pairs and use it to score retrieval recall.
- Write a groundedness and citation-accuracy check for generated answers, separating "did it cite something real" from "does the citation actually support the claim."
- Identify a concrete case where LLM-as-judge scoring disagrees with human evaluation, explain why the judge got it wrong, and describe what a human-reviewed golden set catches that the judge alone doesn't.

## Concepts

**RAG splits one feature into two testable stages.** Retrieval turns a query (here, a ticket thread) into a ranked list of source documents. Generation turns those documents plus the query into an answer. A RAG feature can fail at either stage independently, and the failures look completely different from the outside: a wrong-but-confident answer might mean the retriever handed the model nothing useful, or it might mean the retriever did its job perfectly and the model still ignored, misread, or misattributed what it was given. If you only test the combined output, you can't tell which one broke, which means you don't know whether to fix the search index or the prompt.

**Retrieval evaluation asks a factual, checkable question: were the right documents found?** Given a query, does the retriever's result set contain the documents a human would agree are actually relevant? This is measured with metrics like **recall@k** (of the documents that should have been retrieved, what fraction were, within the top k results), a mechanical, deterministic check with no model judgment involved on the scoring side.

**Generation evaluation asks a harder, semantic question: given what was retrieved, is the answer trustworthy?** This splits further into two distinct checks that are easy to conflate:

- **Groundedness**: is every factual claim in the answer actually supported by the retrieved content, as opposed to invented or drawn from the model's general knowledge?
- **Citation accuracy**: does each citation attached to a claim point at content that *specifically* supports *that* claim, not just at some real, retrievable document that happens to be topically nearby?

That distinction, "cites something real" versus "the citation actually supports the claim," is the crux of this page, and it's exactly where LLM-as-judge scoring tends to fail.

**LLM-as-judge is a useful, imperfect scoring tool.** Having a model score another model's output (grounded / not grounded, relevant / not relevant) is fast and cheap compared to human review, and it scales to a large golden set. But a judge model is subject to the same shortcuts a generation model is: it's far easier to verify "this citation ID exists in the retrieved set" than to verify "this specific sentence in the article supports this specific claim in the answer," and a judge prompt that doesn't force the harder comparison will quietly default to the easier one. Treat judge scores as a fast first pass, not ground truth, and calibrate them against a smaller set of human-reviewed cases so you know where the judge's blind spots are.

## Practical example

Vespera calls this extended feature the **Knowledge Assistant**. It takes the exact same input as Module 6's Ticket Summarizer, a ticket thread, but now also searches the knowledge base first, and its output grows two new fields on top of the three you already locked down:

```json
{
  "summary": "2-3 sentence factual summary of what's happened in the thread so far",
  "sentiment": "frustrated | neutral | satisfied",
  "suggested_next_action": "a short, human-readable suggestion for what the agent should do next",
  "draft_answer": "a draft reply the agent can review and send, grounded in the retrieved articles",
  "citations": ["KB-2210"]
}
```

`summary`, `sentiment`, and `suggested_next_action` are unchanged from Module 6, same names, same meaning, same feature. `draft_answer` and `citations` are new. The system prompt extends Module 6's rules rather than replacing them:

```python
KNOWLEDGE_ASSISTANT_SYSTEM_PROMPT = """\
You are Vespera Helpdesk's knowledge assistant. You will be given a support \
ticket thread and a set of retrieved knowledge-base articles that may be \
relevant to it.

Rules:
- Summarize only what is explicitly present in the thread. Never invent \
details that are not there.
- Base "draft_answer" only on the retrieved articles provided to you. Do \
not use outside knowledge, and do not state anything as policy unless a \
retrieved article actually supports it.
- Every claim in "draft_answer" that depends on a retrieved article must \
be attributable to one of the article IDs listed in "citations". Do not \
cite an article that does not support the specific claim it's attached to.
- "draft_answer" is a draft for a human agent to review and send — it is \
never sent automatically, and it must not claim an action (like a refund) \
has already happened.
- Respond with JSON only, using exactly these fields: "summary", \
"sentiment", "suggested_next_action", "draft_answer", "citations". No \
extra fields, no prose outside the JSON.
"""
```

The knowledge base and the retriever behind it are kept small and swappable, the same way `LLMProvider` kept the model swappable in Module 6:

```python
from typing import Protocol


class Retriever(Protocol):
    def retrieve(self, query: str, top_k: int = 3) -> list[str]:
        """Return up to top_k KB article IDs relevant to the query, ranked."""
        ...


KNOWLEDGE_BASE: dict[str, dict] = {
    "KB-1042": {
        "title": "How to reset your password",
        "content": (
            "To reset your password, go to Account Settings > Security. "
            "If you're locked out of your account, support can verify your "
            "identity and issue a new reset link. This process does not "
            "affect your billing or subscription status."
        ),
    },
    "KB-2210": {
        "title": "Refund eligibility policy",
        "content": (
            "Cancellations submitted within 7 days of the renewal charge "
            "are eligible for a full refund of that charge, processed "
            "automatically within 5 business days. Cancellations submitted "
            "after 7 days require Team Lead approval."
        ),
    },
    "KB-3301": {
        "title": "CSV export stuck on Processing",
        "content": (
            "If a report export stays on 'Processing' for more than 10 "
            "minutes, it usually means the export job is stuck in the "
            "queue. Restarting the export from the report page clears "
            "most stuck jobs; if it recurs, escalate to engineering."
        ),
    },
}


class KeywordRetriever:
    """Toy retriever: ranks KB articles by keyword overlap with the query.

    Vespera's real retriever uses an embedding index; this keeps the
    retrieval-evaluation code on this page runnable without a vector
    database dependency. The evaluation approach below doesn't care which
    retriever implementation is behind the `Retriever` protocol.
    """

    def __init__(self, knowledge_base: dict[str, dict]) -> None:
        self._kb = knowledge_base

    def retrieve(self, query: str, top_k: int = 3) -> list[str]:
        query_words = set(query.lower().split())
        scored = []
        for article_id, article in self._kb.items():
            article_words = set(article["content"].lower().split())
            overlap = len(query_words & article_words)
            if overlap > 0:
                scored.append((overlap, article_id))
        scored.sort(reverse=True)
        return [article_id for _, article_id in scored[:top_k]]


class RecordedRetriever:
    """Test double — always returns a fixed list of article IDs.

    Same role as Module 6's RecordedProvider: it lets you test the code
    that *consumes* retrieval results without depending on real retrieval
    quality, which is evaluated separately below.
    """

    def __init__(self, article_ids: list[str]) -> None:
        self._article_ids = article_ids

    def retrieve(self, query: str, top_k: int = 3) -> list[str]:
        return self._article_ids[:top_k]
```

And the generation call, reusing `LLMProvider` exactly as Module 6 defined it:

```python
import json


def answer_with_knowledge(
    thread: str,
    retriever: Retriever,
    provider: "LLMProvider",
    knowledge_base: dict[str, dict] = KNOWLEDGE_BASE,
    top_k: int = 3,
) -> dict:
    retrieved_ids = retriever.retrieve(thread, top_k=top_k)
    retrieved_context = "\n\n".join(
        f"[{article_id}] {knowledge_base[article_id]['title']}\n"
        f"{knowledge_base[article_id]['content']}"
        for article_id in retrieved_ids
        if article_id in knowledge_base
    )
    user_prompt = f"Ticket thread:\n{thread}\n\nRetrieved articles:\n{retrieved_context}"
    raw = provider.complete(KNOWLEDGE_ASSISTANT_SYSTEM_PROMPT, user_prompt)
    result = json.loads(raw)
    result["_retrieved_ids"] = retrieved_ids  # kept for evaluation, not shown to the agent
    return result
```

## AI/QE workflow

Retrieval and generation get evaluated as two separate pipelines that happen to share one golden dataset of tickets:

1. **Build the golden set**: a curated list of `(ticket, expected_kb_ids)` pairs, written by a human who knows what a correct answer should reference.
2. **Run retrieval evaluation** against the golden set's tickets, scoring recall@k for whatever `Retriever` implementation is under test. This never touches the LLM at all; it's fast, deterministic, and cheap enough to run on every change to the retriever or the KB.
3. **Run generation evaluation** separately, using either `RecordedRetriever` seeded with the golden set's *expected* article IDs (to test generation quality in isolation from retrieval quality) or the real retriever (to test the two stages combined, closer to production behavior).
4. **Score groundedness and citation accuracy** on the generated answers: a cheap mechanical check first (does every cited ID actually appear in the retrieved set?), then an LLM-as-judge pass for the harder semantic question (does the citation actually support the claim?).
5. **Sample judge results against a human-reviewed subset.** This is the step teams skip, and it's the one that catches what this page is really about; see Concepts above and the worked example below.
6. A QE reviews any failure and decides which stage it belongs to: a retrieval miss gets routed to whoever owns the index or embedding model, a generation or citation failure gets routed to whoever owns the prompt. Keeping the two evaluations separate is what makes that routing possible in the first place.

## Code requirements

Examples on this page are Python, continuing Module 6's `LLMProvider` abstraction unchanged: `answer_with_knowledge` above takes the same `LLMProvider` protocol, and `AnthropicProvider` still reads its key from `os.getenv("ANTHROPIC_API_KEY")`, never hardcoded. ## Vespera Systems scenario

The Knowledge Assistant replaces the plain suggestion in Module 6's `suggested_next_action` field with something an agent can act on directly: a draft reply, grounded in real KB content, with citations attached. It still lives in the same ticket detail view, still never sends anything without a human clicking send; that boundary from Module 6's system prompt (no self-authorized refund or account action) carries over unchanged, just applied to a longer piece of generated text instead of a short suggestion. As the QE owning this feature, your job is now genuinely two jobs: is Vespera's search actually finding the right knowledge for a given ticket, and separately, when it does, does the model actually use that knowledge correctly instead of just decorating a plausible-sounding answer with a real-looking citation. ## Failure modes

- **Treating retrieval recall as proof the answer is grounded.** The retriever can find exactly the right article and the model can still misstate what it says, or attach it to a claim it doesn't support. Recall tells you nothing about generation quality.
- **Treating a passing LLM-judge groundedness check as ground truth.** This is the failure mode this page centers on: a judge that only verifies "this citation ID is real and was retrieved" will confidently mark an answer grounded even when the cited article doesn't support the specific claim next to it; see the worked example in Concepts and Exercise above. Always calibrate the judge against a smaller human-reviewed set rather than trusting it in isolation.
- **Conflating citation format with citation accuracy.** "The citation points at a real, retrieved article" is a cheap, deterministic check worth running on every case. "The citation supports this specific claim" is a semantic judgment call that a format check cannot make; running only the cheap check and calling it done is exactly how ungrounded-but-cited answers slip through.
- **A retrieval golden set with no adjacent-but-wrong distractors.** If every golden-set case has one obviously-relevant article and nothing else plausible nearby, you'll never catch the case where the retriever (or the model choosing what to cite) picks the topically-nearby-but-wrong article instead of the right one.
- **Evaluating retrieval and generation as one combined pass/fail.** If you only score the final answer, a retrieval failure and a generation failure look identical from the outside; you lose the ability to tell whether the fix belongs to the index or the prompt.

## Security considerations

Knowledge-base articles and past resolved tickets both need the same discipline as ticket threads in Module 6: no real customer data, PII, or proprietary Vespera content in any fixture, golden-set entry, or example; every article and ticket on this page is fabricated. Because the Knowledge Assistant retrieves from *past tickets* as well as static KB articles, there's a data-scoping question that doesn't exist in Module 6: a retrieval index built carelessly across all tickets could surface one customer's ticket content into another customer's draft answer. This page assumes that scoping is handled correctly by the retrieval layer; Module 8 covers what happens when ticket text is adversarially crafted to try to defeat scoping or extract content it shouldn't have access to. `ANTHROPIC_API_KEY` continues to be read from the environment via `AnthropicProvider`, never hardcoded or checked into a fixture.

## Guardrails

Two guardrails carry forward unchanged from Module 6: `draft_answer` is never sent automatically, an agent always reviews it first, and the system prompt still forbids stating that an action (like a refund) has already happened. This page adds one guardrail specific to RAG: a cheap, deterministic pre-check that rejects any response where a `citations` entry isn't actually among the retrieved article IDs for that call; a model citing an article it was never even given is a clear-cut failure that shouldn't need an LLM judge to catch. The harder guardrail, requiring every refund- or account-eligibility claim to be traceable to a citation that a human (not just the judge) has confirmed actually supports it, is exactly what the human-reviewed golden set exists to enforce, since the judge alone demonstrably isn't sufficient for that class of claim.

## Production considerations

Recall@k against the retrieval golden set is cheap enough to run on every change to the KB or retriever; run it there. Full LLM-judge groundedness scoring costs real model calls, so most teams run it on pull requests touching the prompt or retriever, plus a scheduled full run against the combined golden set. The judge-versus-human agreement rate is itself worth tracking as a metric over time: if it drifts down, that's a signal the judge prompt needs to be sharpened (for instance, forcing it to quote the specific supporting sentence from the cited article rather than just confirming the article exists) before you can trust it to catch regressions unattended. As the knowledge base grows and gets edited, periodically re-run the retrieval golden set; an article rewrite can silently change which queries it ranks for, the same way a prompt edit can silently change generation quality in Module 6.
