## Page purpose

This page exists to set expectations before Module 1 starts, not to teach anything hands-on yet. By the time you leave it, you should know whether this course is aimed at you, what it's going to assume you already know, what the course's one working principle means in practice, and who Vespera Systems is — the fictional company whose story runs through every module that follows. Nothing here is graded and nothing here is tested; Module 1 is where the actual content begins.

## Learning objectives

By the end of this page, you should be able to:

- State the course's working principle — "AI generates. QE validates." — in your own words, and explain why it matters more than any specific tool.
- Describe what this course assumes you already know, and recognize if you're missing a prerequisite before you hit friction in Module 2.
- Describe Vespera Systems and its ticketing platform well enough to recognize it when it comes back, module after module, as the same continuous story rather than a new example each time.
- Identify the two halves of the course — AI as a tool for QE work, and AI as a system that itself needs testing — and see roughly where the line between them falls.

## Concepts

Two ideas carry the whole course, and it's worth being precise about both before Module 1 uses them.

**"AI generates. QE validates."** AI-generated output — a test scenario, a chunk of automation code, a summary of a support ticket, an agent's next action — is a draft. It is never the source of truth. Your judgment is. That's true whether the AI is helping you produce testing artifacts faster, or the AI itself is the feature under test. The phrase is short on purpose: it's meant to be the one thing you can recall under pressure, when a deadline is tempting you to skip the review step because "the AI probably got it right."

**Two directions of AI in QE work.** Most courses about AI and testing conflate two very different relationships between AI and quality engineering. This one keeps them deliberately separate:

- **AI as a productivity tool for QE** — using AI to generate test scenarios, generate automation code, help diagnose a failing test, and formalize the review process around all of that so speed doesn't come at the cost of trust.
- **AI as a system under test** — testing the AI-powered features a product team ships: an LLM feature, a retrieval-augmented system built on top of it, and eventually a tool-using agent, each of which needs its own testing discipline that traditional functional testing doesn't fully cover.

The first half of this course (Modules 1-5) lives in the first bullet. The second half (Modules 6-9) lives in the second. Module 10 and the capstone bring both halves together.

## Practical example

This page sets expectations rather than walking through a hands-on example — the first practical example starts in Module 2, where you'll take a real Vespera requirement and generate test scenarios from it with AI.

## AI/QE workflow

There's no workflow to run through yet — Module 2 introduces the first one, taking you from a written requirement through AI-generated test scenarios and a QE review pass. What's worth internalizing now is the *shape* every later workflow in this course follows: AI produces a first draft quickly, and a QE step immediately follows it to check that draft before it's trusted with anything downstream — a test suite, a merge, a customer-facing action. Every module's workflow is a variation on that same generate-then-validate shape, just applied to a different artifact.

## Code requirements

There's no code on this page. From Module 2 onward, code examples follow the language that best fits what's being tested: Playwright with TypeScript (`@playwright/test`) for the UI automation modules (3, 4, and part of 5), and Python with a small provider abstraction for the AI-systems-under-test modules (6 through 10 and the capstone). Every code example in this course, without exception, avoids hardcoding credentials, API keys, secrets, or anything resembling real customer data — even in examples that are deliberately showing broken or insecure code.

## Vespera Systems scenario

Every module in this course happens inside one company: **Vespera Systems**, which builds **Vespera Helpdesk**, a B2B customer-support and ticketing platform used by mid-size companies. Its traditional product surface looks like a lot of B2B SaaS you've probably tested before — ticket CRUD, SLA tracking and escalation, agent assignment queues, reporting dashboards, and role-based access across Support Agent, Team Lead, and Admin roles.

What makes Vespera the right company for this course is what it's doing *now*: it's layering AI capabilities on top of that traditional app — an LLM feature, a retrieval-augmented system, and a tool-using agent — without giving up any of the surface it already had. You are the QE who owns quality across all of it. Not just the traditional CRUD screens, and not just the new AI features in isolation, but the whole platform as it exists once both are shipping side by side.

This is one continuous, evolving story, not a new unrelated example every module. A requirement you see reviewed in Module 2 is still the thing being automated in Module 3, still the thing that breaks in Module 4, and still the thing being formalized under guardrails in Module 5. An AI feature introduced around Module 6 is still the thing being extended, attacked, and eventually turned into an agent in the modules that follow it. Coming attractions worth knowing the names of now, without getting into how any of them work yet: an **SLA auto-escalation** requirement that anchors the traditional-feature thread, and three AI features — a ticket **summarizer**, a **knowledge assistant**, and a ticket **triage agent** — that anchor the AI-systems-under-test thread. None of that gets worked through here; that's what the rest of the course is for.

## Exercise

This page sets expectations rather than walking through a hands-on example — there's nothing to practice yet. The first exercise in this course is in Module 2, where you'll review a batch of AI-generated test scenarios and fix the weak ones.

## Failure modes

Not applicable to this page in the sense the later modules mean it — there's no artifact here that can fail. The failure mode worth naming at this stage is a *course-level* one: treating either half of this course as optional. Skipping the first half because "I already know how to use AI to write tests" tends to mean skipping the review discipline that makes that usage safe. Skipping the second half because "I don't test AI features yet" tends to age badly given how fast that's changing. The course is ordered the way it is because each half sharpens judgment the other half depends on.

## Security considerations

Not applicable to this page directly — there's no code or data here to secure. The standing rule for the rest of the course: every example that touches credentials, API keys, secrets, or anything resembling real customer data keeps it obviously fake (`sk-fake-...`, `customer@example.com`, and similar), even when the example is specifically showing a *bad* practice. You'll see this rule applied for real starting in Module 2's note about not pasting proprietary requirements into third-party AI tools.

## Guardrails

Not applicable to this page directly — there's no AI output here to guard. The concept itself is introduced properly in Module 5, once Modules 2 through 4 have given you enough informal review experience to know what a guardrail is actually protecting against.

## Production considerations

Not applicable to this page directly. The course does build toward production-shaped concerns — quality gates in CI, human approval steps before customer-facing actions, provider abstraction so a system isn't locked to one AI vendor — but those show up starting in Module 5 and continuing through the capstone, once there's an actual system to run in production.

## Dependencies

This page has none — it's the starting point. What it depends on *you* already having is the course's stated prerequisite knowledge: testing, automation, APIs, basic programming, and CI/CD. If any of those feel shaky, it's worth shoring them up before Module 1, since nothing from here forward re-explains them.
