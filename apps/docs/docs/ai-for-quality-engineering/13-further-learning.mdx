## Page purpose

This page closes the course. It isn't new instructional content: there's nothing here to learn hands-on, nothing that gets tested, and nothing Vespera-shaped. Its only job is to name, briefly and honestly, the territory this course deliberately left out, so you know where the edges of what you just learned are and what to go looking for next if your work takes you past them.

## Why this page skips the usual structure

Every module page in this course carries the same fourteen sections. This one doesn't, on purpose. Learning objectives, Concepts, Practical example, AI/QE workflow, Code requirements, Vespera Systems scenario, Diagram, Exercise, Failure modes, Security considerations, Guardrails, Production considerations, and Dependencies all assume there's a skill being built or a system being worked through, and there isn't one here. Forcing this page into that shape would mean padding a pointer page into a fake eleventh module. So: noted explicitly, skipped deliberately, for all thirteen of them.

## What this course scoped down on

This course followed a Pareto-style priority order: the ten highest-leverage areas of AI in quality engineering, covered in enough depth to actually use, rather than a shallow survey of everything adjacent to the topic. A few large areas got left out entirely, not because they don't matter, but because covering them properly would have doubled the course's length without changing the judgment it's trying to build. In no particular order:

- **Commercial AI test-generation platforms.** This course taught the underlying skill (reviewing and validating AI-generated tests against a checklist) using plain prompting and hand-written code, so the skill transfers no matter which tool you end up using. It never named or evaluated specific commercial products in that space. If your team adopts one, the review discipline from Modules 2 and 5 still applies; the tool just becomes the thing generating the draft.
- **The broader LLMOps ecosystem.** Modules 6 and 7 covered prompt testing, output evaluation, and RAG evaluation as disciplines, using a minimal provider abstraction rather than any particular platform. Production LLMOps tooling (prompt versioning systems, managed evaluation platforms, tracing and observability dashboards purpose-built for LLM pipelines) is a real and fast-moving space worth exploring once you're running these evaluations at scale, beyond what a golden dataset and a script can comfortably handle.
- **Deeper agent-orchestration frameworks.** Module 9 tested a small, deliberately scoped agent with five tools and a hard boundary around what it could do. It didn't cover the frameworks built for orchestrating many agents, complex planning graphs, or long-running autonomous workflows. The testing concerns from Module 9 (tool-call correctness, trajectory bugs, permission boundaries, state and regression) carry over directly to those frameworks; what changes is the surface area, not the underlying questions you're asking.

## Where to go from here

If any of the above is relevant to your work, the honest next step is to explore that category's current options directly: this page intentionally doesn't name products or link to any, in keeping with this course's rule against pointing at external URLs that might drift or go stale. Search for the category, not a brand: "commercial AI test-generation tools," "LLMOps evaluation platforms," "agent-orchestration frameworks." Evaluate anything you find the same way this course taught you to evaluate an AI-generated test: as a draft to validate, not a source of truth.

That's it. That's the whole page. Thanks for working through the course, go validate something.
