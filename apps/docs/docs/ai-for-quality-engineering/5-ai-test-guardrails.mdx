Modules 2 through 4 asked you to review AI-generated scenarios, review AI-generated automation, and judge AI-generated fixes — each time, by applying a checklist in your head. That works when you're the only reviewer and you remember every rule. It stops working the moment a second QE joins the team, or the AI tooling changes providers, or someone is reviewing test code at 5pm on a Friday and skims past something they'd normally catch. This module turns those informal habits into a guardrail *system*: checks that run whether or not a human remembers to run them, gates that block a merge instead of relying on someone noticing, and a division of labor between what a machine should catch and what only a human should decide.

## Page purpose

To take the ad hoc review instincts built in Modules 2-4 and formalize them into a concrete, repeatable guardrail system — automated checks that catch mechanical problems (secrets, banned patterns, missing assertions) before a human ever needs to look, plus a structured approval workflow for the judgment calls that automation can't make. By the end of this module you'll have a real, runnable static-analysis check and a quality-gate checklist you can apply to any AI-generated test, not just the ones in this course.

## Learning objectives

- Explain why "a QE reviews it" isn't a guardrail by itself, and what turns a review habit into a system
- Categorize guardrail types: human review, code review, static analysis, security scanning, quality gates, approval workflows — and know which layer catches which class of problem
- Write a real static-analysis check that fails CI when AI-generated test code contains a hardcoded secret-shaped string
- Apply a concrete quality-gate checklist to a real automation script and produce a pass/fail verdict with reasons, not just a gut feeling
- Recognize which weak patterns a guardrail system can catch automatically and which ones still require a human's domain judgment

## Concepts

**A guardrail is not a review.** A review is an event — someone looks at a diff and forms an opinion. A guardrail is a standing check that runs the same way every time, regardless of who's on call, how tired they are, or how much they trust the AI tool that generated the code that day. The goal of this module is to move as much of Modules 2-4's checklist as possible out of "things a human remembers to check" and into "things that fail the build automatically."

**Six guardrail layers, each catching a different kind of problem:**

1. **Human review** — a person reads the generated test/automation and judges whether it actually tests the right thing. This is irreplaceable for anything that requires understanding the requirement (does this scenario cover the "ticket already Urgent" edge case from Module 2? Does this assertion check the right business rule?). No static tool can tell you whether a test is *meaningful* — only whether it follows certain mechanical rules.
2. **Code review** — the same pull-request process you'd apply to any other code change: readability, naming, duplication, whether the test fits the existing suite's conventions. AI-generated code doesn't get a pass on this just because a human didn't type it character by character.
3. **Static analysis** — automated, rule-based scanning of the code itself, without running it. This catches structural problems: banned patterns (`waitForTimeout`), forbidden selector types (auto-generated CSS classes), missing assertions. This is where today's lint rule lives.
4. **Security scanning** — a static analysis subtype worth calling out on its own, because the failure mode is different in kind, not just degree. A missing assertion makes a test weak. A hardcoded credential in a test file that gets committed to a repo is a security incident waiting to happen, and it deserves its own dedicated check rather than being one bullet point in a general lint config.
5. **Quality gates** — a pass/fail checkpoint that aggregates the results of the layers above (plus manual checklist items) into a single go/no-go decision before code can merge. This is the checklist you'll build later in this module.
6. **Approval workflows** — who is authorized to override a failing gate, and under what circumstances. Not every guardrail should be un-overridable — but every override should be visible, attributed, and justified, not a quiet force-merge.

The layers build on each other: static analysis and security scanning are cheap, fast, and automatic — run them on every commit. Human review and code review are slower and require a person — reserve them for what the automated layers structurally can't judge. A quality gate is where both kinds of check meet before anything ships.

## Practical example

Here's the check this module is built around: a lint rule that fails CI if AI-generated test code contains a hardcoded secret-shaped string. This is deliberately the simplest possible guardrail — a regex-based scanner with no dependencies — because the point isn't sophistication, it's that *this kind of check should exist and should run automatically*, not that it needs to be clever.

```javascript title="scripts/check-no-hardcoded-secrets.js"
#!/usr/bin/env node
// Fails with a non-zero exit code (and CI fails with it) if any staged
// test file contains a hardcoded secret-shaped string. Run this in CI
// against every file AI generated or touched, not just a sample.

const fs = require('fs');
const path = require('path');

// Each pattern targets one common secret shape. Keep patterns narrow
// enough to avoid false-positiving on legitimate test fixtures (e.g. a
// test asserting that a 401 response body contains the word "password").
const SECRET_PATTERNS = [
  {
    name: 'Bearer token literal',
    regex: /Authorization\s*[:=]\s*['"`]Bearer\s+[A-Za-z0-9_\-.]{10,}['"`]/,
  },
  {
    name: 'sk- style API key literal',
    regex: /['"`]sk-[A-Za-z0-9]{16,}['"`]/,
  },
  {
    name: 'hardcoded password assignment',
    // Matches `password: "hunter2"` / `password = 'hunter2'` but not
    // `password: process.env.TEST_PASSWORD` or an empty-string check.
    regex: /password['"`]?\s*[:=]\s*['"`](?!\s*\$\{|process\.env)[^'"`\s]{4,}['"`]/i,
  },
];

function scanFile(filePath) {
  const content = fs.readFileSync(filePath, 'utf8');
  const findings = [];

  content.split('\n').forEach((line, index) => {
    for (const pattern of SECRET_PATTERNS) {
      if (pattern.regex.test(line)) {
        findings.push({
          file: filePath,
          line: index + 1,
          rule: pattern.name,
          snippet: line.trim(),
        });
      }
    }
  });

  return findings;
}

function main() {
  const targetFiles = process.argv.slice(2);
  if (targetFiles.length === 0) {
    console.error('Usage: node check-no-hardcoded-secrets.js <file1> <file2> ...');
    process.exit(2);
  }

  let allFindings = [];
  for (const file of targetFiles) {
    if (!fs.existsSync(file)) continue;
    allFindings = allFindings.concat(scanFile(file));
  }

  if (allFindings.length > 0) {
    console.error(`\nHardcoded secret check FAILED — ${allFindings.length} finding(s):\n`);
    for (const finding of allFindings) {
      console.error(`  ${finding.file}:${finding.line}  [${finding.rule}]`);
      console.error(`    ${finding.snippet}\n`);
    }
    console.error('Replace hardcoded values with environment variables or a secrets manager reference, then re-run.');
    process.exit(1);
  }

  console.log(`Hardcoded secret check passed (${targetFiles.length} file(s) scanned).`);
  process.exit(0);
}

main();
```

An obviously-fake example of what this catches — the kind of thing an AI tool will happily generate if you ask it to "add an authenticated request to the test":

```typescript title="tests/sla-escalation.spec.ts (example of what the check flags — do not commit this)"
test('escalation webhook fires with auth header', async ({ request }) => {
  const response = await request.post('/api/webhooks/slack', {
    headers: {
      Authorization: 'Bearer sk-fake-1234567890abcdef', // flagged: sk- style key literal
    },
    data: { ticketId: 4821 },
  });
  expect(response.ok()).toBeTruthy();
});
```

Wired into CI as a required check on every pull request:

```yaml title=".github/workflows/test-guardrails.yml"
name: Test Guardrails

on:
  pull_request:
    paths:
      - "tests/**"

jobs:
  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Scan changed test files for hardcoded secrets
        run: |
          CHANGED_FILES=$(git diff --name-only origin/main...HEAD -- 'tests/**')
          if [ -n "$CHANGED_FILES" ]; then
            node scripts/check-no-hardcoded-secrets.js $CHANGED_FILES
          fi
```

This runs on *every* pull request touching `tests/`, regardless of whether the code came from an AI tool or a human typed it by hand — the check doesn't know or care about provenance, which is exactly the point. A guardrail that only runs on "AI-generated" code creates a false sense of safety around everything else.

## AI/QE workflow

The workflow this module formalizes:

1. AI generates a test or automation script (Modules 2-3).
2. Before a human ever opens the diff, static analysis and security scanning run automatically — the secret scanner above, plus a broader lint pass (banned patterns like `waitForTimeout`, selector-type checks).
3. If either of those fails, the pull request is blocked immediately. No human review time is spent on code that fails a mechanical check — that's the entire point of putting these first.
4. If static analysis and security scanning pass, a human applies the quality-gate checklist (below) — the judgment-requiring items a machine can't fully evaluate: are the assertions actually meaningful for this requirement, does the test cover the edge cases the requirement calls for, is the isolation strategy sound.
5. The quality gate produces a pass/fail verdict with reasons attached — not a silent approve.
6. Anything that fails the gate but the team believes should still merge (rare, and it should stay rare) goes through the approval workflow: a named override, visible in the PR, from someone with the authority to accept the risk — never a quiet force-merge.

The key shift from Modules 2-4: those modules taught you *what* to look for. This module makes looking for it non-optional and non-forgettable.

## Code requirements

- The secret scanner has no external dependencies — plain Node.js `fs` and regular expressions — so it can run in any CI environment without an install step, and so its logic is auditable in one file.
- Patterns are deliberately narrow (minimum length thresholds, explicit prefixes like `sk-`) to keep false positives low; a guardrail that cries wolf on legitimate code gets disabled by a frustrated team within a month.
- The password pattern explicitly excludes `process.env` references and template-literal interpolation (`` ${...} ``) — the check should never flag the *correct* way to reference a credential, only a literal one.
- The example secret above (`sk-fake-1234567890abcdef`) is obviously non-functional — it doesn't match any real provider's key format and can't be used to authenticate against anything. Never substitute a real key, even temporarily, when testing this check.
- Exit code `1` on any finding, `0` on a clean scan, `2` on misuse — CI treats only `0` as green, matching how any other required check behaves.

## Vespera Systems scenario

Apply this module's quality-gate checklist to Module 2's SLA Auto-Escalation requirement and Module 3's Playwright automation for it. As a reminder of what's under review: the requirement says that when a ticket's SLA countdown hits 60 minutes remaining while it's still `status: "Open"` with no recent agent activity, the system bumps `priority` to `"Urgent"`, sets `escalated_by_system: true`, and fires a Slack webhook notification — with edge cases around already-`Urgent` tickets, unassigned tickets, tickets closed before the mark, simultaneous breaches, and the SLA timer pausing during `"Waiting on Customer"`.

**The checklist:**

| # | Criterion | What it catches |
|---|---|---|
| 1 | Assertions are present and specific — not just "no error was thrown" | Tests that pass regardless of actual behavior |
| 2 | No arbitrary sleeps (`waitForTimeout`, fixed delays) — async waits use Playwright's built-in retrying assertions (`expect.poll`, `toHaveText`, auto-waiting locators) | Flaky tests that pass or fail based on machine speed |
| 3 | Selectors use `data-testid` (or role/label) — never auto-generated CSS classes | Tests that break on every unrelated style change |
| 4 | No hardcoded entity IDs (ticket IDs, user IDs) — data is seeded and referenced by variable, not a magic number | Tests that only work against one specific database state |
| 5 | No hardcoded secrets — covered automatically by the scanner above | Credential leakage into version control |
| 6 | Test isolation — creates and cleans up its own data rather than assuming a shared starting state | Order-dependent test suites that fail when run in parallel or out of sequence |

**Applying it to Module 3's automation, item by item:**

- **The `data-testid="ticket-priority-badge"` selector** — **passes** criterion 3. It's a stable, purpose-built test hook, not an incidental implementation detail like a CSS module class.
- **The hardcoded `page.waitForTimeout(5000)`** — **fails** criterion 2. A fixed 5-second wait is a guess about how long the background escalation job takes. On a slow CI runner it's not long enough and the test flakes; on a fast one it wastes five seconds every run for no benefit. The fix from Module 3 — `expect(page.getByTestId('ticket-priority-badge')).toHaveText('Urgent')`, which polls with Playwright's built-in retrying assertion until it's true or a real timeout elapses — passes.
- **The auto-generated CSS class fallback (`.css-1x2y3z`)** — **fails** criterion 3 outright. It isn't just weaker than `data-testid`; it will break the next time the styling library regenerates class names, with zero relationship to whether the feature still works.
- **Treating escalation as synchronous** — this is an **incorrect assumption**, not a mechanical checklist failure by itself, but it's exactly the kind of thing criterion 1 exists to catch indirectly: an assertion written against the wrong timing model either flakes (caught by criterion 2's review) or silently asserts on stale state. This is also a good example of where the checklist's mechanical items and a human's domain knowledge meet — a static scanner can tell you *that* there's a wait, not whether the wait models the real system correctly. That judgment call belongs to a human reviewer who knows the escalation job runs asynchronously.
- **Poor isolation (assuming ticket IDs start fresh instead of seeding and cleaning up its own ticket)** — **fails** criterion 6 and, in practice, criterion 4 as well if the weak version hardcodes an assumed ticket ID rather than seeding one through the test-only API endpoint and referencing the returned ID.

**Net verdict:** the AI-generated first draft fails the gate on criteria 2, 3, and 6 (and would separately fail security scanning if it ever hardcoded a test credential, which this particular draft didn't). None of those are subtle — that's deliberate. A gate that only catches obscure problems isn't earning its keep; the majority of what it should catch is exactly this kind of mechanical, repeatable mistake. The QE-corrected version from Module 3 — `data-testid` selector, `toHaveText` retrying assertion, seeded-and-cleaned-up ticket — passes all six criteria and is what actually merges.

## Exercise

Here's a new, small AI-generated Playwright test for Vespera's SLA Auto-Escalation feature. Apply this module's six-item quality-gate checklist and determine pass or fail — and cite which specific criteria it fails, by number.

```typescript title="tests/sla-escalation-notify.spec.ts (exercise — do not treat as a working example)"
import { test, expect } from '@playwright/test';

test('team lead is notified when an unassigned ticket breaches SLA', async ({ page, request }) => {
  // Seed a ticket 61 minutes from breach with no assigned agent
  await request.post('/api/test/seed-ticket', {
    data: { id: 7734, status: 'Open', minutesToBreach: 61, assignedAgent: null },
  });

  await page.goto('/dashboard/tickets/7734');
  await page.waitForTimeout(6000);

  await expect(page.locator('.css-priority-badge-9f2a1')).toContainText('Urgent');
});
```

Work out your verdict before reading on: which of the six criteria does this snippet satisfy, and which does it fail? Consider the seeding call, the wait strategy, the selector, and what — if anything — the test actually asserts about the *notification* the test's own name promises to check.

<details>
<summary>Worked answer</summary>

**Verdict: fails the gate.** Three criteria fail:

- **Criterion 2 (no arbitrary sleeps)** — `page.waitForTimeout(6000)` is a fixed guess, exactly the pattern Module 3 already corrected once. It should be a retrying assertion (`toHaveText`, `expect.poll`) waiting on the actual condition, not a timer.
- **Criterion 3 (`data-testid`, not auto-generated classes)** — `.css-priority-badge-9f2a1` is a styling-library-generated class name, the same brittle-selector failure from Module 3's original draft. It should use `data-testid="ticket-priority-badge"`.
- **Criterion 4 (no hardcoded entity IDs)** — ticket `7734` is a magic number baked directly into both the seed call and the URL. It should be seeded through the test-only endpoint and the *returned* ID used to navigate, so the test doesn't depend on that exact ID existing or being available.

There's also a **coverage gap worth flagging even though it's not one of the six mechanical criteria**: the test's name promises to check that "the team lead is notified" — the edge case from Module 2 about unassigned tickets escalating to the team lead instead of an agent — but the test only asserts on the priority badge. It never asserts on the Slack webhook call at all. A human reviewer applying criterion 1 (assertions present and specific) should catch that the test doesn't actually test what its own name claims.

Criteria 5 and 6 pass: no secret-shaped string appears, and the ticket is seeded via the test API rather than assumed to already exist — though the hardcoded ID undercuts the isolation intent, since a second run against a database where `7734` already exists would collide.

</details>

## Failure modes

- **Guardrail fatigue** — too many low-value or noisy checks (aggressive false positives) trains reviewers to click through gate failures without reading them, which is worse than having no gate at all, because it creates false confidence.
- **Checking the code, not the intent** — a test can satisfy every mechanical criterion on this checklist (real assertions, no sleeps, `data-testid` selectors, no hardcoded IDs, no secrets, clean isolation) and still test the wrong thing entirely, because it asserts on the wrong field or misses the requirement's actual edge case. Static checks catch *how* a test is written; only a human checks *what* it verifies — see the "team lead notified" gap in the exercise above.
- **A gate with no teeth** — a quality gate that can always be overridden with no friction and no record isn't a gate, it's a suggestion. If overrides are frequent, that's a signal the gate's criteria are miscalibrated, not that the workflow needs to get more lenient by default.
- **Scanning only what's obviously AI-generated** — treating the secret scanner or lint rules as an "AI code tax" rather than running them on all test code erodes the guardrail's value fast, since the same mistakes happen in human-written code too, and provenance-based scanning creates an obvious way to route around the check (just don't label something as AI-generated).
- **Static analysis drifting stale** — a banned-pattern list that never gets updated as new weak patterns emerge (a new UI library's auto-generated class format, a new secret prefix from a newly adopted AI provider) quietly stops catching what it was built to catch. The checklist needs an owner, not just an initial author.

## Security considerations

- Never commit a real credential to demonstrate what the secret scanner catches — every example in this module uses an obviously fake, non-functional string (`sk-fake-...`), and that discipline should carry into your own test suites: even a "temporary" real key committed to git history is effectively permanent.
- The secret scanner is a safety net, not the only control — pair it with actual secret storage (environment variables injected by the CI runner, a secrets manager) so there's no legitimate reason for a real credential to appear in a test file in the first place.
- Treat a scanner finding as a signal to investigate immediately, not something to triage later — a leaked credential in a public or even internal repo should be rotated on discovery, regardless of whether it's later confirmed to be "just a test key."
- Keep the scanner's pattern list itself out of anything that would help an attacker evade it in a security-sensitive context — for test-guardrail purposes this isn't a serious concern (the patterns here are generic secret shapes, not a security product), but it's worth the habit of not over-explaining detection internals in public-facing documentation for tools with a higher stakes profile.

## Guardrails

This entire module *is* the guardrails section for Modules 2-4's practices, so here's the system stated as a single reference:

- **Human review** — catches: does this test verify the right requirement, does it cover the right edge cases, is the automation's intent sound.
- **Code review** — catches: readability, duplication, consistency with the existing suite's conventions.
- **Static analysis** — catches: banned patterns (`waitForTimeout`), brittle selectors, structural checklist items 1-4 and 6 where they're mechanically detectable.
- **Security scanning** — catches: hardcoded secrets, specifically and automatically, as demonstrated by today's check.
- **Quality gates** — aggregate all of the above plus manual checklist judgment into one pass/fail decision, with reasons attached.
- **Approval workflows** — the deliberate, visible, attributed exception path for the rare case a failing gate still needs to merge — never a silent bypass.

## Production considerations

- Run static analysis and security scanning as required PR checks, not optional/advisory ones — a check a team can merge past without a false-positive investigation isn't providing real protection.
- Keep the secret scanner (and lint checks generally) fast — under a few seconds per run — so it runs on every commit rather than being relegated to a nightly job that only catches problems after they've already been merged.
- Version and review changes to the banned-pattern list and checklist criteria the same way you'd review any other code change — these files are load-bearing, not incidental config.
- Track override frequency on the quality gate as a metric. A rising override rate is an early signal that either the gate's criteria have drifted out of sync with how the app or AI tooling has changed, or that the team is under schedule pressure that's eroding the review discipline this whole module is meant to protect.
- As new AI tools or providers get adopted for test/automation generation (as this course's provider-abstraction principle anticipates elsewhere), re-validate that the existing guardrails still catch that tool's characteristic mistakes — different AI tools tend to have different failure fingerprints.

## Dependencies

- Modules 2 and 3's Vespera SLA Auto-Escalation requirement and its Playwright automation, which this module's worked example and exercise both build directly on.
- Module 4's distinction between "needs updating" and "reveals a real bug," which the checklist's assertion-specificity criterion (item 1) leans on when judging whether an assertion is actually meaningful.
- Standard CI infrastructure capable of running a required check on pull requests (this module's example uses GitHub Actions, matching this site's other automation modules, but the underlying scanner is CI-platform-agnostic Node.js).
- No new external tooling is introduced — the scanner is deliberately dependency-free so its logic stays auditable and portable across CI environments.
