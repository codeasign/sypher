Module 1 made the case for AI as a productivity tool for QE, in the abstract. This module is where that stops being abstract: a real Vespera Systems requirement, a real batch of AI-generated test scenarios, and a real review pass where you, not the AI, decide what's actually good enough to automate. Everything Module 3 turns into Playwright code comes out of this module's review, so the scenario set you land on here isn't a throwaway exercise. It's the input to the next module.

## Page purpose

Teach you how to turn a written requirement into a batch of AI-generated test scenarios, and, the part that actually takes judgment, how to tell a strong scenario from a weak one before it ever reaches automation. By the end, you'll have a reviewed, approved scenario set for one real Vespera requirement, built the same way you'd do it on the job.

## Learning objectives

- Turn a product requirement into a prompt that produces a usable batch of test scenarios, including edge cases the requirement text only implies.
- Recognize the five weak-test patterns AI tends to produce: missing assertions, weak assertions, duplicate tests, happy-path bias, and missing edge cases.
- Review an AI-generated scenario batch against that checklist and fix, or reject, each weak scenario.
- Produce an approved scenario set that's specific enough for another engineer (or another module) to automate without guessing your intent.

## Concepts

**Scenario generation** is AI reading a requirement and proposing a list of test cases: plain descriptions of what to test and what should happen, not automation code yet. That split matters: generating scenarios and generating automation are different skills with different failure modes, which is exactly why this course gives them separate modules (this one, then Module 3).

AI is good at *breadth* (it'll produce a scenario list faster than you'd type the headings) and unreliable at *depth*. It tends to restate the requirement's happy path several times with cosmetic differences, gesture at edge cases without fully specifying them, and write assertions vague enough to pass almost anything. None of that means the output is useless. It means the output is a draft, and drafts get reviewed.

**The weak-test-pattern checklist** is the tool you review a draft against. Five patterns to look for in every AI-generated scenario:

- **Missing assertions**: the scenario describes an action and a vague "and it works" with nothing to actually check.
- **Weak assertions**: there's an assertion, but it's not specific enough to catch a real failure (e.g. "the ticket updates" instead of naming the field and the expected value).
- **Duplicate tests**: two scenarios that differ only in wording, testing the same behavior twice while a real edge case goes uncovered.
- **Happy-path bias**: the batch is heavy on "does the feature work when everything goes right" and light on what happens when it doesn't.
- **Missing edge cases**: a requirement usually implies boundary conditions and interacting states the prose never spells out; a first-pass AI batch tends to miss the ones that take real domain thinking to surface.

You'll use this exact checklist against a real batch below, and again on a fresh one in the exercise.

## Practical example

Here's the requirement as it landed in Vespera's backlog. This is the requirement you'll carry through Modules 2 to 5.

> **SLA Auto-Escalation**
> When a ticket's SLA countdown reaches 60 minutes remaining and the ticket is still `status: "Open"` with no recent agent activity, the system automatically:
> - bumps the ticket's `priority` field to `"Urgent"`,
> - sets `escalated_by_system: true` on the ticket,
> - fires a Slack notification to the assigned agent's team channel (via a webhook).

Reading the requirement text alone gives you the happy path: ticket open, no activity, 60 minutes left, escalate. Getting to a real scenario batch takes one more step: asking what the requirement doesn't say out loud. Five edge cases fall out of a careful read:

- The ticket is **already** `"Urgent"` when the countdown hits 60 minutes: does it escalate (and re-notify) again?
- The ticket has **no assigned agent**: who does the Slack notification go to?
- The ticket gets **resolved or closed** before the 60-minute mark: does anything fire?
- **Multiple tickets** breach the SLA at the same moment: one Slack message per ticket, or a merged digest?
- The ticket is sitting in **`"Waiting on Customer"`** status, where the SLA timer is paused: does that paused time still count toward the 60 minutes?

Those five are exactly what you'd hand to an AI tool as the edge cases to cover, alongside the requirement text itself.

## AI/QE workflow

The shape of this module's workflow, and the one Module 10 later narrates stage by stage across the whole course:

1. **Write the prompt.** Paste the requirement (sanitized; see Security considerations below), state the domain constraints AI can't infer on its own (field names, status values, what "recent agent activity" means), and explicitly ask for edge cases, not just the happy path.
2. **Generate the batch.** AI returns a list of scenarios: a title, a short setup description, and an expected outcome each.
3. **Review against the checklist.** Walk every scenario through the five weak-test patterns above. Some pass as-is. Some need a rewrite. Some get thrown out as duplicates.
4. **Fix or reject.** For each weak scenario, either sharpen it (name the field, name the value, split the duplicate) or drop it if it's not adding coverage.
5. **Approve the set.** What's left is the scenario set that ships to automation. This is a deliberate, named checkpoint: nothing downstream should touch a scenario AI produced but a QE never reviewed.

AI owns step 2. You own steps 3 through 5. That split is the whole point of this module.

## Vespera Systems scenario

Here's a realistic first-pass batch, as AI actually returned it for the SLA Auto-Escalation requirement above. Six scenarios, a mix of strong and weak. Read each one before checking the verdict underneath.

| # | Scenario | Setup | Expected outcome |
|---|----------|-------|-------------------|
| 1 | Ticket breaches SLA and escalates | Ticket `status: "Open"`, no agent activity, SLA countdown reaches 60 minutes | Ticket updates and the agent is notified |
| 2 | Open ticket reaches SLA threshold | A ticket with 60 minutes left on its SLA and no recent activity | The system escalates the ticket |
| 3 | Ticket priority changes on SLA breach | Ticket `status: "Open"`, no agent activity, SLA countdown reaches 60 minutes | `priority` is `"Urgent"`, `escalated_by_system` is `true`, and a Slack message is sent to the assigned agent's team channel |
| 4 | Already-urgent ticket at SLA threshold | Ticket already has `priority: "Urgent"`, SLA countdown reaches 60 minutes | Nothing changes: `priority` stays `"Urgent"`, `escalated_by_system` is not re-set, and no new Slack message is sent |
| 5 | Resolved ticket doesn't escalate | Ticket resolved before the SLA countdown reaches 60 minutes | The resolved ticket doesn't get escalated |
| 6 | Ticket in "Waiting on Customer" near SLA threshold | Ticket sits in `status: "Waiting on Customer"` for 45 of its last 60 minutes, then returns to `"Open"` | The paused 45 minutes don't count toward the 60-minute mark: escalation timing reflects only the time spent `"Open"` |

Now for the review pass, the checklist applied to each row:

- **#1: weak assertion.** "Ticket updates and the agent is notified" doesn't say which field changes, to what value, or which agent gets which message. It's checking that *something* happened, not that the *right* thing happened.
- **#2: duplicate of #1.** Same setup, same vague outcome, different wording. It adds no coverage; drop it rather than "fixing" it twice.
- **#3: strong.** Names the exact fields (`priority`, `escalated_by_system`) and the exact target (Slack to the assigned agent's team channel). This is the fixed version of #1/#2: keep this one, discard the other two.
- **#4: strong.** A real edge case (already-`Urgent`, no double-escalation) with a specific, falsifiable assertion. Keep as-is.
- **#5: weak assertion, and happy-path bias in the batch as a whole.** "Doesn't get escalated" doesn't say what to check instead: is `escalated_by_system` still `false`? Was no Slack call made at all? Also worth noticing: five of six scenarios in this batch are variations on "escalation fires correctly." Only #4, #5, and #6 touch a not-escalating path, and #5 is the vaguest of the three.
- **#6: strong, but incomplete as a batch.** Covers the paused-timer edge case with a specific, checkable outcome. Good scenario, but the batch as delivered is still missing two edge cases the requirement implies: no assigned agent (who gets notified?) and multiple simultaneous breaches (one Slack message each, not a digest). That's a missing-edge-case gap in the batch, not a flaw in any single scenario.

Fixing #1/#2 into one scenario, dropping the duplicate, sharpening #5, and adding the two missing edge cases gives the approved set this module hands to Module 3:

1. **SLA breach on an eligible ticket escalates correctly**: `status: "Open"`, no recent agent activity, SLA countdown reaches 60 minutes → `priority` becomes `"Urgent"`, `escalated_by_system` becomes `true`, one Slack message sent to the assigned agent's team channel.
2. **Already-Urgent ticket does not double-escalate**: ticket already `priority: "Urgent"` at the 60-minute mark → no field changes, no new Slack message.
3. **Ticket with no assigned agent escalates to the team lead**: eligible ticket with no assigned agent at the 60-minute mark → escalation still fires (`priority`, `escalated_by_system` update), but the Slack notification goes to the team lead instead of an assigned agent.
4. **Resolved ticket does not escalate**: ticket resolved/closed before the 60-minute mark → `escalated_by_system` remains `false`, no Slack message sent, `priority` unchanged.
5. **Multiple simultaneous breaches notify individually**: two or more eligible tickets cross the 60-minute mark at the same time → each ticket escalates independently and one Slack message is sent per ticket, not a single merged digest.
6. **Paused SLA timer during "Waiting on Customer" doesn't count toward the 60 minutes**: ticket spends part of its lifetime in `"Waiting on Customer"` → only time spent in `"Open"` counts toward the 60-minute threshold; escalation timing reflects that.

Six scenarios, each with a specific setup and a specific, checkable outcome, no duplicates, and every edge case from the requirement's careful read represented. This is the approved scenario set Module 3 automates.

For each one, decide: is it strong as written, or does it fall into one (or more) of the five weak-test patterns? If it's weak, rewrite it so it would survive review.

| # | Scenario | Setup | Expected outcome |
|---|----------|-------|-------------------|
| A | Escalation fires at the SLA threshold | Open ticket, no activity, 60 minutes left | `priority` is `"Urgent"`, `escalated_by_system` is `true`, one Slack message sent to the assigned agent's team channel |

| D | Escalated ticket keeps its urgent status | Ticket already escalated once (`escalated_by_system: true`, `priority: "Urgent"`), SLA countdown crosses 60 minutes again in a later cycle | `priority` remains `"Urgent"`, `escalated_by_system` stays `true`, and no additional Slack message is sent |

As a hint: notice that B and C are close enough to be a duplicate pair even though their wording differs more than #1/#2 did in the worked example, and that E is gesturing at a real edge case without specifying what "handling" actually means.

## Failure modes

- **Treating the first AI batch as the final batch.** The single biggest failure mode isn't any one weak scenario: it's shipping the batch straight to automation without the review pass. A vague assertion becomes a vague automated test, and a vague automated test that "passes" tells you nothing.
- **Fixing wording instead of substance.** Rewriting "the ticket updates" as "the ticket updates correctly" isn't a fix: it's the same weak assertion with a reassuring adjective bolted on. A real fix names the field and the value.
- **Missing the edge cases the requirement only implies.** AI batches tend to cover what the requirement states directly and skip what a careful domain read surfaces, like the paused-timer or no-assigned-agent cases here. That gap doesn't show up as an error; it shows up as a gap, which is why the review step has to actively hunt for what's *not* there, not just grade what is.
- **Over-trusting scenario count as a proxy for coverage.** Six scenarios sounds thorough. Two of the six the worked example started with were duplicates. Count is not coverage; distinct, specific behavior is.

## Security considerations

Never paste a real, proprietary Vespera requirement (or your own company's) into a third-party AI tool as-is. Requirement text can carry real product details, internal field names, business logic, or roadmap information that isn't yours to send to another company's servers, and depending on the tool, that input may be logged, retained, or used to improve someone else's model. Once it's left your organization's boundary, you generally can't get it back.

The practical fix is what this module already modeled: sanitize before you prompt. Keep the domain fictional or genericized (as this course does with Vespera), strip or replace real customer/company/internal-system names, and keep field names and business rules only as specific as the test-generation task actually needs, not a copy-paste of the original ticket. If a requirement is too sensitive to sanitize without losing what makes it testable, that's a sign the tool needs to run somewhere your organization controls (a self-hosted or enterprise-contracted model), not that sanitization should be skipped.

## Guardrails

This module is entirely informal review: a QE reading a batch and applying the checklist by eye, not a checked-in rule anything enforces automatically. That's a deliberate step in the course's progression: Module 5 takes this exact checklist and turns it into an automatable quality gate (plus a lint rule for a separate, sharper problem: hardcoded secrets in AI-generated code). Nothing here is wrong for being manual yet; it's just not automated *yet*.

## Production considerations

A scenario batch is only as good as the reviewer's domain knowledge: AI can't know that Vespera's SLA timer pauses during `"Waiting on Customer"` unless a human either tells it or catches the gap afterward, which is exactly what happened above. In a real team, that argues for two things: keep the sanitized requirement and the edge-case list AI was given somewhere versioned, so the next person (or the next module) isn't reconstructing your reasoning from scratch, and treat the approved scenario set itself as a deliverable (reviewed, timestamped, and traceable back to the requirement it came from), not a scratch artifact that disappears once automation exists.
