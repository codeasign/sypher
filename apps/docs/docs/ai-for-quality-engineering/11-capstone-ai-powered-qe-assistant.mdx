Module 10 sketched seven components and a thin orchestrator, in interfaces only. This page fills every one of those interfaces in with real, working, simplified code, and proves, not just claims, the two things that separate this from a demo: the components are genuinely separate (you can point to the exact file-and-class boundary between "AI generated this" and "code judged it"), and they're genuinely reusable (the exact same instances run against a second, different Vespera requirement at the end, with zero code changes).

## Page purpose

To build a working AI-Powered QE Assistant as seven independently testable components wired by an orchestrator with no logic of its own, implementing every `Protocol` Module 10 sketched, and to run it end to end against Module 2's SLA Auto-Escalation requirement as this course's most fully worked example. This page carries a hard requirement, not a style preference: if what follows read as one script chaining sequential AI calls with no real boundaries between stages, it would be a failure of this page, not an acceptable simplification. Everything below is built so that a `TestReviewer` bug and a `TestGenerator` bug are two different pieces of code with two different tests, full stop.

## Learning objectives

- Implement all seven pipeline components from Module 10's interface sketch as real Python classes, each satisfying a `Protocol` and each independently unit-testable.
- Demonstrate genuine provider abstraction: swap `LLMProvider` implementations via constructor injection, not a global or a string flag.
- Prove `TestReviewer` and `GuardrailChecker` are separate code paths: one deterministic checklist over scenario text, one deterministic static analysis over generated code, neither of which imports an `LLMProvider` at all.
- Run the assembled pipeline end to end against the SLA Auto-Escalation requirement and read the resulting report.
- Re-run the exact same component instances against a second, unrelated requirement and confirm nothing about the components themselves had to change.

## Concepts

**Two components in this pipeline must never import `LLMProvider`, and that's enforceable, not just documented.** `TestReviewer` and `GuardrailChecker` are the review/guardrail half of "AI generates, QE validates"; if either one could call a model, a bug in judgment and a bug in generation would become indistinguishable again, which is exactly the failure Module 10 spent a whole page naming. Below, both are plain Python classes with no model dependency anywhere in their code, and a short test at the end of this page asserts that structurally, not just by eyeballing the source.

**"Simplified" describes scope, not architecture.** The real Vespera system would have a fuller weak-test-pattern checker, a fuller lint ruleset, and a real Playwright process instead of a recorded one. None of that simplification touches the boundaries between components; a production version of this pipeline would still be these same seven pieces, just with more thorough logic inside each one. Simplifying a component's internals is fine; simplifying away the boundary between components is the one thing this page isn't allowed to do.

**Provider abstraction is demonstrated, not asserted.** `TestGenerator` and `AutomationGenerator` both take an `LLMProvider` through their constructor. The worked example below runs both against a `RecordedProvider` (deterministic, no API calls, no cost) with scripted responses standing in for what a real model would return; swapping in `AnthropicProvider` from Module 6 needs no change to either component's code, only a different object passed to `__init__`.

## Practical example

The dataclasses every component passes between stages, plain data, no behavior:

```python
from dataclasses import dataclass
from typing import Protocol


@dataclass
class TestScenario:
    title: str
    setup: str
    expected_outcome: str


@dataclass
class ReviewResult:
    approved: list[TestScenario]
    rejected: list[tuple[TestScenario, str]]
    notes: list[str]


@dataclass
class GuardrailResult:
    passed: bool
    failed_criteria: list[str]


@dataclass
class ExecutionResult:
    scenario_title: str
    passed: bool
    run_history: list[bool]
    error_message: str | None = None


@dataclass
class AnalysisResult:
    scenario_title: str
    verdict: str  # "passed" | "stale_test" | "real_bug"
    confidence: float
    reasoning: str


@dataclass
class Report:
    requirement: str
    approved_scenario_count: int
    rejected_scenario_count: int
    guardrail_passed: bool
    findings: list[AnalysisResult]
    as_markdown: str
```

**`TestGenerator`: AI-driven, the only component allowed to invent scenario content:**

```python
import json
from ticket_summarizer import LLMProvider  # Module 6's abstraction, reused unchanged


GENERATOR_SYSTEM_PROMPT = """\
You are a QE test-scenario generator. Given a product requirement, return \
a JSON array of test scenarios. Each item has exactly three fields: \
"title", "setup", "expected_outcome". Cover the happy path and plausible \
edge cases implied by the requirement. Respond with JSON only.
"""


class AnthropicTestGenerator:
    def __init__(self, provider: LLMProvider) -> None:
        self._provider = provider

    def generate(self, requirement: str) -> list[TestScenario]:
        raw = self._provider.complete(GENERATOR_SYSTEM_PROMPT, requirement)
        return [TestScenario(**item) for item in json.loads(raw)]
```

**`TestReviewer`: deterministic, Module 2's checklist, no `LLMProvider` import anywhere in this class:**

```python
class ChecklistTestReviewer:
    """Applies Module 2's weak-test-pattern checklist. Simplified —
    real language understanding would catch more than these heuristics
    do — but the simplification is in the heuristics' sophistication,
    never in whether this class calls a model. It doesn't, and can't."""

    VAGUE_MARKERS = ("works", "updates", "behaves as expected", "looks correct", "handled correctly")

    def __init__(self, required_edge_cases: list[str]) -> None:
        self._required_edge_cases = required_edge_cases

    def review(self, scenarios: list[TestScenario]) -> ReviewResult:
        approved: list[TestScenario] = []
        rejected: list[tuple[TestScenario, str]] = []
        seen_setups: set[str] = set()

        for scenario in scenarios:
            outcome = scenario.expected_outcome.lower()
            names_something_specific = any(ch.isdigit() or ch in "\"'" for ch in scenario.expected_outcome)

            if any(marker in outcome for marker in self.VAGUE_MARKERS) and not names_something_specific:
                rejected.append((scenario, "weak assertion — outcome doesn't name a specific field or value"))
                continue

            normalized_setup = " ".join(scenario.setup.lower().split())
            if normalized_setup in seen_setups:
                rejected.append((scenario, "duplicate — same setup as an already-approved scenario"))
                continue

            seen_setups.add(normalized_setup)
            approved.append(scenario)

        covered_text = " ".join(f"{s.setup} {s.expected_outcome}".lower() for s in approved)
        notes = [
            f"missing edge case, not covered by any approved scenario: {case}"
            for case in self._required_edge_cases
            if case.lower() not in covered_text
        ]

        return ReviewResult(approved=approved, rejected=rejected, notes=notes)
```

**`GuardrailChecker`: deterministic static analysis, Module 5's checklist, no `LLMProvider` import here either:**

```python
import re

SECRET_PATTERNS = [
    re.compile(r"""['"`]sk-[A-Za-z0-9]{16,}['"`]"""),
    re.compile(r"""Authorization\s*[:=]\s*['"`]Bearer\s+[A-Za-z0-9_\-.]{10,}['"`]"""),
]


class LintGuardrailChecker:
    def check(self, automation_code: str) -> GuardrailResult:
        failed: list[str] = []

        if any(pattern.search(automation_code) for pattern in SECRET_PATTERNS):
            failed.append("hardcoded secret detected")
        if "waitForTimeout" in automation_code:
            failed.append("arbitrary sleep (waitForTimeout) present")
        if re.search(r"""\.locator\(['"]\.css-""", automation_code):
            failed.append("brittle auto-generated CSS class selector")
        if "data-testid" not in automation_code and "getByTestId" not in automation_code:
            failed.append("no data-testid-based selector found")
        if "expect(" not in automation_code:
            failed.append("no assertions found")

        return GuardrailResult(passed=len(failed) == 0, failed_criteria=failed)
```

**`AutomationGenerator`: AI-driven, has no knowledge of `GuardrailChecker`'s rules:**

```python
AUTOMATION_SYSTEM_PROMPT = """\
You are a Playwright TypeScript test generator. Given approved QE \
scenarios, write one @playwright/test file that automates all of them. \
Use data-testid locators and Playwright's built-in retrying assertions \
(toHaveText, expect.poll) — never waitForTimeout. Never hardcode a \
secret or credential. Respond with TypeScript source only.
"""


class AnthropicAutomationGenerator:
    def __init__(self, provider: LLMProvider) -> None:
        self._provider = provider

    def generate(self, scenarios: list[TestScenario]) -> str:
        scenario_text = "\n".join(f"- {s.title}: {s.setup} -> {s.expected_outcome}" for s in scenarios)
        return self._provider.complete(AUTOMATION_SYSTEM_PROMPT, scenario_text)
```

**`TestExecutor`: deterministic, real implementation shells out to Playwright; a recorded double stands in for this page's worked walkthrough:**

```python
class PlaywrightTestExecutor:
    """Real implementation — writes automation_code to disk and runs it
    through the actual Playwright test runner. Not used in this page's
    worked example (no live browser in a documentation build), but this
    is what a production wiring of TestExecutor looks like."""

    def __init__(self, project_dir: str) -> None:
        self._project_dir = project_dir

    def execute(self, automation_code: str) -> list[ExecutionResult]:
        import subprocess
        import pathlib

        spec_path = pathlib.Path(self._project_dir) / "tests" / "generated.spec.ts"
        spec_path.write_text(automation_code)

        proc = subprocess.run(
            ["npx", "playwright", "test", str(spec_path), "--reporter=json"],
            cwd=self._project_dir, capture_output=True, text=True,
        )
        report = json.loads(proc.stdout or "{}")
        return [
            ExecutionResult(spec["title"], spec["ok"], [spec["ok"]], None if spec["ok"] else spec.get("error"))
            for spec in report.get("specs", [])
        ]


class RecordedExecutor:
    """Test double — returns a scripted list of ExecutionResults instead
    of running a real browser. Used below for the worked walkthrough and
    for testing every component upstream of TestExecutor in isolation."""

    def __init__(self, results: list[ExecutionResult]) -> None:
        self._results = results

    def execute(self, automation_code: str) -> list[ExecutionResult]:
        return self._results
```

**`FailureAnalyzer`: deterministic, Module 4's diagnostic heuristic formalized:**

```python
class HeuristicFailureAnalyzer:
    """Rule-based rather than a live model call in this simplified
    version — Module 10 described this stage as 'AI-assisted,' which
    describes the *kind* of judgment (the same reasoning Module 4 walked
    through with AI's help), not a requirement that every implementation
    literally calls a model. Confidence is deliberately kept below 1.0
    for anything that isn't a clean pass — a QE overriding this verdict
    is the expected path, not an edge case."""

    def analyze(self, results: list[ExecutionResult]) -> list[AnalysisResult]:
        findings = []
        for result in results:
            if result.passed and all(result.run_history):
                findings.append(AnalysisResult(result.scenario_title, "passed", 1.0, "consistently green"))
                continue

            intermittent = len(set(result.run_history)) > 1
            if intermittent:
                findings.append(AnalysisResult(
                    result.scenario_title, "real_bug", 0.7,
                    "Intermittent across runs — Module 4 showed this pattern usually means a live, "
                    "timing-dependent bug, not test flakiness. A QE must trace the actual mechanism "
                    "before this verdict is trusted, the same as the SLA-cron/reply-webhook race.",
                ))
            else:
                findings.append(AnalysisResult(
                    result.scenario_title, "stale_test", 0.6,
                    "Consistently failing, not intermittent — check for a changed selector or renamed "
                    "component before assuming this is a product bug.",
                ))
        return findings
```

**`QEReportBuilder`: deterministic, adds no judgment of its own:**

```python
class MarkdownReportBuilder:
    def build(self, requirement: str, review: ReviewResult, guardrails: GuardrailResult,
              analysis: list[AnalysisResult]) -> Report:
        lines = [
            f"# QE Report — {requirement.splitlines()[0][:70]}",
            "",
            f"- Approved scenarios: {len(review.approved)}",
            f"- Rejected scenarios: {len(review.rejected)}",
            f"- Guardrail check: {'PASSED' if guardrails.passed else 'FAILED — ' + ', '.join(guardrails.failed_criteria)}",
            "",
            "## Findings",
        ]
        for finding in analysis:
            lines.append(f"- **{finding.scenario_title}** — {finding.verdict} (confidence {finding.confidence}): {finding.reasoning}")

        markdown = "\n".join(lines)
        return Report(
            requirement=requirement,
            approved_scenario_count=len(review.approved),
            rejected_scenario_count=len(review.rejected),
            guardrail_passed=guardrails.passed,
            findings=analysis,
            as_markdown=markdown,
        )
```

**The orchestrator: the whole point of this page. Read it and check: is there a single line here that decides whether a scenario or a fix is correct?**

```python
def run_qe_pipeline(
    requirement: str,
    generator: "TestGenerator",
    reviewer: "TestReviewer",
    automation_generator: "AutomationGenerator",
    guardrail_checker: "GuardrailChecker",
    executor: "TestExecutor",
    analyzer: "FailureAnalyzer",
    report_builder: "QEReportBuilder",
) -> Report:
    scenarios = generator.generate(requirement)
    review = reviewer.review(scenarios)

    automation_code = automation_generator.generate(review.approved)
    guardrails = guardrail_checker.check(automation_code)

    execution_results = executor.execute(automation_code) if guardrails.passed else []
    analysis = analyzer.analyze(execution_results) if execution_results else []

    return report_builder.build(requirement, review, guardrails, analysis)
```

There's exactly one conditional in this function, twice: "don't execute code the guardrail already rejected" and "don't analyze results that don't exist." Both are plumbing, deciding *whether to call the next stage at all*, not judgment about whether a scenario, a fix, or a piece of code is correct. Every actual verdict in this pipeline (which scenarios survive review, whether the code passes the gate, whether a failure is stale or real) is produced inside a component, never inside this function. That's the property this whole page had to prove, not just claim.

## AI/QE workflow

1. `AnthropicTestGenerator` drafts scenarios from the requirement: AI, unreviewed.
2. `ChecklistTestReviewer` approves, fixes-by-rejecting, or drops each one: deterministic, no model call.
3. `AnthropicAutomationGenerator` turns the approved set into Playwright TypeScript: AI, unreviewed.
4. `LintGuardrailChecker` statically analyzes that code: deterministic, no model call.
5. `TestExecutor` runs it (or doesn't, if guardrails failed): deterministic, no judgment.
6. `HeuristicFailureAnalyzer` classifies any failures: deterministic, confidence-scored, built for a QE to override.
7. `MarkdownReportBuilder` assembles everything above into one artifact: deterministic, no new judgment.
8. A QE reads the report and makes the calls the pipeline flagged as needing one: the step no component in this pipeline is allowed to replace.

## Code requirements

Every component above satisfies exactly one `Protocol` from Module 10 and takes its dependencies through `__init__`, never a module-level global, never an environment-variable branch inside a method body. `LLMProvider` implementations (`AnthropicProvider`, `RecordedProvider`) are Module 6's, imported unchanged. No API key is ever hardcoded: `AnthropicProvider` reads `ANTHROPIC_API_KEY` from the environment exactly as it has since Module 6. No example requirement, ticket, or scenario in this page is real Vespera or customer data.

## Vespera Systems scenario

**Running the pipeline against Module 2's SLA Auto-Escalation requirement, this course's most fully worked example, start to finish:**

```python
sla_requirement = (
    'SLA Auto-Escalation: when a ticket\'s SLA countdown reaches 60 minutes remaining '
    'and the ticket is still status "Open" with no recent agent activity, the system '
    'bumps priority to "Urgent", sets escalated_by_system to true, and notifies the '
    'assigned agent\'s team channel via Slack.'
)

# A RecordedProvider standing in for what a real model would return —
# deterministic, no API calls, matching Module 6's first-pass batch and
# Module 3's automation almost exactly, on purpose.
generator_provider = RecordedProvider(json.dumps([
    {"title": "SLA breach on an eligible ticket escalates correctly",
     "setup": "status Open, no recent agent activity, SLA countdown reaches 60 minutes",
     "expected_outcome": 'priority becomes "Urgent", escalated_by_system becomes true, one Slack message sent'},
    {"title": "Already-Urgent ticket does not double-escalate",
     "setup": "ticket already priority Urgent at the 60-minute mark",
     "expected_outcome": "no field changes, no new Slack message"},
    {"title": "duplicate of the first scenario",
     "setup": "status Open, no recent agent activity, SLA countdown reaches 60 minutes",
     "expected_outcome": "the ticket updates and the agent is notified"},
]))

automation_provider = RecordedProvider(
    "import { test, expect } from '../fixtures';\n"
    "test('SLA breach escalates', async ({ seedTicket, page }) => {\n"
    "  const ticket = await seedTicket({ status: 'Open', minutesToBreach: 61 });\n"
    "  await page.goto(`/dashboard/tickets/${ticket.id}`);\n"
    "  await expect(page.getByTestId('ticket-priority-badge')).toHaveText('Urgent');\n"
    "});\n"
)

recorded_execution = [
    ExecutionResult("SLA breach on an eligible ticket escalates correctly", True, [True, True, True]),
]

report = run_qe_pipeline(
    requirement=sla_requirement,
    generator=AnthropicTestGenerator(generator_provider),
    reviewer=ChecklistTestReviewer(required_edge_cases=[
        "no assigned agent", "resolved before breach", "multiple simultaneous breaches",
        "waiting on customer", "already urgent",
    ]),
    automation_generator=AnthropicAutomationGenerator(automation_provider),
    guardrail_checker=LintGuardrailChecker(),
    executor=RecordedExecutor(recorded_execution),
    analyzer=HeuristicFailureAnalyzer(),
    report_builder=MarkdownReportBuilder(),
)

print(report.as_markdown)
```

```text title="report.as_markdown"
# QE Report — SLA Auto-Escalation: when a ticket's SLA countdown reaches 60 minutes remaini

- Approved scenarios: 2
- Rejected scenarios: 1
- Guardrail check: PASSED

## Findings
- **SLA breach on an eligible ticket escalates correctly** — passed (confidence 1.0): consistently green
```

`ChecklistTestReviewer` rejected the third scenario as a weak assertion; its outcome text ("the ticket updates and the agent is notified") hits the vague-marker check before the reviewer ever gets to compare setups, so it never even reaches the duplicate-detection step that would have flagged it against the first scenario's identical setup. That's a real limitation of a heuristic this simple, not a mistake in the worked example: the same third scenario Module 2 caught by hand for being a duplicate gets caught here too, just for a different, earlier-triggering reason. Its `notes` field (not shown in the markdown above, but present on `review.notes`) flags every one of the five required edge cases the two-scenario batch above doesn't actually cover, since this scripted `RecordedProvider` response is deliberately thin. That gap is real and correctly detected: a production run would loop back to `TestGenerator` with that feedback, which this simplified pipeline doesn't automate, on purpose. Deciding *whether* to regenerate is exactly the kind of judgment call this course has argued belongs to a QE, not to an autonomous loop.

## Failure modes

- **A `TestReviewer` or `GuardrailChecker` that imports `LLMProvider` "just for one thing."** The instant either class calls a model, this page's central claim, that review and guardrail checking are structurally incapable of being confused with generation, stops being true, no matter how small the model call looks.
- **An orchestrator that grows a third `if`.** The two conditionals in `run_qe_pipeline` above are load-bearing and deliberately minimal; a third one that inspects *content* rather than *whether a prior stage produced output at all* is where the anti-pattern creeps back in, one line at a time.
- **Treating `HeuristicFailureAnalyzer`'s verdict as final.** Confidence scores below `1.0` exist specifically so a QE knows which findings need a second look; code that auto-files a bug or auto-merges a fix based on this component's output alone has quietly removed the human step the whole pipeline was built to protect.
- **Skipping the reusability exercise.** A pipeline that "works" only demonstrated once, against the requirement it was designed around, hasn't actually proven the components are reusable; that's what the second requirement in the exercise is for, and skipping it means taking this page's central claim on faith instead of verifying it yourself.

## Security considerations

`AnthropicProvider`'s `ANTHROPIC_API_KEY` is read from the environment, never hardcoded, exactly as established since Module 6; nothing about wiring seven components together changes that rule. Every requirement, scenario, and piece of ticket-shaped text used as example data on this page is fabricated, the same discipline this course has held since Module 2's note about not pasting proprietary requirements into a third-party tool. `PlaywrightTestExecutor`'s real implementation shells out to a subprocess and writes generated code to disk; treat `AutomationGenerator`'s output the same way Module 8 taught you to treat any AI output reaching something that can act: never execute it against a production environment, and keep the executor scoped to a disposable test project directory, never a path that could touch anything else.

## Guardrails

`LintGuardrailChecker` is the guardrail component in this pipeline, but the orchestrator's gate, `executor.execute(...)` only runs `if guardrails.passed`, is itself a guardrail decision, expressed as one line of plumbing rather than logic living inside any component. That's a deliberate design choice worth naming: the *decision rule* ("don't execute ungated code") is simple enough to live in the orchestrator without becoming the anti-pattern this page warns against, precisely because it doesn't inspect *what* the code does, only whether an earlier, real component already said no.

## Production considerations

A real deployment of this pipeline would swap exactly three of the seven components for their full implementations: `PlaywrightTestExecutor` instead of `RecordedExecutor`, a fuller NLP-based `TestReviewer`, and a fuller lint ruleset in `GuardrailChecker`, while `TestGenerator`, `AutomationGenerator`, `HeuristicFailureAnalyzer`, and `MarkdownReportBuilder` could plausibly ship close to as-is. That short a list is itself evidence the component boundaries are drawn in the right places: swapping an implementation's internals didn't require touching anything else's. Cost and latency follow the same pattern established in Modules 6 through 9: cheap deterministic stages (review, guardrails, analysis, reporting) can run on every change; the two AI-driven stages are where a real deployment would think about caching, batching, or running on a schedule rather than per-commit.
