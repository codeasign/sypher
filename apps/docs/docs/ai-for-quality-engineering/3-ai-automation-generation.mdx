Module 2 ended with six approved scenarios for the SLA Auto-Escalation requirement — reviewed, specific, no duplicates, every edge case from the requirement's careful read represented. None of that is a test yet. A scenario says *what* should be true; automation is the thing that actually checks it, on a real browser, against a real (test) backend, on every pull request. That's a different job with a different set of ways to get it wrong, and this module is about learning to spot them before they merge.

## Page purpose

To turn Module 2's approved scenario set into real Playwright TypeScript automation, and to build the review habit that catches the specific ways AI-generated automation tends to fail: tests that pass or fail depending on machine speed, selectors that break on the next unrelated style change, code built on a wrong mental model of how the system actually behaves, and tests that only work because of what some other test happened to leave behind. By the end, you'll have working, QE-corrected automation for one full scenario, and the checklist to apply to the rest.

## Learning objectives

- Turn an approved scenario into a Playwright TypeScript test against a real UI, using this site's established fixture and locator conventions.
- Recognize the four automation-specific weak patterns AI tends to produce: non-determinism, brittle selectors, incorrect assumptions, and poor isolation.
- Correct each of the four patterns with the right Playwright mechanism — retrying assertions instead of sleeps, `data-testid` instead of implementation-detail selectors, a wait strategy that matches how the system actually works, and self-contained setup and teardown.
- Review a fresh piece of AI-generated automation against that same checklist and fix what it gets wrong.

## Concepts

Scenario generation (Module 2) is about breadth and coverage — did AI think of the right cases. Automation generation is about correctness under real execution conditions — does the check actually run reliably, against the actual DOM, without depending on luck. AI is decent at producing plausible-looking boilerplate fast: a `test()` block, some navigation, an assertion that reads correctly at a glance. What it's unreliable at is everything that requires actually knowing your system — your real selector strategy, whether an operation happens instantly or gets processed later, and how your test data is supposed to come and go. When AI doesn't know those things, it guesses, and the guesses fall into four recognizable patterns.

**Non-determinism** — the test's outcome depends on timing that isn't actually pinned down: a fixed `page.waitForTimeout(5000)` standing in for "wait until the thing I care about is true." On a slow CI runner it's not long enough and the test flakes; on a fast one it wastes time every single run for no benefit. Playwright's own locators and assertions already retry until a condition holds or a real timeout elapses — a hardcoded sleep throws that away and replaces it with a guess.

**Brittle selectors** — coupling the test to something that changes for reasons that have nothing to do with whether the feature works: an auto-generated CSS class from a styling library, a DOM position (`nth-child`, an XPath index), anything that's an implementation detail rather than a deliberate test hook. `data-testid` exists specifically so tests have something stable to grab onto that survives a restyle.

**Incorrect assumptions** — the code is built on a wrong model of how the system behaves. The classic version here: treating an operation as synchronous (finishes instantly, as part of the same request) when it's actually processed by a background job some seconds later. You can't fix this with a better wait mechanism alone — a `toHaveText` that fires the instant the page loads still fails, because the job genuinely hasn't run yet. The fix has to match the real system, not just retry harder.

**Poor isolation** — a test that depends on data existing already, or on running in a particular order, instead of creating and cleaning up its own state. It "works" on your machine because your test database happens to be in the shape the test assumes. It breaks the moment someone runs the suite in parallel, reruns a single spec, or the seed data changes.

These four show up together constantly, because they usually come from the same root cause: AI generating a test against an *assumed* system instead of the real one. The fix for all four is the same shape — replace the assumption with something that's actually true of Vespera's system, and verifiable.

## Practical example

Here's the DOM shape Vespera's ticket dashboard actually renders for a ticket's priority. This is the real selector surface any automation for this feature has to work against:

```html
<div class="ticket-detail">
  <span data-testid="ticket-priority-badge">Normal</span>
</div>
```

`data-testid="ticket-priority-badge"` is the one thing on this element that's there *on purpose*, for tests. Everything else about that `<span>` — its CSS class, its position in the DOM — can change the next time someone touches the stylesheet, and none of that should be able to break a test that only cares about one thing: what does the badge say.

The scenario this module builds in full is the first one Module 2 approved:

> **SLA breach on an eligible ticket escalates correctly** — `status: "Open"`, no recent agent activity, SLA countdown reaches 60 minutes → `priority` becomes `"Urgent"`, `escalated_by_system` becomes `true`, one Slack message sent to the assigned agent's team channel.

That's the scenario AI's first automation draft below gets wrong in four separate ways, and the one the QE-corrected version gets right.

## AI/QE workflow

1. **Hand AI the approved scenario, not a vague description.** The scenario's setup and expected outcome from Module 2 — status, timing, exact field values — is the spec. AI automates what you give it; a vague input produces a vague test regardless of how good the tool is.
2. **AI generates a draft test.** Real Playwright TypeScript, not pseudocode — but a first draft, the same way Module 2's first scenario batch was a first draft.
3. **Review the draft against the four-pattern checklist.** Non-determinism, brittle selectors, incorrect assumptions, poor isolation — walk the code looking for each one specifically, the same way Module 2 walked scenarios against its five weak-test patterns.
4. **Fix each issue with the right mechanism**, not a workaround that happens to make the test pass. A longer `waitForTimeout` is not a fix for non-determinism; it's the same bug with a bigger number.
5. **Land on the QE-corrected version.** This is what actually merges — and, as Module 5 will show, what a formal quality gate checks automatically going forward.

## Code requirements

Vespera's automation suite is Playwright TypeScript using `@playwright/test` — the same framework and house style as this site's dedicated Playwright course: `test.extend()` for fixture composition, `data-testid` locators, real fixture setup and teardown rather than inline boilerplate repeated per spec.

A few rules this module holds to without exception, because they're exactly what turns into Module 5's automated checks:

- Selectors are `data-testid` (or role/label) — never a styling-library-generated class, never a DOM position.
- Waiting uses Playwright's built-in retrying locators and assertions (`toHaveText`, `expect.poll`) — never `waitForTimeout`.
- Test data is created and torn down by the test itself, through a test-only API surface (`/api/test/seed-ticket` to create, a matching delete to clean up) — never assumed to already exist.
- The test-only seed and cleanup endpoints only exist in test/staging environments — see Security considerations below.

## Vespera Systems scenario

Here's what AI actually produced for the first approved scenario, before any review:

```typescript title="tests/sla-escalation.spec.ts (AI's first draft — do not use)"
import { test, expect } from '@playwright/test';

test('SLA breach escalates ticket to Urgent', async ({ page }) => {
  // Ticket 1001 is the first ticket in a fresh test database, and
  // escalation runs synchronously as part of the SLA check, so the
  // badge should already say Urgent as soon as the page loads.
  await page.goto('/dashboard/tickets/1001');

  await page.waitForTimeout(5000);

  const badge = page.locator('.css-1x2y3z');
  await expect(badge).toContainText('Urgent');
});
```

It runs. It might even pass, some of the time, on some machines. That's exactly the problem — walking it against the four-pattern checklist:

- **Poor isolation.** Ticket `1001` is never seeded by this test; the comment openly admits it's assuming a specific ID happens to exist because the database happens to be fresh. Run this test twice, or run it after any other test has created a ticket, and the assumption breaks.
- **Incorrect assumption.** The comment says escalation "runs synchronously as part of the SLA check." It doesn't — Vespera processes SLA escalation with an asynchronous background job that runs some seconds after the 60-minute threshold is crossed, not as part of loading the ticket page. Any wait strategy built on "instant" is built on a false model of the system.
- **Non-determinism.** `page.waitForTimeout(5000)` is a guess at how long that background job takes, layered on top of the wrong assumption above. Five seconds might be plenty most of the time and not enough on a loaded CI runner — the test's outcome depends on machine speed, not on whether escalation actually happened.
- **Brittle selector.** `.css-1x2y3z` is a styling-library-generated class, not a test hook. It has no relationship to the feature working correctly and will change the next time someone touches the component's styles — completely unrelated to whether escalation logic still works.

The corrected version replaces all four with something backed by how Vespera's system actually behaves. First, a fixture that owns seeding and cleanup so no individual test has to repeat that boilerplate or forget the teardown:

```typescript title="fixtures.ts"
import { test as base, type APIRequestContext } from '@playwright/test';

type SeedTicketOptions = {
  status: 'Open' | 'Waiting on Customer' | 'Resolved';
  minutesToBreach: number;
  assignedAgent?: string | null;
  priority?: 'Normal' | 'Urgent';
};

type SeededTicket = {
  id: number;
  status: string;
  priority: string;
  escalated_by_system: boolean;
  assigned_agent: string | null;
};

type TestFixtures = {
  seedTicket: (options: SeedTicketOptions) => Promise<SeededTicket>;
};

export const test = base.extend<TestFixtures>({
  // Test-scoped: hands the test a function it can call one or more
  // times to seed tickets, and tracks every ticket it creates so they
  // can all be cleaned up afterward — regardless of how many the test
  // seeded, or whether the test passed or failed.
  seedTicket: async ({ request }, use) => {
    const createdIds: number[] = [];

    const seed = async (options: SeedTicketOptions): Promise<SeededTicket> => {
      const response = await request.post('/api/test/seed-ticket', { data: options });
      const ticket: SeededTicket = await response.json();
      createdIds.push(ticket.id);
      return ticket;
    };

    await use(seed);

    for (const id of createdIds) {
      await request.delete(`/api/test/tickets/${id}`);
    }
  },
});

export { expect } from '@playwright/test';
```

And the corrected spec, built on that fixture:

```typescript title="tests/sla-escalation.spec.ts"
import { test, expect } from '../fixtures';
import type { APIRequestContext } from '@playwright/test';

test('SLA breach on an eligible ticket escalates correctly', async ({ seedTicket, page, request }) => {
  const ticket = await seedTicket({
    status: 'Open',
    minutesToBreach: 61,
    assignedAgent: 'agent-priya', // fake test-fixture identifier, not a real Vespera user
  });

  await page.goto(`/dashboard/tickets/${ticket.id}`);

  // Escalation is processed by an async background job, not the page
  // load — this waits, with Playwright's built-in retry, for the badge
  // to actually say "Urgent" instead of assuming it already does.
  await expect(page.getByTestId('ticket-priority-badge')).toHaveText('Urgent');

  // The Slack call is fired by the backend job too, so it can lag
  // slightly behind the badge update — poll the capture endpoint
  // instead of assuming both land at the same moment.
  await expect
    .poll(async () => (await getSlackCallsForTicket(request, ticket.id)).length, {
      message: 'waiting for the escalation webhook to fire',
      timeout: 15_000,
    })
    .toBe(1);

  const [webhookCall] = await getSlackCallsForTicket(request, ticket.id);
  expect(webhookCall.channel).toBe('team-agent-priya');
  expect(webhookCall.text).toContain('escalated');
});

async function getSlackCallsForTicket(request: APIRequestContext, ticketId: number) {
  const response = await request.get(`/api/test/slack-webhook-calls?ticketId=${ticketId}`);
  return response.json();
}
```

Every one of the four issues is gone for a specific reason, not a general "looks cleaner" improvement: `seedTicket` creates and later deletes its own ticket, so the test's starting state doesn't depend on what any other test left behind; the wait strategy models the real asynchronous job instead of assuming instant completion; `expect(...).toHaveText(...)` and `expect.poll(...)` retry until the real condition holds instead of guessing a fixed delay; and `page.getByTestId('ticket-priority-badge')` targets the one thing on that element that exists specifically so tests can find it. This is the version that merges — and the exact code Module 5's quality gate evaluates.

## Exercise

Here's a fresh AI-generated draft, this time for a different scenario from Module 2's approved set: **"Ticket with no assigned agent escalates to the team lead."** It has its own planted issues — not the same four lines as the worked example above, but the same four categories of weak pattern. Find them, name which category each one falls into, and rewrite the test so it would survive review.

```typescript title="tests/sla-escalation-team-lead.spec.ts (AI-generated — exercise, do not treat as a working example)"
import { test, expect } from '@playwright/test';

test('unassigned ticket escalates and notifies the team lead', async ({ page, request }) => {
  await request.post('/api/test/seed-ticket', {
    data: { status: 'Open', minutesToBreach: 61, assignedAgent: null },
  });

  await page.goto('/dashboard/tickets');
  await page.getByText('Team Lead Queue').click();

  for (let attempt = 0; attempt < 3; attempt++) {
    await page.reload();
    await page.waitForTimeout(2000);
    const priorityText = await page.locator('//div[@class="ticket-row"][1]/span[3]').textContent();
    if (priorityText?.includes('Urgent')) break;
  }

  await expect(page.locator('//div[@class="ticket-row"][1]/span[3]')).toContainText('Urgent');
});
```

Work through it before checking the answer: what does the seed call's response get used for, what happens if two people run this suite at the same time, and what happens the day the team lead queue isn't sorted with the newest ticket first?

<details>
<summary>Worked answer</summary>

Three planted issues, same categories as the worked example, different code shapes:

- **Poor isolation.** The seed call's response is discarded — the test never captures the ticket's `id`, so it has no way to navigate straight to *its own* ticket or to delete it afterward. Instead it opens a list view and reads whatever happens to be in the first row. That "works" only by accident: if any other ticket is also `Urgent` and sorted above it, or if two copies of this test run in parallel, the test is checking the wrong ticket entirely — and nothing it created ever gets cleaned up.
- **Brittle selector.** `//div[@class="ticket-row"][1]/span[3]` is a positional XPath: "the first row, the third span." It has no connection to what that span actually means, and it breaks the moment a column gets reordered or an extra element gets added anywhere above it in the tree — for a completely unrelated reason. It's the same category of problem as `.css-1x2y3z` from the worked example, just coupled to DOM position instead of a generated class name.
- **Non-determinism.** The `for` loop with `page.reload()` and `waitForTimeout(2000)` three times is still a fixed-delay guess dressed up as a retry — it caps out at 6 seconds of guessing instead of one 5-second guess, and it still has no actual relationship to when the background job finishes. It's non-determinism wearing a different shape than a single sleep, not a different problem.

A corrected version, using the same `seedTicket` fixture from the worked example and navigating straight to the ticket it owns:

```typescript title="tests/sla-escalation-team-lead.spec.ts"
import { test, expect } from '../fixtures';
import type { APIRequestContext } from '@playwright/test';

test('unassigned ticket escalates and notifies the team lead', async ({ seedTicket, page, request }) => {
  const ticket = await seedTicket({
    status: 'Open',
    minutesToBreach: 61,
    assignedAgent: null,
  });

  await page.goto(`/dashboard/tickets/${ticket.id}`);

  await expect(page.getByTestId('ticket-priority-badge')).toHaveText('Urgent');

  await expect
    .poll(async () => (await getSlackCallsForTicket(request, ticket.id)).length, {
      message: 'waiting for the escalation webhook to fire',
      timeout: 15_000,
    })
    .toBe(1);

  const [webhookCall] = await getSlackCallsForTicket(request, ticket.id);
  expect(webhookCall.channel).toBe('team-lead');
});

async function getSlackCallsForTicket(request: APIRequestContext, ticketId: number) {
  const response = await request.get(`/api/test/slack-webhook-calls?ticketId=${ticketId}`);
  return response.json();
}
```

Same fixture, same `data-testid`, same retrying-assertion pattern as the worked example — because once the underlying pattern is fixed once, correctly, it's reusable across every scenario in the approved set, not just the one it was first built for.

## Failure modes

- **Treating a green run as proof.** A test built on a wrong assumption or a lucky sleep can pass plenty of times before it flakes — a single passing run after "fixing" the draft isn't the same as the test being correct, it might just mean this run happened to be fast enough.
- **Fixing the symptom instead of the pattern.** Swapping `.css-1x2y3z` for `nth-child(2)` because the first selector broke is still a brittle selector — it just moved. The fix is always "use the test hook," never "find a different implementation detail that happens to work today."
- **Sleep debt.** One unnecessary five-second wait looks harmless in isolation. Multiplied across a growing suite and every CI run, it's real, ongoing pipeline time spent waiting for nothing.
- **Debugging the wrong layer.** A test failing because of an incorrect timing assumption looks, at a glance, exactly like a test failing because of a real bug. Confusing the two wastes investigation time now and sets up Module 4's harder version of the same problem — telling a real regression apart from a test that was simply wrong about how the system works.

## Security considerations

The test-only seed and cleanup endpoints (`/api/test/seed-ticket`, the matching delete) must never be reachable outside test and staging environments — they let a caller create and delete tickets with no normal authorization flow, which is exactly the kind of capability that should not exist anywhere near production data. Gate them behind an environment check on the backend, not just by convention or because nobody's found it yet.

Never hardcode a real Slack webhook URL, API token, or any other credential in a spec file, even temporarily while debugging — Module 5 introduces a scanner that catches this automatically going forward, but until then it's a manual review requirement every time. And keep seeded fixture data obviously fake, the same discipline Module 2 applied to requirement text: `agent-priya` here is a fixture label, not a real Vespera user, the same way every example on this page stays fictional.

## Guardrails

Right now, this module's four-pattern checklist is something a QE applies by reading the diff — a review habit, not an enforced check. That's the same deliberate gap Module 2 left open: Module 5 takes this exact checklist and turns items 2 (no arbitrary sleeps), 3 (`data-testid` selectors), 4 (no hardcoded IDs), and 6 (isolation) into an automated quality gate, applied to this exact worked example. The "incorrect assumption" pattern stays a human judgment call even after that — a static scanner can tell you a wait exists, not whether it models the real system correctly.

## Production considerations

Isolation problems that never surface locally show up fast the moment CI runs specs in parallel — a test that "happens to work" because of execution order on one machine will collide with itself, or with another test, the instant two workers touch the same assumed ticket ID at once. Fixed sleeps compound the same way: a few unnecessary seconds per test, multiplied across a real suite running on every pull request, adds up to real infrastructure cost over time, not just an annoyance. Treat the test-only endpoints as an operational surface with an owner — someone has to keep them out of production builds as the app evolves, not just get them right once. And treat this automation itself as a production asset: Module 4 picks up here with a real DOM change that breaks this exact suite, which only matters because the suite is good enough to be worth maintaining in the first place.
