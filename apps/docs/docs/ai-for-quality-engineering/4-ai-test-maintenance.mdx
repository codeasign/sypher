Module 3 ended with a green, QE-corrected suite covering the SLA Auto-Escalation requirement: real fixtures, real `data-testid` locators, real retrying assertions against Vespera's actual asynchronous escalation job. Green doesn't mean finished. Apps change, and every one of those changes is a chance for a passing test to start failing, sometimes because the test was right and something broke, sometimes because the app moved on and the test didn't. This module is about the AI-assisted version of that diagnosis, and about the one way it can go quietly, dangerously wrong.

## Page purpose

To use AI to diagnose a failing test after a real Vespera app change, and to build the judgment to tell apart two failures that can look identical from the test runner's output: one where the test just needs updating, and one where the test is still right and something underneath it is actually broken. The second case is the one this module spends the most time on, because it's the one where an AI-proposed fix can make the problem *look* solved while leaving it fully live in production.

## Learning objectives

- Diagnose a failing Playwright test with AI by supplying real evidence, the new DOM, the application code that changed, and the actual failure log, instead of asking AI to guess from the test alone.
- Recognize when an AI-proposed fix is correct: a genuine structural change (a renamed or restructured component) gets a genuine new locator, and the test goes green because it's checking the same real thing again.
- Recognize when an AI-proposed fix is dangerous: wrapping a failing assertion in a longer timeout or a retry doesn't fix anything, it just waits or tries long enough for a real, intermittent backend bug to happen not to show up on that particular run.
- Trace through a concrete backend race condition, Vespera's SLA-check cron job racing against its "agent replied" webhook handler, and understand exactly why the intermittent test failure it produces is signal, not noise.
- Apply the same reasoning to a new failing test and log in this module's exercise, without being told in advance which category it falls into.

## Concepts

A failing test after an app change falls into one of two categories, and the test runner's output alone often can't tell you which.

**The test is stale.** The application changed in a way that doesn't affect behavior: a component got renamed, restructured, or re-styled, but what it *does* is identical. The fix belongs in the test: find the new stable hook, point the locator at it, done. This is what Module 3's brittle-selector pattern was already teaching you to guard against; this module is the day that guard actually gets exercised by a real redesign.

**The test is still right.** The application changed in a way that *does* affect behavior, usually not the change you were looking at, but something adjacent to it that got disturbed. The test failing is doing exactly its job. The fix belongs in the application, not the test, and touching only the test doesn't make the underlying problem go away; it just stops you from seeing it.

AI is genuinely useful for the first category: shown the new DOM, it's good at spotting "this text is still here, it just moved" and proposing a sensible new locator. AI is dangerous for the second category, for a structural reason, not a quality-of-model reason: an LLM asked to "fix this failing test" is optimizing for the test passing, and the cheapest way to make almost any flaky assertion pass is to give it more time or more attempts. That fix *works*, in the narrow sense that the exit code turns green. It works precisely because it doesn't need to understand the bug at all, which is exactly why it's the wrong tool for a bug that needs understanding.

## Practical example

Here's the DOM shape Module 3's automation was built against, the priority badge as a plain, purpose-built element:

```html
<div class="ticket-detail">
  <span data-testid="ticket-priority-badge">Normal</span>
</div>
```

And here's what Vespera's ticket dashboard redesign actually ships. The visible text is identical; a QE clicking around the UI by hand would never notice anything changed:

```html
<div class="ticket-detail">
  <div class="priority-pill priority-pill--urgent">
    <span class="priority-pill__label">Urgent</span>
  </div>
</div>
```

The badge became a `<PriorityPill>` component. Same information, same visual result, completely different markup, and the one attribute that existed purely so tests could find it, `data-testid="ticket-priority-badge"`, didn't come along for the ride. Nobody removed it on purpose; it just wasn't part of the new component, because nothing in a component redesign automatically preserves a test hook unless someone remembers to.

## AI/QE workflow

1. **Don't diagnose from the test alone; gather evidence first.** The failing assertion, the current DOM (or the component's source diff), and the actual CI log across more than one run. A single red run tells you a test failed; a run history tells you whether it's failing every time or some of the time, and that distinction is most of the diagnosis.
2. **Hand AI the evidence, not just the failure.** "This test fails, fix it" invites a guess. "Here's the locator that used to work, here's the new rendered DOM, here's the failure log" gives AI something to actually reason from.
3. **Evaluate what the proposed fix touches.** A fix that updates a locator to point at a real, present element in the new DOM is addressing the actual change. A fix that only adds a timeout, a retry, or a `waitForTimeout` is not addressing anything; it's the exact non-determinism pattern from Module 3, just proposed as a "solution" instead of caught as a mistake.
4. **Treat intermittent failures as a different problem than consistent ones.** A locator that's gone is gone on every single run: 100% reproducible. A failure that passes most of the time and fails occasionally is a different animal entirely, and AI tends to file both under "flaky, add a retry." That's the point in this workflow where a QE has to stop and ask *why* it's intermittent before accepting any fix.
5. **Verify the fix against the real system, not against the runner's exit code.** For a stale locator, that means confirming the new locator targets the same real element and the same real behavior. For anything intermittent, that means finding the actual mechanism, reading the backend code path, reproducing it deterministically if you can, before believing the test going green means the problem is gone.

## Code requirements

- A locator fix must point at a real, purpose-built hook that exists in the application (`data-testid`, or a documented role/label fallback), never a positional or styling-derived workaround invented just to make the test pass again.
- If the new DOM has no stable hook at all, the fix is a product-code change (add the `data-testid`), coordinated with the developer who owns that component, not a workaround in the test.
- No fix may add `test.describe.configure({ retries })`, `test.setTimeout()`, or widen an `expect.poll` timeout on a failing assertion without first identifying, outside the test, why the underlying value is inconsistent. "It passed after I added retries" is not a diagnosis.
- Any test-only endpoint added to reproduce a timing-dependent bug deterministically is subject to the same environment-gating rule as Module 3's seed and cleanup endpoints; it must not be reachable outside test and staging.
- A code review diff that changes only test timing/retry configuration, with no corresponding application-code change, for a bug whose symptom is "the system was sometimes in the wrong state," should be treated as incomplete, not merge-ready.

## Vespera Systems scenario

### Case 1: the locator is stale (good fix)

The redesign ships, and Module 3's exact test starts failing every single run:

```text title="CI log — 100% reproducible"
1) tests/sla-escalation.spec.ts:8:3 › SLA breach on an eligible ticket escalates correctly

  Error: expect(locator).toHaveText(expected) failed

  Locator:  getByTestId('ticket-priority-badge')
  Expected string: "Urgent"
  Received: <element(s) not found>
  Timeout:  15000ms

  Call log:
    - expect.toHaveText with timeout 15000ms
    - waiting for getByTestId('ticket-priority-badge')
```

Handed the failing assertion, the CI log above, and a DOM dump of the new ticket detail page, AI's diagnosis is straightforward and correct: `ticket-priority-badge` isn't in the DOM anywhere anymore, but a `<div class="priority-pill priority-pill--urgent">` containing the same text is; it correctly identifies this as a rename, not a behavior change, and proposes adding a new stable hook to the component rather than inventing a fragile selector against the class name:

```tsx title="components/PriorityPill.tsx — QE-requested, developer-applied"
export function PriorityPill({ level }: { level: PriorityLevel }) {
  return (
    <div
      className={`priority-pill priority-pill--${level.toLowerCase()}`}
      data-testid="priority-pill"
    >
      <span className="priority-pill__label">{level}</span>
    </div>
  );
}
```

```diff title="tests/sla-escalation.spec.ts"
- await expect(page.getByTestId('ticket-priority-badge')).toHaveText('Urgent');
+ await expect(page.getByTestId('priority-pill')).toHaveText('Urgent');
```

The test goes green again, and it's green for the right reason: the assertion checks the same real thing it always did, through a selector that once again exists on purpose. This is the whole good case: one line changed, backed by a one-line product change, both traceable directly to the actual redesign.

### Case 2: the failure is a real race condition (bad fix)

Separately, while re-verifying Module 2's approved edge cases against the redesigned dashboard, a different test starts failing, not every run, only some of them. It covers a case the original requirement already implies: escalation only fires when there's "no recent agent activity," which means an agent reply landing right around the SLA breach moment is a real boundary this system has to get right in both directions.

```typescript title="tests/sla-escalation-reply-race.spec.ts"
import { test, expect } from '../fixtures';

test('an agent reply arriving after escalation has already fired must not cancel it', async ({
  seedTicket,
  page,
  request,
}) => {
  const ticket = await seedTicket({
    status: 'Open',
    minutesToBreach: 61,
    assignedAgent: 'agent-priya', // fake test-fixture identifier, not a real Vespera user
  });

  // Trigger the SLA-check cron job directly instead of waiting for its
  // real interval — this is what actually commits the escalation.
  await request.post('/api/test/trigger-sla-check');

  await expect(page.getByTestId('priority-pill')).toHaveText('Urgent');

  // The escalation has already fired at this point. A reply landing
  // now should have no effect on it — only a *pending* escalation, one
  // that hasn't fired yet, should ever be cancelled by a reply.
  await request.post('/api/test/simulate-agent-reply', {
    data: { ticketId: ticket.id, agent: 'agent-priya' },
  });

  await page.reload();
  await expect(page.getByTestId('priority-pill')).toHaveText('Urgent');

  const ticketState = await (await request.get(`/api/test/tickets/${ticket.id}`)).json();
  expect(ticketState.escalated_by_system).toBe(true);
});
```

```text title="CI run history — intermittent"
Run 1418  PASS
Run 1419  FAIL
  Error: expect(received).toBe(expected)
  Expected: true
  Received: false
    at tests/sla-escalation-reply-race.spec.ts:27:34
Run 1420  PASS
Run 1421  PASS
Run 1422  FAIL
  Error: expect(received).toBe(expected)
  Expected: true
  Received: false
```

Here's the actual mechanism, and it's a real bug, not a testing artifact. Vespera's SLA-check cron job runs on its own schedule: when it finds a ticket past the 60-minute mark with no recent activity, it commits the escalation in one pass: sets `priority` to `"Urgent"`, sets `escalated_by_system` to `true`, and fires the Slack webhook. Separately, the "agent replied" webhook handler exists to cancel an escalation when an agent shows up before it happens, which is correct behavior *if* the escalation is still pending. The bug is that the reply handler doesn't check whether the escalation is still pending or already fired; it looks for any escalation record tied to the ticket and cancels it regardless of status. If a reply lands in the narrow window right after the cron job has already committed an escalation for that same ticket, the reply handler silently reverts it: `escalated_by_system` flips back to `false`, priority reverts to `"Normal"`, even though the escalation already correctly happened and the Slack message may already be on its way. It's the same shape of problem as an unsynchronized read racing an unsynchronized write, and it only shows up when the timing lines up, which is exactly why the test only fails sometimes.

Asked to "fix this flaky test," AI's proposed fix looks reasonable at a glance and is exactly the wrong move:

```typescript title="AI's proposed fix — do not use"
test.describe.configure({ retries: 3 });

// ...same test body, unchanged
```

The test goes consistently green in CI after this. Nothing about the bug changed. `test.describe.configure({ retries: 3 })` tells Playwright to silently re-run a failing test up to three more times and report success on the first pass, so as long as the race resolves in the test's favor on at least one of four attempts (which, at this bug's real-world frequency, it almost always will), the CI dashboard shows a clean green run every time, with no visible record that three of those four attempts actually failed. The underlying reply-handler bug is still fully live: in production, some fraction of real escalations are still getting silently cancelled by a coincidentally-timed reply, and there is now no signal anywhere, not in the test, not in CI history, telling anyone that's happening. The test didn't get fixed. It got quieted.

The real fix belongs in the reply handler, not the test: cancel the escalation only when its status is still `pending`, never when it's already `active`. The test itself should stay exactly as strict as it was: no retries, no widened timeout, because its intermittent failure is the only thing currently telling anyone this bug exists.

## Exercise

Here's a new failing test, from a different edge case in Module 2's approved set: **"ticket is resolved/closed before the 60-minute mark, no escalation fires."**

```typescript title="tests/sla-escalation-resolved-before-breach.spec.ts"
import { test, expect } from '../fixtures';

test('ticket resolved just before the SLA deadline does not escalate', async ({
  seedTicket,
  page,
  request,
}) => {
  const ticket = await seedTicket({
    status: 'Open',
    minutesToBreach: 61,
    assignedAgent: 'agent-priya',
  });

  await request.patch(`/api/test/tickets/${ticket.id}`, { data: { status: 'Resolved' } });
  await request.post('/api/test/trigger-sla-check');

  await page.goto(`/dashboard/tickets/${ticket.id}`);
  await expect(page.getByTestId('priority-pill')).toHaveText('Normal');

  const calls = await (await request.get(`/api/test/slack-webhook-calls?ticketId=${ticket.id}`)).json();
  expect(calls.length).toBe(0);
});
```

```text title="CI run history — intermittent"
sla-escalation-resolved-before-breach.spec.ts › ticket resolved just before the SLA deadline does not escalate

Run 2201  PASS
Run 2202  FAIL
  Error: expect(received).toBe(expected)
  Expected: 0
  Received: 1
    at tests/sla-escalation-resolved-before-breach.spec.ts:19:22
Run 2203  PASS
Run 2206  FAIL
  Error: expect(received).toBe(expected)
  Expected: 0
  Received: 1
```

The DOM here hasn't changed; the locator is fine, the badge does say `"Normal"` every time. The failure is only ever on the Slack call count, and only some of the time. Before you look at the answer: is this a test that just needs updating, or does it reveal a real bug? What does the test's own sequence of calls, resolve, then immediately trigger the SLA check, suggest about what might be racing here, and what would an AI-proposed retry actually be hiding if you're wrong?

<details>
<summary>Worked answer</summary>

This reveals a real bug, a different specific mechanism than Case 2 above, but the same category of problem: two operations touching the same ticket's state without enough coordination between them.

The test resolves the ticket, then immediately calls `/api/test/trigger-sla-check`. If Vespera's SLA-check job reads ticket status from a snapshot taken at the *start* of its evaluation pass rather than re-checking status at the moment it actually commits an escalation, there's a window where the resolve write hasn't yet become visible to that pass; the job still sees the ticket as `"Open"` and escalates it anyway, firing a Slack message for a ticket support already closed. This is a time-of-check-to-time-of-use gap, not the same bug as the reply handler in Case 2, but structurally the same shape: state changes out from under a decision that was made against a slightly stale read.

The tell is the same as before: the failure is intermittent, not constant, and nothing about the DOM or the locator is involved. If this got "fixed" by adding a retry or a longer wait before checking the webhook count, the test would go green, and Vespera would keep occasionally sending unnecessary, confusing escalation notifications for tickets that were already resolved, with nothing in CI ever pointing at why. The real fix is in the SLA-check job: re-verify the ticket's current status immediately before committing an escalation, not just at the start of the batch. The test stays exactly as strict as it is now.

</details>

## Failure modes

- **Accepting a green run as the finish line.** The whole point of this module is that "passing now" and "correct" are not the same claim, especially for anything that was failing intermittently before the fix.
- **Letting AI's fix category default to test-side.** An LLM optimizing for "make this pass" will reach for retries and timeouts before it reaches for "this might be an application bug," because the former is always available and the latter requires actually understanding the system.
- **Treating all intermittent failures as flaky by default.** Flaky infrastructure exists and is real, but "sometimes fails" is also exactly what a live race condition looks like from the outside; the two are indistinguishable from the test runner's output alone, and only distinguishable by tracing the actual mechanism.
- **Fixing without a diff to point at.** A stale-locator fix should always trace back to a specific, nameable application change. A fix with no application-code counterpart, for a bug that involves state being wrong, is a fix that didn't actually happen.
- **Silently absorbing retries into CI config.** `retries` set at the project or suite level, rather than per-test with a linked reason, hides exactly this failure mode at a place most people never look.

## Security considerations

`/api/test/trigger-sla-check` and `/api/test/simulate-agent-reply` join the same test-only API surface introduced in Module 3, and carry the same requirement: they must be unreachable outside test and staging, gated on the backend by an environment check, because both let a caller force real business logic, escalation, notification, to run on demand with no normal authorization path. That's a meaningful capability to leave reachable anywhere near production. As always, keep every identifier in these examples obviously fake: `agent-priya` is a fixture label, not a real Vespera user, the same as every other example on this page.

## Guardrails

Right now, catching "the fix was a retry, not a root cause" is a human review judgment call, exactly the kind of informal practice Module 5 turns into an enforced check. Module 5's quality gate extends to flag any diff that adds or widens `retries`, `test.setTimeout()`, or a `poll(...)` timeout on an existing assertion without an accompanying application-code change or a linked bug reference, not because retries are always wrong, but because a retry with no explanation attached is indistinguishable, in a diff, from a bug getting quietly buried.

## Production considerations

An escalation that gets silently rolled back is an SLA commitment the system believes it kept and didn't; a ticket that should have gotten urgent attention sat unescalated instead, and nothing in the product surfaces that fact to anyone. If the CI fix for Case 2 had been the AI-proposed retry, this bug would still be live right now, discoverable only by noticing a pattern in customer complaints or auditing escalation records directly, a much slower and much more expensive way to find the same bug a test was already catching for free. Treat an intermittent-failure rate as a production signal worth graphing over time, the same way you'd graph an error rate, rather than something CI retry settings are meant to make disappear.
