Nine modules in, you've done every stage of the AI-QE pipeline by hand, once each, on real Vespera work: generated scenarios from a requirement (Module 2), reviewed and approved them, automated them (Module 3), diagnosed a failure without being fooled by a fix that only looked like one (Module 4), and formalized the review habits into an automated gate (Module 5). Modules 6 through 9 did the same kind of work against a different kind of target: AI systems themselves. This module is where those two threads meet: not as new content, but as one assembled shape. You've already built every piece. What's missing is the wiring, and naming, precisely, the wrong way to wire it, so the capstone doesn't repeat it.

## Page purpose

To walk the full AI-QE pipeline (Requirement → AI generates → QE reviews → guardrails → automation → execution → analysis → report) stage by stage, end to end, using Module 2's SLA Auto-Escalation requirement as the running example, explicitly citing which earlier module taught each stage. This page also sketches the interface each stage will need as a real component, class or function signatures, not implementations, and names the one architectural mistake the capstone is built to avoid: writing the whole thing as a single script that chains AI calls in sequence with no real boundaries between stages. By the end of this page, you should be able to look at the interface sketch below and know exactly what the capstone has to build, without having seen a line of its implementation yet.

## Learning objectives

- Narrate the eight-stage AI-QE pipeline end to end against one real requirement, citing which module taught each stage.
- Explain precisely what makes "one script that calls the LLM repeatedly in sequence" an anti-pattern, in terms of what it can't do that a component-based version can.
- Read a component interface sketch (signatures only) and know what each component's single responsibility is and what it must NOT do.
- Distinguish which pipeline stages are AI-driven, which are deterministic code, and which require a human, and explain why collapsing that distinction is exactly what the anti-pattern does.

## Concepts

**The pipeline was never new, it was just distributed across nine modules.** Module 1 named it. Every module since has implemented one or two of its stages against a real Vespera artifact, without ever calling out "this is pipeline stage 3." Naming that mapping explicitly is most of this page's job:

| Pipeline stage | Taught in | What it produced, concretely |
|---|---|---|
| Requirement | Module 2 | The SLA Auto-Escalation requirement text and its five edge cases |
| AI generates | Module 2 | A first-pass batch of test scenarios from that requirement |
| QE reviews | Module 2 | The weak-test-pattern checklist, applied by hand, producing an approved scenario set |
| Guardrails | Module 5 | The secret scanner, the six-item quality-gate checklist, the CI wiring |
| Automation | Module 3 | Real Playwright TypeScript, generated from the approved scenarios, reviewed against Module 5's gate |
| Execution | Module 5 (as CI) | The guardrail pipeline's CI job, which is also where the automation actually runs |
| Analysis | Module 4 | The real-bug-vs-stale-test distinction, the hardest judgment call in the whole pipeline |
| Report | *(new here)* | Nothing before this module produced a report as a deliverable in its own right |

Modules 6 through 9 ran a parallel version of roughly the same shape against a different kind of target, an LLM feature, a RAG system, an agent, with "requirement" replaced by "prompt or feature spec" and "automation" replaced by "eval suite," but the same generate → review → guard → execute → analyze → report skeleton held throughout. That's not a coincidence this page is pointing out for elegance's sake; it's why one pipeline abstraction, built once, can serve both halves of this course instead of needing two.

**"Generation" and "validation" are not adjacent steps in the same function, they are different components with different failure modes.** A `TestGenerator` can be wrong because the model hallucinated a scenario that doesn't apply. A `TestReviewer` can be wrong because its checklist is incomplete. A `GuardrailChecker` can be wrong because a pattern list went stale. Three different bugs, three different owners, three different tests you'd write to catch each one, which is only possible if they're three different pieces of code in the first place.

**The single prompt-chain-script anti-pattern.** Picture the whole pipeline written as one script: call the LLM to generate scenarios, feed that output straight into another LLM call asking it to "review" them, feed *that* into a call asking for automation code, run it, feed the result into one more call asking for a report. It's fast to write, and it will even produce a plausible-looking report. Here's exactly what it can't do:

- **No independent test point.** If the final report is wrong, you cannot tell whether generation was bad, review was bad, or the automation itself was bad; every stage is invisible except the last one.
- **A generation bug and a guardrail bug look identical from outside.** Both just mean "something further downstream was wrong." Without a boundary between the stages, you can't even ask which.
- **No provider swap without touching everything.** If review should reasonably run on a cheaper or more constrained model than generation, a single script chaining raw calls has no seam to put that decision; it's one undifferentiated block of prompting.
- **Nothing here is unit-testable.** You can't mock "the reviewer" in isolation to test the orchestrator's control flow, because there is no reviewer; there's just the next paragraph in the same prompt chain.

None of this is about code style. It's the direct, mechanical consequence of collapsing seven different responsibilities into one undifferentiated sequence of AI calls. The capstone's hard requirement, separately testable components, wired by a thin orchestrator with no logic of its own, exists specifically to avoid every bullet point above.

## Practical example

Narrated against Module 2's exact requirement, stage by stage:

1. **Requirement.** "When a ticket's SLA countdown reaches 60 minutes remaining and the ticket is still `status: "Open"` with no recent agent activity, the system automatically escalates it," the text from Module 2, unchanged.
2. **AI generates.** The same six-scenario first-pass batch from Module 2's worked example, two of which were later recognized as duplicates of each other.
3. **QE reviews.** Module 2's weak-test-pattern checklist, applied to that batch, producing the six-scenario approved set (after fixing the weak assertions, dropping the duplicate, and adding the two missing edge cases the batch had skipped).
4. **Guardrails.** Module 5's six-item quality gate and secret scanner, run against whatever automation stage 5 below produces, not against the scenarios themselves, which is a text-review problem, not a static-analysis one.
5. **Automation.** Module 3's Playwright TypeScript, generated from the approved scenario set, using `data-testid="ticket-priority-badge"` and the async-aware wait strategy Module 3 settled on.
6. **Execution.** The automation actually runs, in CI, per Module 5's wiring, and produces a pass/fail result per scenario.
7. **Analysis.** If something failed, Module 4's judgment call: is this a stale locator (fix the test), or a real, possibly intermittent bug (block the fix, file it)? Module 4's SLA-cron-versus-reply-webhook race condition is exactly this stage's hardest case.
8. **Report.** A QE-facing summary: which scenarios passed, which failed and why, which failures are confirmed bugs versus needs-updating tests, and what's still open. Nothing before this module built this as a real deliverable; it existed only as prose narration in earlier modules ("here's the net verdict").

## AI/QE workflow

The workflow *is* the eight stages above, run start to finish, with one addition this module makes explicit for the first time: **the report is not optional narration, it's an artifact.** Every earlier module effectively produced one (Module 2's "approved scenario set," Module 5's "net verdict"), but always as prose inside a lesson, never as something the pipeline itself outputs as a first-class result a QE lead could read without having read the whole page it came from. The capstone's `QEReportBuilder` is what turns that pattern into a real component.

## Code requirements

Interface sketches only on this page, Python, using `Protocol` the same way Module 6 introduced it, matching every AI-systems-under-test module from here forward. No method body does real work; every one raises `NotImplementedError` or is left as `...`. Nothing here should be copied into a project expecting it to run; this is the shape the capstone fills in, not a working draft of it.

```python
from typing import Protocol


class TestGenerator(Protocol):
    """AI-driven. Single responsibility: requirement text in, draft
    scenarios out. Never reviews its own output."""
    def generate(self, requirement: str) -> list["TestScenario"]: ...


class TestReviewer(Protocol):
    """Deterministic code, not an LLM call — applies a checklist
    (Module 2's weak-test-pattern rules) to AI-generated scenarios and
    returns which passed, which were fixed, which were dropped."""
    def review(self, scenarios: list["TestScenario"]) -> "ReviewResult": ...


class GuardrailChecker(Protocol):
    """Deterministic code — Module 5's secret scanner and quality-gate
    checklist, applied to generated automation code, not to scenario
    text. A genuinely separate code path from TestReviewer, even though
    both produce a pass/fail-with-reasons verdict."""
    def check(self, automation_code: str) -> "GuardrailResult": ...


class AutomationGenerator(Protocol):
    """AI-driven. Approved scenarios in, automation source code out.
    Knows nothing about whether its own output will pass the guardrail
    check — that's GuardrailChecker's job, not this component's."""
    def generate(self, scenarios: list["TestScenario"]) -> str: ...


class TestExecutor(Protocol):
    """Deterministic code — runs automation code (e.g. via a subprocess
    invoking the test runner) and returns raw pass/fail results per
    scenario. No AI involvement, no judgment calls."""
    def execute(self, automation_code: str) -> "ExecutionResult": ...


class FailureAnalyzer(Protocol):
    """AI-assisted, QE-validated — Module 4's judgment call, formalized:
    given an execution failure plus supporting evidence (app diff, CI
    history), classify it as stale-test-needs-updating or
    real-bug-found, with a confidence level a QE can override."""
    def analyze(self, execution_result: "ExecutionResult") -> "AnalysisResult": ...


class QEReportBuilder(Protocol):
    """Deterministic code — assembles every prior stage's output into
    one QE-facing report. Adds no new judgment of its own; it only
    presents judgments the earlier stages already made."""
    def build(self, review: "ReviewResult", guardrails: "GuardrailResult",
               execution: "ExecutionResult", analysis: "AnalysisResult") -> "Report": ...
```

The orchestrator that wires these together belongs in the capstone, not here, but its shape is worth previewing, because "thin" is a concrete property, not a vibe: it calls each component once, in order, passing one stage's output to the next stage's input, and contains no prompting, no checklist logic, and no pass/fail decision anywhere in its own body. If you can point to a line in the orchestrator that decides something rather than delegating it, that line belongs in one of the seven components above, not in the wiring between them.

## Exercise

Vespera has a new requirement: **"Duplicate Ticket Detection"**, when a customer submits a new ticket that's substantially similar to one of their own open tickets from the last 24 hours, the system flags it as a possible duplicate for an agent to review, rather than auto-merging or auto-closing it. Without writing any code, sketch, in prose or bullets, what happens at each of the eight pipeline stages for this requirement: what would `TestGenerator` plausibly produce, what weak patterns might a QE need to catch in `TestReviewer`, what would `GuardrailChecker` be checking against, roughly what the automation would need to do, and what an intermittent-versus-real-bug judgment call might look like for this specific feature (hint: think about what "substantially similar" and "last 24 hours" imply about timing and fuzzy-matching edge cases). There's no worked answer provided; the point is rehearsing the pipeline shape against an unfamiliar requirement before the capstone asks you to trust it against a real one.

## Failure modes

- **Treating this page's sketch as optional context before the capstone.** The capstone assumes you understand *why* seven components beat one script, not just that the rule exists; if the anti-pattern section above didn't land, the capstone's hard requirement will read as arbitrary strictness rather than a real architectural constraint.
- **Collapsing TestReviewer and GuardrailChecker into one component because "they both check things."** They check different things, at different stages, with different logic (a checklist applied to scenario text versus static analysis applied to generated code); merging them because they're both "checks" is exactly the kind of boundary-blurring the anti-pattern warns about, even without going all the way to a single script.
- **Making the orchestrator smart.** The moment the orchestrator contains an `if` statement deciding whether a result was good enough to proceed, that decision has quietly moved out of the component whose job it was and into the wiring, which is the anti-pattern creeping back in one function at a time.
- **Skipping FailureAnalyzer's confidence/override property.** An analyzer that hands down a verdict with no way for a QE to disagree recreates the "AI generates, QE validates" violation this whole course has been warning about, just one pipeline stage later than usual.

## Security considerations

Nothing on this page executes anything; it's Python `Protocol` definitions with no bodies, so there's no direct security surface here. What's worth carrying forward into the capstone: every component that touches real data (a real requirement, real ticket text, a real API key for `AutomationGenerator`'s or `TestGenerator`'s own LLM calls) inherits every rule this course has followed since Module 2: sanitize inputs, never hardcode credentials, keep example data obviously fake.

## Guardrails

`GuardrailChecker` is itself a guardrail, Module 5's, wired into the pipeline as a named stage rather than a standalone script run by hand. The meta-guardrail this page adds on top: the interface boundaries themselves. A `TestReviewer` that can only see scenarios, never automation code, structurally cannot be the thing that approves a hardcoded secret slipping through; that's `GuardrailChecker`'s job, and the type signature above enforces that division whether or not anyone remembers to enforce it by convention.

## Production considerations

A pipeline assembled from independently swappable components can evolve one stage at a time: swap `AutomationGenerator`'s underlying model without touching `TestReviewer`, or replace `TestExecutor`'s runner without touching anything upstream of it, which is the practical payoff of everything this page argued for structurally. The single-script version can't do this at all; changing anything means re-reading and re-testing the whole chain, because there was never a seam to change just one part.
