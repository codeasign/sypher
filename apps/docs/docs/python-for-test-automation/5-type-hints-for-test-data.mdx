Here's an honest starting point: Python is not going to stop you at runtime the way a strictly typed language would. If you write a type hint that says a function takes a string and you pass it a number anyway, Python runs it anyway — it won't crash because of the hint alone. So why bother? Because type hints still make your code easier to read, and they make your editor genuinely more helpful while you're writing it.

## What a type hint looks like

Take the helper function from earlier:

```python
def build_test_user(role):
    return {
        "username": f"test_{role}",
        "role": role,
        "is_active": True,
    }
```

Adding type hints means annotating the parameter and the return value:

```python
def build_test_user(role: str) -> dict:
    return {
        "username": f"test_{role}",
        "role": role,
        "is_active": True,
    }
```

`role: str` says "this parameter is expected to be a string." `-> dict` says "this function returns a dict." Nothing about how the function runs has changed — it's the exact same code. What's changed is that anyone reading this function — including you, three weeks from now — immediately knows what to pass in and what to expect back, without reading the function body.

## What you get from this in practice

Open this function in VS Code with the Python extension installed, and the moment you call it, your editor suggests `role` should be a string and warns you (with a squiggly underline, not a crash) if you pass something else — like a number where a role name was expected. That's autocomplete and early warning working in your favor, entirely at the editing stage, before you've ever run the code.

```python
build_test_user(role=123)  # your editor flags this — role should be a str
```

Running that line wouldn't actually crash — Python still executes it, since it doesn't enforce hints at runtime. But your editor caught the mistake for you before you even got that far, which is exactly the value type hints bring: earlier warnings, better autocomplete, more readable code — without changing how Python itself behaves.

Take the `build_test_appointment(status)` function you wrote earlier and add type hints to it: `status: str` for the parameter, and `-> dict` for the return type.
