You've made it to the last stop. No new syntax here — just you, taking everything you've learned about data, functions, and pytest, and pointing it at a real piece of a real application. Let's model a permission system.

## The system we're testing

`rbac-healthcare-system` is a small healthcare app with four roles: **admin**, **doctor**, **nurse**, and **patient**. Each role is allowed to do different things — admins can manage users, doctors can complete appointments, nurses can schedule them, and patients can only see their own records. That's the whole idea behind RBAC ("role-based access control," a gloss you've seen before in this app's docs): what a user is allowed to do depends entirely on which role they hold.

The app's own documentation spells out exactly who can do what, in this table:

| Action | Admin | Doctor | Nurse | Patient |
|---|---|---|---|---|
| View all users | Yes | No | No | No |
| Delete users | Yes | No | No | No |
| View all appointments | Yes | No | Yes | No |
| View own appointments | No | Yes | No | Yes |
| Schedule appointments | No | No | Yes | No |
| Complete appointments | No | Yes | No | No |
| Cancel appointments | No | Yes | Yes | No |
| Create medical records | No | Yes | No | No |
| View medical records | Yes | Yes | No | Yes (own only) |

As a manual tester, you've probably clicked through a table exactly like this one — logging in as each role, one at a time, checking whether a button is there or a page throws an error. That works, but it doesn't scale, and it's easy to miss a row when you're doing it by hand. Let's turn this table into something a pytest test can check for us.

## Step 1: model one row of the table

Every row in that table is really the same shape repeated: a role, an action, and whether that role is allowed to do it. A dict is the natural fit:

```python
permission_case = {
    "role": "admin",
    "action": "View all users",
    "expected": True,
}
```

`expected` here means "what the table says should happen" — `True` for "Yes," `False` for "No." Keeping this as a plain dict of plain values keeps the whole exercise simple: we're not testing the live app over the network for this part, we're testing that our understanding of the rules (encoded as data) matches the rules our tests will eventually check against.

## Step 2: turn a few rows into data

You don't need to encode all nine rows to get the idea — a handful is enough to prove the pattern works. Let's take four rows straight from the table above:

```python
permission_cases = [
    {"role": "admin", "action": "View all users", "expected": True},
    {"role": "doctor", "action": "View all users", "expected": False},
    {"role": "nurse", "action": "Schedule appointments", "expected": True},
    {"role": "patient", "action": "Delete users", "expected": False},
]
```

Add a type hint on a function that works with this data, and your editor knows every item in the list should look like this shape — enough to catch an obvious mistake, like typing `"Roll"` instead of `"role"`, while you're writing the code.

## Step 3: a tiny function that checks a permission

To make this actually testable, we need something to check a case against. In the real app, this logic would live in a permissions module and get called against a logged-in user. Here, to keep the focus on data and testing rather than wiring up a server, we'll write a small stand-in function that looks up the answer the same way the table does:

```python
def has_permission(role: str, action: str) -> bool:
    for case in permission_cases:
        if case["role"] == role and case["action"] == action and case["expected"]:
            return True
    return False
```

This says: "search through our known cases, and return `True` only if we find a matching row where the expected result was `True`." It's a simplified stand-in for the real permission check the app would run against its own rules — but it's enough to build a real pytest test around.

## Step 4: write the pytest tests

Now for the payoff — tests that check a role against the matrix, using `assert` the way you've been practicing throughout this course:

```python
def test_admin_can_view_all_users():
    assert has_permission("admin", "View all users") is True


def test_doctor_cannot_view_all_users():
    assert has_permission("doctor", "View all users") is False


def test_nurse_can_schedule_appointments():
    assert has_permission("nurse", "Schedule appointments") is True
```

Run that with `pytest` and you'll see three green checks — a small, repeatable proof that your understanding of the permission table matches what the code expects:

```text
collected 3 items

test_permission_matrix.py ...                                          [100%]

3 passed in 0.02s
```

This is the same shape of test you'd eventually point at the real running app: instead of checking `has_permission` against a local list, you'd call the app's actual API at `http://localhost:5000` and check the response — using exactly the `requests` calls and fixtures from earlier. The data and the `assert` statements barely change; only where the data comes from does.

## Where to go from here

You started this course not knowing what a variable was, and you've ended it modeling a real permission system and asserting against it with pytest. That's a genuinely useful skill on its own — plenty of test automation work is exactly this: taking a rule that lives in a spec or a README, encoding it as data, and writing assertions that catch the day someone breaks it.

From here, the concepts you've built — functions, dicts and sets, `requests`, fixtures, `conftest.py` — carry over directly into whichever direction you take test automation next: Selenium for browser automation, Playwright's Python bindings if you want the same modern tooling this site's TypeScript-based Playwright course covers, or deeper API testing with `requests` and pytest alone. None of those require unlearning anything here — they build on it.

And if you've enjoyed seeing Python in action and want to go deeper into the language itself — data analysis, async code, building real applications — **Python for AI Engineers** on this site covers all of that in detail.

Either way, well done. You've built a real habit here, and it'll pay off every time you write a test from now on.

## Try it

Add a fifth case to `permission_cases` for the row **"View medical records" / patient / Yes (own only)** — treat "own only" as `True` for this exercise, since our simplified model doesn't yet distinguish "own" from "all." Then write one more test asserting `has_permission("patient", "View medical records") is True`. Once that passes, try adding a case that should be `False` (for example, nurse trying to create medical records) and write a test asserting that one is correctly denied too.
