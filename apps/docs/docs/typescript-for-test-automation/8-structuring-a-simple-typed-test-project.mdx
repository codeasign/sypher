By now you've written types like `TestPatient` and `TestAppointment`, and you've probably built a few helper functions for things like logging into the RBAC Healthcare System or creating a test appointment through the API. If all of that is sitting in one giant test file, you've probably already felt the pain: you scroll past the same interface definition three times before you find the actual test you're looking for.

This page is about fixing that. Not with anything fancy — just by giving your types and helpers their own home, so every test file can import them instead of redefining them.

## The problem with one big file

Imagine a single file called `patient.test.ts` that has grown to include:

- The `TestPatient` and `TestAppointment` interfaces
- A `loginAsNurse()` helper
- A `createTestAppointment()` helper
- Ten actual tests

Every time you want to write a new test file — say, one for admin-only actions — you either copy-paste those types and helpers to the top of the new file, or you import them from `patient.test.ts` (which is confusing, because now a "test" file is secretly also a "shared code" file). Neither option scales well once you have a handful of test files.

The fix is simple: pull the shared stuff out into its own files, and let test files stay focused on just testing.

A few things worth noticing:

- `jest.config.js` lives at the project root, not inside `tests/`. It's project-level configuration, so it belongs next to `package.json`.
- `tsconfig.json` also lives at the root, for the same reason — it configures TypeScript for the whole project.
- Everything test-related lives inside a `tests/` folder. Some teams instead co-locate tests right next to the code they cover, but for a pure test-automation project like this one, a single `tests/` folder is the more common and easier-to-navigate choice.
- `types.ts` and `helpers.ts` sit inside `tests/` alongside the `*.test.ts` files, because they're only used by tests — they aren't "app code," so there's no need to bury them somewhere else.

## Pulling your types into `types.ts`

Instead of defining `TestPatient` and `TestAppointment` at the top of every test file, define them once:

```typescript
// tests/types.ts
export interface TestPatient {
  id: string;
  fullName: string;
  role: "patient";
  dateOfBirth: string;
}

export interface TestAppointment {
  id: number;
  patientId: number;
  doctorId: number;
  scheduledAt: string;
  status: "scheduled" | "completed" | "cancelled";
}
```

Notice the `export` keyword in front of each interface. Without it, these types would only be usable inside `types.ts` itself — `export` is what makes them available to other files.

## Pulling your helpers into `helpers.ts`

Same idea for functions you call repeatedly across tests, like logging in or creating an appointment through the backend at `http://localhost:5000`:

```typescript
// tests/helpers.ts
import { TestPatient, TestAppointment } from "./types";

export async function loginAsNurse(): Promise<string> {
  const response = await fetch("http://localhost:5000/api/auth/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username: "nurse1", password: "nurse123" }),
  });
  const data = await response.json();
  return data.token;
}

export async function createTestAppointment(
  token: string,
  patientId: number
): Promise<TestAppointment> {
  const response = await fetch("http://localhost:5000/api/appointments", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
    },
    body: JSON.stringify({ patientId, doctorId: 5, scheduledAt: new Date().toISOString() }),
  });
  return response.json();
}
```

Notice that `helpers.ts` imports `TestAppointment` from `./types` — the `./` means "look in this same folder." This is the whole point of splitting things up: `helpers.ts` doesn't redefine `TestAppointment`, it just reuses the one true definition.

## Using it all from a test file

Now a real test file stays short and readable, because it only contains the things that make it a test:

```typescript
// tests/appointment.test.ts
import { loginAsNurse, createTestAppointment } from "./helpers";

describe("appointment creation", () => {
  it("creates an appointment for a patient", async () => {
    const token = await loginAsNurse();
    const appointment = await createTestAppointment(token, 42);

    expect(appointment.status).toBe("scheduled");
    expect(appointment.patientId).toBe(42);
  });
});
```

Compare that to a file where `TestAppointment`, `loginAsNurse`, and `createTestAppointment` are all defined above this test — it would take three times as many lines before you even got to the part that matters: what's actually being tested.

## Where Jest config fits in

`jest.config.js` at the project root tells Jest (and, through `ts-jest` or a similar setup, TypeScript) where to find your tests and how to run them. A minimal version looks like this:

```javascript
// jest.config.js
module.exports = {
  preset: "ts-jest",
  testEnvironment: "node",
  testMatch: ["**/tests/**/*.test.ts"],
};
```

That `testMatch` line is what tells Jest "look inside the `tests/` folder for anything ending in `.test.ts`." Because `types.ts` and `helpers.ts` don't end in `.test.ts`, Jest knows to leave them alone — they get imported by test files, but Jest never tries to run them as tests themselves.

## Why this is worth doing early

You might only have three test files right now, so copy-pasting a type definition doesn't feel like a big deal yet. But this structure pays off the moment a second person joins the project, or the moment `TestAppointment` needs a new field. With everything centralized:

- You update `TestAppointment` in exactly one place (`types.ts`), and every test file that imports it gets the update automatically.
- A new teammate can open `tests/helpers.ts` and immediately see every reusable action available to them, instead of hunting through test files.
- Your actual test files read like a list of test cases, not a mix of setup code and test cases tangled together.

## Try it

Create a small project structure by hand (you don't need to run it, just create the files):

1. Make a `tests/` folder containing `types.ts`, `helpers.ts`, and a test file named `nurse.test.ts`.
2. In `types.ts`, define and export an interface called `TestNurse` with `id: string`, `fullName: string`, and `shift: "day" | "night"`.
3. In `helpers.ts`, import `TestNurse` from `./types` and write a function `createTestNurse(shift: "day" | "night"): TestNurse` that returns a hardcoded nurse object using that shift.
4. In `nurse.test.ts`, import `createTestNurse` from `./helpers` and write one `it(...)` test that calls it and asserts the returned nurse's `shift` matches what you passed in.

If your test file only needs one `import` line to get everything it needs, you've structured it correctly.
