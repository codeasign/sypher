So far you've been running TypeScript files by hand with `tsc` and `node`. That's fine for a quick script, but it's not how testing works. A real test needs a **test runner** — a tool that finds your test files, runs them, checks whether each check inside passed or failed, and prints a clear report. The test runner we'll use throughout this course is **Jest**, one of the most popular test runners in the JavaScript and TypeScript world.

By the end of this page, you'll have Jest running TypeScript tests in your project, and you'll have seen both a passing test and a failing one — because reading that output is a skill you'll use constantly from here on.

## Install Jest and ts-jest

Open a terminal in your project folder (the same one from earlier pages) and run:

```bash
npm install --save-dev jest ts-jest @types/jest
```

Here's what each package does:

- **jest** — the test runner itself. It finds your test files, runs them, and reports pass/fail.
- **ts-jest** — a bridge that lets Jest understand TypeScript directly, so you don't have to manually compile `.ts` files with `tsc` before every test run.
- **@types/jest** — type definitions for Jest's functions (like `expect` and `test`), so VS Code can give you autocomplete and catch typos as you write tests.

The `--save-dev` flag means these are **dev dependencies** — tools you need while building and testing your project, but not something an end user of the app would ever need. Testing tools always go here.

## Configure Jest for TypeScript

Jest needs to be told to use `ts-jest` to handle `.ts` files. Create a file called `jest.config.js` in the root of your project (the same folder as `package.json`):

```javascript
module.exports = {
  preset: "ts-jest",
  testEnvironment: "node",
};
```

`preset: "ts-jest"` tells Jest to run every test file through `ts-jest` first, so it understands TypeScript syntax and types without you compiling anything by hand. `testEnvironment: "node"` tells Jest to run your tests in a plain Node.js environment, which is what we want for backend and API-style checks — later pages will explain when that changes.

## Write the smallest possible test

Let's prove the whole loop works before we do anything test-automation-specific. Create a new file called `sanity.test.ts`. The `.test.ts` ending matters — it's how Jest recognizes a file as containing tests it should run.

```typescript
test("2 + 2 equals 4", () => {
  expect(2 + 2).toBe(4);
});
```

Let's break that down:

- `test(...)` declares one test case. The string `"2 + 2 equals 4"` is just a human-readable label — it's what shows up in the report, so make it describe what's being checked.
- The second argument is a function containing the actual check.
- `expect(2 + 2)` wraps the value you want to check.
- `.toBe(4)` is a **matcher** — it states what you expect that value to equal. If `2 + 2` doesn't equal `4`, the test fails.

There's nothing about testing an app here yet — this is deliberately the simplest possible check, just so you can see Jest run, pass, and report before anything more realistic gets added.

## Run it

Add a script to your `package.json` so `npm test` runs Jest:

```json
{
  "scripts": {
    "test": "jest"
  }
}
```

Now run it:

```bash
npm test
```

## Reading a passing result

You should see something like this in your terminal:

```bash
PASS  ./sanity.test.ts
  √ 2 + 2 equals 4 (2 ms)

Test Suites: 1 passed, 1 total
Tests:       1 passed, 1 total
Snapshots:   0 total
Time:        1.234 s
```

That green `PASS` and the checkmark (√) next to your test's label are what you're looking for. The summary at the bottom — "1 passed, 1 total" — is the first thing your eyes should go to once you have many tests running at once.

## Reading a failing result

Now let's deliberately break it, so you know what failure looks like *before* you're staring at a real one under pressure. Change the test to something false:

```typescript
test("2 + 2 equals 4", () => {
  expect(2 + 2).toBe(5);
});
```

Run `npm test` again, and this time you'll see red output instead:

```bash
FAIL  ./sanity.test.ts
  × 2 + 2 equals 4 (3 ms)

  ● 2 + 2 equals 4

    expect(received).toBe(expected)

    Expected: 5
    Received: 4

      1 | test("2 + 2 equals 4", () => {
    > 2 |   expect(2 + 2).toBe(5);
        |                 ^
      3 | });

Test Suites: 1 failed, 1 total
Tests:       1 failed, 1 total
```

Notice how much detail Jest gives you for free: it tells you which test failed, exactly what it **Expected** versus what it actually **Received**, and it even points an arrow (`^`) at the line and the exact expression that caused the failure. This is the report you'll be reading dozens of times a day once you're writing real tests — getting comfortable with "Expected vs. Received" now will save you time later. Go ahead and change `.toBe(5)` back to `.toBe(4)` so your test passes again before moving on.

This tiny `2 + 2` check isn't testing anything about the healthcare app yet — that comes soon. The point of this page was to see the whole machine turn over once: write a check, run it, and read what it tells you. Every test you write from here on, no matter how complex, produces exactly this same shape of report.

## Try it

Add a second test to `sanity.test.ts` that checks a string instead of a number — for example, that `"nurse".toUpperCase()` equals `"NURSE"` (one of the four roles in the RBAC healthcare app you'll be testing later). Run `npm test` and confirm you see two passing tests in the summary. Then deliberately break your new test's expected value, run it again, and read the red output before fixing it back.
