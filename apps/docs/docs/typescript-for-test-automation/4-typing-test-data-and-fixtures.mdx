Every test you write needs data to work with. A test that logs in as a patient needs a patient. A test that checks appointment status needs an appointment. Right now, if you write that data as a plain object, TypeScript has no idea what shape it's supposed to be — which means it can't stop you from typing `frstName` instead of `firstName` and getting a confusing failure five lines later.

The fix is small and pays off immediately: describe the shape once with an `interface`, then reuse it everywhere. This is called a **fixture** — a plain-English word for "some sample data, set up ahead of time, that your tests use as a known starting point."

## Modeling a patient

Here's an `interface` for a patient in the RBAC healthcare app:

```typescript
interface TestPatient {
  id: number;
  firstName: string;
  lastName: string;
  dateOfBirth: string;
}
```

This says: "any object I call a `TestPatient` must have these four fields, with these exact types." Now if you write a patient object that's missing `dateOfBirth`, or that spells a field wrong, TypeScript flags it before you ever run the test — not after.

```typescript
const patient: TestPatient = {
  id: 1,
  firstName: "Alice",
  lastName: "Nguyen",
  dateOfBirth: "1990-04-12",
};
```

## Modeling an appointment

Appointments in this app connect a patient to a doctor, on a date, with a status. That status is worth being strict about — an appointment can only ever be `'scheduled'`, `'completed'`, or `'cancelled'`. Using a union of exact string values (rather than just `string`) means TypeScript will reject a typo like `'compelted'` immediately:

```typescript
interface TestAppointment {
  id: number;
  patientId: number;
  doctorId: number;
  date: string;
  status: 'scheduled' | 'completed' | 'cancelled';
}
```

## Building fixtures with a helper function

Instead of retyping a full patient object in every test file, write one helper function that builds and returns it. This is the same helper-function pattern you used earlier in the course — a small function you can call from any test that needs this data:

```typescript
function makeTestPatient(overrides?: Partial<TestPatient>): TestPatient {
  return {
    id: 1,
    firstName: "Alice",
    lastName: "Nguyen",
    dateOfBirth: "1990-04-12",
    ...overrides,
  };
}
```

Don't worry too much about `Partial<TestPatient>` — it's a built-in TypeScript helper that means "this can be a `TestPatient`, but every field is optional." That's what lets you call `makeTestPatient()` to get sensible defaults, or `makeTestPatient({ firstName: "Priya" })` when one particular test needs a different first name, without retyping the whole object.

Now a Jest test can lean on that helper and assert against the fixture it gets back:

```typescript
test("makeTestPatient returns a patient with the given first name", () => {
  const patient = makeTestPatient({ firstName: "Priya" });

  expect(patient.firstName).toBe("Priya");
  expect(patient.lastName).toBe("Nguyen");
  expect(patient.dateOfBirth).toBe("1990-04-12");
});
```

Notice that `patient` is fully typed as `TestPatient` here — your editor knows `patient.firstName` exists and is a `string`, without you writing any extra annotations. That's the whole payoff: type it once, in the interface and the helper function, and every test that uses the fixture gets the checking for free.

You can do the exact same thing for appointments:

```typescript
function makeTestAppointment(overrides?: Partial<TestAppointment>): TestAppointment {
  return {
    id: 100,
    patientId: 1,
    doctorId: 5,
    date: "2026-08-01",
    status: 'scheduled',
    ...overrides,
  };
}

test("makeTestAppointment can build a completed appointment", () => {
  const appointment = makeTestAppointment({ status: 'completed' });

  expect(appointment.status).toBe('completed');
  expect(appointment.patientId).toBe(1);
});
```

## Try it

Write an interface called `TestDoctor` with fields `id: number`, `name: string`, and `specialty: string`. Then write a `makeTestDoctor` helper function that returns a `TestDoctor` with default values, and a small Jest test that calls the helper and uses `expect()` to check that `specialty` matches what you passed in.
