Open any real test file in an automation project and, before you've written a single line yourself, you'll already see the same handful of patterns over and over. This page is about recognizing them — not mastering them, just recognizing them — so the next time you open a test file, it reads like a sentence instead of a wall of symbols.

We'll use our own app as the example throughout this course: `rbac-healthcare-system`, a healthcare app with four roles — admin, doctor, nurse, and patient. Its backend runs at `http://localhost:5000` (with a Swagger page listing every API endpoint at `/api-docs`), and its frontend runs at `http://localhost:3002`. Keep those two addresses in your head — you'll see them constantly.

## The three types you'll see everywhere

TypeScript is JavaScript with labels attached to your data, saying "this is a piece of text" or "this is a number." Those labels are called **types**. Here are the three you'll run into almost immediately:

```typescript
const patientName: string = "Meera Nair";
const appointmentId: number = 4521;
const isUrgent: boolean = false;
```

Read that plain-English: `patientName` is a variable, it holds text (`string`), and its value is `"Meera Nair"`. `appointmentId` holds a number, and `isUrgent` holds a boolean — a fancy word for "true or false, nothing else."

The `: string`, `: number`, and `: boolean` bits are the type labels. They don't change what the code does — they're there so that if you (or your editor) ever try to put a number where a name should go, TypeScript stops you before the test even runs. Think of it as a second pair of eyes that never gets tired.

You'll also see this shorthand, where there's no explicit label at all:

```typescript
const patientName = "Meera Nair";
```

That's still fully typed — TypeScript looked at `"Meera Nair"` and figured out it's a `string` on its own. This is called **inference**, and it's why most code you read won't have `: string` written everywhere. The label is only spelled out when it isn't obvious, or when a test author wants to be extra clear.

## console.log() — your "check what's actually happening" tool

Before we go any further: meet `console.log()`. It prints whatever you put inside its parentheses to the screen when the file runs. That's it. That's the whole idea.

```typescript
const role: string = "nurse";
console.log(role);
```

Running this file prints `nurse` to your terminal. Why does this matter so early? Because from here on, in every module in this course, `console.log()` is how you check your own work. Not sure what a variable actually contains right now? Log it. Not sure if a value is `undefined` or the string `"undefined"`? Log it. Long before we get to running real automated checks with Jest, you can already run a plain TypeScript file yourself and see exactly what's inside it. That habit — "if in doubt, log it" — will save you more time than almost anything else in this course.

## Typed variables holding real values from our app

Here's a small typed variable that a test for our RBAC healthcare app might use to remember who is currently logged in:

```typescript
const currentRole: string = "doctor";
const isLoggedIn: boolean = true;
const activePatientId: number = 1042;

console.log(`${currentRole} is logged in: ${isLoggedIn}, viewing patient ${activePatientId}`);
```

That last line uses backticks and `${...}` to build one printed sentence out of several variables — you'll see this pattern (called a **template string**) constantly in test files whenever someone wants a readable log message or test name.

## What an interface looks like

A single typed variable is fine for one value. But a real patient, or a real user account, has several pieces of information that all belong together — a name, an id, a role. That's what an **interface** is for: a shape describing what an object should look like.

```typescript
interface Patient {
  id: number;
  name: string;
  role: "patient";
  isAdmitted: boolean;
}

const meera: Patient = {
  id: 1042,
  name: "Meera Nair",
  role: "patient",
  isAdmitted: false,
};

console.log(meera.name);
```

Read the `interface` block as a checklist: "anything I call a `Patient` must have an `id` that's a number, a `name` that's a string, a `role` that's exactly the word `patient`, and an `isAdmitted` that's true or false." Then `meera` is one real object that satisfies that checklist. If you tried to create a `Patient` without a `name`, or with `isAdmitted: "yes"` instead of `true`, TypeScript would flag it immediately — again, before anything even runs.

You'll see this exact pattern used for users and roles across our app too:

```typescript
type Role = "admin" | "doctor" | "nurse" | "patient";

interface User {
  id: number;
  name: string;
  role: Role;
}

const drShah: User = {
  id: 7,
  name: "Dr. Shah",
  role: "doctor",
};

console.log(`${drShah.name} logged in as ${drShah.role}`);
```

That `type Role = "admin" | "doctor" | "nurse" | "patient";` line is worth pausing on, because it's everywhere in this codebase. It says: "a `Role` can only ever be one of these four exact words — nothing else is allowed." If a test ever tries to set someone's role to `"guest"`, TypeScript rejects it on the spot, because `"guest"` isn't in that list. This is exactly how the real RBAC healthcare app keeps its four roles — admin, doctor, nurse, patient — from ever being typo'd or confused in a test.

That's genuinely most of what you need to recognize a test file on sight: a typed variable, an interface describing an object's shape, and `console.log()` used to check what's really there. Everything else in this course builds on exactly these three ideas.

## Try it

Create a new file called `scratch.ts` anywhere on your machine and write:

1. An `interface` called `Appointment` with three fields: `id` (a `number`), `patientName` (a `string`), and `isConfirmed` (a `boolean`).
2. One real `const` value matching that interface, using any patient name you like from our RBAC healthcare app (or make one up).
3. A `console.log()` line that prints a sentence using that appointment's `patientName` and whether it `isConfirmed`, using a template string like `` `${...} appointment confirmed: ${...}` ``.

Run the file (your editor or `npx ts-node scratch.ts` will do it) and confirm the sentence prints exactly what you expect. If it doesn't, that's `console.log()` already doing its job — telling you what your code actually contains, not what you assumed it contains.
