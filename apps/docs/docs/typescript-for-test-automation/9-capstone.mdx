You've made it to the last stop. No new syntax here — just you, taking everything you've learned about types, functions, and Jest, and pointing it at a real piece of a real application. Let's model a permission system.

## The system we're testing

`rbac-healthcare-system` is a small healthcare app with four roles: **admin**, **doctor**, **nurse**, and **patient**. Each role is allowed to do different things — admins can manage users, doctors can complete appointments, nurses can schedule them, and patients can only see their own records. That's the whole idea behind RBAC ("role-based access control," a gloss you've seen before in this app's docs): what a user is allowed to do depends entirely on which role they hold.

The app's own documentation spells out exactly who can do what, in this table:

| Action | Admin | Doctor | Nurse | Patient |
|---|---|---|---|---|
| View all users | Yes | No | No | No |
| Delete users | Yes | No | No | No |
| View all appointments | Yes | No | Yes | No |
| View own appointments | No | Yes | No | Yes |
| Schedule appointments | No | No | Yes | No |
| Complete appointments | No | Yes | No | No |
| Cancel appointments | No | Yes | Yes | No |
| Create medical records | No | Yes | No | No |
| View medical records | Yes | Yes | No | Yes (own only) |

As a manual tester, you've probably clicked through a table exactly like this one — logging in as each role, one at a time, checking whether a button is there or a page throws an error. That works, but it doesn't scale, and it's easy to miss a row when you're doing it by hand. Let's turn this table into something TypeScript can check for us.

## Step 1: model the roles

A role is one of exactly four strings, so a union type is the natural fit:

```typescript
type Role = "admin" | "doctor" | "nurse" | "patient";
```

Nothing new — you've written unions like this before. The payoff is the same as always: if you ever typo `"docter"` somewhere, TypeScript stops you before the test even runs.

## Step 2: model one row of the table

Every row in that table is really the same shape repeated: a role, an action, and whether that role is allowed to do it. An interface describes that shape:

```typescript
interface PermissionCase {
  role: Role;
  action: string;
  expected: boolean;
}
```

`expected` here means "what the table says should happen" — `true` for "Yes," `false` for "No." Keeping that as a plain boolean keeps the whole exercise simple: we're not testing the live app over the network, we're testing that our understanding of the rules (encoded as data) matches the rules our tests will eventually check against.

## Step 3: turn a few rows into data

You don't need to encode all nine rows to get the idea — a handful is enough to prove the pattern works. Let's take four rows straight from the table above:

```typescript
const permissionCases: PermissionCase[] = [
  { role: "admin", action: "View all users", expected: true },
  { role: "doctor", action: "View all users", expected: false },
  { role: "nurse", action: "Schedule appointments", expected: true },
  { role: "patient", action: "Delete users", expected: false },
];
```

Because `permissionCases` is typed as `PermissionCase[]`, TypeScript checks every object in that array against the shape you defined. Try changing `role: "admin"` to `role: "superadmin"` and your editor will complain immediately — that's the whole benefit of typing this data instead of leaving it as loose objects.

## Step 4: a tiny function that checks a permission

To make this actually testable, we need something to check a case against. In the real app, this logic would live in a permissions module and get called against a logged-in user. Here, to keep the focus on typing and testing rather than wiring up a server, we'll write a small stand-in function that looks up the answer the same way the table does:

```typescript
function hasPermission(role: Role, action: string): boolean {
  return permissionCases.some(
    (c) => c.role === role && c.action === action && c.expected
  );
}
```

This says: "search through our known cases, and return true only if we find a matching row where the expected result was true." It's a simplified stand-in for the real permission check the app would run against its own rules — but it's typed the same way, and it's enough to build a real Jest test around.

## Step 5: write the Jest test

Now for the payoff — a test that checks a role against the matrix, using `expect()` the way you've been practicing throughout this course:

```typescript
describe("RBAC permission matrix", () => {
  it("allows admin to view all users", () => {
    expect(hasPermission("admin", "View all users")).toBe(true);
  });

  it("does not allow doctor to view all users", () => {
    expect(hasPermission("doctor", "View all users")).toBe(false);
  });

  it("allows nurse to schedule appointments", () => {
    expect(hasPermission("nurse", "Schedule appointments")).toBe(true);
  });
});
```

Run that with your test runner and you'll see three green checkmarks — a small, typed, repeatable proof that your understanding of the permission table matches what the code expects. This is the same shape of test you'd eventually point at the real running app: instead of calling `hasPermission` against a local array, you'd call the app's actual API at `http://localhost:5000` and check the response. The types and the `expect()` assertions barely change — only where the data comes from does.

## Where to go from here

You started this course not knowing what a type annotation was, and you've ended it modeling a real permission system and asserting against it with Jest. That's a genuinely useful skill on its own — plenty of test automation work is exactly this: taking a rule that lives in a spec or a README, encoding it as typed data, and writing assertions that catch the day someone breaks it.

If you want to take these same typed-testing habits and point them at a real browser — clicking buttons, filling in forms, checking what actually renders on screen — this site's **[Playwright Test Automation](/docs/playwright-test-automation/)** course picks up right where this leaves off, using this same RBAC app as its running example.

And if you've enjoyed seeing TypeScript in action and want to go deeper into the language itself — generics, advanced types, the parts we only touched lightly here — **[Learn TypeScript](/docs/learn-typescript/)** on this site covers all of that in detail.

Either way, well done. You've built a real habit here, and it'll pay off every time you write a test from now on.

## Try it

Add a fifth case to `permissionCases` for the row **"View medical records" / patient / Yes (own only)** — treat "own only" as `true` for this exercise, since our simplified model doesn't yet distinguish "own" from "all." Then write one more `it()` block that asserts `hasPermission("patient", "View medical records")` is `true`. Once that passes, try adding a case that should be `false` (for example, nurse trying to create medical records) and write a test asserting that one fails the permission check too.
