When you call an API in a test, whatever comes back is just an unknown blob of data as far as TypeScript is concerned — unless you tell it what shape to expect. Once you do, your editor starts autocompleting property names for you, and TypeScript will flag it immediately if you typo `token` as `toekn` or try to use a number where a string should be. That's the whole point of this page: describing the *shape* of an API response so TypeScript can help you write correct assertions.

## Describing a response shape with an interface

You've already seen `interface` used to describe objects like a `TestUser`. You can use the exact same idea to describe what an API sends back. Here's the shape of the response from the RBAC healthcare system's login endpoint:

```typescript
interface LoginResponse {
  token: string;
}
```

That's it — the real login endpoint (`POST http://localhost:5000/api/auth/login`) responds with a small JSON object containing one field, `token`, which is a JWT (a long string that proves who you are on later requests). By writing this interface, you're telling TypeScript: "whenever I get a login response, expect an object with a `token` property that's a string." Nothing magical happens on the network because of this — the interface is purely a promise you make to TypeScript about the data's shape.

## Calling the real login endpoint

Node has a built-in `fetch` function, so you don't need to install anything extra to make an HTTP request. Here's a small helper function that logs in and returns a typed response:

```typescript
interface LoginResponse {
  token: string;
}

async function login(username: string, password: string): Promise<LoginResponse> {
  const response = await fetch("http://localhost:5000/api/auth/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, password }),
  });

  const data: LoginResponse = await response.json();
  return data;
}
```

Notice the `: Promise<LoginResponse>` on the function signature — that's saying "this function eventually gives you a `LoginResponse`, wrapped in a promise because it's asynchronous." The `data: LoginResponse` on the line above tells TypeScript to trust that whatever `response.json()` hands back matches that shape. From this point on, if you type `data.` in your editor, autocomplete will suggest `token` for you, and if you write `data.tokn`, TypeScript will underline it as an error before you ever run the test.

## Asserting on the typed response with Jest

Now let's use that typed `login` function in an actual Jest test, logging in as one of the seeded demo users:

```typescript
test("nurse1 logs in and receives a token", async () => {
  const result: LoginResponse = await login("nurse1", "nurse123");

  expect(typeof result.token).toBe("string");
  expect(result.token.length).toBeGreaterThan(0);
});
```

Because `result` is typed as `LoginResponse`, TypeScript already knows `result.token` exists and is a string — you're not guessing about the response shape, you're asserting against a contract you wrote down yourself. If the API ever changed and started returning `accessToken` instead of `token`, updating the `LoginResponse` interface would immediately surface every place in your test suite that needs updating, since TypeScript would complain about `result.token` no longer existing.

## Try it

Extend the `LoginResponse` interface and the test above for a different role. Log in as `admin` / `admin123` instead of `nurse1`, and write a Jest test that asserts `result.token` is a truthy string. Then, just to see TypeScript's help in action, try renaming `token` to `authToken` in the interface only (not in the `login` function) and notice how your editor immediately flags `result.token` as an error in the test — that's the type checker doing exactly the job you gave it.
