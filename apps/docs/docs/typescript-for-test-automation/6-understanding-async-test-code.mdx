You've probably already typed `async` and `await` into your test files without thinking too hard about them, just because an example told you to. Let's fix that. By the end of this page you'll know exactly why they're there and what would break without them.

## The problem: your code runs faster than the network

When your test calls the login API, the request has to travel to `http://localhost:5000`, the server has to check the username and password, and then a response has to travel back. That takes time — maybe 50 milliseconds, maybe 500. Your test code, on the other hand, runs almost instantly.

If you don't tell JavaScript to wait, it won't. It will fire off the login request and immediately move on to the next line, which is usually where you try to check the result. But the result isn't back yet — so you'd be checking something that doesn't exist.

`await` is the instruction that says "pause right here until this finishes, then give me the real answer." `async` is what makes a function allowed to use `await` inside it. They always travel together: if a function contains `await`, that function must be marked `async`.

## Seeing it without await first

Here's what happens if you call `fetch` but forget to `await` it:

```typescript
function loginBroken(username: string, password: string) {
  const result = fetch("http://localhost:5000/api/auth/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, password }),
  });

  console.log(result);
  return result;
}
```

Run that and `result` is not the login response at all. It's something called a **Promise** — a plain-English way to think of it is "a receipt for an answer that's still on its way." The receipt itself has no token, no username, nothing useful yet. You need to trade the receipt in for the real thing, and `await` is how you do that trade.

## Fixing it with async/await

```typescript
async function login(username: string, password: string): Promise<{ token: string }> {
  const response = await fetch("http://localhost:5000/api/auth/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, password }),
  });

  const data = await response.json();
  return data as { token: string };
}
```

Two `await`s show up here, and both matter for the same reason:

- `await fetch(...)` pauses until the server actually responds.
- `await response.json()` pauses until the response body has been fully read and parsed into an object.

Notice the function itself is declared `async function login(...)`. That's not decoration — it's required. TypeScript won't let you write `await` inside a function unless that function is `async`.

You'll also see the return type is `Promise<{ token: string }>` rather than just `{ token: string }`. That's TypeScript being honest with you: an `async` function always hands back a Promise (a receipt), even though the *value inside* that Promise is the typed object you actually care about. Anyone calling `login()` will need their own `await` to unwrap it.

## Putting it together in a Jest test

This is the pattern you'll use constantly: an `async` test function, an `await`ed call to `login`, and then assertions on the real, resolved result.

```typescript
test("nurse1 can log in and receive a token", async () => {
  const result: { token: string } = await login("nurse1", "nurse123");

  expect(result.token).toBeTruthy();
  expect(typeof result.token).toBe("string");
});
```

Walk through why every `async`/`await` is where it is:

- The test callback is `async () => { ... }` because it contains `await` inside it — without `async`, that `await` would be a syntax error.
- `await login("nurse1", "nurse123")` pauses until `login` itself has finished — which, remember, has its own `await`s inside it pausing for the network round trip and the JSON parsing.
- Only once that whole chain has settled does `result` hold the real, typed `{ token: string }` object instead of a receipt for one.

Only after both of those `await`s have finished do the `expect()` lines run. That ordering is exactly the point — you're checking the token *after* it exists, never before.

## What if you forget `await`?

If you wrote `const body = response.json();` without `await`, `body` would be a Promise, not an object. `body.token` would then be `undefined`, because you'd be reaching into the receipt instead of the answer. Your assertion would fail — but the confusing part is it fails for a reason that has nothing to do with your login logic being wrong. Forgetting `await` is one of the most common causes of tests that fail with strange, seemingly unrelated errors, so it's worth checking first whenever a result looks unexpectedly empty.

## Try it

Write a small async function called `getPatientCount` that:

1. Is declared `async` and returns `Promise<number>`.
2. Sends a `GET` request to `http://localhost:5000/api/patients/count` using `fetch` (you can imagine this endpoint exists for the exercise).
3. Awaits the response, awaits `.json()`, and returns the `count` field as a number.

Then write a one-line Jest test that calls `await getPatientCount()` and uses `expect(...).toBeGreaterThanOrEqual(0)` on the result. The goal isn't the healthcare logic — it's noticing where each `await` has to go, and why the test function itself needs `async` in front of it.
