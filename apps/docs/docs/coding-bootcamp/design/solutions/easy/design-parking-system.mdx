# Design Parking System — Solution

## Problem Overview

Design a class tracking available big/medium/small parking spaces, with an `addCar` method that parks a car of a given type if space remains, decrementing the count and returning whether it succeeded.

## Brute Force Approach

There isn't a separate "brute force" for this problem — it's a design/state-tracking exercise, not an algorithmic one. The direct approach (three counters, checked and decremented on each call) **is** the optimal solution.

## Optimal Approach: Three Counters, Indexed by Car Type

**Idea:** Store the three capacity counts (indexed by car type `1`, `2`, `3`) at construction time. Each `addCar` call is just: check whether the relevant counter is positive, and if so decrement it and return `true`; otherwise return `false`.

**Algorithm:**
1. In the constructor, store `big`, `medium`, and `small` — either as three named fields, or as a single array/map indexed by car type (avoiding an `if`/`else if`/`else` chain in `addCar`).
2. In `addCar(carType)`: if the count for `carType` is greater than `0`, decrement it and return `true`; otherwise return `false`.

**Why This Works:** The problem is entirely captured by "how many spaces of each type are currently free" — there's no interaction between space types (a big car can't use a medium or small space), so three independent counters fully model the system. Each `addCar` call is O(1): a single comparison and, on success, a single decrement.

**Complexity Analysis:**
- **Time:** O(1) per `addCar` call.
- **Space:** O(1) — three integers, regardless of how many cars are processed.

## Deep Dive

### Visual Walkthrough

For `ParkingSystem(1, 1, 0)`:

```
counts: {1: 1, 2: 1, 3: 0}

addCar(1): counts[1] == 1 > 0 -> park, counts[1] -= 1 -> counts = {1:0, 2:1, 3:0} -> true
addCar(2): counts[2] == 1 > 0 -> park, counts[2] -= 1 -> counts = {1:0, 2:0, 3:0} -> true
addCar(3): counts[3] == 0     -> no space                                        -> false
addCar(1): counts[1] == 0     -> no space (already parked earlier)               -> false
```

### Edge Cases to Consider

- **A capacity of `0` for some type from the start**: every `addCar` call for that type returns `false` immediately, with nothing to decrement — no special-casing needed since the check `count > 0` already handles a starting value of `0` correctly.
- **All capacities `0`**: every single call returns `false` — the class still behaves correctly with no spaces to manage.
- **Repeated calls for the same type after it's exhausted**: once a counter hits `0`, it simply stays `0` forever (never decremented below `0`), so every subsequent call for that type correctly keeps returning `false`.
- **Interleaved car types**: since each type has its own independent counter, calls for different types never affect each other — order doesn't matter across types, only the count of calls *per type*.

## Key Takeaways

- Not every "design" problem needs a clever algorithm — sometimes the design *is* the answer: pick the right small piece of state (three counters here) and the operations fall out directly.
- Indexing counts by the car-type integer itself (`counts[1]`, `counts[2]`, `counts[3]`, with index `0` left unused) avoids an `if`/`else if`/`else` chain and keeps `addCar` a single array lookup, at the minor cost of one wasted array slot.
- Every operation here is O(1) — there's no data structure choice that would meaningfully improve on three plain integers.
