# Count Operations to Obtain Zero — Solution

## Problem Overview

Given two non-negative integers, repeatedly subtract the smaller from the larger until either becomes zero. Count how many subtractions that takes.

## Brute Force Approach

**Idea:** Simulate exactly what the problem describes — loop while both numbers are nonzero, subtract the smaller from the larger each time, and count the iterations.

**Complexity Analysis:**
- **Time:** O(max(num1, num2)) — in the worst case (e.g. `num1 = 1`, `num2 = 100000`), one unit is subtracted per operation.
- **Space:** O(1).

## Optimal Approach: Batch the Subtractions with Division (GCD-style)

**Idea:** When one number is much larger than the other, the naive simulation repeats the *same* subtraction (of the smaller number) over and over until the roles swap — that's exactly what integer division computes in one step. Instead of subtracting one at a time, figure out how many times the smaller number fits into the larger, add that many operations at once, and reduce the larger number to its remainder — the same reduction Euclid's GCD algorithm uses.

**Algorithm:**
1. While both `num1` and `num2` are nonzero:
   - If `num1 >= num2`: this operation would repeat `num1 // num2` times before `num1` drops below `num2` — add `num1 // num2` to the count, and set `num1 = num1 % num2`.
   - Otherwise: symmetrically, add `num2 // num1` to the count, and set `num2 = num2 % num1`.
2. Return the count.

**Why This Works:** Repeatedly subtracting `num2` from `num1` while `num1 >= num2` is exactly what `num1 // num2` (the count) and `num1 % num2` (the result) compute directly — the loop would perform precisely `num1 // num2` subtractions before `num1` first becomes less than `num2`, landing on the value `num1 % num2`. Applying this shortcut whenever one number is temporarily the larger one collapses what could be many single-unit subtractions into one division, without changing the final operation count.

**Complexity Analysis:**
- **Time:** O(log(min(num1, num2))) — the same logarithmic bound as the Euclidean GCD algorithm, since each step at least halves the smaller of the two values (a well-known property of the mod operation in this recurrence).
- **Space:** O(1).

## Deep Dive

### Visual Walkthrough

For `num1 = 20`, `num2 = 4`:

```
20 >= 4: count += 20 // 4 = 5  -> count = 5
         num1 = 20 % 4 = 0

num1 is now 0 -- loop ends

total operations = 5
```

Compare to the naive simulation, which would take 5 individual iterations (20→16→12→8→4→0) — the batched version computes the same total in a single division.

For `num1 = 2`, `num2 = 3` (the case where neither number is a multiple of the other):

```
2 < 3: count += 3 // 2 = 1  -> count = 1
       num2 = 3 % 2 = 1
now (num1=2, num2=1)

2 >= 1: count += 2 // 1 = 2  -> count = 3
        num1 = 2 % 1 = 0

num1 is now 0 -- loop ends

total operations = 3
```

### Edge Cases to Consider

- **Either number starts at zero**: the `while` condition is false immediately, so the loop never runs — `0` operations, matching the problem's implicit rule that no subtraction is needed if one side is already zero.
- **Equal numbers** (e.g. `num1 = num2 = 50`): one division gives `50 // 50 = 1` operation, reducing to `50 % 50 = 0` immediately — matches the naive simulation's single subtraction to zero.
- **One number is exactly a multiple of the other** (e.g. `100` and `1`): the division computes the full count (`100`) in one step, rather than iterating 100 times.
- **Neither number divides the other evenly**: the algorithm still terminates correctly, alternating which side gets reduced via its modulo, exactly mirroring how Euclid's algorithm always terminates.

def count_operations(num1: int, num2: int) -> int:
    count = 0
    while num1 != 0 and num2 != 0:
        if num1 >= num2:
            count += num1 // num2
            num1 %= num2
        else:
            count += num2 // num1
            num2 %= num1
    return count

## Key Takeaways

- Whenever a simulation repeats the *same* operation many times in a row, check whether integer division can compute "how many times" and the resulting remainder in one step — this is a common way to turn an O(n) simulation into an O(log n) one.
- This is structurally identical to the Euclidean algorithm for GCD, just also tracking a running count of the division steps rather than only the final remainder.
- The naive one-at-a-time simulation is still a perfectly valid, simpler-to-write answer when the input size doesn't demand the optimization — worth having as a first correct solution before reaching for the batched version.
