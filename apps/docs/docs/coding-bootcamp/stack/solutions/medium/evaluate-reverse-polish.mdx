# Evaluate Reverse Polish Notation — Solution

## Problem Overview

Given an arithmetic expression written in Reverse Polish (postfix) Notation as a list of tokens, evaluate it to a single integer.

## Brute Force Approach

There isn't a meaningfully different "brute force" here — RPN was specifically designed to be evaluated with a stack in a single linear pass, and that pass **is** the optimal approach. The only alternative would be converting to infix and using an expression parser, which is strictly more work for the same result.

## Optimal Approach: Stack Evaluation

**Idea:** Scan the tokens left to right. Push every number onto a stack. When an operator is encountered, pop the top two values off the stack, apply the operator, and push the result back on. By the time the scan finishes, exactly one value remains on the stack — the final answer.

**Algorithm:**
1. For each token:
   - If it's a number, push it onto the stack.
   - If it's an operator (`+`, `-`, `*`, `/`), pop the top two values — call them `b` (popped first) and `a` (popped second) — compute `a <op> b`, and push the result.
2. After processing every token, the stack holds exactly one value — return it.

**Why This Works:** Reverse Polish Notation is constructed so that by the time you encounter an operator, both of its operands have already appeared earlier in the token stream — a stack is exactly the right structure to hold "operands seen so far, waiting to be combined." Since RPN has no parentheses and no precedence rules to resolve (the token order *is* the evaluation order), no lookahead or precedence handling is ever needed.

**Complexity Analysis:**
- **Time:** O(n) — one pass over the tokens, each pushed and popped at most once.
- **Space:** O(n) — the stack, worst case holding every number token if operators are clustered at the end.

## Deep Dive

### Visual Walkthrough

For `tokens = ["2", "1", "+", "3", "*"]`:

```
token '2': push 2          stack: [2]
token '1': push 1          stack: [2, 1]
token '+': pop 1 (b), pop 2 (a) -> 2 + 1 = 3, push 3
                            stack: [3]
token '3': push 3          stack: [3, 3]
token '*': pop 3 (b), pop 3 (a) -> 3 * 3 = 9, push 9
                            stack: [9]

final stack: [9] -> answer 9
```

### Edge Cases to Consider

- **Operand order for `-` and `/`**: the value popped *first* is the right-hand operand (`b`), and the value popped *second* is the left-hand operand (`a`) — the expression is `a <op> b`, not `b <op> a`. Getting this backwards silently produces the wrong sign/magnitude for every subtraction and division.
- **Negative number tokens** (e.g. `"-11"`, `"-3"`): these are single tokens representing a negative literal, not a `-` operator applied to something — parsing must distinguish "is this token exactly `+`, `-`, `*`, or `/`" from "does this token merely *start* with a `-` sign".
- **Division truncates toward zero, not floor**: `6 / -2` should give `-3` (which happens to agree with floor division here), but a case like `-7 / 2` gives `-3` under truncation vs. `-4` under floor division — the two disagree whenever the division isn't exact and the result is negative. Python especially needs to avoid its native `//` operator for this reason.
- **A deeply nested expression** (e.g. the 13-token example): the stack naturally handles arbitrary nesting depth without any special-casing — each `+`/`-`/`*`/`/` just resolves whatever is currently on top.

def evaluate_rpn(tokens: list) -> int:
    stack = []
    for tok in tokens:
        if tok in ('+', '-', '*', '/'):
            b = stack.pop()
            a = stack.pop()
            if tok == '+':
                stack.append(a + b)
            elif tok == '-':
                stack.append(a - b)
            elif tok == '*':
                stack.append(a * b)
            else:
                stack.append(int(a / b))   # truncate toward zero, not floor (//)
        else:
            stack.append(int(tok))
    return stack[-1]

class Solution {
    public int evalRPN(String[] tokens) {
        Deque<Integer> stack = new ArrayDeque<>();
        for (String tok : tokens) {
            if (tok.equals("+") || tok.equals("-") || tok.equals("*") || tok.equals("/")) {
                int b = stack.pop();
                int a = stack.pop();
                switch (tok) {
                    case "+": stack.push(a + b); break;
                    case "-": stack.push(a - b); break;
                    case "*": stack.push(a * b); break;
                    default:  stack.push(a / b); break;  // Java int division truncates toward zero
                }
            } else {
                stack.push(Integer.parseInt(tok));
            }
        }
        return stack.pop();
    }
}

fn eval_rpn(tokens: &[&str]) -> i64 {

int evalRPN(char** tokens, int tokensSize) {

func evalRPN(tokens []string) int {

                result = a - b

                result = a * b

## Key Takeaways

- A stack is the natural fit for RPN evaluation because postfix notation guarantees both operands of any operator have already been seen — no precedence rules or parentheses to resolve, unlike infix expressions.
- Operand order matters for non-commutative operators: the value popped first is always the *right*-hand operand, the value popped second is the *left*-hand operand.
- Most compiled/statically-typed languages (Java, C++, C, C#, Rust, Go) already truncate integer division toward zero by default — the real risk is in dynamically-typed or floating-point-native languages (Python's `//` floors instead of truncating; JavaScript/TypeScript need an explicit `Math.trunc`).
