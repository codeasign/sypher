# Remove Covered Intervals — Solution

## Problem Overview

Given a list of intervals, count how many remain after removing every interval that's fully covered by another (`[a,b]` is covered by `[c,d]` when `c <= a` and `b <= d`).

## Brute Force Approach

**Idea:** For every interval, check every *other* interval to see if it covers it.

**Complexity Analysis:**
- **Time:** O(n²) — a pairwise comparison for every interval.
- **Space:** O(1) extra.

## Optimal Approach: Sort, Then Track the Running Max End

**Idea:** Sort intervals by start ascending, breaking ties by end **descending**. Then scan left to right, tracking the largest end value seen so far among intervals *kept*. An interval is covered exactly when its end doesn't exceed that running maximum — because sorting guarantees that any interval which could possibly cover the current one has already been seen.

**Algorithm:**
1. Sort intervals by `(start, -end)` — ascending start, and for ties, descending end.
2. Track `maxEnd = 0` and a `count` of kept intervals.
3. For each interval `[a, b]` in sorted order: if `b > maxEnd`, this interval is *not* covered by anything seen so far — keep it (`count += 1`, `maxEnd = b`). Otherwise, it's covered — skip it.
4. Return `count`.

**Why This Works:** After sorting by start ascending, any interval that could cover the current one must have a start `<= ` the current interval's start — which, given the sort order, means it was already processed. Among all intervals processed so far with an equal-or-earlier start, `maxEnd` is the largest end reached — so if the current interval's end doesn't exceed `maxEnd`, *some* earlier interval both starts no later and ends no earlier, which is exactly the covering condition. The tie-break (`-end` for equal starts) matters because among intervals that share the same start, the one with the largest end must be processed *first* so its `maxEnd` is in place before evaluating the shorter ones sharing that same start — otherwise a same-start-smaller-end interval could be wrongly counted as kept before its coverer is seen.

**Complexity Analysis:**
- **Time:** O(n log n) — dominated by the sort; the scan itself is O(n).
- **Space:** O(n) or O(log n) depending on the sort implementation's overhead, plus O(1) extra for the scan.

## Deep Dive

### Visual Walkthrough

For `intervals = [[1,4],[3,6],[2,8]]`:

```
sorted by (start asc, end desc): [1,4], [2,8], [3,6]

[1,4]: 4 > maxEnd(0)  -> keep, count=1, maxEnd=4
[2,8]: 8 > maxEnd(4)  -> keep, count=2, maxEnd=8
[3,6]: 6 <= maxEnd(8) -> covered (by [2,8], since 2<=3 and 6<=8) -> skip

count = 2
```

### Edge Cases to Consider

- **Identical intervals repeated** (e.g. `[[1,5],[1,5],[1,5]]`): after sorting, the first is kept (`maxEnd` becomes `5`); every subsequent identical copy has `end == maxEnd`, which is `not > maxEnd`, so it's correctly treated as covered (an interval trivially "covers" an exact duplicate of itself).
- **Same start, different ends** (e.g. `[[1,2],[1,4],[3,4],[1,6]]`): the descending-end tiebreak ensures `[1,6]` is processed before `[1,2]` and `[1,4]` (all sharing start `1`), so `maxEnd` is already `6` by the time the shorter ones are checked — both get correctly marked covered.
- **No interval covers any other** (e.g. disjoint intervals like `[[1,2],[3,4],[5,6]]`): every interval's end exceeds the running max at the point it's checked, so all are kept — `count` equals the input length.
- **A single interval**: trivially kept, `count = 1`, since there's nothing else that could cover it.

## Key Takeaways

- Sorting by start ascending guarantees every potential "coverer" of the current interval has already been processed by the time you reach it — turning an O(n²) pairwise check into an O(n) scan after the sort.
- The descending-end tiebreak for equal starts is the detail that makes this correct, not just fast — without it, a same-start shorter interval could be counted as "kept" before the longer one that actually covers it is even seen.
- Tracking a single running maximum (`maxEnd`) is sufficient because coverage only depends on the *widest* interval seen so far — no need to remember every previously-kept interval individually.
