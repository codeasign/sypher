# Search Suggestions System — Solution

## Problem Overview

Given a list of products and a search word, return up to 3 lexicographically-smallest products sharing each successive prefix of the search word (as it's typed character by character).

## Brute Force Approach

**Idea:** For each prefix of the search word, scan the *entire* product list, filter to the ones starting with that prefix, sort the matches, and take the first 3.

**Complexity Analysis:**
- **Time:** O(k × n log n), where `k` is the search word's length and `n` is the number of products — a fresh filter-and-sort for every single prefix.
- **Space:** O(n) per prefix for the filtered/sorted list.

## Optimal Approach: Sort Once, Binary Search Per Prefix

**Idea:** Sort the products **once**, up front. Because the list is sorted, every group of products sharing a given prefix occupies a single *contiguous* block — so instead of re-filtering the whole list for every prefix, binary search for where that block starts, then just read off up to 3 entries from there (stopping early the moment an entry no longer matches the prefix).

**Algorithm:**
1. Sort `products` lexicographically, once.
2. For each prefix length `i` from `1` to `len(searchWord)` (building the prefix incrementally):
   - Binary search the sorted list for the first index where `products[index] >= prefix` (the standard "lower bound" search).
   - From that index, collect up to 3 consecutive products that still start with the prefix — stop as soon as one doesn't (since the block is contiguous, that means there are no more).
   - Append that (possibly-empty) list of up to 3 products to the result.
3. Return the result.

**Why This Works:** Sorting groups every prefix's matches into one contiguous run — this is exactly the same property that makes binary search applicable to "find where values matching X begin" in a sorted array. Since sorting only needs to happen once, and each subsequent binary search is O(log n), the total cost collapses from `O(k × n log n)` to `O(n log n + k log n)` — the one-time sort plus one binary search per prefix character.

**Complexity Analysis:**
- **Time:** O(n log n) for the sort, plus O(k log n) for the binary searches (`k` = search word length) — the per-prefix scan afterward is O(1) since it's capped at 3 items.
- **Space:** O(n) for the sorted copy of `products`; O(k) for the result.

### Edge Cases to Consider

- **No product matches a prefix at all** (e.g. `searchWord = "abc"` against `products = ["xyz"]`): the binary search lands at whatever index the prefix *would* be inserted at, but the entry there (if any) doesn't actually start with the prefix — the collection step immediately stops, yielding an empty list for every character.
- **A shorter product that's itself a prefix of a longer one** (e.g. `"zoo"` and `"zoom"`): sorting correctly places the shorter one first (`"zoo" < "zoom"` lexicographically, since a proper prefix always sorts before its extensions) — this is easy to get backwards by hand but falls out correctly from any standard string comparison.
- **All products match every prefix** (e.g. `products = ["havana"]`, `searchWord = "havana"`): every prefix step returns the same single-element list.
- **More than 3 matches for a short prefix, narrowing to fewer as the prefix grows**: the binary search index shifts forward (or the surrounding matches fall away) as the prefix lengthens, naturally shrinking the match count without any extra bookkeeping.

import bisect

def search_suggestions(products: list, search_word: str) -> list:
    products = sorted(products)
    result = []
    prefix = ""
    for ch in search_word:
        prefix += ch
        idx = bisect.bisect_left(products, prefix)
        matches = []
        for i in range(idx, min(idx + 3, len(products))):
            if products[i].startswith(prefix):
                matches.append(products[i])
            else:
                break
        result.append(matches)
    return result

class Solution {
    public List<List<String>> suggestedProducts(String[] products, String searchWord) {
        Arrays.sort(products);
        List<List<String>> result = new ArrayList<>();
        StringBuilder prefix = new StringBuilder();
        for (char ch : searchWord.toCharArray()) {
            prefix.append(ch);
            String p = prefix.toString();
            int idx = lowerBound(products, p);
            List<String> matches = new ArrayList<>();
            for (int i = idx; i < Math.min(idx + 3, products.length); i++) {
                if (products[i].startsWith(p)) matches.add(products[i]);
                else break;
            }
            result.add(matches);
        }
        return result;
    }

    private int lowerBound(String[] arr, String target) {
        int lo = 0, hi = arr.length;
        while (lo < hi) {
            int mid = (lo + hi) / 2;
            if (arr[mid].compareTo(target) < 0) lo = mid + 1;
            else hi = mid;
        }
        return lo;
    }
}

                matches.push(products[i].clone());
            } else {
                break;
            }
        }
        result.push(matches);
    }

## Key Takeaways

- Sorting once and binary-searching per prefix is a big win over re-filtering the full list for every prefix — the sort is the one-time cost, and each subsequent lookup is logarithmic.
- Because the product list is sorted, all matches for a given prefix are guaranteed contiguous — this is precisely the property that makes "binary search for the start, then scan a few forward" both correct and cheap.
- A common subtlety: a shorter string that's a prefix of a longer one (`"zoo"` vs `"zoom"`) always sorts *before* its longer extension — worth double-checking by hand when authoring test data for this kind of problem, since it's an easy detail to get backwards.
