# Reverse Integer — Solution

## Problem Overview

Reverse the digits of a signed 32-bit integer. If the reversed value falls outside `[-2^31, 2^31 - 1]`, return `0` instead.

## Brute Force Approach

Convert the number to a string, reverse it, parse it back to an integer, then check whether the result fits in a signed 32-bit range. This is straightforward in a language with arbitrary-precision integers (Python) or where numbers don't silently wrap on overflow (JavaScript's doubles), but is risky to port directly to a language with true fixed-width integers — parsing a reversed string back into a 32-bit `int` can itself overflow *during* the parse, before you ever get the chance to check the bound.

**Complexity Analysis:**
- **Time:** O(d), where `d` is the number of digits.
- **Space:** O(d) for the string.

## Optimal Approach: Digit-by-Digit with a Pre-Multiply Overflow Check

**Idea:** Build the reversed number one digit at a time, purely with integer arithmetic — no strings, no intermediate value ever needs to be wider than a 32-bit int. The key trick: check *before* each `result * 10 + digit` step whether it's about to overflow, rather than computing it and checking after (by which point the overflow has already happened and the value is corrupted).

**Algorithm:**
1. `result = 0`.
2. While `x != 0`:
   - `digit = x % 10` (in a language with truncating integer division/modulo, this correctly produces a *negative* digit when `x` is negative — no separate sign-handling needed).
   - `x = x / 10` (truncating toward zero).
   - Before folding `digit` in, check the boundary: if `result > INT_MAX / 10`, **or** `result == INT_MAX / 10` and `digit > 7`, the next step would overflow past `INT_MAX` — return `0`. Symmetrically, if `result < INT_MIN / 10`, **or** `result == INT_MIN / 10` and `digit < -8`, it would underflow past `INT_MIN` — return `0`.
   - `result = result * 10 + digit`.
3. Return `result`.

**Why This Works:** `x % 10` and `x / 10` with **truncating** semantics (the default in Java, C++, C, C#, Rust, and Go — the exact behavior Python's `%`/`//` do *not* have, which is why Python's solution below takes a different, string-based route) correctly peel digits off from both positive and negative numbers without needing to special-case the sign. `INT_MAX / 10` and `INT_MIN / 10` are each safe to compute on their own (no addition or subtraction involved) — the trap to avoid is trying to fold `digit` into that division directly (`(INT_MIN - digit) / 10`), since `INT_MIN` minus a *positive* `digit` overflows past the representable range before the division even happens. Comparing `digit` against the fixed boundary values `7`/`-8` separately, only in the case where `result` already equals the divided bound exactly, sidesteps that trap entirely — `7` and `-8` come from `INT_MAX % 10` and `INT_MIN % 10`, the last digit of the boundary values themselves.

**Complexity Analysis:**
- **Time:** O(d), where `d` is the number of digits (at most 10 for a 32-bit int).
- **Space:** O(1) — a handful of integer variables, no string allocation.

## Deep Dive

### Visual Walkthrough

For `x = -1563847412` (the "just barely overflows" case):

```
digits peeled (in order): -2, -1, -4, -7, -4, -8, -3, -6, -5, -1
running result: -2, -21, -214, -2147, -21474, -214748, -2147483,
                -21474836, -214748365, then...

Last step: result = -214748365, digit = -1, about to fold in -1
Check: result < INT_MIN / 10
     = -214748365 < -214748364
     TRUE -- would underflow -- return 0
```

The true mathematical reversal is `-2147483651`, which is just 4 past `INT_MIN` (`-2147483648`) — the overflow check catches it on the very last digit, before the corrupting multiply ever happens.

### Edge Cases to Consider

- **Palindromic numbers** (e.g. `2147447412`): reverse exactly to themselves — a useful sanity check that the algorithm doesn't accidentally alter a value that's already its own reverse.
- **Trailing zeros** (e.g. `120 -> 21`): dropped automatically, since leading zeros in the *reversed* digit sequence just don't get multiplied back in — there's no explicit zero-stripping step needed.
- **Overflow by a wide margin** (e.g. `1534236469 -> 9646324351`, far past `INT_MAX`) vs. **overflow by a razor-thin margin** (`-1563847412 -> -2147483651`, just 4 past `INT_MIN`) — both must be caught by the same check; test data should include both, not just the obvious wide-margin case.
- **`x = 0`**: the loop never executes, `result` stays `0`.

class Solution {
    public int reverse(int x) {
        int result = 0;
        while (x != 0) {
            int digit = x % 10;                             // truncates toward zero
            x /= 10;
            // MAX_VALUE/MIN_VALUE divided by 10 first, then the exact boundary
            // checked separately -- MIN_VALUE - digit would itself overflow if
            // computed directly, so it's never computed that way.
            if (result > Integer.MAX_VALUE / 10 || (result == Integer.MAX_VALUE / 10 && digit > 7)) return 0;
            if (result < Integer.MIN_VALUE / 10 || (result == Integer.MIN_VALUE / 10 && digit < -8)) return 0;
            result = result * 10 + digit;
        }
        return result;
    }
}

fn reverse(x: i32) -> i32 {
    let mut x = x;
    let mut result: i32 = 0;
    while x != 0 {
        let digit = x % 10;                     // truncates toward zero
        x /= 10;
        // checked_mul/checked_add return None on overflow instead of
        // panicking or wrapping -- no manual MAX/MIN bound math needed.
        result = match result.checked_mul(10).and_then(|r| r.checked_add(digit)) {
            Some(v) => v,
            None => return 0,
        };
    }
    result
}

## Key Takeaways

- The universal trick for "detect overflow before it happens" is to check `result` against `MAX / 10` (a division only, always safe) and handle the exact-boundary case separately by comparing `digit` to a fixed constant — resist the temptation to fold `digit` into the bound itself (`(MAX - digit) / 10` or `(MIN - digit) / 10`), since computing `MIN - digit` for a positive `digit` overflows the exact same way the thing you're trying to prevent does.
- Truncating integer division/modulo (the default in most fixed-width-integer languages) naturally handles negative numbers digit-by-digit without any separate sign-handling branch — this is *not* how Python's `%`/`//` behave, which is why Python's solution takes the string-based route instead.
- Rust's `checked_mul`/`checked_add` sidestep the whole "compute the bound manually" problem entirely — they return `None` exactly when the fixed-width operation would have overflowed, letting the overflow check *be* the arithmetic instead of a separate manual comparison.
- Always test both "overflows by a lot" and "overflows by the smallest possible margin" cases — the second is a much more effective test of whether the check is actually correct, not just approximately right.
