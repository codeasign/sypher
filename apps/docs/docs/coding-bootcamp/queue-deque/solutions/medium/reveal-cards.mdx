# Reveal Cards in Increasing Order — Solution

## Problem Overview

Rearrange a deck of cards so that repeatedly revealing the top card and moving the next card to the bottom produces the cards in increasing order.

## Brute Force Approach

**Idea:** Try every permutation of the deck, run the reveal simulation on each, and check whether it produces an increasing sequence. This is factorial time and completely impractical — there's no reason to pursue it once the queue-simulation insight (below) is available.

**Complexity Analysis:**
- **Time:** O(n! × n) — not viable.
- **Space:** O(n).

## Optimal Approach: Simulate the Reveal Process on Indices, Not Cards

**Idea:** Run the *reveal process itself* — but instead of running it on actual card values, run it on the **positions** `0, 1, ..., n-1` in a queue. Each time the simulation would "reveal" a position, that position is where the *next-smallest* remaining card value belongs. Since the reveal order of positions doesn't depend on what values end up there, this can be computed once, independently of the actual card values — then the smallest card goes to the first revealed position, the second-smallest to the second revealed position, and so on.

**Algorithm:**
1. Sort the deck's values in increasing order.
2. Create a queue containing every index `0` through `n-1`, in order.
3. For each value in the sorted list (smallest first):
   - Pop the front index off the queue — that's where this value belongs in the result.
   - If the queue still has entries, pop the new front and push it to the back (simulating "move the next card to the bottom").
4. Return the result array.

**Why This Works:** The reveal-and-rotate process is a fixed, deterministic sequence of position visits that has nothing to do with what values are written at those positions — it's purely a function of `n`. Running it once on plain indices tells you exactly *which* original position will be revealed 1st, 2nd, 3rd, etc. Assigning the sorted values to those positions in that same order guarantees the reveal sequence comes out sorted, because "1st revealed position gets the smallest value, 2nd revealed position gets the 2nd-smallest," and so on, by construction.

**Complexity Analysis:**
- **Time:** O(n log n) — dominated by the sort; the queue simulation itself is O(n).
- **Space:** O(n) for the queue and result array.

## Deep Dive

### Visual Walkthrough

For `deck = [17, 13, 11, 2, 3, 5, 7]` (n = 7):

```
sorted values: 2, 3, 5, 7, 11, 13, 17
index queue:   [0, 1, 2, 3, 4, 5, 6]

value 2  -> pop index 0 -> result[0]=2.  rotate: pop 1, push to back -> queue [2,3,4,5,6,1]
value 3  -> pop index 2 -> result[2]=3.  rotate: pop 3, push to back -> queue [4,5,6,1,3]
value 5  -> pop index 4 -> result[4]=5.  rotate: pop 5, push to back -> queue [6,1,3,5]
value 7  -> pop index 6 -> result[6]=7.  rotate: pop 1, push to back -> queue [3,5,1]
value 11 -> pop index 3 -> result[3]=11. rotate: pop 5, push to back -> queue [1,5]
value 13 -> pop index 1 -> result[1]=13. rotate: pop 5, push to back -> queue [5]
value 17 -> pop index 5 -> result[5]=17. queue now empty, no rotation

result: [2, 13, 3, 11, 5, 17, 7]
```

Revealing this deck: 2, then rotate 13 to the bottom; 3, then rotate 11 to the bottom; 5, then rotate 17 to the bottom; 7 — giving `2, 3, 5, 7, 11, 13, 17`, sorted.

### Edge Cases to Consider

- **Single card**: the index queue has only `[0]`; the one sorted value goes straight to position `0`, no rotation ever happens.
- **Two cards**: the first (smaller) value takes index `0`; the queue then rotates its remaining single index (`1`) to the back of itself (a no-op for a length-1 queue), and the second value takes index `1` — the deck ends up unchanged from sorted order, matching the reveal process's behavior for `n = 2`.
- **Already-sorted input**: the algorithm doesn't shortcut anything by noticing this — it still runs the full simulation, and (for `n <= 2`) can produce output identical to the sorted input, or for larger `n`, still needs the interleaved rearrangement despite the input coincidentally already being sorted.

```python
from collections import deque

def reveal_cards(deck: list) -> list:
    n = len(deck)
    sorted_deck = sorted(deck)
    result = [0] * n
    index_queue = deque(range(n))
    for card in sorted_deck:
        idx = index_queue.popleft()
        result[idx] = card
        if index_queue:
            index_queue.append(index_queue.popleft())
    return result
```

```c
int revealCmp(const void* a, const void* b) { return *(int*)a - *(int*)b; }

// A circular buffer of size deckSize: front/count track the current queue
// window (never grows past deckSize slots -- a naive "just keep appending"
// array without wraparound overflows its allocation once rotations exceed
// the initial size).
void deckRevealedIncreasing(int* deck, int deckSize, int* result) {
    int* sorted = (int*)malloc(deckSize * sizeof(int));
    memcpy(sorted, deck, deckSize * sizeof(int));
    qsort(sorted, deckSize, sizeof(int), revealCmp);

    int* indexQueue = (int*)malloc(deckSize * sizeof(int));
    for (int i = 0; i < deckSize; i++) indexQueue[i] = i;
    int front = 0, count = deckSize;

    for (int k = 0; k < deckSize; k++) {
        int idx = indexQueue[front];
        front = (front + 1) % deckSize;
        count--;
        result[idx] = sorted[k];
        if (count > 0) {
            int next = indexQueue[front];
            front = (front + 1) % deckSize;
            count--;
            int backPos = (front + count) % deckSize;
            indexQueue[backPos] = next;
            count++;
        }
    }
    free(sorted);
    free(indexQueue);
}
```

```csharp
class Solution {

        Array.Sort(sorted);

        for (int i = 0; i < n; i++) indexQueue.Enqueue(i);

            result[idx] = card;

            }
        }
```

## Key Takeaways

- The key trick is decoupling "which positions get revealed in what order" (a pure function of `n`, computable on plain indices) from "which values go where" (just assign the sorted values in that same order) — this turns a seemingly stateful simulation problem into sort-plus-one-linear-pass.
- Simulating the *rule* (reveal one, rotate one) on index placeholders instead of the real data is a reusable pattern whenever a problem describes a process whose *mechanics* don't actually depend on the specific values involved.
- The dominant cost is the sort — the queue simulation itself is strictly O(n), so there's no asymptotic benefit to avoiding a real `Queue`/`Deque` structure here, unlike some tighter-constrained problems.
