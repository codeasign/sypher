Every example so far has used a literal ID: `patient_id: 20`, `doctor_id: 5`. Those numbers were real and correct at the time they were written, checked against a freshly seeded database. This module explains exactly why hardcoding them is fragile, using a real, measured example of it going wrong, and builds the fixture pattern that fixes it for good.

## A real inconsistency in this app's seed data

Run `npm run seed` a second time against a database you have already seeded once, then log in as `patient1` again:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"patient1","password":"pass@123"}'
```

The first time, on a fresh database, `patient1` might come back as user `id: 20`. Reseed once more, and that same login now returns `id: 77`. Nothing about the account changed (same username, same password, same role) but its ID moved.

Here is why: `seed.js` deletes every non-admin user and re-inserts the full list fresh on every run, so the *data* really is reset each time. But the `users` table's `id` column is `INTEGER PRIMARY KEY AUTOINCREMENT`, and SQLite's `AUTOINCREMENT` keyword guarantees IDs are never reused, even after a `DELETE`: the next insert always continues from the highest ID that table has ever seen, not from the lowest gap available. Reseed three times, and you are not back to a clean `id: 20`, you are at whatever number thirty-some deleted-and-reinserted users add up to.

That is a real, verified property of this specific app's seed data, not a hypothetical: **the exact numeric ID of any seeded user is not stable across reseeds.** A test that hardcodes `patient_id: 20` will pass right after a fresh seed and can quietly break (pointing at the wrong patient, or a patient that no longer exists at all) after nothing more than running `npm run seed` again.

## The fix: look values up, don't hardcode them

Rather than typing a literal ID and hoping it still points at what you think it does, fetch a real seeded user by role at the start of the test, and use whatever ID comes back:

```typescript
// tests-ts/helpers/fixtures.ts
import request from 'supertest';
import app from '../../server';
import { loginAs, authHeader, Role } from './auth';

export interface SeededUser {
  id: number;
  username: string;
  full_name: string;
}

export async function getFirstUserWithRole(role: Role): Promise<SeededUser> {
  const admin = await loginAs('Administrator');
  const response = await request(app)
    .get(`/api/users/role/${role}`)
    .set(authHeader(admin.token));

  if (!response.body.length) {
    throw new Error(`No seeded users found with role ${role}`);
  }

  return response.body[0];
}
```

This is itself a fixture: a small piece of setup logic that gets your test into a known, valid state before the actual test runs, without the test needing to know or care about specific ID values. Using it instead of a hardcoded number:

```typescript
import { getFirstUserWithRole } from './helpers/fixtures';

it('creates an appointment using a looked-up patient and doctor', async () => {
  const patient = await getFirstUserWithRole('Patient');
  const doctor = await getFirstUserWithRole('Doctor');
  const admin = await loginAs('Administrator');

  const response = await request(app)
    .post('/api/appointments')
    .set(authHeader(admin.token))
    .send({
      patient_id: patient.id,
      doctor_id: doctor.id,
      appointment_date: '2026-09-10T10:00:00',
      reason: 'fixture-based test',
    });

  expect(response.status).toBe(201);
});
```

This test passes identically whether `patient1` is `id: 20`, `id: 77`, or anything else: it never assumes a specific number, only that *some* seeded Patient and *some* seeded Doctor exist, which `npm run seed` always guarantees regardless of how many times it has been run. That guarantee, a stable shape of data even when the exact values inside it drift, is what a good fixture is actually built around.

Every hardcoded ID in the earlier modules of this course was correct against a fresh seed at the time it was written, exactly the way yours will be the first time you run it. From here forward, prefer `getFirstUserWithRole(...)` (or `loginAs(...).userId`, when the current user's own ID is what you need) over typing a literal number: it is the difference between a test that depends on a snapshot of the database staying frozen forever, and one that depends only on the seed script's actual guarantees.

## Setup and teardown, and why this app doesn't give you much of it

Jest's `beforeAll`/`beforeEach`/`afterAll`/`afterEach` hooks are the standard place to put fixture setup and cleanup:

```typescript
describe('appointment tests', () => {
  let doctor: SeededUser;
  let patient: SeededUser;

  beforeAll(async () => {
    doctor = await getFirstUserWithRole('Doctor');
    patient = await getFirstUserWithRole('Patient');
  });

  it('uses the fixtures looked up once for the whole suite', async () => {
    // doctor and patient are already available here
  });
});
```

`beforeAll` runs once before every test in the `describe` block, ideal for fixtures like this, which are safe to reuse across many read-only tests rather than re-fetching per test. `beforeEach` runs before *every single* test instead, which you would reach for if a test mutates shared state in a way that could affect the next one.

Where this app makes teardown harder than it should be: there is no endpoint to fully reset the database to a known state between test runs, and the data your tests create (appointments, medical records) has no automatic cleanup. Tests in this course that create data generally either do not bother deleting it afterward (harmless clutter in a local dev database) or explicitly delete what they created in an `afterEach`/`afterAll` when leaving it around would interfere with a later test. Both are legitimate choices; what matters is being deliberate about which one a given test needs, rather than assuming the database resets itself, because it does not.

## Try it

Add a `getFirstUserWithRole('Nurse')` call to a new test, and use it to create an appointment as that nurse. Then, without changing your test at all, run `npm run seed` again and re-run the test. Confirm it still passes, using whatever new ID that nurse ends up with.
