Almost every endpoint in the RBAC app requires proof of who's asking before it does anything. You've been logging in by hand in every module so far — this is the module where that stops, and you build one small, reusable piece of test infrastructure that every module after this one imports instead.

## How the app's auth actually works

`POST /api/auth/login` takes a `username` and `password`. If they're valid, it signs a **JWT (JSON Web Token)** — a compact, self-contained string that encodes who the user is and what role they have — and sends it back:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"doctor1","password":"pass@123"}'
```

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": { "id": 5, "username": "doctor1", "role": "Doctor", "full_name": "Dr. James Wilson" }
}
```

Every protected endpoint expects that token sent back on an `Authorization` header, in the form `Bearer <token>`. The server verifies the token's signature (proving it wasn't tampered with) and reads the role encoded inside it to decide what that request is allowed to do — that role check is the entire foundation of the RBAC matrix you'll test thoroughly soon.

Two failure modes are worth knowing precisely, because you'll test both directly and they return *different* status codes:

- **No token at all** → `401 { "error": "Access token required" }`. The server can't even tell who's asking.
- **A token that's invalid, malformed, or expired** → `403 { "error": "Invalid or expired token" }`. The server knows *something* was sent, but it doesn't trust it.

That distinction — missing credentials get `401`, credentials that exist but don't check out get `403` — isn't a convention every API follows the same way, so it's worth confirming against the app you're actually testing rather than assuming. You'll rely on it directly in the negative-testing module.

## The four accounts you'll use throughout this course

The seed data gives you one working account per role, and these four logins are what every RBAC-aware test in this course is built around:

| Role | Username | Password |
|---|---|---|
| Administrator | `admin` | `admin123` |
| Doctor | `doctor1` | `pass@123` |
| Nurse | `nurse1` | `pass@123` |
| Patient | `patient1` | `pass@123` |

## Building a reusable auth helper

Re-deriving this login logic in every test file — build the body, send it, pull `token` off the response, remember which password goes with which role — is exactly the kind of repetition worth eliminating once, in one place. Create `tests-ts/helpers/auth.ts`:

```typescript
import request from 'supertest';
import app from '../../server';

export type Role = 'Administrator' | 'Doctor' | 'Nurse' | 'Patient';

const CREDENTIALS: Record<Role, { username: string; password: string }> = {
  Administrator: { username: 'admin', password: 'admin123' },
  Doctor: { username: 'doctor1', password: 'pass@123' },
  Nurse: { username: 'nurse1', password: 'pass@123' },
  Patient: { username: 'patient1', password: 'pass@123' },
};

export interface AuthSession {
  token: string;
  userId: number;
}

export async function loginAs(role: Role): Promise<AuthSession> {
  const { username, password } = CREDENTIALS[role];
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username, password });

  if (response.status !== 200) {
    throw new Error(`Login failed for ${role}: ${response.status} ${JSON.stringify(response.body)}`);
  }

  return { token: response.body.token, userId: response.body.user.id };
}

export function authHeader(token: string) {
  return { Authorization: `Bearer ${token}` };
}
```

A couple of design choices worth explaining. `Role` is a **union of string literals** — TypeScript will only let you pass one of those four exact strings to `loginAs`, which means a typo like `loginAs('Docter')` is a compile error instead of a runtime surprise. `CREDENTIALS` is typed as `Record<Role, ...>`, so if a fifth role were ever added to `Role`, TypeScript would immediately flag that `CREDENTIALS` is now missing an entry for it — the type system keeps the two in sync for you. And `loginAs` throws immediately if login fails, rather than silently returning `undefined` — a test that then tries to use a missing token fails with a confusing, unrelated error far from the real cause; failing loudly, right where the real problem is, is worth the extra `if` check.

`authHeader(token)` exists just to save you from typing out the `Authorization: Bearer <token>` header by hand at every call site — small, but it's one less thing to get wrong.

## Using it

From here on, every module reaches for this exact pattern instead of re-deriving login logic:

```typescript
import request from 'supertest';
import app from '../server';
import { loginAs, authHeader } from './helpers/auth';

describe('auth helper in action', () => {
  it('logs in as a doctor and hits a protected endpoint', async () => {
    const doctor = await loginAs('Doctor');

    const response = await request(app)
      .get('/api/appointments')
      .set(authHeader(doctor.token));

    expect(response.status).toBe(200);
  });

  it('rejects requests with no token at all', async () => {
    const response = await request(app).get('/api/appointments');
    expect(response.status).toBe(401);
    expect(response.body.error).toBe('Access token required');
  });

  it('rejects requests with a garbage token', async () => {
    const response = await request(app)
      .get('/api/appointments')
      .set('Authorization', 'Bearer not-a-real-token');
    expect(response.status).toBe(403);
    expect(response.body.error).toBe('Invalid or expired token');
  });
});
```

All three pass against the real app — `loginAs('Doctor')` returns a real, working session; a request with no `Authorization` header at all comes back `401`; a request with a token that fails signature verification comes back `403`. Every RBAC-aware test from this point forward starts the same way: `const session = await loginAs(role)`, then `.set(authHeader(session.token))` on whatever request comes next.

## Try it

Add a `Nurse` case to a new test: log in with `loginAs('Nurse')`, then send a request to `GET /api/users` (list all users — an Administrator-only endpoint) using that nurse's token. Assert on the status code you get back, and check `response.body.requiredRoles` in the failure response — the server tells you exactly which roles it would have accepted.
