If you have tested software by clicking through a UI, you already understand testing: you are checking that the app does what it is supposed to do, and catching it when it does not. API testing is the same idea, aimed at a different layer: instead of clicking a button and watching a screen update, you send a request directly to the server and check what comes back.

## What API testing actually covers

Think about what happens when you click "Book Appointment" in the RBAC healthcare app's UI. The browser does not do anything magical. It builds an HTTP request (something like `POST /api/appointments` with a JSON body describing the patient, doctor, date, and reason) and sends it to the Express server. The server validates it, checks who is making the request and whether they are allowed to, writes to the database, and sends back a response. The UI just takes that response and turns it into something you can see.

API testing means skipping the "turn it into something you can see" part and testing the request/response exchange directly. You send the same `POST /api/appointments` request the UI would have sent, and you assert on the actual response (status code, headers, body) instead of on rendered pixels.

That gives you a few things UI testing structurally cannot:

- **Speed.** No browser to launch, no page to render, no animation to wait out. A request/response round trip against the RBAC app takes milliseconds.
- **Precision.** If a test fails, you know exactly which endpoint and which field caused it. A UI test failure often means digging through a screenshot to figure out what actually broke underneath.
- **Coverage that does not need a UI at all.** The RBAC app's permission rules, what a Nurse can do that a Patient cannot, live entirely on the server. You can verify all of that without a frontend rendering a single pixel.

What it cannot tell you: whether the "Book Appointment" button actually calls the right endpoint, whether the confirmation message renders correctly, or whether a doctor's dashboard visually reflects the new appointment. That is what UI-level testing is for. Neither layer replaces the other; they catch different kinds of bugs.

## The request/response contract

Every API test you write in this course is built around the same shape: send a request, get a response, assert on the response. That exchange is a *contract*, an agreement about what a given request means and what response it produces.

Take the RBAC app's login endpoint as a concrete example. The contract for `POST /api/auth/login` looks roughly like this:

- **Request:** a JSON body with `username` and `password`.
- **Success response:** `200`, with a JSON body containing a `token` and a `user` object.
- **Failure response:** `401`, with a JSON body containing an `error` message, if the credentials are wrong.

An API test's whole job is to check that this contract actually holds, not just on the happy path, but at its edges too. What happens with a wrong password? A missing field entirely? A username that does not exist? Each of those is a separate, specific claim about the contract, and each one becomes its own test.

## Where API tests fit in the test pyramid

You will often see testing described as a pyramid: a large base of fast, cheap, narrowly-scoped tests, a smaller middle layer, and a thin top layer of slow, expensive, broad tests.

API tests sit in the middle. They are broader than a unit test (a login test exercises real routing, real middleware, a real database) but they do not pay the cost of a browser and a rendered UI the way an end-to-end test does. That middle position is exactly why teams invest heavily here: you get confidence that close to matches what a full end-to-end test would give you, at a fraction of the time and flakiness.

For the RBAC app specifically, that middle layer is where its permission logic actually lives. A Nurse being blocked from deleting a medical record is not a UI decision, it is a server-side check. Testing it at the API layer catches that logic directly, without needing a browser at all.

## Why teams invest in this layer

A team that only tests through the UI ends up with a slow, flaky suite that takes forever to tell them what broke. A team that only writes unit tests can have every function individually correct while the endpoints wired around them are still broken: a route that forgets to call the function it is supposed to, for instance, no unit test would ever catch.

API tests close that gap. They run fast enough to execute on every single commit, they are specific enough to point straight at the broken endpoint, and they exercise real, wired-together behavior (routing, middleware, database queries, authorization) the way the app is actually used, not code in isolation. That is the layer this whole course lives in, and by the end of it, you will have built a full suite of exactly this kind of test against a real, non-trivial application.

## Try it

Using `curl` (or a REST client if you prefer), send a `POST` request to `http://localhost:5000/api/auth/login` with an intentionally wrong password for the `admin` account. Write down, in plain English, what you think the contract *should* say for this case (status code, and what the body should contain), then run the request and compare it to what actually comes back.
