Every test so far has mostly asked "does this work when everything is correct?" Negative testing asks the more valuable question: "what does this do when something is wrong?" And the answer is worth confirming against the real app rather than assuming, because it does not always match your first guess.

## Don't assume the status code, confirm it

It would be reasonable to assume any authentication failure returns `401 Unauthorized`. This app does not work that way, and you already have the evidence from the authentication module: a request with **no token at all** gets `401`, but a request with a token that is **present but invalid** (malformed, tampered with, or expired) gets `403`. Two different failure states, two different codes, and only one of them is the code you might have guessed for both.

```typescript
it('missing token gets 401, invalid token gets 403', async () => {
  const noToken = await request(app).get('/api/appointments');
  expect(noToken.status).toBe(401);
  expect(noToken.body.error).toBe('Access token required');

  const badToken = await request(app)
    .get('/api/appointments')
    .set('Authorization', 'Bearer not-a-real-token');
  expect(badToken.status).toBe(403);
  expect(badToken.body.error).toBe('Invalid or expired token');
});
```

That is the whole discipline of this module: do not write the assertion you assume is correct, send the request, read what actually comes back, and assert on that. If the real behavior seems wrong, that is worth flagging separately; but the test itself should describe reality, not your prior guess about it.

## Wrong credentials vs. missing token

A wrong username or password at login is a separate case from a missing/invalid token: it happens *before* a token even exists:

```typescript
it('rejects a wrong password with 401 and a generic message', async () => {
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'wrong-password' });

  expect(response.status).toBe(401);
  expect(response.body.error).toBe('Invalid credentials');
});
```

Notice the message does not say which part was wrong: not "wrong password" specifically, just `Invalid credentials`, the same message a nonexistent username gets too. That is a deliberate security property worth testing *for*, not around: revealing "that username does not exist" vs. "that password is wrong" as two different messages would let an attacker enumerate valid usernames one guess at a time. A test that asserts the message stays generic for both cases is protecting that property.

## Malformed and missing fields

`POST /api/auth/register` runs its input through `express-validator`, and a bad payload comes back as a structured `400` with one entry per broken field:

```typescript
it('reports every validation failure on a bad registration payload', async () => {
  const response = await request(app)
    .post('/api/auth/register')
    .send({ username: 'ab', email: 'not-an-email', password: '123', role: 'SuperAdmin' });

  expect(response.status).toBe(400);
  expect(response.body.errors).toEqual(
    expect.arrayContaining([
      expect.objectContaining({ path: 'username', msg: 'Username must be at least 3 characters' }),
      expect.objectContaining({ path: 'email', msg: 'Invalid email address' }),
      expect.objectContaining({ path: 'password', msg: 'Password must be at least 6 characters' }),
      expect.objectContaining({ path: 'role', msg: 'Invalid role' }),
    ]),
  );
});
```

`expect.arrayContaining([...])` checks that the array includes at least these entries, in any order, without requiring you to match the array exactly, useful here since a fifth error (a missing `full_name`) also comes back in the real response, and this test is not about that field. `expect.objectContaining({...})` does the same thing one level down, for individual objects: check the fields you care about, ignore the rest (here, each error object also has `type` and `location` fields this test does not need to mention).

Not every endpoint validates its input this thoroughly, and that is worth testing *as its own fact*, not silently working around. `POST /api/appointments` has no validation layer at all: send it a payload missing a required field, and it does not come back as a clean `400`:

```typescript
it('returns a raw 500 for a missing required field, not a clean 400', async () => {
  const admin = await loginAs('Administrator');
  const response = await request(app)
    .post('/api/appointments')
    .set(authHeader(admin.token))
    .send({ doctor_id: 5, appointment_date: '2026-09-01T10:00:00', reason: 'test' }); // no patient_id

  expect(response.status).toBe(500);
  expect(response.body.error).toBe('Error creating appointment');
});
```

`patient_id` is a `NOT NULL` column in the database, so leaving it out does not get caught by a validation layer: it fails at the database itself, and the route's generic error handling turns that into a `500` with a vague message. That is a real, verified gap in this app's input handling, not a guess, and it is exactly the kind of thing negative testing is for: documenting precisely how an endpoint fails today, so a future change to add real validation here has a test that will need deliberately updating, rather than a gap nobody was watching.

## Boundary and malformed-input values

A few more shapes worth checking deliberately, each verified against the real app:

```typescript
it('a non-numeric ID in the URL is treated as not found, not a bad request', async () => {
  const admin = await loginAs('Administrator');
  const response = await request(app)
    .get('/api/appointments/not-a-number')
    .set(authHeader(admin.token));

  expect(response.status).toBe(404); // SQLite's parameter binding just finds no match
});

it('an empty login body is a credentials failure, not a validation failure', async () => {
  const response = await request(app).post('/api/auth/login').send({});
  expect(response.status).toBe(401); // login has no express-validator layer either
  expect(response.body.error).toBe('Invalid credentials');
});
```

Neither of those is the "obvious" answer either: a non-numeric ID might reasonably come back as `400 Bad Request` in a stricter API, and an empty login body might reasonably trigger a validation error before ever reaching a database lookup. This app does neither; both fall through to whatever the underlying logic naturally produces once you send data it was not specifically guarded against. Testing that honestly is more valuable than testing the version of the API you expected to find.

## Try it

Test `PUT /api/appointments/999999` (an appointment ID that does not exist) as an Administrator, sending a valid-looking update body. Check the actual status code and message that comes back, and compare it to what `DELETE` on the same nonexistent ID returns. They are two different routes handling "the thing you asked for does not exist"; confirm for yourself whether they agree with each other or not.
