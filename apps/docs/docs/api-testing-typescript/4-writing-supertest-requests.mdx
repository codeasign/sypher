The last module got one request working end to end. This one is about the actual vocabulary you will use constantly: the HTTP methods, the chained methods that shape a request before it is sent, and what you get back once it lands.

## The four methods you'll use

Supertest gives you one method per HTTP verb, and you will reach for all four constantly against this API:

```typescript
request(app).get('/api/appointments');
request(app).post('/api/appointments');
request(app).put('/api/appointments/21');
request(app).delete('/api/appointments/21');
```

Each of these returns a chainable request object. Nothing is actually sent over the wire until you `await` it (or attach `.then()`/`.expect()`, which you will see more of soon). That is worth internalizing early: `request(app).get(...)` on its own does not do anything yet, it just builds up a description of the request you are about to make.

## Shaping the request before it's sent

Three chained methods cover almost everything you will need to configure a request:

**`.send(body)`** attaches a JSON body. You will use it constantly on `POST` and `PUT` requests:

```typescript
const response = await request(app)
  .post('/api/appointments')
  .set('Authorization', `Bearer ${token}`)
  .send({
    patient_id: 20,
    doctor_id: 5,
    appointment_date: '2026-09-01T10:00:00',
    reason: 'Annual checkup',
  });
```

**`.set(header, value)`** attaches a header. The one you will type the most in this course by far is `Authorization`, since almost every endpoint in the RBAC app requires a valid Bearer token. You will build a small helper for this in the very next module so you are not retyping `Bearer ${token}` everywhere by hand.

**`.query(params)`** appends query-string parameters to the URL. It is worth knowing the syntax even though, as it happens, none of the RBAC app's own endpoints actually read anything from `req.query`: every filter this API supports (by role, by ID) is a path parameter, not a query string. You can still call `.query()` against a real endpoint here and confirm it is simply ignored rather than causing an error:

```typescript
const response = await request(app)
  .get('/api/appointments')
  .set('Authorization', `Bearer ${token}`)
  .query({ foo: 'bar' }); // harmless -- this API doesn't read it

expect(response.status).toBe(200); // unaffected either way
```

You will use `.query()` for real the moment you are working against an API that supports filtering or pagination through the URL. It is common enough elsewhere that it is worth knowing now, even against an app that does not happen to use it.

## Reading what comes back

Once you `await` a Supertest call, you get a response object with everything you need to make assertions:

```typescript
const response = await request(app)
  .post('/api/appointments')
  .set('Authorization', `Bearer ${token}`)
  .send({ patient_id: 20, doctor_id: 5, appointment_date: '2026-09-01T10:00:00', reason: 'Annual checkup' });

console.log(response.status);   // 201
console.log(response.body);     // { message: 'Appointment created successfully', appointmentId: 21 }
console.log(response.headers);  // { 'content-type': 'application/json; charset=utf-8', ... }
```

- **`response.status`** is the numeric HTTP status code. This is what you will assert on most.
- **`response.body`** is the parsed response body. Supertest automatically parses JSON responses for you, so this is already a real object, not a string you have to `JSON.parse()` yourself.
- **`response.headers`** is every response header, lowercased, as a plain object, useful when you care about things like `content-type` or a custom header an API sets.

## A full round trip

Put it together against a real resource: create an appointment, update it, fetch it, then delete it, checking the response at every step:

```typescript
import request from 'supertest';
import app from '../server';

describe('appointment round trip', () => {
  it('creates, updates, fetches, and deletes an appointment', async () => {
    const login = await request(app)
      .post('/api/auth/login')
      .send({ username: 'admin', password: 'admin123' });
    const token = login.body.token;

    const created = await request(app)
      .post('/api/appointments')
      .set('Authorization', `Bearer ${token}`)
      .send({
        patient_id: 20,
        doctor_id: 5,
        appointment_date: '2026-09-01T10:00:00',
        reason: 'Annual checkup',
      });
    expect(created.status).toBe(201);
    const appointmentId = created.body.appointmentId;

    const updated = await request(app)
      .put(`/api/appointments/${appointmentId}`)
      .set('Authorization', `Bearer ${token}`)
      .send({ status: 'completed' });
    expect(updated.status).toBe(200);

    const fetched = await request(app)
      .get(`/api/appointments/${appointmentId}`)
      .set('Authorization', `Bearer ${token}`);
    expect(fetched.body.status).toBe('completed');

    const deleted = await request(app)
      .delete(`/api/appointments/${appointmentId}`)
      .set('Authorization', `Bearer ${token}`);
    expect(deleted.status).toBe(200);
  });
});
```

Running that against the seeded RBAC data prints exactly this shape of response at each step: `{"message":"Appointment created successfully","appointmentId":21}` on create, `{"message":"Appointment updated successfully"}` on update, the full appointment object (including `status: "completed"` and joined `patient_name`/`doctor_name` fields) on the fetch, and `{"message":"Appointment deleted successfully"}` on delete. One request, one assertion, one clear signal about what the API actually did at each step.

## Try it

Write a test that fetches the full list of doctors from `GET /api/users/role/Doctor` (with a valid admin token set via `.set()`) and asserts on three things from the response: the status code, that `response.body` is an array, and that at least one entry has `role` equal to `"Doctor"`.
