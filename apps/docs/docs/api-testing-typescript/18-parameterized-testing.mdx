You have already used `it.each` once, in the RBAC matrix module, without a full explanation of how it works. This module gives it that explanation, and adds its sibling, `describe.each`, the two tools that let you stop copy-pasting near-identical tests and instead describe a pattern once, over a table of inputs.

## `test.each` (and its alias, `it.each`)

`test.each` takes an array of values (often tuples) and runs the same test body once per entry, substituting placeholders into the test name so each run shows up as its own separately reported result:

```typescript
describe('every protected endpoint rejects requests with no token', () => {
  const protectedEndpoints: Array<[string, string]> = [
    ['get', '/api/appointments'],
    ['post', '/api/appointments'],
    ['get', '/api/medical-records'],
    ['get', '/api/patients'],
    ['get', '/api/users'],
    ['get', '/api/users/role/Doctor'],
  ];

  test.each(protectedEndpoints)('%s %s -> 401 with no token', async (method, path) => {
    const response = await (request(app) as any)[method](path);
    expect(response.status).toBe(401);
    expect(response.body.error).toBe('Access token required');
  });
});
```

Run that, and Jest reports six individually named results (`get /api/appointments -> 401 with no token`, `post /api/appointments -> 401 with no token`, and so on) from one test body. `%s` in the name string substitutes each tuple's values in order (there is also `%i` for integers, `%d` for numbers more generally, and `%p` for pretty-printing an object). Without `test.each`, checking this same claim across six endpoints means six nearly-identical `it(...)` blocks, differing only in the method and path, exactly the kind of repetition that is easy to under-maintain, since adding a seventh endpoint later means remembering to copy the pattern again rather than just adding one line to an array.

`(request(app) as any)[method](path)` looks unusual: it is calling `request(app).get(path)` or `request(app).post(path)` dynamically, based on the `method` string from the table, since Supertest does not have a single method that takes the HTTP verb as a parameter. The `as any` is a deliberate, narrow type-check bypass: TypeScript cannot verify at compile time that `method` is definitely `'get'` or `'post'` rather than an arbitrary string, so this tells it "trust me here" for this one dynamic call, rather than losing type safety across the whole file.

## `describe.each`

Where `test.each` parameterizes one test, `describe.each` parameterizes a whole group, useful when each row in your table needs more than one assertion, or its own setup:

```typescript
describe.each([
  ['Administrator', 200],
  ['Doctor', 200],
  ['Nurse', 200],
  ['Patient', 403],
] as const)('GET /api/patients as %s', (role, expectedStatus) => {
  it(`returns ${expectedStatus}`, async () => {
    const session = await loginAs(role);
    const response = await request(app)
      .get('/api/patients')
      .set(authHeader(session.token));

    expect(response.status).toBe(expectedStatus);
  });
});
```

This produces four separate `describe` blocks (`GET /api/patients as Administrator`, `GET /api/patients as Doctor`, and so on) each containing its own `it(...)`. The `as const` after the array tells TypeScript to treat each tuple as a fixed, literal pair (`readonly ['Administrator', 200]`) rather than widening it to the more general `(string | number)[]`: without it, `role` would be typed as `string`, and passing it to `loginAs(role)` (which expects the specific `Role` union) would not type-check.

## Why this pays off specifically for RBAC and CRUD coverage

This course has two categories of test that are naturally repetitive by design: the RBAC matrix (the same claim, checked across 4 roles) and CRUD lifecycles (the same create-read-update-delete shape, across different resources). Both are exactly what `test.each`/`describe.each` are for: expressing "this claim, repeated across this table of inputs" as one block instead of as many near-duplicate ones. Going back through the RBAC-matrix module's tests and converting any remaining one-role-at-a-time `it(...)` blocks into a single `describe.each` is not just tidier, it also means a fifth role, if this app ever added one, would need exactly one new row in an array, not a new block of test code written and reviewed from scratch.
