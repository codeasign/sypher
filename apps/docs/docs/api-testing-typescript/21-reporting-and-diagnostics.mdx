Jest's terminal output is fine while you are actively writing tests, but it is not what you hand to someone else. A teammate reviewing a failed CI run, or you yourself a week later, need something more durable than scrollback. This module covers two separate things: a shareable report of the whole run, and failure messages rich enough that you do not have to re-run a test just to see what actually happened.

## An HTML report of the whole run

```bash
npm install --save-dev jest-html-reporters
```

```javascript
// jest.config.js
module.exports = {
  // ...your existing config
  reporters: ['default', ['jest-html-reporters', { publicPath: './html-report', filename: 'report.html' }]],
};
```

`reporters` takes an array: `'default'` keeps Jest's normal terminal output exactly as it has always been, and the second entry adds `jest-html-reporters` alongside it, rather than replacing it. Run the suite, and alongside the usual terminal output, you get a real file:

```bash
📦 report is created on: .../backend/html-report/report.html
```

Open that file in a browser and you get a filterable, clickable summary of every test (pass/fail status, duration, and full error output for anything that failed) in a form you can attach to a PR, send a teammate, or archive as a CI artifact. This does not change how any test runs; it is purely a different lens on the same results Jest was already producing.

## Rich failure messages, without re-running anything

The more valuable habit is making individual failures self-explanatory the first time, so a failure in CI does not send you back to your machine just to reproduce what request was actually sent and what came back. A small custom assertion helper does this directly:

```typescript
// tests-ts/helpers/diagnostics.ts
import { Response } from 'supertest';

export function expectStatus(response: Response, expected: number) {
  if (response.status !== expected) {
    throw new Error(
      [
        `Expected status ${expected}, got ${response.status}`,
        `Request: ${response.request.method} ${response.request.url}`,
        `Response body: ${JSON.stringify(response.body, null, 2)}`,
      ].join('\n'),
    );
  }
}
```

Used in place of a plain `expect(response.status).toBe(expected)`:

```typescript
it('deliberately fails to show the rich error message', async () => {
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'wrong-on-purpose' });

  expectStatus(response, 200); // it's actually 401 -- see what that failure looks like
});
```

A plain `expect(response.status).toBe(200)` failing here would tell you "expected 200, received 401" and nothing else, accurate, but you would still have to go add a `console.log` and re-run to see *why*. `expectStatus` throwing its own `Error` with a custom message puts everything you would need for a first diagnosis directly in the failure output instead:

```bash
Expected status 200, got 401
Request: POST http://127.0.0.1:56225/api/auth/login
Response body: {
  "error": "Invalid credentials"
}
```

That is the entire request and the entire response, right there in the test output (in CI, in the HTML report, anywhere this failure gets read) without needing to reproduce it locally first just to find out what actually happened. The cost is small (one small helper function, reused everywhere you would otherwise write a bare status assertion) and the payoff compounds every time a test fails somewhere you cannot immediately attach a debugger to, which in practice is most of the time a real CI failure gets noticed.

## Try it

Extend `expectStatus` into a sibling helper, `expectBody`, that fails with the same rich format (expected vs. actual, request details, full response body) when a specific field in the response body does not match what you expected. Use it to check that a failed login's `response.body.error` really does equal `'Invalid credentials'`, and deliberately break the expected value once to see your own diagnostic message in action.
