You have been verifying writes by reading them back through the API: create, then `GET` the same resource. That is honest and it works, but it has a blind spot: it trusts the very API you are testing to tell you the truth about what it did. This module goes one level deeper and checks the database directly.

## Why read back through the database at all

If a route's `GET` handler and its `POST` handler share a bug (say, both silently ignore a field) testing "does `GET` show what `POST` claimed to write" will not catch it, because both sides agree with each other, incorrectly. Querying the actual SQLite row sidesteps that: it is not asking the app what it thinks happened, it is asking the database what actually happened.

Being in-process pays off directly here: since your test and the running application are in the very same Node.js process either way, nothing stops you from also opening the same SQLite file the app itself uses and querying it directly, alongside your API calls:

```typescript
// tests-ts/helpers/db.ts
import sqlite3 from 'sqlite3';
import path from 'path';

const DB_PATH = path.join(__dirname, '../../database/rbac.db');

export function queryOne<T = any>(sql: string, params: any[] = []): Promise<T | undefined> {
  return new Promise((resolve, reject) => {
    const db = new sqlite3.Database(DB_PATH);
    db.get(sql, params, (err, row) => {
      db.close();
      if (err) reject(err);
      else resolve(row as T);
    });
  });
}
```

This opens its own short-lived connection to the exact same database file `server.js` reads and writes (not a copy, not a mock, the real file on disk) runs one query, and closes the connection. `db.get(...)` returns a single row (or `undefined` if nothing matched), which is wrapped in a Promise here so it plays nicely with `async`/`await` the same way every Supertest call in this course already does.

## Verifying a write against the real row

```typescript
import { getFirstUserWithRole } from './helpers/fixtures';
import { queryOne } from './helpers/db';

it('creates an appointment via the API and confirms the row directly in SQLite', async () => {
  const patient = await getFirstUserWithRole('Patient');
  const doctor = await getFirstUserWithRole('Doctor');
  const admin = await loginAs('Administrator');

  const created = await request(app)
    .post('/api/appointments')
    .set(authHeader(admin.token))
    .send({
      patient_id: patient.id,
      doctor_id: doctor.id,
      appointment_date: '2026-09-12T10:00:00',
      reason: 'db-verification test',
    });
  expect(created.status).toBe(201);

  const row = await queryOne(
    'SELECT * FROM appointments WHERE id = ?',
    [created.body.appointmentId],
  );

  expect(row).toBeDefined();
  expect(row.patient_id).toBe(patient.id);
  expect(row.doctor_id).toBe(doctor.id);
  expect(row.reason).toBe('db-verification test');
  expect(row.status).toBe('scheduled'); // the column's default, confirmed at the storage layer
});
```

That last assertion is worth noticing specifically: `status` defaults to `'scheduled'` at the database level (it is a `DEFAULT 'scheduled'` column, never set explicitly in the request), and checking it against the real row confirms that default is actually being applied by SQLite, not just assumed, and not just reported back optimistically by a `GET` handler that might have its own default-filling logic layered on top.

## Test isolation, and this app's real limitation here

"Test isolation" means one test's data and side effects should not affect another test's outcome. The clean version of this, common in larger production systems, uses a completely separate database for tests, often reset to a known-empty state before every single test runs.

This app does not give you that option out of the box: `DB_PATH` is a fixed path to one file, `database/rbac.db`, with no environment variable or config to point it somewhere else, and there is no endpoint that resets the database to a known state on demand. Every test in this course, and every test you write against this app, shares one real, persistent SQLite file, the same one `npm start` uses for local development.

Rather than pretend otherwise, the practical approach used throughout this course is to write tests that do not depend on the database being empty or in any particular starting state:

- **Assert on what you create, not on totals.** A test checking "the appointment I just created has the right fields" survives however many other appointments already exist. A test checking "there are exactly 3 appointments in the system" breaks the moment any other test (or your own manual `curl` testing) adds a fourth.
- **Look up fixtures dynamically** (from the last module) rather than assuming a specific row is present at a specific ID, for exactly the reasons already covered there.
- **Clean up when leaving data around would actively interfere** with another test (deleting something you created in an `afterEach` or `afterAll` when its continued presence would change another test's results) but do not feel obligated to delete every single thing a test creates; a few extra rows in a local dev database rarely cause harm.

A genuinely isolated setup (a fresh, empty database per test run, maybe even per test file) is achievable for an app like this: an in-memory `:memory:` SQLite database, or a `DB_PATH` that reads from an environment variable, are both standard ways teams solve exactly this. Getting there means changing how the app itself is configured, which is outside what a test suite alone can do without also modifying the application under test. Knowing that limitation, and writing tests that are robust to it rather than tests that quietly assume it away, is the actual skill this module is teaching.

## Try it

Write a test that updates a medical record's `diagnosis` through `PUT /api/medical-records/:id`, then queries the row directly with `queryOne('SELECT * FROM medical_records WHERE id = ?', [id])` and asserts the `diagnosis` column actually changed. Then add one more direct-database assertion most API responses do not expose at all: check that `updated_at` is a non-null, real timestamp string.
