The schema validation you just learned works against schemas *you* wrote by hand. This module uses a schema someone else already wrote: the RBAC app's own OpenAPI spec — the same one powering the Swagger UI at `/api-docs` — as the source of truth instead.

## Getting the spec as data, not just a web page

The Swagger UI is generated from `@swagger` comments sitting directly above each route handler in `src/routes/*.js` — that's the same annotation style you can see if you open any route file in the RBAC repo. `swagger-jsdoc`, the library that builds that page, can also just hand you the resulting spec as a plain JavaScript object, which is exactly what you want in a test:

```bash
npm install --save-dev swagger-jsdoc @types/swagger-jsdoc ajv
```

```typescript
// tests-ts/helpers/spec.ts
import swaggerJsdoc from 'swagger-jsdoc';

export function getOpenApiSpec() {
  return swaggerJsdoc({
    definition: {
      openapi: '3.0.0',
      info: { title: 'RBAC Healthcare System API', version: '1.0.0', description: 'x' },
      servers: [{ url: 'http://localhost:5000', description: 'Development server' }],
      components: {
        securitySchemes: { bearerAuth: { type: 'http', scheme: 'bearer', bearerFormat: 'JWT' } },
      },
      security: [{ bearerAuth: [] }],
    },
    apis: ['./src/routes/*.js'],
  }) as any;
}
```

This mirrors the exact configuration `server.js` itself uses to build the Swagger page — so `getOpenApiSpec()` returns precisely the same spec object a real caller sees, generated fresh from the current state of the route comments every time you call it. If someone edits a `@swagger` block tomorrow, your tests see that change immediately, with nothing to keep in sync by hand.

## Catching undocumented (or over-documented) endpoints

One of the most useful things an OpenAPI-aware test can check has nothing to do with response shapes at all: does every route the app actually serves have a matching entry in the spec, and vice versa? A route that exists in code but was never documented is invisible to anyone relying on the Swagger page — including future you.

```typescript
it('documents every route the app actually registers', () => {
  const spec = getOpenApiSpec();
  const documented = new Set<string>();
  for (const [routePath, methods] of Object.entries<any>(spec.paths)) {
    for (const method of Object.keys(methods)) {
      documented.add(`${method.toUpperCase()} ${routePath}`);
    }
  }

  const registered = [
    'POST /api/auth/register', 'POST /api/auth/login',
    'GET /api/users', 'GET /api/users/{id}', 'PUT /api/users/{id}',
    'DELETE /api/users/{id}', 'GET /api/users/role/{role}',
    'POST /api/appointments', 'GET /api/appointments',
    'GET /api/appointments/{id}', 'PUT /api/appointments/{id}', 'DELETE /api/appointments/{id}',
    'POST /api/medical-records', 'GET /api/medical-records',
    'GET /api/medical-records/{id}', 'PUT /api/medical-records/{id}', 'DELETE /api/medical-records/{id}',
    'GET /api/patients/{patientId}/records', 'GET /api/patients',
  ];

  const missing = registered.filter((r) => !documented.has(r));
  expect(missing).toEqual([]);
});
```

That `registered` list is written out by hand here for clarity, matched against every route this app's routers actually define. Run it, and it passes with an empty `missing` array — right now, this app's spec and its real routes are in sync. That's exactly the point of a test like this: it doesn't need there to be a bug today to be worth having. The moment someone adds a new endpoint without a `@swagger` comment above it, or deletes a route but leaves the stale documentation behind, this is the test that turns that silently-drifted state into a loud, specific failure.

## Validating a request against the spec's own schema

The request bodies documented in this app's `@swagger` comments are full JSON Schema, which means you can validate a real payload against them directly — no hand-written Zod schema required, because the spec already *is* the schema:

```typescript
import Ajv from 'ajv';

it('validates a real login request body against the spec-derived schema', async () => {
  const spec = getOpenApiSpec();
  const schema = spec.paths['/api/auth/login'].post.requestBody.content['application/json'].schema;

  const ajv = new Ajv();
  const validate = ajv.compile(schema);

  const payload = { username: 'admin', password: 'admin123' };
  expect(validate(payload)).toBe(true);

  const response = await request(app).post('/api/auth/login').send(payload);
  expect(response.status).toBe(200);
});
```

[Ajv](https://ajv.js.org) is a JSON Schema validator — `ajv.compile(schema)` turns a schema into a reusable validation function, and calling that function on a value returns `true` or `false`. Reaching into `spec.paths['/api/auth/login'].post.requestBody...` looks verbose, but it's just walking the same nested structure you'd see reading the raw spec — `paths` → the route → the HTTP method → `requestBody` → the JSON content type → its `schema`.

A payload that violates the documented contract fails clearly, with the exact field and reason:

```typescript
it('catches a request body that violates the spec', () => {
  const spec = getOpenApiSpec();
  const schema = spec.paths['/api/auth/register'].post.requestBody.content['application/json'].schema;
  const validate = new Ajv().compile(schema);

  const badPayload = { username: 'ab', role: 'SuperAdmin' }; // missing required fields
  expect(validate(badPayload)).toBe(false);
  console.log(validate.errors);
});
```

```json
[
  {
    "instancePath": "",
    "schemaPath": "#/required",
    "keyword": "required",
    "params": { "missingProperty": "email" },
    "message": "must have required property 'email'"
  }
]
```

By default Ajv stops at the first violation it finds rather than collecting every problem with a payload — here, the missing `email` field, even though `role: 'SuperAdmin'` is also invalid against the documented enum. That's worth knowing going in: a single failed validation doesn't mean it's the *only* thing wrong, just the first thing Ajv happened to check.

## Where this stops, honestly

This app's Swagger comments document request bodies thoroughly, but they don't define response schemas — every `responses` block in its route comments is just a status code and a plain-English description, with no `content`/`schema` underneath. That's a real limit of what this particular spec covers, not something to route around by inventing response schemas that don't actually exist in the documentation. If you want response-shape guarantees, the Zod schemas from the previous module are exactly the tool for that — OpenAPI testing and hand-written schema validation aren't competing approaches, they're covering different parts of the same contract: what this app promises about *requests* lives in the spec; what it promises about *responses* is something you can still verify, you just have to define that part of the contract yourself.

## Try it

Pick `POST /api/appointments` and pull its `requestBody` schema out of `getOpenApiSpec()` the same way. Validate two payloads against it with Ajv: one that includes all four required fields (`patient_id`, `doctor_id`, `appointment_date`, `reason`), and one missing `reason`. Confirm the first validates and the second doesn't, and log `validate.errors` for the failing case to see exactly what Ajv reports.
