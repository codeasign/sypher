Every module so far has touched authorization in passing. This one maps it out completely: exactly which of the app's 4 roles can do what, on every endpoint, verified against the app's actual behavior rather than assumed from a README.

## Mapping the real matrix

The RBAC app's own `authorizeRoles(...)` middleware is the ground truth for what is actually enforced: it is what runs on every request, and it is what you will be asserting against. Walking the route files gives you this picture of the core of the matrix (a couple of endpoints with the same shape as ones already shown, like updating your own profile, are left out for brevity):

| Endpoint | Administrator | Doctor | Nurse | Patient |
|---|---|---|---|---|
| `POST /api/appointments` (create) | ✅ | ✅ | ✅ | ✅ |
| `GET /api/appointments` (list) | ✅ all | ✅ own only | ✅ all | ✅ own only |
| `GET /api/appointments/:id` | ✅ any | ✅ own only | ✅ any | ✅ own only |
| `PUT /api/appointments/:id` | ✅ | ✅ | ✅ | ❌ |
| `DELETE /api/appointments/:id` | ✅ | ✅ | ❌ | ❌ |
| `POST /api/medical-records` (create) | ❌ | ✅ | ❌ | ❌ |
| `GET /api/medical-records` (list) | ✅ all | ✅ own only | ✅ all | ✅ own only |
| `GET /api/medical-records/:id` | ✅ any | ✅ own only | ✅ any | ✅ own only |
| `PUT /api/medical-records/:id` | ❌ | ✅ | ❌ | ❌ |
| `DELETE /api/medical-records/:id` | ✅ | ✅ | ❌ | ❌ |
| `GET /api/patients` (list all patients) | ✅ | ✅ | ✅ | ❌ |
| `GET /api/patients/:id/records` | ✅ any | ✅ any | ✅ any | ✅ own only |
| `GET /api/users` (list all) | ✅ | ❌ | ❌ | ❌ |
| `GET /api/users/:id` | ✅ any | own only | own only | own only |
| `DELETE /api/users/:id` | ✅ | ❌ | ❌ | ❌ |

Two rows are worth pausing on because they are easy to get wrong by intuition alone: creating an appointment (`POST /api/appointments`) has no role restriction at all in this app, so every authenticated role, including Patient, can create one. And `GET /api/medical-records/:id` and `GET /api/patients/:id/records` let a Nurse or Doctor view *any* patient's records, not just ones they are directly treating: there is no per-patient assignment check beyond the basic role gate. Neither of those is a guess; both are exactly what the route code does, and you will verify the second one yourself again in the security module, from a different angle.

## Data-driven tests across all 4 roles

Testing the same claim once per role is repetitive and easy to under-cover: it is tempting to test the "interesting" roles and skip the rest. Jest's `it.each` runs the same test body once per entry in an array, which makes testing all 4 roles as cheap as testing one:

```typescript
import request from 'supertest';
import app from '../server';
import { loginAs, authHeader, Role } from './helpers/auth';

describe('DELETE /api/medical-records/:id — role gate', () => {
  const cases: Array<[Role, number]> = [
    ['Administrator', 404], // role check passes, then 404 because the record doesn't exist
    ['Doctor', 404],
    ['Nurse', 403],
    ['Patient', 403],
  ];

  it.each(cases)('role %s gets %i', async (role, expectedStatus) => {
    const session = await loginAs(role);
    const response = await request(app)
      .delete('/api/medical-records/999999')
      .set(authHeader(session.token));

    expect(response.status).toBe(expectedStatus);
  });
});
```

`it.each(cases)` takes an array of tuples and runs the test once per tuple, substituting `%s` and `%i` in the test name with that row's values, so this produces four separate, individually-named test results (`role Administrator gets 404`, `role Doctor gets 404`, and so on), not one test looping silently. You will go much deeper on this pattern, including `describe.each` for parameterizing whole groups of tests, in the parameterized testing module; this is a preview of exactly why it is worth learning properly.

Notice the request targets medical record ID `999999`, which does not exist. That is deliberate: this app's route checks the role *before* looking up the record, so a nonexistent ID isolates exactly one thing (did the role check pass or fail) without needing a real record to already exist for each role to attempt against. An allowed role reaches the "not found" branch and gets `404`; a disallowed role never gets that far and gets `403` instead. Run it, and the disallowed cases come back with a body worth asserting on too:

```json
{
  "error": "Access denied. Insufficient permissions.",
  "requiredRoles": ["Administrator", "Doctor"],
  "userRole": "Nurse"
}
```

That `requiredRoles` field is worth checking, not just the status code: it is the middleware telling you exactly what it expected, which makes a passing test into a small piece of living documentation for what this endpoint's contract actually is.

## Testing scoped access, not just allow/deny

Some rows in the matrix are not a clean allow/deny: every role can call `GET /api/appointments`, but what comes back depends on who is asking. That needs a different kind of assertion: not just the status code, but a check on the *content* of what a scoped role gets back.

```typescript
it('scopes a patient to only their own appointments', async () => {
  const patient = await loginAs('Patient'); // patient1, userId 20

  const response = await request(app)
    .get('/api/appointments')
    .set(authHeader(patient.token));

  expect(response.status).toBe(200);
  expect(response.body.length).toBeGreaterThan(0);
  expect(response.body.every((appt: any) => appt.patient_id === patient.userId)).toBe(true);
});
```

That last assertion is the real point of the test: not just that the request succeeded, but that every single appointment in the response actually belongs to the patient who asked for it. A scoping bug that leaked one other patient's appointment into the list would return `200` just like a correct response would; only checking the actual contents catches it.

## Try it

Write an `it.each` test covering all 4 roles against `GET /api/patients` (list all patients): Administrator, Doctor, and Nurse should all get `200`, Patient should get `403`. Then extend it: for the roles that get `200`, add an assertion that `response.body` is a non-empty array. That combination, a data-driven pass/fail check plus a content check for the roles that pass, is the same two-part shape you will use for almost every endpoint in this matrix.
