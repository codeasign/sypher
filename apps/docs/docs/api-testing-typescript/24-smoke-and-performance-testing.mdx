Not every situation calls for running the entire suite. Sometimes what you actually want is a fast, narrow answer to one question, "is the app fundamentally broken right now?", in a few seconds, not a few minutes. This module covers that narrower kind of test, and where "is it fast enough" starts needing a different kind of testing altogether.

## What a smoke test is for

A smoke test suite is a small, deliberately shallow set of checks against the most critical paths through an app: not exhaustive, not edge-case-aware, just "does the absolute core still work." The name comes from hardware testing: power something on and check whether smoke comes out before bothering with anything more detailed. For this app, that is something like: can someone log in, and does at least one protected endpoint respond correctly to a valid request.

## Tagging tests for fast, targeted runs

Jest does not have a first-class "tag" feature, but a simple, common convention (a marker like `@smoke` inside a `describe` block's name) combined with `--testNamePattern` gets you the same result:

```typescript
describe('critical path @smoke', () => {
  it('login works', async () => {
    const response = await request(app)
      .post('/api/auth/login')
      .send({ username: 'admin', password: 'admin123' });

    expect(response.status).toBe(200);
  });
});
```

```bash
npx jest --testNamePattern="@smoke"
```

`--testNamePattern` matches against the full combined name of `describe` + `it` blocks, so any test whose name contains `@smoke` anywhere in that combined string runs; everything else reports as `skipped` rather than actually executing. This is a real, useful command to have as a documented `npm run test:smoke` script: a fast, few-second sanity check you can run constantly during active development, reserving the full suite for before a commit or in CI.

## Basic response-time assertions

A response-time assertion is exactly what it sounds like: measuring how long a request actually took, and asserting it stayed under some budget. Supertest does not track this for you automatically, so it is a small amount of manual timing around the call:

```typescript
it('login responds within a reasonable budget', async () => {
  const start = Date.now();
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'admin123' });
  const elapsed = Date.now() - start;

  expect(response.status).toBe(200);
  expect(elapsed).toBeLessThan(1000);
});
```

Run against the real app, login consistently takes somewhere around 140 to 160ms. Most of that is the real, deliberately-slow `bcrypt.compare` call from the mocking module, not network or Express overhead, since this is all happening in-process. A `1000`ms budget here is generous on purpose: the goal of a check like this is not to catch a 20ms regression, it is to catch something going catastrophically wrong (a query that used to be indexed and no longer is, an accidental infinite retry loop, a dependency that started hanging). Set the budget too tight, and the assertion becomes noise that fails on ordinary machine-load variance instead of on a real problem.

## Where this ends and real performance testing begins

A single in-process request taking 150ms tells you almost nothing about how this app behaves under real load: hundreds of concurrent users, sustained traffic over time, a database under genuine write pressure. That is a different discipline entirely, usually called load testing or performance testing, using tools built specifically for it (k6, Artillery, Gatling) that can simulate many simultaneous virtual users hitting a *real, running, network-accessible* server, which means it has to be genuinely black-box, not in-process, since the entire point is measuring how the app behaves under concurrent network traffic, the very thing in-process testing deliberately sidesteps.

The response-time assertions in this module are a single-request sanity check, not a substitute for that: they catch "this one request got dramatically slower than it used to be," not "this app falls over at 500 concurrent users." Knowing which question you are actually answering is the important part: a passing response-time assertion in this suite says nothing about how the app holds up under real load, and a passing load test does not replace the fast, specific feedback a response-time assertion gives you on every single test run.

## Try it

Add a second `@smoke`-tagged test checking that `GET /api/patients` responds successfully for an Administrator, with its own response-time assertion. Then run `npx jest --testNamePattern="@smoke"` and confirm only your two tagged tests execute, with everything else in the suite reporting as skipped rather than actually running.
