The last few modules quietly set `maxWorkers: 1` in `jest.config.js` and moved on. This module explains exactly what that gave up, why it was the right call for this specific app, and what parallel execution actually requires when an app's design does support it.

## Jest's worker model

By default, Jest doesn't run your test files one after another — it spins up a pool of worker processes (roughly matched to your CPU core count) and hands out test files to whichever worker is free next, so multiple files genuinely execute at the same moment, in separate OS processes. For a large suite on a multi-core machine, this is usually a significant speedup: ten files split across four workers can finish in a fraction of the time ten files run one at a time would take.

`maxWorkers: 1` turns that off entirely — every file runs in a single worker, strictly one after another. You saw exactly why this course needs that setting back when you first ran the whole suite together:

```bash
SQLITE_BUSY: database is locked
```

## Why shared state breaks parallelism here

Jest's worker processes are genuinely separate OS processes, each with its own memory — that isolation is exactly what makes parallel execution safe *in general*. The problem isn't Jest's model; it's this specific app's fixed `DB_PATH`, pointing every worker at the exact same on-disk SQLite file with no per-worker separation. Two workers writing to that one file at nearly the same moment is precisely what SQLite's `SQLITE_BUSY` error exists to report — the database itself telling you two connections just collided over the same resource.

This is the same root cause as the port collision from the coverage module, one layer down: there, every test file collided over one shared *port*; here, every worker collides over one shared *file*. Both come from the same source — this app has exactly one instance of a resource (a listening socket, a database file) that assumes only one thing will ever use it at a time, and Jest's normal way of running tests violates that assumption the moment more than one worker is active.

## What real per-worker isolation would look like

Jest gives every worker a `process.env.JEST_WORKER_ID` — a small integer, unique per worker, stable for that worker's whole lifetime. If this app's `DB_PATH` were configurable (via an environment variable, say), a genuinely parallel-safe setup could point each worker at its own database file:

```javascript
// hypothetical -- this app's actual DB_PATH is a fixed path, not configurable
const DB_PATH = process.env.TEST_DB_PATH
  ? `${process.env.TEST_DB_PATH}.worker-${process.env.JEST_WORKER_ID}.db`
  : path.join(__dirname, '../../database/rbac.db');
```

Four workers would then mean four separate SQLite files, each seeded independently, each fully isolated from the others — no shared resource left to collide over, and `maxWorkers` could go back to its default. That's a real, standard pattern for parallelizing a test suite that touches a database. It's also *not* something achievable purely from the test side here: `src/config/database.js`'s `DB_PATH` is a hardcoded path with no environment override, so making this work would mean modifying the application under test, not just how you test it — which is a real, honest limit on what this particular app supports today, not a gap in what you've learned.

## The trade this course made, explicitly

`maxWorkers: 1` gives up parallel speed in exchange for correctness with the app exactly as it exists. For a suite this size, running everything through one worker still finishes in a few seconds — the trade is barely noticeable in practice, and a suite that reliably passes every time beats a faster one that intermittently fails for a reason that has nothing to do with the code being tested. As this course's suite (or any suite built on an app with this same shared-file constraint) grows into the hundreds or thousands of tests, that trade-off shifts, and modifying the app to support real per-worker isolation stops being optional — but knowing exactly why you'd need to make that change, and what specifically it would require, is worth having clear before you're the one debugging a flood of `SQLITE_BUSY` failures in a much larger suite.

## Try it

Temporarily remove `maxWorkers: 1` from `jest.config.js` and run the suite two or three times in a row. Note whether `SQLITE_BUSY` shows up every time, only sometimes, or not at all in a given run — and think through why a race condition like this one might not fail the same way on every single execution, even though the underlying risk is always there.
