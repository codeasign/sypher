You have already done a full create-update-delete round trip against appointments. This module makes the pattern explicit and repeatable, using medical records as a second resource, and adds the piece that round trip skipped: proving a change actually *persisted*, not just that the endpoint responded like it did.

## The four operations, and what "success" means for each

CRUD stands for Create, Read, Update, Delete, the four operations almost every resource in a real API supports in some form. Each one has a different shape of "correct":

- **Create** (`POST`) should return a status indicating something new exists, `201 Created`, plus enough information to find that new thing again (here, an `id`).
- **Read** (`GET`) should return the resource's current state, matching whatever was last written.
- **Update** (`PUT`) should return success, and, critically, the *next* `GET` should reflect the change. A `200` from `PUT` alone does not prove anything actually changed in the database.
- **Delete** (`DELETE`) should return success, and the *next* `GET` for that same resource should now fail, usually `404`.

That last point in each case is the one people skip when they are in a hurry: testing that an update or delete "worked" by only checking the response of the update/delete call itself, and never actually reading the resource back afterward. A route can return `200` while silently doing nothing to the database; only a follow-up read proves persistence.

## Full lifecycle test against medical records

```typescript
import request from 'supertest';
import app from '../server';
import { loginAs, authHeader } from './helpers/auth';

describe('medical record CRUD lifecycle', () => {
  it('creates, reads, updates, and deletes a medical record', async () => {
    const doctor = await loginAs('Doctor');

    // CREATE
    const created = await request(app)
      .post('/api/medical-records')
      .set(authHeader(doctor.token))
      .send({
        patient_id: 20,
        diagnosis: 'Seasonal allergies',
        prescription: 'Loratadine 10mg',
      });
    expect(created.status).toBe(201);
    const recordId = created.body.recordId;

    // READ — confirm what was actually written
    const afterCreate = await request(app)
      .get(`/api/medical-records/${recordId}`)
      .set(authHeader(doctor.token));
    expect(afterCreate.body.diagnosis).toBe('Seasonal allergies');
    expect(afterCreate.body.notes).toBeNull();

    // UPDATE
    const updated = await request(app)
      .put(`/api/medical-records/${recordId}`)
      .set(authHeader(doctor.token))
      .send({
        diagnosis: 'Seasonal allergies (resolved)',
        prescription: 'Loratadine 10mg',
        notes: 'Follow up in 2 weeks',
      });
    expect(updated.status).toBe(200);

    // READ again — prove the update actually persisted
    const afterUpdate = await request(app)
      .get(`/api/medical-records/${recordId}`)
      .set(authHeader(doctor.token));
    expect(afterUpdate.body.diagnosis).toBe('Seasonal allergies (resolved)');
    expect(afterUpdate.body.notes).toBe('Follow up in 2 weeks');

    // DELETE
    const deleted = await request(app)
      .delete(`/api/medical-records/${recordId}`)
      .set(authHeader(doctor.token));
    expect(deleted.status).toBe(200);

    // READ again — prove the delete actually persisted
    const afterDelete = await request(app)
      .get(`/api/medical-records/${recordId}`)
      .set(authHeader(doctor.token));
    expect(afterDelete.status).toBe(404);
  });
});
```

Five requests, four operations, but eight assertions in total: every write is followed by a read that proves it actually took effect. That is the whole discipline this module is teaching: a CRUD test is not complete until it has checked the *after* state, not just the *response* to the write.

Notice too that creating a medical record required logging in as `Doctor` specifically. `POST /api/medical-records` is one of the RBAC app's role-gated endpoints, restricted to doctors only. You will map out exactly which operations are gated to which roles, across every resource, in the RBAC permission matrix module. For now, `Doctor` is simply the role that is allowed to do the write you are testing.

## Try it

Write the equivalent lifecycle test for appointments, but this time use the `Nurse` role for the create and update steps (nurses are allowed to manage appointments in this app). For the delete step, try using that same nurse session and see what happens, then try it again with `Doctor` instead. You will get two different results; hold onto that observation, since it is exactly the kind of role-by-operation difference the RBAC permission matrix module maps out in full.
