Every module up to this point has focused on one technique at a time, mostly against appointments and medical records. This capstone points the whole toolkit (setup, auth, CRUD, the RBAC matrix, negative cases, and the CI pipeline) at a part of the app this course has only ever touched in passing: the `/api/users` endpoints.

## The area you're covering

Users has come up constantly as a supporting character: you have logged in through it, looked up fixtures through it, checked admin-only access through it, but it has never gotten a complete suite of its own. It is a good capstone target for exactly that reason: it is real, it is already partially familiar, and building full coverage for it means applying everything from this course end to end, not learning anything new.

Here is what it actually does, and the real, verified rules governing it:

- `GET /api/users`: list every user. Administrator only.
- `GET /api/users/:id`: view one user. An Administrator can view anyone; anyone else can only view their own profile.
- `PUT /api/users/:id`: update `full_name`, `phone`, `email`. Same ownership rule as viewing.
- `DELETE /api/users/:id`: Administrator only.
- `GET /api/users/role/:role`: list users by role. Open to any authenticated user.

## Building the suite, end to end

**Setup and fixtures.** Nothing new to install: every helper this suite needs already exists from earlier modules.

```typescript
// tests-ts/users.test.ts
import request from 'supertest';
import app from '../server';
import { loginAs, authHeader, Role } from './helpers/auth';
import { getFirstUserWithRole } from './helpers/fixtures';
```

**The RBAC matrix**, using `describe.each` the way the parameterized-testing module covered:

```typescript
describe.each([
  ['Administrator', 200],
  ['Doctor', 403],
  ['Nurse', 403],
  ['Patient', 403],
] as const)('GET /api/users as %s', (role, expectedStatus) => {
  it(`returns ${expectedStatus}`, async () => {
    const session = await loginAs(role);
    const response = await request(app).get('/api/users').set(authHeader(session.token));
    expect(response.status).toBe(expectedStatus);
  });
});
```

**Ownership, not just role.** This endpoint's real rule is not a flat allow/deny, it is "yourself, or an admin," which needs its own pair of tests rather than a table:

```typescript
describe('GET /api/users/:id — ownership', () => {
  it('lets a user view their own profile', async () => {
    const patient = await loginAs('Patient');
    const response = await request(app)
      .get(`/api/users/${patient.userId}`)
      .set(authHeader(patient.token));
    expect(response.status).toBe(200);
    expect(response.body.id).toBe(patient.userId);
  });

  it('blocks a user from viewing someone else\'s profile', async () => {
    const patient = await loginAs('Patient');
    const admin = await getFirstUserWithRole('Administrator');
    const response = await request(app)
      .get(`/api/users/${admin.id}`)
      .set(authHeader(patient.token));
    expect(response.status).toBe(403);
  });

  it('lets an Administrator view anyone\'s profile', async () => {
    const admin = await loginAs('Administrator');
    const patient = await getFirstUserWithRole('Patient');
    const response = await request(app)
      .get(`/api/users/${patient.id}`)
      .set(authHeader(admin.token));
    expect(response.status).toBe(200);
  });
});
```

**CRUD, with a real read-after-write check**:

```typescript
describe('PUT /api/users/:id', () => {
  it('updates and persists a profile change', async () => {
    const patient = await loginAs('Patient');
    const updated = await request(app)
      .put(`/api/users/${patient.userId}`)
      .set(authHeader(patient.token))
      .send({ full_name: 'Updated Name', phone: '555-0000', email: 'updated@example.com' });
    expect(updated.status).toBe(200);

    const fetched = await request(app)
      .get(`/api/users/${patient.userId}`)
      .set(authHeader(patient.token));
    expect(fetched.body.full_name).toBe('Updated Name');
  });
});
```

**Negative cases**, the way the negative-testing module covered, do not assume, confirm:

```typescript
describe('negative cases', () => {
  it('rejects a request with no token', async () => {
    const response = await request(app).get('/api/users');
    expect(response.status).toBe(401);
  });

  it('returns 404 for a user ID that does not exist', async () => {
    const admin = await loginAs('Administrator');
    const response = await request(app)
      .get('/api/users/999999')
      .set(authHeader(admin.token));
    expect(response.status).toBe(404);
  });
});
```

**CI.** Nothing to add here at all: this file lives in `tests-ts/`, matches the `testMatch` pattern already in `jest.config.js`, and the GitHub Actions workflow from the CI module already runs every file matching that pattern. Push this file, and it is covered by the required check without touching the workflow.

## Where to go from here

You started this course importing an Express app directly into a test file and asserting on a login response. By this point you have built a suite that covers CRUD, the full RBAC matrix across 4 roles, schema and OpenAPI contract validation, direct database verification, deliberate security testing, flaky-test diagnosis on a real bug, and a CI pipeline that gates merges on all of it. That is not a toy exercise. It is the actual shape of API test ownership on a real team.

If you want to take these same habits, the same RBAC app, the same real permission matrix, and point them at a browser instead of an API, this site's Playwright Test Automation course picks up from here, testing the same application's UI directly. And if API testing itself is what you want to go deeper on in a different language, the equivalent course in this site's other stacks covers the same ground with a different toolchain, so you can compare how the same problems get solved elsewhere.

Either way, you are not new to API testing anymore. You have found a real bug, documented a real security gap, and built a real, CI-gated suite from nothing. That is the job.
