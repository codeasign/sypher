Every test you have written so far has used `expect(x).toBe(y)` and not much else. Jest ships a much larger set of matchers, and picking the right one is the difference between a test that tells you exactly what broke and one that either misses real bugs or breaks every time something unrelated changes.

## Status codes: the first and cheapest check

Status code assertions are the fastest signal you have, and they should usually be the first assertion in any test:

```typescript
const response = await request(app)
  .get('/api/patients')
  .set(authHeader(adminSession.token));

expect(response.status).toBe(200);
```

Supertest also gives you `.expect(200)` as a chained method, which throws immediately if the status does not match; some teams prefer that inline style over a separate `expect()` call. Both are checking the same thing; this course sticks to `expect(response.status).toBe(...)` because keeping every assertion in the same `expect(...)` form makes a failing test easier to scan.

## Header checks

Headers tell you about the response itself, separate from its content. The RBAC API's responses are consistently JSON, and it is a reasonable, cheap sanity check to confirm that on any endpoint you are not sure about:

```typescript
expect(response.headers['content-type']).toMatch(/application\/json/);
```

`toMatch` takes a regular expression (or substring) rather than requiring an exact match, useful here because the real header value is `application/json; charset=utf-8`, and you care that it is JSON, not about the exact charset suffix tagging along.

## Body shape assertions

This is where most of your real assertions live. A `GET /api/patients/20/records` response has real structure (a nested `patient` object, arrays of `appointments` and `medicalRecords`, a `summary` object) and different matchers are suited to checking different parts of that shape.

**`toHaveProperty`** checks that a specific, possibly nested, property exists, and optionally, what it equals:

```typescript
expect(response.body).toHaveProperty('patient');
expect(response.body).toHaveProperty('summary.totalAppointments');
expect(response.body.patient).toHaveProperty('full_name', 'John Smith');
```

The dotted-path form (`'summary.totalAppointments'`) reaches into nested objects without you having to write `response.body.summary.totalAppointments` and risk a `TypeError` if `summary` happened to be missing: `toHaveProperty` fails cleanly instead.

**`toMatchObject`** checks that the response contains *at least* the fields and values you specify; extra fields you do not mention are ignored:

```typescript
expect(response.body.patient).toMatchObject({
  id: 20,
  username: 'patient1',
  full_name: 'John Smith',
});
```

This is usually the better default over asserting on the entire object with `toEqual`. The real response also includes `email`, `phone`, and `created_at`, fields this particular test does not care about. `toMatchObject` lets the test express exactly that: "these fields matter here, and I am deliberately not asserting on the rest."

**`toEqual`** checks for a complete, exact match: every field, no more, no less:

```typescript
expect(response.body.summary).toEqual({
  totalAppointments: 2,
  scheduledAppointments: 1,
  completedAppointments: 1,
  cancelledAppointments: 0,
  totalMedicalRecords: 2,
});
```

`toEqual` is the right call when you genuinely want to lock down every field: a small, complete object like this `summary` block is a good candidate. It is the wrong call for a large object like the full `patient` record, where locking in every field means the test breaks the next time an unrelated field gets added to the response, for a reason that has nothing to do with what the test was actually checking.

## What makes an assertion good vs. brittle

The theme running through all of this: **assert on what the test is actually about, and nothing more.** A test checking that patient records are scoped correctly should not fail because someone added a `last_login` field to the user object: that is an unrelated change tripping an assertion that was too broad. A few concrete habits that keep assertions from becoming brittle:

- Prefer `toMatchObject` over `toEqual` for anything with fields your test does not care about.
- Assert on values, not on incidental structure: checking `response.body.length` for an expected count is more brittle than checking `response.body.some(r => r.id === expectedId)`, since the first breaks if seed data changes even slightly.
- Do not assert on things you do not control and are not testing: timestamps, auto-incrementing IDs from unrelated records, database-internal fields.
- One logical claim per test where reasonably possible, so a failure tells you specifically what is wrong rather than "something in this large block of assertions."

## Try it

Send `GET /api/patients/20/records` as an admin, and write three assertions against the response: one `toHaveProperty` check on a nested field inside `summary`, one `toMatchObject` check against the `patient` object using only two or three fields you actually care about, and one status-code check. Then deliberately swap your `toMatchObject` check to `toEqual` using the same partial field set, run it, and read the failure. It is a good way to feel the difference between the two matchers firsthand.
