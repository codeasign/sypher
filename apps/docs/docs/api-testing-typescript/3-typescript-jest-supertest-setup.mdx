Time to turn the RBAC backend from "a server I can `curl`" into "a server I can write real TypeScript tests against." By the end of this page you'll have a working `.test.ts` file that imports the app, sends it a request with Supertest, and passes.

## What each piece does

Three tools are doing distinct jobs here, and it's worth knowing what each one is actually for before you install them:

- **Jest** is the test runner. It finds your test files, runs them, checks your `expect()` assertions, and reports pass/fail. It's the outer loop everything else plugs into.
- **ts-jest** is a transform that lets Jest understand `.ts` files directly. Without it, Jest only knows how to run plain JavaScript — ts-jest compiles your TypeScript on the fly before handing it to Jest.
- **Supertest** is the library that actually builds and sends the HTTP requests in your tests, and gives you a chainable API (`.post(...)`, `.send(...)`, `.expect(...)`) for making assertions on the response.

`jest` and `supertest` are already listed in the RBAC backend's `package.json`, so `npm install` back in the setup module already pulled them in. What's missing is the TypeScript layer on top.

## Installing the TypeScript layer

From inside `backend/`, install TypeScript itself, the Jest/TypeScript bridge, and the type definitions for Jest, Supertest, and Node:

```bash
npm install --save-dev typescript ts-jest @types/jest @types/supertest @types/node
```

There's one real, current gotcha worth knowing about here: `npm install typescript` today can pull in TypeScript's newer native-compiler line (version 7 and up), which doesn't yet expose the classic JavaScript compiler API that `ts-jest`'s transform depends on — you'll get an error like `does not expose the JavaScript compiler API required by ts-jest` the first time you try to run a test. If that happens, pin TypeScript to the last classic-API major line instead:

```bash
npm install --save-dev typescript@^6.0.0
```

This is exactly the kind of thing worth checking with `npx tsc --version` after installing, rather than assuming — tooling versions shift, and a five-second sanity check saves you a confusing error later.

## Configuring TypeScript for tests

Add a `tsconfig.json` in `backend/`:

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "CommonJS",
    "esModuleInterop": true,
    "allowJs": true,
    "strict": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "types": ["jest", "node"]
  },
  "include": ["tests-ts/**/*.ts"]
}
```

Most of that is standard, but two options are doing specific work worth calling out:

- **`esModuleInterop: true`** lets you write `import app from '../server'` instead of the older `import app = require('../server')` syntax, even though `server.js` uses CommonJS's `module.exports`. Without it, TypeScript is stricter about mixing the two module styles.
- **`allowJs: true`** matters because `server.js` — the file you're importing — is plain JavaScript with no type declarations of its own. With `strict` mode on, TypeScript would otherwise refuse to import it, complaining it "implicitly has an `any` type." `allowJs` tells TypeScript it's fine to pull in untyped JavaScript alongside your typed test code. You didn't write `server.js` and you're not about to rewrite someone else's backend just to satisfy the type checker — you're testing its *behavior*, so treating it as `any` here is the right call, not a compromise.

## Configuring Jest

Add a `jest.config.js` in `backend/` as well:

```javascript
module.exports = {
  preset: 'ts-jest',
  testEnvironment: 'node',
  testMatch: ['**/tests-ts/**/*.test.ts'],
  forceExit: true,
};
```

`preset: 'ts-jest'` wires the transform in, so Jest can run `.ts` files at all. `testMatch` points Jest specifically at a new `tests-ts/` folder — keeping your TypeScript suite separate from the small set of example JavaScript tests the RBAC repo already ships in `tests/`, so the two don't collide or get mixed together while you're building your own suite. And `forceExit: true` is there because of exactly the listener issue explained a moment ago: importing `server.js` starts it listening on a port that nothing in the test explicitly closes, so without `forceExit`, Jest sits there after your tests finish, waiting for a handle that's never coming.

## Your first passing test

Create `backend/tests-ts/smoke.test.ts`:

```typescript
import request from 'supertest';
import app from '../server';

describe('smoke test', () => {
  it('logs in as admin', async () => {
    const response = await request(app)
      .post('/api/auth/login')
      .send({ username: 'admin', password: 'admin123' });

    console.log(response.status, response.body);

    expect(response.status).toBe(200);
    expect(response.body).toHaveProperty('token');
  });
});
```

Walking through the unfamiliar parts: `describe(...)` groups related tests under a shared label — here, just one test, but you'll nest many under one `describe` block soon. `it(...)` (equivalently `test(...)`) declares a single test case with a description and the function that runs it. `expect(response.status).toBe(200)` is Jest's assertion syntax — `expect()` wraps the value you're checking, and `.toBe(...)` is a *matcher* that compares it against what you expected, failing the test with a readable diff if it doesn't match.

Before running it, make sure nothing else is bound to port `5000` — stop the dev server if it's running, for the exact reason covered a moment ago. Then run:

```bash
npx jest
```

You should see the app's own startup logs print first — `Database initialized successfully`, `Server is running on port 5000` — because importing `server.js` really does boot it, followed by your `console.log` showing the real response, and finally a passing test:

```bash
PASS tests-ts/smoke.test.ts
  smoke test
    ✓ logs in as admin (155 ms)

Test Suites: 1 passed, 1 total
Tests:       1 passed, 1 total
```

That's the whole loop, end to end: TypeScript compiles your test, Jest runs it, Supertest drives the real Express app in-process, and you get a pass/fail based on a real response from real application code. Every module from here builds on exactly this shape.

## Try it

Add a second `it(...)` block to `smoke.test.ts` that logs in with a wrong password instead, and assert on the status code you'd expect back for invalid credentials. Run `npx jest` again and confirm both tests pass in the same run.
