This course assumes you're already comfortable with JavaScript/TypeScript basics — variables, functions, `async`/`await`, maybe a bit of Node. What it doesn't assume is any API testing experience, so we're starting from the very beginning of that: getting a real backend running on your machine, and proving to yourself that you can talk to it before you write a single test.

Every module in this course runs against the same system under test: a 4-role RBAC (Role-Based Access Control) healthcare app called `rbac-healthcare-system`. It has an Express API, a SQLite database, JWT authentication, and a Swagger page documenting every endpoint. By the end of this page, that app will be running on your machine, seeded with realistic data, and you'll have made one real request against it — just to confirm the wiring works.

## Confirm Node and TypeScript are ready

You'll need Node.js installed — version 18 or later is safest. Check what you've got:

```bash
node --version
npm --version
```

You should see two version numbers. If either command isn't found, install Node from [nodejs.org](https://nodejs.org) (the LTS build) before continuing — `npm` ships bundled with it.

TypeScript itself doesn't need a separate install right now — you'll add it as a project dependency alongside Jest and Supertest, and that's covered in its own module shortly. For now, just confirm `npx` is available, since it's how you'll run locally-installed TypeScript tools without polluting your global environment:

```bash
npx --version
```

## Clone the RBAC app

Clone the system under test:

```bash
git clone https://github.com/codedbyabhishekc/rbac-healthcare-system.git
cd rbac-healthcare-system
```

This course only touches the `backend/` folder — there's no browser or UI involved anywhere in this course, since every test you write imports the Express app and drives it with Supertest instead of clicking through a frontend.

## Install and configure the backend

```bash
cd backend
npm install
mkdir database
```

The `database` folder is where the app's SQLite file lives once the server creates it — it isn't checked into the repo, so you have to make it yourself.

Next, create a `.env` file inside `backend/`:

```bash
PORT=5000
JWT_SECRET=any-long-random-string-you-want
NODE_ENV=development
```

`JWT_SECRET` is the key the server uses to sign and verify login tokens — you'll see exactly how that works in the authentication module. For local development, any long random string is fine; it just needs to exist.

Start the server once to confirm it boots and creates its database:

```bash
npm start
```

You should see:

```bash
Connected to SQLite database
Database initialized successfully
Server is running on port 5000
Swagger documentation available at http://localhost:5000/api-docs
```

Leave that running for a moment, and open [http://localhost:5000/api-docs](http://localhost:5000/api-docs) in a browser. That's the Swagger UI — a live, browsable list of every endpoint this app exposes, generated straight from comments in the route files. You'll come back to this page a lot; whenever you're unsure what an endpoint expects, it's the fastest place to check.

## Seed the database

A freshly created database is empty, and an empty database makes for a boring — and unrealistic — test suite. Stop the server (`Ctrl+C`) and run the seed script:

```bash
npm run seed
```

This populates the database with 3 Administrators, 8 Doctors, 7 Nurses, 15 Patients, 20 appointments, and 15 medical records. Every account uses the password `pass@123`, except the default admin account, which uses `admin` / `admin123` — that's the login you'll use most often across this course. Start the server back up with `npm start` once seeding finishes.

## Make one real request

Before touching TypeScript or Jest at all, let's prove the environment actually works with a plain `curl` request — the same login request the app's own frontend would make:

```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```

You should get back something like this (the token itself will be a long, unreadable string — that's expected):

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": 1,
    "username": "admin",
    "email": "admin@hospital.com",
    "role": "Administrator",
    "full_name": "System Administrator"
  }
}
```

That response is the whole app in miniature: you sent credentials, the server checked them against the database, and it handed back a signed token plus the logged-in user's details. Every protected endpoint in this course expects that token on later requests — you'll build a small helper around this exact call in the authentication module, so you never have to retype this logic again.

## Try it

With the server still running, log in as a different seeded user — try `doctor1` with password `pass@123` — using the same `curl` command with the username and password swapped. Check the `role` field in the response and confirm it says `"Doctor"` instead of `"Administrator"`. That role field is what drives every permission check you'll test later in this course, so it's worth seeing it change with your own eyes before moving on.
