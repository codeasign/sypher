You have built up close to a dozen `.test.ts` files across this course by now, but every one of them has been run individually, one file at a time. This module starts by finally running all of them together, and immediately hits a real problem worth understanding before coverage numbers mean anything at all.

## What happens the first time you run everything together

```bash
npx jest
```

Run this with more than one file in `tests-ts/` that imports `../server`, and here is what actually happens:

```bash
FAIL tests-ts/auth-helper.test.ts
  ● auth helper › logs in as each role and hits a protected endpoint

    listen EADDRINUSE: address already in use :::5000
```

This is not the dev-server conflict from earlier in this course; the dev server is stopped. This is happening between your *own test files*. Jest gives every test file a fresh module registry, so every file that does `import app from '../server'` independently re-triggers that same `app.listen(5000)` side effect you learned about back in the in-process testing module. The first file to reach that line wins the port; every other file's own attempt fails with the exact same `EADDRINUSE`, and because nothing in `server.js` catches that failure, it crashes the whole file's test run, not just that one assertion.

There is a second problem hiding right behind it, if you remove that crash and run with Jest's default parallelism (multiple worker processes at once):

```bash
SQLITE_BUSY: database is locked
```

Two test files running as genuinely separate OS processes, both writing to the same on-disk `database/rbac.db` file at the same moment, can collide at the SQLite level too: this app's fixed `DB_PATH` has no per-worker isolation, exactly as covered in the database testing module.

## The fix

Two small additions to `jest.config.js` solve both problems together:

```javascript
module.exports = {
  preset: 'ts-jest',
  testEnvironment: 'node',
  testMatch: ['**/tests-ts/**/*.test.ts'],
  setupFiles: ['./tests-ts/helpers/suppress-listen-errors.ts'],
  maxWorkers: 1,
  forceExit: true,
};
```

`maxWorkers: 1` solves the `SQLITE_BUSY` problem directly: it tells Jest to run every test file in a single worker process, one after another, so there is never more than one process touching the database file at once.

That alone does not fix `EADDRINUSE`, though: even within one process, each file still gets its own fresh module registry, so each one still tries to bind port `5000` fresh. `setupFiles` points at a new helper that runs before every single test file, and defuses that specific collision:

```typescript
// tests-ts/helpers/suppress-listen-errors.ts
import http from 'http';

const proto = http.Server.prototype as any;
const originalListen = proto.listen;
proto.listen = function (...args: any[]) {
  this.on('error', (err: any) => {
    if (err.code !== 'EADDRINUSE') throw err;
  });
  return originalListen.apply(this, args);
};
```

This patches `http.Server.prototype.listen`, a real Node core object, genuinely shared across every test file running in the same process, unlike the per-file module registry, so that *every* server this app tries to create gets an `'error'` handler attached right before it is told to listen. An `EADDRINUSE` on any server past the first one now just fires a handled, silent event instead of an unhandled exception that crashes the file. Supertest was never relying on this specific listener anyway (it opens its own ephemeral server per request), so a losing bind attempt costs nothing.

Run `npx jest` again with both changes in place, and every file passes, together, in one run, which is what actually makes a whole-suite coverage report possible in the first place.

## Endpoint coverage vs. code coverage

"Coverage" means two different things worth keeping separate:

**Code coverage** asks: which *lines* of the application's source code ran during the test suite? Jest can measure this directly with `--coverage`:

```bash
npx jest --coverage --collectCoverageFrom='src/routes/**/*.js'
```

Run against the suite built up through this course so far, the real output looks like this:

```bash
-------------------------|---------|----------|---------|---------|
File                     | % Stmts | % Branch | % Funcs | % Lines |
-------------------------|---------|----------|---------|---------|
All files                |   26.48 |     4.91 |     9.3 |   26.48 |
 appointment.routes.js   |   27.63 |     7.89 |      20 |   27.63 |
 auth.routes.js          |   52.77 |    21.42 |      50 |   52.77 |
 medicalRecord.routes.js |   16.66 |        0 |       0 |   16.66 |
 patient.routes.js       |   22.58 |        0 |       0 |   22.58 |
 user.routes.js          |      20 |        0 |       0 |      20 |
-------------------------|---------|----------|---------|---------|
```

That is a real, honest number from a small slice of this course's tests: most of this app's route code genuinely is not exercised yet by just a couple of spec files. `% Stmts` counts individual statements executed; `% Branch` counts which sides of `if`/`else`-style decisions were actually taken (much harder to fill in fully, and consistently the lowest number here); `% Funcs` counts distinct functions called at all.

**Endpoint coverage** asks a different, coarser question: of the 19 routes this app actually registers, how many have *any* test at all, regardless of how many lines or branches inside them got exercised? This is the same cross-check you built in the OpenAPI testing module, repurposed:

```typescript
it('every registered endpoint has at least one test file mentioning it', () => {
  const testedEndpoints = new Set([
    'POST /api/auth/login',
    'GET /api/appointments',
    'POST /api/appointments',
    'GET /api/patients',
    'GET /api/users',
    // ...grows as you write more spec files
  ]);
  // compare against the full registered list from the OpenAPI module
});
```

The two numbers tell you different things, and neither one alone is the whole picture. High endpoint coverage with low code coverage often means your tests hit the happy path of every endpoint but skip most of its error handling and edge cases. High code coverage concentrated on a few endpoints, with several endpoints untouched, means broad depth in a narrow slice of the app rather than broad breadth across it.

## Identifying real gaps in this suite

Looking at the real numbers above, `medicalRecord.routes.js` sits at 16.66%, the lowest of any route file, and a real, honest signal rather than an abstract example: this course has spent real depth on appointments and auth, but comparatively little direct test code exercising medical records specifically. That is an actionable, specific gap a real coverage report is supposed to surface, not a hypothetical one invented for this module.
