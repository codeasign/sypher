Every module so far has deliberately kept everything real: real app, real database, real password hashing, real tokens. That has been the right default. This module is about the narrow, deliberate exception: when replacing a piece of real behavior with a controlled fake actually makes a test better, and, just as important, when it quietly makes a test lie to you.

## This app doesn't have much to mock, and that's worth saying honestly

A lot of API testing material assumes you are testing against a payment gateway, an email provider, a third-party geocoding service, something genuinely external, slow, rate-limited, or costly to call in a test suite. The RBAC app does not have any of that. Everything it does (hashing passwords, signing tokens, storing data) happens locally, inside the same process your tests run in. There is no external dependency here to mock, and manufacturing one just to demonstrate `jest.mock()` would mean testing something that is not actually true about this app.

What this app *does* have is one piece of real, local work that is meaningfully slow relative to everything else it does: password hashing.

## A legitimate case for mocking: hashing cost

```typescript
const bcrypt = require('bcryptjs');
const start = Date.now();
await bcrypt.hash('somepassword', 10);
console.log(Date.now() - start, 'ms'); // 57ms, on a normal dev machine
```

57 milliseconds does not sound like much on its own, but `bcrypt.hash` runs on every single registration, and it is deliberately slow: that is the whole point of a hashing algorithm with a configurable cost factor, making brute-force attacks expensive. Across a test suite with dozens of tests that each register a fresh user just to get to the interesting part of the test, that cost adds up in a way that has nothing to do with what those particular tests are actually checking.

For tests where the correctness of hashing genuinely is not the point (say, a suite of registration *validation* tests, checking that a short username or invalid email gets rejected) mocking `bcryptjs` is a reasonable, deliberate trade:

```typescript
jest.mock('bcryptjs', () => ({
  hash: jest.fn(async (value: string) => `mocked-hash-of-${value}`),
  compare: jest.fn(async () => true),
}));

import app from '../server'; // import AFTER the mock is declared

it('registers a user without paying real hashing cost', async () => {
  const response = await request(app)
    .post('/api/auth/register')
    .send({
      username: 'validationtest',
      email: 'validationtest@example.com',
      password: 'password123',
      role: 'Patient',
      full_name: 'Validation Test User',
    });

  expect(response.status).toBe(201);
});
```

`jest.mock('bcryptjs', () => ({...}))` tells Jest: whenever any code in this test file (including code the app itself imports, like `auth.routes.js`) does `require('bcryptjs')`, hand it this fake object instead of the real library. The mock has to be declared before the `import app from '../server'` line. Jest hoists `jest.mock()` calls to the top of the file automatically specifically so this ordering works, but it is worth writing it in that order visually too, since that is the order it actually takes effect.

## What NOT to mock, proven, not just claimed

Here is the same mock, used somewhere it absolutely should not be: a test that is actually about whether authentication works correctly.

```typescript
jest.mock('bcryptjs', () => ({
  hash: jest.fn(async (value: string) => `mocked-hash-of-${value}`),
  compare: jest.fn(async () => true), // ALWAYS true
}));

import app from '../server';

it('logs in with the WRONG password — because compare is mocked to always succeed', async () => {
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'definitely-the-wrong-password' });

  console.log(response.status, response.body);
  // 200 -- a REAL, valid, usable admin token, from a genuinely wrong password.
});
```

Run that, and it does not just pass: it returns a real `200`, with a real, signed, usable admin JWT, for a password that is not the admin account's password. Mocking `compare` to always return `true` did not make the test faster and harmless; it silently deleted the entire thing the login endpoint exists to check. A test suite with this mock in place would keep passing right through an actual regression that broke password checking completely, which is close to the worst possible failure mode a test suite can have: reporting green while the thing it claims to verify is actually broken.

The rule that keeps this from happening: **never mock the specific behavior a test exists to verify.** A validation test mocking `hash` is fine, because that test is not about hashing, it is about whether a malformed `email` gets rejected before hashing is ever reached. A login-correctness test mocking `compare` is never fine, because password comparison *is* the thing being tested. The same caution applies to the app and the database themselves: mocking `app` or SQLite would mean you are no longer testing the RBAC application at all, you are testing your own mock's behavior back at yourself, which is exactly the trap the in-process approach from earlier in this course was designed to avoid in the first place.

## Try it

Write two versions of a test that registers a new user with a duplicate username (one that already exists, like `admin`) and expects the `409 Conflict` response the app returns for that case. Write one version with `bcryptjs` mocked, and one without. Confirm both pass identically, and explain, in your own words, why this particular test is a safe place to use the mock, using the same reasoning from this module rather than just copying the conclusion.
