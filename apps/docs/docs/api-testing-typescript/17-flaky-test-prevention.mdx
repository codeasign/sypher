A flaky test is one that passes sometimes and fails other times, with no change to the code being tested — which makes it worse than a test that's simply wrong. A consistently wrong test gets fixed quickly, because it's obviously broken. A flaky one erodes trust slowly: people start re-running failed suites "just in case," and eventually stop believing red means something's actually broken. This module is about three concrete causes, one of which you can reproduce right now in this exact app's own test suite.

## Shared state: a real, diagnosed example

The RBAC repo ships its own example tests in `tests/auth.test.js`, separate from the TypeScript suite you've been building. One of them is genuinely flaky, and the cause is worth tracing end to end, because it's the single most common source of flaky API tests in general: two pieces of setup code that both assume they're the only thing touching shared state.

Its `Role-Based Authorization Tests` block does this in `beforeAll`:

```javascript
await request(app).post('/api/auth/register').send({
  username: 'patient1',
  email: 'patient1@example.com',
  password: 'password123',
  role: 'Patient',
  full_name: 'Patient One',
});

const patientResponse = await request(app)
  .post('/api/auth/login')
  .send({ username: 'patient1', password: 'password123' });
patientToken = patientResponse.body.token;
```

This assumes `patient1` doesn't already exist. But `npm run seed` — the exact seed script this whole course has been running since the setup module — already creates a `patient1` account, with the password `pass@123`, not `password123`. Run this against a seeded database, and here's what actually happens: the `register` call fails with `409` (`"Username or email already exists"`), and the `login` call fails too, with `401` (`"Invalid credentials"`, since `password123` isn't the seeded account's real password). `patientResponse.body.token` is therefore `undefined`, and `patientToken` ends up as the string `undefined`.

Every later test in that block sends `Authorization: Bearer undefined` — a syntactically well-formed but completely invalid token. `jwt.verify` rejects it, and instead of the `403` with `"Access denied. Insufficient permissions."` the test expects for a patient being denied an admin-only action, it gets a *different* `403`, with `"Invalid or expired token"` — and the assertion `expect(response.body.error).toContain('Access denied')` fails, for a reason that has nothing to do with role-based authorization at all.

Whether this test passes or fails depends entirely on whether the database happens to already have a `patient1` user in it when the suite runs — which is exactly what makes it flaky rather than simply broken: it can pass on a fresh, unseeded database and fail on a seeded one, with zero code changes in between.

The fix is the same one from the fixtures module: don't assume a specific user doesn't exist (or does exist, or has a specific ID) — either look up what's actually there, or use a name that's guaranteed not to collide, like one built from a timestamp:

```typescript
const uniqueUsername = `flakytest_${Date.now()}`;
await request(app).post('/api/auth/register').send({
  username: uniqueUsername,
  email: `${uniqueUsername}@example.com`,
  password: 'password123',
  role: 'Patient',
  full_name: 'Flaky Test Patient',
});
```

## Timing assumptions

JWTs encode their `iat` (issued-at) and `exp` (expiry) claims as Unix timestamps in whole seconds, not milliseconds — that's part of the JWT specification itself, not something specific to this app. Two tokens issued within the same second carry an identical `iat`. A test asserting "this second token was issued strictly after the first one" by comparing `iat` values directly can fail intermittently, purely depending on how fast two requests happen to run relative to the second boundary — nothing about the app is actually broken when that happens.

The general principle: don't assert on wall-clock ordering or exact timing unless you have a real reason to believe the values can't collide. If you do need to prove one thing happened after another, assert on something that's actually guaranteed to differ — an auto-incrementing ID, or an explicit sequence you control — rather than a timestamp that might not have enough resolution to tell two fast operations apart.

## Unclosed connections

You've already met this one directly, back when you first ran a test file that imports `server.js`: the app's `app.listen()` call is triggered as a side effect of the import, and nothing in this app ever closes that listener — which is exactly why `jest.config.js` sets `forceExit: true`. Without it, Jest would hang after every single run, and depending on your CI environment's timeout settings, that hang can look like an intermittent failure rather than a consistent one — a job that sometimes finishes just under the timeout and sometimes doesn't, purely based on system load that has nothing to do with your tests.

The database helper from the database-testing module has the same category of risk in miniature: `queryOne(...)` opens a fresh SQLite connection on every call and closes it (`db.close()`) once the query resolves. Forgetting that `close()` call wouldn't break any individual test, but it would leave connections accumulating across a large suite — the kind of resource leak that doesn't show up as a clean, repeatable failure, just as things getting slower and occasionally timing out the more tests you run in one process.

The pattern worth internalizing: anything your tests open — a listener, a connection, a file handle — has to be explicitly closed somewhere, or configured to be force-terminated deliberately (`forceExit`), rather than left for the process to sort out on its own.

## Avoiding hardcoded waits

You won't find a single `setTimeout`-based wait anywhere in this course, and that's deliberate, not an accident of the examples chosen. Every asynchronous operation this app does — a database write, a hashed password, a signed token — is something Supertest and `await` can wait on directly and deterministically. A hardcoded wait like `await new Promise(r => setTimeout(r, 500))` is a guess about how long something takes, and guesses are exactly where flakiness comes from: too short, and the test fails on a slow CI runner even though the app is fine; too long, and every test run wastes time waiting for something that already finished. Every wait in this entire course is `await`ing a real promise tied to a real operation completing — never a fixed amount of clock time — and that's the discipline worth carrying into every test you write from here on.

## Try it

Fix the actual flaky test: copy the `Role-Based Authorization Tests` block from `tests/auth.test.js` into your own TypeScript suite, and change its `beforeAll` to use `getFirstUserWithRole('Patient')` from the fixtures module instead of registering a fresh `patient1`. Run it against a freshly seeded database, then reseed and run it again — confirm it passes both times, unlike the original.
