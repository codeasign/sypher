Field-by-field assertions work, but they do not scale well. A response with fifteen fields means either fifteen `toHaveProperty` calls or one large `toMatchObject` block, and either way, a field silently changing type (a `string` that becomes a `number`, say) is easy to miss unless you happened to assert on that exact field. Schema validation flips the approach: define the shape a response is supposed to have once, and let a validation library check the whole thing against real data automatically.

## Installing Zod

[Zod](https://zod.dev) is a TypeScript-first schema library: you define a schema as a value, and TypeScript can infer a matching type from it automatically, so your schema and your types never drift apart.

```bash
npm install --save-dev zod
```

## Defining a schema

Here is a schema for the login response you have been testing since the authentication module:

```typescript
import { z } from 'zod';

const LoginResponseSchema = z.object({
  token: z.string(),
  user: z.object({
    id: z.number(),
    username: z.string(),
    email: z.string(),
    role: z.enum(['Administrator', 'Doctor', 'Nurse', 'Patient']),
    full_name: z.string(),
  }),
});
```

Each field gets a validator describing its expected type (`z.string()`, `z.number()`, and so on) and `z.enum([...])` restricts a field to one of a fixed set of values, which is exactly what `role` actually is in this app. Nesting `z.object({...})` inside another `z.object({...})` mirrors the real nested shape of the response.

## Validating a real response against it

```typescript
import request from 'supertest';
import { z } from 'zod';
import app from '../server';

it('validates the login response shape', async () => {
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'admin123' });

  const result = LoginResponseSchema.safeParse(response.body);

  expect(result.success).toBe(true);
});
```

`safeParse` checks the value against the schema and returns a result object instead of throwing: `{ success: true, data: ... }` if it matches, or `{ success: false, error: ... }` if it does not. That makes it easy to assert on in a test (`expect(result.success).toBe(true)`) without wrapping anything in a `try`/`catch`. If you ever want validation to throw immediately instead, useful outside of tests, in application code, `schema.parse(value)` does that.

When validation fails, `result.error.issues` tells you exactly what did not match and where:

```json
[
  {
    "expected": "number",
    "code": "invalid_type",
    "path": ["role"],
    "message": "Invalid input: expected number, received string"
  }
]
```

That `path` array is what makes schema validation worth the setup: instead of a generic assertion failure, you get the exact field, and exactly what was expected versus what showed up.

## Validating a whole array at once

The real payoff shows up on list endpoints, where field-by-field assertions get repetitive fast. Wrap a schema in `z.array(...)` and validate every item in one call:

```typescript
const AppointmentSchema = z.object({
  id: z.number(),
  patient_id: z.number(),
  doctor_id: z.number(),
  appointment_date: z.string(),
  status: z.enum(['scheduled', 'completed', 'cancelled']),
  reason: z.string().nullable(),
  notes: z.string().nullable(),
  patient_name: z.string(),
  doctor_name: z.string(),
});

it('validates every appointment in the list', async () => {
  const admin = await loginAs('Administrator');
  const response = await request(app)
    .get('/api/appointments')
    .set(authHeader(admin.token));

  const result = z.array(AppointmentSchema).safeParse(response.body);

  expect(result.success).toBe(true);
});
```

That one assertion validates the type and shape of every appointment the seeded database returns, not just the first one, and not just the fields you happened to think to check. Notice `reason` and `notes` are `.nullable()` rather than plain `z.string()`: the real API does return `null` for `notes` when none was provided, and a schema that did not account for that would fail on perfectly valid data. Matching a schema to reality, not to what you assume the shape should be, is the whole point.

## Why this catches contract drift

"Contract drift" is what happens when an API's actual behavior quietly diverges from what callers expect (a field renamed, a type changed from a number to a string, a previously-required field made optional) without anyone updating the tests that were supposed to catch it. Field-by-field assertions only catch drift in the exact fields you wrote an assertion for. A schema, defined once against the full shape, catches drift anywhere in that shape automatically, including in fields nobody thought to assert on individually. That is the tradeoff worth internalizing: schema validation costs a bit more setup upfront, in exchange for structural coverage you would otherwise have to maintain by hand, field by field, forever.

## Try it

Write a `MedicalRecordSchema` covering the fields returned by `GET /api/medical-records/:id`, and validate a real record against it after creating one as a doctor. Deliberately get one field wrong on purpose first, type `diagnosis` as `z.number()` instead of `z.string()`, run the test, and read the exact `path` and `message` Zod gives you back before fixing it.
