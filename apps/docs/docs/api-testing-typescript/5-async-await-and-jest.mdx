Every single test you have written so far has used `async`/`await`. This page slows down and explains exactly why that is non-negotiable for API tests, and walks through the mistakes that trip people up when they first get here.

## Why API tests are async by nature

Sending a request and getting a response back is not instantaneous. Even in-process, against a local database, there is real work happening: Express routes the request, middleware checks the token, a query runs against SQLite, a response gets built. None of that happens in the same tick of the event loop as the line of code that kicked it off.

Supertest reflects that honestly: `request(app).post(...)` does not return a response, it returns a `Promise` that *eventually* resolves to one. `async`/`await` is what lets you write code that waits for that promise to settle before moving on to the next line, while still reading top-to-bottom like ordinary synchronous code:

```typescript
it('logs in as admin', async () => {
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'admin123' });

  expect(response.status).toBe(200);
});
```

The `async` keyword on the test function tells Jest "this test returns a promise, wait for it before deciding pass or fail." The `await` inside pauses execution of that function at that exact line until the login request actually resolves. Skip either half of that, and things go wrong in ways that are worth seeing on purpose, once, so you recognize them immediately later.

## What happens when you forget `await`

Here is the same test with the `await` dropped:

```typescript
it('shows what happens without await', () => {
  const response = request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'admin123' });

  console.log('response.status:', response.status);
  expect(response.status).toBe(200);
});
```

Run that, and here is exactly what prints:

```bash
response.status: undefined

Expected: 200
Received: undefined
```

`response` here is not a response at all, it is still the pending request object Supertest builds up before it is ever sent. Reading `.status` off it does not error, because that property genuinely does not exist yet on that object; it just comes back `undefined`. The test does fail, which is the good news, but it fails with a confusing "expected 200, received undefined" instead of a message that points you straight at the missing `await`. The moment you see a test fail with an unexpected `undefined` where a real value should be, forgetting `await` on the request that produced it is the very first thing worth checking.

## The "missing return" version of the same mistake

You will occasionally see async code written with `.then()` chains instead of `await`, and if you ever do reach for that style, there is a matching trap: forgetting to `return` the promise.

```typescript
// Broken: the promise chain isn't returned, so Jest doesn't wait for it
it('logs in as admin', () => {
  request(app)
    .post('/api/auth/login')
    .send({ username: 'admin', password: 'admin123' })
    .then((response) => {
      expect(response.status).toBe(200);
    });
});
```

Jest has no way to know this test is still doing async work, because the test function itself returns `undefined` immediately: the `.then()` callback, with the actual assertion inside it, might not even run until *after* Jest has already decided the test passed. That is a worse failure mode than the missing-`await` case: instead of a confusing failure, you can get a false pass, with your assertion never actually checked. `async`/`await` avoids this entirely, since an `async` function always returns a promise Jest automatically waits on, which is exactly why every test in this course is written that way, and why it is the style worth defaulting to rather than mixing in `.then()` chains by hand.
