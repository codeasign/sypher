Every module so far has added one more file to `tests-ts/`. At this point you already have `helpers/auth.ts`, `helpers/fixtures.ts`, `helpers/db.ts`, and `helpers/spec.ts`, alongside a growing number of spec files. This module is about the shape that growth should keep taking as the suite gets genuinely large: not a new technique, but the organizing principle behind everything you have already built.

## The folder structure this course has been building toward

```text
backend/
  tests-ts/
    helpers/
      auth.ts        loginAs(role), authHeader(token)
      fixtures.ts     getFirstUserWithRole(role)
      db.ts           queryOne(sql, params) — direct SQLite verification
      spec.ts         getOpenApiSpec() — the app's own OpenAPI spec, as data
    appointments.test.ts
    medical-records.test.ts
    patients.test.ts
    users.test.ts
    auth.test.ts
    rbac-matrix.test.ts
    security.test.ts
  jest.config.js
  tsconfig.json
```

Two kinds of file live in `tests-ts/`, and they have different jobs. **Helpers** know *how* to do something generic (log in, look up a fixture, query the database, fetch the spec) without knowing anything about which specific test is calling them. **Specs** (the `.test.ts` files) know *what* is being verified for a specific piece of the app, and lean on the helpers rather than re-deriving that "how" themselves. That split is exactly why the authentication module built `loginAs` once instead of letting every module since re-write its own login logic: every spec file from that point on has been able to stay focused on what it is actually testing.

## Organizing specs by resource, not by test type

Notice the spec files above are named after what they test (`appointments.test.ts`, `users.test.ts`) rather than after the kind of test inside them (there is no `crud.test.ts` or `negative.test.ts` sitting alongside them). A resource-based split means everything about testing appointments (its CRUD lifecycle, its RBAC rules, its negative cases) lives in one file, which is where you would actually go looking when appointments-related behavior changes. A test-type-based split scatters that same knowledge across several files, and touching one endpoint means remembering to check all of them.

This is not a hard rule: a suite testing something with far more cross-cutting concerns than this app might reasonably split differently. But for a REST API organized around a handful of clear resources, matching your test files to those resources keeps the mental model simple: one file per "thing," the same way the app itself is organized one route file per resource.

## Config lives at the root, once

`jest.config.js` and `tsconfig.json` sit at the `backend/` root, not inside `tests-ts/`: they are project-level configuration, read once when the suite starts, not something any individual spec or helper needs to reach into. Keeping them at the root also matches where the app's own `package.json` lives, so `npm test` (or `npx jest`) works the same way regardless of which subfolder you are currently working in.

## What belongs in a helper vs. what doesn't

A good helper does one clearly-named thing and has no opinion about which test calls it. `loginAs('Doctor')` does not know or care whether the test that calls it is checking CRUD behavior, RBAC, or security: it just returns a valid session for that role. That is what makes it reusable across close to every spec file in this course.

A helper that started returning different results depending on which test file imported it, or that hardcoded assumptions specific to one test ("assume this is being called from the appointments suite"), would stop being a helper and start being hidden, fragile coupling between files that look independent but secretly are not. If you notice a helper growing a parameter whose only purpose is "so this one specific test can get different behavior," that is usually a sign the logic belongs in that specific test instead, not in the shared helper.
