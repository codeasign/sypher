Every test in this course so far started from an endpoint that already existed, and you wrote a test against its actual behavior. Real work often runs the other direction: someone hands you a requirement or a user story, and you have to figure out what "correctly implemented" even means in terms of concrete, checkable test cases — ideally before the feature is even fully built.

## Starting from a requirement, not an endpoint

Take a realistic, plainly-worded requirement for this app:

> As a Nurse, I need to be able to view and manage patient appointments so I can keep the schedule up to date, but I should not have access to sensitive medical record details, since that's outside a nurse's role.

That's a real product requirement, in the kind of language it would actually arrive in — no status codes, no endpoint names, no mention of tests at all. Test design starts by translating it into specific, checkable claims, and this course has already built every tool needed to verify each one.

## Turning the requirement into concrete test cases

Breaking that one sentence down, clause by clause, produces a real test-case list:

| Claim from the requirement | Concrete test case |
|---|---|
| Nurse can view patient appointments | `GET /api/appointments` as Nurse → `200`, returns appointments |
| Nurse can manage (update) appointments | `PUT /api/appointments/:id` as Nurse → `200` |
| Nurse should not see sensitive medical record details | `GET /api/medical-records` as Nurse → **check actual behavior** |
| Nurse should not see sensitive medical record details | `POST /api/medical-records` as Nurse → `403` |

That third row is worth pausing on, because it's exactly the kind of gap real test design is supposed to surface *before* code ships, not after. Checking this app's actual, verified behavior from the RBAC matrix module: `GET /api/medical-records` has no role restriction at all — a Nurse can currently list every medical record in the system, which directly contradicts what this requirement asks for. A test case here isn't just "does the code do what's expected" — it's "here's a specific, written-down claim from the requirement, and here's whether the app currently satisfies it." Writing the test *first*, against the requirement, surfaces this mismatch as a concrete, actionable finding — "this requirement isn't met, here's exactly where" — rather than something someone happens to notice by accident later.

## From test cases to code

Each row in a table like that maps directly onto the patterns you've already built:

```typescript
describe('Nurse appointment and medical-record access', () => {
  it('can view appointments', async () => {
    const nurse = await loginAs('Nurse');
    const response = await request(app).get('/api/appointments').set(authHeader(nurse.token));
    expect(response.status).toBe(200);
  });

  it('can update an appointment', async () => {
    const nurse = await loginAs('Nurse');
    const patient = await getFirstUserWithRole('Patient');
    const doctor = await getFirstUserWithRole('Doctor');
    const created = await request(app)
      .post('/api/appointments')
      .set(authHeader(nurse.token))
      .send({ patient_id: patient.id, doctor_id: doctor.id, appointment_date: '2026-10-01T09:00:00', reason: 'checkup' });

    const updated = await request(app)
      .put(`/api/appointments/${created.body.appointmentId}`)
      .set(authHeader(nurse.token))
      .send({ status: 'completed' });
    expect(updated.status).toBe(200);
  });

  it('cannot create a medical record', async () => {
    const nurse = await loginAs('Nurse');
    const patient = await getFirstUserWithRole('Patient');
    const response = await request(app)
      .post('/api/medical-records')
      .set(authHeader(nurse.token))
      .send({ patient_id: patient.id, diagnosis: 'test' });
    expect(response.status).toBe(403);
  });

  it('documents the current gap: a Nurse CAN list all medical records', async () => {
    const nurse = await loginAs('Nurse');
    const response = await request(app).get('/api/medical-records').set(authHeader(nurse.token));
    // The requirement says a Nurse shouldn't see this. The app currently allows it.
    // This test documents that gap explicitly rather than silently ignoring it.
    expect(response.status).toBe(200);
  });
});
```

That last test is deliberately named to say what it actually is: not a claim that the current behavior is *correct*, but an honest record of what the app *does*, written against a requirement it doesn't yet fully satisfy. Test cases like this are exactly what gets handed back to whoever owns the requirement — a specific, reproducible, already-written finding, instead of a vague "I think nurses can see too much."

## The general shape of this process

Regardless of the specific feature, going from requirement to test design follows the same few steps every time: read the requirement and pull out every distinct, checkable claim it makes (not just the obvious happy path — "should not" clauses are claims too, and often the ones nobody double-checks); map each claim onto a specific request against a specific endpoint with a specific role; run it against the real app and record what actually happens, whether or not it matches expectations; and only then decide whether a mismatch is a bug to report, a requirement to clarify, or — as with the Nurse and medical records case above — a real, existing gap worth surfacing on its own.

## Try it

Take this requirement: "As a Patient, I should only ever be able to book an appointment for myself, never for another patient." Break it into a table of concrete test cases the way this module did, then write one real test against the actual app for each row. You've already found the relevant behavior earlier in this course — decide whether each resulting test documents a met requirement or an unmet one, and name each test accordingly.
