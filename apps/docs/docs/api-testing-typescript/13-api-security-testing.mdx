Negative testing checks that the API fails the way you'd expect. Security testing goes further — it actively tries to make the API do something it shouldn't, on behalf of someone it shouldn't. This module finds one genuine, verified gap in the RBAC app, and confirms two things it defends against correctly.

## JWTs are signed, not encrypted

Before testing anything, it's worth seeing this directly: a JWT is base64-encoded and cryptographically **signed**, not encrypted. Anyone holding a token can read its contents without ever knowing the server's secret — decoding the middle segment of any real token proves it:

```typescript
const token = patientSession.token;
const payload = token.split('.')[1];
console.log(Buffer.from(payload, 'base64url').toString());
// {"id":20,"username":"patient1","role":"Patient","iat":...,"exp":...}
```

That's not a vulnerability by itself — nothing sensitive (like a password) is in there — but it's a fact worth internalizing before testing auth: a token being unreadable was never part of its security model. What actually protects the app is that a token can't be *modified* without invalidating its signature, which is exactly the next thing worth confirming directly rather than assuming.

```typescript
it('rejects a token with a tampered payload, even if the shape looks valid', async () => {
  const patient = await loginAs('Patient');
  const [header, payload, signature] = patient.token.split('.');

  const decoded = JSON.parse(Buffer.from(payload, 'base64url').toString());
  const tamperedPayload = Buffer.from(
    JSON.stringify({ ...decoded, role: 'Administrator' }),
  ).toString('base64url');
  const forgedToken = `${header}.${tamperedPayload}.${signature}`; // old signature, new claims

  const response = await request(app)
    .get('/api/users')
    .set('Authorization', `Bearer ${forgedToken}`);

  expect(response.status).toBe(403);
  expect(response.body.error).toBe('Invalid or expired token');
});
```

Editing the payload without the server's secret invalidates the signature, and `jwt.verify` rejects the whole token outright — you can't escalate a role by hand-editing a token's claims. That's a real assertion worth having in a suite: it turns "the app is presumably safe from this" into "this app is confirmed safe from this, on every test run."

## SQL injection resistance

Every query in this app's route handlers uses parameterized placeholders (`?`) rather than building SQL by string concatenation — which means user input is passed as data, never interpreted as part of the query itself. Confirming that holds is a one-line test:

```typescript
it('does not let a SQL injection payload bypass login', async () => {
  const response = await request(app)
    .post('/api/auth/login')
    .send({ username: "admin' OR '1'='1", password: 'anything' });

  expect(response.status).toBe(401);
  expect(response.body.error).toBe('Invalid credentials');
});
```

This test is expected to pass, and that's the point — not every security test exists to catch a bug. Some exist to lock in a defense that already works, so a future refactor that accidentally swaps a parameterized query for string concatenation gets caught immediately instead of shipping quietly.

## A real, verified gap: parameter tampering on appointment creation

Here's one that isn't a defense holding up — it's a genuine finding. `POST /api/appointments` takes `patient_id` directly from the request body, and never checks it against the identity of whoever is actually authenticated. A patient can create an appointment *as* a different patient entirely:

```typescript
it('lets a patient create an appointment under a different patient_id (parameter tampering)', async () => {
  const patient1 = await loginAs('Patient'); // patient1, userId 20

  const response = await request(app)
    .post('/api/appointments')
    .set(authHeader(patient1.token))
    .send({
      patient_id: 28, // a completely different patient — not patient1's own id
      doctor_id: 5,
      appointment_date: '2026-09-05T10:00:00',
      reason: 'tampered',
    });

  // Documenting the app's real, current behavior: this succeeds.
  expect(response.status).toBe(201);
  expect(response.body).toHaveProperty('appointmentId');
});
```

Run it against the real app, and it does succeed — `201`, a real `appointmentId` back, and a row in the database attributing an appointment to patient 28 that patient 20 never should have been able to create. This is exactly the kind of thing this module exists to catch: not a hypothetical, but a request you can actually send, right now, that does something a well-designed permission model shouldn't allow.

Writing that test isn't about breaking the app for its own sake — it's about turning an assumption ("surely a patient can only book for themselves") into a documented, verifiable fact about what the API currently does, whether or not that fact is the one you'd want. A test like this is genuinely valuable sitting in a suite even while the gap remains unfixed — the day someone adds the missing ownership check, this exact test is the one that will need to flip from `toBe(201)` to `toBe(403)`, and until then it's an honest, live record of the actual risk.

## Try it

`POST /api/medical-records` takes a `patient_id` in its body too, and it's Doctor-only. Log in as `doctor1` and try creating a medical record with a `patient_id` that isn't one of that doctor's actual patients — does the same gap exist here, or does this route behave differently? Write the test, run it against the real app, and let the actual response tell you which it is rather than assuming it matches the appointments endpoint.
