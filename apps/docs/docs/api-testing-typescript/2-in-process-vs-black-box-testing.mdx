There are two fundamentally different ways to test an API, and it's worth understanding both before you write a single test, because the choice shapes everything downstream — how fast your suite runs, what it can and can't catch, and how much setup it needs.

## Black-box: testing over the network

The way most people picture API testing is **black-box**: the server is running somewhere — on your machine, in a container, in a staging environment — and your test sends a real HTTP request over the network to reach it, the same way a mobile app or a browser would.

```typescript
// Black-box: talking to a server that has to already be running
const response = await fetch('http://localhost:5000/api/auth/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ username: 'admin', password: 'admin123' }),
});
```

This is called black-box because your test treats the server as a sealed box: it doesn't know or care what's running inside — Express, Fastify, a different language entirely — it only knows the box accepts HTTP requests and returns HTTP responses. That's genuinely valuable: it's the most realistic possible test, because it's exercising the exact same network boundary a real client would cross. It also means the server has to already be up and reachable before the test can run.

## In-process: importing the app directly

The other approach — the one this course is built around — is **in-process**: instead of sending a request over the network to a running server, your test imports the application object directly, in the same process as the test itself, and drives it with a library that simulates HTTP requests without ever touching a real socket.

```typescript
// In-process: importing the app itself, no server needs to be running
import request from 'supertest';
import app from '../server';

const response = await request(app)
  .post('/api/auth/login')
  .send({ username: 'admin', password: 'admin123' });
```

That `app` is the same Express application object the real server uses — same routes, same middleware, same validation, same database queries. Supertest wraps it in a lightweight, ephemeral HTTP server under the hood for the duration of each request, but it's not the server you'd deploy — it's spun up in memory, for that one call, entirely within your test process. Nothing about your route logic, your middleware, or your authorization checks changes; what changes is how the request physically gets there.

## What each approach catches — and misses

Black-box testing is the more complete picture in one specific sense: it exercises everything between your test and the server, including things that live outside your application code entirely — a reverse proxy, TLS termination, a load balancer, DNS. If any of that layer is broken, only a black-box test sitting on the other side of it will notice.

What it costs you is speed and control. Every request is a real network round trip, so a suite of even a few hundred tests gets noticeably slow. And because the server is a separate, already-running process, you have far less control over its exact state — you can't as easily reset it between tests, or reach in and verify what actually happened at the database level, without going through the API again.

In-process testing gives up that outer layer entirely — you're not testing your reverse proxy or your deployment config, because there isn't one here. What you get in exchange: tests that run in milliseconds instead of tens of milliseconds each, no separate process to start, stop, or babysit, and a test process that's the same Node.js process your test data setup and database assertions run in, so you can freely mix API calls with direct checks against the database when you need to (you'll do exactly that in the database testing module).

For testing the actual behavior of your routes, middleware, and authorization logic — which is the overwhelming majority of what a healthy API test suite spends its time doing — in-process gets you the same signal, faster and with less to manage.

## Why this course tests in-process

Every module from here on imports the RBAC app's Express `app` object directly rather than sending requests to a separately running server. That's a deliberate choice, not just a convenience — API tests that run in milliseconds are tests people actually run constantly, on every save, not just once before a merge.

There's a real, concrete wrinkle worth knowing about upfront, because you'll hit it the moment you write your first in-process test: this particular app's `server.js` starts listening on port `5000` as a side effect of being loaded — it wasn't written with a guard like `if (require.main === module)` to skip that step when it's imported rather than run directly. That means importing it in a test does two things at once: it gives you the `app` object to test against, and it also tries to bind port `5000` for real, exactly like running `npm start` would.

Two consequences follow directly from that, and both are things you'll actually see:

- **If your dev server is already running on `:5000` when you run the test suite, the import throws `EADDRINUSE`** — port already in use. The fix isn't complicated once you know the cause: stop the dev server before running tests. You'll never need both running at once, since your tests don't need a separately running server at all.
- **After the last test finishes, Jest hangs instead of exiting**, because that `app.listen()` call is still holding the process open, and the code doesn't export the underlying server object, so there's nothing for a test to explicitly close. The practical fix, and the one you'll configure in the next module, is running Jest with `--forceExit` so it exits cleanly once your tests are done rather than waiting forever on a listener nothing can reach.

Neither of these is a flaw in your test code — they're a property of the specific app you're testing, and knowing about them now means you won't waste time debugging a mysterious hang later, wondering what you did wrong.

## Try it

With the dev server stopped, write a throwaway two-line script that imports the RBAC app's `server.js` with `require('../server')` and logs `typeof app` (it'll be `'function'` — an Express app is callable). Then, while that script is still running in one terminal, open a second terminal and try starting the dev server with `npm start`. Read the error it gives you, and connect it back to what you just learned about why it happens.
