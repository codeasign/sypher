Every test in this course has run on your own machine so far. This module wires the exact same suite into GitHub Actions, so it runs automatically on every push and pull request — and because this course tests in-process, the workflow ends up simpler than you might expect: there's no separate server to start and keep alive in the background at all.

## What CI actually needs to do

Walking backward from `npx jest` to a clean checkout, four things have to happen in order:

1. **Install dependencies** — the usual `npm install`.
2. **Create the database schema** — `server.js` only creates its tables as a side effect of `initializeDatabase()`, which normally only runs when the server boots. Since this course's tests never start a long-running server, CI needs its own small, one-shot way to create that schema before seeding can work.
3. **Seed the database** — `npm run seed` needs the tables to already exist, exactly as you saw back in the setup module.
4. **Run the suite** — `npx jest`, importing the app fresh, entirely in-process, the same way it's run on your machine.

## A schema-init script for CI

`seed.js` opens its own direct connection to `database/rbac.db` and expects the tables to already be there — it doesn't create them itself. Rather than starting the whole server just to trigger that side effect (and then having to remember to stop it again), a tiny standalone script does exactly the one thing CI actually needs:

```javascript
// backend/init-db.js
const { initializeDatabase } = require('./src/config/database');

initializeDatabase()
  .then(() => {
    console.log('Schema ready.');
    process.exit(0);
  })
  .catch((err) => {
    console.error(err);
    process.exit(1);
  });
```

This calls the exact same `initializeDatabase()` function `server.js` calls internally, without ever touching `app.listen()` — no port gets bound, nothing lingers, and the process exits cleanly the moment the tables exist. Run it once, and `npm run seed` has everything it needs.

## The workflow

```yaml
# .github/workflows/api-tests.yml
name: API Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install dependencies
        run: npm install

      - name: Set up environment
        run: |
          mkdir -p database
          echo "PORT=5000" >> .env
          echo "JWT_SECRET=${{ secrets.TEST_JWT_SECRET }}" >> .env
          echo "NODE_ENV=test" >> .env

      - name: Create database schema
        run: node init-db.js

      - name: Seed database
        run: npm run seed

      - name: Run tests
        run: npx jest

      - name: Upload HTML report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: backend/html-report/
```

A few details worth explaining. `defaults.run.working-directory: backend` means every `run:` step executes inside `backend/` automatically, so the workflow doesn't need `cd backend &&` repeated on every line. `secrets.TEST_JWT_SECRET` is a GitHub Actions secret rather than a literal string in the workflow file — even though this is only used to sign test tokens in a throwaway CI database, hardcoding secrets directly into a checked-in YAML file is a habit worth never forming, test-only or not. `if: always()` on the upload step means the HTML report from the reporting module gets uploaded whether the tests passed or failed — a report is arguably more useful on a failing run than a passing one, so skipping the upload specifically when something broke would defeat its purpose.

Notice what's absent: no step starts the app and leaves it running in the background, no step waits for a health check to confirm a server came up, no step has to remember to shut anything down afterward. `npx jest` in the last real step imports the app fresh, the same way every test file has all along — CI is just a clean environment running the identical command you've been running locally the whole course.

## Making it a required check

Once this workflow exists and has run successfully at least once, go to the repository's branch protection settings and add **API Tests** as a required status check for the `main` branch. From that point on, a pull request that fails this workflow can't be merged — the exact same suite you've been building becomes an actual gate on the codebase, not just documentation of intent.

## Try it

Add a matrix strategy to the workflow that runs the suite against two Node.js versions (for example, 18 and 20) using `strategy.matrix.node-version` and `node-version: ${{ matrix.node-version }}` in the `setup-node` step. Push it and confirm two separate jobs show up in the Actions tab, each running the full suite independently.
