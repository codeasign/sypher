## What RAG adds

A plain LLM call answers from whatever the model learned during training — nothing else. That's exactly what produced the fabricated rate limit and fabricated survey statistic back in Module 2: the model had no real source to answer from, so it filled the gap with something plausible-sounding.

**RAG (Retrieval-Augmented Generation)** adds one step before generation: look up relevant text from a real source — Fernwood's docs, in this course — and hand it to the model as context, so it can answer *from that text* instead of guessing. RAG doesn't eliminate hallucination (Module 8 and Module 14 both show you real cases where it still happens), but it gives the model something real to ground its answer in, and gives you, the QE, something concrete to check the answer against.

**Chunking** — splitting a document into smaller pieces before doing anything else with it. You can't hand an entire document to a retrieval step and ask "is this relevant" usefully — you need small enough pieces that a single chunk is about one specific thing, so a search can tell them apart. Fernwood's `billing-and-plans.md` is short enough to treat as one chunk per file for this course's system; a real document set would usually split each file into several chunks (by paragraph or heading).

**Embedding** — turning a piece of text into a list of numbers (a vector) that captures its meaning, produced by a model trained specifically for this. Two pieces of text with similar meaning end up with similar vectors, even if they don't share many of the same words.

**Vector search / retrieval** — given the user's question, embed the question the same way, then find which chunk embeddings are numerically closest to it. "Closest" is usually measured with **cosine similarity** — a number from -1 to 1, where 1 means "pointing in exactly the same direction" (very similar meaning) and 0 means unrelated.

**Context** — the retrieved chunks, handed to the model along with the question, with an instruction to answer only from what's given.

**Generation** — the model producing an answer using that context, the same `ollama.chat()` call from Modules 1–2, just with a different, more constrained prompt.

## Hands-on: compute a real embedding similarity

Pull the embedding model this course uses:

```bash
ollama pull nomic-embed-text
```

This is a small, isolated example — one concept, in isolation, before Module 5 folds it into the real pipeline:

```python
# experiments/embedding_similarity.py
import ollama

def embed(text: str) -> list[float]:
    response = ollama.embeddings(model="nomic-embed-text", prompt=text)
    return response.embedding

def cosine_similarity(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = sum(x * x for x in a) ** 0.5
    norm_b = sum(y * y for y in b) ** 0.5
    return dot / (norm_a * norm_b)

question = "How many projects can I have on the Free plan?"
related_chunk = "The Free plan supports up to 3 active projects."
unrelated_chunk = "Invite a teammate to a project from Project Settings."

emb_question = embed(question)
emb_related = embed(related_chunk)
emb_unrelated = embed(unrelated_chunk)

print("question vs. related:  ", cosine_similarity(emb_question, emb_related))
print("question vs. unrelated:", cosine_similarity(emb_question, emb_unrelated))
```

Run it:

```bash
python experiments/embedding_similarity.py
```

**Run it now.** The "question vs. related" score should come out noticeably higher than "question vs. unrelated" — that gap *is* retrieval. A vector search over more chunks is doing exactly this comparison, at scale, and returning whichever chunks scored highest.

## Where each stage can fail

Keep this list — Module 5 triggers one of these on purpose, and Module 8 spends an entire module diagnosing failures across all four:

- **Chunking failure** — a chunk is too big (mixes unrelated facts, hurting the embedding's precision) or too small (loses the surrounding context that made it meaningful).
- **Embedding failure** — the embedding model doesn't capture the similarity a human reader would see immediately (different wording for the same concept scores lower than expected).
- **Retrieval failure** — the right chunk exists and is embedded fine, but doesn't rank high enough to be returned — a **retrieval miss**. This is the specific failure Module 5 triggers on purpose.
- **Generation failure** — retrieval worked, the right chunk made it into context, but the model still answers incorrectly, ignores the context, or adds something not actually in it.

Modules 6–8 give you a systematic way to tell these apart instead of guessing which one happened.

## QE lesson

Notice the shape of what you just did: isolate one stage (embedding), give it a clean input where you already know the expected relationship (related vs. unrelated), and check the actual output against that expectation. That's unit testing applied to a pipeline stage instead of a function — and it's exactly the instinct Module 8 formalizes into a real debugging method for the full pipeline.
