## Page purpose

RAGAS's metrics are LLM-as-a-judge evaluators someone else already built and validated. This page has you build one yourself, from scratch, with Ollama — so the mechanism stops being a black box, and so you have the skill for the cases (Module 11's UX rubric, Module 14's custom checks) where no built-in RAGAS metric fits.

## Learning objectives

By the end of this page, you should be able to:

- Explain what LLM-as-a-judge means and how it differs from the metrics you've been calling.
- Write a structured judge prompt that returns a parseable verdict.
- Choose between pass/fail and score-based evaluation for a given case.
- Validate a judge against known-good and known-bad cases before trusting its verdict on anything else.

## What LLM-as-a-judge actually is

Every RAGAS metric you ran in Modules 6–8 is this same idea, already built: an LLM given a rubric, given the thing to evaluate, asked to return a structured verdict. There's nothing more exotic underneath faithfulness or context recall than that. Building your own gives you a tool for whatever a QE needs to check that doesn't already have a maintained RAGAS metric — and it forces you to confront the real risk of this whole approach head-on: **the judge is itself an LLM call, with everything about LLMs you've learned since Module 1 — including that it can be wrong, and that it can be inconsistent between runs.**

## A judge prompt, and structured output

Write the rubric explicitly, and force a parseable response:

```python
# eval/judge.py
import json
import ollama

JUDGE_MODEL = "llama3.2:3b"

JUDGE_PROMPT = """You are a QA judge for a support assistant. Compare the ANSWER
to the REFERENCE for the given QUESTION. Decide PASS if the ANSWER conveys the
same meaning as the REFERENCE, even if worded differently. Decide FAIL if the
ANSWER contradicts the REFERENCE, is missing the key fact from the REFERENCE,
or fabricates something not in the REFERENCE.

Respond with ONLY a JSON object in this exact shape, no other text:
{{"verdict": "PASS" or "FAIL", "reasoning": "one sentence explaining why"}}

QUESTION: {question}
REFERENCE: {reference}
ANSWER: {answer}
"""

def judge_answer(question: str, answer: str, reference: str) -> dict:
    prompt = JUDGE_PROMPT.format(question=question, reference=reference, answer=answer)
    response = ollama.chat(
        model=JUDGE_MODEL,
        messages=[{"role": "user", "content": prompt}],
        format="json",
    )
    return json.loads(response.message.content)
```

`format="json"` tells Ollama to constrain generation to valid JSON — without it, a small local model will occasionally wrap its answer in explanation text your `json.loads()` call can't parse. This is the structured-evaluation half of the technique: a free-text judgment is hard to build anything automated on top of; a fixed `{"verdict": ..., "reasoning": ...}` shape is something you can aggregate, threshold, and gate on.

## Pass/fail vs. score-based

This judge returns **PASS/FAIL** — a binary verdict, deliberately. Binary verdicts are easier to validate (Module 3's positive/negative case design maps directly onto them), easier to aggregate ("11 of 12 passed"), and harder for the model to fudge than a number. A **score-based** judge (say, 1–5) gives you more granularity — useful when "acceptable" genuinely isn't binary, like Module 11's user-experience rubric — but it's also easier for an under-calibrated judge to produce a comfortable middle score without committing to a real verdict. Prefer pass/fail unless you have a specific reason the extra granularity is worth the extra calibration burden.

## Validating the judge before trusting it

**This is not optional, and it's the actual point of this page.** A judge you haven't validated is a metric you're taking on faith — exactly what Module 3 told you never to do with a golden dataset. Build known-good and known-bad cases where *you* already know the right verdict, and check the judge against them:

```python
# eval/validate_judge.py
from eval.judge import judge_answer

cases = [
    {
        "question": "How many active projects can I have on the Free plan?",
        "reference": "Up to 3 active projects.",
        "answer": "You can have up to 3 active projects on the Free plan.",
        "expected": "PASS",   # known-good: correct, different wording
    },
    {
        "question": "How many active projects can I have on the Free plan?",
        "reference": "Up to 3 active projects.",
        "answer": "You can have up to 10 active projects on the Free plan.",
        "expected": "FAIL",   # known-bad: wrong number
    },
    {
        "question": "Does the Free plan include priority support?",
        "reference": "No. Priority support is only included on the Team plan.",
        "answer": "No, priority support is only available on the Team plan.",
        "expected": "PASS",   # known-good: correct, rephrased
    },
    {
        "question": "Does the Free plan include priority support?",
        "reference": "No. Priority support is only included on the Team plan.",
        "answer": "Yes, all plans include priority support.",
        "expected": "FAIL",   # known-bad: direct contradiction
    },
]

correct = 0
for case in cases:
    result = judge_answer(case["question"], case["answer"], case["reference"])
    match = result["verdict"] == case["expected"]
    correct += match
    print(f"expected={case['expected']:4s} got={result['verdict']:4s} match={match}  reasoning={result['reasoning']}")

print(f"\n{correct}/{len(cases)} judge verdicts matched the known-correct answer.")
```

Run it:

```bash
python -m eval.validate_judge
```

**Run it now.** If the judge doesn't score all four correctly, don't move on — a judge that fails on cases you already know the answer to has no business scoring cases you don't. This validation set doesn't need to be large, but it does need at least one case per direction you expect real answers to fail in: a subtly wrong number, a direct contradiction, a fabricated addition.

## Judge consistency and judge bias

Run `validate_judge.py` again, unchanged. Same variance you've seen since Module 1 applies here too — a judge call is still an LLM call. If a verdict flips between runs on the exact same input, that's a consistency problem worth knowing about before you rely on this judge for anything with stakes (like a CI gate in Module 13). **Judge bias** is a related but different risk: a judge can be systematically lenient (passing answers that are subtly wrong because they "sound right") or systematically harsh (failing correct answers phrased unusually) — something a single validation pass won't always catch, especially if your known-good/known-bad cases don't cover the specific way a real answer tends to drift. Widening your validation set over time, whenever you spot a verdict you disagree with, is the practical defense.

## Human evaluation vs. LLM evaluation

An LLM judge doesn't replace a human reviewer — it changes what the human reviews. Instead of reading every response yourself, you read the validation set (small, fixed, high-stakes to get right) and spot-check disagreements the judge flags going forward. That's a real trade: less total review time, at the cost of trusting an imperfect judge for everything you *don't* spot-check. Whether that trade is worth it depends on what's being gated — the same risk-based judgment call a QE already makes about how much manual regression testing versus automation a given feature warrants.
