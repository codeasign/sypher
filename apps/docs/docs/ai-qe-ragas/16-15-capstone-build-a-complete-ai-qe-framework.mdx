## Question 1: "How do I know whether my AI/RAG system is actually getting better?"

Walk through the real, current answer using your own project:

1. **You have a stored baseline** (`baseline.json`) recording the last accepted pass rate against a specific, versioned dataset (`dataset_version` from Module 3).
2. **You make a real change**: a prompt edit, a retrieval config change, a new model, the same kind of change Module 8 and Module 14 had you make on purpose.
3. **You re-run the evaluation** (`eval/ci_gate.py`, or the full `eval/run_all_metrics.py` for a deeper look) against the same dataset.
4. **You account for variance before trusting the number**: Module 6 told you a single run's exact score isn't ground truth; Module 10 gave you the discipline to run more than once before concluding anything.
5. **You compare to baseline with a relative threshold**, not a fixed absolute number. Module 13's gate does this automatically on every PR.
6. **You update the baseline deliberately**, reviewed like any other test-suite change, only when an improvement holds up across repeated runs.

That loop, baseline, change, re-run, account for variance, compare, decide, *is* the answer to "is it getting better." Not a single score, a **process** that produces a defensible answer every time you ask the question again.

## Question 2: "When evaluation fails, how do I find out why?"

This is Module 8's five-way diagnostic, now with a real, complete case to walk end to end, reusing `gd-004` from your own Module 5 run, which really did fail this way:

**The failure:** `"Does the Free plan include priority support?"` The reference answer is `"No. Priority support is only included on the Team plan."` In one real run, the system answered `"Not documented."`

**Step 1: test data.** Reread `gd-004`'s reference answer against `billing-and-plans.md`. It's correct and unambiguous. Test data isn't the cause.

**Step 2: retrieval.** Check `retrieved_docs` for this row. `billing-and-plans.md`, the doc that actually contains the answer, was retrieved. Retrieval isn't the cause.

**Step 3: prompt.** The doc states "Team: ...priority support" and never explicitly states "Free: no priority support." `SYSTEM_PROMPT` instructs the model to say `"Not documented."` if the answer "is not contained in the CONTEXT", and the model treated an absence-based negative conclusion as not being "contained," rather than reasoning from exclusion. **This is the cause**: an overly literal prompt instruction, not a retrieval gap or a model incapable of the reasoning.

**Step 4: confirm, don't just theorize.** A fix worth testing: loosen the instruction to explicitly permit negative inference, *"If the CONTEXT clearly implies a negative answer (something is true only for a different plan/role than the one asked about), state that clearly instead of saying Not documented."* Re-run `gd-004` and Module 8's other under-answering cases (`gd-003`, `gd-005`, `gd-008`) against the revised prompt and check whether they now pass without also breaking the genuinely-unanswerable cases (`gd-009`–`gd-012`) into false positives, the real risk of loosening a conservative prompt.

**Step 5: where the quality gate fits.** Once the revised prompt is in place, this exact case belongs in `golden_dataset_smoke.json` if it isn't already, so a future prompt edit that reintroduces this failure gets caught by Module 13's gate on the very next PR, instead of being rediscovered by hand.

This is the complete loop the two opening questions were always pointing toward: **diagnose to a specific, evidenced cause, fix it, confirm the fix without breaking something else, and feed the case back into the gate that protects it going forward.**

## What you can say you can do

By this point, with your own finished `aiqe-ragas` project as evidence: you can engineer and validate test data instead of trusting AI output on faith; build and knowingly break a real RAG system; run and interpret RAGAS metrics without treating any single score as ground truth; root-cause an evaluation failure to a specific layer instead of guessing; build and validate your own LLM-as-a-judge; compare models fairly instead of by impression; evaluate user experience as its own axis; and wire all of it into a CI gate that blocks a real regression on real evidence.

## Learning checkpoint

Before you consider this course complete, you should now be able to:

- Answer both opening questions using your own project as evidence, not this page's summary of them.
- Point to the specific file in your project responsible for each row in the artifact table above.
- Explain, from the `gd-004` walkthrough, why the diagnostic order (data → retrieval → prompt → model → evaluator) mattered.

## Where this goes next

Nothing about this framework is finished in the sense of "done": a real system keeps changing, and the golden dataset, the prompt, the models available in Ollama, and the CI thresholds will all keep moving with it. What you have now isn't a finished artifact; it's the process for finding out, with evidence, whether each future change actually made things better.
