## Page purpose

You've been eyeballing `RagPipeline`'s answers against `golden_dataset.json` by reading them. This page replaces that with a real, repeatable, scored evaluation using RAGAS, run against your own pipeline and your own dataset, not sample data.

## Learning objectives

By the end of this page, you should be able to:

- Explain concretely why `assertEquals` fails against RAG output, with a real example.
- Build a RAGAS evaluation dataset from `golden_dataset.json` and `RagPipeline`'s real output.
- Run a first real RAGAS evaluation against your own system and read the result.
- Explain what evaluation variability means for RAGAS scores specifically.

## Why `assertEquals` doesn't work here

Run `gd-001` through your pipeline and compare it to its reference answer:

```python
answer = "You can have up to 3 active projects on the Free plan."
reference = "Up to 3 active projects."

assert answer == reference  # AssertionError
```

**This fails, and the system isn't wrong.** Both sentences say exactly the same thing. An exact-match assertion can't tell "differently worded, same meaning" apart from "wrong." It can only tell you the strings differ. You already knew this in the abstract from Module 1; this is the concrete case where it actually costs you a false failure.

RAGAS's metrics solve this by using an LLM (and, for some metrics, an embedding model) to judge *properties* of the response, is it supported by the retrieved context, does it actually address the question, does it cover what the reference says, instead of comparing strings. That LLM-as-judge mechanism is exactly what Module 9 teaches you to build yourself; RAGAS's built-in metrics are a maintained, tested version of the same idea.

## Building a RAGAS evaluation dataset

RAGAS evaluates rows with four fields: `user_input` (the question), `retrieved_contexts` (what your pipeline retrieved), `response` (what your pipeline generated), and `reference` (your validated answer). You already have all four: `golden_dataset.json` supplies `user_input` and `reference`; `RagPipeline.ask()` supplies `retrieved_contexts` and `response`.

```python
# eval/build_eval_dataset.py
import json
from rag_pipeline import RagPipeline

def build_eval_rows(golden_path: str = "golden_dataset.json") -> list[dict]:
    with open(golden_path) as f:
        dataset = json.load(f)

    pipeline = RagPipeline()
    rows = []
    for case in dataset["cases"]:
        result = pipeline.ask(case["question"])
        rows.append({
            "user_input": case["question"],
            "retrieved_contexts": result["retrieved_contexts"],
            "response": result["answer"],
            "reference": case["reference_answer"],
        })
    return rows
```

Every row here is a real, current run of your actual system, not a fixture, not sample data. Run this again after you change the prompt, the model, or `TOP_K`, and you get a fresh evaluation dataset reflecting that change.

## Running a first real evaluation

```python
# eval/run_first_eval.py
from ragas import evaluate, EvaluationDataset
from ragas.metrics import Faithfulness, ResponseRelevancy
from ragas.llms import LangchainLLMWrapper
from ragas.embeddings import LangchainEmbeddingsWrapper
from ragas.run_config import RunConfig
from langchain_ollama import ChatOllama, OllamaEmbeddings

from eval.build_eval_dataset import build_eval_rows

rows = build_eval_rows()
eval_dataset = EvaluationDataset.from_list(rows)

evaluator_llm = LangchainLLMWrapper(ChatOllama(model="qwen2.5:3b", temperature=0))
evaluator_embeddings = LangchainEmbeddingsWrapper(OllamaEmbeddings(model="nomic-embed-text"))

result = evaluate(
    dataset=eval_dataset,
    metrics=[Faithfulness(), ResponseRelevancy()],
    llm=evaluator_llm,
    embeddings=evaluator_embeddings,
    run_config=RunConfig(timeout=300, max_workers=2),
)

print(result)
df = result.to_pandas()
print(df[["user_input", "faithfulness", "answer_relevancy"]])
```

Run it:

```bash
python -m eval.run_first_eval
```

**Two things worth noticing before you run it.** First, the evaluator model here is `qwen2.5:3b`, not `llama3.2:3b`, deliberately. RAGAS's metrics work by asking the evaluator model to produce fairly involved structured output internally (breaking a response into individual claims, then judging each one). In practice, `llama3.2:3b` struggles to reliably produce that structured output and metric calls fail outright with a parsing error; `qwen2.5:3b` handles it far more reliably. This is exactly the kind of local-model limitation Module 9 will have you build tooling to work around directly. Second, `run_config=RunConfig(timeout=300, max_workers=2)` matters more than it looks: RAGAS's default fires up to 16 concurrent requests, but a single local Ollama server processes requests far more serially than that. Left at the default, most calls end up queued past their timeout and fail. Module 12 comes back to this concurrency setting specifically as a real, measurable optimization.

**Run it now.** You'll see several `DeprecationWarning` lines: one for `LangchainLLMWrapper`, and one per metric class imported from `ragas.metrics` (RAGAS is migrating these to `ragas.metrics.collections`). All of it is expected with the version this course installs; everything still runs correctly, RAGAS is just signposting where its API is heading next. Give it a while: every row runs one or more real LLM calls per metric, against your own local model, on CPU unless you have a GPU Ollama can use.

### Reading the result

`print(result)` shows a dict of mean scores, one per metric, across all 12 rows, something like `{'faithfulness': <your score>, 'answer_relevancy': <your score>}`. The exact numbers are yours; they depend on your model, your pipeline's real answers, and RAGAS's own LLM-judge calls, so this page won't show you a specific value as if it were a fact about the metric. `result.to_pandas()` gives you the same two scores broken out **per row**. This is where you actually work, since a mean can hide one bad row behind eleven good ones.

Note the column name: even though you imported `ResponseRelevancy`, its score column is `answer_relevancy`, an old name RAGAS kept for backward compatibility. Small detail, but it'll trip you up in a `KeyError` if you guess instead of checking.

## Evaluation variability

Run the exact same script again, with no code changes. **Expect the scores to move slightly.** Two independent sources of variance stack here: your RAG pipeline's own generation step is non-deterministic (Module 1), and RAGAS's LLM-as-judge metrics call a model to make their own judgment, which is *also* non-deterministic. A faithfulness score of `0.83` on one run and `0.79` on the next isn't a regression. It's the same kind of variance you've been observing since Module 1, now showing up in a score instead of raw text. Module 10 covers what to do about this rigorously (repeated runs, confidence intervals); for now, the QE habit to build is simple: **never trust a single evaluation run's exact number as ground truth**, the same way you wouldn't trust a single flaky test run as proof a bug is fixed.

## Local vs. hosted evaluation models

RAGAS can be pointed at a hosted API model as its judge instead of a local one, nothing about the `evaluate()` call changes except which `llm`/`embeddings` objects you pass in. This course stays local-first throughout, on purpose: no per-call API cost while you're iterating dozens of times per module, no data leaving your machine, and full determinism-of-environment (no upstream model version changing under you). The trade-off, honestly, is exactly what you just saw: a small local model is a weaker, less reliable judge than a large hosted one. One model in this course's own pull list (`llama3.2:3b`) couldn't reliably produce the structured output RAGAS's metrics need, and swapping in a different, still-small, still-local model (`qwen2.5:3b`) was the fix, not abandoning local evaluation altogether. That's the honest trade-off with local-first evaluation: more setup judgment required, in exchange for zero per-call cost and full control over your data. It's also exactly why Module 9 spends real effort validating a judge before trusting it.
