## Page purpose

Before writing any AI test, you need to see the specific way an AI system breaks the testing assumptions you already rely on. This page gets you looking at real non-deterministic output from your own hands, not a description of it, and reframes AI test strategy using vocabulary you already have: risk, coverage, oracle.

## Learning objectives

By the end of this page, you should be able to:

- Explain, with your own captured output as evidence, why the same prompt can produce different responses.
- Distinguish a deterministic test oracle from the kind you need for an AI system.
- Describe AI quality risk in terms of risk, coverage, and oracle — not just "it's non-deterministic."
- State what an AI test strategy needs to cover that a traditional one doesn't.

## The assumption traditional testing relies on

`assertEquals(4, add(2, 2))` works because `add` is deterministic: same input, same output, every time, forever. Your test oracle — the thing that tells you pass or fail — is a single fixed expected value. Traditional test strategy, coverage, and regression testing are all built on top of that assumption, even when you don't state it explicitly.

An LLM call breaks the assumption at the root. Don't take that on faith — run it.

## Hands-on: watch it happen

From your `aiqe-ragas` project (Module 0), create `experiments/check_variance.py`:

```python
# experiments/check_variance.py
import ollama

MODEL = "llama3.2:3b"
PROMPT = "In one sentence, what does test coverage mean?"

for i in range(5):
    response = ollama.chat(model=MODEL, messages=[{"role": "user", "content": PROMPT}])
    print(f"--- run {i + 1} ---")
    print(response.message.content)
```

Run it:

```bash
python experiments/check_variance.py
```

**Run it now before continuing.** You'll get five responses to the exact same prompt. Look at them side by side.

### Explaining the result

Some of the five are probably worded differently. You may see different sentence structures, different emphasis, maybe even a different example. This isn't a bug in Ollama and it isn't a bug in your script — it's the model sampling from a probability distribution over possible next words each time it generates, rather than deterministically computing one fixed answer. Run the script again right now, with no code changes at all, and you'll very likely get five more variations.

This is the fact every technique in this course exists to work around: **you cannot write `assert response == expected_string` against this kind of system and expect it to hold up.**

## Reframing this in QE terms

You already have the vocabulary for this — it just needs remapping:

- **Test oracle** — for `add(2, 2)`, the oracle is "equals 4." For an LLM response, the oracle has to become a *property* the response should have (mentions coverage, is under N words, doesn't contradict the reference answer) rather than one fixed string. Building good oracles for AI output is most of what Modules 6–9 are about.
- **Coverage** — for traditional code, coverage usually means "which lines/branches ran." For an AI system, coverage means something closer to "which categories of input have I tested" — positive, negative, edge, ambiguous, unanswerable, adversarial (Module 3 builds this out as a golden dataset).
- **Risk** — traditional risk analysis asks what's likely to break and what it costs if it does. AI risk analysis asks the same question, but the failure modes are different in kind: a wrong-but-confident answer (hallucination), a right answer built on the wrong reasoning (ungrounded), a retrieval step that quietly returns the wrong document, a response that's factually fine but unusable in tone.
- **Regression** — for deterministic code, a regression means behavior changed when it shouldn't have. For an AI system, behavior can drift even when *nothing about your code changed* — a model update, a prompt template edit, or even normal sampling variance can shift scores. Reproducibility and baselines (later modules) exist specifically to tell real regressions apart from noise.

## A first AI test strategy statement

Put this in words before writing a single evaluation script: an AI test strategy for this course's project needs to (1) define the categories of input worth testing — the coverage question, (2) define what "acceptable" looks like for each, without demanding exact-match — the oracle question, and (3) prioritize which failure modes matter most for the system you're building — the risk question. Module 3 turns (1) and (2) into a real golden dataset. Modules 6–9 turn (2) into real, running evaluation code.
