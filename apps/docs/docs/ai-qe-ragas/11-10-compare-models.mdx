## Page purpose

Module 2 had you eyeball two models' answers side by side, useful for a first impression, not enough to justify a real decision. This page builds a fair, controlled comparison between `llama3.2:3b` and `qwen2.5:3b` on your own project, and is honest about exactly how much (and how little) confidence a comparison this size can actually support.

## Learning objectives

By the end of this page, you should be able to:

- List every variable that has to be held constant for a model comparison to be fair.
- Build a real comparison scorecard covering quality, latency, and consistency.
- Explain why "local" doesn't mean "free" when it comes to comparing cost.
- Explain the difference between statistical significance and practical significance, honestly, for a dataset this small.

## Why fairness is the whole point

An unfair comparison is worse than no comparison. It produces a confident-sounding wrong answer about which model to use. **Hold constant:** the dataset (`golden_dataset.json`), the questions, the retrieval configuration (`TOP_K`, same `RagPipeline`), the prompt (`SYSTEM_PROMPT`), and the evaluation configuration (the same judge, same rubric). **Vary exactly one thing:** the generation model. If you change the prompt *and* the model at the same time, and quality changes, you'll have no way to know which change caused it, the same confound as changing two things in one A/B test.

## Extending `RagPipeline` for a fair swap

Add a model override to `ask()`, so retrieval, prompt, and everything else stay identical between runs:

```python
# rag_pipeline.py (extend the ask() method from Module 5)
def ask(self, question: str, top_k: int = TOP_K, gen_model: str = GEN_MODEL) -> dict:
    retrieved = self.retrieve(question, top_k=top_k)
    context = "\n\n".join(chunk["text"] for chunk in retrieved)
    prompt = f"CONTEXT:\n{context}\n\nQUESTION:\n{question}"
    response = ollama.chat(
        model=gen_model,
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": prompt},
        ],
    )
    return {
        "question": question,
        "answer": response.message.content,
        "retrieved_contexts": [c["text"] for c in retrieved],
        "retrieved_docs": [c["source_doc"] for c in retrieved],
    }
```

Only `gen_model` changes between calls: `top_k`, `SYSTEM_PROMPT`, and `self.store` (retrieval) are identical for both models, by construction.

## Building the scorecard

```bash
ollama pull qwen2.5:3b
```

```python
# eval/compare_models.py
import json
import time
from rag_pipeline import RagPipeline
from eval.judge import judge_answer

MODELS = ["llama3.2:3b", "qwen2.5:3b"]

def run_scorecard(models: list[str], golden_path: str = "golden_dataset.json") -> dict:
    with open(golden_path) as f:
        dataset = json.load(f)

    pipeline = RagPipeline()
    scorecard = {model: {"passed": 0, "total": 0, "latencies": []} for model in models}

    for case in dataset["cases"]:
        for model in models:
            start = time.time()
            result = pipeline.ask(case["question"], gen_model=model)
            elapsed = time.time() - start

            verdict = judge_answer(case["question"], result["answer"], case["reference_answer"])

            scorecard[model]["total"] += 1
            scorecard[model]["passed"] += verdict["verdict"] == "PASS"
            scorecard[model]["latencies"].append(elapsed)

    return scorecard

if __name__ == "__main__":
    scorecard = run_scorecard(MODELS)
    for model, stats in scorecard.items():
        avg_latency = sum(stats["latencies"]) / len(stats["latencies"])
        print(f"{model}")
        print(f"  pass rate: {stats['passed']}/{stats['total']}")
        print(f"  avg latency: {avg_latency:.2f}s")
```

Run it:

```bash
python -m eval.compare_models
```

**Run it now.** This is a real, current run of both models against your unmodified project. Expect it to take a while, since it's `2 models × 12 questions × (1 generation call + 1 judge call)`.

## Reading the scorecard honestly

**Quality** is the pass rate from Module 9's validated judge, the same judge for both models, which matters as much as holding the dataset constant. **Latency** is wall-clock time per call, which for local models is a real and directly comparable number, unlike a hosted API where network conditions add noise you can't control for.

**Cost**, for local models, isn't the per-token dollar figure you'd track against a hosted API. There's no invoice. It's still real: your own machine's compute time, which is exactly what the latency numbers above are measuring, plus whatever hardware you dedicated to running two 2–3B-parameter models locally in the first place. Don't let "local" quietly become "free" in how you talk about this comparison.

**Consistency**: run `run_scorecard` a second time, unchanged, and compare pass rates and latencies to the first run. Some movement is expected, for the same reasons Module 6 told you not to trust a single evaluation run's exact numbers. A model whose pass rate swings widely between identical runs is telling you something about its reliability that a single run's score would have hidden entirely.

## Statistical significance vs. practical significance, and an honest limit

With 12 questions, be honest about what you can and can't conclude. A 9/12 vs. 7/12 pass-rate difference is a small enough sample that it could plausibly be noise rather than a real quality gap. Formal significance testing (confidence intervals on a proportion, or a test like a binomial or chi-squared comparison) generally wants a good deal more than 12 trials per arm to say anything with real confidence, and running this course's scorecard on 12 questions is meant to teach you the *method*, not to produce a publishable result. If you want an actual answer for a real decision, the fix isn't a different statistical formula, it's a bigger golden dataset (more cases, still built with Module 3's same review discipline, not just more volume).

Even with a genuinely larger, statistically solid sample: **statistical significance isn't the same question as practical significance.** A real, confidently-measured 2-percentage-point quality difference might not be worth choosing the slower or more resource-hungry model over the faster one, that's a judgment call about your specific risk tolerance and constraints, the same "what can we do vs. what should we do" distinction from any engineering trade-off, not something a p-value decides for you.

## QE lesson

A model comparison is an experiment, and an experiment with confounded variables or too small a sample produces a confident-sounding wrong answer, same as a flaky, under-powered test suite claiming to prove a feature works. The scorecard's numbers are only as trustworthy as the fairness of how they were produced.
