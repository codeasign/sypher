## Page purpose

Module 6 ran two metrics without dwelling on what they actually check. This page runs all six of the metrics this course uses — for real, against your own `RagPipeline` — and treats each as answering a specific, different question about your system, not as one generic "quality score."

## Learning objectives

By the end of this page, you should be able to:

- State, in one sentence each, what faithfulness, response relevancy, context precision, context recall, context entity recall, and noise sensitivity each actually check.
- Pick the right metric for a given failure you suspect.
- Explain why two metrics can legitimately disagree on the same row.
- Explain why this course never tells you a fixed number that "means good."

## Running all six for real

```python
# eval/run_all_metrics.py
from ragas import evaluate, EvaluationDataset
from ragas.metrics import (
    Faithfulness,
    ResponseRelevancy,
    ContextPrecision,
    ContextRecall,
    ContextEntityRecall,
    NoiseSensitivity,
)
from ragas.llms import LangchainLLMWrapper
from ragas.embeddings import LangchainEmbeddingsWrapper
from ragas.run_config import RunConfig
from langchain_ollama import ChatOllama, OllamaEmbeddings

from eval.build_eval_dataset import build_eval_rows

rows = build_eval_rows()
eval_dataset = EvaluationDataset.from_list(rows)

evaluator_llm = LangchainLLMWrapper(ChatOllama(model="qwen2.5:3b", temperature=0))
evaluator_embeddings = LangchainEmbeddingsWrapper(OllamaEmbeddings(model="nomic-embed-text"))

result = evaluate(
    dataset=eval_dataset,
    metrics=[
        Faithfulness(),
        ResponseRelevancy(),
        ContextPrecision(),
        ContextRecall(),
        ContextEntityRecall(),
        NoiseSensitivity(),
    ],
    llm=evaluator_llm,
    embeddings=evaluator_embeddings,
    run_config=RunConfig(timeout=300, max_workers=2),
)

df = result.to_pandas()
cols = ["user_input", "faithfulness", "answer_relevancy", "context_precision",
        "context_recall", "context_entity_recall", "noise_sensitivity(mode=relevant)"]
print(df[cols].to_string())
```

**Run it now** — expect this to take a while; six metrics means several LLM judge calls per row. Note the last column name: `NoiseSensitivity()` defaults to `mode="relevant"`, and that mode is baked into the column name RAGAS produces — `noise_sensitivity(mode=relevant)`, not the plain `noise_sensitivity` you might guess from the class name. Same lesson as `answer_relevancy` in Module 6: check the real column names on your own `df.columns`, don't guess them from the import name.

## What each metric actually checks

- **Faithfulness** — of the claims made in the response, how many are actually supported by the retrieved context? This checks the response against its *own* context, not against the reference answer — it catches a model adding something the context never said, whether or not that addition happens to be true.
- **Response relevancy** (`answer_relevancy` column) — does the response actually address the question asked? A response can be perfectly faithful to its context and still relevancy-fail by wandering off-topic, over-hedging, or answering a slightly different question than the one asked.
- **Context precision** — of the chunks retrieval returned, how many were actually useful for answering? Low precision means retrieval is pulling in noise alongside (or instead of) the useful chunk.
- **Context recall** — did retrieval bring back *everything* needed to support the reference answer? This is the metric most directly tied to Module 5's retrieval miss: a genuine miss shows up here as low recall, because the chunk that would have supported the reference answer never made it into `retrieved_contexts`.
- **Context entity recall** — specifically, do the named entities in the reference answer (plan names, role names, specific terms) show up in what was retrieved? Useful when a domain is entity-dense — Fernwood's plan names and role names are a good example — and a generic recall score might look fine while a specific named detail is still missing.
- **Noise sensitivity** — when retrieval returns a mix of relevant and irrelevant chunks (which `TOP_K = 2` guarantees will happen sometimes), how often does the response get pulled off-track by the irrelevant one? This is the metric that most directly tests robustness to imperfect retrieval, rather than assuming retrieval was clean.

## Picking the right metric for a suspected failure

Match the symptom to the metric that actually isolates it, instead of reading all six every time:

| You suspect... | Check this metric first |
|---|---|
| The model is making things up | Faithfulness |
| The answer is technically grounded but doesn't actually answer the question | Response relevancy |
| Retrieval is pulling in irrelevant chunks | Context precision |
| Retrieval is missing the chunk that had the answer (Module 5's failure) | Context recall |
| A specific plan/role/term is getting lost even though "something" was retrieved | Context entity recall |
| The answer degrades specifically when irrelevant chunks are also retrieved | Noise sensitivity |

## When metrics disagree

It's normal — expected, even — for one metric to look fine while another looks bad on the exact same row. Context recall can be high (the right chunk was retrieved) while faithfulness is low (the model still invented something beyond it). Faithfulness can be high (nothing invented) while response relevancy is low (technically grounded, but doesn't actually answer what was asked). **Disagreement between metrics isn't a bug in RAGAS — it's the whole reason this course uses more than one metric.** A single blended "quality score" would hide exactly this kind of distinction, and Module 8 depends on being able to see it.

## No arbitrary thresholds

You will not find "faithfulness above 0.8 is good" anywhere in this course, and that's deliberate, not an omission. What counts as an acceptable score depends on your use case (a support bot answering billing questions has a much lower tolerance for unfaithful claims than a brainstorming assistant), your dataset (a harder, more adversarial golden dataset should produce lower scores on a system that hasn't changed at all), your baseline (is this run better or worse than your own system's last run — Module 10 and Module 13 build this out), and your risk tolerance for the specific failure that metric catches. A QE doesn't accept "80% code coverage is good" as a universal rule either — coverage on payment code and coverage on a tooltip aren't the same risk. Metric scores deserve the same judgment.
