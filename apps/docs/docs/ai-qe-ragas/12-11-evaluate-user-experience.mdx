## Page purpose

Every metric and judge so far checks whether an answer is *right*. None of them check whether it's *pleasant to receive*. This page adds that as a separate, required evaluation axis, run as an additional layer on top of, not instead of, Module 7's correctness metrics.

## Learning objectives

By the end of this page, you should be able to:

- Explain, with a real example from your own project, why correctness and user experience are separate axes.
- Build a UX rubric judge covering clarity, conciseness, tone, and actionability.
- Run it against a real answer and interpret disagreement between UX and correctness scores.
- Explain why a UX judge needs the same validation discipline as any other judge.

## Correct isn't the same as good

Go back to Module 5's real data: `"Not documented."` in response to "Can a Viewer edit tasks in a project?" is arguably *defensible*, the model was told to say exactly that when the context doesn't support an answer, and it did. But sit in the user's seat: a two-word dead end, no explanation, no next step. Compare that to `"No, Viewers only have read-only access, so they cannot edit tasks. If you need edit access, ask a project Owner to change your role to Editor."`, clearer, warmer, and it tells the user what to do next. Correctness alone can't distinguish these; a rubric built specifically for user experience can.

## Building a UX rubric

```python
# eval/ux_rubric.py
import ollama

UX_MODEL = "llama3.2:3b"

UX_PROMPT = """You are reviewing a support assistant answer for USER EXPERIENCE
quality only — not whether it is factually correct.

For each of the following, answer true or false:
- clear: Is the answer easy to understand on first read?
- concise: Does it avoid unnecessary padding or repetition?
- appropriate_tone: Is the tone professional and friendly, not curt or robotic?
- actionable: If it cannot fully answer, does it still help the user (e.g. suggest what to do next), rather than just a dead end?

Respond with ONLY a JSON object:
{{"clear": true/false, "concise": true/false, "appropriate_tone": true/false, "actionable": true/false, "reasoning": "one sentence"}}

QUESTION: {question}
ANSWER: {answer}
"""

def evaluate_ux(question: str, answer: str) -> dict:
    prompt = UX_PROMPT.format(question=question, answer=answer)
    response = ollama.chat(model=UX_MODEL, messages=[{"role": "user", "content": prompt}], format="json")
    import json
    return json.loads(response.message.content)
```

Notice the shape: four separate true/false checks plus reasoning, not one blended score, the same "don't collapse distinct signals into one number" principle from Module 7's metric disagreement discussion applies here too. A response can be clear and concise while still having the wrong tone, and averaging that into a single number would hide it.

## Running it for real, and reading a real disagreement

```python
# experiments/run_ux_rubric.py
from eval.ux_rubric import evaluate_ux

cases = [
    ("Can a Viewer edit tasks in a project?", "Not documented."),
    ("Can a Viewer edit tasks in a project?",
     "No, Viewers only have read-only access, so they cannot edit tasks. "
     "If you need edit access, ask a project Owner to change your role to Editor."),
]

for question, answer in cases:
    result = evaluate_ux(question, answer)
    print(f"answer: {answer}")
    print(f"  ux: {result}")
    print()
```

**Run it.** In one real run of this exact script, the rubric scored `"Not documented."` as `clear: false, concise: false, appropriate_tone: true, actionable: true`, and the reasoning claimed it "provides a clear suggestion... to contact support," which the two-word answer never actually says. **Sit with that, don't smooth it over**: this is a real, observed instance of exactly the judge unreliability Module 9 warned you about: a small local model inventing a justification for a verdict that doesn't hold up against the actual text. It's also, honestly, a case of the judge's own `concise: false` verdict being questionable for a two-word answer. Neither of those failures make the UX rubric useless. They make it a tool you validate and spot-check, the same way Module 9 told you to, not one you take on faith because it returned tidy JSON.

The longer answer, in the same run, scored `clear: true, concise: true, appropriate_tone: true, actionable: true`, a clean, uncontroversial verdict. That contrast is the actual lesson: **a UX judge is more reliable on clearly-good or clearly-bad cases than on a terse-but-technically-fine edge case**, validate it against exactly that kind of edge case, not only obvious ones, before trusting it in a pipeline.

## Layering UX onto correctness, not replacing it

Run both Module 9's correctness judge and this UX rubric on the same row and keep both results, don't merge them into one pass/fail:

```python
# eval/full_row_eval.py
from eval.judge import judge_answer
from eval.ux_rubric import evaluate_ux

def evaluate_row(question: str, answer: str, reference: str) -> dict:
    return {
        "correctness": judge_answer(question, answer, reference),
        "user_experience": evaluate_ux(question, answer),
    }
```

A response that's correct with poor UX and a response that's incorrect with excellent UX are different problems needing different fixes: a prompt tweak for the first (Module 8's territory), possibly a real capability gap for the second. Keeping the two evaluations separate is what makes each failure legible instead of blending into one ambiguous "quality" number.

## Evaluating for different personas

The same answer can be right for one audience and wrong for another: a terse, jargon-heavy answer might suit a technical admin persona while failing a first-time user persona. If your system serves more than one audience, that's a rubric input, not an afterthought: extend `UX_PROMPT` with an explicit persona line ("the user is a first-time Fernwood user with no technical background") and re-run validation for that persona specifically, rather than assuming one rubric covers everyone.

## QE lesson

This is the same principle as separating functional testing from usability testing in traditional QE: a feature can pass every functional test and still fail a usability review, and neither review substitutes for the other. AI evaluation needs the same split, and it's easy to skip if "the metrics all passed" starts to feel like the whole picture.
