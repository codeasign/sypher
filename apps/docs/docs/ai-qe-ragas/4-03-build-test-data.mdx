## Page purpose

Every module for the rest of this course evaluates against one thing: the golden dataset you build on this page. Get it wrong here and every later score is meaningless. This page treats a golden dataset the way it has to be treated: an engineered artifact you design, generate a draft of, catch real errors in, correct by hand, and version, never something you take from an LLM and trust.

## Learning objectives

By the end of this page, you should be able to:

- Distinguish source of truth from reference answer, and explain why a golden dataset needs both.
- Design test cases across positive, negative, edge, ambiguous, unanswerable, and hallucination-trap categories.
- Generate a draft dataset with Ollama, find a real error in it, and correct it by hand.
- Explain why a golden dataset needs review and versioning, the same as code.

## Source of truth vs. reference answer

**Source of truth** is the real material that makes an answer correct or incorrect: for this course, a small set of product docs you're about to create. **Reference answer** is what a human (you) writes down as the correct response to a specific question, after reading the source of truth. The reference answer is *your* engineered artifact, checked against the source of truth. It is never generated by the same model you're going to test, and never trusted just because it sounds right.

```
Source of Truth  ──▶  Golden Dataset  ──▶  System Under Test  ──▶  Evaluation  ──▶  Result
 (the docs)           (questions +          (the RAG system,        (RAGAS,
                       reference answers,    Module 5)               Modules 6+)
                       written by you)
```

Keep that chain in mind for the rest of this course. Evaluation never "proves" the system under test is correct. It checks the system's output against a reference answer *you* validated, which reduces risk and builds confidence, nothing stronger.

## Designing the test cases

A golden dataset isn't just "questions the system should get right." A real one deliberately covers the ways a question can go wrong:

- **Positive**: a clearly answerable question with a direct answer in the docs.
- **Negative**: a question whose correct answer is "no," or that rules something out.
- **Edge**: a boundary condition (exactly at a limit, immediately after an event) where an off-by-one error in reasoning would show up.
- **Ambiguous**: a question with more than one reasonable reading, where a good answer should address the well-supported reading and not silently guess at the other.
- **Unanswerable**: a question the docs genuinely don't cover. The *correct* answer is "not documented," not a guess.
- **Hallucination-trap**: a specific, checkable-sounding question about something that doesn't exist in the docs at all, designed to catch a model that invents a plausible answer rather than admitting it doesn't know.

## Hands-on: draft with Ollama, then catch a real error

Drafting by hand from scratch is slow. Use Ollama to generate a first draft, then review it like you'd review a pull request: assume it has a bug until you've checked.

```python
# experiments/draft_dataset.py
import ollama

with open("docs/billing-and-plans.md") as f:
    doc_text = f.read()

prompt = f"""Based only on the following documentation, write 2 question/answer
pairs a user might ask. Answer only from the text given.

DOCUMENTATION:
{doc_text}
"""

response = ollama.chat(model="llama3.2:3b", messages=[{"role": "user", "content": prompt}])
print(response.message.content)
```

**Run it**, then check every claim in the output against `docs/billing-and-plans.md` line by line. It's common to see something like the model stating the Free plan allows "up to 5 projects" (confusing the 5-*teammates* limit with the 3-*projects* limit) or inventing a discount percentage that isn't in the text. That's not a hypothetical risk: treat it as expected, and go find your own instance of it before moving on.

**This is the actual review step, not optional polish:** the moment you find a wrong number or an invented detail, that draft answer does not go into `golden_dataset.json` until you've rewritten it by hand against the real doc text, the way `gd-001` through `gd-012` above already were. A dataset entry generated but never checked isn't a golden dataset case; it's an unverified guess with a JSON wrapper around it.

## Validating the dataset

Before treating `golden_dataset.json` as ready to use, check it mechanically:

```python
# eval/validate_dataset.py
import json

REQUIRED_CATEGORIES = {"positive", "negative", "edge", "ambiguous", "unanswerable", "hallucination_trap"}

def validate(path: str) -> list[str]:
    with open(path) as f:
        data = json.load(f)

    errors = []
    seen_ids = set()
    seen_categories = set()

    for case in data["cases"]:
        if case["id"] in seen_ids:
            errors.append(f"duplicate id: {case['id']}")
        seen_ids.add(case["id"])
        seen_categories.add(case["category"])

        if not case["question"].strip():
            errors.append(f"{case['id']}: empty question")
        if not case["reference_answer"].strip():
            errors.append(f"{case['id']}: empty reference_answer")

    missing = REQUIRED_CATEGORIES - seen_categories
    if missing:
        errors.append(f"missing categories: {missing}")

    return errors

if __name__ == "__main__":
    errors = validate("golden_dataset.json")
    if errors:
        print(f"{len(errors)} problem(s) found:")
        for e in errors:
            print(f" - {e}")
    else:
        print("golden_dataset.json is structurally valid.")
```

Run it:

```bash
python eval/validate_dataset.py
```

This only checks structure: no duplicate IDs, no empty fields, every required category represented. It cannot check that a reference answer is actually *correct*; that's still on you, and it's exactly why the manual review step above isn't skippable.

## Versioning the dataset

`golden_dataset.json` is a test suite, so treat changing it like changing test code: commit it to version control, and review any edit (adding a case, correcting a reference answer, or removing one) the same way you'd review a pull request that changes assertions. The `dataset_version` field exists so that later evaluation results (Module 6 onward) can record *which version of the dataset* produced a given score. Without that, a score improving or dropping over time is impossible to interpret: you wouldn't know if the system changed or the test data did.
