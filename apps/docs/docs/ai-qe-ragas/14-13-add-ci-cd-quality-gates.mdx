## Page purpose

Everything so far has run on your own machine, on demand. This page wires it into GitHub Actions as a real quality gate — and makes a deliberate, justified choice about what runs on every pull request versus what only runs on a schedule, based on the real latency you've already experienced in this course.

## Learning objectives

By the end of this page, you should be able to:

- Explain why running the full evaluation suite on every commit usually isn't practical.
- Build a real CI quality gate that compares against a baseline instead of a fixed number.
- Explain absolute vs. relative thresholds, and why this course's gate uses relative.
- Explain how the gate avoids failing a PR on noise instead of a real regression.

## Why not the full suite on every commit

You have direct evidence for this, not just a general claim: local, CPU-bound evaluation in this course has taken real minutes per row once multiple LLM-judge calls are involved, and Module 8 already showed you a metric run where local-model timeouts and parsing failures were a live problem, not a hypothetical one. Running a full RAGAS metric suite against every push would make CI slow enough that people stop waiting for it — and a quality gate nobody waits for stops being a gate. The fix isn't skipping evaluation in CI; it's splitting what runs where.

## A validated, fast gate for pull requests

Module 9's judge is the right tool for a PR gate specifically because you already validated it and it's a single JSON call per row — fast and reliable, unlike the multi-call structured-output metrics from Modules 6–8. Build a small, deliberately curated smoke subset — not a random sample, an engineered one, the same discipline as Module 3:

```json
// golden_dataset_smoke.json
{
  "dataset_version": "1.0.0",
  "cases": [
    { "id": "gd-001", "category": "positive", "question": "How many active projects can I have on the Free plan?", "reference_answer": "Up to 3 active projects.", "source_doc": "projects-and-tasks.md" },
    { "id": "gd-003", "category": "negative", "question": "Can a Viewer edit tasks in a project?", "reference_answer": "No. Viewers have read-only access; only Owners and Editors can edit tasks.", "source_doc": "sharing-and-permissions.md" },
    { "id": "gd-009", "category": "unanswerable", "question": "Does Fernwood support Gantt charts?", "reference_answer": "Not documented.", "source_doc": null }
  ]
}
```

Three cases, one from each of the riskiest categories to regress silently: a positive fact, a negative/exclusion fact, and an unanswerable-question guardrail.

## The gate script

```python
# eval/ci_gate.py
import argparse
import json
import sys
from rag_pipeline import RagPipeline
from eval.judge import judge_answer

def run_pass_rate(dataset_path: str) -> dict:
    with open(dataset_path) as f:
        dataset = json.load(f)

    pipeline = RagPipeline()
    results = []
    for case in dataset["cases"]:
        result = pipeline.ask(case["question"])
        verdict = judge_answer(case["question"], result["answer"], case["reference_answer"])
        results.append({"id": case["id"], "verdict": verdict["verdict"]})

    passed = sum(r["verdict"] == "PASS" for r in results)
    return {"pass_rate": passed / len(results), "total": len(results), "results": results}

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--dataset", required=True)
    parser.add_argument("--baseline", required=True)
    parser.add_argument("--threshold", type=float, default=0.10)
    parser.add_argument("--report", default=None)
    args = parser.parse_args()

    current = run_pass_rate(args.dataset)

    with open(args.baseline) as f:
        baseline = json.load(f)

    regression = baseline["pass_rate"] - current["pass_rate"]
    print(f"baseline pass_rate: {baseline['pass_rate']:.2f}")
    print(f"current  pass_rate: {current['pass_rate']:.2f}")
    print(f"regression: {regression:.2f} (fail threshold: {args.threshold})")

    if args.report:
        with open(args.report, "w") as f:
            json.dump(current, f, indent=2)

    if regression > args.threshold:
        print(f"FAIL: pass rate dropped by more than {args.threshold}")
        sys.exit(1)

    print("PASS: no regression beyond threshold")

if __name__ == "__main__":
    main()
```

`baseline.json` is a small, versioned file checked into the repo — `{"pass_rate": 0.83, "dataset_version": "1.0.0"}` — updated deliberately (a reviewed change, like any other test-suite update) whenever a real, accepted improvement moves the number, never edited just to make a failing gate pass.

## Absolute vs. relative thresholds

An **absolute threshold** ("pass rate must be ≥ 0.8, always") is simple but arbitrary in exactly the way Module 7 told you to avoid — it doesn't account for how hard your dataset is or what your system's own realistic baseline looks like. A **relative threshold**, what this gate uses, compares against your own system's last accepted result and asks "did this get meaningfully worse," which is a fairer question for a non-deterministic system than any fixed number could be. `--threshold 0.10` here is a starting point for this course's tiny dataset, not a rule — tune it against how much your own baseline naturally moves between runs (Module 6's evaluation variability), or a single normal fluctuation will trip the gate.

## Handling non-determinism in CI

The same variance from Module 6 applies here — a single run's pass rate moving a little between identical commits is expected, not a regression. The relative threshold already absorbs small movement; if your own baseline is especially noisy, the more thorough fix is running the gate two or three times and gating on the average, at the cost of CI time. Don't chase perfect stability by shrinking the threshold to zero — that just converts ordinary variance into constant false failures, the CI equivalent of a flaky test everyone learns to ignore.

## The workflow: PR smoke gate vs. nightly full run

```yaml
# .github/workflows/eval.yml
name: AI Quality Evaluation

on:
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 6 * * *"
  workflow_dispatch: {}

jobs:
  smoke-gate:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Install and start Ollama
        run: |
          curl -fsSL https://ollama.ai/install.sh | sh
          ollama serve &
          sleep 5
          ollama pull llama3.2:3b
          ollama pull nomic-embed-text
      - name: Install Python dependencies
        run: pip install -r requirements.txt
      - name: Run PR smoke gate
        run: python -m eval.ci_gate --dataset golden_dataset_smoke.json --baseline baseline.json --threshold 0.10

  full-nightly-eval:
    if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Install and start Ollama
        run: |
          curl -fsSL https://ollama.ai/install.sh | sh
          ollama serve &
          sleep 5
          ollama pull llama3.2:3b
          ollama pull nomic-embed-text
      - name: Install Python dependencies
        run: pip install -r requirements.txt
      - name: Run full evaluation and write report
        run: python -m eval.ci_gate --dataset golden_dataset.json --baseline baseline.json --threshold 0.10 --report reports/nightly.json
      - uses: actions/upload-artifact@v4
        with:
          name: nightly-eval-report
          path: reports/nightly.json
```

Every pull request gets a fast, validated gate — 3 cases, one judge call each, minutes not tens-of-minutes. The full 12-case dataset (and, if you extend `ci_gate.py` to call RAGAS's per-metric breakdown from Module 7, a deeper diagnostic report) runs nightly on a schedule instead, where the extra latency doesn't block anyone waiting on a PR.
