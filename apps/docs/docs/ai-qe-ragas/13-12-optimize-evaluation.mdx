## Page purpose

Every RAGAS run so far has taken real, noticeable time. This page explains why, gives you one real, measurable optimization to apply to your own evaluation suite, and — just as important — tells you honestly when it isn't worth bothering yet.

## Learning objectives

By the end of this page, you should be able to:

- Explain concretely why local RAGAS evaluation is slow.
- Apply one real concurrency optimization and measure real before/after timing on your own machine.
- Explain the model-size-vs-speed and CPU-vs-GPU trade-offs in your own words.
- State when optimizing evaluation speed is premature.

## Why this has been slow

Two separate causes, both real and both already visible in what you've run:

**Model size and hardware.** Every metric call is a real inference pass on a language model. Unless Ollama has a GPU available to it, that inference runs on CPU — noticeably slower than GPU inference, and the smaller the model, the less this hurts, but it never disappears. Check whether your own Ollama is using a GPU:

```bash
curl -s http://localhost:11434/api/ps
```

Look for `"size_vram"` in the response. `0` means the model is running entirely on CPU. That alone explains a large share of the wait you've experienced in this course.

**Concurrency mismatched to what your server can actually do.** RAGAS's default `RunConfig` allows up to 16 concurrent requests. A single local Ollama server does not process 16 generations at once the way a large hosted API with many backend replicas might — most of those requests just queue, and enough of them queue past their timeout to fail outright. You've already been working around this since Module 6 with `RunConfig(max_workers=2, timeout=300)`; this page is where you find out, on your own machine, whether `2` was actually the right number.

## Apply one real optimization: tune concurrency

Run the same small evaluation at two different `max_workers` settings and time both for real:

```python
# experiments/optimize_workers.py
import time
from ragas import evaluate, EvaluationDataset
from ragas.metrics import Faithfulness
from ragas.llms import LangchainLLMWrapper
from ragas.run_config import RunConfig
from langchain_ollama import ChatOllama

from eval.build_eval_dataset import build_eval_rows

rows = build_eval_rows()[:4]  # a small, fixed slice — same rows for both runs
eval_dataset = EvaluationDataset.from_list(rows)
evaluator_llm = LangchainLLMWrapper(ChatOllama(model="qwen2.5:3b", temperature=0))

for workers in (1, 2, 4):
    start = time.time()
    evaluate(
        dataset=eval_dataset,
        metrics=[Faithfulness()],
        llm=evaluator_llm,
        run_config=RunConfig(timeout=300, max_workers=workers),
    )
    elapsed = time.time() - start
    print(f"max_workers={workers}: {elapsed:.1f}s")
```

**Run it now, and record your own three numbers.** This course won't hand you a specific "optimal" value as fact, because it genuinely depends on your hardware — but expect the relationship to be non-linear, not a straight line down as workers increase. A CPU-bound single local server has a real ceiling on how much true parallelism it can offer; past that ceiling, adding more concurrent requests just adds queuing overhead without adding real throughput, and can push you back toward the timeouts Module 6 had you avoid in the first place. Whatever number wins on your own hardware is the number worth keeping — that's the actual optimization, not a fixed value copied from this page.

## Other real levers, briefly

- **Batching / smaller slices while iterating** — you don't need to run all 12 golden dataset rows on every iteration while you're still tuning a prompt or a chunking change. Evaluate a small, representative slice (like Module 13's smoke subset) during active development, and save the full 12-row run for when you actually need the complete picture.
- **Caching** — `LangchainLLMWrapper` accepts a `cache` argument (`from ragas.cache import DiskCacheBackend; LangchainLLMWrapper(ChatOllama(model="qwen2.5:3b"), cache=DiskCacheBackend())`) so an identical judge call isn't re-run. Worth adopting once you're re-running the *same* rows repeatedly (for example, debugging one metric on one row) rather than genuinely new evaluations.
- **Model size vs. speed** — a smaller evaluator model is faster per call, at some cost to judgment quality; Module 9 already gave you the tool (a validation set) to check whether a faster model is still trustworthy before switching to it purely for speed.
- **CPU vs. GPU** — if Ollama has GPU access, `size_vram` in `ollama ps` output will show non-zero, and generation/evaluation speed improves substantially. This isn't something this course can set up for you — it depends entirely on your own hardware and Ollama's GPU support for it.

## When NOT to optimize this yet

If you're still actively changing the prompt, the chunking, or the golden dataset itself, the bottleneck isn't evaluation speed — it's how many iterations you need before the design settles. Optimizing `max_workers` before that saves you seconds per run while you're still making changes that invalidate the run entirely. Optimize evaluation speed once you're running the *same*, stable configuration repeatedly — for regression checks, CI (Module 13), and model comparisons (Module 10) — not while the thing under test is still actively changing under you.

## QE lesson

This mirrors optimizing a slow test suite: profile first (you did, with the `ollama ps` check and the timing experiment), fix the actual bottleneck (concurrency mismatched to what the backend can do, not "AI is just slow"), and don't spend effort optimizing a suite that's still being actively rewritten. Premature optimization costs the same thing here it always does — time spent tuning something that's about to change again.
