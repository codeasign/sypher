## Learning objectives

By the end of this page, you should be able to:

- Provoke a fabricated response on purpose and explain why it happened.
- Run the same prompt through two different local models and compare the results.
- State honestly what "more reproducible" does and doesn't mean for a local LLM.

## Controlling variance, not eliminating it

`ollama.chat()` accepts an `options` dict. Two settings matter most for testing:

```python
# experiments/temperature_check.py
import ollama

MODEL = "llama3.2:3b"
PROMPT = "In one sentence, what does test coverage mean?"

for i in range(3):
    response = ollama.chat(
        model=MODEL,
        messages=[{"role": "user", "content": PROMPT}],
        options={"temperature": 0, "seed": 42},
    )
    print(f"--- run {i + 1} ---")
    print(response.message.content)
```

**Run it.** `temperature` controls how much randomness goes into picking the next word. `0` pushes the model toward its most likely output at each step instead of sampling more broadly. `seed` fixes the random number generator's starting point. Together, they get you *much* closer to the same answer every run than Module 1's defaults did.

**Be honest about what you're seeing.** Compare this output to Module 1's. It should be far more consistent, but don't assume it's byte-identical every single time. Floating-point execution order on real hardware isn't always perfectly reproducible even with a fixed seed, so "more consistent" is the accurate claim, not "guaranteed identical." Carrying that honestly is itself a QE habit: know the actual guarantee a control gives you, not the one you wish it gave you.

## Provoking a bad response on purpose

Ask the model something specific and checkable that it has no real way to know:

```python
# experiments/provoke_fabrication.py
import ollama

MODEL = "llama3.2:3b"
PROMPT = "According to the latest industry survey, what percentage of QA teams have adopted AI-assisted testing tools?"

response = ollama.chat(model=MODEL, messages=[{"role": "user", "content": PROMPT}])
print(response.message.content)
```

**Run it.** You'll very likely get back a specific, confident-sounding percentage, something like "62%" or "around 45%." You gave the model no survey, no source, no data. Any number it states is fabricated by construction, stated with exactly the same confident phrasing it would use for something true.

This is worth sitting with for a second: this course refuses to show you an invented number as if it were real (you've probably noticed the "no fabricated numeric results" discipline already in how this course is written), and you just watched a model do precisely that, presented as fact, without hesitation. That's not a special failure case. It's the model's default behavior whenever an honest "I don't know" is a less likely-sounding completion than a plausible guess. Module 3's hallucination-trap test cases and Module 14's hallucination testing both exist specifically to catch this pattern automatically instead of noticing it by accident.

## Comparing two models on the same prompt

Pull a second model. This course uses it again for a rigorous, fair comparison in Module 10, and as the RAGAS evaluator model starting in Module 6 (more on why a separate evaluator model matters there), so it's worth having now:

```bash
ollama pull qwen2.5:3b
```

```python
# experiments/compare_models.py
import ollama

PROMPT = "In one sentence, what does test coverage mean?"
MODELS = ["llama3.2:3b", "qwen2.5:3b"]

for model in MODELS:
    response = ollama.chat(model=model, messages=[{"role": "user", "content": PROMPT}])
    print(f"--- {model} ---")
    print(response.message.content)
```

**Run it.** Look at the two responses side by side: wording, length, structure, and (if you run the fabrication prompt through both) whether both models fabricate the same way. Different models trained differently will phrase things differently and can fail differently on the exact same input. That's the whole reason Module 10 treats model comparison as a real experiment with controls, not a vibe check. You're about to see for yourself that "which model is better" isn't obvious from eyeballing a couple of outputs.

## QE lesson

None of this is a detour from testing. It's reconnaissance. Before you can write a useful test oracle or golden dataset case, you need a first-hand feel for how the system under test actually behaves: how much it varies, how it fails when it doesn't know something, and how differently two configurations of "the same kind of system" can behave. Traditional QE does this too, informally, before writing a test plan for an unfamiliar application. This is that same instinct, applied to a model instead of a UI.
