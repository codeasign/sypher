## Page purpose

"The score is low, but the answer looks fine to me" is the moment most QEs new to AI evaluation get stuck, and the moment where guessing costs the most time. This page gives you a real investigation procedure, then runs it against two failures you cause yourself, so root-causing a low score becomes a method instead of a hunch.

## Learning objectives

By the end of this page, you should be able to:

- List, in order, what to check before concluding a low score means "the system is broken."
- Distinguish a retrieval failure from a prompt failure using evidence, not intuition.
- Reproduce two real failures in your own project and trace each to its actual root cause.
- Name reference-answer problems and evaluator problems as categories you must also rule out.

## Five places the problem can actually be

When a score comes back low, resist the urge to immediately blame "the model." There are five distinct places the real cause can live:

1. **Test data**: the golden dataset's reference answer is wrong, ambiguous, or the question doesn't match its own category.
2. **Retrieval**: the chunk that would support a correct answer never made it into `retrieved_contexts`.
3. **Prompt**: the retrieved context was fine, but the system prompt caused the model to hedge, over-decline, or over-commit.
4. **Model**: same prompt, same context, and a different model would still get it right or wrong differently, a genuine model-capability limit.
5. **Evaluator**: the metric's own LLM judge is miscalibrated, and the *score* is wrong even though the *system* isn't.

The investigation order matters: check retrieval before prompt, and prompt before blaming the model. Each earlier check is cheaper to rule out and more likely to be the real cause than people expect.

## Failure 1: retrieval (reusing Module 5's real miss)

You already reproduced this in Module 5. Now look at it through a metric instead of eyeballing it:

```python
# experiments/diagnose_retrieval_failure.py
from ragas import evaluate, EvaluationDataset
from ragas.metrics import ContextRecall
from ragas.llms import LangchainLLMWrapper
from ragas.run_config import RunConfig
from langchain_ollama import ChatOllama
from rag_pipeline import RagPipeline

pipeline = RagPipeline()
result = pipeline.ask("How do I mark something as finished?", top_k=1)

row = [{
    "user_input": "How do I mark something as finished?",
    "retrieved_contexts": result["retrieved_contexts"],
    "response": result["answer"],
    "reference": "Set the task's status to Done.",
}]

evaluator_llm = LangchainLLMWrapper(ChatOllama(model="qwen2.5:3b", temperature=0))
scored = evaluate(
    dataset=EvaluationDataset.from_list(row),
    metrics=[ContextRecall()],
    llm=evaluator_llm,
    run_config=RunConfig(timeout=300, max_workers=2),
)
print(scored.to_pandas()[["user_input", "context_recall"]])
```

**Run it.** Context recall checks whether the retrieved context could support the reference answer. At `top_k=1`, `retrieved_contexts` contains only `data-export-and-deletion.md`, which says nothing about task status. There's no way that context could support "Set the task's status to Done," so a low recall score here isn't a surprising or ambiguous result. It's the metric correctly reporting a fact you already confirmed by hand in Module 5. **This is what a genuine retrieval failure looks like from the metric side: recall low, and the cause is entirely upstream of generation.**

## Failure 2: a prompt that causes real fabrication

Weaken the system prompt so it discourages the model from declining to answer:

```python
# experiments/diagnose_prompt_failure.py
import ollama
from rag_pipeline import RagPipeline

BAD_PROMPT = """You are a helpful, confident support assistant for Fernwood, a
project management app. Use the CONTEXT below to help answer the question.
Always give the user a specific, direct, confident answer — do not say you
do not know."""

pipeline = RagPipeline()
retrieved = pipeline.retrieve("What is the rate limit on Fernwood's public API?")
context = "\n\n".join(c["text"] for c in retrieved)
prompt = f"CONTEXT:\n{context}\n\nQUESTION:\nWhat is the rate limit on Fernwood's public API?"

response = ollama.chat(
    model="llama3.2:3b",
    messages=[{"role": "system", "content": BAD_PROMPT}, {"role": "user", "content": prompt}],
)
print(response.message.content)
```

**Run it.** `docs/` has no mention of a public API anywhere. Retrieval correctly returns no relevant chunk, exactly as it should for an unanswerable question. But in one real run of this exact script, the model (instructed not to say it doesn't know) answered: **"Fernwood's public API has a rate limit of 50 requests per minute."** A specific, confident, entirely fabricated number, for a question `docs/` never addresses. Retrieval did its job correctly here; **the failure is entirely in the prompt.**

Score it to confirm:

```python
# experiments/score_prompt_failure.py
from ragas import evaluate, EvaluationDataset
from ragas.metrics import Faithfulness
from ragas.llms import LangchainLLMWrapper
from ragas.run_config import RunConfig
from langchain_ollama import ChatOllama

row = [{
    "user_input": "What is the rate limit on Fernwood's public API?",
    "retrieved_contexts": ["<paste your retrieved context text here>"],
    "response": "<paste the fabricated answer you got above>",
    "reference": "Not documented. No public API is mentioned anywhere in the docs.",
}]

evaluator_llm = LangchainLLMWrapper(ChatOllama(model="qwen2.5:3b", temperature=0))
scored = evaluate(
    dataset=EvaluationDataset.from_list(row),
    metrics=[Faithfulness()],
    llm=evaluator_llm,
    run_config=RunConfig(timeout=300, max_workers=2),
)
print(scored.to_pandas()[["user_input", "faithfulness"]])
```

A specific rate-limit claim with nothing in the retrieved context to support it has nowhere to draw faithfulness from. Expect this score to come back low, for the same structural reason context recall came back low in Failure 1: the metric is reporting something you can already verify by reading the context yourself.

**A third pattern, already in your Module 5 data:** re-check your Module 5 full-dataset run for `gd-003`, `gd-004`, or `gd-005`, cases where the correct document *was* retrieved and the pipeline still answered `"Not documented."` That's the opposite prompt problem: a system prompt so conservative it under-uses context it was actually given. Same root cause category (prompt), opposite failure direction. Worth having both in mind, since "make the prompt stricter" isn't a universal fix if strictness itself is what's causing the failure.

## Ruling out model, reference-answer, and evaluator problems

These three are real causes you must still rule out, even without a dedicated repro on this page:

- **Model problem**: swap in a different model (Module 10 gives you the harness to do this fairly) with the same prompt and same context. If the second model gets it right, the first model's capability was the actual limit, not your prompt or retrieval.
- **Reference-answer problem**: before trusting a low score, reread the reference answer against the real source doc, the same review discipline from Module 3. A reference answer that's wrong, outdated, or arguably ambiguous will produce a "failure" that isn't the system's fault at all.
- **Evaluator problem**: sanity-check the judge itself: read the row by hand, decide what score *you'd* give it, and compare. A judge that disagrees with your own careful read on a case that isn't genuinely close is a signal the evaluator needs attention, not the system under test. Module 9 builds a real, validated judge; keep this manual sanity check as your stopgap until then.

*(These three are reasoned about here, not reproduced with a hands-on repro on this page. Treat them as real checks to run, not equivalent in confidence to the two failures you just caused and diagnosed yourself.)*

## QE lesson

This is root-cause analysis, not a new skill. It's the same discipline as triaging a failing CI job: check the cheapest, most likely layer first (test data), work outward (retrieval, then prompt, then model), and don't rule out the tool doing the measuring (the evaluator) just because it's convenient to trust it. The only new part is that "the system" now has more layers than a deterministic app did.
