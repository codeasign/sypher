This course assumes you are already comfortable with Python basics: variables, functions, `for` loops, maybe a `class` or two. What it does not assume is any API testing experience, so we start from the very beginning of that: getting a real backend running, and proving to yourself that you can talk to it over HTTP before you write a single test.

Every module in this course runs against the same system under test: a 4-role RBAC (Role-Based Access Control) healthcare app called `rbac-healthcare-system`. It has an Express API, a SQLite database, JWT authentication, and a Swagger page documenting every endpoint. This course tests it **black-box**, over real HTTP, from a completely separate Python project, so by the end of this page you will have two things running side by side: the Node backend, and a Python project that can reach it.

## Confirm Python and pip are ready

You will need Python 3.10 or later. Check what you have:

```bash
python3 --version
pip3 --version
```

If either command is not found, install Python from [python.org](https://python.org); `pip` ships bundled with it. On some systems the commands are just `python` and `pip` instead of `python3`/`pip3`; either is fine as long as they point at a Python 3.10+ install.

## Clone and run the RBAC app

This is the system under test. Clone it anywhere on your machine, separate from the Python project you will build in a minute:

```bash
git clone https://github.com/codedbyabhishekc/rbac-healthcare-system.git
cd rbac-healthcare-system/backend
npm install
mkdir database
```

The `database` folder is where the app's SQLite file lives once the server creates it. It is not checked into the repo, so you have to make it yourself.

Create a `.env` file inside `backend/`:

```bash
PORT=5000
JWT_SECRET=any-long-random-string-you-want
NODE_ENV=development
```

Start the server:

```bash
npm start
```

You should see:

```bash
Connected to SQLite database
Database initialized successfully
Server is running on port 5000
Swagger documentation available at http://localhost:5000/api-docs
```

Leave that running. This course never imports the app's code, so the server has to actually stay up while you work. Every test you write is a real network request to `http://localhost:5000`.

## Seed the database

Stop the server for a moment (`Ctrl+C`) and run the seed script:

```bash
npm run seed
```

This populates the database with 3 Administrators, 8 Doctors, 7 Nurses, 15 Patients, 20 appointments, and 15 medical records. Every seeded account uses the password `pass@123`, except the default admin account, which uses `admin` / `admin123`. That is the login you will use most often across this course. Start the server back up with `npm start` once seeding finishes.

## Confirm Swagger loads

With the server running, open [http://localhost:5000/api-docs](http://localhost:5000/api-docs) in a browser. That is the Swagger UI, a browsable list of every endpoint this app exposes, generated straight from comments in the route files. You will dig into exactly how to pull this spec programmatically in Module 5; for now, just confirm the page loads and lists endpoints under headings like **Authentication**, **Users**, **Appointments**, **Medical Records**, and **Patient Records**.

## Set up your Python test project

Now, in a completely different folder (not inside the cloned repo, since this course never touches its source) create the project you will build up over the rest of this course:

```bash
mkdir rbac-api-tests
cd rbac-api-tests
python3 -m venv venv
source venv/bin/activate   # on Windows: venv\Scripts\activate
```

A virtual environment keeps this project's packages separate from anything else on your machine, worth doing even for a test project you might think of as "throwaway." Install the two packages this whole course is built on:

```bash
pip install pytest httpx
```

`pytest` is the test runner and framework; `httpx` is the HTTP client you will use to actually send requests. You will set both of these up properly, with real config files, in the next module; this is just enough to make the smoke check below possible.

## Make one real request

Before writing any test infrastructure, prove the environment works end to end with a plain Python script, the same login request the app's own frontend would make:

```python
# smoke_check.py
import httpx

response = httpx.post(
    "http://localhost:5000/api/auth/login",
    json={"username": "admin", "password": "admin123"},
)

print(response.status_code)
print(response.json())
```

Run it:

```bash
python3 smoke_check.py
```

You should get back something like this (the token itself will be a long, unreadable string, which is expected):

```bash
200
{'token': 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...', 'user': {'id': 1, 'username': 'admin', 'email': 'admin@hospital.com', 'role': 'Administrator', 'full_name': 'System Administrator'}}
```

That response is the whole app in miniature: you sent credentials over HTTP, the server checked them against the database, and it handed back a signed token plus the logged-in user's details. Every protected endpoint in this course expects that token on later requests. You will build a proper pytest fixture around this exact call in the authentication module, so you never have to retype this logic again.

## Try it

With the server still running, edit `smoke_check.py` to log in as a different seeded user (try `doctor1` with password `pass@123`) and print just the `role` field from the response. Confirm it says `"Doctor"` instead of `"Administrator"`. That role field is what drives every permission check you will test later in this course, so it is worth seeing it change with your own eyes before moving on.
