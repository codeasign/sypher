Every test you've written so far picks one specific input and checks one specific outcome — a hand-picked payload, a hand-picked ID. Property-based testing flips that: instead of you choosing the examples, a tool generates many varied inputs automatically, straight from the spec's own schema, and checks a general property holds across all of them — here, "the real response matches what the spec says is possible." [Schemathesis](https://schemathesis.readthedocs.io/) is the library for doing this against an OpenAPI spec specifically, and it's a natural fit for a course that's been treating the spec as ground truth since Module 5.

## Installing it

```bash
pip install schemathesis
```

## Loading the schema you already know how to fetch

Schemathesis needs the same spec `dict` you've been using since Module 5 — you already have a way to get it that doesn't depend on a clean `/openapi.json` URL existing:

```python
import schemathesis

from conftest import fetch_openapi_spec   # the helper you wrote in Module 5

raw_spec = fetch_openapi_spec()
schema = schemathesis.from_dict(raw_spec, base_url="http://localhost:5000")
```

`schemathesis.from_dict(...)` builds a `schema` object that knows every path, method, and declared parameter/body schema — everything you were walking by hand in Module 6, now driving actual generated test cases instead of a printed checklist.

## The core pattern: one decorator, many generated cases

```python
@schema.parametrize()
def test_api_matches_its_own_spec(case):
    case.call_and_validate()
```

`@schema.parametrize()` works like `@pytest.mark.parametrize`, but instead of a list you wrote, it expands into one test per operation in the schema, and for each operation, `case.call_and_validate()` does three things: generates realistic-but-varied input data matching that operation's declared parameters and request body schema, sends the actual request, and asserts the response matches what the spec says — the right status code is one of the documented ones, and the response body (where a schema is declared) matches its shape. Run `pytest -v` and you'll see one result per operation, the same way `@pytest.mark.parametrize` reports one result per tuple.

## Handling auth

Straight out of the box, this fails hard on every protected endpoint — Schemathesis doesn't know your app requires a bearer token, so it sends none, and gets `401` back for almost everything. Pass a real token in explicitly, the same way you've passed `headers` to every `httpx` call in this course:

```python
def get_admin_token() -> str:
    import httpx

    response = httpx.post(
        "http://localhost:5000/api/auth/login",
        json={"username": "admin", "password": "admin123"},
    )
    return response.json()["token"]


ADMIN_HEADERS = {"Authorization": f"Bearer {get_admin_token()}"}


@schema.parametrize()
def test_api_matches_its_own_spec_authenticated(case):
    case.call_and_validate(headers=ADMIN_HEADERS)
```

`call_and_validate(headers=...)` merges your headers into whatever Schemathesis generated for that case, the same way you'd pass `headers=` to a plain `httpx` call. Using the Administrator's token here means every operation runs with the *most* permissive role — worth knowing, since it means this pass won't surface RBAC-specific denials the way Module 10's hand-written matrix tests do. Property-based testing here is complementary to that matrix, not a replacement for it: it's checking "does the response shape match the spec," not "does the right role get denied."

## A real, verified spec ambiguity this uncovers

Recall from Module 6: `POST /api/auth/login` and `POST /api/auth/register` don't declare their own `security` override — they simply have no `security` key on the operation at all, while the spec's top-level document *does* declare a default `security: [{bearerAuth: []}]`. Read strictly, that means these two operations technically inherit the document-wide requirement, even though the real app doesn't enforce it on them. A spec-literal tool like Schemathesis may include an `Authorization` header on generated login/register requests as a result — harmless here, since `auth.routes.js` never actually checks it, but worth noticing: the tool is following the spec exactly as written, and the spec itself is what's slightly imprecise. That's not a Schemathesis bug; it's the spec-vs-reality gap Module 6 flagged, now showing up in a different tool's behavior instead of your own code.

## What it actually catches — reusing what you already found by hand

Run the authenticated version above against `POST /api/appointments` specifically, and there's a good chance you'll see a failure that looks familiar:

```bash
FAILED test_api_matches_its_own_spec_authenticated[POST /api/appointments]

schemathesis.exceptions.CheckFailed: Undocumented HTTP status code

Received: 500
Documented: 201
```

That's the exact same gap you found by hand in Module 11 — a request missing `patient_id` gets a raw `500` because this route has no validation layer — except this time, Schemathesis found the input that triggers it by generating varied payloads against the schema automatically, rather than you deliberately constructing one. That's the real value of property-based testing over hand-written cases: it doesn't just check the examples you thought to write, it explores the space around them, and it's structurally suited to finding exactly the kind of contract violation — a status code the spec never claimed was possible — this course has been teaching you to care about since Module 1.

## Where this fits next to everything else you've built

Property-based testing isn't a replacement for the rest of this course's hand-written suite — it's a different kind of net, best run alongside the others. Your `test_medical_record_crud_lifecycle` from Module 7 proves one specific, meaningful business scenario works correctly end to end; Schemathesis proves that, across a much wider space of inputs than you'd hand-write, no operation returns something outside its documented contract. A mature suite runs both: hand-written tests for scenarios you know matter, and a Schemathesis pass as a broad, low-effort check that nothing about the contract itself has quietly drifted.

## Try it

Restrict Schemathesis to just one path instead of the whole schema — `schema["/api/medical-records"]["POST"].as_strategy()` combined with Hypothesis's `@given`, or the simpler route of filtering inside your test function by checking `case.operation.path`. Run it several times and see whether it independently rediscovers the "missing `diagnosis` still returns `201`" gap you found by hand back in Module 7, rather than an undocumented-status failure — a spec violation Schemathesis's default checks won't catch on their own, since a `201` *is* documented for that operation, even though the field it created is incomplete. That's worth sitting with: automated, spec-driven checks catch contract drift in status codes and shapes; they don't replace a human noticing "this succeeded when it probably shouldn't have."
