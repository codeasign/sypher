The checklist from the last module turned every path in the spec into a named test case. This module writes the first real ones — a full Create/Read/Update/Delete lifecycle against medical records, checked at every step against exactly what `spec["paths"]["/api/medical-records"]` and `spec["paths"]["/api/medical-records/{id}"]` say should happen.

## The four operations, and what "success" means for each

CRUD stands for Create, Read, Update, Delete — the four operations almost every resource in a real API supports in some form. The spec gives you the expected status code for each:

- **Create** (`POST /api/medical-records`) — spec says `201`, plus enough information to find the new thing again (`recordId`).
- **Read** (`GET /api/medical-records/{id}`) — spec says `200`, with the resource's current state.
- **Update** (`PUT /api/medical-records/{id}`) — spec says `200` — and, critically, the *next* `GET` should reflect the change. A `200` from `PUT` alone doesn't prove anything actually changed in the database; the spec documents the response, not the side effect.
- **Delete** (`DELETE /api/medical-records/{id}`) — spec says `200`, and the *next* `GET` for that same resource should now fail — `404`, per `spec["paths"]["/api/medical-records/{id}"]["get"]["responses"]`.

That last point in each case is the one people skip when they're in a hurry: testing that an update or delete "worked" by only checking the response of the update/delete call itself, and never actually reading the resource back afterward. A route can return `200` while silently doing nothing to the database — only a follow-up read proves persistence, and the spec's own documented responses for the `GET` endpoints are exactly what you check that follow-up read against.

## Full lifecycle test

```python
def test_medical_record_crud_lifecycle(login_as, api_client):
    doctor = login_as("Doctor")

    # CREATE — spec says 201
    created = api_client.post(
        "/api/medical-records",
        headers=doctor["headers"],
        json={
            "patient_id": 20,
            "diagnosis": "Seasonal allergies",
            "prescription": "Loratadine 10mg",
        },
    )
    assert created.status_code == 201
    record_id = created.json()["recordId"]

    # READ — confirm what was actually written; spec says 200
    after_create = api_client.get(
        f"/api/medical-records/{record_id}", headers=doctor["headers"]
    )
    assert after_create.json()["diagnosis"] == "Seasonal allergies"
    assert after_create.json()["notes"] is None

    # UPDATE — spec says 200
    updated = api_client.put(
        f"/api/medical-records/{record_id}",
        headers=doctor["headers"],
        json={
            "diagnosis": "Seasonal allergies (resolved)",
            "prescription": "Loratadine 10mg",
            "notes": "Follow up in 2 weeks",
        },
    )
    assert updated.status_code == 200

    # READ again — prove the update actually persisted
    after_update = api_client.get(
        f"/api/medical-records/{record_id}", headers=doctor["headers"]
    )
    assert after_update.json()["diagnosis"] == "Seasonal allergies (resolved)"
    assert after_update.json()["notes"] == "Follow up in 2 weeks"

    # DELETE — spec says 200
    deleted = api_client.delete(
        f"/api/medical-records/{record_id}", headers=doctor["headers"]
    )
    assert deleted.status_code == 200

    # READ again — spec says a missing record is 404
    after_delete = api_client.get(
        f"/api/medical-records/{record_id}", headers=doctor["headers"]
    )
    assert after_delete.status_code == 404
```

Five requests, four operations, but eight assertions in total — every write is followed by a read that proves it actually took effect. That's the whole discipline this module is teaching: a CRUD test isn't complete until it's checked the *after* state, not just the response to the write, and every status code asserted above is one you can point back at a specific entry in `spec["paths"]`.

Notice too that creating a medical record required logging in as `Doctor` specifically — `spec["paths"]["/api/medical-records"]["post"]["security"]` shows this operation requires auth, and the real app additionally restricts it to doctors only, something the spec's `security` block doesn't distinguish (it just says "some authenticated bearer token," not "which role"). You'll map out exactly which operations are gated to which roles, across every resource, in the RBAC permission matrix module. For now, `Doctor` is simply the role that's allowed to do the write you're testing.

## Checking a request the spec would reject

`requestBody.schema.required` for `POST /api/medical-records` lists `patient_id` and `diagnosis` — worth confirming the app actually enforces that, not just that the spec claims it does:

```python
def test_create_without_required_diagnosis_field(login_as, api_client, openapi_spec):
    required_fields = openapi_spec["paths"]["/api/medical-records"]["post"][
        "requestBody"
    ]["content"]["application/json"]["schema"]["required"]
    assert "diagnosis" in required_fields   # confirm the spec really claims this

    doctor = login_as("Doctor")
    response = api_client.post(
        "/api/medical-records",
        headers=doctor["headers"],
        json={"patient_id": 20},   # diagnosis deliberately omitted
    )

    print(response.status_code, response.text)
```

Run that last `print` and you'll find something worth sitting with: the response is `201`, not a rejection — the record gets created anyway, with `diagnosis` simply absent from the row. The spec *documents* `diagnosis` as required; the real route doesn't actually enforce it. That's not a bug in your test — it's a real, verified gap between what this endpoint promises and what it does, and it's exactly the kind of thing spec-driven testing is supposed to surface. You'll test gaps like this one deliberately, as their own category, in the negative-testing module.
