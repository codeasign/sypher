Every module up to this point has focused on one technique at a time, mostly against appointments and medical records. This capstone points the whole toolkit (the spec, fixtures, RBAC matrix, schema validation, negative cases, and CI) at a part of the app this course has only ever touched in passing: registration and the `/api/users` endpoints.

## The area you're covering

Users has come up constantly as a supporting character: you have logged in through it, looked up fixtures through it, checked admin-only access through it, but it has never gotten a complete, spec-checked suite of its own. It is a good capstone target for exactly that reason: it is real, it is already partially familiar, and building full coverage for it means applying everything from this course end to end, not learning anything new.

## Step 1: pull the checklist straight from the spec

Reuse `list_operations` from Module 6, filtered to just this area:

```python
def test_users_and_auth_checklist(openapi_spec):
    operations = list_operations(openapi_spec)
    relevant = [op for op in operations if "/users" in op["path"] or "/auth" in op["path"]]

    paths = {(op["method"], op["path"]) for op in relevant}
    assert paths == {
        ("POST", "/api/auth/register"),
        ("POST", "/api/auth/login"),
        ("GET", "/api/users"),
        ("GET", "/api/users/{id}"),
        ("PUT", "/api/users/{id}"),
        ("DELETE", "/api/users/{id}"),
        ("GET", "/api/users/role/{role}"),
    }
```

That is the checklist this capstone builds coverage against: seven operations, each with real, verified rules behind it:

- `POST /api/auth/register`: creates a user with whatever `role` is provided; no auth required.
- `GET /api/users`: list every user. Administrator only.
- `GET /api/users/{id}`: view one user. An Administrator can view anyone; anyone else can only view their own profile.
- `PUT /api/users/{id}`: update `full_name`, `phone`, `email`. Same ownership rule as viewing.
- `DELETE /api/users/{id}`: Administrator only.
- `GET /api/users/role/{role}`: list users by role. Open to any authenticated user.

## Step 2: the RBAC matrix, parametrized

Nothing new to install: every fixture this suite needs already exists in `conftest.py` from earlier modules:

```python
# test_users_capstone.py
import pytest


@pytest.mark.parametrize(
    "role,expected_status",
    [
        pytest.param("Administrator", 200, id="admin-can-list-users"),
        pytest.param("Doctor", 403, id="doctor-forbidden"),
        pytest.param("Nurse", 403, id="nurse-forbidden"),
        pytest.param("Patient", 403, id="patient-forbidden"),
    ],
)
def test_list_all_users_role_gate(login_as, api_client, role, expected_status):
    session = login_as(role)
    response = api_client.get("/api/users", headers=session["headers"])
    assert response.status_code == expected_status
```

## Step 3: ownership, not just role

`GET /api/users/{id}` and `PUT /api/users/{id}` are not a flat allow/deny: their real rule is "yourself, or an admin," which needs its own tests rather than a role table:

```python
def test_a_user_can_view_their_own_profile(login_as, api_client):
    patient = login_as("Patient")
    response = api_client.get(f"/api/users/{patient['user_id']}", headers=patient["headers"])
    assert response.status_code == 200
    assert response.json()["id"] == patient["user_id"]


def test_a_user_cannot_view_someone_elses_profile(login_as, get_first_user_with_role, api_client):
    patient = login_as("Patient")
    admin = get_first_user_with_role("Administrator")

    response = api_client.get(f"/api/users/{admin['id']}", headers=patient["headers"])
    assert response.status_code == 403


def test_an_administrator_can_view_anyones_profile(login_as, get_first_user_with_role, api_client):
    admin = login_as("Administrator")
    patient = get_first_user_with_role("Patient")

    response = api_client.get(f"/api/users/{patient['id']}", headers=admin["headers"])
    assert response.status_code == 200
```

## Step 4: registration, then CRUD with a real read-after-write check

Registration is where this suite's data comes from, rather than relying only on seeded accounts, and it is a chance to reuse the `jsonschema` validation from Module 9, since `POST /api/auth/register` is one of the operations the spec actually declares a request schema for:

```python
import jsonschema


def test_registers_a_new_patient_matching_the_spec_schema(openapi_spec, api_client):
    schema = openapi_spec["paths"]["/api/auth/register"]["post"]["requestBody"][
        "content"
    ]["application/json"]["schema"]
    payload = {
        "username": "capstone_patient",
        "email": "capstone_patient@example.com",
        "password": "correct-horse-1",
        "role": "Patient",
        "full_name": "Capstone Test Patient",
    }
    jsonschema.validate(instance=payload, schema=schema)   # confirm it matches the spec first

    response = api_client.post("/api/auth/register", json=payload)
    assert response.status_code == 201


def test_updates_and_persists_a_profile_change(login_as, api_client):
    patient = login_as("Patient")

    updated = api_client.put(
        f"/api/users/{patient['user_id']}",
        headers=patient["headers"],
        json={"full_name": "Updated Name", "phone": "555-0000", "email": "updated@example.com"},
    )
    assert updated.status_code == 200

    fetched = api_client.get(f"/api/users/{patient['user_id']}", headers=patient["headers"])
    assert fetched.json()["full_name"] == "Updated Name"   # the write actually persisted
```

That `test_updates_and_persists_a_profile_change` test is the same discipline Module 7 taught with medical records: a `200` from `PUT` alone does not prove anything changed, so the test reads the resource back and checks the new value actually stuck.

## Step 5: negative cases, confirmed rather than assumed

The same "do not assume, confirm" discipline from Module 11, applied here:

```python
def test_rejects_a_request_with_no_token(api_client):
    response = api_client.get("/api/users")
    assert response.status_code == 401


def test_returns_404_for_a_user_id_that_does_not_exist(login_as, api_client):
    admin = login_as("Administrator")
    response = api_client.get("/api/users/999999", headers=admin["headers"])
    assert response.status_code == 404
```

## Where to go from here

You started this course guessing at a JSON URL for the RBAC app's spec and finding it was not there. By this point you have built a suite that pulls the real spec out of a page that was not designed to hand it to you, generates a checklist from it, validates requests and responses against real and hand-written contracts, covers a full 4-role permission matrix, deliberately documents where the app's real behavior and its own spec disagree, runs property-based checks that rediscover those gaps automatically, and gates merges on all of it in CI. That is not a toy exercise. It is the actual shape of API test ownership on a real team, and the spec-first habit (checking reality against a written contract instead of trusting whatever the code currently does) travels to any API you test next, documented or not.

If you want to take these same RBAC-app habits and point them at a browser instead of an API, this site's Playwright Test Automation course picks up from here. And if API testing itself is what you want to go deeper on in a different language, the TypeScript edition of this course covers the same ground with a different toolchain, worth comparing, since a few of the real gaps you found here (the missing `diagnosis` validation, the unvalidated appointments route) are visible from that side too.
