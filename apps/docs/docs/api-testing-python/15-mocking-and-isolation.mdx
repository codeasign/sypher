Every module so far has deliberately kept everything real: real app, real database, real password hashing, real HTTP round trips. This module explains why that is not just this course's style but close to a hard requirement of black-box testing itself, and covers the one narrow, legitimate place mocking still fits.

## Why black-box testing has almost nothing to mock

An in-process test suite imports the application directly, which means it can reach in and swap out one specific internal piece (a hashing library, a database driver) for a fake, while leaving everything else real. This course's tests do not import anything from the RBAC app at all; they send real HTTP requests to a real, running server, over the network, the same way any external client would. There is no "internal piece" to reach into, because nothing internal is visible from where these tests stand. The RBAC app is a sealed box, and the only surface a black-box test has any control over is the request it sends and the response it reads back.

That is not a limitation to work around, it is most of the reason black-box tests are trustworthy in the first place. Mocking anything the SUT itself does would mean you are no longer testing the RBAC application at all; you would be testing your own mock's behavior back at yourself.

## The one thing that actually is yours to mock: your own HTTP layer

The one piece of code in this whole course that genuinely belongs to *you*, not the app, is the `httpx` calls your test project makes. [`respx`](https://lundberg.github.io/respx/) intercepts `httpx` requests at the transport level, which makes it possible to test your **own** test-infrastructure code deterministically, including failure modes a real, healthy server will not reliably produce on demand.

```bash
pip install respx
```

Say you had built a small retry helper for flaky network conditions:

```python
# a hypothetical helper you might add to conftest.py
import httpx


def resilient_get(url: str, retries: int = 1) -> httpx.Response:
    last_error = None
    for _ in range(retries + 1):
        try:
            return httpx.get(url)
        except httpx.ConnectError as exc:
            last_error = exc
    raise last_error
```

Testing that it actually retries means forcing a connection failure on the *first* attempt and success on the *second*, not something you can ask a real, working server to do on command. `respx` can:

```python
import httpx
import respx


@respx.mock
def test_resilient_get_retries_once_after_a_connection_error():
    route = respx.get("http://fake-service.test/ping")
    route.side_effect = [httpx.ConnectError("simulated network failure"), httpx.Response(200, json={"ok": True})]

    response = resilient_get("http://fake-service.test/ping")

    assert response.status_code == 200
    assert route.call_count == 2
```

`@respx.mock` intercepts every `httpx` call made inside the test function; `route.side_effect` gives it a list to work through in order (a raised exception first, a real `httpx.Response` second) so the first call inside `resilient_get` fails exactly the way a real network hiccup would, and the second succeeds. `route.call_count` confirms the retry actually happened, not just that the function eventually returned something. This is testing *your own code's resilience logic* in isolation; nothing here claims to be testing the RBAC app.

## What NOT to mock, proven, not just claimed

Here is the same tool, used somewhere it would quietly destroy the entire point of this course:

```python
@respx.mock
def test_dangerous_example_never_do_this():
    respx.post("http://localhost:5000/api/auth/login").mock(
        return_value=httpx.Response(200, json={"token": "fake-token", "user": {"role": "Administrator"}})
    )

    response = httpx.post(
        "http://localhost:5000/api/auth/login",
        json={"username": "admin", "password": "definitely-the-wrong-password"},
    )

    print(response.status_code, response.json())
    # 200 -- but this request never reached the real server at all.
```

Run that, and it "passes": a `200`, a token, a role, for a password that is not the admin account's real password. `respx.mock` intercepted the request before it ever left the process; the real RBAC server never saw it, never checked anything, and has no idea this test exists. A test suite with a pattern like this in it would keep reporting green straight through an actual regression that broke password checking completely, which is close to the worst possible failure mode a test suite can have: reporting success while the thing it claims to verify is actually broken, and doing so specifically *because* the test stopped talking to the real app.

The rule that keeps this from happening, adapted from the in-process version of this same lesson: **never mock a request whose real response is the thing a test exists to verify.** Every test against `http://localhost:5000` in the rest of this course is a correctness test in exactly that sense, which means the honest version of this rule, for a black-box suite, is closer to *"never use `respx` against the app you are actually testing at all."* Reserve it entirely for the narrow case this module opened with: proving your own test helpers behave correctly under conditions you cannot reliably reproduce against a real server.

## Try it

Write a `resilient_post` version of the retry helper above, and a `respx`-based test proving it retries a `POST` the same way `resilient_get` retries a `GET`. Then, as a deliberate exercise in seeing the danger yourself: temporarily add a `respx.mock`-decorated test that intercepts `GET /api/appointments` and returns a fake `200` with an empty list, run it, and watch it "pass" regardless of what the real endpoint would actually return, then delete it. That is the whole risk of this module, seen firsthand rather than just described.
