Field-by-field assertions work, but they don't scale — a response with ten fields means either ten separate checks or one large key-set comparison, and either way a field silently changing type is easy to miss unless you happened to assert on that exact field. Schema validation flips the approach: define the shape a response (or request) is supposed to have once, and let a library check the whole thing automatically. This module covers two tools for two different jobs, because the RBAC app's spec itself only gives you one half of the picture.

## What the spec actually declares — and doesn't

Back in Module 5, `spec["components"]["schemas"]` came back empty. Looking closer at individual operations, several of them *do* declare a `requestBody` schema — `POST /api/medical-records`, `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/appointments` all specify exactly what fields a request body needs. None of them declare a schema for their *response* body — every documented response is just a bare `description` string. That's a real, verified asymmetry in this spec: it tells you what to send, but nothing structured about what comes back. The two tools in this module split cleanly along that same line.

## `jsonschema`: validating requests against what the spec actually declares

Since request bodies *are* documented with real JSON Schema, `jsonschema` can validate directly against the spec itself — no schema to hand-write, because the spec already has one:

```bash
pip install jsonschema
```

```python
import jsonschema


def test_medical_record_payload_matches_spec_schema(openapi_spec):
    schema = openapi_spec["paths"]["/api/medical-records"]["post"]["requestBody"][
        "content"
    ]["application/json"]["schema"]

    valid_payload = {
        "patient_id": 20,
        "diagnosis": "Seasonal allergies",
        "prescription": "Loratadine 10mg",
    }
    jsonschema.validate(instance=valid_payload, schema=schema)   # raises if invalid

    invalid_payload = {"patient_id": 20}   # missing required "diagnosis"
    try:
        jsonschema.validate(instance=invalid_payload, schema=schema)
        assert False, "expected validation to fail"
    except jsonschema.ValidationError as exc:
        assert "diagnosis" in str(exc)
```

`jsonschema.validate(instance=..., schema=...)` raises a `jsonschema.ValidationError` if the instance doesn't match the schema, and returns `None` silently if it does — that's why the valid case above has no assertion after it; reaching that line without an exception *is* the pass. This is the most direct form of spec-driven testing in the whole course: the schema being validated against isn't something you wrote by hand and could get subtly wrong — it's the literal document the API's own author published, pulled straight out of `openapi_spec`.

## Pydantic: filling the gap the spec leaves for responses

Since there's no response schema to validate against, you write one — as a Pydantic model, which doubles as both a validator and a set of real Python type hints:

```bash
pip install pydantic
```

```python
from typing import Optional
from pydantic import BaseModel


class LoginUser(BaseModel):
    id: int
    username: str
    email: str
    role: str
    full_name: str


class LoginResponse(BaseModel):
    token: str
    user: LoginUser


def test_login_response_matches_hand_written_contract(api_client):
    response = api_client.post(
        "/api/auth/login", json={"username": "admin", "password": "admin123"}
    )

    parsed = LoginResponse.model_validate(response.json())   # raises on mismatch

    assert parsed.user.role == "Administrator"
```

`LoginResponse.model_validate(...)` takes a plain dict and either returns a fully validated, typed instance — `parsed.user.role` is a real attribute access, not a dict lookup — or raises a `pydantic.ValidationError` naming exactly which field didn't match and why. Nesting `LoginUser` inside `LoginResponse` mirrors the real nested shape of the response, the same way the spec's own `requestBody` schemas nest `properties` inside `properties`.

Deliberately break it to see what the error looks like — change `role: str` to `role: int` and rerun:

```bash
pydantic_core._pydantic_core.ValidationError: 1 validation error for LoginResponse
user.role
  Input should be a valid integer [type=int_parsing, input_value='Administrator', input_type=str]
```

That `user.role` path is what makes this worth the setup over loose `dict` assertions — instead of a generic failure, you get the exact field, nested path included, and exactly what type was expected versus what showed up.

## Validating a whole list at once

The real payoff shows up on list endpoints, where field-by-field assertions get repetitive fast:

```python
class Appointment(BaseModel):
    id: int
    patient_id: int
    doctor_id: int
    appointment_date: str
    status: str
    reason: Optional[str] = None
    notes: Optional[str] = None
    patient_name: str
    doctor_name: str


def test_every_appointment_in_the_list_matches_the_contract(login_as, api_client):
    admin = login_as("Administrator")
    response = api_client.get("/api/appointments", headers=admin["headers"])

    appointments = [Appointment.model_validate(item) for item in response.json()]

    assert len(appointments) > 0
```

That list comprehension validates the type and shape of *every* appointment the seeded database returns, not just the first one — and a single bad record anywhere in that list raises immediately, naming its index and field. Notice `reason` and `notes` are typed `Optional[str] = None` rather than plain `str` — the real API does return `null` for `notes` when none was provided, and a model that didn't account for that would reject perfectly valid data. Matching a model to reality, not to what you assume the shape should be, is the whole point — the same lesson Module 7 already taught you the hard way when `POST /api/medical-records` accepted a payload the spec's own schema says it shouldn't have.

## Two tools, two different guarantees

`jsonschema` against the spec's `requestBody` schemas tells you: does this payload match what the API's own documentation says it accepts. A hand-written Pydantic model for a response tells you: does this response match the contract *you've* defined, since the spec didn't define one. Neither replaces the other, and neither is inherently "the real one" — the spec is authoritative where it actually documents something, and your own model is the best available substitute exactly where it doesn't.
