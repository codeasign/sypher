The coverage module pointed out that running this course's tests together has none of the shared-process problems an in-process suite has to work around. That good news mostly carries over to parallel execution too, but not entirely, and this module is about exactly where it stops.

## pytest-xdist

pytest does not run test files in parallel by default; [`pytest-xdist`](https://pytest-xdist.readthedocs.io/) adds that:

```bash
pip install pytest-xdist
pytest -n auto
```

`-n auto` spins up one worker process per CPU core and distributes test *functions* (not just files) across them: genuinely separate OS processes, each running a subset of the suite at the same moment. For a suite of any real size, this is usually a significant speedup.

## Why this course's tests are mostly safe to parallelize

Every request this course's tests send goes to the same real, already-running RBAC server, and Express, like most real HTTP servers, is built to handle many concurrent requests at once; that is not a special accommodation for testing, it is just normal server behavior under everyday traffic. Multiple `pytest-xdist` workers hitting `POST /api/auth/login` or `GET /api/appointments` at the same moment is not meaningfully different from multiple real users doing the same thing, and the server does not know or care which case it is handling. That is a genuine structural advantage over an in-process suite testing the exact same app: there is no shared port to bind, no shared module registry, nothing about this course's request/response cycle that assumes it is the only test running at that instant.

## The real exception: your own direct database access

The database-testing module's `db_query` fixture opens its own raw `sqlite3` connection straight to the same file the live server reads and writes. That is a deliberate, useful choice for verifying rows directly, and it is also the one place in this course where parallel workers genuinely can collide. SQLite serializes writes at the file level, and Python's `sqlite3` module does not set a busy timeout by default; several `pytest-xdist` workers each opening their own connection to `rbac.db` at roughly the same moment the live server itself is also writing to it can produce a real, observable error:

```bash
sqlite3.OperationalError: database is locked
```

This is the same underlying mechanism as `SQLITE_BUSY` in any language binding to SQLite: it is not a Python-specific bug or a pytest-xdist bug, it is SQLite itself reporting that two connections tried to touch the file at once. A straightforward mitigation is a busy timeout, giving a blocked connection a real window to wait for the lock to clear instead of failing immediately:

```python
conn = sqlite3.connect(DB_PATH, timeout=10)   # wait up to 10s for a lock to clear, instead of failing instantly
```

That reduces how often it happens, but it does not eliminate the underlying contention the way true per-worker isolation would, and true isolation here would mean each worker pointing at its own copy of the database, which is not something this app supports without modifying its fixed `DB_PATH` in `src/config/database.js`, same limitation the database-testing module already covered.

## A practical middle ground

You do not have to choose between "no parallelism at all" and "parallelism with occasional lock errors." `pytest-xdist` lets you mark specific tests to always run on the same worker, keeping the small number of tests that touch `db_query` serialized relative to each other while everything else (the large majority of this course's tests, which only ever talk HTTP) runs fully parallel:

```python
import pytest


@pytest.mark.xdist_group(name="direct-db-access")
def test_creates_an_appointment_and_confirms_the_row_directly_in_sqlite(...):
    ...
```

`pytest.mark.xdist_group(name=...)` tells `pytest-xdist` to schedule every test sharing that group name onto the same worker, in effect serializing just that subset without giving up `-n auto` for the rest of the suite. That is the practical shape of this trade-off: almost everything in this course parallelizes for free because it is plain HTTP against a server built to handle concurrency, and the handful of tests that step outside that (straight to the database file) are the ones worth being deliberate about.

## Try it

Run the full suite with `pytest -n auto` several times in a row, and separately with `pytest -n 4` a few more times. Note whether `database is locked` shows up at all, and if it does, whether it is every run or only some. Then add `timeout=10` to the `sqlite3.connect(...)` call inside `db_query` and repeat the same runs, to see whether that alone was enough to make the errors disappear, or whether you would still reach for `xdist_group` on a larger suite.
