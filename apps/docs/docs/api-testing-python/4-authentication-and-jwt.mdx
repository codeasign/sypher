Almost every endpoint in the RBAC app requires proof of who is asking before it does anything. You have logged in by hand in every module so far. This is the module where that stops, and you build reusable pytest fixtures that every module after this one relies on automatically, without a single import.

## How the app's auth actually works

`POST /api/auth/login` takes a `username` and `password`. If they are valid, it signs a **JWT (JSON Web Token)**, a compact, self-contained string that encodes who the user is and what role they have, and sends it back:

```python
import httpx

response = httpx.post(
    "http://localhost:5000/api/auth/login",
    json={"username": "doctor1", "password": "pass@123"},
)
print(response.json())
```

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": { "id": 5, "username": "doctor1", "role": "Doctor", "full_name": "Dr. James Wilson" }
}
```

Every protected endpoint expects that token on an `Authorization` header, in the form `Bearer <token>`. The server verifies the token's signature (proving it was not tampered with) and reads the role encoded inside it to decide what that request is allowed to do. That role check is the entire foundation of the RBAC matrix you will test thoroughly soon.

Two failure modes are worth knowing precisely, because you will test both directly and they return *different* status codes:

- **No token at all** produces `401 { "error": "Access token required" }`. The server cannot even tell who is asking.
- **A token that is invalid, malformed, or expired** produces `403 { "error": "Invalid or expired token" }`. The server knows *something* was sent, but it does not trust it.

That distinction, missing credentials get `401` and credentials that exist but do not check out get `403`, is not a convention every API follows the same way, so it is worth confirming against the app you are actually testing rather than assuming. You will rely on it directly in the negative-testing module.

## The four accounts you'll use throughout this course

| Role | Username | Password |
|---|---|---|
| Administrator | `admin` | `admin123` |
| Doctor | `doctor1` | `pass@123` |
| Nurse | `nurse1` | `pass@123` |
| Patient | `patient1` | `pass@123` |

## Building reusable fixtures in `conftest.py`

pytest has a specific, well-known place for shared setup: a file named `conftest.py`. Anything defined as a `@pytest.fixture` inside it is automatically available to every test in the project, with no `import` needed at the call site, just a matching parameter name on the test function. That is a real difference from most other languages' test frameworks, where you would import a helper explicitly; in pytest, fixtures are injected by name.

Create `conftest.py` in your project root, alongside `pytest.ini`:

```python
# conftest.py
import httpx
import pytest

BASE_URL = "http://localhost:5000"

CREDENTIALS = {
    "Administrator": ("admin", "admin123"),
    "Doctor": ("doctor1", "pass@123"),
    "Nurse": ("nurse1", "pass@123"),
    "Patient": ("patient1", "pass@123"),
}


@pytest.fixture
def api_client():
    with httpx.Client(base_url=BASE_URL) as client:
        yield client


@pytest.fixture
def login_as(api_client):
    def _login(role: str) -> dict:
        username, password = CREDENTIALS[role]
        response = api_client.post(
            "/api/auth/login", json={"username": username, "password": password}
        )
        if response.status_code != 200:
            raise RuntimeError(f"Login failed for {role}: {response.status_code} {response.text}")

        body = response.json()
        return {
            "token": body["token"],
            "user_id": body["user"]["id"],
            "headers": {"Authorization": f"Bearer {body['token']}"},
        }

    return _login
```

A few design choices worth explaining. `api_client` uses `yield` instead of `return`: that is what makes it a **generator-based fixture**. Everything before `yield` runs as setup, the yielded value is what the test receives, and anything after `yield` (nothing here, but the `with` block's own cleanup still fires) runs as teardown once the test finishes. Because `api_client` closes over a real `httpx.Client`, every test that uses it (directly, or indirectly through `login_as`) gets one shared, properly-closed connection pool.

`login_as` is a **fixture that returns a function**, sometimes called a fixture factory. A plain fixture gives you a fixed value; here, the test needs to choose *which role* to log in as, and a fixture itself cannot take arguments directly. Returning a callable (`_login`) sidesteps that: the fixture injection happens once per test as usual, but the test itself decides when and with which role to call `login_as(...)`. Notice `login_as` itself depends on `api_client` by naming it as a parameter: pytest resolves that dependency automatically, so any test that asks for `login_as` gets a working, already-connected client behind it for free.

`_login` raises immediately if login fails, rather than returning something half-empty. A test that later tries to use a missing token fails with a confusing, unrelated error far from the real cause. Failing loudly, right where the real problem is, is worth the extra check. The returned `dict` bundles `token`, `user_id`, and a ready-to-use `headers` dict, so call sites rarely need to touch the raw token directly.

## Using it

From here on, every test in this course just asks for `login_as` as a parameter, and pytest wires it up automatically:

```python
# test_auth_fixtures.py

def test_logs_in_as_doctor_and_hits_a_protected_endpoint(login_as, api_client):
    doctor = login_as("Doctor")

    response = api_client.get("/api/appointments", headers=doctor["headers"])

    assert response.status_code == 200


def test_rejects_requests_with_no_token_at_all(api_client):
    response = api_client.get("/api/appointments")

    assert response.status_code == 401
    assert response.json()["error"] == "Access token required"


def test_rejects_requests_with_a_garbage_token(api_client):
    response = api_client.get(
        "/api/appointments", headers={"Authorization": "Bearer not-a-real-token"}
    )

    assert response.status_code == 403
    assert response.json()["error"] == "Invalid or expired token"
```

All three pass against the real app. `login_as("Doctor")` returns a real, working session; a request with no `Authorization` header at all comes back `401`; a request with a token that fails signature verification comes back `403`. Every RBAC-aware test from this point forward starts the same way: `session = login_as(role)`, then `headers=session["headers"]` on whatever request comes next. Notice neither test function imports anything to get `login_as` or `api_client`: naming them as parameters is the entire mechanism.

## Try it

Add a test that logs in with `login_as("Nurse")`, then sends a request to `GET /api/users` (list all users, an Administrator-only endpoint) using that nurse's headers. Assert on the status code you get back, and print `response.json()["requiredRoles"]` from the failure response. The server tells you exactly which roles it would have accepted.
