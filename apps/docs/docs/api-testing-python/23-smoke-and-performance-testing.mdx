Not every situation calls for running the entire suite. Sometimes what you actually want is a fast, narrow answer to one question — "is the app fundamentally broken right now?" — in a few seconds, not a few minutes. This module covers that narrower kind of test, and where "is it fast enough" starts needing a different kind of testing altogether.

## What a smoke test is for

A smoke test suite is a small, deliberately shallow set of checks against the most critical paths through an app — not exhaustive, not edge-case-aware, just "does the absolute core still work." The name comes from hardware testing: power something on and check whether smoke comes out before bothering with anything more detailed. For this app, that's something like: can someone log in, and does at least one protected endpoint respond correctly to a valid request.

## Tagging tests with pytest markers

pytest has a first-class way to tag tests: custom markers, registered in `pytest.ini` so pytest doesn't warn about an unrecognized name:

```ini
[pytest]
testpaths = .
python_files = test_*.py
python_functions = test_*
asyncio_mode = auto
markers =
    smoke: fast, critical-path checks safe to run constantly during development
```

```python
import pytest


@pytest.mark.smoke
def test_login_works(api_client):
    response = api_client.post(
        "/api/auth/login", json={"username": "admin", "password": "admin123"}
    )
    assert response.status_code == 200
```

```bash
pytest -m smoke
```

`-m smoke` runs only the tests decorated with `@pytest.mark.smoke`; everything else is skipped without executing at all. This is a real, useful command to have as a documented step in a `Makefile` or a README — a fast, few-second sanity check you can run constantly during active development, reserving the full suite for before a commit or in CI.

## Basic response-time assertions

A response-time assertion is exactly what it sounds like: measuring how long a request actually took, and asserting it stayed under some budget. `time.perf_counter()` is the right tool for this in Python — it's a monotonic, high-resolution clock meant specifically for measuring elapsed time, unlike `time.time()`, which can jump backward if the system clock adjusts:

```python
import time


@pytest.mark.smoke
def test_login_responds_within_a_reasonable_budget(api_client):
    start = time.perf_counter()
    response = api_client.post(
        "/api/auth/login", json={"username": "admin", "password": "admin123"}
    )
    elapsed_ms = (time.perf_counter() - start) * 1000

    assert response.status_code == 200
    assert elapsed_ms < 1000
```

Measured against the real app, with a reused `httpx.Client` (the way Module 3 taught you to call it — a fresh, unpooled connection on every single call adds its own overhead that has nothing to do with the server), login consistently takes somewhere around 60ms; a trivial endpoint like `/health` is under 1ms on the same reused connection. That roughly 60ms gap is almost entirely the real, deliberately-slow `bcrypt.compare` call happening server-side — not network overhead, not `httpx` overhead. A `1000`ms budget here is generous on purpose: the goal of a check like this isn't to catch a 20ms regression, it's to catch something going catastrophically wrong — a query that used to be indexed and no longer is, an accidental infinite retry loop, a dependency that started hanging. Set the budget too tight, and the assertion becomes noise that fails on ordinary machine-load variance instead of on a real problem.

## Where this ends and real performance testing begins

A single request taking 60ms tells you almost nothing about how this app behaves under real load — hundreds of concurrent users, sustained traffic over time, a database under genuine write pressure. That's a different discipline entirely, usually called load testing or performance testing, using tools built specifically for it. [Locust](https://locust.io/) is worth knowing about specifically here since it's Python-native and reads like an extension of exactly what you've already learned — you define user behavior in Python, and Locust spins up many simulated users running that behavior concurrently against a real, running, network-accessible server:

```python
# locustfile.py -- a different tool, a different question, not part of this course's pytest suite
from locust import HttpUser, task


class RbacUser(HttpUser):
    @task
    def login(self):
        self.client.post("/api/auth/login", json={"username": "admin", "password": "admin123"})
```

That's conceptually similar to the login test above — same endpoint, same payload — but the point of running it isn't a single pass/fail assertion, it's watching how response times, error rates, and throughput change as Locust ramps up from one simulated user to hundreds. That's a genuinely black-box concern by nature, the same way this whole course has been: measuring how the app behaves under concurrent network traffic, the very thing a single `pytest` process running one request at a time can't observe no matter how it's written.

The response-time assertions in this module are a single-request sanity check, not a substitute for that — they catch "this one request got dramatically slower than it used to be," not "this app falls over at 500 concurrent users." Knowing which question you're actually answering is the important part: a passing response-time assertion in this suite says nothing about how the app holds up under real load, and a passing load test doesn't replace the fast, specific feedback a response-time assertion gives you on every single test run.

## Try it

Add a second `@pytest.mark.smoke`-tagged test checking that `GET /api/patients` responds successfully for an Administrator, with its own response-time assertion. Then run `pytest -m smoke -v` and confirm only your two tagged tests execute, with everything else in the suite reporting as deselected rather than actually running.
