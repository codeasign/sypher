Every request so far has used a bare `httpx.get(...)` or `httpx.post(...)` call. That works, but it opens a brand-new connection for every single call — fine for one-off scripts, wasteful once a test suite is sending dozens of requests per run. This module introduces `httpx.Client`, the tool you'll actually use from here on, and `httpx.AsyncClient`, its async counterpart, so you understand both before the rest of the course settles on one.

## Why a `Client` instead of bare `httpx.get`

```python
import httpx

# Works, but opens and closes a connection every single call
r1 = httpx.get("http://localhost:5000/health")
r2 = httpx.get("http://localhost:5000/health")
```

```python
import httpx

# Reuses one connection (and lets you set a base_url once)
with httpx.Client(base_url="http://localhost:5000") as client:
    r1 = client.get("/health")
    r2 = client.get("/health")
```

`httpx.Client(base_url=...)` opens a connection pool once and reuses it across every request made through that client — faster, and it means you stop repeating `http://localhost:5000` on every single call, since `base_url` gets prepended automatically to a path like `/health`. The `with` block is a **context manager**: it guarantees the client's connections get cleaned up when the block exits, even if a request inside it raises an exception. You'll wrap this exact pattern in a pytest fixture in the next module, so every test gets a ready-to-use client without repeating this setup.

## Sync vs. async: what the difference actually is

Every example so far has been **synchronous** — `client.get(...)` blocks the entire program until the response comes back, then execution continues on the next line. For a test suite sending one request, waiting for it, asserting, and moving to the next test, that's not a real limitation; sync is simpler to read and simpler to debug, and it's what this course uses for nearly everything.

**Asynchronous** code, using Python's `async`/`await`, lets your program start a request and, while waiting on the network, do other work in the meantime — including starting *other* requests concurrently instead of one at a time. The payoff shows up specifically when you're firing off many independent requests at once and don't want to wait for them serially. A single login-then-assert test gains nothing from being async; a test that needs to hit ten endpoints concurrently to check they all respond within some time budget genuinely does.

## Writing an async test

Async tests need one more package:

```bash
pip install pytest-asyncio
```

`pytest-asyncio` is what lets pytest run `async def test_...` functions at all — plain pytest doesn't know how to execute a coroutine on its own. Mark each async test with `@pytest.mark.asyncio`:

```python
import httpx
import pytest

BASE_URL = "http://localhost:5000"


@pytest.mark.asyncio
async def test_health_check_async():
    async with httpx.AsyncClient(base_url=BASE_URL) as client:
        response = await client.get("/health")

    assert response.status_code == 200
```

A few things changed from the sync version: the function is `async def`, not `def`; `httpx.AsyncClient` replaces `httpx.Client`; `async with` replaces `with` (the client's own setup/teardown is itself asynchronous); and every actual network call gets an `await` in front of it — `await client.get(...)` — because an async HTTP call returns a coroutine that has to be explicitly awaited to actually run and produce a result. Forgetting that `await` is the single most common mistake with async httpx: `client.get(...)` without it doesn't raise an error, it just gives you a coroutine object instead of a response, and the real failure shows up confusingly later when you try to read `.status_code` off the wrong thing.

To avoid adding `@pytest.mark.asyncio` to every async test by hand, set an `asyncio_mode` in `pytest.ini`:

```ini
[pytest]
testpaths = .
python_files = test_*.py
python_functions = test_*
asyncio_mode = auto
```

With `asyncio_mode = auto`, any `async def test_...` function runs automatically as an async test, no marker required — this course assumes that setting from here on, so async examples in later modules won't repeat the `@pytest.mark.asyncio` decorator.

## Running several requests concurrently

Here's where async actually earns its complexity — firing off multiple independent requests at once with `asyncio.gather`:

```python
import asyncio
import httpx

BASE_URL = "http://localhost:5000"


async def test_multiple_role_lookups_run_concurrently():
    async with httpx.AsyncClient(base_url=BASE_URL) as client:
        login = await client.post(
            "/api/auth/login", json={"username": "admin", "password": "admin123"}
        )
        token = login.json()["token"]
        headers = {"Authorization": f"Bearer {token}"}

        responses = await asyncio.gather(
            client.get("/api/users/role/Doctor", headers=headers),
            client.get("/api/users/role/Nurse", headers=headers),
            client.get("/api/users/role/Patient", headers=headers),
        )

    assert all(r.status_code == 200 for r in responses)
    assert len(responses[0].json()) == 8   # 8 seeded doctors
    assert len(responses[1].json()) == 7   # 7 seeded nurses
```

`asyncio.gather(...)` starts all three coroutines and waits for every one of them to finish, running them concurrently rather than one after another — for three independent, unrelated `GET` requests like these, that's strictly faster than awaiting them in sequence, and it reads almost as plainly as the sequential version would.

## Which one this course uses

Almost every module from here uses **sync** `httpx.Client` — for a test suite that's mostly one request, one assertion, one request, one assertion, async adds ceremony (`async def`, `await`, `AsyncClient`) without a real speed win, since pytest already runs your test *functions* one at a time regardless of whether the requests inside them are sync or async. Async is worth reaching for specifically when a test needs to send several genuinely independent requests and you actually want them running concurrently — rare in this course, but real, and now you have both tools available when it comes up.
