Every test in this course has run on your own machine, with results you read straight off the terminal. This module adds two things a real project needs: a report that survives after the terminal closes, and a GitHub Actions workflow that runs the exact same suite automatically on every push, with one wrinkle this course's black-box approach adds that an in-process test suite would not have: something has to actually start the server first.

## Generating an HTML report

```bash
pip install pytest-html
```

```bash
pytest --html=report.html --self-contained-html
```

`--html=report.html` writes a browsable HTML report alongside the usual terminal output; `--self-contained-html` inlines the report's CSS and JavaScript into that one file, so it is a single artifact you can open directly or hand to a teammate, rather than a folder of linked assets that breaks if you move just the `.html` file on its own. Open `report.html` in a browser and you will see every test, grouped by pass/fail, with the exact assertion failure text for anything that did not pass, the same information `pytest -v` gives you in the terminal, just durable and shareable.

For richer reporting (screenshots, historical trend graphs across runs, a nicer UI) [`allure-pytest`](https://github.com/allure-framework/allure-python) is the more common choice on larger teams:

```bash
pip install allure-pytest
pytest --alluredir=allure-results
```

That produces a directory of result files rather than one HTML file directly; turning it into a browsable report needs the separate Allure command-line tool (`allure serve allure-results`), which is a heavier setup than `pytest-html`, worth it once a team wants trend history across many runs, overkill for a single project just getting CI wired up for the first time. This course sticks with `pytest-html` for its own examples.

## What CI actually needs to do, that your own machine didn't

On your machine, you started the RBAC server once, left it running, and ran `pytest` against it whenever you wanted. A GitHub Actions job starts from nothing every single run (no server, no seeded database) so the workflow has to reproduce all of Module 0's setup steps itself, in order, before `pytest` can do anything useful:

1. **Install the backend's dependencies** and **start the server**: since this course tests over real HTTP, the server has to actually be running and reachable, not just importable.
2. **Wait until it is actually up**: starting a process in the background does not mean it is ready to accept requests yet; the workflow needs to poll until it is, or the first test will just fail against a server that has not finished booting.
3. **Seed the database**: the same `npm run seed` from Module 0.
4. **Install the Python project's dependencies**, then **run pytest**.

## The workflow

```yaml
# .github/workflows/api-tests.yml
name: API Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Check out the RBAC backend
        uses: actions/checkout@v4
        with:
          repository: codedbyabhishekc/rbac-healthcare-system
          path: rbac-app

      - name: Check out this test project
        uses: actions/checkout@v4
        with:
          path: rbac-api-tests

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install backend dependencies
        working-directory: rbac-app/backend
        run: npm install

      - name: Set up backend environment
        working-directory: rbac-app/backend
        run: |
          mkdir -p database
          echo "PORT=5000" >> .env
          echo "JWT_SECRET=${{ secrets.TEST_JWT_SECRET }}" >> .env
          echo "NODE_ENV=test" >> .env

      - name: Start the backend in the background
        working-directory: rbac-app/backend
        run: nohup npm start &

      - name: Wait for the backend to be ready
        run: |
          for i in $(seq 1 30); do
            if curl -sf http://localhost:5000/health; then
              echo "Backend is up"
              exit 0
            fi
            sleep 1
          done
          echo "Backend never became ready" && exit 1

      - name: Seed the database
        working-directory: rbac-app/backend
        run: npm run seed

      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install Python test dependencies
        working-directory: rbac-api-tests
        run: pip install -r requirements.txt

      - name: Run tests
        working-directory: rbac-api-tests
        run: pytest --html=report.html --self-contained-html

      - name: Upload HTML report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: rbac-api-tests/report.html
```

A few details worth explaining. Two separate `actions/checkout@v4` steps run because this is a genuinely black-box course: the system under test and the test project are two different repositories, checked out side by side into `rbac-app/` and `rbac-api-tests/`, rather than one repo containing both the way an in-process test suite might. `nohup npm start &` starts the server and immediately returns control to the next step, instead of blocking the whole job waiting for a process that is meant to run forever: the `&` backgrounds it, and `nohup` keeps it alive after the step that launched it finishes. The polling loop right after is what actually matters here: without it, the very next step could run against a server that is still mid-boot, and you would get flaky, order-dependent failures that have nothing to do with your tests. `secrets.TEST_JWT_SECRET` is a GitHub Actions secret rather than a literal string in the workflow file: even though this only signs test tokens in a throwaway CI database, hardcoding secrets directly into a checked-in YAML file is a habit worth never forming, test-only or not. `if: always()` on the upload step means the report gets uploaded whether the tests passed or failed, arguably more useful on a failing run than a passing one.

## Making it a required check

Once this workflow exists and has run successfully at least once, go to the repository's branch protection settings and add **API Tests** as a required status check for the `main` branch. From that point on, a pull request that fails this workflow cannot be merged: the exact same suite you have been building becomes an actual gate on the codebase, not just documentation of intent.

## Try it

Add a `strategy.matrix` to the workflow that runs the suite against two Python versions (for example, `'3.11'` and `'3.12'`) using `matrix.python-version` and `python-version: ${{ matrix.python-version }}` in the `setup-python` step. Push it and confirm two separate jobs show up in the Actions tab, each independently starting its own backend, seeding its own database, and running the full suite.
