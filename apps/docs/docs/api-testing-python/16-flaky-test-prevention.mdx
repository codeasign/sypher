A flaky test is one that passes sometimes and fails other times, with no change to the code being tested — which makes it worse than a test that's simply wrong. A consistently wrong test gets fixed quickly, because it's obviously broken. A flaky one erodes trust slowly: people start re-running failed suites "just in case," and eventually stop believing red means something's actually broken. This module covers four concrete causes, one of which you can reproduce right now, in this exact app's own shipped test suite.

## Shared state: a real, diagnosed example

The RBAC repo you cloned back in Module 0 ships its own example tests, in `backend/tests/auth.test.js` — a separate JavaScript suite, not the Python one you've been building. One of its blocks is genuinely flaky, and the cause is worth tracing end to end, because it's the single most common source of flaky API tests in general: two pieces of setup code that both assume they're the only thing touching shared state.

Its `Role-Based Authorization Tests` block does this before its tests run:

```javascript
// backend/tests/auth.test.js -- not code you write, but real code in the repo
await request(app).post('/api/auth/register').send({
  username: 'patient1',
  email: 'patient1@example.com',
  password: 'password123',
  role: 'Patient',
  full_name: 'Patient One',
});

const patientResponse = await request(app)
  .post('/api/auth/login')
  .send({ username: 'patient1', password: 'password123' });
patientToken = patientResponse.body.token;
```

This assumes `patient1` doesn't already exist. But `npm run seed` — the exact seed script this whole course has been running since the setup module — already creates a `patient1` account, with the password `pass@123`, not `password123`. You can reproduce exactly what goes wrong from your own Python project, over plain HTTP, without ever running the JavaScript suite yourself:

```python
def test_reproduces_the_real_apps_own_flaky_setup_bug(api_client):
    register = api_client.post(
        "/api/auth/register",
        json={
            "username": "patient1",
            "email": "patient1@example.com",
            "password": "password123",
            "role": "Patient",
            "full_name": "Patient One",
        },
    )
    print("register:", register.status_code, register.json())   # 409 -- patient1 already exists

    login = api_client.post(
        "/api/auth/login", json={"username": "patient1", "password": "password123"}
    )
    print("login:", login.status_code, login.json())   # 401 -- wrong password for the SEEDED patient1

    token = login.json().get("token")   # None -- login never actually succeeded
    response = api_client.get(
        "/api/users", headers={"Authorization": f"Bearer {token}"}
    )
    assert response.status_code == 403
    assert response.json()["error"] == "Invalid or expired token"   # NOT "Access denied..."
```

Run this against a seeded database, and here's what actually happens: the `register` call fails with `409` (`"Username or email already exists"`), and the `login` call fails too, with `401` (`"Invalid credentials"`, since `password123` isn't the seeded account's real password). `token` ends up as literal `None`, and every later request in that JavaScript block sends `Authorization: Bearer None` — a syntactically well-formed but completely invalid token. The server's `jwt.verify` rejects it, and instead of the `403` with `"Access denied. Insufficient permissions."` a genuine role check would produce, it gets a *different* `403`, with `"Invalid or expired token"` — a failure that looks superficially similar but has nothing to do with role-based authorization at all.

Whether that JavaScript suite's block passes or fails depends entirely on whether the database happens to already have a `patient1` user in it when the suite runs — which is exactly what makes it flaky rather than simply broken: it can pass on a fresh, unseeded database and fail on a seeded one, with zero code changes in between.

The fix is the same one from the fixtures module: don't assume a specific user doesn't exist — either look up what's actually there with `get_first_user_with_role`, or use a name that's guaranteed not to collide, like one built from the current time:

```python
import time


def test_registers_a_genuinely_unique_user_every_run(api_client):
    unique_username = f"flakytest_{int(time.time() * 1000)}"

    response = api_client.post(
        "/api/auth/register",
        json={
            "username": unique_username,
            "email": f"{unique_username}@example.com",
            "password": "password123",
            "role": "Patient",
            "full_name": "Flaky Test Patient",
        },
    )

    assert response.status_code == 201
```

## Timing assumptions

JWTs encode their `iat` (issued-at) and `exp` (expiry) claims as Unix timestamps in whole seconds, not milliseconds — that's part of the JWT specification itself, not something specific to this app or to Python. Two tokens issued within the same second carry an identical `iat`. A test asserting "this second token was issued strictly after the first one" by comparing `iat` values directly can fail intermittently, purely depending on how fast two requests happen to run relative to the second boundary — nothing about the app is actually broken when that happens.

The general principle: don't assert on wall-clock ordering or exact timing unless you have a real reason to believe the values can't collide. If you do need to prove one thing happened after another, assert on something that's actually guaranteed to differ — an auto-incrementing ID, or an explicit sequence you control — rather than a timestamp that might not have enough resolution to tell two fast operations apart.

## Unclosed connections

Black-box testing sidesteps one entire category of this risk that an in-process suite has to manage carefully — there's no `app.listen()` side effect here, since these tests never start the server at all; the RBAC backend is a separate process you started yourself back in Module 0, and nothing about running `pytest` opens or closes it. But the database-testing module introduced a real connection of your own to manage: `db_query`'s `sqlite3.connect(DB_PATH)`.

Look back at that fixture, and notice the `try`/`finally`:

```python
conn = sqlite3.connect(DB_PATH)
conn.row_factory = sqlite3.Row
try:
    row = conn.execute(sql, params).fetchone()
    return dict(row) if row else None
finally:
    conn.close()
```

`finally` guarantees `conn.close()` runs whether the query succeeds, raises, or returns early — dropping that `finally` and just calling `conn.close()` as the last line would leave the connection open on any path that exits early or throws. Forgetting it wouldn't break any individual test outright, but it would leave connections accumulating across a large suite — the kind of resource leak that doesn't show up as a clean, repeatable failure, just as things getting slower and occasionally erroring the more tests you run in one session. The pattern worth internalizing: anything your tests open — a database connection, a file handle — has to be explicitly, reliably closed, on every exit path, not just the happy one.

## Avoiding hardcoded waits

You won't find a single bare `time.sleep(N)` anywhere in this course used as a wait for something to become ready, and that's deliberate, not an accident of the examples chosen. Every operation this app does that you've waited on — a login request, a database write — is something `httpx` can wait on directly and synchronously, since a synchronous call already blocks until the real response arrives; there's nothing to guess at. The one place this course genuinely has to wait for something uncertain — the CI module's backend startup — used a polling loop against a real condition (`curl`-ing `/health` in a retry loop) rather than a fixed delay like `sleep 30` and hoping that's long enough.

```python
# the pattern worth reusing anywhere you're waiting on something to become ready
import time
import httpx


def wait_until_healthy(url: str, timeout_seconds: int = 30) -> None:
    deadline = time.time() + timeout_seconds
    while time.time() < deadline:
        try:
            if httpx.get(url).status_code == 200:
                return
        except httpx.ConnectError:
            pass
        time.sleep(1)
    raise TimeoutError(f"{url} never became healthy within {timeout_seconds}s")
```

A hardcoded wait like `time.sleep(30)` is a guess about how long something takes, and guesses are exactly where flakiness comes from: too short, and the test fails on a slow machine even though the thing being waited on is fine; too long, and every run wastes time waiting for something that already finished. `wait_until_healthy` above still calls `time.sleep(1)`, but only as a polling interval *inside* a loop that's checking a real condition on every iteration — it stops the instant the condition is true, rather than sleeping a fixed amount and hoping.
