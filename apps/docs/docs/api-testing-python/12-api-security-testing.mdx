Negative testing checks that the API fails the way you'd expect. Security testing goes further — it actively tries to make the API do something it shouldn't, on behalf of someone it shouldn't. This module finds one genuine, verified gap in the RBAC app, and confirms two things it defends against correctly.

## JWTs are signed, not encrypted

Before testing anything, it's worth seeing this directly: a JWT is base64-encoded and cryptographically **signed**, not encrypted. Anyone holding a token can read its contents without ever knowing the server's secret — decoding the middle segment of any real token proves it:

```python
import base64
import json


def decode_jwt_payload(token: str) -> dict:
    payload_segment = token.split(".")[1]
    padded = payload_segment + "=" * (-len(payload_segment) % 4)   # base64url needs padding restored
    return json.loads(base64.urlsafe_b64decode(padded))


payload = decode_jwt_payload(patient_session["token"])
print(payload)
# {'id': 20, 'username': 'patient1', 'role': 'Patient', 'iat': ..., 'exp': ...}
```

JWTs use base64**url** encoding (`-`/`_` instead of `+`/`/`), and unlike standard base64, they're stored without their trailing `=` padding — `-len(payload_segment) % 4` computes exactly how many `=` characters need adding back before Python's decoder will accept it. That's not a vulnerability by itself — nothing sensitive like a password is in there — but it's a fact worth internalizing before testing auth: a token being unreadable was never part of its security model. What actually protects the app is that a token can't be *modified* without invalidating its signature, which is exactly the next thing worth confirming directly rather than assuming.

```python
def test_rejects_a_token_with_a_tampered_payload_even_if_the_shape_looks_valid(login_as, api_client):
    patient = login_as("Patient")
    header, payload_segment, signature = patient["token"].split(".")

    decoded = decode_jwt_payload(patient["token"])
    tampered = {**decoded, "role": "Administrator"}
    tampered_json = json.dumps(tampered).encode()
    tampered_payload = base64.urlsafe_b64encode(tampered_json).decode().rstrip("=")
    forged_token = f"{header}.{tampered_payload}.{signature}"   # old signature, new claims

    response = api_client.get(
        "/api/users", headers={"Authorization": f"Bearer {forged_token}"}
    )

    assert response.status_code == 403
    assert response.json()["error"] == "Invalid or expired token"
```

Editing the payload without the server's secret invalidates the signature, and the server's `jwt.verify` call rejects the whole token outright — you can't escalate a role by hand-editing a token's claims. That's a real assertion worth having in a suite: it turns "the app is presumably safe from this" into "this app is confirmed safe from this, on every test run."

## SQL injection resistance

Every query in this app's route handlers uses parameterized placeholders (`?`) rather than building SQL by string concatenation — which means user input is passed as data, never interpreted as part of the query itself. Confirming that holds is a one-line test:

```python
def test_does_not_let_a_sql_injection_payload_bypass_login(api_client):
    response = api_client.post(
        "/api/auth/login",
        json={"username": "admin' OR '1'='1", "password": "anything"},
    )

    assert response.status_code == 401
    assert response.json()["error"] == "Invalid credentials"
```

This test is expected to pass, and that's the point — not every security test exists to catch a bug. Some exist to lock in a defense that already works, so a future refactor that accidentally swaps a parameterized query for string concatenation gets caught immediately instead of shipping quietly.

## A real, verified gap: parameter tampering on appointment creation

Here's one that isn't a defense holding up — it's a genuine finding. `POST /api/appointments` takes `patient_id` directly from the request body, and never checks it against the identity of whoever is actually authenticated. A patient can create an appointment *as* a different patient entirely:

```python
def test_lets_a_patient_create_an_appointment_under_a_different_patient_id(
    login_as, get_first_user_with_role, api_client
):
    patient1 = login_as("Patient")   # patient1's own session
    someone_else = get_first_user_with_role("Patient")   # not necessarily patient1

    response = api_client.post(
        "/api/appointments",
        headers=patient1["headers"],
        json={
            "patient_id": someone_else["id"],   # a different patient — not patient1's own id
            "doctor_id": 5,
            "appointment_date": "2026-09-05T10:00:00",
            "reason": "tampered",
        },
    )

    # Documenting the app's real, current behavior: this succeeds.
    assert response.status_code == 201
    assert "appointmentId" in response.json()
```

Run it against the real app, and it does succeed — `201`, a real `appointmentId` back, and a row in the database attributing an appointment to a patient who never should have been able to create it on someone else's behalf. This is exactly the kind of thing this module exists to catch: not a hypothetical, but a request you can actually send, right now, that does something a well-designed permission model shouldn't allow.

Writing that test isn't about breaking the app for its own sake — it's about turning an assumption ("surely a patient can only book for themselves") into a documented, verifiable fact about what the API currently does, whether or not that fact is the one you'd want. A test like this is genuinely valuable sitting in a suite even while the gap remains unfixed — the day someone adds the missing ownership check, this exact test is the one that will need to flip from `201` to `403`, and until then it's an honest, live record of the actual risk.
