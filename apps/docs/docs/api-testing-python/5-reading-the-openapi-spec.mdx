Every module before this one has tested the RBAC app by guessing, from the Swagger UI or from trial and error, what an endpoint expects and returns. This module is the turning point: you'll pull the app's actual OpenAPI spec into Python as a plain `dict`, and from here forward, that spec — not a guess, not the Swagger UI's rendered page — is what every later module checks reality against.

## What's actually in an OpenAPI spec

An OpenAPI (formerly "Swagger") spec is a JSON (or YAML) document describing an API: every path, the HTTP methods each path supports, what request bodies and parameters they expect, and what responses they can return. The Swagger UI page you've been looking at since the setup module — `http://localhost:5000/api-docs` — isn't the spec itself; it's a JavaScript app that *renders* the spec into a browsable page. Underneath that page is a plain data structure, and that's the part worth getting into Python directly.

## The endpoint that isn't quite where you'd expect

The obvious first move is to guess a JSON URL — most `swagger-ui-express` setups expose one at `/api-docs.json` or `/api-docs/swagger.json`. Try both against the RBAC app:

```python
import httpx

for path in ["/api-docs.json", "/api-docs/swagger.json"]:
    response = httpx.get(f"http://localhost:5000{path}")
    print(path, response.status_code, response.headers.get("content-type"))
```

```bash
/api-docs.json 404 text/html; charset=utf-8
/api-docs/swagger.json 200 text/html; charset=utf-8
```

Neither gives you JSON. The first is a plain `404` — that route doesn't exist. The second is more misleading: it returns `200`, but `content-type: text/html` gives it away — that's the Swagger UI's index page again, not a spec file; this particular `swagger-ui-express` setup doesn't register a dedicated JSON route at all, so any unmatched path under `/api-docs` just falls through to the same HTML shell. This is a real, verified property of *this specific app's* Swagger wiring, not a general rule about `swagger-ui-express` — worth confirming for any app you test, rather than assuming one of those two URLs will just work.

## Where the spec actually lives

The Swagger UI page has to get its data from *somewhere* to render anything at all. Looking at what that HTML page actually loads (view source, or just try the script it references):

```python
response = httpx.get("http://localhost:5000/api-docs/swagger-ui-init.js")
print(response.status_code, response.headers.get("content-type"))
print(response.text[:200])
```

```bash
200 application/javascript; charset=utf-8
window.onload = function() {
  // Build a system
  var url = window.location.search.match(/url=([^&]+)/);
  ...
  var options = {
  "swaggerDoc": {
    "openapi": "3.0.0",
```

There it is — the real spec, embedded directly inside a JavaScript file as `options.swaggerDoc`, generated fresh by the server on every request rather than served as a static file. It's not JSON on its own — it's a `.js` file with `var options = {...};` wrapped around a JSON object — but that JSON is real, complete, and exactly what the Swagger UI page itself renders.

## Pulling it into a Python `dict`

A small regex extracts the JSON object out of the surrounding JavaScript:

```python
import json
import re

import httpx


def fetch_openapi_spec(base_url: str = "http://localhost:5000") -> dict:
    response = httpx.get(f"{base_url}/api-docs/swagger-ui-init.js")
    response.raise_for_status()

    match = re.search(r"var options = (\{.*?\n\});\n\s*url = options\.swaggerUrl", response.text, re.DOTALL)
    if not match:
        raise ValueError("Could not find embedded spec in swagger-ui-init.js")

    options = json.loads(match.group(1))
    return options["swaggerDoc"]


spec = fetch_openapi_spec()
print(spec["info"]["title"])
print(list(spec["paths"].keys()))
```

```bash
RBAC Healthcare System API
['/api/users', '/api/users/{id}', '/api/users/role/{role}', '/api/patients/{patientId}/records', '/api/patients', '/api/medical-records', '/api/medical-records/{id}', '/api/auth/register', '/api/auth/login', '/api/appointments', '/api/appointments/{id}']
```

`re.DOTALL` makes `.` in the pattern match newlines too, which it needs to since the embedded JSON spans hundreds of lines. `json.loads(...)` then parses that extracted text exactly the way it would parse any JSON string — the fact that it started life wrapped in JavaScript doesn't matter once it's been sliced out cleanly. Once you have `spec` as a plain Python `dict`, it behaves like any other nested dict: `spec["paths"]` is a dict keyed by URL path, and each path maps to a dict keyed by HTTP method (`"get"`, `"post"`, and so on).

This is exactly the kind of quirk this course's whole philosophy is built around: don't assume where something lives — confirm it, the way you just did with two failed guesses and one that worked. A real project might reach for a dedicated library like `swagger-parser` or a proper `/openapi.json` endpoint if the app exposed one cleanly; this app doesn't, so extracting it directly is the honest, verified path — and it's a useful skill on its own, since not every real API you'll test in your career will make its spec conveniently available either.

## Turn this into a fixture

Add the `fetch_openapi_spec` function itself to `conftest.py`, and wrap it in a fixture so every later module can just ask for the parsed spec:

```python
# conftest.py (add to what Module 4 already has)
import json
import re


def fetch_openapi_spec(base_url: str = BASE_URL) -> dict:
    response = httpx.get(f"{base_url}/api-docs/swagger-ui-init.js")
    response.raise_for_status()
    match = re.search(r"var options = (\{.*?\n\});\n\s*url = options\.swaggerUrl", response.text, re.DOTALL)
    return json.loads(match.group(1))["swaggerDoc"]


@pytest.fixture(scope="session")
def openapi_spec():
    return fetch_openapi_spec()
```

`scope="session"` means the `openapi_spec` fixture runs its setup exactly once for the entire test run, no matter how many test functions ask for it — the spec doesn't change mid-suite, so there's no reason to re-fetch and re-parse it before every single test. Compare that to `api_client` and `login_as` from Module 4, which default to `scope="function"` (a fresh one per test) — the right scope depends on whether a fixture's result is safe to share. Keeping `fetch_openapi_spec` as a plain, importable function alongside the fixture (rather than folding its logic directly into the fixture body) means you can also call it directly from a standalone script — which is exactly what you'll do when wiring it into Schemathesis later in this course.

## What's documented, and what isn't

Skimming `spec["paths"]["/api/appointments"]["get"]["responses"]`, you'll find it lists only `"200"`. You already know from Module 4 that the *real* app also returns `401` and `403` from this exact endpoint when auth fails — the spec just doesn't say so. That's not a mistake you need to report anywhere; it's a real, common gap in hand-annotated specs, and it's exactly the kind of thing worth knowing about *before* you start writing tests based on "what the spec promises." The spec's documented responses are closer to a floor than a ceiling — later modules test both what it promises and what it leaves out.
