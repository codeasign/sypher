Every example so far has used a literal ID — `patient_id: 20`, or medical record ID `999999` for the "definitely doesn't exist" cases. Those numbers were real and correct at the time they were written, checked against a freshly seeded database. This module explains exactly why hardcoding them is fragile, using a real, measured example of it going wrong — and builds the fixture pattern that fixes it for good.

## A real inconsistency in this app's seed data

Run `npm run seed` a second time against a database you've already seeded once, then log in as `patient1` again:

```python
import httpx

response = httpx.post(
    "http://localhost:5000/api/auth/login",
    json={"username": "patient1", "password": "pass@123"},
)
print(response.json()["user"]["id"])
```

The first time, on a fresh database, `patient1` might come back as user `id: 20`. Reseed once more, and that same login now returns `id: 77`. Nothing about the account changed — same username, same password, same role — but its ID moved.

Here's why: `seed.js` deletes every non-admin user and re-inserts the full list fresh on every run, so the *data* really is reset each time. But the `users` table's `id` column is `INTEGER PRIMARY KEY AUTOINCREMENT`, and SQLite's `AUTOINCREMENT` keyword guarantees IDs are never reused, even after a `DELETE` — the next insert always continues from the highest ID that table has ever seen, not from the lowest gap available. Reseed three times, and you're not back to a clean `id: 20` — you're at whatever number thirty-some deleted-and-reinserted users add up to.

That's a real, verified property of this specific app's seed data, not a hypothetical: **the exact numeric ID of any seeded user is not stable across reseeds.** A test that hardcodes `patient_id: 20` will pass right after a fresh seed and can quietly break — pointing at the wrong patient, or a patient that no longer exists at all — after nothing more than running `npm run seed` again.

## The fix: look values up, don't hardcode them

Rather than typing a literal ID and hoping it still points at what you think it does, fetch a real seeded user by role at the start of the test, and use whatever ID comes back. Add this fixture to `conftest.py`:

```python
# conftest.py (add to what earlier modules already have)

@pytest.fixture
def get_first_user_with_role(login_as, api_client):
    def _get(role: str) -> dict:
        admin = login_as("Administrator")
        response = api_client.get(
            f"/api/users/role/{role}", headers=admin["headers"]
        )
        users = response.json()
        if not users:
            raise RuntimeError(f"No seeded users found with role {role}")
        return users[0]

    return _get
```

This is itself a fixture — a small piece of setup logic that gets your test into a known, valid state before the actual test runs, without the test needing to know or care about specific ID values. It's built the same way `login_as` was in Module 4: a fixture that returns a callable, so the test can choose *which* role to look up, and it depends on `login_as` and `api_client` by naming them as its own parameters — pytest resolves that chain automatically. Using it instead of a hardcoded number:

```python
def test_creates_an_appointment_using_looked_up_users(
    login_as, get_first_user_with_role, api_client
):
    patient = get_first_user_with_role("Patient")
    doctor = get_first_user_with_role("Doctor")
    admin = login_as("Administrator")

    response = api_client.post(
        "/api/appointments",
        headers=admin["headers"],
        json={
            "patient_id": patient["id"],
            "doctor_id": doctor["id"],
            "appointment_date": "2026-09-10T10:00:00",
            "reason": "fixture-based test",
        },
    )

    assert response.status_code == 201
```

This test passes identically whether `patient1` is `id: 20`, `id: 77`, or anything else — it never assumes a specific number, only that *some* seeded Patient and *some* seeded Doctor exist, which `npm run seed` always guarantees regardless of how many times it's been run. That guarantee — a stable shape of data, even when the exact values inside it drift — is what a good fixture is actually built around.

Every hardcoded ID in the earlier modules of this course was correct against a fresh seed at the time it was written, exactly the way yours will be the first time you run it. From here forward, prefer `get_first_user_with_role(...)` (or `login_as(...)["user_id"]`, when the current user's own ID is what you need) over typing a literal number — it's the difference between a test that depends on a snapshot of the database staying frozen forever, and one that depends only on the seed script's actual guarantees.

## Fixture scope, and why it matters here

Every fixture you've seen so far defaults to `scope="function"` — pytest tears it down and rebuilds it fresh for every single test function that asks for it. That's the right default for something like `login_as`, since a fresh login per test is cheap and avoids one test's session leaking into another's. But it's not free: a test file with fifty tests that each call `get_first_user_with_role("Doctor")` makes fifty separate `GET /api/users/role/Doctor` calls for data that's identical every time.

```python
import pytest


@pytest.fixture(scope="module")
def seeded_doctor(login_as, api_client):
    admin = login_as("Administrator")
    response = api_client.get("/api/users/role/Doctor", headers=admin["headers"])
    return response.json()[0]


def test_uses_the_module_scoped_doctor_a(seeded_doctor):
    assert seeded_doctor["role"] == "Doctor"


def test_uses_the_module_scoped_doctor_b(seeded_doctor):
    # same doctor object as test_a — fetched once for this whole file
    assert "id" in seeded_doctor
```

`scope="module"` means this fixture runs its setup once per test *file*, and every test in that file that asks for it gets the same cached result — safe here because looking up a doctor is read-only and doesn't mutate anything either test depends on. Reach for a wider scope (`"module"`, or `"session"` like Module 5's `openapi_spec` fixture) specifically when a fixture is read-only and expensive enough that re-running it per test would be wasteful; keep the default `"function"` scope anywhere a test might reasonably mutate what the fixture set up, since a wider scope there would let one test's changes leak into the next.

## Cleaning up after tests that create data

There's no endpoint in this app to fully reset the database to a known state between test runs, and data your tests create — appointments, medical records — has no automatic cleanup. A fixture with teardown code handles this explicitly, using `yield` the same way `api_client` did back in Module 4:

```python
@pytest.fixture
def temporary_appointment(login_as, get_first_user_with_role, api_client):
    admin = login_as("Administrator")
    patient = get_first_user_with_role("Patient")
    doctor = get_first_user_with_role("Doctor")

    created = api_client.post(
        "/api/appointments",
        headers=admin["headers"],
        json={
            "patient_id": patient["id"],
            "doctor_id": doctor["id"],
            "appointment_date": "2026-10-01T09:00:00",
            "reason": "temporary, cleaned up after the test",
        },
    )
    appointment_id = created.json()["appointmentId"]

    yield appointment_id   # the test runs here

    api_client.delete(f"/api/appointments/{appointment_id}", headers=admin["headers"])
```

Everything before `yield` is setup; the yielded value (`appointment_id`) is what the test receives; everything after `yield` is teardown, and — importantly — it runs even if the test itself fails or raises, since pytest always finishes a fixture's teardown code once its setup has completed. Not every test that creates data needs this; plenty of tests in this course leave their created data behind as harmless clutter in a local dev database. Reach for a cleanup fixture like this one specifically when leftover data would interfere with a *different* test later — being deliberate about which case you're in matters more than cleaning up everything by default.

## Try it

Add a `get_first_user_with_role("Nurse")` call to a new test, and use it to create an appointment as that nurse. Then, without changing your test at all, run `npm run seed` again and re-run the test — confirm it still passes, using whatever new ID that nurse ends up with. Then write a `temporary_appointment`-style fixture for medical records, and confirm via a follow-up `GET` after the test that the record it created is actually gone once the test finishes.
