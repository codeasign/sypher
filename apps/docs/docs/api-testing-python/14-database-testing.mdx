You've been verifying writes by reading them back through the API — create, then `GET` the same resource. That's honest and it works, but it has a blind spot: it trusts the very API you're testing to tell you the truth about what it did. This module goes one level deeper and checks the database directly — and, being a black-box course, it needs its own answer to a question the in-process approach never has to ask: how does a separate Python project even get to the database file at all?

## The black-box wrinkle: you're not in the same process

An in-process test suite shares a Node process with the app it's testing, so reaching for the same SQLite file the app already has open is nothing special — it's just another local file. This course's tests are a genuinely separate Python process talking to the app over HTTP, so there's no shared memory or shared file handle to lean on automatically. What there *is*, though, is a shared **filesystem** — as long as the RBAC backend and your `rbac-api-tests` project live on the same machine (true for every setup this course has used since Module 0), the SQLite file at `rbac-healthcare-system/backend/database/rbac.db` is just a file Python can open too, using its own built-in `sqlite3` module — read-only, alongside your HTTP calls, never instead of them.

```python
# conftest.py (add to what earlier modules already have)
import os
import sqlite3

DB_PATH = os.environ.get(
    "RBAC_DB_PATH",
    os.path.join(os.path.dirname(__file__), "..", "rbac-healthcare-system", "backend", "database", "rbac.db"),
)


@pytest.fixture
def db_query():
    def _query_one(sql: str, params: tuple = ()) -> dict | None:
        conn = sqlite3.connect(DB_PATH)
        conn.row_factory = sqlite3.Row
        try:
            row = conn.execute(sql, params).fetchone()
            return dict(row) if row else None
        finally:
            conn.close()

    return _query_one
```

`RBAC_DB_PATH` as an environment variable, with a sensible relative-path default, means this works out of the box for the sibling-folder layout Module 0 set up, but doesn't hardcode an absolute path that would only work on one specific machine. `sqlite3.connect(DB_PATH)` opens a fresh, short-lived connection to the exact same file `server.js` reads and writes — not a copy, not a mock, the real file on disk — and `conn.row_factory = sqlite3.Row` makes rows behave like dicts (`dict(row)`) instead of plain tuples, so field access reads by name rather than by position. The connection closes in a `finally` block regardless of whether the query succeeds, which matters more than it might look like — you'll see exactly why in the flaky-test-prevention module.

## Verifying a write against the real row

```python
def test_creates_an_appointment_and_confirms_the_row_directly_in_sqlite(
    login_as, get_first_user_with_role, api_client, db_query
):
    patient = get_first_user_with_role("Patient")
    doctor = get_first_user_with_role("Doctor")
    admin = login_as("Administrator")

    created = api_client.post(
        "/api/appointments",
        headers=admin["headers"],
        json={
            "patient_id": patient["id"],
            "doctor_id": doctor["id"],
            "appointment_date": "2026-09-12T10:00:00",
            "reason": "db-verification test",
        },
    )
    assert created.status_code == 201

    row = db_query(
        "SELECT * FROM appointments WHERE id = ?", (created.json()["appointmentId"],)
    )

    assert row is not None
    assert row["patient_id"] == patient["id"]
    assert row["doctor_id"] == doctor["id"]
    assert row["reason"] == "db-verification test"
    assert row["status"] == "scheduled"   # the column's default, confirmed at the storage layer
```

That last assertion is worth noticing specifically: `status` defaults to `'scheduled'` at the database level (it's a `DEFAULT 'scheduled'` column, never set explicitly in the request), and checking it against the real row confirms that default is actually being applied by SQLite — not just assumed, and not just reported back optimistically by a `GET` handler that might have its own default-filling logic layered on top. If a route's `GET` handler and its `POST` handler happened to share a bug — say, both silently ignoring a field the same way — testing "does `GET` show what `POST` claimed to write" wouldn't catch it, because both sides would agree with each other, incorrectly. Querying the actual row sidesteps that: it's not asking the app what it thinks happened, it's asking the database what actually happened.

## Test isolation — and this app's real limitation here

"Test isolation" means one test's data and side effects shouldn't affect another test's outcome. The clean version of this, common in larger production systems, uses a completely separate database for tests — often reset to a known-empty state before every single test runs.

This app doesn't give you that option out of the box: `DB_PATH` inside `src/config/database.js` is a fixed path to one file, with no environment variable or config to point it somewhere else, and there's no endpoint that resets the database to a known state on demand. Every test in this course, and every test you write against this app, shares one real, persistent SQLite file — the same one `npm start` uses for local development.

Rather than pretend otherwise, the practical approach used throughout this course is to write tests that don't depend on the database being empty or in any particular starting state:

- **Assert on what you create, not on totals.** A test checking "the appointment I just created has the right fields" survives however many other appointments already exist. A test checking "there are exactly 3 appointments in the system" breaks the moment any other test — or your own manual `curl` testing — adds a fourth.
- **Look up fixtures dynamically** (from the fixtures module) rather than assuming a specific row is present at a specific ID, for exactly the reasons already covered there.
- **Clean up when leaving data around would actively interfere** with another test — deleting something you created when its continued presence would change another test's results — but don't feel obligated to delete every single thing a test creates; a few extra rows in a local dev database rarely cause harm.

A genuinely isolated setup — a fresh, empty database per test run, maybe even per test file — is achievable for an app like this (an in-memory SQLite database, or a `DB_PATH` that reads from an environment variable, are both standard ways teams solve exactly this). Getting there means changing how the app itself is configured, which is outside what a black-box test suite alone can do without also modifying the application under test. Knowing that limitation, and writing tests that are robust to it rather than tests that quietly assume it away, is the actual skill this module is teaching.
