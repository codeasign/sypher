You've built up close to a dozen test files across this course by now. This module finally runs all of them together with `pytest`, and — unlike some in-process test frameworks — that's a genuinely uneventful moment for a black-box suite. What "coverage" actually means here needs its own honest treatment, though, because black-box testing changes the question in a way worth understanding precisely.

## Running everything together is boring, and that's a feature

```bash
pytest
```

If you've followed an equivalent course in a language that tests in-process, running every test file together for the first time is often where real infrastructure problems surface — port collisions, database file locks, one test file's side effects leaking into another's. None of that applies here, for a specific reason worth stating plainly: every test file in this course just sends HTTP requests to a server that was already running before `pytest` started, and nothing about importing a test file starts, stops, or binds anything. There's no shared module registry, no `app.listen()` side effect, no process-level resource any two test files could collide over. Run one file or run all of them, and the only thing that changes is how many requests hit the real server — which is exactly what it's designed to handle.

## Endpoint coverage: reusing the checklist you already built

"Endpoint coverage" asks a specific, coarse question: of the operations this app actually registers, how many have *any* test at all, regardless of how thoroughly? This is the exact checklist you built back in the spec-generation module, repurposed as a cross-check against what you've actually written:

```python
def test_every_documented_operation_has_at_least_one_test_somewhere(openapi_spec):
    all_operations = {
        (op["method"], op["path"]) for op in list_operations(openapi_spec)
    }

    # grows as you write more test files -- kept here as a living, honest checklist
    covered_operations = {
        ("POST", "/api/auth/login"),
        ("GET", "/api/appointments"),
        ("POST", "/api/appointments"),
        ("GET", "/api/patients"),
        ("GET", "/api/users"),
        # ...
    }

    uncovered = all_operations - covered_operations
    print("Not yet covered by name:", uncovered)
```

Printing `uncovered` rather than asserting on it is deliberate for a checklist test like this one — the point is visibility into what's missing, not a hard failure every time you add a new spec operation before you've gotten around to testing it. Once you're confident the list is complete, flipping the `print` into `assert not uncovered` turns it into a real gate.

## Code coverage: measurable for your own code, not the app's

This is where black-box testing draws a hard, honest line that's worth being explicit about rather than glossing over. `pytest-cov` can measure code coverage:

```bash
pip install pytest-cov
pytest --cov=. --cov-report=term-missing
```

But "coverage" here means coverage of *your own Python test project* — your `conftest.py` fixtures, any helper functions you've written, any test file itself. It cannot, and structurally has no way to, measure how much of the RBAC app's own Node/Express route code actually executed while your tests ran, because that code runs in an entirely separate process your Python coverage tool has no visibility into. An in-process suite written in the same language as the app it tests can measure that number directly; a black-box suite fundamentally can't, no matter which coverage tool you reach for.

That's a real trade-off this course has been making since the very first module, not a gap specific to this one. Black-box testing buys you tests that run against the actual deployed shape of the system — the same HTTP surface a real client uses — at the cost of losing line-by-line visibility into the server's own source. If you genuinely need to know what percentage of `appointment.routes.js` your tests exercise, that requires instrumenting the *Node* application with a JS coverage tool (something like `nyc`/Istanbul) running alongside it — a change to how the backend itself is measured, not something achievable purely from the Python side, and outside the scope of what a black-box test project can do on its own.

## What `pytest --cov` on your own project is still good for

Even without visibility into the app's code, measuring your own project's coverage catches a real, specific class of bug: a fixture or helper function with a branch that's never actually exercised by any test. Run it against a project with several conftest.py fixtures and a handful of test files, and a genuinely unused branch — say, an `if` inside `fetch_openapi_spec` handling a case no test ever triggers — shows up by file and line number, the same way it would in any Python project. It's a smaller, narrower signal than the app's own coverage would be, but it's a real one, and it costs nothing extra to check once you're already measuring endpoint coverage.

## Try it

Take the `uncovered` set from `test_every_documented_operation_has_at_least_one_test_somewhere` and, for each operation still in it, write a one-line comment above `covered_operations` noting which future module (or a module you'd add yourself) would be the natural place to cover it. Then run `pytest --cov=. --cov-report=term-missing` on your own project and look for any fixture branch pytest-cov reports as never executed — decide whether it's dead code worth removing, or a real case your test suite is quietly missing.
