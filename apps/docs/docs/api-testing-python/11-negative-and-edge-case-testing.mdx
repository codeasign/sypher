Every test so far has mostly asked "does this work when everything is correct?" Negative testing asks the more valuable question: "what does this do when something is wrong?" — and, in keeping with this whole course, the answer is worth confirming against the real app and its spec rather than assuming, because it doesn't always match your first guess, or the spec's own claims.

## Don't assume the status code — confirm it

It would be reasonable to assume any authentication failure returns `401 Unauthorized`. This app doesn't work that way, and you already have the evidence from Module 4: a request with **no token at all** gets `401`, but a request with a token that's **present but invalid** — malformed, tampered with, or expired — gets `403`. Two different failure states, two different codes, and only one of them is the code you might have guessed for both.

```python
def test_missing_token_gets_401_invalid_token_gets_403(api_client):
    no_token = api_client.get("/api/appointments")
    assert no_token.status_code == 401
    assert no_token.json()["error"] == "Access token required"

    bad_token = api_client.get(
        "/api/appointments", headers={"Authorization": "Bearer not-a-real-token"}
    )
    assert bad_token.status_code == 403
    assert bad_token.json()["error"] == "Invalid or expired token"
```

That's the whole discipline of this module: don't write the assertion you assume is correct — send the request, read what actually comes back, and assert on that. If the real behavior seems wrong, that's worth flagging separately; but the test itself should describe reality, not your prior guess about it.

## Wrong credentials vs. missing token

A wrong username or password at login is a separate case from a missing/invalid token — it happens *before* a token even exists:

```python
def test_wrong_password_gets_401_with_a_generic_message(api_client):
    response = api_client.post(
        "/api/auth/login", json={"username": "admin", "password": "wrong-password"}
    )

    assert response.status_code == 401
    assert response.json()["error"] == "Invalid credentials"
```

Notice the message doesn't say which part was wrong — not "wrong password" specifically, just `Invalid credentials`, the same message a nonexistent username gets too. That's a deliberate security property worth testing *for*, not around: revealing "that username doesn't exist" vs. "that password is wrong" as two different messages would let an attacker enumerate valid usernames one guess at a time. A test that asserts the message stays generic for both cases is protecting that property.

## Malformed and missing fields

`POST /api/auth/register` runs its input through server-side validation, and a bad payload comes back as a structured `400` with one entry per broken field:

```python
def test_registration_reports_every_validation_failure(api_client):
    response = api_client.post(
        "/api/auth/register",
        json={
            "username": "ab",
            "email": "not-an-email",
            "password": "123",
            "role": "SuperAdmin",
        },
    )

    assert response.status_code == 400
    errors_by_field = {e["path"]: e["msg"] for e in response.json()["errors"]}
    assert errors_by_field["username"] == "Username must be at least 3 characters"
    assert errors_by_field["email"] == "Invalid email address"
    assert errors_by_field["password"] == "Password must be at least 6 characters"
    assert errors_by_field["role"] == "Invalid role"
```

Building `errors_by_field` as a dict keyed by `path` sidesteps a problem you'd otherwise have with a plain list: this app's real response also includes a fifth error (a missing `full_name`) alongside the four checked here, and the errors don't come back in a guaranteed order. A dict comprehension makes the test check exactly the fields it cares about, in whatever order they actually arrive, without needing the response to match some exact expected list.

Not every endpoint validates its input this thoroughly, and that's worth testing *as its own fact*, not silently working around. Module 7 already showed you one gap — `POST /api/medical-records` accepts a payload missing its spec-required `diagnosis` field. `POST /api/appointments` goes further: it has no validation layer at all, and a payload missing a required field doesn't come back as a clean `400`:

```python
def test_missing_required_field_on_an_unvalidated_route_gets_a_raw_500(login_as, api_client):
    admin = login_as("Administrator")
    response = api_client.post(
        "/api/appointments",
        headers=admin["headers"],
        json={"doctor_id": 5, "appointment_date": "2026-09-01T10:00:00", "reason": "test"},
        # patient_id deliberately omitted
    )

    assert response.status_code == 500
    assert response.json()["error"] == "Error creating appointment"
```

`patient_id` is a `NOT NULL` column in the database, so leaving it out doesn't get caught by a validation layer — it fails at the database itself, and the route's generic error handling turns that into a `500` with a vague message. That's a real, verified gap in this app's input handling, not a guess — and it's exactly what negative testing is for: documenting precisely how an endpoint fails today, so a future change to add real validation here has a test that will need deliberately updating, rather than a gap nobody was watching.

## Boundary and malformed-input values

A few more shapes worth checking deliberately, each verified against the real app:

```python
def test_non_numeric_id_is_not_found_not_bad_request(login_as, api_client):
    admin = login_as("Administrator")
    response = api_client.get(
        "/api/appointments/not-a-number", headers=admin["headers"]
    )

    assert response.status_code == 404   # SQLite's parameter binding just finds no match


def test_empty_login_body_is_a_credentials_failure_not_a_validation_failure(api_client):
    response = api_client.post("/api/auth/login", json={})

    assert response.status_code == 401   # login has no validation layer either
    assert response.json()["error"] == "Invalid credentials"
```

Neither of those is the "obvious" answer either — a non-numeric ID might reasonably come back as `400 Bad Request` in a stricter API, and an empty login body might reasonably trigger a validation error before ever reaching a database lookup. This app does neither; both fall through to whatever the underlying logic naturally produces once it's handed data it wasn't specifically guarded against. Testing that honestly is more valuable than testing the version of the API you expected to find.

## Try it

Test `PUT /api/appointments/999999` (an appointment ID that doesn't exist) as an Administrator, sending a valid-looking update body. Check the actual status code and message that comes back, and compare it to what `DELETE` on the same nonexistent ID returns. They're two different routes handling "the thing you asked for doesn't exist" — confirm for yourself whether they agree with each other or not.
