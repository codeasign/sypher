Module 10 used `@pytest.mark.parametrize` once, briefly, to cover all 4 roles against one endpoint. This module goes properly deep on it — readable test IDs, stacking multiple parametrize decorators for a full cartesian product, and where to stop, because parametrize can make a test suite harder to read if you reach for it past the point it's actually earning its keep.

## The basic case, and why bare tuples aren't always enough

```python
import pytest

ROLES_AND_EXPECTED_STATUS = [
    ("Administrator", 200),
    ("Doctor", 200),
    ("Nurse", 200),
    ("Patient", 403),
]


@pytest.mark.parametrize("role,expected_status", ROLES_AND_EXPECTED_STATUS)
def test_get_patients_role_gate(login_as, api_client, role, expected_status):
    session = login_as(role)
    response = api_client.get("/api/patients", headers=session["headers"])

    assert response.status_code == expected_status
```

Run `pytest -v` and pytest auto-generates a test ID from each tuple's values — `test_get_patients_role_gate[Administrator-200]`, `test_get_patients_role_gate[Patient-403]`, and so on. That works fine for simple values like these, but once a parameter is something less readable — a dict, a longer string, a `None` — the auto-generated ID gets long and hard to scan in test output. `pytest.param(...)` lets you name each case explicitly:

```python
CASES = [
    pytest.param("Administrator", 200, id="admin-sees-all-patients"),
    pytest.param("Doctor", 200, id="doctor-sees-all-patients"),
    pytest.param("Nurse", 200, id="nurse-sees-all-patients"),
    pytest.param("Patient", 403, id="patient-forbidden"),
]


@pytest.mark.parametrize("role,expected_status", CASES)
def test_get_patients_role_gate_named(login_as, api_client, role, expected_status):
    session = login_as(role)
    response = api_client.get("/api/patients", headers=session["headers"])
    assert response.status_code == expected_status
```

Now `pytest -v` reports `test_get_patients_role_gate_named[patient-forbidden]` instead of `[Patient-403]` — more work to write, worth it once a failing test ID needs to tell a teammate what broke without them having to go read the parameter list to decode it.

## Stacking two parametrize decorators for a cartesian product

Real coverage often needs two independent dimensions at once — every role, against every resource endpoint that has the same allow/deny shape. Stacking two `@pytest.mark.parametrize` decorators multiplies them:

```python
ENDPOINTS = [
    pytest.param("GET", "/api/patients", id="list-patients"),
    pytest.param("GET", "/api/users", id="list-users"),
]

ROLES = [
    pytest.param("Administrator", id="admin"),
    pytest.param("Doctor", id="doctor"),
    pytest.param("Nurse", id="nurse"),
    pytest.param("Patient", id="patient"),
]


@pytest.mark.parametrize("method,path", ENDPOINTS)
@pytest.mark.parametrize("role", ROLES)
def test_reports_status_for_every_role_and_endpoint(login_as, api_client, role, method, path):
    session = login_as(role)
    response = api_client.request(method, path, headers=session["headers"])

    print(f"{role} -> {method} {path} -> {response.status_code}")
    assert response.status_code in (200, 403)   # every combination is one or the other here
```

Two lists of 4 and 2 produce 8 runs — `pytest -v` shows IDs like `test_reports_status_for_every_role_and_endpoint[admin-list-patients]` and `[patient-list-users]`, one for every combination. This is genuinely useful for exploring a matrix's shape quickly, but notice the assertion had to get looser (`in (200, 403)` instead of an exact expected value per combination) — a stacked parametrize like this doesn't know which combinations should pass and which shouldn't, only that you're running all of them. For actual pass/fail-per-case coverage — like the RBAC matrix in Module 10 — a single list of explicit `(role, endpoint, expected_status)` tuples is more honest about what each combination is actually supposed to do, even though it's more typing up front.

## Parametrizing over expected values *and* real spec data together

Combine what you built in Module 6 with parametrize to turn the operation checklist into actual running tests:

```python
def test_every_documented_status_code_is_a_real_possibility(login_as, openapi_spec, api_client):
    documented = openapi_spec["paths"]["/api/medical-records/{id}"]["get"]["responses"]
    assert set(documented.keys()) == {"200", "404"}


@pytest.mark.parametrize(
    "record_id,expected_status",
    [
        pytest.param(999999, 404, id="nonexistent-record"),
    ],
)
def test_medical_record_lookup_status(login_as, api_client, record_id, expected_status):
    doctor = login_as("Doctor")
    response = api_client.get(f"/api/medical-records/{record_id}", headers=doctor["headers"])
    assert response.status_code == expected_status
```

A single-entry parametrize list looks unnecessary at first — you could just write the assertion directly. It earns its place the moment a second case shows up (an existing record ID, once you build one via a fixture from Module 13) and you want both cases to appear as separate, individually-reportable results rather than two `assert` statements buried in one test function that stops at the first failure.

## Where to stop

Parametrize is easy to overuse. If two test cases share the exact same body with only one number different, parametrize almost always improves the test — less duplication, clearer coverage, individually reportable results. If two cases need meaningfully different setup, different assertions, or a different fixture entirely, forcing them into one parametrized function usually makes the test *harder* to read than two separate, plainly-named functions would have been — you end up with `if` branches inside the test body dispatching on the parameter, which defeats the point. The RBAC matrix tests in Module 10 are close to the ideal case: same request shape, same assertion shape, only the role and expected status actually vary.

Take the appointment CRUD lifecycle test from Module 7 and parametrize just the role used for the create/update steps, across `["Administrator", "Doctor", "Nurse"]` (all three are allowed to manage appointments). Give each case a readable `id` with `pytest.param(...)`, run `pytest -v`, and confirm you get three separate, clearly labeled results instead of one test that only ever ran as one role.
