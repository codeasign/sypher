You can now pull the RBAC app's spec into a Python `dict`. This module puts it to work: walking the spec programmatically to produce a checklist of every operation the API exposes, instead of scrolling through the Swagger UI by eye and hoping you did not miss one.

## Why generate the checklist instead of eyeballing it

Eleven paths is not many, and it is tempting to just read the Swagger UI top to bottom and start writing tests. That works until the app grows: a real API can easily have hundreds of operations, and scrolling a UI to keep track of which ones have coverage does not scale. Walking `spec["paths"]` programmatically does two things a manual read does not: it guarantees you do not silently skip an operation, and it gives you something you can re-run every time the spec changes, to see exactly what is new.

## Walking the spec

```python
def list_operations(spec: dict) -> list[dict]:
    operations = []
    for path, methods in spec["paths"].items():
        for method, details in methods.items():
            operations.append({
                "method": method.upper(),
                "path": path,
                "summary": details.get("summary", ""),
                "requires_auth": "security" in details,
                "responses": sorted(details.get("responses", {}).keys()),
            })
    return operations
```

`spec["paths"]` is a dict keyed by URL path; each value is itself a dict keyed by HTTP method (`"get"`, `"post"`, `"put"`, `"delete"`), since a single path in this app can support more than one method: `/api/appointments` has both a `"get"` and a `"post"` entry, for instance. The nested loop walks both levels, and `details.get("security")` checks whether that specific operation declares a security requirement, a decent, if imperfect, proxy for "does this need a token," which you will refine once you notice its blind spot below.

Run it against the real spec:

```python
def test_prints_every_operation(openapi_spec):
    for op in list_operations(openapi_spec):
        print(f"{op['method']:6} {op['path']:35} auth={op['requires_auth']}  responses={op['responses']}")
```

That is all 19 rows, one per method on every one of the 11 paths. That single loop just handed you a checklist: 19 operations, each with its documented response codes. Every module for the rest of this course maps back to a row in that table.

## A blind spot worth catching immediately

Look closely at `POST /api/auth/login` and `POST /api/auth/register`: `requires_auth` reports `False` for both, which matches reality. You already know from Module 4 that login has to work *without* a token, since getting a token is the whole point of calling it. But that is actually the spec doing something subtle: rather than each operation declaring `security: []` (an explicit "no auth needed" override), these two operations simply *omit* the `security` key entirely and rely on **not having one of their own**, while every other operation in the spec repeats `security: [{bearerAuth: []}]` explicitly. Both approaches produce the same real-world behavior here, but if a spec-driven tool ever assumed "no explicit override" and "an operation exists with no security block" meant the same thing as "requires the document's top-level default," it could reach the wrong conclusion for these two operations. You will hit exactly this ambiguity again in Module 20, where a property-based testing tool has to make that same judgment call automatically.

## Building an actual checklist, not just a printout

A checklist is more useful as structured data you can check off than as console output. Turn each operation into an expected test case:

```python
def to_test_case_id(op: dict) -> str:
    path_slug = op["path"].strip("/").replace("/", "_").replace("{", "").replace("}", "")
    return f"{op['method'].lower()}_{path_slug}"


def test_checklist_has_one_case_per_operation(openapi_spec):
    operations = list_operations(openapi_spec)
    checklist = {to_test_case_id(op): op for op in operations}

    assert len(checklist) == len(operations)   # every ID came out unique
    assert "post_api_medical-records" in checklist
    assert "delete_api_appointments_id" in checklist
```

`to_test_case_id` turns something like `("POST", "/api/medical-records")` into `post_api_medical-records`, a stable, readable identifier you could use as an actual test function name (`def test_post_api_medical_records_...`) or as a row label in a coverage spreadsheet. The point is not the specific naming scheme; it is that the mapping from *spec operation* to *identifiable test case* is now something code produces, not something you maintain by hand in a doc somewhere that quietly goes stale.
