Every module so far has added one more fixture to `conftest.py` and, often, one more test function to whatever file you happened to be working in. At this point you likely have `api_client`, `login_as`, `get_first_user_with_role`, `openapi_spec`, and `db_query` all living together in one file. This module is about the shape that growth should keep taking as the suite gets genuinely large — not a new technique, but the organizing principle behind everything you've already built.

## Fixtures know HOW; test files know WHAT

`conftest.py` has been quietly playing one consistent role since Module 4: it holds things that know *how* to do something generic — log in, look up a fixture, query the database, fetch the spec — without knowing anything about which specific test is calling them. Every `test_*.py` file you write, by contrast, knows *what* is being verified for a specific piece of the app, and leans on those fixtures rather than re-deriving that "how" itself. That split is exactly why the authentication module built `login_as` once instead of letting every module since re-write its own login logic — every test file from that point on has been able to stay focused on what it's actually testing.

```text
rbac-api-tests/
  conftest.py          api_client, login_as, get_first_user_with_role,
                        openapi_spec, fetch_openapi_spec, db_query
  test_auth.py
  test_appointments.py
  test_medical_records.py
  test_patients.py
  test_users.py
  test_rbac_matrix.py
  test_security.py
  pytest.ini
```

## Organizing test files by resource, not by test type

Notice the files above are named after what they test — `test_appointments.py`, `test_users.py` — rather than after the kind of test inside them (there's no `test_crud.py` or `test_negative.py` sitting alongside them). A resource-based split means everything about testing appointments — its CRUD lifecycle, its RBAC rules, its negative cases — lives in one file, which is where you'd actually go looking when appointments-related behavior changes. A test-type-based split scatters that same knowledge across several files, and touching one endpoint means remembering to check all of them.

This isn't a hard rule — a suite testing something with far more cross-cutting concerns than this app might reasonably split differently — but for a REST API organized around a handful of clear resources, matching your test files to those resources keeps the mental model simple: one file per "thing," the same way the app itself is organized one route file per resource.

## Config lives at the root, once

`pytest.ini` sits at the project root, not inside any subfolder — it's project-level configuration, read once when pytest starts, not something any individual test file needs to reach into. Keeping it at the root also matches where `conftest.py` lives, since pytest specifically looks for `conftest.py` starting from the root of the directory tree it's running in and auto-discovers any nested ones too.

## Scaling conftest.py itself, when one file gets too big

pytest's fixture discovery isn't limited to a single root `conftest.py` — it's scoped by directory. A `conftest.py` inside a subfolder is automatically available to every test file in that subfolder and below, on top of whatever the root `conftest.py` already provides, with no explicit import needed either way:

```text
rbac-api-tests/
  conftest.py                    shared across everything: api_client, login_as
  tests/
    security/
      conftest.py                 security-specific fixtures, only visible here
      test_jwt_tampering.py
      test_parameter_tampering.py
    rbac/
      conftest.py                 RBAC-matrix-specific fixtures, only visible here
      test_permission_matrix.py
```

That's the pytest-native way to scale past one large, flat `conftest.py` file once a suite genuinely grows large enough to need it — a fixture used by every test in the project stays at the root, while a fixture only relevant to one area of the suite lives in a `conftest.py` scoped to just that area, without needing a separate `helpers/` package and explicit imports the way some other languages' test frameworks require.

## What belongs in a fixture vs. what doesn't

A good fixture does one clearly-named thing and has no opinion about which test calls it. `login_as("Doctor")` doesn't know or care whether the test that calls it is checking CRUD behavior, RBAC, or security — it just returns a valid session for that role. That's what makes it reusable across close to every test file in this course.

A fixture that started returning different results depending on which test file used it, or that hardcoded assumptions specific to one test ("assume this is being called from the appointments suite"), would stop being a fixture and start being hidden, fragile coupling between files that look independent but secretly aren't. If you notice a fixture growing a parameter whose only purpose is "so this one specific test can get different behavior," that's usually a sign the logic belongs in that specific test instead, not in the shared fixture.
