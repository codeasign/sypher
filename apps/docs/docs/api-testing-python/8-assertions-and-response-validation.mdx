The CRUD module asserted on status codes and a handful of body fields, one at a time. This module steps back and covers the full range of things worth asserting on a response (status, headers, and body shape) and, specifically, how to check each one against what the spec says rather than against whatever you happen to notice.

## Status code assertions, done properly

A bare `assert response.status_code == 200` works, but when it fails, the default pytest output only tells you the two numbers did not match, not what the server actually said about *why*. For endpoints that return a useful error body, print it into the assertion:

```python
def test_status_code_with_useful_failure_message(login_as, api_client):
    nurse = login_as("Nurse")
    response = api_client.get("/api/users", headers=nurse["headers"])

    assert response.status_code == 403, f"expected 403, got {response.status_code}: {response.text}"
```

If that assertion ever fails (say, the app changes and nurses gain access to `/api/users`) the failure message includes the *actual* status and body, not just "403 != 200." That is a small habit, but it turns a debugging session that starts with "let me go add a print statement and re-run" into one where the first failure already told you what happened.

## Header assertions

Response headers carry real information beyond the body, worth checking directly rather than ignoring:

```python
def test_login_response_headers(api_client):
    response = api_client.post(
        "/api/auth/login", json={"username": "admin", "password": "admin123"}
    )

    assert response.headers["content-type"].startswith("application/json")
    assert response.headers["access-control-allow-origin"] == "*"
```

`response.headers` behaves like a case-insensitive dict: `response.headers["content-type"]` and `response.headers["Content-Type"]` return the same value, which matters because HTTP header names are not guaranteed to arrive in any particular casing. That second assertion, `access-control-allow-origin`, is checking CORS behavior, which comes from the app's `cors()` middleware rather than anything declared per-operation in the OpenAPI spec; not every useful assertion traces back to the spec, and this course will not pretend otherwise.

## Body shape assertions, field by field

For a handful of fields, direct assertions on `response.json()` are the clearest option:

```python
def test_login_response_shape(api_client):
    response = api_client.post(
        "/api/auth/login", json={"username": "doctor1", "password": "pass@123"}
    )
    body = response.json()

    assert set(body.keys()) == {"token", "user"}
    assert isinstance(body["token"], str) and len(body["token"]) > 20
    assert body["user"]["role"] == "Doctor"
    assert set(body["user"].keys()) == {"id", "username", "email", "role", "full_name"}
```

`set(body.keys()) == {...}` is worth calling out specifically: it does not just check that the fields you expect are present, it checks that *no extra, undocumented fields* are there either, a stricter, and often more valuable, check than a handful of individual `"field" in body` assertions, which would happily pass even if the response grew ten unexpected fields nobody is watching. You will hit the limits of this approach quickly, though: write one of these per endpoint and it gets repetitive fast; the schema validation module replaces this pattern with something that scales.

## Checking the response against what the spec actually documents

Here is where this module ties directly back to Module 5 and 6: pull the documented response codes for an operation straight out of the spec, and assert the real response's status code is *one of* them, rather than hardcoding a number you copied by eye:

```python
def test_response_status_is_one_the_spec_documents(login_as, api_client, openapi_spec):
    documented = set(
        openapi_spec["paths"]["/api/medical-records/{id}"]["get"]["responses"].keys()
    )
    assert documented == {"200", "404"}   # confirm what you're about to check against

    doctor = login_as("Doctor")
    response = api_client.get("/api/medical-records/999999", headers=doctor["headers"])

    assert str(response.status_code) in documented
```

That test would fail loudly, and usefully, if this endpoint ever started returning, say, a bare `500` on some edge case: not just "the test broke," but "the app returned something the spec does not even claim is possible." Reusing the spec as the source of expected values, instead of retyping `{"200", "404"}` by hand in every test, means a spec update automatically updates what your tests consider valid, and a mismatch between the two becomes visible instead of silently tolerated.

## When the spec doesn't say enough to assert against

Not every operation's documented `responses` block is detailed enough to check content against: most of them, as you saw in Module 6, just have a bare `description` string, no `content` or `schema`. In that case, the spec tells you *that* a `200` is expected, but nothing about what shape it should have. That is a real, honest limit: asserting on shape at that point means falling back to what Module 5 called "documented as a floor, not a ceiling." You are testing beyond the spec because the spec has nothing more to check against, and it is worth being explicit about that distinction in a test's own docstring or comment, rather than implying every assertion traces back to a documented promise when some of them do not.

## Try it

Write a test for `GET /api/patients` as a Doctor. Assert the status code is in the set of codes `openapi_spec["paths"]["/api/patients"]["get"]["responses"]` documents, then assert `response.json()` is a list where every item's key set is exactly `{"id", "username", "email", "full_name", "phone", "created_at"}`. Run it once against a fresh seed and once after creating a new patient via `POST /api/auth/register`, and confirm the new patient shows up with the same shape as the rest.
