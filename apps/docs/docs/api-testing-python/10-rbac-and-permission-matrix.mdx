Every module so far has touched authorization in passing. This one maps it out completely: exactly which of the app's 4 roles can do what, on every endpoint, verified against the app's actual behavior — since, as you saw back in Module 7, the spec's own `security` block only tells you "some authenticated user," never *which* role.

## Mapping the real matrix

There's no field in the OpenAPI spec that captures role-level access — this is exactly the kind of gap Module 5 warned you the spec has by design. The real ground truth is the app's behavior itself, verified endpoint by endpoint (a couple with the same shape as ones already shown, like updating your own profile, are left out for brevity):

| Endpoint | Administrator | Doctor | Nurse | Patient |
|---|---|---|---|---|
| `POST /api/appointments` (create) | ✅ | ✅ | ✅ | ✅ |
| `GET /api/appointments` (list) | ✅ all | ✅ own only | ✅ all | ✅ own only |
| `GET /api/appointments/:id` | ✅ any | ✅ own only | ✅ any | ✅ own only |
| `PUT /api/appointments/:id` | ✅ | ✅ | ✅ | ❌ |
| `DELETE /api/appointments/:id` | ✅ | ✅ | ❌ | ❌ |
| `POST /api/medical-records` (create) | ❌ | ✅ | ❌ | ❌ |
| `GET /api/medical-records` (list) | ✅ all | ✅ own only | ✅ all | ✅ own only |
| `GET /api/medical-records/:id` | ✅ any | ✅ own only | ✅ any | ✅ own only |
| `PUT /api/medical-records/:id` | ❌ | ✅ | ❌ | ❌ |
| `DELETE /api/medical-records/:id` | ✅ | ✅ | ❌ | ❌ |
| `GET /api/patients` (list all patients) | ✅ | ✅ | ✅ | ❌ |
| `GET /api/patients/:id/records` | ✅ any | ✅ any | ✅ any | ✅ own only |
| `GET /api/users` (list all) | ✅ | ❌ | ❌ | ❌ |
| `GET /api/users/:id` | ✅ any | own only | own only | own only |
| `DELETE /api/users/:id` | ✅ | ❌ | ❌ | ❌ |

Two rows are worth pausing on because they're easy to get wrong by intuition alone: creating an appointment (`POST /api/appointments`) has no role restriction at all in this app — every authenticated role, including Patient, can create one. And `GET /api/medical-records/:id` and `GET /api/patients/:id/records` let a Nurse or Doctor view *any* patient's records, not just ones they're directly treating — there's no per-patient assignment check beyond the basic role gate. Neither of those is a guess; both come straight from reading the route handlers, and you'll verify the second one yourself again in the negative-testing module, from a different angle.

## Data-driven tests across all 4 roles

Testing the same claim once per role is repetitive and easy to under-cover — it's tempting to test the "interesting" roles and skip the rest. `pytest.mark.parametrize` runs the same test body once per entry in a list, which makes testing all 4 roles as cheap as testing one:

```python
import pytest

ROLES_AND_EXPECTED_STATUS = [
    ("Administrator", 404),  # role check passes, then 404 because the record doesn't exist
    ("Doctor", 404),
    ("Nurse", 403),
    ("Patient", 403),
]


@pytest.mark.parametrize("role,expected_status", ROLES_AND_EXPECTED_STATUS)
def test_delete_medical_record_role_gate(login_as, api_client, role, expected_status):
    session = login_as(role)
    response = api_client.delete(
        "/api/medical-records/999999", headers=session["headers"]
    )

    assert response.status_code == expected_status
```

`@pytest.mark.parametrize("role,expected_status", ROLES_AND_EXPECTED_STATUS)` takes the parameter names as a comma-separated string, then a list of tuples supplying their values — pytest runs the test function once per tuple, substituting `role` and `expected_status` as real function arguments each time. Run `pytest -v` and you get four separate, individually-named results (`test_delete_medical_record_role_gate[Administrator-404]`, `test_delete_medical_record_role_gate[Doctor-404]`, and so on), not one test silently looping. You'll go much deeper on this pattern, including parametrizing over more than two values at once, in the parameterized testing module — this is a preview of exactly why it's worth learning properly.

Notice the request targets medical record ID `999999`, which doesn't exist. That's deliberate: this app's route checks the role *before* looking up the record, so a nonexistent ID isolates exactly one thing — did the role check pass or fail — without needing a real record to already exist for each role to attempt against. An allowed role reaches the "not found" branch and gets `404`; a disallowed role never gets that far and gets `403` instead. The disallowed cases come back with a body worth asserting on too:

```json
{
  "error": "Access denied. Insufficient permissions.",
  "requiredRoles": ["Administrator", "Doctor"],
  "userRole": "Nurse"
}
```

That `requiredRoles` field is worth checking, not just the status code — it's the middleware telling you exactly what it expected, which makes a passing test into a small piece of living documentation for what this endpoint's contract actually is.

## Testing scoped access, not just allow/deny

Some rows in the matrix aren't a clean allow/deny — every role can call `GET /api/appointments`, but what comes back depends on who's asking. That needs a different kind of assertion: not just the status code, but a check on the *content* of what a scoped role gets back.

```python
def test_scopes_a_patient_to_only_their_own_appointments(login_as, api_client):
    patient = login_as("Patient")   # patient1

    response = api_client.get("/api/appointments", headers=patient["headers"])

    assert response.status_code == 200
    appointments = response.json()
    assert len(appointments) > 0
    assert all(appt["patient_id"] == patient["user_id"] for appt in appointments)
```

That last assertion is the real point of the test — not just that the request succeeded, but that every single appointment in the response actually belongs to the patient who asked for it. A scoping bug that leaked one other patient's appointment into the list would still return `200`, exactly like a correct response would; only checking the actual contents catches it.

## Try it

Write a `@pytest.mark.parametrize`-driven test covering all 4 roles against `GET /api/patients` (list all patients) — Administrator, Doctor, and Nurse should all get `200`, Patient should get `403`. Then extend it: for the roles that get `200`, add an assertion that `response.json()` is a non-empty list. That combination — a data-driven pass/fail check plus a content check for the roles that pass — is the same two-part shape you'll use for almost every endpoint in this matrix.
