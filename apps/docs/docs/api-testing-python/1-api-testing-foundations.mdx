You made one request against the RBAC app in the setup module and got back a token. This module slows down and explains what actually just happened: the shape of an API test, how it differs from testing through a UI, and why this course keeps coming back to one specific document, the app's OpenAPI spec.

## What API testing actually covers

A UI test drives a browser: click a button, wait for a page to render, check that some text appears on screen. An API test skips the browser entirely and talks directly to the layer the UI itself talks to, sending an HTTP request and checking what comes back. For the RBAC app, that means instead of filling in a login form and watching a dashboard load, you send `POST /api/auth/login` with a JSON body and check the JSON response.

That difference is not just "faster," though it is, often by an order of magnitude, since there is no browser to launch and no rendering to wait for. It is also *more precise*. A UI test that confirms "the dashboard loaded" is really making several assumptions at once: the request succeeded, the response had the right shape, and the frontend rendered that shape correctly. An API test isolates just the middle piece (did the server do the right thing) without the frontend's rendering logic able to mask or distort what actually came back over the wire.

## The request/response contract

Every HTTP API test you will write in this course follows the same shape:

1. **Send a request**: a method (`GET`, `POST`, `PUT`, `DELETE`), a URL, and usually headers and a body.
2. **Receive a response**: a status code, headers, and usually a body.
3. **Assert** something about that response: the status code, a field in the body, a header, or all three.

```python
import httpx

response = httpx.post(
    "http://localhost:5000/api/auth/login",
    json={"username": "admin", "password": "admin123"},
)

assert response.status_code == 200
assert response.json()["user"]["role"] == "Administrator"
```

That is a complete, if minimal, API test. Everything this course adds from here (fixtures, schema validation, RBAC-aware test matrices, CI) is built on top of exactly this shape: send, receive, assert.

## Why test against a spec, not just current behavior

It would be entirely possible to write this whole course by pointing `httpx` at the RBAC app, noting down whatever it currently returns, and asserting on that. Plenty of real test suites are built exactly that way. The problem is what that approach *cannot* catch: if the app's actual behavior quietly drifts from what it is supposed to do (a field gets renamed, a status code changes, an endpoint that used to require a role stops enforcing it) a test suite built purely by observing current behavior just learns the new, possibly-broken behavior and keeps passing. It has nothing independent to check against.

The RBAC app ships an OpenAPI (Swagger) specification, a machine-readable document describing every endpoint, what it expects, and what it is supposed to return. That spec is a *separate, independent claim* about how the API should behave, written by whoever built the endpoint, not inferred by watching it run. Testing against that claim ("does the real response match what the spec promises") catches a category of bug that behavior-only testing structurally cannot: the case where the code and its own documentation have quietly diverged. You will start reading this app's spec directly in Module 5, and from there, every later module treats it as the reference point, not an afterthought.

None of this means the spec is infallible. You will find real gaps in it before this course is over, places where it under-documents what the app actually does. Finding those gaps *is* part of the value; a good spec-driven test suite does not just confirm the spec, it tells you exactly where reality and documentation disagree.

## Try it

Write a script that sends `GET http://localhost:5000/health` (no auth needed) and prints the status code and full JSON body. Then send `GET http://localhost:5000/api/appointments` with no `Authorization` header at all, and print its status code too. You will get two very different results: one succeeds outright, the other fails because it is a protected endpoint. Hold onto that second one; that failure mode is exactly what Module 4 explains in detail.
