## Page purpose

You've built something real across 21 modules of implementation and two more of refactoring and diagnosis. This page is about presenting it — turning `llmqe/` into something a hiring manager or interviewer can actually understand in a few minutes, and turning your own experience building it into answers you can defend under real questioning, not just describe.

## Learning objectives

By the end of this page, you should be able to:

- Structure a professional README for the LLM Quality & Evaluation Framework.
- Answer the reflection questions about your own build, specifically and concretely, not generically.
- Answer scenario-based interview questions using this course's concepts, not memorized definitions.

## What the README needs

A README that actually gets read front-to-back is organized so a skimmer gets the shape in 30 seconds and a serious reader gets the depth after that. For this project, structure it as:

1. **What it is, in two sentences.** A working evaluation and testing framework for LLM applications, built incrementally against a local Ollama model, covering functional correctness, RAG quality, safety, regression detection, and CI integration.
2. **Architecture diagram.** A simplified version of the module diagrams built across this course — client → validation → evaluation (rule-based, semantic, judge) → RAG → safety → baseline/regression → observability/reporting → CI.
3. **Test strategy.** The tiered approach from Module 7: cheap and exact checks first, escalating to semantic and judge-based evaluation only when needed — and why, referencing the cost/latency argument from Modules 7 and 19.
4. **Evaluation methodology.** How `score_case()` works, and critically, how it was itself validated (Module 8) rather than trusted by default.
5. **Sample datasets.** `qa_dataset.jsonl`, `evaluator_calibration.jsonl`, `retrieval_dataset.jsonl` — link to them directly; a reviewer who can see real data trusts the project more than one reading only prose about it.
6. **Baseline and regression results.** A concrete example — Module 14's safety-regression incident is a strong one to include directly, showing the framework catching something real.
7. **Security/safety tests.** Module 12's suite, with the same responsible framing used throughout this course — defensive, educational, never a weaponizable list.
8. **Reports and CI pipeline.** A sample `latest_report.md` and the two GitHub Actions workflows from Module 19.
9. **Configuration.** `config.py`, and why it exists (Module 20).
10. **Troubleshooting guide.** The three failures from Module 23, written up as a real troubleshooting reference for a future contributor.
11. **Technical decisions.** Module 22's three decisions, in your own words.
12. **Future improvements.** Honest, specific gaps — not a vague "could be better" but real ones you already know about: `groundedness_score()`'s numeric-only limitation (Module 11), the single-provider-in-practice state of `LLMProvider` (Module 21), the input-validation gap in the safety suite (Module 12).

## Reflection questions — answer these about your own build

These aren't rhetorical. Write real answers, specific to your framework, before moving on:

- **What problem did I actually solve?** Not "I built an AI testing framework" — what specific failure modes does it catch, for what specific (fictional) system?
- **Why this evaluation strategy, and not a simpler or more elaborate one?** Revisit Module 22's decision one — can you make the same argument in your own words, with your own examples from the code you wrote?
- **How did I handle non-determinism?** Point to specific mechanisms — `temperature`/`seed` pinning (Module 2), the consistency tests (Module 4), the baseline comparison (Module 13) — not just "LLMs are non-deterministic" as an abstract fact.
- **How did I detect regressions?** Walk through Module 14's two incidents as your own worked examples, not as something the course did to you.
- **How did I validate the evaluator?** Module 8's calibration dataset and the polarity-guard fix are your concrete answer here — a real bug you found and fixed in your own grading logic.
- **How would this scale in production?** Be honest about what's still missing — real observability infrastructure beyond a JSONL file, a real secrets/PII redaction layer (Module 17 named this gap explicitly), and handling far more than four documents and two evaluation datasets.

## Scenario-based interview questions

Work through these using this course's concepts — not generic AI knowledge, and not memorized definitions.

1. *"Your team's AI feature passed every test yesterday and is failing today, with no code changes. Walk me through how you'd investigate."* — Use Module 4's non-determinism vocabulary and Module 13's baseline fields as your investigation checklist, the same way Module 23's failure one worked.

2. *"How do you know your evaluation framework is actually evaluating correctly, and not just confidently wrong?"* — This is Module 8's exact question. Answer with the calibration-dataset technique, not a general statement about "testing the tests."

3. *"A retrieval-augmented system gives a wrong answer. How do you figure out if it's a retrieval problem or a generation problem?"* — Module 10's diagnostic split, applied to a system you didn't build, using the same reasoning you used on Vespera's.

4. *"When would you NOT use an LLM-as-a-judge, even though it's more sophisticated than a rule-based check?"* — Module 7's explicit trade-offs section, plus Module 22's decision one about matching technique to field type.

5. *"How would you design a CI pipeline for an AI feature, given that you can't run a full evaluation suite on every commit?"* — Module 19's two-path design, with the specific reasoning for why safety tests stay on the fast path regardless of cost.

6. *"Tell me about a time your evaluation framework had a bug in it, not the system it was testing."* — Module 8's polarity-guard fix is a real, specific answer, better than any generic claim about "testing the tests" — you have an actual bug and an actual fix to describe.

7. *"How do you decide what's a blocking regression versus an acceptable variation?"* — Module 22's decision three, and the specific reasoning behind treating safety failures as categorically different from ordinary quality flips.
