## Page purpose

Modules 3 through 5 wrote individual, one-off checks. This page formalizes the simplest evaluation techniques (exact matching, rule-based validation, required-field validation, and JSON/schema validation) into a reusable `validate_response()` layer the rest of the framework calls. These techniques are simple on purpose: they are the ones to reach for first, and knowing exactly where their usefulness ends is as important as knowing how to use them.

## Learning objectives

By the end of this page, you should be able to:

- Implement and use exact matching, rule-based validation, required-field validation, and JSON/schema validation.
- State, for each technique, when it is the right tool and when it isn't.
- Build a reusable `validate_response()` function the framework can run against many inputs, not just one hardcoded question.

## Four simple techniques

**Exact matching** checks a field equals one specific expected value. You have already used this correctly, on `"topic"` in Module 3, and incorrectly, on `"answer"`, in the same module. It only belongs on fields with a small, genuinely fixed set of legal values.

**Rule-based validation** is a plain Python function encoding a specific rule ("the answer must not contain this known-wrong value"). Module 5's `answer_contains_known_wrong_value` is one of these. Cheap to write, cheap to run, and only as good as the rules you thought to write.

**Required-field validation** checks that every field the contract promises is actually present (and no unexpected ones snuck in). You have been doing this implicitly with `set(parsed.keys()) == {"answer", "topic"}`; formalizing it means it applies uniformly everywhere the contract is used.

**JSON/schema validation** is a stricter, declarative version of required-field validation: not just which fields exist, but their types and allowed values, checked all at once against a schema instead of a chain of manual assertions.

```python
# llmqe/validation.py
from typing import Any

REQUIRED_FIELDS = {"answer", "topic"}
ALLOWED_TOPICS = {"billing", "security", "product", "other"}


def has_required_fields(parsed: dict) -> bool:
    return set(parsed.keys()) == REQUIRED_FIELDS


def matches_schema(parsed: dict) -> list[str]:
    """Returns a list of schema violations — empty list means valid."""
    errors = []
    if not isinstance(parsed.get("answer"), str) or not parsed["answer"].strip():
        errors.append("'answer' must be a non-empty string")
    if parsed.get("topic") not in ALLOWED_TOPICS:
        errors.append(f"'topic' must be one of {ALLOWED_TOPICS}, got {parsed.get('topic')!r}")
    return errors


def answer_contains_known_wrong_value(answer: str, wrong_values: list[str]) -> bool:
    lowered = answer.lower()
    return any(wrong.lower() in lowered for wrong in wrong_values)


def validate_response(raw_text: str, known_wrong_values: list[str] | None = None) -> list[str]:
    """Runs every simple check available and returns all violations found.
    An empty list means the response passed every check this module knows
    how to run — not a guarantee the content is actually correct."""
    import json

    errors = []
    try:
        parsed = json.loads(raw_text)
    except json.JSONDecodeError:
        return ["response is not valid JSON"]

    if not has_required_fields(parsed):
        errors.append(f"missing or extra fields: {set(parsed.keys())}")

    errors.extend(matches_schema(parsed))

    if known_wrong_values and answer_contains_known_wrong_value(parsed.get("answer", ""), known_wrong_values):
        errors.append("answer contains a known-wrong value")

    return errors
```

Using it collapses Module 5's test into one line:

```python
# tests/test_validation.py
from llmqe.client import OllamaClient, SYSTEM_PROMPT
from llmqe.validation import validate_response

def test_free_plan_rate_limit_question():
    client = OllamaClient()
    result = client.ask_with_system(SYSTEM_PROMPT, "What's the API rate limit on the Free plan?")

    errors = validate_response(result.text, known_wrong_values=["500 requests", "1000 requests", "unlimited"])
    assert errors == [], f"Validation failed: {errors}"
```

**Run it.** The `errors` list, when non-empty, tells you exactly which check failed, useful both for debugging and, in Module 18, for building a readable report instead of a bare pass/fail.

## When to use / When not to use: automated evaluation

Before going further, name the honest limits of *automated evaluation as a category*, not just these four simple techniques, but everything Modules 6 through 8 build, including the semantic and judge-based methods still ahead.

**Use it when:**
- The property you are checking is well-defined enough to encode as a rule, schema, or comparison: "is this valid JSON," "is this number one we already know is wrong," "does this field match one of N allowed values."
- You need the same check to run unattended, repeatedly, at low cost: in a test suite, in CI, across a large dataset.
- You are checking a property, not adjudicating open-ended quality: "did it mention SSO" is automatable; "was this the single best possible answer" mostly is not.

**Don't use it when:**
- The question is genuinely subjective or requires domain judgment a rule cannot encode: automated evaluation will give you a confident number that is quietly measuring the wrong thing.
- You have no known-correct reference to check against at all: automation needs *something* to compare to, even a loose one; without it you are not evaluating, you are guessing with extra steps.
- The stakes are high enough that a human review is warranted regardless of what an automated check says: automation should typically narrow what a human needs to look at, not fully replace their judgment on consequential decisions.

**Trade-offs:** automated evaluation is fast, cheap, and consistent: the same input gets the same verdict every time, which none of the semantic or judge-based techniques in Module 7 can fully promise. What it trades away is nuance: it can only ever check what someone thought to encode as a rule. A validation layer with 100% passing tests tells you "nothing I thought to check for is broken," not "this is a good response." Keep that distinction honest in how you report results, a theme Module 18 returns to directly.

## Building the framework: Milestone 5

`llmqe/validation.py`'s `validate_response()` is Milestone 5: response validation, generalized from Module 5's one hardcoded check into something any test in the framework can call against any question. It is still entirely rule-based, which is exactly its limit: it can only catch fabrications, missing fields, and schema violations you already know to check for. Module 7 builds the technique for catching quality problems you *did not* specifically write a rule for.
