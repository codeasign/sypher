This page gives it one, a Retrieval-Augmented Generation (RAG) pipeline that looks up relevant Vespera documentation before generating an answer. This page covers RAG at a practical level: enough for a QE to reason clearly about what can go wrong, not deep embedding-model theory.

## RAG in plain language

A RAG system adds one step in front of the model call you have been making since Module 2: instead of sending only the user's question, the application first **retrieves** relevant text from a knowledge source and includes it in the prompt, so the model can answer *from that material* instead of from whatever it happened to learn during training. Four terms, defined once and used precisely from here on:

- **Document**: one piece of source material. For Vespera, a short paragraph of real (fictional) product documentation.
- **Chunk**: a document, or a piece of one, sized to fit usefully into a model's context, small enough to embed and retrieve precisely, large enough to still make sense on its own. Vespera's documentation here is short enough that each document *is* one chunk; a real knowledge base with long pages would need to split them, which is where chunking becomes its own design problem.
- **Embedding**: the numeric vector representing a chunk's meaning, from Module 7, used here to compare a question against every chunk and find the closest matches.
- **Retrieval**: the act of finding and returning the chunks most relevant to a given question, before generation happens.

## Building a retriever

```python
# llmqe/rag/retriever.py
from llmqe.eval.scorer import get_embedding, cosine_similarity
from llmqe.rag.documents import DOCUMENTS


class Retriever:
    def __init__(self, documents=DOCUMENTS):
        self.documents = documents
        # Pre-compute embeddings once, rather than re-embedding every
        # document on every query.
        self._doc_embeddings = [(doc, get_embedding(doc["text"])) for doc in documents]

    def retrieve(self, query: str, top_k: int = 2) -> list[dict]:
        query_embedding = get_embedding(query)
        scored = [
            (doc, cosine_similarity(query_embedding, doc_embedding))
            for doc, doc_embedding in self._doc_embeddings
        ]
        scored.sort(key=lambda pair: pair[1], reverse=True)
        return [{"document": doc, "score": score} for doc, score in scored[:top_k]]
```

Try it:

```python
from llmqe.rag.retriever import Retriever

retriever = Retriever()
results = retriever.retrieve("What's the rate limit on the Free plan?")
for r in results:
    print(f"{r['score']:.3f}  {r['document']['id']}  {r['document']['text']}")
```

**Run it.** The `free-plan` document should come back with the highest score: its text is the most semantically relevant to a rate-limit question.

## Wiring retrieval into the assistant

```python
# llmqe/rag/assistant.py
from llmqe.client import OllamaClient
from llmqe.rag.retriever import Retriever

RAG_SYSTEM_PROMPT = """\
You are Vespera Helpdesk's internal product assistant. You will be given \
retrieved documentation and a question. Answer using ONLY the retrieved \
documentation below — if the documentation doesn't contain the answer, \
say so explicitly instead of guessing.

Respond with JSON only: {"answer": "...", "topic": "billing|security|product|other"}
"""


def ask_with_retrieval(question: str, retriever: Retriever, client: OllamaClient) -> dict:
    results = retriever.retrieve(question)
    context = "\n".join(r["document"]["text"] for r in results)
    prompt = f"Retrieved documentation:\n{context}\n\nQuestion: {question}"
    result = client.ask_with_system(RAG_SYSTEM_PROMPT, prompt)
    return {"response": result, "retrieved": results}
```

Run the exact question that produced a hallucinated number back in Module 5:

```python
from llmqe.client import OllamaClient
from llmqe.rag.retriever import Retriever
from llmqe.rag.assistant import ask_with_retrieval

client = OllamaClient()
retriever = Retriever()
result = ask_with_retrieval("What's the API rate limit on the Free plan?", retriever, client)
print(result["response"].text)
```

**Run it.** This time, the answer should correctly state **60 requests per minute**, not because the model got smarter, but because it is now answering *from the retrieved document* instead of guessing.

## Context relevance and context completeness

These sound similar and are worth separating precisely, because Module 10 tests them as distinct failure modes:

**Context relevance:** did retrieval return document(s) that are actually about the question asked? A retriever that returns the `data-retention` document for a rate-limit question has a relevance failure, regardless of what the model does with it afterward.

**Context completeness:** even when retrieval returns a *relevant* document, does it contain everything needed to answer fully? If Vespera's documentation had separate documents for "Free plan rate limits" and "Free plan burst limits," and only one got retrieved, the context would be relevant but incomplete: the model might answer correctly on what it has and simply omit the part it was never given.

Both matter independently: relevant-but-incomplete context produces a partial answer; irrelevant context (whether or not it happens to be complete about the wrong thing) produces a wrong or evasive one.
