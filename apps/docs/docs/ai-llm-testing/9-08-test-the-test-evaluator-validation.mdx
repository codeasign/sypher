## Page purpose

Every technique in Modules 6 and 7 shares an assumption this page finally challenges: that the evaluator itself is correct. It usually isn't, not fully — thresholds are picked somewhat arbitrarily, judge prompts have blind spots, and Module 7 already showed semantic similarity getting fooled by a direct contradiction. This page asks the question the whole framework depends on: **how do we know our evaluator is actually evaluating correctly?** — and catches a real miscalibration in the `score_case()` pipeline you just built.

## Learning objectives

By the end of this page, you should be able to:

- Explain why an evaluator needs its own validation, separate from validating the application it evaluates.
- Build a known-good/known-bad dataset and use it to test an evaluator's accuracy.
- Diagnose a miscalibrated threshold that lets a genuinely wrong answer pass.
- Explain evaluation drift and judge inconsistency as ongoing risks, not one-time bugs to fix and forget.

## The evaluator needs a test suite too

Modules 3 through 7 tested Vespera's assistant. This page tests the thing that's been *grading* the assistant. That's a real distinction, not a formality: a bug in `score_case()` doesn't show up as a wrong answer from the assistant — it shows up as a **wrong verdict about** a correct or incorrect answer, silently, because nothing about a wrong verdict looks different from a right one unless you specifically check.

A **weak evaluator** is one that systematically lets bad output pass, or systematically fails good output — and either failure is expensive in a different way. A weak evaluator that's too lenient means real regressions ship. A weak evaluator that's too strict means your team starts distrusting (and eventually ignoring) the test suite, which is arguably worse, because it undermines every other evaluation technique this course has built once ignored.

## Building a known-good/known-bad dataset

To test an evaluator, you need cases where you — a human — already know the right verdict, so you can check whether the evaluator agrees with you:

```jsonl
{"question": "Does the Pro plan support SSO?", "reference_answer": "Yes, the Pro plan includes SSO support for enterprise identity providers.", "candidate_answer": "Yes, SSO is available on the Pro plan for enterprise identity providers.", "expected_verdict": "pass", "label": "correct, reworded"}
{"question": "Does the Pro plan support SSO?", "reference_answer": "Yes, the Pro plan includes SSO support for enterprise identity providers.", "candidate_answer": "No, the Pro plan does not support SSO.", "expected_verdict": "fail", "label": "direct contradiction"}
{"question": "What's the API rate limit on the Free plan?", "reference_answer": "The Free plan is limited to 60 API requests per minute.", "candidate_answer": "The Free plan allows 500 requests per minute.", "expected_verdict": "fail", "label": "fabricated number"}
{"question": "Does Enterprise include phone support?", "reference_answer": "Yes, Enterprise plan customers get 24/7 phone support.", "candidate_answer": "Enterprise customers can reach support by phone around the clock.", "expected_verdict": "pass", "label": "correct, reworded, no exact keyword overlap"}
```

Save this as `llmqe/eval/datasets/evaluator_calibration.jsonl` — notice this is a *different* dataset from Module 7's `qa_dataset.jsonl`. That one holds questions to ask the assistant; this one holds already-answered pairs to check the *evaluator* against, with a human-assigned `expected_verdict` on each.

## Testing the evaluator against it

```python
# llmqe/eval/evaluator_tests.py
import json
from llmqe.eval.scorer import score_case

def load_calibration_cases(path="llmqe/eval/datasets/evaluator_calibration.jsonl"):
    with open(path) as f:
        return [json.loads(line) for line in f]


def test_evaluator_matches_human_judgment():
    cases = load_calibration_cases()
    mismatches = []

    for case in cases:
        raw_response = json.dumps({"answer": case["candidate_answer"], "topic": "product"})
        result = score_case(case["question"], case["reference_answer"], raw_response)
        actual = "pass" if result["passed"] else "fail"

        if actual != case["expected_verdict"]:
            mismatches.append({"label": case["label"], "expected": case["expected_verdict"], "actual": actual, "detail": result})

    assert not mismatches, f"Evaluator disagreed with human judgment on {len(mismatches)} case(s): {mismatches}"
```

**Run it.**

## Diagnosing a miscalibrated evaluator

**Symptom:** `test_evaluator_matches_human_judgment` fails on the "direct contradiction" case — the evaluator says `pass` on an answer a human immediately recognizes as wrong.

**Hypothesis:** something in `score_case()` is short-circuiting to a pass before the case ever reaches the more careful judge check.

**Investigation:** print the full result for just that case instead of only the pass/fail summary.

```python
result = score_case(
    "Does the Pro plan support SSO?",
    "Yes, the Pro plan includes SSO support for enterprise identity providers.",
    json.dumps({"answer": "No, the Pro plan does not support SSO.", "topic": "security"}),
)
print(result)
```

**Evidence:** `result["stage"]` reads `"similarity"`, not `"judge"` — meaning the case never reached the judge at all. The similarity score between "No, the Pro plan does not support SSO" and the reference answer came back above the `0.9` short-circuit threshold from Module 7's `score_case()`, exactly the false-positive risk that module warned about but didn't yet fix.

**Root cause:** `score_case()`'s similarity short-circuit (`if similarity > 0.9: return passed`) trusts a single number too much — it was added as a cost-saving fast path, but nothing validated that 0.9 was actually a safe cutoff before it started gating real verdicts.

**Fix:** don't fix the *assistant* — it never did anything wrong here. Fix the evaluator. Remove the blind short-circuit and always let the judge weigh in on the specific case type most likely to fool similarity — direct polarity contradictions (yes vs. no):

```python
# llmqe/eval/scorer.py (corrected)
def _is_polarity_contradiction(answer: str, reference_answer: str) -> bool:
    """Cheap guard for the specific false-positive Module 8 caught: a
    yes/no flip that similarity alone can't reliably detect."""
    a, r = answer.lower(), reference_answer.lower()
    a_says_no = a.strip().startswith("no") or " does not " in a or " isn't " in a
    r_says_yes = r.strip().startswith("yes") or " does " in r
    return a_says_no and r_says_yes


def score_case(question: str, reference_answer: str, raw_response: str) -> dict:
    validation_errors = validate_response(raw_response)
    if validation_errors:
        return {"passed": False, "stage": "validation", "errors": validation_errors}

    answer = json.loads(raw_response)["answer"]

    if _is_polarity_contradiction(answer, reference_answer):
        verdict = judge_answer(question, reference_answer, answer)
        return {"passed": verdict["score"] >= 4, "stage": "judge (polarity guard)", "verdict": verdict}

    similarity = semantic_similarity_score(answer, reference_answer)
    if similarity > 0.9:
        return {"passed": True, "stage": "similarity", "similarity": similarity}

    verdict = judge_answer(question, reference_answer, answer)
    return {"passed": verdict["score"] >= 4, "stage": "judge", "verdict": verdict}
```

Re-run `test_evaluator_matches_human_judgment` — it should now pass on all four calibration cases.

**Prevention:** any time you add a fast path or shortcut to an evaluator for cost or speed, add the specific case type it's risking to the calibration dataset *before* trusting it in production — the shortcut in Module 7 wasn't wrong to want, it was wrong to ship unvalidated.

## Judge inconsistency and evaluation drift

Two ongoing risks worth naming explicitly, because neither is a one-time bug you fix and move past:

**Judge inconsistency** — even with `temperature=0`, a judge model isn't guaranteed to give the exact same score on the exact same pairing forever, especially across model versions. Periodically re-run the calibration dataset, not just once after building the evaluator.

**Evaluation drift** — as Vespera's product actually changes (new plans, updated limits), `qa_dataset.jsonl`'s reference answers can quietly become outdated *facts*, independent of anything about model or evaluator quality. An evaluator scoring correctly against a stale reference will confidently produce wrong verdicts. Treat both datasets built in this and the previous module as living assets that need periodic review, not one-time deliverables — the same warning Module 5's known-facts file deserves too.
