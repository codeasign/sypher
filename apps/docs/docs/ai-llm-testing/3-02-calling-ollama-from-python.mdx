## Page purpose

This page writes the first real file of the LLM Quality & Evaluation Framework: a small Python client that sends prompts to Ollama and captures what comes back, built specifically around Vespera's Helpdesk AI Assistant. Every module from here forward calls this client instead of talking to Ollama directly, so getting it right now matters more than its size suggests.

## Learning objectives

By the end of this page, you should be able to:

- Send a prompt to a local model from Python and read the response back into a variable.
- Explain what `temperature` and `seed` control, and why a testing framework needs to care about both.
- Build a reusable `OllamaClient` that Vespera's Helpdesk AI Assistant tests will call for the rest of this course.
- Diagnose a call that silently hangs instead of returning.

## Sending your first prompt from Python

You already confirmed the `ollama` package works back in Setup. Here's the same idea, applied to something closer to what Vespera's assistant actually does — answering a support agent's product question:

```python
from ollama import chat

response = chat(
    model="llama3.2:3b",
    messages=[
        {"role": "user", "content": "Does the Pro plan support single sign-on (SSO)?"}
    ],
)

print(response.message.content)
```

**Run it.** You'll get back a plain-language answer — the model is free-associating from its training data here, since nothing about Vespera's actual plans has been given to it. (That gap — the model answering from general knowledge instead of Vespera's real documentation — is exactly the gap Module 9's RAG system exists to close. For now, keep it in mind rather than fixing it.)

### Explaining the result

`chat()` sent a single HTTP request to your local Ollama server, containing the model name and a list of messages. `response.message.content` is the generated text. The `messages` list is structured as a conversation (each entry has a `role` — `"user"`, `"assistant"`, or `"system"` — and `content`), even though you only sent one message here; multi-turn conversations just append more entries to the same list.

## Terminology: temperature and seed

Two parameters control how much the model's output varies between calls with the same prompt — and a testing framework has to understand both before it can make any claim about reproducibility.

**`temperature`** controls how much randomness goes into picking each next word. At `temperature=0`, the model always picks the single most likely next token — the closest thing to deterministic behavior an LLM offers. Higher values (Ollama's default is `0.8`) let it pick less-likely tokens sometimes, producing more varied, more "creative" — and less predictable — output.

**`seed`** controls the random number generator behind that token selection. Given the same seed, the same prompt, and the same temperature, most models will produce the *same* output run to run — but this guarantee is weaker than it sounds: it can still break across model versions, quantization changes, or hardware differences. Treat `seed` as a way to *reduce* flakiness in your tests, not as a guarantee you're exempt from Module 4's non-determinism testing.

Pass both explicitly:

```python
from ollama import chat

response = chat(
    model="llama3.2:3b",
    messages=[{"role": "user", "content": "Does the Pro plan support SSO?"}],
    options={"temperature": 0, "seed": 42},
)

print(response.message.content)
```

**Run this twice in a row and compare the two outputs.** They should now match, or come very close to it — a sharp contrast with the default-temperature call above, which you should also try running twice to see it vary.

## Building the framework: `OllamaClient`

Wrap this into a real, reusable class — `llmqe/client.py` — this is Milestone 2 (send prompts using Python) and Milestone 3 (capture responses):

```python
# llmqe/client.py
from dataclasses import dataclass
from ollama import chat


@dataclass
class LLMResponse:
    """A captured model response, plus the settings that produced it."""
    text: str
    model: str
    temperature: float
    seed: int | None


class OllamaClient:
    """Thin wrapper around the Ollama chat API.

    Every module from here on calls this instead of the ollama package
    directly, so reproducibility settings and response capture live in
    exactly one place.
    """

    def __init__(self, model: str = "llama3.2:3b", temperature: float = 0, seed: int | None = 42):
        self.model = model
        self.temperature = temperature
        self.seed = seed

    def ask(self, prompt: str) -> LLMResponse:
        response = chat(
            model=self.model,
            messages=[{"role": "user", "content": prompt}],
            options={"temperature": self.temperature, "seed": self.seed},
        )
        return LLMResponse(
            text=response.message.content,
            model=self.model,
            temperature=self.temperature,
            seed=self.seed,
        )
```

Using it looks like this — and this is the shape every later module's test code will follow:

```python
from llmqe.client import OllamaClient

client = OllamaClient()
result = client.ask("Does the Pro plan support SSO?")

print(result.text)
print(f"(model={result.model}, temperature={result.temperature}, seed={result.seed})")
```

Defaulting to `temperature=0` and a fixed `seed` here is a deliberate choice, not an oversight — it's what makes Module 3's first tests possible at all. Module 4 comes back and adds a *second* mode to this client for deliberately testing at realistic, non-zero temperature, once you understand exactly what that trades away.

## Diagnosing a call that hangs

**Symptom:** `client.ask(...)` never returns — no error, no output, the terminal just sits there.

**Hypothesis:** either the server isn't reachable (Setup's failure mode), or the model named in `OllamaClient` was never pulled, and Ollama is silently trying to download it before answering.

**Investigation:** open a second terminal and check what's currently loaded and what's on disk:

```bash
ollama ps
ollama list
```

**Evidence:** `ollama list` doesn't show `llama3.2:3b` — it was never pulled on this machine, or was pulled under a different tag.

**Root cause:** the client requested a model name that doesn't exist locally; depending on version and configuration, Ollama can attempt a pull in the background rather than failing fast, which reads as a hang rather than a clear error.

**Fix:** pull the exact model name the client references, then re-run:

```bash
ollama pull llama3.2:3b
```

**Prevention:** keep the model name in exactly one place — `OllamaClient.__init__`'s default — instead of hardcoding it in multiple test files, so there's only ever one string to check against `ollama list` when this happens again.
