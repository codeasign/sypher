## Page purpose

Module 6's `validate_response()` cannot catch a response that is schema-valid, free of known-wrong values, and still mediocre: vague, half-answering the question, or technically true but unhelpful. This page covers the two techniques built to catch exactly that: semantic similarity and LLM-as-a-judge. Both are more powerful than anything in Module 6, and both introduce a new problem neither rule-based check had: the evaluator itself can now be wrong, which Module 8 addresses head-on.

## Learning objectives

By the end of this page, you should be able to:

- Score an answer's semantic similarity to a reference answer using embeddings.
- Build an LLM-as-a-judge that scores an answer's quality against a rubric.
- Build a small golden evaluation dataset with reference answers and expected properties.
- Explain false positives, false negatives, and evaluator reliability for both techniques, and say when each technique is and isn't the right tool.

## Building a golden evaluation dataset

Everything on this page needs something to evaluate *against*. A golden dataset pairs realistic questions with the properties a correct answer must have. This is Milestone 6:


## Semantic similarity, via embeddings

An **embedding** is a numeric vector representing a piece of text's meaning: texts with similar meaning produce vectors that are numerically close together, even if the wording is completely different. Ollama can generate these directly:

```python
# llmqe/eval/scorer.py
from ollama import embed
import math


def get_embedding(text: str, model: str = "llama3.2:3b") -> list[float]:
    response = embed(model=model, input=text)
    return response.embeddings[0]


def cosine_similarity(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b)


def semantic_similarity_score(answer: str, reference_answer: str) -> float:
    """Returns a 0-1 similarity score between an answer and a reference."""
    return cosine_similarity(get_embedding(answer), get_embedding(reference_answer))
```

Try it against two differently-worded but equivalent answers:

```python
score = semantic_similarity_score(
    "Yes, SSO is supported for Pro plan customers.",
    "Yes, the Pro plan includes SSO support for enterprise identity providers.",
)
print(score)  # expect something high, e.g. > 0.85
```

**Run it**, then compare against an answer that is *topically* similar but factually wrong:

```python
score = semantic_similarity_score(
    "No, the Pro plan does not support SSO.",
    "Yes, the Pro plan includes SSO support for enterprise identity providers.",
)
print(score)  # often still fairly high — same topic, opposite fact
```

### Explaining the result, and its false negatives/positives

This is the first sharp lesson of semantic evaluation: **a contradicted answer can still score highly similar**, because embeddings capture topical closeness, not factual agreement. "Yes SSO" and "no SSO" are about the same subject, in similar phrasing, which is exactly what embeddings are built to detect. That is a **false positive** for this technique: a high similarity score on an answer that is actually wrong. Its **false negative** case is the mirror image: a *correct* answer phrased very differently from the reference (different structure, different emphasis, additional caveats) can score lower than it deserves, flagging a fine answer as suspect. Neither failure means the technique is useless: it means semantic similarity answers "is this about the same thing, phrased somewhat similarly," not "is this factually correct," and treating it as the latter is the mistake to avoid.

## LLM-as-a-judge

Instead of a numeric distance, ask a *second* model call to actually judge the answer against the reference and a rubric, closer to how a human would evaluate it:

```python
# llmqe/eval/judge.py
import json
from llmqe.client import OllamaClient

JUDGE_SYSTEM_PROMPT = """\
You are an evaluator grading a support assistant's answer. You will be \
given a question, a reference answer known to be correct, and a candidate \
answer to grade.

Score the candidate from 1 to 5:
5 = fully correct and consistent with the reference
3 = partially correct, missing or vague on a key detail
1 = contradicts the reference or states something false

Respond with JSON only: {"score": <1-5>, "reason": "<one sentence>"}
"""


def judge_answer(question: str, reference_answer: str, candidate_answer: str) -> dict:
    client = OllamaClient(temperature=0)
    prompt = (
        f"Question: {question}\n"
        f"Reference answer: {reference_answer}\n"
        f"Candidate answer: {candidate_answer}"
    )
    result = client.ask_with_system(JUDGE_SYSTEM_PROMPT, prompt)
    return json.loads(result.text)
```

Run it against the same contradicted answer that fooled semantic similarity:

```python
verdict = judge_answer(
    question="Does the Pro plan support SSO?",
    reference_answer="Yes, the Pro plan includes SSO support for enterprise identity providers.",
    candidate_answer="No, the Pro plan does not support SSO.",
)
print(verdict)  # expect something like {"score": 1, "reason": "Directly contradicts the reference."}
```

**Run it.** Where semantic similarity scored this pairing deceptively high, a reasonable judge model catches the direct contradiction and scores it low. This is the concrete case where the two techniques disagree, and it is worth seeing them disagree on the same input rather than taking it on faith.

### False positives, false negatives, and reliability for LLM-as-a-judge

LLM-as-a-judge is closer to human judgment than embeddings, but it inherits the judged model's own failure modes: it can be **inconsistent** (the same pairing scored differently on different runs, unless you pin `temperature=0` as done above), it can be **fooled by confident wording** the same way a human skimming quickly might be, and it can have **systematic biases**, for instance favoring longer or more detailed answers regardless of correctness, a well-documented tendency in LLM judges generally. A false positive here is a high score given to a subtly wrong answer the judge did not catch; a false negative is a correct answer marked down because the judge misjudged an unusual (but valid) phrasing. Neither failure is rare enough to ignore, which is precisely why Module 8 exists: **the evaluator itself needs to be evaluated**, not trusted by default just because it is more sophisticated than a rule.

## When to use / When not to use: LLM-as-a-judge

**Use it when:** you need to judge answer quality holistically (correctness plus tone, completeness, or helpfulness) in a way no fixed rule can encode, and you have validated the judge against known-good/known-bad examples first (Module 8).

**Don't use it when:** the property is simple enough for Module 6's rule-based checks. Using a judge for "is this valid JSON" wastes a model call on something a schema check answers instantly and perfectly. Also avoid it as your *only* evaluation layer for high-stakes decisions (like a release-blocking CI gate) without a baseline of how often the judge itself is wrong.

**Trade-offs:** a judge is slower and costs more (a full model call, not a vector comparison) than any technique in Module 6, and it is non-deterministic unless pinned. In exchange, it can catch quality problems no one thought to write a rule for, the exact gap this page opened with.

## When to use / When not to use: embeddings / semantic similarity

**Use it when:** you want a fast, cheap, deterministic-ish signal for "is this response roughly on-topic and similarly worded to a reference," useful as a quick first-pass filter before spending judge-model calls on borderline cases.

**Don't use it when:** the question hinges on a specific fact that can flip the correct answer's meaning (yes vs. no, a specific number). As shown above, embeddings can rate a contradicted answer as similar. Do not use similarity score alone to gate anything where being factually wrong is the exact failure you are trying to catch.

**Trade-offs:** embeddings are fast and cheap enough to run on every test case in a large dataset, but the score answers "how alike is this text," not "is this text correct." Conflating the two is the single most common mistake teams make adopting semantic evaluation.

## Combining strategies

None of Module 6's rule-based checks, this page's semantic similarity, or LLM-as-a-judge is sufficient alone. A practical scoring function layers them, cheapest first:

```python
# llmqe/eval/scorer.py (continued)
from llmqe.validation import validate_response
from llmqe.eval.judge import judge_answer


def score_case(question: str, reference_answer: str, raw_response: str) -> dict:
    validation_errors = validate_response(raw_response)
    if validation_errors:
        return {"passed": False, "stage": "validation", "errors": validation_errors}

    import json
    answer = json.loads(raw_response)["answer"]

    similarity = semantic_similarity_score(answer, reference_answer)
    if similarity > 0.9:
        return {"passed": True, "stage": "similarity", "similarity": similarity}

    verdict = judge_answer(question, reference_answer, answer)
    return {"passed": verdict["score"] >= 4, "stage": "judge", "verdict": verdict}
```

Cheap, deterministic checks run first and can pass a case outright (high similarity); anything ambiguous escalates to the more expensive, more nuanced judge call instead of running it on every single case.
