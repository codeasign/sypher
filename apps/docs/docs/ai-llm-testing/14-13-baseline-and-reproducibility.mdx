## Page purpose

Module 4 showed that a single response can vary run to run without being wrong. This page scales that idea up to an entire evaluation suite: how do you tell "our AI feature actually got worse" apart from "today's run just landed on the noisy end of normal variation"? The answer is a **baseline** — a recorded snapshot of expected behavior — and this page builds the machinery to record and compare against one.

## Learning objectives

By the end of this page, you should be able to:

- Explain the baseline-driven workflow, start to finish.
- List what a baseline record needs to track, and why each field matters.
- Record a baseline from the framework's existing evaluation suite and compare a new run against it.
- Explain, concretely, at least three reasons results can shift with unchanged application code.

## The baseline-driven workflow

**Baseline → run evaluation → record results → change something → run again → compare → accept or reject.**

You establish a baseline once, by running your full evaluation suite (Modules 6, 7, and 11's checks, at minimum) against a known-good state and recording exactly what happened. From then on, every future run gets compared against that recording, not against a vague sense of "it usually works." A difference doesn't automatically mean regression — it means *something changed*, and a QE decides whether that change is acceptable (an intentional improvement) or a real problem (Module 14's subject). This page builds the recording and comparison machinery; Module 14 builds the judgment layer on top of it.

## What to track in a baseline record

A baseline entry needs enough detail to answer "what, specifically, changed?" months later, not just "did it pass":

| Field | Why it matters |
|---|---|
| `model` | A model swap (or silent vendor update) can change behavior with zero app code changes. |
| `config` | `temperature`, `seed`, and other options from Module 2 — results aren't comparable across different settings. |
| `prompt_version` | Which version of the system prompt produced this result — Module 14's exact subject. |
| `dataset_version` | Which version of the evaluation dataset was used — a dataset edit (Module 8's concern) changes what "pass" means. |
| `evaluator_version` | Which version of `score_case()` graded the result — Module 8 showed the evaluator itself can change. |
| `test_case` | Which specific input this record is for. |
| `score` / `pass_fail` | The actual outcome. |
| `reason` | Why — especially useful for judge-based failures, where the judge's own `"reason"` field (Module 7) is worth keeping. |
| `latency` | How long the call took — Module 16 builds on this. |
| `timestamp` | When the run happened. |
| `failure_category` | A short label (`"hallucination"`, `"citation_error"`, `"safety_failure"`) so patterns across many failures are visible at a glance. |

## Recording a baseline

```python
# llmqe/baseline/baseline.py
import json
import time
from dataclasses import dataclass, asdict
from pathlib import Path

BASELINE_DIR = Path("llmqe/baseline/baselines")
BASELINE_DIR.mkdir(parents=True, exist_ok=True)


@dataclass
class BaselineRecord:
    model: str
    config: dict
    prompt_version: str
    dataset_version: str
    evaluator_version: str
    test_case: str
    passed: bool
    score: float | None
    reason: str
    latency_seconds: float
    timestamp: float
    failure_category: str | None


def record_baseline(name: str, records: list[BaselineRecord]) -> Path:
    path = BASELINE_DIR / f"{name}.json"
    path.write_text(json.dumps([asdict(r) for r in records], indent=2))
    return path


def load_baseline(name: str) -> list[dict]:
    path = BASELINE_DIR / f"{name}.json"
    return json.loads(path.read_text())
```

Run the evaluation suite once, timing each call, and record it:

```python
import time
from llmqe.client import OllamaClient
from llmqe.eval.scorer import score_case
from llmqe.baseline.baseline import BaselineRecord, record_baseline

def build_baseline():
    client = OllamaClient()
    cases = [
        {"question": "Does the Pro plan support SSO?", "reference_answer": "Yes, the Pro plan includes SSO support for enterprise identity providers."},
        {"question": "What's the API rate limit on the Free plan?", "reference_answer": "The Free plan is limited to 60 API requests per minute."},
    ]
    records = []

    for case in cases:
        start = time.time()
        result = client.ask_with_system(SYSTEM_PROMPT, case["question"])
        latency = time.time() - start

        outcome = score_case(case["question"], case["reference_answer"], result.text)
        records.append(BaselineRecord(
            model=client.model, config={"temperature": client.temperature, "seed": client.seed},
            prompt_version="v1", dataset_version="v1", evaluator_version="v1",
            test_case=case["question"], passed=outcome["passed"], score=outcome.get("similarity"),
            reason=outcome.get("stage", ""), latency_seconds=latency, timestamp=time.time(),
            failure_category=None if outcome["passed"] else outcome["stage"],
        ))

    record_baseline("v1", records)

build_baseline()
```

**Run it.** You now have `llmqe/baseline/baselines/v1.json` — a real, inspectable snapshot of exactly what "working" looked like, on this date, with this model, this prompt, this dataset, this evaluator.

## Comparing a new run against the baseline

```python
# llmqe/baseline/baseline.py (continued)
def compare_to_baseline(baseline_name: str, current_records: list[BaselineRecord]) -> list[dict]:
    """Returns a list of differences between the baseline and a new run,
    keyed by test_case. Doesn't judge whether a difference is good or
    bad — that's Module 14's job."""
    baseline = {r["test_case"]: r for r in load_baseline(baseline_name)}
    diffs = []

    for record in current_records:
        prior = baseline.get(record.test_case)
        if prior is None:
            diffs.append({"test_case": record.test_case, "change": "new test case, no prior baseline"})
            continue
        if prior["passed"] != record.passed:
            diffs.append({
                "test_case": record.test_case,
                "change": f"pass/fail changed: {prior['passed']} -> {record.passed}",
                "prior_reason": prior["reason"], "current_reason": record.reason,
            })

    return diffs
```

## Why results can shift with no application code change

Module 4 named this at the level of a single response; here's the same idea at the level of an entire baseline comparison, made concrete by the fields you just started tracking:

- **A silent model update** — if `model` in a new run's record differs from the baseline's, that alone explains a shift, even with identical prompts and code.
- **An unpinned config** — if `config`'s `temperature`/`seed` differ (Module 2/4), don't be surprised by different scores.
- **A dataset edit** — `dataset_version` changing means "pass" no longer means the same thing it did in the baseline (Module 8's evaluation-drift warning, now with a version field to actually catch it).
- **An evaluator change** — `evaluator_version` differing means the same answer could score differently purely because the *grading* changed, not the thing being graded.
- **Genuine model variance** — even with everything else held constant, some run-to-run variance is expected; this is why `compare_to_baseline()` reports differences for a human to interpret rather than auto-failing on any change at all.

Tracking all five fields is what turns "the score changed, no idea why" into "the score changed because the prompt version moved from v1 to v2" — a diagnosable fact instead of a shrug.

## Building the framework: Milestone 8

`llmqe/baseline/baseline.py` — `BaselineRecord`, `record_baseline()`, `load_baseline()`, and `compare_to_baseline()` — is Milestone 8: baseline comparison.
