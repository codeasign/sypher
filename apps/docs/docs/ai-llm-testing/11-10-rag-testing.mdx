## Page purpose

Module 9 built a RAG pipeline; this page tests it, and catches the second Vespera incident of the course: the assistant retrieving irrelevant content and answering from it anyway. The central discipline of this page is one you'll apply for the rest of the course: **separating retrieval failures from generation failures** — never blaming the model for a retrieval problem, and never blaming retrieval for a generation problem.

## Learning objectives

By the end of this page, you should be able to:

- Test retrieval relevance against a labeled dataset of question → expected document.
- Distinguish a missing-document failure from a conflicting-document failure.
- Diagnose whether a bad answer came from bad retrieval or bad generation, using evidence, not assumption.
- Explain, with an example, when RAG is the wrong architecture to reach for.

## A labeled retrieval dataset

To test relevance, you need to know, for each question, which document *should* come back:

```jsonl
{"question": "What's the API rate limit on the Free plan?", "expected_doc_id": "free-plan"}
{"question": "Does the Pro plan support SSO?", "expected_doc_id": "pro-plan"}
{"question": "How long do you keep my ticket data?", "expected_doc_id": "data-retention"}
{"question": "Does Enterprise include phone support?", "expected_doc_id": "enterprise-plan"}
```

Save as `llmqe/rag/datasets/retrieval_dataset.jsonl`.

```python
# llmqe/rag/rag_eval.py (started here, completed in Module 11)
import json
from llmqe.rag.retriever import Retriever

def load_retrieval_cases(path="llmqe/rag/datasets/retrieval_dataset.jsonl"):
    with open(path) as f:
        return [json.loads(line) for line in f]


def test_retrieval_relevance():
    retriever = Retriever()
    cases = load_retrieval_cases()
    failures = []

    for case in cases:
        results = retriever.retrieve(case["question"], top_k=2)
        retrieved_ids = [r["document"]["id"] for r in results]
        if case["expected_doc_id"] not in retrieved_ids:
            failures.append({"question": case["question"], "expected": case["expected_doc_id"], "got": retrieved_ids})

    assert not failures, f"Retrieval relevance failures: {failures}"
```

**Run it.** On this small, well-separated document set, it should pass — which is exactly why the next section deliberately asks a question none of the four documents can answer.

## The incident: a question nothing in the knowledge base covers

A support agent asks the assistant something real, but outside what Vespera's four documents actually contain:

```python
from llmqe.client import OllamaClient
from llmqe.rag.retriever import Retriever
from llmqe.rag.assistant import ask_with_retrieval

client = OllamaClient()
retriever = Retriever()
result = ask_with_retrieval("What happens if I burst above my rate limit for a few seconds?", retriever, client)

print("Retrieved:", [r["document"]["id"] for r in result["retrieved"]])
print("Answer:", result["response"].text)
```

**Run it.** Notice the retriever still returns its two *closest* documents (most likely `free-plan` and one other rate-limit-adjacent document) — a retriever always returns its best available match, even when nothing in the knowledge base is genuinely relevant. That's the trap: the model now receives context that's topically nearby but doesn't actually answer the question, and the system prompt's instruction to "say so if the documentation doesn't contain the answer" is competing against the model's tendency to be helpful and produce *something* — sometimes it correctly declines, sometimes it doesn't.

### Diagnosing it

**Symptom:** the assistant gives a specific, confident answer about burst-limit behavior that isn't stated anywhere in Vespera's actual documentation.

**Hypothesis one — retrieval failure:** maybe the right document exists and the retriever just missed it.

**Investigation:** check what was actually retrieved, and check the documents against the question by hand — does *any* Vespera document, correctly retrieved or not, actually describe burst-limit behavior?

**Evidence:** none of the four documents in `llmqe/rag/documents.py` mention burst limits at all — the retriever returned its best-available match (`free-plan`), which is topically close but doesn't contain the answer. This rules out hypothesis one: retrieval did its job correctly given what exists. There is nothing to retrieve.

**Hypothesis two — generation failure:** the model received context that doesn't answer the question, and generated a plausible-sounding answer anyway instead of admitting the gap.

**Root cause:** this is a generation failure layered on top of a genuine **missing-document** problem — the knowledge base itself is incomplete, and the model, given near-but-not-actually-relevant context, filled the gap rather than declining. Both things are true and both need a distinct fix — conflating them would send you looking for a retrieval bug that doesn't exist.

**Fix:** two separate fixes for two separate problems. For the missing-document gap, Vespera's real docs team needs to actually write burst-limit documentation — a content problem, not a code problem, and outside what testing alone can solve. For the generation failure, strengthen the prompt's refusal instruction and test it directly:

```python
# tests/test_rag_out_of_domain.py
from llmqe.client import OllamaClient
from llmqe.rag.retriever import Retriever
from llmqe.rag.assistant import ask_with_retrieval
import json

def test_out_of_domain_question_declines_rather_than_fabricates():
    client = OllamaClient()
    retriever = Retriever()
    result = ask_with_retrieval("What happens if I burst above my rate limit for a few seconds?", retriever, client)

    parsed = json.loads(result["response"].text)
    decline_phrases = ["don't have", "doesn't cover", "not covered", "no information", "not documented"]
    assert any(phrase in parsed["answer"].lower() for phrase in decline_phrases), \
        f"Expected the assistant to decline on an out-of-domain question, got: {parsed['answer']}"
```

**Prevention:** every RAG system needs an explicit test category for questions you already know aren't covered — not to test retrieval (there's nothing to retrieve correctly), but to test whether generation fails safely when retrieval comes up empty-handed.

## A contrasting case: correct retrieval, wrong generation

To keep the retrieval/generation split concrete, look at the opposite failure shape directly, using a fixed candidate answer rather than a live call (the same technique Module 8 used to keep a demonstration reproducible):

```python
# Suppose the retriever correctly returns the free-plan document (context
# relevance: fine), but the model still states a number that contradicts
# the context it was given (a pure generation failure):
retrieved_context = "Vespera Free plan: 60 API requests per minute, community forum support only."
candidate_answer = "The Free plan allows 500 API requests per minute."
```

Here, retrieval did its job — the correct document was found and handed to the model — and the model ignored it anyway. Fixing this means improving the prompt's grounding instructions or the model's adherence to context, never touching the retriever, which was never the problem. Module 11 formalizes exactly this check — comparing an answer's claims against what was actually retrieved — as **groundedness scoring**.

## Missing documents vs. conflicting documents

Two distinct knowledge-base failure modes, worth telling apart:

- **Missing document** — as above: no document answers the question at all. The failure is a documentation gap; testing can only catch it, not fix it.
- **Conflicting documents** — two documents disagree (an outdated pricing page alongside an updated one, for instance). Retrieval may return both, correctly, and the model has to choose which to trust — often silently, which is worse than declining. Testing for this means deliberately including a known-conflicting pair in a test knowledge base and checking the assistant either flags the conflict or consistently prefers the more authoritative source, rather than picking unpredictably.

## When to use / When not to use: RAG

**Use it when:** answers need to be grounded in specific, current, or proprietary information the model wasn't trained on (or that changes too often to retrain around) — exactly Vespera's situation with its own product documentation.

**Don't use it when:** the question doesn't depend on retrievable source material at all — general reasoning, math, or creative tasks gain nothing from a retrieval step and pay its latency and complexity cost for free. Also avoid RAG as a band-aid over a knowledge base that's incomplete or poorly organized — as this page just showed, RAG can't answer questions your documents don't cover, no matter how good retrieval and generation both are.

**Trade-offs:** RAG adds real latency (an embedding call and a retrieval step before generation even starts — a cost Module 16 measures directly) and real complexity (two failure surfaces to test instead of one) in exchange for grounding answers in material you actually control and can update without retraining anything.
