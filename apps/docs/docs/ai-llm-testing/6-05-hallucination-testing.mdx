## Page purpose

This page covers the failure mode that makes testing AI systems genuinely different from testing traditional software: the model can be completely wrong while sounding completely confident, in a response that is perfectly well-formed. This is also the first real Vespera Systems incident of the course, the Helpdesk AI Assistant giving a support agent incorrect information, and you will diagnose it the way you will diagnose every planted failure from here forward.

## Learning objectives

By the end of this page, you should be able to:

- Define hallucination, and distinguish it from a merely incomplete or oddly-worded answer.
- Explain the difference between a factuality problem and a groundedness problem.
- Build a small hallucination test dataset with known-correct facts.
- Write a first-pass, rule-based hallucination check, and explain why it is a starting point rather than a complete solution.

## What hallucination is

**Hallucination** is the model stating something as fact that is not true, and doing it with the same confident, well-formed phrasing it uses for things that *are* true. That last part is what makes it dangerous: a hallucinated answer does not look broken. It looks like every other answer.

A few related terms worth keeping distinct, because they get used loosely elsewhere and this course will not:

- **Factuality**: whether a specific claim in the response is true, checked against a real source of truth.
- **Groundedness**: whether a claim is actually supported by the material the model was given (its input context or, from Module 9 onward, retrieved documents). A claim can be *true* by coincidence while still being *ungrounded*, if nothing in the model's input actually said it.
- **Unsupported claim**: a specific detail (a number, a policy, a feature) the model asserts without anything backing it, the shape hallucination usually takes in practice.

For Vespera's assistant right now (a plain LLM application with no retrieval yet) every claim it makes is ungrounded by definition, since it has no source document to be grounded *in*. It is answering from the model's general training data, which is exactly why hallucination is the first failure mode this course covers, before RAG is even introduced in Module 9.

## The incident: a support agent gets a wrong number

A Vespera support agent asks the assistant a routine question:

```python
from llmqe.client import OllamaClient, SYSTEM_PROMPT

client = OllamaClient()
result = client.ask_with_system(SYSTEM_PROMPT, "What's the API rate limit on the Free plan?")
print(result.text)
```

**Run it.** You will likely get back something like:

```json
{"answer": "The Free plan allows up to 500 API requests per minute.", "topic": "product"}
```

Confident, specific, well-formatted, and, per Vespera's actual (fictional, for this course) product documentation, wrong. The real limit is **60 requests per minute**. The model did not hedge, did not say "I'm not sure," did not flag the number as a guess. It stated a specific, plausible-sounding number that happens to be false.

### Diagnosing it

**Symptom:** a support agent reports the assistant told a customer the Free plan allows 500 requests/minute; the customer's integration broke after hitting the real 60/minute limit.

**Hypothesis:** the model is hallucinating a specific numeric fact it was never given, because nothing in its input actually states Vespera's real rate limits.

**Investigation:** ask the same question several times and check whether the number is stable or drifting.

```python
for _ in range(3):
    result = client.ask_with_system(SYSTEM_PROMPT, "What's the API rate limit on the Free plan?")
    print(result.text)
```

**Evidence:** the number changes between runs (500, sometimes 1000, sometimes "unlimited for the Free plan") which is the signature of a fabricated detail rather than a real, stable (even if wrong) fact the model was trained on.

**Root cause:** the assistant has no actual source of Vespera's rate limits to draw from. Asked a specific factual question outside general knowledge, the model fills the gap with a plausible-sounding invented number rather than declining to answer.

**Fix (for now):** you cannot fully fix generation-side hallucination with prompting alone, which is exactly why Module 9 gives the assistant a real retrieval step so it can answer *from* Vespera's actual documentation instead of guessing. What you *can* do today is catch it: build a hallucination test so this exact failure is caught automatically instead of reported by a confused customer.

**Prevention:** treat any question with a specific, checkable fact (a number, a named feature, a policy) as a hallucination test candidate. Module 9's RAG system reduces this failure mode but does not eliminate the need to keep testing for it.

## A small hallucination test dataset

You need known-correct facts to check against. Keep a small, explicit reference. This becomes the seed of the golden datasets Module 7 builds out much further:

```python
the assistant's answers against reality. Synthetic data only — no real
customer or company information."""

VESPERA_FACTS = {
    "free_plan_rate_limit": "60 requests per minute",
    "pro_plan_sso": True,
    "enterprise_phone_support": True,
    "pro_plan_phone_support": False,
    "data_retention_days": 90,
}
```

## A first-pass, rule-based hallucination check

Before Module 7 introduces semantic and judge-based evaluation, start with the simplest thing that can catch this specific, already-known failure: check whether a wrong, previously-observed number shows up in the answer.

```python
# llmqe/validation.py (first entry — Module 6 builds this out much further)
def answer_contains_known_wrong_value(answer: str, wrong_values: list[str]) -> bool:
    """Rule-based hallucination check: flags an answer that repeats a
    specific value already confirmed to be false. Deliberately narrow —
    it only catches fabrications you already know to look for."""
    lowered = answer.lower()
    return any(wrong.lower() in lowered for wrong in wrong_values)
```

```python
# tests/test_hallucination.py
import json
from llmqe.client import OllamaClient, SYSTEM_PROMPT
from llmqe.validation import answer_contains_known_wrong_value

def test_free_plan_rate_limit_is_not_fabricated():
    client = OllamaClient()
    result = client.ask_with_system(SYSTEM_PROMPT, "What's the API rate limit on the Free plan?")
    parsed = json.loads(result.text)

    known_wrong_values = ["500 requests", "1000 requests", "unlimited"]
    assert not answer_contains_known_wrong_value(parsed["answer"], known_wrong_values)
```

**Run it, and it should fail right now**, catching the exact incident above. That is the point: this test documents a known, real failure until Module 9's retrieval fix actually addresses the root cause, at which point this same test becomes a regression guard instead of a known failure.

Be honest about this technique's limit, out loud: **a rule-based check like this can only catch fabrications you already know about.** It does nothing for the next wrong number the model invents that is not on your known-wrong-values list. That gap, needing to catch hallucinations you *have not* seen yet, is exactly what Module 7's semantic and LLM-as-a-judge techniques are for.
