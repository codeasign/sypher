## What an AI Quality Engineer does differently

A traditional QE role tests software that behaves the same way every time you give it the same input. Click the same button twice, you get the same result twice — and when you don't, that's a bug. Most of testing as a discipline — regression suites, exact-match assertions, deterministic fixtures — is built on that assumption holding.

An AI Quality Engineer tests software where that assumption is false by design. Ask an LLM the same question twice and you can legitimately get two differently-worded answers, and sometimes two different *judgment calls* — without either one being a bug. The AI Quality Engineer's job is to build testing practices that still catch real problems — wrong answers, unsafe behavior, quality regressions, retrieval failures, slow responses — inside a system that is *supposed* to vary. That's a genuinely different skill from traditional QE, not a harder version of the same one, and it's what this entire course teaches.

## The distinction this course never lets blur

Read this twice, because the rest of the course assumes you have it:

> **"Using AI to improve testing" and "testing AI systems" are two different activities.**

Using AI to improve testing means pointing a model at your *existing* test suite — generating test cases, summarizing failures, drafting documentation. That's a legitimate, useful thing to do, and Module 15 covers it directly.

Testing AI systems means treating an AI-powered feature — an LLM call, a RAG pipeline, an agent — as the system under test, the same way you'd treat any other application component: something with inputs, outputs, failure modes, and a quality bar it has to clear before it ships.

This course is almost entirely the second one. Every module from 1 through 14 and 16 through 25 is about testing AI systems. Only Module 15 is about using AI to help you test — and it explicitly draws the line back to this distinction when it gets there, precisely because it's the one module where it would be easy to blur the two.

## The loop this course runs on

Every module in this course — from the first Ollama call in Module 0 to the CI-gated regression suite in Module 19 — repeats the same seven-step loop, at increasing depth:

**Build → Run → Observe → Fail → Diagnose → Improve → Automate.**

You build something small, run it against a real model, observe what actually came back (not what you assumed would come back), hit a realistic failure, diagnose it using evidence rather than guessing, improve the implementation, and — later in the course — automate the whole check so a human doesn't have to repeat it by hand. Module 0 walks this loop once, lightly, just to prove your environment works. By Module 19, the same loop is running unattended inside a CI pipeline.

## Vespera Systems

Every module's hands-on work happens inside one continuous story at a fictional company called **Vespera Systems**. Vespera runs a support ticketing platform, and its support team has just been given an internal tool: the **Helpdesk AI Assistant** — an LLM-powered assistant that helps human support agents answer product questions faster. It is not customer-facing, and it doesn't take actions on its own; it's a research aid sitting next to the ticket queue.

You are the QA/SDET Vespera has asked to own quality for this assistant. Across the course, you'll watch it go wrong in the ways real AI features actually go wrong: it gives an agent confidently incorrect information, its knowledge lookup retrieves the wrong document, a prompt tweak quietly makes it worse, a model upgrade shifts its behavior, its evaluation scores wobble between runs for no code-level reason, a safety test catches it following an instruction it should have refused, its response times climb once retrieval is added, and eventually a CI gate blocks a release over a real regression. Each of those isn't a plot device — it's the failure a specific module teaches you to catch.

## What you're building: the LLM Quality & Evaluation Framework

Starting in Module 0 and finishing in Module 21, you build one real project across 15 milestones: the **LLM Quality & Evaluation Framework** — a working toolkit that runs a local model, validates its output, scores it against golden datasets, evaluates RAG retrieval separately from generation, runs safety and reliability checks, compares against a baseline to catch regressions, reports results in a human-readable form, and gates a CI pipeline on all of it. You never get it handed to you complete — each module adds one real, working piece to the same project, and Modules 20-21 refactor it with the judgment of an engineer who's actually used it, not a fresh rewrite.

By Module 24, this framework is the centerpiece of your portfolio, and you'll practice explaining and defending the decisions behind it the way you would in a real interview.
