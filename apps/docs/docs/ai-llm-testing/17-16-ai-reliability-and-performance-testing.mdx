## Page purpose

Every test so far has asked one question: was the answer right? This page asks a completely different one: was it fast enough, reliable enough, and cheap enough to actually run in production? Vespera's assistant can be correct on every case in Module 11's evaluation suite and still fail this page's tests — that gap is the whole point of the **Functional Quality vs. Operational Quality** distinction this page teaches, using a real latency regression the RAG pipeline introduced.

## Learning objectives

By the end of this page, you should be able to:

- Explain Functional Quality vs. Operational Quality, and give an example of a system that's fine on one and fails the other.
- Measure and assert on latency for both the plain assistant and the RAG-backed one.
- Diagnose a performance regression using evidence, not assumption.
- Explain why retries are the wrong fix for some failures, even though they fix others.

## Functional Quality vs. Operational Quality

**Functional Quality** — does it produce the right answer? Everything from Module 3 through Module 12 tests this: validation, evaluation, groundedness, safety.

**Operational Quality** — does it run acceptably in production? Latency, reliability under load, resource consumption, error handling. A model can produce a perfect answer and still fail here — if it takes 12 seconds to arrive, a support agent has already given up and answered from memory instead.

These are genuinely independent axes. Vespera's RAG-backed assistant, by the end of Module 11, was functionally solid — grounded answers, honest citations, safe refusals. This page shows it can still fail operationally, for a reason that has nothing to do with any of that.

## Measuring latency

```python
# llmqe/reliability/perf_tests.py
import time
from llmqe.client import OllamaClient
from llmqe.rag.retriever import Retriever
from llmqe.rag.assistant import ask_with_retrieval, RAG_SYSTEM_PROMPT

def measure_latency(fn, *args, **kwargs) -> tuple[float, object]:
    start = time.time()
    result = fn(*args, **kwargs)
    return time.time() - start, result


def test_plain_call_latency():
    client = OllamaClient()
    latency, _ = measure_latency(client.ask_with_system, RAG_SYSTEM_PROMPT, "Does the Pro plan support SSO?")
    print(f"Plain call latency: {latency:.2f}s")
    assert latency < 3.0, f"Plain call took {latency:.2f}s, expected under 3s"
```

**Run it** to get a real baseline number on your own hardware — this course can't tell you your exact latency, since it depends entirely on your machine, but the *pattern* below holds regardless of the absolute numbers.

## The incident: RAG latency far exceeds the plain call

```python
def test_rag_call_latency():
    client = OllamaClient()

    def ask():
        retriever = Retriever()  # constructed fresh, right here
        return ask_with_retrieval("Does the Pro plan support SSO?", retriever, client)

    latency, _ = measure_latency(ask)
    print(f"RAG call latency: {latency:.2f}s")
    assert latency < 3.0, f"RAG call took {latency:.2f}s, expected under 3s"
```

**Run it.** This fails — and not by a small margin. A single extra retrieval step (one query embedding, a handful of cosine similarity comparisons) shouldn't add anywhere near this much time.

### Diagnosing it

**Symptom:** the RAG-backed call is dramatically slower than the plain call — far more than "one extra embedding lookup" should cost.

**Hypothesis:** something more expensive than a single query embedding is happening on every call.

**Investigation:** time the two pieces of `ask()` separately — constructing the `Retriever` versus calling `.retrieve()` on an already-built one.

```python
latency, retriever = measure_latency(Retriever)
print(f"Retriever() construction: {latency:.2f}s")

latency, _ = measure_latency(retriever.retrieve, "Does the Pro plan support SSO?")
print(f"retriever.retrieve(): {latency:.2f}s")
```

**Evidence:** constructing `Retriever()` is where nearly all the time goes — recall from Module 9 that `Retriever.__init__` embeds every document in the knowledge base up front. `retrieve()` itself, given an already-built retriever, is fast.

**Root cause:** `test_rag_call_latency`'s `ask()` function builds a brand-new `Retriever()` — re-embedding the entire document set — on every single call, instead of reusing one already-built instance. This isn't a flaw in `Retriever` itself (pre-computing embeddings once, at construction, is the right design); it's a caller building it in the wrong place, repeatedly, when it should be built once and reused.

**Fix:** build the retriever once, outside the per-request path, and reuse it:

```python
def test_rag_call_latency_fixed():
    client = OllamaClient()
    retriever = Retriever()  # built once, reused across every call

    latency, _ = measure_latency(ask_with_retrieval, "Does the Pro plan support SSO?", retriever, client)
    print(f"RAG call latency (retriever reused): {latency:.2f}s")
    assert latency < 3.0, f"RAG call took {latency:.2f}s, expected under 3s"
```

**Run it.** Latency should now land close to the plain call's, plus a small, genuine cost for one query embedding and retrieval — the real, acceptable overhead RAG actually adds, once the accidental re-embedding is gone.

**Prevention:** this exact bug — expensive setup work repeated per-request instead of done once and reused — is common enough in real systems that it's worth a permanent perf test, not a one-time fix: `test_rag_call_latency` (corrected) stays in the suite going forward specifically to catch a future reintroduction of this mistake.

## Reliability: timeouts, retries, and failure classification

Not every failure is a wrong answer — a request can also time out, error, or simply take longer than acceptable. Classify these distinctly rather than lumping every non-pass result into one bucket:

```python
# llmqe/reliability/perf_tests.py (continued)
from enum import Enum

class FailureCategory(Enum):
    TIMEOUT = "timeout"
    ERROR = "error"
    SLOW = "slow"          # succeeded, but past the latency budget
    WRONG_ANSWER = "wrong_answer"  # a Module 6-8 evaluation failure, not this module's concern


def classify_call(fn, *args, timeout_seconds: float = 5.0, latency_budget: float = 3.0, **kwargs) -> dict:
    start = time.time()
    try:
        result = fn(*args, **kwargs)
    except Exception as e:
        return {"category": FailureCategory.ERROR, "detail": str(e)}

    latency = time.time() - start
    if latency > timeout_seconds:
        return {"category": FailureCategory.TIMEOUT, "latency": latency}
    if latency > latency_budget:
        return {"category": FailureCategory.SLOW, "latency": latency}
    return {"category": None, "latency": latency, "result": result}
```

A **retry** re-attempts a failed call, usually with backoff between attempts:

```python
def call_with_retry(fn, *args, max_attempts: int = 3, **kwargs):
    last_error = None
    for attempt in range(max_attempts):
        try:
            return fn(*args, **kwargs)
        except Exception as e:
            last_error = e
            time.sleep(2 ** attempt)  # exponential backoff
    raise last_error
```

## When to use / When not to use: retries

**Use them when:** the failure is transient and infrastructure-level — a dropped connection, a momentary server overload, a timeout under unusual load. These are exactly the cases where the same call, tried again a moment later, is likely to succeed.

**Don't use them when:** the failure is about the *content* of the response, not whether the call completed — retrying a hallucinated answer just gets you another generation from the same model, with no reason to expect a better one, and a safety-test failure (Module 12) should never be silently retried until it happens to pass, since that's not fixing the problem, it's hiding it from the test report.

**Trade-offs:** retries improve apparent reliability for transient infrastructure issues, at the cost of slower failure reporting (three attempts take three times as long to finally fail) and, if misapplied to content failures, a false sense that the system is more correct than it actually is. Keep `call_with_retry` scoped to `FailureCategory.TIMEOUT` and `FailureCategory.ERROR` — never `WRONG_ANSWER`.

## Throughput and concurrent requests

A single-request latency test doesn't tell you what happens when several support agents ask questions at once:

```python
from concurrent.futures import ThreadPoolExecutor

def test_concurrent_requests_succeed():
    client = OllamaClient()
    retriever = Retriever()
    questions = ["Does the Pro plan support SSO?"] * 5

    with ThreadPoolExecutor(max_workers=5) as pool:
        futures = [pool.submit(ask_with_retrieval, q, retriever, client) for q in questions]
        results = [f.result() for f in futures]

    assert len(results) == 5
```

**Run it.** On a single local Ollama instance, expect this to be noticeably slower per-request than one call in isolation — local inference typically has limited real parallelism, which is a genuine operational constraint worth knowing about before assuming a local setup like this course's tells you anything about production scaling behavior.
