## Page purpose

Every module since 2 has called `ollama.chat()` through `OllamaClient`, with Ollama's own package imported directly. This page adds one small, deliberately narrow boundary so that could change — not because Vespera is actually switching providers this week, but because "what if it does" is a real enough question to answer cheaply now, while it's still cheap. This completes Milestone 15 alongside Module 20's refactor.

## Learning objectives

By the end of this page, you should be able to:

- Explain what problem a provider boundary solves and what it costs.
- Implement a small `LLMProvider` protocol and prove swappability with a second, real implementation.
- Apply Problem → Constraints → Options → Trade-offs → Decision → Implementation → Consequences to a real abstraction decision in your own code.
- Explain when this kind of abstraction would be unnecessary, tying back to Module 20's over-engineering warning.

## The decision, worked through explicitly

**Problem.** `OllamaClient` (Module 2) imports `from ollama import chat` directly and calls it inline. If Vespera ever needed to run the same framework against a different model runtime — a different local tool, or a hosted API for a heavier evaluation judge — every call site that touches `OllamaClient` internals would need to change, and worse, tests could no longer substitute a fake response without a real Ollama server running.

**Constraints.** The framework has 19 modules of existing code calling `OllamaClient.ask()` and `.ask_with_system()` — any change has to preserve that public interface, or this refactor breaks everything built so far instead of improving it. It also shouldn't add meaningful complexity for a swap that isn't actually happening yet.

**Options considered:**
1. Do nothing — leave `ollama.chat()` called directly; accept that a future provider swap means editing every call site.
2. A minimal `LLMProvider` protocol with one method, injected into `OllamaClient`.
3. A full pluggable-provider framework — provider registry, configuration-driven provider selection, multiple providers active simultaneously.

**Trade-offs.** Option 1 costs nothing now and a real rewrite later. Option 3 solves a problem nobody has yet, at real cost to readability — exactly the over-engineering trap Module 20 named explicitly, applied here to a different part of the codebase. Option 2 costs one small file and one constructor argument, in exchange for a swap point that's real without being speculative machinery.

**Decision.** Option 2 — a minimal provider boundary, nothing more.

## Implementation

```python
# llmqe/providers/base.py
from typing import Protocol

class LLMProvider(Protocol):
    def complete(self, system_prompt: str, user_prompt: str) -> str:
        """Return the raw text completion for a system/user prompt pair."""
        ...
```

```python
# llmqe/providers/ollama_provider.py
from ollama import chat
from llmqe.config import CONFIG

class OllamaProvider:
    def __init__(self, model: str = CONFIG.model, temperature: float = CONFIG.temperature, seed: int | None = CONFIG.seed):
        self.model = model
        self.temperature = temperature
        self.seed = seed

    def complete(self, system_prompt: str, user_prompt: str) -> str:
        response = chat(
            model=self.model,
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": user_prompt},
            ],
            options={"temperature": self.temperature, "seed": self.seed},
        )
        return response.message.content
```

`OllamaClient`'s public interface — the thing every module from 2 through 20 has been calling — doesn't change at all. Internally, it now delegates to a provider instead of calling `ollama.chat()` directly:

```python
# llmqe/client.py (refactored)
from dataclasses import dataclass
from llmqe.providers.base import LLMProvider
from llmqe.providers.ollama_provider import OllamaProvider


@dataclass
class LLMResponse:
    text: str
    model: str
    temperature: float
    seed: int | None


class OllamaClient:
    def __init__(self, provider: LLMProvider | None = None, model: str = "llama3.2:3b",
                 temperature: float = 0, seed: int | None = 42):
        self.model = model
        self.temperature = temperature
        self.seed = seed
        self._provider = provider or OllamaProvider(model, temperature, seed)

    def ask(self, prompt: str) -> LLMResponse:
        return self.ask_with_system("", prompt)

    def ask_with_system(self, system_prompt: str, user_prompt: str) -> LLMResponse:
        text = self._provider.complete(system_prompt, user_prompt)
        return LLMResponse(text=text, model=self.model, temperature=self.temperature, seed=self.seed)
```

Every existing test — Module 3's `test_smoke.py`, Module 5's `test_hallucination.py`, all of it — keeps working unchanged, because `OllamaClient()` with no arguments still defaults to a real `OllamaProvider`.

## Proving swappability, not just claiming it

A provider boundary that's never actually exercised with a second provider is an unverified claim, the same category of problem Module 8 wouldn't accept for an evaluator. Prove it with a real second implementation — a fast, deterministic test double:

```python
# llmqe/providers/recorded_provider.py
class RecordedProvider:
    """Replays a fixed response instead of calling a model. Useful for
    testing calling code's behavior without depending on a live model."""

    def __init__(self, response_text: str):
        self._response_text = response_text

    def complete(self, system_prompt: str, user_prompt: str) -> str:
        return self._response_text
```

```python
# Now genuinely swappable — no Ollama server needed for this test:
from llmqe.client import OllamaClient
from llmqe.providers.recorded_provider import RecordedProvider

def test_validate_response_handles_malformed_json():
    fake_provider = RecordedProvider(response_text="not valid json at all")
    client = OllamaClient(provider=fake_provider)
    result = client.ask_with_system("system", "does the pro plan support sso?")

    from llmqe.validation import validate_response
    errors = validate_response(result.text)
    assert errors == ["response is not valid JSON"]
```

**Run it.** This test runs instantly, with no Ollama server required at all — it's testing `validate_response()`'s handling of malformed JSON, not the model, and the provider boundary is what makes that isolation possible.

## When to use / When not to use: this kind of abstraction

**Use it when:** you have a real, concrete reason to expect the concrete implementation might need to change or be substituted — a genuine second consumer (like `RecordedProvider` above, needed for fast, model-free tests) is the clearest signal an abstraction is pulling its weight, not just decorating the code.

**Don't use it when:** there's no second implementation on the horizon and no test that benefits from swapping one in — an interface with exactly one implementation, forever, is indirection with no payoff, and Module 20's warning against a plugin system for `score_case()`'s four stages was exactly this same judgment call, applied there instead of here.

**Trade-offs.** `LLMProvider` adds one file, one constructor parameter, and one extra layer to trace through when reading `OllamaClient.ask_with_system()` for the first time. In exchange, it made `test_validate_response_handles_malformed_json()`'s fast, server-free test possible, and it means a genuine future provider swap touches `ollama_provider.py` and nothing else — a real, demonstrated benefit, not a speculative one, which is exactly the bar Module 20 set for when abstraction earns its place.

## Consequences

The framework now has a real seam between "code that decides what to ask" and "code that knows how to reach a specific model runtime" — visible in exactly one place (`OllamaClient.__init__`'s `provider` parameter) rather than scattered. Nothing about this decision was free: every new contributor reading `client.py` for the first time now has one more file (`providers/base.py`) to open to understand the full picture. That's the honest cost of the decision made here, paid once, for a benefit (fast tests, a real swap point) that showed up immediately in this same module rather than as a promise about the future.

`llmqe/providers/base.py`, `ollama_provider.py`, and `recorded_provider.py`, plus the refactored `client.py`, complete Milestone 15 — the framework is now refactored and documented with real engineering judgment: two targeted improvements (Module 20's config and evaluator split, this module's provider boundary), each justified by a concrete problem already visible in the code, and each explicitly bounded against becoming more than the problem warranted.
