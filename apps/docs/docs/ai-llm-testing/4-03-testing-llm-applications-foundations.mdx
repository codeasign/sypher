## Page purpose

This page writes the first real test in the LLM Quality & Evaluation Framework, and immediately runs into the central question of this entire course: what does "the test passed" mean when the thing under test is allowed to word its answer differently every time? You will give Vespera's Helpdesk AI Assistant a structured output contract, write a test against it, watch that test flake for a completely predictable reason, and fix it properly.

## Learning objectives

By the end of this page, you should be able to:

- Explain the difference between prompt testing and output validation.
- Give the model a small structured-output contract and validate it parses correctly.
- Explain why exact-match assertions fail against free-text LLM output, using your own flaky test as the example.
- Define "test oracle" for a non-deterministic system, and say what an LLM test can and can't assert with certainty.

## A structured contract for the assistant

So far, Vespera's Helpdesk AI Assistant has returned whatever plain text the model felt like producing. That is fine for a human reading it, but it is nothing a test can reliably check. Give it a small contract instead: a system prompt that constrains the *shape* of the response, even though the *wording* inside that shape still varies:

```python
SYSTEM_PROMPT = """\
You are Vespera Helpdesk's internal product assistant, used by support \
agents to answer product questions quickly.

Respond with JSON only, using exactly these two fields:
- "answer": a plain-language answer to the agent's question, 1-3 sentences.
- "topic": exactly one of "billing", "security", "product", or "other" — \
whichever best classifies the question.

No extra fields. No prose outside the JSON.
"""
```

Update `OllamaClient` to accept a system prompt:

```python
# llmqe/client.py (excerpt — add alongside the existing ask())
def ask_with_system(self, system_prompt: str, user_prompt: str) -> LLMResponse:
    response = chat(
        model=self.model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt},
        ],
        options={"temperature": self.temperature, "seed": self.seed},
    )
    return LLMResponse(
        text=response.message.content,
        model=self.model,
        temperature=self.temperature,
        seed=self.seed,
    )
```

Try it:

```python
from llmqe.client import OllamaClient

client = OllamaClient()
result = client.ask_with_system(SYSTEM_PROMPT, "Does the Pro plan support SSO?")
print(result.text)
```

**Run it.** You should get back something like:

```json
{"answer": "Yes, the Pro plan includes single sign-on (SSO) support for enterprise identity providers.", "topic": "security"}
```

### Explaining the result

The wording of `"answer"` is still the model's own free-text generation: it can and will vary between runs. But `"topic"` is now a constrained field with exactly four legal values, and the overall response is now something a program can `json.loads()` instead of only a human reading prose. That split, a field you can test exactly and a field you can only test loosely, is the seed of everything Modules 6 through 8 build out in depth.

## Prompt testing vs. output validation

These sound similar and get run together constantly, but they are answering two different questions:

**Prompt testing** asks a narrow, mechanical question: *given this input, does the feature reliably return the shape the rest of the application depends on?* Does it parse as JSON? Are exactly `"answer"` and `"topic"` present? Is `"topic"` one of the four allowed values? None of this looks at whether the *content* is any good.

**Output validation** asks the harder question: *given a shape that parses correctly, is the content trustworthy?* A response can pass every prompt test and still be confidently wrong: valid JSON, a legal `"topic"` value, and an `"answer"` that states something false. Modules 5 through 8 are entirely about output validation; this page stops at prompt testing.

## Writing the first test, and watching it flake

Here is a natural first attempt, testing both levels at once:

```python
# tests/test_smoke.py
import json
from llmqe.client import OllamaClient, SYSTEM_PROMPT  # SYSTEM_PROMPT moved to client.py

client = OllamaClient()

def test_sso_question_returns_valid_shape():
    result = client.ask_with_system(SYSTEM_PROMPT, "Does the Pro plan support SSO?")
    parsed = json.loads(result.text)  # fails the test if this isn't valid JSON

    assert set(parsed.keys()) == {"answer", "topic"}
    assert parsed["topic"] in {"billing", "security", "product", "other"}
    assert parsed["answer"] == "Yes, the Pro plan includes single sign-on (SSO) support for enterprise identity providers."
```

**Run it with `pytest` a few times in a row:**

```bash
pytest tests/test_smoke.py -v
```

The shape assertions (`set(parsed.keys())`, the `topic` check) pass reliably. The last line, the exact-match assertion on `"answer"`, passes sometimes and fails other times, even with `temperature=0` and a fixed `seed`, because small wording differences (a rephrased clause, a dropped "the") are common enough in practice that you should not rely on byte-for-byte stability.

## Diagnosing the flake

**Symptom:** `test_sso_question_returns_valid_shape` fails intermittently, always on the same line, with a wording mismatch you can see is *basically correct* when you read it.

**Hypothesis:** the test is asserting exact equality on a field that is inherently free-text, treating it like a deterministic function's return value.

**Investigation:** print the failing value next to the expected one across a few runs.

```python
print(repr(parsed["answer"]))
```

**Evidence:** the actual answers are all factually consistent and reasonably worded ("Yes, SSO is supported on the Pro plan for enterprise identity providers," "Yes, Pro plan customers get SSO support"), none of them wrong, all of them different strings.

**Root cause:** `assert parsed["answer"] == "<exact string>"` is the wrong assertion style for a field the system prompt never promised would be stable: only the *shape* was promised, not the *wording*.

**Fix:** assert on the property that actually matters, that the answer correctly conveys "yes" and mentions SSO, not the exact string:

```python
def test_sso_question_returns_valid_shape():
    result = client.ask_with_system(SYSTEM_PROMPT, "Does the Pro plan support SSO?")
    parsed = json.loads(result.text)

    assert set(parsed.keys()) == {"answer", "topic"}
    assert parsed["topic"] in {"billing", "security", "product", "other"}
    assert "sso" in parsed["answer"].lower() or "single sign-on" in parsed["answer"].lower()
    assert parsed["answer"].lower().startswith("yes") or "yes," in parsed["answer"].lower()
```

**Prevention:** before writing any assertion against LLM output, ask which category the field falls into: *constrained* (exact-match is fine) or *generative* (assert on a property, never on the literal string). You will apply this same split to every evaluation technique from Module 6 onward.

## The test oracle problem

A **test oracle** is whatever a test uses to decide pass or fail. For deterministic code, the oracle is usually "the one correct value." For LLM output, there often is not one correct value: there is a *set of acceptable outputs*, and the oracle has to describe that set instead of naming a single member of it. `"topic" in {"billing", "security", "product", "other"}` is a real oracle, a small, exact set. `"sso" in answer.lower()` is also a real oracle, a property every acceptable answer must have, even though it does not pin down the wording. Neither oracle is weaker than the other; they are just suited to different kinds of fields. Confusing the two (demanding exact-match on a generative field, or accepting anything at all on a constrained one) is where most LLM test suites go wrong before they have even gotten to the harder evaluation questions in Module 6.

## Building the framework: Milestone 4

`tests/test_smoke.py`, in its corrected form above, is Milestone 4: the framework's first real LLM test. It is deliberately small (one input, one shape check, one property-based content check) because Module 6 is where response validation gets formalized into something reusable across many inputs, not one hardcoded question.
