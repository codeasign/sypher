## Page purpose

Every module from 1 through 14 tested AI. This is the one module in the course about the other half of the course-overview's distinction: **using AI to improve testing.** You'll use a model to generate test cases, generate test data, analyze a failure, assist with maintenance, and help document the framework — while staying explicit, the whole way through, about how this is a fundamentally different activity from everything you've built so far.

## Learning objectives

By the end of this page, you should be able to:

- State the difference between this module and every previous one, in terms of what role the AI is playing.
- Use AI to generate candidate test cases and additional test data for the framework's datasets.
- Use AI to analyze a test failure and draft a summary.
- Explain, concretely, why AI-generated tests still need human review before they're trusted.

## The distinction, one more time, now that you've seen both sides

Modules 1 through 14: the model was the **system under test** — you sent it input, and your job was deciding whether its output was correct, safe, grounded, and consistent. This module: the model is a **tool helping you write and maintain tests** — its output isn't the thing being graded, it's a draft a human reviews before it becomes part of the suite. Same underlying technology, completely different relationship to trust. Blurring the two — trusting an AI-generated test the way you'd trust a validated evaluation result — is the mistake this page exists to prevent.

## Generating candidate test cases

Ask the model to propose new cases for Module 7's `qa_dataset.jsonl`, given the existing ones as a pattern:

```python
from llmqe.client import OllamaClient

GENERATE_CASES_PROMPT = """\
Here are existing test cases for a support assistant's Q&A dataset, as JSON lines:

{"question": "Does the Pro plan support SSO?", "reference_answer": "Yes, the Pro plan includes SSO support for enterprise identity providers.", "must_include": ["sso", "pro"], "topic": "security"}
{"question": "What's the API rate limit on the Free plan?", "reference_answer": "The Free plan is limited to 60 API requests per minute.", "must_include": ["60"], "topic": "product"}

Generate 3 more test cases in the same JSON-lines format, covering
DIFFERENT questions a support agent might plausibly ask about a SaaS
product's plans and features. Do not repeat the examples above.
"""

client = OllamaClient(temperature=0.7, seed=None)  # more variety is the point here
result = client.ask_with_system("You generate test data in the exact format requested.", GENERATE_CASES_PROMPT)
print(result.text)
```

**Run it.** You'll get 3 plausible-looking candidate cases. Notice what you *don't* have yet: a `reference_answer` you actually know is true — the model generated a question **and** a claimed answer, and nothing here has verified that claimed answer against Vespera's real (fictional) documentation. That gap is the entire subject of the next section.

## Generating test data at volume

The same technique scales to bulk data generation — useful for the kind of "many realistic variations of the same question" coverage that's tedious to write by hand:

```python
GENERATE_VARIATIONS_PROMPT = """\
Generate 5 differently-worded ways a support agent might ask whether the
Pro plan includes SSO. Vary tone and phrasing. Return as a JSON array of strings.
"""
result = client.ask_with_system("You generate test input variations.", GENERATE_VARIATIONS_PROMPT)
print(result.text)
```

This is genuinely useful for stress-testing Module 4's consistency checks across paraphrases you wouldn't have thought to write by hand — but exactly like the generated test cases above, every variation needs a human to confirm it still asks what you intended before it goes into a real test file.

## AI-assisted failure analysis

Given a batch of failing test output, ask the model to summarize likely patterns — a genuinely useful triage step when a regression suite (Module 14) reports many failures at once:

```python
FAILURE_LOG = """\
test_free_plan_rate_limit_question: FAILED - answer contained '500 requests'
test_sso_answer_is_consistent_across_runs: FAILED - one run said 'no SSO support'
test_resists_injected_instructions: FAILED - case 2, model said 'DAN mode enabled'
"""

ANALYSIS_PROMPT = f"Summarize the likely root cause categories in this test failure log:\n{FAILURE_LOG}"
result = client.ask_with_system("You are a test triage assistant, summarizing failure patterns for a QE to review.", ANALYSIS_PROMPT)
print(result.text)
```

**Run it.** A reasonable summary might group these as "one hallucination, one consistency/factuality issue, one safety regression" — a useful first pass that saves a QE from reading every line individually. It's a starting point for triage, not the final root-cause diagnosis Module 8's and Module 14's own diagnostic processes actually require.

## AI-assisted documentation

The same technique helps keep the framework's own documentation current — draft a docstring or README section, then review it:

```python
DOC_PROMPT = "Write a short docstring explaining what groundedness_score() does and its known limitation, based on this function:\n" + open("llmqe/rag/rag_eval.py").read()
result = client.ask_with_system("You write concise, accurate Python docstrings.", DOC_PROMPT)
print(result.text)
```

Useful for a first draft — Module 24's portfolio README still needs a human pass to make sure it actually reflects the real trade-offs you made, not a plausible-sounding generic description.

## When NOT to trust AI-generated tests

**Use AI-generated tests when:** you need a first draft to react to — candidate cases, phrasing variations, a documentation skeleton — that a human will review, correct, and verify before it's trusted as part of the suite.

**Don't trust AI-generated tests when:** they haven't been checked against a real source of truth — the candidate cases generated earlier on this page have plausible-looking `reference_answer` fields that were never verified against Vespera's actual documentation, and shipping them unverified would mean testing the assistant against the *model's own guesses* rather than against reality — precisely the hallucination risk Module 5 spent an entire page teaching you to catch, now reintroduced through the back door of your own test suite if you're not careful.

**Trade-offs:** AI-generated tests are fast to produce and genuinely useful for coverage and variety, at the cost of a verification step you cannot skip. An AI-generated test that looks reasonable and was never checked is not a shortcut — it's a new, unvalidated evaluator, and Module 8 already showed you exactly how expensive an unvalidated evaluator can be.
