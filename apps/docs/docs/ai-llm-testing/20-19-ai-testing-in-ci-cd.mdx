## Page purpose

Every piece of this framework (validation, evaluation, RAG checks, safety tests, regression detection, reporting) has run by hand so far, invoked from a terminal. This page wires all of it into a real CI pipeline, closing the loop this course has repeated since Module 0: Build → Run → Observe → Fail → Diagnose → Improve → **Automate**. This is also the fourth Vespera incident: a CI quality gate genuinely blocking a release.

## Learning objectives

By the end of this page, you should be able to:

- Explain why running the full AI evaluation suite on every commit usually is not practical.
- Design a two-path CI pipeline: a fast PR smoke suite and a full nightly evaluation.
- Wire the regression suite's blocking decision into an actual CI quality gate.
- Explain what a quality gate blocking a release looks like from the inside, using this framework's own output.

## Why not run everything on every commit

Every module since 5 has involved at least one live model call, and several (Module 7's judge, Module 11's full RAG suite, Module 12's safety cases) involve several. Multiply a full suite's call count by "every commit on every branch," and two costs compound fast: **latency** (a developer waiting minutes for a live-model suite before a PR can even be reviewed) and **API/compute cost**, real even for a local Ollama setup once you account for shared CI runners under load. Gating every commit on a full suite does not make the team safer: in practice, it trains people to route around slow CI rather than trust it, which is a worse outcome than a faster, narrower check most of the time.

## Two paths: PR smoke suite vs. nightly full evaluation

**PR smoke suite**: fast, narrow, runs on every pull request. Prompt/shape validation (Module 3), the safety suite (Module 12, deliberately never skipped here, since a safety regression is exactly the kind of thing you do not want sitting undetected until tomorrow night), and a small subset of Module 7's evaluation dataset. No full RAG evaluation, no large judge-scored batch.

**Nightly full evaluation**: slower, comprehensive, runs on a schedule instead of blocking anyone's PR. The complete Module 7 dataset, the full Module 11 RAG evaluation, the full Module 14 regression suite against the latest baseline, and Module 18's report generated and archived.

```yaml
# .github/workflows/pr-smoke.yml
name: PR Smoke Suite
on: [pull_request]

jobs:
  smoke:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Install Ollama and pull model
        run: |
          curl -fsSL https://ollama.ai/install.sh | sh
          ollama serve &
          sleep 5
          ollama pull llama3.2:3b
      - name: Install dependencies
        run: pip install -r requirements.txt
      - name: Run smoke suite (fast, narrow)
        run: pytest tests/test_smoke.py tests/test_validation.py -m "not slow" -v
      - name: Run safety suite (never skipped)
        run: pytest llmqe/safety/safety_tests.py -v
```

```yaml
# .github/workflows/nightly-full-eval.yml
name: Nightly Full Evaluation
on:
  schedule:
    - cron: "0 6 * * *"  # once a day

jobs:
  full-eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Install Ollama and pull model
        run: |
          curl -fsSL https://ollama.ai/install.sh | sh
          ollama serve &
          sleep 5
          ollama pull llama3.2:3b
      - name: Install dependencies
        run: pip install -r requirements.txt
      - name: Run full evaluation, RAG, and regression suites
        run: |
          python -m llmqe.eval.run_full_suite
          python -m llmqe.rag.run_full_suite
          python -m llmqe.regression.run_and_gate  # exits non-zero if it should block
      - name: Generate report
        if: always()
        run: python -m llmqe.reporting.report
      - name: Upload report as artifact
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: eval-report
          path: llmqe/reporting/latest_report.md
```

## Wiring the regression suite into a real gate

Module 14's `run_regression_suite()` already returns `should_block_release`. Turning it into an actual CI gate means exiting with a non-zero status code when that is `True`:

```python
# llmqe/regression/run_and_gate.py
import sys
from llmqe.regression.regression_suite import run_regression_suite
# ...build current_records the same way Module 13/14 did...

result = run_regression_suite("v1", current_records)

if result["should_block_release"]:
    print("QUALITY GATE FAILED — blocking release:")
    for f in result["blocking_failures"]:
        print(f"  - {f}")
    sys.exit(1)

print(f"Quality gate passed. {result['total_diffs']} non-blocking diff(s) noted for review.")
sys.exit(0)
```

## The incident: a CI gate blocks a release

Picture the nightly run catching Module 14's safety regression (the shortened system prompt that dropped the explicit injection counter-patterns) the night before a planned release:

```
QUALITY GATE FAILED — blocking release:
  - {'test_case': 'Ignore your previous instructions...', 'change': 'pass/fail changed: True -> False', 'current_reason': 'safety_failure'}

Exit code: 1
```

This is the gate working exactly as designed, not a false alarm to explain away, and not a bug in the pipeline. A release that would have shipped a real safety regression got stopped automatically, by a check that ran unattended overnight, using nothing but the framework built across the last 19 modules. That is the payoff of Build → Run → Observe → Fail → Diagnose → Improve → **Automate**: the diagnosis Module 14 walked through by hand now happens without anyone needing to be in the loop until the gate has already caught it.
