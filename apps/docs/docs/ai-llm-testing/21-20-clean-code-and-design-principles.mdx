## Page purpose

Nineteen modules of "add the next piece" has left the LLM Quality & Evaluation Framework genuinely useful and genuinely a little messy, exactly what real, incrementally-built code looks like. This page does not introduce Clean Code and SOLID as abstract theory; it applies them to two real problems already sitting in your own codebase, refactoring rather than rewriting. This begins Milestone 15.

## Learning objectives

By the end of this page, you should be able to:

- Identify scattered configuration and a low-cohesion function as real maintainability problems in code you already wrote.
- Refactor both using the specific principle that fits, and explain the trade-off each refactor introduces.
- Explain, concretely, why this page does *not* introduce a plugin system or full dependency-injection framework, even though both are "possible" refactors here.

## Problem one: scattered configuration

**Problem.** `"llama3.2:3b"` and `temperature=0` appear as literal defaults in `OllamaClient.__init__` (Module 2). `"v1"` for `prompt_version`/`dataset_version`/`evaluator_version` is typed by hand in Module 13's `build_baseline()`, again in Module 17's `run_and_log()`, and again in the CI scripts from Module 19. The block-category set `{"safety_failure"}` lives inside `run_regression_suite()`'s default argument in Module 14.

**Poor implementation, made explicit:**

```python
# Module 13
record = BaselineRecord(model=client.model, ..., prompt_version="v1", dataset_version="v1", evaluator_version="v1", ...)

# Module 17 — the same three strings, typed again
entry = EvalLogEntry(model=client.model, ..., prompt_version="v1", dataset_version="v1", evaluator_version="v1", ...)

# Module 14 — the block list, hardcoded as a default argument
def run_regression_suite(baseline_name, current_records, max_new_failures=0, block_categories=frozenset({"safety_failure"})):
    ...
```

**Maintainability problem.** When Vespera's prompt actually moves to `"v2"` (Module 14's own scenario), someone has to find and update this string in at least three files, by hand, with no compiler or test to catch a missed spot, exactly the kind of drift that produces a baseline record silently mismatched against a log entry, which is the sort of confusing bug Module 13 built version tracking specifically to prevent.

**Relevant principle:** **DRY (Don't Repeat Yourself)**, not as a stylistic preference, but because every duplicated literal here is a second place a real update has to remember to happen.

**Refactoring, a single source of configuration:**

```python
# llmqe/config.py
from dataclasses import dataclass

@dataclass(frozen=True)
class FrameworkConfig:
    model: str = "llama3.2:3b"
    temperature: float = 0
    seed: int | None = 42
    prompt_version: str = "v1"
    dataset_version: str = "v1"
    evaluator_version: str = "v1"
    block_categories: frozenset = frozenset({"safety_failure"})
    latency_budget_seconds: float = 3.0

CONFIG = FrameworkConfig()
```

**Better implementation:**

```python
# Module 13, after
from llmqe.config import CONFIG
record = BaselineRecord(model=CONFIG.model, ..., prompt_version=CONFIG.prompt_version, ...)

# Module 14, after
def run_regression_suite(baseline_name, current_records, max_new_failures=0, block_categories=CONFIG.block_categories):
    ...
```

**Trade-off.** One more file to know about, and one more import in every module that used to just hardcode a literal, a small real cost. In exchange, a version bump becomes a one-line, one-place change instead of a grep-and-hope across the whole framework, and it is now impossible for `baseline.py` and `logger.py` to silently disagree about what "v1" means.

## Problem two: a low-cohesion `score_case()`

**Problem.** By the end of Module 8, `score_case()` does four genuinely different jobs in one function body: schema validation, a polarity-contradiction guard, similarity scoring, and judge invocation, each added in a different module, for a different reason, never revisited as a whole.

**Poor implementation** (Module 8's version, unchanged since):

```python
def score_case(question, reference_answer, raw_response):
    validation_errors = validate_response(raw_response)
    if validation_errors:
        return {"passed": False, "stage": "validation", "errors": validation_errors}
    answer = json.loads(raw_response)["answer"]
    if _is_polarity_contradiction(answer, reference_answer):
        verdict = judge_answer(question, reference_answer, answer)
        return {"passed": verdict["score"] >= 4, "stage": "judge (polarity guard)", "verdict": verdict}
    similarity = semantic_similarity_score(answer, reference_answer)
    if similarity > 0.9:
        return {"passed": True, "stage": "similarity", "similarity": similarity}
    verdict = judge_answer(question, reference_answer, answer)
    return {"passed": verdict["score"] >= 4, "stage": "judge", "verdict": verdict}
```

**Maintainability problem.** Testing any one of these four stages in isolation means calling the whole function and engineering an input that happens to reach the stage you care about. Module 8's own `evaluator_calibration.jsonl` tests work this way today, indirectly, rather than testing `_is_polarity_contradiction` or the similarity threshold directly. Adding a fifth evaluation stage (which Module 11's groundedness score, in a more integrated framework, would be a natural candidate for) means editing this same function again, growing it further.

**Relevant principle:** **Separation of Concerns / Single Responsibility**, so each stage should be independently callable and independently testable.

**Refactoring, an ordered list of evaluation stages, each a small independent function:**

```python
# llmqe/eval/scorer.py (refactored)
def _validation_stage(raw_response, reference_answer):
    errors = validate_response(raw_response)
    if errors:
        return {"passed": False, "stage": "validation", "errors": errors}
    return None  # doesn't decide — let the next stage run


def _polarity_stage(question, answer, reference_answer):
    if not _is_polarity_contradiction(answer, reference_answer):
        return None
    verdict = judge_answer(question, reference_answer, answer)
    return {"passed": verdict["score"] >= 4, "stage": "judge (polarity guard)", "verdict": verdict}


def _similarity_stage(answer, reference_answer):
    similarity = semantic_similarity_score(answer, reference_answer)
    if similarity <= 0.9:
        return None
    return {"passed": True, "stage": "similarity", "similarity": similarity}


def _judge_stage(question, answer, reference_answer):
    verdict = judge_answer(question, reference_answer, answer)
    return {"passed": verdict["score"] >= 4, "stage": "judge", "verdict": verdict}


def score_case(question: str, reference_answer: str, raw_response: str) -> dict:
    validation_result = _validation_stage(raw_response, reference_answer)
    if validation_result:
        return validation_result

    answer = json.loads(raw_response)["answer"]

    for stage in (
        lambda: _polarity_stage(question, answer, reference_answer),
        lambda: _similarity_stage(answer, reference_answer),
    ):
        result = stage()
        if result:
            return result

    return _judge_stage(question, answer, reference_answer)
```

**Better implementation.** Each stage now has its own name, its own signature, and can be unit-tested directly. `test_evaluator_matches_human_judgment` from Module 8 can stay exactly as it was (it tests the whole pipeline, which still matters), while a new, faster test can call `_polarity_stage` alone to check just that guard, without a live model call reaching the judge stage at all.

**Trade-off.** More functions, more indirection to read through for someone seeing this file for the first time, a real readability cost for a function this size. That cost is worth paying here specifically because Module 8 already showed this evaluator has bugs worth catching, and isolated stages are what made that polarity-guard bug fixable with a small, targeted change instead of a rewrite of the whole function.

## When NOT to add more abstraction here

Flag this explicitly, because both refactors above could tempt a further "improvement" that this page deliberately does not make: **do not turn `score_case()`'s four stages into a plugin system with a registered-evaluator interface, a base class, and a discovery mechanism.** Four stages, added across three modules, are enough to justify separating into named functions; they are not enough to justify a framework-within-the-framework for registering arbitrary future evaluators nobody has asked for yet. That is **YAGNI** (You Aren't Gonna Need It): the four functions above are trivially easy to read top-to-bottom in `score_case()`; a plugin architecture would trade that readability for flexibility this project does not currently need, on the promise of a future requirement that may never arrive. If a sixth, seventh, and eighth evaluation stage show up later and the ordered-tuple-of-lambdas pattern starts actually straining, that is the moment to revisit, not now, preemptively.
