## Page purpose

This page introduces no new technique. It is a synthesis pass over three real decisions already made across the last 21 modules, each re-examined through Problem → Constraints → Options → Trade-offs → Decision → Implementation → Consequences, the same structure Module 21 used once, now applied deliberately, in retrospect, to decisions you did not necessarily notice as decisions the first time you made them. The thread running through all three: **"what can we do" is a technical question; "what should we do" is a judgment call**, and this course has been asking you to make that second kind of call since Module 8.

## Learning objectives

By the end of this page, you should be able to:

- Re-derive why LLM-as-a-judge was used in some places in this framework and not others.
- Re-derive why the framework has exactly the amount of abstraction it has, no more, no less.
- Re-derive why the regression gate blocks on safety failures unconditionally but tolerates a small number of other flips.
- Distinguish "what can we do" from "what should we do" using your own words, on a new hypothetical.

## Decision one: why a judge here, but not there

**Problem.** Module 6 needed to check whether a response's `"topic"` field was one of four allowed values. Module 7 needed to check whether a response's free-text answer meant the same thing as a reference answer. Both are "is this response okay" questions, so why did one get a two-line rule-based check and the other get an entire judge-model call?

**Constraints.** A judge call is slow and costs real compute (Module 7 itself said so); a rule-based check is instant. Every case that could legitimately use a rule instead of a judge and did not would be paying that cost for nothing.

**Options.** Use rule-based checks everywhere (fails on `"answer"`, Module 3 already proved exact-match breaks on generative text). Use a judge everywhere (works, but wastes cost on `"topic"`, where a plain set-membership check is both cheaper and *more* reliable than a judge would be). Use each where it fits: a rule for constrained fields, a judge for genuinely generative, holistic quality questions.

**Trade-offs.** The mixed approach requires knowing, for every field, which category it falls into, the same "constrained vs. generative" split Module 3 introduced as the seed of everything since.

**Decision.** Rules for `"topic"` (constrained, small, exact); similarity and judge for `"answer"` (generative, no single correct string). This is why Module 7's tiered `score_case()` runs cheap, exact checks first and only escalates to the judge when the case is genuinely ambiguous, not because judges are expensive to avoid on principle, but because most of what Module 6 checks does not need one.

**Implementation and consequences.** You have already seen both: Module 6's `validate_response()` and Module 7's `judge_answer()`. The consequence worth naming now, in hindsight: neither module claimed its technique was "the right one" universally. Each earned its place for a specific kind of field. Generalizing either one to every field in the system would have been the wrong call in the opposite direction.

## Decision two: why this much abstraction, and no more

**Problem.** Modules 20 and 21 each faced a live "should we add an abstraction here" moment (a scattered-config problem and a hardwired-provider problem) and both times, a more elaborate version of the fix was available and explicitly rejected.

**Constraints.** Every module of this course up to that point had working code with real tests depending on stable interfaces; any refactor had to preserve `OllamaClient.ask_with_system()`'s signature and `score_case()`'s return shape, or it would have broken 18+ modules of accumulated tests instead of improving the codebase they lived in.

**Options, revisited.** For configuration: one shared dataclass, versus a full settings-management layer with environment-variable overrides, validation, and remote config fetching. For the provider: a one-method protocol with a real second implementation, versus a registry-based plugin system supporting arbitrarily many simultaneous providers.

**Trade-offs.** The elaborate versions of both would have been defensible in a larger, longer-lived production system with many real config sources and many real providers actually in play. In *this* framework, at *this* point, neither condition was true: Vespera has one config source and, until this page, exactly one provider (`OllamaProvider`, with `RecordedProvider` added specifically to prove the seam works, not because a second real model provider was needed).

**Decision.** The narrow version, both times, justified by a concrete, already-visible problem, not a speculative future one.

**Implementation and consequences.** `config.py` and `providers/` are small enough to read in under a minute each. That is not an accident or a lack of ambition; it is what "no more abstraction than the problem warrants" produces when followed consistently. The real test of this decision is not today; it is whether, when Vespera someday actually needs a second real provider or a second real config source, `LLMProvider` and `FrameworkConfig` turn out to be exactly the seam that made it easy, or whether they turn out to be too narrow and need revisiting. Either outcome would be a legitimate result of a reasonable decision made with the information available at the time; engineering judgment is not about guaranteeing you will never have to revisit a call, it is about making the call for good, stated reasons.

## Decision three: why this regression threshold, specifically

**Problem.** Module 14's `run_regression_suite()` tolerates up to `max_new_failures` ordinary flips before blocking a release, but blocks unconditionally on anything in `block_categories`, currently just `{"safety_failure"}`. Why not treat every category the same way?

**Constraints.** Block too aggressively (zero tolerance for any flip, ever) and the gate becomes noisy enough that a team starts ignoring or disabling it, the exact failure mode Module 19 warned running the full suite on every commit would cause, now showing up again at the threshold-design level instead of the schedule level. Block too permissively and a real regression ships.

**Options.** A single numeric threshold applied uniformly to every failure category. A per-category policy, where some categories (safety) are non-negotiable and others (an ordinary quality flip) get a small tolerance band. No automated gate at all, every diff reviewed by a human before every release.

**Trade-offs.** A uniform threshold is simpler to implement and explain, but treats a safety regression and a mildly-worse-worded answer as the same severity of problem, which Module 12 already established they are not. A fully manual gate scales the worst; it is the option this course never seriously considered, given that Module 19's entire argument was that a human cannot (and should not have to) review every run by hand.

**Decision.** Per-category policy: `block_categories` unconditional, everything else judged against `max_new_failures`. This is a values judgment as much as a technical one: it says, explicitly, that Vespera's team considers a safety regression categorically worse than an ordinary quality wobble, not just worse by degree.

**Implementation and consequences.** The consequence of this specific decision showed up concretely in Module 19's incident: the safety regression blocked the release regardless of how small a fraction of the suite it represented. A uniform-threshold gate, depending on where the number was set, might not have caught it at all if it was the only failure in an otherwise large, passing suite. That is not a hypothetical difference; it is the exact reason this page picked this decision to revisit.

## What can we do vs. what should we do

Every decision above had a technically valid "what can we do" answer that this course did not choose: judge every field, abstract everything up front, block on any change at all. None of those were *wrong* in the sense of being technically broken; they were wrong for *this* framework, at *this* stage, given *these* constraints and *these* stated priorities (cost, team trust in the gate, the safety-first stance made explicit in decision three). "What should we do" is the question that weighs constraints and consequences, not just feasibility, and it is the question this entire course has been asking you to practice answering, one module at a time, since Module 8 first showed you that even your evaluator's verdict is not automatically the right one just because it is technically possible to compute.
