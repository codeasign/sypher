## Page purpose

Before you can test an AI application, you need a precise picture of what one actually is: not "software with AI in it," but the specific architectural shapes AI applications take, and exactly what makes each of them behave differently from the deterministic software you have tested before. This page builds that picture and introduces Vespera Systems' Helpdesk AI Assistant, the system every later module tests.

## Learning objectives

By the end of this page, you should be able to:

- Name the four AI application shapes covered in this course (LLM app, agent, RAG system, AI workflow) and describe what distinguishes each.
- Explain, concretely, at least three specific ways AI applications differ from traditional deterministic software.
- Draw the architecture of Vespera's Helpdesk AI Assistant and identify which shape it currently is.
- Restate why "testing AI systems" needs a different discipline than "using AI to improve testing," this time grounded in architecture rather than definition.

## What an AI application actually is

An **AI application** is any software where a language model's output directly shapes what the application does or shows: not a chatbot bolted onto the side of a normal app, but software whose core behavior runs through a model call. That covers a wide range of shapes, and this course treats four of them as the ones worth knowing cold:

**LLM application** is the simplest shape. The application sends a prompt to a model and uses the text that comes back, directly. Vespera's Helpdesk AI Assistant, as you will meet it starting in Module 2, begins its life as exactly this: a support agent's question goes in, the model's answer comes back.

**RAG system** (Retrieval-Augmented Generation) is an LLM application with a lookup step bolted in front of the model call. Instead of relying only on what the model already "knows," the application first retrieves relevant text from a knowledge source (Vespera's product documentation, in this course's case) and hands it to the model as context, so the model can answer *using that specific material* instead of guessing from its training data alone. You will meet this shape starting in Module 9, when Vespera's assistant becomes retrieval-backed.

**Agent** is software where the model does not just produce text for a human to read, but decides which *actions* to take (calling a tool, running a lookup, taking a next step) often across multiple steps, sometimes without a human reviewing each one. This course touches agent-shaped systems only lightly (the safety module in Module 12 covers tool-misuse concerns), since agent testing at depth is its own subject.

**AI workflow** is a deterministic pipeline with one or more model calls as steps inside it, where the surrounding control flow (what runs, in what order, under what conditions) is ordinary code, not something the model decides. Much of what you build in this course, the evaluation framework itself, is an AI workflow: ordinary Python that calls a model as one step among several.

## How AI applications differ from traditional software, concretely

"AI is non-deterministic" is the one-line version. Here is what that actually means for testing, point by point:

**The same input can produce a different output, on purpose.** Traditional software: call `add(2, 2)` a thousand times, get `4` a thousand times. Call an LLM with the same prompt a thousand times, and, depending on its configuration, you can get a thousand differently-worded (and occasionally differently-*reasoned*) responses. This is not a hardware fluke to work around; it is how the model is built to work by default. Module 4 covers exactly what to do about it.

**Correctness is a spectrum, not a boolean.** A traditional function either returns the right value or it does not. An LLM response can be well-formed, on-topic, mostly accurate, and still subtly wrong in a way that matters, or perfectly worded and completely fabricated. "Pass" and "fail" stop being self-evident; Modules 6 through 8 are entirely about how you decide.

**The system can fail by being too convincing.** A traditional bug usually announces itself: a crash, a wrong number, an error page. A **hallucination**, the model stating something false with total confidence, often looks exactly like a correct answer until someone checks it against a source. Module 5 is dedicated to this failure mode specifically because it is the one most likely to slip past a QE who is used to bugs looking like bugs.

**Quality can change without a code change.** A traditional application's behavior only changes when someone changes the code. An AI application's behavior can shift because a prompt was reworded, because the model vendor pushed a silent update, or because the underlying data (in a RAG system) changed, none of which necessarily touches your application's source code. Modules 13 and 14 build the machinery for catching this.

**Untrusted input reaches the model's reasoning, not just its data layer.** In traditional software, user input can corrupt data or trigger a code path, but it does not rewrite the program's logic. Text sent to an LLM becomes part of what the model reasons over, which opens the door to prompt injection, a concern Module 12 treats as seriously as SQL injection gets treated in traditional security testing.

## Vespera Systems: the Helpdesk AI Assistant

Vespera Systems runs a support ticketing platform, and its support team has been given a new internal tool: the **Helpdesk AI Assistant**. A support agent, mid-ticket, can ask it a product question ("does the Pro plan support SSO?") and get a fast, plain-language answer instead of digging through documentation themselves. It is internal-only, and for now it does exactly one thing: takes a question, sends it to a model, returns an answer.

That makes it, right now, the simplest of the four shapes: a **plain LLM application**. Nothing is retrieved, nothing acts on the agent's behalf. That is deliberate: Module 2 builds the first real code against exactly this shape, before Module 9 adds retrieval and turns it into a RAG system. Keeping the starting shape simple is what makes the failures added later (irrelevant retrieval in Module 10, an unsafe tool call implication in Module 12) legible as *additions* to something you already understand, rather than new complexity arriving all at once.
