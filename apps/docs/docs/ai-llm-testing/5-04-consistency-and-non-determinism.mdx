## Page purpose

Module 3 fixed one flaky assertion by loosening it. This page asks the harder version of the same question: given that an LLM can legitimately answer the same question differently each time, what actually counts as "the same result," and what counts as a real change? That question, answered here for a single response, comes back in Module 13 at the scale of an entire test suite, comparing runs across days or weeks. This page sets up that later work without duplicating it.

## Learning objectives

By the end of this page, you should be able to:

- Distinguish "acceptable variation" from "an actual quality change" in two LLM responses to the same input.
- Write a consistency test that runs a prompt multiple times and checks the *properties* that should hold across all of them.
- Explain why AI test results can shift even when no application code changed.

## What "consistency" means for a non-deterministic system

For deterministic code, consistency is trivial: same input, same output, every time, and anything else is a bug. For an LLM, consistency has to mean something looser: **same input, same *meaning*, every time**, even if the wording differs. Two responses to "does the Pro plan support SSO?" are consistent if they agree on the yes/no fact and the relevant detail, regardless of whether one says "Yes, SSO is supported" and the other says "Pro plan customers get SSO access." They are *inconsistent* if one says yes and the other says no, or if one mentions SSO and the other suddenly talks about a different feature entirely.

That gives you two failure shapes to test for, and they are different problems:

- **Wording variation** is expected, not a bug, not worth testing against directly (Module 3 already showed you why exact-match fails here).
- **Meaning variation** is a real problem: the model is giving contradictory answers to the same question, which for Vespera's assistant means a support agent could get a different answer depending on when they happened to ask.

## Testing for consistency, not for identical text

Run the same prompt several times and check a property that should hold across all of them, rather than comparing the raw strings to each other:

```python
# tests/test_consistency.py
import json
from llmqe.client import OllamaClient, SYSTEM_PROMPT

def test_sso_answer_is_consistent_across_runs():
    client = OllamaClient(temperature=0.8, seed=None)  # realistic, non-pinned settings
    answers = []

    for _ in range(5):
        result = client.ask_with_system(SYSTEM_PROMPT, "Does the Pro plan support SSO?")
        parsed = json.loads(result.text)
        answers.append(parsed["answer"].lower())

    says_yes = ["yes" in a or "supports sso" in a for a in answers]
    mentions_sso = ["sso" in a or "single sign-on" in a for a in answers]

    assert all(says_yes), f"Inconsistent yes/no answers across runs: {answers}"
    assert all(mentions_sso), f"Some answers dropped the SSO detail entirely: {answers}"
```

**Run it.** Notice this test deliberately uses `temperature=0.8` and `seed=None`, the *opposite* of Module 2's reproducibility settings. That is intentional: Module 2's `temperature=0, seed=42` setup exists to make individual tests reliable to write and debug; this test exists to check whether the underlying feature holds up under the *realistic* conditions of production, where you do not control what settings a real user's request runs with. Both settings are legitimate; they answer different questions, and conflating them is a common mistake.

### Explaining the result

If this test passes, you have confirmed something Module 3's single-shot test never could: not just that *one* response was correctly shaped, but that the *meaning* holds up across repeated asks. If it fails intermittently, you have found a real instability, worth treating as a bug, not explained away as "it's just an LLM."

## Why results can shift with no code change

This is worth stating plainly, because it is one of the most disorienting things about testing AI systems the first time you hit it: **a test suite's pass rate can change from one day to the next with zero commits in between.** None of these require a code change:

- **Temperature/seed drift.** If a test does not pin these explicitly (as Module 2's `OllamaClient` defaults do), results vary run to run by design.
- **A silent model update.** Ollama pulling a new version of a model tag, or a cloud vendor updating "the same" model behind the scenes, can shift behavior without anyone on your team touching anything.
- **Load and timing.** Under different system load, generation can behave slightly differently, especially near the edges of a context window.
- **Nothing at all.** Some genuine run-to-run variance is expected even under fixed settings; models are not perfectly deterministic even at `temperature=0` on every implementation.

This is exactly why Module 13 builds a **baseline**, a recorded snapshot of expected behavior to compare future runs against, instead of relying on "the test passed last time" as a proxy for "nothing changed." This module gives you the vocabulary (acceptable variation vs. real change) that baseline comparison needs; Module 13 gives you the mechanism.

## Strengthening the framework

Module 3's `test_smoke.py` checked one response, once. Add `tests/test_consistency.py` (above) alongside it. This does not claim a new capstone milestone on its own, but it directly strengthens Milestone 4 (the framework's first LLM test) into something that holds up under realistic, non-pinned conditions, and it is the property-based thinking that Milestone 5 (response validation, Module 6) generalizes to many more inputs than just this one SSO question.
