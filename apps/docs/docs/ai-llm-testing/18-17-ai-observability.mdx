## Page purpose

Module 16's latency bug got diagnosed by hand: printing timings, comparing them, reasoning through the evidence live. That does not scale past one investigation session. This page builds the framework's observability layer: a structured, permanent record of every evaluation run, so a future failure gets diagnosed by reading a log instead of re-running ad hoc `print()` statements. This begins Milestone 12.

## Learning objectives

By the end of this page, you should be able to:

- List what to capture for every evaluation run, and explain why each field earns its place.
- Build a structured logger the framework's tests write to automatically.
- Explain why observability matters more for non-deterministic systems than for traditional software.
- State, without hedging, what must never appear in an observability log.

## Why observability matters more here

For deterministic software, a failure is usually reproducible on demand: run the same input again, get the same crash, debug from there. For an AI system, Module 4 already established that re-running the same input might not reproduce anything at all. The failure that happened at 2pm might not happen again at 2:05pm with the same code, same prompt, same everything. That makes **capturing what happened, at the moment it happened**, far more valuable than it is for traditional software: it may be the only record of a failure you will ever get to examine, since you cannot always just reproduce it on request.

## What to capture

This list should look familiar: it is Module 13's baseline fields, generalized from "one comparison snapshot" to "every single run, permanently":

| Field | Captures |
|---|---|
| `model`, `config` | What was actually running (Module 2, Module 13). |
| `prompt_version`, `dataset_version`, `evaluator_version` | Which versions produced this result (Module 13, Module 14). |
| `test_case_id` | Which specific input this record is for. |
| `response` | The actual text the model produced — needed to re-examine a failure without re-running it. |
| `score`, `reason` | The evaluation outcome and, for judge-based results, the judge's own stated reasoning (Module 7). |
| `latency` | How long it took (Module 16). |
| `timestamp` | When it happened. |
| `pass_fail` | The bottom-line outcome. |
| `failure_category` | `hallucination`, `citation_error`, `safety_failure`, `timeout`, `slow` — Module 14 and Module 16's categories, in one shared vocabulary. |

## Building the logger

```python
# llmqe/observability/logger.py
import json
import time
from dataclasses import dataclass, asdict
from pathlib import Path

LOG_PATH = Path("llmqe/observability/eval_log.jsonl")
LOG_PATH.parent.mkdir(parents=True, exist_ok=True)


@dataclass
class EvalLogEntry:
    model: str
    config: dict
    prompt_version: str
    dataset_version: str
    evaluator_version: str
    test_case_id: str
    response: str
    score: float | None
    reason: str
    latency_seconds: float
    timestamp: float
    passed: bool
    failure_category: str | None


def log_eval(entry: EvalLogEntry) -> None:
    with open(LOG_PATH, "a") as f:
        f.write(json.dumps(asdict(entry)) + "\n")


def read_log() -> list[dict]:
    if not LOG_PATH.exists():
        return []
    with open(LOG_PATH) as f:
        return [json.loads(line) for line in f]
```

Wire it into an evaluation run, combining Module 13's baseline machinery with Module 16's latency measurement:

```python
import time
from llmqe.client import OllamaClient
from llmqe.eval.scorer import score_case
from llmqe.observability.logger import EvalLogEntry, log_eval

def run_and_log(question: str, reference_answer: str, client: OllamaClient) -> EvalLogEntry:
    start = time.time()
    result = client.ask_with_system(SYSTEM_PROMPT, question)
    latency = time.time() - start

    outcome = score_case(question, reference_answer, result.text)

    entry = EvalLogEntry(
        model=client.model, config={"temperature": client.temperature, "seed": client.seed},
        prompt_version="v1", dataset_version="v1", evaluator_version="v1",
        test_case_id=question, response=result.text, score=outcome.get("similarity"),
        reason=outcome.get("stage", ""), latency_seconds=latency, timestamp=time.time(),
        passed=outcome["passed"], failure_category=None if outcome["passed"] else outcome["stage"],
    )
    log_eval(entry)
    return entry
```

**Run it** a few times against different questions, then inspect `llmqe/observability/eval_log.jsonl` directly. It is plain JSON Lines, one record per run, readable with any text editor or a one-line script.

## What must never appear in the log

State this without hedging, because an observability log is exactly the kind of file that quietly becomes a liability if this rule slips: **never log credentials, API keys, secrets, PII, or real production data. Synthetic data only, the same rule this course has followed since Module 5's fabricated ticket data.** Every `test_case_id` and `response` in this course's log entries is built from invented Vespera questions and fabricated product facts; a real deployment logging real customer questions would need a redaction or anonymization step before anything reaches a log file like this one, which this course does not build (out of scope for a synthetic-data course) but which a production observability layer absolutely cannot skip.
