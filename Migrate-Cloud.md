# Migrating Content to the Cloud

A practical run-book for getting content — courses, coding problems, mock
exam banks, and (for a from-scratch environment) the full local dataset —
into the production droplet. For the droplet/deploy setup itself (SSH
access, `.env`, Caddy/DNS, `DEPLOY_ENABLED`), see `DEPLOYMENT.md` — this
doc is scoped to running imports, not standing up the stack.

## TL;DR — the one command you need

```bash
npx tsx scripts/publish-content.ts --target production --all
```

That's genuinely it — no separate SSH tunnel step. The only one-time setup
is `scripts/.env.production` (copy `scripts/.env.production.example`, fill
in `IMPORT_TOOL_SECRET`, `IMPORT_ADMIN_EMAIL`, `PRODUCTION_DATABASE_URL`).
The script opens its own SSH tunnel to production Postgres when a step
needs it, waits until it's actually reachable, and closes it again when
the run finishes — success, failure, or Ctrl+C all clean it up the same
way. To publish just one piece instead of everything, swap `--all` for
`--mock-exams`, `--coding-problems`, or `--courses=<slug>`. Full details
and the one-time full-database-migration path are below.

## Which path do I need?

- **Publishing new/updated content to an already-running production** (the
  common case — you authored a new course, added coding problems, topped up
  a mock exam bank): use `scripts/publish-content.ts`, below.
- **Standing up a brand-new production database from your local content**
  (one-time, e.g. first launch or a disaster-recovery restore): use the
  `pg_dump`/`pg_restore` data migration, further down.

## 1. Running the master import — `scripts/publish-content.ts`

One command, run from the repo root, that orchestrates every importer in
the correct order:

```bash
npx tsx scripts/publish-content.ts --target production --all
npx tsx scripts/publish-content.ts --target production --mock-exams
npx tsx scripts/publish-content.ts --target production --coding-problems
npx tsx scripts/publish-content.ts --target production --courses=<slug>[,<slug>...]
```

`--target production` (or `local`) is always required — there's no
default, so this can never run against the wrong environment by omission.
`--all` order: Docusaurus-sourced courses → coding problems (seed + the 5
content-cleanup fixups) → mock exam banks → a read-only catalog verify.

### Prerequisites

**`scripts/.env.production`** — gitignored, never committed. Copy
`scripts/.env.production.example` and fill in:

```env
# Preferred — skips /auth/login and its recaptcha gate entirely (production
# defaults RECAPTCHA_REQUIRED=true, and a reCAPTCHA v2 token can't be
# generated by a CLI script). See "Auth for the HTTP-API importers" below.
IMPORT_TOOL_SECRET=<the same long random value set in the droplet's .env>
IMPORT_ADMIN_EMAIL=<a real ADMIN-role user's email in production>

# Only needed if you're NOT using IMPORT_TOOL_SECRET (falls back to a
# normal password login instead):
IMPORT_ADMIN_PASSWORD=

# Full connection string through the tunnel the script opens itself —
# needed for the direct-DB steps only (mock exams, coding problems).
# Port must match TUNNEL_PORT in publish-content.ts (15432 by default).
PRODUCTION_DATABASE_URL=postgresql://sypher:<real-password>@127.0.0.1:15432/sypher_next
```

That's it — no SSH tunnel to open yourself. When a direct-DB step needs
one, `publish-content.ts` spawns `ssh -N -L 15432:127.0.0.1:5432
deploy@143.110.191.248` as its own child process, using the exact same key/
agent resolution your own interactive `ssh deploy@143.110.191.248` already
uses (no separate key setup), waits until Postgres is actually reachable
through it (a real query, not just "is the port open" — a bare TCP check
isn't reliable, see the comment in the script), then closes it again when
the run ends. Ctrl+C, a step failure, or a clean finish all trigger the
same cleanup.

If the droplet's host/user ever changes, override via `DROPLET_SSH_HOST`/
`DROPLET_SSH_USER` in `scripts/.env.production` — both already default to
the real values, so this is opt-in, not required.

The course-only step (`--courses=<slug>`) doesn't touch the tunnel at
all — it's HTTP-API-driven, not direct-DB.

### Auth for the HTTP-API importers

The course-import steps authenticate against the live API
(`https://api.syphernext.com`, set automatically for `--target
production`), not the database directly. Two ways:

- **`IMPORT_TOOL_SECRET` (preferred)**: a server-to-server credential,
  entirely separate from the public login/register recaptcha gate — see
  `apps/api/src/lib/tsoaAuth.ts`'s `'importTool'` security scheme. Skips
  `/auth/login` completely. Must match the `IMPORT_TOOL_SECRET` already set
  in the droplet's `.env` (see `DEPLOYMENT.md`).
- **Fallback**: `IMPORT_ADMIN_EMAIL` + `IMPORT_ADMIN_PASSWORD`, a normal
  session login. Only works if `RECAPTCHA_REQUIRED=false` on that
  environment — **not** the case in production by default, so in practice
  this path is for local testing only.

Either way, `IMPORT_ADMIN_EMAIL` is required — it's the identity attached
to every write these scripts make (course `authorId`, etc.).

### Example: publish everything after a content session

```bash
npx tsx scripts/publish-content.ts --target production --all
```

One terminal, one command — the tunnel opens and closes on its own around
the steps that need it. Watch the step-by-step progress output; on any failure it stops
immediately (never continues to the next importer) and prints a summary
table — which steps ran, which didn't, and the failed step's stderr tail.

### Example: just published one new course

```bash
npx tsx scripts/publish-content.ts --target production --courses=design-patterns
```

Note: imported courses always land as `status: draft` — publishing is a
separate, explicit step from the admin UI afterward.

### What each importer actually does, for troubleshooting or a manual fallback

If you ever need to run a piece by hand instead of through the
orchestrator (each still respects the same `DATABASE_URL` /
`IMPORT_API_URL` / `IMPORT_TOOL_SECRET` env vars):

| Script | Location | What it does |
|---|---|---|
| `import-docusaurus-course.ts` | `apps/api/scripts/` | Imports a Docusaurus-sourced course (`apps/docs/docs/<slug>`) into `Course`/`CourseModule`, uploading diagrams to Bunny along the way. Needs the local `apps/docs` checkout present. |
| `import-authored-course.mjs` | `apps/web/scripts/` | Imports a staging directory of `.mdx` module files (life-skills/DB-commands/metrics-course family). Not currently wired into `publish-content.ts` — no slug→args manifest exists yet, so this one's still run by hand per course. |
| `seed-coding-problems.ts` | `apps/api/scripts/` | Migrates `apps/docs/docs/coding-bootcamp` MDX into `CodingProblem` rows, upserted by slug. |
| `fixup-coding-problem-*.ts` (5 scripts) | `apps/api/scripts/` | One-off content cleanups over existing `CodingProblem` rows (stray headings, dead links, MDX artifacts) — idempotent, safe to re-run, always included in `--coding-problems`/`--all`. |
| `import-mock-exams.mjs` | `apps/api/scripts/` | Loads every exam folder under `apps/web/question-bank/*.json` into `MockExam`/`MockExamQuestion`, idempotent by the bank's own stable IDs. |
| `check-course-import.mjs` | `apps/api/scripts/` | Ad-hoc verification tool, hardcoded to two specific course slugs from a past task — **not** general-purpose, not wired into the orchestrator. `publish-content.ts`'s own verify step (login + catalog fetch) replaces it for the automated flow. |

### Hard safety rule

`seed-corporate-test.ts` (seeds a fake `TESTCO` company with hardcoded
accounts and the literal password `"password"`) can never run under
`--target production` — `publish-content.ts` checks this structurally
(`FORBIDDEN_IN_PRODUCTION`), not by omission from the step list, so it
can't be reintroduced by a future edit without deliberately removing that
check too.

## 2. One-time full database migration (local → a fresh production)

This is what "migrate the whole local database to the cloud" means the
first time — a scoped, content-only `pg_dump`/`pg_restore`, not a raw
database copy. Do this only once, when standing up a new environment (or
recovering one), not as part of routine content publishing above.

### Scope — what actually gets migrated

Only pure content, verified against the real local dataset before
transfer: `Course`, `CourseModule`, `AuthoredCourseAccess`, `CourseAccess`,
`NavAccess`, `CodingProblem`, `MockExam`, `MockExamQuestion`, `BlogPost`,
`Video`. Everything user/company/test-account-linked (`User`, `Company`,
comments, bookmarks, progress, mock-exam attempts, sessions, payments,
etc.) is deliberately excluded — audit every local `User` row first
(`.local`/`example.com`/`test`-pattern emails are dev fixtures, not real
people) before assuming otherwise for your own environment.

### Sequence

```bash
# 1. Local: scoped, data-only export (schema NOT included — production's
#    own `prisma migrate deploy`, which runs automatically on container
#    boot, creates the schema; this only carries rows).
pg_dump "postgresql://sypher:sypher@localhost:5433/sypher_next" \
  --data-only --no-owner --no-privileges -Fc \
  -t '"Course"' -t '"CourseModule"' -t '"AuthoredCourseAccess"' \
  -t '"CourseAccess"' -t '"NavAccess"' -t '"CodingProblem"' \
  -t '"MockExam"' -t '"MockExamQuestion"' -t '"BlogPost"' -t '"Video"' \
  -f content_export.dump

# 2. Confirm production's schema is at the same migration count as local
#    BEFORE transferring anything (a schema mismatch between dump-time and
#    restore-time is a real corruption risk, not a formality):
npx prisma migrate status   # locally, from apps/api
ssh deploy@143.110.191.248 "cd /opt/sypher && docker compose exec api npx prisma migrate status"

# 3. Transfer
scp content_export.dump deploy@143.110.191.248:/opt/sypher/

# 4. Restore on the droplet — data-only, into the schema Prisma already
#    created, with FK-checking triggers off so table load order doesn't matter
ssh deploy@143.110.191.248
cd /opt/sypher
docker compose exec -T postgres pg_restore -U sypher -d sypher_next --data-only --disable-triggers < content_export.dump

# 5. Null the authorId columns — every locally-authored row is attributed
#    to the local dev seed admin, not a real production user
docker compose exec -T postgres psql -U sypher -d sypher_next -c \
  'UPDATE "Course" SET "authorId" = NULL; UPDATE "BlogPost" SET "authorId" = NULL; UPDATE "Video" SET "authorId" = NULL;'
```

Create your first real production admin account any time relative to the
above — order doesn't matter, since nothing in this dataset requires a
`User` row to exist (no non-null FK survives the exclusions above).

### A gotcha to know about before you restore

An app-level bootstrap (not a migration) seeds a handful of default
`NavAccess` rows (`browse-videos`, `course-audit`,
`manage-course-authoring`, `manage-videos`, `reported-comments`, ...) the
first time the `api` container starts. If your dump also contains
`NavAccess` rows with the same keys, `pg_restore`'s `COPY` will hit a
duplicate-key conflict and **roll back the entire table's restore** (not
just the one conflicting row — Postgres `COPY` is all-or-nothing per
invocation). Check the values actually match (they did, when this was hit
in practice) and hand-`INSERT` just the missing keys rather than force an
`ON CONFLICT` overwrite of rows the app itself already seeded correctly.

### Verifying the restore

```bash
docker compose exec -T postgres psql -U sypher -d sypher_next -c '
SELECT '"'"'Course'"'"', count(*) FROM "Course"
UNION ALL SELECT '"'"'CourseModule'"'"', count(*) FROM "CourseModule"
UNION ALL SELECT '"'"'CodingProblem'"'"', count(*) FROM "CodingProblem"
UNION ALL SELECT '"'"'MockExam'"'"', count(*) FROM "MockExam"
UNION ALL SELECT '"'"'MockExamQuestion'"'"', count(*) FROM "MockExamQuestion"
UNION ALL SELECT '"'"'BlogPost'"'"', count(*) FROM "BlogPost"
UNION ALL SELECT '"'"'Video'"'"', count(*) FROM "Video";'
```

Compare every count against the same query run locally before you
transferred — they should match exactly.
